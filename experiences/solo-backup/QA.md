# Windows 업무 백업 · 설계와 검증

## 0.2.0 B2 클라우드 (2026-11-09)

사용자 「전부 이어서 진행」과 가입 완료 뒤 지역·서버 설정 확인 요청에 따라 별도 시험 계정의 비공개 버킷을 연결했다. 운영자 계정의 실제 지역은 US East였고 해당 S3 Endpoint로 실제 통신했다. 기본 암호화, keep-last 수명 주기, Object Lock 꺼짐, 버킷 전용 Read and Write 키, 무료 한도·사용량 알림을 콘솔에서 확인했다. 결제 수단 추가·한도 상향·실제 업무 자료 업로드는 하지 않았다. 계정·버킷 식별자와 자격증명은 공개 소스에 기록하지 않는다.

설계 검토 Fable 9건 중 6건을 일부 또는 전부 반영했다(F2·F3·F4·F5·F8·F9). 프로필별 엔진·스케줄, 명시적 자식 환경, 클라우드 60분 주기, 제한된 HEAD 사전 확인, 서버 시간과의 편차 검사, repack 없는 prune을 적용했다. F1 모듈 전역 상태 의심은 기존 엔진이 인스턴스 상태라 재현되지 않았으며 분리 회귀 시험을 추가했다. F6 자동 lifecycle 조회는 후속으로 두고 콘솔 확인 필요를 지속 표시한다. F7 수동 unlock UI·지수 백오프는 후속이며 강제 잠금 해제는 하지 않는다. 구조 검사를 매번 생략하라는 F4 제안은 무결성 기준을 유지하기 위해 채택하지 않았다. 요청 수 예산·다운로드 예상량·클라우드 작업의 즉시 취소는 미구현이다. 기존 명령별 제한 시간과 안전 종료 대기는 유지했다.

새 `b2.cjs`는 공식 HTTPS Endpoint와 UUID prefix를 검증하고 S3 path lookup·지역을 명시한다. `profiles.cjs`는 로컬·클라우드 상태·캐시·선택·스케줄을 분리한다. 설정·키 변경·복구에서 저장소 ID를 대조하고, cloud init은 cat config의 명확한 missing-repository(exit10) 뒤에만 한다. 네트워크/권한 오류로 다른 저장소를 새로 만들지 않는다. 암호·접근 키는 Windows 암호 보관 파일에만 저장한다. 선택적 운영자 연결 프리셋도 암호화되며 renderer에는 Endpoint·버킷만 전달한다. 준비만으로 폴더 선택·저장소 생성·업로드·자동 백업을 시작하지 않는다. 복구 키에는 B2 접근 키를 넣지 않는다.

자동 시험은 최초 34개 전부 통과 후 검수 지적을 반영한 최종 36개 전부 통과·실패/생략 0, 124.2초. 기존 실제 Windows restic 시험 26개와 신규 10개(Endpoint/복구 키 변조, 부모 환경 오염, 중단 init의 동일 prefix·암호 재사용, 실패 키 교체 보존·오류 비밀값 가림, restore-only import, 정리의 전체 점검·시계 조건, 프로필별 스케줄, 암호화 프리셋의 재시작·잘못된 대상 재사용 거절, 명시적으로 바꾼 저장소의 키 재시도, HEAD의 Date 누락/양방향 6분 편차/403/404/소켓·전체 마감과 삭제 차단)다. 증거: 공용 작업본 `.tmp/solo-backup-cloud-20261109/tests-final.tap`과 최종 `tests-fixed.tap`.

실제 B2에서 8MiB 무작위 파일·한글 문서·빈 폴더로 최초 백업/전체 점검→문서 수정 후 두 번째 백업→복구 SHA-256·내용·빈 폴더 대조→새 앱 상태에서 복구 키 import 및 다시 복구→접근 키 재검증까지 통과했다. 최초 연결·백업 80.2초, 복구 18.8초, 전체 시험 165.4초의 단일 관찰이며 성능 보장으로 일반화하지 않는다. 같은 PC의 별도 상태 폴더 시험이고 물리적으로 다른 PC 시험은 아니다. 증거 `live-cloud-result.json`; 첫 harness 복호화 실패 `live-cloud-failure*.json`도 남겼다. 실패 원인은 Electron Local State가 다른 시험 프로필을 사용한 것이며 원래 암호화 프로필로 바꾼 뒤 통과했다. 기존 보관 파일은 지우거나 평문으로 옮기지 않았다.

Claude Opus가 화면 3개와 프리셋 흐름을 작성했다. 실제 Electron 화면에서 키 입력 없이 암호화된 연결 정보 읽기→폴더 선택→준비→복구 키 저장→자동 클라우드 백업/전체 점검→복구가 통과했다. 탭 전환 때 키 입력칸이 비워지고 로컬 프로필이 변경되지 않는 것도 확인했다. 1440/390px의 설정·대시보드 캡처 모두 가로 넘침 없음, renderer 오류 0. 기존 로컬 UI 흐름도 실제 백업·복구 통과. 증거 `gui-cloud-result.json`과 `.tmp/solo-backup-mvp-20261108/gui-result.json`.

검수에서 긴 수동 작업의 전역 IPC 잠금이 다른 프로필까지 막는 문제를 수정했다. 백업·전체 점검·복구는 네이티브 확인창/폴더 선택 후 엔진 작업을 시작하고 즉시 IPC를 마치며, 이후 오류·진행·완료는 기존 상태 이벤트로 전달한다. 초기화·키 파일 선택 같은 대화상자 절차는 직렬화한다. 실제 Electron에서 지연·실패하는 시험 백업 중 로컬 탭 전환→폴더 선택이 가능하고, 오류가 비활성 탭 및 돌아온 대시보드에 표시되는 것을 확인했다(`manual-job-switch-result.json`). 프리셋 A 대신 B 저장소·새 키로 초기화를 시도하다 중단된 경우 B의 저장된 키를 우선해 재시도하도록 수정했다. 복구 전용 시험은 health가 정상일 때에도 삭제가 거절되는지 확인하도록 보강했다.

아르곤 3건 반영(진행 중 탭 안내, 폴더 선택 뒤 다음 행동, 초기화 대상과 저장 키가 다를 때 안내), Fable 5건 중 2건 반영(저장소 객체 생성과 업무 파일 업로드 구분, 프리셋 없는 경우 키 안내). Fable 2건은 실제 import의 lastBackup 채움·initializing의 필수 provider를 확인해 재현되지 않았고, 미완료 클라우드 연결을 처음부터 다시 설정하는 UI 1건은 후속이다. Fable은 전체 소스와 상태 분기를 읽었지만 이 검수 통로는 그림 입력을 지원하지 않아 독립 시각 검수는 하지 못했다. 화면 캡처는 GPT가 직접 확인했다. 초기 Fable 준비가 옛 캡처 사용을 거절했는데 호출이 시작된 한 회차는 중단하고 통과로 가져오지 않았다. 새 캡처·소스 해시로 준비한 응답만 수신했다.

백엔드 첫 검수 GPT 2건 반영, Claude 5건 중 3건 반영(수동 작업 잠금, HEAD 오류 주입 시험, restore-only 시험 보강). Claude 1건은 기존 health.status 검사로 재현되지 않았고, 미완료 초기화 재설정 UI 1건은 후속이다. 두 번째 Claude와 화면 Fable이 각각 낸 P3는 실제 네이티브 폴더 선택 중 자동 작업이 시작되는 경합으로 재현했다. 분리 실행 직전에 job·stopping·closing을 다시 검사해 요청 실패를 IPC로 알리도록 고쳤다. 원래 빈 오류 표시와 수정 뒤 안내 표시를 실제 Electron으로 대조했다(`dialog-race-original.json`, `dialog-race-fixed.json`). Fable의 pending 안내 P2도 요청 처리 대기로 좁혀 고쳤다.

## 0.1.0 기록 (2026-11-08)

기준일 2026-11-08. 사용자가 요청한 첫 Windows 자동 백업·복구 구현이다. 기존 SYNK PC 앱과 분리된 패키지로 개발하며, 임시 생성 자료만 시험한다. 개인 자료·실제 고객 저장소·운영 클라우드·Windows 시작 등록은 시험으로 변경하지 않는다.

## 설계 경계

- restic 0.19.1의 암호화·중복 제거·저장소 잠금·복구 검증을 사용한다. 직접 암호 포맷을 만들지 않는다.
- 완료 백업은 restic exit 0, 고유 run 태그의 스냅샷 1개, 구조 검사 성공, 완료 태그 재조회 순서로 확인한다. 부분 백업 exit 3과 구조 검사 실패는 최신 완료본을 바꾸지 않는다.
- 생성 전 Windows DPAPI로 암호를 저장하고 초기화 중 설정도 먼저 기록한다. 첫 백업 전에 복구 키를 별도 파일로 쓰고 다시 읽어 확인한다. 일반 상태·로그·renderer에 암호를 전달하지 않는다.
- 앱이 만든 저장소 ID·vault 태그·호스트가 맞고 최신 완료본과 전체 점검 이력이 확인된 때만 24시간 이전 스냅샷을 정확한 ID로 정리한다. imported 저장소는 복구 전용이다. 잠금을 강제로 제거하거나 손상 저장소를 자동 수리하지 않는다.
- 복구 전에 각 디렉터리 subtree의 `restic ls --json --recursive` 목록을 읽어 파일 유형·이름·크기를 확인한다. 사용자 복구 폴더 안에 매번 새 하위 폴더를 만들고 `restic dump --archive tar`의 바이너리 stdout을 tar-stream 3.2.2로 바로 읽는다. 중간 아카이브를 디스크에 만들지 않는다. 파일은 `wx`로 새로 만들며 원래 Windows SID/DACL을 적용하지 않는다. 사전 목록과 파일·폴더 집합 및 크기를 대조하고 SHA-256으로 쓰기 후 재검증한다.
- renderer는 경로·암호·임의 명령을 전달할 수 없다. 네이티브 선택창을 main이 열고 선택값을 보관한다. sandbox/contextIsolation, 엄격한 CSP, 외부 탐색·권한 차단을 적용한다.
- 첫 시험판은 로컬·외장 드라이브만 지원한다. B2 고객 분리·인증·과금·불변 보관은 다음 구현 범위이며 지금 완료한 것처럼 표시하지 않는다.

사용자 원문 「최신화된 버전 하나만 집중해서 보관하는 느낌으로 진행하고싶어. 이 외것들은 과금 변경으로 한번 기획해보자」를 보관 정책의 기준으로 삼았다. 기본 상품을 장기 이력 보관으로 바꾸지 않는다. 24시간 내부 안전 이력은 UI 상세·README에 명시하며 그 이전의 실수·암호화 피해까지 복구한다고 주장하지 않는다.

## 만들기 전 Fable 검토

실제 응답 모델 `claude-fable-5-1`, `end_turn`, 끝 표식 `DESIGN_REVIEW_COMPLETE`. 첫 요청은 생각 토큰으로 출력 상한에 닿아 답이 없었고 검토 완료로 세지 않았다. 보존한 원응답의 두 번째 요청으로 검토를 완료했다. 승인된 한도 있는 검수 크레딧과 기존 `tools/lib/클로드키.js` 통로를 사용했다.

P1 제안 6건 중 4건을 반영했다: 전체 데이터 매회 재읽기를 첫 회·매일 점검으로 분리, 검사 실패 시 health 하향, 복구 키 필수·읽기 대조, 태그 변경 뒤 ID 재열거. 나머지 2건은 다음 근거로 채택하지 않았다.

- 부분 스냅샷을 최신 verified로 승격하라는 제안: 누락된 파일이 있는 결과가 정상본을 대체하면 사용자 요구와 어긋난다. 부분 백업은 오류로 표시하고 기존 완료본을 유지한다. 일상 작업 폴더부터 시험하며 열린 DB의 일관성은 이번 범위에서 제외한다.
- 실패 뒤 자동 unlock/prune 제안: 단일 앱 프로세스라는 사실만으로 다른 restic 프로세스의 잠금이 안전하다고 볼 수 없다. 손상·중단은 자동 수리하지 않는다. 오래된 잠금은 원인을 확인한 뒤 처리할 후속 범위다.

경로를 main에서 선택, 복구 전 여유 공간 확인, state 하위 TEMP/cache, 절전 복귀 재시도, 바이너리 고정·런타임 다운로드 금지도 반영했다. 볼륨 GUID 자동 재탐색은 후속이며 현재는 저장소 ID를 매번 비교해 드라이브 문자 재사용에 잘못 쓰지 않는다. 이동된 드라이브는 복구 키로 실제 위치를 다시 선택해 복구한다.

화면 원본 3개는 `claude-opus-5-5`가 작성했다. GPT는 엔진·IPC·포장·시험을 담당했다. security-audit 스킬은 저장·복구·비밀 경계의 guidance로만 사용했으며 독립된 전체 보안감사 완료를 뜻하지 않는다.

## 복구 경로의 Fable 재설계 검토

연속 두 코드 검수에서 SID/DACL, FAT32 임시 ZIP 한도 문제가 나와 패치 전에 Fable에게 스트림 설계를 다시 보였다. `claude-fable-5-1`, `end_turn`, `DESIGN_REVIEW_COMPLETE`. 원응답은 공용 작업본 `.tmp/solo-backup-mvp-20261108/restore-redesign-review.md`에 보존했다. 앞 요청은 응답 파일 없이 종료되어 완료로 세지 않았고 예산 예약도 지우지 않았다.

5건 중 4건을 반영했다: 사전 매니페스트와 전체 복구 집합 대조, 미지원 노드 쓰기 전 거절, 디렉터리 subtree를 명령으로 확인, stdout 소비 실패·자식 종료를 모두 기다리는 I/O 처리. stderr는 기존처럼 끝부분만 보관하면서 계속 읽는다. TAR 끝의 두 0 블록도 확인한다. 경로 금지 문자·장치명·대소문자 중복은 기존 검증을 유지했다.

하드링크를 TAR TypeLink로 내보낸다는 나머지 1건의 전제는 [고정 restic 0.19.1 구현](https://github.com/restic/restic/blob/v0.19.1/internal/dump/tar.go)과 달랐다. 이 버전은 일반 파일 내용을 각 이름에 내보낸다. TypeLink 복사 코드는 추가하지 않고, 각 이름의 크기를 세는 ls 목록과 실제 하드링크 백업·복구 시험으로 확인한다. `stats --mode restore-size`는 하드링크를 한 번만 세므로 복구 공간 계산에서 제외했다. 중간 ZIP과 zlib.crc32를 제거해 FAT32의 아카이브 한도와 Node 22.0/22.1 API 불일치도 없앴다. FAT32 실물 볼륨 시험은 하지 않았다.

## 실제 시험

Node 내장 시험 + 공식 Windows x64 restic으로 26개 검증, 26 통과·0 실패·0 생략, 종료 0(마지막 기능 시험 106.0초). 공용 작업본 `.tmp/solo-backup-mvp-20261108/engine-v12.tap`과 도구 실행 결과로 확인했다. 받은 TAP를 묶음에 넣을 때 검수 도구의 종료 코드가 null로 표시되는 것은 수신 형식이며 실제 명령은 종료 0이었다. 한글·공백·빈 파일·바이너리의 복구 해시, 수정·삭제 반영, 24시간 안전 이력, 누락 원본·부분 종료·검사 실패 시 최신 완료본 유지, 잘못된 키·저장소 교체 차단, 키만으로 새 앱 상태 복구, 복구 전용 정리 금지, 정확한 이전 ID 정리, 스케줄 중복 방지, 실제 pack 손상 검출, 정션 거절을 포함한다. 여러 원본 폴더·하드링크의 독립 파일 복구, 아카이브 없는 복구, 정상 종료 뒤 잠금 없음, 스트림 중단·엔트리 누락·중복·크기 불일치·위험 경로도 확인했다. 시험용 암호 보관기는 테스트 전용이며 실제 DPAPI 확인은 앱 시험에서 따로 했다.

첫 실행 12개 중 5개 실패 원인은 Windows `C/Users` 상위 폴더 ACL·타임스탬프 복원이었다. 오류를 무시하지 않고 선택한 작업 폴더 subtree만 복구하도록 고친 뒤 전부 통과했다. 원래 실패한 시험 자료도 보존했다.

추가 시험은 24MB 이상 진행 출력의 메모리 제한, 나눠 들어온 UTF-8, DPAPI 실패 뒤 동일 키 재연결, 초기화 실패 뒤 기록·암호를 보존한 재설정, 복구 실패 직후 health 하향과 정리 금지, 경로 이탈·ADS·Windows 장치명 차단이다. 보호 ACL 및 가상 이전 SID를 가진 시험 파일을 복구해 현재 계정으로 내용을 읽고 원본의 보호 DACL·가상 SID가 이식되지 않는 것도 확인했다. 이 시험은 같은 Windows 계정의 별도 상태 폴더에서 진행했으며 별도 실제 PC·두 Windows 사용자 계정 시험은 아니다.

실제 Electron 화면에서 최초 폴더 선택→복구 키 저장→자동 백업→전체 점검→새 폴더 복구를 실행하고 파일 내용을 대조했다. Windows safeStorage 암호화, 평문 키가 설정·암호화 파일에 없는 것, 앱 재시작 후 복호화도 확인했다. 추가로 새 앱 상태에서 복구 키·저장소를 불러오는 복구 전용 화면의 단추 활성화와 실제 파일 복구를 확인했다. renderer 오류 0, 1440/390px 캡처에서 가로 넘침 없음. Windows 시작 등록과 개인 자료는 바꾸지 않았다.

최종 스트림 방식의 배포 후보에서도 64MiB 무작위 바이너리, 한글 파일, 중첩·빈 폴더의 복구 해시·빈 폴더가 일치했다. 실제 Electron·restic·tar-stream을 포함한 실행 파일로 확인했다. TB 규모 성능이나 실제 기기 고장·다른 Windows SID에서 실행한 실측으로 확대 해석하지 않는다. 의존성은 package-lock.json으로 고정하고 `npm ci --omit=dev --ignore-scripts`의 결과만 포장했다. 설치 당시 npm audit의 알려진 취약점은 0건이며 독립 보안감사를 뜻하지 않는다.

스트림 소비 실패를 재현한 시험에서 Windows의 즉시 kill이 restic 잠금을 남기는 것을 확인했다. 출력 파이프를 닫고 restic이 스스로 오류 처리·잠금 해제를 마치도록 기다리며, 5초 안에 끝나지 않을 때만 해당 자식을 종료한다. 일반 앱 종료는 새 작업을 받지 않고 진행 중 작업을 끝까지 기다린다. 정전·OS 강제 종료로 남은 잠금은 자동으로 지우지 않는다. 종료 대화상자 문구는 Claude가 작성했다. 하드링크 시험의 첫 실패는 스냅샷의 경로 정렬 순서를 고정해 가정한 시험 오류였고, 복구경로.json으로 실제 위치를 찾아 검증하도록 고쳤다. 실패한 TAP도 보존했다.
