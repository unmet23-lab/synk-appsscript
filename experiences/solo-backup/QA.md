# Windows 업무 백업 · 설계와 검증

## 0.3.1 정기 백업과 Windows 자동 실행 (2026-11-09)

사용자가 연결된 폴더의 정기 백업과 Windows 로그인 시 실행을 명시 요청했다. 화면 조작 중 Esc로 중단된 뒤에는 컴퓨터 유즈를 쓰지 않고 기존 엔진·Electron API와 명령으로 진행했다. 기존 클라우드 프로필의 `automatic`만 켰으며 작업 폴더·접근 키·복구 연결은 유지했다. Windows Run의 단일 `SoloWorkBackup` 항목은 별도로 설치한 0.3.1의 `WorkBackup.exe --background`를 가리킨다. 이전 0.3.0은 보존하고 기존 바탕 화면 바로가기를 새 설치본으로 바꿨다.

등록 시 `name: SoloWorkBackup`을 쓰지만 조회는 기본 AppUserModelId를 써서, Windows에는 켜졌는데 `openAtLogin`만 false가 되는 오류를 재현했다. `main.cjs`에서 앱 준비 전에 같은 AppUserModelId를 설정했다. 동일 Run 명령에서 지정 전 false·지정 후 true를 확인했고 `executableWillLaunchAtLogin`과 활성 항목도 대조했다. UI 파일·백업 주기·보관 정책은 바꾸지 않았다.

0.3.1 배포 파일 363개의 해시를 확인했다. 시작 등록과 동일한 명령으로 실제 설치본을 백그라운드 실행했으며 수동 백업이나 시험용 tick은 부르지 않았다. 자동으로 restic 백업 자식이 실행됐고 **11월 9일 04:44:52 KST**의 새 완료본에 사용자 폴더 68파일·139,101,869바이트가 기록됐다. 별도 읽기 전용 원격 조회에서도 최신 완료 ID·작업 경로·68개 파일과 총 바이트가 앱 기록과 같고 pending 표시는 없었다. 원본의 전체 SHA-256은 실행 전후 같았다. 이번 새 백업의 구조 점검은 통과했고 전체 데이터 점검 시각은 앞 성공 이력을 유지한다. Windows 재부팅·로그오프를 실행한 시험은 아니다. PC가 깨어 있고 앱이 실행 중일 때 60분 간격으로 시도한다.

전체 `tests/*.test.cjs`를 실제 Windows restic으로 실행해 **48/48 통과, skip 0**이다. 백엔드 검수 `solo-backup-startup-20261109`: **GPT 0건·Claude 3건(일부 1·재현 안 됨 2)**, 현재 파일 증명 통과. 시험 보강 제안은 전체 시험과 실제 Windows API 재현으로 일부 반영했고 구현 문자열을 그대로 비교하는 정적 시험은 추가하지 않았다. lock·README 버전 누락 의심은 실제 파일 대조로, 바로가기 AUMID 충돌 의심은 휴대용 패키징과 명시 AUMID 없는 기존 바로가기로 해소했다. Claude 검수는 기존 무료 크레딧 0.120284달러를 사용했으며 새 결제·충전은 없다. 증거는 공용 작업본의 무시된 `.tmp/solo-backup-autostart-20261109/`에 있다.

0.3.1 전체 실행 폴더 ZIP(176,823,646바이트)도 기존 비공개 Drive 복구 폴더에 보관했다. 소유자 단독 권한과 원격 크기·SHA-256 일치를 확인했다(`2829e4641713109c52c4606588ddb83f1c2e27cf0ca17080211a3056be20e2f4`). 이번 ZIP의 독립 재다운로드 검증은 하지 않았으며 기존 사본과 복구 키는 그대로 보존했다.

## 0.3.0 Google 자동 복구 (2026-11-09)

사용자의 외부 복구 키 보관·자동화 요청과 이번 작업의 로그인 위임에 따라 기존 클라우드 백업에 계정 복구를 더했다. B2 실제 계정의 지역·버킷·기존 백업용 키와 원본 파일은 유지했다. 별도의 버킷 제한 Read Only 키를 만들고 권한·저장소 ID를 확인했다. Google Drive API, 별도 데스크톱 OAuth 클라이언트와 PKCE·서명된 OIDC 검증을 연결했다. 신규 Google 프로젝트는 계정 프로젝트 수 한도로 만들 수 없어 설계 보완 검토 뒤 기존 SYNK 계정 프로젝트를 사용했다. 기존 웹 OAuth 클라이언트·프로젝트 공개 모드·과금은 바꾸지 않았다. 프로젝트 공유 신뢰와 복구 연속성은 README에 명시한다.

앱 전용 Google 사본에는 복구 키와 읽기 전용 B2 키만 함께 넣고, 백업용 쓰기 키·Google 토큰·로컬 작업 경로는 넣지 않는다. 현재 PC의 Google 토큰과 복구 준비 기록은 Windows safeStorage로 보관한다. 원격 사본을 대기 상태로 만든 뒤 다시 내려받아 내용·계정·SHA-256을 대조하고 확정한다. 응답이 유실되어도 같은 세대를 찾아 재개하며, 교체 실패 때문에 이전 사본을 삭제하지 않는다. 매일 재확인과 삭제된 사본 재생성을 구현했다. 로컬 연결 해제는 외부 사본이나 프로젝트 전체 권한을 취소하지 않는다.

설계 Fable 최초 25건 중 19건 반영·3건 일부 반영, 보완 6건 중 5건 반영이다. 프로젝트 연속성(D1)은 유지 기록과 독립 수동 사본까지 적용했고 별도 프로젝트 분리는 후속, 중복 세대(D13)는 자동 선택을 막고 시각별로 보이며 구세대 전용 설명은 후속, 재시도(D16)는 인증 재요청·권한·공간 오류를 구분하되 공간 오류도 제한된 간격으로 재확인한다. 로컬 프로필 계정 복구(D21)는 이번 클라우드 범위에서 제외했고, 추가 암호문구(D22)·사용자 지정 이름(D24)은 후속이다. 보완 F1의 `restic restore` 명령 추가 제안은 기존의 검증된 dump→TAR 스트림 복구를 실제로 사용하므로 채택하지 않았다. F2~F6의 실시간 읽기 키 검증·배타적 잠금 확인·게시 저널·분실 시 권한 회수 순서·실제 Google 공개 모드 확인·고정 공식 주소의 회전 JWKS를 반영했다. Workspace 조직별 접근 정책까지 실측한 것은 아니다.

### 실제 외부 보관·복구

- 별도 비공개 일반 Drive 폴더에 수동 복구 키를 보관했다. 소유자 단독 권한, 크기·MD5·SHA-256을 확인하고 브라우저로 다시 내려받아 바이트 일치를 검증했다. 이 사본에는 B2 접근 키가 없다. 앱 데이터 프로젝트가 없어져도 찾을 수 있는 별도 보조 경로이며 앱의 자동 동기화 기능으로 세지 않는다.
- 실제 소유자 Google 로그인 후 복구 전용 B2 권한과 restic config/snapshots를 확인했다. 자동 복구 정보를 앱 전용 Drive에 게시하고 원격 다운로드·내용 대조·확정 및 후보 재발견을 완료했다.
- 이전 PC의 Local State, 암호 보관 파일, B2 키, 수동 복구 키를 복사하지 않은 **빈 앱 상태**에서 Google에 다시 로그인했다. 원격 후보 선택·읽기 전용 연결·최신본 복구를 수행하여 사용자 승인 자료 68개, 139,101,869바이트(약 132.7MiB)를 새 폴더에 복구했다. 전체 파일 SHA-256이 원본과 같고 시험 전후 원본도 같았다. 복구 구간은 약 46초의 단일 관찰이며 성능 보장이 아니다. 다른 물리 PC나 다른 Windows 계정의 실측은 아니다.
- 비밀값과 계정·버킷·저장소 식별자는 공개 문서에 넣지 않았다. 원본 영수증과 해시 목록은 공용 작업본의 무시된 `.tmp/solo-backup-recovery-20261109/` 및 사용자 보안 폴더에만 있다.
- 원래 앱 설정에 검증한 암호화 복구 연결을 설치하고 실제 원격 사본을 다시 검증했다. 기존 백업 접근 키와 자동 백업 꺼짐 상태는 그대로다. 최종 0.3.0 실행 파일 363개의 해시를 확인했고, 원래 앱 상태와 빈 상태에서 복구한 앱 상태 모두 설치본 재시작 후 Google 연결·복구 가능 상태를 유지했다. 시작 등록은 시험 모드에서 금지했고 renderer 오류는 0이었다. 필수 검수 통과 뒤 사용자 배포 폴더의 별도 0.3.0 경로에 설치했으며 0.2.0은 유지했다.
- 전체 실행 폴더의 ZIP(176,823,587바이트)을 같은 비공개 Drive 폴더에도 보관했다. 소유자 단독 권한과 원격 크기·SHA-256이 로컬 배포본과 같음을 확인했다. ZIP SHA-256은 `6d60d3e7521a42e3b74b9ab0c3a014e6b6dc3379ab25f628bde7bfba85346789`다. 기존 메타데이터 인증의 본문 접근은 `appNotAuthorizedToFile`로 제한되어 ZIP의 독립 재다운로드는 하지 못했으며, 위 수동 복구 키의 재다운로드 검증과 구분한다. 권한은 늘리지 않았다. 설치본을 가리키는 바탕 화면 바로가기도 확인했다.

### 시험과 코드 검수

실제 Windows restic을 사용하는 기존 시험과 신규 복구 시험 47개 전부 통과했다. 이후 추가한 미게시 계정 전환·최초 게시 재시도 시험을 포함해 `recovery.test.cjs` 12개 전부 통과했다. PKCE/state/loopback Host·취소, 실제 서명된 JWT의 위조·claim 거절, 같은 계정 바인딩, 엄격한 복구 정보 스키마, B2 쓰기/관리 권한 거절, 원격 생성/확정 응답 유실, 기록 손상·교체·재시도, 원격 삭제·키 폐기, HTTP 리디렉션·크기 제한·오류 가림, 읽기 전용 restic 명령 제한을 확인했다.

백엔드 첫 판 GPT 4건(반영 4)·Claude 6건(반영 5, 일부 1), 끝 판 GPT 0건·Claude P3 2건(재현 안 됨 2)이다. 처음 발견한 빈 앱 상태 예외, 원격 사본이 없는데 완료 표시가 남는 문제, 최초 게시 전 잘못 연결한 계정의 전환 불가를 고쳤다. 손상된 로컬 기록은 빈 앱에서만 격리 후 재연결하고, 기존 저장소가 있는 앱에서는 계정 바인딩을 버리지 않고 차단한다. 이 정책 때문에 Claude의 손상 기록 복구 제안은 일부만 반영했다. 끝 판의 파일 이동 busy 고착 의심은 busy를 세우기 전이라 재현되지 않았고, 429/5xx는 실제 HTTP 계층에서 NETWORK로 분류되어 이전 증거를 유지한다. 계정 재인증·접근 거절은 검증 전 자동 백업 관문을 유지하는 의도한 동작이다. 최종 백엔드 증명은 `solo-backup-recovery-backend-final-20261109` 사슬이다.

화면은 Claude가 작성하고 아르곤 지적 2건을 반영했다. 기존 저장소에 복구 후보를 가져오도록 잘못 안내하던 버튼·문구를 상태와 맞췄다. 그림·diff가 빠진 Fable 응답은 미완료 원문으로 보존하고 통과로 세지 않았다. 이후 Fable이 전체 코드·diff와 두 폭의 실제 캡처를 함께 검토한 5건을 반영했다. 문구 수정 뒤 좁은 diff 재검수 2건은 P2 안내 세분화 후속 1건·P3 트레이/제한 시간 의심 재현 안 됨 1건이다. 합계 아르곤 2건(반영 2)·Fable 7건(반영 5·후속 1·재현 안 됨 1). `solo-backup-recovery-ui-20261109` → `solo-backup-recovery-ui-final-20261109` 증명 검사와 배포 조건을 통과했다.

네이티브 Electron의 1440/390 폭에서 가로 넘침·renderer 오류 없이, 후보 명시 선택·작업 중 차단·자동 보관 후 수동 키 필수 해제·읽기 전용 쓰기 버튼 숨김·오류 상태의 이전 확인 시각 표시를 확인했다. 처음 캡처의 탭 요약과 본문 불일치는 시험 상태의 profiles 값 누락이었다. 시험 데이터를 일치시키고 다시 확인했으며 옛 캡처도 보존했다. 캡처는 상태를 주입한 시험 화면이며 실제 계정 로그인 증거와 구분한다. 최종 포장 시험의 첫 실패는 비동기 waitForFunction 조건이 Promise를 참으로 취급해 시작 시 확인이 끝나기 전에 단추를 누른 시험 오류였고, 실제 활성화 상태를 기다린 뒤 원래/복구 프로필 모두 통과했다.

이미지 요청은 공용 API 도구가 비용 상한을 계산하지 못해 거절하여 그대로 유지했다. 사용자가 기존 무료 크레딧 총 10달러 사용을 명시 승인한 뒤 공식 CLI의 단일 요청·호출 비용 상한과 출력 한도, 예비분을 둔 공용 사용 기록 예약으로 실행했다. 최종 Fable 두 호출과 Claude 문구 수정의 기록상 합계는 1.8784735달러다. 새 결제·충전·키 한도 해제·구독 대체는 하지 않았다.

### 남은 범위

일반 고객의 가입·과금·키 발급, 새 PC에서 백업용 연결로 전환, 코드 서명·업데이트, 독립 Google 프로젝트로 이전할 때의 사본 이관, 외부 사본의 오래된 세대 정리·키 교체/폐기·계정 분실 복구, 실물 새 PC·대용량 시험은 후속이다. 오류 본문 없이 attention만 남는 드문 상태에서는 모드별 안내를 더 세분화할 수 있다(P2); 실제 원격 검증·새 폴더 복구 관문은 유지된다. 현재 소유자용 복구 키 준비를 일반 고객의 무설정 자동 가입으로 확대해서 설명하지 않는다. Google 로그인을 잃어도 앱이 임의로 본인 확인을 우회하지 않는다.

## 0.2.0 B2 클라우드 (2026-11-09)

## 0.1.0 기록 (2026-11-08)

기준일 2026-11-08. 사용자가 요청한 첫 Windows 자동 백업·복구 구현이다. 기존 SYNK PC 앱과 분리된 패키지로 개발하며, 임시 생성 자료만 시험한다. 개인 자료·실제 고객 저장소·운영 클라우드·Windows 시작 등록은 시험으로 변경하지 않는다.

## 설계 경계

- restic 0.19.1의 암호화·중복 제거·저장소 잠금·복구 검증을 사용한다. 직접 암호 포맷을 만들지 않는다.
- 완료 백업은 restic exit 0, 고유 run 태그의 스냅샷 1개, 구조 검사 성공, 완료 태그 재조회 순서로 확인한다. 부분 백업 exit 3과 구조 검사 실패는 최신 완료본을 바꾸지 않는다.
- 생성 전 Windows DPAPI로 암호를 저장하고 초기화 중 설정도 먼저 기록한다. 첫 백업 전에 복구 키를 별도 파일로 쓰고 다시 읽어 확인한다. 일반 상태·로그·renderer에 암호를 전달하지 않는다.
- 앱이 만든 저장소 ID·vault 태그·호스트가 맞고 최신 완료본과 전체 점검 이력이 확인된 때만 24시간 이전 스냅샷을 정확한 ID로 정리한다. imported 저장소는 복구 전용이다. 잠금을 강제로 제거하거나 손상 저장소를 자동 수리하지 않는다.
- 복구 전에 각 디렉터리 subtree의 `restic ls --json --recursive` 목록을 읽어 파일 유형·이름·크기를 확인한다. 사용자 복구 폴더 안에 매번 새 하위 폴더를 만들고 `restic dump --archive tar`의 바이너리 stdout을 tar-stream 3.2.2로 바로 읽는다. 중간 아카이브를 디스크에 만들지 않는다. 파일은 `wx`로 새로 만들며 원래 Windows SID/DACL을 적용하지 않는다. 사전 목록과 파일·폴더 집합 및 크기를 대조하고 SHA-256으로 쓰기 후 재검증한다.
- renderer는 경로·암호·임의 명령을 전달할 수 없다. 네이티브 선택창을 main이 열고 선택값을 보관한다. sandbox/contextIsolation, 엄격한 CSP, 외부 탐색·권한 차단을 적용한다.
- 첫 시험판은 로컬·외장 드라이브만 지원한다. B2 고객 분리·인증·과금·불변 보관은 다음 구현 범위이며 지금 완료한 것처럼 표시하지 않는다.

사용자 원문 「최신화된 버전 하나만 집중해서 보관하는 느낌으로 진행하고싶어. 이 외것들은 과금 변경으로 한번 기획해보자」를 보관 정책의 기준으로 삼았다. 기본 상품을 장기 이력 보관으로 바꾸지 않는다. 24시간 내부 안전 이력은 UI 상세·README에 명시하며 그 이전의 실수·암호화 피해까지 복구한다고 주장하지 않는다.

## 만들기 전 Fable 검토

실제 응답 모델 `claude-fable-5-1`, `end_turn`, 끝 표식 `DESIGN_REVIEW_COMPLETE`. 첫 요청은 생각 토큰으로 출력 상한에 닿아 답이 없었고 검토 완료로 세지 않았다. 보존한 원응답의 두 번째 요청으로 검토를 완료했다. 승인된 한도 있는 검수 크레딧과 기존 `tools/lib/클로드키.js` 통로를 사용했다.

P1 제안 6건 중 4건을 반영했다: 전체 데이터 매회 재읽기를 첫 회·매일 점검으로 분리, 검사 실패 시 health 하향, 복구 키 필수·읽기 대조, 태그 변경 뒤 ID 재열거. 나머지 2건은 다음 근거로 채택하지 않았다.

- 부분 스냅샷을 최신 verified로 승격하라는 제안: 누락된 파일이 있는 결과가 정상본을 대체하면 사용자 요구와 어긋난다. 부분 백업은 오류로 표시하고 기존 완료본을 유지한다. 일상 작업 폴더부터 시험하며 열린 DB의 일관성은 이번 범위에서 제외한다.
- 실패 뒤 자동 unlock/prune 제안: 단일 앱 프로세스라는 사실만으로 다른 restic 프로세스의 잠금이 안전하다고 볼 수 없다. 손상·중단은 자동 수리하지 않는다. 오래된 잠금은 원인을 확인한 뒤 처리할 후속 범위다.

경로를 main에서 선택, 복구 전 여유 공간 확인, state 하위 TEMP/cache, 절전 복귀 재시도, 바이너리 고정·런타임 다운로드 금지도 반영했다. 볼륨 GUID 자동 재탐색은 후속이며 현재는 저장소 ID를 매번 비교해 드라이브 문자 재사용에 잘못 쓰지 않는다. 이동된 드라이브는 복구 키로 실제 위치를 다시 선택해 복구한다.

화면 원본 3개는 `claude-opus-5-5`가 작성했다. GPT는 엔진·IPC·포장·시험을 담당했다. security-audit 스킬은 저장·복구·비밀 경계의 guidance로만 사용했으며 독립된 전체 보안감사 완료를 뜻하지 않는다.

## 복구 경로의 Fable 재설계 검토

연속 두 코드 검수에서 SID/DACL, FAT32 임시 ZIP 한도 문제가 나와 패치 전에 Fable에게 스트림 설계를 다시 보였다. `claude-fable-5-1`, `end_turn`, `DESIGN_REVIEW_COMPLETE`. 원응답은 공용 작업본 `.tmp/solo-backup-mvp-20261108/restore-redesign-review.md`에 보존했다. 앞 요청은 응답 파일 없이 종료되어 완료로 세지 않았고 예산 예약도 지우지 않았다.

5건 중 4건을 반영했다: 사전 매니페스트와 전체 복구 집합 대조, 미지원 노드 쓰기 전 거절, 디렉터리 subtree를 명령으로 확인, stdout 소비 실패·자식 종료를 모두 기다리는 I/O 처리. stderr는 기존처럼 끝부분만 보관하면서 계속 읽는다. TAR 끝의 두 0 블록도 확인한다. 경로 금지 문자·장치명·대소문자 중복은 기존 검증을 유지했다.

하드링크를 TAR TypeLink로 내보낸다는 나머지 1건의 전제는 [고정 restic 0.19.1 구현](https://github.com/restic/restic/blob/v0.19.1/internal/dump/tar.go)과 달랐다. 이 버전은 일반 파일 내용을 각 이름에 내보낸다. TypeLink 복사 코드는 추가하지 않고, 각 이름의 크기를 세는 ls 목록과 실제 하드링크 백업·복구 시험으로 확인한다. `stats --mode restore-size`는 하드링크를 한 번만 세므로 복구 공간 계산에서 제외했다. 중간 ZIP과 zlib.crc32를 제거해 FAT32의 아카이브 한도와 Node 22.0/22.1 API 불일치도 없앴다. FAT32 실물 볼륨 시험은 하지 않았다.

## 실제 시험

Node 내장 시험 + 공식 Windows x64 restic으로 26개 검증, 26 통과·0 실패·0 생략, 종료 0(마지막 기능 시험 106.0초). 공용 작업본 `.tmp/solo-backup-mvp-20261108/engine-v12.tap`과 도구 실행 결과로 확인했다. 받은 TAP를 묶음에 넣을 때 검수 도구의 종료 코드가 null로 표시되는 것은 수신 형식이며 실제 명령은 종료 0이었다. 한글·공백·빈 파일·바이너리의 복구 해시, 수정·삭제 반영, 24시간 안전 이력, 누락 원본·부분 종료·검사 실패 시 최신 완료본 유지, 잘못된 키·저장소 교체 차단, 키만으로 새 앱 상태 복구, 복구 전용 정리 금지, 정확한 이전 ID 정리, 스케줄 중복 방지, 실제 pack 손상 검출, 정션 거절을 포함한다. 여러 원본 폴더·하드링크의 독립 파일 복구, 아카이브 없는 복구, 정상 종료 뒤 잠금 없음, 스트림 중단·엔트리 누락·중복·크기 불일치·위험 경로도 확인했다. 시험용 암호 보관기는 테스트 전용이며 실제 DPAPI 확인은 앱 시험에서 따로 했다.

첫 실행 12개 중 5개 실패 원인은 Windows `C/Users` 상위 폴더 ACL·타임스탬프 복원이었다. 오류를 무시하지 않고 선택한 작업 폴더 subtree만 복구하도록 고친 뒤 전부 통과했다. 원래 실패한 시험 자료도 보존했다.

추가 시험은 24MB 이상 진행 출력의 메모리 제한, 나눠 들어온 UTF-8, DPAPI 실패 뒤 동일 키 재연결, 초기화 실패 뒤 기록·암호를 보존한 재설정, 복구 실패 직후 health 하향과 정리 금지, 경로 이탈·ADS·Windows 장치명 차단이다. 보호 ACL 및 가상 이전 SID를 가진 시험 파일을 복구해 현재 계정으로 내용을 읽고 원본의 보호 DACL·가상 SID가 이식되지 않는 것도 확인했다. 이 시험은 같은 Windows 계정의 별도 상태 폴더에서 진행했으며 별도 실제 PC·두 Windows 사용자 계정 시험은 아니다.

실제 Electron 화면에서 최초 폴더 선택→복구 키 저장→자동 백업→전체 점검→새 폴더 복구를 실행하고 파일 내용을 대조했다. Windows safeStorage 암호화, 평문 키가 설정·암호화 파일에 없는 것, 앱 재시작 후 복호화도 확인했다. 추가로 새 앱 상태에서 복구 키·저장소를 불러오는 복구 전용 화면의 단추 활성화와 실제 파일 복구를 확인했다. renderer 오류 0, 1440/390px 캡처에서 가로 넘침 없음. Windows 시작 등록과 개인 자료는 바꾸지 않았다.

최종 스트림 방식의 배포 후보에서도 64MiB 무작위 바이너리, 한글 파일, 중첩·빈 폴더의 복구 해시·빈 폴더가 일치했다. 실제 Electron·restic·tar-stream을 포함한 실행 파일로 확인했다. TB 규모 성능이나 실제 기기 고장·다른 Windows SID에서 실행한 실측으로 확대 해석하지 않는다. 의존성은 package-lock.json으로 고정하고 `npm ci --omit=dev --ignore-scripts`의 결과만 포장했다. 설치 당시 npm audit의 알려진 취약점은 0건이며 독립 보안감사를 뜻하지 않는다.

스트림 소비 실패를 재현한 시험에서 Windows의 즉시 kill이 restic 잠금을 남기는 것을 확인했다. 출력 파이프를 닫고 restic이 스스로 오류 처리·잠금 해제를 마치도록 기다리며, 5초 안에 끝나지 않을 때만 해당 자식을 종료한다. 일반 앱 종료는 새 작업을 받지 않고 진행 중 작업을 끝까지 기다린다. 정전·OS 강제 종료로 남은 잠금은 자동으로 지우지 않는다. 종료 대화상자 문구는 Claude가 작성했다. 하드링크 시험의 첫 실패는 스냅샷의 경로 정렬 순서를 고정해 가정한 시험 오류였고, 복구경로.json으로 실제 위치를 찾아 검증하도록 고쳤다. 실패한 TAP도 보존했다.
