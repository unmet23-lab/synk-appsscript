## 1단계 시험 버킷 실측 M1~M7 — 2026-11-12

유호님 승인(11-12 「승인, B2 시험 진행」)으로 0.5.0을 올렸던 운영자 B2 계정(US East)에 1단계 시험 버킷 하나를 만들었다. 비공개 · 서버 쪽 암호화(SSE-B2)이고, 수명 규칙은 접두사 `t/`에 「숨긴 지 30일 뒤 삭제」, `ci/`에 「올린 지 7일 뒤 숨김 · 숨긴 지 1일 뒤 삭제」, 두 접두사 모두 끝나지 않은 큰 파일은 1일 뒤 취소다. B2 콘솔은 출입증 권한을 「읽기와 쓰기 · 읽기만 · 쓰기만」으로만 고르게 해서 삭제 권한 없는 출입증을 만들 수 없었다. 그래서 마스터 출입증을 새로 만드는 대신 콘솔에서 **1시간 뒤 저절로 만료되는 임시 관리 출입증**(모든 버킷 · 읽기와 쓰기 — 출입증 만들기 권한이 들어 있음을 콘솔 목록에서 확인)을 만들어 API(v4)로 시험 출입증을 만들고, 실측 뒤 지웠다(지운 뒤 인증 401). 비밀값은 화면에서 읽자마자 DPAPI로 감싸 저장소 밖(`%LOCALAPPDATA%\SynkWorkBackupStage1`)에 두고 출력 · 기록에 남기지 않았다. 0.5.0 버킷 · 출입증 둘 · Google 복구 정보는 건드리지 않았다.

남은 시험 출입증: 실측 쓰기(`t/`, 삭제 없음) · 읽기(`t/`) · 서버 흉내(시험 버킷 전체, 삭제 있음 — 되살리기 도구 · 연습용) · CI 쓰기(`ci/`, 삭제 없음) · CI 읽기(`ci/`). listBuckets 없는 실측 출입증 하나는 M7에서 지웠다.

도구: [`server/tools/b2-setup.mjs`](server/tools/b2-setup.mjs) · [`b2-measure.mjs`](server/tools/b2-measure.mjs), restic 0.19.1(고정 해시 대조), 씨앗 고정 합성 자료 272개 · 26,768,003바이트(한글 이름 · 빈 폴더 포함). 실행마다 새 하위 접두사(`t/r…/`)를 쓴다. 아래는 두 번째 실행(`rc1d394`)의 값이다. 첫 실행(`re2ad0f`)은 같은 값으로 M4까지 돌다가 M5의 목록 읽기에서 B2가 유휴 연결을 끊어(`other side closed`) 멈췄다 — B2 기본 API · S3 요청에 재시도를 넣고 처음부터 다시 돌렸다.

## 1단계 회차 실행기와 T7 — 2026-11-12

[설계 4.2](STAGE1_DESIGN.md#42-앱과-따로-도는-예약-로드맵-2)의 회차 실행기를 첫 증분으로 만들었다. `WorkBackupRun.exe --run hourly|logon|wake|unlock|manual`이 상태 잠금을 잡고(못 잡으면 「바쁨(화면)」만 적고 끝, 화면 앱을 깨우지 않음), 실행하는 파일만 확인하고(restic.exe는 크기만 — 해시는 엔진이 고정 값으로 워커마다), 쉼(배터리 30% 아래 · 절전 · 종량 회선, 직접 누른 회차는 쉬지 않음)을 판단한 뒤, 워커를 회차 모드(`SWB_MODE=run`, [`worker/runner.cjs`](worker/runner.cjs))로 띄워 `$run` 한 번 하고 끝난다. 엔진의 회차(`runOnce`)는 할 때가 됐는지(55분) 보고, 오래된 잠금을 `unlock`으로 풀고(M3b), 종료 11은 「바쁨」(점검 실패로 안 적음), 종료 3은 「부분」으로 돌려준다. 회차마다 `runs.jsonl` 한 줄(정해 둔 칸만), 도는 동안 `progress.json`(종류 · 단계 · 퍼센트만). 잠금 둘(`engine.lock` · `ui.lock`)과 작업 스케줄러 등록은 다음 증분이다 — 그 전까지는 실행기를 예약에 걸지 않는다(지금 잠금은 화면 앱과 같은 `native.lock`이라, 회차 중에 화면 앱을 열면 조용히 안 열린다).

- **작업 폴더:** 설치 뒤 `--install`이 회차 작업 폴더를 관리자 소유 · T2 권한으로 만든다(설치기가 만든 폴더면 권한을 다시 놓는다). 표준 사용자가 먼저 같은 이름으로 만든 폴더는 넘겨받지 못한다 — 깨끗한 Windows에서 잰 아래 표대로 작업 스케줄러가 상승된 관리자에게도 모두 거절한다. 그래서 회차는 Administrators나 SYSTEM이 소유한 폴더에만 등록하고 아니면 뿌리 폴더에 두며, `--install`은 그 폴더를 건드리지 않고 `SCHEDULE_FOLDER_NOT_OURS`로 알리고(설치는 계속), `--uninstall`은 그 폴더를 건너뛰고 나머지를 지우며 지우지 못한 것은 세어 알린다(전에는 첫 실패에서 멈춰 뿌리 폴더의 작업까지 남겼다).

[설계 4.2 「도우미」의 「먼저 잴 것」](STAGE1_DESIGN.md#도우미--섀도-복사본만-만든다): 관리자 확인이 켜진 이 PC에서, 관리자가 만든 섀도 복사본 연결을 지나 보통 권한이 다른 프로그램이 쥔 파일을 읽고 restic으로 백업할 수 있는지. 측정 스크립트는 `test-support/t5-vss-measure.ps1`이다(보통 권한으로 띄우면 관리자 확인 한 번 · 관리자 쪽은 C: 복사본 하나와 관리자만 쓰는 폴더 안 연결 하나만 만들고, 끝나면 그 둘을 번호로 지운다).

- **세 번째 시도(17:48):** 한가할 때 띄웠는데, 그 사이 Windows가 C:에 새 복원 지점(약 2GB)을 만들어 두었다. 새 조건대로 스크립트가 복사본을 만들지 않았다(아무것도 바뀌지 않음). C:에는 앞으로도 복원 지점이 생기므로 측정은 D:로 옮겼다(스크립트에 `-Drive` · 묻는 방식은 같다).

- **되살리기에서 본 것:** `restic restore`로 되살리면 그 파일이 돌아온다. 다만 연결 폴더(`snap-D`)는 숨김 · 시스템 폴더로 돌아오고, 관리자 폴더의 권한(보통 권한은 읽기만)이 되살린 폴더에도 붙는다. 스크립트는 숨김 폴더를 안 찾아 「not found」로 적었고, 그 권한 때문에 시험 폴더를 못 지웠다(되살린 쪽의 소유자는 보통 사용자라 권한을 되돌린 뒤 지움 · 스크립트도 고침). 앱의 되살리기는 `restic restore`를 쓰지 않고 `dump`로 파일을 꺼내 자체로 풀므로 권한을 붙이지 않는다. 연결(정션)과 읽기만 되는 중간 폴더를 끼운 재현에서도 `dump`는 내용을 그대로 돌려줬다. 이 회차에서 백업 안 내용을 해시로 견주지는 못했다(되살린 파일 3MB는 있었다) — 다음에 스크립트를 돌리면 `dump` 해시와 판 안 폴더 종류까지 함께 적는다.

## 1단계 옮겨 오기를 다시 돌릴 때 놓은 파일 넘겨받기와 미리 보기 목록 기억(화면 세션 E8 · E11) — 2026-11-16

[설계 4.6 「장부와 이어받기」](STAGE1_DESIGN.md). 화면 세션이 옮겨 오기 화면 4b를 지으려고 부탁한 엔진 일 가운데, 바로 아래 절의 판이 다음으로 미룬 둘이다. 화면이 받는 값은 공유 노트 「화면세션_옮겨오기4b_답」의 끝 절에 있다.

- **넘겨받기(E11):** 앞선 판은 끝난 옮겨 오기를 다시 시작하면 새 번호로 모든 파일을 다시 내려받았다. 실패 몇 개를 다시 해 보려 해도 그랬다. 이제 앞 장부에서 놓음 · 이미 있음 · 따로 둠 · OneDrive 확인으로 끝난 파일은 다시 받지 않고 넘겨받는다.
- **넘겨받는 조건:** 이번에 놓을 자리가 앞 장부의 자리와 같아야 한다. 이번 백업 목록의 크기와 시각이 앞 장부와 같아야 한다. 지금 디스크의 파일도 같은 크기이고 시각이 2초 안이어야 한다(FAT는 2초 단위로 시각을 적는다). 「(복구본)」으로 나란히 둔 것, 내용을 확인하지 못한 것, 그 뒤에 바뀐 것은 다시 받는다. 내용은 다시 해시하지 않는다. 크기와 시각을 그대로 둔 채 내용만 바꾼 파일은 넘겨받는 한계를 받아들였다.
- **장부에 적는 시각:** 파일 줄마다 디스크의 시각(`m`)과 백업 목록의 시각(`b`)을 더 적는다. 넘겨받은 파일은 새 장부의 머리 줄 바로 뒤에 옮겨 적어서, 이 판의 이어받기와 다음 판이 새 장부만 읽어도 된다. 공간이 모자라 멈추면 장부에는 아무것도 남지 않는다.
- **미리 보기와 시작의 셈:** 앞선 판의 미리 보기는 끝나지 않은 옮겨 오기도, 다시 시작할 옮겨 오기도 모든 파일을 셌다. 그래서 같은 PC에서 다시 돌리면 이미 놓인 파일 몫까지 공간을 요구해 거절하기 쉬웠다. 이제 미리 보기와 시작이 같은 셈을 한다. 이어받기는 자기 장부를 읽기만 해서(자르거나 지우지 않는다) 남은 것만 세고, 다시 시작은 넘겨받을 것을 빼고 센다.
- **위 폴더를 하나씩:** 이어받기 갈래는 남은 파일이 있는 위 폴더를 통째로 다시 받았다. 큰 프로젝트 폴더에서 파일 하나가 바뀌어도 그 폴더 전체를 다시 내려받았다. 이제 남은 파일이 200개 이하이고 「남은 파일 수 × 256MB」가 그 위 폴더의 크기보다 작으면 남은 파일만 하나씩 받는다. 256MB는 파일 하나를 따로 받을 때 드는 restic 시작과 색인 읽기를 바이트로 어림한 값이다.
- **미리 보기 목록 기억(E8):** 갈래를 바꿀 때마다 클라우드의 폴더 목록과 꾸러미를 다시 읽어 몇 분씩 걸렸다. 이제 옛 PC의 판 번호가 같으면 10분 동안 기억한다. 판이 늘거나 지워졌거나, 다른 옛 PC거나, 10분이 지나면 다시 읽는다. 시작은 기억한 목록을 가져가고 기억을 비운다. 목록이 클 수 있어서 기억은 10분이 지나면 요청이 없어도 스스로 놓는다.
- **새 값:** `counts.carried`(넘겨받은 수, 다른 결과 수의 일부), 넘겨받은 항목의 `carried: true`, 장부 머리 줄의 `carryFrom`.
- **시험:** `tests/move-plan.test.cjs`에 셋을 더했다(넘겨받기 조건 표, 목록 기억, Windows 파일 시험 S152). 시작 상태의 기대값도 고쳤다. `tests/move-restore.test.cjs`(실제 restic)에는 다시 돌리기 하나를 더했다. 실제 restic을 넣어 엔진 208, 앱 · 작업자 · 회차 실행기 98, 서버 부호 56이 모두 통과했고 건너뛴 것은 없다. 엔진의 실제 restic 백업 시험은 459초가 걸려 8분 제한을 넘겼고, 느린 시험 표시(30분 제한)로 통과했다.
- **검수:** GPT 2차 검수 `workbackup-move-e8e11-20261116`이 P2 하나를 냈다. 기억이 만료되어도 끝난 타이머가 목록을 붙들어 수거되지 않는다는 지적이다. 재현한 뒤 타이머가 목록을 가리키지 않게 고쳤고, 고친 판 `workbackup-move-e8e11-r2-20261116`은 지적 0건이다.

## 1단계 옮겨 오기 다시 깔기 화면(4b)을 위한 엔진 값(화면 세션 E3 ~ E7, E9, E10, E12 ~ E15) — 2026-11-16

[설계 4.6 「창 앱과 회차에 이은 것」](STAGE1_DESIGN.md). 화면 세션이 옮겨 오기 화면 4a를 올린 뒤, 다시 깔기 화면 4b를 지으려고 부탁한 엔진 일이다. E8(미리 보기 목록 기억)과 E11(끝난 옮겨 오기를 다시 돌릴 때 놓은 파일 넘겨받기)은 장부와 내려받기 짜임을 바꾸므로 다음 판으로 나눴다. 부호 표와 값의 꼴은 공유 노트 「화면세션_옮겨오기4b_답」에 있다.

- **미리 보기(E3):** 폴더마다 파일이 놓일 뿌리와 갈래를 보인다. 옛 PC와 새 PC에서 각각 어느 동기화 폴더(OneDrive, 그 밖의 동기화, 없음) 안인지, 그리고 옛 폴더가 OneDrive여서 일부만 올 수 있는지도 보인다.
- **실패 부호(E4 · E13):** 앞선 판은 옮겨 오기의 실패가 거의 다 `MOVE_FAILED`라 화면이 까닭을 말하지 못했다. 이제 다섯 경우에 부호를 붙인다. 공간 부족(`MOVE_NO_SPACE`), 폴더 하나의 목록이 100만 개를 넘음(`MOVE_LIST_TOO_BIG`), 이 PC의 사용자 폴더를 못 읽음(`MOVE_PROFILE`), 옛 PC의 판이 사라짐(`MOVE_SNAPSHOT_GONE`), 연결 끊김(`MOVE_NETWORK`)이다. 새로 시작하면 도는 동안 앞선 실패 칸을 비운다.
- **「내용 확인 못 함」(E5):** OneDrive에 있으나 내용을 확인하지 못한 파일 수를 따로 센다.
- **폴더 열기(E6):** 새 메서드 `moveOpen`이 마지막 결과가 적은 자리(따로 둔 곳, 새 폴더, 놓인 뿌리)만 연다.
- **진행(E7):** 창 상태에 받은 양, 전체 양, 지금 받는 폴더, 속도를 싣는다. 속도는 5초 넘게 쌓인 차이로 센다.
- **이어받기(E9):** 놓기 시작한 옮겨 오기는 처음 고른 자리로 잇는다. 화면이 다른 고름을 보내도, 그 사이 이 PC가 쓰는 PC가 되었어도 그렇다. 한 파일도 놓지 못하고 멈춘 옮겨 오기(공간 부족)는 새 고름을 받는다(GPT 첫 검수 GA1).
- **넘길 폴더 적기(E10):** 새 메서드 `setNextSources`가 복구 전용 연결에서 쓰는 PC가 된 뒤 백업할 폴더를 경로로 적는다. 마지막 결과의 뿌리(따로 둔 것 제외)와 이미 고른 폴더만 받는다.
- **넘긴 뒤 붙들기(E12):** 바꿀 것이 없다. 서버가 자리를 옮기며 붙들기를 지우고, 새로 쓰는 PC의 정리는 옛 PC의 판을 건드리지 않으며, 옛 PC는 옮겨진 것으로 쉰다.
- **다시 시작(E13):** 끝난 옮겨 오기를 다시 시작하면, 앞선 결과는 새 결과가 적힐 때까지 남는다. 그래서 공간 부족으로 바로 멈춰도 확인서와 넘기기의 기본값이 사라지지 않는다.
- **폴더 고르기 닫음(E14):** 복구 전용 연결에서 폴더 고르기 창을 닫으면 `CANCELED`를 돌려준다.

- **옮겨 오기 상태(E1):** 새 메서드 `moveState`가 `{ from, choices, startedAt, unfinished, released, resultAt, complete, running }`을 돌려준다. PC가 꺼지거나 앱이 끝나 도중에 멈춘 옮겨 오기는 작업도, 결과도, 실패 칸도 남기지 않는다. 그래서 화면은 이 메서드로 그 사실을 읽는다(`unfinished`: 시작했고 결과가 없음). `running`은 이 창에서 지금 옮겨 오기가 도는지다.

## 1단계 되돌리기 셋 — 복구 전용 PC의 되돌리기 · 취소 실패 표시 · 끝난 결과(화면 세션 부탁 1 · 2 · 3) — 2026-11-16

[설계 4.5 「되돌리기 셋」](STAGE1_DESIGN.md). 화면 세션의 Fable 5.2 검수가 짚은 엔진 쪽 세 자리를 고쳤다.

- **복구 전용 PC의 되돌리기:** 앞선 판은 되돌리기를 부르기 전에 저장소의 호스트가 이 기기 번호인지 보아, 옛 PC 번호로 읽는 복구 전용 연결은 늘 `OTHER_BACKUP`으로 막혔다. 감염된 PC 대신 깨끗한 다른 PC에서 되돌리는 길이 엔진에서 막혀 있던 것이다. 이제 이 손님 저장소를 읽는 복구 전용 연결도 부를 수 있다. 서버는 그 요청으로 쓰는 자리를 이 PC로 옮긴다. 이 PC는 그 뒤에도 읽기만 한다. 받은 쓰기 출입증은 쓰지 않고, 그 출입증을 쓸 수 있을 때까지 기다리지도 않는다. 새 읽기 출입증은 봉투에 올린 뒤 그것으로 읽는다. 창은 이 PC의 멈춤만 서버 상태로 따른다. 옮겨짐, 용량 한도, 옮겨 오기 고정은 쓰는 PC 몫으로 남는다. 회차는 복구 전용 연결을 건드리지 않는다. 답을 잃은 요청 뒤에는 읽기 출입증만 다시 받게 한다.
- **취소 실패 표시(버그 고침):** 「되돌리기 취소」 작업이 실패하면 서버는 원래 작업을 다시 고르기 기다림으로 돌린다. 앞선 판은 그 원래 작업을 넘겨받으며 취소 작업(`undo: true`)으로 적었다. 이제는 취소가 아닌 것으로 적는다. 창은 넘겨받은 작업을 읽어 서버의 `undoOf`로 표시를 바로잡고, 실패한 취소 작업의 부호를 `undoError`로 그 작업을 고를 때까지 보인다. 취소 요청의 답을 잃은 경우(상태에 취소 작업이 보임)는 전처럼 취소로 넘겨받는다.
- **끝난 결과:** 상태에 `restoreEnded { jobId, result, at }`를 싣는다. `result`는 `continued`(되돌린 상태로 계속) 또는 `undone`(취소 작업이 끝나 되돌리기 전으로 돌아감)이다. 일주일, 새 되돌리기(답을 잃은 새 요청과 회차가 먼저 넘겨받은 이 PC의 새 작업 포함), 화면이 새 메서드 `restoreSeen(jobId)`로 알렸다고 할 때까지 남고, 창을 다시 열어도 남는다. 실패는 전처럼 `restore` 칸에 남는다. `restore`에 `finishedAt`도 더했다.
- **회차가 먼저 상태를 읽을 때(GPT 첫 검수 GA1):** 회차와 창은 같은 서버 상태로 멈춤을 잇는다. 앞선 판은 창이 스스로 바꾼 것만 알아, 회차가 먼저 멈춤을 풀거나 작업을 넘겨받으면 끝난 결과와 취소 실패를 놓쳤다. 앞선 판부터 있던 「답을 잃은 되돌리기의 출입증 다시 받기」도 같은 이유로 빠졌다. 이제 바뀐 것을 엔진 설정에 남긴다. 넘겨받은 멈춤은 `serverRestore.adopted`, 풀린 작업은 `restoreReleased`에 적는다. 창은 다음 살핌에 그 작업을 읽은 뒤에 지운다. 못 읽었으면 다음 살핌에 다시 읽는다. 답을 잃은 요청의 멈춤이 창이 보기 전에 풀리면, 풀린 작업 칸에 그 사실(`lost`)을 남겨 창이 출입증을 다시 받게 한다(GPT 둘째 검수 GA1).
- **답을 잃은 「되돌리기 취소」(GPT 둘째 검수 GA2):** 창은 답이 오지 않은 취소를 보기 파일에 적는다. 다음 살핌에서 같은 작업이 그대로 고르기를 기다리면 취소는 일어나지 않은 것이므로(서버에 닿지 않았거나 이미 실패) 취소 실패로 알린다. 서버가 취소 작업을 시작했으면 상태에 그 작업이 보이고, 취소로 넘겨받는다. 그 취소가 다음 살핌 전에 끝까지 마쳤으면, 원래 작업이 서버에서 `undone`이고 열린 되돌리기가 없으므로 끝난 결과를 「취소 완료」로 알린다(GPT 셋째 검수 GA1).
- **곁 고침:** `restoreChoose`의 「계속」 답 `ok`가 서버의 실제 답(`{state:'continued'}`)에서 늘 거짓이었다. 창은 그 값을 쓰지 않았지만 바로잡았다.
- **시험:** `account.test.cjs` 25개(새 셋 — 회차가 먼저 읽고 창이 나중에 읽는 순서 포함), 엔진 시험 전체 175 통과 · 1 건너뜀, 추천 백업 시험 9/9(실제 restic · 계획기), 앱 · 작업자 · 회차 실행기 시험 68 통과 · 4 건너뜀.

## 1단계 옮겨 오기를 창 앱과 회차에 잇기 — 2026-11-16

[설계 4.6 「창 앱과 회차에 이은 것」](STAGE1_DESIGN.md). 옮겨 오기 세션이 만든 엔진 · 호스트 쪽(4.6 · 4.6b)을 조율 세션이 창 앱 계약, 작업자, 회차 실행기에 이었다. 창 앱 호스트의 `files.*` · `folders.*` · `reinstall.*`는 설치 세션이 먼저 이어 두었다.

- **창 앱 메서드 열:** 옛 기기 고르기, 자리 미리 보기, 옮겨 오기 시작(엔진 작업 `move`, 진행률), 결과, 다시 깔 것 목록, 다시 깔기(엔진 작업을 잡지 않고 창 곁에서 돈다), 앱 설정 되돌리기, 다시 로그인할 곳과 그 표시, 옛 PC 백업 놓아주기. 모두 복구 전용 연결에서 된다. 옛 기기는 저장소에 판이 있는 기기 가운데 하나로만, 폴더마다 고른 자리는 정해진 낱말로만 받는다. 이미 쓰는 PC가 옛 기기의 판을 꺼낼 때는 모든 폴더를 새 폴더로만 놓는다.

## 1단계 되살리기 실패 칸 · 기본 놓을 자리 · 거절 부호(화면 세션 부탁 2 · 4 · 5) — 2026-11-16

화면 세션이 Fable 5.2 최종 검수에서 받은 엔진 쪽 일 셋이다.

- **되살리기 실패를 따로(4):** 전체 되살리기가 실패하면 이제 백업 실패(`lastError`)가 아니라 `lastRestoreError { code, at, path? }`에 적힌다. 부호는 저장소 잠금이면 `BUSY`, 오류가 가진 대문자 부호(엔진의 낱말 부호, `ENOENT` 같은 시스템 부호)는 그대로, 그 밖은 `RESTORE_FAILED`이다. `path`는 만들다 만 되살리기 폴더다. 되살리기가 성공하면 `lastRestoreError`만 지우고 백업의 실패와 바쁨 경고는 그대로 둔다. 그래서 되살리기 한 번으로 실패한 백업이 「안전합니다」가 되지 않는다.
- **기본 놓을 자리(2):** `restoreLatest` · `restoreSelected`가 `{ place: 'default' | 'pick' }`를 받는다. `default`면 대화창 없이 Windows의 다운로드 폴더(창 앱 호스트의 새 메서드 `folders.downloads`) 아래에 「되살린 파일 (11월 16일)」을 만든다. 같은 날 다시 하면 「되살린 파일 (11월 16일) 2」처럼 옆에 만들고, 이미 있는 폴더에는 넣지 않는다. 추천 백업 판도 같은 날짜 폴더 안에 놓인다. 놓을 자리 검사는 전과 같이 먼저 돈다.
- **거절 부호(5):** 놓을 자리가 백업 폴더나 앱 폴더와 겹치면 `OUTPUT_UNSAFE`, 마지막 폴더를 빼려 하면 `LAST_FOLDER`가 화면에 간다.
- **시험:** 실제 restic 엔진 시험에 하위 시험 하나를 더해 26/26(되살리기 실패가 백업 실패를 바꾸지 않음, 겹치는 자리의 부호, 날짜 폴더와 같은 날 두 번째). 추천 백업 실제 시험(0.6.1 시험판의 계획기 · restic)에 기본 자리 확인을 더해 통과. 작업자 시험에 `LAST_FOLDER` 확인을 더해 앱 · 작업자 12/12. Rust는 `cargo check --bins` 통과.
- **검수:** GPT 2차 `workbackup-restoreplace-20261116` 1건(38KB · 117초) — GA1 P1 가장 새 판이 추천 백업 판이면 날짜 폴더 없이 놓임 → 반영. 다시 검수 `workbackup-restoreplace-r2-20261116` 0건 — 배포 조건 충족.
- **아직:** 다운로드 폴더 메서드는 다음 창 앱 빌드부터 통한다. 그 전 판의 호스트에서는 `내 사용자 폴더\Downloads`를 쓴다.

## 1단계 창 앱의 개통 잇기 덧붙임(화면 세션 부탁 7 · 8 · 10 · 11 · 12 · 13) — 2026-11-16

[설계 4.5 「먼저 만든 것(11-16 — 앱 쪽 잇기)」의 「창 쪽 덧붙임」](STAGE1_DESIGN.md#흐름과-인증). 화면 세션이 개통 잇기 설계를 Fable 5.2에 검토받았고, 그 지적 가운데 엔진 몫 여섯 가지를 이번에 넣었다. 9번(기기가 다 찬 새 PC의 끊기)은 개통 서버 세션 몫이다.

- **되돌리기 상태(7):** 엔진의 멈춤(`serverRestore`)이 작업 번호를 함께 적고, 계정 상태에 `restore`(멈춤 여부 · 작업 번호 · 서버가 말한 상태 · 고르기 기다림 · 실패 부호 · 취소 작업인지)가 실린다. 창을 닫았다 열어도 남는다. 답을 못 받은 요청은 서버 상태에서 이 기기의 작업을 찾아 번호를 잇고, 그 요청이 가져왔어야 할 출입증 둘을 `needs`에 적는다.
- **취소 동안 멈춤(8):** 「되돌리기 취소」는 서버가 만든 새 작업 번호로 멈춤을 이어 둔다. 서버 상태에 이 기기의 작업이 더 이상 열려 있지 않으면 회차와 창 모두 멈춤을 푼다. 실패한 되돌리기는 창이 작업을 한 번 더 읽어 실패 부호를 남기고, 다른 되돌리기를 할 때까지 보인다. 멈춤이 있는 동안 창은 1분마다 서버를 살핀다(평소에는 1시간).
- **분실 뒤 새 출입증으로 열기(10):** 이 PC가 받은 새 읽기 출입증이 있으면 그것으로 연다. 없고 서버가 읽기 출입증이 없거나 Google 걸음이 남았다고 하면 봉투의 죽은 출입증을 쓰지 않고 `READ_KEY`로 먼저 거절한다. 설정이 없는 PC의 「출입증 다시 받기」는 옛 봉투의 저장소 정보로 새 봉투를 써서 올린다.
- **다시 열어도 남는 상태(11):** Google 걸음은 창의 기억만으로 판단하지 않고 봉투를 올리기 직전에 서버에 묻는다. 서버의 마지막 말(Google 걸음 · 읽기 출입증 · 되돌리기), 되돌리기가 남긴 단계(`left`), 받은 읽기 출입증이 아직 봉투에 없는지(`readKeyPending`)를 `account-v3/view.json`에 남긴다. 비밀값은 없다. 창이 살필 때 남긴 단계를 다시 한다.
- **복구 전용 연결의 폴더 고르기(12):** 계정의 백업을 연 복구 전용 연결에서 「폴더 고르기」가 설정(`nextSources`)에 남는다. 「이 PC에서 이어서 백업」은 쓰는 자리를 옮기기 전에 폴더를 검사해, 폴더가 틀리면 옛 PC가 계속 쓴다.
- **로그인 그만두기(13):** 새 메서드 `cancelGoogle`이 브라우저에서 기다리는 Google 로그인을 끊는다. 기다리던 요청은 `CANCELED`로 끝나고, 되돌리기 요청이었으면 멈춤도 푼다.
- **분실 뒤 남은 출입증(GPT 지적):** 개통 클라이언트의 분실 신고는 이 PC가 받아 둔 미확정 읽기 출입증을 지우지 않는다. 서버는 그 출입증도 지웠으므로, 분실을 안 순간(이 PC의 신고, 서버 상태에서 처음 본 분실, 읽기 출입증 없음) 그때 들고 있던 출입증의 지문을 보기 파일에 적고 봉투 · 열기 · 다시 받기에서 거른다. 분실 뒤에 받은 출입증은 Google 걸음을 함께 알고 받으므로 거르지 않는다. 봉투를 올린 적 없는 백업에 「이어서 백업」이 복구 수단을 적지 않게도 막았다.

## 1단계 회차의 개통 서버 상태와 측정 — 2026-11-16

- rfd 취소 버튼 지적은 실제 고정 버전 0.18.0이 사용하는 custom ID 1000/1001과 native IDCANCEL=2가 구분됨을 원문으로 확인했다. Enter 기본은 첫 취소 버튼이고 Esc/닫기는 `Cancel`이므로 확인으로 매핑되지 않는다. OS 마우스·키보드로 직접 누른 시험은 하지 않았다.
- 실패한 이전 임시 사본은 자동 삭제하지 않는다. DPAPI로 암호화된 읽기 키를 가진 비운영 형제 폴더이며 자동 실행 대상이 아니다. 실패 증거와 경합한 기존 폴더를 보존하는 정책이다.
- 첫 소스 업로드 전 관련 시험은 워크트리의 홍보 자료·루트 `parse5` 의존성 누락으로 멈췄다. 해당 자료를 `가볍게 --되살림`으로 복원하고 고정 잠금 파일로 `npm ci --ignore-scripts`를 실행했다. 재현한 웹 배포 4개·SNS 발행 2개는 모두 통과했으며 처음 실패 로그는 보존했다. Rust 앱이나 관련 없는 배포 코드를 고치거나 시험 관문을 끄지 않았다.

## 배포 범위와 남은 일

실행 파일과 리소스를 `Documents/업무백업-시험판/0.6.0-rust-beta.1/`에 설치했다. 설치된 EXE·리소스 291개 해시가 최종 후보와 일치하고, 한글 설치 경로에서도 로컬 전체·선택 복구 시험을 통과했다(`native-smoke-tNb7dk`). 두 필수 검수의 현재 후보 대조도 통과했다.

Rust 시험판 자동 시작은 켜지 않았고 기존 0.5.0이 정기 백업을 계속 맡는다.

이번 시험으로 확인한 것은 이 PC의 파일 백업·복구와 호환 경계다. Rust판의 실제 Windows 재로그인 자동 실행, 새 Google 로그인, 다른 PC·OS 조합, 장시간/대용량 작업, 재개 가능한 복구, VSS/전체 Windows 이미지 복구, 서명 설치·자동 업데이트는 완료로 주장하지 않는다. 웹뷰와 Node가 함께 있으므로 메모리·속도 향상도 측정 전에는 주장하지 않는다. 엔진 전체 Rust 이식과 운영 백업 전환은 다음 단계다.

화면 `solo-backup-recommended-ui-20261110`: 아르곤 1건은 최신 사용자 범위가 로컬 기본이라 재현되지 않았다. Fable 3건 중 로컬 USD 필드·100개 초과 제외 경로 열기는 후속, 현행 브리지 계약과 다른 이벤트 반환값은 재현되지 않았다. Fable은 전체 UI 소스와 준비·완료 상태 4장 캡처를 봤고 빈 상태·부분 진단은 측정 결과만 봤다. 실제 UI 시험 8장을 모두 Fable이 직접 봤다고 세지 않는다.

### 설치와 검수 집계 확인

`Documents/업무백업-시험판/0.6.1-rust-beta.1/`에 새로 설치했다. 실행 파일과 리소스 294개가 위 최종 후보의 SHA-256과 모두 같았다. 기존 버전 폴더와 기본 앱 상태·자동 시작은 교체하지 않았다. 설치만 했으며 사용자 화면에 새 앱을 띄우지 않았다.

검수 집계 도구가 필수 목록 밖 추가 아르곤의 유효한 재확인 답을 무시하는 오류를 별도 재현·수리했다. 새 코드의 필수 검수/같은 입력/미해결 응답 경계 관련 시험 **6/6** 통과, 독립 검수 `solo-backup-review-aggregate-20261110`은 GPT 0건·Claude P3 2건(재현 안 됨1·품질 후속1)이다. 백업·화면의 최종 검수 입력과 응답은 고치지 않고 현재 후보 대조를 통과했다.

집계 도구 전체 시험은 앞 18개가 통과한 뒤 이번 수정과 관계없는 긴 화면 캡처에서 진행이 멈췄다. 실행한 시험 PID와 명령을 확인하고 그 시험 프로세스만 종료했으며 원시 로그 `gate-tests-after.tap`를 남겼다. 이어 바뀐 재확인 집계·필수 검수·입력 증명에 해당하는 6개를 별도 실행해 통과했다(`gate-relevant-after.tap`). 전체 시험 통과로 보고하지 않는다.

소스 올리기 때 고른 44개 시험 파일은 631항목 중 629개 통과·2개 실패였다(`publish-apply.log`, 808초). 같은 화면 캡처 정지를 다시 확인해 이 세션의 해당 시험만 종료했고, 다른 하나는 가벼운 워크트리에서 생략된 기존 캐릭터 HTML 3개였다. 세 파일만 `가볍게 --되살림`으로 복원한 뒤 올리기 도구와 같은 워크트리 환경(`CI=1`)에서 서체 시험 **11/11**을 통과했다(`font-worktree-ci.tap`). 일반 로컬 환경의 별도 실행은 Git 밖 마케팅 서체 34벌 누락으로 10/11이었으며 그 로그도 보존했다. 해당 자료·캡처 코드는 이번 변경에 포함되지 않는다. 미완료 캡처와 변경 경계 6/6 통과를 명시한 `--시험건너뜀` 사유로 소스를 올리며 전체 시험 통과로 바꾸어 적지 않는다.
