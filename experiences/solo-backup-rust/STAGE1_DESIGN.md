## 0. 한눈에

1단계가 끝나면 이렇게 된다.

- 처음 쓰는 사람이 설치 → Google 로그인 → 「보호 시작」만으로 클라우드 백업을 시작한다. 입력 칸이 없다.
- 앱 창을 닫아도, 트레이가 없어도 Windows 작업 스케줄러가 매시간 · 로그인 직후 · 깨어난 직후 · 잠금 해제 때 회차를 띄운다. 회차 사이에는 아무 프로그램도 떠 있지 않다. 회차가 도는 동안에도 앱은 열리고 진행을 보여 준다.
- 켜진 프로그램이 쥔 파일 몇 개 때문에 나머지 전체의 보호가 멈추지 않는다. 그 파일은 그것이 든 마지막 판을 고정해 지키고, 관리자 계정이면 섀도 복사본에서 그 파일만 다시 읽어 채운다.
- PC에 있는 출입증으로는 백업을 **30일 안에 되돌릴 수 있게만** 망칠 수 있다(11-12 유호님 「30일로 넣기」). 서버가 매일 저장소가 이상하게 바뀌었는지 보고 알리며, 손님이 「이 시각으로 되돌리기」를 누르면 서버가 지운 것 없이 복사로 되살린다.
- 새 PC에서는 설치 → Google 로그인 → 「이 PC로 옮겨 오기」로 원래 자리(또는 OneDrive 밖 새 폴더)에 되살리고, 그 PC가 쓰는 기기가 되는 순간 옛 PC 출입증을 끊고, 같은 저장소에 이어서 백업한다.
- 컴퓨터 전체용 설치 파일 하나와 자동 업데이트가 있고, 깨끗한 Windows에서 같은 흐름을 GitHub Actions가 돌린다.
- 손님은 솔리오 「백업·복구」 탭에서 시작한다. 솔리오가 엔진을 받아 깔고, 엔진이 남기는 상태 파일을 읽어 보인다. 솔리오가 엔진에 넘기는 것은 정해진 요청 낱말과 값, 그리고 Google 주소 힌트뿐이고, 그 요청으로는 되돌릴 수 있는 일만 된다(4.13). AI 도구에서는 같은 상태를 MCP로 볼 수 있다(4.16).

끝난 기준은 로드맵의 **관문 1** 그대로다. 시험 하나하나를 관문과 7장에서 짝지었다. 유호님 손은 화면 시안 고르기 한 번(11-13에 시안 A 「확인서」로 정하셨다)과 [11장](#11-유호님께-여쭐-것과-때)의 일뿐이다.

## 2. 사용자 흐름

### 2.1 처음 시작

엔진 설치 파일을 직접 여는 길이다. 11-15부터 관문 1의 「사람 한 번」은 솔리오 「백업·복구」 탭에서 시작하는 길(4.13의 표, 전체 5번 · 앱 안 2번)로 센다.

| 차례 | 사람이 하는 것 | 전체 누름 | 앱 안 누름 |
|---|---|---|---|
| 1 | 내려받은 설치 파일 열기 | 1 | |
| 2 | SmartScreen 「추가 정보 → 실행」(서명 전 시범판) | 2 | |
| 3 | 관리자 확인 「예」 — 설치 창 없이 설치하고, 끝나면 **로그인한 사용자 · 보통 권한으로** 앱을 연다 | 1 | |
| 4 | 「Google로 시작」 | 1 | 1 |
| 5 | 브라우저에서 계정 고르기 · 「계속」(로그인돼 있지 않으면 입력이 더해진다) | 2 | |
| 6 | 「보호 시작」 — 보호할 폴더(문서 · 바탕화면 · 사진 + 진단이 찾은 작업 폴더 제안)와 예상 용량이 보이고, 이 단추가 곧 범위 동의다 | 1 | 1 |
| | 합 | 8 | 2 |

- SmartScreen 두 번은 OS 코드 서명(3단계) 뒤 빠진다. Smart App Control이 켜진 PC는 설치가 아예 막히므로 이 표에 넣지 않고 2단계에서 따로 센다.
- 5번은 지금 요청(`prompt=consent select_account`)에서 동의 화면에 권한 체크 칸이 뜨면 한 번 더 들 수 있다. 새 Google 프로젝트로 실제 화면을 2주차에 먼저 세고, 넘치면 요청 꼴(동의를 처음 한 번만)을 고치거나 관문 숫자를 유호님께 여쭙는다.
- 보호 시작 뒤 앱이 혼자 하는 것: 개통(서버) → 저장소 만들기 → 봉투 보관 · 다시 받아 확인 → 예약 작업 등록 → 첫 백업. 첫 백업이 도는 동안 「창을 닫아도 됩니다」 한 줄, 끝나면 알림 한 번. 첫 백업 동안 전원이 연결돼 있으면 절전을 막는다.
- 보호 범위 화면에 OneDrive 정책을 적는다: 「OneDrive에만 있는 파일 N개는 OneDrive가 지킵니다 — 이 백업에는 없습니다」(4.2).
- 두 번째 복구 수단(복구 코드)은 첫 화면에 넣지 않고 첫 주 안에 한 번 권한다. 첫 복구 수단은 자동으로 만들어지는 봉투다.
- 첫 화면에 「Google 2단계 인증을 켜 두세요」 한 줄(Google 계정에 들어갈 수 있는 사람은 백업도 읽을 수 있다 — 로드맵 6장).

### 2.2 평소

앱을 열 일이 없다. 알림은 「문제 + 할 일 하나」일 때만 뜨고, 같은 문제는 하루 한 번이다.

| 알림 | 할 일 하나 |
|---|---|
| 첫 백업이 끝남(한 번) | 없음 — 「이제 매시간 저절로 지킵니다」 |
| 사흘 넘게 소식이 없음 | PC가 켜져 있으면 원인별(회선 · 용량 · 재로그인), 꺼져 있으면 서버가 메일로 — 서버는 측정이 왔는지만 알므로 「백업을 못 함」이 아니라 「소식이 없음」이라고 쓴다 |
| 몇 파일만 못 지킴(부분 판) | 「[프로그램]이 쓰는 중인 파일 N개는 [날짜] 판으로 지킵니다」 — 할 일 없음, 그 프로그램을 닫으면 다음 회차에 새로 담긴다 |
| 폴더를 찾을 수 없음 | 「다시 고르기 · 빼기」 — 그 폴더의 마지막 판은 고정해 둔다 |
| 저장소 점검 실패 · 저장소가 바뀜(서버 탐지) | 「백업이 바뀌었습니다 — 되돌릴 수 있는 날이 N일 남았습니다 · 확인하기」 |
| 되살리기 증명에서 손상 | 「확인하기」 — 그날 |
| 많은 파일이 한꺼번에 지워지거나 바뀜 | 「확인하기」 — 확인 전까지 이전 판을 지우지 않는다 |
| 새 기기가 이 계정에 연결됨 · 되돌리기 요청됨 | 「내가 한 게 아니면 끊기」 |
| 되돌린 뒤 고르기를 기다림 | 「여기서부터 계속 · 되돌리기 취소」(하루 한 번) |
| 용량 상한에 가까움 · 넘음 | 「폴더 줄이기」 |
| Google 봉투 재확인 실패 | 「다시 로그인」 |
| 업데이트 준비됨 | 「설치」(관리자 확인이 뜬다, 표준 사용자 계정은 「관리자에게 부탁하기」 문구로 일주일에 한 번) |

### 2.3 새 PC로 옮겨 오기

설치 → 「Google로 시작」 → 앱이 이 계정의 상태를 보고 갈래를 고른다.

- **보통:** 「이 계정에 백업이 있습니다」 → 「이 PC로 옮겨 오기」 → 되살릴 자리(원래 자리 / OneDrive 밖 새 폴더, 용량과 함께) → 진행(내려받는 기다림은 따로 「약 N분」, 끊겨도 이어서) → 해시 대조 → 결과(되살린 수 · 이미 있던 같은 파일 수 · 「(복구본)」으로 나란히 둔 수 · 건너뛴 연결 · 특수 파일 수와 목록) → 다시 깔 프로그램 목록 · 다시 로그인할 곳 체크리스트 → 「옛 PC 연결 끊기」(기본 예) → 이 PC가 쓰는 기기가 되어 같은 저장소에 이어서 백업한다.
- **「옛 PC 연결 끊기」에서 아니오:** 이 PC는 되살리기까지만 하고 백업은 시작하지 않는다(쓰는 기기는 하나 — 여러 PC는 로드맵 4단계).
- **이 계정의 백업이 최근에 대량으로 숨겨졌다(서버 탐지):** 「사고 전으로 되돌린 뒤 옮겨 오기」를 먼저 내놓는다(2.5).
- **같은 PC를 다시 깔았다(파일이 디스크에 그대로):** 「되살리지 않고 이어서 백업」. 옮겨 오기를 그대로 돌리면 그사이 고친 파일마다 옆에 옛 「(복구본)」이 생기기 때문이다.

### 2.4 분실 · 탈취

1. 다른 PC의 앱(설정 서랍 「내 기기」) 또는 휴대폰에서 기기를 연결할 때 받은 메일의 링크 → 확인 쪽에서 **Google 로그인**(만료 없는 링크 하나로는 실행하지 않는다) → 「분실 신고」.
2. 서버가 즉시 그 기기의 쓰기 출입증과 **손님 읽기 출입증**을 지운다. 이때부터 전에 받은 봉투 · 복구 코드는 못 쓴다 — 화면에 「분실 신고 뒤에는 새 기기를 이을 때까지 서버가 필요하고, 전에 받은 복구 코드는 못 씁니다」를 적는다.
3. 화면이 「Google 계정에서 그 기기를 로그아웃하고 '업무 백업' 접근을 지우세요」를 바로 가는 주소와 함께 보인다. 분실한 PC의 갱신 토큰으로 봉투를 계속 읽을 수 있기 때문이다.
4. 남은 · 새 기기는 **자기 Google 토큰이 끊긴 것**으로 3이 끝났음을 확인하고 → 다시 로그인 → 서버가 새 읽기 출입증을 준다 → 새 봉투를 올려 다시 받아 확인 → 새 복구 코드를 권한다. 남은 기기가 하나도 없으면 새 PC의 옮겨 오기가 이 순서를 밟는다.
5. **남은 기기가 없을 때의 확인(다시 확인 F7).** PC가 한 대뿐인 손님의 새 PC에는 끊길 토큰이 없어, 손님이 3을 건너뛰어도 흐름이 지나간다. 그래서 (가) 새 PC가 로그인 직후 **자기 토큰을 Google 철회 주소로 스스로 끊고** 다시 로그인을 받는다 — Google의 철회가 그 계정 · 그 앱의 다른 갱신 토큰(분실 PC 것)에도 미치면 3을 앱이 대신 한 셈이 된다. 미치는지는 2주차 Google 로그인 자리에서 토큰 둘로 잰다. (나) 미치지 않으면 서버가 「분실 신고 뒤 첫 개통」임을 기억해, 새 봉투를 올리기 전에 「Google에서 접근을 지웠습니다」를 건너뛸 수 없는 걸음으로 띄우고, 화면 · QA에 「남은 기기가 없을 때는 손님 걸음에 기댄다」(관문의 「끊은 출입증의 읽기 거부」는 B2 출입증까지라는 뜻)를 적는다. T10의 「남은 기기 0」에 어느 쪽으로 확인했는지 적는다.

### 2.5 사고 뒤 되돌리기

설정 서랍 「사고가 났을 때 되돌리기」(또는 서버 탐지 알림) → 서버가 시간대별 숨김 · 올리기 수로 「대량으로 바뀌기 직전」을 기본 시각으로 내놓는다 → 미리 보기는 「그 시각의 완료본: 날짜 · 파일 수」(앱이 숨겨진 판을 읽어 해독한다 — M9) → 방금 한 Google 로그인으로 「되돌리기」 →

1. 서버가 그 손님의 쓰기 출입증을 모두 새로 바꾸고(요청한 기기만 새 것을 받는다), **손님 읽기 출입증도 새로 만든다** — 출입증을 빼앗긴 상황을 전제로 한 흐름이기 때문이다. 요청한 기기가 새 읽기 출입증으로 봉투를 다시 올려 받아 확인하면 서버가 옛 읽기 출입증을 지우고, 앱이 새 복구 코드를 권한다(다시 확인 N1). 이 PC가 감염됐을 수 있으면(같은 사용자 권한의 프로그램은 Google 토큰도 읽는다) 2.4의 Google 걸음(3~5)을 함께 밟는다.
2. 요청한 기기는 엔진 잠금을 쥔 채 기다린다. 쓰는 기기가 하나라 다른 쓰는 쪽이 없다.
3. 서버 도구가 더하는 일을 먼저(pack → 색인 → 판 → 열쇠 · 설정), 숨기는 일을 나중에(판 → 색인 → pack) 한다. 지우는 것은 없다. 도중에 멈춰도 다시 부르면 이어서 한다.
4. 앱이 저장소를 점검하고, **자동 백업과 정리를 멈춘 채** 손님이 파일을 꺼낼 수 있게 한다. 손님이 「여기서부터 계속」(되돌린 상태를 새 기준으로) 또는 「되돌리기 취소」(같은 도구로 되돌리기 직전 시각으로)를 고를 때까지다.
5. 요청과 실행은 그 계정의 모든 기기 알림 + 메일로 알린다.

## 3. 구조와 권한 경계

| 부분 | 하는 일 | 권한 | 떠 있는 때 |
|---|---|---|---|
| 화면 앱 `WorkBackup.exe`(Tauri) | 창, (설정에서 켤 때만) 트레이 | 사용자 보통 권한 | 사용자가 열었을 때만. 창을 닫으면 웹 화면을 내리고, 하던 작업이 끝나면 프로세스도 끝난다 |
| 회차 실행기 `WorkBackupRun.exe --run <계기>` | 백업 · 채움 · 점검 · 정리 · 증명 · 봉투 재확인 · 측정 보내기 · 알림 | 사용자 보통 권한(작업 스케줄러, 로그인한 동안) | 회차 동안만 |
| 도우미 `WorkBackupRun.exe --vss-helper` | 섀도 복사본 만들기 · 연결 · 지우기만(파일을 읽지도 올리지도 않는다) | 같은 사용자의 관리자 권한(관리자 계정일 때만) | 채움 판을 만드는 동안만 |
| 엔진(Node 워커 + restic 0.19.1) | 지금 엔진 + 1단계 고침 | 띄운 쪽의 권한(관리자 쪽에서는 돌지 않는다) | 회차 · 화면 작업 동안 |
| 개통 서버 | 초대 명단 · 출입증 발급과 끊기 · 되살리기 도구 · 저장소 탐지 · 회차 기록 · 메일 | 회사 서버 안 따로 둔 컨테이너 · 실행 사용자 | 늘 |
| B2 손님용 계정 · 버킷 | 손님별 접두사 저장소 | — | — |
| Google 앱 전용 공간 | 봉투(복구 암호 + 읽기 출입증) | 손님 Google 계정 | — |

권한 경계:

- **기기 쓰기 출입증**(쓰는 기기에만, DPAPI): 자기 손님 접두사 안의 목록 · 읽기 · 올리기 · 숨기기. 영구 삭제 · 출입증 만들기 · 버킷 설정은 못 한다. 올리기 권한에는 숨기기 · 같은 이름 덮어쓰기 · 접두사 안 복사가 들어 있으므로 「못 지운다」가 아니라 **「30일 동안 되돌릴 수 있게만 망칠 수 있다」**가 정확한 말이고, 화면 · 문서도 그렇게 쓴다.
- **손님 읽기 출입증**(봉투 · 복구 코드): 목록 · 읽기, 숨겨진 옛 판도 판 번호로 읽는다(M9).
- **서버 출입증 셋**(4.4): 출입증 일(만들기 · 지우기 · 목록)과 파일 일(되살리기 · 저장량 세기 — 삭제 권한 없음)을 서로 다른 출입증 · 프로세스로 나누고, 서버 밖 감사용(목록 · 버킷 설정 읽기만)을 따로 둔다. 출입증 만들기 권한은 B2 문서상 계정 전체 권한과 같다. 복구 암호는 서버에 없으므로 서버는 백업 내용을 읽지 못한다.
- **도우미**: 관리자 권한이지만 파일을 읽거나 올리지 않는다. 사용자 쓰기 폴더에 쓰지 않는다. 보통 권한이 고칠 수 있는 입력은 크기 제한을 둔 자료(볼륨 이름 · 요청 번호)로만 받는다(4.2).

## 4. 항목별 설계

### 4.1 한 줄기 · 엔진 갈래 · 창 닫기 · 잠금 둘 (로드맵 1)

- **Electron 0.5.0 동결.** `experiences/solo-backup/`은 고치지 않는다. 지금 Rust 판은 엔진을 `../solo-backup/src`에서 가져오므로(`scripts/stage-resources.cjs`), 엔진을 `experiences/solo-backup-rust/engine/`으로 **갈라 온다**. 첫 커밋은 `src` · `tests` · `package.json` · lock · 고지문을 바이트 그대로 복사하고 두 쪽 시험 결과가 같은지 보인다(T1 — 0.5.0 쪽 기준선 81개 중 통과 80 · 건너뜀 1, 11-12). 화면 원천도 `experiences/solo-backup-rust/ui/`로 옮긴다.
- **0.5.0 자료와의 관계:** 0.7.0은 0.5.0 저장소 · 봉투 v1을 읽지 않는다. 로드맵 9장의 「0.5.0 사본은 옮겨 오기 시험 재료」는 그 사본을 **읽기 전용 원본 자료**로 시험 저장소에 다시 백업해 쓰는 뜻으로 고쳐 읽는다(0.5.0 사본 자체는 1단계 끝까지 건드리지 않는다).
- **새 상태 폴더:** 설정 · 자격 · 기록은 `%APPDATA%\SynkWorkBackup`, restic 캐시 · 임시는 `%LOCALAPPDATA%\SynkWorkBackup`(100GB 저장소의 캐시가 수백 MB라 Roaming에 두지 않는다). 0.5.0(`SoloWorkBackup`) · 시험판(`SoloWorkBackupRustBeta`)과 따로이며 그 둘을 읽지도 쓰지도 않는다. Windows Run 시작 등록은 쓰지 않는다. 판 이름 0.7.0, 식별자 `im.synk.workbackup`.
- **잠금 둘.** 지금 하나뿐인 `native.lock`을 나눈다.
  - **엔진 잠금**(`engine.lock`) — restic을 돌리거나 설정을 쓰는 쪽이 쥔다. 회차 실행기는 회차 동안, 화면 앱은 작업(지금 백업 · 복구 · 옮겨 오기 · 설정 바꾸기)을 하는 동안만 쥔다. 쥘 때마다 설정을 디스크에서 다시 읽는다.
  - **화면 잠금**(`ui.lock`) — 창 하나만 뜨게 한다.
  - 그래서 회차가 도는 동안에도 앱은 언제나 열린다. 회차 실행기가 남기는 진행 파일(`progress.json`)로 「백업 중 N%」를 보이고, 그동안의 조작은 회차가 끝난 뒤로 미룬다. 화면 앱이 작업으로 엔진 잠금을 쥐고 있으면 회차는 「바쁨(화면 작업)」으로 기록하고 끝난다. 앞 판의 「회차를 화면 앱에 넘김」은 없앤다(응답 없는 창 앞에서 넘김만 쌓이는 문제를 없앤다).
  - 트레이 모드의 Rust 프로세스는 엔진 잠금을 쥐지 않는다. 채움 판을 만드는 동안 엔진 잠금은 회차 실행기가 쥐고, 도우미는 엔진 잠금과 상관없다.
- **창 닫기:** 닫으면 웹 화면을 없애고(WebView2 프로세스 0), 하던 작업이 있으면 화면 없이 마친 뒤 끝난다. 화면 앱 안의 30초 타이머 예약(`startScheduler`)은 끈다. 예약은 작업 스케줄러 하나다.
- **트레이(설정에서 켤 때만):** Rust 프로세스와 아이콘만 남기고 워커는 내린다(목표 30MB 이하, T14에서 잰다). 아이콘을 누르면 워커와 창을 다시 띄운다.

### 4.2 앱과 따로 도는 예약 (로드맵 2)

#### 회차 작업

- 사용자마다 계기별 작업 넷: `\SYNK 업무 백업\회차 - <계정 이름> - <계기> · <SID 짧은 표시>`(매시간 · 로그온 · 깨어남 · 잠금 해제). 작업 하나에 계기 넷을 걸면 동작 인자가 하나뿐이라 회차가 왜 시작됐는지 기록할 수 없어 나눴다(11-12 구현, [결정](../../docs/_ops/결정.md)). 넷이 겹치면 엔진 잠금에서 뒤 것이 「바쁨」으로 끝난다. 보안 주체는 그 사용자(프로세스 토큰의 SID — 환경 변수가 아니다), 「사용자가 로그온한 경우에만 실행」(InteractiveToken), 가장 낮은 권한 수준. 이름의 계정 이름은 토큰 SID로 찾은 이름(`USERNAME`은 비거나 다른 계정에게서 물려받을 수 있다), SID 짧은 표시는 SID의 SHA-256 앞 여섯 자리라 이름이 같은 다른 계정(도메인 · 로컬)과 갈린다. 덮어쓰거나 지우기 전에 작업 스케줄러가 저장한 주체(계정 이름만 남는다 — T2에서 확인)를 SID로 되풀어 내 작업인지 보고, 같은 이름에 다른 계정의 작업이 있으면 다른 자리로 넘어가지 않고 등록을 멈춘다(`SCHEDULE_FOREIGN`). 일부만 되면 원래 있던 작업은 원래 XML로 되돌린다.
- 계기 넷: 로그온(2분 늦춤), 매시간(무기한 반복), 깨어남(System 로그 `Microsoft-Windows-Power-Troubleshooter` 이벤트 1, 2분 늦춤), 세션 잠금 해제. 잠금 해제는 최신 대기(S0) 노트북에서 깨어남 이벤트가 최대 절전 복귀 때만 남는 것을 받친다.
- 설정: 배터리에서도 시작 · 배터리로 바뀌어도 멈추지 않음, 놓친 회차는 가능해지면 바로(StartWhenAvailable), 겹치면 새 것을 버림(IgnoreNew), 우선순위 7(보통 아래). 작업 스케줄러의 실행 시간 제한은 72시간으로 넉넉히 두고, **실행기가 스스로 시간을 재서 restic을 정상 종료**시킨다(강제 종료는 잠금을 남긴다).
- 동작: 설치 폴더 절대 경로의 `WorkBackupRun.exe --run hourly|logon|wake|unlock`.
- 만드는 때: 보호 시작 때 앱(보통 권한)이 작업 스케줄러 COM API로 만든다. 폴더 `\SYNK 업무 백업\`은 설치기(관리자)가 만들고 보통 사용자가 그 안에 자기 작업을 만들 수 있게 폴더 권한을 준다. 앱은 그 폴더를 Administrators나 SYSTEM이 소유할 때만 쓴다 — 표준 사용자가 먼저 같은 이름으로 만든 폴더는 관리자도 넘겨받지 못한다(4.2 「컴퓨터 전체 설치」, 11-13 깨끗한 Windows 실측). 안 되면 뿌리 폴더에 사용자 이름을 붙인 작업으로 한다 — 이벤트 · 로그온 계기를 보통 권한으로 만들 수 있는지와 함께 실측했다(T2, 11-13 CI — 표준 사용자도 뿌리 · 폴더 둘 다 넷을 만들고 다시 읽고 지운다, [QA](QA.md#1단계-잠금-둘--회차-작업-등록--2026-11-13)). 한 자리에 넷이 다 되면 다른 자리의 같은 이름 작업은 지워 두 번 뜨지 않게 한다. 도우미 작업은 사용자가 작업을 만들 수 있는 이 폴더와 다른, 관리자만 쓰는 폴더 `\SYNK 업무 백업 도우미\`에 둔다 — 그 폴더도 표준 사용자가 먼저 만들 수 있으니(관리자는 그 안에 작업을 넣지도 못한다) 도우미 증분(T5)에서 소유자를 확인하고 아닐 때의 자리를 정한다.

#### 회차가 하는 일

1. 엔진 잠금을 잡는다(못 잡으면 「바쁨(화면 작업)」 기록 후 끝).
2. `restic unlock`(오래된 잠금만 — `--remove-all`은 쓰지 않는다). 도중에 죽은 회차가 남긴 잠금은 `check` · `forget`을 종료 11로 막고, restic도 앱도 스스로 치우지 않았다. 11-12 실측 M3b: 백업을 도중에 죽이면 잠금 1개가 남고 `check` 종료 11, 삭제 권한 없는 출입증의 `unlock`이 종료 0으로 그 잠금을 숨기고, 그 뒤 `check` · 백업 모두 0.
3. 쉼 판단: 배터리로 돌고 30% 아래 · 절전 모드 · 종량 회선(Windows 연결 비용이 「무제한」이 아님)이면 클라우드 올리기 · 구조 점검 · 증명을 쉬고 쉼 사유를 기록한다. 직접 누른 「지금 백업」은 예외다.
4. 할 때가 됐나: 마지막 시도가 55분 안이면 「아직」으로 바로 끝난다. 일시정지 · 시계 이상은 지금 규칙(`protection.cjs`) 그대로다.
5. 원본 폴더 확인: 없는 폴더는 그 폴더만 빼고 백업하고(11-14부터 — 그 전에는 하나만 없어도 회차 전체가 실패했다), 그 폴더가 든 마지막 판을 고정하고 알린다(「완료본 · 부분 판 · 채움 판」).
6. 용량 상한: 올리기 전에 원본 크기를 다시 훑는다(진단 계획기를 쓴다). 직전 판의 처리 바이트로만 보면 폴더에 200GB를 넣은 다음 회차가 통과해 전부 올린다.
7. 백업: `restic backup --exclude-cloud-files`(OneDrive 온라인 전용 파일은 읽는 순간 내려받히므로 백업하지 않는다 — 보호 범위 화면에 「OneDrive에만 있는 파일 N개는 OneDrive가 지킵니다」를 보이고, 용량 상한도 디스크에 있는 것만 센다).
8. 결과 나누기: 종료 0 → **온전 판**. 종료 3 → **부분 판** — 못 읽은 목록 U는 restic **표준 오류의 JSON 줄**(`message_type: error`)의 `item` 경로에서 모으고(오류 글은 Windows 언어에 따라 달라 기대지 않는다, 줄 수가 많아도 잘리지 않게 따로 모은다), 실행기가 그 파일을 직접 열어 보아 공유 위반(오류 32 · 33)인지 확인한다. 종료 11 → 「바쁨 — 다음 회차에」(점검 실패로 적지 않는다, 회차에서는 `--retry-lock`을 길게 준다).
9. 부분 판이고 U에 공유 위반 파일이 있으면 도우미에게 섀도 복사본을 부탁해 **채움 판**을 만든다(아래).
10. 점검: 회차마다 `check --with-cache`, 캐시 없는 구조 점검은 하루 한 번, 내용 읽기 점검은 4주에 걸쳐 1/4씩 매주(`--read-data-subset`). 덮어쓰기는 구조 점검에 안 잡히므로(검토 실험) 서버 탐지(4.4)가 하루 안에 잡는다.
11. 정리(아래 「완료본 · 부분 판 · 채움 판」의 규칙과 4.4의 대량 변경 멈춤).
12. 날마다 할 일: 증명(매주), 봉투 재확인(하루), 측정 보내기.
13. 회차 기록 · 진행 파일 · 알림 판단 → 엔진 잠금을 놓고 끝.

실행기 · 워커 · restic은 모두 「보통 아래」 우선순위로 돈다. I/O 우선순위를 더 낮출지는 처음 백업 속도 기준(70%)을 재고 정한다. 로그오프 · 시스템 종료 알림을 받으면 같은 정상 종료 길로 끝낸다. 정상 종료 수단(restic에 중단 신호를 보내는 법)은 구현에서 재고, 안 되더라도 다음 회차의 2번이 받친다.

#### 완료본 · 부분 판 · 채움 판

「최신 완료본 + 24시간」 규칙에서 새 판에 빠진 것은 24시간 뒤 사라진다. 빠지는 길은 셋이다 — 못 읽은 파일, 사라진 원본 폴더, 사용자가 뺀 폴더. 검토 실험대로 **바뀐 뒤 잠긴 파일은 종료 3이고 새 판에 통째로 없다**(바뀌지 않은 잠긴 파일은 열지 않으므로 종료 0, 앞 판 내용이 이어진다). 그래서 이렇게 정한다.

- **판의 종류(꼬리표):** 온전 판(`complete`), 부분 판(`partial` + 못 읽은 목록 U), 채움 판(`fill` + 어느 부분 판을 채우는지). U와 채움 경로 맞추기 정보는 작은 JSON으로 같은 저장소에 함께 넣는다(새 PC에서도 읽힌다).
- **「지금 상태」로 되살리기:** 이 기기의 가장 새 판 S를 기준으로 하고, S가 부분 판이면 U의 파일은 S를 채운 채움 판에서, 없으면 그 파일이 든 가장 새 판에서 가져온다. 화면은 「N개 파일은 [날짜] 판에서 가져옵니다」.
- **먼저 만든 것(11-14 — 「지금 상태」 되살리기):** 전체 되살리기는 폴더마다 그 폴더가 든 가장 새 온전 판, 그보다 새로운 부분 판이 있으면(목록이 하나이고 잘리지 않았고 그 폴더 자체를 못 읽었다고 하지 않을 때) 그 판에서 되살린다 — 정리가 지키는 판과 같은 규칙이고, 온전 판에 없는 폴더는 그 폴더가 든 가장 새 부분 판에서. 되살리는 판이 부분 판이면 그 목록의 파일마다 그 판보다 앞선 판(온전 판 · 목록 있는 부분 판, 새 것부터)에서 처음 나오는 것을 가져오되, 그 자리를 읽을 수 있었는데 없는 판에서 멈추고(그때 이미 지워짐), 앞 판 목록은 필요할 때만 읽으며, 어느 판에도 없으면 `복구경로.json`에 「어느 백업에도 없음」으로 적는다(채움 판은 아직 없다 — 도우미 T5). 정리는 지키는 부분 판의 못 읽은 경로마다 그것을 읽을 수 있었던 가장 새 앞 판을 지킨다(U별 고정, 11-14 — 못 읽은 판은 건너뛰고 목록을 모르는 판은 지키며 지나간다, 어느 판도 못 읽은 파일은 더 지키지 않아 늘 잠긴 파일로 판이 쌓이지 않는다). 목록 판의 내용은 상태 폴더 `lists/`에 캐시한다.
- **정리 규칙(이 기기 판만):** 가장 새 판 하나, 가장 새 온전 판(또는 채움으로 다 채운 부분 판) 하나, 가장 새 판의 U 파일마다 그 파일이 든 가장 새 판, 고정된 판(사라진 폴더 · 뺀 폴더 · 대량 변경 멈춤 · 되돌린 뒤 · 옮겨 오기 원본)은 남기고, 나머지 24시간이 지난 판은 정리한다. 부분 판은 pending으로 쌓이지 않는다 — 가장 새 부분 판 하나만 남긴다. **판을 남기면 그 판에 딸린 채움 판 · meta 판도 함께 남긴다**(다시 확인 N3 — 안 그러면 남긴 부분 판의 U 파일이 사라진다).
- **순서:** U 목록은 백업이 끝나야 안다. meta 판(U · 채움 경로 맞추기)이 저장된 **뒤에만** 부분 판 꼬리표를 붙이고, meta 없는 판은 되살리기 · 정리 계산에 쓰지 않는다(그 사이에 죽으면 「U를 모르는 부분 판」이 남아, 그것으로 되살리면 파일이 말없이 빠진다).
- **한 번도 읽힌 적 없는 파일:** 권한이 거부된 파일처럼 어느 판에도 든 적 없는 파일만 U에 남으면 온전 판이 다시는 안 생겨 옛 온전 판이 영영 고정된다. 그런 U만 남은 판은 「더 채울 것이 없는 판」으로 쳐 온전 판 자리를 잇게 하고, 그 파일은 「읽을 수 없는 파일 N개」로 한 번 알린다. 표준 사용자의 늘 잠긴 파일 알림도 날마다가 아니라 처음과 오래 이어질 때(일주일)만 띄운다.
- **온라인 전용으로 바뀐 파일:** OneDrive가 저절로 비운 파일은 다음 판에서 빠진다. 정책대로 지키지 않되(4.2의 7), 대량 변경 비교는 디스크에 자리표시자가 남아 있는 것을 「지워짐」으로 세지 않는다 — 한꺼번에 비울 때마다 거짓으로 멈추지 않게.
- **사라진 원본 폴더:** 그 폴더만 빼고 백업하고, 그 폴더가 든 마지막 판을 고정하고 「폴더를 찾을 수 없음 → 다시 고르기 · 빼기」를 알린다. 외장 드라이브를 일주일 빼 둬도 그 폴더의 하나뿐인 백업이 사라지지 않는다.
- **먼저 만든 것(11-14 — 사라진 원본 폴더):** 고른 폴더마다 `lstat`이 `ENOENT`일 때만 「없음」(권한 오류 · 파일로 바뀜은 지금처럼 회차를 멈춘다), 있는 폴더만 백업하고 그 판은 온전 판이다(restic 판의 `paths`에는 넘긴 폴더만). 하나도 없으면 실패하고 아무것도 지우지 않는다. 정리는 판들의 `paths`에 나온 폴더 중 가장 새 온전 판에 없는 폴더마다 그 폴더가 든 가장 새 온전 판(그보다 새로운 목록 있는 부분 판과 그 목록도)을 지키고, 폴더가 돌아오면 푼다. 「전체 되살리기」는 가장 새 판에 없는 폴더를 그 판에서 함께 되살리고 `복구경로.json`에 그 판의 시각을 적는다. 알림은 「백업할 폴더를 찾을 수 없습니다 · 확인하기」(`folders` 화면) — 「다시 고르기 · 빼기」는 폴더 바꾸기를 여는 다음 증분과 함께. 파일 골라 되살리기 목록은 아직 가장 새 판 하나만(4.12).
- **폴더 더하기 · 빼기:** 지금 엔진은 설정 뒤 폴더 변경을 막는다(`handlers.cjs`). 1단계에서 연다. 뺄 때는 「이 폴더의 백업은 30일 뒤 지워집니다」를 보이고 그때까지 그 폴더가 든 마지막 판을 고정한다.
- **먼저 만든 것(11-15 — 폴더 더하기 · 빼기):** 엔진 `changeSources` — 더한 폴더는 설정 때와 같은 검사, 이미 고른 폴더와 같은 폴더는 바뀜 없음, 서로 포함되면 거절, 남는 폴더는 1~30개. 뺀 폴더는 설정의 `removedSources`(경로 · 뺀 때)에 남고, 정리가 처음 그것을 본 때(그 정리의 시각 — 클라우드는 서버 시각, PC 시계가 틀린 채 빼도 일찍 지우지 않게)부터 30일 동안 사라진 폴더와 같은 규칙으로 그 폴더가 든 마지막 판을 지킨 뒤 목록에서 빠진다. 다시 더하면 그 줄을 지운다. 사라진 폴더 규칙은 이제 「지금 고른 폴더 또는 30일 안에 뺀 폴더」에만 들고, 그 폴더마다(가장 새 온전 판에 든 폴더도) 되살리기가 쓰는 판 — 그 폴더가 든 가장 새 온전 판과 더 새로운 가장 새 부분 판 — 을 지킨다(끝판 카본 — 그 뒤 판이 모두 부분 판이면 그 폴더의 더 새 내용은 가장 새 것이 아닌 부분 판에만 있다). 전체 되살리기는 뺀 폴더도 그동안 함께 되살리고 `복구경로.json`에 `removedAt`(새 PC의 복구 전용 연결은 뺀 목록을 몰라 사라진 폴더처럼 판의 시각만). 창 앱 메서드 `addSources` · `removeSource`는 대화 상자를 먼저 띄우고 바꿀 때만 엔진 잠금을 잡는다. 화면의 「더하기 · 빼기」 단추와 알림 「다시 고르기 · 빼기」는 화면 구현(4.12) 때.
- **먼저 만든 것(11-14 — 「늦어질 때의 최소」의 ①②):** 종료 3이면 restic 표준 오류의 JSON 줄(`message_type: error`의 `item`)에서 U를 빠짐없이 모으고(20만 개에서 자르고 `cut` 표시), 같은 회차 꼬리표의 **목록 판**(`--stdin`, `workbackup-unreadable.json`)을 먼저 저장한 뒤에야 `pending` → `partial`. 목록이 없거나 못 저장하면 지금처럼 실패하고 판은 `pending`으로 남는다. 부분 판은 `lastBackup`(복구가 쓰는 온전 판)을 바꾸지 않고 `lastPartial`(개수 · 시각)만 남긴다. 정리는 가장 새 온전 판 + 그보다 새로운 가장 새 부분 판과 그 목록 판 하나를 지킨다. 온전 판이 아직 하나도 없으면 첫 부분 판이 온전 판 자리를 잇고(못 읽은 파일은 어차피 어느 판에도 없다 — 「한 번도 읽힌 적 없는 파일」의 가장 좁은 경우, 끝판 카본 A1 · A2), 그 자리가 부분 판인 동안은 그보다 앞선 목록 있는 부분 판도 지킨다(앞 판이 남긴 저장소 — GPT GA1). 알림 「몇 파일을 백업하지 못했습니다」(이전 백업이 지킨다고 말하지 않음). U 파일마다 그 파일이 든 판 고정 · 「지금 상태」 복구 · 채움 · 한 번도 읽힌 적 없는 파일 · 사라진 폴더는 다음 증분.
- **늦어질 때의 최소:** 채움 판 전체가 5주 안에 안 되면 ① 부분 판을 가장 새 것 하나만 남기고 ② 알림을 「몇 파일만 못 지킴」으로 하고 ③ 「파일 되살리기」에서 부분 판을 고를 수 있게 하는 데까지 하고, 그 경우 관문의 「열린 파일」 기준은 못 넘었다고 QA에 적는다.

#### 도우미 — 섀도 복사본만 만든다

검토(F4)가 앞 판의 도우미(관리자 restic이 원본을 직접 읽고 사용자 폴더에 쓰는 꼴)에서 두 통로를 실험으로 보였다. 첫째, 확인과 읽기 사이에 원본 경로의 **중간 폴더**를 연결점으로 바꾸면 restic이 따라가 남의 파일을 백업에 싣는다. 둘째, 관리자 프로세스가 사용자 쓰기 폴더(설정 · 캐시 · 임시)에 쓰면, 그 폴더를 미리 연결점으로 바꿔 관리자 쓰기를 다른 자리로 돌릴 수 있다. 그래서 도우미가 하는 일을 줄인다(검토 권고 A).

- **도우미가 하는 일:** 요청받은 볼륨(고정 로컬 NTFS)의 섀도 복사본을 WMI로 만들고(`Win32_ShadowCopy.Create`), 관리자만 쓰는 작업 폴더(`%ProgramData%\SynkWorkBackup\helper\<사용자 SID>\`, 그 사용자는 읽기 · 지나가기만) 안에 그 복사본을 가리키는 연결을 만들고, 요청한 회차 실행기가 끝나면 연결과 섀도 복사본을 지운다. 파일을 읽지도, 올리지도, 사용자 폴더에 쓰지도 않는다. 관리자 쪽에서 Node · restic을 돌리지 않는다(Rust만).
- **채움은 보통 권한 회차가 한다:** 회차 실행기가 그 연결 아래의 U 파일 경로로 `restic backup`을 돌려 채움 판을 만들고, 연결 접두사를 원래 경로로 되돌리는 맞추기 정보를 함께 넣는다. 섀도 복사본은 파일 권한을 그대로 지키므로 사용자는 원래 읽을 수 있는 것만 읽는다 — 관리자 쪽에 「읽어서 내보내는」 기능이 아예 없다.
- **입력과 확인:** 요청 파일(사용자 상태 폴더의 `vss-request.json`)은 연결점을 따라가지 않게 열어 크기 제한을 두고 자료로만 읽는다 — 볼륨 이름 목록과 요청한 실행기의 프로세스 번호뿐이다. 도우미는 그 프로세스가 설치 폴더의 실행기이고 같은 사용자인지 확인하고, 그 프로세스가 끝나면(또는 상한 시간이 지나면) 정리한다. 하루 만들기 횟수 상한과 「내가 만든 섀도 복사본 번호」는 관리자만 쓰는 폴더에 두고, 도우미가 시작할 때 남은 것을 먼저 지운다.
- **채움의 비용(다시 확인 N4):** 연결 이름은 볼륨마다 **고정**한다(`…\helper\<SID>\snap-C` 같은 꼴). 요청마다 이름이 다르면 restic이 앞 채움 판을 부모로 못 써서, 잠긴 큰 파일(10GB 메일 보관 파일 같은 것)을 매시간 통째로 다시 읽는다. 채움은 하루 6번까지(4시간에 한 번) 하고, 그 사이 회차는 부분 판으로 둔다. `Win32_ShadowCopy.Create`로 만든 것은 다시 켜도 남으므로 지우기(설치 제거)에서 남은 섀도 복사본 · 도우미 폴더를 함께 치운다. 시스템 보호가 꺼진 볼륨에서도 만들어지는지는 T5에서 본다.
- **시작할 때 확인:** ① 자기 실행 파일 · 그 위 폴더(Program Files까지)의 소유자가 관리자 · SYSTEM · TrustedInstaller이고 그 밖의 누구에게도 쓰기 · 고치기 · 지우기 · 권한 바꾸기 · 소유자 바꾸기가 없다 ② 경로를 환경 변수에서 읽지 않는다(실행 파일 위치는 `GetModuleFileName`, Windows 폴더는 API — 작업 스케줄러가 사용자 환경 변수를 물려주므로 예전 SilentCleanup처럼 `%windir%` 바꿔치기를 막는다) ③ 「보통 권한이 만든 연결점은 따라가지 않는다」는 Windows 완화 정책(리디렉션 신뢰)을 켠다.
- **등록:** 설치기(관리자)가 설치 끝에 `WorkBackupRun.exe --register-helper`를 부른다. 관리자 확인을 한 계정이 설치기를 띄운 세션에 로그인한 계정과 같을 때만(설치기 자신의 세션 번호로 찾은 세션 사용자의 SID와 관리자 토큰의 사용자 SID를 견준다 — 콘솔 세션은 원격 접속 · 사용자 전환 중이면 다른 사람일 수 있다) 그 사용자의 도우미 작업을 「가장 높은 수준의 권한으로 실행」 · 계기 없이 만든다. 작업 보안 설명자는 관리자 · SYSTEM 전체, 그 사용자는 읽기 · 실행만이다. 동작은 고정 인자(`--vss-helper`)뿐이고 `$(Arg)` 치환을 쓰지 않는다.
- **표준 사용자:** 다른 사람이 관리자 암호를 넣어 준 표준 사용자에게는 도우미가 없다. 부분 판 규칙으로 지키고, 화면에 「이 계정은 표준 사용자라, 켜진 프로그램이 쥔 파일은 그 프로그램을 닫았을 때 새로 담깁니다」를 적는다.
- **먼저 잴 것(T5):** 보통 권한 프로세스가 도우미가 만든 연결을 지나 섀도 복사본의 파일을 읽을 수 있는지, restic이 그 경로로 채움 판을 만들 수 있는지. 관리자 확인이 켜진 PC에서만 뜻이 있어(CI 실행기는 꺼져 있다) 이 PC 시험 설치를 2주차로 앞당긴다(11장). **안 되면** 검토 권고 B(관리자 restic을 쓰되 원본 폴더 핸들을 쥐어 조상 이름 바꾸기를 막고, 관리자만 쓰는 작업 폴더에 캐시 · 임시를 두고, Node 없이 Rust가 restic을 부르고, 백업까지만 하고 점검 · 승격은 보통 회차가)로 가고 그 까닭을 결정 표에 적는다.
- **먼저 잰 것(11-15 T5 첫 측정 — 권고 A로 간다):** 관리자 확인이 켜진 이 PC에서, 관리자가 만든 복사본 연결(`mklink /d` — PowerShell `New-Item`은 장치 경로를 거절한다)을 지나 보통 권한이 다른 프로그램이 쥔 파일을 원본과 같은 바이트로 읽었고, 보통 권한 restic이 그 경로로 백업했다. 복사본 너머에서도 파일 권한은 그대로이고(보통 권한은 `System Volume Information`을 못 연다), 관리자 폴더에 보통 권한은 못 쓴다. 시스템 보호가 꺼진 볼륨(D:)에서도 복사본이 만들어진다(3.8초). 판의 `paths`는 연결 경로 그대로라 채움 판의 맞추기 정보가 꼭 있어야 하고, 되살리기는 지금처럼 `dump`로 꺼내 자체로 푼다(`restic restore`는 관리자 폴더의 권한을 되살린 폴더에 붙인다). 실측은 [QA](QA.md#1단계-도우미-t5-첫-측정--2026-11-15-권고-a가-된다).
- **기존 섀도 복사본을 잃게 할 수 있다(11-15 T5 첫 시도):** 디스크가 바쁠 때 새 복사본을 만들면 차이 영역이 제때 늘지 못해 Windows가 그 볼륨의 기존 복사본을 모두 버린다(시스템 기록 volsnap 25). 이 PC는 그날 아침 Windows 업데이트가 만든 복원 지점을 그렇게 잃었다. 손님 PC에서 하루 여러 번 만들면 같은 일로 손님의 복원 지점이나 다른 백업 프로그램의 복사본을 잃게 할 수 있다. 그래서 도우미는 디스크가 바쁠 때 만들지 않고, 기존 복사본이 있는 볼륨에서 어떻게 할지(부하가 낮을 때만 만들기 · 그 볼륨은 부분 판으로 두기)는 T5와 72시간 시험에서 재고 정한다. 차이 영역 크기를 바꾸는 것은 시스템 설정이라 하지 않는다.

#### 회차 기록

`runs.jsonl` 한 줄에 계기, 시작 · 끝, 결과(complete · partial · fill · skipped · failed · busy · not-due), 쉼 사유, 종료 코드, 못 읽은 파일 수, 새로 · 바뀐 · 그대로인 파일 수, 더한 바이트, 처리한 바이트, 워커 준비까지 ms, restic 시작까지 ms, 작업 객체의 최대 메모리(`PeakJobMemoryUsed`) · CPU 시간, 측정 판에서는 주고받은 바이트를 적는다. 1MB마다 돌려 쓴다. 파일 이름 · 경로는 넣지 않는다.

주고받은 바이트는 restic에 `HTTPS_PROXY`로 실행기 안의 작은 CONNECT 프록시를 주고 양쪽 바이트만 세어 잰다(TLS는 끝까지 그대로). 측정 판 설정에서만 켠다.

「회차 빠짐」은 PC가 깨어 있고 사용자가 로그인한 시간마다 회차 기록이 하나 이상 있는지로 센다. 잠든 시간은 System 로그에서 S3 대기(Kernel-Power 42 잠들기 · Power-Troubleshooter 1 깨어남)와 최신 대기(Kernel-Power 506 · 507)를 모두 읽어 빼고, 앞 회차가 돌고 있던 시간은 따로 센다. 설치 때 `powercfg /a`의 대기 방식을 측정 항목에 넣는다(이 PC는 S3 대기). Task Scheduler 운영 로그는 켜지 않는다(시스템 설정 변경).

#### 알림

- Windows 알림(토스트). 앱 식별자(AUMID)는 설치기가 시작 메뉴 바로 가기에 붙인다. 문구는 2.2 표.
- 누르면 `synk-workbackup:open?topic=<정해진 낱말>`로 화면 앱이 그 화면을 연다. 주소는 인자 하나 전체를 고정 목록과 정확히 견주고, 주제에는 「기기 끊기 실행」 · 「되돌리기 실행」처럼 한 번 누르면 실행되는 화면을 넣지 않는다(웹 쪽이 그 화면을 띄워 놓고 누르게 만들 수 있다). 배포 판에서는 시험 · 이전 인자(`--test-mode` · `--smoke` · `--migration-preview`)를 컴파일에서 뺀다.
- 같은 문제는 하루 한 번(`notify.json`). 해결되면 그 문제의 기록을 지운다.
- 실측: 보통 권한 회차의 알림이 실제로 떴는지는 `ToastNotificationManager.History`로 우리 앱 알림이 알림 센터에 있는지 읽어 센다. 화면 조작은 하지 않는다(T4).
- 뼈대(11-13, `src-tauri/src/notify.rs`): 주제 낱말은 2.2 표의 할 일에 맞춘 여덟 — `status` · `folders` · `changes` · `devices` · `restore` · `space` · `signin` · `update`. 장부 `notify.json`은 `days`(문제마다 마지막으로 보인 현지 날짜)와 `once`(한 번만 보일 문제)뿐이고, 회차가 판단한 문제 중 없는 것은 해결로 보고 그 날짜를 지운다 — 판단하지 못한 회차는 그대로 둔다. 보이기에 실패한 알림은 표시하지 않아 다음 회차가 다시 해 본다.
- 판단은 회차 실행기가 회차 기록(경로 없음)으로 한다. 워커가 프로필마다 마지막 백업 시각(`lastBackupMs`, 엔진 설정의 `lastBackup.at`)을 결과에 붙인다 — 창에서 한 백업도 들어가므로 회차 기록만 세는 것보다 맞다. ① 새 판이 생긴 회차 → 「첫 백업이 끝남」(한 번) ② 자동으로 도는 프로필 중 마지막 백업이 72시간을 넘은 것 → 「사흘 넘게」. 꺼 둠 · 설정 전 · 읽기 전용 · 잠시 멈춤은 그 사람이 고른 것이라 판단하지 않는다. 원인은 이 회차가 기다린 까닭으로만 쓴다(데이터 요금제 회선 · 배터리 · 시계) — 용량 · 재로그인처럼 까닭을 아직 가르지 못하는 것은 「확인하기」. 프로필 결과 없이 끝난 회차(워커가 못 뜸 · 자원 확인 실패)는 판단하지 못한다. 창의 작업으로 끝난 첫 백업은 창이 숨어 있을 때(트레이)만 화면 앱이 알리고, 열려 있으면 보인 것으로 친다.
- 주소 등록은 Tauri 원본 틀의 딥 링크 칸을 쓴다(`tauri.conf.json` `plugins.deep-link.desktop.schemes` — tauri-cli가 읽고, 딥 링크 플러그인은 링크하지 않는다). 설치 때 `HKLM\SOFTWARE\Classes\synk-workbackup`에 명령 `"<설치 폴더>\WorkBackup.exe" "%1"`을 쓰고, 지울 때는 그 명령이 이 설치의 화면 앱일 때만 지운다. 화면 앱은 정확한 열기 주소 하나만 받아 창을 연다 — 지금 알림은 둘 다 상태 화면(곧 창)이고, 주제마다 다른 화면으로 가는 것은 새 화면(4.12)과 함께 넣는다. 나머지 2.2 알림(부분 판 · 폴더 · 점검 · 증명 · 대량 변경 · 기기 · 용량 · 봉투 · 업데이트)은 그 기능이 들어올 때 같은 장부에 문제 이름을 더한다.

#### 컴퓨터 전체 설치

- Tauri 묶음의 NSIS 설치기를 `perMachine`으로 만든다: `C:\Program Files\SYNK 업무 백업\`(제품 이름 그대로 — 시작 메뉴 · 앱 목록 · 작업 스케줄러 폴더와 같은 이름, 11-13 [결정](../../docs/_ops/결정.md)). 설치 창 쪽은 빼고(진행 창만) 관리자 확인은 한 번이다. 설치 자리는 늘 Program Files이고 `/D=`나 앞 설치 자리를 쓰지 않는다.
- 틀: Tauri CLI 2.12.4의 NSIS 틀을 그대로 두고(`src-tauri/nsis/upstream-installer.nsi`, 해시 고정) 빌드 때 다섯 곳만 정확히 한 번씩 바꾼다(`scripts/nsis-template.cjs`) — 진행 창만, Program Files 고정, **이미 깔린 판 위에는 제자리 갱신**(기본 틀은 판을 올릴 때 옛 판의 지우기를 먼저 돌려 모든 사용자의 회차 작업을 지운다), 바탕 화면 바로 가기 없음, 끝에 앱 열기. 낮춰 깔기는 막는다(`allowDowngrades` 끔). CLI를 올리면 틀을 새로 받아 다섯 곳을 다시 본다.
- 설치 끝 「앱 열기」는 설치기의 관리자 토큰이 아니라 **로그인한 사용자 · 보통 권한으로** 띄운다. 그러지 않으면 다른 사람이 관리자 암호를 넣어 준 PC에서 그 관리자 계정으로 첫 설정이 진행된다. 첫 실행의 계정과 권한 수준을 T5 · T13에서 확인한다.
- 설치기가 하는 일: 파일 복사, 시작 메뉴 바로 가기(AUMID `im.synk.workbackup`), 회차 작업 폴더 `\SYNK 업무 백업`과 그 권한(`WorkBackupRun.exe --install` — 관리자 토큰으로만, T2가 잰 권한 그대로, 설치기가 만든 폴더는 권한을 다시 놓는다). **표준 사용자가 먼저 같은 이름으로 만든 폴더는 넘겨받지 못한다** — 작업 스케줄러가 상승된 관리자에게도 그 폴더의 권한 · 소유자 바꾸기, 폴더 · 그 안 작업 지우기, 작업 넣기를 모두 거절한다(11-13 깨끗한 Windows에서 잼, [QA](QA.md#1단계-컴퓨터-전체-설치기--2026-11-13)). 그래서 회차는 Administrators나 SYSTEM이 소유한 폴더에만 등록하고 아니면 뿌리 폴더에 두며(표준 사용자는 물건의 소유자를 남으로 둘 수 없어 속일 수 없다), `--install`은 그런 폴더를 건드리지 않고 알린다(설치는 계속). 설치 · 지우기 중에는 설치 폴더의 표식(`.installing`, 30분 — 끊긴 설치가 남긴 것은 그 뒤 무시)으로 회차와 화면 앱이 새로 뜨지 않게 하고(자물쇠 · 상태 · 자원에 닿기 전에 끝남), 도는 화면 앱 · 회차의 네 이미지(`WorkBackup.exe` · `WorkBackupRun.exe` · `node.exe` · `restic.exe`)를 Restart Manager 세션 하나로 닫는다 — 설치는 묻지 않고, 닫지 못하면 표식을 먼저 지우고 아무것도 옮기지 않은 채 멈춘다 — 다른 사용자 세션의 프로세스는 닫을 수 없어(사용자를 바꿔 쓰는 PC에서는 그 사람 트레이에 남은 창 앱 때문에 흔하다) 그때는 「다른 사용자가 이 컴퓨터에 로그인해 … 로그아웃한 뒤 다시 해 주세요」라고 알린다. 그 뒤 실행 파일 둘은 덮어쓰지 않고 `.old`로 비켜 두고 새로 쓴다(매핑된 이미지는 이름만 바뀐다). 표식 뒤에 설치가 멈출 수 있는 곳은 틀의 파일 쓰기 오류(우리 밖 프로그램이 설치 파일을 쥔 때)뿐이다. 파일은 건너뛰지 않는다(`AllowSkipFiles off` — NSIS 기본은 건너뛰고, 조용한 설치는 판이 섞인 채 성공으로 끝난다): 물음은 「다시 · 취소」이고 조용한 설치는 곧바로 실패로 끝난다. 그 물음 · 실패 창이 열려 있는 동안에는 회차가 돌지 않는다(실행 파일이 비켜져 있어 표식의 30분과 무관). 창을 닫으면(조용한 설치는 곧바로) 실패 부름이 실행 파일을 되돌리고 표식을 지우지만 이미 쓴 파일은 남아, 다른 판으로 올리다 멈췄으면 다시 설치해야 한다(같은 판 다시 설치면 그대로 돈다). GPT 검수 세 회차가 같은 훅에 P1을 내 설계 관문(Fable 5.2 설계 검토)을 거쳤다. 뒤 증분에서 `synk-workbackup:` 주소 처리기(HKLM, 화면 열기만 — 알림과 함께), 도우미 폴더와 도우미 등록(위 조건 — T5와 함께).
- 지우기: 화면 앱 · 도는 회차를 먼저 닫는다 — 설정 앱에서 지우면 한 번 묻고, 취소하거나 닫지 못하면 아무것도 바뀌기 전에 멈춘다 — 그다음 표식, 그리고 `WorkBackupRun.exe --uninstall`(관리자 토큰으로만)이 이 설치의 회차 실행기를 `--run <계기>`로 부르는 모든 사용자의 회차 작업을 설치기의 폴더와 뿌리 폴더에서 멈추고 지우고(지우지 못한 것은 세고 나머지를 잇는다), 설치기의 폴더가 비면 그 폴더도 지운다 — 다른 것을 부르는 작업은 이름이 같아도 두고, 사용자가 먼저 만든 같은 이름 폴더는 그 사용자의 것으로 둔다. 표식 뒤에는 묻거나 멈추는 걸음이 없다(닫기와 표식 사이에 창 앱이 다시 열리면 틀 자체의 확인이 묻지 않고 닫는다 — 사람은 이미 한 번 동의했다). 그 뒤 파일 · 바로 가기 · 등록 · 표식을 지운다. 뒤 증분에서 주소 처리기와 도우미가 남긴 섀도 복사본 · 도우미 폴더도 지운다. 사용자 상태(`%APPDATA%\SynkWorkBackup`) · 캐시(`%LOCALAPPDATA%\SynkWorkBackup`) · 클라우드 백업은 지우지 않는다(T19).
- 실측: CI `workbackup-clean-windows`(4.11)가 이 원천으로 빌드한 설치기로 조용히 설치 → 파일 해시(창 앱은 Tauri가 묶음 종류를 적어 넣은 판 — 빌드가 같은 세 바이트를 바꿔 영수증에 적는다) · 설치 폴더 권한 · 앱 목록 등록 · 바로 가기와 AUMID · 작업 폴더 소유자와 권한 → 표준 사용자가 그 폴더에 회차 넷을 등록(설치 · 지우기 설정 · 폴더 권한 바꾸기는 거절) → 설치된 `node.exe`로 띄운 프로세스를 둔 채 다시 설치(닫거나, 다른 사용자 것이라 못 닫으면 바뀐 것 없이 멈춤) · 넷이 남음 → 지우기(같은 두 길) 뒤 넷 · 폴더 · 바로 가기 · 등록 · 파일이 사라지고 사용자 상태는 남음 → 표준 사용자가 폴더를 먼저 만든 판으로 한 바퀴 더(그 폴더는 그대로, 회차는 뿌리 폴더, 지우기 뒤 회차만 사라짐)까지 본다([QA](QA.md)). 관리자 확인 창과 첫 실행의 계정 · 권한 수준은 이 PC 시험 설치(T13)에서 본다.

### 4.3 Node 워커 — 재고 나서 옮긴다 (로드맵 3)

- 2주차 첫머리에 같은 합성 자료(D1)로 잰다: 회차 시작(작업 시작 → restic 시작), 회차 최대 메모리(작업 객체 Peak), CPU 시간, 설치 크기. 넘으면 이식이 5주 밖의 일이 되므로 일찍 잰다.
- 비교 기준은 같은 회차를 Rust가 restic을 바로 부르는 시험 실행기(백업 · 구조 점검만)로 돌린 값이다.
- 옮기는 문턱: 회차 시작이 3초를 넘거나, 회차 메모리가 Rust만 쓸 때보다 100MB 넘게 크면 회차가 쓰는 부분(예약 · 백업 · 점검 · 정리 · 증명)부터 Rust로 옮긴다. 옮길 때는 엔진 시험 전부를 Rust 시험으로 옮겨 같은 결과를 내게 한다. 복구 · 검색은 다음 단계다.
- 문턱 안이면 1단계에서는 옮기지 않는다(지금 설치 크기 143MB도 150MB 안이다). 판단과 숫자를 QA에 남긴다.
- **11-12 T7 결과 — Node 그대로**([QA](QA.md#1단계-회차-실행기와-t7--2026-11-12)): 같은 판의 두 번째 회차부터 restic 시작까지 0.27~0.69초, 워커 자체 최대 44~56MB. 빌드 직후 첫 회차만 3.8초였고 새 복사본 재측정으로 새 파일을 처음 열 때 한 번 드는 값(2.2~2.4초)임을 확인해, 시작 문턱은 「같은 판의 두 번째 회차부터」로 잰다. 72시간 예행에서 다시 켠 뒤 첫 회차가 3초를 넘으면 다시 연다.
- 리소스 확인 비용: 지금 `verify_resources`는 리소스 전체(약 143MB)를 해시한다. 매시간 회차마다 하면 회차 시작 3초와 배터리에 든다. 회차 실행기는 자기가 실행하는 파일(node · restic · 워커 · 엔진)만 해시하고 설치 폴더 권한을 확인하는 것으로 갈음할 수 있는지 T7에서 잰다. 전체 확인은 화면 앱 시작 · 업데이트 뒤에 한다.
- 실행기는 워커를 화면 앱과 같은 통신(표준 입출력 프레임)으로 부른다. 옮기게 되면 워커 자리에 Rust 엔진을 끼우면 된다.

11-12 시험 버킷 실측([QA](QA.md#1단계-시험-버킷-실측-m1m7--2026-11-12)): listBuckets가 없으면 버킷 확인이 403이고 restic이 저장소 설정 파일조차 못 읽어 만들 수 없다(그래서 기기 · 읽기 출입증 모두 listBuckets를 둔다). 삭제 권한 없는 출입증의 판 지정 없는 삭제는 204 + 숨김 표시로 끝나고, 판 지정 삭제는 403이다. forget · prune · unlock도 그 출입증으로 끝까지 돌며 영구 삭제는 0건이었다. 그래서 restic S3 통로 그대로 안전망이 된다. 손님 읽기 출입증은 숨겨진 옛 판을 판 번호로 읽는다(S3 `versionId` · 기본 API 둘 다 200, M9). 출입증 이름에 메일 · 사람 이름을 넣지 않는다.

#### 수명 규칙과 버킷 설정 (손님 버킷)

- 접두사 ""(버킷 전체) 규칙 하나: 숨긴 지 30일 뒤 삭제(11-12 유호님 「30일로 넣기」), 올린 뒤 숨기기는 없음, 끝나지 않은 큰 파일은 1일 뒤 취소.
- B2 수명 규칙은 하루 한 번 돈다. 새 판이 올라와 덮인 옛 판도 「숨김」으로 세어 30일 뒤 지운다(공식 문서). 그래서 덮어쓰기 공격도 30일 안에는 되돌릴 수 있다. B2는 겹치는 규칙 가운데 가장 작은 값을 쓰므로, 매일 대조(4.5)가 「규칙이 정확히 이것 하나」인지 본다.
- 올리는 쪽이 올린 시각을 정하는 기능(사용자 지정 올린 시각)은 손님 계정에서 켜지 않는다 — 켜면 쓰기 출입증으로 「T 전」 판을 만들어 되살리기 도구를 속일 수 있다.
- 비용: 숨긴 판은 30일 동안 저장비가 든다. 내부 24시간 정리로 날마다 숨겨지는 양(변경량)이 30일 쌓인다. 72시간 시험과 합성 자료로 「원본 대비 늘어나는 비율」을 재서 QA에 적는다(M5는 합성 자료라 작았다).
- 수명 규칙의 실제 동작(숨김 표시로 숨긴 것 · 덮여서 옛 판이 된 것 · 표시를 지워 되살린 것 · 복사로 되살린 것)은 시험 버킷 `ci/`(숨긴 지 1일 뒤 삭제)에서 보았다(M8, 11-12 설치 → 11-15 확인 끝). 숨긴 것과 덮인 옛 판은 지워지고, 표시를 지워 되살린 것과 복사로 되살린 것은 남는다 — 되살리기 도구는 둘 중 어느 쪽을 써도 된다. 실제 삭제는 규칙 날짜보다 하루 남짓 늦을 수 있다(일찍 지우지는 않는다).

#### 되살리기 도구 — 「이 시각으로 되돌리기」

서버의 파일 프로세스가 그 손님 접두사 안에서만 한다(B2 기본 API). **늘 복사한다 — 도구에는 영구 삭제 호출이 없다**(검토 Q5).

1. 접두사의 모든 판을 읽는다(`b2_list_file_versions`). `locks/`는 계산에서 뺀다.
2. 이름마다 「T 시각의 상태」(T 전 마지막 판이 올리기면 그 판, 숨김이거나 없으면 없음)와 「지금 상태」를 견준다. restic은 `config` 말고는 모든 파일 이름이 내용의 SHA-256이고 B2 서버 안 복사는 SHA-1을 그대로 둔다. 그래서 **같은 이름 · 같은 SHA-1 · 같은 크기는 같은 판**으로 본다(앞서 되살린 복사본), SHA-1이 다르면 덮어쓰기다.
3. T에 있었는데 지금 숨겨졌거나 다른 판이면 → T의 판을 서버 안에서 복사해 새 최신 판으로 만든다(`b2_copy_file`). T에 없었는데 지금 있으면 → 숨긴다(되돌릴 수 있다). 그 밖은 그대로.
4. 차례는 더하기 먼저(data → index → snapshots → keys → config), 숨기기 나중(snapshots → index → data). 도중에 멈춰도 보이는 것이 필요한 것보다 많은 쪽이라 restic이 열 수 있다.
5. 미리 보기와 실행 사이에 판이 바뀔 수 있으니 실행 직전에 목록을 다시 읽어 다시 계획한다. 이미 복사된 것은 2의 규칙으로 건너뛰므로 멈춘 뒤 다시 부르면 이어서 한다.
6. 한 일(복사한 판 · 숨긴 판 · 원래 숨긴 시각)을 서버 기록에 남긴다. 숨김 표시를 지우지 않으므로 「언제 숨겨졌나」가 B2에 그대로 남아 두 번째 되돌리기도 정확하다. 「되돌리기 취소」는 같은 도구를 되돌리기 직전 시각으로 부르는 것이다.
7. T가 29일보다 오래면 거절한다(수명 규칙이 하루 한 번 돌아 30일째 것은 이미 지워졌을 수 있다).
8. 2.5의 순서(쓰기 출입증 교체 → 쓰는 기기 대기 → 도구 → 점검 → 자동 백업 · 정리 멈춤 → 손님 고르기)를 지킨다. 대표가 손으로 하지 않는다. 손님 앱 → 서버 API다.

11-12 실측(M4 · M4b): 같은 출입증으로 전부 forget · prune, 설정 · 열쇠 파일 삭제, pack 덮어쓰기를 해서 저장소를 열 수 없게 만든 뒤, 늘 복사하는 도구가 판 10개를 복사해 7.6초 만에 되돌렸다. 두 판 모두 되살았고 `check --read-data` 0, 손님 읽기 출입증으로 꺼낸 66/66 해시 일치, 바로 다시 계획하면 할 일 0이었다. 복사한 만큼의 저장비는 옛 판이 지워질 때까지(길어야 30일) 두 번 든다 — 100GB면 한 달 1달러 안쪽이다.

#### 저장소가 바뀌었는지 서버가 매일 본다

안전망은 「30일 안에 알아채고 되돌린다」가 전제인데, 같은 이름 · 같은 크기로 pack을 덮어쓰면 구조 점검이 통과하고(검토 실험), 내용 읽기 점검만 잡는다. 그래서 서버의 매일 저장량 세기(어차피 모든 판을 읽는다)에 탐지를 더한다 — 내려받기도 복구 암호도 필요 없다.

- 같은 이름에 올리기 판이 둘 이상인데 SHA-1이 다름(도구의 복사 기록에 없는 것) — restic은 같은 이름을 다른 내용으로 두 번 올리지 않는다.
- `config` · `keys/`가 숨겨지거나 새로 올라옴.
- 하루 숨김 수가 그 기기가 보낸 회차 기록(정리한 판 수)과 안 맞게 큼.
- 걸리면 손님 메일 + 앱 알림 「백업이 바뀌었습니다 — 되돌릴 수 있는 날이 N일 남았습니다」, 운영자 메일. 내용 읽기 점검은 4주에 걸쳐 1/4씩 매주 돌려 따로 받친다.

#### 대량 삭제 · 변경 멈춤 (조사 문서 「다음 3」)

- 정리로 사라질 판 가운데 가장 새 것과 남을 최신 완료본을 `restic diff --json`으로 견준다. 바로 앞 판과 견주면 한 시간치 변화만 보아, 몇 시간에 걸친 암호화 · 삭제를 놓친다.
- 처음 문턱(시험으로 맞춘다): 지워진 파일이 30% 이상이면서 200개 이상, 또는 내용이 바뀐 파일이 50% 이상이면서 200개 이상, 또는 지워진 바이트가 30% 이상이면서 1GB 이상.
- 걸리면 정리를 멈추고 그 판을 번호로 고정한다(사용자가 답할 때까지 끈끈하게). 알림 「많은 파일이 한꺼번에 지워지거나 바뀌었습니다. 확인하기 전까지 이전 판을 지우지 않습니다」 → 화면에서 「내가 한 일이 맞음」 · 「바뀌기 전 판으로 되살리기」.
- 폴더 목록을 바꾼 직후, 기기의 첫 백업, 되돌린 직후는 비교에서 뺀다. 이름 바꾸기 · 폴더 옮기기는 diff에 지움과 더함으로 나와 잘못 걸릴 수 있다 — T17에서 문턱을 맞추고, 「랜섬웨어 감지」라고 부르지 않는다.

### 4.5 Google 로그인 하나로 시작 — 시범 규모 개통 (로드맵 5)

#### 흐름과 인증

앱이 개통 서버에서 한 번 쓰는 nonce를 받는다 → Google 로그인(지금의 PKCE · 데스크톱 클라이언트, 범위 `openid email drive.appdata`, nonce는 서버가 준 것) → ID 토큰을 서버에 보낸다 → 서버가 Google 공개 열쇠로 서명 · 대상 · 발급자 · `email_verified` · **nonce**를 확인한다(데스크톱 클라이언트의 ID는 설치 파일에 있어 「대상 = 우리 클라이언트」만으로는 우리 앱이 받았다는 증명이 안 된다 — nonce가 훔친 ID 토큰의 재사용과 갱신 토큰으로 받은 ID 토큰을 가른다) → 처음이면 초대 명단의 메일과 맞추고 손님을 **Google sub로 묶는다**(그 뒤로는 sub로만 찾고, 같은 메일에 다른 sub가 오면 거절) → 「기기 개통」.

- **개통은 두 걸음:** 서버가 손님 자리(처음이면 손님 번호와 접두사 `c/<무작위 16자>/`)와 기기 쓰기 출입증(+ 처음이면 손님 읽기 출입증)을 만들어 한 번 돌려준다 → 앱이 DPAPI로 보관했다고 알린다. 몇 분 안에 알리지 않은 출입증은 서버가 지운다(서버는 비밀값을 저장하지 않으므로, 응답이 사라지면 주인 없는 출입증이 남고 손님은 하루 상한에 걸린다).
- 앱이 저장소를 만들고(`restic init`), 복구 암호와 읽기 출입증을 봉투에 넣고 다시 내려받아 확인한다 → 예약 등록 → 첫 백업.
- **토큰마다 할 수 있는 일:** 기기 토큰은 측정 보내기 · 상태 읽기와 출입증을 새로 만들지 않는 몇 가지(받았다는 알림 · 확정 · 되돌리기 계획 · 「여기서부터 계속」 · 도움 요청 · 내 기기 목록)까지다 — 정확한 표는 [구현 설계](#server-build)의 「API와 권한 표」. 새 출입증 발급 · 기기 끊기 · 되돌리기는 서버 nonce가 맞는 **방금 한 Google 로그인**을 요구한다.
- **서버 주소는 실행 파일에 박는다.** 사용자가 쓸 수 있는 파일에서 읽으면 바꿔치기한 주소로 ID 토큰이 간다.
- **손님 읽기 출입증은 손님당 하나**다. 둘째 기기는 봉투에서 받는다. 서버가 새로 만드는 때는 분실 신고 · 되돌리기 뒤뿐이고, 그때 봉투 · 복구 코드를 바꾼다(2.4). 지금 `recovery-vault.cjs`의 읽기 출입증 접두사 규칙(`work-backup/<보관함>`)은 새 접두사를 거절하므로 같이 고친다.

#### 제한

- 초대 명단에 넣은 Google 계정에만 개통한다. 명단은 서버 관리 명령으로 넣고, 메일 주소는 저장소에 적지 않는다. 1단계에는 유호님의 시험 계정이, 2단계 노트북 시험(4.14)에는 손님 자리 둘(이 노트북의 계정과 예전 노트북의 계정)이 들어간다. 4주 회차가 끝나면 둘째 손님 자리를 해지하고 손님이 「통째로 받기」로 자료를 남기게 하는데, 그 해지 관리 명령(쓰기 출입증을 지우고 읽기만 남긴 뒤 나중에 지우기)은 2단계 전에 더한다.
- 엔진과 개통 서버는 **Google 계정으로만** 손님을 안다. 1단계에는 SYNK ID 토큰을 엔진에 넘기지 않는다. 솔리오가 SYNK ID를 Google로 로그인해 그 주소를 알면 `hint`로 넘기고, 앱은 그 주소를 Google 로그인 창의 `login_hint`로만 쓴다(4.13 「로그인」). 손님을 묶는 것은 언제나 ID 토큰의 sub다.
- 손님당 **쓰는 기기 1 + 읽기만 하는 기기 2**, 출입증 만들기 하루 5번, 요청 속도 제한.
- 앱: 회차마다 원본 크기를 다시 훑어 상한(시범 100GB)을 막는다(4.2의 6).
- 서버: 접두사별 저장량(보이는 것 · 숨긴 것)을 매일 센다. 상한의 1.5배를 넘으면 그 손님 앱에 「용량 초과」를 알리고 올리기를 멈춘다. 출입증은 끊지 않는다.
- B2 계정 지출 상한(저장 · 내려받기 · 거래)을 콘솔에서 건다(11장). 상한에 닿으면 그 계정 손님 **모두**의 올리기가 멈춘다 — 시범 규모에서는 감수하고, 서버가 하루치 급증을 보면 그 기기 출입증만 끊는 길을 둔다. 올리기 상한은 앱이 지키는 약속이라, 고친 앱이나 빼앗긴 출입증은 무시할 수 있다는 것도 적어 둔다.

#### 계정 분리와 운영 탈취 대비

- 손님 자료는 시험 · 0.5.0과 **다른 B2 계정**에 둔다(가입은 유호님 — 2주차 안에, 11장).
- 개통 서버는 회사 서버의 **같은 compose 프로젝트 안 따로 떨어진 서비스**다. 회사 스택 스크립트가 그 프로젝트를 올리고 내리므로 별도 compose면 장애 조치 · 건강 확인 밖에 놓인다. 자기 이미지 꼬리표(회사 이미지와 따로 올릴 수 있게) · 자기 실행 사용자 · 자기 볼륨 · 자기 비밀값 파일 · Caddy만 닿는 자기 네트워크를 준다. 회사 Caddy에 `/backup-api/` 길 하나를 더한다. HA 조정기 · 백업 스크립트와의 맞물림은 구현 전에 회사 서버 담당 원문으로 확인한다.
- SQLite는 지속 디스크에 두고 회사 백업에 넣는다. 이 DB를 잃으면 「Google 계정 ↔ 접두사」가 사라져 손님이 자기 자리에 다시 개통할 수 없다(봉투로 읽기 복구는 된다). 덤프에는 메일 주소와 토큰 해시가 든다.
- 출입증 일 · 파일 일 프로세스를 나눈다(4.4 표). 되살리기 도구의 버그가 출입증을 건드리지 못한다.
- **매일 대조**(개통 서버 안 + 서버 밖 감사 예약): 서버가 만들지 않은 출입증, 삭제 · 출입증 · 버킷 권한이 있는 출입증(서버 자기 것 제외), 접두사 없는 손님 출입증, 그리고 **버킷 설정** — 수명 규칙이 정확히 기대값 하나인지 · 복제 규칙 · 기본 암호화. 어긋나면 운영자 메일. 대조가 서버 안에서만 돌면 서버가 털렸을 때 대조도 같이 털리므로, 목록 · 설정 읽기만 하는 감사 출입증으로 GitHub Actions 예약 실행에서도 하루 한 번 본다.
- GitHub Actions 비밀값에는 시험 버킷의 쓰기(삭제 없음) · 읽기 출입증과 감사 출입증만 넣는다. 출입증 만들기 권한은 넣지 않는다.
- 서버까지 털렸을 때 쓸 사본은 3단계 전에 정한다. 후보와 한계는 9장 Q10. 2단계부터 남의 실자료가 올라오고 그 관문이 「데이터 사고 0」이므로, 고른 안이 싸면 2단계 시작 전에 켜는 쪽을 유호님께 여쭙는다.

#### 봉투 v3와 Google 프로젝트

- 봉투는 복구 암호 + 그 손님 접두사의 읽기 출입증 + 저장소 위치 · 번호다. 서버가 멈추거나 사업을 접어도 새 PC 복구와 「통째로 받기」가 된다(분실 신고 직후는 예외 — 2.4). 올린 뒤 다시 받아 내용 · 계정 · 해시를 대조하고 하루 한 번 재확인하는 지금 방식을 그대로 쓴다.
- 손님을 받기 전에 백업 전용 Google 프로젝트로 나누고 운영 게시로 바꾼다(「시험 중」이면 갱신 토큰이 7일에 끊겨 하루 재확인이 멈춘다). `drive.appdata`는 민감 범위 검증 대상이 아니다. 운영 게시 때 동의 화면에 홈페이지 · 개인정보 처리방침 주소가 필요한지 콘솔에서 먼저 본다 — 필요하면 「약관 · 개인정보 문구는 요청하실 때」와 부딪혀 유호님 차례가 하나 더 생긴다. 0.3.0 때 계정의 프로젝트 수 한도로 새 프로젝트를 못 만들었으니 안 쓰는 프로젝트 정리나 한도 요청이 들 수 있다. 앱 전용 공간은 프로젝트마다 따로라 새 봉투가 0.5.0 봉투와 섞이지 않는다.
- 갱신 토큰이 7일 뒤에도 사는지는 72시간 시험으로 못 본다 — 「참고」로 2단계에서 본다.

#### 개통 서버 구현 설계(11-16, 개통 서버 세션)

위 절들을 어떻게 만들지 정한 판이다. 11-16 Fable 5.2 설계 검토(P0 0 · P1 5 · P2 11 · P3 6, 판정 「고친 뒤 구현」)를 넣었다. 건마다의 처리는 이 절 끝의 표에 있다. 앱 쪽 API 모양은 옮겨 오기 세션 · 조율 세션과 같이 쓰려고 공유 노트 `서버API.md`에도 같은 내용을 둔다. 둘이 다르면 이 절이 정본이다.

**서비스 셋.** 이미지 하나로 회사 compose 안에 서비스 셋을 띄운다. 서비스마다 실행 사용자(uid)가 다르고, 루트 파일 시스템은 읽기 전용이며, 권한(capability)은 모두 빼고, 비밀값 파일은 그 서비스에만 붙인다.

| 서비스 | 하는 일 | 가진 비밀값 | 닿는 곳 |
|---|---|---|---|
| `workbackup-api` | 손님 앱 요청, Google 토큰 확인, SQLite, 제한, 매일 일 차례, 메일 | 두 일꾼에게 보내는 요청 서명 열쇠 둘, 메일 서명 열쇠 | Caddy(둘만 있는 앞 네트워크), 두 일꾼(뒤 네트워크 둘), Google, 메일 중계 |
| `workbackup-keys` | 출입증 만들기 · 지우기 · 목록, 버킷 설정 읽기 | 출입증 일 출입증 | api가 붙은 뒤 네트워크 하나, B2 |
| `workbackup-files` | 접두사 하나의 판 목록 요약(저장량 · 탐지 · 되돌릴 시각 제안), 되살리기 계획과 실행 | 파일 일 출입증 | api가 붙은 다른 뒤 네트워크, B2 |

- api는 B2 출입증을 하나도 갖지 않는다. 두 일꾼은 서로 닿지 않고 Caddy에도 닿지 않는다.
- api와 Caddy는 둘만 있는 새 네트워크에 둔다. 회사 `edge` 네트워크에는 붙이지 않는다(회사 앱과 api가 Caddy를 거치지 않고 닿게 되고, `edge`는 주소가 셋만 남았다). Caddy는 그 네트워크에서 고정 주소를 받고, api는 그 주소가 보낸 `X-Forwarded-For`만 믿는다. Caddy의 `depends_on`에 api를 넣지 않는다 — api가 고장 나도 회사 사이트는 뜬다. Caddy는 `/backup-api/*`의 본문을 1MB로 막는다.
- api가 일꾼에게 보내는 요청은 요청마다 HMAC-SHA256 서명(일꾼마다 다른 열쇠, 시각 ±60초, 메서드와 본문 해시를 넣음)이 붙는다. 같은 요청 번호는 한 번만 받는다(일꾼 메모리 — 다시 뜨면 잊지만 시각 ±60초가 받친다).
- 출입증 일꾼은 api가 시키는 대로 하지 않고 스스로 막는다. 받는 일은 「쓰기 · 읽기 출입증 만들기(접두사, 이름)」 · 「출입증 지우기(번호 · 이름)」 · 「출입증 목록」 · 「버킷 설정」뿐이다. 권한 목록 · 버킷 · 이름 꼴은 일꾼 코드에 박혀 있고, 접두사는 `c/<소문자 · 숫자 16자>/`만 받는다. 이름이 우리 꼴(`wbw-` · `wbr-` + 20자)이고 접두사가 그 꼴인 출입증만 지운다 — 서버 자기 출입증 · 감사 출입증은 지우지 못한다. 지울 출입증이 이미 없으면 성공으로 답한다. 자기 볼륨에 하루 만들기 횟수를 따로 세어 계정 전체 하루 50개를 넘기지 않는다.
- 파일 일꾼의 출입증에는 삭제 권한이 없다(4.4 표). 파일 일꾼은 (접두사, 시각)만 받고 계획은 자기가 읽은 목록으로 만든다 — api가 준 계획을 실행하지 않는다. 손님마다 하루 되돌리기 실행을 3번까지 자기 볼륨에 센다.
- 그래서 api가 털려도 출입증 일꾼으로는 「손님 접두사 안의 삭제 권한 없는 출입증을 하루 50개까지 만들기」와 「손님 출입증 지우기」밖에 못 하고, 파일 일꾼으로는 「손님을 29일 안의 어느 시각으로 되돌리게(복사 · 숨기기) 하기」밖에 못 한다. 뒤의 것도 30일 안에 알아채지 못하면 손님 자료를 잃는 길이므로, 서버까지 털렸을 때의 사본(Q10)을 2단계 전에 정한다는 4.5의 결정에 이 길을 더해 둔다.
- 출입증 일 출입증의 권한은 writeKeys · listKeys · deleteKeys와 버킷 설정 읽기(listBuckets · readBuckets · readBucketEncryption · readBucketReplications)다. B2 문서(b2_create_key, 11-16 확인)는 새 출입증의 권한이 만드는 출입증의 권한 안이어야 하는지 말하지 않는다. 실측(시험 개통)에서 거절되면 listFiles · readFiles · writeFiles를 더하고(삭제는 여전히 없다) 그 까닭을 이 줄에 적는다.

**요청을 손님마다 한 줄로.** 출입증을 만들거나 지우거나 쓰는 자리를 바꾸는 요청(개통, 받았다는 알림, 쓰는 자리 가져오기, 끊기, 분실 신고, 읽기 출입증 바꾸기 · 확정, 되돌리기 실행 · 고르기)과 10분 정리는 손님마다 한 번에 하나만 돈다. 겹친 요청은 기다리지 않고 `BUSY`로 답한다. api는 프로세스 하나라 프로세스 안 잠금으로 세운다(HA를 다시 켜 api가 두 곳에서 뜰 수 있게 되면 DB 칸으로 옮긴다). DB에도 「손님당 `active` 쓰기 기기 하나」를 부분 고유 색인으로 못 박는다. 출입증을 지울 때는 먼저 `deleting`으로 적고 B2에서 지운 뒤 `deleted`로 적는다. 받았다는 알림은 `pending`인 출입증에만 먹고, 이미 지워졌으면 답의 `acked`에 빠져 앱이 다시 받는다. nonce는 서명 확인이 끝난 뒤 다른 일보다 먼저 `UPDATE … WHERE used_at IS NULL` 한 문장으로 차지한다.

**인증.**

- **Google ID 토큰:** Google JWKS(`Cache-Control`을 따라 캐시, 모르는 열쇠 번호면 다시 받되 1분에 한 번까지)로 RS256 서명을 보고, 발급자 · 대상(설정한 데스크톱 클라이언트) · `azp` · 만료(±60초)를 본다. **발급이 10분보다 오래된 토큰은 거절한다**(「방금 한 로그인」). `email_verified`가 참이어야 하고, `nonce`는 서버가 준 것이어야 하며 목적이 맞고 아직 안 쓴 것이어야 한다.
- **nonce:** 32바이트 무작위, 10분, 한 번. 목적은 요청 이름 그대로다(`provision` · `take-write-seat` · `revoke` · `lost` · `read-key-rotate` · `restore-run` · `restore-undo`). 「읽기 출입증 바꾸기」로 받은 로그인으로 분실 신고를 하지 못한다.
- **기기 토큰:** 개통 때 서버가 32바이트를 만들어 한 번 준다. 서버는 SHA-256만 저장한다. 앱은 DPAPI로 둔다. 4.5 「토큰마다 할 수 있는 일」의 「측정 보내기 · 상태 읽기까지만」을 아래 표로 넓혀 정한다 — 더한 것은 「받았다는 알림 · 확정(그 출입증을 받은 기기만) · 되돌리기 계획 · 「여기서부터 계속」(요청한 기기만) · 도움 요청 · 내 기기 목록」이고, 모두 출입증을 새로 만들거나 손님 자료를 숨기지 않는다.
- **손님 묶기:** 처음에는 초대 명단의 메일(소문자로 맞춤)과 견주고 Google sub로 묶는다. 그 뒤로는 sub로만 찾는다. 같은 메일에 다른 sub가 오면 거절한다(`SUB_MISMATCH`).

**API와 권한 표.** 주소는 `https://workspace.synk.im/backup-api/v1/`이고 앱 실행 파일(설치 폴더의 엔진 원천)에 박는다. 요청과 답은 JSON이고, 요청 본문은 64KB(측정은 1MB)까지다. 기기 토큰은 `Authorization: Bearer`, 방금 한 로그인은 본문의 `google: {idToken, nonce}`다. 실패는 `{ok:false, code}`이고 코드는 `NOT_INVITED` · `SUB_MISMATCH` · `NONCE` · `TOKEN` · `DEVICE` · `DEVICE_STATE` · `LIMIT_DEVICES` · `LIMIT_KEYS_DAY` · `RATE` · `BUSY` · `TOO_OLD` · `BAD_INPUT` · `NOT_FOUND` · `SERVER`다. 모든 답에 `Cache-Control: no-store`를 붙인다. 「상태」 칸에 없는 상태의 기기 토큰은 `DEVICE_STATE`(그 상태를 함께 싣는다)로 거절한다.

**여러 걸음 요청과 하루 상한.**

- 하루 상한은 출입증 수가 아니라 「출입증을 만드는 요청」의 수로 센다. 손님마다 24시간에 5번이고, 요청이 출입증을 하나라도 만든 뒤에 센다. 분실 신고와 그 뒤의 첫 읽기 출입증 바꾸기, 되돌리기 실행은 사고 대응이라 이 상한에 넣지 않는다(출입증 일꾼의 계정 하루 50개는 그대로 받친다).
- 상한은 옛 출입증을 지우기 전에 본다. `take-write-seat` · `restore/run`은 옛 쓰기 출입증을 먼저 지우고 쓰는 자리를 이 기기로 적은 뒤 새 것을 만든다. 새 것 만들기에서 실패하면 그 기기는 「쓰기 출입증 없는 쓰는 기기」로 남고, 같은 요청을 다시 부르면 지울 것이 없으므로 쓰는 자리를 그대로 두고 새 것만 만든다. 그래서 어느 걸음에서 멈춰도 다시 부르면 이어진다. 응답이 사라져 10분 정리가 새 쓰기 출입증을 지운 경우도 같은 요청(「다시 받기」)으로 이어진다.

**기기와 역할.** 기기의 역할은 쓰기 · 읽기만 둘이고, 상태는 `active` · `moved` · `revoked` · `lost` · `abandoned`(받았다는 알림 없이 끝난 개통)다. 손님당 `active` 쓰기 기기는 하나, 읽기만 하는 기기는 둘까지다. 쓰는 자리는 `take-write-seat` · `restore/run`으로만 옮긴다. 옮겨진 기기(`moved`)에는 사흘 메일을 보내지 않고, 상태에 「[기기 이름]으로 옮겨졌습니다」를 실어 회차를 쉬게 한다(4.6 N2). 같은 PC를 다시 깔아 기기 토큰을 잃으면 개통이 새 기기를 만든다. 죽은 기기로 셋이 차면 `LIMIT_DEVICES` 답의 기기 목록을 보고 로그인만으로 쓰는 기기가 아닌 죽은 기기를 끊는다. 새 기기 개통 · 쓰는 자리 옮김 · 되돌리기 요청은 다른 기기의 다음 상태 읽기에 알림거리로 싣고 손님 메일을 보낸다(4.8).

**두 걸음 발급.** 출입증을 만들기 전에 `keys` 표에 이름과 `creating`을 적고, B2가 만들면 `pending`으로 적고 답한다. 앱이 `keys/ack`를 보내면 쓰기 출입증은 `active`, 읽기 출입증은 `acked`(봉투를 올린 뒤 `confirm`으로 `active`)가 된다. 10분 안에 알림이 없거나 B2의 답을 못 받은 출입증(`creating`)은 1분마다 도는 정리가 지운다(이름으로 찾아 지운다). 처음 개통에서 모든 출입증이 그렇게 지워진 기기는 `abandoned`가 된다. 그래서 응답이 사라져도 주인 없는 출입증이 남지 않는다.

**손님 읽기 출입증.** 손님마다 「확정 하나 + 미확정 하나」까지만 둔다. 새로 만들면 앞선 미확정 것을 지우고, `confirm`이 앞선 확정 것을 지운다. 분실 신고는 확정 · 미확정을 모두 지우고 새 것을 만들지 않는다 — 손님 읽기 출입증이 없는 동안 봉투 · 복구 코드는 못 쓴다(2.4의 2). 되돌리기는 옛 확정 출입증을 바로 지우지 않고 새 것의 `confirm` 때 지운다 — 새 봉투가 올라가기 전에 손님이 봉투를 잃지 않게. 미확정 출입증이 있으면 상태에 `unconfirmed`로 싣고 앱의 하루 봉투 재확인이 올리기와 `confirm`을 다시 한다. 7일 넘게 미확정이면 운영자에게 알린다. 분실 뒤 Google 걸음(`googleStepRequired`, 2.4의 5 (나))은 `confirm` 때만 끄고, 개통 · 바꾸기 답과 상태에 싣는다.

**되돌리기.**

- `restore/run`을 받으면 그 손님의 쓰기 출입증을 모두 지우고, 요청한 기기를 쓰는 기기로 적고(옛 쓰는 기기는 `moved`), 새 쓰기 출입증과 새 읽기 출입증을 준다. 읽기만 하던 기기가 요청하면 그것이 곧 쓰는 자리 옮김이다. 겹친 `restore/run`은 `BUSY`이고, 되돌리기 중에도 `lost` · `revoke`는 된다.
- B2는 지운 출입증을 잠깐 더 받으므로(11-13 실측 몇 초 — S17의 M10에서 다시 잰다) 출입증을 지운 뒤 60초 기다렸다가 도구를 돌린다. 파일 일꾼은 도구를 돌리기 직전에 읽은 목록의 가장 늦은 올린 시각(B2 시계)을 「직전 시각」으로 `restore_jobs`에 적는다. 다 하고 나면 목록을 다시 읽어 다시 계획하고, 할 일이 남았으면 3바퀴까지 더 돈다.
- 끝나면 상태의 `restore.awaitingChoice`가 참이 되고, 앱은 모든 기기에서 자동 백업 · 정리를 멈춘다. 요청한 기기는 `restore/run`을 부르기 전에 이 PC에 끈끈한 멈춤 표시를 쓰고 `choose`가 성공해야 지운다 — 서버가 닿지 않아도 되살린 옛 판이 24시간 규칙으로 정리되지 않게.
- 「여기서부터 계속」은 요청한 기기만 한다. 「되돌리기 취소」는 같은 도구를 「직전 시각」으로 부르고, 끝나면 고르기 없이 `continued`가 된다.
- api가 되돌리기 도중 다시 뜨면 `running` 작업을 다시 계획해 잇는다(도구는 다시 불러도 이어서 한다 — 4.4의 5). 복사는 같은 차례 묶음 안에서 넷씩 함께 돌린다. 결제 수단이 없는 지금 손님 계정은 거래가 하루 2,500건이라 그보다 큰 되돌리기는 하루에 끝나지 않는다 — 2단계에서 결제 수단을 붙일 때 풀린다.

**탐지 규칙(매일).** 파일 일꾼이 접두사의 모든 판을 한 번 읽어 저장량과 함께 낸다. 규칙은 「지금 남아 있는 판」이 아니라 「일어난 일」로 쓴다 — 일의 시각(다른 내용 판의 올린 시각, 숨김 표시의 시각)이 손님의 **기준 시각**보다 뒤일 때만 건다. 기준 시각은 마지막으로 끝난 되돌리기의 고른 때다. 그래서 되돌린 다음 날부터 옛 사고는 다시 걸리지 않고, 되돌린 뒤의 새 공격은 걸린다.

- 같은 이름에 SHA-1이 서로 다른 올리기 판이 둘 이상이다 → 「덮어쓰기」(`config`면 「설정 바뀜」, `keys/`면 「열쇠 바뀜」). SHA-1이 40자 16진이 아닌 판은 「다름」으로 본다. 복사로 되살린 판은 옛 SHA-1 그대로라 걸리지 않는다. `locks/`는 뺀다.
- `config` · `keys/`에 숨김 표시가 있다 → 「설정 바뀜」 · 「열쇠 바뀜」. 맨 처음 올린 열쇠 파일보다 하루 넘게 뒤에 새 이름의 열쇠 파일이 올라왔다 → 「열쇠 바뀜」.
- 보이는 `snapshots/` 수가 0이 됐다(전날 1개 이상) → 「숨김 급증」. 측정과 상관없이 보는 규칙이다. 엔진의 정리는 늘 가장 새 판을 남기므로 0은 정상에서 나오지 않는다. 「전날의 절반 아래」는 쓰지 않는다 — 주말 동안 꺼 둔 PC가 켜진 날 첫 회차의 정리가 하루치 시간별 판을 한꺼번에 숨겨 정상에서도 걸린다(11-16 시험에서 찾음). 그래서 「가장 새 판 하나만 남기고 숨기기」는 아래 측정 규칙이 받친다 — 측정을 꾸며 보내면 이 하나는 피할 수 있지만, 남은 판이 쓰는 `data/`를 숨기면 `data/` 규칙에 걸린다.
- 그 기간 숨긴 `snapshots/` 파일 수가 그 기간 쓰는 기기였던 모든 기기가 보낸 회차 기록의 `prunedSnapshots`(숨긴 `snapshots/` 파일 수) 합보다 5개 넘게 많다 → 「숨김 급증」. 측정으로 인정하는 수는 「전날 보이던 판 수 − 1」을 넘지 못한다(기기 토큰을 가진 쪽이 큰 수를 보내 피하지 못하게). 그 기간의 회차 기록이 하나도 안 왔으면 이 규칙은 7일까지 미루고 운영자에게만 「측정 없음」을 알린다.
- 그 기간 숨긴 `data/` 바이트가 1GB 이상이면서 (보이는 바이트 + 그 숨긴 바이트)의 절반을 넘는다 → 「숨김 급증」. 그 기간 회차 기록에 「손님이 대량 변경을 확인함」(`massChangeConfirmed`)이 있으면 건너뛴다.
- 걸리면 알림거리(「백업이 바뀌었습니다 — 되돌릴 수 있는 날이 N일 남았습니다」, N = 29 − 가장 이른 걸린 일이 지난 날)와 손님 메일, 운영자 메일을 낸다. 같은 일(판 번호)은 한 번만 알린다.
- **되돌릴 시각 제안:** 기준 시각 뒤의 걸린 일 가운데 가장 이른 것의 1초 전을 첫 후보로 내고, 지난 29일의 시간별 숨김 수에서 「20개 이상이면서 그 기간 시간당 중앙값의 5배 이상」인 몰림의 첫 숨김 1초 전을 함께 낸다. 미리 보기(그 시각의 완료본 날짜 · 파일 수)로 손님이 고른다.

**저장량과 용량.** 보이는 바이트 · 개수(마지막 판이 올리기인 이름), 숨긴 바이트 · 개수(나머지 올리기 판), 보이는 `snapshots/` 수를 손님마다 매일 `usage_daily`에 적는다. 보이는 바이트가 상한(원본 100GB)의 1.5배를 넘으면 상태의 `overQuota`를 켜고 앱이 올리기를 멈춘다. 출입증은 끊지 않는다. 그동안에도 정리는 돌고, 원본이 앱 상한(100GB) 아래로 줄면 앱은 백업을 다시 한다. 서버 표시는 다음 매일 세기에서 1.5배 아래로 내려가면 꺼진다. 하루에 보이는 바이트와 숨긴 바이트의 합이 200GB 넘게 늘면 운영자 메일을 보내고, 그 기기 출입증만 끊는 관리 명령(`admin.mjs cut-device`)을 둔다 — 첫 백업이 하루 100GB일 수 있어 저절로 끊지는 않는다.

**매일 대조.** 서버 안에서는 출입증 일꾼의 목록 · 버킷 설정을 `keys` 표와 견준다. 서버 밖에서는 `server/audit.mjs`를 GitHub Actions 예약(`workbackup-audit.yml`, 하루 한 번)이 감사 출입증으로 돌린다. 둘 다 같은 판정 함수(`server/reconcile.mjs`)를 쓰고, 계정 · 버킷 · 기대 규칙을 설정으로 받는다.

- 출입증: 아는 서버 출입증(출입증 일 · 파일 일 · 감사 — 번호를 설정으로 받는다) 밖의 출입증 가운데 이름이 `wbw-` · `wbr-` 꼴이 아니거나, 접두사가 `c/<16자>/` 꼴이 아니거나, 버킷이 손님 버킷 하나가 아니거나, 권한이 기기 쓰기 권한보다 넓거나, 만료가 있는 것. 접두사 하나에 `wbw-`가 둘 이상이거나 `wbr-`가 셋 이상인 것(표 없이도 본다). 서버 안 대조는 여기에 「표에 없는 출입증」, 「지웠다고 적었는데 남은 출입증」, 「표에는 있는데 B2에 없는 출입증」을 더하고, B2의 답을 못 받아 `creating`으로 남은 이름의 출입증은 지운다.
- 버킷: 버킷이 하나 · 비공개 · 기본 암호화 SSE-B2 · 수명 규칙이 정확히 기대값 하나 · 복제 규칙 없음.
- 서버 밖 감사는 모든 오류를 잡아 정해진 낱말과 HTTP 상태만 찍는다(B2 오류 글에는 이름이 들 수 있다). 개수와 어긋난 종류만 찍고 출입증 번호 · 버킷 이름을 찍지 않는다. 어긋나면 그 실행이 실패하고 GitHub가 저장소 주인에게 메일을 보낸다. 감사가 아예 안 도는 것은 서버 안 매일 일이 GitHub 공개 API로 「마지막 성공한 감사가 36시간 안인가」를 보고 아니면 운영자에게 알린다.
- T11의 「모르는 출입증 · 삭제 권한 출입증을 일부러 만들기」는 시험 개통 자리에서 임시 관리 출입증으로 만들어 두 대조가 잡는지 보고 바로 지운다. 「수명 규칙 바꿈」은 손님 버킷에서 바꾸지 않고 대역 시험으로만 본다.
- 「사용자 지정 올린 시각」은 계정 설정이라 API로 읽을 수 없다. 켜지 않는다는 것만 적어 둔다(4.4).

**측정 받기(4.9의 받는 쪽).** 보내는 쪽은 조율 세션이 만든다. 받는 꼴은 이렇다.

- 회차: `trigger`(hourly · logon · wake · unlock · manual · window) · `startedAt` · `durationMs` · `result`(complete · partial · fill · skipped · failed · busy · not-due · paused) · `pause`(battery · saver · metered · clock · user · none) · `exitCode` · `unreadable` · `files{new,changed,unmodified}` · `bytes{added,processed}` · `peakMemory` · `cpuMs` · `workerReadyMs` · `resticStartMs` · `fill{tried,result}` · `proof{checked,damaged,changedSource,noSample}` · `prunedSnapshots`(그 회차가 숨긴 `snapshots/` 파일 수) · `massChangeConfirmed` · `transferred{up,down}`.
- 알림: `kind` · `shownAt` · `clickedAt`. 설치 단계: `step` · `durationMs` · `ok`. `kind`와 `step`은 닫힌 낱말 목록(`server/telemetry.mjs`의 `NOTICE_KINDS` · `INSTALL_STEPS`, 공유 노트에 사본)에 있는 것만 받는다 — 「소문자 · 숫자 · -」 꼴만 보면 폴더 이름도 그 꼴이라 샌다. 환경: `appVersion` · `windows`(빌드 번호 꼴) · `standby`(S3 · S0 · unknown).
- 글자 값은 정해진 낱말과 판 번호 꼴만 받는다. 그 밖의 글자 값이 든 항목은 버리고, 모르는 칸은 저장하지 않고 센다. 그래서 파일 이름 · 경로가 실수로 실려도 DB에 남지 않는다(T25). 도움 요청 묶음도 같은 검사를 거친 칸만 저장하고 메일에 싣는다.
- 한 번에 회차 200개까지, 7일 안의 것만 받는다. 같은 (기기, 시작 시각, 계기)는 한 번만 저장하므로 다시 보낸 묶음이 `prunedSnapshots`를 두 번 더하지 않는다. 90일 뒤 지운다.

**메일.** PULSE 중계와 같은 꼴의 업무 백업 중계(`server/mail-relay/`, founder@synk.im 소유 Apps Script)에 api가 자기 RSA 열쇠로 서명해 보낸다. 같은 열쇠의 메일은 한 번만 간다.

- 받는 사람은 그 손님 메일과 운영자 주소뿐이고, 중계도 따로 막는다 — 중계의 스크립트 속성 `ALLOW_SHA256`(받을 수 있는 주소의 SHA-256 목록)에 없는 주소로는 보내지 않는다. 그래서 api의 서명 열쇠를 가진 쪽도 founder@synk.im 이름으로 아무에게나 보내지 못한다. 2단계는 유호님 노트북 시험이라 목록은 유호님 주소와 운영자 주소다.
- 보내는 이름 · 회신 주소 · 문구를 유호님이 고르시기 전에는 보내기를 끈다. 그동안 생긴 메일은 `held`로 남고 켠 뒤에도 보내지 않는다 — 켠 뒤에 생긴 것만 간다. 문구를 고르시면 그 문구를 중계 안 틀(틀 번호 + 숫자 · 기기 이름만 받음)로 옮겨 중계를 다시 배포한다. 시험은 유호님 주소로만 한다.
- 사흘 메일은 서버가 지금 멈춰 있거나 지난 2시간 안에 10분 넘게 멈췄을 때만 미룬다(서버가 1분마다 남기는 심장 박동으로 본다). 측정은 7일까지 모았다가 오므로 지난 멈춤은 「소식 없음」의 원인이 아니다.

**DB.** SQLite 하나(`node:sqlite`, WAL)를 api 볼륨에 둔다. 표는 5.3에 `key_requests`(하루 상한) · `alerts` · `outbox`(보낼 메일) · `heartbeat` · `detect_seen` · `help`를 더한다. `keys`의 상태는 `creating` · `pending` · `acked` · `active` · `retired` · `deleting` · `deleted`, `restore_jobs`에는 「직전 시각」 · 바퀴 수를 더한다. 매일 `VACUUM INTO`로 백업 폴더에 사본을 만들고, 그 폴더를 회사 백업에 어떻게 실을지는 반영 묶음을 만들 때 회사 서버 원문으로 확인해 이 절에 적는다.

**봉투 v3의 꼴(5.4 보완).** 5.4의 칸에 Drive 기록 맞추기에 쓰는 칸(`generationId` · `generation` · `subject` · `bucketId` · `resticVersion`)을 더한다. 앱 전용 공간의 표시(`appProperties.app`)는 `synk-workbackup-recovery-v3`이라 v1과 섞이지 않는다. 읽기 출입증은 이름 접두사가 정확히 `c/<번호>/`이고 권한이 읽기뿐이며 만료가 없어야 한다.

**휴대폰 분실 신고 쪽 — 1단계 범위에서 뺀다.** 1단계에서는 다른 PC의 앱이나 새 PC의 앱에서 신고한다. PC가 한 대뿐인 손님이 그 PC를 잃으면 새 PC를 마련할 때까지 앱으로는 신고할 길이 없다. 그동안은 운영자 명령(`admin.mjs lost <기기>`)으로 대신하고, 화면 글에 「다른 PC가 없으면 SYNK에 연락해 주세요」를 적는다. T10의 「남은 기기 0」은 이 길과 새 PC의 신고로 판정한다. 메일 링크로 여는 웹 쪽은 Google 프로젝트에 웹 클라이언트를 더할 때(유호님 손 묶음) 만들고, 서버는 그때 대상 클라이언트 목록에 그 번호를 더한다.

**먼저 잴 것(M10).** 출입증을 지운 뒤에도 미리 받은 B2 인증 토큰과 올리기 주소가 통하는지 재지 않았다. 시험 개통 자리에서 인증 토큰과 올리기 주소를 받고 → 출입증을 지우고 → 10초 · 1분 · 10분 뒤에 숨기기 · 올리기 · 내려받기를 해 본다. 통하면 분실 신고의 「즉시」와 T10의 「옛 출입증 거부」를 그 시간만큼 고쳐 적고, 되돌리기 전 기다림도 그만큼 늘린다.

**만드는 파일.** `server/`의 `main.mjs`(진입) · `boot.mjs` · `server.mjs`(api) · `google-token.mjs` · `store.mjs` · `keys-worker.mjs` · `files-worker.mjs` · `rpc.mjs`(서명 요청) · `detect.mjs` · `reconcile.mjs` · `jobs.mjs` · `mail.mjs` · `telemetry.mjs` · `admin.mjs` · `audit.mjs` · `config.mjs`(설정 파일 · 비밀값 폴더) · `Dockerfile` · `README.md`(회사 서버에 두는 법) · `mail-relay/` · `tests/`. 회사 `deploy/compose.yaml`에는 서비스 셋을 `workbackup` 프로필로 꺼진 채 넣고, `deploy/Caddyfile`에는 `/backup-api/*` 길을 연다. 프로필을 켜는 일은 회사 HA의 컨테이너 검사를 함께 고치는 인프라 판으로 한다(README). 앱 쪽은 `engine/src/provision-client.cjs`(새 파일)와 `recovery-auth.cjs`(서버 nonce로 로그인 · 토큰 철회) · `recovery-http.cjs`(서버 주소) · `recovery-vault.cjs`(봉투 v3 · 새 읽기 출입증 규칙) · `recovery-service.cjs`(v3 올리기 · 읽기 출입증 바꾸기). 엔진에 잇는 것(`b2.cjs`의 새 접두사 꼴, 호스트 = 기기 번호, `handlers.cjs` · `methods.json` · `bridge.js`)은 조율 세션에 보낸다. 기기 쓰기 출입증은 지금 DPAPI 통로(`secret.encrypt`)로 보관하므로 `secret.rs`는 바꾸지 않는다.

### 4.6 새 PC로 옮겨 오기 v1 (로드맵 6)

#### 기존 경계를 바꾸는 일 — 따로 짚는다

지금(0.5.0 · Rust 시험판)은 원래 작업 폴더와 백업 저장소를 복구 대상으로 고를 수 없고, 늘 새 하위 폴더(`01-폴더이름`)에 쓴다. 1단계에서 바꾸는 것: **「옮겨 오기」 흐름에서만** 원래 자리에 쓴다(검토 Q1: 조건을 달아 받아들임). 지키는 것은 이렇다.

- **덮어쓰지 않는다 — 수단까지 못 박는다.** Node `fs.rename` · Rust `std::fs::rename` · 엔진 `atomic()`은 Windows에서 있는 파일을 덮는다(검토 실험). 그래서 임시 이름에 쓴 뒤 Rust 호스트 호출로 `MoveFileExW`를 **바꾸기 없이**(`MOVEFILE_REPLACE_EXISTING` 없이) 부른다. 「이미 있음」으로 실패하면 그때 견준다 — 크기 · 시각이 같으면 「이미 있음」, 다르면 내려받아 SHA-256으로 견주고 같으면 「이미 있음」, 다르면 `이름 (복구본).확장자`(있으면 `(복구본 2)` …)로 같은 방식으로 겹치지 않게 둔다. 폴더는 만들기만 한다.
- **OneDrive 안이면:** 온라인 전용 자리표시자는 내용을 읽지 않고(읽으면 내려받는다) 크기 · 시각으로만 견준다. OneDrive 동기화가 그 폴더를 받는 중이면(우리가 「없음」을 본 뒤 OneDrive가 같은 이름을 내려놓을 수 있다) 「OneDrive 밖 새 폴더」를 기본으로 둔다.
- **자동 실행 자리는 원래 자리로 되돌리지 않는다.** 시작프로그램 폴더 · 셸 프로필(PowerShell 프로필 폴더 등) · 그 밖에 로그인 때 저절로 실행되는 자리는 따로 둔 폴더로 되살린다. 옛 PC가 감염돼 있었을 때 백업이 새 PC에 실행 파일을 심는 길을 막는다.
- **연결점 · 특수 이름은 건너뛰고 센다.** 지금 전체 복구는 목록에 파일 · 폴더가 아닌 것이 하나라도 있으면 쓰기 전에 멈춘다(`restore-tar.cjs`). 그런데 Windows는 모든 프로필의 문서 폴더에 연결점(「My Music」 등)을 두고, restic은 그것을 링크로 기록한다(검토 실험, 이 PC 문서 폴더 맨 위 연결점 4개). 옮겨 오기 · 전체 복구는 링크 · 특수 노드 · 안전하지 않은 이름(끝이 점 · 공백, 예약어)을 건너뛰고 결과 화면에 「건너뜀 N개」와 목록을 보인다. 백업 쪽은 지금처럼 링크로 기록하고 따라가지 않는다.
- **장부와 이어받기:** 쓴 파일마다 「되살림 · 대조 통과」를 장부(`migration/<번호>.jsonl`)에 적고, 그것을 이어받기 상태로도 쓴다 — 끊긴 뒤 다시 시작하면 장부에 있는 파일은 크기 · 시각이 그대로일 때 건너뛴다. 전원이 연결돼 있으면 옮겨 오기 동안 절전을 막는다. 앱은 원래 자리의 파일을 지우는 기능을 갖지 않는다.
- 평소 「파일 되살리기」(골라 복구 · 전체 복구)는 지금처럼 새 폴더로만 쓴다. 백업 중인 기기 자신에서는 이 흐름을 열지 않는다.

#### 쓰는 기기는 한 번에 하나

- 한 저장소를 여러 기기가 쓰면, 엔진의 「최신 완료본」 고르기가 기기를 안 가리고(`retain` · `probeBody` · `restoreLatest` · `openFileCatalog`, 그리고 새로 만들 증명 v2 · 대량 변경 비교 — 다섯 자리), 점검 · 정리의 배타 잠금이 서로의 회차를 종료 11로 실패시킨다(검토 실험). 그래서 1단계는 **손님 저장소에 쓰는 기기는 한 번에 하나**로 못 박는다.
- 새 기기가 이어서 백업을 시작하는 순간이 옛 기기 쓰기 출입증을 끊는 순간이다(서버가 한 요청 안에서 한다). 「옛 PC 연결 끊기」에서 '아니오'면 새 기기는 되살리기까지만 한다.
- **자리를 넘겨준 옛 PC(다시 확인 N2):** 끊긴 뒤에도 옛 PC를 한동안 같이 쓰는 일은 흔하다. 그대로 두면 옛 PC가 인증 오류 → 「다시 로그인」 → 새 출입증을 받아 쓰는 자리를 도로 가져가고 새 PC가 말없이 멈춘다. 그래서 ① 끊긴 PC는 「이 PC의 백업은 [기기 이름]으로 옮겨졌습니다 — 여기서 고친 파일은 백업되지 않습니다」 상태로 서고 회차는 쉰다 ② 서버는 그 기기에 사흘 메일을 보내지 않는다 ③ 쓰는 자리를 가져오는 것은 그 뜻을 적은 단추(「이 PC로 다시 백업」)와 다른 기기 알림으로만 한다.
- 그래도 모든 판 고르기에 「호스트 = 이 기기」 조건을 넣는다. 옮겨 오기만 원본 기기를 명시한다. restic 호스트 이름은 **기기 번호**다(지금은 보관함 번호).
- 새 PC는 같은 저장소에 이어서 백업한다. 되살린 파일과 내용이 같아 첫 백업에 올라갈 것이 거의 없다(중복 제거 — T16에서 「더한 바이트」로 잰다).

#### 다른 기기 판의 정리

다른 기기의 판은 다음일 때만 정리 대상이 된다 — **이 기기의 옮겨 오기 장부가 그 판의 모든 파일을 되살려 대조까지 통과했거나, 사용자가 화면에서 「나머지는 필요 없음」을 눌렀을 때**. 분실 신고 · 「끊김」만으로는 정리하지 않는다(그 판이 그 자료의 하나뿐인 사본일 수 있다 — 늘어나는 용량은 서버가 세어 알린다). 유예 30일은 그 조건이 찬 때부터 센다. 정리하는 주체는 그 판을 옮겨 받은 기기 하나다. 서버가 알려 준 「끊김」만 믿지 않고 로컬 장부의 판 번호와 함께 본다. 건너뛴 것(연결점 · 특수 이름 · OneDrive가 되살리는 폴더)이 있으면 자동 조건은 차지 않고 손님 단추로만 풀리므로, 옮겨 오기 결과 화면에 「옛 PC 판이 남아 있는 까닭」을 보인다. 엔진 정리 규칙 변경이라 GPT 2차 검수를 받는다.

#### 자리 맞추기 · OneDrive

- 백업할 때마다 그 PC의 알려진 폴더 위치(문서 · 바탕화면 · 사진 · 음악 · 동영상 · 다운로드, OneDrive로 옮겨졌는지)를 작은 JSON으로 함께 넣는다(`새-PC-준비.json`과 같은 길).
- 새 PC에서: 옛 알려진 폴더 아래 경로 → 새 PC의 같은 알려진 폴더(`SHGetKnownFolderPath` — OneDrive로 옮겨졌으면 그 자리). 옛 사용자 프로필 아래 다른 경로 → 새 프로필 아래 같은 상대 경로(자동 실행 자리는 위 규칙대로 뺀다). 그 밖(D 드라이브 프로젝트 폴더 등) → 같은 드라이브가 있으면 같은 경로, 없으면 사용자가 고른다.
- OneDrive 기본값(검토 Q2): 옛 PC의 그 폴더가 OneDrive 안이었고 새 PC도 같은 OneDrive면 그 폴더는 OneDrive가 되살리므로 우리는 「없는 파일만 채우기」 또는 건너뛰기. 옛 PC는 로컬이었고 새 PC가 OneDrive면 「OneDrive 밖 새 폴더」가 기본이다. 남은 공간은 로컬에서 읽을 수 없다(11-12 이 PC에서 OneDrive 계정 레지스트리 · 설정 파일에는 용량 알림을 띄운 시각만 있었다). 그래서 되살릴 용량과 함께 「OneDrive 남은 공간을 넘으면 동기화가 멈출 수 있습니다」라고 적는다(유료 1TB 손님도 있어 「무료 5GB」라고 쓰지 않는다).
- 기다림: 내려받을 양 ÷ 지난 회차에서 잰 회선 속도로 「약 N분」을 따로 보인다(50GB · 100Mbps면 이론상 약 67분).

#### 다시 깔 것 · 다시 로그인할 곳 · 옛 PC 끊기

- 진단(inventory)이 찾은 프로그램 목록을 보여 주고, winget에 있는 것은 이름 · 명령까지 보인다. 설치는 하지 않는다(4단계).
- 다시 로그인할 곳은 진단이 찾은 앱 종류에서 만든 고정 체크리스트다(브라우저 · 메신저 · 클라우드 드라이브 · AI 도구 · 공동인증서 안내). 설문을 하면 그 결과로 2단계 전에 고친다.
- 옮겨 오기가 끝나고 대조가 통과하면 「옛 PC 연결 끊기」(기본 예) → 이 PC가 쓰는 기기가 되고 옛 기기 쓰기 출입증이 지워진다(T16에서 옛 출입증의 거부까지 본다).

### 4.7 되살리기 증명 v2 (로드맵 7)

- 매주 이 기기의 최신 판에서 백업한 폴더마다 무작위 파일을 고른다(합 64MiB 안, 폴더마다 적어도 하나, 큰 파일은 건너뜀). 폴더에 고를 파일이 없으면 「표본 없음」으로 따로 센다.
- `restic dump`로 받아 메모리에서 SHA-256만 계산한다. 평문을 디스크에 쓰지 않는다(지금 표본과 같은 원칙).
- 원본 대조: 원본 파일의 크기와 수정 시각이 그 판의 기록과 같으면 원본을 읽어 SHA-256을 견준다. 바뀐 파일은 「원본이 바뀌어 대조 못 함」으로 따로 센다.
- 결과를 둘로 나눈다(검토 F19): **dump 실패 · 크기 불일치 → 손상**(그날 알림 + 정리 보류, 지금 `probeHold`). **dump 성공 + 원본과 다름 → 「원본이 시각을 그대로 둔 채 바뀜」** — restic은 크기 · 시각이 같으면 다시 읽지 않으므로 그 파일의 백업이 낡은 것이다. 손상으로 세지 않고, 다음 회차에서 그 파일을 다시 읽게 한다.
- 화면 첫 줄의 「증명 날짜」는 마지막 통과 날짜다.
- 일부러 깨뜨린 저장소 시험: 시험 저장소의 pack 하나를 바꿔치기해 증명 · 서버 탐지 · 매주 1/4 내용 읽기 가운데 무엇이 먼저 찾는지 본다(T15, 「손님보다 먼저 찾아낸 비율」의 시작 값).

### 4.8 분실 · 탈취 (로드맵 8)

- **두 번째 복구 수단 「복구 코드」:** 저장소 위치 · 번호, 복구 암호, 손님 읽기 출입증을 담은 한 장이다. 앱 창에서 바로 인쇄하거나 고른 자리(USB)에 바로 쓴다 — 임시 HTML을 기본 브라우저로 여는 길은 복구 암호가 디스크 · 브라우저 기록에 남으므로 쓰지 않는다. 백업 폴더 · OneDrive 폴더 안에는 저장하지 못하게 하는 0.5.0 규칙(복구 키는 작업 폴더와 떨어진 곳)을 잇는다. 첫 주 안에 한 번 권하고 건너뛸 수 있다. 새 PC의 「복구 코드로 되살리기」에서 파일을 열거나 글을 붙여 넣으면 Google 없이 된다.
- **분실 신고:** 2.4의 순서. 옛 쓰기 · 읽기 출입증은 신고 즉시 지운다(끊으려고 누른 것이다). 그 뒤 새 기기를 이을 때까지 서버가 필요하다는 것, 옛 복구 코드는 못 쓴다는 것을 화면과 문서에 적는다.
- **새 기기 개통 · 되돌리기 요청 · (3단계) 해지 요청:** 기존 기기에 알리고(다음 회차 알림) 메일을 보낸다. 해지는 재확인 없이 지우지 않는다. 1단계에는 3단계가 쓸 틀만 둔다.

### 4.9 시범 측정 통로 (로드맵 9)

- **모으는 것:** 회차 기록(5.5의 칸), 알림 표시 · 누름(종류 · 시각), 설치 단계(단계 · 걸린 시간 · 성공), Windows 판 · 대기 방식. 기기 이름은 「내 기기」 목록에만 쓰고 측정에는 넣지 않는다. 파일 이름 · 경로 · 폴더 이름 · 내용은 보내지 않는다.
- **새지 않는다는 시험:** 합성 자료의 파일 · 폴더 이름에 표식 글자를 넣고, 측정 · 도움 요청 묶음과 서버 DB에 그 글자가 없는지 본다(T25).
- **보내는 때:** 회차 끝에 기기 토큰으로 보낸다. 못 보내면 7일까지 모았다가 보낸다.
- **시험 기기를 쓰는 사람에게(2단계는 유호님):** 첫 화면 아래 한 줄 「시범 동안 백업 결과 숫자(파일 이름 없이)를 SYNK로 보냅니다」.
- **도움 요청:** 앱 안 단추 → 보낼 내용(판 · Windows 판 · 최근 회차 50줄 · 오류 번호 · 경로 없는 설정 요약)을 먼저 보이고 → 손님 글과 함께 서버로 보낸다. 엔진의 마지막 오류 글은 넣지 않는다(restic 표준 오류에는 파일 경로가 있다). 답은 Claude가 쓰고, 시범 동안은 유호님이 확인한 뒤 보낸다(2단계 운영).

### 4.10 설치 프로그램과 자동 업데이트 (로드맵 10)

- 4.2의 NSIS perMachine 설치기 하나다.
- **Tauri 업데이터:** 업데이트 묶음을 Tauri 자체 서명 열쇠로 서명하고, 앱에 박은 공개 열쇠로 검증한다. OS 코드 서명과는 따로다.
- **업데이트 자리:** 공개 저장소의 GitHub Releases에는 두지 않는다(저장소가 비공개로 돌아가면 끊긴다). 설치 파일을 받는 곳과 같은 곳(회사 서버의 정적 경로 또는 synk.im 내려받기 쪽)에 두고, 기존 PC 앱 피드의 방식을 따른다.
- **자동 갱신의 첫 후보는 판마다 폴더(11-13 설치기 설계 관문의 대안 D, Fable 5.2 검토):** 4.2의 제자리 덮어쓰기는 갱신이 돌던 백업 · 복구를 묻지 않고 끊고(일꾼이 실행기보다 먼저 닫히면 그 회차가 「실패」로 적힐 수 있다 — 알림 증분에서 본다), 파일 쓰기 도중 멈추면 판이 섞이고, 다른 사용자 세션에 창 앱이 있으면 멈춘다. 판마다 폴더 + 고정 실행기는 셋을 다 없앤다.
- **코드 서명을 넣으면** 번들러가 서명하는 것은 묶음 종류 글자를 바꾼 창 앱이므로, 영수증의 창 앱 해시는 그때부터 설치기에서 꺼낸 파일로 적는다(지금은 `build.ps1`이 같은 세 바이트를 바꿔 적고 CI가 설치된 파일과 대조한다).
- **관리자 확인을 받아들인다(검토 Q6).** 컴퓨터 전체 설치라 업데이트 설치에도 관리자 확인이 뜬다. 권한 있는 업데이트 도우미는 도우미와 같은 종류의 통로를 하나 더 여는 일이라 1단계에서 만들지 않는다. 설치는 엔진 잠금을 쥐고 한다(회차 도중에 실행 파일을 바꾸지 않는다). 표준 사용자 계정에서는 「업데이트 준비됨」을 날마다 띄우지 않고 「관리자에게 부탁하기」 문구로 일주일에 한 번 띄운다. 서버가 「이 판 아래는 더 못 씀」을 말할 수 있게 한다(측정에 판이 온다) — 도우미 같은 권한 코드의 고침이 깔리지 않은 채 남지 않게.
- **열쇠 보관:** 만들 때 암호를 걸고, 이 PC의 열쇠 층(`SYNK_보안`)에 둔다. 그 층은 [복원 체계](../../docs/컴퓨터를%20잃어버렸을%20때.md)가 암호문으로 비공개 저장소와 Drive에 올린다. 공개 저장소 · Actions 비밀값에는 넣지 않는다(서명은 이 PC에서만). 열쇠를 잃으면 이미 깔린 판을 갱신할 수 없으므로(Tauri 문서), 만든 날 복원 시험 도구로 암호문에서 되살려 보는 것까지 한다(T19).

### 4.11 깨끗한 Windows 자동 연습 (로드맵 11)

- 작업 흐름: `.github/workflows/workbackup-clean-windows.yml`. 계기는 손으로(workflow_dispatch), 이 두 폴더를 바꾼 push, 매주다. [관문 · 자동화 한 장](../../docs/_ops/관문_자동화.md)에 같은 커밋으로 적는다. 저장소가 크므로 필요한 폴더만 성기게 받는다(sparse checkout, blob 거르기).
- **두 갈래(검토 F18):** push마다는 실행기 안의 판 관리가 되는 S3 대역(MinIO 판 관리 켬)으로 엔진 · 설치 · 옮겨 오기 흐름을 돌린다. 실제 B2는 매주 · 손으로 돌릴 때만, CI 자료 D0(약 100MB)로 시험 버킷 `ci/`에 한다. B2 무료 한도의 셈: 저장 10GB(실측 `t/` 약 0.3GB · 72시간 D1 1.5GB + 변경 · CI 주 0.2GB · 속도 측정 D2 3GB가 `ci/`에서 8일 뒤 치워짐), 내려받기는 월 평균 저장량의 3배까지 무료다. 결제 수단 없는 계정이 한도를 넘으면 어떻게 되는지는 확인하지 않았으므로 넘기지 않게 위 셈을 지킨다.
- **1번 실행기:** 빌드(restic은 공식 판을 받아 고정 해시 대조) → 설치(관리자, 조용히) → 합성 자료 → 작업 스케줄러로 회차 한 번 → 잠긴 파일 시험(파일을 독점으로 연 채 회차 → 부분 판 → 채움 판) → 해시 목록을 산출물로 올린다(합성 자료뿐이라 공개돼도 된다).
- **2번 실행기(깨끗한 새 VM):** 설치 → 「옮겨 오기」를 복구 코드 길로(Google 없음) → 원래 자리와 새 폴더 둘 다 → 해시 전수 대조.
- **3번:** 표준 사용자 계정을 만들어 그 사용자 작업(암호 로그온 — DPAPI가 돌아야 하므로)으로 회차를 돌려 VSS 없는 길과 도우미 없음을 확인한다.
- **공개 로그:** restic은 저장소 주소(버킷 이름 · 접두사)를 출력에 찍는다. 공개 저장소의 Actions 로그는 누구나 보므로 주소 · 버킷 이름도 비밀값으로 넣어 가리고(11-12 넣음), 엔진 오류 글(restic 표준 오류)을 로그에 그대로 내지 않는다. 복구 암호 · 출입증은 산출물 · 로그에 남기지 않는다.
- 포크에서 온 PR에는 비밀값이 가지 않으므로 PR에서는 빌드 · 단위 시험만 돈다. `pull_request_target`으로 바꾸지 않는다.
- **못 재는 것:** 실행기는 Windows Server · 관리자 · 관리자 확인 꺼짐이라 관리자 확인 창 · Smart App Control · OneDrive 폴더 이동 · Google 동의 · 알림 표시 · **도우미의 권한 경계**가 재현되지 않는다. 그래서 이 PC 시험 설치를 2주차로 앞당겨 거기서 잰다(T5 · T13 · T14). 실행기에서 「로그온한 경우에만」 작업이 도는지는 첫 실행에서 확인하고, 안 돌면 CI에서만 암호 로그온으로 돌린다.
- **화면 시험:** 화면 조작(컴퓨터 유즈) 대신 tauri-driver(WebView2 + msedgedriver)로 웹 화면 안쪽 흐름만 본다. 서버 · Google은 시험 대역으로 둔다.
- 3연속 통과(실제 B2 갈래)가 관문이다.
- **이 PC 측정:** D1로 메모리 · CPU · 증분 시간 · 회차당 주고받는 양, D2로 처음 백업 속도를 잰다. 휴대폰 핫스팟일 때는 큰 올리기를 미룬다.

### 4.12 화면 다시 (로드맵 12)

- 뼈대부터 다시 짠다: [디자인 참고 장부](../../docs/디자인/참고사이트/README.md)(마지막 크롤링 11-10 뒤 것만 새로) · 참고 카드(11-11 「포인트 색 한 자리」 — 보안 제품 예시 포함) → 시안 둘(정적 HTML, 1440 · 390) → 유호님이 고른다 → Claude가 Tauri 화면으로 옮긴다 → 카본 + Fable 검수. **2주차부터 나란히 한다** — 5주차 한 주에 시안 · 고르기 · 구현 · 검수를 넣으면 기각될 때 물러설 자리가 없다.
- **시안 고르기는 끝났다(11-13).** 유호님이 시안 A 「확인서」로 정하셨다. A는 26화면이고 카본과 Fable 5.2 검수를 반영했다([시안 README](ui-mockups/README.md) · [결정](../../docs/_ops/결정.md)).
- **보이는 법은 검정 클라이언트 말씨다(11-16).** 같은 날 정해진 SYNK 플랫폼 PC 클라이언트 방향(검정 바탕, 구 하나, 흰 종이와 펠트 물건을 거둠)과 A의 흰 종이가 어긋나, 두 판을 실제 창 크기로 견줘 보여 드렸고 유호님이 「검정으로 옮기기」라고 하셨다. A의 문구 · 흐름 · 숫자는 그대로 두고, 종이 · 도장 · 회색 책상만 걷었다. 물건은 왼쪽 위의 작은 구 하나이고 창이 열릴 때 켜지며 회차가 도는 동안 빛줄기가 돈다. 상태 색은 상태 한 줄 앞의 점 하나에만 둔다([결정](../../docs/_ops/결정.md) 11-16 「업무 백업 엔진 창 · 검정 클라이언트 말씨로」).
- **Tauri 화면은 [`ui/`](ui/)다(11-16).** 엔진 상태 → 화면 모델(`screen-model.js`, 엔진의 단계 · 오류 글을 그대로 옮기지 않는다) → 그리기(`screen-view.js`, 순수 함수) → 입구(`app.js`)로 나눴다. `scripts/stage-ui.cjs`가 0.5.0 화면 대신 이 폴더를 `dist/`로 옮기며 CSP · 금지 항목 · 글꼴 지문을 본다. 엔진 · 서버에 아직 없는 화면(옮겨 오기 1~4 · 사고 되돌리기 · 분실 신고 · 복구 코드 · 보호 범위 · 지워진 목록)은 예시 상태로 그리고 단추는 「아직 준비 중」 한 줄만 띄운다. 실제 상태로 도는 것과 예시로 그린 것의 표는 [QA](QA.md)의 「1단계 화면 — 검정 말씨로 Tauri에 옮김」 절이다.
- 한 화면에 「안전함 · 마지막 확인 · 증명 날짜」, 「파일 되살리기」, 「새 PC로 옮겨 오기」와 그 증거(확인서의 줄)만 둔다. 나머지(폴더 · 외장 드라이브 · 도우미 상태 · 복구 코드 · 내 기기 · 사고 되돌리기 · 트레이 · 측정 안내 · 업데이트)는 설정 서랍에 넣는다.
- 1단계에 새로 생기는 화면: 첫 시작 둘(Google로 시작 · 보호 범위 확인 — OneDrive 줄 포함), 회차 진행 보기, 부분 보호 안내(몇 파일은 어느 판으로 지키는지), 폴더를 찾을 수 없음, 옮겨 오기 넷(자리 고르기 · 진행 · 결과 · 다시 깔 것), 사고 되돌리기 셋(시각 · 미리 보기 · 되돌린 뒤 고르기), 분실 신고 단계, 복구 코드 인쇄, 기기 끊기 확인 웹 쪽, 알림 문구.
- 화면 글 검사: 기본 화면에 restic · 스냅샷 · 버킷 · 출입증 · 저장소 · pack · prune 같은 말이 나오면 시험이 실패한다. 목록은 `ui/banned-words.js` 하나이고, 화면 모델의 모든 상태(`tests/ui-words.test.cjs`), 화면 원천의 손님이 보는 글, Playwright 캡처(`test-support/ui-shots.cjs`), 실제 창의 tauri-driver 시험(`test-support/ui-driver.cjs`)이 같은 목록으로 본다. 엔진 쪽 네이티브 대화창 글은 화면이 고칠 수 없어 엔진 담당에 넘겼다(QA 같은 절).

### 4.13 솔리오에 잇기 (로드맵 13)

로드맵의 [솔리오와의 관계](ROADMAP.md#solio-relation)와 [플랫폼 화면의 솔리오](ROADMAP.md#solio-platform)를 따른다. 손님의 입구는 솔리오 「백업·복구」 탭이고, 엔진은 솔리오가 받아 깔고 부르는 따로 된 프로그램이다. 솔리오 화면(`desktop/` · `experiences/synk-account/`)은 GPT 솔리오 세션이 고친다. 이 절은 엔진 쪽 계약만 정하고, 화면 쪽에 넘길 것은 끝에 모은다. 11-16 Fable 5.2 설계 검토(24건)를 반영한 판이다(9장 반영표).

#### 처음 시작 — 솔리오에서

엔진이 없는 PC에서 솔리오 「백업·복구」 탭은 단추 둘을 보인다. 처음 보호하는 PC는 「보호 시작」, 새 PC는 「이 PC로 옮겨 오기」다(옮겨 오기는 4.6). 아래 표는 「보호 시작」의 길이다.

| 차례 | 사람이 하는 것 | 전체 누름 | 앱 안 누름 |
|---|---|---|---|
| 1 | 솔리오 「백업·복구」 탭에서 「보호 시작」. 솔리오가 엔진 설치 파일을 받아 크기 · SHA-256 · 서명을 확인한다 | 1 | 1 |
| 2 | 관리자 확인 「예」. 설치 창 없이 깔고, 끝나면 엔진이 로그인한 사용자의 보통 권한으로 Google 로그인을 바로 연다 | 1 | |
| 3 | 브라우저에서 계정 고르기와 「계속」 | 2 | |
| 4 | 엔진 창의 보호 범위 확인 「보호 시작」. 2.1의 6번과 같다 | 1 | 1 |
| | 합 | 5 | 2 |

- 관문 1의 「사람 한 번」은 11-15부터 이 표의 길로 센다(로드맵 관문 1). 2.1 표는 엔진 설치 파일을 직접 여는 길로 남는다. 솔리오 설치 자체의 누름은 플랫폼 PC 앱의 몫이라 이 표에 넣지 않는다.
- SmartScreen 두 번이 빠지는지는 확인 필요다. 브라우저나 Electron의 내려받기 길로 받으면 「인터넷에서 받은 파일」 표시가 붙을 수 있고, 그러면 SmartScreen 두 번이 남아 전체 누름이 7번이 된다. 그래서 솔리오는 PC 앱 본체 프로세스가 HTTPS로 직접 받아 자기 폴더에 쓴다(Chromium 내려받기를 쓰지 않는다). 표시가 붙는지, SmartScreen이 뜨는지는 2주차 이 PC 시험 설치와 2단계 노트북에서 센다(T30).
- 받은 설치 파일은 쓰기 · 지우기 공유 없이 연 핸들을 쥔 채로 크기 · SHA-256(피드 목록과 견줌) · 자체 서명(업데이터와 같은 열쇠, 4.10)을 확인하고, 그 핸들을 쥔 채로 실행한다. 확인과 실행 사이에 같은 사용자의 다른 프로그램이 파일을 바꿔치기하지 못하게 하려는 것이다. 하나라도 틀리면 열지 않고 「다시 받기」를 보인다. Smart App Control이 켜진 PC는 2.1과 같이 따로 센다.
- 엔진은 깔려 있는데 이 사용자의 상태 파일이 없으면(같은 PC의 다른 Windows 계정) 솔리오는 설치 파일을 다시 열지 않고 `setup` 요청만 남긴 뒤 엔진 창을 연다.
- 2번에서 엔진 창의 「Google로 시작」(2.1의 4번)을 누르지 않게 한다. 손님은 솔리오에서 이미 단추를 눌렀기 때문이다. 솔리오가 설치 파일을 열기 전에 `setup` 요청(아래)을 남기고, 설치기가 끝에 엔진을 열면 엔진이 그 요청을 읽어 Google 로그인으로 바로 간다. 요청이 없거나 만료됐으면 2.1처럼 「Google로 시작」 화면을 보인다.

#### 로그인 — 두 번 하지 않게

- 솔리오는 SYNK 계정(SYNK ID — Google 또는 이메일)으로 로그인한다. 엔진은 복구 봉투를 손님의 Google 앱 전용 공간에 두므로 Google 동의가 꼭 든다(4.5). 둘을 하나로 합치지 않고, 사람 쪽에서 두 번째 로그인이 되지 않게만 한다.
- 솔리오가 SYNK ID를 Google로 로그인했고 그 Google 주소를 알 때만, 그 주소를 `setup` 요청의 `hint`로 넘긴다. 엔진은 Google 요청에 `login_hint`로 붙인다. PC 앱은 기본 브라우저로 로그인하므로(`desktop/AUTH.md`), 브라우저에 그 계정이 로그인돼 있으면 계정 고르기와 「계속」만 남는다(위 표의 3번). 브라우저의 Google 로그인이 끊겼으면 Google이 암호를 다시 묻고, 그만큼 누름이 늘어난다.
- 이메일로 로그인한 손님은 Google 로그인이 한 번 더 든다. 화면에 「복구 정보는 손님의 Google 계정에 보관합니다. 우리 서버가 멈춰도 되살릴 수 있게 하려는 것입니다」 한 줄을 둔다. 관문 1의 사람 한 번은 Google로 로그인한 손님으로 센다(2.1의 5번과 같은 처리).
- 1단계에서는 SYNK ID의 토큰을 엔진에 넘기지 않는다. 엔진과 개통 서버는 Google 계정으로만 손님을 안다(4.5의 초대 명단). 넘기지 않는 까닭은 둘이다. 엔진의 상태 폴더에 비밀값이 하나 더 쌓이고, 솔리오 로그인이 바뀔 때마다 엔진도 따라 바뀌어야 한다. SYNK 계정과 백업 손님을 잇는 일(결제 · 해지)은 3단계 가입 · 결제와 함께 정한다.
- `hint`는 비밀값이 아니다. 엔진은 254자 이하이고 @가 하나인 주소 꼴만 받고, 다르면 버린다.

#### 상태 파일 — 솔리오가 읽는 것

- 자리: `%APPDATA%\SynkWorkBackup\solio\status.json`(5.1의 사용자 상태 폴더 안).
- 쓰는 쪽: 회차 실행기와 화면 앱이 회차와 작업이 끝날 때마다 쓴다. 같은 폴더의 임시 이름에 쓴 뒤 바꿔 넣어, 읽는 쪽이 반쪽 파일을 보지 않게 한다. 64KB를 넘지 않는다.
- 담는 것(꼴 번호 `v: 1`): 엔진 판, 보호 상태 낱말 하나(`safe` · `attention` · `paused` · `not-set-up` · `moved` · `restore-only` 따위 고정 목록 — `restore-only`는 옮겨 오기만 하고 「옛 PC 연결 끊기 — 아니오」를 고른, 쓰는 기기가 아닌 PC다), 마지막으로 백업을 확인한 시각, 마지막 되살리기 증명 날짜와 결과, 주의 주제 낱말 목록(4.2 「알림」의 여덟 낱말과 같은 목록), 지금 도는 작업의 단계 낱말과 진행 백분율, 보호 중인 폴더 수와 원본 크기의 합, 쓰는 기기인지, 다음 회차 예정 시각, 이 파일을 쓴 시각.
- 넣지 않는 것: 파일 이름, 경로, 폴더 이름, 계정 주소, 출입증, 저장소 주소. 솔리오는 자주 바뀌는 다른 프로그램이고 MCP 보기 도구(4.16)도 이 파일을 읽어 AI 쪽으로 보내므로, 이 파일에는 처음부터 아무 이름도 두지 않는다. 폴더 이름을 보여야 하는 화면은 엔진 창을 연다.
- 엔진이 있는지: 솔리오는 상태 파일보다 먼저 엔진 설치를 본다. 컴퓨터 전체 설치의 제거 등록(`HKLM`의 설치된 앱 항목)이 있고 그 설치 폴더에 `WorkBackupRun.exe`가 있어야 「있음」이다. 엔진을 지워도 사용자 상태 폴더는 남으므로(4.2 「컴퓨터 전체 설치」), 엔진이 없는데 상태 파일이 있으면 옛 `safe`를 보이지 않고 「백업 엔진이 지워졌습니다 — 다시 깔기」를 보인다.
- 솔리오의 판단: 엔진은 있는데 이 파일이 없거나 상태가 `restore-only`이면 「보호 시작」(위의 `setup`만 넘기는 길)을 보인다. `restore-only` PC에서 보호를 시작하면 옮겨 온 저장소와 다른 Google 계정의 새 손님 자리로 시작한다(4.14의 2단계 둘째 걸음). 같은 계정을 고르면 4.6의 「이 PC가 쓰는 기기가 되기」로 넘긴다. 지금 시각이 이 파일의 다음 회차 예정 시각보다 2시간 넘게 지났으면 「확인 중」으로 보이고 엔진 창 열기를 내놓는다. 엔진이 멈췄다는 판단과 메일은 서버의 사흘 규칙(4.5)이 하고, 솔리오는 판단하지 않는다.
- 꼴 번호: 솔리오는 모르는 칸을 무시한다. 꼴 번호가 솔리오가 아는 것보다 크면 「엔진이 새 판입니다 — 솔리오를 업데이트해 주세요」를 보인다. 꼴을 바꿀 때는 GPT 솔리오 세션과 같이 바꾼다.

#### 요청 파일 — 솔리오가 넘기는 것

- 자리: `%APPDATA%\SynkWorkBackup\solio\requests\`에 요청마다 파일 하나(`<시각>-<난수>.json`, 8KB 상한). 엔진은 4.2 「도우미」의 요청 파일과 같이 연결점을 따라가지 않게 열고, 크기 제한을 두고, 자료로만 읽는다.
- 먼저 차지하고 실행한다: 처리하는 쪽(화면 앱이나 회차 실행기)은 요청을 `requests\claimed\`로 덮지 않는 이름 바꾸기로 옮기고, 옮기기에 성공한 쪽만 처리한다. 그래서 둘이 같은 요청을 처리하지 않는다. 처리 도중 엔진이 죽어 `claimed\`에 남은 요청은 다음에 다시 하지 않고 「실패」 결과로 치운다. 요청 하나가 회차마다 엔진을 되풀이해 죽이지 못하게 하려는 것이다.
- 요청 낱말은 넷이다.
  - `setup` + `mode`(`protect` · `move`) + `hint`(없어도 된다): 처음 시작 이어 하기(위). 30분이 지나면 버린다. 이미 설정을 마친 PC나 「옮겨졌습니다」 상태의 PC에서는 버린다. `restore-only` PC에서 온 `mode: protect`는 받는다(위 「솔리오의 판단」).
  - `pick` + 동작 낱말 + 엔진이 낸 보고서의 번호 + 후보 번호 목록. 동작은 둘이다. `restore`는 MCP 찾기 결과(4.16)의 파일을 새 폴더로 되살린다. 자리는 사람이 고르지 않으므로 정해 둔다. 사용자의 「다운로드」 알려진 폴더 안의 `되살린 파일 <시각>` 새 폴더이고, 그 폴더가 백업 범위나 저장소와 겹치면 「엔진 창에서 확인 필요」로 돌려준다. 내려받기가 드는 일이라 `run-now`와 같은 쉼 규칙(종량 회선 · 배터리 · 절전 · 쉬는 회선)을 지키고, 요청으로 되살리는 양은 하루 5GB까지다. 넘으면 「엔진 창에서 확인 필요」다. 원래 자리로 되살리는 일은 요청으로 열지 않는다. `free`는 공간 보고서(4.15)의 후보 가운데 가 등급 자동 대상(손님이 첫 설정에서 동의한 다시 만들 수 있는 것)만 비운다. 제안 항목(다시 만들 수 있는지 알 수 없는 것), 휴지통, 나 등급은 「엔진 창에서 확인 필요」로 돌려준다. 1단계의 1판은 아무것도 비우지 않으므로 `pick free`는 모두 거절한다.
  - `space-setting` + 정해진 설정 이름과 값: 삭제 범위를 줄이는 쪽(시작선 낮추기, 자동 비우기 끄기, 나 등급 자동 끄기)만 받는다. 시작선을 올리거나, 가 등급 자동이나 나 등급 자동이나 휴지통 비우기를 켜는 것처럼 삭제를 켜거나 넓히는 값은 「엔진 창에서 확인 필요」로 돌려준다.
  - `run-now`: 「지금 백업」. 다만 요청으로 온 것은 화면에서 직접 누른 「지금 백업」의 예외(4.2 3번 — 쉬지 않음)를 물려받지 않는다. 종량 회선 · 배터리 · 절전 · 「쉬는 회선」(4.14)이면 쉬고 「쉼 — 엔진 창에서 지금 백업을 누르면 쉬지 않고 합니다」를 돌려준다. 회차 간격만 건너뛴다.
- 「엔진 창 열기」는 요청 파일을 쓰지 않는다. 지금 있는 열기 주소 `synk-workbackup:open?topic=<낱말>`(4.2 「알림」, 고정 목록과 정확히 견줌)을 그대로 쓰고, 그 목록에 `move`(옮겨 오기 화면 — 누르기만으로 실행되지 않는다)를 더해 아홉 낱말이 된다.
- 넣지 않는 것: 경로, 파일 이름, 명령 줄, 자유 글. 엔진은 칸 이름을 고정 목록과 견주고, 모르는 칸이 하나라도 있으면 요청을 통째로 버린다. 정해진 값 밖의 것은 `hint` 하나뿐이고, 그것도 주소 꼴만 받는다.
- 보고서 번호: 엔진은 보고서(공간 보고, MCP 찾기 결과)마다 번호와 만든 시각을 붙인다. 요청의 보고서가 그 종류의 가장 새 보고서가 아니거나 24시간이 지났으면 거절한다. 후보가 가리키는 항목은 실행 직전에 엔진이 다시 검증한다. 공간 비우기는 [공간 비우기 설계](SPACE_DESIGN.md) 5.1의 확인을, 되살리기는 새 폴더 규칙을 그대로 쓴다.
- 누가 눌렀는지는 이 파일로 알 수 없다. 같은 사용자 권한의 프로그램은 누구나 이 폴더에 쓸 수 있고, 셸을 쓰는 AI 도구도 마찬가지다. 그래서 이 요청으로 할 수 있는 일을 되돌릴 수 있는 일로만 묶는다. 처음 시작 이어 하기, 새 폴더로 되살리기, 다시 만들 수 있다고 손님이 이미 동의한 것 비우기, 삭제 범위를 줄이는 설정, 쉼 규칙을 지키는 지금 백업이 그것이다. 그 밖에 삭제를 켜거나 넓히는 일, 나 등급 비우기, 원래 자리로 되살리기, 폴더 더하기 · 빼기, 기기 끊기, 되돌리기는 요청으로 열지 않고 엔진 창 안에서 손님이 확인해야 돈다. 같은 사용자 권한의 악성 프로그램은 이 길이 없어도 파일을 바로 지울 수 있으므로, 이 경계가 새 구멍을 내지 않는다.
- 결과: 엔진은 요청마다 같은 이름의 결과 파일을 `solio\results\`에 남긴다. 낱말 하나(했음 · 거절과 까닭 낱말 · 엔진 창에서 확인 필요 · 쉼 · 실패)뿐이다. 솔리오가 읽고 지우며, 하루가 지난 것은 엔진이 치운다.
- 읽는 때: 화면 앱이 떠 있으면 화면 앱이 바로 읽는다. 아니면 솔리오가 엔진의 요청 작업 `\SYNK 업무 백업\요청 - <계정 이름> · <SID 짧은 표시>`를 작업 스케줄러로 깨운다(`IRegisteredTask::Run`). 이 작업은 계기가 없고, 보호 시작 때 다른 회차 작업과 같이 만든다(4.2 「회차 작업」). 4.2의 대체 자리(작업 스케줄러 뿌리 폴더)에 회차 작업을 둔 PC에서는 이 작업도 같은 자리에 같은 이름 꼴로 두고, 솔리오는 `\SYNK 업무 백업\` 다음 뿌리 폴더 순서로 찾는다. 다른 회차가 돌고 있으면 작업 스케줄러가 새 실행을 버리므로(겹치면 새 것을 버림), 회차 실행기는 어느 계기로 돌든 끝에 요청 폴더를 한 번 더 읽는다. 그래서 회차 실행기는 솔리오의 자식으로 뜨지 않고, 다른 회차와 같은 깨끗한 환경 · 보통 아래 우선순위로 뜬다. 솔리오가 업데이트로 꺼져도 회차가 함께 죽지 않는다. 회차 기록의 계기는 `request`다. 엔진 잠금을 못 잡으면 「바쁨」으로 끝나고, 요청은 다음 회차 끝에 처리된다. `pick restore` 하나는 30분을 넘기지 않고, 넘으면 남은 것을 「엔진 창에서 이어서」로 돌려준다.

#### 엔진 설치 · 업데이트 · 지우기

- 엔진 설치 파일과 업데이트 목록은 솔리오 PC 앱 피드와 같은 곳에 둔다(로드맵 13번, 4.10). 솔리오는 그 목록에서 엔진 설치 파일의 주소, 크기, SHA-256, 서명을 읽는다.
- 엔진의 자동 업데이트는 엔진이 혼자 한다(4.10). 솔리오는 엔진을 업데이트하지 않는다. 솔리오가 꺼져 있거나 솔리오 판이 바뀌어도 엔진은 그대로 돈다.
- 솔리오를 지워도 엔진은 남는다. 백업이 말없이 멈추면 안 되기 때문이다. 엔진은 Windows 「설치된 앱」에서 따로 지운다. 솔리오 「백업·복구」 탭에 그 안내를 둔다.

#### 화면을 어디에 그리나 — 11-16 방향과 함께 정할 것

- 지금 설계는 「파일 되살리기」와 「새 PC로 옮겨 오기」를 엔진 창(4.12, 시안 A 「확인서」)에서 한다. 11-16에 유호님이 PC 클라이언트를 전시 작품 같은 클라이언트로 정하셨고, 클릭을 줄이고, 워크스페이스와 PULSE는 같은 창 안에서 연다고 하셨다([결정](../../docs/_ops/결정.md) 11-16 「SYNK 플랫폼 PC 클라이언트 방향」). 엔진 창이 솔리오 밖의 두 번째 창으로 뜨는 것이 그 방향과 맞는지는 화면 세션이 시안을 보여 드리고 여쭙는다(11-16 다섯 세션 나눔).
- 어느 쪽이 되든 이 절의 계약은 그대로 쓴다. 솔리오 창 안에 그리게 되면 솔리오가 상태 파일 위에 읽기 전용 질의(되살릴 파일 찾기 · 판 목록 · 진행)를 더 받아야 한다. 그때 상태 파일 꼴 2와 질의 통로(같은 사용자만 여는 이름 있는 파이프)를 정하고 설계 검토에 올린다.

#### 화면 쪽에 넘길 것(GPT 솔리오 세션)

- 「준비 중」을 실제 입구로 바꾸는 날은 2단계 노트북 시험을 시작하는 날이고, 유호님 계정에만 바꾼다(로드맵 2단계).
- 엔진이 없으면 「보호 시작」과 「이 PC로 옮겨 오기」를 둔다. 둘 다 PC 앱 본체가 HTTPS로 직접 받기 → 공유 없는 핸들로 크기 · SHA-256 · 서명 확인 → `setup` 요청(`mode`) → 같은 핸들로 설치 파일 실행이다. Node와 Electron의 기본 파일 열기는 늘 쓰기 공유로 열므로, 공유 없는 핸들은 작은 네이티브 호출(`CreateFileW`의 공유 0)이 든다. 엔진은 있는데 상태 파일이 없으면 `setup`만 넘긴다. 엔진이 지워졌으면 옛 상태를 보이지 않는다.
- 엔진이 있으면 상태 파일의 보호 상태, 마지막 확인, 증명 날짜, 주의를 보인다. 「파일 되살리기」와 「새 PC로 옮겨 오기」는 엔진 창 열기 주소로 연다.
- `hint`는 SYNK ID가 Google 로그인이고 그 주소를 알 때만 넘긴다.
- 공간 보고서(4.15)는 경로가 들어 있다. 솔리오는 그 내용을 서버, 로그, 오류 보고로 보내지 않는다. GPT 솔리오 세션이 그 시험을 둔다.
- Mac은 「Windows에서만 쓸 수 있음」으로 안내한다.
- 상태 파일, 요청 파일, 결과 파일의 꼴과 시험용 견본은 엔진 쪽이 `contract/solio/`에 만들어 둔다.

### 4.14 우리 노트북을 0번 손님으로 (로드맵 15)

- **때:** 관문 1을 넘은 날부터 이 노트북의 실제 자료를 엔진으로도 함께 지킨다. 11-09 복원 체계([컴퓨터를 잃어버렸을 때](../../docs/컴퓨터를%20잃어버렸을%20때.md))는 그대로 둔다. 엔진이 복원 체계를 대신할지는 이 시험과 2단계를 모두 넘은 뒤 유호님께 여쭙는다.
- **범위와 차례:** 관문 1을 넘은 날 시범 상한과 같은 원본 100GB(작업 폴더와 문서)로 시작한다. 2단계의 옮겨 오기는 이 100GB를 받는다. 이 노트북 전체(11-07 기준 약 1TB)로 늘리는 것은 2단계가 끝난 뒤다. 예전 노트북이 1TB를 내려받지 않게 하고, 저장비가 4주 동안 늘지 않게 하려는 것이다. 늘린 뒤 처음 백업 시간, 회차 시간, 메모리, 월 저장비를 잰다.
- **돈:** 손님용 B2 계정에 올리기 전에 금액을 말씀드리고 여쭙는다. 100GB면 월 약 0.7달러, 1TB면 월 약 7달러이고 이력과 숨긴 판만큼 더 든다. 손님용 B2 계정은 결제 수단이 없어 무료 한도(10GB)에 막혀 있으므로(11장), 100GB를 올리려면 결제 수단을 넣는 일이 먼저다. 그것은 유호님 손이다.
- **회선:** 휴대폰 핫스팟일 때는 큰 올리기를 미룬다. 4.2의 쉼 판단은 종량 회선이면 쉬는데, 핫스팟이 Windows에서 종량 회선으로 잡히는지는 확인 안 함이다. 그래서 엔진 설정 서랍에 「쉬는 회선」을 둔다. 손님이 고른 Wi-Fi 이름에서는 종량 회선과 같이 쉬고(직접 누른 「지금 백업」만 예외), 처음 백업에도 매시간 증분에도 같이 든다. 지금 Wi-Fi 이름은 회차 실행기가 Windows 연결 정보(`Networking_Connectivity`, 이미 쓰는 기능)로 읽는다. 최신 Windows 11은 Wi-Fi 이름을 읽을 때 위치 권한을 물을 수 있어, 권한 없이 읽히는지는 확인 필요다. 읽히지 않으면 엔진 창은 그 핫스팟을 Windows 설정에서 「데이터 통신 연결」로 두는 길을 안내한다(손님이 고르는 Windows 설정이고, 엔진이 바꾸지 않는다). 이 노트북은 0번 손님을 시작하는 날 핫스팟을 넣고 어느 길이 되는지 적는다.
- **2단계 노트북 시험과 「쓰는 기기는 하나」(4.6):** 예전 노트북이 이 노트북 저장소의 쓰는 기기가 되면 이 노트북의 백업이 4주 동안 멈추고, 30일 뒤에는 예전 노트북이 이 노트북의 판을 정리한다. 반대로 「옛 PC 연결 끊기 — 아니오」를 고르면 예전 노트북에서 회차가 돌지 않아 관문 2의 4주를 잴 수 없다. 그래서 이렇게 한다(Claude 판단(기술), 반대하시면 되돌린다).
  1. 예전 노트북에서 「이 PC로 옮겨 오기」를 이 노트북 저장소로 한다. 끝에 「옛 PC 연결 끊기」는 「아니오」를 고른다. 이 노트북은 계속 쓰는 기기다. 해시 전수 대조와 옮겨 오기에 든 사람 손 시간은 여기서 잰다.
  2. 그다음 예전 노트북은 따로 된 손님 자리(이 노트북과 다른 Google 계정을 초대 명단에 하나 더 넣는다)로 「보호 시작」을 하고 4주 회차를 잰다. 어느 Google 계정을 쓸지는 판이 서면 여쭙는다.
  3. 4주가 끝나면 예전 노트북의 손님 자리를 「통째로 받기」로 남길지 여쭙고 해지한다. 이 노트북 저장소는 처음부터 끝까지 그대로다.
  - 「옛 PC 연결 끊기 — 예」(쓰는 기기 넘기기)는 깨끗한 Windows 자동 연습(T12)과 두 기기 시험(T21)에서 잰다.
  - 2단계 동안에도 이 노트북이 쓰는 기기이므로 공간 훑기와 공간 비우기의 4주 시험(공간 비우기 설계 9장)은 멈추지 않는다.
- **빈 Windows 복구 연습:** 11-16 결정으로 2단계 노트북 시험이 그 연습을 맡는다(로드맵 2단계). 그래서 15번의 연습을 따로 하지 않는다. 「어제처럼 일할 수 있는가」는 2단계에서 걸린 시간과 사람 손 횟수로 잰다. 이 노트북에 새 Windows 계정을 만드는 연습은 하지 않는다.
- **공간 비우기와의 관계:** 나 등급(클라우드에만 두기)은 이 실자료 백업이 대조된 뒤에만 만든다([공간 비우기 설계](SPACE_DESIGN.md) 9장). 이 노트북은 마지막 접근 시각 갱신이 꺼져 있어(11-16 `fsutil behavior query disablelastaccess` = 1) 나 등급은 자동이 아니라 제안만 된다(공간 비우기 설계 3.1).
- 결과는 [QA](QA.md)에 숫자로 남긴다.

### 4.15 공간 비우기 1판 — 엔진 쪽 (로드맵 16)

정본은 [공간 비우기 설계](SPACE_DESIGN.md)다. 이 절은 1단계에 엔진이 할 일과, 그 설계가 1단계 엔진 규칙에 닿는 자리만 적는다.

- **1단계에 만드는 것:** 분석과 예측(1판)뿐이다. 지우는 기능은 1단계에 만들지 않는다. 가 등급 자동은 이 노트북 4주 시험 뒤, 나 등급은 0번 손님 백업이 대조된 뒤에 만든다(공간 비우기 설계 9장).
- **훑기 — 언제:** 백업을 하든 쉬든, 실패하든 멈춰 있든, 그날 처음 도는 회차 끝에 하루 한 번 훑는다. 분석은 회선이 필요 없기 때문이다. 보호 시작을 마치지 않은 PC에는 회차가 없으므로 훑지 않는다.
- **훑기 — 어떻게:** 엔진 잠금을 쥐지 않고 읽기만 한다. 보통 아래 우선순위와 낮은 디스크 우선순위로 돌고, 하루 5분을 넘기지 않는다. 다 못 훑으면 다음 날 이어서 훑는다. 작업 사본의 상태를 볼 때 `git`은 `--no-optional-locks`로 불러 색인 잠금을 만들지 않는다. 훑기는 Rust로 한다. 수십만 개의 파일을 걷는 일이라 Node 워커를 띄우지 않는다. 훑기가 실패하거나 시간을 넘겨도 그 회차의 백업 결과는 그대로이고, 회차 기록에는 훑기의 걸린 시간 · CPU 시간 · 다 훑었는지를 백업과 다른 칸(`space`)에 적는다.
- **보고서:** `%APPDATA%\SynkWorkBackup\solio\space.json`. 보고서 번호와 만든 시각, 마지막으로 한 바퀴를 다 훑은 날, 드라이브마다 크기 · 남은 공간 · 지난 14일 증가 속도 · 「이대로면 며칠 뒤 시작선」, 「지난 7일 늘어난 것」 다섯 줄, 후보 목록(번호 · 등급 · 크기 · 까닭 낱말 · 사람이 읽는 이름)을 담는다. 증가 속도와 「지난 7일」은 한 바퀴를 다 훑은 값끼리만 견줘, 날짜가 섞인 값을 내지 않는다. 1MB와 후보 1,000개를 넘지 않는다.
- **보고서의 경로:** 상태 파일과 달리 이 보고서에는 후보의 경로가 들어간다. 손님이 무엇이 비워질지 보고 골라야 하기 때문이다. 같은 사용자 권한의 프로그램(셸을 쓰는 AI 도구 포함)은 이 파일을 읽을 수 있지만, 그 프로그램은 디스크의 폴더를 직접 훑을 수도 있으므로 새로 드러나는 것은 없다. MCP 동의(4.16)는 우리 도구가 AI 쪽으로 보내는 것에만 걸린다. 솔리오가 이 내용을 PC 밖으로 보내지 않는 계약은 4.13 「화면 쪽에 넘길 것」에 있다.
- **모르는 꼬리표의 판:** 이 판의 엔진이 모르는 꼬리표가 붙은 판은 지우지도 고르지도 않는다. 지우지 않는 자리는 모든 정리 길(매 회차 정리, 4.6의 다른 기기 판 정리, 폴더 빼기 30일)이다. 고르지 않는 자리는 정리의 「가장 새 확인된 판」 대조, 폴더별로 지킬 판 고르기, 「지금 상태」 되살리기, 파일 골라 되살리기, 되살리기 증명, 대량 변경 비교다. 나중 판이 만들 `cloud-only` 판(공간 비우기 설계 3.2)을 옛 판 엔진이 다른 기기에서 지우거나, 그 판을 기준 판으로 골라 되살리기에서 파일을 빠뜨리거나 정리를 멈추지 않게 하려는 것이다. 이 규칙은 1단계 정리 고침과 함께 넣고 정리 규칙의 GPT 2차 검수에 같이 올린다(T33). `cloud-only` 판 고정 자체와 그 꼬리표를 떼는 공격의 탐지는 나 등급을 만들 때 넣고 그때 GPT 2차 검수를 받는다(공간 비우기 설계 3.2).
- **대량 변경 멈춤(4.4)과의 관계:** 비우기 장부의 경로를 비교에서 빼되, 장부를 그대로 믿지 않는다. 장부는 사용자 폴더의 파일이라 파일을 망치는 프로그램이 경로를 적어 넣을 수 있다. 그래서 장부 줄이 엔진이 실제로 비운 것과 맞을 때만 뺀다. 가 등급은 그 경로가 가 등급 규칙의 꼴에 들고 장부의 크기 · 수정 시각이 그 판의 기록과 같을 때, 나 등급은 그 파일이 고정된 `cloud-only` 판에 있을 때다. 1판은 지우지 않아 장부가 비어 있으므로, 가 등급 자동을 켤 때 함께 넣는다.
- **72시간 시험:** 1단계의 72시간 시험은 1판의 훑기를 켠 채로 한다. 가 등급 자동을 켤 때 72시간 시험을 다시 한다. 둘 다 「회차 빠짐 0」이 그대로여야 한다.
- **화면:** 솔리오 「공간」 탭은 1판이 나올 때 GPT 솔리오 세션이 더한다(로드맵 「플랫폼 화면의 솔리오」 표). 1판에는 지우는 단추가 없다.

### 4.16 AI 도구에서 솔리오 쓰기 — MCP (로드맵 17)

- **1단계에 만드는 것:** 보기 도구만 1단계 끝 무렵에 만들어 우리 세션부터 쓴다. 요청 도구와 솔리오의 「AI 도구에 연결」 단추는 2단계 노트북 시험에서 유호님이 쓰시는 AI 도구로 시험한다.
- **모양:** `WorkBackupRun.exe --mcp`가 표준 입출력으로 MCP 서버가 된다. 인터넷 쪽으로는 열지 않고, 프로그램을 따로 더 깔지 않는다.
- **떠 있는 동안:** AI 도구는 하루 종일 떠 있고 세션마다 서버를 띄우므로, 이 프로세스가 여럿 떠 있을 수 있다. 그래서 이 프로세스는 엔진 잠금을 쥐지 않는다. 스스로 끝나면 AI 도구가 서버가 죽은 것으로 보고 세션 중간에 솔리오 도구가 사라질 수 있으므로(다시 띄우는지는 도구마다 다르다), 프로세스는 표준 입력이 닫힐 때까지 가볍게 남고 5분 동안 요청이 없으면 워커만 내린다. 설치 · 업데이트 표식(`.installing`, 4.2 「컴퓨터 전체 설치」)이 보이면 바로 끝난다(요청마다, 그리고 1분마다 본다). 72시간 시험의 「회차 사이 상주 0」은 회차 실행기와 화면 앱을 센다. MCP 프로세스는 AI 도구가 띄운 동안만 있는 것이라 따로 세어 적는다(T14, T32).
- **허용 목록:** MCP는 워커의 메서드를 `methods.json`과 따로 둔 짧은 허용 목록으로만 부른다. 상태 읽기, 판 목록, 파일 목록 열기 · 찾기 · 닫기뿐이다. `methods.json`의 `allowedReadOnly`는 「복구 전용 연결에서도 부를 수 있다」는 뜻이고 그 안에 되살리기 같은 바꾸는 메서드도 들어 있으므로, AI 쪽 경계로 쓰지 않는다.
- **잠금과 회선:** 회차가 엔진 잠금을 쥐고 있으면 기다리지 않고 「백업 중이라 잠시 뒤에 다시 해 주세요」를 돌려준다. 파일 찾기는 restic이 저장소를 읽으므로(공유 잠금) 그동안 회차의 정리는 「바쁨」으로 다음 회차에 미뤄질 수 있다. 그래서 찾기는 한 시간에 10번, 한 번에 60초를 넘기지 않는다. 종량 회선과 「쉬는 회선」(4.14)에서는 찾기를 하지 않고 「지금은 내려받기를 쉬는 회선입니다」를 돌려준다.
- **보기 도구 넷:**
  - `protection_status`: 상태 파일(4.13) 그대로다. 이름이 없어 동의 전에도 답한다.
  - `space_report`: 공간 보고서(4.15)다. 경로가 들어 있어 동의가 든다.
  - `find_restorable`: 이름 일부로 백업 안의 파일을 찾는다. 판 시각, 크기, 경로를 50개까지 돌려준다. 동의가 든다. 1단계의 찾기는 지금 파일 목록(`openFileCatalog`)과 같이 가장 새 확인된 판만 본다. 그래서 「어제 지운 보고서」처럼 지금 판에 없는 파일은 못 찾는다. 옛 판까지 찾는 것은 「파일 골라 되살리기에 옛 판 폴더」(트랙의 남은 일)와 함께 넓힌다. 큰 저장소에서 첫 찾기가 60초 안에 끝나는지는 T32에서 잰다.
  - `ai_subscription`: AI 구독 한도다. 플랫폼 PC 앱이 읽기 전용 자료를 내주는 계약을 GPT 쪽과 정한 뒤에만 내놓는다(로드맵 「플랫폼 화면의 솔리오」 표). 그 전에는 도구 목록에 없다.
- **요청 도구(2단계):** 이 도구들은 제안만 만든다. 엔진의 `solio\proposals\`에 제안 파일(보고서 번호, 후보 번호, 제안 낱말)을 쓰고 「솔리오에서 확인해 주세요」를 돌려준다. 솔리오는 제안을 엔진이 만든 설명(후보의 이름 · 크기 · 되돌리는 법)으로 보인다. AI가 쓴 자유 글은 승인 화면에 보이지 않는다. AI가 웹 페이지나 메일 속 지시에 속아 그럴듯한 설명을 붙여도, 손님은 엔진의 설명만 보고 고른다.
  - `propose_restore`: 찾기 결과의 파일을 새 폴더로 되살리기. 손님이 솔리오에서 누르면 4.13의 `pick restore` 요청이 된다.
  - `propose_free_space`: 공간 보고서의 가 등급 자동 대상 비우기. 손님이 누르면 `pick free` 요청이 된다. 그 밖의 후보와 1판에서는 내놓지 않는다.
  - `propose_backup_scope`: 백업 범위에 폴더 더하기. 범위를 바꾸는 일은 요청으로 열지 않으므로, 손님이 누르면 엔진 창의 폴더 화면(`topic=folders`)이 열리고 거기서 확인한다.
  - AI 도구가 셸로 요청 폴더에 직접 쓰는 경우는 4.13의 「되돌릴 수 있는 일로만 묶기」가 막는다.
- **나가는 것과 동의:** 동의가 드는 도구가 동의 전에 불리면, 엔진은 창을 열지 않고 「엔진 창의 설정 서랍 『AI 도구』에서 이 도구를 켜 주세요」를 돌려준다. 동의 화면을 열기 주소로 띄우지 않는 것은, 한 번 누르면 실행되는 화면을 열기 주소에 넣지 않는다는 4.2의 규칙 때문이다(웹 페이지나 속은 AI가 몇 번이든 띄울 수 있다). 설정 서랍은 MCP 연결이 알려 온 도구 이름과 처음 본 때를 도구마다 한 줄로 보이고(이름은 그 도구가 스스로 알린 것이라고 적고, 이 서버를 띄운 프로그램의 경로를 함께 보인다), 「AI 도구에 파일 이름과 폴더 이름이 나갑니다. 파일 내용은 나가지 않습니다」를 보인 뒤 도구마다 켜고 끈다. 손님이 고른 낱말(예: 「건강」, 「계약」)이 든 경로는 결과에서 빼고, 뺀 수도 알리지 않는다. 찾는 낱말에 그 낱말이 들면 찾지 않는다.
- **연결:** Claude Code는 연결 명령, Claude 앱은 확장 파일, Codex와 Cursor는 설정 파일 한 줄로 잇는다. 세부는 만들 때 각 도구의 공식 문서로 정한다(로드맵 17번). 1단계에서는 우리 세션에 Claude Code 연결 명령으로만 잇는다.
- **기록:** 도구 호출마다 도구 이름, 결과 수, 걸린 ms만 회차 기록과 같은 꼴로 남긴다. 찾은 낱말과 결과 경로는 남기지 않는다.

## 5. 데이터

### 5.1 PC

- 사용자별 `%APPDATA%\SynkWorkBackup\`: 프로필 설정 · DPAPI 자격(복구 암호 · 기기 쓰기 출입증 · 기기 토큰 · Google 토큰), `device.json`(기기 번호 · 손님 번호, 비밀 아님 — 서버 주소는 실행 파일에 박는다), `runs.jsonl` · `notify.json` · `progress.json` · `vss-request.json` · `telemetry-queue.jsonl` · `migration/<번호>.jsonl`(옮겨 오기 장부 겸 이어받기 상태), `engine.lock` · `ui.lock`.
- 사용자별 `%LOCALAPPDATA%\SynkWorkBackup\`: restic 캐시 · 임시.
- 컴퓨터 쪽: 설치 폴더(관리자만 쓰기), 작업 스케줄러 작업 폴더 둘, `%ProgramData%\SynkWorkBackup\helper\<SID>\`(도우미 작업 폴더 — 관리자만 쓰기, 그 사용자는 읽기 · 지나가기만: 섀도 복사본 연결 · 만든 섀도 복사본 번호 · 하루 횟수).

### 5.2 저장소 (B2)

- 손님 계정에 버킷 하나(비공개, 서버 쪽 암호화 켬, 수명 규칙은 4.4 — 규칙 하나만).
- `c/<손님 번호>/r/`가 손님당 restic 저장소 하나다. 손님 번호는 메일에서 만들지 않은 무작위 16자다. 판 꼬리표: `complete` · `partial` · `fill` · `meta`(U 목록 · 채움 경로 맞추기 · 알려진 폴더), 호스트 = 기기 번호.
- 지금 `b2.cjs`의 경로 검사(`work-backup/<보관함>`)와 `recovery-vault.cjs`의 읽기 출입증 규칙에 새 꼴을 더한다. `b2.cjs` 사전 확인(HeadBucket)은 접두사 출입증에서 200이므로(M1) 그대로 쓰고, 오류 문구 「버킷 전체 Read and Write 권한이 필요합니다」만 바꾼다.

### 5.4 봉투와 복구 코드

- 봉투 v3: `{format:'synk-workbackup-recovery', version:3, generationId, generation, createdAt, subject, repository:{endpoint,bucket,prefix}, repositoryId, password, readKey:{keyId,applicationKey}, bucketId, resticVersion}` — 뒤의 Drive 기록 맞추기 칸은 [구현 설계](#server-build)의 「봉투 v3의 꼴」. 앱 전용 공간 표시는 `synk-workbackup-recovery-v3`.
- 복구 코드: 같은 내용을 글(줄 바꿈 · 검사 숫자 포함)과 파일로 준다. 앱 창에서 바로 인쇄하거나 고른 자리에 바로 쓰고, 임시 파일을 남기지 않는다.

**Q10 후보와 한계(검토 답 요약):**
- **다른 B2 계정으로 복제:** 원본에서 영구 삭제해도 목적지에 남고 목적지 쓰기 출입증에는 삭제 권한이 없다. 그런데 숨김 표시가 복제되지 않아 목적지는 줄지 않고 지금까지 올린 것 전부가 쌓인다(변경량만큼 계속 는다). 목적지를 줄이려면 서버 밖에서 도는 정리가 따로 든다. 공격자가 복제 규칙을 끄면 그 뒤 것은 안 넘어간다(매일 대조가 잡는다).
- **객체 잠금:** 이 설계에서는 정리가 숨기기만 하고 실제 삭제는 수명 규칙이 하므로, 「올린 뒤 N일 잠금 + 서버가 지금 보이는 판의 잠금을 날마다 늘림」이면 숨겨진 판만 잠금이 풀려 수명 규칙이 지우고, 그 기간 안의 영구 삭제는 계정 주인의 열쇠로도 안 된다. 값은 잠금을 늘리는 서버 일과 그 권한, 되돌릴 수 없다는 점(해지해도 N일은 못 지운다). restic 정리 · 수명 규칙과 실제로 맞물리는지는 M8과 같은 자리에서 작은 접두사로 잰다.
- **다른 회사 저장소:** 값과 일이 가장 크다. 위 둘이 안 될 때.

## 11. 유호님께 여쭐 것과 때

로드맵 7장의 묶음을 1단계 설계에 맞춰 풀었다. 11-12 「승인, B2 시험 진행」 · 「Actions 비밀값 넣기 진행」으로 앞 둘을 마쳤다. 검토를 반영해 뒤를 막는 일을 **2주차(11-16 ~ 22)로 앞당겼다** — 한 번에 모아 여쭙고, 유호님 손이 드는 자리만 그때그때 부탁드린다. 돈은 들지 않는다(시험은 B2 무료 10GB 안, 새 결제 없음).

이 표는 11월 12일의 계획이다. 지금 상태는 [트랙](../../docs/_ops/트랙.md)에 있다. 끝난 일은 「때」 칸에 「끝」으로 적었다.
