이 문서의 낱말. **복구 암호** · **클라우드 출입증**은 로드맵 머리와 같다. **회차**는 예약이 백업 프로그램을 한 번 띄워 할 일을 하고 끝내는 한 번이다. **온전 판**은 원본을 다 읽은 백업 판, **부분 판**은 켜진 프로그램이 쥔 파일 몇 개를 못 읽은 판, **채움 판**은 그 못 읽은 파일만 섀도 복사본에서 다시 읽은 판이다. **도우미**는 섀도 복사본을 만들고 지우기만 하는 관리자 권한 작업이다. **개통 서버**는 손님별 클라우드 자리와 출입증을 만들고 끊는 작은 서버다. **봉투**는 Google 앱 전용 공간에 넣는 복구 정보다. **쓰는 기기**는 손님 저장소에 백업을 올리는 기기이고 한 번에 하나다.

## 0. 한눈에

1단계가 끝나면 이렇게 된다.

- 처음 쓰는 사람이 설치 → Google 로그인 → 「보호 시작」만으로 클라우드 백업을 시작한다. 입력 칸이 없다.
- 앱 창을 닫아도, 트레이가 없어도 Windows 작업 스케줄러가 매시간 · 로그인 직후 · 깨어난 직후 · 잠금 해제 때 회차를 띄운다. 회차 사이에는 아무 프로그램도 떠 있지 않다. 회차가 도는 동안에도 앱은 열리고 진행을 보여 준다.
- 켜진 프로그램이 쥔 파일 몇 개 때문에 나머지 전체의 보호가 멈추지 않는다. 그 파일은 그것이 든 마지막 판을 고정해 지키고, 관리자 계정이면 섀도 복사본에서 그 파일만 다시 읽어 채운다.
- PC에 있는 출입증으로는 백업을 **30일 안에 되돌릴 수 있게만** 망칠 수 있다(11-12 유호님 「30일로 넣기」). 서버가 매일 저장소가 이상하게 바뀌었는지 보고 알리며, 손님이 「이 시각으로 되돌리기」를 누르면 서버가 지운 것 없이 복사로 되살린다.
- 새 PC에서는 설치 → Google 로그인 → 「이 PC로 옮겨 오기」로 원래 자리(또는 OneDrive 밖 새 폴더)에 되살리고, 그 PC가 쓰는 기기가 되는 순간 옛 PC 출입증을 끊고, 같은 저장소에 이어서 백업한다.
- 컴퓨터 전체용 설치 파일 하나와 자동 업데이트가 있고, 깨끗한 Windows에서 같은 흐름을 GitHub Actions가 돌린다.

끝난 기준은 로드맵의 **관문 1** 그대로다. 시험 하나하나를 관문과 7장에서 짝지었다. 유호님 손은 화면 시안 고르기 한 번과 [11장](#11-유호님께-여쭐-것과-때)의 일뿐이다.

## 2. 사용자 흐름

### 2.1 처음 시작

| 차례 | 사람이 하는 것 | 전체 누름 | 앱 안 누름 |
|---|---|---|---|
| 1 | 내려받은 설치 파일 열기 | 1 | |
| 2 | SmartScreen 「추가 정보 → 실행」(서명 전 시범판) | 2 | |
| 3 | 관리자 확인 「예」 — 설치 창 없이 설치하고, 끝나면 **로그인한 사용자 · 보통 권한으로** 앱을 연다 | 1 | |
| 4 | 「Google로 시작」 | 1 | 1 |
| 5 | 브라우저에서 계정 고르기 · 「계속」(로그인돼 있지 않으면 입력이 더해진다) | 2 | |
| 6 | 「보호 시작」 — 보호할 폴더(문서 · 바탕화면 · 사진 + 진단이 찾은 작업 폴더 제안)와 예상 용량이 보이고, 이 단추가 곧 범위 동의다 | 1 | 1 |

- SmartScreen 두 번은 OS 코드 서명(3단계) 뒤 빠진다. Smart App Control이 켜진 PC는 설치가 아예 막히므로 이 표에 넣지 않고 2단계에서 따로 센다.
- 5번은 지금 요청(`prompt=consent select_account`)에서 동의 화면에 권한 체크 칸이 뜨면 한 번 더 들 수 있다. 새 Google 프로젝트로 실제 화면을 2주차에 먼저 세고, 넘치면 요청 꼴(동의를 처음 한 번만)을 고치거나 관문 숫자를 유호님께 여쭙는다.
- 보호 시작 뒤 앱이 혼자 하는 것: 개통(서버) → 저장소 만들기 → 봉투 보관 · 다시 받아 확인 → 예약 작업 등록 → 첫 백업. 첫 백업이 도는 동안 「창을 닫아도 됩니다」 한 줄, 끝나면 알림 한 번. 첫 백업 동안 전원이 연결돼 있으면 절전을 막는다.
- 보호 범위 화면에 OneDrive 정책을 적는다: 「OneDrive에만 있는 파일 N개는 OneDrive가 지킵니다 — 이 백업에는 없습니다」(4.2).
- 두 번째 복구 수단(복구 코드)은 첫 화면에 넣지 않고 첫 주 안에 한 번 권한다. 첫 복구 수단은 자동으로 만들어지는 봉투다.
- 첫 화면에 「Google 2단계 인증을 켜 두세요」 한 줄(Google 계정에 들어갈 수 있는 사람은 백업도 읽을 수 있다 — 로드맵 6장).

### 2.2 평소

앱을 열 일이 없다. 알림은 「문제 + 할 일 하나」일 때만 뜨고, 같은 문제는 하루 한 번이다.

| 알림 | 할 일 하나 |
|---|---|
| 첫 백업이 끝남(한 번) | 없음 — 「이제 매시간 저절로 지킵니다」 |
| 사흘 넘게 소식이 없음 | PC가 켜져 있으면 원인별(회선 · 용량 · 재로그인), 꺼져 있으면 서버가 메일로 — 서버는 측정이 왔는지만 알므로 「백업을 못 함」이 아니라 「소식이 없음」이라고 쓴다 |
| 몇 파일만 못 지킴(부분 판) | 「[프로그램]이 쓰는 중인 파일 N개는 [날짜] 판으로 지킵니다」 — 할 일 없음, 그 프로그램을 닫으면 다음 회차에 새로 담긴다 |
| 폴더를 찾을 수 없음 | 「다시 고르기 · 빼기」 — 그 폴더의 마지막 판은 고정해 둔다 |
| 저장소 점검 실패 · 저장소가 바뀜(서버 탐지) | 「백업이 바뀌었습니다 — 되돌릴 수 있는 날이 N일 남았습니다 · 확인하기」 |
| 되살리기 증명에서 손상 | 「확인하기」 — 그날 |
| 많은 파일이 한꺼번에 지워지거나 바뀜 | 「확인하기」 — 확인 전까지 이전 판을 지우지 않는다 |
| 새 기기가 이 계정에 연결됨 · 되돌리기 요청됨 | 「내가 한 게 아니면 끊기」 |
| 되돌린 뒤 고르기를 기다림 | 「여기서부터 계속 · 되돌리기 취소」(하루 한 번) |
| 용량 상한에 가까움 · 넘음 | 「폴더 줄이기」 |
| Google 봉투 재확인 실패 | 「다시 로그인」 |
| 업데이트 준비됨 | 「설치」(관리자 확인이 뜬다, 표준 사용자 계정은 「관리자에게 부탁하기」 문구로 일주일에 한 번) |

### 2.3 새 PC로 옮겨 오기

설치 → 「Google로 시작」 → 앱이 이 계정의 상태를 보고 갈래를 고른다.

- **보통:** 「이 계정에 백업이 있습니다」 → 「이 PC로 옮겨 오기」 → 되살릴 자리(원래 자리 / OneDrive 밖 새 폴더, 용량과 함께) → 진행(내려받는 기다림은 따로 「약 N분」, 끊겨도 이어서) → 해시 대조 → 결과(되살린 수 · 이미 있던 같은 파일 수 · 「(복구본)」으로 나란히 둔 수 · 건너뛴 연결 · 특수 파일 수와 목록) → 다시 깔 프로그램 목록 · 다시 로그인할 곳 체크리스트 → 「옛 PC 연결 끊기」(기본 예) → 이 PC가 쓰는 기기가 되어 같은 저장소에 이어서 백업한다.
- **「옛 PC 연결 끊기」에서 아니오:** 이 PC는 되살리기까지만 하고 백업은 시작하지 않는다(쓰는 기기는 하나 — 여러 PC는 로드맵 4단계).
- **이 계정의 백업이 최근에 대량으로 숨겨졌다(서버 탐지):** 「사고 전으로 되돌린 뒤 옮겨 오기」를 먼저 내놓는다(2.5).
- **같은 PC를 다시 깔았다(파일이 디스크에 그대로):** 「되살리지 않고 이어서 백업」. 옮겨 오기를 그대로 돌리면 그사이 고친 파일마다 옆에 옛 「(복구본)」이 생기기 때문이다.

### 2.4 분실 · 탈취

1. 다른 PC의 앱(설정 서랍 「내 기기」) 또는 휴대폰에서 기기를 연결할 때 받은 메일의 링크 → 확인 쪽에서 **Google 로그인**(만료 없는 링크 하나로는 실행하지 않는다) → 「분실 신고」.
2. 서버가 즉시 그 기기의 쓰기 출입증과 **손님 읽기 출입증**을 지운다. 이때부터 전에 받은 봉투 · 복구 코드는 못 쓴다 — 화면에 「분실 신고 뒤에는 새 기기를 이을 때까지 서버가 필요하고, 전에 받은 복구 코드는 못 씁니다」를 적는다.
3. 화면이 「Google 계정에서 그 기기를 로그아웃하고 '업무 백업' 접근을 지우세요」를 바로 가는 주소와 함께 보인다. 분실한 PC의 갱신 토큰으로 봉투를 계속 읽을 수 있기 때문이다.
4. 남은 · 새 기기는 **자기 Google 토큰이 끊긴 것**으로 3이 끝났음을 확인하고 → 다시 로그인 → 서버가 새 읽기 출입증을 준다 → 새 봉투를 올려 다시 받아 확인 → 새 복구 코드를 권한다. 남은 기기가 하나도 없으면 새 PC의 옮겨 오기가 이 순서를 밟는다.
5. **남은 기기가 없을 때의 확인(다시 확인 F7).** PC가 한 대뿐인 손님의 새 PC에는 끊길 토큰이 없어, 손님이 3을 건너뛰어도 흐름이 지나간다. 그래서 (가) 새 PC가 로그인 직후 **자기 토큰을 Google 철회 주소로 스스로 끊고** 다시 로그인을 받는다 — Google의 철회가 그 계정 · 그 앱의 다른 갱신 토큰(분실 PC 것)에도 미치면 3을 앱이 대신 한 셈이 된다. 미치는지는 2주차 Google 로그인 자리에서 토큰 둘로 잰다. (나) 미치지 않으면 서버가 「분실 신고 뒤 첫 개통」임을 기억해, 새 봉투를 올리기 전에 「Google에서 접근을 지웠습니다」를 건너뛸 수 없는 걸음으로 띄우고, 화면 · QA에 「남은 기기가 없을 때는 손님 걸음에 기댄다」(관문의 「끊은 출입증의 읽기 거부」는 B2 출입증까지라는 뜻)를 적는다. T10의 「남은 기기 0」에 어느 쪽으로 확인했는지 적는다.

### 2.5 사고 뒤 되돌리기

설정 서랍 「사고가 났을 때 되돌리기」(또는 서버 탐지 알림) → 서버가 시간대별 숨김 · 올리기 수로 「대량으로 바뀌기 직전」을 기본 시각으로 내놓는다 → 미리 보기는 「그 시각의 완료본: 날짜 · 파일 수」(앱이 숨겨진 판을 읽어 해독한다 — M9) → 방금 한 Google 로그인으로 「되돌리기」 →

1. 서버가 그 손님의 쓰기 출입증을 모두 새로 바꾸고(요청한 기기만 새 것을 받는다), **손님 읽기 출입증도 새로 만든다** — 출입증을 빼앗긴 상황을 전제로 한 흐름이기 때문이다. 요청한 기기가 새 읽기 출입증으로 봉투를 다시 올려 받아 확인하면 서버가 옛 읽기 출입증을 지우고, 앱이 새 복구 코드를 권한다(다시 확인 N1). 이 PC가 감염됐을 수 있으면(같은 사용자 권한의 프로그램은 Google 토큰도 읽는다) 2.4의 Google 걸음(3~5)을 함께 밟는다.
2. 요청한 기기는 엔진 잠금을 쥔 채 기다린다. 쓰는 기기가 하나라 다른 쓰는 쪽이 없다.
3. 서버 도구가 더하는 일을 먼저(pack → 색인 → 판 → 열쇠 · 설정), 숨기는 일을 나중에(판 → 색인 → pack) 한다. 지우는 것은 없다. 도중에 멈춰도 다시 부르면 이어서 한다.
4. 앱이 저장소를 점검하고, **자동 백업과 정리를 멈춘 채** 손님이 파일을 꺼낼 수 있게 한다. 손님이 「여기서부터 계속」(되돌린 상태를 새 기준으로) 또는 「되돌리기 취소」(같은 도구로 되돌리기 직전 시각으로)를 고를 때까지다.
5. 요청과 실행은 그 계정의 모든 기기 알림 + 메일로 알린다.

## 3. 구조와 권한 경계

| 부분 | 하는 일 | 권한 | 떠 있는 때 |
|---|---|---|---|
| 화면 앱 `WorkBackup.exe`(Tauri) | 창, (설정에서 켤 때만) 트레이 | 사용자 보통 권한 | 사용자가 열었을 때만. 창을 닫으면 웹 화면을 내리고, 하던 작업이 끝나면 프로세스도 끝난다 |
| 회차 실행기 `WorkBackupRun.exe --run <계기>` | 백업 · 채움 · 점검 · 정리 · 증명 · 봉투 재확인 · 측정 보내기 · 알림 | 사용자 보통 권한(작업 스케줄러, 로그인한 동안) | 회차 동안만 |
| 도우미 `WorkBackupRun.exe --vss-helper` | 섀도 복사본 만들기 · 연결 · 지우기만(파일을 읽지도 올리지도 않는다) | 같은 사용자의 관리자 권한(관리자 계정일 때만) | 채움 판을 만드는 동안만 |
| 엔진(Node 워커 + restic 0.19.1) | 지금 엔진 + 1단계 고침 | 띄운 쪽의 권한(관리자 쪽에서는 돌지 않는다) | 회차 · 화면 작업 동안 |
| 개통 서버 | 초대 명단 · 출입증 발급과 끊기 · 되살리기 도구 · 저장소 탐지 · 회차 기록 · 메일 | 회사 서버 안 따로 둔 컨테이너 · 실행 사용자 | 늘 |
| B2 손님용 계정 · 버킷 | 손님별 접두사 저장소 | — | — |
| Google 앱 전용 공간 | 봉투(복구 암호 + 읽기 출입증) | 손님 Google 계정 | — |

권한 경계:

- **기기 쓰기 출입증**(쓰는 기기에만, DPAPI): 자기 손님 접두사 안의 목록 · 읽기 · 올리기 · 숨기기. 영구 삭제 · 출입증 만들기 · 버킷 설정은 못 한다. 올리기 권한에는 숨기기 · 같은 이름 덮어쓰기 · 접두사 안 복사가 들어 있으므로 「못 지운다」가 아니라 **「30일 동안 되돌릴 수 있게만 망칠 수 있다」**가 정확한 말이고, 화면 · 문서도 그렇게 쓴다.
- **손님 읽기 출입증**(봉투 · 복구 코드): 목록 · 읽기, 숨겨진 옛 판도 판 번호로 읽는다(M9).
- **서버 출입증 셋**(4.4): 출입증 일(만들기 · 지우기 · 목록)과 파일 일(되살리기 · 저장량 세기 — 삭제 권한 없음)을 서로 다른 출입증 · 프로세스로 나누고, 서버 밖 감사용(목록 · 버킷 설정 읽기만)을 따로 둔다. 출입증 만들기 권한은 B2 문서상 계정 전체 권한과 같다. 복구 암호는 서버에 없으므로 서버는 백업 내용을 읽지 못한다.
- **도우미**: 관리자 권한이지만 파일을 읽거나 올리지 않는다. 사용자 쓰기 폴더에 쓰지 않는다. 보통 권한이 고칠 수 있는 입력은 크기 제한을 둔 자료(볼륨 이름 · 요청 번호)로만 받는다(4.2).

## 4. 항목별 설계

### 4.1 한 줄기 · 엔진 갈래 · 창 닫기 · 잠금 둘 (로드맵 1)

- **Electron 0.5.0 동결.** `experiences/solo-backup/`은 고치지 않는다. 지금 Rust 판은 엔진을 `../solo-backup/src`에서 가져오므로(`scripts/stage-resources.cjs`), 엔진을 `experiences/solo-backup-rust/engine/`으로 **갈라 온다**. 첫 커밋은 `src` · `tests` · `package.json` · lock · 고지문을 바이트 그대로 복사하고 두 쪽 시험 결과가 같은지 보인다(T1 — 0.5.0 쪽 기준선 81개 중 통과 80 · 건너뜀 1, 11-12). 화면 원천도 `experiences/solo-backup-rust/ui/`로 옮긴다.
- **0.5.0 자료와의 관계:** 0.7.0은 0.5.0 저장소 · 봉투 v1을 읽지 않는다. 로드맵 9장의 「0.5.0 사본은 옮겨 오기 시험 재료」는 그 사본을 **읽기 전용 원본 자료**로 시험 저장소에 다시 백업해 쓰는 뜻으로 고쳐 읽는다(0.5.0 사본 자체는 1단계 끝까지 건드리지 않는다).
- **새 상태 폴더:** 설정 · 자격 · 기록은 `%APPDATA%\SynkWorkBackup`, restic 캐시 · 임시는 `%LOCALAPPDATA%\SynkWorkBackup`(100GB 저장소의 캐시가 수백 MB라 Roaming에 두지 않는다). 0.5.0(`SoloWorkBackup`) · 시험판(`SoloWorkBackupRustBeta`)과 따로이며 그 둘을 읽지도 쓰지도 않는다. Windows Run 시작 등록은 쓰지 않는다. 판 이름 0.7.0, 식별자 `im.synk.workbackup`.
- **잠금 둘.** 지금 하나뿐인 `native.lock`을 나눈다.
  - **엔진 잠금**(`engine.lock`) — restic을 돌리거나 설정을 쓰는 쪽이 쥔다. 회차 실행기는 회차 동안, 화면 앱은 작업(지금 백업 · 복구 · 옮겨 오기 · 설정 바꾸기)을 하는 동안만 쥔다. 쥘 때마다 설정을 디스크에서 다시 읽는다.
  - **화면 잠금**(`ui.lock`) — 창 하나만 뜨게 한다.
  - 그래서 회차가 도는 동안에도 앱은 언제나 열린다. 회차 실행기가 남기는 진행 파일(`progress.json`)로 「백업 중 N%」를 보이고, 그동안의 조작은 회차가 끝난 뒤로 미룬다. 화면 앱이 작업으로 엔진 잠금을 쥐고 있으면 회차는 「바쁨(화면 작업)」으로 기록하고 끝난다. 앞 판의 「회차를 화면 앱에 넘김」은 없앤다(응답 없는 창 앞에서 넘김만 쌓이는 문제를 없앤다).
  - 트레이 모드의 Rust 프로세스는 엔진 잠금을 쥐지 않는다. 채움 판을 만드는 동안 엔진 잠금은 회차 실행기가 쥐고, 도우미는 엔진 잠금과 상관없다.
- **창 닫기:** 닫으면 웹 화면을 없애고(WebView2 프로세스 0), 하던 작업이 있으면 화면 없이 마친 뒤 끝난다. 화면 앱 안의 30초 타이머 예약(`startScheduler`)은 끈다. 예약은 작업 스케줄러 하나다.
- **트레이(설정에서 켤 때만):** Rust 프로세스와 아이콘만 남기고 워커는 내린다(목표 30MB 이하, T14에서 잰다). 아이콘을 누르면 워커와 창을 다시 띄운다.

### 4.2 앱과 따로 도는 예약 (로드맵 2)

#### 회차 작업

- 사용자마다 계기별 작업 넷: `\SYNK 업무 백업\회차 - <계정 이름> - <계기> · <SID 짧은 표시>`(매시간 · 로그온 · 깨어남 · 잠금 해제). 작업 하나에 계기 넷을 걸면 동작 인자가 하나뿐이라 회차가 왜 시작됐는지 기록할 수 없어 나눴다(11-12 구현, [결정](../../docs/_ops/결정.md)). 넷이 겹치면 엔진 잠금에서 뒤 것이 「바쁨」으로 끝난다. 보안 주체는 그 사용자(프로세스 토큰의 SID — 환경 변수가 아니다), 「사용자가 로그온한 경우에만 실행」(InteractiveToken), 가장 낮은 권한 수준. 이름의 계정 이름은 토큰 SID로 찾은 이름(`USERNAME`은 비거나 다른 계정에게서 물려받을 수 있다), SID 짧은 표시는 SID의 SHA-256 앞 여섯 자리라 이름이 같은 다른 계정(도메인 · 로컬)과 갈린다. 덮어쓰거나 지우기 전에 작업 스케줄러가 저장한 주체(계정 이름만 남는다 — T2에서 확인)를 SID로 되풀어 내 작업인지 보고, 같은 이름에 다른 계정의 작업이 있으면 다른 자리로 넘어가지 않고 등록을 멈춘다(`SCHEDULE_FOREIGN`). 일부만 되면 원래 있던 작업은 원래 XML로 되돌린다.
- 계기 넷: 로그온(2분 늦춤), 매시간(무기한 반복), 깨어남(System 로그 `Microsoft-Windows-Power-Troubleshooter` 이벤트 1, 2분 늦춤), 세션 잠금 해제. 잠금 해제는 최신 대기(S0) 노트북에서 깨어남 이벤트가 최대 절전 복귀 때만 남는 것을 받친다.
- 설정: 배터리에서도 시작 · 배터리로 바뀌어도 멈추지 않음, 놓친 회차는 가능해지면 바로(StartWhenAvailable), 겹치면 새 것을 버림(IgnoreNew), 우선순위 7(보통 아래). 작업 스케줄러의 실행 시간 제한은 72시간으로 넉넉히 두고, **실행기가 스스로 시간을 재서 restic을 정상 종료**시킨다(강제 종료는 잠금을 남긴다).
- 동작: 설치 폴더 절대 경로의 `WorkBackupRun.exe --run hourly|logon|wake|unlock`.
- 만드는 때: 보호 시작 때 앱(보통 권한)이 작업 스케줄러 COM API로 만든다. 폴더 `\SYNK 업무 백업\`은 설치기(관리자)가 만들고 보통 사용자가 그 안에 자기 작업을 만들 수 있게 폴더 권한을 준다. 안 되면 뿌리 폴더에 사용자 이름을 붙인 작업으로 한다 — 이벤트 · 로그온 계기를 보통 권한으로 만들 수 있는지와 함께 실측했다(T2, 11-13 CI — 표준 사용자도 뿌리 · 폴더 둘 다 넷을 만들고 다시 읽고 지운다, [QA](QA.md#1단계-잠금-둘--회차-작업-등록--2026-11-13)). 한 자리에 넷이 다 되면 다른 자리의 같은 이름 작업은 지워 두 번 뜨지 않게 한다. 도우미 작업은 사용자가 작업을 만들 수 있는 이 폴더와 다른, 관리자만 쓰는 폴더 `\SYNK 업무 백업 도우미\`에 둔다.

#### 회차가 하는 일

1. 엔진 잠금을 잡는다(못 잡으면 「바쁨(화면 작업)」 기록 후 끝).
2. `restic unlock`(오래된 잠금만 — `--remove-all`은 쓰지 않는다). 도중에 죽은 회차가 남긴 잠금은 `check` · `forget`을 종료 11로 막고, restic도 앱도 스스로 치우지 않았다. 11-12 실측 M3b: 백업을 도중에 죽이면 잠금 1개가 남고 `check` 종료 11, 삭제 권한 없는 출입증의 `unlock`이 종료 0으로 그 잠금을 숨기고, 그 뒤 `check` · 백업 모두 0.
3. 쉼 판단: 배터리로 돌고 30% 아래 · 절전 모드 · 종량 회선(Windows 연결 비용이 「무제한」이 아님)이면 클라우드 올리기 · 구조 점검 · 증명을 쉬고 쉼 사유를 기록한다. 직접 누른 「지금 백업」은 예외다.
4. 할 때가 됐나: 마지막 시도가 55분 안이면 「아직」으로 바로 끝난다. 일시정지 · 시계 이상은 지금 규칙(`protection.cjs`) 그대로다.
5. 원본 폴더 확인: 없는 폴더는 그 폴더만 빼고 백업하고(지금은 하나만 없어도 회차 전체가 실패한다 — `paths.cjs`), 그 폴더가 든 마지막 판을 고정하고 알린다(「완료본 · 부분 판 · 채움 판」).
6. 용량 상한: 올리기 전에 원본 크기를 다시 훑는다(진단 계획기를 쓴다). 직전 판의 처리 바이트로만 보면 폴더에 200GB를 넣은 다음 회차가 통과해 전부 올린다.
7. 백업: `restic backup --exclude-cloud-files`(OneDrive 온라인 전용 파일은 읽는 순간 내려받히므로 백업하지 않는다 — 보호 범위 화면에 「OneDrive에만 있는 파일 N개는 OneDrive가 지킵니다」를 보이고, 용량 상한도 디스크에 있는 것만 센다).
8. 결과 나누기: 종료 0 → **온전 판**. 종료 3 → **부분 판** — 못 읽은 목록 U는 restic **표준 오류의 JSON 줄**(`message_type: error`)의 `item` 경로에서 모으고(오류 글은 Windows 언어에 따라 달라 기대지 않는다, 줄 수가 많아도 잘리지 않게 따로 모은다), 실행기가 그 파일을 직접 열어 보아 공유 위반(오류 32 · 33)인지 확인한다. 종료 11 → 「바쁨 — 다음 회차에」(점검 실패로 적지 않는다, 회차에서는 `--retry-lock`을 길게 준다).
9. 부분 판이고 U에 공유 위반 파일이 있으면 도우미에게 섀도 복사본을 부탁해 **채움 판**을 만든다(아래).
10. 점검: 회차마다 `check --with-cache`, 캐시 없는 구조 점검은 하루 한 번, 내용 읽기 점검은 4주에 걸쳐 1/4씩 매주(`--read-data-subset`). 덮어쓰기는 구조 점검에 안 잡히므로(검토 실험) 서버 탐지(4.4)가 하루 안에 잡는다.
11. 정리(아래 「완료본 · 부분 판 · 채움 판」의 규칙과 4.4의 대량 변경 멈춤).
12. 날마다 할 일: 증명(매주), 봉투 재확인(하루), 측정 보내기.
13. 회차 기록 · 진행 파일 · 알림 판단 → 엔진 잠금을 놓고 끝.

실행기 · 워커 · restic은 모두 「보통 아래」 우선순위로 돈다. I/O 우선순위를 더 낮출지는 처음 백업 속도 기준(70%)을 재고 정한다. 로그오프 · 시스템 종료 알림을 받으면 같은 정상 종료 길로 끝낸다. 정상 종료 수단(restic에 중단 신호를 보내는 법)은 구현에서 재고, 안 되더라도 다음 회차의 2번이 받친다.

#### 완료본 · 부분 판 · 채움 판

「최신 완료본 + 24시간」 규칙에서 새 판에 빠진 것은 24시간 뒤 사라진다. 빠지는 길은 셋이다 — 못 읽은 파일, 사라진 원본 폴더, 사용자가 뺀 폴더. 검토 실험대로 **바뀐 뒤 잠긴 파일은 종료 3이고 새 판에 통째로 없다**(바뀌지 않은 잠긴 파일은 열지 않으므로 종료 0, 앞 판 내용이 이어진다). 그래서 이렇게 정한다.

- **판의 종류(꼬리표):** 온전 판(`complete`), 부분 판(`partial` + 못 읽은 목록 U), 채움 판(`fill` + 어느 부분 판을 채우는지). U와 채움 경로 맞추기 정보는 작은 JSON으로 같은 저장소에 함께 넣는다(새 PC에서도 읽힌다).
- **「지금 상태」로 되살리기:** 이 기기의 가장 새 판 S를 기준으로 하고, S가 부분 판이면 U의 파일은 S를 채운 채움 판에서, 없으면 그 파일이 든 가장 새 판에서 가져온다. 화면은 「N개 파일은 [날짜] 판에서 가져옵니다」.
- **정리 규칙(이 기기 판만):** 가장 새 판 하나, 가장 새 온전 판(또는 채움으로 다 채운 부분 판) 하나, 가장 새 판의 U 파일마다 그 파일이 든 가장 새 판, 고정된 판(사라진 폴더 · 뺀 폴더 · 대량 변경 멈춤 · 되돌린 뒤 · 옮겨 오기 원본)은 남기고, 나머지 24시간이 지난 판은 정리한다. 부분 판은 pending으로 쌓이지 않는다 — 가장 새 부분 판 하나만 남긴다. **판을 남기면 그 판에 딸린 채움 판 · meta 판도 함께 남긴다**(다시 확인 N3 — 안 그러면 남긴 부분 판의 U 파일이 사라진다).
- **순서:** U 목록은 백업이 끝나야 안다. meta 판(U · 채움 경로 맞추기)이 저장된 **뒤에만** 부분 판 꼬리표를 붙이고, meta 없는 판은 되살리기 · 정리 계산에 쓰지 않는다(그 사이에 죽으면 「U를 모르는 부분 판」이 남아, 그것으로 되살리면 파일이 말없이 빠진다).
- **한 번도 읽힌 적 없는 파일:** 권한이 거부된 파일처럼 어느 판에도 든 적 없는 파일만 U에 남으면 온전 판이 다시는 안 생겨 옛 온전 판이 영영 고정된다. 그런 U만 남은 판은 「더 채울 것이 없는 판」으로 쳐 온전 판 자리를 잇게 하고, 그 파일은 「읽을 수 없는 파일 N개」로 한 번 알린다. 표준 사용자의 늘 잠긴 파일 알림도 날마다가 아니라 처음과 오래 이어질 때(일주일)만 띄운다.
- **온라인 전용으로 바뀐 파일:** OneDrive가 저절로 비운 파일은 다음 판에서 빠진다. 정책대로 지키지 않되(4.2의 7), 대량 변경 비교는 디스크에 자리표시자가 남아 있는 것을 「지워짐」으로 세지 않는다 — 한꺼번에 비울 때마다 거짓으로 멈추지 않게.
- **사라진 원본 폴더:** 그 폴더만 빼고 백업하고, 그 폴더가 든 마지막 판을 고정하고 「폴더를 찾을 수 없음 → 다시 고르기 · 빼기」를 알린다. 외장 드라이브를 일주일 빼 둬도 그 폴더의 하나뿐인 백업이 사라지지 않는다.
- **폴더 더하기 · 빼기:** 지금 엔진은 설정 뒤 폴더 변경을 막는다(`handlers.cjs`). 1단계에서 연다. 뺄 때는 「이 폴더의 백업은 30일 뒤 지워집니다」를 보이고 그때까지 그 폴더가 든 마지막 판을 고정한다.
- **늦어질 때의 최소:** 채움 판 전체가 5주 안에 안 되면 ① 부분 판을 가장 새 것 하나만 남기고 ② 알림을 「몇 파일만 못 지킴」으로 하고 ③ 「파일 되살리기」에서 부분 판을 고를 수 있게 하는 데까지 하고, 그 경우 관문의 「열린 파일」 기준은 못 넘었다고 QA에 적는다.

#### 도우미 — 섀도 복사본만 만든다

검토(F4)가 앞 판의 도우미(관리자 restic이 원본을 직접 읽고 사용자 폴더에 쓰는 꼴)에서 두 통로를 실험으로 보였다. 첫째, 확인과 읽기 사이에 원본 경로의 **중간 폴더**를 연결점으로 바꾸면 restic이 따라가 남의 파일을 백업에 싣는다. 둘째, 관리자 프로세스가 사용자 쓰기 폴더(설정 · 캐시 · 임시)에 쓰면, 그 폴더를 미리 연결점으로 바꿔 관리자 쓰기를 다른 자리로 돌릴 수 있다. 그래서 도우미가 하는 일을 줄인다(검토 권고 A).

- **도우미가 하는 일:** 요청받은 볼륨(고정 로컬 NTFS)의 섀도 복사본을 WMI로 만들고(`Win32_ShadowCopy.Create`), 관리자만 쓰는 작업 폴더(`%ProgramData%\SynkWorkBackup\helper\<사용자 SID>\`, 그 사용자는 읽기 · 지나가기만) 안에 그 복사본을 가리키는 연결을 만들고, 요청한 회차 실행기가 끝나면 연결과 섀도 복사본을 지운다. 파일을 읽지도, 올리지도, 사용자 폴더에 쓰지도 않는다. 관리자 쪽에서 Node · restic을 돌리지 않는다(Rust만).
- **채움은 보통 권한 회차가 한다:** 회차 실행기가 그 연결 아래의 U 파일 경로로 `restic backup`을 돌려 채움 판을 만들고, 연결 접두사를 원래 경로로 되돌리는 맞추기 정보를 함께 넣는다. 섀도 복사본은 파일 권한을 그대로 지키므로 사용자는 원래 읽을 수 있는 것만 읽는다 — 관리자 쪽에 「읽어서 내보내는」 기능이 아예 없다.
- **입력과 확인:** 요청 파일(사용자 상태 폴더의 `vss-request.json`)은 연결점을 따라가지 않게 열어 크기 제한을 두고 자료로만 읽는다 — 볼륨 이름 목록과 요청한 실행기의 프로세스 번호뿐이다. 도우미는 그 프로세스가 설치 폴더의 실행기이고 같은 사용자인지 확인하고, 그 프로세스가 끝나면(또는 상한 시간이 지나면) 정리한다. 하루 만들기 횟수 상한과 「내가 만든 섀도 복사본 번호」는 관리자만 쓰는 폴더에 두고, 도우미가 시작할 때 남은 것을 먼저 지운다.
- **채움의 비용(다시 확인 N4):** 연결 이름은 볼륨마다 **고정**한다(`…\helper\<SID>\snap-C` 같은 꼴). 요청마다 이름이 다르면 restic이 앞 채움 판을 부모로 못 써서, 잠긴 큰 파일(10GB 메일 보관 파일 같은 것)을 매시간 통째로 다시 읽는다. 채움은 하루 6번까지(4시간에 한 번) 하고, 그 사이 회차는 부분 판으로 둔다. `Win32_ShadowCopy.Create`로 만든 것은 다시 켜도 남으므로 지우기(설치 제거)에서 남은 섀도 복사본 · 도우미 폴더를 함께 치운다. 시스템 보호가 꺼진 볼륨에서도 만들어지는지는 T5에서 본다.
- **시작할 때 확인:** ① 자기 실행 파일 · 그 위 폴더(Program Files까지)의 소유자가 관리자 · SYSTEM · TrustedInstaller이고 그 밖의 누구에게도 쓰기 · 고치기 · 지우기 · 권한 바꾸기 · 소유자 바꾸기가 없다 ② 경로를 환경 변수에서 읽지 않는다(실행 파일 위치는 `GetModuleFileName`, Windows 폴더는 API — 작업 스케줄러가 사용자 환경 변수를 물려주므로 예전 SilentCleanup처럼 `%windir%` 바꿔치기를 막는다) ③ 「보통 권한이 만든 연결점은 따라가지 않는다」는 Windows 완화 정책(리디렉션 신뢰)을 켠다.
- **등록:** 설치기(관리자)가 설치 끝에 `WorkBackupRun.exe --register-helper`를 부른다. 관리자 확인을 한 계정이 설치기를 띄운 세션에 로그인한 계정과 같을 때만(설치기 자신의 세션 번호로 찾은 세션 사용자의 SID와 관리자 토큰의 사용자 SID를 견준다 — 콘솔 세션은 원격 접속 · 사용자 전환 중이면 다른 사람일 수 있다) 그 사용자의 도우미 작업을 「가장 높은 수준의 권한으로 실행」 · 계기 없이 만든다. 작업 보안 설명자는 관리자 · SYSTEM 전체, 그 사용자는 읽기 · 실행만이다. 동작은 고정 인자(`--vss-helper`)뿐이고 `$(Arg)` 치환을 쓰지 않는다.
- **표준 사용자:** 다른 사람이 관리자 암호를 넣어 준 표준 사용자에게는 도우미가 없다. 부분 판 규칙으로 지키고, 화면에 「이 계정은 표준 사용자라, 켜진 프로그램이 쥔 파일은 그 프로그램을 닫았을 때 새로 담깁니다」를 적는다.
- **먼저 잴 것(T5):** 보통 권한 프로세스가 도우미가 만든 연결을 지나 섀도 복사본의 파일을 읽을 수 있는지, restic이 그 경로로 채움 판을 만들 수 있는지. 관리자 확인이 켜진 PC에서만 뜻이 있어(CI 실행기는 꺼져 있다) 이 PC 시험 설치를 2주차로 앞당긴다(11장). **안 되면** 검토 권고 B(관리자 restic을 쓰되 원본 폴더 핸들을 쥐어 조상 이름 바꾸기를 막고, 관리자만 쓰는 작업 폴더에 캐시 · 임시를 두고, Node 없이 Rust가 restic을 부르고, 백업까지만 하고 점검 · 승격은 보통 회차가)로 가고 그 까닭을 결정 표에 적는다.

#### 회차 기록

`runs.jsonl` 한 줄에 계기, 시작 · 끝, 결과(complete · partial · fill · skipped · failed · busy · not-due), 쉼 사유, 종료 코드, 못 읽은 파일 수, 새로 · 바뀐 · 그대로인 파일 수, 더한 바이트, 처리한 바이트, 워커 준비까지 ms, restic 시작까지 ms, 작업 객체의 최대 메모리(`PeakJobMemoryUsed`) · CPU 시간, 측정 판에서는 주고받은 바이트를 적는다. 1MB마다 돌려 쓴다. 파일 이름 · 경로는 넣지 않는다.

주고받은 바이트는 restic에 `HTTPS_PROXY`로 실행기 안의 작은 CONNECT 프록시를 주고 양쪽 바이트만 세어 잰다(TLS는 끝까지 그대로). 측정 판 설정에서만 켠다.

「회차 빠짐」은 PC가 깨어 있고 사용자가 로그인한 시간마다 회차 기록이 하나 이상 있는지로 센다. 잠든 시간은 System 로그에서 S3 대기(Kernel-Power 42 잠들기 · Power-Troubleshooter 1 깨어남)와 최신 대기(Kernel-Power 506 · 507)를 모두 읽어 빼고, 앞 회차가 돌고 있던 시간은 따로 센다. 설치 때 `powercfg /a`의 대기 방식을 측정 항목에 넣는다(이 PC는 S3 대기). Task Scheduler 운영 로그는 켜지 않는다(시스템 설정 변경).

#### 알림

- Windows 알림(토스트). 앱 식별자(AUMID)는 설치기가 시작 메뉴 바로 가기에 붙인다. 문구는 2.2 표.
- 누르면 `synk-workbackup:open?topic=<정해진 낱말>`로 화면 앱이 그 화면을 연다. 주소는 인자 하나 전체를 고정 목록과 정확히 견주고, 주제에는 「기기 끊기 실행」 · 「되돌리기 실행」처럼 한 번 누르면 실행되는 화면을 넣지 않는다(웹 쪽이 그 화면을 띄워 놓고 누르게 만들 수 있다). 배포 판에서는 시험 · 이전 인자(`--test-mode` · `--smoke` · `--migration-preview`)를 컴파일에서 뺀다.
- 같은 문제는 하루 한 번(`notify.json`). 해결되면 그 문제의 기록을 지운다.
- 실측: 보통 권한 회차의 알림이 실제로 떴는지는 `ToastNotificationManager.History`로 우리 앱 알림이 알림 센터에 있는지 읽어 센다. 화면 조작은 하지 않는다(T4).

- 설치 끝 「앱 열기」는 설치기의 관리자 토큰이 아니라 **로그인한 사용자 · 보통 권한으로** 띄운다. 그러지 않으면 다른 사람이 관리자 암호를 넣어 준 PC에서 그 관리자 계정으로 첫 설정이 진행된다. 첫 실행의 계정과 권한 수준을 T5 · T13에서 확인한다.
- 설치기가 하는 일: 파일 복사, 시작 메뉴 바로 가기(AUMID 포함), `synk-workbackup:` 주소 처리기(HKLM, 화면 열기만), 작업 폴더 둘(사용자용 · 도우미용)과 그 권한, 도우미 등록(위 조건).
- 지우기: 작업(다른 사용자의 회차 작업 포함) · 바로 가기 · 주소 처리기, 도우미가 만들고 남긴 섀도 복사본 · 도우미 폴더를 지운다. 사용자 상태와 클라우드 백업은 지우지 않는다(T19).

### 4.3 Node 워커 — 재고 나서 옮긴다 (로드맵 3)

- 2주차 첫머리에 같은 합성 자료(D1)로 잰다: 회차 시작(작업 시작 → restic 시작), 회차 최대 메모리(작업 객체 Peak), CPU 시간, 설치 크기. 넘으면 이식이 5주 밖의 일이 되므로 일찍 잰다.
- 비교 기준은 같은 회차를 Rust가 restic을 바로 부르는 시험 실행기(백업 · 구조 점검만)로 돌린 값이다.
- 옮기는 문턱: 회차 시작이 3초를 넘거나, 회차 메모리가 Rust만 쓸 때보다 100MB 넘게 크면 회차가 쓰는 부분(예약 · 백업 · 점검 · 정리 · 증명)부터 Rust로 옮긴다. 옮길 때는 엔진 시험 전부를 Rust 시험으로 옮겨 같은 결과를 내게 한다. 복구 · 검색은 다음 단계다.
- 문턱 안이면 1단계에서는 옮기지 않는다(지금 설치 크기 143MB도 150MB 안이다). 판단과 숫자를 QA에 남긴다.
- **11-12 T7 결과 — Node 그대로**([QA](QA.md#1단계-회차-실행기와-t7--2026-11-12)): 같은 판의 두 번째 회차부터 restic 시작까지 0.27~0.69초, 워커 자체 최대 44~56MB. 빌드 직후 첫 회차만 3.8초였고 새 복사본 재측정으로 새 파일을 처음 열 때 한 번 드는 값(2.2~2.4초)임을 확인해, 시작 문턱은 「같은 판의 두 번째 회차부터」로 잰다. 72시간 예행에서 다시 켠 뒤 첫 회차가 3초를 넘으면 다시 연다.
- 리소스 확인 비용: 지금 `verify_resources`는 리소스 전체(약 143MB)를 해시한다. 매시간 회차마다 하면 회차 시작 3초와 배터리에 든다. 회차 실행기는 자기가 실행하는 파일(node · restic · 워커 · 엔진)만 해시하고 설치 폴더 권한을 확인하는 것으로 갈음할 수 있는지 T7에서 잰다. 전체 확인은 화면 앱 시작 · 업데이트 뒤에 한다.
- 실행기는 워커를 화면 앱과 같은 통신(표준 입출력 프레임)으로 부른다. 옮기게 되면 워커 자리에 Rust 엔진을 끼우면 된다.

11-12 시험 버킷 실측([QA](QA.md#1단계-시험-버킷-실측-m1m7--2026-11-12)): listBuckets가 없으면 버킷 확인이 403이고 restic이 저장소 설정 파일조차 못 읽어 만들 수 없다(그래서 기기 · 읽기 출입증 모두 listBuckets를 둔다). 삭제 권한 없는 출입증의 판 지정 없는 삭제는 204 + 숨김 표시로 끝나고, 판 지정 삭제는 403이다. forget · prune · unlock도 그 출입증으로 끝까지 돌며 영구 삭제는 0건이었다. 그래서 restic S3 통로 그대로 안전망이 된다. 손님 읽기 출입증은 숨겨진 옛 판을 판 번호로 읽는다(S3 `versionId` · 기본 API 둘 다 200, M9). 출입증 이름에 메일 · 사람 이름을 넣지 않는다.

#### 수명 규칙과 버킷 설정 (손님 버킷)

- 접두사 ""(버킷 전체) 규칙 하나: 숨긴 지 30일 뒤 삭제(11-12 유호님 「30일로 넣기」), 올린 뒤 숨기기는 없음, 끝나지 않은 큰 파일은 1일 뒤 취소.
- B2 수명 규칙은 하루 한 번 돈다. 새 판이 올라와 덮인 옛 판도 「숨김」으로 세어 30일 뒤 지운다(공식 문서). 그래서 덮어쓰기 공격도 30일 안에는 되돌릴 수 있다. B2는 겹치는 규칙 가운데 가장 작은 값을 쓰므로, 매일 대조(4.5)가 「규칙이 정확히 이것 하나」인지 본다.
- 올리는 쪽이 올린 시각을 정하는 기능(사용자 지정 올린 시각)은 손님 계정에서 켜지 않는다 — 켜면 쓰기 출입증으로 「T 전」 판을 만들어 되살리기 도구를 속일 수 있다.
- 비용: 숨긴 판은 30일 동안 저장비가 든다. 내부 24시간 정리로 날마다 숨겨지는 양(변경량)이 30일 쌓인다. 72시간 시험과 합성 자료로 「원본 대비 늘어나는 비율」을 재서 QA에 적는다(M5는 합성 자료라 작았다).
- 수명 규칙의 실제 동작(숨김 표시로 숨긴 것 · 덮여서 옛 판이 된 것 · 표시를 지워 되살린 것 · 복사로 되살린 것)은 시험 버킷 `ci/`(숨긴 지 1일 뒤 삭제)에서 사흘 동안 본다(M8, 11-12 설치 → 11-14 이후 확인).

#### 되살리기 도구 — 「이 시각으로 되돌리기」

서버의 파일 프로세스가 그 손님 접두사 안에서만 한다(B2 기본 API). **늘 복사한다 — 도구에는 영구 삭제 호출이 없다**(검토 Q5).

1. 접두사의 모든 판을 읽는다(`b2_list_file_versions`). `locks/`는 계산에서 뺀다.
2. 이름마다 「T 시각의 상태」(T 전 마지막 판이 올리기면 그 판, 숨김이거나 없으면 없음)와 「지금 상태」를 견준다. restic은 `config` 말고는 모든 파일 이름이 내용의 SHA-256이고 B2 서버 안 복사는 SHA-1을 그대로 둔다. 그래서 **같은 이름 · 같은 SHA-1 · 같은 크기는 같은 판**으로 본다(앞서 되살린 복사본), SHA-1이 다르면 덮어쓰기다.
3. T에 있었는데 지금 숨겨졌거나 다른 판이면 → T의 판을 서버 안에서 복사해 새 최신 판으로 만든다(`b2_copy_file`). T에 없었는데 지금 있으면 → 숨긴다(되돌릴 수 있다). 그 밖은 그대로.
4. 차례는 더하기 먼저(data → index → snapshots → keys → config), 숨기기 나중(snapshots → index → data). 도중에 멈춰도 보이는 것이 필요한 것보다 많은 쪽이라 restic이 열 수 있다.
5. 미리 보기와 실행 사이에 판이 바뀔 수 있으니 실행 직전에 목록을 다시 읽어 다시 계획한다. 이미 복사된 것은 2의 규칙으로 건너뛰므로 멈춘 뒤 다시 부르면 이어서 한다.
6. 한 일(복사한 판 · 숨긴 판 · 원래 숨긴 시각)을 서버 기록에 남긴다. 숨김 표시를 지우지 않으므로 「언제 숨겨졌나」가 B2에 그대로 남아 두 번째 되돌리기도 정확하다. 「되돌리기 취소」는 같은 도구를 되돌리기 직전 시각으로 부르는 것이다.
7. T가 29일보다 오래면 거절한다(수명 규칙이 하루 한 번 돌아 30일째 것은 이미 지워졌을 수 있다).
8. 2.5의 순서(쓰기 출입증 교체 → 쓰는 기기 대기 → 도구 → 점검 → 자동 백업 · 정리 멈춤 → 손님 고르기)를 지킨다. 대표가 손으로 하지 않는다. 손님 앱 → 서버 API다.

11-12 실측(M4 · M4b): 같은 출입증으로 전부 forget · prune, 설정 · 열쇠 파일 삭제, pack 덮어쓰기를 해서 저장소를 열 수 없게 만든 뒤, 늘 복사하는 도구가 판 10개를 복사해 7.6초 만에 되돌렸다. 두 판 모두 되살았고 `check --read-data` 0, 손님 읽기 출입증으로 꺼낸 66/66 해시 일치, 바로 다시 계획하면 할 일 0이었다. 복사한 만큼의 저장비는 옛 판이 지워질 때까지(길어야 30일) 두 번 든다 — 100GB면 한 달 1달러 안쪽이다.

#### 저장소가 바뀌었는지 서버가 매일 본다

안전망은 「30일 안에 알아채고 되돌린다」가 전제인데, 같은 이름 · 같은 크기로 pack을 덮어쓰면 구조 점검이 통과하고(검토 실험), 내용 읽기 점검만 잡는다. 그래서 서버의 매일 저장량 세기(어차피 모든 판을 읽는다)에 탐지를 더한다 — 내려받기도 복구 암호도 필요 없다.

- 같은 이름에 올리기 판이 둘 이상인데 SHA-1이 다름(도구의 복사 기록에 없는 것) — restic은 같은 이름을 다른 내용으로 두 번 올리지 않는다.
- `config` · `keys/`가 숨겨지거나 새로 올라옴.
- 하루 숨김 수가 그 기기가 보낸 회차 기록(정리한 판 수)과 안 맞게 큼.
- 걸리면 손님 메일 + 앱 알림 「백업이 바뀌었습니다 — 되돌릴 수 있는 날이 N일 남았습니다」, 운영자 메일. 내용 읽기 점검은 4주에 걸쳐 1/4씩 매주 돌려 따로 받친다.

#### 대량 삭제 · 변경 멈춤 (조사 문서 「다음 3」)

- 정리로 사라질 판 가운데 가장 새 것과 남을 최신 완료본을 `restic diff --json`으로 견준다. 바로 앞 판과 견주면 한 시간치 변화만 보아, 몇 시간에 걸친 암호화 · 삭제를 놓친다.
- 처음 문턱(시험으로 맞춘다): 지워진 파일이 30% 이상이면서 200개 이상, 또는 내용이 바뀐 파일이 50% 이상이면서 200개 이상, 또는 지워진 바이트가 30% 이상이면서 1GB 이상.
- 걸리면 정리를 멈추고 그 판을 번호로 고정한다(사용자가 답할 때까지 끈끈하게). 알림 「많은 파일이 한꺼번에 지워지거나 바뀌었습니다. 확인하기 전까지 이전 판을 지우지 않습니다」 → 화면에서 「내가 한 일이 맞음」 · 「바뀌기 전 판으로 되살리기」.
- 폴더 목록을 바꾼 직후, 기기의 첫 백업, 되돌린 직후는 비교에서 뺀다. 이름 바꾸기 · 폴더 옮기기는 diff에 지움과 더함으로 나와 잘못 걸릴 수 있다 — T17에서 문턱을 맞추고, 「랜섬웨어 감지」라고 부르지 않는다.

### 4.5 Google 로그인 하나로 시작 — 시범 규모 개통 (로드맵 5)

#### 흐름과 인증

앱이 개통 서버에서 한 번 쓰는 nonce를 받는다 → Google 로그인(지금의 PKCE · 데스크톱 클라이언트, 범위 `openid email drive.appdata`, nonce는 서버가 준 것) → ID 토큰을 서버에 보낸다 → 서버가 Google 공개 열쇠로 서명 · 대상 · 발급자 · `email_verified` · **nonce**를 확인한다(데스크톱 클라이언트의 ID는 설치 파일에 있어 「대상 = 우리 클라이언트」만으로는 우리 앱이 받았다는 증명이 안 된다 — nonce가 훔친 ID 토큰의 재사용과 갱신 토큰으로 받은 ID 토큰을 가른다) → 처음이면 초대 명단의 메일과 맞추고 손님을 **Google sub로 묶는다**(그 뒤로는 sub로만 찾고, 같은 메일에 다른 sub가 오면 거절) → 「기기 개통」.

- **개통은 두 걸음:** 서버가 손님 자리(처음이면 손님 번호와 접두사 `c/<무작위 16자>/`)와 기기 쓰기 출입증(+ 처음이면 손님 읽기 출입증)을 만들어 한 번 돌려준다 → 앱이 DPAPI로 보관했다고 알린다. 몇 분 안에 알리지 않은 출입증은 서버가 지운다(서버는 비밀값을 저장하지 않으므로, 응답이 사라지면 주인 없는 출입증이 남고 손님은 하루 상한에 걸린다).
- 앱이 저장소를 만들고(`restic init`), 복구 암호와 읽기 출입증을 봉투에 넣고 다시 내려받아 확인한다 → 예약 등록 → 첫 백업.
- **토큰마다 할 수 있는 일:** 기기 토큰은 측정 보내기 · 상태 읽기까지만. 새 출입증 발급 · 기기 끊기 · 되돌리기는 서버 nonce가 맞는 **방금 한 Google 로그인**을 요구한다.
- **서버 주소는 실행 파일에 박는다.** 사용자가 쓸 수 있는 파일에서 읽으면 바꿔치기한 주소로 ID 토큰이 간다.
- **손님 읽기 출입증은 손님당 하나**다. 둘째 기기는 봉투에서 받는다. 서버가 새로 만드는 때는 분실 신고 · 되돌리기 뒤뿐이고, 그때 봉투 · 복구 코드를 바꾼다(2.4). 지금 `recovery-vault.cjs`의 읽기 출입증 접두사 규칙(`work-backup/<보관함>`)은 새 접두사를 거절하므로 같이 고친다.

#### 제한

- 초대 명단(시범자 메일)에만 개통한다. 명단은 서버 관리 명령으로 넣는다. 메일 주소는 저장소에 적지 않는다.
- 손님당 **쓰는 기기 1 + 읽기만 하는 기기 2**, 출입증 만들기 하루 5번, 요청 속도 제한.
- 앱: 회차마다 원본 크기를 다시 훑어 상한(시범 100GB)을 막는다(4.2의 6).
- 서버: 접두사별 저장량(보이는 것 · 숨긴 것)을 매일 센다. 상한의 1.5배를 넘으면 그 손님 앱에 「용량 초과」를 알리고 올리기를 멈춘다. 출입증은 끊지 않는다.
- B2 계정 지출 상한(저장 · 내려받기 · 거래)을 콘솔에서 건다(11장). 상한에 닿으면 그 계정 손님 **모두**의 올리기가 멈춘다 — 시범 규모에서는 감수하고, 서버가 하루치 급증을 보면 그 기기 출입증만 끊는 길을 둔다. 올리기 상한은 앱이 지키는 약속이라, 고친 앱이나 빼앗긴 출입증은 무시할 수 있다는 것도 적어 둔다.

#### 계정 분리와 운영 탈취 대비

- 손님 자료는 시험 · 0.5.0과 **다른 B2 계정**에 둔다(가입은 유호님 — 2주차 안에, 11장).
- 개통 서버는 회사 서버의 **같은 compose 프로젝트 안 따로 떨어진 서비스**다. 회사 스택 스크립트가 그 프로젝트를 올리고 내리므로 별도 compose면 장애 조치 · 건강 확인 밖에 놓인다. 자기 이미지 꼬리표(회사 이미지와 따로 올릴 수 있게) · 자기 실행 사용자 · 자기 볼륨 · 자기 비밀값 파일 · Caddy만 닿는 자기 네트워크를 준다. 회사 Caddy에 `/backup-api/` 길 하나를 더한다. HA 조정기 · 백업 스크립트와의 맞물림은 구현 전에 회사 서버 담당 원문으로 확인한다.
- SQLite는 지속 디스크에 두고 회사 백업에 넣는다. 이 DB를 잃으면 「Google 계정 ↔ 접두사」가 사라져 손님이 자기 자리에 다시 개통할 수 없다(봉투로 읽기 복구는 된다). 덤프에는 메일 주소와 토큰 해시가 든다.
- 출입증 일 · 파일 일 프로세스를 나눈다(4.4 표). 되살리기 도구의 버그가 출입증을 건드리지 못한다.
- **매일 대조**(개통 서버 안 + 서버 밖 감사 예약): 서버가 만들지 않은 출입증, 삭제 · 출입증 · 버킷 권한이 있는 출입증(서버 자기 것 제외), 접두사 없는 손님 출입증, 그리고 **버킷 설정** — 수명 규칙이 정확히 기대값 하나인지 · 복제 규칙 · 기본 암호화. 어긋나면 운영자 메일. 대조가 서버 안에서만 돌면 서버가 털렸을 때 대조도 같이 털리므로, 목록 · 설정 읽기만 하는 감사 출입증으로 GitHub Actions 예약 실행에서도 하루 한 번 본다.
- GitHub Actions 비밀값에는 시험 버킷의 쓰기(삭제 없음) · 읽기 출입증과 감사 출입증만 넣는다. 출입증 만들기 권한은 넣지 않는다.
- 서버까지 털렸을 때 쓸 사본은 3단계 전에 정한다. 후보와 한계는 9장 Q10. 2단계부터 남의 실자료가 올라오고 그 관문이 「데이터 사고 0」이므로, 고른 안이 싸면 2단계 시작 전에 켜는 쪽을 유호님께 여쭙는다.

#### 메일

메일 보내는 길은 이미 있다. PULSE가 쓰는 **메일 중계**(founder@synk.im 소유 Apps Script 웹 앱 · `script.send_mail` 범위 · 회사 서버가 RSA로 서명한 요청만 받고 같은 열쇠의 메일은 한 번만 보냄 · 하루 상한, `docs/마케팅/온라인마케팅지도/engagement/company/pulse-mail-relay/`)와 같은 꼴로, 업무 백업용 중계를 따로 배포하고 개통 서버가 자기 열쇠로 서명한다. 보내는 이름 · 받는 회신 주소 · 문구는 유호님이 고른다(11장). 사흘 메일은 서버가 멈췄던 동안에는 보내지 않는다.

#### 봉투 v3와 Google 프로젝트

- 봉투는 복구 암호 + 그 손님 접두사의 읽기 출입증 + 저장소 위치 · 번호다. 서버가 멈추거나 사업을 접어도 새 PC 복구와 「통째로 받기」가 된다(분실 신고 직후는 예외 — 2.4). 올린 뒤 다시 받아 내용 · 계정 · 해시를 대조하고 하루 한 번 재확인하는 지금 방식을 그대로 쓴다.
- 손님을 받기 전에 백업 전용 Google 프로젝트로 나누고 운영 게시로 바꾼다(「시험 중」이면 갱신 토큰이 7일에 끊겨 하루 재확인이 멈춘다). `drive.appdata`는 민감 범위 검증 대상이 아니다. 운영 게시 때 동의 화면에 홈페이지 · 개인정보 처리방침 주소가 필요한지 콘솔에서 먼저 본다 — 필요하면 「약관 · 개인정보 문구는 요청하실 때」와 부딪혀 유호님 차례가 하나 더 생긴다. 0.3.0 때 계정의 프로젝트 수 한도로 새 프로젝트를 못 만들었으니 안 쓰는 프로젝트 정리나 한도 요청이 들 수 있다. 앱 전용 공간은 프로젝트마다 따로라 새 봉투가 0.5.0 봉투와 섞이지 않는다.
- 갱신 토큰이 7일 뒤에도 사는지는 72시간 시험으로 못 본다 — 「참고」로 2단계에서 본다.

### 4.6 새 PC로 옮겨 오기 v1 (로드맵 6)

#### 기존 경계를 바꾸는 일 — 따로 짚는다

지금(0.5.0 · Rust 시험판)은 원래 작업 폴더와 백업 저장소를 복구 대상으로 고를 수 없고, 늘 새 하위 폴더(`01-폴더이름`)에 쓴다. 1단계에서 바꾸는 것: **「옮겨 오기」 흐름에서만** 원래 자리에 쓴다(검토 Q1: 조건을 달아 받아들임). 지키는 것은 이렇다.

- **덮어쓰지 않는다 — 수단까지 못 박는다.** Node `fs.rename` · Rust `std::fs::rename` · 엔진 `atomic()`은 Windows에서 있는 파일을 덮는다(검토 실험). 그래서 임시 이름에 쓴 뒤 Rust 호스트 호출로 `MoveFileExW`를 **바꾸기 없이**(`MOVEFILE_REPLACE_EXISTING` 없이) 부른다. 「이미 있음」으로 실패하면 그때 견준다 — 크기 · 시각이 같으면 「이미 있음」, 다르면 내려받아 SHA-256으로 견주고 같으면 「이미 있음」, 다르면 `이름 (복구본).확장자`(있으면 `(복구본 2)` …)로 같은 방식으로 겹치지 않게 둔다. 폴더는 만들기만 한다.
- **OneDrive 안이면:** 온라인 전용 자리표시자는 내용을 읽지 않고(읽으면 내려받는다) 크기 · 시각으로만 견준다. OneDrive 동기화가 그 폴더를 받는 중이면(우리가 「없음」을 본 뒤 OneDrive가 같은 이름을 내려놓을 수 있다) 「OneDrive 밖 새 폴더」를 기본으로 둔다.
- **자동 실행 자리는 원래 자리로 되돌리지 않는다.** 시작프로그램 폴더 · 셸 프로필(PowerShell 프로필 폴더 등) · 그 밖에 로그인 때 저절로 실행되는 자리는 따로 둔 폴더로 되살린다. 옛 PC가 감염돼 있었을 때 백업이 새 PC에 실행 파일을 심는 길을 막는다.
- **연결점 · 특수 이름은 건너뛰고 센다.** 지금 전체 복구는 목록에 파일 · 폴더가 아닌 것이 하나라도 있으면 쓰기 전에 멈춘다(`restore-tar.cjs`). 그런데 Windows는 모든 프로필의 문서 폴더에 연결점(「My Music」 등)을 두고, restic은 그것을 링크로 기록한다(검토 실험, 이 PC 문서 폴더 맨 위 연결점 4개). 옮겨 오기 · 전체 복구는 링크 · 특수 노드 · 안전하지 않은 이름(끝이 점 · 공백, 예약어)을 건너뛰고 결과 화면에 「건너뜀 N개」와 목록을 보인다. 백업 쪽은 지금처럼 링크로 기록하고 따라가지 않는다.
- **장부와 이어받기:** 쓴 파일마다 「되살림 · 대조 통과」를 장부(`migration/<번호>.jsonl`)에 적고, 그것을 이어받기 상태로도 쓴다 — 끊긴 뒤 다시 시작하면 장부에 있는 파일은 크기 · 시각이 그대로일 때 건너뛴다. 전원이 연결돼 있으면 옮겨 오기 동안 절전을 막는다. 앱은 원래 자리의 파일을 지우는 기능을 갖지 않는다.
- 평소 「파일 되살리기」(골라 복구 · 전체 복구)는 지금처럼 새 폴더로만 쓴다. 백업 중인 기기 자신에서는 이 흐름을 열지 않는다.

#### 쓰는 기기는 한 번에 하나

- 한 저장소를 여러 기기가 쓰면, 엔진의 「최신 완료본」 고르기가 기기를 안 가리고(`retain` · `probeBody` · `restoreLatest` · `openFileCatalog`, 그리고 새로 만들 증명 v2 · 대량 변경 비교 — 다섯 자리), 점검 · 정리의 배타 잠금이 서로의 회차를 종료 11로 실패시킨다(검토 실험). 그래서 1단계는 **손님 저장소에 쓰는 기기는 한 번에 하나**로 못 박는다.
- 새 기기가 이어서 백업을 시작하는 순간이 옛 기기 쓰기 출입증을 끊는 순간이다(서버가 한 요청 안에서 한다). 「옛 PC 연결 끊기」에서 '아니오'면 새 기기는 되살리기까지만 한다.
- **자리를 넘겨준 옛 PC(다시 확인 N2):** 끊긴 뒤에도 옛 PC를 한동안 같이 쓰는 일은 흔하다. 그대로 두면 옛 PC가 인증 오류 → 「다시 로그인」 → 새 출입증을 받아 쓰는 자리를 도로 가져가고 새 PC가 말없이 멈춘다. 그래서 ① 끊긴 PC는 「이 PC의 백업은 [기기 이름]으로 옮겨졌습니다 — 여기서 고친 파일은 백업되지 않습니다」 상태로 서고 회차는 쉰다 ② 서버는 그 기기에 사흘 메일을 보내지 않는다 ③ 쓰는 자리를 가져오는 것은 그 뜻을 적은 단추(「이 PC로 다시 백업」)와 다른 기기 알림으로만 한다.
- 그래도 모든 판 고르기에 「호스트 = 이 기기」 조건을 넣는다. 옮겨 오기만 원본 기기를 명시한다. restic 호스트 이름은 **기기 번호**다(지금은 보관함 번호).
- 새 PC는 같은 저장소에 이어서 백업한다. 되살린 파일과 내용이 같아 첫 백업에 올라갈 것이 거의 없다(중복 제거 — T16에서 「더한 바이트」로 잰다).

#### 다른 기기 판의 정리

다른 기기의 판은 다음일 때만 정리 대상이 된다 — **이 기기의 옮겨 오기 장부가 그 판의 모든 파일을 되살려 대조까지 통과했거나, 사용자가 화면에서 「나머지는 필요 없음」을 눌렀을 때**. 분실 신고 · 「끊김」만으로는 정리하지 않는다(그 판이 그 자료의 하나뿐인 사본일 수 있다 — 늘어나는 용량은 서버가 세어 알린다). 유예 30일은 그 조건이 찬 때부터 센다. 정리하는 주체는 그 판을 옮겨 받은 기기 하나다. 서버가 알려 준 「끊김」만 믿지 않고 로컬 장부의 판 번호와 함께 본다. 건너뛴 것(연결점 · 특수 이름 · OneDrive가 되살리는 폴더)이 있으면 자동 조건은 차지 않고 손님 단추로만 풀리므로, 옮겨 오기 결과 화면에 「옛 PC 판이 남아 있는 까닭」을 보인다. 엔진 정리 규칙 변경이라 GPT 2차 검수를 받는다.

#### 자리 맞추기 · OneDrive

- 백업할 때마다 그 PC의 알려진 폴더 위치(문서 · 바탕화면 · 사진 · 음악 · 동영상 · 다운로드, OneDrive로 옮겨졌는지)를 작은 JSON으로 함께 넣는다(`새-PC-준비.json`과 같은 길).
- 새 PC에서: 옛 알려진 폴더 아래 경로 → 새 PC의 같은 알려진 폴더(`SHGetKnownFolderPath` — OneDrive로 옮겨졌으면 그 자리). 옛 사용자 프로필 아래 다른 경로 → 새 프로필 아래 같은 상대 경로(자동 실행 자리는 위 규칙대로 뺀다). 그 밖(D 드라이브 프로젝트 폴더 등) → 같은 드라이브가 있으면 같은 경로, 없으면 사용자가 고른다.
- OneDrive 기본값(검토 Q2): 옛 PC의 그 폴더가 OneDrive 안이었고 새 PC도 같은 OneDrive면 그 폴더는 OneDrive가 되살리므로 우리는 「없는 파일만 채우기」 또는 건너뛰기. 옛 PC는 로컬이었고 새 PC가 OneDrive면 「OneDrive 밖 새 폴더」가 기본이다. 남은 공간은 로컬에서 읽을 수 없다(11-12 이 PC에서 OneDrive 계정 레지스트리 · 설정 파일에는 용량 알림을 띄운 시각만 있었다). 그래서 되살릴 용량과 함께 「OneDrive 남은 공간을 넘으면 동기화가 멈출 수 있습니다」라고 적는다(유료 1TB 손님도 있어 「무료 5GB」라고 쓰지 않는다).
- 기다림: 내려받을 양 ÷ 지난 회차에서 잰 회선 속도로 「약 N분」을 따로 보인다(50GB · 100Mbps면 이론상 약 67분).

#### 다시 깔 것 · 다시 로그인할 곳 · 옛 PC 끊기

- 진단(inventory)이 찾은 프로그램 목록을 보여 주고, winget에 있는 것은 이름 · 명령까지 보인다. 설치는 하지 않는다(4단계).
- 다시 로그인할 곳은 진단이 찾은 앱 종류에서 만든 고정 체크리스트다(브라우저 · 메신저 · 클라우드 드라이브 · AI 도구 · 공동인증서 안내). 설문을 하면 그 결과로 2단계 전에 고친다.
- 옮겨 오기가 끝나고 대조가 통과하면 「옛 PC 연결 끊기」(기본 예) → 이 PC가 쓰는 기기가 되고 옛 기기 쓰기 출입증이 지워진다(T16에서 옛 출입증의 거부까지 본다).

### 4.7 되살리기 증명 v2 (로드맵 7)

- 매주 이 기기의 최신 판에서 백업한 폴더마다 무작위 파일을 고른다(합 64MiB 안, 폴더마다 적어도 하나, 큰 파일은 건너뜀). 폴더에 고를 파일이 없으면 「표본 없음」으로 따로 센다.
- `restic dump`로 받아 메모리에서 SHA-256만 계산한다. 평문을 디스크에 쓰지 않는다(지금 표본과 같은 원칙).
- 원본 대조: 원본 파일의 크기와 수정 시각이 그 판의 기록과 같으면 원본을 읽어 SHA-256을 견준다. 바뀐 파일은 「원본이 바뀌어 대조 못 함」으로 따로 센다.
- 결과를 둘로 나눈다(검토 F19): **dump 실패 · 크기 불일치 → 손상**(그날 알림 + 정리 보류, 지금 `probeHold`). **dump 성공 + 원본과 다름 → 「원본이 시각을 그대로 둔 채 바뀜」** — restic은 크기 · 시각이 같으면 다시 읽지 않으므로 그 파일의 백업이 낡은 것이다. 손상으로 세지 않고, 다음 회차에서 그 파일을 다시 읽게 한다.
- 화면 첫 줄의 「증명 날짜」는 마지막 통과 날짜다.
- 일부러 깨뜨린 저장소 시험: 시험 저장소의 pack 하나를 바꿔치기해 증명 · 서버 탐지 · 매주 1/4 내용 읽기 가운데 무엇이 먼저 찾는지 본다(T15, 「손님보다 먼저 찾아낸 비율」의 시작 값).

### 4.8 분실 · 탈취 (로드맵 8)

- **두 번째 복구 수단 「복구 코드」:** 저장소 위치 · 번호, 복구 암호, 손님 읽기 출입증을 담은 한 장이다. 앱 창에서 바로 인쇄하거나 고른 자리(USB)에 바로 쓴다 — 임시 HTML을 기본 브라우저로 여는 길은 복구 암호가 디스크 · 브라우저 기록에 남으므로 쓰지 않는다. 백업 폴더 · OneDrive 폴더 안에는 저장하지 못하게 하는 0.5.0 규칙(복구 키는 작업 폴더와 떨어진 곳)을 잇는다. 첫 주 안에 한 번 권하고 건너뛸 수 있다. 새 PC의 「복구 코드로 되살리기」에서 파일을 열거나 글을 붙여 넣으면 Google 없이 된다.
- **분실 신고:** 2.4의 순서. 옛 쓰기 · 읽기 출입증은 신고 즉시 지운다(끊으려고 누른 것이다). 그 뒤 새 기기를 이을 때까지 서버가 필요하다는 것, 옛 복구 코드는 못 쓴다는 것을 화면과 문서에 적는다.
- **새 기기 개통 · 되돌리기 요청 · (3단계) 해지 요청:** 기존 기기에 알리고(다음 회차 알림) 메일을 보낸다. 해지는 재확인 없이 지우지 않는다. 1단계에는 3단계가 쓸 틀만 둔다.

### 4.9 시범 측정 통로 (로드맵 9)

- **모으는 것:** 회차 기록(5.5의 칸), 알림 표시 · 누름(종류 · 시각), 설치 단계(단계 · 걸린 시간 · 성공), Windows 판 · 대기 방식. 기기 이름은 「내 기기」 목록에만 쓰고 측정에는 넣지 않는다. 파일 이름 · 경로 · 폴더 이름 · 내용은 보내지 않는다.
- **새지 않는다는 시험:** 합성 자료의 파일 · 폴더 이름에 표식 글자를 넣고, 측정 · 도움 요청 묶음과 서버 DB에 그 글자가 없는지 본다(T25).
- **보내는 때:** 회차 끝에 기기 토큰으로 보낸다. 못 보내면 7일까지 모았다가 보낸다.
- **시범자에게:** 첫 화면 아래 한 줄 「시범 동안 백업 결과 숫자(파일 이름 없이)를 SYNK로 보냅니다」.
- **도움 요청:** 앱 안 단추 → 보낼 내용(판 · Windows 판 · 최근 회차 50줄 · 오류 번호 · 경로 없는 설정 요약)을 먼저 보이고 → 손님 글과 함께 서버로 보낸다. 엔진의 마지막 오류 글은 넣지 않는다(restic 표준 오류에는 파일 경로가 있다). 답은 Claude가 쓰고, 시범 동안은 유호님이 확인한 뒤 보낸다(2단계 운영).

### 4.10 설치 프로그램과 자동 업데이트 (로드맵 10)

- 4.2의 NSIS perMachine 설치기 하나다.
- **Tauri 업데이터:** 업데이트 묶음을 Tauri 자체 서명 열쇠로 서명하고, 앱에 박은 공개 열쇠로 검증한다. OS 코드 서명과는 따로다.
- **업데이트 자리:** 공개 저장소의 GitHub Releases에는 두지 않는다(저장소가 비공개로 돌아가면 끊긴다). 설치 파일을 받는 곳과 같은 곳(회사 서버의 정적 경로 또는 synk.im 내려받기 쪽)에 두고, 기존 PC 앱 피드의 방식을 따른다.
- **관리자 확인을 받아들인다(검토 Q6).** 컴퓨터 전체 설치라 업데이트 설치에도 관리자 확인이 뜬다. 권한 있는 업데이트 도우미는 도우미와 같은 종류의 통로를 하나 더 여는 일이라 1단계에서 만들지 않는다. 설치는 엔진 잠금을 쥐고 한다(회차 도중에 실행 파일을 바꾸지 않는다). 표준 사용자 계정에서는 「업데이트 준비됨」을 날마다 띄우지 않고 「관리자에게 부탁하기」 문구로 일주일에 한 번 띄운다. 서버가 「이 판 아래는 더 못 씀」을 말할 수 있게 한다(측정에 판이 온다) — 도우미 같은 권한 코드의 고침이 깔리지 않은 채 남지 않게.
- **열쇠 보관:** 만들 때 암호를 걸고, 이 PC의 열쇠 층(`SYNK_보안`)에 둔다. 그 층은 [복원 체계](../../docs/컴퓨터를%20잃어버렸을%20때.md)가 암호문으로 비공개 저장소와 Drive에 올린다. 공개 저장소 · Actions 비밀값에는 넣지 않는다(서명은 이 PC에서만). 열쇠를 잃으면 이미 깔린 판을 갱신할 수 없으므로(Tauri 문서), 만든 날 복원 시험 도구로 암호문에서 되살려 보는 것까지 한다(T19).

### 4.11 깨끗한 Windows 자동 연습 (로드맵 11)

- 작업 흐름: `.github/workflows/workbackup-clean-windows.yml`. 계기는 손으로(workflow_dispatch), 이 두 폴더를 바꾼 push, 매주다. [관문 · 자동화 한 장](../../docs/_ops/관문_자동화.md)에 같은 커밋으로 적는다. 저장소가 크므로 필요한 폴더만 성기게 받는다(sparse checkout, blob 거르기).
- **두 갈래(검토 F18):** push마다는 실행기 안의 판 관리가 되는 S3 대역(MinIO 판 관리 켬)으로 엔진 · 설치 · 옮겨 오기 흐름을 돌린다. 실제 B2는 매주 · 손으로 돌릴 때만, CI 자료 D0(약 100MB)로 시험 버킷 `ci/`에 한다. B2 무료 한도의 셈: 저장 10GB(실측 `t/` 약 0.3GB · 72시간 D1 1.5GB + 변경 · CI 주 0.2GB · 속도 측정 D2 3GB가 `ci/`에서 8일 뒤 치워짐), 내려받기는 월 평균 저장량의 3배까지 무료다. 결제 수단 없는 계정이 한도를 넘으면 어떻게 되는지는 확인하지 않았으므로 넘기지 않게 위 셈을 지킨다.
- **1번 실행기:** 빌드(restic은 공식 판을 받아 고정 해시 대조) → 설치(관리자, 조용히) → 합성 자료 → 작업 스케줄러로 회차 한 번 → 잠긴 파일 시험(파일을 독점으로 연 채 회차 → 부분 판 → 채움 판) → 해시 목록을 산출물로 올린다(합성 자료뿐이라 공개돼도 된다).
- **2번 실행기(깨끗한 새 VM):** 설치 → 「옮겨 오기」를 복구 코드 길로(Google 없음) → 원래 자리와 새 폴더 둘 다 → 해시 전수 대조.
- **3번:** 표준 사용자 계정을 만들어 그 사용자 작업(암호 로그온 — DPAPI가 돌아야 하므로)으로 회차를 돌려 VSS 없는 길과 도우미 없음을 확인한다.
- **공개 로그:** restic은 저장소 주소(버킷 이름 · 접두사)를 출력에 찍는다. 공개 저장소의 Actions 로그는 누구나 보므로 주소 · 버킷 이름도 비밀값으로 넣어 가리고(11-12 넣음), 엔진 오류 글(restic 표준 오류)을 로그에 그대로 내지 않는다. 복구 암호 · 출입증은 산출물 · 로그에 남기지 않는다.
- 포크에서 온 PR에는 비밀값이 가지 않으므로 PR에서는 빌드 · 단위 시험만 돈다. `pull_request_target`으로 바꾸지 않는다.
- **못 재는 것:** 실행기는 Windows Server · 관리자 · 관리자 확인 꺼짐이라 관리자 확인 창 · Smart App Control · OneDrive 폴더 이동 · Google 동의 · 알림 표시 · **도우미의 권한 경계**가 재현되지 않는다. 그래서 이 PC 시험 설치를 2주차로 앞당겨 거기서 잰다(T5 · T13 · T14). 실행기에서 「로그온한 경우에만」 작업이 도는지는 첫 실행에서 확인하고, 안 돌면 CI에서만 암호 로그온으로 돌린다.
- **화면 시험:** 화면 조작(컴퓨터 유즈) 대신 tauri-driver(WebView2 + msedgedriver)로 웹 화면 안쪽 흐름만 본다. 서버 · Google은 시험 대역으로 둔다.
- 3연속 통과(실제 B2 갈래)가 관문이다.
- **이 PC 측정:** D1로 메모리 · CPU · 증분 시간 · 회차당 주고받는 양, D2로 처음 백업 속도를 잰다. 휴대폰 핫스팟일 때는 큰 올리기를 미룬다.

### 4.12 화면 다시 (로드맵 12)

- 뼈대부터 다시 짠다: [디자인 참고 장부](../../docs/디자인/참고사이트/README.md)(마지막 크롤링 11-10 뒤 것만 새로) · 참고 카드(11-11 「포인트 색 한 자리」 — 보안 제품 예시 포함) → 시안 둘(정적 HTML, 1440 · 390) → 유호님이 고른다 → Claude가 Tauri 화면으로 옮긴다 → 카본 + Fable 검수. **2주차부터 나란히 한다** — 5주차 한 주에 시안 · 고르기 · 구현 · 검수를 넣으면 기각될 때 물러설 자리가 없다.
- 한 화면에 「안전함 · 마지막 확인 · 증명 날짜」, 「파일 되살리기」, 「새 PC로 옮겨 오기」만 둔다. 나머지(폴더 · 외장 드라이브 · 도우미 상태 · 복구 코드 · 내 기기 · 사고 되돌리기 · 트레이 · 측정 안내 · 업데이트)는 설정 서랍에 넣는다.
- 1단계에 새로 생기는 화면: 첫 시작 둘(Google로 시작 · 보호 범위 확인 — OneDrive 줄 포함), 회차 진행 보기, 부분 보호 안내(몇 파일은 어느 판으로 지키는지), 폴더를 찾을 수 없음, 옮겨 오기 넷(자리 고르기 · 진행 · 결과 · 다시 깔 것), 사고 되돌리기 셋(시각 · 미리 보기 · 되돌린 뒤 고르기), 분실 신고 단계, 복구 코드 인쇄, 기기 끊기 확인 웹 쪽, 알림 문구.
- 화면 글 검사: 기본 화면에 restic · 스냅샷 · 버킷 · 출입증 · 저장소 · pack · prune 같은 말이 나오면 시험이 실패한다.

## 5. 데이터

### 5.1 PC

- 사용자별 `%APPDATA%\SynkWorkBackup\`: 프로필 설정 · DPAPI 자격(복구 암호 · 기기 쓰기 출입증 · 기기 토큰 · Google 토큰), `device.json`(기기 번호 · 손님 번호, 비밀 아님 — 서버 주소는 실행 파일에 박는다), `runs.jsonl` · `notify.json` · `progress.json` · `vss-request.json` · `telemetry-queue.jsonl` · `migration/<번호>.jsonl`(옮겨 오기 장부 겸 이어받기 상태), `engine.lock` · `ui.lock`.
- 사용자별 `%LOCALAPPDATA%\SynkWorkBackup\`: restic 캐시 · 임시.
- 컴퓨터 쪽: 설치 폴더(관리자만 쓰기), 작업 스케줄러 작업 폴더 둘, `%ProgramData%\SynkWorkBackup\helper\<SID>\`(도우미 작업 폴더 — 관리자만 쓰기, 그 사용자는 읽기 · 지나가기만: 섀도 복사본 연결 · 만든 섀도 복사본 번호 · 하루 횟수).

### 5.2 저장소 (B2)

- 손님 계정에 버킷 하나(비공개, 서버 쪽 암호화 켬, 수명 규칙은 4.4 — 규칙 하나만).
- `c/<손님 번호>/r/`가 손님당 restic 저장소 하나다. 손님 번호는 메일에서 만들지 않은 무작위 16자다. 판 꼬리표: `complete` · `partial` · `fill` · `meta`(U 목록 · 채움 경로 맞추기 · 알려진 폴더), 호스트 = 기기 번호.
- 지금 `b2.cjs`의 경로 검사(`work-backup/<보관함>`)와 `recovery-vault.cjs`의 읽기 출입증 규칙에 새 꼴을 더한다. `b2.cjs` 사전 확인(HeadBucket)은 접두사 출입증에서 200이므로(M1) 그대로 쓰고, 오류 문구 「버킷 전체 Read and Write 권한이 필요합니다」만 바꾼다.

### 5.4 봉투와 복구 코드

- 봉투 v3: `{format:'synk-workbackup-recovery', version:3, repository:{endpoint,bucket,prefix}, repositoryId, password, readKey:{keyId,applicationKey}, createdAt}`.
- 복구 코드: 같은 내용을 글(줄 바꿈 · 검사 숫자 포함)과 파일로 준다. 앱 창에서 바로 인쇄하거나 고른 자리에 바로 쓰고, 임시 파일을 남기지 않는다.

### 5.5 측정 항목 — 보내는 것과 보내지 않는 것

## 8. 벤치마킹 근거

[경쟁 20개군 조사](../solo-backup/RESEARCH.md)(11-09)의 결론 — 적은 평상시 조작, 마지막 확인된 완료 시각, 복구 증명, 범위를 숨기지 않기 — 를 그대로 기준으로 쓴다. 1단계의 새 기능은 11-12에 따로 모았다. 공식 문서로 기능을, 사용자 글로 좋거나 불편한 까닭을 나눴고, 검색 요약으로만 본 것은 그렇게 적었다. 전수조사가 아니다.

| 주제 | 출처 · 사용자 반응 | 가져올 점 → 1단계 적용 |
|---|---|---|
| 앱 밖에서 도는 예약 | KopiaUI 일정은 KopiaUI가 떠 있어야 돈다는 [포럼 글](https://kopia.discourse.group/t/windows-server-kopiaui-not-snapshot-on-schedule/2167)(2023-07). Duplicati는 트레이와 서비스 두 방식이 있고([Windows 안내](https://docs.duplicati.com/platform-specific-guides/using-duplicati-with-windows)), 서비스로 깔아도 로그인 전까지 백업이 줄 서 있었다는 [포럼 글](https://forum.duplicati.com/t/service-installation-has-queued-backups-until-user-logs-in-interactively/21185)(2025-08) | 화면 앱을 예약자로 쓰지 않는다 → 작업 스케줄러 회차 하나(4.2). 조용히 실패하지 않게 「마지막 소식」 기준의 사흘 메일 |

**Q10 후보와 한계(검토 답 요약):**
- **다른 B2 계정으로 복제:** 원본에서 영구 삭제해도 목적지에 남고 목적지 쓰기 출입증에는 삭제 권한이 없다. 그런데 숨김 표시가 복제되지 않아 목적지는 줄지 않고 지금까지 올린 것 전부가 쌓인다(변경량만큼 계속 는다). 목적지를 줄이려면 서버 밖에서 도는 정리가 따로 든다. 공격자가 복제 규칙을 끄면 그 뒤 것은 안 넘어간다(매일 대조가 잡는다).
- **객체 잠금:** 이 설계에서는 정리가 숨기기만 하고 실제 삭제는 수명 규칙이 하므로, 「올린 뒤 N일 잠금 + 서버가 지금 보이는 판의 잠금을 날마다 늘림」이면 숨겨진 판만 잠금이 풀려 수명 규칙이 지우고, 그 기간 안의 영구 삭제는 계정 주인의 열쇠로도 안 된다. 값은 잠금을 늘리는 서버 일과 그 권한, 되돌릴 수 없다는 점(해지해도 N일은 못 지운다). restic 정리 · 수명 규칙과 실제로 맞물리는지는 M8과 같은 자리에서 작은 접두사로 잰다.
- **다른 회사 저장소:** 값과 일이 가장 크다. 위 둘이 안 될 때.
