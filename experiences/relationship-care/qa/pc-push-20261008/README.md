# 플레저 · PC 알림 준비 상태 · 2026-10-08

실제 PC 알림 수신을 확인하기 전의 읽기 전용 운영 집계와 공개 UI 관찰이다. **실제 알림 수신 검증은 아직 완료하지 않았다.**

## 운영 집계

2026-10-08 **02:11:09 KST**에 공용 자격증명 모듈의 `질의읽기: true`와 `질의전용(sql)`을 거쳐 SELECT 집계만 실행했다. 실행한 PowerShell 명령 전체, SQL 및 결과는 [readiness.json](readiness.json)에 있다. Management API의 POST는 SELECT 질의를 전달하는 통로이며 발송 함수를 호출하지 않았다.

| 확인 항목 | 결과 |
| --- | ---: |
| 등록 구독 | 0 |
| 활성 구독 | 0 |
| 오늘 평가된 활성 구독 | 0 |
| 최근 결과가 sent / failed / skipped인 구독 | 각각 0 |
| 활성 `synk-care-push-dispatch` cron | 1 |

계정 식별자·메일·구독 endpoint·키·토큰은 조회 결과나 증거 문서에 포함하지 않았다. 이 집계는 cron의 활성 여부까지 확인하며 이번에 실제 예약 발송이 일어났다는 뜻은 아니다.

## 공개 화면 관찰

주 작업자가 **Codex 인앱 브라우저**에서 기존 SYNK SSO로 복귀하고, 기존 ‘동기화 확인용’ 1명 수첩을 불러오는 것을 확인했다. 알림 설정은 **‘이 기기에 알림 켜기’**가 보이는 준비 상태였으며 시간은 **오전 9시·한국 시간**이었다.

Chrome 새 탭을 여는 도구에 오류가 있어 이 화면 점검은 IAB에서 진행했다. 따라서 Chrome의 알림 권한·구독 생성·운영체제 알림 수신을 확인한 결과로 해석하지 않는다. 사용자는 알림 허용 확인에 **“알림은 나중에 확인”**이라고 답했다. PC 알림 수신 시험도 사용자 요청으로 보류하며, 알림 권한·시험 일정은 변경하지 않았다.

## 현재 검증 경로

현재 앱에는 즉시 보내는 **테스트 알림** 기능이 없다. [화면](../../index.html)의 알림 제어는 켜기·시간 저장·재확인·끄기이며, 서버 설정 API도 `status / subscribe / update / unsubscribe`만 허용한다. [기존 푸시 구현 기록](../push-20261007/README.md)과 [운영 시간 경계 검증](../ops-roundtrip-20261008/README.md)을 함께 참고한다.

사용자가 추후 수신 시험을 재개하고 실제 알림을 허용할 때의 검증 경로는 다음과 같다. 지금 실행할 작업은 아니다.

1. 오늘로 정한 후속 챙김을 계정에 저장한다.
2. 알림 시간을 한국 시간으로 2~3분 뒤로 지정하고 해당 브라우저의 기기 알림을 켠다.
3. Care 탭을 닫고 Chrome은 실행된 상태로 둔다.
4. 정규 예약 실행 후 실제 PC 시스템 알림과 클릭 이동을 확인한다.

하루 한 번 평가하므로 빈 수첩으로 먼저 예약 시각을 넘기지 않도록 대상 기록을 먼저 저장한다. 서버의 `sent`는 push gateway 수락 결과이며 OS의 실제 수신 증거를 대신하지 않는다.

이번에는 시험 알림을 발송하거나 worker·dispatcher를 수동 호출하지 않았고, 사용자 수첩·알림 권한·구독을 변경하지 않았다. UI의 기존 SSO 복귀 과정과 읽기 전용 SQL을 구분한다. 휴대폰 검증은 사용자의 기존 보류를 유지한다.
