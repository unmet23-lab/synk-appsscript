## 새 추천·로딩 변경 · 공개 반영과 운영 확인 완료

**오늘 챙길 한 사람**은 오늘 일정 → 내가 정한 기한이 된 후속 챙김 → 7일 안 일정 → 마지막 챙김이 30일 이상 지난 사람 또는 기록이 없는 사람 순서로 제안한다. 기존 Core Domain과 Trail을 재사용하며 사람마다 한 가지와 이유를 보여 준다. 복사·준비는 실제 챙김으로 세지 않고, 직접 남긴 활동·일정 완료·완료한 후속 챙김을 기준으로 다시 살핀다. 직접 정한 다음 챙김 날 전에는 일반 안부를 보류하되 명시적인 생일·일정 제안은 유지한다. 조심스러운 날 주변의 일반 안부도 보류하며 기억을 임의로 초안에 삽입하지 않는다. 자세한 기준은 [제품 설명](../README.md)에 있다.

계정 설정·로그인·수첩을 처음 확인하는 동안 로딩을 표시하고 합계와 입력을 가려 빈 수첩으로 오인하지 않게 했다. **179개 시험·로컬 브라우저 QA·공식 Opus 5.5 / max 최종 검수를 완료했다.** policy `68b4cc3b2afb758af62112b7cd31ad004b908544`로 앱 파일 5개와 명세를 게시했다. [공개 주소 41개 파일](focus-20261007/public-verification.json)의 SHA·MIME이 일치하고 [Pages `37611829907`·전체 사이트 검사 `37611830710`](focus-20261007/deployment-ci.json)이 모두 성공했다. [실제 계정](focus-20261007/public-browser.json)을 다시 열어 기존 시험 기록과 새 추천을 확인했으며 실제 자료는 바꾸지 않았다. [공개 375px 화면](focus-20261007/public-focus-375.png)도 확인했다. 일정·후속·안부 연결, 복사만으로 추천이 사라지지 않는 것과 직접 챙긴 뒤 변경되는 것을 확인했다. 375/320px에서 가로 넘침이 없고 이유 본문은 17px, 주행동 단추는 높이 56px다. 근거는 [최종 QA](focus-20261007/README.md), [변경 목록](focus-20261007/scoped-build.json), [로딩 화면](focus-20261007/loading.png), [375px 화면](focus-20261007/focus-final-375.png)에 있으며 아래 초기 공개 검증과 구분한다.

## 구현과 검증

계정의 **첫 조회·첫 실패·이미 받은 수첩의 저장 대기**를 구분한다. V4 브라우저에서 최초 실패 시 입력·기기 이전 잠금과 재시도, 재시도 성공, `idle` 및 저장 중 재수정 직후 새 사람 화면 진입·저장 응답 뒤 선택 유지를 확인했다. [수동 관찰](focus-20261007/account-manual-v4.json)과 [375px 실패 안내](focus-20261007/account-failure-375.png)를 남겼다. V5의 손상 캐시 제거 후 미수신 수첩 보호는 실제 동기화 모듈 단위 시험으로 확인했다. 마지막으로 미저장 수첩 선택 중 같은 계정의 재연결이 와도 가림을 유지하는 회귀를 추가했다. 계정 화면 시험은 전체 179개에 포함된 15/15다. BFCache의 로그인 이동 표시 복구는 세션 변경 없는 소스·단위 검증이며 실제 Chrome 복귀를 재현한 것으로 표시하지 않는다. 상세 범위는 [최종 QA](focus-20261007/README.md)를 따른다.

- 하위 경로 안의 `config.json`으로 계정을 연결한다. 앱 키는 `care`, API 제품은 `platform`이며 등록된 공개 콜백과 주소가 정확히 같아야 한다. 기존 로컬 `/api/account-config`와 네이티브 연결은 유지한다.
- 공개 웹에서는 녹음 파일을 브라우저에서 재생할 수 있지만 받아쓰기는 제공하지 않는다. 녹음을 서버로 전송하지 않으며 직접 확인한 텍스트를 입력한다. PC 로컬 앱의 받아쓰기 기능과 구분해 안내한다.
- 고정 목록의 앱·기존 펠트/폰트·엔진·계정 모듈·공개 설정·해시 명세만 산출한다. **초기 공개본은 39개 파일**이며 새 추천·로딩 후보에는 두 모듈이 추가되므로 각 빌드의 명세로 파일 수와 SHA를 확인한다. 개인 기록, 로컬 저장소, 서버, 시험 파일, 비밀 키는 포함하지 않는다. 초기 공개판에는 닫힌 앱 알림이 없었고, 이후 기기별 직접 동의하는 [Web Push](push-20261007/README.md)를 운영에 추가했다. [10월 8일 운영 검증](ops-roundtrip-20261008/README.md)은 두 실제 로그인 세션과 완료/미룬 후속의 cron 건너뛰기까지이며, 실물 기기 수신은 미검증이다. 내보낸 ICS의 알림은 사용자가 가져온 달력 앱의 설정과 실행에 따른다.

## 게시용 빌드

실제 등록된 공개 클라이언트 ID를 담은 기존 공개 설정 스키마를 입력한다. `clients.care.redirectUri`는 `https://synk.im/care/`와 정확히 일치해야 한다. 출력은 저장소 `.tmp` 안의 **존재하지 않는 새 폴더**만 허용하며 이전 빌드를 덮어쓰지 않는다.

```powershell
node tools/prepare-care-public.mjs .tmp/synk-care-public-20261007 <공개설정.json> https://synk.im/care/
```

이 명령은 파일 생성만 하며 게시·계정 등록을 실행하지 않는다. 게시 담당자는 `build-manifest.json`의 파일 수·바이트·SHA와 실제 게시 바이트를 대조한다. 공개 설정만 입력하고 서버 비밀 키·사용자 토큰을 넣지 않는다. 실제 계정 등록·CORS·공개 포털 설정 일치는 별도 운영 검증 항목이다.

```powershell
node --test experiences/relationship-care/tests/public-build.test.mjs experiences/relationship-care/tests/account.test.mjs experiences/synk-account/tests/personal-account.test.mjs experiences/synk-account/tests/core.test.mjs
node experiences/relationship-care/qa/public-web-smoke.cjs
node experiences/synk-account/qa/personal-apps-smoke.cjs
```

## PC·휴대폰 실제 확인 순서

아래는 사용자가 연기한 물리 두 기기 확인을 재개할 때의 절차이며 아직 실행하지 않았다. 기존 ‘동기화 확인용’ 기록은 보존한다. 개인 수첩이 없는 전용 QA 계정에서 별도 시험 표식을 정하고, 사용자가 두 기기의 `https://synk.im/care/`에서 직접 로그인한다. 계정 비밀번호·토큰을 전달하거나 복사하지 않는다.

1. PC에서 `QA-플레저-날짜-임의표식` 인물과 시험 일정/메모를 만들고 **계정에 저장했어요**를 확인한다.
2. 휴대폰에서 같은 계정으로 로그인해 그 표식만 확인하고, 시험 메모에 휴대폰 확인 문구를 더해 저장한다.
3. PC에서 **계정 자료 새로고침**으로 변경을 확인한다. 작업 중 입력이 있다면 먼저 처리하고, 충돌이 나오면 표시된 두 기록을 확인해 직접 선택한다.
4. PC에서 해당 QA 인물만 삭제하고 연결된 시험 항목의 삭제를 확인한다. 휴대폰에서 새로고침해 사라졌는지 확인한 뒤 양쪽에서 로그아웃한다. 기존 수첩 전체 삭제나 실제 인물 삭제는 하지 않는다.

증거에는 기기 종류·시각·QA 표식의 저장/조회/삭제 결과만 남긴다. 개인 내용, 비밀번호, 토큰, 브라우저 저장소 덤프, 인증 query URL은 기록하지 않는다. 실패 시 미저장 입력을 보존하고 완료로 표시하지 않는다.
