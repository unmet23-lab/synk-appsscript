## 처음 짚은 다섯 곳은 어떻게 됐나

1. **셰이더 컴파일**: `onFirstUse` 6.98초 → 0.50초. `app.js`의 시작 단계가 `renderer.compileAsync`로 미리 컴파일한다. 풀렸다.
2. **자동차 모델을 맨 마지막에 받음**: `car.glb` 끝 10.3초 → 1.8초. 모델·텍스처를 처음에 함께 요청한다. 풀렸다.
3. **휴대폰 `coins()` 1.7초**: 상위에서 사라졌다.
4. **지형 계산**: landscape.js `hash`가 0.85~0.91초로 그대로다. 지금 남은 CPU 중 가장 크고, 가장 긴 작업(1.4~1.5초)도 이 무렵이라 지형 생성으로 보인다(추정 — 긴 작업과 함수의 연결은 재지 않았다). 미리 구운 높이 지도나 워커로 옮기면 1초쯤 더 줄 수 있다.
5. **하늘 조명 PMREM**: 상위에 보이지 않는다(로컬 v6에서 하나를 함께 쓰게 했다는 기록이 있다).

## 2026-10-04 후속 · 현재 로컬 판의 지형 워커

공개판 측정 뒤 v9 지형 LOD·표본 재사용과 v10 주행 변경이 들어간 **현재 원문**에서 변경 전·후를 각각 다시 쟀다. 위 10-03 공개 수치와 아래 로컬 수치로 개선율을 계산하지 않는다. 공개 홈페이지·기존 전달 ZIP은 갱신하지 않았다.

### 구현과 선택 근거

- `init → setupTerrain → buildCourseTerrain → createLandscapeHeight`에서 높이·미분·surface·색을 반복 계산하던 경로를 `terrain-data.js`로 분리했다. `landscape.js`의 원래 함수와 도로·해안 보호 표본을 그대로 사용한다. 높이 지도 보간으로 도로 가장자리·해안 교점·소품 접지가 달라지는 일을 피하려고 **모듈 워커**를 선택했다.
- 모델·텍스처 요청과 함께 워커를 시작한다. 워커는 THREE·DOM·WebGL 없이 66개 지형의 typed array를 생성하고, 396개 ArrayBuffer의 소유권을 메인에 전달한다. 메인은 배열을 복사하거나 높이를 다시 계산하지 않고 기존 재질에 붙인다. 장면의 난수·소품·LOD·재질 수명은 기존 메인 경로가 맡는다.
- 기존 월드 단계별 UI 양보, `prepareFirstFrame`의 선택/화질/캐릭터/크기 재확인, `compileAsync → 실제 첫 렌더 → 다음 프레임 → ready` 순서를 유지했다. 워커 생성·로딩·메시지 실패, 15초 제한, 잘못된 전달 구조는 같은 생성기의 동기 경로로 복구한다. 초기화 실패 시 워커를 취소하고 늦은 응답을 무시한다.
- `build-site.mjs`에 공유 도로·계산·워커·시작 모듈을 포함했다. 패키지 실제 실행을 막던 기존 `garage-core.js` 누락도 같은 목록에서 보완했다. 중간 구현에서 발생했던 THREE 1.4MB 중복 다운로드는 최종 워커의 의존성을 제거해 없앴다.

### 같은 로컬 조건의 전후 측정

캐시 없는 새 Chrome 프로세스·헤드리스 GPU/ANGLE D3D11, 컴퓨터 1440×900·휴대폰 흉내 390×844/DPR3. 각 조건 3회 중앙값이며 순차 측정이다. CPU·네트워크 제한은 걸지 않았다. 휴대폰 실기기 결과가 아니다. [전후 수치·원문 해시](terrain-startup-measurements-20261004.json), 개별 `terrain-startup-before/after-20261004-{desktop,phone}-{1,2,3}.json`에 원본 관측을 남겼다.

| 항목 | 컴퓨터 변경 전 → 후 | 휴대폰 흉내 변경 전 → 후 |
|---|---|---|
| 자산 완료 → 지형 단계 완료 | 483 → 399ms | 476 → 360ms |
| 워커 대기 뒤 메인 지형 단계¹ | 변경 전 별도 타이머 없음 → **31ms** | 변경 전 별도 타이머 없음 → **30ms** |
| `landscape.js hash` 메인 CPU 자기 시간 | **267 → 35ms** | **241 → 26ms** |
| 메인 긴 작업 합계 | 1,751 → 1,511ms | 1,752 → 1,102ms |

| 시작 단추 관측² | 3,151 → 3,323ms | 2,531 → 2,417ms |
| 앱 초기화 시작 → ready | 2,332 → 2,498ms | 2,284 → 2,049ms |

¹ `terrainMainMs`는 하늘 설정·도로·지형 조립·물 설정을 포함한다. 변경 전의 자산→지형 구간은 자산 설정/남은 폰트 대기도 포함할 수 있어 순수 지형 CPU와 동일 지표는 아니다. 워커의 실제 계산은 421~502ms, 자산 뒤 응답을 기다린 시간은 241~394ms였다. 계산을 없앤 것이 아니라 UI 스레드 밖으로 옮기고 자산 로딩과 겹쳤다.

² 페이지 이동 시작부터 Playwright가 활성 단추를 관측한 시간이라 관측 지연도 포함한다. 전체 시작 시간은 컴퓨터에서 개선되지 않았다. 특히 변경 후 컴퓨터의 620/747ms 긴 작업은 `shadersMs → firstFrameMs`와 겹치는 첫 렌더 구간이며, 지형 구간으로 주장하지 않는다. 지형으로 인한 메인 정지는 줄었지만 전체 로딩 완료 시각까지 빨라졌다고 일반화하지 않는다.
