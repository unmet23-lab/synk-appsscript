# 회사 DB 빈 칸 잔여 — 재기와 한 번 정리

> 2026-10-22 Claude. 「문의 접수」 문의 한 건 지우기(순서표 이력 25, 실제 사슬 26)의 GPT 2차 검수 GA2 후속. 운영 측정·결정은 아래 「10-22 운영 측정」, 남은 일은 [트랙](../../../../../../_ops/트랙.md) LAB TOPIK 4급 줄.

SQLite는 줄을 지우거나 고칠 때 옛 바이트를 지우지 않는다. 옛 칸은 페이지 안 빈 칸으로, 넘침 페이지는 빈 페이지 목록으로, 고친 페이지의 새 판은 WAL로 간다. 체크포인트 전에는 DB 파일에 옛 판 페이지가 그대로 있다. 지우기 판부터 문의 줄을 쓰고 지울 때 `secure_delete`를 켜고 WAL을 비우지만, 그 전 판이 남긴 바이트는 그대로다. 문의 암호문은 같은 서버의 `encryption.key`로 풀리므로 암호문 조각도 잔여로 본다.

## 합성 DB로 본 것 (`free-space.test.mjs`)

| 경로 | 새 판 지우기 뒤 | 빈 페이지 덮기 뒤 | VACUUM 뒤 |
|---|---|---|---|
| 옛 판에서 긴 초안 → 짧은 초안: 넘침 페이지가 빈 목록으로 | 남음 | 0 | 0 |
| 옛 판에서 짧은 초안 → 긴 초안: 옛 칸 앞머리(암호문 자리)가 페이지 안 빈 칸에 | 남음 | 남음 | 0 |

- 빈 페이지 덮기(빈 목록을 채웠다 `secure_delete`로 지우기)는 빈 페이지만 0으로 만든다. 그래서 정리는 VACUUM 하나로 한다. VACUUM 뒤에도 rowid 순서·본문은 그대로다(앱의 `all()`이 rowid 순서로 읽는다).
- 새 판에도 틈이 있다. `secure_delete`는 연결 설정이라 그 연결이 하는 쓰기에만 듣는다. 다른 종류 쓰기(끔)가 페이지를 나누거나 합치면, 옮겨진 문의 칸의 옛 자리와 해제된 페이지가 남는다. 합성 시험(씨앗 6개, 지운 600줄)의 결과는 아래와 같다. FAST는 합칠 때 해제된 페이지를 지우지 않아 버렸다.

  | 쓰기 꼴 | OFF | FAST | ON |
  |---|---|---|---|
  | 키우기만 | 62줄 | 2줄 | 2줄 |
  | 키운 뒤 줄이기 | 269줄 | 232줄 | 0줄 |

  그래서 Store 연결 전체를 ON으로 했다([`store.mjs`](../../store.mjs) `218a28d6f`, 합치기 대조 시험은 `store-performance.test.mjs`, WAL 약 6% 더). ON으로도 나누기만 하면 SQLite가 다시 짠 페이지의 빈 가운데에 드물게 사본이 남는다(600줄 중 2줄). 지운 뒤 0을 보장해야 하면 VACUUM이다. 이력 25(문의 지우기)에 함께 싣는다([트랙](../../../../../../_ops/트랙.md)).

## 재기 — 읽기 전용

```
node scan.cjs <이름표> [--out <파일>]
```

- 쓰기 노드에서 `free-space-node.py scan`이 돈다. 신원·주소·SSH는 `tools/server-backup/read-status.cjs`와 같다. 결과는 숫자뿐이다. 고객 글·초안·암호문·해시는 내지 않는다.
- 읽는 순서:
  - DB 주인(uid)으로 낮춘 자식 프로세스가 읽는다. 앱이 DB를 열고 있을 때(-wal·-shm이 있을 때)만 읽는다. root가 사이드카 파일을 만들지 않게 하려는 것이다.
  - 자식은 권한을 낮추기 전에(root) 자기만의 마운트 이름공간을 만들고 전파를 private으로 바꾼 뒤, DB 폴더를 `/mnt`에 다시 붙여 그 경로로 읽는다(`owner_view`). 운영 DB 폴더는 위 두 마디(`/srv/synk/recovery-final-…/prepared`)가 root 전용(0700)이라 낮춘 uid로는 원래 경로를 지나지 못한다(10-23 `WAL_SIDECARS_MISSING`). 폴더를 열어 두고 fchdir로 상대 경로를 주면 파이썬 파일 읽기는 되지만, SQLite가 getcwd로 절대 경로를 만들어 마디마다 lstat하므로(`os_unix.c` `unixFullPathname`, 3.40.1) 연결이 같은 자리에서 막힌다.
  - 이름공간의 모든 마운트가 private이 된 것(전파 표시 `shared:`·`master:` 없음)을 `/proc/self/mountinfo`로 본 뒤에만 붙인다. 아니면 붙이지 않고 멈춘다(`MOUNT_PRIVATE_FAILED`·`MOUNT_STILL_SHARED`, 결과의 `code`). 붙인 자리는 자식과 그 자식이 끝나면 이름공간과 함께 사라진다 — 호스트 마운트 표에는 생기지 않는다.
  - `mode=ro` 연결 하나를 열어 둔 채, 앞 읽기 트랜잭션에서 `data_version`·수·산 값·논리 스냅샷(serialize)을 읽는다.
  - 실제 DB·WAL 파일 바이트는 다른 파이썬 프로세스가 읽어 넘긴다. 이 프로세스가 DB 파일을 따로 열었다 닫으면 열어 둔 연결의 POSIX 잠금이 풀리기 때문이다.
  - 같은 연결의 뒤 읽기 트랜잭션에서 `data_version`과 산 값을 한 번 더 읽는다. 이 셋이 「조용한 한 번」이어야 한다 — 그사이 다른 연결의 커밋이 없고(`data_version` 그대로, WAL 프레임을 다 쓴 뒤 커밋을 공개하는 순간이 앞 스냅숏 뒤에 와도 잡힌다), DB·WAL 파일의 크기·수정 시각(체크포인트 포함)과 앞뒤 산 값이 같아야 한다. 아니면 0.5초 쉬고 처음부터 다섯 번까지 다시 읽는다. 그사이 쓰기가 있으면 지워진 값이 산 값으로 숨거나, 다른 종류 쓰기가 페이지를 나눠 스냅숏에 없는 사본을 남길 수 있어서다. 끝내 조용하지 않으면 `residue.changedDuringScan`이 참이고 판정하지 못한 것으로 친다. 논리 스냅샷의 구역은 앞의 산 값과, 실제 파일은 뒤의 산 값과 견준다.
- 결과 칸:
  - `pragma.freelist_count`는 빈 페이지 수다.
  - `residue.freelist`·`inPage`는 논리 스냅샷의 빈 목록 페이지와 b-tree 페이지 안 빈 칸이다.
  - `residue.logical`·`dbFile`·`walFile`은 논리 스냅샷·실제 DB 파일·WAL 프레임을 페이지마다 자른 것이다. WAL 끝의 덜 쓴 프레임도 센다. 테이블 잎 페이지는 칸을 풀어, 넘치는 산 초안을 그 칸이 이 페이지에 둔 본문 끝까지만 본다. 체크포인트 전 DB 파일에 남은 옛 페이지는 `dbFile`에서 잡힌다. 덜 쓴 마지막 WAL 프레임(끊긴 쓰기)은 칸 경계를 믿을 수 없어 `walTorn`으로 따로 센다.
  - `payloadResidue`·`draftResidue`는 `"payload":"`·`"replyDraft":"` 뒤의 값 가운데 지금 어느 줄에도 없는 것(지운 줄이나 옛 판)의 가짓수다. 닫힌 초안은 길이와 상관없이(6,000자 초안도) 그대로 견준다. 잘린 초안은 앞부분으로 견주고, 12바이트보다 짧으면 판정 못 함(`draftShort`)으로 센다.
  - 빈 칸(`freelist`·`inPage`)의 `payloadLive`·`draftLive`는 산 줄의 사본이다. 그 줄을 지우면 잔여가 되므로 `scan.cjs` 요약은 `copies`로 따로 보인다.
- 못 세는 것: 넘침 페이지에 이어지는 초안 글처럼 표식이 없는 조각이다. 빈 페이지가 0이어도, 다시 쓰인 페이지의 빈 칸이나 넘침 페이지의 남는 끝에 그런 조각이 있을 수 있다. 확실히 없애야 하면 VACUUM이다. 페이지 안 옛 칸은 앞머리(암호문 자리)가 오래 남으므로 `payloadResidue`로 잡힌다. 다른 종류(`socialInbox` 등)의 같은 이름 칸도 산 값으로 친다.
- 종료 코드: 잔여를 세지 못했거나(메모리 부족 `skipped`) 조용한 한 번을 얻지 못하면 읽기 전용 실행도 종료 1이다(요약의 `decided` 거짓). 잠시 뒤 다시 잰다.
- 로컬: `python3 free-space-node.py --db <company.sqlite>`. 시험은 둘이다.
  - `node --test free-space.test.mjs`: 잔여·VACUUM·덮기·멈춤 길·실제 파일의 옛 페이지·동시 쓰기를 본다. 파이썬 3.11+가 있으면 scan까지 본다.
  - `python3 free-space-node.test.py`: 표식 판정·칸 풀기·WAL 프레임과, 막는 조건·READY 손 맞춤을 본다. 다시 붙이기의 차례와 멈춤(전파가 private이 아니면 붙이지 않음), 자식의 차례(붙이기 → 권한 낮추기 → 붙인 경로로 재기)도 본다. 리눅스에서 root가 아닌 사용자로 돌리면 왜 fchdir로 모자란지(위 마디를 닫은 폴더에서 SQLite가 열지 못함)도 실제로 본다.

## 정리 — 잔여가 있을 때만

```
node scan.cjs <이름표> --vacuum --approval <승인 파일> --out <파일>
```

- 전제: 운영 DB 파일을 다시 쓰는 일이라 유호님 승인 문장(대상·시간·끊김)을 파일로 받는다. 도구는 그 해시를 결과에 남긴다. 반영 전에 `vacuum.mjs`·`free-space-node.py`를 아르곤·GPT 2차 검수에 다시 보인다([운영 원칙](../../../../../../AI_운영원칙.md) 「백엔드 검수」).
- 막는 조건(아무것도 하지 않고 멈춤, 못 읽은 것도 막음):
  - 릴리스·운영 잠금이 잡혀 있음(`/proc/locks`로만 본다).
  - 이름에 backup·restore·dr·rearm·release·deploy·maintenance·disarm이 든 synk-* 서비스가 돈다.
  - DB가 120MB를 넘는다. 크기는 DB 파일이 아니라 논리 크기(page_count × page_size)에 WAL을 더해 잰다 — 체크포인트가 막히면 새 페이지가 WAL에 쌓여 파일보다 크다. `vacuum.mjs`도 앞 WAL을 비운 뒤 같은 상한을 다시 본다. 아래 예산 안에 끝난다고 볼 수 없으니 따로 창을 잡는다.
  - 26시간 안에 끝난 정기 백업이 없다. 따로 사본을 만들지 않는다 — 사본도 빈 칸까지 담는다.
  - 회사 컨테이너가 healthy가 아니다.
  - 데이터 디스크·메모리 여유가 DB 크기의 3·4배가 안 된다.
  - 앞 scan이 실패했다.
- 하는 일(`vacuum.mjs`, 회사 컨테이너 안 node = 앱과 같은 SQLite):
  1. WAL을 비운다. 기다리지 않고 짧게 여러 번 시도하고, 끝내 못 비우면 시작하지 않는다(종료 2). 오래 읽는 연결이 있으면 뒤 비우기도 막혀 옛 페이지가 DB 파일에 남기 때문이다. 비운 뒤 논리 크기가 상한을 넘으면 시작하지 않는다(종료 6).
  2. READY를 낸다. `free-space-node.py`가 이 순간 잠금·서비스를 다시 보고 GO나 STOP을 보낸다(STOP·무응답이면 종료 5).
  3. 자식 프로세스가 같은 연결·읽기 트랜잭션에서 논리 지문(표마다 rowid 순서, WITHOUT ROWID는 기본 키 순서)과 `data_version`을 읽는다. 이어서 `secure_delete=ON`·`temp_store=MEMORY`(잠시 만드는 사본 DB를 디스크에 쓰지 않음)로 VACUUM하고, 지문을 다시 읽는다.
  4. VACUUM이 예산(잠금 기다림 1초 + 일 3초)을 넘으면 자식을 SIGKILL로 끝낸다(종료 3). 커밋 전이면 SQLite가 그 쓰기를 버리고 잠금은 프로세스와 함께 풀린다. 워커 스레드로는 끊을 수 없었다 — `process.exit`이 VACUUM 끝까지 기다려 커밋됐다.
  5. WAL을 TRUNCATE한다. 못 비우면 실패다(종료 4). VACUUM이 쓴 새 페이지는 WAL에, 옛 페이지는 DB 파일에 남아 있기 때문이다. 이어서 `quick_check`를 본다.
- 끊김: 재시작이 없다. 앱의 쓰기만 VACUUM 동안 기다린다(앱 `busy_timeout` 5초, 동기 node:sqlite라 그동안 요청 처리도 잠깐 멈춘다). 45MB 합성 DB에서 VACUUM 0.46초, 15ms마다 쓰던 쪽의 최대 대기 0.42초·실패 0이었다. 릴리스의 배포 전 백업부터 재무장까지와는 겹치지 않게 한다. 사후 확인이 DB를 앞뒤로 견준다.
- 확인: `scan.cjs`는 아래가 모두일 때만 종료 0이다.
  - `vacuum.exit` 0·`quickCheck` ok·`walTruncated`.
  - `logical`이 same이거나, 그사이 앱이 썼으면 app-wrote-meanwhile.
  - 뒤 scan이 판정할 수 있었고(`decided`), 빈 페이지 0·모든 칸 잔여 0·빈 칸과 덜 쓴 WAL 꼬리에 산 줄 사본도 판정 못 한 조각도 0(`afterClean`).
- 남는 틈 — 릴리스 잠금은 잡지 않는다: 릴리스 도구는 잠금이 잡혀 있으면 LOCK_NB로 실패한다. 그래서 주간 복원 연습(`deploy/dr-drill/restore-drill.py`)과 같이 `/proc/locks`·서비스로 보기만 하고, VACUUM 바로 앞(READY)에서 한 번 더 본다. 그 확인과 VACUUM 시작 사이(ms)에 릴리스가 시작하는 경쟁은 남는다. VACUUM은 4초 안에 끝나거나 끊긴다.
- 남는 것:
  - 정리 전 백업(GCS 30일, Drive는 [보존 규칙](../../../../../../AI_운영원칙.md#보관-위치))은 그대로다. 지우기 전 백업은 그 문의를 산 줄로 통째로 가지므로, 빈 칸 정리와 별개로 보존 기한이 지나야 사라진다.
  - 지운 파일 블록은 ext4 빈 공간에 남는다. 운영 데이터 디스크는 주 1회 `fstrim.timer`가 돈다(마운트 discard는 꺼짐).
