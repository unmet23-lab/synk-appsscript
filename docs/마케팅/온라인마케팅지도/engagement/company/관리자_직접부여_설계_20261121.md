# Workspace 관리자 직접 부여 설계 (2026-11-21)

대표 요청(2026-11-21): 「Workspace 관리자 화면(나만 쓰는 총 관리 기능 — 초대, 권한 부여, 화면 보며 관리)에서 반 연결 같은 것을 내가 임의로 부여할 수 있게 해 줘」. 대표는 범위 넷을 모두 골랐다. 그 뒤 Fable 5.2 설계 검토(판정 「고쳐서 짓기」)를 보고 「넷 다, 막이 더해서」를 골랐다. 이 판은 그 검토를 반영했다. 지적별 반영은 [8절](#review)에 있다.

이 문서는 설계다. 코드는 아직 바꾸지 않았다. 정하실 것은 [7절](#decide)에 있다. SYNK-talk 경로는 `origin/master` 기준이다(로컬 master는 origin과 갈라져 있다).

## 1. 목적과 범위

지금 반, 교사 배정, 명부, 이용 권한은 운영 SQL로만 세운다([개강 준비](../../../../온라인반_TOPIK4급/README.md#open-class)). 이 일을 대표가 Workspace 관리자 화면에서 하게 한다. 넷을 모두 첫 판에 넣는다.

| | 할 일 | 원천 |
|---|---|---|
| ① | 기존 반에 SYNK ID를 학생 또는 교사로 넣고 뺀다. 반 연결 코드를 쓰지 않는다 | `engine.learners`, `engine.staff`, `engine.staff_classes` |
| ② | 반을 만들고 끈다 | `engine.classes` |
| ③ | 이용 권한을 주고 거둔다 | `engine.synk_entitlements` (`engine.apply_synk_entitlement`) |
| ④ | 다른 직원을 Workspace 관리자로 올리고 내린다 | 회사 서버 `users` |

같은 첫 판에 넣는 막이:

- 옛 `teach` 함수의 골든 표본을 맡은 반 학생으로 좁힌다([3절](#teach-golden)).
- 쓰기와 ④는 최근 15분 안에 SYNK ID로 직접 로그인했을 때만 된다.
- 하루 상한과 대표 알림을 둔다.

범위 밖:

- 수업 영상 이용 기간 주기(`engine.classroom_access` 넣기)와 반 영상 설정(`engine.classroom_channels`). 지금처럼 운영 SQL로 한다. 학생을 빼거나 옮길 때 영상 이용을 거두는 일은 범위 안이다.
- 원장(`director`)과 검수자(`inspector`) 자격. 운영 SQL로 남긴다.
- 운영 SQL이 해임한 직원 되살리기.
- 학생의 학습 기록, 제출물, 녹음을 관리자 화면에서 보기.
- 학생 대신 반 공유(sharing)나 동의를 켜기.
- 결제와 환불.
- 중앙 관리자 열람권(`admin.*`) 주기.

## 2. 신원과 권한 문

### 이 화면을 무엇으로 보나

2026-09-19 결정([결정_2026-09.md:59](../../../../_ops/보관/결정_2026-09.md), 정본 [공개판_설계.md:33·42·46](../../../../공개판_설계.md))은 직원 자격을 코드, 초대 링크, 앱 안 가입으로 주지 않는다고 정했다. 직원 계정은 운영자 도구로 만든다. 다른 학생의 녹음과 기록을 열람하게 되는 위험 때문이다.

이번 관리자 화면은 그 「운영자 도구」다. 운영 SQL로 하던 일을 같은 사람(대표)이 화면에서 한다. 누군가 스스로 권한을 얻는 새 입구가 아니다.

공개판_설계 46행은 「공개 가입으로 만든 계정은 직원이 되지 않는다」고 적었다. 운영 SQL은 10-22부터 교사의 SYNK ID(공개 가입 계정)에 직원 줄을 세워 왔다([개강 준비](../../../../온라인반_TOPIK4급/README.md) 95·107행). 그래서 46행을 「공개 가입 계정은 스스로 직원이 되지 않는다. 운영자(운영 SQL 또는 대표만 쓰는 관리자 화면)가 직원 줄을 세운 SYNK ID만 직원이다」로 고치고 결정 한 행을 남긴다([6절 바꿀 파일](#files)).

### 그대로 지키는 선

- 회사 직무나 Workspace 역할로 반 권한이 생기지 않는다([WORKSPACE_ACCESS.md](WORKSPACE_ACCESS.md) 66·75·94·137·190행).
- 로그인에 성공했다고 교사나 관리자 권한이 생기지 않는다([플랫폼 계정 설계](../../../../SYNK_플랫폼_계정과_연결_설계.md) 1204행).
- 기존 반 연결 코드는 그대로 둔다. 코드로는 여전히 자기 학생 줄에만 들어간다.
- 반 공유와 동의는 학생 본인만 켠다.
- 중앙 관리자 열람권(`admin.*`)은 화면에서 줄 수 없다. 운영 SQL로만 준다.
- Workspace 관리자로 올려도 중앙 권한은 따라가지 않는다.

### 두 겹의 문

| 문 | 확인하는 곳 | 확인하는 것 |
|---|---|---|
| 회사 문 | 회사 서버 | 최신 `users` 행의 활성 관리자, SYNK ID 세션, 같은 출처, `x-csrf-token`, 응답 뒤 재확인. 쓰기와 ④는 최근 15분 안의 대화형 로그인 |
| 중앙 문 | `synk-account` | 토큰, 살아 있는 Auth 세션, `messenger` 제품 세션, 계정 활성, op에 맞는 수동 열람권. 쓰기는 Auth 세션의 인증 시각이 15분 안 |

- 회사 서버는 지금처럼 관리자 본인의 SYNK ID 세션 토큰과 publishable 키로만 중앙을 부른다. `synk-identity.mjs:21-22`가 `service_role`과 `sb_secret_` 키를 거부한다. 서버 키를 새로 두지 않는다.
- ④는 회사 서버 안의 일이다. 중앙 표를 건드리지 않는다.

### 열람권 둘

| 열람권 | 여는 op |
|---|---|
| `platform` / `admin.workspace-grants` | 반, 학생, 이용 권한, 감사 목록 |
| `platform` / `admin.workspace-staff` | 교사 넣기와 빼기 |

- 둘 다 source `manual`이다. 판정 꼴은 명부 열람권(`lib/synk-account-member-directory.js:17-30`의 `permitted`)과 같고 capability 이름만 다르다.
- 둘 다 운영 SQL로 대표 계정에만 넣는다. 대표가 고른 범위라 기본은 기한 없이 준다.
- 끄는 길: 운영 SQL로 그 줄의 `revoked_at`을 지금으로 적는다. 다음 요청부터 막힌다. 교사 넣기만 끄고 나머지는 남길 수 있다.
- 사람 고르기는 전체 SYNK ID 명부를 쓴다. 대표 계정에는 `admin.member-directory`가 이미 있다(WORKSPACE_ACCESS.md 8행).
- 이 도구가 쓰는 이용 권한 줄은 source를 `workspace-admin`으로 적는다. 관리자 판정은 source `manual`만 인정한다. 그래서 허용 목록에 구멍이 나도 이 도구로는 관리자 열람권을 만들 수 없다.

### 최근 대화형 로그인 15분

회사 서버는 대표의 토큰을 15초마다 확인하고 브라우저 로그인은 갱신 토큰으로 계속 이어 간다(`synk-identity.mjs:101, 123-153`). 그래서 회사 세션 하나만 있으면 중앙 쓰기를 언제든 부를 수 있다. 쓰기 op와 ④에 15분 재확인을 건다. 읽기 op에는 걸지 않는다.

- 회사 서버는 `complete()`가 `login` 흐름을 마칠 때만 세션 항목에 `interactiveAt`을 적는다.
- `renew`, `refreshBrowser`, `validateSession`의 자동 갱신은 이 값을 올리지 않는다.
- 이 값은 저장하지 않는다. 회사 서버가 다시 켜지면 다시 확인해야 한다.
- 15분이 지났으면 회사 서버가 409 `REAUTH_REQUIRED`를 준다. 화면은 「SYNK ID로 다시 확인」 단추를 보인다. 단추는 `/api/synk-id/start`의 `login` 흐름을 `expectedAccountId`(지금 SYNK ID)와 함께 부른다(`synk-identity.mjs:55-58`). 그래서 다른 계정으로 바뀌지 않는다.

중앙에서 확인한 원천:

- 지금 `createAuthVerifier`(`lib/synk-auth.js:22-65`)는 `iat`, `exp`, `session_id`, `client_id`만 읽는다. `iat`는 토큰을 갱신할 때마다 새로 찍히므로 로그인 시각이 아니다.
- 명부 판정은 같은 DB 연결로 `auth.sessions`를 이미 읽는다(`synk-account-member-directory.js:21`). 그래서 중앙은 그 세션의 시작 시각(`auth.sessions.created_at`)과 인증 시각(`auth.mfa_amr_claims`, 토큰 `amr`의 원천)을 읽을 수 있다.
- 중앙 쓰기는 두 시각 가운데 늦은 쪽이 15분 안이어야 한다. 아니면 401 `REAUTH_REQUIRED`다.
- 구현 첫 확인: 운영 토큰 하나로 OAuth 승인 뒤 두 시각이 어떻게 찍히는지 본다. 승인 화면(`experiences/synk-account/src/portal.mjs`)이 이미 로그인된 브라우저에서 비밀번호를 다시 묻지 않고 승인하면, 인증 시각이 오래되어 중앙이 거절한다. 그때는 승인 화면에 「다시 확인」 요청을 받아 로그인을 다시 거치게 하는 길을 더한다.
- 지은 모양(11-21~22, 위 두 시각 추정은 GPT 세 회차 P1 뒤 버림): 시각을 짐작하지 않고 표 줄로 묶는다. 회사 화면 「SYNK ID로 다시 로그인」 → `https://synk.im/id/?reauth=1&next=<등록된 Workspace 승인 주소>` → 포털이 로컬 로그아웃 뒤 새로 로그인시키고, 승인 `redirect_url`을 받은 직후 `admin-reauth-mark`(그 브라우저 세션의 대화형 로그인 5분 안 승인만) → 회사 서버가 코드를 교환한 새 Messenger 토큰과 PKCE verifier로 `admin-reauth-claim` → `bound:true`일 때만 회사 `interactiveAt`(중앙 `loginAt`)을 적고, 중앙 쓰기는 호출 세션에 묶인 줄의 로그인 시각이 15분 안일 때만 연다. Auth가 승인 세션을 남기지 않는 한계(GA1 · GA2)는 받아들인 경계로 계약(SYNK-talk `docs/C0_API계약.md` 「재확인 묶기」)에 적었다. 설계 검토 기록 `.tmp/admin-grants-20261121/설계검토_재확인과_권한쓰기_Fable.md` · `설계검토2_…` · `설계검토3_권한함수_Fable.md`.
- 운영 확인(11-22, 읽기 전용): `auth.oauth_authorizations` 칸 모두 있음 · 승인 코드 최대 36자 · 소유자 연결이 auth 표를 읽음 · 토큰 갱신이 `mfa_amr_claims.updated_at`을 올리지 않음 · PostgreSQL 17.6. 남은 것: 운영 Auth의 수동 계정 연결이 켜져 있고 비밀번호 변경 재인증이 꺼져 있어, 옛 세션을 쥔 쪽이 비밀번호를 바꾼 뒤 새로 로그인하는 길은 이 재확인이 막지 못한다 — 모든 SYNK ID 로그인에 닿는 설정이라 유호님이 정한다.

### 하루 상한과 대표 알림

- 중앙 상한은 감사 표에서 그 행위자의 최근 24시간 성공 건수로 센다. 넘으면 429 `DAILY_LIMIT`다.
- 회사 상한은 회사 `audit`에서 센다.
- 상한 숫자는 [7절](#decide) 7의 기본값을 따른다.
- 중앙(SYNK-talk 함수)에는 메일이나 메신저로 밖에 알리는 통로가 없다.
- 회사 서버에는 메신저 알림과 기기 알림(web push)이 있다(`server.mjs:386`, `messenger.notifyCompanyUsers`, 자동화 알림의 꼴 `server.mjs:575`).
- 그래서 회사 서버가 쓰기와 ④가 끝날 때마다 대표에게 메신저 알림을 보낸다. 대표의 휴대폰에도 기기 알림으로 간다.
- 회사 서버가 털리면 알림도 막힐 수 있다. 그래서 관리자 화면 맨 위에 중앙 감사 표에서 읽은 「최근 부여」 목록을 둔다(op `audit.list`).

### 자격 증명 없는 시작 세션 막기

`launch.mjs:32-42`는 이 PC에서 첫 활성 관리자의 세션을 자격 증명 없이 만든다(`/api/launch`, `server.mjs:1661`).

- `/api/launch`가 만든 세션 본문에 `via:'launch'`를 적는다.
- 중앙 호출 경로와 ④는 `via:'launch'` 세션, SYNK ID가 없는 세션, `interactiveAt`이 없는 세션을 모두 거절한다.
- 시험으로 고정한다.

## 3. 중앙(SYNK-talk) 새 동작

### 자리: `synk-account`의 새 action

`supabase/functions/synk-account/index.ts`에 action `admin-workspace-grants`를 더한다. 명부처럼 감싸기 함수(`withAdminGrants`)로 붙인다. 새 파일은 `lib/synk-account-admin-grants.js`이고 `동봉.json`에 한 줄을 더한다.

`synk-classroom` 관리자 경로를 고르지 않은 까닭:

- 회사 서버의 토큰은 `messenger` 제품이다. `synk-classroom`은 `world`와 `platform`만 받고 나머지를 `PRODUCT_FORBIDDEN`으로 막는다(`lib/synk-classroom-server.js:11-12`). 이 문을 넓히면 교실 함수 전체의 제품 경계가 흔들린다.
- `synk-classroom`은 `SYNK_CLASSROOM_ENABLED` 스위치와 「교사 본인, 학생 본인」 신원 모델 위에 있다. 관리자는 둘 다 아니다.
- 권한 판정이 명부와 같다. 판정을 함수 하나(예: `adminPermitted(q, identity, capability)`)로 빼서 명부와 함께 쓴다. 기존 명부 시험이 그대로 통과해야 한다.

치르는 값과 막이:

- 명부 규칙이 두 함수에 걸린다. 학생을 계정에 이을 때의 부수 쓰기(공유 줄, 마을 소속)를 `lib/synk-classroom-roster.js`로 뺀다. 수락(`lib/synk-classroom-enrollment.js:88-112`의 `claim`)과 이 도구가 그 함수를 함께 쓴다.
- 그래서 `supabase/functions/_shared/synk-classroom-runtime.js` 묶음을 같은 커밋에서 다시 만든다.

### 공통 규칙

- 요청은 POST다. 머리글은 `X-SYNK-Product: messenger`, `X-SYNK-Contract: 1`이다. 본문은 `{action:'admin-workspace-grants', op, ...}`이다.
- 쿼리 문자열이나 op에 없는 키가 오면 400 `INVALID_GRANT_REQUEST`다.
- 모든 동작은 한 트랜잭션이다. 첫 질의에서 op에 맞는 열람권을 판정한다. 없으면 403 `GRANTS_FORBIDDEN`이다.
- 쓰기 동작은 `requestId`(UUID)와 `confirm:true`를 받는다. `confirm`이 없으면 400 `CONFIRM_REQUIRED`다.
- 재전송은 감사 표로 가린다. `request_hash`는 op와 정렬한 입력의 SHA-256이다. 같은 `requestId`와 같은 해시면 처음 결과를 돌려준다. 해시가 다르면 409 `REQUEST_CONFLICT`다.
- 이 판정은 다른 쓰기보다 먼저 한다. 이용 권한은 특히 `apply_synk_entitlement`를 부르기 전에 끊는다. 그 함수는 `valid_from`이 다르면 같은 사건도 `conflict`로 보기 때문이다.
- `schema_ver`는 운영 SQL처럼 그때 최신 조각의 계약판이다. `lib/계약판.js` 통로로 읽는다.
- 성공한 쓰기는 같은 트랜잭션에서 감사 표에 한 줄을 쓴다.
- 거절한 쓰기도 감사한다. 트랜잭션을 되돌린 뒤 따로 짧은 트랜잭션으로 결과 코드만 한 줄 쓴다.
- DB 오류는 Postgres 코드만 로그에 남긴다. 응답은 503 `GRANTS_UNAVAILABLE`이다.

잠금 차례는 실제 교실 코드에 맞춘다.

1. 대상 Auth UUID의 advisory 잠금. `withContext`(`lib/synk-classroom-store.js:47`)와 수락 `claim`(92행)이 잡는 열쇠와 같다. 그래서 대상 본인의 수락과 줄을 선다.
2. 반 advisory 잠금 `'synk-class-workflow:'+classId`(같은 파일 53행). 수락 `claim`은 이 잠금을 잡지 않는다.
3. 반 줄 `for share`(54행).
4. 직원 줄과 배정 줄 `for share`(56-57행).
5. 명부 줄 `for update`. 수락의 `scope`(`synk-classroom-enrollment.js:38`)와 같은 세기다. `withContext`는 명부를 `for share`로 읽는다(59행).
6. 계정 줄 `for update`.

두 반을 잠글 때(옮기기)는 `class_id` 순서로 2를 두 번 잡는다. 줄 잠금은 반 잠금보다 먼저 잡지 않는다.

### SYNK ID를 Auth UUID로 풀기

- `engine.synk_accounts` 줄이 있어야 한다. 없으면 404 `ACCOUNT_NOT_FOUND`다.
- 그 줄의 status가 `active`여야 한다. 아니면 409 `ACCOUNT_UNAVAILABLE`이다.
- `engine.synk_auth_links`와 `auth.users`(`deleted_at is null`)로 이어진 로그인 주인이 정확히 하나여야 한다. 둘 이상이면 409 `LOGIN_OWNER_AMBIGUOUS`다. 근거는 「한 사람은 로그인 주인 하나」 규칙이다([로그인 지도 5절](../../../../SYNK_로그인_지도_20261112.md)).
- 명부와 직원 줄은 그 SYNK ID에 이어진 모든 Auth UUID로 찾는다. 지운 로그인 주인도 포함한다. 지운 주인의 줄이 있으면 409 `LEARNER_ON_OLD_LOGIN`이다. 그 줄의 주인 바꾸기는 운영 SQL로 한다(`clearLearnerOwner`, `synk-classroom-store.js` 앞부분).

### 학생 넣기 (`learner.add`)

`engine.learners.auth_user_id`는 unique다. 한 사람은 명부 한 줄에만 이어진다. 그래서 아래 차례로 판정한다.

1. 대상이 이 반의 교사이면 409 `TEACHER_OF_CLASS`다.
2. 대상의 명부 줄이 없고 `learnerId`를 주면, 그 빈 줄에 잇는다. 빈 줄은 같은 반, active, `auth_user_id`가 빈 줄이어야 한다. 이미 이어진 줄이면 409 `LEARNER_ROW_TAKEN`이다.
3. 대상의 명부 줄이 없고 `learnerId`가 없으면, 새 줄을 만든다.
4. 대상의 줄이 이 반에 있고 켜져 있으면 `duplicate`로 성공한다.
5. 대상의 줄이 이 반에 있고 꺼져 있으면 그 줄을 다시 켠다.
6. 대상의 줄이 다른 반에 있으면 409 `ACCOUNT_ALREADY_ENROLLED`와 그 반 이름을 돌려준다. `move:true`일 때만 옮긴다(아래 「옮기기」).

잇기, 다시 켜기, 옮기기 뒤의 부수 쓰기는 `lib/synk-classroom-roster.js` 하나로 한다.

- `engine.synk_classroom_sharing` 줄은 `enabled false`로 둔다. 학생이 켤 때까지 꺼져 있다.
- 새 반에 마을이 있으면 그 소속을 잇는다. 수락 `claim` 106-110행과 같다.
- 그 줄에 남은 반 연결 코드는 기존 트리거(`engine.synk_classroom_invite_roster_changed`)가 거둔다.

학생을 넣으면 그 반 교사가 보게 되는 것:

- 「이번 주 과제」 글은 반 공유와 무관하게 학생이 낸 것을 그 반 교사가 본다(`lib/synk-classroom-homework.js:5`). 넣은 뒤 학생이 내는 과제는 바로 교사에게 간다.
- 다시 켠 줄이면 그 반에서 예전에 낸 과제와 옛 엔진 기록이 다시 보인다.
- 동의 기록은 만들지 않는다. 옛 엔진의 과제 배정과 녹음 올리기는 지금처럼 유효한 동의 기록을 전제로 한다([공개판_설계.md](../../../../공개판_설계.md) 88행).
- WORLD 계정의 학습 기록은 학생이 반 공유를 켜야 교사 화면에 들어간다.

새 줄의 칸:

- `enrolled_at`은 넣은 시각, `lifecycle_status`는 `재학`이다.
- 임시 비밀번호 칸(`temp_password_*`)은 비워 둔다. 그래서 옛 학생번호 입구로는 이 줄에 들어올 수 없다.
- 빼기의 생애 칸(`effective_at`, `exit_reason`)은 이 도구가 적지 않는다. 그 칸은 사건에서 파생하는 칸이다(`20260902600000_learner_lifecycle_c16.sql` 머리말).

학생 번호(`student_code`) 규칙:

- 반과 무관한 전역 순번이다. 꼴은 기존 발급기 정본 `'SYNK-' + String(n).padStart(3,'0')`(`lib/학생계정.js:19`)을 따른다. 예: `SYNK-1043`.
- 이 꼴을 내던 상담시트 발급기는 v9.346에서 학원 운영 시스템과 함께 지웠다(SYNK-appsscript `Code.js:22`). 지금은 DB가 유일한 발급처다.
- n은 DB 전체에서 이 꼴 번호의 최댓값에 1을 더한 값이다. 전역 advisory 잠금(`'synk-student-code'`) 안에서 정한다.
- 옛 학생번호 로그인은 대문자로 바꾸고 하이픈을 지운 꼴로 찾는다(`lib/auth-password-change.js:93`). 그 꼴로 이미 있는 번호와 겹치면 다음 수로 간다.
- 사람 이름을 넣지 않는다. 한 번 쓴 번호는 다시 쓰지 않는다. 옮겨도 번호는 그대로 간다([학생ID 종단 설계](../../../../학생ID_종단_설계.md) 36행).

### 옮기기 (`learner.add`의 `move:true`)

- 그 줄의 `class_id`를 이 반으로 바꾸고 켠다. 새 줄은 만들지 않는다. `learner_id`와 번호는 그대로 간다.
- 옛 반의 공유 줄과 마을 소속을 끈다.
- 옛 반의 수업 영상 이용 줄(`engine.classroom_access`)에 `revoked_at`을 적는다. 새 반의 영상 이용은 운영 SQL로 준다.
- 옛 엔진 기록(`learner_id`로 이어진 학습 사건, 전사문, AI 첨삭)은 새 반 교사에게 보인다. `teach`의 담당 판정이 `learners.class_id`로 반을 고르기 때문이다(`supabase/functions/teach/staff.ts:68-78`).
- 「이번 주 과제」 글은 옛 반에 남는다.
- 확인 창이 위 셋을 알린다.

### 학생 빼기 (`learner.remove`)

- 줄을 지우지 않는다. 명부 줄을 지우는 통로는 만들지 않기로 했다(`20260902600000_learner_lifecycle_c16.sql` 머리말).
- `active`를 false로, `revoked_before`를 지금으로 바꾼다.
- `auth_user_id`는 남긴다. 다시 넣거나 옮길 때 같은 줄을 쓴다.
- 공유 줄과 마을 소속을 끈다.
- 수업 영상 이용 줄이 있으면 `revoked_at`을 적는다.
- 남은 반 연결 코드는 트리거가 거둔다.
- 교실 기록은 지우지 않는다. 교사 화면은 활성 명부만 읽으므로 그 학생은 바로 빠진다.
- 이미 꺼진 줄이면 `duplicate`로 성공한다.

빼기는 넣기를 온전히 되돌리지 않는다.

- 뺀 학생은 다른 반 코드로 들어올 수 없다. 수락은 꺼진 줄도 「이미 명부에 있음」으로 본다(`synk-classroom-enrollment.js:99-100`, `ACCOUNT_ALREADY_ENROLLED`). 다른 반에 넣으려면 이 화면에서 옮긴다.
- 다시 넣어도 수업 영상 이용은 돌아오지 않는다. 운영 SQL로 다시 준다.
- 다시 넣은 학생에게는 `revoked_before`가 남는다. 그 전에 받은 로그인으로는 반이 보이지 않으므로 한 번 다시 로그인해야 한다.

### 교사 넣기와 빼기

넣기:

- `engine.staff`의 기본 키는 `auth_user_id`다(`20260806234000_staff_c7.sql:84`).
- 직원 줄이 없으면 role `teacher`로 만든다. 표시 이름은 계정 프로필 이름이다. 감사 표에 「이 도구가 만든 직원 줄」로 적는다.
- 직원 줄이 `teacher`나 `director`로 살아 있으면 그대로 쓴다.
- 직원 줄이 `inspector`이면 409 `STAFF_ROLE_CONFLICT`다.
- 직원 줄이 꺼져 있으면, 감사 표의 마지막 기록이 「이 도구가 닫음」일 때만 다시 켠다. 그 밖의 꺼진 줄은 409 `STAFF_INACTIVE`이고 운영 SQL로 정한다.
- 대상이 이 반의 활성 학생이면 409 `LEARNER_OF_CLASS`다.
- 그다음 `engine.staff_classes`에 (staff_id, class_id)를 넣는다. 이미 있으면 `duplicate`로 성공한다.

교사를 넣으면 생기는 것:

- 그 사람에게 직원(교사) 자격이 생긴다.
- 그 반 학생이 이미 낸 과제 글과 앞으로 낼 과제 글이 보인다(공유와 무관).
- 그 반 학생의 옛 엔진 기록(전사문, AI 첨삭, 관찰)이 `teach`에서 보인다.
- 반 공유를 켠 학생의 WORLD 학습 기록이 교사 화면에 들어간다.

빼기:

- 배정 줄(`engine.staff_classes`)을 지운다. 이 표에는 active 칸이 없다.
- 배정 줄에 켜고 끄는 칸을 더하는 길은 고르지 않았다. 이 표를 읽는 자리가 8개 파일, 19곳이다(교실 판정, 수락, 과제, 교사 조회, `teach`의 feedback · observation · staff 등). 하나라도 빠지면 조용히 통과한다.
- 지우면 그 교사가 낸 반 연결 코드 줄이 함께 지워진다(`20261009235000_synk_classroom_enrollment_c16.sql:29`, `on delete cascade`). 수락 기록도 들어 있다. 그래서 지우기 전에 그 줄들(코드 ID, 학생 ID, 만든 시각, 만료, 수락 시각, 수락 계정, 거둔 시각)을 감사 표 `before`에 담는다. 코드 해시는 담지 않는다.
- 그 사람의 마지막 배정을 지웠고 그 직원 줄이 이 도구가 만든 줄이면, 직원 줄을 `active=false`, `revoked_before=now()`로 닫는다. 감사 표에 「이 도구가 닫음」으로 적는다.
- 운영 SQL이 만든 직원 줄은 닫지 않는다. 배정만 지운다.
- 교사의 반 판정은 요청마다 다시 읽는다(`synk-classroom-store.js:35-41`). 다음 요청부터 그 반이 보이지 않는다.
- 닫힌 직원 줄은 옛 함수의 직원 판정(`lib/토큰.js:95-107`의 `active`, `revoked_before`)에서도 빠진다. `teach`와 `companion`(마스코트 두뇌, AI 비용이 든다)이 403이 된다.

### `teach` 골든 표본을 맡은 반으로 좁히기

옛 `teach` 함수는 살아 있는 `teacher`나 `director` 직원이면 들어간다(`supabase/functions/teach/index.ts:102-104`). 골든 표본 큐(`teach/golden.ts`)는 `staff_classes`를 잇지 않는다. 그래서 반이 없는 교사도 모든 학생의 전사문과 AI 첨삭을 본다(`golden.ts:56-74`). 나침반, 회고, 피드백, 관찰은 이미 맡은 반으로 좁힌다(`teach/staff.ts:68-78`).

- 추첨은 그대로 둔다. 풀 질의는 `lib/골든표본` 풀술어와 글자까지 같아야 하고 `tests/골든표본.test.js`가 그것을 대조한다(`golden.ts:14-21`).
- 상세 읽기(`golden.ts:56-74`)에 담당 조건을 건다. `teacher`는 맡은 반 활성 학생의 표본만 본다. `director`는 지금처럼 전체를 본다. 조건은 `담당학생인가`와 같은 식이다.
- 판정(`gold/judge`, `판정하기`)도 같은 조건으로 막는다.
- 큐의 감사 줄(`teach.gold.queue`)에는 실제로 보인 표본만 적는다.
- 그래서 `큐읽기`가 `staff_id` 대신 직원 신원(staff_id와 role)을 받는다(`teach/index.ts:128`).

### 이용 권한 주기와 거두기

허용 목록은 서버 상수다. 화면이 정하지 않는다.

| product | capability | 쓰는 곳 | 기한 |
|---|---|---|---|
| `platform` | `library.world`, `library.messenger`, `library.teacher`, `library.path`, `library.pulse`, `library.care`, `library.fortune` | 플랫폼 서재 메뉴(SYNK-appsscript `desktop/src/library-access.cjs:7, 24-25`) | 없음 |
| `world` | `practice.plus` | 서재의 WORLD 메뉴(같은 파일 27행) | 꼭 정한다. 최대 6개월 |
| `world` | `town.access.trial` | 마을 입장(`lib/modern-town-store.js:12`) | 꼭 정한다. 최대 6개월 |

첫 판 목록에 넣지 않는 것:

- `admin.*` 전부.
- `town.access.subscription`. 정액 이용이라 첫 판에서는 운영 SQL로 둔다.
- `town.entry.topik1`. 학습 확인을 통과했다는 기록이라 사람이 주는 권한이 아니다.

메뉴 권한은 자료 권한이 아니다.

- `library.teacher`를 줘도 담당 반이 없으면 학생을 볼 수 없다.
- `library.messenger`는 회사 구성원 권한이 따로 있어야 쓸 수 있다(SYNK-appsscript `desktop/README.md` 269행).

쓰기는 `engine.apply_synk_entitlement`로 한다.

- 재전송은 이 함수를 부르기 전에 감사 표에서 끊는다(공통 규칙).
- 인자: `p_source`는 `workspace-admin`이다. `p_event_id`는 `requestId`다. `p_source_ref`는 `{synk_user_id}.{product}.{capability}`다.
- `p_source_revision`은 지금 판에 1을 더한다. 지금 판은 같은 트랜잭션에서 그 줄을 잠그고 읽는다.
- `p_valid_from`은 주기 때는 지금, 거두기 때는 기존 값이다. 거두기는 `p_revoked` true다.
- 이 함수는 사건 줄(`engine.synk_entitlement_events`, 덧붙이기만 된다), 판 비교, 잠금을 이미 한다.
- 결과가 `conflict`나 `ownership-conflict`면 409 `ENTITLEMENT_CONFLICT`다.
- 이 함수는 모든 역할의 실행 권한을 거둬 두었다. `synk-account`는 `SUPABASE_DB_URL`(소유자 연결)로 부르므로 권한을 새로 주지 않는다.
- 거두기는 source가 `workspace-admin`인 줄만 할 수 있다. 결제, 학습 확인, 운영 SQL(`manual`) 줄은 목록에 보이지만 거둘 수 없다(409 `ENTITLEMENT_NOT_EDITABLE`).
- 허용 목록 밖이면 403 `CAPABILITY_NOT_ALLOWED`다. 기한이 없거나 6개월을 넘으면 400 `INVALID_VALID_UNTIL`이다.

### 마이그레이션

새 조각이 하나 필요하다. 이름은 `2026112x……_synk_admin_grants_c18.sql` 꼴이다. 기존 조각의 checksum 검사와 선행 판 검사를 따른다.

- `engine.synk_admin_grant_audit`를 만든다. 칸: `audit_id`, `at`, `request_id`(unique, 거절 줄은 빈 값 허용), `request_hash`, `actor_synk_user_id`, `op`, `target_synk_user_id`, `class_id`, `learner_id`, `staff_id`, `entitlement_ref`, `before`, `after`, `outcome`.
- 상한을 세도록 (`actor_synk_user_id`, `op`, `at`) 색인을 둔다.
- RLS를 켜고 모든 역할의 권한을 거둔다.
- `engine.synk_immutable()` 트리거로 고치기와 지우기를 막는다. `engine.synk_account_audit`와 같은 방식이다.
- 이름과 이메일은 적지 않는다. ID만 적는다. 계정 줄은 탈퇴 뒤에도 `deleted`로 남으므로 ID가 가리킬 곳은 남는다.
- 함수 권한은 바꾸지 않는다.
- 적용 후 확인 목록(`supabase/확인_적용후상태.sql`)에 새 표를 더한다.

## 4. 회사 서버

### 중앙을 부르는 경로

- `POST /api/admin/synk-grants` 하나를 더한다. 본문은 `{op, ...}`다.
- op는 3절 목록만 받는다. op마다 받는 키를 정해 두고 그 밖의 키는 400이다. 받은 키만 중앙에 넘긴다.
- 같은 출처와 `x-csrf-token`은 지금의 POST 문(`server.mjs:1480-1482`)이 이미 본다.
- 명부 경로(`server.mjs:1702-1715`)의 `check()`를 중앙 호출 앞뒤로 부른다. 같은 세션 해시, 같은 CSRF, 최신 `users` 행의 role `admin`을 본다.
- 데모 요청, 쿼리 문자열, `via:'launch'` 세션은 거절한다.
- 쓰기 op는 `interactiveAt`이 15분 안이어야 한다. 아니면 409 `REAUTH_REQUIRED`다.
- 쓰기 op는 회사 `audit`에도 한 줄을 쓴다. 칸은 action `synk-grant`, op, requestId, 대상 ID, 결과 코드다.
- 쓰기가 끝나면 대표에게 메신저 알림을 보낸다(2절).
- 기존 `POST /api/members/:id/assignment`(`server.mjs:1835-1851`)는 넓히지 않는다. 그 경로는 「다른 관리자는 못 바꾼다」, 「role은 manager, member, viewer만」이라는 보호 계약을 지킨다.

### `synk-identity.mjs`에 붙일 호출

- `searchMemberDirectory`(154-173행) 옆에 `callAdminGrants(row, op, payload)`를 둔다.
- 앞뒤 검사는 명부와 같다. SYNK 세션(`row.body.synkIdentity`), `users` role `admin`, `sessionAllowed`를 본다. 응답 뒤 `entryIsCurrent`, `sessionAllowed`, role을 다시 본다.
- 머리글도 같다. Bearer 토큰, publishable `apikey`, `X-SYNK-Product: messenger`, `X-SYNK-Contract: 1`이다. 시간 제한은 8초다.
- 중앙의 401 `REAUTH_REQUIRED`는 그대로 화면에 넘긴다. 다른 401과 403은 `GRANTS_FORBIDDEN`으로 바꾼다. 연결 실패와 시간 초과는 retryable 503이다.
- 응답 꼴을 op마다 검사한다. 모르는 칸은 버린다. 꼴이 틀리면 503이다.
- 쓰기는 자동으로 다시 보내지 않는다. 화면이 같은 `requestId`로 다시 보낼 수 있다.
- `attachSession`에 대화형 여부를 넘긴다. `complete()`의 `login` 흐름만 `interactiveAt`을 적는다(2절).
- 세션 상태(`status`)에 `reauthNeeded`를 더해 화면이 미리 안다.

### 관리자 올리기와 내리기 (④)

경로: `POST /api/members/:id/admin-role`. 본문은 `{admin, role, teamId, expectedRole, confirm:true}`다. `role`과 `teamId`는 내릴 때만 쓴다.

회사 주인(`ownerId`):

- 회사 주인 한 명만 올리고 내린다.
- 주인은 새 문서 `store.get('settings','workspaceOwner')`(`{userId, setAt, setBy}`)에 둔다. `settings`/`company`에 두지 않는다. `/api/settings`(`server.mjs:1937`)와 여러 시험·미리보기 도구가 `company` 문서를 통째로 다시 쓰기 때문이다. 따로 두면 그 덮어쓰기에서 구조로 보존된다.
- 적는 자리 셋:
  - `/api/setup`(`server.mjs:1654-1658`)이 첫 관리자를 만들 때 같은 트랜잭션에서 적는다.
  - 부팅 때 비어 있으면 한 번 적는다. 활성 관리자가 정확히 한 명일 때만 적는다. 여럿이면 적지 않고 이 경로는 닫힌 채 실패한다. 회사 `audit`에 `workspace-owner-set`을 남긴다.
  - 그 밖의 경로는 이 문서를 쓰지 않는다. 주인 바꾸기는 이번 범위 밖이다.
- 화면에는 `permissions(user)`(`server.mjs:621`)의 새 값 `manageAdmins`로 알린다. 주인에게만 true다. 화면이 role로 짐작하지 않는다.

대상과 막이:

- 부르는 세션은 주인의 SYNK ID 세션이고 `interactiveAt`이 15분 안이어야 한다. `via:'launch'` 세션은 거절한다.
- 대상은 활성 직원이고 SYNK ID가 이어진 계정(`synk_identity_links`)이어야 한다. 회사 비밀번호만 쓰는 계정은 올리지 않는다.
- 자기 자신은 내리지 못한다. 주인도 내리지 못한다.
- 마지막 활성 관리자는 내리지 못한다. 주인 보호로 지켜지지만 따로 한 번 더 검사한다.
- 트랜잭션 안에서 주인과 대상의 최신 `users` 행을 다시 읽는다. `workspace-access-service.mjs:7`의 `admin()`과 같은 방식이다.
- 대상의 지금 role이 `expectedRole`과 다르면 409다.
- 올리기는 하루 상한이 있다(7절 7). 회사 `audit`에서 센다.
- 바꾼 뒤 대상의 세션을 모두 끊는다(`store.revokeUser`).
- 내릴 때 viewer로 바꾸면 assignment 경로의 넘기기 취소를 같이 한다.
- 내릴 때 그 사람에게 걸린 담당(새 의뢰 담당, 고객 업무 담당자와 검토자)을 경고로 돌려준다. `workspaceProfiles.save`의 `warnings`와 같다.
- 회사 `audit`에 `admin-role-granted` 또는 `admin-role-revoked`와 바꾸기 전후 role을 적는다. 대표에게 메신저 알림을 보낸다.

관리자가 여럿이 되면 바뀌는 자리:

- 「첫 활성 관리자」를 고르는 자리가 넷이다. 넷 모두 주인을 먼저 고르게 바꾼다.
  - `server.mjs:921` 수집 정리의 행위자.
  - `post-performance.mjs:418` 성과 기록의 행위자.
  - `launch.mjs:32` 시작 링크의 대상.
  - `client-projects.mjs:117` `requestOwner()`. 새 공개 의뢰의 담당자가 설정에 없을 때 쓴다.
- 관리자의 비밀번호 재설정(`server.mjs:1928`)과 이용 중지(`server.mjs:1936`)는 지금처럼 막는다. 관리자를 멈추려면 먼저 내린다.
- Workspace 관리자는 회사의 모든 기능과 자료를 연다(`workspace-access.mjs:44-45`). 고객 의뢰, 채널 연결, 자동 답장 키 같은 설정도 포함된다.
- 중앙의 명부, 반, 이용 권한, 교사 넣기는 따라가지 않는다. 올린 관리자의 SYNK ID로 부르면 중앙이 403을 준다. 시험으로 고정한다.

## 5. 화면 (`public/admin-workspace.js`)

- 회원 관리 범위 칸(`directoryModes`, 93행)에 「반」과 「이용 권한」을 더한다. 지금은 「Workspace 회원」, 「전체 SYNK ID」, 「직원 상세·성과」 셋이다.
- 두 칸은 관리자가 SYNK ID로 로그인했을 때만 보인다. 중앙이 거절하면 「이 SYNK ID에는 반과 이용 권한을 관리할 권한이 없어요.」를 보이고 단추를 숨긴다.
- 관리자 화면 맨 위에 「최근 부여」 목록을 둔다. 중앙 감사 표(`audit.list`)의 최근 7일 성공과 거절이다.
- 「반」: 반 목록에서 반 하나를 열면 교사와 학생 명부가 나온다. 단추는 반 만들기, 반 끄기, 학생 넣기, 교사 넣기, 줄마다 빼기다. 빈 명부 줄에는 「SYNK ID 잇기」가 있다. 교사 단추는 `admin.workspace-staff`가 없으면 숨긴다.
- 「이용 권한」: 사람을 고르면 그 사람의 권한 줄과 출처, 기한이 나온다. 단추는 권한 주기와 `workspace-admin` 줄의 거두기다. 다른 출처의 줄은 읽기만 한다.
- 「전체 SYNK ID」의 줄마다 「이용 권한」 단추를 두어 바로 간다.
- 직원 상세에 「관리자로 올리기」와 「관리자에서 내리기」를 둔다. `manageAdmins`일 때만 보인다.
- 쓰기 단추를 눌렀는데 `REAUTH_REQUIRED`가 오면 「SYNK ID로 다시 확인」 단추를 보인다. 다시 확인한 뒤 같은 확인 창으로 돌아온다.

사람 고르기:

- 「전체 SYNK ID」 검색(`/api/admin/member-directory/synk`)을 고르기 창 안에서 다시 쓴다. 검색을 새로 만들지 않는다.
- SYNK ID를 직접 쳐서 넣는 칸은 두지 않는다.
- 고른 사람의 이름, 로그인 이메일, 가입일을 확인 창에 다시 보인다.

확인 창(`app.js:672`의 `modal`을 쓴다):

- 학생 넣기: 「코드 없이 바로 이 반에 들어가요. 이 학생이 내는 과제 글은 반 공유와 상관없이 이 반 선생님이 봐요.」
- 학생 빼기: 「명부 줄은 남아요. 이 사람은 다른 반 코드로 들어갈 수 없고, 다른 반에는 여기서 옮겨야 해요. 다시 넣어도 수업 영상 이용은 돌아오지 않아요.」
- 옮기기: 옛 반과 새 반 이름. 「옛 학습 기록이 새 반 선생님에게 보여요. 과제 글은 옛 반에 남아요. 옛 반의 수업 영상 이용은 멈춰요.」
- 교사 넣기: 「이 사람에게 직원(교사) 자격이 생겨요. 이 반 학생이 낸 과제 글과 옛 학습 기록(녹음 받아쓰기, AI 첨삭)을 보게 돼요.」
- 교사 빼기, 거두기, 반 끄기: 무엇이 바로 멈추는지 한 줄로 보인다.
- 관리자로 올리기: 대상 이름을 직접 쳐야 단추가 켜진다. 「회사 자료 전부를 열 수 있어요. 반과 이용 권한은 따라가지 않아요.」
- 확인 창을 열 때 `requestId`를 만든다. 다시 누르면 같은 값을 보낸다.

그 밖:

- 쓰기 뒤 새로 읽도록 `adminIsTrackedWrite`(303행)에 새 경로 둘을 더한다.
- 디자인 문법은 [워크스페이스 시그널 README](../../../../디자인/워크스페이스_시그널/README.md)의 「Workspace 전면 개편과 관리자 화면 · 2026-11-14」 기록을 따른다.

## 6. 위험, 바꿀 파일, 시험, 배포

### 위험과 막이

| 위험 | 막이 |
|---|---|
| 권한 상승 | 회사 관리자와 중앙 수동 열람권, 두 겹을 모두 요구한다. 교사 넣기는 열람권을 따로 둔다. `admin.*`는 허용 목록 밖이다. 이 도구가 쓰는 source `workspace-admin`은 관리자 판정(`manual`)에 걸리지 않는다. 관리자 올리기는 주인만 하고 중앙 권한은 따라가지 않는다. |
| 교사 자격이 「그 반」보다 넓음 | 옛 `teach` 골든 표본이 반을 보지 않았다. 상세와 판정에 담당 조건을 건다. 이 도구가 만든 직원 줄은 마지막 배정을 지울 때 닫는다. |
| 다른 학생 기록 열람 | 교사 넣기는 그 반 학생의 과제 글(공유 무관), 옛 엔진 기록, 공유를 켠 학생의 WORLD 기록을 연다. 학생 넣기는 앞으로 낼 과제 글을, 옮기기는 옛 엔진 기록을 새 반 교사에게 연다. 막이는 열람권 둘, 15분 재확인, 하루 상한, 대표 알림, 감사, 확인 창 문구다. `class.people`은 기록을 싣지 않는다. |
| 회사 서버 세션 탈취 | 회사 서버가 대표 토큰을 계속 갱신한다. 쓰기와 ④는 회사의 `interactiveAt`과 중앙의 인증 시각, 둘 다 15분 안이어야 한다. 하루 상한이 피해를 묶는다. 대표의 휴대폰에 알림이 가고, 화면 맨 위에 중앙 감사 목록이 있다. 중앙 열람권 줄은 운영 SQL로 바로 거둘 수 있다. |
| 자격 증명 없는 시작 세션 | `/api/launch` 세션에 `via:'launch'`를 적고, 중앙 호출과 ④가 거절한다. |
| 잘못된 SYNK ID | 명부에서 고르기만 한다. 확인 창에 이름, 이메일, 가입일을 보인다. 중앙이 계정 활성과 로그인 주인 하나를 확인한다. 빼기는 온전한 되돌리기가 아니다(줄과 번호가 남고, 다른 반 코드로 못 들어오고, 영상 이용이 돌아오지 않는다). 그래서 넣기 확인 창을 무겁게 둔다. |
| 동시 변경 | 교실 코드와 같은 잠금 차례를 쓴다. unique 제약(`learners.auth_user_id`, `staff_classes` 기본 키, `class_key`, `student_code`)이 마지막을 막는다. 학생 번호는 전역 잠금 안에서 정한다. 재전송은 `request_hash`로 가린다. ④는 `expectedRole`을 본다. |
| 감사 | 중앙 감사 표(덧붙이기만, 거절 포함), 이용 권한 사건 표, 회사 `audit`에 남는다. 교사 빼기로 지워지는 코드 줄은 감사 `before`에 남는다. 이름과 이메일은 적지 않는다. |
| 관리자가 여럿 | 「첫 활성 관리자」 자리 넷을 주인 우선으로 바꾼다. 주인은 `settings` 덮어쓰기와 분리한 문서에 둔다. |

### 배포 차례

회사 판은 둘로 나눈다. ④는 중앙과 상관없이 설 수 있고, 되돌릴 때의 차례가 달라서다.

1. SYNK-talk: 마이그레이션, `synk-account` 함수, 다시 만든 `synk-classroom` 묶음, `teach` 함수를 올리고 CI를 통과시킨다.
2. 운영 SQL 두 줄: 대표 계정에 `platform` / `admin.workspace-grants`와 `platform` / `admin.workspace-staff`, source `manual`을 넣는다. 운영 DB 쓰기이므로 대표 허락 뒤 한 트랜잭션으로 한다.
3. 회사 판 A: 주인 문서, 「첫 활성 관리자」 자리 넷, `via:'launch'`, `interactiveAt`, ④, 대표 알림.
4. 회사 판 B: 중앙 호출 경로와 「반」, 「이용 권한」 칸, 최근 부여 목록. 판 A와 1, 2가 선 뒤에 올린다.
5. 운영 확인: 대표 계정으로 `test-` 반에서 넣기와 빼기를 한 번 해 본다.

회사 판 A와 B는 `.tmp/company-ha-release-order-20261020.md`의 06시 · 17시 묶음 규칙을 따른다.

되돌릴 때의 차례:

1. 회사 판 B를 먼저 되돌린다. 화면에서 두 칸이 사라진다.
2. 급하면 운영 SQL로 두 열람권 줄의 `revoked_at`을 적는다. 중앙 쓰기가 바로 막힌다.
3. 중앙 함수를 되돌린다. 감사 표는 남긴다(덧붙이기만 하는 표라 옛 코드와 부딪히지 않는다). `teach` 골든 조건은 따로 되돌리지 않는다.
4. 회사 판 A를 되돌리기 전에 올린 관리자를 모두 내린다. 옛 코드는 다른 관리자를 바꾸지 못하고 「첫 활성 관리자」를 다시 짐작한다.

## 7. 정할 것

1. **다른 반 학생 옮기기.** 기본값: 확인 창(옛 기록이 새 반 교사에게 보임, 과제는 옛 반에 남음, 옛 반 영상 이용 멈춤)을 거쳐 옮긴다.
2. **새 학생 번호의 꼴.** 기본값: 반과 무관한 전역 순번, 기존 발급기 꼴(예: `SYNK-1043`).
3. **수업 영상 기간.** 기본값: 주기는 운영 SQL로 둔다. 빼기와 옮기기의 거두기는 이 화면이 한다.
4. **이용 권한 허용 목록과 기한.** 기본값: `library.*` 일곱은 기한 없이 준다. `practice.plus`와 `town.access.trial`은 기한을 꼭 정하고 최대 6개월이다. `town.access.subscription`은 첫 판에서 뺀다.
5. **관리자를 올리고 내리는 사람.** 기본값: 대표(주인)만 한다. 15분 재확인을 거친다.
6. **올린 관리자에게 중앙 권한을 줄지.** 기본값: 주지 않는다. 시험으로 고정한다.
7. **하루 상한.** 기본값: 교사 넣기 5건, 반 만들기 5건, 관리자 올리기 1건.
