# 플랫폼 제작 인사이트 조사와 여러 계정의 역할

사용자 요청은 PC가 꺼져 있어도 공개 콘텐츠 조사를 이어 가고, 완성 결과가 들어오면 워크스페이스와 열려 있는 자료 화면에 반영하는 것이다. 직원은 준비된 제작 양식을 골라 사용중 표시를 확인한다. 외부 SNS 게시나 직원 자동 배정은 포함하지 않는다.

## 한도를 늘리기 위한 계정 묶음이 아니라 조사 분담

기존에 연결돼 있고 현재 구독에서 Spark를 사용할 수 있는 계정만 대상으로 한다. 계정이 여러 개라는 이유로 각 계정에 신규10개씩을 요구하거나 회사 전체의 하루 신규 가이드10개 상한을 늘리지 않는다. 같은 원본의 갱신은 새 입장으로 세지 않고 실제 확인 시각·제작 품질·브랜드 적용을 개선한다. 구독 한도나 동시 작업 제한에 걸리면 무리한 중복 실행 대신 실제 부족 범위와 다음 회차를 남긴다. 새 결제·권한·인증·로그인·외부 AI API를 자동으로 마련하지 않는다.

첫05:00 KST 전체 조사는 유지한다. 추가 슬롯은 다음처럼 3시간 간격으로 엇갈리고 계정별 반복은6시간인 역할 분담 예시다. 실제 계정/구독/연결/쓰기 가능 여부를 확인한 뒤 기존 예약 지침에서 작업을 분담한다. 이 표 자체는 실제 예약 생성이나 계정 배정 증거가 아니다.

| 한국 시간 | 조사 역할 | 목표 |
|---|---|---|
| 05:00 | 전체 조사 | 공개 후보18~24개를 깊게 비교하고 하루 신규 약10개를 선별한다. |
| 08:00·14:00·20:00 | YouTube·TikTok 원문 담당 | 최근 공개 영상/광고와 원본의 제작 구조를 재확인하고 기존 가이드의 관찰·실행안을 보완한다. |
| 11:00·17:00·23:00 | Facebook·Instagram·브랜드 적용 담당 | 실제 공개 릴스/광고의 새 신호와 브랜드별 차이·준비물·실행순서·어필을 보완한다. |

하루 슬롯7개를 먼저 모두 켜야 한다는 뜻은 아니다. 기존계정 하나만 사용할 수 있으면05:00을 유지하고 필요한 추가 회차를 그 계정의 실제 한도 안에서 배정한다. 조사 시간이 긴 회차와 다음 회차가 겹칠 때 동일 writer는 진행 중 작업을 중단하거나 같은 Doc에 두 완성 결과를 동시에 쓰지 않는다. 초과 슬롯이나 확인을 기다리는 회차는 보류한다.

## 매 실행 시각과 원문 시각

예약 지침에는 특정 날짜나 ‘현재시각’을 고정하지 않는다. 매 실행의 시작과 완료에 공개 읽기전용 [워크스페이스 시각](https://workspace.synk.im/api/creative-research/time)을 실제로 조회한다. 응답은 `{now,nowKst,timeZone:'Asia/Seoul',dateKst,windows:{sixHoursAgo,dayAgo,weekAgo}}`이고 회사·계정·Doc 정보를 포함하지 않으며 캐시하지 않는다. 첫 응답의 실제UTC `now`를 시작/기준에, 마지막 응답의 `now`를 완료에 쓴다. 아직 배포 전이거나 읽기에 실패하면 사용 가능한 네이티브 신뢰 시간 도구 또는 원격 컴퓨터의 실제 시스템 UTC 시계를 조회해 Asia/Seoul(UTC+09:00)로 변환하고 사용한 방법을 밝힌다. 모델 기억·사용자가 예전에 말한 시간·검색 페이지의 오래된 스니펫은 현재 시각 근거가 아니다. 정확한 시각을 실제로 조회하지 못하면 완료 시각을 지어내거나 새 JSON을 완료 처리하지 않는다.

대체 시계의 값도 저장 계약에 맞게 정규화한다. `researchStartedAt/asOfAt/researchCompletedAt/checkedAt`에는 초가 필수이고 소수점은 없거나1~3자리, 시간대는 `Z` 또는 `±HH:MM`이어야 한다. 권장 출력은 UTC의 `YYYY-MM-DDTHH:mm:ss.sssZ`다. 마이크로초·나노초는 소수점 앞3자리까지만 남기고 반올림하지 않으며, 오프셋 시각은 같은 순간의 UTC로 변환한다. 초 단위 입력을 `.000`으로 직렬화할 때는 밀리초까지 실측했다고 하지 않고 실제 도구의 초 단위 정밀도를 한계에 남긴다. 분까지만 있는 시각·시간대 없는 값·콜론 없는 오프셋은 그대로 제출하지 않는다. 초를 임의로 채우지 말고 초와 시간대가 있는 실제 시계를 다시 조회한다. 조회할 수 없으면 이전 완료 본문을 보존하고 시각 확인 불가로 보류한다. 이 정규화는 표기만 바꾸며 과거 게시일·원문 확인 시각을 현재 값으로 고치지 않는다.

v1 보고서의 선택 시각 필드는 다음 세 개이며 하나라도 넣으면 모두 필요하다. 새 producer 지침은 세 개를 채운다. 기존 v1 보고서의 세 필드가 모두 없는 형식은 호환한다.

- `researchStartedAt`: 이번 실제 조사 시작 시각.
- `asOfAt`: 6시간/24시간/7일 구간을 판단할 이번 조사 기준 시각. 시작 시점의 실제 시각을 사용한다.
- `researchCompletedAt`: 검증과 작성이 끝난 뒤 다시 조회한 실제 완료 시각.

시작≤기준≤완료≤서버의 실제현재시각이어야 한다. `date`는 완료 시각의 한국 날짜이며, 항목별 `checkedAt`은 실제로 그 원문을 확인한 시각으로 조사구간 안에 둔다. 조사 중 자정이 넘어가도 항목을 확인한 시각을 완료일로 바꾸지 않는다. 서버가 받아들이는 조사 시작의 한국 날짜도 오늘/어제 범위로 제한한다. 그보다 오래 걸린 회차는 실제 원문을 새로 확인하거나 한계를 알리고 이전 완료 문서를 보존하며 시각만 고치지 않는다. `research.publishedAt`은 원문에 표시된 실제 게시 시각이고 모르면null이다. 오래된 영상의 게시일·조회수·반응을 지금 값처럼 바꾸지 않는다. 갱신된 표시정보와 이전 제작 가이드의 관찰 근거는 독립된 날짜로 표시한다.

게시 정보가 `YYYY-MM-DD`까지만 보이면 producer는 `publishedAt:null`과 원문 게시 날짜·시각/시간대 미확인 한계를 기록한다. 임의 자정·한국 시간대나 이번 조사 시각을 게시 시각으로 채우지 않는다. 날짜만 있는 native Doc를 수신 경계에서 정규화하는 v15 호환 후보는 운영에 적용하지 않았다. 현재 운영의 엄격한 시각 검증에 맞춰 producer 원문을 바로잡으며 직접 JSON/API 검증도 완화하지 않는다. 항목별 `checkedAt`도 실제 확인 시각이며 마지막 조사 시각으로 일괄 복사하지 않는다.

최근6시간 신호,24시간 변화,7일 반복 패턴은 기준 시각에서 거슬러 올라간 실제 구간이다. 플랫폼에 해당 시간 필터가 있으면 실제 적용 여부와 조건을 남긴다. 필터가 없으면 공개 게시 시각을 확인해 직접 비교하거나 제한을 밝힌다. 게시 시각이 없으면 그 구간의 신규라고 확정하지 않는다. TikTok Top Ads의7/30일 표시기간과 게시시각, Meta 광고의 시작일과 릴스 게시일, 국가 검색조건과 실제자료국가는 서로 다르다. 어떤 필터/범위로 원문을 찾았고 어떤 항목이 미확인인지 `research.whyNow`와 `research.limitations`에 기록한다. 최근30일 같은 기간 설명도 이번 실제 기준 시각으로 계산한다.

## 근거와 실제 제공 범위

관찰 근거의 `observedFacts.sourceUrl`도 해당 항목의 `source/kind`와 같은 URL 검증을 받는다. 주소를 생략하면 항목의 원문 주소를 쓰며, 다른 플랫폼·형식의 보조 근거를 이 필드에 넣어 전체 보고서 검증을 깨뜨리지 않는다. 보조 출처는 관찰 문장과 한계에서 설명하거나 별도 허용 항목으로 구분한다. `evidenceLevel`은 `video-watched/page-read/metadata-only`만 허용하며 검색 요약만 본 자료는 JSON에서 제외한다. `metadata-only`의 `hook/structure`는 생략 또는 정확한 빈 문자열만 쓰고 `productionGuide`는 넣지 않는다.

이번 새 producer JSON에는 구체 영상·릴스·광고만 담는다. `best-practice/insight`, Studio 검색 수요·계정 인사이트는 채팅의 보조 참고로만 설명하며 기존 저장 자료는 유지한다. 기존 형식이 서버에 호환된다는 사실을 공개 조사자가 계정 연결 없이 인사이트를 가져올 수 있다는 뜻으로 해석하지 않는다.

`metrics`에는 `views/likes/comments/shares/saves/reach` 여섯 키만 둔다. TikTok의 `ctrTopPercent/budgetLabel/durationSeconds`는 선택 필드이며 `entries` 안의 해당 항목 최상위, 즉 `metrics/research`와 같은 깊이에 둔다. 이 세 필드를 `metrics`나 `research` 안에 넣으면 보고서 전체가 거절된다. CTR Top은 실제 클릭률이 아니라 Top Ads 표본의 상대 상위 백분위다.

제작 가이드의 훅·실행안에도 근거 없는 통계·효과/절감/성공률 보장·확인하지 않은 이용자 성과를 넣지 않는다. 원문 통계는 표본·조건·출처를 확인하며, 자체 목표는 실제 결과와 구분한다. SYNK가 제공하는지 확인되지 않은 당일 수업·대기 없는 배정·무료 입학 가능성 진단 등은 신청/즉시 제공/예약 가능을 약속하지 않고 기획 검토안으로만 남긴다. 원문 관찰과 우리 제안은 구분하고, 확인하지 않은 재생·컷·대사·수치를 실제 확인한 사실로 보고하지 않는다. 보조 참고만 있는 보고서를 준비된 제작 가이드10개로 간주하지 않는다.

배수·시간 절감·관광객0명·실패 없음·독점·완전 전환도 실제 조건·표본·측정 근거가 없으면 성과 주장으로 쓰지 않는다. 필요한 가상 입력이나 시험 목표는 각 장면에서 가상 제작 시험 또는 검증 전 목표라고 명시하고 실제 사례·확인된 결과로 표현하지 않는다. 가상 표시를 붙여도 이용자에게 성공·무실패를 보장하지 않는다.

## writer마다 전용 비공유 Doc

동일 Doc를 여러 Gemini 계정/작업의 결과 저장소로 쓰지 않는다. 서버의 source마다 `{id,documentId,connectionId|null}`를 연결하고 각 Doc는 한 writer만 갱신한다. 기존05시 작업은 기존 전용 Doc를 그대로 유지한다. 추가 source의 Doc ID와 writer가 실제로 지정되지 않았다면 기본 Doc에 대신 쓰지 않고 회차 결과를 채팅에만 남기며 미연결을 알린다.

서버가 읽을 수 있는 Doc는 기존 OAuth 앱의 전용 표식이 있고 기존 연결 계정으로 읽을 수 있는 문서다. Gemini에 계정이 보인다는 사실만으로 다른 계정의 Doc 쓰기나 서버 읽기가 되는 것은 아니다. 추가 writer 계정에 맞는 기존 연결이 없거나 Doc의 실제 소유 계정이 다르면 새로운 OAuth/공유 권한 없이 그 source를 활성화할 수 있다고 주장하지 않는다. 민감한 계정 식별자·토큰 대신 운영 상태에 연결 가능/미확인 여부만 기록한다.

각 writer는 조사 중 이전 완료 본문을 보존한다. 최종 보고서를 완성하고 검증한 뒤 자신의 Doc 본문을 단일 JSON과 마지막 `SYNK_CREATIVE_RESEARCH_COMPLETE`로 교체한다. 부분 결과·진행 로그·사람용 보고서를 이 Doc에 섞지 않는다. 저장 실패/확인 대기/무권한이면 이전 본문을 지키고 해당 source만 보류한다. 같은 원본이 다른 source에서 들어와도 회사 풀은 canonical 원본과 실제 확인 시각으로 중복을 막으며 개인 메모·선택 상태를 보존한다.

전용 GoogleDoc의 자동 반영 본문은 **일반 문단의 순수 텍스트 JSON 객체 하나**와 마지막 한 줄 `SYNK_CREATIVE_RESEARCH_COMPLETE`로 저장한다. 네이티브 코드블록·서식 있는 코드 영역·Markdown 코드펜스·사람용 제목이나 설명은 Doc에 넣지 않는다. 채팅의 설명용 코드블록을 그대로 복사해 Doc에 붙이지 않으며, 코드블록 경계문자 `U+EC03`·`U+EC02`도 본문에 넣지 않는다. 완료 행에는 앞의 숨은 문자나 접두사 없이 정확한 일반 밑줄 문자로 된 완료 표시만 둔다.

JSON은 실제 직렬화된 문자를 유지한다. 문자열 내부의 유효한 JSON 이스케이프인 `\"`, `\\`, `\n` 등을 제거하거나 전체 본문을 Markdown 방식으로 unescape하지 않는다. JSON 배열·속성·URL·완료 표시를 Markdown용 역슬래시로 다시 이스케이프하지 않는다. 허용되는 파일 앞 BOM과 본문 밖 공백을 제외한 JSON의 첫 문자는 `{`이며, 마지막 완료 행과 JSON 본문은 줄바꿈으로 구분한다.

저장한 뒤 **같은 지정 Doc에서 실제 본문 텍스트를 다시 읽어** JSON 파싱, 보고서 식별자·시각·항목의 내용 일치, 마지막 완료 행의 정확한 문자 일치를 확인한다. 채팅 코드블록, 화면의 저장 표시, Markdown 변환 과정에서 숨은 경계문자가 빠진 결과만으로 이 검증을 대신하지 않는다. 첫 JSON 문자와 완료 행 앞에 `U+EC03`·`U+EC02`가 남아 있으면 전달 형식 오류로 기록하고, 읽은 원문을 임의로 정리한 파생본의 성공을 실제 저장 성공으로 보고하지 않는다.

전달 형식 교정은 같은 완성 보고서의 일반 문단 저장을 고치는 단계다. 이 전달 형식 교정 단계에서는 별도 원문 조사를 시작하지 않는다. 다음 예약의 새 조사 회차는 기존 계약대로 실제 현재 시각을 조회하고 새 원문을 확인한다. `reportId`의 명시적 교정 버전을 제외한 실제 조사 시각·날짜·확인 시각·출처·수치를 새 값으로 바꾸지 않고, 최근 검색 창의 의미나 JSON 스키마를 완화하지 않는다. 실제 읽은 Doc 원문 검증과 서버 수신·반영은 별도 단계로 보고한다. 형식 오류를 capacity 재시도 대상으로 바꾸지 않으며, 기존에 정한 일시 용량 오류의 총 횟수·대기·권한 범위를 그대로 유지한다.

이미 접수된 제작 가이드의 내용·근거 수준을 정정할 때는 새 `reportId`와 선택 필드 `supersedesReportId`로 기존 접수 보고서를 명시한다. 교정 보고서에는 실제 접수된 대상만 포함하며, 같은 작성 경로·공유 범위·원래 조사 시각 3개·항목 확인 시각·현재 출처 영수증이 모두 일치해야 한다. 서버는 이 조건을 확인한 교정에 한해 과거의 잘못된 `video-watched` 가이드를 정직한 `page-read` 가이드와 적용 제안으로 바꿀 수 있다. 새 관찰로 갱신된 항목·다른 작성 경로·미접수 항목이 섞이면 전체 교정을 거절한다. 수정 시간을 새 원문 확인 시각으로 꾸미거나 근거 수준을 높여 보존 조건을 우회하지 않는다. 일반 예약 조사는 이 필드 없이 기존 계약대로 진행하며, 접수 여부를 모르면 교정 대상을 추정하지 않는다.

교정도 기존 ID·직원 메모·비공개/보관·사용 상태와 하루 신규 입장 수를 보존한다. 접수 전 원문과 기존 보고서는 보관하며, 같은 교정 보고서의 재수신으로 항목을 더 만들지 않는다. 하루 제한으로 보류된 항목 수는 그 보고서에서 입장하지 못한 개수이며, 다음 날 자동 처리할 별도 대기열을 뜻하지 않는다. 다음 회차의 새 조사와 기존 항목 갱신은 원래 일정으로 계속한다.

기존 네이티브 클라우드 Docs 도구가 명시한 일시적 capacity/out-of-capacity·quota/rate-limit에만 최초 포함 총3회 이하로 저장한다. 재시도 전 자기Doc를 읽어 같은 최종 JSON·reportId·실제 시각·완료 표시가 이미 저장됐으면 즉시 끝내고, 성공 여부를 읽지 못하거나 다른 writer의 새 본문이 있으면 덮어쓰지 않는다. 지원되는 클라우드 대기로 Retry-After를 우선하고 없으면30초·120초, 최초 오류부터10분 이내에서만 재시도한다. 인증·권한·사용자 확인·읽기 실패·잘못된 JSON에는 이 재시도를 적용하지 않으며 새 조사·예약·유료 API·로컬 우회로 바꾸지 않는다.

현재 Doc 등록은 새로 읽어 올 writer의 입구를 통제한다. 이미 서버가 받아들인 자동 회사 보고서의 `entryIds/automaticSourceId`로 출처가 증명된 회사 자료는 source를 빼거나 Doc를 교체한 뒤에도 현재의 확인된 writer가 같은 원문의 최신 관찰·가이드를 개선할 수 있다. 임의 sourceTag만 있는 행·다른 소유자의 수동 자료·모든 개인 자료는 이 갱신 대상이 아니다. 자료의 메모·보관·선택 상태와 원문 게시·관찰·가이드 근거 시각을 보존한다. 용량 때문에 새 참고 관찰을 보류해도 같은 유효 보고서의 제작 가이드 반영을 막지 않으며, 전체 보류와 참고 관찰/제작 가이드 보류 수를 나누어 표시한다.

## PC 독립성과 실제 확인 범위

[Spark 예약 도움말](https://support.google.com/gemini/answer/17094710?hl=en)은 클라우드에서 실행돼 기기가 꺼져도 계속한다고 명시한다. 실행 시간은 근사치이며 사용량·동시 작업·높은 트래픽 때문에 지연/미실행할 수 있다. `Run now`는 시험용 선택 기능이고 매회 수동 실행 의무가 아니다.

[Spark 기능 도움말](https://support.google.com/gemini/answer/17094507?hl=en)은 기존 Docs 편집을 지원하되 공유 문서 편집은 확인이 필요하다고 설명한다. 로컬 Chrome 자동탐색은 PC/Chrome이 켜져 있어야 하고 확인을 요구하며, 원격 브라우저도 로그인에서 사용자 인계로 멈출 수 있다. 이 도움말의 종료 절에는 기기 종료 조건에 관해 예약 전용 도움말과 충돌하는 문장이 있어 모든 경로를 같은 무인 실행으로 보장하지 않는다. 비공유 Doc의 매회 무승인 기록도 문서만으로 확정하지 않고 실제 예약에서 확인한다.

[Custom Apps 도움말](https://support.google.com/gemini/answer/17209137?hl=en)은 모든 외부 MCP 쓰기에 수동 확인을 요구한다. 이를 무인 업로드 우회로 사용하거나 읽기 기능으로 쓰기를 위장하지 않는다. native 월정액 기능과 개발자 API는 별개이며 새 유료 API로 전환하지 않는다.

실제 자동화 성공은 각 source의 예약 실행→완성 Doc 저장→서버 수신/엄격 검증→신규/갱신/보류 숫자→열린 자료 화면 반영→같은 보고서 재수신 추가0으로 확인한다. 앱의 변경 알림은 현재 권한에서 다시 읽으라는 신호만 전달하며 보고서 본문·개인 자료를 이벤트에 넣지 않는다. 네트워크 재연결 후에도 현재 상태를 다시 조회한다. 직원 선택/해제 역시 서버의 원자적 판정과 재조회 결과를 기준으로 한다. 실제 프로듀서 저장·운영 연결을 확인하기 전 후보 소스나 합성 시험을 상시 자동화 완료로 보고하지 않는다.

이 원문은 최신 요청의 운영 계약이다. 실제 source/예약/계정 설정은 현재 연결·승인된 범위와 운영 인수 결과에 맞춰 별도로 남긴다. 공용 server/CSS 전체 교체, 다른 자료 삭제, 현재 진행 중 조사 중단은 하지 않는다.
