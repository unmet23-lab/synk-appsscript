## 한 줄 결론

워크스페이스에는 24·72시간 관측의 틀(관측 예약, 지표 10개, 같은 조건 비교, 「수치 보완」 할 일)과 수집기가 **이미 있다**. 새로 만들 것은 넷이다.

1. 워크스페이스 밖에서 올린 게시물을 **게시 주소 하나로** 관측 대상에 넣는 길
2. 수집기가 비워 두는 지표(평균 시청 시간·완주·저장·도달 등)를 공식 API에서 **더 받아 오기**
3. 관측 시점을 **놓치지 않게** 하는 운영 점검
4. 맞춤 도구 유입을 **추적 링크**로 세고, 제작 방식 v2 §6의 판정(계정 안 상위 25%)을 붙이기

## 2. 빈 곳

1. **밖에서 올린 게시물이 관측 대상이 아니다.** API(`POST /api/post-performance`)와 작업실 폼(제작 도구 → 게시 준비·성과 → 「2. 게시 후 성과」의 「게시한 콘텐츠 등록」)으로 주소를 넣을 수는 있지만, 캠페인·성과에서 바로 가는 입구가 없고 게시 시각을 손으로 넣어야 한다. 넣은 시각이 플랫폼 시각과 5분 넘게 다르면 수집기가 게시물은 찾지만 자동 기록을 거부하고(`PUBLISHED_AT_MISMATCH`) 재시도 없이 「손 입력 필요」로 넘긴다(`post-performance.mjs:283, 289-292`). 유튜브 주소에는 채널 정보가 없어 등록 단계에서 남의 영상도 받는다(`post-performance.mjs:146`). 형식은 게시 묶음 없이는 못 정해 72시간 중앙값 비교에서 빠진다(「자료 부족」만 뜸).
2. **채워지는 지표가 적다.** 수집기가 요청하는 것은 유튜브 조회·좋아요·댓글(+공유), 인스타 조회·도달·공유·저장뿐이다. 평균 시청 시간·완주율·3초 유지율·맞춤 도구 유입은 늘 손 입력이고, 인스타는 권한이 없어 넷 다 비어 있을 가능성이 크다.
3. **관측을 놓칠 수 있다.** 10-15 두 건의 24시간 관측을 놓쳤는데, 그때는 운영 수집기가 아직 돌지 않던 때(커밋 `be42bc375`, 10-17 전)로 보여 「돌면서 놓친」 증거는 아니다. 다만 지금 규칙은 세 번 실패(5분·15분 뒤 재시도)하면 창이 닫힐 때까지 「손 입력 필요」로 넘겨서(`post-performance.mjs:246, 289-291`), 35분 넘는 장애가 나면 6시간 창을 통째로 잃는다. 놓친 지점은 「지금 숫자로 과거를 채우지 않는다」 규칙 때문에 빈칸으로 남는다(규칙 자체는 맞다).
4. **맞춤 도구 유입을 못 센다.** 추적 링크를 붙인 게시물만 셀 수 있다. 이번 편처럼 DM·설명란에 GitHub 주소를 바로 넣으면 셀 길이 없다.
5. **판정이 없다.** 같은 형식 3편 이상의 중앙값 비교는 있지만, 제작 방식 v2 §6의 「그 계정 안에서 상위 25% / 하위」 판정과 다음 할 일(세 편 더 / 훅 바꿔 다른 계정에서 시험)은 없다.

## 3. 원천별로 더 받을 수 있는 것

2026-10-18 공식 문서 기준. 출처 번호는 이 장 끝 목록. Fable이 같은 날 인스타 미디어 인사이트·변경 기록과 유튜브 지표 정의(I1 I2 I3 I5 Y1)는 페이지로 다시 확인했다. Y2·Y3·Y5·Y8·Y12·Y16·I4·I6·I7·G1은 다시 보지 못해, 그 출처에만 기댄 줄은 「확인 필요」로 표시했다.

| 쇼츠 「Stayed to watch」(봤음 대 넘김) | **없음** | — | Y16 |

- 24시간 지점은 `videos.list` 값을 지금처럼 그 시각에 찍는다.
- 72시간 지점의 시청 지표(평균 시청 시간·평균 시청 비율·공유 등)는 처리 지연 때문에 그 시각에 받을 수 없다. 나중에 받는 값은 「지금 숫자로 과거 채우기」가 아니라 플랫폼이 날짜별로 다시 센 값이라 원칙과 충돌하지 않는다. 그러나 **지금 코드는 받지 못한다** — 비교는 관측 시각이 `dueAt`~`closesAt` 안인 값만 쓰고 지연을 관측 시각 차로 재므로(`post-performance.mjs:97-104`, `publication-learning.mjs:46`), 5일째 값은 `measurementWindowMissed=true`로 빠진다.
- 그래서 **「창 지표」를 별도 출처 종류로** 둔다: `kind:'window'`, 창 시작·끝(태평양시 날짜), `fetchedAt`, `lagged:true`를 남기고, 72시간 지점에서 **비어 있는 지표에만** 보완 저장한다(그 시각에 찍은 값은 덮지 않는다). 창은 **「게시일(태평양시) 포함 3일」**로 고정한다 — 하루 단위라 게시 시각에 따라 게시 뒤 48~72시간을 덮지만, 같은 창 정의끼리만 비교하므로 괜찮다. 게시 5일째에 **한 번만** 받고 다시 받아 덮지 않는다. 창 지표끼리 비교할 때는 관측 지연 규칙(15분)을 적용하지 않는다.
- 권한은 `yt-analytics.readonly` + `youtube.readonly`(Y3 Y10). 브랜드 채널은 **채널마다 따로 승인**해 채널별 refresh token을 보관해야 한다(Y3 Y11 Y13).
- **함정:** OAuth 동의 화면이 「외부 + 테스트」 상태면 refresh token이 **7일 뒤 만료**돼 자동 수집이 일주일마다 끊긴다(Y12, 확인 필요). 같은 OAuth를 쓰는 10-15 유튜브 발행 연결도 같이 끊긴다. 운영(게시) 상태로 바꾸면 미검증 경고가 뜨지만 우리만 쓰면 문제없다(Y15).
- 할당량: Data API 하루 10,000단위, `videos.list` 1단위(Y8 Y14). Analytics 요청 1건 1단위(Y5)는 확인 필요.

| 리포스트·페북 동시게시 조회 | `reposts` · `crossposted_views` · `facebook_views` | 〃 | I1 I2 |

- 게시물 지표는 기간이 `lifetime`뿐이라 24·72시간에 **스냅샷**으로 찍어야 한다. 최대 48시간 늦게 차므로 24시간 값은 덜 찰 수 있다. 값이 없으면 0이 아니라 빈 결과가 온다(I1).
- 권한은 `instagram_business_basic` + `instagram_business_manage_insights`(Instagram 로그인 — I1 I3 I5에 명시, 10-18 재확인). 우리 소유 계정만 쓰면 App Review 없이 Standard Access로 된다(I3 I4).
- 장기 토큰은 60일, 발급 24시간 뒤부터 갱신 가능(I5 I6). 회사 서버에는 이미 자동 갱신이 있다(`oauth.mjs:274-283`, 만료 7일 전·발급 24시간 뒤, Instagram 로그인 토큰만 — 10-14에 재사용한 금고 토큰은 대상이 아니다). 호출 한도 「앱·사용자 쌍마다 24시간에 4,800 × 노출 수」(I4 I7)가 Instagram 로그인 토큰에도 같은지는 확인 필요.
- API에 없는 것: 릴스 팔로우 수(`follows`·`profile_visits`는 피드·스토리만), 유지율 곡선, 조회 출처, 팔로워·비팔로워 구분(I1 I8).

## 4. 밖에서 올린 게시물 등록

- **화면(Claude, 10-18 만듦 · 서버 통합 브랜치에 포함):** 캠페인·성과 02 「게시물별 관측 기록」 머리에 「게시 주소로 추가 ↗」(쓰기 권한일 때만). 누르면 작업실의 기존 등록 폼이 열린다 — 입구를 둘로 나누지 않으려고 새 대화상자 대신 그 폼에 「주소 확인」을 붙였다. 계정을 고르고 주소를 붙이면 서버(S1)가 읽은 게시 시각·제목·형식을 채우고 24·72시간 확인 시각을 보여 준다. 사람은 형식(쇼츠/영상/릴스)만 확인하고 저장한다. 남의 게시물이면 저장을 막는다. 확인 불가(`ownerMatch: null`)·게시 시각 없음이면 유튜브·인스타는 채널 연결과 주소를 확인한 뒤 재조회하도록 안내하고, 나머지 플랫폼은 게시 시각 손 입력을 안내한다. 유튜브·인스타 등록은 서버가 소유·플랫폼 게시 시각을 다시 확인한다. 서버가 S1과 함께 `lookupAvailable` 신호를 켜기 전에는 「주소 확인」이 보이지 않고 지금처럼 게시 시각을 손으로 넣는다. 폼은 그 자리만 고쳐 그려서 계정을 고를 때 맨 위로 튀던 기존 문제도 없앴다. 게시 흐름 49/49·캠페인 115/115·딥링크 QA 다섯 경우를 재확인했고, 18:57 안내 수정도 보존했다. 상세·고친 파일은 [GPT 인계 「Claude가 맡은 화면」](성과_자동수집_1단계_GPT인계_20261018.md).
- **서버(GPT):**
  - 유튜브: 주소의 영상 ID → Data API `videos.list`(`snippet.publishedAt`·제목·`contentDetails.duration`). 쇼츠 여부는 API가 따로 알려 주지 않으므로 주소 형태(`/shorts/`)와 길이로 제안하고 사람이 확인한다.
  - 인스타: 연결 계정의 미디어 목록에서 permalink의 shortcode가 같은 항목을 찾아 `timestamp`·`media_product_type`(REELS)을 쓴다. 댓글 DM 등록 도구의 `inspectPost`(SYNK-talk `tools/synkbrief-publication.js:135-148`)는 id·permalink만 읽으므로, 비슷하게 쓰되 `timestamp,media_product_type` 필드를 더한다.
  - **소유 확인:** 유튜브는 `snippet.channelId`가 고른 채널의 `externalId`와 같을 때만, 인스타는 연결 계정의 미디어 목록에 있을 때만 받는다. 지금 `register`는 유튜브 주소에 채널 정보가 없어 남의 영상도 받는다(`post-performance.mjs:146`).
  - **화면이 부를 계약(새):** 입력 `channelId`·`url` → 출력 `publishedAt`(플랫폼 값)·`suggestedFormat`·`title`·`ownerMatch`. 사람이 확인하면 기존 `POST /api/post-performance`로 등록한다.
  - 게시 시각은 사람이 넣지 않고 플랫폼 값을 쓴다(5분 어긋남으로 자동 기록이 거부되는 일이 없어진다). 손 입력 플랫폼(스레드·X 등)은 자동 채움이 안 되므로 지금처럼 사람이 넣는다.
  - 게시 묶음이 없어도 형식을 정할 수 있게 출처 표시(예: `origin: 'external'`)와 함께 `publicationFormat`을 허용한다. 그래야 72시간 비교의 같은 형식 표본에 들어간다.
  - 이미 `closesAt`이 지난 지점은 지금처럼 `missed`로 두고, 손 입력(과거 `measuredAt`)은 그대로 받는다.
- **이 저장소의 게시 절차:** Claude·GPT가 브라우저로 직접 올린 뒤 같은 등록 API를 한 번 부르게 한다(게시 결과 문서의 「게시」 단계 끝에 한 줄). 그러면 이번처럼 Claude 예약 작업으로 따로 읽을 필요가 없다.

## 6. 제작 방식 v2 §6의 네 숫자와 맞물림

| v2 §6 | 워크스페이스 지표 | 받는 길 |
|---|---|---|
| 초반 유지(인스타 3초 유지율, 유튜브 본 비율) | `earlyRetention3sPct` | 인스타: `reels_skip_rate`로 `100 − 넘긴 비율`을 계산해 넣는다(추정·개발 중 지표라 출처에 표시). 유튜브: 쇼츠 「Stayed to watch」는 API에 없어 **손 입력**. `engagedViews ÷ views`를 참고로 따로 보여 줄 수는 있으나 같은 지표가 아니다 |
| 평균 시청률·완주 | `averageWatchSeconds`, `completionRatePct` | 평균 시청 시간: 유튜브 `averageViewDuration`(72시간 지점은 「창 지표」로 게시 5일째 한 번), 인스타 `ig_reels_avg_watch_time`. 완주율: 두 플랫폼 모두 바로 주는 API가 없다 — 유튜브는 유지율 곡선 끝값(`audienceWatchRatio`, 쇼츠 지원은 확인 필요)으로 근사할 수 있고, 확인 전까지는 손 입력. 유튜브 `averageViewPercentage`는 완주율이 아니므로 별도 칸으로 보여 준다 |
| 보내기 ÷ 도달, 저장 | `shares`, `reach`, `saves` | 인스타: `shares`·`reach`·`saved`(지금 수집기가 이미 요청한다 — 통계 권한만 있으면 들어온다). 유튜브: `shares`는 Analytics(늦게 반영), 저장·도달은 API에 없다 → 유튜브는 「보내기 ÷ 조회」로 본다 |
| 맞춤 프로그램으로 넘어간 수 | `toolVisits` | 게시물별 추적 링크(사이트 반응 칸의 「추적 링크 클릭」). GitHub traffic API는 14일 합계·유입처만 줘서 게시물별로 가를 수 없으니 보조로만 쓴다 |

판정은 v2 §6대로 「그 계정 안에서 상위 25%」다. 제안하는 정의: 같은 채널·플랫폼·형식·출처·단위(창 지표는 같은 창 정의)의 이전 게시물이 **4편 이상**일 때만 계산하고, 이번 값이 그 표본의 nearest-rank 75백분위 이상이면 「상위 25%」, 25백분위 이하면 「하위」, 그 사이는 「보통」. 3편 이하면 중앙값 비교와 같이 「자료 부족」(중앙값 비교는 지금처럼 3편부터 보여 준다). 어떤 지표로 판정할지(네 숫자를 따로 볼지, 하나로 합칠지)는 8장에서 정한다.

기록: v2 §6은 `node tools/채널성과.js --적기`와 회차 `성과.json`에 남기라고 한다. 워크스페이스 기록을 정본으로 하고 `성과.json`은 거기서 내보내는 안을 8장에 둔다.

## 8. 유호님이 정할 것

1. 유튜브·인스타 @yuhobuilds를 통계 권한까지 다시 연결할지(구글·메타 동의 화면은 유호님이 직접).
2. 3초 유지율처럼 API가 없는 지표를 손 입력으로 계속 받을지, 칸을 줄일지.
3. 10-18 세션 공유 편을 지금 있는 등록 API로 미리 넣을지. 넣는다면 세 가지를 알고 넣는다: ① 자동으로 잡히는 건 유튜브 조회·좋아요·댓글과 인스타 좋아요·댓글뿐이다(인스타 조회·도달·저장·공유는 통계 권한이 없어 빈칸, `collectors.mjs:405-412, 434`). ② 게시 시각은 유튜브 스튜디오·인스타 게시 정보에 나온 값을 **그대로** 넣는다(5분 넘게 다르면 자동 기록을 거부하고 재시도도 없다). ③ 형식 없이 들어가 72시간 비교 표본에서는 빠진다. 24시간 지점 마감은 게시 + 24시간 + 6시간(유튜브 10-19 22시대).
4. 판정에 쓸 지표 — v2 네 숫자를 따로 볼지, 하나로 합칠지(예: 초반 유지 우선).
5. 기록의 정본 — 워크스페이스 기록을 정본으로 하고 회차 `성과.json`·`채널성과.js`는 거기서 내보낼지.
