## 1. 지금 무엇이 부족한가

**의뢰를 시작할 곳이 없다.** 플랫폼 첫 화면은 「담당자에게 받은 링크」 입력칸이다. 새 손님은 synk.im 문의 양식에 글을 남기고, 담당자가 프로젝트를 만들어 초대 링크를 보내야 앱에 들어온다. 유호님이 말한 첫 단계가 앱에 없다.

**같은 것을 여러 번 묻는다.** 지금 손님이 만나는 입력은 다섯 군데다.

| 어디 | 칸 | 겹침 |
|---|---|---|
| synk.im 문의 양식 | 이름 · 메일 · 글 | 뒤에서 다시 받음 |
| 발주서(2026-10-01, 앱 밖) | 6단계 약 30칸 | 앱의 제작 설계와 따로 논다 |
| 고객 앱 01 제작 설계 | **8묶음 43칸** | 대상 · 분위기 · 피할 말이 02와 겹침 |
| 고객 앱 02 취향 보드 | 7칸 + 참고자료 | 위와 겹침 |
| 제작 전 준비 · 납품 규격표 | 직원이 정한 항목 · 줄마다 10칸 | 파일을 다시 고르게 함 |

10월 제작 설계에서 필수는 메시지 · 근거 · 행동 셋뿐이었지만, 화면은 여전히 긴 접이식 양식이다.

**화면은 「양식이 쌓인 관리 화면」이다.** 둥근 흰 카드 · 알약 · 원 번호 · 회색 글. 고객이 봐야 할 작업물은 카드 안 작은 그림이고, 예시 프로젝트의 장면은 납작한 임시 그림이다. 11-03 크몽 상세 2판에서 유호님이 「프론트가 부실 · AI 티」라고 한 겹 구조와 같다(둥근 카드 · 알약 · 원 번호 · 같은 겹 순서).

**내부 확인 단계가 없다.** 손님 답을 유호님과 Claude가 함께 보고 빠진 것을 되묻는 자리가 없고, 답은 다시 사람이 콘티로 옮긴다.

## 2. 받는 정보 판단 — 작업 시간과 결과에 실제로 도움이 되나

기준은 셋이다. ① 제작 규칙 순서 0 「브리프 한 장」(대상 · 한 문장 · 바라는 행동 · 길이 · 비율 · 플랫폼 · 무엇으로 이길지) ② 첫 리허설(오미톡) — 주문 전 요청 셋(약 10칸)만으로 글 콘티 → 장면 그림 → 영상 → 납품까지 갔고, 어디서 시간이 샜는지 ③ 제작자 · 손님 원문(3절).

| 받는 것 | 어디에 쓰나 | 없으면(근거) | 판정 |
|---|---|---|---|
| 이름 · 종류 | 준비물 목록, 모델 추천, 피할 말 | 무엇을 물을지 정하지 못한다 | **받음** |
| 올릴 곳 → 비율 | 컷 구도, 자막 안전 구역 | 용도 불일치로 통째 수정. 드롭샷 「기획 방향과 실제 용도 불일치」, 캐럿 「처음부터 9:16으로 요청」 | **받음** |
| 길이 · 구성 | 컷 수, 값 | 견적 불가 | **받음**(값을 그 자리에 보임) |
| 제품 원본 사진 정면 · 옆면 | 합성의 바탕. 리허설: 캔 렌더 · 합성으로 글자 오류를 막았다 | 후기의 낮은 점수 까닭 「글자 · 로고 오류」, 크몽 판매글 「로고, 패키지 문구, 비율이 달라질 수 있습니다」 | **받음 · 해상도 바로 점검** |
| 로고 파일 | 끝 화면 · 자막 | 1차안에 자리만 잡게 된다 | **받음** |
| 라벨 · 패키지 인쇄 파일 | 제품 위 글자. 리허설 「사진에서 라벨을 펴는 일이 하나 더 든다」 | 작업이 하나 는다 | 있으면 받음 |
| 쓰는 모습 · 크기 | 손 동작 · 크기감. 리허설 「캔 따는 손가락 동작」을 피해 콘티를 다시 짰다 | 다시 뽑기 | **한 줄이라도 받음** |
| 제품 페이지 주소 | 사실 확인, 재입력 방지 | 다시 묻게 된다 | 있으면 받음 |
| 누가 · 언제 찾나 | 장면 배경 · 캐스팅 | 저희가 제안(막지 않음) | **받음** |
| 남길 한 가지 | 한 문장 | 저희가 제안 | **받음** |
| 보고 나서 할 일 | 끝 화면 | 저희가 제안 | 고르기로 받음 |
| 화면에 나올 정확한 글자 | 후반 글자. 리허설 「11월 편의점 출시」 사실 확인 | 문구 바뀌면 재편집 | **받음 · 화면에 바로 얹어 보임** |
| 피할 말 | 콘티 · 글. 리허설 효능 말 | 심사 · 재작업 | **받음 · 업종별 후보를 꺼내 줌** |
| 자랑할 사실 | 근거 | 없음 | 선택 |
| 무엇으로 이길지(이야기 / 임팩트) | 제작 규칙 첫 칸, 콘티 엔진까지 정함 | 저희가 제안 | **받음 · 작품으로 보여 줌** |
| 참고 광고 + 어디가 좋았나 | 뼈대 원본. 드롭샷 「링크만 전달하면 제작사가 추측」 | 시안 반복 | **받음 · 이유를 고르기로** |
| 모델 | 캐스팅 | 저희가 추천 | **받음 · 업종별 추천** |
| 받고 싶은 날 | 일정 | 납기 분쟁 | **받음** |
| 최종 확인자 | 의견 창구. 「담당자가 만족했다고 끝난 게 아니다」(앤드스튜디오), Superside 후기 「too many cooks」 | 완성 뒤 뒤집힘 | **받음**(새로 넣음) |
| 연락처 | 답장 | 연락 불가 | **받음** |
| 광고비 집행 여부 | AI 표시 · 심사 규격 | 뒤늦게 규격 재작업 | 체크 하나 |
| 성과 지표 · 목표 · 기간 · 기준 · 출처(5칸) | 제작에 안 쓰임. 반응 리포트는 납품 뒤 도구가 잰다 | 영향 없음 | **뺌** |
| 보조 가치 · 근거 3쌍 | 15~30초에 안 들어감 | 영향 없음 | **뺌**(자랑할 사실 한 칸) |
| 예산 3칸 · 상담 구성 | 값이 고정돼 무의미 | 영향 없음 | **뺌** |
| 색감 · 구도 · 의상 · 목소리 · 등장인물 글 | 손님이 글로 쓰기 어렵고, 참고 광고 · 모델로 대신 | 영향 없음 | **뺌** |
| 납품 규격표 10칸 | 올릴 곳에서 저희가 제안, 손님은 확인만 | 영향 없음 | 저희가 채움 |

결과: 43칸 + 7칸 + α → **아홉 화면, 꼭 받는 칸 약 12개.** 보내기를 막는 칸은 이름 · 연락처 · 동의 셋뿐이다(이름은 프로젝트의 이름표, 나머지는 공개 약속 「제품 사진 한 장과 올릴 곳만으로 시작」 · 메모 「사용자 관문은 엄격하게 막지 않기」). 보내기 단추는 잠그지 않고, 빠진 칸이 있으면 그 칸으로 데려간다. 비어 있으면 그 자리에 「없으면 어떻게 하는지」를 적는다.

**이 답이 실제로 시간을 줄이는지:** 첫 주문부터 잰다 — 의뢰서 완료율, 되물은 칸 수, 1차안 첫 판 승인율, 수정 회차, 의뢰서 → 1차안 시간. 지금은 실제 주문이 없어 가설이다.

## 3. 조사 — 출처 · 반응 → 채택 → SYNK 적용

표본 조사다(확인일 2026-11-04). G2 · Reddit 일부는 막혔고 숨고 · 드롭샷 · 크몽 맞춤 견적의 실제 질문 목록은 비공개다. 제작자 쪽 자료 다수는 판매글 · 플랫폼 블로그라 이해관계가 있다.

## 4. 새 흐름

```
의뢰(공개) ─▶ 의뢰서 작성 ─▶ 접수증 ─▶ [확인] Claude 1차 → 유호 ─▶ (빠진 것만 되묻기) ─▶ 1차안 전달 ─▶ 컷마다 의견 ─▶ 수정판 ─▶ 이대로 제작 ─▶ 제작 ─▶ 영상 확인 ─▶ 납품
                                    고객 방이 바로 열림             내부 확인 화면                       한 문장 · 글 콘티 · 장면 이미지
```

| 단계 | 손님 | 저희 | 화면 |
|---|---|---|---|
| 1 의뢰 | synk.im/pulse 또는 앱 첫 화면 「광고 의뢰하기」 | — | 첫 화면 |
| 2 작성 | 아홉 화면, 자동 저장 · 이어서 쓰기 | — | 의뢰서 + 모니터 |
| 3 접수 | 접수증 · 돌아올 링크 · 이 기기 기억 | 알림 | 접수증 → 고객 방 |
| 4 확인 | 「저희 차례」 + 받은 의뢰서 · 자료 | 자동 점검 → Claude 1차 확인(한 문장 후보 · 모델 · 뼈대 후보 · 걸리는 것) → 유호님 확인 | 내부 확인 |
| 4' 되묻기 | 그 칸만 답 · 파일 | 고른 칸만 묻기 | 고객 방 「이것만 더」 |
| 5 1차 전달 | 공개 약속 「영상 전 세 번 확인」 순서: 모델 → 한 문장과 글 콘티 → 컷마다 장면 이미지. 컷마다 좋아요 / 고칠 곳. 모델을 맡긴 손님은 고객 방 「이 모델로 갈까요?」에서 먼저 답한다 | `propose_model` → 글 콘티 판(그림 없음) → 장면 이미지 판. 판(round) 보내기 | 고객 방 · 1차안 |
| 6 수정 | 의견 모아 보내기 → 반영된 판. 고칠 곳을 적어 두면 주 단추가 「의견 보내기」로 바뀌어 의견을 둔 채 제작이 시작되지 않는다 | 의견은 기존 장면 의견 기록(`recordSceneReview`)으로 들어간다 | 1차안 |

**왼쪽 레일:** 01 의뢰서 · 02 확인 · 03 1차안 · 04 제작 · 05 영상 확인 · 06 납품. 옛 취향 보드 · 콘셉트 · 제작 설계는 직원 작업 탭으로 옮기고, 옛 자료가 있는 프로젝트는 읽을 수 있게 둔다. 큰 건에서 콘셉트 비교가 필요하면 1차안 안에 「방향 먼저 고르기」로 낸다.

**한 원본:** 의뢰서 답은 확인이 끝날 때 제작 설계(`strategy`)의 칸으로 옮겨 담아, 직원 도구(장면 · 캐스팅 · 납품 규격 등)가 그대로 쓴다.

**Claude가 끼는 자리:** `node tools/PULSE의뢰.js 목록 · 받기 <번호> · 메모 <번호>`(작업실 예약과 같은 자격). 받기는 의뢰서 · 파일을 git 밖 `synk-vendor/pulse-orders/<번호>/`로 내리고, 메모는 직원만 보는 칸에 올린다. 새 의뢰가 들어오면 Windows 예약(운영 사본)이 AI 없이 알아채 `크레딧실행.js`로 Claude를 깨워 1차 확인을 쓰고, 유호님께 텔레그램 한 줄을 보낸다(본인 알림, 링크 없음).

**범위 밖(이번에 만들지 않음):** 결제 · 계약서(결제 전 장면 확인 · 납기 · 수정 횟수 공개는 트랙 §1 미정 약속). 메일 발송(회사 서버에 없음) — 링크를 잃으면 담당자가 새로 발급. 상품 링크 자동 채우기(서버가 임의 주소를 여는 위험 · AI 호출 비용, 첫 주문을 본 뒤).

## 5. 서버 설계

새 모듈 `pulse-requests.mjs`(저장은 기존 `store`, 새 kind `pulseRequests`).

- **초안:** `POST /pulse/api/request/start` → 토큰 하나(HttpOnly · SameSite=Strict 쿠키 `synk_pulse_request`, Path=/pulse, 해시만 저장, 30일) + csrf. `POST …/save`(답 전체, 40KB). 저장은 길이 · 제어문자 · 고르는 값만 보고 메일 · 번호 · 주소 · 날짜 형식은 **보낼 때** 본다(쓰는 중에 형식 때문에 자동 저장이 끊기지 않게, 스킴 없는 주소는 보낼 때 `https://`를 붙인다). 마지막 저장에서 14일 지나면 지움. 저장 실패는 화면에 보이고 8초 뒤 다시 한다.
- **파일:** `POST …/request/media`. 사진 · 영상은 서명 확인 뒤 화면에 띄울 수 있게, webp · heic · heif · svg · ai · eps · pdf · ppt · pptx · mov는 **첨부 전용**(`Content-Disposition: attachment` + CSP sandbox, 화면에 넣지 않음)으로 받고 이것도 앞부분 서명을 확인한다. 초안 하나 30파일 · 400MB, 파일 하나 100MB(첨부 30MB). 소리 파일은 받지 않는다.
- **문턱:** Origin 일치, 허니팟, 주소당 시작 20회/시간 · 파일 2GB/일, 전체 시작 300회/일 · 파일 10GB/일 · 접수 50건/일, 디스크 여유 20GB 아래면 받지 않음(직원 서버와 같은 볼륨이라). 넘으면 「잠시 뒤 다시」 + hello@synk.im.
- **접수:** `POST …/submit`(requestId로 멱등). 시스템 경로 `clientProjects.createFromRequest()`로 프로젝트(stage `received`, 담당 = PULSE 담당자 설정값, 없으면 활성 관리자)와 초대를 만들고, 파일을 프로젝트 쪽 폴더로 옮겨 `studio.assets`(author customer)에 올리고, 고객 세션 쿠키를 심는다. 파일은 앞으로만 옮기고 되돌리지 않는다 — 옮긴 파일은 프로젝트가 가리키기 전까지 아무 일도 하지 않고 백업에도 오르지 않으며, 어디서 멈춰도 다시 보내면 그대로 잇는다(GPT 검수 세 회차 뒤 Fable 설계 검토로 구조를 바꿈. 옮기고 되돌리던 처음 설계는 잠금이 풀린 사이의 경쟁을 막지 못했고, 하드 링크 안은 백업의 「링크 하나」 검사와 부딪혔다). 응답 `{number,at,link}` — 초대 원문은 이때 한 번뿐.
- **보존:** 동의 문구대로 접수 뒤 90일 동안 움직임이 없고 제작으로 이어지지 않은 의뢰는 연락처 · 답 · 파일을 지우고 번호만 남겨 보관(`archived`)으로 돌린다(`clientProjects.retireRequest`). 유지보수 타이머(6시간, 예약 게이트 안)에서만 돈다 — 익명 요청이 지우기의 방아쇠가 되지 않게 한다. 직원이 확인한 건 · 그 사이 바뀐 건은 건드리지 않는다.
- **고객 액션:** `request_answer`(되묻기 답: 글이나 파일), `answer_model`(제안 수락 · 다른 모델 · 말로 요청), `submit_draft_review`, `approve_draft`(의견이 남은 판은 승인 불가, 글 콘티 판은 장면 이미지로, 장면 이미지 판은 제작으로). **직원 액션:** `request_note`(내부 메모, 손님에게 안 보임), `request_ask`, `request_confirm`(strategy로 옮김), `propose_model`, `send_draft`(판 스냅숏 — 확인 끝 · 모델 확정이 먼저, 그림이 다 있으면 장면 이미지 판 · 아니면 글 콘티 판). 장면 자체는 기존 `scenes`를 쓴다. 보내기를 응답 못 받고 다시 누르면 접수 뒤 10분만 같은 프로젝트로 링크를 다시 준다(원문 초대는 저장하지 않음).
- **백업:** 파일은 기존 `studioMedia` kind 문서로 남겨 `workspaceMediaNames` · HA 목록을 그대로 탄다. 첨부 전용 파일은 `.intake` 이름 규칙을 재사용 — 백업 정규식 · 복원 시험에 든 것을 시험으로 확인.
- **공개 파일 · 캐시:** `server.mjs` files 맵과 `sw.js` FILES에 새 모듈 · 그림을 더하고 판을 올린다.

**옛 프로젝트:** 서버가 `requestFlow`를 계산한다(`usesRequestFlow`) — 의뢰서가 있거나, 담당자가 막 만들어 아직 아무 자료도 없는 프로젝트만 새 방을 쓴다. 자료가 쌓인 프로젝트는 옛 탭 그대로다.

**바로 의뢰 주소:** `https://workspace.synk.im/pulse-app/?start=request` — synk.im/pulse의 「광고 의뢰하기」가 여기로 온다.

**초안이 기한으로 사라졌을 때:** 마지막 저장에서 14일이 지나면 서버가 초안과 파일을 지운다. 그 뒤 손님이 이어 쓰면 글은 화면에 있는 그대로 새 초안으로 옮기고, 함께 지워진 파일은 칸에서 빼고 그 자리에서 알린다. 보내려던 순간에 알게 되면 자료 없이 조용히 접수하지 않고 한 번 멈춰 알린 뒤, 손님이 다시 누르면 보낸다.

**받고 싶은 날은 약속이 아니다:** 손님이 적은 날은 답에만 남고 프로젝트의 전달 예정일(`dueDate`)로 옮기지 않는다. 전달 예정일은 담당자가 정한다.

**작은 반복 영상:** 의뢰서 「무엇으로 오래 남을까요?」 모니터의 `assets/request/film-gift.mp4`(1.1MB) · `film-maejin.mp4`(0.3MB)는 완성작 둘에서 뽑은 소리 없는 반복이다. 저장소 용량 관문이 mp4를 받지 않아 다른 완성작처럼 git 밖(공용 작업본 · 회사 판 후보)에 둔다.
