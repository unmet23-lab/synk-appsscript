# PULSE 판 4 · 판매 전 고침 설계 (2026-11-10)

> 11-10 구매 점검([README 11절](README.md#11-판매-전-구매-점검11-10) · 보고 페이지)의 막힘 M1~M4와 보완 B1~B13을 고친다. 유호님 「추천대로 고쳐」(11-10)로 D1~D4는 보고서 추천 그대로다. 판매 시작 목표 11-17. 이 문서는 만들기 전 Fable 설계 검토용이고, 검토 반영은 맨 끝 표에 적는다.

## 0. 정한 것과 확인한 사실

| # | 정한 것(11-10) |
|---|---|
| D1 | 첫 10건 동안 앱 의뢰서 · 방향 제안 값 = 크몽 런칭가(15초 29만 · 30초+편집본 59만 · 60초 149만). 10건 뒤 크몽 · 앱을 함께 39만 · 89만 · 199만. 정가와 견주는 할인 표시는 하지 않는다 |
| D2 | 글 콘티 승인 → 크몽 결제 요청(값 · 기간 · 수정 그대로) → 손님 크몽 결제 → 담당자 「결제 확인」 → 장면 이미지. 완성본은 앱과 크몽 「작업물 발송」 둘 다, 끝에 크몽 구매확정 · 후기 안내 |

**크몽에서 확인한 것(공개 도움말, 11-10).** ① 상품과 다른 조건으로 받을 때는 크몽 메시지에서 협의한 뒤 전문가가 **안전결제요청**을 보내고, 손님이 결제하면 새 주문이 된다([전문가센터 741](https://kmong.com/support/expert-center/posts/741)). 크몽 메시지는 손님이 「문의하기」로 먼저 여는 구조라, 앱 손님은 크몽 상품 쪽에서 접수 번호로 문의를 먼저 보낸다. 승인 전(임시 저장) 상품으로 보낼 수 있는지는 공개 문서에 없다 — 판매 시작 전 심사 통과가 조건이다(D5 ①, 유호님 손). 금지되는 것은 크몽 밖에서 대금을 주고받거나 크몽 손님을 밖으로 빼는 일이고, 결제를 모두 크몽에서 하는 흐름을 막는 문구는 없다([고객센터 158](https://kmong.com/support/customer-center/posts/158)). 수수료 · 부가세를 따로 요구하면 직접 결제 유도다. ② 결제 뒤 「요청사항」을 설정하면 손님이 답을 끝낸 때부터 작업일이 센다. 이미 받은 자료면 「작업 시작 → 네, 받았습니다」로 넘긴다([759](https://kmong.com/support/expert-center/posts/759)). ③ 거래 취소는 작업물 도착 전 손님 요청 → 전문가 수락이고 **24시간 안에 답이 없으면 자동 취소**, 작업물 도착 뒤에는 수정 요청을 먼저, 구매확정 뒤에는 취소 없음([145](https://kmong.com/support/customer-center/posts/145) · [118](https://kmong.com/support/customer-center/posts/118)). 진행률 환불표는 없다. 맞춤 제작의 청약철회 거절은 판매 이용약관(2025-09-18 개정, [573](https://kmong.com/support/expert-center/posts/573)) 12조대로 **사전 별도 고지와 손님의 서면(전자문서) 동의**가 있어야 쓸 수 있다 — 그래서 D3은 상세 글 · 앱에 밝히고, 제작이 시작되는 장면 이미지 승인 때 손님 동의를 기록한다(1-3). ④ 작업물 발송 뒤 7일 응답이 없으면 8일째 자동 구매확정. ⑤ 개인 전문가는 서비스 금액 세금계산서를 못 끊고, 손님은 크몽 결제 내역의 카드 전표 · 현금영수증을 받으며, 구매 수수료(주문 금액의 4.5%, [138](https://kmong.com/support/customer-center/posts/138)) 세금계산서는 크몽에 신청한다([131](https://kmong.com/support/customer-center/posts/131)). 그래서 앱의 값 옆에 「크몽 결제 때 구매 수수료가 더해져요」를 둔다.

## 1. 결제 단계 (M1 · M2)

### 1-1 상태 — `studio.request.payment`

```
{ status: 'requested' | 'confirmed' | 'cancelled',
  requestedAt, requestedBy, amount,          // 담당자가 크몽에서 결제 요청을 보낸 때 · 값(원)
  confirmedAt, confirmedBy, ref, dueDate,    // 결제를 확인한 때 · 크몽 주문 번호(직원만) · 받으실 날(KST)
  cancelledAt, cancelledBy, note }           // 결제 뒤 취소 · 환불(D3) · 크몽 자동 취소 — 사유(직원만)
```

- 없으면 「아직 결제 안내 전」. 값(`amount`)의 기본은 고른 방향의 값(`directionProposal.price`), 없으면 의뢰서 패키지 값이고, 담당자가 바꿔 적을 수 있다.
- 손님 보기에는 `status · requestedAt · confirmedAt · amount`만 내린다(`ref`는 뺀다 — `requestView`).

### 1-2 동작(직원만)

| 동작 | 입력 | 하는 일 | 막는 것 |
|---|---|---|---|
| `payment_request` | `amount`(1만~1억 원) | `status:'requested'` · 손님 알림 `payment_requested`(메일 순간) | 확인 전 의뢰서 · 이미 확인한 결제(취소 뒤에는 다시 됨) |
| `payment_confirm` | `ref`(선택, 40자) · `dueDate`(기본 오늘 + 패키지 일수, KST) | `status:'confirmed'` · 손님 알림 `payment_confirmed`(앱 안만). 받으실 날은 이 값이 방향 제안의 날을 대신한다(크몽 작업일이 결제부터 세므로). 사진 상품이 첫 장을 이미 승인했으면 이때 `producing` | 확인 전 의뢰서 · 이미 확인함 |
| `payment_cancel` | `note`(사유, 300자) | `status:'cancelled'` — 결제 뒤 전액 환불 · 크몽 자동 취소(24시간)를 적는다. 손님 보기에는 상태만 | 확인한 결제가 없음 |

요청 없이 바로 확인해도 된다. 손님이 크몽 패키지를 바로 샀으면: 크몽 주문 뒤 메시지 · 요청사항으로 앱 의뢰서 주소를 보낸다(주문 뒤 연락 공유는 허용, [754](https://kmong.com/support/expert-center/posts/754) · 금지는 결제 전 연락처 공유와 외부 결제뿐) → 손님 접수 → 확인 → `payment_confirm(ref=크몽 주문 번호)`. 크몽 작업일은 「작업 시작 → 네, 받았습니다」로 넘긴다. 무상 작업은 `ref`에 적는다.

### 1-3 문턱(서버)

- 문턱은 `status==='confirmed'`만 통과한다(요청 · 취소는 막힘). 보관을 풀어도 같다.
- `send_draft`가 장면 이미지 판(`kind:'images'`)이 되면 결제 확인이 있어야 한다 — 「결제가 확인된 뒤에 장면 이미지를 보낼 수 있어요」(409). 모든 컷에 그림이 붙어 있어도 담당자가 `kind:'script'`를 골라 글 콘티 판으로 보낼 수 있고, 직원 화면은 보내기 전에 「장면 이미지 판이 되므로 결제 확인이 필요해요」를 보인다. 사진 상품은 첫 장을 승인하기 전(`approvedRound` 없음)의 판은 모두 허용하고, 승인 뒤 판부터 결제가 필요하다.
- `approve_draft`가 제작을 시작하는 판(장면 이미지 판)이면 결제 확인과 **손님 동의(`terms:true`)**가 있어야 한다 — 확인 상자에 원문 ③ 한 줄과 체크를 두고 `round.termsAcceptedAt`을 `approvedAt`과 함께 남긴다(맞춤 제작 청약철회 제한의 서면 동의). 사진 상품은 첫 장 승인에 같은 동의를 받고, 승인은 받되 `producing`으로 옮기지 않고 결제 확인 때 옮긴다.
- 의뢰 흐름 프로젝트(`studio.request.status==='confirmed'`)에 시안 · 최종본 올리기(`addVersion`)는 결제 확인 뒤에만(1차 영상이 결제 전에 손님에게 가는 길을 막는다).
- 옛 흐름 프로젝트(의뢰서 없음)와 지금 열린 프로젝트는 건드리지 않는다. 운영의 의뢰 흐름 프로젝트는 시험 셋이 모두 보관이라 옮겨 담을 자료가 없다.

### 1-4 손님 화면

- 고객 방 상태 `pay`(손님 차례) — 결제가 확인되지 않았고, ① 담당자가 결제를 요청했거나 ② 영상은 글 콘티를 승인했고 아직 장면 이미지 판이 없을 때 · 사진은 첫 장을 승인했을 때. `roomState`에서 되묻기 다음, 판 상태 · `make`보다 먼저 본다. 취소되면 카드가 「결제가 취소됐어요 · 다시 진행하시려면 담당자에게 알려 주세요」. 확인 뒤는 지금의 `prepare-images` · `make`.
- 결제 안내 카드(방 지금 차례 자리): 제목 「크몽에서 결제해 주세요」 · 값 줄(「29만원 · 크몽 결제 때 구매 수수료가 더해져요」) · 세 걸음(① 크몽 상품에서 「문의하기」로 접수 번호를 보내 주세요 — 번호 복사 단추 ② 담당자가 같은 값 · 기간 · 수정 횟수로 결제 요청을 보내 드려요 ③ 결제하시면 확인 뒤 장면 이미지를 만들기 시작해요) · 크몽 상품 단추(새 창) · 「결제 · 취소 · 증빙」 펼침(원문 다섯 줄 중 ① ② ③). `requested`면 ②에 「보냈어요 · 11월 12일」 표시와 「크몽 메시지에서 결제해 주세요」.
- 크몽 상품 주소는 화면 상수(`KMONG_GIG`, 영상 상품 #854445 — 심사 뒤 공개). 사진 상품은 크몽에 아직 없어 카드가 「결제 방법은 담당자가 크몽 메시지로 안내해 드려요」로 간다(사진 결제 길은 남은 일). 상수를 비우면 단추 없이 「담당자가 안내해 드려요」.
- 1차 영상 「파일 받기」: 고객 방에서는 시안에 두지 않는다. 받기는 납품(최종본)에서만(`views.mjs` 영상 확인 아래 줄).
- 방향 「자세히」 결제 줄 · 고른 뒤 방 글 · 첫 화면 「맡기면 이렇게 진행돼요」 5단계에 「글 콘티를 보신 뒤 크몽에서 결제」를 넣는다(B3 · M2).

### 1-5 담당자 화면(`desk-view.mjs`)

내부 확인 옆 칸에 결제 줄 — 「결제 안내 전」 → 「크몽 결제 요청 보냄 · 29만원 · 11-12 14:02」 → 「결제 확인 · 11-12 18:30 · 주문 번호」. 단추 「크몽에 결제 요청 보냄」(값 미리 채움) · 「결제 확인」(주문 번호 칸). 장면 이미지 판 보내기 단추는 확인 전에는 까닭과 함께 꺼 둔다.

### 1-6 최소안(서버 판 전, 화면 묶음만)

서버 판이 늦어도 판매를 시작할 수 있게 화면만으로 먼저 낸다: 글 콘티 승인 뒤 장면 이미지 판이 오기 전은 `pay`(손님 차례) — 제목 「글 콘티를 확인해 주셨어요」, 글 「결제가 확인되면 장면 이미지를 만들어요」, 카드 첫 줄 「아직 결제 전이시면」, 메일 약속 없이 「담당자가 안내해 드려요」. 1차 영상 「파일 받기」 걷기, 값(D1) · 크몽 말 · 원문 다섯 줄. 운영 규칙 「결제 확인 뒤에 장면 이미지 판을 보낸다」는 담당자 화면 줄과 트랙에 적는다. 서버 상태(`payment`)가 오면 같은 카드가 요청 · 확인 · 취소를 따른다. 새 기능(다시 열기 코드 · 결제 단추)은 서버가 `/pulse/api/features`에 알릴 때만 그린다.

## 2. 돌아오는 길 (M4)

지금: 손님 세션 12시간, 「이 기기 기억하기」(30일)는 손님이 골라야 켜짐, 접수증의 30일 링크는 그 자리에서 한 번만 보임, 메일 링크는 앱 첫 화면, 첫 화면에는 「담당자에게 받은 링크」 칸뿐. 새 기기 · 12시간 뒤에 막힌다.

| | ① 접수 확인 메일에 방 링크 | ② 메일로 코드 받아 열기 |
|---|---|---|
| 손님 손 | 첫 메일의 링크 한 번(30일) | 첫 화면 「메일로 다시 열기」 → 주소 → 메일의 여섯 자리 → 열림(메일 왕복 한 번) |
| 주소를 잘못 적었을 때 | 방 열쇠가 남의 메일함에 간다(Fable 11-07 지적 그대로) | 코드만 간다. 남이 쓰려면 앱에 와서 자기 주소로 코드를 따로 받아야 한다 |
| 메일이 퍼질 때(전달 · 메일 검사기) | 링크가 곧 열쇠라 전달하면 열린다, 30일 | 코드는 10분 · 한 번 · 다섯 번 틀리면 끝 |
| 서버 | 초대 원문을 보낼 때까지 들고 있어야 한다(지금 설계는 해시만 둔다) | 원문을 들고 있을 필요 없음. 코드 · 문턱 · 세션 발급이 새로 는다 |
| 30일 뒤 · 기기 바뀜 | 초대 기한이 지나면 막힘 | 프로젝트가 열려 있는 동안 늘 |

**고름: ②.** 메일에 방 열쇠를 넣지 않는 11-07 원칙을 지키면서 새 기기 · 30일 뒤까지 푼다. ①의 「한 번에 열림」은 「이 기기 기억하기」와 접수증 링크가 맡는다. 판 2 설계 「안 만드는 것」의 「메일 안의 접수 링크」는 그대로 안 만들고, 바뀌는 것은 「코드 메일 한 통」이 메일 종류에 더해지는 것이다(결정 표에 근거).

### 2-1 서버

- `POST /pulse/api/mail-open` `{email}` — 같은 출처 · 허니팟. 주소 꼴이 맞으면 **곧바로 늘 같은 답**(「진행 중인 의뢰가 있으면 이 주소로 코드를 보냈어요」)을 준다 — 맞는 프로젝트가 있든 없든 같은 HMAC 계산을 한 번 거치고, 코드 만들기 · 보내기는 답한 뒤 요청 밖(메모리 큐, 하나씩)에서 한다(응답 시간으로 주소가 드러나거나 요청이 중계를 30초 기다리지 않게). 안에서는 받는 사람 규칙(`pulseMailRecipient` — 담당자가 고친 주소 우선 · 메일 끔이면 없음)으로 맞는 프로젝트 중 메일 대상(`pulseMailEligibility` — 보관 아님 · 방 열쇠 살아 있음)을 모두 찾는다. 있으면 여섯 자리 코드를 만들어 해시(HMAC, 메일 열쇠 문서의 소금)만 `pulseMailCodes`에 두고 중계로 보낸다(함을 거치지 않음 — 코드 원문은 보낸 뒤 버린다). 메일이 꺼져 있거나 연결이 끊겼으면 보내지 않고, 중계 답이 끊김이면 순간 메일과 같은 `connection: broken` 복구 길을 탄다.
- `POST /pulse/api/mail-open/verify` `{email,code}` — 맞으면 손님 세션을 만든다(`acceptedInvite:true` 꼴 — 메일함을 가진 사람이라 초대 기한과 상관없이, 보관 · 방 닫힘 · 새 초대에는 끝난다). 확인하는 순간 보관 · `inviteHash`를 다시 보고, `/pulse/api/open`과 같은 기기 처리(다른 프로젝트의 기억한 기기는 잊고 쿠키를 지움)를 한다. 맞는 프로젝트가 둘 이상이면(같은 모델로 다음 편) 세션 대신 고르기 표(제목 · 접수 번호)와 5분짜리 한 번 쓰는 고르기 표를 주고, `…/verify/pick`이 고른 프로젝트의 세션을 만든다. 쿠키는 지금과 같은 12시간, 화면은 바로 「이 기기 기억하기」를 권한다.
- 문턱: 코드 10분 · 한 번 쓰면 끝 · 다섯 번 틀리면 끝. 새 코드가 실제로 보내진 뒤에만 그 주소의 앞 코드를 무효로 한다(남이 같은 주소로 요청해 손님이 넣던 코드를 죽이지 않게). 보내기는 주소마다 1시간 3통 · 하루 6통, 주소(IP)마다 1시간 10번 요청 · 20번 확인, 전체 코드 메일 하루 30통 — 서버 셈이고 중계 상한(200)과 MailApp 남은 몫(100)은 순간 메일과 함께 쓴다. 넘으면 같은 답(보내지 않음). 맞춰 보기는 시간 고정 비교.
- 기록에는 주소 · 코드를 쓰지 않는다(프로젝트 id · 결과 코드만). `pulseMailCodes`는 하루 지나면 지운다.
- 코드 메일: 제목 「〔SYNK PULSE〕 프로젝트 열기 코드 482913」, 본문 「아래 코드를 PULSE 앱에 넣어 주세요 · 10분 동안 쓸 수 있어요 · 요청하지 않으셨으면 이 메일은 지우셔도 돼요」(코드는 본문에도).

### 2-2 화면

- 첫 화면 「받은 링크로 내 프로젝트 열기」 → 「내 프로젝트 다시 열기」 한 판: 위 「메일로 코드 받기」(주소 → 코드 여섯 칸 → 열기), 아래 「접수증이나 메일의 링크가 있으면」 붙여 넣기(지금 칸). 「담당자에게 받은 링크」 말은 「받은 링크」로.
- 메일의 앱 주소는 `…/pulse-app/?open=mail` — 열린 세션 · 기억한 기기가 있으면 그대로 방으로, 없으면 다시 열기 판이 열린 채 주소 칸에 초점. 주소는 주소창에 싣지 않는다.
- 접수증 「돌아올 링크」 옆에 한 줄: 「다른 기기에서는 첫 화면 「메일로 다시 열기」로 여실 수 있어요.」
- 다시 열기 판의 답 아래 한 줄(같은 답 원칙은 지킨다): 「몇 분 안에 오지 않으면 스팸함을 보시고, 그래도 없으면 hello@synk.im으로 접수 번호를 보내 주세요. 접수증의 링크가 있으면 아래 칸에 붙여 넣어도 열려요.」

- 본문 끝에 「다음 할 일」 한 줄(순간마다, 예: 「컷마다 좋아요 · 고칠 곳을 남기고 「의견 보내기」나 「이대로 장면 이미지 만들기」를 눌러 주세요」)과, 받으실 날이 있으면 「받으실 날(11월 20일)은 확인을 기다리는 날만큼 늦어져요」를 둔다.
- 링크 안내 두 줄은 「PULSE 앱에서 확인해 주세요: …/pulse-app/?open=mail」 · 「이 기기를 기억해 두셨다면 바로 열려요. 다른 기기에서는 「메일로 다시 열기」에 이 주소를 넣으면 코드를 보내 드려요.」로 바꾼다.
- 접수 확인은 직원 손 없이 손님이 적은 주소로 바로 나가는 유일한 메일이라, 공개 의뢰서로 남의 주소에 임의 문장을 보내는 길이 되지 않게 **고정 글만** 쓴다(제목 「〔SYNK PULSE〕 의뢰를 받았어요 · 번호」, 이름 · 제품 이름 없음). 본문: 번호 · 다음에 일어날 일(평일 10~19시 확인, 빠진 칸만 여쭘) · 다시 여는 법 · 결제는 글 콘티를 보신 뒤 크몽에서 · 「의뢰하신 적이 없으면 이 메일은 지우셔도 돼요」. 주소(해시)마다 하루 1통, 접수 확인 전체 하루 20통을 넘으면 보내지 않는다(접수증이 같은 안내를 한다).
- 함 줄: `moment:'request_received'` · `eventIds:['request:<프로젝트 id>']` · `dueAt = 접수 + 30초`. 접수(`pulseRequests.submit` → `createFromRequest`) 뒤 같은 트랜잭션에서 넣고, `fill`의 묶기 대상이 아니며, `deliver`는 이 순간에 stale · read · acted를 건너뛴다(손님 대상 알림 사건이 없어서). 메일이 꺼져 있으면 넣지 않는다.
- 사진 상품은 `images_ready`의 말이 「첫 장이 왔어요」 · 「고친 첫 장이 왔어요」, 다음 할 일도 사진 말로.
- 받으실 날은 결제 확인 때 정한 날(`payment.dueDate`)이 있으면 그것, 없으면 방향 제안의 날.
- 순간이 여덟이 되면 한 의뢰에 메일이 8~12통이고 10~21일에 흩어져 건당 하루 1~2통이다. MailApp 남은 몫 100 안에서 동시에 열 건까지 넉넉하다(코드 메일 30통 상한은 서버 셈 — 중계는 순간과 코드를 가르지 않는다).
- 직원 화면 메일 줄(`MAIL_MOMENT`)에 새 순간 이름을 더한다.
