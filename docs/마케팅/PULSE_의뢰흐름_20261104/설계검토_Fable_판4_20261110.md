## 2. 설계 결함(P0~P3)

**P0: 없음.** 스위치가 꺼진 채 구조만 들어가고, 라이브 데이터 · 인증을 바로 깨는 지시는 없다.

### P1

**P1-1. 삭제 순서가 백업 · HA · 복원 수락을 멈춘다 — 「deleting 인물의 파일을 백업이 건너뛴다」는 지금 자료 모양으로는 구현할 수 없다.**
- 5-6 순서: `status:'deleting'` → **파일 지우기** → 동의 암호문 · 출처 문서 정리 → 묘비. 그런데 백업이 복사할 이름을 모으는 `personaMediaOf(kind, doc)`(`workspace-media.mjs:9~21`)는 **파일 문서(`pulsePersonaSources` · `pulsePersonaRevisions`)만** 받고 `pulsePersonas.status`를 모른다. 출처 문서는 `diskName==null && deletedAt`일 때만 비고(`:12`), 판 문서는 `assets[].diskName`이 문자열이 아니면 **예외**다(`:16~19`) — 「지우는 중」을 표시할 자리가 없다.
- 재현: 관리자 삭제 확인 → 트랜잭션에서 `deleting` → `studio-media/<판 자산>.png` unlink → (서버 멈춤 또는 그냥 다음 단계 전) `node backup.mjs` → `copyFile` ENOENT에서 **백업 전체 실패**(`backup.mjs:26`, catch 없음). `workspace-backup.mjs:62`, `workspace-restore-acceptance.mjs:95`, `deploy/ha/node-host.py:225`(canonical 목록 대조)도 같은 이름을 센다. 「도중에 멈추면 deleting이 남아 이어 한다」지만 **누가 다시 돌리는지** 없고, 그동안 매일 백업이 빨갛다. 배포 · 백업 관문은 드문 입력도 P1.
- 고침(더 단순): 순서를 **문서 먼저, 파일 나중**으로. 한 트랜잭션에서 `pulsePersonas.status='deleting'` + 출처 문서 `diskName→null, deletedAt` + 판 문서 `assets→[], deletedAt` + 지울 이름 목록은 `personaMediaOf`가 읽지 않는 칸(`pendingUnlink`)에 → 커밋 뒤 unlink(ENOENT 무시) → 목록 비우고 묘비. 그러면 `personaMediaOf`는 손대지 않아도 되고(출처 묘비 처리 `:12`는 이미 있음, 판 문서만 `assets:[]` 묘비 허용 한 줄), `node-host.py` 고정 목록도 그대로다. 이것은 기획 12-2 「파일 → 묘비」 순서를 바꾸는 것이라 결정 표에 한 줄 적는다.

### P2

**P2-1. 잘못 연결한 뒤 되돌릴 길이 없다 — `workspaceId` 한 번 귀속 · 이동 없음(3-4)에 관리자 교정조차 없다.**
- 재현: 직원이 프로젝트를 브랜드 X에 잘못 연결(4-4) → X의 admin에게 「보관 대기」가 뜨고(4-2) 그림(기준 얼굴)이 열림 → admin이 `reuse` 승인 → `workspaceId=X` 영구. 직원이 알아채도 「브랜드 사이 옮기기 없음」 · `workspaceId` 불변 · 삭제는 원 프로젝트가 끝나기 전엔 막힘(5-6) → 진짜 고객 Y는 그 인물을 끝내 못 받고, X는 「이 모델로 의뢰」까지 할 수 있다. 직원 실수가 전제라 P2지만 결과는 남의 얼굴 자산의 영구 오귀속이다.
- 고침: 「이동」은 그대로 없애되 **관리자 전용 「귀속 취소」**(같은 브랜드의 다시 쓰기 참조가 0이고 `reuse` 승인을 철회로 돌릴 때만 `workspaceId→null`)를 둔다. 또는 `reuse` 승인 뒤 직원이 한 번 더 「귀속 확인」해야 `workspaceId`가 채워지게(두 사람 확인). 전자가 가볍다.

**P2-2. 「한 트랜잭션」 문장이 두 구현 함정을 부른다(4-1).**
- `store.transaction(fn)`은 **동기**다(`store.mjs:93` — `fn()` 즉시 `COMMIT`). 「고객 세션 중앙 확인 → proof 소모 → 기록」을 한 트랜잭션에 넣으라고 읽고 `async fn`을 넣으면, 첫 `await`에서 `COMMIT`이 먼저 나가고 뒤 쓰기는 트랜잭션 밖이 된다(조용히). 또 `store.consume`(`:101`)은 스스로 `transaction`을 열어 **안에서 부르면 중첩 BEGIN으로 터진다**.
- 고침: 4-1을 「① `identity.authenticate`(비동기) → 몸통 읽기 → 다시 `authenticate`(`customer-routes.mjs:47~50` 꼴) → ② 동기 트랜잭션 하나에서 `readToken` + `DELETE FROM tokens WHERE hash=?`(`consume` 말고) + 프로젝트 · 초안 · 회원 재확인 + 기록」으로 고쳐 적는다.

**P2-3. 묘비 뒤 90일 정리가 영영 그 프로젝트를 건너뛸 수 있다(판 3 후속에 기대고 있음).**
- `openPersonaProjectIds`는 `status`가 `PERSONA_SETTLED` 밖이면 열림으로 센다(`pulse-personas.mjs:15`). 5-6 묘비는 「`deletedAt`, 이름 · 판 id만」 — `status`가 지워지거나 `deleting`으로 남으면 원 프로젝트는 `retireUnconfirmed`에서 영원히 빠진다(`pulse-requests.mjs:312`). 90일 정리는 **동의 문구의 약속**(`:302`)이라 연락처 · 답이 약속보다 오래 남는다.
- 고침: 판 4 문서에 「묘비는 `deletedAt`이 있으면 `openPersonaProjectIds`가 건너뛴다(또는 `deleted`를 SETTLED에 더함)」를 **판 3 의존이 아니라 판 4 요구**로 적고 7절 시나리오 10에 넣는다.

**P2-4. 다시 쓰기 의뢰의 연결 확인 권한이 두 사람 사이에서 막힌다(4-4).**
- 다시 쓰기 의뢰는 공개 `submit` 길이라 새 프로젝트 `ownerId`는 `requestOwner()`(설정 담당자 또는 첫 관리자, `client-projects.mjs:99`)다. 4-4는 연결 확인에 「그 프로젝트 `allowed()` **그리고** 브랜드 `staffOwnerId` 또는 관리자」 둘 다를 요구한다. 설정 담당자 ≠ 브랜드 담당이면 관리자가 아닌 누구도 확인을 못 한다. 지금은 관리자 한 사람 운영이라 안 보이지만 정상 경로의 교착이다.
- 고침: 다시 쓰기 의뢰로 생기는 프로젝트의 `ownerId`를 브랜드 `staffOwnerId`(활성이면)로 정하고 아니면 `requestOwner()`.

**P2-5. 방 안 의뢰서(`request_save` · `request_submit`)로 `modelChoice:'persona'`를 붙임 없이 저장할 수 있다 — 5-4 저장 규칙 · 4-5 끔 규칙이 공개 초안 `save`만 적는다.**
- `applyRequestAction`의 `request_save/submit`(`pulse-requests.mjs:396~401`)은 `normalizeRequestAnswers`를 그대로 타고 `MODEL_CHOICES`에 `persona`가 있다(`:51·76`). 재현: 방 안에서 `modelChoice:'persona'` 저장 → `castingOf.kind==='persona'`, 참조 없음 → 방향 제안은 모델 없이 통과(`:477`) → 글 콘티 통과 → 제작 시작만 409(`:382`)로 막히는 막다른 프로젝트. 자산 노출은 없고 직원이 모델을 제안하면 풀리므로 P2.
- 고침: 방 안 의뢰서에서는 `persona`를 거절(다시 쓰기는 내 모델에서만 시작) — 5-4 · 4-5에 한 줄.

### P3

- **P3-1.** 1절 「초안 쿠키 14일」(틀림, 위 표).
- **P3-2. 연결 요청 자동 철회(3-2)가 초대 링크 새로 만들기에도 걸린다.** 초대는 30일(`client-projects.mjs:14`)이고 제작은 2~4주라 담당자가 링크를 다시 만드는 일(`invite` `:198`)이 보통이다 — 그때 고객의 `pending`이 소리 없이 `withdrawn`. 더 단순: 쓰지 말고 **결정 때 계산**(프로젝트 보관 · `inviteRevision` 달라짐이면 승인 거절 + 직원 화면에 표시).
- **P3-3. `kind: link | join`을 저장하지 말고 결정 때 계산.** 요청과 결정 사이에 직원이 프로젝트를 연결하면 저장된 `kind`가 낡는다.
- **P3-4. `retention.until`의 형과 시간대가 없다.** 「승인 카드에 날짜로 보인 값」을 `YYYY-MM-DD`로 두면 `until <= now` 비교가 하루 어긋난다(서버 UTC — `kstDay`가 같은 문제로 생겼다, `pulse-requests.mjs:107·629`). ISO 순간(KST 그날 끝)으로 굳힌다. `until` 없는 `reuse` 승인은 영영 안 만료되니 필수로.
- **P3-5. 첫 화면 「내 모델」 입구가 켜졌는지 알 길이 없다.** `myModels`는 `projectView`에만 있고(`pulse-features.mjs:57`) 첫 화면이 받는 `publicView`(`:55`, `/pulse/api/request` · `/pulse/api/features`)에는 없다. 4-5 「화면에는 입구가 없다」가 켠 뒤에도 그대로가 된다. `publicView`에 `myModels`를 더한다(값은 켬 여부뿐이라 노출 위험 없음).
- **P3-6. 「내 모델로 모아 두기」 단추를 보이려면 「이 로그인한 사람이 이 프로젝트의 브랜드 회원인가」를 읽는 경로가 필요한데 없다.** 고객 길은 질의 금지(`customer-routes.mjs:19`)라 `POST /api/customer/pulse/project-state {proof}` 꼴이 필요하다(증표를 읽기에도 써야 함).
- **P3-7. 역할 문장이 어긋난다.** 3-1 「사용 중지 = admin」, 5-3 상세 「사용 중지 요청」(역할 없음), 5-6 「admin 또는 직원」 — 한 줄로.
- **P3-8. 증표 토큰이 쌓인다.** 만료 토큰 정리는 **시작 때 한 번**(`store.mjs:61`). 5분 증표를 누를 때마다 찍으면 재시작 전까지 남는다. `readToken`이 기한을 보니 안전하지만 증표 발급에 문턱(주소별) 또는 소모 때 만료 행 정리를 더한다.
- **P3-9. 로그인 흐름은 메모리다**(`customer-identity.mjs:56 flows` Map). 로그인 도중 서버가 다시 뜨면 「흐름을 못 찾은 실패」라 PULSE에서 시작했어도 `/consultation/?login=failed`로 간다. 받아들이되 7절 「로그인 돌아오기」에 적는다. 또 `/pulse-app/?login=failed`는 `app.mjs:48`의 `replaceState`가 지우므로 그 앞에서 읽어야 한다(`sw.js`는 질의 있는 주소를 캐시 안 해 괜찮다).
- **P3-10. 5-4 표 넷째 줄(글 콘티 보내기에 `usage` 승인 요구)은 군더더기이고 판 1 결정과 부딪힌다.** `personaRef`는 서버가 `usage` 승인 때만 붙이므로 「참조가 있다」가 곧 「그 판의 usage 승인이 있다」다. `send_draft`에 새 가드를 넣으면 판 1 GA1(「방향 · 글 콘티는 인물을 만드는 동안 먼저 맞춘다」, `pulse-requests.mjs:375`)을 되돌린다. 넷째 줄을 지우고 제작 시작(`approve_draft` 이미지 판 · `payment_confirm` 사진) 재검사만 남긴다.
- **P3-11. `reuse` 승인 둘이 동시에 오면.** 「한 번 채워지면 안 바뀜」이지만 처음 · 연장 모두 「새 reuse 승인」이라 트랜잭션 안에서 `workspaceId==null || ===W`를 보지 않으면 두 줄이 생긴다. 한 줄로 적는다.
- **P3-12. 보내기의 `modelChoice`는 몸통에서 온다**(`pulse-requests.mjs:236`), 붙임은 저장된 초안 행에 있다. 「다른 선택이면 붙임을 보지 않는다(이미 지워져 있다)」는 마지막 저장 뒤 화면이 바뀐 경우 참이 아니다 — 보내기에서 「몸통이 `persona`면 붙임 필수, 아니면 붙임 무시 · 지움」으로 적는다.
- **P3-13. 4-3 「참조한 판 하나」 우선순위.** `castingSelection.personaRef.revisionId`가 있으면 그것, 없으면 `workspaceRequest.revisionId` — 명시.
- **P3-14. 실제 인물의 다시 쓰기 동의는 판 3 `pulsePersonaConsents`에 「다시 쓰기」 범위를 기계가 읽을 칸이 있어야** 서버가 3-4 조건을 본다 — 판 3 가정 목록에 넣는다(아래 8-5).
- **P3-15. 보관 대기 노출 순서.** 판 3 품질 승인자(초대 세션)가 아닌 브랜드 admin이 그림을 먼저 보고 보관을 정한다. 기획 7절(브랜드 소유)과는 맞으니 유지하되, 고객 방 안내 한 줄이 「누가 볼 수 있게 되는지」를 말해야 한다.

## 3. 8절 판단 여섯

1. **일회용 증표(4-1) — 충분하다, 더 단순한 길은 없다.** 세션 토큰을 안 담고, 목적 · 프로젝트(또는 초안) · `inviteRevision`에 묶이고, 5분 · 한 번(`DELETE` 동반)이면 바꿔치기 · 재사용 · 다른 초안이 모두 닫힌다. 쿠키 Path를 넓히는 대안은 `/pulse/api/*`의 CSRF · 출처 규칙을 흔들어 더 위험하다. 고칠 것은 P2-2(동기 트랜잭션 순서 · `consume` 중첩)와 P3-8(토큰 정리)뿐. 선택: 증표 몸통에 발급한 `pulse-session`의 `auth.hash`를 넣어 소모 때 그 세션이 아직 살아 있는지도 보면 「세션이 끝난 뒤 5분」 창도 닫힌다(값은 작다).
2. **한 번 귀속 · 이동 없음(3-4) vs 기획 7절** — 기획은 「브랜드 간 이동은 별도 사용 권한 확인」이지 금지가 아니다. 판매 전이라 이동을 안 만드는 것은 맞지만, 그러면 **교정 길**(P2-1)은 있어야 한다. 판 4 문서에 「이동은 판 5 이후 별도, 관리자 귀속 취소는 판 4」로 적으면 어긋남이 닫힌다. 동의를 브랜드에 묶고 원 프로젝트를 기록으로만 쓰는 쪽(A3 · GA3 고침)은 맞다.
3. **만료 계산(3-4)** — 함수 하나 · `ready`인 다시 쓰기 인물만 · 요청당 `now` 하나는 좋다. `paused · retired · withdrawn · deleting`을 안 가리는 것도 맞다. 빠진 것: `until`의 형 · 시간대 · 필수(P3-4); `scope:'project'` 인물에는 시계가 없어 원 프로젝트가 정리돼도 파일이 영구히 남는다 — 「자동 영구 삭제 끔」 결정 안의 일이지만 9절 보관 기간 결정 항목에 「프로젝트 전용 인물의 기한」도 넣는다. 저장된 `expired`(SETTLED)는 쓰이지 않는 상태가 되는데 해는 없다.
4. **24시간 붙임 + 직원 연결 확인(5-4)** — 익명 보내기로 남의 인물을 붙이는 길은 닫혔다: 붙이기는 회원 세션 + 증표, 보내기는 `attachedBy`가 그 브랜드의 지금 회원 + 24시간 + 「다시 쓸 수 있음」, 그 위에 직원 확인. 남는 틈은 같은 브라우저를 24시간 안에 다른 사람이 쓰는 경우뿐이고 직원 확인이 받는다. 고칠 것은 P3-12(몸통 vs 행)와 P2-5(방 안 의뢰서 길). 더 단순한 대안(보내기도 증표로 `/api/customer/pulse/submit {proof}`)이 있지만 `submit`의 잠금 · 파일 옮기기 로직(`pulse-requests.mjs:243~276`)을 옮겨야 해 지금 설계가 싸다.
5. **단계별 가드 표(5-4) · 초대 경로 넓히기(4-3)와 판 3** — 판 3이 master에 없어 **맞물림을 확인하지 못했다.** 판 4가 판 3에 기대는 가정을 구현 전에 대조할 목록: ① `usage` 승인만 `castingSelection.personaRef`를 붙이고 승인 판을 기록한다 ② `pulsePersonaApprovals` 꼴에 `workspaceId` · `authMethod` · `termsHash` · `viewedHash` 칸이 있다 ③ 가드가 「원 프로젝트 또는 다시 쓰기 조건」을 받을 자리(인자 하나)가 있다 ④ `/pulse/api/persona/*`의 보이는 자산 집합이 함수 하나라 판 4가 넓힐 수 있다 ⑤ 동의 문서에 다시 쓰기 범위 칸(P3-14) ⑥ 묘비 `status` 처리(P2-3). 표 자체는 교착이 없다(연결 확인 → usage → 방향 → 글 콘티 → 제작 시작이 한 방향). 빈틈은 넷째 줄의 군더더기(P3-10)와 P2-4의 권한 교착.
6. **기획 12-2 · 7절과 어긋나는 곳, 빠진 시나리오** — 어긋남: (가) 이동 금지(위 2) (나) 삭제 순서를 P1-1대로 바꾸면 12-2 「파일 → 묘비」와 달라진다(결정 표에 적으면 됨) (다) 기획 4절 카드의 「마지막 사용」이 5-3에 없다(작음) (라) 12-2 「customer-routes 알려진 경로에 추가」를 접두 일치로 바꾼 것은 적혀 있어 괜찮다. 빠진 시나리오는 4절.

## 4. 빠진 것 · 더 단순하게 갈 곳

**빠진 시나리오(기획 10절 5 · 8 · 9 · 10 기준):**
- 5: 원본 사진(`pulsePersonaSources`)은 어느 고객 길로도 안 나간다는 시험(4-2 사슬은 판 자산만, 4-3도) — 7절에 명시가 없다. 회원이 아닌 SYNK ID가 `claim`을 두 프로젝트에 내도 서로 못 본다.
- 8: 실제 인물에서 동의 범위 밖이라 연결 확인이 막히는 길(4-4)의 시험이 없다. 연결 확인 뒤 직원이 그 프로젝트의 연결을 끊었을 때 `workspaceRequest`가 남아 삭제가 막히는 것(5-6)은 있다.
- 9: 만료 → 새 `reuse` 승인 → 다시 `ready`로 돌아오는 연장 시험, 이미 `producing`인 프로젝트는 만료 뒤에도 가드가 안 걸려 그대로 간다는 시험(가드가 제작 시작까지만 돈다 — 1절 표 마지막 줄)이 없다.
- 10: 브랜드 닫기 → 다시 열기 뒤 보관 대기 · 회원 접근이 돌아오는지, 묘비 뒤 90일 정리가 도는지(P2-3), 스위치를 켰다 끈 뒤 붙임이 남은 초안의 보내기(409 문구)가 없다.
- 공통: `reuse` 승인 동시 둘(P3-11), 중앙 계정이 `active`가 아니게 된 회원(`verify`가 거절해 세션은 죽지만 회원 줄과 `attachedBy`는 남는다 — 해는 없고 적기만).

**덜어 낼 것(판매 전 무게 기준):**
- **삭제의 「건너뛰기」 기계를 없앤다**(P1-1 고침이 곧 단순화) — 문서 먼저 · 파일 나중이면 `workspaceMediaNames` · `node-host.py` · 백업 시험을 안 건드린다.
- **`pulseWorkspaceClaims`의 서버 자동 `withdrawn` 전이를 없앤다**(P3-2 · P3-3) — `client-projects.mjs`의 보관 · 초대 경로마다 훅을 다는 대신 결정 때 계산. 전이표가 `pending → approved | rejected | withdrawn(본인)` 셋으로 준다.
- **가드 표의 단계 이름을 없앤다**(P3-10) — 가드 조건은 「원 프로젝트(판 3) 또는 (연결 확인된 다시 쓰기 프로젝트 ∧ 다시 쓸 수 있음 ∧ 참조한 판 일치)」 하나로 모든 자리에서 같다.
- 「내 모델」 상세(승인 이력 · 변형 · 사용 프로젝트)는 목록 · 카드 · 「이 모델로 의뢰」 뒤로 미뤄도 시나리오 8 · 9 · 10은 선다. `stop` · `delete-request`는 직원 할 일만 만들어 싸니 남긴다.
- 역할 둘(admin · member)은 유지해도 되지만, 판매 전에는 「모두 admin」으로 시작하고 member를 비워 두는 것도 된다(문서는 그대로, 화면 입구만 하나).

## 5. 판정

**고치고 진행** — P1 하나(삭제 순서 ↔ 백업)와 P2 다섯(귀속 교정 길 · 트랜잭션 서술 · 묘비 상태 · 연결 확인 권한 교착 · 방 안 의뢰서 길)을 문서에 반영한 뒤, 판 3이 master에 오르면 8-5의 여섯 가정을 코드로 대조하고 구현한다. 구조(증표 · 브랜드 귀속 · 만료 계산 · 단계 가드)는 다시 설계할 필요가 없다.
