# PULSE 고객 앱 · 판 2 메일 알림 설계 (2026-11-07 · 같은 날 Fable 검토 반영 고침)

> 결정 11-07 ③ 「앱 밖 알림은 메일 먼저 — 방향 제안 도착 · 글 콘티 · 영상 확인 · 납품 네 순간만, 문구는 Claude가 쓴다. 알림톡은 법인 뒤」. 첫 판(길 C · Gmail API)은 Fable 설계 검토 P1 6 · P2 7로 고쳤고, 고친 판의 Fable 다시 검토 P1 1 · P2 9 · P3 2를 구현과 함께 넣었다 — 아래가 지금 판이고, 지적마다 어떻게 반영했는지는 맨 끝 두 표에 있다. 구현: 서버 `company/pulse-mail.mjs`, 중계 `company/pulse-mail-relay/relay.gs` · `relay-manifest.json`(clasp가 올리는 뿌리 세 파일과 이름이 달라 라이브 Apps Script에 섞이지 않는다).

## 목적

손님은 의뢰서를 보낸 뒤 앱을 닫는다. 지금은 차례가 손님에게 넘어와도 앱 안 알림과(설치했다면) 기기 알림뿐이라, 앱을 다시 열기 전에는 모른다. 네 순간에만 짧은 메일 한 통으로 「지금 손님 차례」를 알린다. 실주문 0건이라 켠 뒤 첫 메일은 시험 주문으로 founder@synk.im에 받아 본다.

## 길 고르기 — 길 B(founder@synk.im 소유 Apps Script 중계)

확인한 사실(11-07): 회사 서버의 GCP 프로젝트(`synk-bake-unmet27`)는 개인 계정 소유라 조직(synk.im)이 없어 동의 화면 「내부(Internal)」를 만들 수 없다. 「외부」로 두면 시험 상태는 갱신 토큰이 7일에 끊기고, 게시 상태는 검증 안 된 앱 경고 화면이다. 이 PC에는 gcloud가 없고, clasp에는 unmet23 로그인 하나뿐이다.

B를 고른 까닭 둘. ① **중계에 비밀값이 없다** — 회사 서버가 요청에 RSA 서명을 하고, 중계는 공개 열쇠로만 확인한다. 개인 열쇠는 회사 서버가 기기 알림 VAPID 열쇠처럼 스스로 만들어 암호 저장소에 둔다(사람 손 · 화면 입력 칸을 거치지 않는다). 공개 열쇠는 비밀이 아니라 스크립트 속성에 적어도 된다. ② **중계가 같은 열쇠의 메일을 한 번만 보낸다** — 함의 줄 id를 열쇠로 보내고, 중계가 보낸 열쇠를 적어 두므로 응답을 못 받아도 같은 열쇠로 다시 보내면 「이미 보냄」이 돌아온다. 첫 판의 「응답 없으면 unknown, 다시 안 보냄」(한 통 빠짐)이 「안전하게 다시 보냄」이 된다.

B의 위험과 막음: 웹 앱 주소가 하나 는다(주소만으로는 아무것도 못 보낸다 — 서명 · 시각 · 제목 머리 · 받는 사람 하나 · 하루 상한). Workspace 관리 설정이 「모든 사용자」 웹 앱을 막으면 배포 때 바로 보인다 — 그때는 막힘을 적고 C로 돌아가 다시 고른다. 중계 코드를 고칠 때는 founder@ 편집기에서 다시 배포해야 하므로 코드를 작게(약 150줄) 두고 판 번호(`RELAY_VERSION`)를 연결 확인에서 맞춰 본다.

## 중계(founder@synk.im 소유 Apps Script, 저장소 `company/pulse-mail-relay/`)

- `appsscript.json`: V8, 시간대 Asia/Seoul, 권한은 `https://www.googleapis.com/auth/script.send_mail` 하나, 웹 앱 실행 = 배포한 사람 · 액세스 = 모든 사용자.
- `doPost` 받는 꼴: `{v:1, op:'send'|'ping', key, ts, to, subject, body, sig}`. 서명은 `JSON.stringify(['pulse-mail/v1',op,key,ts,to,subject,body])`의 RSASSA-PKCS1-v1_5 SHA-256(2048비트). Apps Script에는 RSA 확인 함수가 없어 BigInt로 공개 지수 거듭제곱을 직접 하고(65537 — 곱셈 열일곱 번), 다이제스트는 `Utilities.computeDigest`로 맞춘다. 공개 열쇠(n)는 스크립트 속성 `SERVER_KEY_N`.
- 막는 것(꼴 · 시각을 RSA보다 먼저): 서명 틀림 · 시각 ±10분 밖 · `ts` 정수 아님 · 열쇠 꼴(`^[a-z0-9:_-]{8,160}$`) · 받는 사람 하나(254자 안, 쉼표 · 꺾쇠 · 공백 없음) · 제목이 〔SYNK PULSE〕로 시작하고 150자 안 · 제어 문자 없음 · 본문 4,000자 안(줄바꿈만) · 하루 상한 200통(`MailApp.getRemainingDailyQuota()`도 본다). 보낼 이름 · 답장 주소는 중계 코드에 박고 요청에서 받지 않는다.
- 한 번만: **잠금 하나가 확인 → `sending` → `MailApp.sendEmail` → `sent`까지 감싼다**(`tryLock(20000)`, 못 얻으면 `busy` — 서버는 재시도). 그래서 `sending`은 실행이 보내는 중에 죽은 경우에만 남고 그때만 `unknown`(다시 안 보냄). `sent`면 `duplicate`, 보내기가 예외면 열쇠를 지우고 `failed`(서버가 같은 열쇠로 다시). 열쇠는 서버 줄 id의 sha256 앞 24자, 값은 `sent:<시각>`, 7일 지난 열쇠는 부를 때마다 50개까지 지운다(200통 × 7일 ≈ 60KB — 속성 500KB 안).
- 답: `{ok, status:'sent'|'duplicate'|'unknown'|'busy'|'rejected'|'failed', code, version}`. `ping`은 서명 · 시각만 보고 `{ok, version, remaining}`. `status`(열쇠만 서명)는 보내지 않고 `k:<열쇠>`만 읽어 `{state:'sent'|'sending'|'none'}`.
- 시험: Node `vm`에 가짜 `MailApp` · `PropertiesService` · `LockService` · `Utilities` · `ContentService`를 넣고 실제 Node 개인 열쇠로 서명한 요청을 돌린다(BigInt 확인 길이 Node `crypto.verify`와 같은 답인지).

## 서버(새 `pulse-mail.mjs`)

- **설정 문서** `pulseMailSettings/main`(관리자만, 바꿀 때 `audit('pulse-mail-settings')`): `enabled` · `enabledAt`(켠 순간 — P1-3 물금) · `relayUrl` · `connection`(`unknown|ok|broken`, 확인 시각 · 사유 코드). 환경 변수는 비상 정지(`SYNK_PULSE_MAIL_STOP=1`)만. 관리자 화면은 켜기 전에 메일 칸이 있는 의뢰 흐름 프로젝트 수와 주소 도메인 묶음을 보여 준다(합성 주소가 보이면 담당자가 `request_contact`로 끈다 — P1-3).
- **열쇠**: `store.secret('pulse-mail-relay-key')` — 없으면 서버가 RSA 2048 열쇠를 만들어 넣는다(VAPID와 같은 길). 관리자 화면에 공개 열쇠 n(16진)과 지문만 보인다. 주소 해시용 소금도 같은 비밀 문서에 둔다.
- **함** `pulseMailOutbox`: `{id, projectId, moment, eventIds[], firstEventAt, lastEventAt, dueAt, state, reason, attempts, nextAttemptAt, sendingAt, sentAt, recipientHash, createdAt}`. 주소 원문 · 제목 · 본문은 두지 않는다. `recipientHash`는 소금 넣은 HMAC(주소가 짧아 그냥 해시는 되찾을 수 있다 — P2), 「보낸 뒤 주소가 바뀌었나」를 직원 화면에 보이는 데만 쓴다.
- **채우기**(P1-3 · P1-4 · P2): 30초마다, 켜져 있고 연결이 끊기지 않았을 때 의뢰 흐름 프로젝트마다 고객 알림 투영의 네 순간 사건 중 `createdAt > enabledAt`인 것을 본다. 이미 함의 어느 줄에 든 사건은 건너뛴다. 같은 프로젝트 · 같은 순간의 `pending` 줄이 있으면 사건 id를 더하고 `dueAt = 마지막 사건 + 3분`(처음 사건 + 15분을 넘지 않음), 없으면 새 줄(`id = <프로젝트>:<순간>:<첫 사건 id 해시 12자>`). 고친 제안 · 파일 여러 개가 3분 안에 오면 한 통이다.
- **보내기**(P1-6): 같은 30초 일(`runtimeJob('pulseMail')`, 한 번에 하나 — 돌고 있으면 건너뜀, `schedule:false`면 타이머 없음)에서 `dueAt`과 `nextAttemptAt`이 지난 `pending`을 오래된 순으로 다섯 통까지. 보내기 직전에 다시 본다 — 꺼짐 · 비상 정지 · 연결 끊김이면 멈춤, 프로젝트가 대상에서 빠졌거나 받는 사람이 없거나 꺼졌으면 `skipped`(사유), 처음 사건이 48시간을 넘었으면 `skipped:expired`(끊김이 풀릴 때 묵은 메일이 한꺼번에 나가지 않게), 줄의 마지막 사건이 투영에서 사라졌으면 `skipped:stale`, 손님이 앱에서 이미 읽었으면 `skipped:read`, 손님이 그 순간의 일을 이미 했으면 `skipped:acted`(방향 답 · 그 판 글 콘티 의견이나 확인 · 그 영상 승인이나 의견 · 그 최종 파일 수령 확인). 그다음 `sending`(시각 · 시도 +1)을 적고 중계를 부른다(30초 기한, 302는 `script.googleusercontent.com`으로 가는 것만 따라감).
  - 판정 순서: 판 번호 다름 → 끊김, 그다음 중계 JSON의 상태, JSON이 아니면 HTTP 상태(429 · 5xx는 HTML이어도 재시도, 2xx HTML · 401 · 403 · 404는 끊김).
  - `sent` · `duplicate` → `sent`. `rejected`는 코드로 가른다 — `signature` · `no_key` · `clock` · `format`은 연결 문제라 끊김(줄은 안 태움), `key` · `to` · `subject` · `body`는 그 줄만 `failed`. `busy`(하루 상한)는 1시간 뒤, `busy`(잠금)는 재시도. 중계가 `unknown` → `unknown`(다시 안 보냄), 10분 뒤 `status`로 한 번 되물어 `sent`면 `sent`(사유 `confirmed_later`)로 닫는다 — 보내지 않으니 「unknown 자동 재시도 없음」과 맞는다.
  - 망 오류 · 시간 초과 · 429 · 5xx → `pending`으로 되돌리고 1 · 5 · 15분 뒤 다시(같은 열쇠라 중계가 두 번 보내지 않는다), 네 번째도 안 되면 `failed`.
  - JSON이 아닌 답(로그인 · 권한 화면) · 401 · 403 · 404 · `RELAY_VERSION` 다름 → 설정 문서 `connection: broken`(사유), 그 줄은 시도 횟수를 태우지 않고 `pending`으로, 함 전체가 멈춘다(P1-2 — 첫 판의 `invalid_grant`에 해당). 끊긴 뒤 10분마다 서버가 스스로 `ping`해 통과하면 풀린다(관리자 손 없이 — 관리자 화면의 연결 확인도 같은 길).
  - `sending`으로 5분 넘게 남은 줄(서버가 그사이 꺼짐)은 `pending`으로 되돌린다 — 같은 열쇠라 안전하다.
- **보존**(P2): `sent` · `skipped` · `failed` · `unknown` 줄은 90일 뒤 지운다. 기록(로그)에는 프로젝트 id · 순간 · 상태 · 사유 코드만 쓰고 주소 · 제목 · 본문은 쓰지 않는다.
- **담당자 `request_contact`**(P1-5): 직원 전용 행동 `{email?, mailOff?}` — 주소 꼴을 보고 `studio.request.contact`에 그때의 의뢰서 주소(`basedOn`)와 함께 적고, 직원 화면 연락처 줄(`row.contact`)도 같이 고친다. 확인 뒤에도 주소를 고치거나 메일을 끌 수 있다. 손님이 그 뒤 의뢰서 주소를 고치면(확인 전에만 됨) 손님 주소가 이기고 직원 화면에 그렇게 보인다. 손님 알림 사건은 만들지 않는다.
- **직원 화면**(`desk-view.mjs`): 프로젝트 옆 칸에 메일 한 줄 — 「메일 · 11-08 14:02 Gmail에 넘김」(실제 도착 · 반송은 founder@ 받은편지함에서 본다), 「메일 안 보냄 · 앱에서 먼저 보셨어요」, 「메일 실패 · 직접 연락해 주세요」, 「메일 연결 전」, 「메일 연결 끊김 · 다시 연결」. 주소 고치기 · 메일 끄기 단추. 다시 보내기 단추는 두지 않는다.
- **손님 보기**: `mail: {mailOn, mailTo}` — 켜짐 · 연결 ok · 받는 사람 있음 · 안 꺼짐일 때만, 주소는 가린 꼴(`b***@example.com`). 고객 방은 초대 링크를 가진 누구나(최종 확인자 포함) 열므로 손님 보기의 `request`에서 `contact`를 뺀다(직원 보기에는 둔다).

## 화면 글

`mail.mailOn`일 때만 메일 말이 나온다 — 저희 차례인 고객 방 글 끝에 「차례가 오면 메일(가린 주소)로도 알려 드려요.」, 방향 화면 「더 보기」 표에 「알림 · 글 콘티가 오면 메일(가린 주소)로도 알려 드려요」. 접수증에는 늘 「연락받을 곳」 줄(방금 적은 메일이나 휴대폰)을 되비춰 틀린 주소를 바로 알아보게 한다(P1-5). 「메일 말 없음」 시험은 꺼졌을 때 그대로 지킨다.

## 시험(빈칸 없이 — P2)

- 채우기: 네 순간만 · 글 콘티는 script 판과 round 1만 · 물금 전 사건은 안 넣음 · 메일 칸 없음 · 꺼짐 · 체험 · 옛 흐름 · 보관은 안 넣음 · 같은 사건 두 번 안 넣음 · 3분 안 고친 제안 둘과 파일 셋이 한 줄 · 15분 상한.
- 보내기(가짜 중계 fetch): sent · duplicate → sent, rejected → failed, 429 · 500 · 시간 초과 → 같은 열쇠로 다시 · 네 번째 failed, HTML · 403 · 판 번호 다름 → 끊김 · 시도 안 태움 · 함 멈춤 · ping 뒤 풀림, stale(투영에서 사라짐 · 방향 이미 답함), read, 보낼 때 담당자가 고친 새 주소, mailOff, 5분 넘은 sending 되돌림, 한 번에 하나(돌고 있으면 건너뜀), `schedule:false`면 타이머 없음, 비상 정지.
- 본문: 제목 · 본문에 프로젝트 이름 · 순간 줄, 이름의 줄바꿈 · 제어 문자 제거, 초대 토큰 · 내부 id · AI 도구 이름 없음.
- 서명 · 중계: Node 서명을 중계의 BigInt 확인이 받음 · 한 글자 바뀐 본문 거절 · 시각 밖 · 제목 머리 · 받는 사람 둘 · 하루 상한 · sent/sending 열쇠.
- 보존 · 기록: 90일 지운 뒤 남는 줄 없음, 함 · 기록에 주소 · 제목 없음.
- 담당자 주소 고치기 · 끄기, 손님 보기 `mailOn` · `mailTo`, 화면 글 세 곳.
