## 1. 지금 실물(11-10 origin 기준)

- **고객 SYNK ID 로그인**(`customer-identity.mjs`): 중앙 계정 확인을 요청마다 다시 한다(시간 캐시 없음). 사용자 id는 `synk:<UUID>`, 세션 8시간, 쿠키 `synk_customer_session`(`Path=/api/customer`, `SameSite=Lax`, HttpOnly), POST는 origin · `X-CSRF-Token` 확인. **운영에 켜져 있다** — 11-10 `GET /api/customer/me` → `loginAvailable:true`(최상위 세션이 직접 읽음). 로그인 흐름은 메모리에만 있다(서버가 다시 뜨면 진행 중 로그인은 실패). 쓰는 곳은 상담(`/consultation/`)뿐이고, `customer-routes.mjs`는 알려진 경로 여덟 개만 받으며 `synk-id/start`는 빈 몸통만 받는다. 콜백 뒤 성공 · 실패 모두 `/consultation/`(실패는 `?login=failed`)로 보낸다. 주소 뒤 질의(`?…`)는 막는다.
- **프로젝트 접근**(`client-projects.mjs`): 초대 링크 해시 → `pulse-session` 토큰 `{projectId, inviteRevision, csrf, openedAt}`(720분). 메일 코드로 다시 열면 `acceptedInvite`, 기억한 기기는 `deviceHash`로 따로 본다. PULSE 쿠키 `synk_pulse_session` · `synk_pulse_request` · `synk_pulse_device`는 모두 **`Path=/pulse`, `SameSite=Strict`**, HttpOnly이고 `/pulse/api/*`에만 간다(`/pulse-app/` 쪽 요청에는 안 감). 초안 토큰 · 쿠키는 30일, 손대지 않은 초안은 14일 뒤 지운다. `ownerId`는 직원 담당자다(공개 의뢰서로 생긴 프로젝트는 `requestOwner()`).
- **두 쿠키는 길이 겹치지 않는다:** 고객 SYNK ID 쿠키는 `/pulse/*`로 가지 않고, PULSE 쿠키는 `/api/customer/*`로 가지 않는다. 한 요청에서 「이 프로젝트에 들어온 사람」과 「이 SYNK ID 회원」을 함께 증명하는 길이 지금은 없다 — 판 4 설계의 첫 문제다.
- **인물**(판 1 · 판 3): `PERSONA_KINDS`에 `customerWorkspaces`까지 이름이 있다. `createPersonaGuard`는 `persona.originProjectId === row.id` · 상태 `ready` · 판 `published` · 묘비 없음을 본다(「고객 브랜드로 넓히는 것은 판 4」 주석). 가드가 도는 곳은 모델 없는 방향 제안 · 결제 확인(사진 첫 장) · 제작 시작(`approve_draft` 이미지 판)이고, 글 콘티 보내기(`send_draft`)는 `castingOf().agreed`만 본다 — `personaRef`가 있으면 `agreed`다. `PERSONA_SETTLED`는 `ready · retired · expired · withdrawn`이고, 그 밖의 상태(묘비 포함)인 인물이 있는 원 프로젝트는 90일 정리에서 빠진다. 스위치 `myModels`는 기본 끔이고 프로젝트 응답(`projectView`)에만 실린다.
- **백업 소유 목록**(`workspace-media.mjs`의 `personaMediaOf`): 출처 문서는 `diskName===null && deletedAt`이면 비고, 판 문서는 `assets[].diskName`이 문자열이 아니면 예외로 멈춘다. 백업(`backup.mjs`)은 목록의 파일이 없으면 전체가 실패한다.
- **저장소 트랜잭션**(`store.mjs`): `store.transaction(fn)`은 동기다(`fn()` 뒤 바로 COMMIT). `store.consume`은 스스로 트랜잭션을 연다. 만료 토큰 정리는 서버 시작 때 한 번.

## 2. 범위

| 판 4가 하는 것 | 하지 않는 것 |
|---|---|
| 고객 브랜드(`customerWorkspaces`)와 회원, 직원이 확인한 연결 | 이메일 · 회사명 일치로 자산 합치기 |
| 프로젝트 ↔ 브랜드 연결(직원 행동) | `ownerId`의 뜻 바꾸기(직원 담당자 그대로) |
| 「내 모델」 목록 · 카드 · 「이 모델로 의뢰」, 보관 대기와 다시 쓰기 동의 | 공개 캐스팅북에 전용 인물 올리기 |
| 다시 쓰기 의뢰(사진 다시 올리기 · 다시 학습 없이) | 결제 · 가격 · 해외 통화 |
| 연장 · 철회 · 만료 · 사용 중지 · 삭제 요청 · 관리자 귀속 취소 | 자동 영구 삭제(보관 기간 결정 전까지 끔) |

| | 고객에게 새 알림을 실제로 보내기(통로는 기존 것, 스위치 끔) |

**만드는 차례(판매 전 무게):** 연결 · 합류 → 보관 대기 · 다시 쓰기 동의 → 목록 · 카드 · 「이 모델로 의뢰」 → 다시 쓰기 의뢰 · 연결 확인 · 사용 확인 → 만료 · 중지 · 철회 · 삭제. 「내 모델」 상세(승인 이력 · 변형 · 사용 프로젝트)는 그 뒤에 붙여도 시나리오 8 · 9 · 10은 선다.

## 3. 데이터

### 3-1. 고객 브랜드 `customerWorkspaces`

```
{ id, name,                      // name은 표시용. 맞추기에 쓰지 않는다
  status: 'active' | 'closed', closedAt, closedBy,
  staffOwnerId,                  // 이 브랜드를 맡은 직원(관리자는 모두 가능)
  members: [{ synkUserId, displayName, role: 'admin' | 'member',
              addedAt, addedBy, via: { claimId } | { staffNote } }],
  revision, createdAt, createdBy, history: [...] }   // 덧붙이기만, 최근 200줄
```

- 회원은 중앙 SYNK ID 사용자(`synkUserId` UUID)만이다. 이메일 칸은 두지 않는다.
- **역할(한 줄 정리):** **admin** — 내 모델 보기 · 「이 모델로 의뢰」 · 보관 대기 보기 · 다시 쓰기 동의(처음 · 연장 · 재개) · 철회 · 사용 중지 요청 · 삭제 요청. **member** — 내 모델 보기 · 「이 모델로 의뢰」. 판매 전에는 연결 요청을 승인할 때 **admin으로 넣는 것이 기본값**이고 member는 직원이 고를 때만이다. 다시 쓰기 동의는 브랜드에 자산을 남기는 결정이라 브랜드 admin만 한다. 프로젝트 승인(얼굴 · 동작 · 사용 · 최종 영상)은 지금처럼 그 프로젝트 승인자가 초대 세션으로 한다 — 브랜드 역할이 프로젝트 승인권을 만들지 않고, 프로젝트 승인자가 브랜드 동의를 대신하지도 않는다. 직원은 4-4 권한으로 사용 중지 · 풀기 · 삭제를 한다.
- **닫힌 브랜드:** `status:'closed'`면 회원 경로가 그 브랜드를 없는 것처럼 다루고(목록 · 그림 · 붙이기 · 보내기 · 동의 모두), 가드(5-4)가 그 브랜드에 기대는 사용을 막는다. 인물 문서 · `workspaceId`는 그대로 남는다(기록). 닫는 순간 그 브랜드 인물을 쓰는 진행 중 프로젝트마다 직원 할 일이 생긴다. 다시 열기는 관리자만이고, 다시 열면 회원 접근 · 보관 대기가 돌아온다.
- 대행사가 여러 고객을 맡으면 고객 브랜드마다 따로 만든다. 한 사람이 여러 브랜드의 회원일 수 있다.

### 3-2. 연결 요청 `pulseWorkspaceClaims`(새 문서 종류)

```
{ id, projectId, inviteRevision, synkUserId, displayName,
  status: 'pending' | 'approved' | 'rejected' | 'withdrawn',
  createdAt, decidedAt, decidedBy, workspaceId, note }
```

- 같은 프로젝트 · 같은 사람의 `pending`은 하나만(두 번 눌러도 같은 줄). 결정된 줄은 지우지 않는다.
- 전이는 셋뿐: `pending → approved | rejected`(직원, 4-4), `pending → withdrawn`(요청한 본인, `/api/customer/pulse/claim/withdraw`). 서버가 저절로 바꾸는 전이는 없다.
- **연결(link)인지 합류(join)인지는 저장하지 않고 결정 때 계산한다** — 그 순간 프로젝트에 `customerWorkspaceId`가 있으면 합류, 없으면 연결. 결정 때 프로젝트가 보관됐거나 `inviteRevision`이 요청 때와 다르면 승인을 막고 직원 화면에 「손님이 다시 요청해야 해요」를 보인다(초대 링크를 새로 만든 뒤의 요청은 새 링크로 다시 받는다).
- 문서뿐이라 파일 소유 목록은 바뀌지 않는다. DB 백업에 그대로 든다.

### 3-3. 프로젝트 쪽

- `clientProjects.customerWorkspaceId`(선택): **직원 행동으로만** 붙이고 뗀다(프로젝트 기록 한 줄, 4-4 권한). 손님이 보내는 값으로 정하지 않는다.
- `clientProjects.workspaceRequest`(선택, 다시 쓰기 의뢰가 만든 프로젝트만): `{workspaceId, personaId, revisionId, attachedBy: synkUserId, attachedAt, confirmedAt, confirmedBy}` — 담당자가 접수 때 확인하면(4-4) `customerWorkspaceId`로 옮겨 적고 `confirmedAt` · `confirmedBy`를 더한다. **확인 뒤에도 지우지 않는다** — 사용 확인 전 단계의 참조로 삭제 검사(5-6)가 이것을 본다. 확인 전에는 초대 세션에 인물 자산이 열리지 않는다(4-3).
- **다시 쓰기 의뢰 프로젝트의 담당자:** 보내기 때 그 브랜드가 활성이고 `staffOwnerId`가 일하는 직원이면 `ownerId`를 그 사람으로, 아니면 지금처럼 `requestOwner()`. 연결 확인이 「프로젝트 권한 + 브랜드 담당」 둘 다를 요구해도(4-4) 같은 사람이 맡게 되어 교착이 없다.

### 3-4. 인물 쪽(판 3 문서에 더하기만)

- **브랜드 귀속 `pulsePersonas.workspaceId`:** null로 태어난다(판 3). 채우는 때는 하나뿐이다: 원 프로젝트가 직원 행동으로 브랜드 W에 연결돼 있고, 그 인물에 **W에 묶인** 다시 쓰기 동의(`reuse` 승인)가 생길 때. 한 번 채워지면 **다른 브랜드로 바뀌지 않는다**(옮기기는 판 5 이후 별도). 원 프로젝트의 연결을 끊거나 다른 브랜드에 다시 이어도 W 그대로다(원 프로젝트는 기록일 뿐 — 5-7).
- **관리자 귀속 취소(잘못 연결한 경우의 교정 길):** 관리자만, 그 브랜드에서 그 인물을 참조하는 끝나지 않은 다시 쓰기 프로젝트가 0이고 `reuse` 승인을 철회로 돌릴 때만 `workspaceId→null`(근거 한 줄 · 브랜드 `history` · 감사 기록). 그 뒤 원 프로젝트를 올바른 브랜드에 연결하면 그 브랜드의 보관 대기에 다시 나타난다.
- **다시 쓰기 동의 `reuse` 승인**(판 3 `pulsePersonaApprovals` 꼴 그대로): `{personaId, revisionId, workspaceId, terms: {보관 자료, 목적, until, 철회 방법, 백업 잔존 기간}, termsHash, by: synkUserId, authMethod: 'synk-member', at, supersedes}`. `viewedHash`에 브랜드 이름 · 보관 문안 해시를 넣는다. **그 브랜드의 admin만 내 모델의 「보관 대기」(처음) · 상세(연장 · 재개)에서 승인한다** — 원 프로젝트가 브랜드 W에 연결돼 있어야 W의 보관 대기에 나타나므로 브랜드 없이 받은 동의는 없다. 초대 세션으로는 받지 않는다. 받을 때 동기 트랜잭션 안에서 `persona.workspaceId`가 null이거나 W인지 보고, 앞선 유효한 `reuse`가 있으면 `supersedes`로 대체한다 — 동시에 둘이 와도 유효한 동의는 하나다. 실제 인물이면 당사자 동의(판 3 `pulsePersonaConsents`)의 기계가 읽는 「다시 쓰기」 범위 칸이 그것을 허락해야 받는다.
- **보관 `pulsePersonas.retention`:** `{ scope: 'project' | 'reuse', until, reuseApprovalId }` — 기본 `project`. `reuse` 승인이 `scope:'reuse'`와 `until`을 정한다. **`until`은 필수이고 ISO 순간이다** — 승인 카드에 보인 날짜의 한국 시각 그날 끝(예: `2027-11-10` → `2027-11-10T14:59:59.999Z`). 운영 제안은 「마지막 납품 뒤 12개월」이지만 승인하는 순간의 값으로 굳힌다 — 마지막 사용이 늘어도 저절로 늘지 않는다. 연장 · 재개는 새 `reuse` 승인뿐. 철회(브랜드 admin)는 `scope:'project'`로 돌리고, 인물은 내 모델에 「다시 쓰기 꺼짐」으로 남는다(삭제 요청은 계속 됨).
- **상태:** 판 3 상태에 `paused`(사용 중지) · `deleting`(삭제 진행) · `deleted`(묘비)를 더한다. `PERSONA_SETTLED`에 `paused` · `deleted`를 더하고, `openPersonaProjectIds`는 `deletedAt`이 있는 인물을 상태와 상관없이 건너뛴다(판 3 후속에 기대지 않는 판 4 요구 — 묘비 뒤 90일 정리가 다시 돈다). `deleting`은 열린 것으로 둔다(삭제 도중 원 프로젝트를 정리하지 않음).
- **만료는 저장하지 않고 읽을 때 계산한다 — `ready`인 다시 쓰기 인물에만:** `effective = (status==='ready' && retention.scope==='reuse' && until <= now) ? 'expired' : status`. `paused · retired · withdrawn · deleting · deleted`는 시계가 지나도 그대로 보인다. 계산 함수는 하나(`personaUsability(persona, workspace, now)`)이고 회원 경로 · 붙이기 · 보내기 · 초대 경로 · 연결 확인 · 가드가 모두 이것만 부른다. 한 요청 안에서는 처음 읽은 `now` 하나를 쓴다.
- **「다시 쓸 수 있음」**(이 문서 전체가 이 말을 쓴다): `persona.workspaceId === W` · 브랜드 W `active` · `retention.scope==='reuse'` · W에 묶인 유효한 `reuse` 승인 · 계산한 상태 `ready` · 묘비 없음 · 쓰려는 판이 `published`이고 묘비 없음.

## 4. 경로와 권한

### 4-1. 두 증명을 잇는 법 — 목적 묶인 일회용 증표

쿠키 길(`/pulse` · `/api/customer`)을 바꾸지 않는다. 대신 PULSE 쪽에서 **5분 · 한 번 · 목적 하나**짜리 증표를 받아 고객 SYNK ID 쪽 요청 몸통에 싣는다.

```
1) PULSE 앱 → POST /pulse/api/project/workspace-proof {purpose}   (synk_pulse_session + X-Pulse-CSRF)
   서버: 세션 유효 · 프로젝트 보관 아님 · inviteHash 있음을 보고, 만료된 pulse-proof 행을 지운 뒤
   ← { proof }   // store.mint('pulse-proof', …, {purpose, projectId, inviteRevision, sessionHash}, 5분)
                 // purpose: 'workspace-claim' | 'workspace-state'
2) PULSE 앱 → POST /api/customer/pulse/claim { proof }   (synk_customer_session + X-CSRF-Token)
   ① 비동기: identity.authenticate → 몸통 읽기 → 다시 authenticate(customer-routes.mjs의 지금 꼴)
   ② 동기 트랜잭션 하나: readToken(proof) + DELETE FROM tokens WHERE hash=?(store.consume은 쓰지 않는다 — 중첩 트랜잭션)
      + 목적 · 프로젝트가 맞고 프로젝트 보관 아님 · inviteHash 있음 · inviteRevision 같음 · sessionHash의 세션이 아직 살아 있음
      + 연결 요청 기록
```

다시 쓰기 붙이기도 같은 꼴이다: `POST /pulse/api/request/persona-proof`(초안 쿠키 + CSRF, 초안 `status==='draft'`일 때만, 목적 `persona-attach`, 초안 id) → `POST /api/customer/pulse/draft-persona {proof, workspaceId, personaId, revisionId}`(①② 같은 순서, ②에서 초안이 아직 `draft`인지 다시 확인). 증표에는 세션 토큰을 담지 않고(세션 해시만), 화면 JS는 HttpOnly 쿠키를 끝까지 보지 못한다. 목적이 다르거나 · 두 번째거나 · 5분이 지났거나 · 다른 프로젝트 · 초안이거나 · 발급한 세션이 끝났으면 거절한다. 증표 발급은 주소마다 문턱(분당 몇 번)을 둔다.

### 4-2. 고객 SYNK ID 경로 `/api/customer/pulse/*`

| `POST /api/customer/pulse/draft-persona` | 다시 쓰기 붙이기(4-1) | 증표 + 그 `workspaceId`의 회원 + 그 브랜드에서 「다시 쓸 수 있음」 |
| `POST /api/customer/pulse/reuse` · `/reuse/withdraw` | 다시 쓰기 동의(처음 · 연장 · 재개) · 철회 | 브랜드 admin. 동의는 새 `reuse` 승인(처음이면 보관 대기 인물만, 재개는 관리자의 중지 풀기가 먼저 — 5-6), 철회는 `scope:'project'` |

- `customer-routes.mjs`의 「알려진 경로 여덟」은 정확 일치 목록이라, `/api/customer/pulse/`는 앞부분 일치로 PULSE 회원 처리기에 넘기고 그 처리기가 다시 정확한 꼴(`<personaId>` · `<assetId>`는 UUID)만 받는다. 질의 금지 규칙은 그대로.
- **로그인 뒤 돌아갈 곳:** `synk-id/start`의 「빈 몸통만」 검사를 「`returnTo` 하나만 있는 몸통도」로 넓힌다. `returnTo`는 `'/consultation/'` · `'/pulse-app/'` 두 문자열과 정확히 같을 때만 받고(그 밖은 `/consultation/`) 로그인 흐름(flow)에 저장한다. 콜백은 성공이면 그 값으로, **실패여도 흐름을 찾았으면 그 값 + `?login=failed`로** 302한다(흐름을 못 찾은 실패 — 서버가 로그인 도중 다시 뜬 경우 포함 — 만 지금처럼 `/consultation/?login=failed`). 저장하는 것은 허용 목록의 문자열 자체라 열린 이동이 생기지 않는다. PULSE 앱은 `?login=failed`를 `app.mjs`의 주소 지우기(`replaceState`) 앞에서 읽는다.
- **스위치를 첫 화면에도:** `pulseFeatures.publicView()`에 `myModels`(켬 여부만)를 더해 첫 화면이 「내 모델」 입구를 정할 수 있게 한다.
- 응답에 데이터셋 · 학습 파일 경로 · 내부 실패 판 · 동의 원문 · 다른 회원의 SYNK ID는 싣지 않는다(회원 이름만).

### 4-3. 초대 세션 경로(판 3 `/pulse/api/persona/*`) — 다시 쓰기 프로젝트만 넓힌다

- 원 프로젝트: 판 3 그대로(그 프로젝트에 공개한 판의 자산만).
- **다시 쓰기 프로젝트 P:** 직원이 연결을 확인해 `P.customerWorkspaceId === persona.workspaceId`가 된 뒤에만, 그 브랜드에서 「다시 쓸 수 있음」이고 **P가 참조한 판 하나**의 공개 자산을 보고 이 광고의 사용 확인(`usage`)을 할 수 있다. 참조한 판은 `castingSelection.personaRef.revisionId`가 있으면 그것, 없으면 `workspaceRequest.revisionId`다. `workspaceRequest`만 있는 동안(직원 확인 전)은 아무 자산도 열리지 않는다.
- 어느 경우에도 브랜드 목록 · 다른 판 · 다른 프로젝트 · 출처 사진 · 동의 자료는 초대 세션으로 열리지 않는다. 초대 세션의 승인 기록은 나중에 회원이 생겨도 「초대 링크로 승인」 그대로 남는다. 고객 방에는 「이 인물은 브랜드 관리자가 내 모델에서 보관을 정할 수 있고, 정하면 그 브랜드 회원들이 다음 광고에 쓸 수 있어요」 안내 한 줄을 둔다(누가 보게 되는지).

### 4-4. 직원 경로 `/api/customer-workspaces/*`

- 결정은 근거 한 줄(`note`)을 꼭 받는다 — 예: 「지정 승인자 본인이 메일 회신으로 확인」. 앱은 근거를 검증하지 않고 기록만 한다(앱 밖 확인). 모든 결정은 브랜드 `history`와 감사 기록에 남는다.
- **실제 인물의 다시 쓰기 의뢰:** `workspaceRequest`를 확인할 때 직원 화면이 새 광고의 사용 조건(브랜드 · 제품 · 매체 · 지역 · 기간)과 당사자 동의 범위를 나란히 보이고, 범위 밖이면 확인을 막고 새 당사자 동의를 요청하게 한다.
- 회원 빼기 · 프로젝트 끊기 · 브랜드 닫기는 그 즉시 `/api/customer/pulse/*`의 다음 요청부터 막힌다(캐시 없음).

### 4-5. 막아 둘 길

- **스위치 `myModels`가 꺼져 있으면:** `/api/customer/pulse/*`(동의 포함) · `/pulse/api/project/workspace-proof` · `/pulse/api/request/persona-proof`가 모두 404, 다시 쓰기 프로젝트 넓히기(4-3)가 꺼지고, 공개 의뢰서 저장 · 보내기에서 `modelChoice:'persona'`를 서버가 거절한다(첫 화면 · 의뢰서에 입구가 없다). 이미 붙은 인물(켜져 있을 때 만든 프로젝트)은 가드가 그대로 본다 — 끄는 것이 진행 중 제작을 지우지 않는다. 켰다 끈 뒤 붙임이 남은 초안을 보내면 「내 모델에서 다시 골라 주세요」 409.
- **방 안 의뢰서(`request_save` · `request_submit`)는 스위치와 상관없이 `modelChoice:'persona'`를 거절한다** — 다시 쓰기는 내 모델에서만 시작한다(붙임 없는 `persona` 프로젝트가 제작 시작에서야 막히는 막다른 길을 없앤다).

## 5. 흐름

### 5-1. 처음 연결 · 합류(한 번)

고객 방(초대 세션)이 증표(`workspace-state`)로 `project-state`를 읽어, 프로젝트가 아직 브랜드에 없거나 연결된 브랜드에 지금 로그인한 사람이 회원이 아니면 「내 모델로 모아 두기」를 보인다(로그인 전이면 로그인부터) → SYNK ID 로그인(`returnTo:'/pulse-app/'`) → 돌아온 고객 방이 증표(`workspace-claim`)를 받아 요청 → 직원 작업실 「연결 요청」 → 담당자가 앱 밖에서 이 사람이 이 프로젝트의 승인자 · 연락처인지 확인하고 근거와 함께 승인 → 브랜드 생성 또는 회원 추가(+ 프로젝트 연결). 이메일 · 회사명이 같아도 저절로 합치지 않는다.

### 5-2. 다시 쓰기 동의

판 3에서 인물이 `ready`가 되고 원 프로젝트가 브랜드 W에 연결되면 그 인물이 W의 내 모델 「보관 대기」에 나타난다(admin에게만). admin이 「브랜드 ○○의 다음 광고에도 이 인물 쓰기」를 열면 보관할 자료(기준 얼굴 · 동작 시안 · 필요한 학습 파일), 목적, 보관 끝 날짜, 철회 방법, 백업 잔존 기간을 보이고 별도 승인(`reuse`, W에 묶임)을 받는다. 그 순간 `workspaceId`가 W로 채워진다(3-4).

### 5-3. 내 모델 보기

로그인한 회원에게만: PULSE 앱 첫 화면의 「내 모델」 입구(`publicView.myModels`가 켜졌을 때), 고객 방 모델 카드, 납품 화면. 카드는 대표 그림 · 이름 · 상태(사용 가능 · 사용 중지 · 기간 끝 · 다시 쓰기 꺼짐) · 사용 범위 요약 · 보관 끝 날짜 · 마지막 사용 · 「이 모델로 의뢰」. admin은 보관 대기 카드와 동의 · 연장 · 철회 · 사용 중지 요청 · 삭제 요청도 본다. 쓸 수 없는 인물은 회색 카드와 까닭 한 줄.

### 5-4. 다시 쓰기 의뢰와 검사

「이 모델로 의뢰」 → 공개 의뢰서를 연다. 초안 쿠키가 없으면 먼저 `POST /pulse/api/request/start`로 초안을 만들고(지금 길 그대로), 있으면 그 초안을 쓴다 → 화면이 증표(`persona-attach`)를 받아 `draft-persona`로 붙인다 → 서버가 「다시 쓸 수 있음」(그 `workspaceId` 기준)을 보고 초안에 `{modelChoice:'persona'}`와 붙임 `{workspaceId, personaId, revisionId, attachedBy, attachedAt, expiresAt: attachedAt+24시간}`을 함께 쓴다 → 의뢰서는 **새 제품 · 목적 · 매체 · 지역 · 기간 · 출력 언어만** 다시 묻고 사진 칸을 열지 않는다.

- **저장:** `modelChoice:'persona'`는 서버가 `draft-persona`로만 쓴다 — 화면이 저장으로 보내면 붙임이 있을 때만 그대로 두고 없으면 거절한다. 손님이 다른 모델 선택(카탈로그 · 맞춤 · 추천 · 없음)으로 바꿔 저장하면 서버가 붙임을 지운다.
- **보내기(동기 트랜잭션):** 보내기 몸통의 `modelChoice`가 `persona`면 붙임이 꼭 있어야 하고 — 24시간 안 · `attachedBy`가 **그 `workspaceId` 브랜드의** 지금 회원 · 그 브랜드 활성 · 「다시 쓸 수 있음」 — 하나라도 어긋나면 「내 모델에서 다시 골라 주세요」(다시 로그인)로 409. 몸통이 다른 선택이면 붙임을 보지 않고 지운다.
- 새 프로젝트는 `workspaceRequest`를 달고 생기고, 담당자는 3-3대로 정한다.

**가드(`createPersonaGuard`) 조건은 한 줄이다:** 원 프로젝트(판 3 그대로) **또는** (연결 확인된 다시 쓰기 프로젝트 — `row.customerWorkspaceId === persona.workspaceId` — ∧ 「다시 쓸 수 있음」 ∧ 참조한 판 일치). 이 가드를 부르는 자리는 지금 셋(모델 없는 방향 제안 · 결제 확인 · 제작 시작)에 둘을 더한다 — 직원 연결 확인, 초대 세션의 사용 확인(`usage`). `personaRef`는 서버가 `usage` 승인 때만 붙이므로, 글 콘티 보내기는 지금처럼 `castingOf().agreed`만 본다(판 1 GA1 — 방향 · 글 콘티는 인물을 만드는 동안 먼저 맞춘다 — 그대로). 이미 제작 중인 프로젝트는 그 뒤 만료 · 중지가 와도 가드가 다시 돌지 않아 그대로 간다(진행 중 프로젝트는 직원 할 일로만 알린다).

### 5-5. 얼굴이 바뀌는 요청

새 얼굴 · 나이 · 얼굴 구조처럼 정체성이 달라지면 새 판(revision)을 만들고 기준 얼굴 · 동작 시안 승인을 다시 받는다(판 3 흐름). 옛 프로젝트는 `castingSelection.personaRef.revisionId`가 옛 판을 그대로 가리킨다. 헤어 · 착장 변형은 같은 판의 변형 자산이고 그 프로젝트의 장면 승인으로 확인한다.

### 5-6. 만료 · 사용 중지 · 철회 · 삭제

- **만료:** 읽을 때 계산(3-4, `ready`인 다시 쓰기 인물만). 새 선택 · 붙이기 · 보내기 · 연결 확인 · 사용 확인 · 제작 시작이 409로 막히고 이전 납품 이력은 그대로. 연장은 새 `reuse` 동의뿐이고, 연장하면 다시 「사용 가능」.
- **사용 중지:** 브랜드 admin(요청) 또는 직원 → 즉시 `paused`(막히는 곳은 만료와 같음, 만료 계산이 가리지 않음). 진행 중 프로젝트는 직원 할 일로 넘기고, 앱이 이미 집행 중인 광고를 취소했다고 말하지 않는다. 재개는 관리자의 중지 풀기 + 새 `reuse` 동의.
- **철회:** 브랜드 admin → `scope:'project'`. 새 다시 쓰기만 막히고 진행 중 다시 쓰기 프로젝트는 직원 할 일로.
- **삭제 — 문서 먼저, 파일 나중(결정 표 11-10, 기획 12-2의 「파일 → 묘비」를 바꿈):** 고객 요청은 직원 할 일만 만든다 → 관리자 확인 → **동기 트랜잭션 하나:** 참조 확인 — 참조는 함수 하나(`personaReferences`)가 정한다: **끝나지 않은**(보관 아님 · 최종 납품 확인 전) 프로젝트 가운데 그 인물의 원 프로젝트, `workspaceRequest.personaId`가 그 인물인 것(확인 여부와 상관없이), `castingSelection.personaRef`가 그 인물인 것, 그리고 24시간 안의 초안 붙임. 있으면 막고 목록을 보인다(납품 끝난 프로젝트는 참조만 남기고 막지 않는다). 없으면 같은 트랜잭션에서 `pulsePersonas.status='deleting'`, 출처 문서 `diskName→null` + `deletedAt`, 판 문서 `assets→[]` + `deletedAt`, 동의 암호문 지움, 지울 파일 이름은 `personaMediaOf`가 읽지 않는 칸(`pendingUnlink`)에 → 커밋 뒤 파일 지우기(없는 파일은 건너뜀) → 트랜잭션으로 `pendingUnlink` 비우고 `status:'deleted'` + `deletedAt`(이름 · 판 id만 남는 묘비).
  - 이 순서면 백업 소유 목록은 커밋 순간부터 그 파일을 세지 않는다 — `personaMediaOf`는 판 문서의 `assets:[]` + `deletedAt` 묘비를 받는 한 줄만 고치고, `deploy/ha/node-host.py` 고정 목록 · 백업 시험은 그대로다. 파일이 지워지기 전에 백업이 돌면 그 파일이 하루 더 백업에 들 뿐이다.
  - 도중에 멈추면 `status:'deleting'` + `pendingUnlink`가 남는다. **서버 시작 때 이어 하기**가 남은 이름을 지우고 묘비까지 끝내며, 직원 화면에 「삭제 이어 하기」 단추도 둔다(같은 일, 멱등).
  - 자동 영구 삭제는 보관 기간이 정해질 때까지 끈다. 백업에 남는 기간은 동의 문안에 사실대로 적는다.

### 5-7. 프로젝트 정리와 다른 자료

90일 정리 · 보관 · 초대 링크 닫기는 그 프로젝트 자료만 다룬다. 인물 파일은 판 1 소유 목록이 지키고 `retireRequest`는 돌려주지 않는다. 브랜드에 귀속된 인물은 원 프로젝트가 정리 · 보관 · 연결 끊김이 돼도 내 모델에 남고 같은 브랜드의 다른 다시 쓰기 프로젝트도 그대로 돈다(`originProjectId`는 기록으로만). 원 프로젝트의 초대 링크를 닫아도 다른 프로젝트의 참조 · 브랜드 회원 접근은 그대로다. 인물이 묘비가 되면 원 프로젝트도 다시 90일 정리 대상이 된다(3-4).

## 7. 시험

- **시나리오 5:** 고객 A의 초대 세션 · A 회원 세션 · 자산 주소로 B의 인물 목록 · 자산 · 동의를 읽는 길 0 — 특히 A 회원이 B 인물의 공개 판 `assetId`를 직접 불러도 404, 출처 사진은 어느 고객 길로도 0. 회원이 아닌 SYNK ID는 빈 목록, 남의 `personaId`로 `draft-persona` → 404, 한 사람이 두 프로젝트에 요청을 내도 서로의 프로젝트를 못 봄. 증표를 다른 목적 · 다른 프로젝트 · 다른 초안 · 두 번째로 쓰면 거절, 5분 뒤 · 발급 세션이 끝난 뒤 · `inviteRevision`이 바뀐 뒤 · 프로젝트가 보관된 뒤 거절, 보낸 초안의 증표는 거절. 직원이 `allowed()` 없는 프로젝트를 브랜드에 연결 → 403.
- **시나리오 8:** 다시 쓰기 의뢰가 사진 업로드 0 · 학습 요청 0으로 연결 확인 → 사용 확인 → 제작 시작까지 간다. 직원 방향 제안 · 글 콘티는 사용 확인 전에도 막히지 않는다. 실제 인물에서 동의 범위 밖이면 연결 확인이 막힌다. 다시 쓰기 의뢰 프로젝트의 담당자가 브랜드 담당으로 정해져 연결 확인을 한 사람이 끝낸다.
- **시나리오 9:** 만료 · 중지 · 철회 · 닫힌 브랜드 · 삭제 진행 인물은 선택 · 붙이기 · 보내기 · 연결 확인 · 사용 확인 · 제작 시작이 모두 409, 이전 납품 이력은 그대로. 중지된 인물의 보관 날짜가 지나도 `paused`로 보인다. 만료 → 새 `reuse` 동의 → 다시 사용 가능. 이미 제작 중인 프로젝트는 만료 뒤에도 그대로 간다. 보관 날짜 비교가 한국 시각 날짜 경계에서 맞다.
- **시나리오 10:** 원 프로젝트를 90일 정리 · 보관 · 초대 닫기 · 연결 끊기 한 뒤에도 브랜드 인물 파일 · 다른 프로젝트 참조가 그대로이고 내 모델에 남으며, 고객에게 새로 보이는 것 0. 브랜드 닫기 → 다시 열기 뒤 보관 대기 · 회원 접근이 돌아옴. 묘비 뒤 90일 정리가 원 프로젝트를 다시 다룸.
- **브랜드 귀속 · 교정:** A에 연결해 동의 → `workspaceId=A` → 원 프로젝트를 끊고 B에 연결해도 A 그대로, B 목록 · 보관 대기에 없음. 관리자 귀속 취소는 다시 쓰기 참조가 0이고 동의를 철회할 때만, 그 뒤 B에 연결하면 B의 보관 대기에 나타남.
- **동의 주체 · 경합:** 다시 쓰기 동의는 그 브랜드 admin만 — member · 초대 세션 · 다른 브랜드 admin은 거절, 보관 대기 그림은 그 브랜드 admin만 열림. 동의가 동시에 둘 와도 유효한 동의는 하나.
- **붙임과 모델 선택:** 붙인 뒤 카탈로그 모델로 바꿔 저장하면 붙임이 지워지고 보내기는 카탈로그로 간다. 저장 뒤 화면에서 선택을 바꿔 바로 보내도 몸통 기준으로 맞게 간다. 붙임 없이 `modelChoice:'persona'`를 저장 · 보내기 → 거절. 방 안 의뢰서에서 `persona` → 거절. 초안 쿠키 없이 「이 모델로 의뢰」 → 초안 생성 → 증표 → 붙임 순서로 끝까지.
- **삭제:** 연결 확인은 끝났고 사용 확인 전인 다시 쓰기 프로젝트가 있으면 막힘, 원 프로젝트가 제작 중이어도 막힘. 삭제 확인과 붙이기가 동시에 오면 하나만 이김. 커밋 뒤 · 파일 지우기 전에 백업을 돌려도 백업이 성공한다. 도중에 멈춘 뒤 서버를 다시 띄우면 이어서 묘비까지 끝난다.
- **동시성:** 같은 연결 요청 두 번 → 한 줄. 회원을 뺀 직후의 `models` · `draft-persona` · 보내기 → 막힘. 연결을 끊은 직후 그 프로젝트의 사용 확인 → 막힘. 초대 링크를 새로 만든 뒤의 연결 요청 승인 → 막히고 「다시 요청」 표시.
- **스위치 끔:** 4-5의 경로 · 동작이 모두 닫힘, 첫 화면 · 의뢰서에 입구 없음, 한국어 화면 바이트가 판 4 직전과 같음.
- **로그인 돌아오기:** `returnTo`가 허용 목록 밖이면 `/consultation/`, 실패 · 취소도 PULSE 앱으로 돌아오고 `?login=failed`를 주소 지우기 전에 읽음, 로그인 도중 서버가 다시 뜨면 `/consultation/?login=failed`(받아들인 한계). 설치 앱 · 휴대폰 · PC 브라우저(실물 휴대폰은 끝 보고에 미확인으로).
