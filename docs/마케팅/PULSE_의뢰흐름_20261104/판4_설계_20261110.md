# PULSE 판 4 설계 — 고객 브랜드 연결 · 내 모델 · 다시 쓰기 · 만료(2026-11-10)

> 상태: **설계 3판 — GPT · 아르곤 설계 검토와 다시 검토 반영(10절).** Fable 설계 검토는 주간 한도(11-16 12:00 KST 초기화) 뒤, 구현 전에 받는다. 구현은 판 3이 master에 오른 뒤.
> 정본 관계: [기획 12절](다국어와_고객전용인물_기획_20261108.md#12-구현-설계2026-11-09--이-절이-9·10절보다-앞선다)의 「소유권」 「권한 경계」 「보관 · 삭제」를 판 4 몫만큼 구체화한다. 판 4 범위에서 둘이 어긋나면 이 문서가 앞선다. 판 3(인물 접수 · 직원 검토 · 승인)의 문서 · 경로 · 승인 꼴은 판 3 구현을 따르고, 판 3이 이 문서의 가정과 다르게 나오면 구현 전에 이 문서를 고친다.

## 1. 지금 실물(11-10 origin 기준)

- **고객 SYNK ID 로그인**(`customer-identity.mjs`): 중앙 계정 확인을 요청마다 다시 한다(시간 캐시 없음). 사용자 id는 `synk:<UUID>`, 세션 8시간, 쿠키 `synk_customer_session`(`Path=/api/customer`, `SameSite=Lax`, HttpOnly), POST는 origin · `X-CSRF-Token` 확인. **운영에 켜져 있다** — 11-10 `GET /api/customer/me` → `loginAvailable:true`. 쓰는 곳은 상담(`/consultation/`)뿐이고, `customer-routes.mjs`는 알려진 경로 여덟 개만 받으며 콜백 뒤 성공 · 실패 모두 `/consultation/`(실패는 `?login=failed`)로 보낸다. 주소 뒤 질의(`?…`)는 막는다.
- **프로젝트 접근**(`client-projects.mjs`): 초대 링크 해시 → `pulse-session` 토큰 `{projectId, inviteRevision, csrf, openedAt}`(720분), 기억한 기기 · 메일 코드 다시 열기(`acceptedInvite`). PULSE 쿠키는 `synk_pulse_session` · `synk_pulse_request` · `synk_pulse_device`이고 모두 **`Path=/pulse`, `SameSite=Strict`**, HttpOnly다. 초안 쿠키는 14일간 남는다. `ownerId`는 직원 담당자다.
- **두 쿠키는 길이 겹치지 않는다:** 고객 SYNK ID 쿠키는 `/pulse/*`로 가지 않고, PULSE 쿠키는 `/api/customer/*`로 가지 않는다. 한 요청에서 「이 프로젝트에 들어온 사람」과 「이 SYNK ID 회원」을 함께 증명하는 길이 지금은 없다 — 판 4 설계의 첫 문제다.
- **인물**(판 1 · 판 3): `PERSONA_KINDS`에 `customerWorkspaces`까지 이름이 있다. `createPersonaGuard`는 지금 `persona.originProjectId === row.id`만 통과시킨다(「고객 브랜드로 넓히는 것은 판 4」 주석). `PERSONA_SETTLED`는 `ready · retired · expired · withdrawn`이고, 그 밖의 상태(모르는 값 포함)인 인물이 있는 원 프로젝트는 90일 정리에서 빠진다. 스위치 `myModels`는 기본 끔.

## 3. 데이터

### 3-1. 고객 브랜드 `customerWorkspaces`

```
{ id, name,                      // name은 표시용. 맞추기에 쓰지 않는다
  status: 'active' | 'closed', closedAt, closedBy,
  staffOwnerId,                  // 이 브랜드를 맡은 직원(관리자는 모두 가능)
  members: [{ synkUserId, displayName, role: 'admin' | 'member',
              addedAt, addedBy, via: { claimId } | { staffNote } }],
  revision, createdAt, createdBy, history: [...] }   // 덧붙이기만, 최근 200줄
```

- 회원은 중앙 SYNK ID 사용자(`synkUserId` UUID)만이다. 이메일 칸은 두지 않는다.
- 역할은 둘로 시작한다. **admin** — 내 모델 보기 · 다시 쓰기 · 다시 쓰기 동의(처음 · 연장 · 재개) · 철회 · 사용 중지 · 삭제 요청. **member** — 내 모델 보기 · 다시 쓰기 의뢰 시작. 다시 쓰기 동의는 브랜드에 자산을 남기는 결정이라 **브랜드 admin만**(SYNK ID 로그인) 한다. 프로젝트 승인(얼굴 · 동작 · 사용 · 최종 영상)은 지금처럼 그 프로젝트 승인자가 초대 세션으로 한다 — 브랜드 역할이 프로젝트 승인권을 만들지 않고, 프로젝트 승인자가 브랜드 동의를 대신하지도 않는다.
- **닫힌 브랜드:** `status:'closed'`면 회원 경로가 그 브랜드를 없는 것처럼 다루고(목록 · 상세 · 그림 · 붙이기 · 보내기 모두), 가드(5-4)가 그 브랜드에 기대는 사용을 막는다. 인물 문서 · `workspaceId`는 그대로 남는다(기록). 닫는 순간 그 브랜드 인물을 쓰는 진행 중 프로젝트마다 직원 할 일이 생긴다. 다시 여는 것은 관리자만.
- 대행사가 여러 고객을 맡으면 고객 브랜드마다 따로 만든다. 한 사람이 여러 브랜드의 회원일 수 있다.

### 3-2. 연결 요청 `pulseWorkspaceClaims`(새 문서 종류)

```
{ id, projectId, synkUserId, displayName,
  kind: 'link' | 'join',          // link: 프로젝트가 아직 브랜드에 없음, join: 이미 연결된 브랜드에 회원으로 들어가기
  status: 'pending' | 'approved' | 'rejected' | 'withdrawn',
  createdAt, decidedAt, decidedBy, workspaceId, note }
```

- 같은 프로젝트 · 같은 사람의 `pending`은 하나만(두 번 눌러도 같은 줄). 결정된 줄은 지우지 않는다.
- 전이: `pending → approved | rejected`(직원, 4-4), `pending → withdrawn`(요청한 본인이 `/api/customer/pulse/claim/withdraw`로, 또는 그 프로젝트가 보관 · 초대 링크가 새로 만들어지면 서버가). 결정된 줄은 다시 바뀌지 않는다.
- 문서뿐이라 파일 소유 목록(`workspace-media.mjs`)은 바뀌지 않는다. DB 백업에 그대로 든다.

### 3-3. 프로젝트 쪽

- `clientProjects.customerWorkspaceId`(선택): **직원 행동으로만** 붙이고 뗀다(프로젝트 기록 한 줄, 4-4 권한). 손님이 보내는 값으로 정하지 않는다.
- `clientProjects.workspaceRequest`(선택, 다시 쓰기 의뢰가 만든 프로젝트만): `{workspaceId, personaId, revisionId, attachedBy: synkUserId, attachedAt, confirmedAt, confirmedBy}` — 담당자가 접수 때 확인하면(4-4) `customerWorkspaceId`로 옮겨 적고 `confirmedAt` · `confirmedBy`를 더한다. **확인 뒤에도 지우지 않는다** — 사용 확인 전 단계의 참조로 삭제 검사(5-6)가 이것을 본다. 확인 전에는 초대 세션에 인물 자산이 열리지 않는다(4-3).

### 3-4. 인물 쪽(판 3 문서에 더하기만)

- **브랜드 귀속 `pulsePersonas.workspaceId`:** null로 태어난다(판 3). **한 번 채워지면 바뀌지도 지워지지도 않는다** — 브랜드 사이에 옮기는 길은 없다. 채우는 때는 하나뿐이다: 원 프로젝트가 직원 행동으로 브랜드 W에 연결돼 있고, 그 인물에 **W에 묶인** 다시 쓰기 동의(`reuse` 승인, 아래)가 있을 때. 원 프로젝트의 연결을 나중에 끊거나 다른 브랜드에 다시 연결해도 `workspaceId`는 W 그대로다(원 프로젝트는 기록일 뿐 — 5-7).
- **다시 쓰기 동의 `reuse` 승인**(판 3 `pulsePersonaApprovals` 꼴 그대로): `{personaId, revisionId, workspaceId, terms: {보관 자료, 목적, until, 철회 방법, 백업 잔존 기간}, termsHash, by: synkUserId, authMethod: 'synk-member', at}`. `viewedHash`에 브랜드 이름 · 보관 문안 해시를 넣는다. **그 브랜드의 admin만 내 모델의 「보관 대기」에서 승인한다**(5-2) — 원 프로젝트가 브랜드 W에 연결돼 있어야 그 인물이 W의 「보관 대기」에 나타나므로 브랜드 없이 받은 동의는 없다. 초대 세션으로는 받지 않는다. 실제 인물이면 당사자 동의(판 3 `pulsePersonaConsents`)의 범위에 다시 쓰기가 들어 있어야 받는다.
- **보관 `pulsePersonas.retention`:** `{ scope: 'project' | 'reuse', until, reuseApprovalId }` — 기본 `project`. `reuse` 승인이 `scope:'reuse'`와 `until`을 정한다. `until`은 승인 카드에 날짜로 보인 값 그대로다(운영 제안은 「마지막 납품 뒤 12개월」이지만 승인하는 순간의 날짜로 굳힌다 — 마지막 사용이 늘어도 저절로 늘지 않는다). 연장 · 재개는 새 `reuse` 승인뿐. 철회(브랜드 admin)는 `scope:'project'`로 돌리고, 인물은 내 모델에 「다시 쓰기 꺼짐」으로 남는다(이력 · 삭제 요청은 계속 됨).
- **상태:** 판 3 상태에 `paused`(사용 중지)와 `deleting`(삭제 진행)을 더한다. `PERSONA_SETTLED`에 `paused`를 더하고(검토 끝난 인물), `deleting`은 열린 것으로 둔다(정리가 원 프로젝트를 건너뜀 — 자료를 남기는 쪽).
- **만료는 저장하지 않고 읽을 때 계산한다 — `ready`인 다시 쓰기 인물에만:** `effective = (status==='ready' && retention.scope==='reuse' && until <= now) ? 'expired' : status`. `paused · retired · withdrawn · deleting`은 시계가 지나도 그대로 보인다. 계산 함수는 하나(`personaUsability(persona, workspace, now)`)이고 회원 경로 · 붙이기 · 보내기 · 초대 경로 · 가드가 모두 이것만 부른다. 한 요청 안에서는 처음 읽은 `now` 하나를 쓴다.
- **다시 쓸 수 있음**의 정의(이 문서 전체가 이 말을 쓴다): `persona.workspaceId === W` · 브랜드 W `active` · `retention.scope==='reuse'` · W에 묶인 철회 안 된 `reuse` 승인 · 계산한 상태 `ready` · 묘비 없음 · 쓰려는 판이 `published`이고 묘비 없음.

## 4. 경로와 권한

### 4-1. 두 증명을 잇는 법 — 목적 묶인 일회용 증표

쿠키 길(`/pulse` · `/api/customer`)을 바꾸지 않는다. 대신 PULSE 쪽에서 **5분 · 한 번 · 목적 하나**짜리 증표를 받아 고객 SYNK ID 쪽 요청 몸통에 싣는다.

```
1) PULSE 앱 → POST /pulse/api/project/workspace-proof   (synk_pulse_session + X-Pulse-CSRF)
   서버: 세션 유효 · 프로젝트 보관 아님 · inviteHash 있음을 보고
   ← { proof }   // store.mint('pulse-proof', …, {purpose:'workspace-claim', projectId, inviteRevision}, 5분)
2) PULSE 앱 → POST /api/customer/pulse/claim { proof }   (synk_customer_session + X-CSRF-Token)
   서버(한 트랜잭션): 고객 세션 중앙 확인 → proof 읽고 그 자리에서 소모 → 목적 · 프로젝트가 맞고,
   프로젝트가 보관 아님 · inviteHash 있음 · inviteRevision이 지금 값과 같을 때만 연결 요청 기록
```

다시 쓰기 붙이기도 같은 꼴이다: `POST /pulse/api/request/persona-proof`(초안 쿠키 + CSRF, 초안 `status==='draft'`일 때만) → `{proof}`(목적 `persona-attach`, 초안 id) → `POST /api/customer/pulse/draft-persona {proof, workspaceId, personaId, revisionId}`(한 트랜잭션에서 소모 · 초안이 아직 `draft`인지 다시 확인). 증표에는 세션 토큰을 담지 않고, 화면 JS는 HttpOnly 쿠키를 끝까지 보지 못한다. 목적이 다르거나 · 두 번째거나 · 5분이 지났거나 · 다른 프로젝트 · 초안이면 거절한다.

### 4-2. 고객 SYNK ID 경로 `/api/customer/pulse/*`

| 경로 | 하는 일 | 확인 |
|---|---|---|
| `GET /api/customer/pulse/models` | 내가 회원인 **활성** 브랜드들의 내 모델 카드(브랜드별). admin에게는 「보관 대기」(원 프로젝트가 그 브랜드에 연결됐고 `ready`인데 아직 `workspaceId`가 없는 인물)도 | 요청마다 회원 목록 · 역할 · 브랜드 상태를 다시 읽는다 |
| `GET /api/customer/pulse/models/<personaId>` | 상세 — 승인 이력(종류 · 판 · 날짜 · 승인 방식), 이 브랜드에 연결된 사용 프로젝트, 변형 | 회원 + 활성 브랜드 + `persona.workspaceId`가 그 브랜드 + 묘비 아님 |
| `GET /api/customer/pulse/asset/<assetId>` | 카드 · 상세의 그림 | **사슬로 확인:** 자산 → 그 자산을 가진 판(`published` · 묘비 아님) → 그 판의 인물(묘비 아님) → `persona.workspaceId`가 요청자가 회원인 **활성** 브랜드, 또는 (「보관 대기」) `workspaceId`가 비었고 원 프로젝트의 `customerWorkspaceId`가 요청자가 **admin**인 활성 브랜드. 하나라도 어긋나면 404. `Cache-Control: private, no-store` |
| `POST /api/customer/pulse/claim` · `/claim/withdraw` | 연결 · 합류 요청(4-1), 내 요청 철회 | 증표 + 고객 세션 / 본인 요청만 |
| `POST /api/customer/pulse/draft-persona` | 다시 쓰기 붙이기(4-1) | 증표 + 그 `workspaceId`의 회원 + 그 브랜드에서 「다시 쓸 수 있음」 |
| `POST /api/customer/pulse/reuse` · `/reuse/withdraw` | 다시 쓰기 동의(처음 · 연장 · 재개) · 철회 | 브랜드 admin. 동의는 새 `reuse` 승인(`authMethod:'synk-member'`, 처음이면 「보관 대기」 인물만), 재개는 관리자 확인이 먼저(5-6), 철회는 `scope:'project'` |
| `POST /api/customer/pulse/stop` | 사용 중지 요청 — 즉시 `paused` | 브랜드 admin |
| `POST /api/customer/pulse/delete-request` | 삭제 요청(직원 할 일만 만든다) | 브랜드 admin |

- `customer-routes.mjs`의 「알려진 경로 여덟」은 정확 일치 목록이라, `/api/customer/pulse/`는 앞부분 일치로 PULSE 회원 처리기에 넘기고 그 처리기가 다시 정확한 꼴(`<personaId>` · `<assetId>`는 UUID)만 받는다. 질의 금지 규칙은 그대로.
- **로그인 뒤 돌아갈 곳:** `synk-id/start` 몸통에 `returnTo`(허용 목록 `'/consultation/'` · `'/pulse-app/'` 두 문자열과 정확히 같을 때만, 그 밖은 `/consultation/`)를 받아 로그인 흐름(flow)에 저장한다. 콜백은 성공이면 그 값으로, **실패여도 흐름을 찾았으면 그 값 + `?login=failed`로** 302한다(흐름을 못 찾은 실패만 지금처럼 `/consultation/?login=failed`). 저장하는 것은 허용 목록의 문자열 자체라 열린 이동이 생기지 않는다. 콜백 주소의 허용 질의(state · code · error)는 그대로다.
- 응답에 데이터셋 · 학습 파일 경로 · 내부 실패 판 · 동의 원문 · 다른 회원의 SYNK ID는 싣지 않는다(회원 이름만).

### 4-3. 초대 세션 경로(판 3 `/pulse/api/persona/*`) — 다시 쓰기 프로젝트만 넓힌다

- 원 프로젝트: 판 3 그대로(그 프로젝트에 공개한 판의 자산만).
- **다시 쓰기 프로젝트 P:** 직원이 연결을 확인해 `P.customerWorkspaceId === persona.workspaceId`가 된 뒤에만, 그 브랜드에서 「다시 쓸 수 있음」이고 **P가 참조한 판 하나**(`workspaceRequest.revisionId` 또는 `castingSelection.personaRef.revisionId`)의 공개 자산을 보고 이 광고의 사용 확인(`usage`)을 할 수 있다. `workspaceRequest`만 있는 동안(직원 확인 전)은 아무 자산도 열리지 않는다.
- 어느 경우에도 브랜드 목록 · 다른 판 · 다른 프로젝트 · 원본 사진 · 동의 자료는 초대 세션으로 열리지 않는다. 초대 세션의 승인 기록은 나중에 회원이 생겨도 「초대 링크로 승인」 그대로 남는다.

### 4-4. 직원 경로 `/api/customer-workspaces/*`

| 일 | 권한(모두 쓰기 권한 `current(user,true)` 위에서) |
|---|---|
| 연결 · 합류 요청 결정(새 브랜드 만들기 / 기존 브랜드에 회원 추가 + 프로젝트 연결 / 거절) | 요청 프로젝트에 `allowed()` + (기존 브랜드면) 그 브랜드 `staffOwnerId` 또는 관리자 |
| 프로젝트 연결 · 끊기, 다시 쓰기 의뢰의 `workspaceRequest` 확인 | **그 프로젝트에 `allowed()`** + 브랜드 `staffOwnerId` 또는 관리자 — 둘 다 |
| 회원 역할 바꾸기 · 빼기, 브랜드 닫기 | 브랜드 `staffOwnerId` 또는 관리자 |
| 사용 중지 풀기 · 삭제 실행 · 브랜드 다시 열기 | 관리자 |

- 결정은 근거 한 줄(`note`)을 꼭 받는다 — 예: 「지정 승인자 본인이 메일 회신으로 확인」. 앱은 근거를 검증하지 않고 기록만 한다(앱 밖 확인). 모든 결정은 브랜드 `history`와 감사 기록에 남는다.
- **실제 인물의 다시 쓰기 의뢰:** `workspaceRequest`를 확인할 때 직원 화면이 새 광고의 사용 조건(브랜드 · 제품 · 매체 · 지역 · 기간)과 당사자 동의 범위를 나란히 보이고, 범위 밖이면 확인을 막고 새 당사자 동의를 요청하게 한다.
- 회원 빼기 · 프로젝트 끊기 · 브랜드 닫기는 그 즉시 `/api/customer/pulse/*`의 다음 요청부터 막힌다(캐시 없음).

### 4-5. 스위치 `myModels`가 꺼져 있으면

`/api/customer/pulse/*`(다시 쓰기 동의 포함) · `/pulse/api/project/workspace-proof` · `/pulse/api/request/persona-proof`가 모두 404, 다시 쓰기 프로젝트 넓히기(4-3)가 꺼지고, 의뢰서 저장 · 보내기에서 `modelChoice:'persona'`를 서버가 거절한다(화면에는 입구가 없다). 이미 붙은 인물(켜져 있을 때 만든 프로젝트)은 가드가 그대로 본다 — 끄는 것이 진행 중 제작을 지우지 않는다.

## 5. 흐름

### 5-1. 처음 연결 · 합류(한 번)

고객 방(초대 세션)에서 「내 모델로 모아 두기」 — 프로젝트가 아직 브랜드에 없거나, 연결된 브랜드에 지금 로그인한 사람이 회원이 아닐 때 보인다 → SYNK ID 로그인(`returnTo:'/pulse-app/'`) → 돌아온 고객 방이 증표를 받아 연결(`link`) · 합류(`join`) 요청 → 직원 작업실 「연결 요청」 → 담당자가 앱 밖에서 이 사람이 이 프로젝트의 승인자 · 연락처인지 확인하고 근거와 함께 승인 → 브랜드 생성 또는 회원 추가(+ 프로젝트 연결). 이메일 · 회사명이 같아도 저절로 합치지 않는다.

### 5-2. 다시 쓰기 동의

판 3에서 인물이 `ready`가 되고 **원 프로젝트가 브랜드 W에 연결되면** 그 인물이 W의 내 모델 「보관 대기」에 나타난다(admin에게만). admin이 「브랜드 ○○의 다음 광고에도 이 인물 쓰기」를 열면 보관할 자료(기준 얼굴 · 동작 시안 · 필요한 학습 파일), 목적, 보관 끝 날짜, 철회 방법, 백업 잔존 기간을 보이고 별도 승인(`reuse`, W에 묶임, `authMethod:'synk-member'`)을 받는다. 그 순간 `workspaceId`가 W로 채워진다(3-4). 고객 방(초대 세션)에는 「브랜드 관리자가 내 모델에서 보관을 정할 수 있어요」 안내 한 줄만 둔다.

### 5-3. 내 모델 보기

로그인한 회원에게만: PULSE 앱 첫 화면의 「내 모델」 입구, 고객 방 모델 카드, 납품 화면. 카드는 대표 그림 · 이름 · 상태(사용 가능 · 사용 중지 · 기간 끝 · 다시 쓰기 꺼짐) · 사용 범위 요약 · 보관 끝 날짜 · 「이 모델로 의뢰」만 먼저 보이고, 상세에서 승인 이력 · 사용 프로젝트 · 변형 · 사용 중지 요청 · (admin) 연장 · 철회 · 삭제 요청을 본다. 쓸 수 없는 인물은 회색 카드와 까닭 한 줄.

### 5-4. 다시 쓰기 의뢰와 단계별 검사

「이 모델로 의뢰」 → 공개 의뢰서를 연다. 초안 쿠키가 없으면 먼저 `POST /pulse/api/request/start`로 초안을 만들고(지금 길 그대로), 있으면 그 초안을 쓴다 → 화면이 증표를 받아(`persona-proof`, 초안이 `draft`일 때만) `draft-persona`로 붙인다 → 서버가 「다시 쓸 수 있음」(그 `workspaceId` 기준)을 보고 초안에 `{modelChoice:'persona'}`와 붙임 `{workspaceId, personaId, revisionId, attachedBy, attachedAt, expiresAt: attachedAt+24시간}`을 함께 쓴다 → 의뢰서는 **새 제품 · 목적 · 매체 · 지역 · 기간 · 출력 언어만** 다시 묻고 사진 칸을 열지 않는다.

- **저장:** `modelChoice:'persona'`는 서버가 `draft-persona`로만 쓴다 — 화면이 저장으로 보내면 붙임이 있을 때만 그대로 두고 없으면 거절한다. 손님이 다른 모델 선택(카탈로그 · 맞춤 · 추천 · 없음)으로 바꿔 저장하면 서버가 붙임을 지운다.
- **보내기(한 트랜잭션, `modelChoice==='persona'`일 때만):** 붙임이 있고 24시간 안 · `attachedBy`가 **그 `workspaceId` 브랜드의** 지금 회원 · 그 브랜드 활성 · 「다시 쓸 수 있음」. 하나라도 어긋나면 「내 모델에서 다시 골라 주세요」(다시 로그인)로 409. 다른 모델 선택이면 붙임을 보지 않는다(이미 지워져 있다).
- 새 프로젝트는 `workspaceRequest`를 달고 생긴다.

단계별로 보는 것을 나눈다(가드가 한 줄 조건으로 직원 일을 막지 않게):

| 단계 | 누가 | 보는 것 |
|---|---|---|
| 연결 확인(`workspaceRequest` → `customerWorkspaceId`) | 직원(4-4 권한) | 「다시 쓸 수 있음」 + (실제 인물) 동의 범위 대조 |
| 직원 인물 지정 · 방향 제안(모델 없이) | 직원 | 연결된 브랜드 = `persona.workspaceId` + 「다시 쓸 수 있음」 |
| 이 광고의 사용 확인(`usage`) | 새 프로젝트 승인자(초대 세션, 4-3) | 위와 같음 + 보인 사용 조건 해시 — 승인되면 서버가 `castingSelection.personaRef`를 붙인다 |
| 글 콘티 보내기 · 제작 시작(`approve_draft`) | 직원 · 손님 | 위와 같음 + **이 프로젝트의 `usage` 승인이 있고 그 판이 `personaRef`의 판과 같음** |

`createPersonaGuard`는 이 표의 단계 이름을 받아 원 프로젝트 조건(판 3 그대로) **또는** 표의 조건을 본다.

### 5-5. 얼굴이 바뀌는 요청

새 얼굴 · 나이 · 얼굴 구조처럼 정체성이 달라지면 새 판(revision)을 만들고 기준 얼굴 · 동작 시안 승인을 다시 받는다(판 3 흐름). 옛 프로젝트는 `castingSelection.personaRef.revisionId`가 옛 판을 그대로 가리킨다. 헤어 · 착장 변형은 같은 판의 변형 자산이고 그 프로젝트의 장면 승인으로 확인한다.

### 5-6. 만료 · 사용 중지 · 철회 · 삭제

- **만료:** 읽을 때 계산(3-4, `ready`인 다시 쓰기 인물만). 새 선택 · 붙이기 · 보내기 · 연결 확인 · 사용 확인 · 글 콘티 · 제작 시작이 409로 막히고 이전 납품 이력은 그대로. 연장은 새 `reuse` 동의뿐.
- **사용 중지:** 브랜드 admin 또는 직원 → 즉시 `paused`(막히는 곳은 만료와 같음, 만료 계산이 가리지 않음). 진행 중 프로젝트는 직원 할 일로 넘기고, 앱이 이미 집행 중인 광고를 취소했다고 말하지 않는다. 재개는 관리자 확인 + 새 `reuse` 동의.
- **철회:** 브랜드 admin → `scope:'project'`. 새 다시 쓰기만 막히고 진행 중 다시 쓰기 프로젝트는 직원 할 일로.
- **삭제(멱등 · 이어 하기 가능):** 고객 요청은 직원 할 일만 만든다 → 관리자 확인 → **한 트랜잭션:** 참조 확인 — 참조는 함수 하나(`personaReferences`)가 정한다: **끝나지 않은**(보관 아님 · 최종 납품 확인 전) 프로젝트 가운데 그 인물의 원 프로젝트, `workspaceRequest.personaId`가 그 인물인 것(확인 여부와 상관없이 — 연결 확인 뒤 사용 확인 전 단계 포함), `castingSelection.personaRef`가 그 인물인 것, 그리고 24시간 안의 초안 붙임. 있으면 막고 목록을 보인다(납품 끝난 프로젝트는 참조만 남기고 막지 않는다), 없으면 `status:'deleting'` + 삭제 작업 기록(이 순간부터 가드 · 붙이기 · 보내기 · 연결 확인 · 사용 확인이 막힌다) → 파일 지우기(원본 · 파생, 없는 파일은 건너뜀) → 동의 암호문 · 출처 문서 정리 → 묘비(`deletedAt`, 이름 · 판 id만). 도중에 멈추면 `deleting`이 남아 같은 작업을 이어 한다. 백업 소유 목록(`workspace-media.mjs`)은 `deleting` 인물의 파일을 「지우는 중」으로 건너뛴다(없는 파일 때문에 백업이 멈추지 않게). 자동 영구 삭제는 보관 기간이 정해질 때까지 끈다. 백업에 남는 기간은 동의 문안에 사실대로 적는다.

### 5-7. 프로젝트 정리와 다른 자료

90일 정리 · 보관 · 초대 링크 닫기는 그 프로젝트 자료만 다룬다. 인물 파일은 판 1 소유 목록이 지키고 `retireRequest`는 돌려주지 않는다. 브랜드에 귀속된 인물은 원 프로젝트가 정리 · 보관 · 연결 끊김이 돼도 내 모델에 남고 같은 브랜드의 다른 다시 쓰기 프로젝트도 그대로 돈다(`originProjectId`는 기록으로만). 원 프로젝트의 초대 링크를 닫아도 다른 프로젝트의 참조 · 브랜드 회원 접근은 그대로다.

## 6. 화면

- **PULSE 앱:** 「내 모델」 입구 셋(5-3), 카드 · 상세 · 사용 중지 · 연장 · 철회 · 삭제 요청, admin의 「보관 대기」와 「브랜드 ○○의 다음 광고에도 이 인물 쓰기」 동의, 의뢰서 모델 단계의 「내 모델 다시 쓰기」(판 3이 둔 자리), 고객 방의 「내 모델로 모아 두기」와 보관 안내 한 줄. 새 글은 `t()` 사전, 영어 문안은 세 겹(역번역 Opus → Fable → 아르곤).
- **직원 작업실:** 연결 · 합류 요청 목록(다음 행동 한 줄 먼저), 브랜드(회원 · 연결 프로젝트 · 인물 · 기록), 다시 쓰기 의뢰 연결 확인(실제 인물은 동의 범위 대조), 인물의 만료 · 중지 · 철회 · 삭제 표시와 삭제 진행.
- **설치 앱:** 같은 화면을 쓴다. 로그인 창을 앱 안에서 열 때 `returnTo` 흐름이 성공 · 실패 모두 설치 앱으로 돌아오는지 확인한다(PC 앱은 `workspace.synk.im/pulse-app/`을 연다).

## 7. 시험

- **시나리오 5:** 고객 A의 초대 세션 · A 회원 세션 · 자산 주소로 B의 인물 목록 · 자산 · 동의를 읽는 길 0 — 특히 A 회원이 B 인물의 공개 판 `assetId`를 직접 불러도 404. 회원이 아닌 SYNK ID는 빈 목록, 남의 `personaId`로 `draft-persona` → 404. 증표를 다른 목적 · 다른 프로젝트 · 다른 초안 · 두 번째로 쓰면 거절, 5분 뒤 거절, `inviteRevision`이 바뀌거나 프로젝트가 보관되면 거절, 보낸 초안의 증표는 거절. 직원이 `allowed()` 없는 프로젝트를 브랜드에 연결 → 403.
- **시나리오 8:** 다시 쓰기 의뢰가 사진 업로드 0 · 학습 요청 0으로 연결 확인 → 사용 확인 → 제작 시작까지 간다. 직원 방향 제안은 사용 확인 전에도 막히지 않는다.
- **시나리오 9:** 만료 · 중지 · 철회 · 닫힌 브랜드 · 삭제 진행 인물은 선택 · 붙이기 · 보내기 · 연결 확인 · 사용 확인 · 글 콘티 · 제작 시작이 모두 409, 이전 납품 이력은 그대로. 중지된 인물의 보관 날짜가 지나도 `paused`로 보인다.
- **시나리오 10:** 원 프로젝트를 90일 정리 · 보관 · 초대 닫기 · 연결 끊기 한 뒤에도 브랜드 인물 파일 · 다른 프로젝트 참조가 그대로이고 내 모델에 남으며, 고객에게 새로 보이는 것 0.
- **브랜드 귀속:** A에 연결해 동의 → `workspaceId=A` → 원 프로젝트를 끊고 B에 연결해도 A 그대로, B 목록 · 「보관 대기」에 나타나지 않음.
- **동의 주체:** 다시 쓰기 동의는 브랜드 admin만 — member · 초대 세션 · 다른 브랜드 admin은 거절, 「보관 대기」 그림은 그 브랜드 admin만 열림.
- **붙임과 모델 선택:** 붙인 뒤 카탈로그 모델로 바꿔 저장하면 붙임이 지워지고 보내기는 카탈로그로 간다. 붙임 없이 `modelChoice:'persona'`를 저장 · 보내기 → 거절. 초안 쿠키 없이 「이 모델로 의뢰」 → 초안 생성 → 증표 → 붙임 순서로 끝까지.
- **삭제 참조:** 연결 확인은 끝났고 사용 확인 전인 다시 쓰기 프로젝트가 있으면 삭제가 막힌다. 원 프로젝트가 제작 중이어도 막힌다.
- **동시성 · 경합:** 같은 연결 요청 두 번 → 한 줄. 회원을 뺀 직후의 `models` · `draft-persona` · 보내기 → 막힘. 연결을 끊은 직후 그 프로젝트의 사용 확인 → 막힘. 붙인 뒤 만료 시각이 지나거나 24시간이 지나면 보내기 409. 삭제 확인과 붙이기가 동시에 오면 하나만 이긴다(삭제가 이기면 붙이기 409, 붙이기가 이기면 삭제가 참조 목록을 보이며 멈춤). 삭제 도중 멈춘 뒤 다시 실행하면 이어서 끝난다.
- **스위치 끔:** 4-5의 경로 · 동작이 모두 닫힘, 화면 입구 없음, 한국어 화면 바이트가 판 4 직전과 같음.
- **로그인 돌아오기:** `returnTo`가 허용 목록 밖이면 `/consultation/`, 실패 · 취소도 PULSE 앱으로 돌아옴, 설치 앱 · 휴대폰 · PC 브라우저(실물 휴대폰은 끝 보고에 미확인으로).
