# PULSE 판 4 설계 — 고객 브랜드 연결 · 내 모델 · 다시 쓰기 · 만료(2026-11-10)

> 상태: **설계 초안 → Fable 설계 검토 전.** 검토를 거쳐 확정하면 판 3이 master에 오른 뒤 구현한다.
> 정본 관계: [기획 12절](다국어와_고객전용인물_기획_20261108.md#12-구현-설계2026-11-09--이-절이-9·10절보다-앞선다)의 「소유권」 「권한 경계」 「보관 · 삭제」를 판 4 몫만큼 구체화한다. 판 4 범위에서 둘이 어긋나면 이 문서가 앞선다. 판 3(인물 접수 · 직원 검토 · 승인)의 문서 · 경로 · 승인 꼴은 판 3 구현을 따른다.
> 기획 10절 시나리오 중 5 · 8 · 9 · 10을 맡는다.

## 1. 지금 실물(11-10 origin 기준)

- **고객 SYNK ID 로그인**(`customer-identity.mjs`): 중앙 계정 확인을 요청마다 다시 한다(시간 캐시 없음). 사용자 id는 `synk:<UUID>`, 세션 8시간, 쿠키 `synk_customer_session`(`Path=/api/customer`, `SameSite=Lax`, HttpOnly), POST는 origin · `X-CSRF-Token` 확인. **운영에 켜져 있다** — 11-10 `GET /api/customer/me` → `loginAvailable:true`. 쓰는 곳은 상담(`/consultation/`)뿐이고, `customer-routes.mjs`는 알려진 경로 여덟 개만 받으며 콜백 뒤 `/consultation/`으로 고정해 보낸다. 주소 뒤 질의(`?…`)는 막는다.
- **프로젝트 접근**(`client-projects.mjs`): 초대 링크 해시 → `pulse-session` 토큰 `{projectId, inviteRevision, csrf, openedAt}`(720분), 기억한 기기 · 메일 코드 다시 열기(`acceptedInvite`). PULSE 쿠키는 `synk_pulse_session` · `synk_pulse_request` · `synk_pulse_device`이고 모두 **`Path=/pulse`, `SameSite=Strict`**, HttpOnly다. `ownerId`는 직원 담당자다.
- **두 쿠키는 길이 겹치지 않는다:** 고객 SYNK ID 쿠키는 `/pulse/*`로 가지 않고, PULSE 쿠키는 `/api/customer/*`로 가지 않는다. 한 요청에서 「이 프로젝트에 들어온 사람」과 「이 SYNK ID 회원」을 함께 증명하는 길이 지금은 없다 — 판 4 설계의 첫 문제다.
- **인물**(판 1 · 판 3): `PERSONA_KINDS`에 `customerWorkspaces`까지 이름이 있다. `createPersonaGuard`는 지금 `persona.originProjectId === row.id`만 통과시킨다(「고객 브랜드로 넓히는 것은 판 4」 주석). 스위치 `myModels`는 기본 끔.

## 2. 범위

| 판 4가 하는 것 | 하지 않는 것 |
|---|---|
| 고객 브랜드(`customerWorkspaces`)와 회원, 직원이 확인한 연결 | 이메일 · 회사명 일치로 자산 합치기 |
| 프로젝트 ↔ 브랜드 연결(직원 행동) | `ownerId`의 뜻 바꾸기(직원 담당자 그대로) |
| 「내 모델」 목록 · 상세 · 「이 모델로 의뢰」 | 공개 캐스팅북에 전용 인물 올리기 |
| 다시 쓰기 의뢰(사진 다시 올리기 · 다시 학습 없이) | 결제 · 가격 · 해외 통화 |
| 다시 쓰기 동의, 만료 · 사용 중지 · 삭제 요청 | 자동 영구 삭제(보관 기간 결정 전까지 끔) |
| 프로젝트 정리가 브랜드 인물을 건드리지 않음 | 고객에게 새 알림을 실제로 보내기(통로는 기존 것, 스위치 끔) |

## 3. 데이터

### 3-1. 고객 브랜드 `customerWorkspaces`

```
{ id, name,                      // name은 표시용. 맞추기에 쓰지 않는다
  status: 'active' | 'closed',
  staffOwnerId,                  // 이 브랜드를 맡은 직원(관리자는 모두 가능)
  members: [{ synkUserId, displayName, role: 'admin' | 'member',
              addedAt, addedBy, via: { claimId } | { staffNote } }],
  revision, createdAt, createdBy, history: [...] }   // 덧붙이기만, 최근 200줄
```

- 회원은 중앙 SYNK ID 사용자(`synkUserId` UUID)만이다. 이메일 칸은 두지 않는다.
- 역할은 둘로 시작한다. **admin** — 내 모델 보기 · 다시 쓰기 · 사용 중지 · 삭제 요청 · 다시 쓰기 동의. **member** — 내 모델 보기 · 다시 쓰기 의뢰 시작. 프로젝트 승인(얼굴 · 동작 · 사용 · 최종 영상)은 지금처럼 그 프로젝트 승인자가 초대 세션으로 한다 — 브랜드 역할이 프로젝트 승인권을 만들지 않는다.
- 대행사가 여러 고객을 맡으면 고객 브랜드마다 따로 만든다. 한 사람이 여러 브랜드의 회원일 수 있고, 브랜드 사이에 인물을 옮기는 길은 두지 않는다(옮기려면 새 사용 권한 확인 → 직원 처리, 판 4 밖).

### 3-2. 연결 요청 `pulseWorkspaceClaims`(새 문서 종류)

```
{ id, projectId, synkUserId, displayName,
  status: 'pending' | 'approved' | 'rejected' | 'withdrawn',
  createdAt, decidedAt, decidedBy, workspaceId, note }
```

- 같은 프로젝트 · 같은 사람의 `pending`은 하나만(두 번 눌러도 같은 줄). 결정된 줄은 지우지 않는다.
- 문서뿐이라 파일 소유 목록(`workspace-media.mjs`)은 바뀌지 않는다. DB 백업에 그대로 든다.

### 3-3. 프로젝트 쪽

- `clientProjects.customerWorkspaceId`(선택): **직원 행동으로만** 붙이고 뗀다(프로젝트 기록 한 줄). 손님이 보내는 값으로 정하지 않는다.
- `clientProjects.workspaceRequest`(선택, 다시 쓰기 의뢰가 만든 프로젝트만): `{workspaceId, personaId, revisionId, attachedBy: synkUserId, attachedAt}` — 담당자가 접수 때 확인하면 `customerWorkspaceId`로 옮겨 적는다.

### 3-4. 인물 쪽(판 3 문서에 더하기만)

- `pulsePersonas.workspaceId`: null로 태어난다(판 3). 아래 두 조건이 **모두** 서면 서버가 채운다 — ① 원 프로젝트가 직원 행동으로 브랜드 W에 연결됨, ② 그 인물에 고객의 다시 쓰기 동의(아래 승인 종류 `reuse`)가 있음. 둘 중 하나가 풀리면(연결 끊김 · 동의 철회) 다시 null이 되고 내 모델에서 빠진다.
- `pulsePersonas.retention`: `{ scope: 'project' | 'reuse', until, reuseApprovalId }` — 기본 `project`. `until`은 다시 쓰기 동의 때 보인 기간(운영 제안은 마지막 납품 뒤 12개월, 유호님 결정 전까지 문안 초안의 값). 마지막 사용으로 저절로 늘지 않는다.
- 상태에 `paused`(사용 중지) 쓰임을 더한다. **만료는 저장하지 않고 읽을 때 계산한다**(`until <= now` → `expired`) — 일괄 작업 없이, 시계가 지나는 순간부터 모든 검사가 같은 답을 낸다. 직원 화면은 계산값을 보인다.
- 승인 종류에 `reuse`(다시 쓰기 동의)를 더한다(판 3 `pulsePersonaApprovals` 꼴 그대로 — `viewedHash`에 보관 자료 · 목적 · 기간 문안의 해시를 넣는다). 실제 인물이면 당사자 동의(판 3 `pulsePersonaConsents`)의 범위에 다시 쓰기가 들어 있어야 `reuse`를 받는다.

## 4. 경로와 권한

### 4-1. 두 증명을 잇는 법 — 목적 묶인 일회용 증표

쿠키 길(`/pulse` · `/api/customer`)을 바꾸지 않는다. 대신 PULSE 쪽에서 **5분 · 한 번 · 목적 하나**짜리 증표를 받아 고객 SYNK ID 쪽 요청 몸통에 싣는다.

```
1) PULSE 앱 → POST /pulse/api/project/workspace-proof   (synk_pulse_session + X-Pulse-CSRF)
   ← { proof }   // store.mint('pulse-proof', …, {purpose:'workspace-claim', projectId, inviteRevision}, 5분)
2) PULSE 앱 → POST /api/customer/pulse/claim { proof }   (synk_customer_session + X-CSRF-Token)
   서버: 고객 세션 중앙 확인 → proof 읽고 즉시 소모 → 목적 · 프로젝트 · inviteRevision이 지금 값과 같은지 → 연결 요청 기록
```

다시 쓰기 붙이기도 같은 꼴이다: `POST /pulse/api/request/persona-proof`(초안 쿠키 + CSRF) → `{proof}`(목적 `persona-attach`, 초안 id) → `POST /api/customer/pulse/draft-persona {proof, personaId, revisionId}`. 증표에는 세션 토큰을 담지 않고, 화면 JS는 HttpOnly 쿠키를 끝까지 보지 못한다.

### 4-2. 고객 SYNK ID 경로 `/api/customer/pulse/*`(스위치 `myModels`가 꺼져 있으면 모두 404)

| 경로 | 하는 일 | 확인 |
|---|---|---|
| `GET /api/customer/pulse/models` | 내가 회원인 브랜드들의 내 모델 카드(브랜드별) | 요청마다 회원 목록을 다시 읽는다 |
| `GET /api/customer/pulse/models/<personaId>` | 상세 — 승인 이력(종류 · 판 · 날짜 · 승인 방식), 이 브랜드에 연결된 사용 프로젝트, 변형 | 회원 + `persona.workspaceId`가 내 브랜드 |
| `GET /api/customer/pulse/asset/<assetId>` | 카드 · 상세의 그림(공개된 판의 기준 얼굴 · 변형만) | 회원 + 그 자산이 공개 판 자산 목록에 있음. `Cache-Control: private, no-store` |
| `POST /api/customer/pulse/claim` | 연결 요청(4-1) | 증표 + 고객 세션 |
| `POST /api/customer/pulse/draft-persona` | 다시 쓰기 붙이기(4-1) | 증표 + 회원 + 인물 쓸 수 있음(5-4) |
| `POST /api/customer/pulse/stop` | 사용 중지 요청 — 즉시 `paused` | 브랜드 admin |
| `POST /api/customer/pulse/delete-request` | 삭제 요청(직원 할 일만 만든다) | 브랜드 admin |

- `customer-routes.mjs`의 「알려진 경로 여덟」은 정확 일치 목록이라, `/api/customer/pulse/`는 앞부분 일치로 PULSE 회원 처리기에 넘기고 그 처리기가 다시 정확한 꼴(`<personaId>` · `<assetId>`는 UUID)만 받는다. 질의 금지 규칙은 그대로.
- **로그인 뒤 돌아갈 곳:** `synk-id/start` 몸통에 `returnTo`(허용 목록 `'/consultation/'` · `'/pulse-app/'`만)를 받아 로그인 흐름(flow)에 저장하고, 콜백이 그 값으로 302한다. 콜백 주소의 허용 질의(state · code · error)는 그대로다.
- 응답에 데이터셋 · 학습 파일 경로 · 내부 실패 판 · 동의 원문 · 다른 회원의 SYNK ID는 싣지 않는다(회원 이름만).

### 4-3. 초대 세션 경로(판 3 `/pulse/api/persona/*`) — 바꾸지 않는다

프로젝트가 브랜드에 연결돼도 초대 세션은 **그 프로젝트에 공개한 판의 자산만** 읽고 승인한다. 브랜드 목록 · 다른 프로젝트 · 원본 사진 · 동의 자료는 어느 경로로도 열리지 않는다. 초대 세션의 승인 기록은 나중에 회원이 생겨도 「초대 링크로 승인」 그대로 남는다.

### 4-4. 직원 경로 `/api/customer-workspaces/*`

| 일 | 권한 |
|---|---|
| 연결 요청 보기 · 결정(새 브랜드 만들기 / 기존 브랜드에 회원 추가 + 프로젝트 연결 / 거절) | 그 요청 프로젝트에 `allowed()` + (기존 브랜드에 넣을 때) 그 브랜드의 `staffOwnerId` 또는 관리자 |
| 프로젝트 연결 · 끊기, 회원 역할 바꾸기 · 빼기, 브랜드 닫기 | 브랜드 `staffOwnerId` 또는 관리자 |
| 사용 중지 풀기 · 삭제 실행 | 관리자 |

- 결정은 근거 한 줄(`note`)을 꼭 받는다 — 예: 「지정 승인자 본인이 메일 회신으로 확인」. 앱은 근거를 검증하지 않고 기록만 한다(앱 밖 확인). 모든 결정은 브랜드 `history`와 감사 기록에 남는다.
- 회원 빼기 · 프로젝트 끊기 · 브랜드 닫기는 그 즉시 `/api/customer/pulse/*`의 다음 요청부터 막힌다(캐시 없음).

## 5. 흐름

### 5-1. 처음 연결(한 번)

고객 방(초대 세션)에서 「내 모델로 모아 두기」(스위치 켬 + 프로젝트가 아직 브랜드에 없음) → SYNK ID 로그인(`returnTo:'/pulse-app/'`) → 돌아온 고객 방이 증표를 받아 연결 요청 → 직원 작업실 「연결 요청」 → 담당자가 앱 밖에서 이 사람이 이 프로젝트의 승인자 · 연락처인지 확인하고 근거와 함께 승인 → 브랜드 생성 또는 회원 추가 + 프로젝트 연결. 이메일 · 회사명이 같아도 저절로 합치지 않는다.

### 5-2. 다시 쓰기 동의

판 3에서 인물이 `ready`가 된 뒤 고객 방에 「다음 광고에도 이 인물 쓰기」 카드 — 보관할 자료(기준 얼굴 · 동작 시안 · 필요한 학습 파일), 목적, 기간, 철회 방법, 백업 잔존 기간을 보이고 별도 승인(`reuse`)을 받는다. 프로젝트 승인자가 초대 세션으로 승인한다(승인 방식이 기록된다). 원 프로젝트가 브랜드에 연결돼 있으면 그 순간 `workspaceId`가 채워진다(3-4).

### 5-3. 내 모델 보기

로그인한 회원에게만: PULSE 앱 첫 화면의 「내 모델」 입구, 고객 방 모델 카드, 납품 화면. 카드는 대표 그림 · 이름 · 상태(사용 가능 · 사용 중지 · 기간 끝) · 사용 범위 요약 · 만료일 · 「이 모델로 의뢰」만 먼저 보이고, 상세에서 승인 이력 · 사용 프로젝트 · 변형 · 사용 중지 요청을 본다. 기간이 끝났거나 중지된 인물은 회색 카드와 「연장 · 재개는 담당자에게」 한 줄.

### 5-4. 다시 쓰기 의뢰

「이 모델로 의뢰」 → 공개 의뢰서(초안 쿠키)를 열고 모델 단계에 「내 모델」을 미리 고른다 → 화면이 증표를 받아 `draft-persona`로 붙인다 → 서버 확인: 회원, `persona.workspaceId`가 그 브랜드, 상태 `ready`, 만료 전, 판이 공개된 판 → 초안에 `{modelChoice:'persona', 인물 참조, attachedBy, attachedAt}` → 의뢰서는 **새 제품 · 목적 · 매체 · 지역 · 기간 · 출력 언어만** 다시 묻고 사진 칸을 열지 않는다 → 보내기 때 다시 확인(붙인 사람이 아직 회원 · 인물 쓸 수 있음 — 고객 쿠키 없이 저장된 `attachedBy`와 지금 회원 목록으로) → 새 프로젝트는 `workspaceRequest`를 달고 생긴다 → 담당자가 접수 때 브랜드 연결을 한 번 확인 → 이 광고의 사용 확인(판 3 승인 종류 `usage`)을 새 프로젝트 승인자가 → 제작 시작 때 가드가 다시 본다.

**가드 넓히기**(`createPersonaGuard`): 지금 조건(원 프로젝트) **또는** 「`row.customerWorkspaceId`가 있고 `persona.workspaceId`와 같으며, `retention.scope==='reuse'` · 만료 전 · 상태 `ready` · 이 프로젝트에 `usage` 승인이 있음」. 판은 공개된 판이어야 하는 지금 조건 그대로.

### 5-5. 얼굴이 바뀌는 요청

새 얼굴 · 나이 · 얼굴 구조처럼 정체성이 달라지면 새 판(revision)을 만들고 기준 얼굴 · 동작 시안 승인을 다시 받는다(판 3 흐름). 옛 프로젝트는 `castingSelection.personaRef.revisionId`가 옛 판을 그대로 가리킨다. 헤어 · 착장 변형은 같은 판의 변형 자산이고 그 프로젝트의 장면 승인으로 확인한다.

### 5-6. 만료 · 사용 중지 · 삭제

- **만료:** 읽을 때 계산(3-4). 새 선택 · 붙이기 · 보내기 · 방향 제안 · 제작 시작이 409로 막히고 이전 납품 이력은 그대로. 연장은 새 `reuse` 동의뿐.
- **사용 중지:** 브랜드 admin 또는 직원 → 즉시 `paused`(막히는 곳은 만료와 같음). 진행 중 프로젝트는 직원 할 일로 넘기고, 앱이 이미 집행 중인 광고를 취소했다고 말하지 않는다. 재개는 관리자 확인 + 새 `reuse` 동의.
- **삭제:** 고객 요청은 직원 할 일만 만든다 → 관리자 확인 → 참조 확인(진행 중 프로젝트가 쓰면 막고 알림, 납품 끝난 프로젝트는 참조만 남김) → 파일 지우기(원본 · 파생 · 동의 암호문) → 묘비(`deletedAt`, 이름 · 판 id만). 자동 영구 삭제는 보관 기간이 정해질 때까지 끈다. 백업에 남는 기간은 동의 문안에 사실대로 적는다.

### 5-7. 프로젝트 정리와 다른 자료

90일 정리 · 보관 · 초대 링크 닫기는 그 프로젝트 자료만 다룬다. 인물 파일은 판 1 소유 목록이 지키고 `retireRequest`는 돌려주지 않는다. 브랜드에 묶인 인물은 원 프로젝트가 정리 · 보관돼도 내 모델에 남는다(`originProjectId`는 기록으로만). 원 프로젝트의 초대 링크를 닫아도 다른 프로젝트의 참조 · 브랜드 회원 접근은 그대로다.

## 6. 화면

- **PULSE 앱:** 「내 모델」 입구 셋(5-3), 카드 · 상세 · 사용 중지 요청, 의뢰서 모델 단계의 「내 모델 다시 쓰기」(판 3이 둔 자리), 고객 방의 「내 모델로 모아 두기」 · 「다음 광고에도 이 인물 쓰기」. 새 글은 `t()` 사전, 영어 문안은 세 겹(역번역 Opus → Fable → 아르곤).
- **직원 작업실:** 연결 요청 목록(다음 행동 한 줄 먼저), 브랜드(회원 · 연결 프로젝트 · 인물 · 기록), 인물의 만료 · 중지 · 삭제 요청 표시.
- **설치 앱:** 같은 화면을 쓴다. 로그인 창을 앱 안에서 열 때 `returnTo` 흐름이 설치 앱에서도 돌아오는지 확인한다(PC 앱은 `workspace.synk.im/pulse-app/`을 연다).

## 7. 시험

- **시나리오 5:** 고객 A의 초대 세션 · A 회원 세션 · 자산 주소로 B의 인물 목록 · 자산 · 동의를 읽는 길 0. 회원이 아닌 SYNK ID는 빈 목록, 남의 `personaId`로 `draft-persona` → 404(있음을 드러내지 않음). 증표를 다른 목적 · 다른 프로젝트 · 두 번째로 쓰면 거절, 5분 뒤 거절, `inviteRevision`이 바뀌면 거절.
- **시나리오 8:** 다시 쓰기 의뢰가 사진 업로드 0 · 학습 요청 0으로 제작 시작까지 간다.
- **시나리오 9:** 만료 · 중지 인물은 선택 · 붙이기 · 보내기 · 방향 제안 · 제작 시작이 모두 409, 이전 납품 이력은 그대로.
- **시나리오 10:** 원 프로젝트를 90일 정리 · 보관 · 초대 닫기 한 뒤에도 브랜드 인물 파일 · 다른 프로젝트 참조가 그대로이고, 고객에게 새로 보이는 것 0.
- **동시성 · 경합:** 같은 연결 요청 두 번 → 한 줄. 회원을 뺀 직후의 `models` · `draft-persona` · 보내기 → 막힘. 연결을 끊은 직후 내 모델에서 빠짐. 붙인 뒤 만료 시각이 지나면 보내기에서 409.
- **스위치 끔:** 새 경로 404, 화면 입구 없음, 한국어 화면 바이트가 판 4 직전과 같음.
- **로그인 돌아오기:** `returnTo`가 허용 목록 밖이면 `/consultation/`, 설치 앱 · 휴대폰 · PC 브라우저에서 돌아오기(실물 휴대폰은 끝 보고에 미확인으로).

## 8. 검토 받을 판단(Fable에게)

1. 두 쿠키를 잇는 일회용 증표(4-1)가 세션 토큰 노출 없이 충분한가, 더 단순한 길이 있는가.
2. `workspaceId`를 「직원 연결 + 다시 쓰기 동의」 두 조건으로 서버가 채우고 풀리면 비우는 방식(3-4)의 함정.
3. 만료를 저장하지 않고 읽을 때 계산하는 방식(3-4)이 검사 자리마다 같은 답을 내는가.
4. 다시 쓰기 의뢰의 보내기가 고객 쿠키 없이 `attachedBy` + 지금 회원 목록으로 재확인하는 방식(5-4)의 빈틈.
5. 브랜드 역할 둘(admin · member)과 프로젝트 승인권을 분리한 것(3-1)이 맞는가.
6. 기획 12-2 · 7절과 어긋나는 곳, 빠진 시나리오.
