# SNS 검수형 자동발행 시스템 — 구현 기록

2026-09-10 구현, 09-11 승인 검증·YouTube 부분 실패 보완. 콘텐츠 한 벌을 계정별로 검사하고, 최종본과 발행 설정의 해시에 유호님 승인을 묶은 뒤 공식 연결이 있는 채널을 처리하는 로컬 도구다. 승인 뒤 본문·계정·미디어·발행 설정이 바뀌면 발행 직전 재검증에서 중단한다. 이 문서는 구현 범위이며 실제 계정의 게시 완료 기록을 대신하지 않는다.

## 이번에 실제로 만든 것

- `docs/마케팅/sns-계정.json`: 현재 20개 계정의 회사·채널·발행 방식·필수 설정을 한곳에 둔다. 비밀번호와 토큰은 넣지 않는다. 09-10 첫 게시물 묶음은 티스토리 추가 전 제작되어 19개 항목 그대로다.
- `tools/sns-자격.ps1`: 인증값을 평문 파일 대신 Windows 자격 증명 관리자에 `SYNK/SNS/...` 이름으로 저장·조회한다.
- `tools/sns-발행.js`, `tools/lib/sns-publisher.js`: 연결 점검, 발행 계획 생성, 해시 승인, 중복 방지, 발행 결과 기록을 맡는다.
- 직접 발행기: YouTube, Telegram, Pinterest, Facebook, Threads, LinkedIn, TikTok. 실제 권한·심사·형식 조건은 별도로 갖춰야 한다. Instagram 발행기는 미구현이며 항상 차단한다. HTTPS 미디어 호스트만 등록해도 활성화되는 구조는 아니다.
- 수동 보조기: 네이버 블로그, 카카오톡 채널, 티스토리, Substack. 검수 파일을 정리하고 공식 편집 화면을 열어 최종 예약·게시만 사람이 한다.

```powershell
npm run sns:연결점검
node tools/sns-발행.js --도움
node tools/sns-발행.js --준비 --묶음 "<패키지폴더>" --출력 "<계획.json>"
node tools/sns-발행.js --승인 "<계획.json>" --항목 "<항목ID>" --근거 "<실제 최종 검수 근거>"
node tools/sns-발행.js --발행 "<계획.json>" --항목 "<항목ID>"
node tools/sns-발행.js --수동열기 "<계획.json>" --항목 "<수동 채널 항목ID>"
```

꺾쇠 안은 실제 값으로 바꾼다. `--계획` 명령은 없다. `--준비`는 계획 JSON과 검수용 Markdown을 쓰며 승인·발행하지 않는다. 기존 계획을 다시 생성하면 승인 정보가 초기화되므로 기존 게시 결과와 최종본을 먼저 대조한다. 다른 파일명의 계획을 만들면 기존 계획의 결과 기록을 자동으로 이어받지 않는다.

`--승인`은 현재 필수 파일·원본 변경을 검사하고 발행 내용과 설정을 기록한다. 직접 통로의 저장 자격에서는 비밀이 아닌 게시 대상 ID·API 버전만 승인 지문에 포함하며, 토큰·비밀키는 계획에 넣지 않는다. 이 명령은 외부 로그인·권한·앱 심사를 검증하거나 완료하지 않는다. 계획 명령은 기본적으로 계획에 기록된 계정 설정을 사용하며 `--계정설정 "<계정.json>"`으로 명시한 경우에만 덮어쓴다.

`--발행`은 현재 승인과 실제 파일·설정을 재검증한다. 수동 채널은 `manual-required` 기록만 남기며 편집기를 자동으로 열거나 게시하지 않는다. `--수동열기`가 같은 승인 검증 뒤 본문을 복사하고 공식 편집기·자료 폴더를 연다. 최종 예약·게시는 사람이 수행한다.

## 09-11 승인과 부분 실패 처리

- 새 승인 형식은 `version: 2`와 `publicationHash`를 사용한다. 제목·본문·계정 키와 표시 계정·플랫폼·언어·미디어 경로/순서/실제 바이트·대체텍스트·링크·원격 미디어 주소·공개범위·예약시각·구독 알림·TikTok 통제값, 사용 계정의 공개 설정 및 자격의 게시 대상 ID/API 버전을 포함한다. 기존 `contentHash`는 결과 대조용으로 유지한다.
- 예전 형식의 승인은 자동 승격하지 않는다. 현재 최종본과 발행 설정을 다시 검수해야 한다. 파일 검증이 통과해도 사람의 내용·음성·권리 검수가 완료됐다는 뜻은 아니다. 토큰 갱신만으로는 승인을 무효화하지 않으며, 토큰 소유자의 실제 계정·권한 확인은 별도 연결 검증 범위다. 원격 미디어는 URL을 묶으며 그 주소의 내용 불변성을 검증하지 않는다.
- YouTube는 영상 ID를 받자마자 같은 계획의 `.결과.json`에 ID·URL과 `partial` 상태를 기록한다. 썸네일·각 자막의 성공도 차례로 기록하며, 이후 실패해도 기존 영상 ID와 완료 작업을 보존한다. 전체 처리가 성공해야 `private`·`unlisted`·`public`·`scheduled` 상태로 마친다. `partial`은 전체 완료도, 영상이 외부에 없다는 뜻도 아니다.
- `partial` 또는 실행 중 중단된 `publishing` 항목은 재실행을 차단한다. 내용 변경·재승인·라이브러리의 `force` 옵션도 이 차단을 해제하지 않는다. 기록된 기존 영상을 확인해 남은 썸네일·자막 등을 마무리해야 하며 자동 복구 기능은 없다. 재시도하려고 결과 파일을 삭제하거나 새 계획으로 우회하지 않는다.
- 중복 방지는 같은 계획의 기록에 한정된다. 다른 계획·브라우저 수동 게시·동시 실행·원격 성공 응답 유실을 통합 감지하지 않는다. 예전 `failed` 기록에 원격 ID가 없다면 먼저 실제 계정의 게시 결과를 대조한다. 새 중앙 큐나 예약 작업은 설치하지 않았다.
- 예약시각은 현재 YouTube·Facebook 발행기만 처리한다. 다른 직접 통로에 예약시각을 적어도 예약 실행되지 않으므로 예약용으로 호출하지 않는다. TikTok은 업로드 후 `processing`을 반환하며 최종 게시 완료를 재조회하는 기능은 없다. Threads 첨부는 승인된 HTTPS 미디어 주소가, TikTok은 공개범위 통제값이 추가로 필요하다.

회귀 검사: `node --test tests/sns-발행.test.js`. 외부 요청과 Windows 자격 저장은 mock으로 격리한다. 승인 시험은 임시 fixture 계획에만 기록하고 정리하며 실제 콘텐츠를 승인·게시하지 않는다.

## 유호님에게 남는 손

아래는 **연결 구현·계정 권한이 갖춰진 뒤의 목표 운영**이다. 현재 모든 플랫폼이 이 단계에 도달한 것은 아니다.

1. 게시하려는 최종본을 눈으로 확인하고 승인한다.
2. 공식 OAuth·본인 인증·앱 심사에서 필요한 사용자 동작을 처리한다. 플랫폼별 토큰 갱신·권한 유지 구현이 필요하며 지금 ‘처음 한 번이면 끝’이라고 보장할 수 없다.
3. 네이버·카카오·티스토리·Substack은 공식 편집기에서 예약 시간과 공개 대상을 확인해 최종 예약·게시한다.

도구는 계정별 패키지 수집·필수 파일 검사·승인 재검증·지원 채널의 자막/썸네일 처리·같은 계획의 결과 기록을 맡는다. 실제 미디어 비율·품질·모든 플랫폼 조건을 자동으로 검증하거나, 모든 통로의 예약·게시 후 확인까지 구현한 것은 아니다.

### 09-11 실제 연결 진입점 재검수

`tools/lib/sns-publisher.js`의 `authorizeYoutube`, `credentialFields`, `openCredentialForm`과 CLI를 대조했다. YouTube는 공식 동의 화면 → 코드 교환 → 선택 채널 검증 → 보관소 저장까지 구현돼 있다. 반면 아래 명령은 **이미 발급받은 값을 입력하는 로컬 폼**만 연다. 폼 제목의 ‘공식 연결’은 플랫폼 OAuth 화면이나 권한 검증의 증거가 아니다.

| 대상 | 기존 진입점 | 아직 필요한 구현·외부 조건 |
|---|---|---|
| Threads | `node tools/sns-발행.js --자격-연결 yuhobuilds-threads` 또는 `synkbrief-threads` | 실제 별도 프로필, 게시 권한이 있는 공식 연결, 동의·코드 교환·토큰 갱신 구현 |
| Instagram | 같은 명령의 계정 키 `lab-instagram`, `yuhobuilds-instagram`, `synkbrief-instagram` | 전문 계정·공식 권한 연결, 동의·코드 교환, 직접 발행기 구현. 폼 저장이나 HTTPS 주소만으로 활성화되지 않음 |
| TikTok | 같은 명령의 계정 키 `lab-tiktok`, `yuhobuilds-tiktok`, `synkbrief-tiktok` | 앱/게시 권한·심사 조건 확인, 동의·코드 교환·토큰 갱신, 공개범위 통제·최종 게시 상태 확인 구현 |

폼은 `127.0.0.1`의 임의 포트를 Chrome에서 열고 최대 20분 기다린다. 제출은 Windows 자격 보관소에 저장하지만 토큰 유효성·계정 소유를 검증하지 않는다. TikTok `refreshToken` 필드가 있어도 자동 갱신 기능은 없다. 특정 Chrome 프로필/자동화 세션 선택 기능도 없어 현재 로그인 브라우저와 같다고 가정하지 않는다. 이번 점검은 코드 읽기이며 자격 조회·저장, 연결 폼 실행, 계획 승인·게시·예약은 하지 않았다. 기존 브라우저 로그인과 API 연결은 별도 상태다.

## 티스토리 적용

09-10 유호님이 「AI가 게시용 완성본을 만들고 나는 붙여넣기·최종 검수만 한다」는 운영 조건으로 추가를 확정하고 `https://yuhobuilds.tistory.com/`을 개설했다. 티스토리는 공식 Open API를 2024년 2월 말까지 순차 종료했고 외부 API를 통한 글쓰기·수정·파일 첨부도 종료했으므로, 직접 발행 연결로 표시하지 않는다. [티스토리 공식 종료 공지](https://notice.tistory.com/2664), [공식 API 문서의 종료 안내](https://tistory.github.io/document-tistory-apis/)

자동화 도구에는 `shift-tistory`를 `manual-assisted`로 등록하고, `Tistory` 플랫폼 이름과 `본문.md` 필수 검사를 추가했다. 앞으로 AI가 제목·본문·이미지·대체텍스트·링크·분류·검색 설명까지 한 묶음으로 만든 뒤 승인 해시를 고정하고 공식 편집기를 연다. 유호님에게 남는 것은 공개 전 최종 확인과 게시 동작이다. 티스토리는 실제 회사 작업의 긴 과정 원문, 네이버는 국내 검색용 재구성, `synk.im`은 회사·상품 공식 정본으로 역할을 나눈다.
