# 출석 체크인 설계 v1 — 회전 PIN + 하루 퀘스트 입구

> **지위**: SYNK-talk 출석 기능의 설계 정본. 2026-08-07 유호님이 가져온 외부 설계(Wi-Fi BSSID + PIN 이중 인증)를
> 검토·판정한 결과물이며, 컨텍스트 독립 반박 1패스를 반영했다.
> **구현 위치**: `unmet23-lab/SYNK-talk`(Expo + Supabase). 이 저장소(Apps Script)는 §9 시트 다리만 맡는다.
> **구현 시점**: 로그인·데이터 계약(P0/L0/C0) 공사 완료 뒤. 개원(파일럿 2027-02-11) 전 마일스톤.

## 0. 판정 요약

| 항목 | 판정 | 근거 요약 |
|---|---|---|
| 현장 디스플레이 30초 회전 PIN | **채택** | 물리적 현장성 검증 + 구현 단순. 단 4자리→**6자리**, 저장식→**TOTP 유도식**으로 변경 |
| Wi-Fi BSSID 검증 | **보류** (§11 재검토 트리거) | 스푸핑 내성은 인정. 그러나 전원 Wi-Fi 접속 강제·AP 관리 부담이 개원 규모에선 이득을 초과 |
| 별도 백엔드 서버 + Redis + 자체 JWT | **기각** | 확정 스택(Supabase Edge Function + Postgres + Supabase Auth)으로 전부 대체. TOTP 유도식이라 PIN 저장소 자체가 불필요 |
| GPS를 PIN의 짝으로 | **기각** | 반박 패스가 격추: 실내 GPS 오차·픽스 지연이 30초 창과 충돌해 정직한 학생이 구조적으로 실패. 모의 위치 앱으로 스푸핑도 쉬움 |
| 디스플레이 "오늘의 문제" 정답 = 출석 | **기각** | 정답은 30초마다 안 바뀌어 중계 방어 0 + 오답 학생의 출석이 불이익이 되는 설계 |
| 출석 = 하루 퀘스트 입구 (§8) | **채택 (본체)** | 체크인 성공 응답이 개인화 숙제 퀘스트를 실어 보낸다 — 출석·숙제·수집이 한 동작 |

⚠ 위 기각·보류 항목은 **재제안 금지 기록**이다. 뒤집으려면 §11의 재검토 트리거 또는 유호님의 새 확정이 필요하다.

## 1. 원칙

- **출석은 보안 게이트가 아니라 수집기의 입구다.** 이 기능의 목적 우선순위: ①하루 학습 루프(퀘스트) 트리거 ②출석 로그 자동화(스트릭·포인트·달력·리포트 재료) ③부정 방지. 보안 장치는 ③을 위해 ①②의 UX를 해치지 않는 선까지만.
- v9.147 「수집기 우선」 축과 같은 방향: 체크인은 로그를 낳고, 학생을 입구까지 데려온다.
- 위성 수업(댄스·보컬·뷰티·원어민 회화·글로벌 영어)은 출석 체크 없음(유호님 기확정) — 범위 밖.

## 2. 구성 요소

| 구성 | 역할 | 물리 |
|---|---|---|
| SYNK-talk 앱 | 학생 체크인 UI + 퀘스트 수행 | Expo · Supabase Auth 로그인 |
| Edge Function `attendance` | PIN 검증·출석 기록·퀘스트 발급 | Supabase |
| Edge Function `display` | 디스플레이용 현재 PIN 응답 | Supabase |
| 교실 디스플레이 | PIN + (v2) 라이브 보드 표시 | TV/노트북 브라우저, 기기 토큰으로 인증 |
| Postgres | `classrooms`·`classroom_devices`·`attendance` | Supabase (L0 계약에 편입) |
| 시트 다리 | Supabase → `attendance` 시트 동기화 | 이 저장소 Apps Script (§9) |

`active_pins` 테이블·Redis·별도 서버는 **없다**(§4 TOTP 유도식).

```
     │                              ├─ ③ 학생: 화면 PIN 입력        │
     │                              ├─ ④ 인증 토큰 + PIN 전송 ─────>│
     │                              │                              ├─ ⑤ TOTP 재계산·대조 (현재+직전 창)
     │                              │                              ├─ ⑥ 시도 제한·중복 검사
     │                              │                              ├─ ⑦ attendance 기록
     │                              │<─ ⑧ 성공 + 오늘의 퀘스트 ─────┤  (코어엔진 개인화)
     │                              └─ ⑨ 퀘스트 즉시 시작            │
```

## 4. PIN 설계 — TOTP 유도식

- **계산**: `PIN = HMAC-SHA256(secret, floor(unixtime / 30)) → 하위 비트 → 6자리 십진수` (RFC 6238 방식). 강의실별 `secret`은 `classrooms.pin_secret`(서버 전용, 클라이언트 노출 금지).
- **저장 없음**: 발급·만료 관리가 필요 없다. 검증 = 서버가 같은 식으로 재계산해 대조.
- **grace**: 현재 창 + **직전 창 1개**를 유효로 인정(경계 입력·네트워크 지연 흡수). 원안의 "5~10초 유예"보다 단순하고 충분하다.
- **6자리인 이유**: 4자리는 유효 코드 2개(현재+직전) 기준 시도당 성공률 2/10,000 — 시도 제한이 느슨하면 한 학기 안에 브루트포스가 현실이 된다. 6자리 = 시도당 2/1,000,000.
- **시도 제한(필수 — 이것 없이는 배포 금지)**:
  - 학생당 **연속 실패 5회 → 5분 잠금**, **일일 총 시도 30회 상한**.
  - 6자리 + 일 30회 = 학생당 하루 성공 확률 ≈ 0.006% — 충분.
  - 카운터는 Postgres에 둔다(레이트리밋은 상태다 — "저장 없음"은 PIN에 한한 말이다).
- **중복 출석**: 같은 학생·같은 날 2번째 체크인은 성공 응답(멱등)하되 행은 추가하지 않는다. (기존 소비 엔진은 Set 기반이라 중복이 무해하지만, 원본층에서부터 깨끗하게.)

## 5. 디스플레이 기기 인증

- **PIN 응답 엔드포인트가 열려 있으면 전체가 무너진다** — 결석 학생이 직접 호출해 PIN을 원격 취득하는 단일 실패점.
- `classroom_devices`에 기기당 토큰을 1회 발급(원장 셋업 시), 디스플레이 브라우저에 저장. `display` Function은 이 토큰 없으면 401.
- 토큰 유출 의심 시 행 삭제 후 재발급(원장 클릭 단위 절차는 구현 시 함께 작성).

## 6. 데이터 모델 (Supabase — L0 계약 편입 대상)

```sql
-- 강의실
classrooms (
  id           uuid PK,
  name         text,                -- 'A강의실'
  pin_secret   text,                -- 서버 전용. RLS로 클라이언트 완전 차단
  created_at   timestamptz
)

-- 디스플레이 기기
classroom_devices (
  id            uuid PK,
  classroom_id  uuid FK,
  device_token  text UNIQUE,        -- 해시 저장 권장
  label         text,               -- 'A강의실 TV'
  created_at    timestamptz
)

-- 출석 (원본)
attendance (
  id            uuid PK,
  student_id    text,               -- 기존 학생 id 체계 유지
  date          date,               -- 학원 시간대 기준
  method        text,               -- '앱PIN' | '수동' | (기존값 병존: '출석(폼)' 등)
  classroom_id  uuid FK NULL,       -- 수동 기록은 NULL 허용
  checked_at    timestamptz,
  UNIQUE (student_id, date)         -- §4 멱등의 물리적 근거
)

-- 시도 제한
attendance_attempts (
  student_id    text,
  date          date,
  fail_count    int,
  locked_until  timestamptz NULL,
  PRIMARY KEY (student_id, date)
)
```

원안의 `allowed_bssids` 배열 컬럼은 **넣지 않는다** — BSSID 보류(§11)가 풀릴 때 추가.

## 7. API 명세 (C0 계약 편입 대상)

**① 디스플레이 PIN** — `GET /display/pin`
- 인증: `X-Device-Token` (§5). 응답: `{ "pin": "482913", "secondsLeft": 17 }`
- 디스플레이는 `secondsLeft` 후 재요청(폴링). 실패 시 화면에 "직원 호출" 표시.

**② 학생 체크인** — `POST /attendance/check-in`
- 인증: Supabase Auth 토큰. 바디: `{ "pin": "482913" }` (classroom은 PIN이 어느 강의실 secret과 맞는지로 서버가 판별 — 강의실 수가 적어 전 강의실 대조 비용 무시 가능).
- 성공 응답 (**퀘스트 동봉이 본체 — §8**):
```json
{
  "success": true,
  "checkedAt": "2027-02-11T14:00:12+08:00",
  "streak": 5,
  "quest": { "quest_id": "...", "items": [ ... ] }
}
```
- 실패: `INVALID_PIN`(사유 미분화 — 만료/오입력 구분 노출 금지) · `LOCKED`(잠금 해제 시각 동봉) · `NO_SESSION_TODAY`(수업일 아님).

## 8. 하루 퀘스트 입구 — 이 기능의 본체

- 체크인 성공 시 Edge Function이 **오늘의 개인화 숙제 퀘스트를 발급해 응답에 동봉**한다. 별도 화면 이동 없이 "체크인 → 퀘스트 시작"이 한 호흡.
- 개인화 재료: 학생의 성향·숙련도(mastery)·최근 오답 + **TOPIK 토픽/급수별 문항**. 발급 로직의 정본은 `docs/코어엔진_설계.md`(코어엔진 = 개인화 단일 원천) — 이 문서는 **인터페이스만 정의**한다: `발급(student_id, date) → quest`.
- 퀘스트 수행 결과는 수집층 로그(hw/quiz/talk/voice/mastery — `docs/수집층_실행지.md`)로 되돌아와 다음 날 개인화 재료가 된다. **출석·숙제·수집이 하나의 순환.**
- 게임 보상 접점: 체크인 = 스트릭 +1·출석 포인트, 퀘스트 완료 = 기존 숙제 보상 라인. 기존 게임화(개근왕·출석달력·몬스터)와의 정합은 §9 다리를 통해 유지.

## 9. 시트 다리 (이행기 — 이 저장소 몫)

- **진실 원천은 Supabase `attendance`**(확정 스택 원칙: Postgres = 원본, 시트 = 파생). 시트로 **단방향 동기화**만 한다.
- 기존 소비처(스트릭·개근왕·달력·포인트·리포트·학부모 메일)는 attendance 시트의 **`student_id`·`date`·`method` 3열만** 읽는다 — 다리는 이 3열 계약만 지키면 된다.
- 구현: Apps Script 시간 트리거가 마지막 동기 시각 이후의 Supabase 행을 끌어와 시트에 append (`method='앱PIN'`/`'수동'`). 기존 폼 출석·GPS 출석 행과 병존, dedup은 기존 Set 계산이 흡수.
- ⚠ **이중 기록 금지**: 앱 체크인은 반드시 Supabase에만 쓰고 다리로만 시트에 온다. 시트에 직접 쓰는 경로를 만들면 진실 원천이 둘이 된다.
- 이 다리의 규격은 L0 계약의 「시트 파생」 절에 등재한다(시트→원본 되쓰기는 금지 방향).

## 10. 폴백 (필수 요건 — 부속 아님)

출석이 스트릭·포인트와 직결되므로 **기술 실패 = 학생 보상 손실**이다. 다음 경로 없이 라이브 금지:
- **강사 수동 오버라이드**: 강사/원장 권한으로 학생·날짜 지정 출석 기록(`method='수동'`). 폰 없음·배터리·권한 거부·앱 장애 전부 이 경로로 흡수.
- **디스플레이 장애**: PIN을 못 띄우면 그 교시는 전원 수동 처리(운영 절차 1줄이면 됨).
- **오프라인 학생 기기**: 체크인은 온라인 필수(PIN 검증이 서버라). 실패 시 앱은 "선생님께 말씀드리세요" 안내 — 복잡한 오프라인 큐는 만들지 않는다.

## 11. BSSID — 보류 조건과 재검토 트리거

- **보류 근거**: 전 학생 Wi-Fi 접속 강제(미접속 = 정당 학생 거부) · AP 교체/메시 다중 BSSID 관리가 비개발자 운영에 지속 부담 · 강사 상주 소규모에서 PIN 중계 부정은 출결 보드·주간 리포트 이상 패턴으로 노출.
- **인정한 강점**(반박 패스): BSSID는 OS API 반환값이라 비루팅 기기에서 위조 사실상 불가 — 스푸핑 내성은 GPS·PIN보다 강하다. Expo 구현도 EAS 빌드 환경이면 평이(`react-native-wifi-reborn` + iOS `Access WiFi Information` 엔타이틀먼트 + 정밀 위치 권한).
- **재검토 트리거(둘 중 하나면 재판정)**: ①PIN 중계 부정이 실제 관측됨 ②분반·시간대·강사 확장으로 "강사 눈" 전제가 깨짐.
- 그때의 설계: `classrooms.allowed_bssids` 추가 + 체크인 바디에 `bssid` 필드 — 본 설계에 열려 있는 확장점.

## 12. 디스플레이 v2 — 교실 라이브 보드 (채택된 도전안)

- v1 = PIN 크게 + 남은 초. v2 = PIN은 구석, 화면의 주인공은 **방금 체크인한 학생의 몬스터가 입장하는 실시간 연출**(Supabase Realtime 구독).
- 출석이 통제 절차가 아니라 교실 전체가 보는 **입장 세리머니**가 된다 — 추가 보안 비용 0. v1 배포 후 별도 트랙.

## 13. 구현 전제·순서

1. **선행**: SYNK-talk 로그인·P0/L0/C0 계약 안정화 (현재 공사 중 — 세션보드 참조).
2. L0에 §6 테이블 + C0에 §7 API 등재 (계약 먼저, 구현 뒤 — 기존 절차 그대로).
3. Edge Function 2종 + 앱 체크인 화면 + 디스플레이 페이지 (SYNK-talk repo).

5. 리허설 환경 왕복 시험 → 파일럿 전 실교실 실측(디스플레이 시인성·PIN 입력 소요·잠금 오작동).

## 14. 보안 체크리스트 (배포 게이트)

- [ ] `pin_secret` 클라이언트 노출 경로 0 (RLS + Edge Function 전용 접근)
- [ ] `display` 엔드포인트 기기 토큰 없이 401
- [ ] 시도 제한(5연속→5분 잠금·일 30회) 동작 실측
