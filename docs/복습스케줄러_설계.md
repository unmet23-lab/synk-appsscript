## 1. 왜 이것인가 (철학 대조 — ①②③④)

| 기준 | 이 설계 |
|---|---|
| ① 재미·실사용 도움·신선 | **신선함의 1수단 = 그 시점의 최신 기능**(유호 확정 08-13 · Ⅰ-3 ①): FSRS-6(2025-05 · 21 파라미터 · 사용자별 망각곡선 모양 `w20`)는 Anki 기본값이 됐고 SM-2 대비 같은 유지율에 복습 20~30% 적다는 벤치마크(정찰 §2). 실사용 도움 = «오늘 다시 물을 것»이 학생마다 다르다 — 맞는 것을 또 묻지 않고 흐려질 때 묻는다. 재미 = 이 설계가 만드는 화면은 0 — 기존 퀴즈·과제 통로에 «무엇을 낼지»만 바꾼다(Ⅱ-8 「새 화면을 늘려서 풀지 않는다」) |
| ② 엔진 | ㉠ 실력 이해에 **시간 축**을 더한다(「무엇을 틀리는가」→「무엇이 언제 흐려지는가」). A-1 ㉡ 행동층(「읽은 성향으로 다음에 할 일을 바꾸는 자리」 — 🔴 가장 비어 있는 칸)의 **첫 실물 후보**: 읽은 것(기억 상태)이 «다음에 낼 것»을 바꾼다 |
| ③ 운영 | 사람 손 0 · 벤더 호출 0 · **API 비용 0**(우리 소유 결정적 알고리즘 — 모델 의존 없음) |
| ④ 완결 | 모였나(리뷰 로그가 사건으로 저장) · 닿았나(스케줄러가 사람 손 없이 읽어 다음 출제를 바꾼다) · 늘었나(A-1 ㉠ 행에 「언제 흐려지나」 칸 · ㉡ 행동층 ✓) — **셋 다 지금 ✗**, 이 설계의 인수 조건이 셋을 ✓ 로 만드는 것이다 |

🔑 **Ⅰ-2 검사**: AI 가 두 배 똑똑해지면 이 기능도 좋아지는가 — **예.** 스케줄러 자체는 모델 무관이지만 «카드의 rating 을 내는
판정»(교정이 그 기술을 틀렸다고 읽는 정확도·퀴즈 채점)은 모델이 좋아질수록 정확해지고, 스케줄은 그 입력 위에 선다.

## 4. 설계 — 순수 계산기 + 소비자 하나 + 사건 하나 (얇게)

```
[리뷰 사건]  학생이 항목을 만난 결과 1건 = (learner, card_id, rating, at)
     │  원천 = 기존 사건(quiz.answered 정오+확신도 · submission 정오/교정 태그) → 파생(새 입력 UI 0)
     ▼
[스케줄러 lib/복습스케줄.js (순수 · 결정적)]  카드 상태(S·D·R·due) ← FSRS-6 (ts-fsrs 또는 이식)
     │  입력 = 그 학생의 리뷰 사건 열 전부(재계산 가능 · 상태 저장은 «캐시»일 뿐 정본은 사건)
     ▼
[소비자]  due ≤ 오늘 인 카드 → 개인 퀴즈 재출제 재료(14일 고정 창 «대체»)
```

- **카드 = (learner_id, card_id)** — card_id 의 «종류»는 §7-ⓐ. 후보 넷 비교:

| 후보 | 장점 | 단점 |
|---|---|---|
| ⓐ 오류 태그 23 | 수집층 정본 · 2년치 집계와 붙는다 · 교정마다 rating 이 난다(매일) | 태그 = «오류 유형»이라 「항목을 안다/모른다」보다 거칠다 · 정상 문장엔 rating 0 |
| ⓑ `engine.skills` 30(grammar 18) | 생성 트랙 `skill_ids`·성과회수 기술 축(겨냥×후속)과 같은 키 · talk 정본 | 태그와 매핑 0 → 교정 결과로 rating 을 내려면 **태그→skill 표**가 먼저(⏳E2 와 같은 자리의 일) |
| ⓒ 퀴즈 문항 id | 가장 고운 단위 · `quiz_log` 정오·확신도가 그대로 rating | 문항은 재출제가 곧 «같은 문제 또 내기» — 변형 출제와 안 붙는다 |
| ⓓ 어휘(단어) | 전통 SRS 의 자리 · 학생이 직관으로 안다 | 우리 수집층에 어휘 단위 사건이 0(새 입력 필요 — 「재미없는 설문」 금지와 부딪친다) |

  🔑 권고(AI 조립분 — 판정 아님): **ⓐ로 시작**(오늘 있는 사건으로 내일 돈다 · 비용 0) → 태그→skill 표가 서는 날 ⓑ로 «키만»
  갈아 끼운다(스케줄러는 card_id 를 문자열로만 본다 — 종류를 모른다).
- **rating 4등급 매핑**(FSRS Again/Hard/Good/Easy · §7-ⓒ 판정 후보): 틀림 → Again · 맞음+`guess` → Hard(「찍어서 맞힘」 —
  A-1 이 이미 별도 재료로 쓰는 그 값) · 맞음+`low` → Hard 또는 Good(판정) · 맞음+표기 없음(`null`) → **Good**(⚠ Easy 가 아니다 —
  「안 물렸다」를 「확신했다」로 읽지 않는다 · 학습자상태 주석 그대로) · Easy 는 «두 번 연속 빠른 정답» 같은 파생 조건에만(판정).
- **결정적**: 같은 사건 열 → 같은 상태. 시각은 사건 `occurred_at`(몽골 날짜는 기존 `lib/몽골날짜.js`). `enable_fuzz=false`(재현 —
  §12류 픽스처가 문다). `request_retention` 기본 0.9(Anki 기본 · §7-ⓑ 판정 자리에 같이) · `maximum_interval` 은 시즌(교재 1권 ≈
  2달 · 철학 Ⅱ-4) 을 넘지 않게(장기 간격은 개원 첫 해엔 뜻이 없다 — 값은 판정).
- **저장**: 정본은 사건(append-only — 상태 표는 파생·재계산 가능). 새 사건 종류를 열지 않는 길 = 기존 `quiz.answered`·
  `submission.created`(+교정 결과)에서 파생 — **새 계약 칸 0**. 상태 캐시가 필요하면(매 조회마다 전 사건 재계산이 무거운 날)
  그때 파생 표 1개 — 지금은 학생 0명·사건 0이라 재계산이 0원이다(Ⅰ-8 「못 재는 것을 미리 짓지 않는다」).
- **개인화 파라미터**: 첫 해는 **기본 21 파라미터**(학생별 재추정은 리뷰 수백 건 뒤 — 옵티마이저는 ts-fsrs binding · 그날 별건).
- **학생에게 돌려주기(Ⅱ-8)**: 새 화면 0 — 퀴즈 끝 관찰 한 줄 「이 자리는 지난주에 세 번 틀렸는데 오늘은 맞았어요」(어제의 나 대조 ·
  ㉢ 비교 금지 그대로) 자리가 이미 있다(`src/어제의나.js`) — due 카드를 맞힌 날 그 한 줄의 재료가 된다(카피는 카피 정본).

## 5. 하지 않는 것

- 🚫 런타임 품질 문턱(「기억률이 낮으면 과제를 바꾼다」 같은 분기) — 상태기반 불변식 5 · ㉠ 그대로. 스케줄러는 «순서»만 바꾼다.
- 🚫 학생끼리 비교(㉢) · 🚫 「복습 N개 남음」 같은 압박 카운터(synk-brand Y3) — 화면에 숫자를 안 낸다.
- 🚫 생성 과제 `skill_ids` 회전을 due 로 바꾸기(§3 — 확정 충돌 · E2 자리에서만).
- 🚫 어휘 단위 새 입력 UI(ⓓ) — 재미없는 설문 금지(철학 ㉡ 이해 층).

## 6. 인수 조건(픽스처 — 구현 때 상시 기계로)

1. 순수·결정적: 같은 사건 열 → 같은 due(fuzz 0) · 시각 축은 `occurred_at` 하나.
2. rating 매핑 표가 **한 곳**(lib 상수)이고 `null` 확신도가 Easy 로 안 간다(학습자상태 주석 대조).
3. 소비자 교체 = 14일 고정 창 «대체»가 아니라 **병행 후 교체**: 첫 판은 due 목록을 «같이» 내고 기존 회귀(`tests/퀴즈재출제.test.js`)가
   그대로 초록 — 행동 교체는 유호 판정 뒤 한 커밋.
4. 계약 면적 0(새 사건 종류 0 · 새 칸 0) — c12 검증기 회귀가 그대로.
5. A-1 ㉠ 행 「언제 흐려지나」 칸과 ㉡ 행동층 ✓ 는 **첫 실학생 리뷰 사건이 쌓인 뒤**에만 올린다(학생 0명 — 지금 ✓ 로 적으면
   F207 · 「설계상 ✓」 금지 · 상태기반 §12-17 선례).
