## Vellum — 말과 행동이 닿는 접점

### 사용자가 느끼게 될 역할

“이 앱이 나에게 어떤 말로, 어느 정도의 도움을 주는가”를 맡는다. 같은 내용이라도 한꺼번에 보여 줄지, 하나씩 같이 살펴볼지, 먼저 혼자 해 보도록 기다릴지가 달라진다. 캐릭터가 말할 때는 실제 확인한 사실을 사용하고, 모르는 내용을 아는 척하지 않는 것이 핵심이다.

- **현재 코드로 설명할 수 있는 예:** 편지 연습에서 “먼저 혼자 해 보기”를 고르면 글을 먼저 쓰고 나서 점검을 열 수 있다. “하나씩 살펴보기”는 한 부분부터 확인하게 한다. 마스코트는 시간·계절·다시 만난 날과 화면의 사건에 따라 준비된 반응을 고른다.
- **앞으로 만들 경험의 예:** 내가 주민에게 우산을 준 사실을 그 주민만 기억하고 비 오는 날 실제로 사용한다. 다른 주민은 직접 보거나 전해 들은 근거가 있을 때만 그 일을 언급한다. 이 예는 목표이며 현재 완성 기능이 아니다.

### 준비된 설계

1. 확인된 재료·명시 취향·목표로 템플릿 또는 승인된 생성 경로를 고른다. 실제로 전달한 말과 근거·버전을 연결해 재현한다. 공개 회사 안내나 라디오 DJ에 비공개 학생 원장을 붙이지 않는다. [V-1]
2. 실제 첫 제출·첫 녹음 같은 순간을 중복 축하하지 않고, 본인에게 먼저 알려 주는 방향이다. 안내의 사실, 성취 근거, 권한, 전달 여부를 나누어 다룬다. [V-1]
3. 마을 대화는 정해진 장면의 주제 안에서 학습자가 자기 말로 답하고, 확신이 낮으면 주민답게 되묻는 설계다. 기본 주민 대화는 실행 중 외부 AI 호출 없이 준비한 말과 기기 계산을 쓰는 방향이다. 자유로운 모든 주제를 이해하는 범용 대화가 완성됐다는 뜻은 아니다. [V-7]
4. Atlas가 방향을 주어도 캐릭터의 허용 반응은 Vellum에 둔다. 첫 공동 손잡이는 말의 양 `vellum.chatter: standard/quiet`다. [공통-2]

### 미구현·다음 일

1. **공통 말의 양 연결:** Atlas의 `vellum.chatter`를 기존 반응 판정 자리와 이어 “조용히” 선택이 실제 혼잣말 빈도에 반영되게 한다. 개인화가 없어도 기존 기본 동작은 유지한다.
2. **주민 하나의 사실 기반 반응:** 누가 어떤 사실을 어떻게 알았는지, 마지막으로 어떤 반응을 했는지를 입력으로 받는 공통 선택기를 Vellum에 만든다. Trail은 사실·정정의 시간 관계, Loom은 우산을 쓰는 실제 모습을 맡는다.
3. **먼저 닫을 한 장면:** 우산을 준 주민의 재회 한 장면을 끝까지 연결하고, 모르는 주민이 과거를 아는 척하지 않는지·같은 칭찬을 반복하지 않는지·기억 삭제 뒤에도 옛 반응이 돌아오지 않는지 시험한다.
4. **그다음 콘텐츠 확대:** 주민별 사연·대사·시간표를 콘텐츠 자료로 더한다. 이를 Vellum 공통 코드에 주민 이름별 조건문으로 쌓지 않는다.

## Loom — 재질과 장면을 실제 출력으로

### 사용자가 느끼게 될 역할

가까운 펠트의 섬유, 접촉 그림자, 눈깜빡임, 잔잔한 움직임, 읽기 편한 배치를 같은 세계처럼 연결한다. 문서·홈페이지·앱·영상이 제각각의 브랜드처럼 보이지 않도록 승인된 자산과 제작 원천을 공유한다.

- **현재 코드로 설명할 수 있는 예:** 교수와 가이드의 몸 이미지는 유지한 채 눈 부위만 깜빡이고, 녹음하거나 화면을 벗어나면 움직임을 멈춘다. 웹 제작 시연에는 눈을 감은 모습을 정지 상태로 확인하는 조작도 있다.
- **앞으로 만들 경험의 예:** 미래 한국의 마을에서 가까운 몽글의 펠트와 멀리 보이는 풍경이 같은 빛과 바람을 받는다. 내가 꾸민 공간의 흔적이 실제 기록에 따라 남는다. 이것은 현재 전체 구현이 아니다.

### 준비된 설계

1. 색·서체·재질·간격 → 공통 부품 → 문서·웹·앱·영상별 출력 → 실제 결과 점검의 제작 경로가 정의되어 있다. 승인 자산을 바꾸면 파생본과 소비자도 함께 맞춘다. [L-1]
2. 몸·잔털·알파를 유지하며 좁은 눈 영역만 바꾸고, 그림자·접지·카메라를 안정시키는 표현 기준이 있다. 움직임 줄이기, 숨김, 정지와 복귀를 분리한다. [L-2]
3. 경험의 흔적을 재질과 공간에 남기는 Patina는 설계 방향이다. 실제 기록 없이 달력만 지나도 성취·친밀도를 지어내거나 쉬었다고 흔적을 깎지 않는다. [L-2]
4. Atlas의 첫 손잡이는 `loom.motion: calm/standard`다. OS의 움직임 줄이기와 녹음 중 정지는 그보다 우선한다. [공통-2]

### Unity·Unreal과의 차이

**Loom은 현재 SYNK의 재질·자산·움직임·출력 방식을 묶은 공통 제작/표현 엔진이다.** 이 감사에서 확인한 공통 장면 코드는 JavaScript 운동 계산과 WebGL 2의 2.5D 표시기다. Unity·Unreal처럼 완성된 3D 게임 실행기를 자체 개발했다는 뜻이 아니다. 향후 Unity·Unreal을 쓰더라도 Loom의 승인 자산·재질 원칙·표현 설정을 그쪽 소비자로 연결할 수 있다는 설계 방향이며, 그 연결이 현재 완료됐다는 증거는 이번 범위에서 없다. [L-1, L-4]

### 시험과 배포에서 확인 가능한 범위

### 미구현·다음 일

1. **개인화 움직임 연결:** Atlas `loom.motion`을 앱의 공통 모션 입력과 장면의 기존 계수에 연결한다. 낮은 움직임 설정에서도 정보와 학습은 모두 전달되어야 한다.
2. **한 장면의 공유 시간:** 주민의 행동·소품·빛·바람을 같은 사건과 시간으로 움직이게 한다. Vellum이 반응을 정하고 Loom은 그것을 표현한다.

## Reed — 소리와 감상 경험

### 사용자가 느끼게 될 역할

필요한 소리는 적절히 나고, 공부나 녹음을 방해할 때는 조용해진다. 음악은 곡마다 갑자기 커지거나 반복 경계에서 끊기지 않도록 다듬는다. 음악을 아름답게 들려주는 것 자체가 Reed의 결과이며, 모든 소리에 사용자 추적이 붙어야 하는 것은 아니다.

- **현재 코드로 설명할 수 있는 예:** 한국어 녹음을 시작하면 효과음과 햅틱을 막고 BGM을 음소거한다. 녹음 중 못 들었던 효과음을 끝난 뒤 몰아서 재생하지 않는다. 라디오용 파일 목록은 장르 묶음과 순서에 따라 정리할 수 있다.
- **앞으로 만들 경험의 예:** 사용자가 “조용히”를 선택하면 마을의 가이드 소리·효과음을 줄이는 공통 결정이 적용되고, 녹음 도중에는 항상 무음 제한이 우선한다. 자동으로 사용자의 감정을 추측해 배경음악을 바꾸는 기능을 뜻하지 않는다.

### 준비된 설계

1. 승인 곡의 원본·사용 판·편집 조건·음량·피크·무음·이음새·사용처와 실제 청취 결과를 연결한다. AI 도구로 곡을 만들었다는 사실과 작품의 품질은 따로 확인한다. [R-1]
2. 개인 앱 자습 재생기·개인 청취 기록·곡 사이 개인 오답 개입은 현재 범위에서 접었다. 유튜브 라디오와 안내는 유지하는 방향이다. 사용자 수가 늘었다고 자동 복원하지 않는다. [R-1]
3. 방송의 집단 흐름을 보는 계기와 개인의 선호·집중·감정 추론을 구분한다. 동시 시청자 변화는 개인 체류나 특정 곡의 효과 증명이 아니다. [R-1]
4. 첫 Atlas 손잡이는 `reed.cues: on/quiet`이며, 녹음 중 무음·허용 목록·본인이 끈 소리를 되살리지 않는 제한을 우회할 수 없다. [공통-2]

- 현재 회사 전체의 배포 버전, 운영 DB·개인 기록, 로그인 상태, 모든 서버 함수, 현재 라디오 정상 여부.
- 전체 자동 시험 통과 여부, 오늘의 앱/웹 실제 렌더 결과, 실사용자의 만족·학습 효과, 모바일 발열·멀미·배터리.
- Unity·Unreal 프로젝트의 구현 정도와 배포, 16명 동시 접속 마을, 모든 콘텐츠로 이어지는 공통 SYNK 계정 기억.
- 설계가 링크하지만 현재 작업본에 없는 일부 과거 상세 산출물. 예: `experiences/loom-living/README.md`, `docs/라디오/선정무대_20260910/라이브13/반영보고.md`, `docs/_ops/라디오생동_20260909/v2/완료보고.md`. 이들은 존재하는 다른 원문·코드·최근 기록으로 범위를 좁혀 설명했고, 없어진 이유는 추정하지 않았다.

지도에는 “설계 / 코드 있음 / 특정 화면 연결 / 과거 게시 확인 / 현재 운영 확인 / 실사용 효과”를 별도 칸으로 보여 주는 것이 맞다. 세 엔진을 하나의 완료율로 합치면, 단독 기능의 이미 이룬 부분과 앞으로 필요한 Atlas 연결을 모두 오해하게 된다.
