OneDrive의 기존 작업 MD는 유지한다. QA·미디어 폴더 안의 작업 MD도 보관하되 의존성·빌드·캐시·Git 내부와 비밀값은 제외한다. 작업 분기(worktree)의 MD와 소스는 주 작업본과 같은 내용의 사본을 줄이고, 내용이 다르거나 주 작업본에 없는 파일을 원경로 목록과 함께 보존한다. 비밀 포함·내장 미디어·크기 등으로 제외된 문서는 복사 점검의 경로와 사유를 확인한다. 제외 기록이 남아 있으면 모든 작업 문서 보존을 완료했다고 해석하지 않는다.

## 새 컴퓨터에서 순서대로

1. **계정 접근부터 확보한다.** Microsoft·GitHub와 Google 두 계정에 로그인할 수 있는지 확인한다. 도난이었다면 해당 기기의 세션·자격을 폐기한다. 2단계 인증 복구 수단은 잃어버린 PC 밖에 있어야 한다.
2. **OneDrive에서 이 파일과 복원 목록을 받는다.** 먼저 `SYNK/복원 시작.md`를 연다. 원래 구조의 파일은 `SYNK/시스템/SYNK-appsscript/docs/컴퓨터를 잃어버렸을 때.md`에 있다. 새 백업의 ID·해시·범위와 남은 제한은 같은 OneDrive의 `SYNK/시스템/SYNK_원본창고/백업_복원안전목록.json`에서 찾는다. 이 목록은 기존 상태 원문에서 비밀값 없는 복원 필드만 골라 매번 갱신한다. 로컬 파일이 보이는 것만으로 전송 완료를 판단하지 않는다. 동기화 오류·대기 상태와 최근 복사 시각을 확인한다.
3. **작업 사본을 먼저 별도 보존한다.** `SYNK-appsscript`, `SYNK-talk`, `SYNK-website`, `SYNK_원본창고`를 새 PC의 같은 `Documents` 아래 나란히 복원한다. Videos 문서는 새 PC `Videos`의 원래 상대 경로로 돌린다. 사용자 이름이 달라도 기존 상대 링크가 연결되는 구조를 유지한다.
4. **개발 환경과 저장소를 준비한다.** Git·Node.js·Python 및 사용하는 공식 AI 앱/CLI를 설치한다. Git 이력이 필요하면 별도 폴더에 저장소를 내려받아 OneDrive 작업 사본과 차이를 확인하고 합친다. 아직 올리지 않은 사본 위에 강제 초기화나 checkout을 하지 않는다. 의존성은 각 저장소의 lock 파일·README를 따라 설치한다.
5. **공동 작업 입구를 읽는다.** `SYNK-appsscript/AGENTS.md` → [AI 운영 원칙](AI_운영원칙.md) → [문서 지도](문서_지도.md) → 해당 원문·최근 diff 순서로 이어간다. 브랜드 기준은 [DESIGN](../DESIGN.md), 엔진은 [담당 원문·코드](엔진8종_상향설계_v3.md#engine-owner-sources)에서 찾는다. 오래된 진행 메모를 최신 규칙으로 적용하지 않는다.
6. **필요한 미디어만 복원한다.** [원본창고의 OneDrive 이관 복원 목록](../../SYNK_원본창고/OneDrive_이관_20261018/복원목록.json)에 OneDrive 원래 경로 → Google 계정·파일 ID → 로컬 이관 경로가 기록된다. 목록에 실제 완료·검증이 기록된 항목만 보관 완료로 판단한다. 새 로컬 미디어 폴더는 OneDrive 밖에 둔다. 내려받은 크기·SHA-256을 영수증과 비교하고, 실제 코드·콘티의 그 경로 참조만 새 위치로 연결한다. 모든 문서의 과거 경로를 일괄 치환하지 않는다. 수노곡판·미니맥스곡생산의 새 음원 기본 위치는 `~/Videos/SYNK PULSE/음악/`, 단추판의 한눈에 그림은 `~/Videos/SYNK/엔진·브랜드/요소 검토`다. 예전 음원·그림은 이관 복원 목록에서 찾는다.
7. **자격과 암호화 백업을 별도로 복구한다.** `.env`, 토큰, 개인키, DB를 평문 OneDrive 소스에 넣지 않는다. Apps Script·Google·GitHub는 정상 로그인 절차를 다시 밟고 필요한 자격만 재발급한다. 암호화 백업은 아래 열쇠 조건이 갖춰졌을 때 격리 폴더에서 먼저 검증한다.
8. **실제 실행을 확인한다.** 요청 범위의 앱·스크립트를 실행하고 관련 시험·사용 화면을 확인한다. 예약 작업은 복원 설정·경로·사용자 권한을 확인한 후 재등록한다. 백업 종료값, 업로드 목록·원격 대조, 실제 복호화·복원 검증은 각각 확인한다.

LoRA 제작 환경은 원경로 목록에 따라 `C:\SYNK-LoRA`의 소스·설정을 먼저 복원하고, 모델과 학습 미디어는 20TB Drive의 해당 복원 목록에서 필요한 것만 받는다. 가상환경·설치 패키지는 소스의 의존성 목록과 실행 안내를 따라 다시 설치한다.

브랜드 킷·엔진지도·로드맵·성우 비교의 기존 HTML 5개는 내장 그림·음원·서체를 Google Drive 원문으로 보존하고, OneDrive의 같은 위치에는 이름 끝에 `_문서사본.html`을 붙인 가벼운 사본을 준비했다. 본문·설계 데이터·동작 코드는 유지하며 원본 링크를 문서 안에 표시한다. [HTML 원문 복원 안내](../../SYNK_원본창고/OneDrive_HTML_경량화_20261018/README.md)에 계정·파일 ID·해시가 있다. 기존 Drive 사본 일부는 API 다운로드 권한이 없으므로 그 계정으로 웹 링크를 열어 내려받는다. 메타데이터 해시 검증과 실제 재다운로드 검증은 안내에서 구분한다.

## 암호화 백업의 열쇠와 설정

원본창고의 `암호.js`는 암호화된 파일을 `비밀키_잠금.json`과 사용자가 기억하는 암호로 푼다. 기존 열쇠는 `~/.synk-backup-key/`에 있고, 복원용 사본은 OneDrive `SYNK/복구열쇠/`의 `공개키.pem`, `비밀키_잠금.json`, `읽어주세요.md`에 보관했다. 2026-10-18 기준 세 파일의 복사 후 해시와 OneDrive 공급자 `IN_SYNC` 상태를 확인했다. **잠긴 비밀키를 풀려면 사용자의 암호가 필요하며, 새 열쇠를 만들어도 옛 백업을 풀 수 없다.** 암호는 문서·로그에 적지 않는다. 2026-10-18 사용자가 로컬 입력창에 한 번 입력한 암호로 실제 Drive 암호문 11개를 복호화·해시 대조했다. 암호·풀린 개인키는 저장하지 않았다. 새 PC에서도 기존 열쇠와 암호로 격리 복원부터 확인한다. 입력 도구와 보호 조건은 [복원 시험 도구](../tools/restore-drill/README.md)에 있다.

원본창고 README의 talk DB 복원 절차·서버 백업 구조를 따른다. DB는 새 격리 대상에서 먼저 풀고 확인한다. PostgreSQL 클라이언트와 `%APPDATA%/postgresql/pgpass.conf` 같은 자격 경로는 새 PC에서 다시 준비하고 사용자 전용 권한을 적용한다. 앱의 별도 AppData 가상화 경로와 일반 예약 작업 경로가 다를 수 있다([백업 현장 노트](현장노트/백업_업로드.md)). 비밀값 없는 모니터 설정과 설치 스크립트가 있어도 Windows 예약 작업 자체는 새 PC에 자동 생성되지 않는다.

기존 `PC_백업_20261003/되살리기.py`는 같은 폴더의 `복원목록.json`을 읽는다. OneDrive에 보관한 `복원목록_최소.json`은 경로·Drive ID·계정·크기·해시 및 ZIP 내부 경로 등 복원 필드를 유지하므로, 새 PC에서 `복원목록.json`이라는 이름으로 복사해 사용할 수 있다. 기존 원문을 덮어쓰는 절차가 아니다. 그 도구가 전제하는 예전 OneDrive 게임 백업 ZIP은 [OneDrive 이관 복원 목록](../../SYNK_원본창고/OneDrive_이관_20261018/복원목록.json)에서 원래 경로를 찾아 Google Drive에서 먼저 내려받고, 확인한 ZIP 위치를 복원 실행에 사용한다.

## 평소 갱신과 확인

아래 Windows 예약은 로컬 소스·미디어와 추가 사본을 갱신한다. PC가 켜져 있고 해당 Windows 사용자로 로그인되어 있어야 하며, 꺼져서 놓친 예약은 다시 실행 가능한 때 처리한다. 서버 자료의 독립 예약은 이 표 다음에 구분한다. 미디어·옛 원본은 OneDrive에 다시 넣지 않는다.

| 보관소 | 자동 작업 | 주기 |
|---|---|---|
| OneDrive | 안전 문서·소스·작업트리의 다른 MD/소스 갱신, 전수 공급자 동기화 확인 | 30분·로그온 |
| GitHub | 비공개 저장소의 미보존 커밋을 전용 ref로 보존·원격 SHA 확인, 공개 저장소의 미게시 이력은 암호화해 20TB Drive에 보존 | 2시간·로그온 |
| 20TB `77yuhbs` | 서버·DB 암호화 받기와 원격 보존 / 새 미디어·같은 이름의 수정판 보존 | 매일 05:30 / 12:30 |
| 5TB `unmet23` | 기존 원본의 계정·파일 ID·휴지통 여부·크기·체크섬 대조 | 일요일 14:00 |

서버에서는 **매일 07:10 KST(+최대 2분)** 별도 `synk-server-backup.timer`가 실행된다. 회사 서버의 DB·객체·회사 DR·업무 문서/첨부, 조사 서버의 Argon·synkbrief, 라디오 서버의 운영 소스/설정과 백업 실행기 자체를 20TB의 `server-independent/<역할>/`에 암호화한다. 이 경로는 노트북 로그인과 독립이며 기존 PC 추가 백업도 유지한다. 원격 최종 영수증의 `sourceKey`·판본·계정·파일 ID·원문/암호문 해시를 기준으로 복원한다. 실행 경로·감시·역할별 확인 명령은 [서버 백업 README](../tools/server-backup/README.md)를 따른다.

서버 15분 감시는 실패·예약 해제·26시간 지연을 기존 Cloud Monitoring 이메일 채널로 알리며 라디오 원격 영수증도 확인한다. 별도 회사·조사 정상 신호 부재 정책은 45분 부재+10분 집계 후 판단하여 서버나 감시 프로세스 자체 중단도 잡는다. 정책 생성 뒤 실제 정상 신호 두 경로를 확인했다. 이메일 받은편지함 수신 및 실제 45분 중단 사고 시험은 확인 범위 밖이다. 로컬 Windows 알림과 서로 다른 경로다.

Git 점검에서 새 암호화 이력·보호 소스가 생기면 `SYNK Git 암호문 백업`을 바로 요청한다. 이 보조 예약은 기존 Drive 전송이 끝나면 같은 잠금을 받아 해당 묶음을 올리고 대조하며, 끝난 뒤 Git 상태를 다시 확인한다. 다음 날 미디어 예약까지 기다리지 않는다. 이미 실행 중이면 같은 전송을 중복 시작하지 않는다.

`SYNK 백업 상태 확인`은 15분·로그온마다 다섯 실행 경로의 영수증과 실제 예약 활성 여부를 확인하며 Git 암호문 전송 예약의 누락·비활성도 함께 감시한다. 실패·중단·예약 누락·오래 갱신되지 않은 백업은 Windows 알림 센터(Windows PowerShell 발신)에 알린다. 같은 문제는 하루 한 번만 다시 알리고, 정상 복구도 한 번 알린다. 알림 전달 실패는 다음 점검에서 재시도한다. OneDrive 정상 동기화 대기는 즉시 실패로 알리지 않지만 마지막 정상 확인이 2시간 이상 오래되면 지연으로 알린다. GitHub는 6시간, 미디어는 36시간, 옛 원본 점검은 8일이 기준이며 서버는 다음 05:30 예정에서 6시간의 실행 여유를 둔다.

통합 결과는 `SYNK_원본창고/backup-health.json`이다. OneDrive의 로컬 SHA·공급자 `IN_SYNC`, GitHub 원격 ref SHA, Drive 원격 메타데이터 대조, 실제 암호 복호화·전체 복원은 서로 다른 확인이다. 매일 실행의 실패 원장은 유지하며 별도 보완 성공은 `backup-repair-status.json`의 원래 실행 ID·수정 단계·대조 결과와 함께 읽는다. 부분 보완으로 전체 자료의 기준 시각을 새로 바꾸지 않으며, 보완 확인 시각은 `repairedAt`으로 구분한다.

- `python -X utf8 tools/backup-health.py`: 네 보관소의 최신 실행·예약을 조회한다. `--notify`를 붙인 때만 Windows 알림을 보낸다.
- `node tools/onedrive-backup.cjs`: 변경분을 복사하고 전수 동기화를 점검한다. 종료 0은 공급자 동기화 확인, 2는 대기, 1은 실패다.
- `node tools/GitHub백업.cjs --check`: 원격과 로컬 커밋 차이를 확인한다. `--apply`는 비공개 저장소의 안전한 커밋만 전용 ref로 보존한다.
- PowerShell 7에서 `./tools/install-four-backups.ps1`: 현재 PC의 경로·사용자로 네 보관소 예약과 통합 감시를 등록한다. 기존 서버 매일 예약이 있으면 유지하고, 새 PC에서는 Python·Node·백업 도구와 계정·열쇠부터 준비한다. 이전 작업 XML은 설치 증거 폴더에 보존한다.

- `node tools/이어하기꾸러미.js --재기 --원드라이브`: 대상과 제외 사유를 재확인한다. 실제 복사는 하지 않는다.
- `node tools/이어하기꾸러미.js --원드라이브`: 현재 문서·소스 사본을 갱신한다. 기존 목적지 파일을 자동 삭제하지 않는다. 실제 클라우드 동기화 완료는 별도 확인한다.
- `node tools/보존점검.cjs`: 현재 보관 영수증과 로컬 원문 차이를 확인한다. 클라우드 원격 존재·실제 복원을 대신하지 않는다.
- 원본창고의 `python -X utf8 백업상태.py`: 마지막 정기 백업의 상태를 읽는다. 부분 실패를 전체 성공으로 해석하지 않는다.

GitHub 전용 백업 ref는 기본 clone에서 자동으로 내려오지 않는다. 새 별도 clone에서 `git ls-remote origin 'refs/synk-backup/*'`로 보관 SHA를 찾고, `git fetch origin refs/synk-backup/<40자리SHA>` → `git switch -c recovered-YYYYMMDD FETCH_HEAD`로 복원한다. 원래 작업본이나 기본 가지를 강제로 덮지 않는다. 새 미디어와 암호문은 원본창고의 `원본_복원목록.json`·`서버_복원목록.json`(분할 파일이 있으면 함께)에 기록된 계정·ID·해시로 받는다.

큰 산출물 등이 들어 있어 GitHub 보관 정책을 통과하지 못한 비공개 저장소의 옛 이력은 20TB Drive의 `Git-보관`에 암호화한 Git bundle과 manifest를 함께 보관한다. 두 파일을 복원 목록으로 찾아 내려받고 해시를 비교한 뒤, 기존 열쇠·암호로 원본창고에서 `node 암호.js 풀기 <파일.bundle.enc> <별도경로/복원.bundle>`을 실행한다. 별도 clone에서 manifest의 `prerequisites`마다 `git fetch origin <ref>`를 실행하고, `git bundle verify <복원.bundle>`으로 확인한 뒤 `git fetch <복원.bundle> <원래ref>:refs/heads/recovered-YYYYMMDD`로 별도 가지에 가져온다. 암호문 생성과 원격 보존, 실제 사용자 열쇠로 복호화한 결과는 구분한다. 정확한 절차와 현재 증거는 [Git 자산 보관](_ops/github-storage/README.md)을 따른다.

공개 저장소에 아직 게시하지 않은 가지·stash·분리 작업 이력이 생기면 공개 원격에 쓰지 않고 같은 Drive 경로로 암호화해 보존한다. 이 경우에는 선행 커밋이 필요 없는 완전 bundle을 만들므로 빈 저장소에서도 복원할 수 있다. 처음에는 전체 조상 이력을 포함해 파일이 클 수 있다.

비밀값이 있거나 포함 여부를 확정하지 못해 OneDrive 평문 사본에서 제외한 소스는 `Git-보관/protected-sources/`의 개별 `.source.enc`와 manifest로 보존한다. 미커밋 원문도 포함하며, 파일 내용이 바뀌면 기존 암호문을 유지하고 새 버전을 만든다. 원본창고의 복원 목록에서 두 파일을 받아 암호문 해시를 확인하고, `node 암호.js 풀기 <파일.source.enc> <별도경로/원래파일명>`으로 푼 뒤 manifest의 원문 SHA256·크기와 대조한다. 실제 비밀번호·토큰을 OneDrive로 옮기거나 이 안내에 적지 않는다. 로컬 암호문 생성만으로 원격 보존이 끝난 것은 아니므로 `protected-source-backup-status.json`의 현재 원문 지문·원격 검증을 확인한다.

## 업무 문서·조사 서버·앱 데이터 복원

[플랫폼 데이터 계약](SYNK_플랫폼_계정과_연결_설계.md#platform-data-storage-20261018)이 계정별 역할과 실제 연결을 정한다. 앱의 계정·학습·개인 문서는 기존 Supabase DB와 비공개 객체 저장소, Workspace 업무는 회사 서버와 unmet23의 지정 문서·첨부를 정본으로 사용한다. Drive 5TB·20TB는 서버 디스크를 늘리는 설정이 아니다.

기존 매일 05:30 백업에 `Workspace백업.js 받기`와 `Argon백업.js 받기`, `workspace-백업`·`argon-백업` 묶음을 연결했다. 지정한 업무 원문과 운영 DB에 등록된 원격 첨부를 수집하고, 조사 서버의 설정·이전 본문·상태·재인증에 필요한 기존 자격을 암호화한다. 조사 작업이 실행 중이면 상태 백업은 최대 30분 기다린 뒤 재시도하며, 계속 실행 중이거나 본문·목록이 달라지면 실패를 남긴다. 원본을 멈추거나 삭제하지 않는다.

`workspace-collection-status.json`과 `argon-백업/latest.json`은 **수집 확인**이다. `workspace-backup-status.json`은 두 수집과 각 묶음의 전송·원격 대조까지 완료한 결과이며 기존 15분 알림에서 별도로 감시한다. 첫 검증은 원본창고에서 `python -X utf8 -B 매일백업.py --workspace-only`로 두 묶음만 실행할 수 있다. 원래 회사·DB 백업 영수증은 덮지 않는다. 암호문은 `서버_복원목록.json`에 분류된다.

업무 문서 복원 시 원래 계정·문서 ID·판본·내보낸 형식·해시를 manifest로 대조한다. DOCX/XLSX나 Docs 구조 JSON 사본이 원래 문서의 전체 수정 이력·공유 권한까지 복원하지는 않는다. `workspace-백업/pending-native.json`은 수집 범위 밖 문서와 권한 제한 목록이며, 소유 문서 목록 조회만으로 백업됐다고 판단하지 않는다. 원문 ID를 새 사본 ID로 일괄 교체하지 않는다.

메신저는 회사 DB·원래 암호화 키·Drive 연결 정보·첨부 본문을 함께 복원한다. Argon은 암호문 안의 allowlist·SHA·원래 경로와 별도 보존한 `tools/argon-schedules` 소스로 복원하고, 옛 인증을 무조건 활성화하지 말고 필요한 계정만 정상 재인증한다. Supabase는 DB와 객체 본문을 함께 대조하며 사본 이후 삭제·동의 철회가 되살아나지 않게 확인한다. 운영 복원 전 격리 검증이 필요하다. 회사의 GCS 백업과 위 20TB 서버 사본·Supabase 일일 백업은 서버에서 실행한다. Windows의 05:30 경로는 추가 사본으로 유지한다.

### 2026-10-18 실제 복원 시험과 남은 인수

- 사용자 기존 키로 실제 암호문 11개 복호화·크기/SHA256 일치: 업무 6, Argon, PostgreSQL, Git, 회사 Workspace, 회사 DR. 업무 파일 구조와 Argon 42원문의 SHA도 확인했다.
- Git 6개 이력은 별도 저장소에 실제 복원했다. 필요한 선행 이력은 비공개 GitHub에서 받고 bundle 검증·연결 검사·6개 소스 읽기를 확인했다. 선행 전체 blob을 미리 내려받은 완전 오프라인 clone은 아니다.
- 회사 DR 1,086파일·이미지 3개와 DB 2개를 검증하고, 외부 네트워크 없는 컨테이너에서 기존 키·자격정보 11건·참조 파일 24건·앱 기동·페이지 3개·비로그인 거부까지 확인했다. 실제 사용자 로그인과 운영 트래픽 전환은 하지 않았다.
- Supabase 동일 계열 격리 복원에서 124테이블·127,729행 전수 해시 일치, Vault 5행 실제 해독을 확인했다. 스키마 정의 1,295개는 존재하지만 확장 생성자의 차이로 ACL/소유자 표기 17개가 달랐다. 서비스 재개 전 관리 역할·권한과 삭제/동의 상태를 추가 인수해야 한다.
- Vault 루트키는 DB 덤프와 별개의 필수 복구 자료다. `SYNK_원본창고/talk-백업/vault-root/<projectRef>/`의 암호문·manifest와 `supabase-vault-key-backup-status.json`의 20TB 원격 ID를 함께 보존한다. 덤프가 요구하는 `rootKeySha256`과 캡슐을 대조한 뒤 임시 제한 경로에서만 푼다. 키를 회전하면 원본창고의 `node SupabaseVault키백업.cjs`로 새 캡슐을 수집한 뒤 20TB 원격 검증과 서버 dependency 갱신까지 마친다. 로컬 수집 성공만으로 원격 보존을 판정하지 않는다. 격리 PostgreSQL에서는 `supabase_vault`를 preload하고 `vault.getkey_script`가 제한된 임시 파일의 원키를 반환하도록 구성해야 했다. 기존 Management API 토큰을 상시 서버로 옮기거나 키를 자동 회전하지 않았다.
- 옛 문서는 우선 9개를 별도 수집·암호화·원격 재다운로드까지 확인했다. 우선순위 밖 1,121개는 미수집으로 남아 있으며, 이 9개와 새 Vault 키 캡슐은 앞의 사용자 키 복호화 11개에 포함하지 않는다.

서버의 시험 컨테이너·DB·임시 원키·우리 시험 사본은 정리했다.
