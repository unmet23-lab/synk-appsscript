# SYNK 장애·복구 안내

> 2026-10-17 문서 정리. 서비스별 현재 담당 원문으로 연결한다. 이번 정리는 실제 서버·백업·트리거를 조회하거나 변경한 작업이 아니다.

## 먼저 서비스와 증거를 확인한다

장애가 난 주소·발생 시각·화면의 오류·마지막 정상 동작을 남긴다. 토큰·비밀번호·학생 식별 정보는 캡처와 전달 자료에서 가린다. 같은 노트북에 파일이 있다는 이유로 모든 서비스가 노트북에서 실행된다고 보지 않는다.

## Apps Script에 남아 있는 것

2026-10-02 학원 운영 Apps Script는 제거됐다. 현재 배포 목록은 `.claspignore`의 `Code.js`·`엔진_synkbrief.js`·`appsscript.json`이다. 댓글·DM 처리와 Meta 토큰 갱신의 운영 원문은 Supabase `synkbrief-dm`이며, Apps Script는 운영 상태 메일과 기존 호환 입구를 맡는다.

- 알림 문제는 Apps Script의 실행 기록과 현재 트리거 목록에서 실패 시각·함수를 먼저 확인한다. `synkbrief운영알림상태()`는 관리자에게 활성 상태·키 설정 여부·마지막 점검·메일 상태·현재 사용자 소유 타이머 수를 보여 준다. 값이 없거나 오래됐으면 정상으로 간주하지 않는다.
- `synkbrief정기점검`은 명시 설정된 운영 점검 타이머다. `트리거정리()`는 다른 핸들러를 제거하는 변경 함수이므로 단순 상태 조회나 만능 복구 버튼으로 실행하지 않는다. 필요한 설정·복구는 DM 담당 원문과 실제 상태를 대조한 뒤 수행한다.
- 옛 `resetAllTriggers`, `triggerManifest_`, 출석·포인트·상담·시즌회고 배치는 현재 복구 대상이 아니다. `dailyBackupJob` 등의 이름은 옛 트리거 정리용 호환 함수로만 남아 있으며 데이터 백업을 수행하지 않는다.

## 배포 뒤 문제가 생겼을 때

마지막 정상 배포판과 문제가 난 배포판을 확인하고, 해당 서비스의 배포 절차로 필요한 코드·설정·공개 버전을 함께 대조한다. 편집기에 파일을 붙여넣고 저장한 사실만으로 공개 웹앱의 복구를 완료했다고 판단하지 않는다. 이전 학원 엔진 전체를 복원하거나 `clasp pull`로 현재 공동 작업본을 덮어쓰지 않는다.

긴급하게 원격 코드를 고쳤다면 바꾼 파일·배포판·시각을 남겨 저장소와 다시 맞춘다. 정상 동작은 해당 주소의 실제 요청·응답·수신 결과로 확인한다.

## 데이터 복구가 필요할 때

‘매일 백업되므로 하루 정도는 안전하다’는 옛 안내는 폐기한다. 실제 백업의 생성 시각·대상·완료 기록·해시와 복원 가능한 범위를 확인한다. 회사 VM 사본은 Supabase 데이터·Drive 원문·계정 접근 권한 전체의 백업이 아니다.

회사 데이터는 위의 서버 복구 절차에 따라 원래 DB·암호 키·등록 파일을 함께 보존하고 새 격리 위치에서 먼저 검증한다. 손상된 원본 위에 옛 시트나 빈 DB를 바로 덮어쓰지 않는다. 마지막 정상 사본 이후의 기록 누락과 중복 실행 여부까지 확인한 뒤 운영 전환을 판단한다.
