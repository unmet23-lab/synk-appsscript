# 학생 ID 종단 설계 v2.1

> 2026-09-13 · Core·Trail이 같은 사람의 입학, 학습, 종료와 이후 소식을 잇는 기준.
> 현재 [철학](SYNK_철학.md), [철학 적용 기준](철학_적용기준.md), [엔진 설계](엔진7종_상향설계_v3.md)를 따른다.
> 과거 판정 경위와 당시 실측은 [v2 고정판](https://github.com/unmet23-lab/synk-appsscript/blob/f657502b1c85/docs/학생ID_종단_설계.md)에 남긴다. 끝난 판정과 옛 개원·졸업 예정일을 작업 대기로 되살리지 않는다.

## 0. 목적

학생이 졸업 뒤 연락처나 계정을 바꾸어도 자신의 학습 기록과 이어질 수 있게 한다. 오래 쌓인 기록을 학생의 다음 선택과 지원에 쓸 수 있어야 하며, 번호나 연락처를 오래 보관했다는 사실만으로 동일인 확인이나 계정 복구가 완성되지는 않는다.

## 1. 범위

이 문서는 식별자, 번호 발급, 재학·종료 사건, 시간의 뜻, 연락처와 기록 반환의 연결을 정한다. 로그인·복구 구현은 Talk 인증 계약, 공개 사례·학습자료 활용은 해당 동의 계약, 학생이 받는 물건은 [가져가는 것](가져가는것_설계_v1.md)이 정한다.

내부 집계나 파생 저장소의 구현 방식은 실제 소비자·비용·재생성 가능성에 따라 바꿀 수 있다. 과거에 표를 만들지 않았다는 결정이나 당시 학생 수를 영구 금지로 쓰지 않는다. 원본 사건의 보존과 사람의 동일성은 유지한다.

## 2. 현재 구현과 남은 연결

2026-09-13 저장소 코드 대조이며 라이브 데이터 실측은 아니다.

| 자리 | 확인한 구현 | 남은 확인·구현 |
|---|---|---|
| 번호 발급 | `엔진_폼리포트.js`의 `학생ID_발급_`·`학생ID카운터세우기`, `tests/학생ID종단.test.js` | 실제 카운터 초기화·라이브 발급 이력 |
| 종료 사건 | `엔진_운영배치.js`의 `exitLog시트_`·`퇴소사건필요_`·`syncProfiles`; 복학 후 재퇴소도 새 사건으로 기록 | 사건 기록 후 명부 삭제 전 실패하면 중복 사건 가능; 재처리 판단 보완 |
| 종료사유·종료일 | `EXIT_LOG_HEADERS`와 여섯 종료사유가 이미 구현됨 | 사람이 입력한 사유·효력일의 실제 충실도 |
| Talk 생애주기 | `20260902600000_learner_lifecycle_c16.sql`에 다섯 열 존재 | `exit_log`를 Talk에 전달하는 `trail-sync` 구현은 현재 functions에서 찾지 못함 |
| 입학 시즌 | 시트 `ENTRY_SEASON_HEADS_`·명부스윕, Talk `20260907100000_learner_entry_season_c16.sql`·`roster-ingest` 연결 | 실제 운영에서 전달된 행·정정 절차 |
| 복구 연락처 | Talk auth의 `recovery_email` 저장 경로 | 연락처를 이용한 계정 복구·계정 연결 사건의 완결성 |
| 학생에게 번호 전달 | 기록장·증서 조판 도구 존재 | 학생 앱 표시, 실물 수령, 분실 후 재연결 결과 |

## 3. 세 가지 식별자를 구분한다

| 식별자 | 뜻 | 변경 원칙 |
|---|---|---|
| `learner_id` | 기록을 잇는 내부 사람 키 | 다른 사람에게 재사용하지 않는다 |
| `student_code` | 사람이 읽는 학원 번호. 예: `SYNK-042` | 졸업·복학·개명 후에도 같은 번호, 재발급·재사용하지 않는다 |
| `auth_user_id` 등 로그인 주체 | 현재 계정이 누구의 기록에 접근하는지 정하는 인증 연결 | 복구·계정 변경은 본인 확인과 연결 이력을 통해 처리 |

번호가 같거나 UUID가 있다는 것만으로 두 계정의 동일인을 확인하지 않는다. 앞으로 다른 상품의 계정 체계를 연결할 때도 학원 번호를 모든 사용자에게 강제할 필요는 없다.

## 4. 규약과 데이터베이스 보장을 구분한다

`unique`는 중복을 막지만 기존 번호의 변경을 막지는 않는다. `on delete restrict`는 연결된 자식 기록이 있을 때 삭제를 막으며, 자식이 없는 학생 행이나 부모의 번호 변경까지 보장하지 않는다.

현재 검색에서 `student_code` 변경을 차단하는 전용 트리거는 확인하지 못했다. 번호 불변·계정 복구 계약을 구현할 때 실제 변경 경로와 권한을 함께 검증한다. 종료 처리를 `learners` 삭제로 대신하지 않는다. 적법한 삭제·철회 처리는 해당 데이터 계약에 따라 기록 연속성과 충돌하는 부분을 명시해 처리한다.

## 5. 수집·연결 기준

### ㉠ 번호는 되돌아가지 않는다

상담시트의 현재 최대 번호만 보고 다음 번호를 만들면 마지막 행 삭제 뒤 번호가 재사용될 수 있다. 영속 카운터는 현재 코드의 방식대로 발급 번호를 먼저 예약한 뒤 학생 행에 쓴다. 잠금 안에서 예약하며 행 쓰기가 실패해도 번호를 되돌리지 않는다. 빈 번호가 생기는 편이 다른 사람의 기록이 합쳐지는 것보다 낫다.

초기 카운터는 과거 발급 이력·보존 자료와 대조한 최대값으로 세운다. 카운터가 없거나 유효하지 않으면 임의로 1부터 발급하지 않는다. 현재 발급 시험은 카운터 부재, 예약 순서, 쓰기 실패 후 재사용 방지를 다룬다.

### ㉡ 종료는 사건으로 남긴다

정본은 `exit_log`다. 납입시트의 `payStatus`와 상담시트의 `처리상태`는 입력원이며 종료 사건과 같은 뜻으로 쓰지 않는다.

- 종료사유는 현재 코드의 `졸업·중도이탈·휴학·이사·미정·기타` 여섯 값이다. 빈칸은 아직 기록하지 않은 상태다. 기존 값의 의미를 바꾸면 과거 행 처리까지 검토한다.
- 퇴소감지일은 기계가 알아챈 날, 종료일은 실제로 끝난 날이다. 자동으로 알 수 없는 종료일·사유를 만들어 넣지 않는다.
- 휴학→복학→재퇴소는 한 학생의 새 사건이다. 현재 코드는 마지막 사건 이후 명부에 돌아온 흔적을 읽어 재퇴소를 기록한다. 학생당 최초 한 번만 기록한다는 옛 제한은 폐기한다.
- 새 열은 기존 위치 기반 소비자를 보존하며 추가한다. `마지막_완료_시즌ID`는 완료 판정과 시즌 식별자 계약을 먼저 맞춘 후 기록한다.

### ㉢ 복구 연락처와 로그인 통로는 다르다

현재 결정은 **성인에게 선택으로 받고 마지막 시즌에 한 번 권하는 연락처**다. 미성년자의 복구 연락처 수집을 자동 확대하지 않는다. 연락처가 없는 졸업생이 생길 수 있으므로 안내·실제 복구 결과를 보고 개선한다. 특정 연도까지 재검토를 금지하지 않는다.

`recovery_email` 열과 저장 경로가 있어도 이메일 로그인, 본인 확인, 계정 복구가 생기는 것은 아니다. 기존 한 학생·한 계정 구조를 바꿀 때는 연결 사건과 이전 계정 접근 회수를 함께 설계한다. 주소를 새 계정에 복사하는 것으로 동일인을 단정하지 않는다.

### ㉣ 시각과 생애주기 상태

| 값 | 뜻 |
|---|---|
| `enrolled_at` | 상담시트 등록일. 첫 반배정일과 다르다 |
| `observed_at` | 종료를 기계가 관측한 시각 |
| `effective_at` | 실제 종료 효력 시각. 원천이 없으면 미확인 |
| `exit_reason` | 종료 사건의 사유 |
| `lifecycle_status` | `재학·종료·미상`; 기본 `미상`은 정상 재학으로 세지 않는다 |
| `entry_season` | 첫 반배정이 속한 시즌의 시작일 키 `yyyy-MM-dd`. 등록일에서 추정하지 않는다 |

앞의 다섯 열은 Talk에 이미 추가되어 있다. 열이 존재하는 것과 `exit_log` 사건을 읽어 값이 갱신되는 것은 별개다. 종료일 공란을 관측일로 대체하는 현재 소비자는 그 한계를 드러내며, 실제 종료일인 것처럼 보고하지 않는다. 재입학 등 새로운 사건을 도입할 때 최신 상태를 접는 규칙을 명시한다.

입학 시즌은 시트와 Talk 양쪽에 연결되어 있다. 현재 코드가 한 번 채운 값을 자동 덮어쓰지 않으며 Talk도 `entry_season is null`인 행만 채운다. 정정은 두 곳의 첫 값과 이력을 확인한 뒤 처리한다. 모르는 과거 값을 소급 추정하지 않는다.

### ㉣-2 수신 성공과 값 반영을 구분한다

명부 인제스트는 재학생 중심이므로 명부에서 사라진 것만으로 종료를 알 수 없다. 종료 원천을 별도로 전달하고, 누락·미등록 식별자·알 수 없는 값·실패를 실제 처리 결과에서 드러내야 한다. HTTP 성공이나 정상 배치 종료를 모든 열의 반영으로 해석하지 않는다.

생애주기 `미상`과 인제스트 성공 여부를 한 값에 섞지 않는다. 받은 원본, 유효한 변경, 적용 실패를 구분해 재처리해도 원본 사건을 잃지 않게 한다. 새로운 중앙 검문·승인 큐를 기본으로 만들 필요는 없다.

### ㉤ 학생이 자기 번호를 들고 나간다

학생의 기록장·증서에는 자기 번호가 무엇인지, 언제 쓰는지, 잃었을 때 어디로 연락하는지 이해할 수 있게 설명한다. 문구는 현재 브랜드 기준을 따른다. 내부 `learner_id`를 학생이 기억하거나 복사하게 만들지 않는다.

졸업 뒤 기록 열람과 학습 이용 권한은 분리한다. 졸업했다고 모든 학습 기능을 일괄 잠그지 않는다. 정규 과정 후 첫 TOPIK 4급 미달 시 **앱 계정 6개월 무료 온라인 케어**는 현재 [철학](SYNK_철학.md)의 계약대로 적용한다.

### ㉥ 개인정보와 활용 동의

개별 식별자·이름·연락처·궤적 원본은 내부 계약과 본인에게 반환하는 경로에서만 다룬다. 본인에게 자기 번호를 전달하는 것과 명단을 외부에 공개하는 것을 혼동하지 않는다.

외부 보고는 승인된 비식별 집계를 사용한다. 소수 집계의 재식별 가능성도 고려한다. `outcome_log`의 `활용동의` 없는 행은 사례로 쓰지 않는다. 공개·홍보·학습자료 승격의 동의는 각각 해당 목적 계약을 따르며 연락처 제공을 다른 활용 동의로 대신하지 않는다.

## 6. 다음 구현은 실제 사용 시점에 맞춘다

번호 발급과 사건 수집은 기록이 생기는 시점부터 지킨다. 남은 작업은 종료 인제스트, 생애주기 상태 접기, 계정 복구·연결, 학생의 실제 번호 수령과 재연결이다. 과거 연도·라운드·특정 모델 배정을 지금의 선행 조건으로 유지하지 않는다.

새 파생 테이블이나 연결 기능이 필요하면 실제 입력·소비자·이동 계약을 설계한다. 기존 append 원장을 버리거나 불명확한 과거 날짜를 채워 넣지 않는다.

## 6-2. 읽는 자리

| 소비자 | 필요한 값·변화 |
|---|---|
| Core·Temper | 같은 사람의 근거를 연결하고 재학·종료 코호트의 뜻을 지킨다 |
| Trail | 종료·성과·입학 시즌의 시간 축을 잇고, 실제로 읽은 범위만 학생·강사에게 전달한다 |
| Prism | 동의와 확인 등급을 통과한 집계로 성과·약속 이행을 본다. 분모 0은 미확인이다 |
| 학생의 기록·계정 | 자기 기록 열람, 안내된 번호, 본인 확인을 통한 재연결 |

`my_trail`·`trail-sync` 등 상위 설계의 후보 이름을 현재 구현 완료로 읽지 않는다. 소비자별 실제 배선은 [엔진 도달](엔진도달_설계.md)과 코드에서 확인한다.

## 7. 아직 확인하지 않은 것

라이브 카운터와 학생 코드 무결성, 실제 종료사유·날짜 입력률, Talk 종료 인제스트, 학생의 앱 번호 표시와 실물 수령, 이메일 복구 왕복, 과거 행에 대한 변경·삭제 방지는 이번 문서 정리로 검증하지 않았다. 원본 없는 시간·동일인 연결은 미확인으로 남긴다.

## 8. 현재 결정

종료사유 여섯 값, 성인 선택 연락처·마지막 시즌 안내, append 종료 원장은 2026-08-30에 정해져 코드와 연결됐다. 이를 미판정 네 건으로 다시 열지 않는다. 저장 모양·재검토 연도·당시 학생 수는 제품 발전을 막는 규칙이 아니다. 목적·동의·기록 연속성에 영향을 주는 변경은 현재 계약에 맞추어 구체적으로 처리한다.

## 9. 유지 기준

같은 사람의 원본 기록을 보존하고, 모르는 값은 모른다고 남기며, 그 기록이 실제로 읽혀 학생의 다음 선택과 지원에 도움이 되는지 확인한다.
