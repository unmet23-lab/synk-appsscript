# 학원 운영 최소판 — 출결과 TOPIK 만료 관리 (설계, 2026-11-27)

> 이 표는 11월 27일의 계획이다. 진행과 남은 일은 [트랙](../../_ops/트랙.md)이 잇는다.

## 1. 목적

모두의 창업 1R 사업계획서(11-26 개선본) Q2 표 1은 운영 앱이 「출결 관리, TOPIK 만료일 자동 추적 → 만료 전 4급 갱신까지 관리」를 「실가동」한다고 적었다. 지금 워크스페이스에는 이 기능이 없다(10-02 옛 시트 시스템을 지울 때 출석도 함께 없어졌다). 유호님이 11-27 「응, 둘 다 만들어」로 12월 1일 13시 제출 전에 만들어 이 문장을 사실로 만들기로 하셨다.

실학생은 아직 0명이다(몽골 직영 어학원은 2027년 9월 개원). 이번 판의 목표는 교사와 원장이 실제 반에서 쓸 수 있는 기능을 운영에 올리고, 시험 반으로 동작을 확인하는 것이다.

## 2. 쓰는 사람과 흐름

| 사람 | 하는 일 | 자리 |
|---|---|---|
| 교사 | 오늘 수업의 출결을 반 명단에서 한 번에 찍는다. 학생의 TOPIK 회차 · 급수 · 성적 발표일을 넣는다. | 워크스페이스 「내 수업」 → 반 |
| 원장(staff 역할 `director`) | 하루 한 번 배정된 반 전체의 요약을 본다: 오늘 결석 · 지각, 3회 연속 결석, TOPIK 만료 90일 안 학생. | 워크스페이스 첫 화면 「내 차례」 카드 한 장 → 원장 요약 |

1. **출결.** 반 화면 위에 「오늘 출결」 띠. 날짜(기본 오늘, 서울 시각), 명단 한 줄마다 `출석 · 지각 · 결석 · 공결` 네 단추와 사유 메모(200자). 「모두 출석」 한 번 누르고 예외만 바꾼다. 저장하면 줄마다 저장 시각과 찍은 사람이 남는다. 지난 날짜도 고칠 수 있고, 고치면 revision이 오른다.
2. **TOPIK.** 학생 줄의 「TOPIK」 칸에서 회차(예: 제105회), 급수(1~6, 미달은 0), 성적 발표일을 넣는다. 만료일은 발표일 + 2년으로 서버가 계산한다(국립국제교육원 TOPIK 안내: 성적 유효기간은 발표일로부터 2년). 배지: `유효`, `90일 안 만료`, `30일 안 만료`, `만료`. 한 학생에게 여러 회차를 쌓고, 가장 최근 유효 성적을 대표로 보인다.
3. **원장 요약.** 오늘 결석 · 지각 수, 최근 수업 3회 연속 결석인 학생, 만료 90일 안 · 만료된 학생과 대표 급수. 학생 이름을 누르면 그 반의 학생 줄로 간다. 같은 요약이 「내 차례」에 카드 한 장(「TOPIK 만료 임박 n명 · 연속 결석 n명」)으로 오르고, 0명이면 오르지 않는다.

외부 알림(메신저 · 문자 · 텔레그램)은 이번 판에 넣지 않는다. 워크스페이스 화면과 「내 차례」만 쓴다.

## 3. 데이터 (중앙 Supabase `engine` 스키마)

기존 「담당 반과 학생 케어」와 같은 사슬을 쓴다. 회사 서버 SQLite에는 학생 자료를 두지 않는다(WORKSPACE_ACCESS 「LAB 수업 데이터를 옮기지 않는다」).

```sql
create table engine.synk_class_attendance (
  attendance_id uuid primary key default gen_random_uuid(),
  class_id uuid not null references engine.classes(class_id),
  learner_id uuid not null references engine.learners(learner_id) on delete cascade,
  session_date date not null,
  status text not null check (status in ('present','late','absent','excused')),
  note text not null default '' check (char_length(note) <= 200),
  recorded_by uuid not null references engine.staff(staff_id),
  revision integer not null default 1,
  created_at timestamptz not null, updated_at timestamptz not null,
  unique (class_id, learner_id, session_date)
);
create table engine.synk_learner_topik (
  topik_id uuid primary key default gen_random_uuid(),
  learner_id uuid not null references engine.learners(learner_id) on delete cascade,
  class_id uuid not null references engine.classes(class_id),
  test_round text not null check (char_length(test_round) between 1 and 20),
  level smallint not null check (level between 0 and 6),
  announced_on date not null,
  expires_on date generated always as ((announced_on + interval '2 years')::date) stored,
  recorded_by uuid not null references engine.staff(staff_id),
  revision integer not null default 1, idempotency_key text not null, fingerprint text not null,
  created_at timestamptz not null, updated_at timestamptz not null,
  unique (learner_id, test_round), unique (class_id, recorded_by, idempotency_key)
);
```

- 두 표 모두 RLS를 켜고 정책은 0이다. 함수(`synk-classroom`)만 읽고 쓴다.
- 학생 계정이 지워지거나 반에서 빠지면 기존 케어 삭제 트리거와 같은 자리에서 두 표의 그 학생 행을 지운다.
- 한 반의 출결 행은 학생 수 × 수업일만큼 쌓인다. 한 반 상한 20,000행, 한 학생 TOPIK 상한 20행을 둔다.

## 4. 권한과 개인정보

- 교사: 자기 반(`staff_classes`)의 학생만 읽고 쓴다. 원장: 자기에게 배정된 반들의 요약만 본다(전체 반 범위는 이번 판에 만들지 않는다. 원장을 모든 반에 배정해 쓴다).
- **여쭐 것 (유호님):** 지금 케어는 학생이 계정을 잇고 공유를 켠 경우만 다룬다. 출결과 TOPIK 성적은 학원이 수강 계약을 이행하려고 남기는 기록이라, 앱의 학습 공유 동의와 따로 **반 명단에 오른 모든 학생**에게 적용하려 한다. 교사와 원장만 보고 학생 앱에는 이번 판에 보이지 않는다. 처리방침 「SYNK 계정과 학습 기록」 절에 「학원 수강생의 출결과 TOPIK 성적(회차 · 급수 · 발표일)」 항목과 보관 기간(수강 종료 후 1년)을 더한다.
- 저장소에는 실학생 자료를 적지 않는다. 시험 반은 지어낸 이름만 쓴다.

## 6. 시험 계획

- 만료 계산: 발표일 + 2년, 윤년 2월 29일(→ 2월 28일 또는 3월 1일, Postgres `interval '2 years'` 결과를 시험으로 고정), 서울 날짜 경계.

- 삭제: 학생 계정 삭제 · 반 제외 시 두 표의 행이 사라짐.
- 회사 서버: `teaching-service.test.mjs`의 경로 허용 목록과 반 범위.

## 9. Fable 설계 검토 반영과 유호님 결정 (11-27 새벽)

Fable 판정은 「고쳐서 짓기」였다(SYNK-talk origin/master `fe95977b` 기준). 유호님은 적용 범위를 「공유 켠 학생만」으로 정하셨다. 그래서 아래처럼 고쳐 짓는다. 위 절과 다르면 이 절이 맞다.

- **범위:** 기존 케어의 `eligible()`(계정을 잇고 공유를 켠 학생)과 같다. 두 표에 `synk_user_id not null`과 `sharing_revision`을 두고, 읽을 때 케어처럼 지금 공유 revision과 맞는 행만 보인다. 공유를 끄면 보이지 않고, 다시 켜면 새 revision부터 쌓인다.
- **삭제:** `on delete cascade`를 쓰지 않는다. 기존 `synk_teaching_account_deleted` 트리거(계정 `status='deleted'` → `synk_user_id`로 지움)에 두 표를 더한다. 반에서 빠진 학생(`active=false`)의 행은 케어와 같이 남기되 읽지 않는다. 처리방침의 보관 문장은 케어와 같은 기준으로 맞춘다.
- **원장:** 역할 값을 새로 내지 않는다. 「담당 반 요약」을 기존 `/api/teacher/overview` 응답에 한 구역(`attendance`, `topik`)으로 더해 교사와 원장(원장은 모든 반에 배정) 모두에게 보인다. 별도 원장 경로와 「내 차례」 카드는 다음 판으로 미룬다.
- **모듈:** `synk-classroom-teaching.js`에 넣지 않고 숙제처럼 별도 저장 모듈(`store.attendance`, `store.topik`)로 둔다.
- **TOPIK 표:** `kind`(`I` · `II`), `round integer`, `unique(learner_id, kind, round)`. `class_id`는 두지 않고 학생의 반을 따른다. 요약에 「유효한 4급 이상 없음」을 더한다.
- **출결 묶음 저장:** 명단 전체를 한 트랜잭션으로 저장하고, 한 줄이라도 revision이 어긋나면 전부 409. 멱등 키를 둔다. 「최근 수업」은 그 반에 출결 행이 있는 날짜로 센다. `(class_id, session_date)` 인덱스.
- **날짜:** 화면이 학원 현지 날짜를 보내고 서버는 범위(오늘 + 1일까지, 400일 전까지)만 검사한다. 만료 배지 기준일을 응답에 함께 준다.
- **처리방침:** 「SYNK 계정과 학습 기록」 절에 출결과 TOPIK 성적을 더하는 문구를 운영 반영 **전에** 공개한다. 그 전에는 기능 스위치를 꺼 둔다.
- **시험 더함:** 잇지 않은 학생 거절, 보관 · 삭제, 상한 도달, 묶음 부분 충돌, 미래 날짜, 스위치 꺼짐, 기존 `/api/workspace` 응답 회귀.
- **일정:** 중앙 배포는 11월 29일까지.

## 10. 검수 반영과 나눔 (11-27 아침)

- **검수:** SYNK-talk 가지 `claude/attendance-topik`은 GPT 지적 10건을 고쳐 `a5a48776`이 됐다. 출결 `revision`은 표 전체가 함께 쓰는 순번이고, 멱등은 원장 표 `engine.synk_class_record_requests`(키와 요청의 해시만 남김)가 맡는다. 워크스페이스 가지는 카본 지적 8건을 고쳐 `932d858ba0`이 됐다.
- **만료 임박 기준:** 학생마다 유효한 4급 이상 성적 가운데 가장 늦게 만료되는 성적(`topik.level4`)으로 판정한다. 그런 성적이 없으면 대표 성적으로 판정한다.
- **나눔:** 지점 · 반과 지점의 연결 · 재학생 체류(c19)와 워크스페이스 「학생 관리」 한 장은 학생 관리 세션(설계 `docs/디자인/학생관리_20261127/설계.md`)이 이 가지 위에 쌓는다. 반 출결과 TOPIK 저장, 반 출결 띠는 이 설계가 맡는다. 중앙 배포는 c18 · c19를 한 번에 묶는다.
- **화면:** 지금 화면은 임시판이다. 유호님은 11-27 「시안은 일단 셋 볼게. 그리고 만약 시안 중 맘에드는거없으면 노란화면으로 가자」로 정하셨다. 시안 셋 가운데 고르시면 그 겉으로 바꾸고, 고르신 것이 없으면 노란 「학생 관리」 시안의 겉으로 간다.
