## 2. 「살아 있는 마을」을 위한 기술 기반

### 2-1. 시간과 틱

- **틱은 브라우저 맥박이 만든다.** `day-app.mjs:493`이 1초마다 `presence`를 보내고, 서버의 `updatePresence`가 앞창(foreground)에 있던 시간만 계산해(`presence.mjs:16-19`) `advanceLivingState`가 C1·첫 하루·가판을 앞으로 민다(`server.mjs:43-65`, `core.mjs:186-198`). 서버 쪽 스케줄러·크론은 없다.
- **시계가 모듈마다 따로 있다.** `life.uMs`·`day.uMs`·`bazaar.uMs`는 앞창 누적 ms이고, 벽시계를 쓰는 것은 받침 한 건뿐이다(`day.mjs:405` `readyAt = startedAt + 30000`). 마을의 「오늘」, 시간대, 요일, 한국 날짜라는 개념이 없다.
- **앱을 닫으면 아무것도 진행하지 않는다.** 의도된 설계다(`presence.mjs:1-2`, README 「서버 재시작으로 오프라인 시간을 따라잡지 않으며」). 30분 쉬면 다음 「방문」으로 끊는 규칙만 있다(`presence.mjs:4`, `:20`). 이는 마을 설계 §1의 「내가 없는 동안에도 시간이 흐르는 아름다운 세계」, NPC 자율생활 §11의 `advanceBasis`(active-world-time / elapsed-server-time / player-decision)·§12의 미접속 요약과 어긋난다. 지금 코드에서 설계의 세 기준 중 맞는 것은 「앞창 시간」과 「맡긴 준비 한 건의 서버 시각」뿐이다.

### 2-2. 스케줄러와 주민 상태

- **주민 레지스트리가 없다.** 주민 ID가 파일마다 따로 적혀 있다(`day.mjs:12`, `day-scene.mjs:17-18`, `day-residents.mjs:13-20`).
- **주민 상태는 모듈별 고정 필드다.** `day.routine`의 `cafeMs·workshopMs·researcherMs·pairMs·returnMs·habitMs`와 그 상한(14,000/3,000/8,000 …)이 저장 검사에 박혀 있다(`day.mjs:37`, `:52-54`). `life.routine.phase`가 따로 있다. 위치·목표 글은 화면용으로 매번 계산한다(`day.mjs:428-511`). 설계가 요구한 주민 실행 자료(고유 목적·시간대별 일과·단기 목표·행동 원형·현재 실행 계획, NPC 자율생활 §3)는 하나도 저장되지 않는다.
- **예약은 손으로 엮은 상호 잠금이다.** 열린 장면의 구성원 집합(`day.mjs:418-421`)과 core의 바쁨 판정(`core.mjs:121-170`, `:401-411`, `:537-557`). 생활 하나를 더하면 core에 서로를 막는 조건이 늘어 조합이 곱으로 커진다.
- **재사용할 수 있는 패턴:** 먼저 말 걸기 예산(45초 뒤 첫 제안, 보통 15분 창 2회·180초 간격, 활발 4회·90초, 조용히 0, 같은 원인 한 번만, `life.mjs:143-157`), 역할 셋(함께 정함/구경/맡김)과 도움 방식 셋(시범/협력/기획)이 장면마다 같은 꼴, 장면 중단·재개(`DAY_RESUME`/`DAY_RETRY`)와 「자리가 바뀌면 계획 무효」(`day.mjs:116-123`).

### 2-3. 콘텐츠 데이터 형식

- **대사·선택지·장면 단계가 모두 리듀서와 뷰 함수의 문자열이다**(`day.mjs:517-599`, `core.mjs:310-384`, `life.mjs:257-321`, `bazaar.mjs:339` 이후). Vellum 후보도 코드 안에서 만들고(`core.mjs:263-308`), `contentRef`(FT10.06A 등)는 원고 문서의 번호일 뿐 실제 글은 코드 분기로 고른다(`core.mjs:363-365`).
- 데이터처럼 생긴 것은 읽기 문항 배열 하나다(`understanding.mjs:2-94`). 원고는 `docs/디자인/싱크타운_*.md` 마크다운에 있고 실행 데이터로 옮기는 단계가 없다.
- **장소 넷이 최소 일곱 곳에 따로 적혀 있다**(`walk.mjs:10-11`, `day.mjs:13`, `:19`, `day-scene.mjs:15`, `day-environment.mjs:6`, `day-district.mjs:19`, `day-app.mjs:7`). `town-layout.mjs`는 이름과 달리 이웃집·나무·길만 공유한다.
- **좌표계가 둘이다.** FT10·FT51·C1은 옛 2D 화면의 퍼센트 좌표(`core.mjs:16-22`, `life.mjs:12`)를 3D에서 `cafePoint`로 바꿔 쓰고(`day-scene.mjs:509`), 첫 하루는 미터를 쓴다(`day.mjs:19`, `:424-427`).
- 옛 2D 찻집 화면(`preview.html`·`app.mjs`·`life-ui.mjs`)과 교사 연결판(`linked.html`)이 같은 core를 쓰고 있어, core를 바꿀 때마다 2D 길도 지켜야 한다.

### 2-4. 저작 도구

- **주민·대사·사건·일정 저작 도구는 없다.** 원고 → 코드 손 이식이다. 콘텐츠 검사기(설계 §6-6의 어휘 수준·높임 일관성·민감 대사·중복 검사)도 없다.
- 3D 환경은 블렌더 굽기 길이 있다(`qa/blender-town-20261018/blender/town_bake.py`, `build-set.mjs`, `qa/blender-merged-20261018/blender/merged_build.py`). 다만 구운 GLB는 Git 밖 원본 창고(`town-합친판3-20261019`)에 있고 공개 빌드가 그 사본에 기댄다.
- 검증 도구는 많다: 화면 하네스 `qa-*.cjs`, 같은 와이파이 휴대폰 중계 `qa/blender-merged-20261018/phone-preview.mjs`·`phone-hud.js`.

### 2-5. 세이브 구조

- **사람 하나당 JSON 문서 하나**(`schema:1`). 로컬: `%LOCALAPPDATA%/SYNK/town-preview/ft10-v1.json`(임시 파일 → fsync → 이름 바꾸기, `server.mjs:11-21`). 리허설: 계정별 파일(`experiences/synk-world-app/town-host.mjs`). 운영: Postgres `engine.synk_modern_town_state` 1행(JSONB ≤ 8MB) + 명령 영수증 표.
- 판(revision)은 문서 전체 하나와 자리 판(`worldRevision`)·좌석 판(`lifeSeatRevision`)뿐이다. 설계의 엔티티별 판·outbox(`docs/아틀라스_구현명세.md` 9-2-1)는 없다.
- **문서 안에서 끝없이 자라는 배열:** Trail `events`, `commands`(로컬은 무한, 운영은 32개로 자름 — `SYNK-talk/lib/modern-town-domain.mjs:36`), `day.emitted`·`day.history`, `life.contacts`·`life.history`, `bazaar.emitted`, `support.presentations`(1만 한도). 압축·스냅샷·보관 기한이 없다.
- **이관**은 `restoreState`가 없는 열쇠를 채우는 방식이다(`core.mjs:42-55`). 콘텐츠 판이 바뀔 때의 이관 규칙은 없다.
- **커질수록 느려진다 — 실측.** 이 노트북, 메모리 저장(파일·DB 없음), 이 폴더의 `tools/bench-town-growth.mjs`로 첫 하루 외출을 반복해 사실을 쌓았다.

## 4. 지금 코드 위에 설계를 올릴 때의 막힘

표시: **구조**(다시 짜야 한다) · **결정**(먼저 정해야 미술·코드를 덜 버린다) · **구현**(지금 구조에 붙일 수 있다).

1. **구조 — 세계 시계가 없다.** 시간대 빛·날씨·계절·주민 일정·버스 시간표·「어느 때나 두 주민」·미접속 요약이 모두 시계 위에 선다. 호스트 시각 기반 마을 시계(낮밤은 사용자 시간대, 달력·날씨는 한국 날짜와 마을 씨앗)와 단계별 진행 기준(`advanceBasis`)을 새로 둬야 한다. 지금의 「앞창 시간만 흐른다」는 개인 장면 진행에는 맞지만 마을의 하루에는 맞지 않는다.
2. **구조 — 주민이 데이터가 아니다.** 주민 레지스트리 + 일정표 + 목표/계획 단계 + 예약이 필요하다. 지금 방식(장면별 고정 타이머 + core의 바쁨 깃발)은 주민·장면이 늘수록 상호 잠금이 곱으로 늘어 열 가지 생활·주민 열몇 명을 받을 수 없다.
3. **구조 — 콘텐츠가 코드다.** 장면·대사·반응 후보·조건을 데이터로 빼고 검사기(Strata 어휘 수준·높임 일관성·민감 대사·중복, 마을 §6-6)를 붙여야 원고(이미 마크다운으로 많이 있다)를 실행으로 옮길 수 있다. 장소 목록·좌표계도 하나로 합친다.
4. **구조 — 세이브와 맥박.** 엔티티별 상태(집·자리·주민 관계·약속) + 사실 로그 압축/스냅샷 + 증분 검증으로 바꾸고, 맥박은 시간만 전하고 변화가 없으면 저장하지 않으며 응답에서 상태 전체를 빼야 한다. 지금 꼴이면 **기억이 쌓일수록 느려지는** 구조라 「나를 기억하는 마을」과 정면으로 부딪친다(§2-5 실측).
5. **결정 — 구운 빛과 「시간의 빛(필수)」.** 지금 WORLD 기본은 한 시각의 햇빛을 텍스처에 구운 판이고, 구운 재질은 실시간 빛을 받지 않는다(`day-district.mjs:38-55`). 시간대마다 굽기(휴대폰 내려받기 ×N), 밝기·색 보정만, 실시간 빛(v20)으로 돌아가기 중 하나를 미술 투자 전에 골라야 한다.
6. **결정 — 엔진.** 미추적 문서 `docs/SYNK_WORLD_앱구성안_20261009.md`(Git에 없음)가 Unity 전환을 「제안」으로 둔다. 서버 리듀서는 렌더러와 떨어져 있어 살아남지만 Three.js 화면·구운 판 로더·표현 코드는 옮겨지지 않는다(그 문서도 그렇게 적는다). 런타임 층을 새로 짤 때 리듀서·콘텐츠 데이터를 렌더러 독립으로 두면 어느 쪽이든 손실이 적다.
7. **결정·구현 — 권한을 주는 길.** 앱 안 TOPIK 1급+ 통과를 무엇으로 판정해 1급+ 통과 표시 권한을 줄지, 체험 권한을 언제 누구에게 줄지가 없다. 검사만 있어서, 손으로 권한을 넣은 계정이 아니면 공개 WORLD에서 3D 타운에 들어갈 수 없다(운영 DB의 권한 행은 확인하지 않음). 「살아 있는 마을」을 실제 학습자에게 보이려면 이 길이 첫 조각과 함께 있어야 한다.
8. **구현 — 학습 왕복.** 타운 안 읽기·대화 결과를 계정 학습 원장으로 보내는 어댑터, 계정 학습 요약을 받아 주민 말의 쉬운/확장 판을 고르는 어댑터. 계약은 문서에 있다(`docs/아틀라스_구현명세.md` 9-2-1 「Atlas 요약 어댑터」).
9. **운영 위험(P3 · 확인 필요).**
   - `SYNK-talk`에서 `node tools/synk-town-build.js --check` → `Error: Stale Town runtime`. 운영 묶음 `supabase/functions/synk-town/town-runtime.mjs`의 마지막 커밋은 10-10(`1daa892`)이고, 그 뒤 synk-town 리듀서가 바뀌었다(10-14 일괄 커밋 `daa164053`, 10-20 `support.mjs` 갈래 다섯, 10-20·21 `understanding.mjs` 12문항). 묶음 안 갈래는 `["detail","sequence","negation"]`(`town-runtime.mjs:7857` — 커밋된 판과 작업본 판 모두), 원천은 다섯(`support.mjs:11`). 참고로 SYNK-talk 공용 작업본의 `town-runtime.mjs`(10-18 22:42)·`synk-town-build.js`(10-09)에는 다른 세션이 남긴 **미커밋 수정**이 이미 있었다(이번 검토는 `--check`로 읽기만 했고 아무것도 쓰지 않았다). 실제 배포된 함수가 어느 판인지는 확인하지 않았다. 클라이언트(WORLD 공개 빌드)는 최신 원천을 싣기 때문에 서버와 판이 어긋날 수 있다.
   - synk-town 시험 16파일 중 **9파일(161개)이 미추적**이다(`bazaar`·`day`·`day-store`·`life`·`life-store`·`presence`·`support`·`support-bazaar-store`·`walk`). Git에 있는 것은 7파일 52개(커밋 기록의 「Town tests 50/50」은 이쪽). CI는 `tests/*.test.js`만 돌려(`.github/workflows/syntax-check.yml:155`) synk-town 시험은 추적·미추적 모두 CI에 없다. 공개 저장소에는 생활·이동 리듀서의 시험이 없는 셈이다.

## 7. 판정 — 설계를 지금 코드에 바로 얹을 수 있는가

**아니다. 다만 버릴 것은 적다.**

- **그대로 쓰는 것:** 3D 마을과 그래픽(v20·구운 판), 직접 걷기·카메라·충돌, 계정 옷차림 연결, 명령 계약과 원자 저장, 운영 계정 저장과 권한 검사, Trail(사실·인지)·Vellum(아는 것만 반응)·Loom(보인 뒤 기록)의 개념, 먼저 말 걸기 예산, 역할 셋·도움 방식 셋.
- **먼저 다시 짜야 하는 것(마을 런타임 층):** ① 세계 시계, ② 주민 레지스트리·일정·목표·계획·예약, ③ 콘텐츠 데이터 형식과 검사기, ④ 엔티티로 나눈 세이브·로그 압축·가벼운 맥박. 지금 구조는 「장면 하나 = 리듀서 모듈 하나 + core 상호 잠금 + 코드 안 대사 + 끝없이 커지는 한 덩어리 저장」이라, 열 가지 생활·열몇 주민·계절을 얹으면 개발 비용과 실행 비용이 함께 비선형으로 커진다. 특히 「살아 있는 마을」의 세 조건 — 나 없이도 흐르는 시간, 데이터로 늘어나는 주민 행동, 오래 쌓여도 버티는 기억 — 이 셋 다 지금 구조에 자리가 없다.
- **먼저 정해야 하는 것:** 구운 빛과 시간대 빛, 엔진(웹 유지/Unity), 권한 부여(통과 판정 → 입장권, 체험 발급), 미접속 동안 무엇이 진행되는지(설계는 「공개 일상은 진행, 개인 선택은 멈춤」).
- 이 판정은 코드·시험·기록 대조에 근거한다. 실제로 재미있는지, 학생이 변화를 알아보는지는 아무도 관찰하지 않았다(참가자 0명).

## 8. 첫 세로 조각 추천 — 「찻집 골목의 하루」

**증명할 것:** 처음 온 사람이 10~15분 안에 ① 마을이 나 없이도 움직인다(시간·날씨·주민 일정), ② 내 선택 때문에 주민 행동이 바뀌고 다음에 와도 남아 있다, ③ 마을이 나에게 맞춰진다(내 시간대·내 선택·내 한국어 수준)를 스스로 말로 설명할 수 있는가.

**범위 — 새 장소·새 미술 없이, 있는 네 장소와 세 주민으로:**

1. **마을 시계(새 런타임 층 ①):** 호스트 시각 기반. 사용자 시간대의 아침·낮·저녁·밤 네 구간, 한국 날짜와 마을 씨앗으로 정하는 날씨 두 가지(맑음·비) — 같은 날 같은 날씨. 화면은 빛 색·밝기와 비 입자만(구운 판이면 색 보정, 아니면 v20 실시간 빛 — §4-5 결정이 이 조각의 선행 조건).
2. **주민 일정(새 런타임 층 ②):** 찻집 주인·공방 주인·연구원을 데이터 파일 하나로 등록하고, 구간마다 장소·행동 둘 이상 + 비 오면 처마 밑으로 덮어쓰기. 계획 단계(예약 → 이동 → 행동 → 마침)와 「어느 때나 두 주민」을 시험으로 고정. 지금의 14초 대본을 이 일정으로 대체.
3. **내 선택이 남기는 변화:** 이미 있는 FT10 자리·방향 합의를 일정에 연결 — 「오후에는 내가 고른 자리에서 공방 주인이 쉰다」. 다음 날 와도 그 습관이 일정에 남는다.
4. **돌아왔을 때 한 줄:** 앱을 닫았던 동안의 주민 공개 일상을 사건 하나로만 요약(「공방 주인이 받침을 고쳐 두었어요」 + 화면에 보이는 흔적 하나). 밀린 부탁·감사 목록은 만들지 않는다(NPC 자율생활 §12).
5. **개인화 둘:** 접속 시간대 습관(밤에 오는 사람에게 밤 구간 주민을 더 채움, 마을 §8)과 이미 있는 「먼저 말 거는 정도」를 일정·접근에 반영.
6. **한국어 한 장면:** 찻집 주인과 3차례 대화 한 장면 — 고르기 답(뜻이 다른 옳은 한국어 둘), 되묻기 세 단추(다시/천천히/무슨 뜻), 쉬운 판·확장 판 두 대사 중 지금 읽기 기록으로 고르기. 답은 계정 학습 원장으로 보내는 어댑터 하나(§4-8)를 이 장면에서만 먼저 연결.
7. **데이터와 저장(새 런타임 층 ③·④):** 위 일정·대사·후보를 데이터 파일로 두고 검사기 시험을 붙인다. 시계·일정은 저장하지 않고 계산한다. 맥박 응답에서 상태 전체를 빼고, 변화가 없으면 저장하지 않고, 사실 로그에 스냅샷을 둔다 — 「기록이 늘어도 맥박 비용이 일정하다」를 벤치(`review/bench-town-growth.mjs`)로 확인.

**하지 않는 것:** 새 장소, 이웃 16명, 경제·코인, 펫·낚시·버스·농사, 새 주민 미술, 열 가지 생활의 나머지, 결제.
