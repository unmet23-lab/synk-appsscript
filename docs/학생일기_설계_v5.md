## 0. 🔴 v4 에서 틀린 셋 — 철회한다

### ㉠ 새 표를 판 것이 틀렸다

두 집안이 이번에 **둘 다** 반대했다. 제미나이는 v2 때 「독립 표를 파라」고 했다가 이번에
「전면 백지화하라」로 바꿨는데, 바뀐 이유가 내 문서다 — v4 가 **「옮겨 심을 규율 다섯」**을
목록으로 적자 그 비용이 드러났다.

그리고 실물을 열어 보니 기존 `engine.submissions` 에 **필요한 칸이 이미 다 있다.**

```
task_ref · task_snapshot · task_format · task_schema_ver
body_original · image_refs · audio_ref · audio_duration_sec · capture_meta
transcript · transcript_verified · transcript_state · stt_segments · stt_confidence
code_switch_spans · redaction_ver · redaction_result · audio_deleted_at
occurred_at · schema_ver
```

🔑 `audio_duration_sec` 과 `capture_meta` 는 v4 가 새 표에 만들려던 바로 그 칸이고,
`code_switch_spans`(몽골어 섞임 구간)까지 **이미 서 있다.**

🔴 그리고 GPT 가 짚은 아픈 자리 하나 — **유호님이 09-05 에 열어 주신 예외는 「화면 하나」였다.**
「새 테이블 0」 기둥은 그대로 살아 있는데 내가 그 예외를 표까지 늘려 읽었다.

### ㉡ 「열었는데 안 썼다」를 분모로 센 것이 유호님 확정과 부딪친다

유호님 확정 = 「안 쓴 날은 아무 일도 일어나지 않는다(결손으로 세지 않는다)」.
그런데 v4 는 `diary.opened` 를 분모에 넣었다. 그러면 탭을 한 번 열고 닫은 학생에게
**0/1 이라는 부정 신호**가 남는다. 두 집안이 각각 다른 각도로 짚었고 결론이 같다.

⇒ **분모를 버린다.** 「쓴 것」만 센다.

### ㉢ 「처리 트리거를 건드리면 과제 통로 한복판」이라던 판단이 틀렸다

v4 는 그것이 위험해서 새 표를 팠다. 실물을 보니 **그 트리거의 고아 잡 문제는 이미 있고,
코드에 적혀 있기까지 하다.** `SYNK-talk/supabase/functions/radio-promote/index.ts:28-33`:

> ■ 승격 행의 submissions 는 pipeline_jobs 트리거를 그대로 탄다 … **그 잡은 집는 소비자가
> 없어 queued 로 남는다**

그리고 배달(`deliver`)도 **배정 시점에** `submissions` 행을 만든다(`:779`·`:948`·`:977`).
교정 엔진은 `event_type='submission.created'` 로 조인하므로 배정 잡·승격 잡을 안 집는다.
⇒ **지금도 고아 잡이 두 갈래로 쌓이고 있다.** 트리거를 고치면 셋(배정·승격·일기)이 함께 풀린다.

## 1. 한 줄

**일기는 기존 제출 표에 앉되 사건 이름이 다르다.** 그래서 소비자 대부분이 스스로 걸러 내고,
남는 셋은 한 줄짜리 처방으로 닫는다.

## 2. 유호님이 정하신 여섯 (결정.md · 09-05)

| | 확정 |
|---|---|
| 빈도 | 강제 없이 열어둔다. 안 쓴 날은 아무 일도 안 일어난다 |
| 물음 | 사소한 일상 |
| 목적 | 학생 자신의 기록. 성향은 덤 |
| 자리 | 앱 아래 탭 하나 (**화면 예외는 여기까지다**) |
| 쓴 뒤 | 쌓이는 것 보여주기 + AI 맞장구. 🔴 고치지 않는다 · 🚫 평가도 안 한다 |
| 다시 보기 | 날짜 목록 + 시즌 끝 종이 |

## 3. 일기를 기존 칸에 어떻게 앉히나

| 기존 칸 | 일기가 넣는 것 |
|---|---|
| `task_type` | **`일기`** (계약 값 +1) |
| `task_format` | `자유발화` |
| `task_ref` | `diary:{diary_date}:{prompt_id}` — 과제의 `task-{날짜}` 와 이름공간이 안 겹친다 |
| `task_snapshot` | `{ver, prompt_id, prompt_text, prompt_pack_ver, diary_date}` |
| `task_schema_ver` | `diary.v1` |
| `body_original` | 학생이 친 글 |
| `audio_ref` · `audio_duration_sec` · `capture_meta` | 소리와 그 봉투 (기존 규율 그대로) |
| `transcript_state` | **`null`** = 전사 대상 아님 (§8) |
| `code_switch_spans` | 언어 판정 결과 (기존 칸) |

🔑 **`learner_id` 를 이 표에 안 넣는다.** L0 계약이 「같은 행에 학생을 두 번 적으면 사건과
표가 다른 학생을 가리킬 수 있다」는 이유로 일부러 뺀 자리다. v4 스키마가 그 함정을 다시 팠다.

## 4. 사건 셋과, 계약에 등재할 자리 여섯

| 사건 | 무엇 | payload 필수 |
|---|---|---|
| `diary.opened` | 물음을 띄웠다 | `prompt_id` · `prompt_text` · `prompt_pack_ver` · `diary_date` |
| `diary.written` | 일기를 남겼다 | 제출 규격(기존 `submission.created` 와 같은 다섯) |
| `intervention.delivered` | **AI 맞장구** (§6) | 기존 규격 그대로 |

🔴 `diary.opened` 가 물음 스냅샷을 **자기 payload 에** 진다. v4 는 그걸 제출 행에만 뒀는데,
그러면 **열고 안 쓴 순간의 물음이 영구히 사라진다**(팩을 개정하면 복원 불가).

🔴 **새 사건을 계약에 넣는 일은 값목록 한 줄이 아니다.** 실물이 여섯 자리를 요구한다 —
`이벤트검증.js` 의 값목록 · `앱사건` · `이벤트별필수`, `사건출처.js`, 생산자 장부, 엔진도달 장부.
하나라도 빠지면 회귀가 빨개지거나 `source_kind` 가 빈 채로 쌓인다.

🔑 **사건과 표 행은 한 트랜잭션이다.** 기존 `/events` 가 그 불변식을 명시적으로 묶어 두었고,
일기 통로도 같은 묶음을 쓴다. 안 묶으면 사건만 남은 고아가 멱등키에 막혀 영구화된다.

## 5. 처리 대기표 트리거 하나를 고친다

```sql
-- 지금: 모든 submissions INSERT 에 줄이 선다
-- 뒤: 사건 종류를 보고 넣는다
create or replace function engine.enqueue_pipeline_job() returns trigger
  language plpgsql as $function$
begin
  if exists (select 1 from engine.learning_events e
              where e.event_id = NEW.event_id
                and e.event_type = 'submission.created') then
    insert into engine.pipeline_jobs (submission_id) values (NEW.submission_id)
      on conflict (submission_id) do nothing;
  end if;
  return NEW;
end
$function$;
```

**딸려 오는 이득 둘** — 배정 행(`deliver`)과 라디오 승격 행이 만들던 고아 잡이 함께 멈춘다.
⚠ 이미 쌓인 고아 잡을 걷을지는 별건이다(이 판에서 안 닫는다).

**남는 거르개 둘** — 진행률의 「첫날인가」 질의와 성과 회수. 각각 한 줄이다.

⚠ 성과 회수는 개입 전후를 `학습자상태()` 로 다시 계산하므로 **입력을 좁히면 같은 학생이
호출자마다 다른 상태가 된다**(심문 지적). ⇒ 좁히는 것은 «성과 회수가 세는 개입 대상»이지
상태 계산 입력이 아니다. 이 구분을 구현 때 못 박는다.

## 6. AI 맞장구는 기존 개입 통로로 남긴다

두 집안이 똑같이 「맞장구의 원문·모델·판·시각이 어디에도 없다」고 짚었다. 맞다 —
v4 는 유호님 확정을 §2 에 적어 놓고 스키마와 사건 어디에도 자리를 안 만들었다.

| 무엇 | 어디 |
|---|---|
| 맞장구 원문 | `intervention.delivered` 의 `output_text` (기존 규격) |
| 어느 일기에 대한 답인가 | `parent_event_id` = 그 `diary.written` |
| 모델·프롬프트 판 | 기존 개입 사건의 판 칸 |
| 학생이 실제로 봤나 | `content.viewed` (**재생·표시 완료** — 기존 뜻 그대로) |

🔑 이렇게 두면 시즌 종이에 그날의 맞장구를 **다시 만들지 않고 그대로 찍는다.**
v4 대로면 인쇄 때마다 새로 만들어 내용이 달라졌다.

🚫 맞장구는 고치지 않고 평가하지 않는다(유호 확정). 그 규율은 프롬프트가 진다.

## 7. 축 — 분모 없이 센다

| 사건 | 자발발화축에서 |
|---|---|
| `diary.written` | **센다** |
| `diary.opened` | **안 센다** (§0㉡) |

**세는 것 넷** — 남긴 수 · 길이(글자 수 / `audio_duration_sec`) · 시각대 · 매체.
창과 판은 기존 `학습자상태` 규약 그대로.

🚫 집중띠에 섞지 않는다. 집중띠는 「시간대별 착석 대비 완료율」이라 분모가 다르다.
🚫 AI 가 성향을 판정하지 않는다. 이 축은 세는 자다.

⚠ **세기만 해서는 이해 대장 ㉡ 칸이 안 찬다**(심문 지적 · 맞다). §9 가 그것을 정직하게 적는다.

## 8. 전사와 언어

### ㉠ 전사는 기본값이 「안 함」이다 — 그리고 이것이 값을 «미룬다»

`transcript_state` 를 비운다(`null`). 소리 변환기는 `대기` 만 집으므로 안 걸린다.

⚠ **이 미루기의 값을 정직하게 적는다.** 한국어로 «말한» 학생의 발음·어휘가 그동안 엔진에
안 닿는다. 두 집안이 이것을 「게이트 위반」이라고 짚었고, 반박하지 않는다 —
§10 이 이 값을 재는 것을 남은 일로 세운다.

🔑 되돌릴 수 있는 쪽으로 둔 것뿐이다. 소리를 무기한 보관하므로(형제 규약 「반드시 보관」)
언어 판정이 서는 날 거슬러 올라가 캔다. 반대 방향(잘못 굳힌 한국어 전사)은 못 되돌린다.

### ㉡ 언어는 글자로 «가늠»하되, 못 가늠하면 그렇게 적는다

| 무엇 | 값 | 어떻게 |
|---|---|---|
| 한글 자모가 주면 | `ko` | 글자 |
| 키릴이 주면 | `mn` | 글자 |
| 둘이 섞이면 | `mixed` | 글자 + `code_switch_spans` |
| 🔴 로마자면 | `unknown` | **판정하지 않는다** |
| 글 없이 소리만 | `unknown` | — |

🔴 **로마자를 판정하지 않는 이유가 둘이다.** 몽골 학습자는 자판 바꾸기가 번거로우면 로마자로
몽골어를 쓰고(제미나이 지적), 반대로 한국어를 로마자로 적기도 한다(`annyeong`).
글자만으로는 셋을 못 가른다. ⇒ 지어내느니 `unknown` 이 정직하다.

⚠ **글자 판정은 판정이 아니라 가늠이다.** 쓰는 곳은 전사줄에서 빼는 데 하나뿐이고,
엔진 재료의 언어 라벨로는 안 쓴다.

## 9. 완결 도장 — 지금은 전부 ✗

| 칸 | 지금 | 언제 ✓ 가 되나 |
|---|---|---|
| 모였나 | ✗ | 통로가 서고 첫 행이 쌓일 때 |
| 닿았나 | ✗ | 자발발화축이 그 행을 읽고 값을 낼 때 |
| 늘었나 | ✗ | 이해 대장 ㉡ 칸에 «무엇을 알게 됐는지» 이름을 댈 수 있을 때 |
| 누구에게 | 학생 (예정) | 날짜 목록·시즌 종이가 돌 때 |

🔴 **「늘었나」는 세는 것만으로 안 찬다.** 남긴 글의 «내용»을 어디에 잇는지 이 판은 안 정했고
(§10-1), 정하지 않는 한 이 칸은 ✗ 다.

## 10. 남은 일 — 정직하게

1. 🔴 **남긴 글의 내용을 엔진 어디에 잇나.** 지금 축은 수·길이·시각·매체 넷뿐이라
   「친구와 놀아 행복했다」와 「학교가 힘들어 그만두고 싶다」가 같은 행이 된다(심문 지적).
   ⇒ 이것이 「늘었나」의 열쇠다.
2. **소리를 안 캐는 동안 잃는 값.** §8㉠ 이 인정한 그 값을 안 재봤다.
3. **맞장구를 무슨 말로 하나.** 몽골어는 감수자가 한 분뿐이라 검수 전엔 화면에 못 올린다.
4. **하루 여러 장의 중복과 의도를 못 가른다.** 같은 초안의 재전송은 접히지만,
   두 기기가 각자 초안을 만들면 둘 다 저장된다. 받아들이는 비용으로 적는다.
5. **참여율·녹음 길이.** 용량 계산의 두 입력.
6. **날짜 목록 상한 · 소리만 남긴 날의 종이 표현.**
7. **최신 수단 정찰.**

## 11. 심문에 바라는 것

1. **§0 의 철회 셋이 충분한가.** v4 에서 틀린 넷째가 있나.
2. **§3 의 칸 배치가 기존 규율과 부딪치지 않는가.** 특히 `task_ref` 이름공간과
   `transcript_state=null` 이 다른 소비자에게 어떻게 보이나.
3. **§5 의 트리거 수정이 배정·승격 갈래를 깨지 않는가.** 지금 쌓이는 고아 잡에 기대는
   소비자가 정말 0인가.
4. **§6 의 맞장구 배치가 기존 개입 통로의 뜻을 안 넓히는가.**
5. **§10-1 이 「늘었나」의 유일한 열쇠인가.** 내용을 잇지 않고 그 칸을 채울 길이 있나.
