# Glide 업데이트(비용) 실측·절약 설계

> 작성 2026-07-11 · Maker 플랜(월 500 업데이트, 초과분 개당 $0.02) 출시 대비
> 데이터소스 = 구글시트 직결(확정). 그래서 업데이트를 **양쪽**에서 소비한다.

## 1. 업데이트가 소비되는 곳 (SYNK 실제 구조)

Glide 공식 기준 "업데이트" = ①앱에서 행 추가·편집·삭제 각 1개 + ②외부 시트가 바뀌어 Glide가 다시 읽는 sync 1개(변경 없으면 0, 여러 변경은 1 sync로 묶임).

**(A) 앱 사용자 액션 — 아웃바운드, 각 1개**
- 강사가 앱에서 포인트 지급 → point_logs 행 추가 = 1
- 학생 프로필/자기소개 편집 = 1
- (출석을 앱으로 하면) 출석 체크 = 1  ← **미정, 최대 변수**

**(B) 백엔드 트리거의 시트 변경 → 인바운드 sync**
- `parentSweep`(10분마다) → `today_board` 갱신: 출결 바뀌는 수업 시간대에 sync 유발
- `calcAll`(매일 14·22시) → point_logs 정산·profiles 게이지 갱신
- 번역·공지·주제 갱신(새 공지 올릴 때만)
- 월간 배치(리포트·아카이브 등)

## 2. 이미 적용된 절약 장치 (설계자가 의식함)

- `writeIfChanged`: 값이 실제로 바뀔 때만 시트에 씀 → 변경 없으면 sync 안 함
- 등원 알림 포인터를 시트가 아닌 Script Properties에 저장(주석에 "월 ~150업데이트 제거" 명시)
- 숙제 일괄지급: 강사가 여러 학생을 1탭으로 저장 → 시트→앱 sync 묶음당 1개(개별 버튼 대비 ~85% 절감)

## 3. 출석 방식별 예상 소비 (학생 30명·월 20수업일 기준, 거친 추정)

| 방식 | 출석분 업데이트 | 판단 |
|---|---|---|
| **앱(Glide)에서 출석** | 30명 × 20일 = **~600/월** | 출석만으로 500 초과. 포인트·프로필·트리거 더하면 큰 초과 |
| **구글폼/QR 등 외부 입력** | 폼은 시트에 쌓이고 Glide는 읽기 → sync 소수 | 출석분 업데이트 대폭 절감. **updates 관점 유리** |

> 판정: updates 비용만 보면 **출석은 외부(폼/QR)가 유리**. 단 학생 경험(앱 안에서 원터치 출석)과 트레이드오프라 유호님 기획 판단 사안. 앱 출석을 꼭 원하면 Business 플랜(월 5,000) 전환을 전제로.

## 4. 첫 달 실측 방법 (출시 후)

1. Glide 편집기 → 좌하단 팀/앱 이름 클릭 → **Billing/Usage** → 이번 달 Updates 사용량 확인(누적 카운터)
2. 매주 1회 기록: 주차별 증가폭 = 주간 소비 속도
3. 월 환산이 **400을 넘기면** 아래 절약 레버 적용, **500을 반복 초과하면** Business 전환 검토(초과분 $0.02 × 개수 vs 플랜 차액 비교)

## 5. 절약 레버 (초과 시 순서대로)

1. **출석을 외부(폼/QR)로** — 가장 큰 절감(위 표)
2. **`parentSweep` 주기 완화** — 10분 → 15~20분. `today_board`가 Glide 소스로 물려 있으면 sync 횟수 직결 감소(수업 시간대 한정 실행이면 영향 적음)
3. **강사 포인트를 일괄탭 위주로** — 개별 버튼 남발 억제(이미 구조는 있음)
4. 그래도 초과면 **Business 플랜**(월 5,000, 에디터 10·행 10만)
