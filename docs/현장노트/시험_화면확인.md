> 마지막 확인: 2026-10-18
> 쓴 AI: Claude Code(Claude Opus 5.5) — 09-30~10-17 Claude 메모에서 옮김 · GPT(Codex) 10-17 Chrome 확장 연결 오류 범위, 10-18 옛 리허설 의존성·스크롤 완료 판정 추가 · Claude Code 10-18 `node --test <폴더>` 실패 추가

시험·화면 확인을 「통과」로 잘못 읽거나, 시험이 공용 작업본의 남의 증거를 덮은 함정이다. 틀은 [README](README.md)를 따른다.

## node --test와 CI

### Node fetch가 Range 요청에 identity를 덧붙여 인코딩 거절 시험이 달라진다
- 증상: 10-18 영상 Range 시험에서 `Accept-Encoding: identity;q=0, br, gzip`을 주었지만 예상 406 대신 206을 받았다.
- 원인: Node 24.20 fetch가 Range 요청의 실제 헤더를 `identity;q=0, br, gzip, identity`로 보냈다. 뒤의 identity가 허용값이 되어 요청이 달라졌다. 로컬 수신 서버에서 실제 헤더를 확인했다.
- 고침: 정확한 인코딩 제외를 시험하는 한 요청만 `node:http.request`로 보내고 나머지는 실제 fetch 흐름을 유지한다. 제품의 헤더 해석을 시험 도구의 덧붙임에 맞춰 바꾸지 않는다.
- 다시 확인: `company/static-media.test.mjs`의 인코딩 제외는 406, 일반 범위 요청은 206이며 관련 서버/캐시 25/25·통합 후보 701/701. 후보 `.tmp/company-pulse-structure-release-20261018/qa/result.json`.

### 명시한 시험 파일이 없어도 Node 24가 나머지만 실행하고 통과한다
- 증상: 10-18 회사 후보에서 시험 경로 16개를 넘겼지만 실제 TAP은 기존 219개만 통과했다. 추가하려던 6개 시험 파일은 후보에 없었다.
- 원인: Node 24.20의 명시 경로 처리에서 없는 파일이 다른 유효한 시험과 함께 전달되면 나머지만 실행할 수 있다. 선택 목록 길이와 종료 코드 0만으로 전부 실행됐다고 볼 수 없다.
- 고침: 실행 전에 모든 시험이 동결 manifest에 있고 원문 해시가 일치하는지 확인한다. 빠진 시험 원문을 후보에 포함하고, 실제 TAP 총수·실패·건너뜀과 원문 불변을 대조한다.
- 다시 확인: `.tmp/company-backend-read-release-v4-20261018/run-candidate-tests.cjs`가 파일 누락을 실행 전 거절하며, 최종 후보 16개 파일의 실제 실행 결과는 같은 폴더 `qa/result.json`에 남긴다.

### 시험 안에서 다시 부른 node --test가 빈 출력을 내고 끝난다
- 증상: 10-18 배포 묶음 회귀를 자식 `node --test`로 연결했는데 종료 코드 0·stdout 빈 문자열로 수십 ms 만에 끝났다. 실행 건수 단언이 이를 실패로 잡았다.
- 원인: 부모 시험의 `NODE_TEST_CONTEXT`가 자식에게 넘어가 독립 시험 실행기 대신 부모의 시험 worker 문맥으로 실행됐다.
- 고침: 공용 `tests/lib/띄우기.js`로 실행하고 자식 환경에서 `NODE_TEST_CONTEXT`만 제거한다. 종료 코드뿐 아니라 실제 시험 건수가 0보다 크고 실패·건너뜀 0인지 확인한다.
- 다시 확인: Talk `node --test tests/backend-lock-runtime.test.js`가 실제 classroom 27개·personal signing 22개를 실행해 통과하는지 본다. 원천 시험만 통과한 것을 Edge 묶음 통과로 대신하지 않는다.

### 운영 합성 시험의 정리 재개가 제품 배포 상태 때문에 막힌다
- 증상: 10-18 설정 동기화 시험 도구의 독립 검토에서 `--cleanup`도 제품 함수 배포 대조를 요구해, 함수 장애나 후속 배포 뒤에는 이미 만든 합성 계정을 정리할 수 없었다.
- 원인: 새 시험 계정을 만들 때 필요한 배포 검사를 소유 기록으로 정리만 재개하는 경로에도 적용했다. 설정 시험은 생성 응답 유실·정리 중단에 대비한 영속 소유 기록도 필요했다.
- 고침: 새 `--run --운영`은 대상·만료·JWT·배포 원문 일치를 모두 확인하고, 정리 재개는 대상·만료·journal·nonce·Auth 소유 및 정확한 Core ID를 확인한 후 정리한다. 비밀 없는 journal을 쓰기 전에 fsync하며, Auth 생성 응답을 잃어도 임의 재생성하지 않는다.
- 다시 확인: 도구와 배포 원문 helper의 독립 시험 27개 통과. 실제 운영의 설정 흐름 16개 후 같은 journal로 정리를 재개해 활성 계정·세션·Auth 연결·Auth 계정 0을 확인했다. [운영 검증 기록](../_ops/qa/backend-production-20261018/result.json).

### 파이프로 받은 `node --test` 출력에 요약 줄이 없다
- 증상: `node --test … 2>&1 | grep '^# (tests|pass|fail)'`가 아무 줄도 못 잡는다. 실패 몇 개만 보이고 총 수·통과 수가 없어 시험이 다 돌았는지 모른다(10-17).
- 원인: Node 24는 파이프에 쓸 때도 TAP이 아닌 보고기를 쓴다.
- 고침: `node --test --test-reporter=tap --test-reporter-destination=<파일> <시험들>` 뒤 `grep -E '^# (tests|pass|fail|skipped)' <파일>`, 실패는 `grep '^not ok' <파일>`과 그 뒤의 `location:`·`error:`로 본다.
- 다시 확인: `node --test tests/AI토큰장부.test.js 2>&1 | grep -cE '^# (tests|pass|fail)'`가 0, tap 보고기 파일에는 `# tests 4`가 있다(10-17).

### `node --test <폴더>/`가 「Cannot find module」로 실패한다
- 증상: 10-18 claude-session-share에서 `node --test test/`가 `Error: Cannot find module '…\test'`와 `not ok 1 - test`만 내고 끝났다(Node 24.20).
- 원인: Node 21부터 `--test` 뒤 인자를 글롭으로 읽는다. 폴더 이름은 파일에 맞지 않아 그 폴더를 모듈로 불러오려 한다.
- 고침: 저장소 폴더에서 인자 없이 `node --test`(`**/*.test.mjs`·`test/**` 등을 스스로 찾는다, Node 20에서도 됨)나 `node --test test/*.test.mjs`를 쓴다. 문서의 시험 명령도 그렇게 적는다.
- 다시 확인: 같은 폴더에서 `node --test test/`와 `node --test --test-reporter=tap`의 `# tests` 줄을 비교한다.

### 이 저장소의 CI는 전체 시험을 돌리지 않는다
- 증상: GitHub Actions가 초록이거나 「skipped」인데 정리 커밋이 깨뜨린 시험 21개가 10-03까지 쌓여 있었다.
- 원인: `.github/workflows/syntax-check.yml`은 비공개 저장소에서 저장소 변수 `SYNK_SELFHOSTED=on` + 자체 리눅스 러너가 있을 때만 돈다(08-18 「돈 안 쓴다」 결정). 지금은 push마다 skipped다. SYNK-talk의 CI는 push마다 전체 `npm test`를 돈다 — 두 저장소가 다르다.
- 고침: 파일·문서를 지우거나 토큰·생성기를 바꾼 뒤에는 `node --test --test-reporter=tap tests/*.test.js > <결과>`를 직접 돌려 `not ok`를 전후로 견준다. 공용 작업본이라 남의 작업 중인 파일 때문에 실패할 수 있으니, 실패한 시험이 읽는 파일이 `git status`에 걸리는지부터 본다. 로컬 CI 흉내는 `node tools/test-ci.js`(UTC·홈 폴더 없음, 리눅스는 못 흉내 냄). 비공개 저장소에 GitHub 호스팅 실행을 새로 붙이지 않는다(계정 전체 분 한도).
- 다시 확인: `gh run list --workflow syntax-check.yml -L 3 --json conclusion --jq '.[].conclusion'`이 skipped면 그대로다(10-17 skipped).

### 실제 키를 자동으로 읽는 도구가 시험 중에 실제 키를 보낸다
- 증상: 가짜 API 서버 흐름 시험에서 도구가 보안 폴더의 실제 Typecast 키를 가짜 서버로 보냈고, 단언 실패 문구에 그 값이 찍혀 대화 기록에 남았다(10-07, 밖으로 나가지는 않았지만 키 교체를 권함).
- 원인: 「보안 폴더 키 파일 자동 연결」 기능이 시험 모드에서도 켜져 있었다.
- 고침: 키를 읽는 코드를 더할 때 시험 환경 변수(가짜 API 주소 등)가 있으면 끄는 조건을 같이 넣는다. 단언은 키 값이 아니라 개수·길이만 본다. 시험 출력은 pass/fail 줄만 거른다.
- 다시 확인: 실제 키 파일이 있는 PC에서 시험을 돌리기 전에 그 끄는 조건을 grep으로 찾는다.

### 남아 있던 리허설 시험이 사라진 모듈과 옛 API를 부른다
- 증상: Talk `atlas-memory-api-rehearsal.test.js`가 없는 `atlas-memory-client.js`를 불러 시험 시작부터 실패했다(10-18). 연결 fixture도 없었고, cron 응답 시험은 옛 `index.ts`의 `health` 필드를 찾았다.
- 원인: 리허설 도구·시험은 옛 `atlas-memory/events` 계약에 남아 있었지만 실제 기억 저장은 Core 계정의 `synk-learning?view=memory`로 옮겨졌다. 댓글 DM도 본체에서 `lib/synkbrief-webhook.js`로 응답 처리를 위임했다.
- 고침: 없는 모듈을 빈 구현으로 메우지 않고 현행 계정 클라이언트·처리기·PGlite를 쓰는 리허설로 바꿨다. 기본 실행은 자격증명을 읽지 않는 준비 모드로 유지했다. cron 시험은 실제 `refresh` 분기의 `checked/failed/skipped`와 실패 503을 검사하며 다른 분기 응답이 누락을 숨기지 못하는 변이 시험을 더했다.
- 다시 확인: Talk `node --test tests/atlas-memory-api-rehearsal.test.js tests/조용한실패.test.js`와 관련 계정·SQL 시험을 실행한다. `.tmp/backend-migration-repair-20261018/verification.json`은 원격 Auth·운영 DB를 호출하지 않은 로컬 결과다.

### 희소 파일 시험이 디스크가 찬 날 ENOSPC로 실패한다
- 증상: `client-delivery-archive.test.mjs`의 「bounded size rejects oversized sparse files」가 ENOSPC로 실패한다(10-14 C: 여유 1.1GB).
- 원인: 한도(2GB)+1바이트로 `truncate`하므로 NTFS에서 2GB 넘는 여유가 있어야 한다.
- 고침: 회사 전체 시험 전에 여유를 보고 2GB 미만이면 먼저 알린다. ENOSPC 실패는 꾸러미 탓으로 적지 말고, 여유를 확보한 뒤 그 파일만 다시 돌려 기록한다.
- 다시 확인: `df -h /c`의 여유가 2GB를 넘는 상태에서 그 시험 파일만 돌려 통과하는지.

### 몇 ms 사이 같은 크기로 덮어쓴 파일의 시각이 그대로다
- 증상: 「preflight 뒤 바뀐 파일」 시험이 Windows에서 30번 중 3번 실패한다(`Missing expected rejection`, 10-13).
- 원인: 원본 기록과 덮어쓰기가 5~8ms 간격이면 NTFS가 같은 mtime/ctime을 찍고 크기·ino도 같아 stat 서명이 그대로다. 다른 프로그램 때문에 타이머 해상도가 1/8/15.625ms로 바뀌어 재현이 들쭉날쭉하다.
- 고침: 변경 감지를 시험할 때는 원본을 `utimes(path, old, old)`(60초 전)로 과거로 돌린 뒤 진짜로 덮어쓴다(같은 관용구 `delivery-file-inspection.test.mjs`). 원인 재현은 `--import` 로더 훅으로 `node:fs/promises`의 mtimeMs/ctimeMs를 16ms·1s 단위로 내려서 한다.
- 다시 확인: 1s로 내리는 훅을 걸면 옛 시험이 10/10 실패하고 고친 시험은 통과한다.

### `node --test tests/`처럼 폴더를 넘기면 시험이 하나도 안 돈다
- 증상: 데스크톱 전체 시험을 `node --test tests/`로 돌리자 요약이 「tests 1 · fail 1」이고 실패 이름이 `tests`였다(10-18, Node 24).
- 원인: 인자로 준 폴더를 시험 파일 하나로 실행하려다 실패한다. 폴더 안을 찾지 않는다.
- 고침: 셸 글롭으로 파일을 넘긴다: `node --test tests/*.test.*`(데스크톱 68개 파일, 858개 시험). 실패가 나오면 이번 변경이 없는 깨끗한 판(`git archive HEAD <폴더> | tar -x -C <임시>`)에서 같은 파일을 돌려 원래 깨진 것인지 가른다.
- 다시 확인: 요약의 tests 수가 수백이다. 10-18 master에서는 development-catalog·renderer-personalization·renderer-state·native-logout-provider의 6개가 이번 변경과 상관없이 원래 실패했다.

## 공용 증거를 덮는 시험

### 시험이 저장소 안 qa 폴더의 남의 캡처·보고서를 지우거나 덮는다
- 10-17 후속: 한글 `qa/flow.cjs`·WORLD `account-browser.test.mjs`·정적 QA 4개는 `tools/lib/qa-evidence.cjs`를 사용해 `.tmp/qa-runs` 아래 실행별 폴더와 소스 해시를 남기도록 고쳤다. 기존 캡처 삭제·덮어쓰기를 제거했고 두 실제 Chrome 흐름 동시 실행에서 추적 증거 211개 변경 0을 확인했다. 다른 QA는 기존 출력 경계를 계속 확인한다.
- 10-17 재검토: 명시한 파일만 해시하면 공통 모듈 변경을 놓칠 수 있다. 리터럴 로컬 import/require와 여러 줄 import/export의 전이 의존을 포함하도록 보완했다(누락 재현 후 관련 시험 13개 통과). 범위를 넓힌 이전 증거는 정상적으로 stale이며 당시 통과 기록은 보존한다. 원격·계산 경로·서버 URL 별칭은 추측하지 않고 미해결 목록과 명시 소스로 범위를 확인한다.
- 증상: 공용 작업본에서 확인을 돌렸더니 다른 세션의 미커밋 캡처·report.json·failure.png가 바뀌거나 사라졌다.
- 원인: 출력 위치가 스크립트 폴더나 `docs/_ops/qa/…`로 박혀 있는 시험이 있다. 알려진 것:
  - `experiences/hangul-stage/qa/flow.cjs` — 시작하자마자 qa 폴더 jpg를 모두 지우고 캡처·`flow-result.json`을 새로 쓴다.
  - `experiences/synk-world-app/qa/*-static.test.mjs`(frozen /world)·`account-browser.test.mjs` — 추적 파일인 report.json·failure.png를 쓴다.
  - 회사 `qa/verify-workspace-care-browser.mjs` — 기본 출력이 `docs/_ops/qa/workspace-care-20261009/browser`다.

## 화면 확인

### 빈 포트 서버에서 본인 페이지의 모듈·폰트를 403으로 막는다
- 증상: 운영 홈 브라우저 시험은 문서·CSS만 뜨고 「원문 연결 중」에서 멈췄다. 모듈과 폰트 GET은 403이었다(10-17).
- 원인: 시험은 `listen(0)`으로 빈 포트를 배정했지만 Origin 허용 목록은 전달받은 `port=0`을 썼다. Chrome의 모듈·폰트 요청은 Origin을 보낸다.
- 고침: `req.socket.localPort`의 실제 수신 포트로 Origin을 대조한다.
- 다시 확인: 본인 Origin의 app.js는 200, 다른 포트·외부 Origin은 403. PC·390px 실제 Chrome에서 원문·참고카드·트랙·보존 상태를 읽는 시험 통과.

### 통화 시험에서 Playwright 오프라인 흉내가 이미 맺어진 미디어 연결을 끊지 않는다
- 증상: 10-17 직원 통화 실제 Cloud 시험에서 `context.setOffline(true)` 6초 동안 HTTP 요청은 `ERR_INTERNET_DISCONNECTED`로 실패했지만 통화 화면은 계속 「통화 중」이었고 상대 소리도 끊기지 않았다. 망 복구를 시험했다고 착각하기 쉽다.
- 원인: 관찰상 오프라인 흉내는 새 HTTP 요청을 막았지만 이미 맺어진 WebRTC 미디어와 SDK 신호 연결은 이어졌다(SDK는 ICE 재시작만 한 번 기록). 흉내가 막는 범위의 내부 구현은 확인하지 않았다.
- 고침: 이 흉내는 heartbeat 실패 같은 HTTP 쪽 처리 확인에만 쓰고, 망 끊김·전환 복구는 실제 기기에서 Wi-Fi를 끄거나 망을 바꿔 확인한다. 보고에는 「미검증」으로 적는다.
- 다시 확인: 같은 시험에서 오프라인 동안 통화 화면 상태가 `connected`로 남고 상대 쪽 소리 진폭이 0이 아닌지.

### 헤드리스 Chrome으로 마이크·화면 공유를 실제로 주고받을 수 있다(유호님 창을 건드리지 않음)
- 증상: 통화·화면 공유 확인을 유호님 Chrome 확장으로 하면 권한 창·화면 선택 창이 유호님 화면에 뜬다.
- 원인: 확장은 유호님 창 안에서 돈다. 화면 선택 창은 페이지 바깥 브라우저 화면이라 자동으로 고를 수도 없다.
- 고침: Codex 런타임의 Playwright로 `chromium.launch({ channel: 'chrome', headless: true, args: ['--use-fake-ui-for-media-stream', '--use-fake-device-for-media-stream', '--autoplay-policy=no-user-gesture-required'] })`. 마이크는 가짜 삐 소리, `getDisplayMedia`는 선택 창 없이 가짜 화면(`monitor`)과 소리 트랙을 준다. `browser.newContext()`를 둘 열면 로그인 쿠키가 분리된 두 사람이 된다. 받은 소리는 `AudioContext` 분석기로 진폭을, 화면은 `requestVideoFrameCallback` 횟수로 잰다. 보기: `.tmp/company-voice-20261017/frontend-sdk/scripts/voice-cloud-qa.mjs`.
- 다시 확인: `.tmp/company-voice-20261017/frontend-sdk/scripts/probe-display.mjs`가 마이크 이름 `Fake Default Audio Input`과 화면 `monitor`·소리 1개를 출력하는지. 한 PC의 두 세션이므로 「두 기기 검증」으로 보고하지 않는다.

### 가려진 창에서는 SYNK 게임이 스스로 멈춘다
- 증상: 앱 미리보기 창이 다른 창 뒤에 있으면 자바스크립트로 돌린 게임 흐름이 45초 뒤 시간 초과로 끝나고 음성도 안 난다. CSS 전환이 멈춘 채 찍히거나 캡처가 시간 초과된다.
- 원인: 창이 가려지면 `document.hidden`이 되고, 게임은 `visibilitychange`에서 일시정지한다. 브라우저도 가려진 탭의 타이머를 늦춘다.
- 고침: 실제 플레이 확인은 격리된 헤드리스 Chrome으로 한다: `require.resolve('playwright', { paths: [path.join(process.env.USERPROFILE, '.cache/codex-runtimes/codex-primary-runtime/dependencies/node/node_modules')] })` → `chromium.launch({ channel: 'chrome', headless: true, args: ['--autoplay-policy=no-user-gesture-required'] })`. 보기: `experiences/order-rush/qa/atlas-smoke.cjs`. 녹화·시연 영상도 헤드리스 창과 게임 소리만 찍는다.
- 다시 확인: 헤드리스에서 `document.visibilityState`가 `visible`이고 게임 시계가 흐른다.

### 앱 안 브라우저 창이 가려져 있으면 read_page가 빈 페이지(Viewport 0x0)를 준다
- 증상: 10-18 격리 업무실 서버를 `preview_start`로 열자 `read_page`가 「(empty page) Viewport: 0x0」이었다. `tabs_context`는 창이 가려져 있다고 했다.
- 원인: 창이 가려져 그 탭의 보이는 크기가 0이라 그리지 않는다.
- 고침: `resize_window`로 크기(예: 1280×900)를 주면 가려진 채로도 그려져 읽기·클릭·찍기가 된다. 다 보면 `preset: desktop`으로 되돌린다. 가려진 페이지는 `document.hasFocus()`가 거짓이니 초점 확인은 `document.activeElement`로 한다.
- 다시 확인: 크기를 준 뒤 `read_page`가 로그인 칸 ref를 준다.

### 업무실 화면이 응답 뒤 맨 위로 튀고 입력 초점이 사라진다
- 증상: 10-18 제작 도구 「게시한 콘텐츠 등록」에서 계정을 고르거나 주소 확인 응답이 오면 화면이 맨 위로 갔다(`main.scrollTop` 512 → 0). `window.scrollY`는 늘 0이라 그것만 재면 놓친다.
- 원인: 스크롤 칸은 window가 아니라 `<main>`이다. 전체 `render()`(app.js `shell()`)가 `app.innerHTML`을 갈아 끼워 `<main>`이 새로 생기고, 초점 복원 목록(`data-action`·`data-tab` 등)에 `data-pf-*`가 없다.
- 고침: 응답·폼 안 변경은 전체 render() 대신 그 자리만 고치는 함수로 한다(`pfInboxPaint`·`pfReviewPaint`·`pfRegisterPaint`). 쓰는 중인 칸·열린 선택 상자가 바뀌지 않게 입력 칸은 갈아 끼우지 않고 값·disabled·안내만 고친다.
- 다시 확인: `document.querySelector('main').scrollTop`을 바꾸기 전·후로 잰다. 깊은 링크(`publicationAction=…`)의 스크롤·초점은 새로 고침 첫 로딩에서 다른 모듈의 늦은 render()에 풀린다(기존 `prepare`도 같음, 10-18 미해결). 깊은 링크 자체는 이미 열린 화면에서 `pfOpenTarget({action:'register'})`처럼 불러 확인한다.

### 헤드리스 크롬의 소프트웨어 WebGL에는 KHR_parallel_shader_compile이 없다
- 증상: 10-17 우리 집 3D 방 첫 그림 시험을 `--use-angle=swiftshader --enable-unsafe-swiftshader`로 띄우자 셰이더 미리 엮기 확인 두 개가 「확장 없음」으로 건너뛰어졌다.
- 원인: SwiftShader(소프트웨어 WebGL)는 이 확장을 내주지 않는다. GPU 인자를 주면 이 PC의 Intel 그래픽(ANGLE D3D11)으로 그리고 확장이 있다(Chrome·Edge 같음).
- 고침: 셰이더 엮기·GPU 멈춤을 재거나 시험할 때는 `args:['--enable-gpu','--use-angle=d3d11','--ignore-gpu-blocklist']`로 띄우고, 확장이 없는 기계에서는 그 확인만 건너뛴다(보기 `experiences/brand-opening/qa/home-room-first-frame.test.mjs`). 화면 멈춤은 아래 항목대로 트레이스의 화면 교체 간격으로, 화면 일 멈춤은 `PerformanceObserver({type:'longtask'})`로 잰다(`.tmp/world-room-firstpaint-20261017/measure.mjs`·`trace.mjs`).
- 다시 확인: 그 인자로 띄운 페이지에서 `document.createElement('canvas').getContext('webgl2').getExtension('KHR_parallel_shader_compile')`가 null이 아니다.

### 스크린캐스트·Playwright 녹화가 실제로는 바뀌던 화면을 멈춘 것처럼 비운다
- 증상: 10-18 WORLD 우리 집 문 열림 측정에서 CDP `Page.startScreencast` 프레임이 문이 열리기 시작하는 탭 뒤 1.2초에 0.14~0.47초 비었다(PC, 바꾸기 전·후 모두). Playwright `recordVideo`도 같은 자리에서 같은 그림이 이어졌다. 같은 실행의 크롬 트레이스에서는 `Display::DrawAndSwap`이 4ms 남짓마다 이어졌고(가장 큰 빈틈 37ms) 합성기의 `AnimationHost::TickAnimations`도 81번 돌았다.
- 원인: 모른다. 화면 교체는 계속되는데 스크린캐스트 캡처만 쉰다. 실제로 화면이 선 구간(셰이더를 하나씩 엮던 바꾸기 전 판)은 트레이스와 스크린캐스트 둘 다에 나왔다.
- 고침: 화면 멈춤은 `browser.startTracing(page,{categories:['viz','cc','blink.user_timing',…]})`로 찍고 `Display::DrawAndSwap` 간격으로 잰다(탭 순간은 `performance.mark`로 표시). 스크린캐스트·녹화의 빈틈은 후보로만 쓰고 트레이스로 확인한다. 도구 `.tmp/world-room-firstpaint-20261017/trace.mjs`(`SCREENCAST=1`이면 둘을 같이 찍음)·`trace-gaps.cjs`.
- 다시 확인: `SCREENCAST=1 node trace.mjs pc <json>`이 찍는 스크린캐스트 빈틈과 `node trace-gaps.cjs <json> 80`의 화면 교체 빈틈을 견준다(10-18: 스크린캐스트 `1218:256`, 화면 교체는 탭 직후 93ms 하나뿐).

### 개발 플랫폼 창의 원격 디버깅 포트를 다른 세션이 브라우저로 쓴다
- 증상: `npm run dev:platform -- --remote-debugging-port=9333`으로 띄운 개발 창이 꿀팁 사이트 페이지로 바뀌어 있었고, 그 상태에서 구독 화면 요청이 `UNTRUSTED_SENDER`로 거절됐다. 창이 다른 창 뒤에 있으면 `Page.captureScreenshot`도 멈춘다(10-17).
- 원인: 다른 세션의 CDP 스크립트가 같은 9333에 붙어 그 창을 페이지 캡처용 브라우저로 `Page.navigate`했다(`Get-NetTCPConnection -RemotePort 9333`에 그 세션의 node가 붙어 있었다). 플랫폼 화면이 아닌 페이지에서 온 IPC는 본체가 거절한다(정상 동작). 캡처는 창이 가려져 `document.hidden`이면 그리지 않아 기다린다.
- 고침: 세션마다 겹치지 않는 포트로 띄운다(예: `--remote-debugging-port=9455`, 스크립트는 `CDP_PORT`로). 같은 데이터 폴더로는 개발 창이 하나만 뜨므로 다시 띄우기 전에 그 포트에 붙은 연결부터 본다. 창을 앞으로 꺼낼 때는 같은 명령으로 한 번 더 실행하거나(앱이 두 번째 실행을 받아 창을 보임), user32 `ShowWindow(최소화 6 → 되살리기 9)`를 쓴다. 확인은 캡처 대신 `Runtime.evaluate`로 화면 글자·`synkDesktop.subscriptions.snapshot()`을 읽는다.
- 다시 확인: `http://127.0.0.1:<포트>/json`의 url이 `synk-desktop://platform/index.html`이고, `document.hidden`이 false다.

### 워크트리에서 띄운 개발 창은 SYNK ID 설정이 없어 로그인 전으로 뜬다

### 자동 검증의 시험 면제와 작업본 경로는 실제 실행 근거에 묶는다
- 증상: 10-18 Hermes 사전 검사에서 다른 형식의 검사 이름만 적으면 JS 시험 변경이 문법 검사만으로 통과했고, 작업본 루트를 junction으로 바꾸면 외부 폴더에 검사 근거를 쓸 수 있었다.
- 원인: 시험 면제를 실제 adapter 실행 조건과 연결하지 않았고 루트의 realpath 전에 lstat로 링크를 거르지 않았다.
- 고침: 해당 형식 변경과 실제 adapter 실행이 있을 때만 시험 면제를 허용하고 taskDir·workspace·snapshot-files 루트 링크를 먼저 거른다. 실패 후 수정은 같은 공식 세션의 프리뷰에서 재검사하고 최종 원본 반영 영수증은 별도 검사만 작성한다.
- 다시 확인: `tests/hermes-synk-validation-preview.test.cjs` 11개와 `tests/hermes-synk-validation.test.cjs` 28개에서 실제 Git 작업본·junction·실패 후 수정·원본/HEAD/인덱스 보존을 확인했다. 근거 `.tmp/hermes-multilang-20261018/`.
### 다중 형식 검사에서도 원본 의존성과 실제 값 소비를 분리한다
- 증상: TypeScript 시험용 node_modules junction으로 원본 패키지에 쓰기가 전달됐고, JSON의 값은 읽지 않고 키 존재만 확인한 시험도 값 소비로 인정됐다. 화면 사전 검사는 workspace-write 내부의 증거 경로를 거절했다.
- 원인: 실행 의존성을 원본에 쓰기 연결했고 Proxy의 has와 get을 같은 증거로 셌으며 최종 검사와 사전 검사의 저장 경계 차이를 놓쳤다.
- 고침: 컴파일용 연결은 실제 시험 전에 해제하고 실행 의존성은 용량·파일 수 제한이 있는 사본으로 만들어 변경도 검사한다. JSON은 변경 값 get을 요구한다. 화면 근거는 고정된 `.tmp/synk-validation-preview/<실행>/browser-*`만 작업본 내부에 허용하고 HTTP에서 `.tmp`를 제공하지 않는다.
- 다시 확인: 데이터 검증 시험 28개·화면 시험 13개, 전체 형식 결합 preview 통과. 원본 패키지 marker 불변·키 존재만 확인하는 시험 거절·PC/모바일 화면 근거와 `.tmp` HTTP 차단을 재현했다. 근거 `.tmp/hermes-multilang-20261018/review-runtime/`, `preview-combined/`.
