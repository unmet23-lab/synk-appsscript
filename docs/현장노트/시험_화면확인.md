### CI에서 실패한 시험을 `git archive HEAD` 사본으로 돌리면 통과한다 (2026-10-19)
- 증상: 위 8개를 `git archive HEAD <파일들> | tar -x`로 꺼낸 사본에서 돌리자 10/10 통과했다. 같은 때 공용 작업본에서는 8개가 실패했다.
- 원인: 공용 작업본의 로컬 master가 origin/master와 갈라져 있었다(10-19 로컬에만 180, origin에만 85커밋). CI가 돈 `efff8455e`는 origin에만 있었고, 공용 작업본에는 같은 내용이 미커밋 수정으로만 있었다.
- 고침: CI 재현은 `git fetch` 뒤 CI가 돈 커밋(`gh run view <id> --json headSha`)이나 `origin/master`에서 `git cat-file blob <rev>:<경로>`로 꺼내 돌린다(저장소 바이트 그대로라 LF다). 「깨끗한 판」으로 `git archive HEAD`를 쓰는 것은 로컬 master가 그 커밋을 품을 때만이다.
- 다시 확인: `git merge-base --is-ancestor <CI 커밋> HEAD`가 실패하면 HEAD로는 그 CI를 재현할 수 없다.

### 파이프로 받은 `node --test` 출력에 요약 줄이 없다
- 증상: `node --test … 2>&1 | grep '^# (tests|pass|fail)'`가 아무 줄도 못 잡는다. 실패 몇 개만 보이고 총 수·통과 수가 없어 시험이 다 돌았는지 모른다(10-17).

## 화면 확인

### 가려진 창에서는 SYNK 게임이 스스로 멈춘다
- 증상: 앱 미리보기 창이 다른 창 뒤에 있으면 자바스크립트로 돌린 게임 흐름이 45초 뒤 시간 초과로 끝나고 음성도 안 난다. CSS 전환이 멈춘 채 찍히거나 캡처가 시간 초과된다.
- 원인: 창이 가려지면 `document.hidden`이 되고, 게임은 `visibilitychange`에서 일시정지한다. 브라우저도 가려진 탭의 타이머를 늦춘다.
- 고침: 실제 플레이 확인은 격리된 헤드리스 Chrome으로 한다: `require.resolve('playwright', { paths: [path.join(process.env.USERPROFILE, '.cache/codex-runtimes/codex-primary-runtime/dependencies/node/node_modules')] })` → `chromium.launch({ channel: 'chrome', headless: true, args: ['--autoplay-policy=no-user-gesture-required'] })`. 보기: `experiences/order-rush/qa/atlas-smoke.cjs`. 녹화·시연 영상도 헤드리스 창과 게임 소리만 찍는다.
- 다시 확인: 헤드리스에서 `document.visibilityState`가 `visible`이고 게임 시계가 흐른다.

### 업무실 화면이 응답 뒤 맨 위로 튀고 입력 초점이 사라진다
- 증상: 10-18 제작 도구 「게시한 콘텐츠 등록」에서 계정을 고르거나 주소 확인 응답이 오면 화면이 맨 위로 갔다(`main.scrollTop` 512 → 0). `window.scrollY`는 늘 0이라 그것만 재면 놓친다.
- 원인: 스크롤 칸은 window가 아니라 `<main>`이다. 전체 `render()`(app.js `shell()`)가 `app.innerHTML`을 갈아 끼워 `<main>`이 새로 생기고, 초점 복원 목록(`data-action`·`data-tab` 등)에 `data-pf-*`가 없다.
- 고침: 응답·폼 안 변경은 전체 render() 대신 그 자리만 고치는 함수로 한다(`pfInboxPaint`·`pfReviewPaint`·`pfRegisterPaint`). 쓰는 중인 칸·열린 선택 상자가 바뀌지 않게 입력 칸은 갈아 끼우지 않고 값·disabled·안내만 고친다.
- 다시 확인: `document.querySelector('main').scrollTop`을 바꾸기 전·후로 잰다.

### 작업실 깊은 링크가 첫 로딩에서 초점·스크롤을 잃는다(응답 순서 경쟁)
- 증상: 10-18 `…publicationAction=register`를 새로 열거나 새로 고치면 주소 칸에 초점이 갔다가 BODY·`main.scrollTop` 0으로 끝날 때가 있었다(실행마다 달랐다). 이미 열린 화면에서 `pfOpenTarget`을 부르면 늘 정상이었다.
- 원인: 첫 로딩에 전체 render()가 다섯 번 온다. `loadWorkroom`의 끝(workroom.js:33, `workroom-guide`·`content-workspace` 응답)이 `pfFocusTarget` 뒤에 오면 그 다시 그리기가 `<main>`과 칸을 새로 만들어 풀린다. 비교로 연 `publicationAction=prepare`는 `productionId`·`versionId`가 없어 대상으로 읽히지도 않았다 — 비교용 링크에도 필수 값을 넣는다.
