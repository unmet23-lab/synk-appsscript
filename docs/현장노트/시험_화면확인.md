### CI에서 실패한 시험을 `git archive HEAD` 사본으로 돌리면 통과한다 (2026-10-19)
- 증상: 위 8개를 `git archive HEAD <파일들> | tar -x`로 꺼낸 사본에서 돌리자 10/10 통과했다. 같은 때 공용 작업본에서는 8개가 실패했다.
- 원인: 공용 작업본의 로컬 master가 origin/master와 갈라져 있었다(10-19 로컬에만 180, origin에만 85커밋). CI가 돈 `efff8455e`는 origin에만 있었고, 공용 작업본에는 같은 내용이 미커밋 수정으로만 있었다.
- 고침: CI 재현은 `git fetch` 뒤 CI가 돈 커밋(`gh run view <id> --json headSha`)이나 `origin/master`에서 `git cat-file blob <rev>:<경로>`로 꺼내 돌린다(저장소 바이트 그대로라 LF다). 「깨끗한 판」으로 `git archive HEAD`를 쓰는 것은 로컬 master가 그 커밋을 품을 때만이다.
- 다시 확인: `git merge-base --is-ancestor <CI 커밋> HEAD`가 실패하면 HEAD로는 그 CI를 재현할 수 없다.
- 10-19 덧붙임(커밋 전 검증도 같다): 로컬 HEAD에 내 경로를 얹어 꺼낸 판에서는 이어하기꾸러미 시험 하나가 실패했다. 그 시험이 읽는 회사 서버 시험 파일 4개의 합성 키 판이 origin에만 있었다. origin/master에 내 경로를 얹은 커밋을 `commit-tree`로 만들고(가지 없음) `git clone --shared --no-checkout` 클론에 `core.autocrlf=false`·`core.longpaths=true`를 켠 뒤 그 커밋을 꺼내 돌리면 CI와 같은 판·LF로 잴 수 있다. 이 저장소는 경로가 길어 scratchpad 클론에서 `core.longpaths`가 없으면 체크아웃이 「Filename too long」으로 멈춘다(10-19 백업 도구 85개 중 84 통과·1 설계된 건너뜀).
- 10-19 덧붙임(Claude, 0.4.32 후보 시험): `git archive <커밋> -- desktop atlas experiences … | tar -x`(Windows tar)는 한글 이름 파일 몇 개(`experiences/20260909/체험열기.cmd` 등)를 「Invalid empty pathname」으로 못 풀어 멈춘다. 공유 클론(`git clone --shared --no-checkout`) + `core.autocrlf=false`·`core.longpaths=true` + 희소 체크아웃(`/desktop/ /atlas/ /experiences/ /account/`)으로 꺼내고 `desktop/node_modules`만 공용 작업본에 junction으로 건다. 다 쓴 뒤에는 junction을 먼저 `[IO.Directory]::Delete(p,$false)`로 지운다.

### push 뒤 syntax-check 실행이 줄줄이 cancelled로 끝난다 (2026-10-19)
- 증상: 10-19 밤 계정판 3차 커밋 셋(`724fe663c`·`69950a3b7`·`33de840a4`)을 올린 뒤 세 커밋의 syntax-check가 모두 cancelled였다. 그 뒤로도 다른 세션이 1~2분마다 올려 `9c906b35c`·`44b71394b`·`609742d03`·`33de840a4` 실행이 잇달아 cancelled로 끝났다.
- 원인: `.github/workflows/syntax-check.yml`이 `concurrency: syntax-${{ github.ref }}`·`cancel-in-progress: true`라 master에 새 push가 오면 돌던 실행을 끊는다. 실행 하나가 몇 분 걸려 바쁜 때는 끝까지 도는 실행이 드물다. cancelled는 실패가 아니지만 내 커밋의 판정도 아니다.
- 고침: 내 커밋을 품은 뒤 커밋의 실행 가운데 끝까지 돈 것으로 판정한다 — `gh run list --branch master --workflow syntax-check.yml --json databaseId,headSha,conclusion`에서 고르고 `git merge-base --is-ancestor <내 커밋> <headSha>`로 품었는지 본다. 기다릴 때는 최신 실행을 따라가며 success·failure만 끝으로 치고 cancelled면 다음 실행으로 넘어가는 루프를 상한을 두고 뒤에서 돌린다. 그동안 내 변경을 읽는 시험은 손으로 돌려 둔다(문서만 바꿨으면 `rg -l "<문서 파일명>" tests`로 찾은 루트 시험 — 10-19 결정·설계·트랙을 읽는 9개 122/122).
- 다시 확인: `MSYS_NO_PATHCONV=1 git show origin/master:.github/workflows/syntax-check.yml | grep -A2 concurrency`가 `cancel-in-progress: true`면 아직 그대로다.

### 휴대폰 흉내 캡처에서 가로 넘침이 숨는다
- 증상: 영어판 긴 버튼 문구가 320~430px 화면 밖으로 나갔는데 `scrollWidth > innerWidth` 검사는 「이상 없음」이었다(09-30 홈페이지).
- 원인: 휴대폰 흉내(`isMobile`) Chrome은 가로 스크롤 대신 페이지 전체를 축소하고 `innerWidth`도 같이 늘린다. 실제 휴대폰도 같아서 사용자는 글자가 작아진 페이지를 본다.
- 고침: 휴대폰 폭 검사에 `innerWidth > visualViewport.width + 1`(축소됨)을 꼭 넣는다. 원인 요소는 `isMobile:false`로 같은 폭을 열어 `getBoundingClientRect().right > innerWidth`인 가장 깊은 요소로 찾는다. 화면 좌표로 픽셀을 재는 스크립트는 `innerHeight` 대신 `visualViewport.height`를 쓴다. `white-space:nowrap`을 줄 때는 영어 번역 길이를 먼저 본다.
- 다시 확인: 넘치는 요소를 일부러 넣은 페이지에서 `innerWidth > visualViewport.width`가 참이 된다.

### `overflow-x:clip`으로 가린 넘침은 scrollWidth에 안 잡히는데 전체 캡처는 넓어진다
- 증상: 10-19 PATH 시안에서 화면 끝까지 닿는 막대를 `:after{left:-100vmax;right:-100vmax}`로 그렸다. `scrollWidth`는 1440 그대로였는데 Playwright `fullPage` 캡처가 2840px 폭으로 나왔다.
- 원인: `html,body{overflow-x:clip}`이 사용자 스크롤은 막지만 레이아웃 넘침 자체는 남는다. 캡처는 그 넘침까지 포함한 크기로 찍는다. 휴대폰에서 확대·축소로 그 넘침이 보일 위험도 있다.
- 고침: 끝까지 닿는 바탕은 `box-shadow:0 0 0 100vmax #fff` + `clip-path:inset(0 -100vmax)`, 아래 선은 `border-image:linear-gradient(...) 0 0 1 0 / 0 0 1px 0 / 0 100vmax`(바깥으로 뻗는 테두리 그림)로 바꿨다. 둘 다 그림 넘침이라 레이아웃 폭을 만들지 않는다.
- 다시 확인: 같은 화면의 `fullPage` 캡처 폭이 창 폭(1440)과 같다.

- 고침: 같은 공식 파일 화면의 Raw 링크를 열어 원문에서 해당 정의만 확인했다. `TrackInfo.encryption`과 `Encryption.Type.GCM=1`은 원문에 있었으며 실제 Cloud/SDK 실행 검증과 구분했다.
- 다시 확인: GitHub 코드 화면의 Raw로 연 원문에서 필요한 정의를 찾고, Code 화면의 부분 DOM만으로 필드 부재를 단정하지 않는다.

### 구역만 찍은 캡처에 「본문으로 바로 가기」와 메뉴 막대가 찍힌다 (2026-10-19 Claude)
- 증상: 회사 페이지 한 구역을 Playwright `locator.screenshot()`으로 찍자, 화면에서는 안 보이는 「본문으로 바로 가기」 알약과 유리 메뉴 막대가 구역 한가운데에 찍혔다. 시안 탓인 줄 알고 찾았는데 공개본을 같은 순서로 찍어도 똑같았다.
- 원인: 화면보다 긴 요소를 찍으면 Playwright가 요소를 이어 찍으면서 `position:fixed` 요소(`.skip`·`.bar`)를 찍힌 그림 위에 다시 얹는다. 그 순간에도 `.skip`은 초점이 없고 `top:-80px`이라 페이지 문제는 아니다.
- 고침: 구역 캡처 전에 `page.addStyleTag({content: '.bar,.skip{visibility:hidden!important}'})`를 넣는다. 캡처에 이상한 것이 보이면 먼저 공개본을 같은 순서로 찍어 견준다(SYNK-appsscript 세션 scratchpad의 `skip-probe.mjs` 방식).
- 다시 확인: 같은 구역을 다시 찍어 두 요소가 없고, 쪽 전체 캡처(`fullPage`)에는 원래부터 안 보인다.

### vm으로 읽은 표를 `deepStrictEqual`로 견주면 값이 같아도 실패한다 (2026-10-19 Claude)
- 증상: `tests/라디오오버레이층.test.js`에서 `무대.html`의 `장면조각` 표(`vm.runInNewContext`로 읽음)와 `판.json`의 자리를 `assert.deepStrictEqual`로 견줬더니, 오류 문에 찍힌 두 배열이 `[63.756, 56.642, 7.476, 5.313]`으로 똑같은데 실패했다.
- 원인: vm 컨텍스트에서 만든 배열·객체는 다른 실행 영역의 `Array.prototype`을 가진다. `deepStrictEqual`은 원형까지 견준다.
- 고침: 읽은 값을 `JSON.parse(JSON.stringify(…))`로 한 번 풀어 이 영역의 값으로 바꾼 뒤 견준다. 열쇠 이름만 견주는 `Object.keys(…).sort()`는 문자열이라 그대로 된다.
- 다시 확인: 같은 표를 풀지 않고 견주면 실패, 풀어서 견주면 통과한다(10-19 라디오 시험 73/73).

### 앱 안 브라우저 zoom은 키우지 않고 잘라만 줘서 1920 화면의 작은 얼굴을 못 본다 (2026-10-19 Claude)
- 증상: 1920×1080 무대 지면의 까몽 눈 조각 자리를 보려고 앱 안 브라우저를 `resize_window` 1920×1080으로 두고 `zoom`했더니 40×30 영역이 36×27px로만 나왔다(좌표 틀도 800×450으로 줄어 있었다).
- 원인: 패널보다 큰 크기는 줄여 그리고, `zoom`은 그 줄인 화면을 자르기만 한다(「not magnified」).
- 고침: 헤드리스 크롬으로 실제 크기를 찍는다 — `chrome --headless=new --window-size=1920,1080 --virtual-time-budget=6000 --user-data-dir=<임시> --screenshot=<png> <주소>`. 타이머로 서서히 뜨는 지면은 `--virtual-time-budget`이 있어야 다 뜬 화면이 찍힌다. 한글 쿼리는 `encodeURIComponent`로 만든 주소를 노드 스크립트에서 넘긴다(Git Bash는 한글 변수 이름을 못 쓴다). 확인용 고정 인자(`무대.html?고정=깜빡`)로 얼굴마다 찍어 2배로 잘라 견준다.
- 다시 확인: 찍은 PNG가 1920×1080이고, 잘라 키운 눈 자리에서 털 결이 보인다(10-19 세 결 × 네 얼굴 12장).
