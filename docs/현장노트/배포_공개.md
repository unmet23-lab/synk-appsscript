## Platform 0.4.26 공개 전송과 동시 게시

### 다운로드 지연은 TLS 검증을 유지한 다른 전송기로 대조한다
- 증상: gh 다운로드는 TLS handshake timeout, curl 대용량 전송은 지연됐다. 작은 파일·Range 조회는 성공했다.
- 원인: 전송 지연은 관측했지만 네트워크·라이브러리의 근본 원인은 확정하지 않았다.
- 고침: Node HTTPS로 같은 공개 설치파일 전체를 읽어 크기와 SHA를 대조했다. Windows 파일은 검증 뒤 설치에 썼고 Range 재조립 결과도 같은 전체 SHA였다. TLS 검증·대상/해시 검사는 유지했다.
- 다시 확인: public-download-* 3개와 publication.json은 모두 검증된 공개 바이트를 기록한다. [현재 릴리스](../SYNK_플랫폼_계정과_연결_설계.md#care-native-closed-20261018).

### 게시 직전 다른 main 변경으로 push가 거절되면 검토한 트리를 통합한다
- 증상: 전체 공개 다운로드 대조 동안 다른 게시가 먼저 반영돼 feed 전환 push가 non-fast-forward로 거절됐다.
- 원인: 배포 시작 후 공개 main이 진행됐다. 설치파일은 이미 같은 불변 릴리스로 공개됐고 feed는 아직 이전 판이었다.
- 고침: 강제 push 없이 최신 main과 내 게시 커밋을 merge-tree로 통합했다. 다른 작업의 68개 경로를 바이트 그대로 보존하고 feed가 검토한 manifest인지 확인했다. pending 게시 영수증의 원본을 보존한 뒤 같은 게시를 재개했다.
- 다시 확인: 공개0a92bd7의 Pages built·변경19/19와 현재 PC 설치/수신을 확인했다. 다음 게시도 최신 원격과 영수증을 다시 확인한다.

### 공개 설치파일 대조가 「The operation was aborted due to timeout」으로 끊긴다 (2026-10-18)
- 증상: 0.4.27 게시(`publish.cjs --apply`)가 초안을 공개로 바꾼 뒤 세 설치파일을 끝까지 읽다가 5분 만에 멈췄다. 홈페이지·feed는 0.4.26 그대로였다.
- 원인: 0.4.26의 `node-download.cjs`는 파일 하나를 한 연결로 끝까지 읽고 `AbortSignal.timeout(300000)`이 그 전체에 걸린다. 그날 밤 Wi-Fi 전체 받기는 초당 1.7MB 남짓이고 이 연결은 0.2MB라 400MB를 5분 안에 못 받았다. 세 파일을 한꺼번에 24연결로 나눠 받아도 연결마다 너무 느려 조각 제한(90초)에 걸렸다.
- 고침: `node-download.cjs`를 4MB 정확한 Range(`Content-Range` 대조) 조각 받기 + 이어 붙인 전체 바이트·SHA 대조로 바꿨다(0.4.26 `range-download.cjs` 방식, TLS 검증 유지). 먼저 단독 실행으로 파일을 하나씩 16연결·조각 제한 5분으로 받아 두면, 게시 도구가 다시 부를 때 받아 둔 조각을 이어 붙여 바로 대조한다. 초안을 공개로 바꾼 뒤 멈춘 것이라 같은 게시 명령을 다시 돌리면 업로드는 건너뛴다.
- 다시 확인: 세 파일을 16연결로 차례로 받아 24분(Windows 473초 · Mac arm64 511초 · x64 470초), `.tmp/board-used-release-20261018/public-download-*.json` 세 개의 bytes·sha256이 `preview.json`과 같았다. 같은 게시 명령은 받아 둔 조각을 이어 붙여 24초 만에 끝나 synk-policy `81ad293`을 올렸고, `downloads/publication.json`의 `publicArtifacts` 전송 방식이 Range 대조다.

### 라디오 스크립트가 `Could not resolve hostname synk-radio`로 바로 끝난다
- 증상: 라디오 반영·검수·팩 스크립트가 `ssh: Could not resolve hostname synk-radio`(scp도 같은 문구)로 서버에 닿기 전에 끝난다(10-17 이후).
- 원인: 10-17에 저장소의 라디오 스크립트 52개가 서버 주소·계정(`synk@<주소>`) 대신 SSH 별칭 `synk-radio`를 쓰도록 바뀌었다. 주소는 저장소에 두지 않고 이 PC의 `~/.ssh/config` 한 곳에만 둔다. 같은 때 `StrictHostKeyChecking=no`를 `accept-new`로 바꿨다.
- 고침: `node tools/라디오서버열쇠.js`(상태 보기)가 찍는 `Host synk-radio` 블록을 `~/.ssh/config`(Windows는 `%USERPROFILE%\.ssh\config`)에 넣는다. 서버를 다시 만들어 호스트 키가 바뀌었으면 `ssh-keygen -R <주소>`로 옛 키를 지우고 한 번 접속한다 — `accept-new`는 처음 보는 키만 받고 바뀐 키로는 접속하지 않는다.
- 다시 확인: `ssh synk-radio "uptime"`이 서버 가동 시간을 찍는다.

### 라디오 서버 「설정만」 백업이 4GB 방송 묶음을 받기 시작한다
- 증상: `/opt/synk-radio`를 그림·소리 확장자만 빼고 tar로 받았더니 10분에 55MB(초당 약 90KB)로 끝없이 받았다(10-17). 서버 부하 평균은 2코어에 1.97이었고, 송출은 계속 🟢였다.
- 원인: 방송 묶음이 `.ts`(개당 75~100MB)이고, `.flac.first-blocksize…-backup`처럼 이름 끝이 다른 백업도 있어서 확장자로는 안 빠진다. 서버에서 나오는 속도도 송출 중이라 느리다.
- 고침: 크기로 고른다 — `find opt/synk-radio -type f -size -5M ! -name '*.log' ! -iname '*.ts' …(그림·소리·글꼴 형식)` 목록만 tar로 묶는다(10-17 125개 9.4MB, 90초). 받기를 멈출 때는 PC의 node·ssh를 끄고 서버에 tar가 안 남았는지 `pgrep -a tar`로 본다. 4.7GB 전체는 받지 않는다 — 방송 묶음은 창고의 원본으로 다시 만든다(`~/Documents/SYNK_원본창고/묶음백업.js`).
- 다시 확인: 서버 `du -sh /opt/synk-radio`(10-17 4.7GB, 디스크 30GB 중 95% 사용).

### 라디오 `.env`를 tar가 못 읽는다
- 증상: `tar: opt/synk-radio/.env: Cannot open: Permission denied`로 종료 2(10-17). 같은 폴더의 `송출/.env`는 읽혔다.
- 원인: 맨 위 `.env`는 root 전용(600)이고 ssh 계정은 `synk`다. 서비스(`radio-bot`)는 systemd가 root로 이 파일을 읽어 넘긴다.
- 고침: 목록은 `synk`로 만들고 묶기만 `sudo -n tar --null -T - -cf -`로 한다(이 서버는 비밀번호 없는 sudo가 된다).
- 다시 확인: `ssh … 'sudo -n true && echo ok'`.

### SYNK-website의 dist를 올리면 라이브에만 있던 남의 작업이 되돌아간다
- 증상: 브랜치의 `dist/*.html`을 그대로 복사하면 그 사이 라이브에 올라간 다른 작업(아틀라스 진입, PATH 로고 간격, 질문 답)이 되돌아간다.
- 원인: synk.im은 synk-policy `origin/main`이 그대로 서빙된다. 홈페이지 원고 저장소 SYNK-website(기본 가지 `codex/company-conversations`, master·main 없음)의 `dist/`는 라이브의 정본이 아니다. 다른 세션·GPT가 공개본을 직접 고치거나 원고만 고친 일이 있어, 원고 빌드·커밋된 dist·공개본이 셋 다 다르다.
- 고침: 공개 후보는 「공개본 + 내가 바꾼 파일만」(또는 「공개본 + (손대지 않은 원고 빌드 → 내 빌드)의 차이」 3방향)으로 만든다. 바꾸지 않은 파일·토큰은 공개본 값 그대로 둔다. 페이지는 통째로 덮지 말고 바뀐 섹션만 id로 옮겨 심는다. synk-policy 로컬 클론은 작업본으로 쓰지 않고 객체 저장소로만 쓴다: 별도 인덱스 `read-tree origin/main` → `hash-object -w --no-filters` → `update-index --cacheinfo` → `write-tree` → `commit-tree -p origin/main` → `git push origin <커밋>:refs/heads/main`. 커밋 직전에 `fetch`해 `origin/main`이 그대로인지 다시 본다.
- 다시 확인: `git ls-remote origin main`이 새 커밋이고, 후보에서 내 변경을 뺀 나머지가 공개본과 같다.

### 공개본 `account/dist/platform.js`를 master 빌드로 덮으면 남의 미공개 기능이 같이 나간다

### 공개본 번들을 고치면 `platform.html`의 `?v=`도 같이 바꿔야 한다
- 증상: 10-18 GPT 0.4.24부터 `account/platform.html`이 `./dist/platform.js?v=…`·`./benefits.css?v=…`로 부른다. 번들만 바꿔 올리면 주소가 그대로라 이미 받아 둔 브라우저·CDN이 옛 번들을 계속 쓸 수 있다. 같은 날 공개본이 한 시간 안에 두 번(`b45319c` 17:50 → `cb7005c` 18:03) 바뀌어, 만들어 둔 후보의 바탕이 낡았다.
- 원인: `?v=`는 그 파일 sha256 앞 12자다(`1ee4ff043b3f`·`35983c432263`·`f597f9b68d34`로 확인). `platform.css`·`member-insight.css`에는 아직 `?v=`가 없다. GPT는 공개본 번들을 직접 고쳐 짧은 간격으로 올린다.
- 고침: 번들을 바꾸면 `sha256sum account/dist/platform.js | cut -c1-12`로 `platform.html`의 `?v=`를 같이 바꾼다(`benefits.css`도 같다). 커밋 직전 `fetch` 뒤 바탕 파일 셋(번들·CSS·HTML)의 blob이 후보를 만든 공개본과 같은지 보고, 다르면 새 공개본 위에서 같은 바꾸기(정확히 한 번 나오는 원문만 바꾸는 스크립트)를 다시 돌린다. 후보에 HTML이 들면 `check.mjs`의 route가 `text/html`로 돌려줘야 한다(아니면 Playwright가 「Download is starting」으로 멈춘다).
- 다시 확인: 공개 뒤 `curl https://synk.im/account/platform.html | grep -o 'platform.js?v=[0-9a-f]*'`가 공개 번들 sha256 앞 12자와 같다(10-18 synk-policy `e9cf357`).
