## talk 함수(Supabase)

### 배포할 커밋이 origin보다 뒤처져 남이 올린 운영 판을 덮는다
- 증상: 10-04 전사 함수 배포가 1시간 전 다른 쪽이 PR을 합쳐 운영에 올린 판(예산 기록 포함)을 지웠다(곧바로 되돌림). talk의 `tools/배포빚.js`는 내 작업본 장부만 읽어 「최신」이라고 했다. 10-05에는 「품는가」 확인을 출력만 하고 멈추지 않아 배포가 그대로 나갔다.
- 원인: talk `tools/원격배포.js`는 지금 작업본 파일을 그대로 올린다. 운영 함수가 아직 master에 안 합친 PR 가지나 로컬 커밋에서 올라가 있기도 하고, 원격 가지 머리는 배포된 판보다 늦을 수 있다.
- 고침: 배포 직전에 `git -C <talk> fetch origin` → `git merge-base --is-ancestor origin/master <배포할 커밋>`(운영 함수가 PR 가지에서 올라가 있으면 그 가지 머리도)을 배포 명령과 `&&`로 묶어 거짓이면 배포가 안 나가게 한다. 배포 전에 `tools/배포대조.js <함수>`를 내 배포 판에서 돌려 「배포본과 다른 파일」이 내가 바꾼 파일뿐인지 본다. origin 장부(`git show origin/master:docs/_ops/배포장부.jsonl`)에서 그 함수의 최근 배포 head를 본다. 리허설에서 장부에 없는 남의 판은 내 변경과 무관하면 덮지 않는다(왕복 도구는 `함수목록`으로 게이트를 좁힌다).
- 다시 확인: 배포 뒤 `tools/배포대조.js <함수>`가 「같음」이다.

### 함수 판 번호가 내 배포 사이에 하나 건너뛴다
- 증상: 내가 올린 v23 다음이 v25다.
- 원인: Supabase는 함수 비밀값을 바꾸면 코드 변경 없이 모든 함수의 판 번호를 하나 올린다(`updated_at`은 그대로).
- 고침: 남이 덮었다고 단정하지 말고 `배포대조`와 비밀값 `updated_at`을 먼저 본다.
- 다시 확인: Management API 비밀값 목록의 `updated_at`이 건너뛴 시각과 맞는다.

### 운영 설정값을 두 쪽이 서로 다른 지시를 근거로 번갈아 덮는다
- 증상: 10-05 저녁 Claude 세션이 낮춘 학생 월 한도를 GPT가 24분 뒤 「복원」하고, 다시 Claude가 낮췄다. 서로 유호님의 다른 말씀을 근거로 썼다.
- 원인: 함수 비밀값(`SYNK_TUTOR_ENABLED`, `SYNK_AI_*_MICRO_USD` 한도, 가격표)은 커밋·장부에 남지 않는다. 먼저 보이는 흔적은 비밀값 목록의 `updated_at`(값은 다이제스트만)과 나중에 쓰는 talk `docs/_ops/회화튜터검증/<날짜>.json`이다.
- 고침: 설정을 말하거나 바꾸기 전과 바꾼 뒤에 `/secrets` 다이제스트를 후보 값의 sha256과 맞춰 지금 값을 보고 결정 표와 대조한다(값은 출력하지 않는다). 달라져 있으면 `updated_at` 앞뒤의 커밋·GPT 검증 기록에서 쓴 쪽과 근거를 찾고, 상대도 유호님 지시가 근거면 덮어쓰지 않고 트랙 §1에 두 지시와 지금 값을 적어 유호님이 정하게 한다. 바꾸는 스크립트는 「지금 값이 내가 본 값일 때만 쓴다」로 짠다.
- 다시 확인: 일을 마치기 전에 다이제스트를 다시 읽어 결정 표와 같다.

### 비밀값 쓰기와 겹친 배포가 성공 줄 없이 끝난다
- 증상: 운영 배포 도구가 성공 줄 없이 끝나 장부 줄이 없는데, 실제로는 코드가 올라가 있었다(`updated_at`도 그대로).
- 원인: 같은 때 다른 쪽이 비밀값을 썼다.
- 고침: 실패로 단정하지 않는다. 함수가 새 코드로 답하는지와 `배포대조`를 본 뒤 한 번 더 배포해 장부를 맞춘다. 함수 설정값은 다시 배포하지 않아도 바로 적용된다.
- 다시 확인: 다시 배포한 뒤 장부 줄과 `배포대조` 「같음」.

### `${JSON.stringify(x)}::jsonb`로 넘긴 JSON이 운영에서만 저장에 실패한다
- 증상: 프로필·학습 기록 저장이 운영 함수에서 실패하는데 시험은 모두 초록이었다(10-03).
- 원인: 운영의 `npm:postgres@3.4.4`가 jsonb 매개변수를 한 번 더 문자열로 직렬화한다. 시험의 PGlite는 이 직렬화를 흉내 내지 못한다.
- 고침: JSON은 `${q.json(x)}`(postgres.js 타입 매개변수)로 넘긴다. 새 쓰기 경로는 3.4.4 직렬화를 흉내 내는 시험 도구(talk `3c24ea0`)로도 돌린다. postgres 판을 올리면 이 동작을 다시 본다.
- 다시 확인: talk에서 `git grep -n -E 'JSON\.stringify\([^)]*\)\}::jsonb' -- lib supabase`가 주석 한 줄(`supabase/functions/events/index.ts`의 08-06 왕복 시험 메모 — 같은 함정이 그때도 있었다)만 낸다(10-17).

### 새 마이그레이션 이름의 계약 번호가 작으면 master 배포가 막힌다
- 증상: `_c16` 이름 조각을 c18 뒤에 운영에 올렸더니 master(c18) 배포가 「저장소가 DB보다 앞선다」로 1시간 넘게 막혔다(10-14).
- 원인: `tools/원격배포.js 판뒤처짐`은 `engine.schema_migrations`에서 version이 가장 큰 기록 이름의 `_cNN`을 저장소 최신 파일 번호와 견준다.
- 고침: 새 조각 이름은 그때 최대 계약 번호 이상으로 짓는다. 막혔으면 기록 전용 조각(예: `…_synk_contract_c18`)으로 되돌린다. 분기 조각은 `tests/lib/migration-branches.js`(계보·separatelyVerified)와 `tools/lib/연동사후상태.js`(연동 표)에, 새 cron은 `tests/조용한실패.test.js`·`tests/회차장부.test.js`·`tools/검증_마이그레이션.sh`에 등록하고, 새 도구에는 `인자게이트`를 단다.
- 다시 확인: 배포 전 `tools/원격배포.js 판뒤처짐`이 통과한다.

### 옛 커밋의 함수 본체를 쓰면 운영 env 허용 목록이 빠진다
- 증상: 옛 커밋의 운세 `index.ts`를 쓰다 `SYNK_FORTUNE_CLIENT_IDS` 허용 목록이 빠진 판이 약 4분 운영에 나갔다(10-14).
- 원인: 동봉 lib만 운영과 맞추고 본체는 대조하지 않았다.
- 고침: 배포 전에 본체의 `Deno.env.get(…)` 목록을 운영 배포본과 비교한다. master 밖에서 배포돼 온 함수는 운영 배포본(ESZIP)에서 원문을 꺼내 재료를 복원한 뒤 내 변경만 얹는다.
- 다시 확인: 새 판의 env 목록 = 운영 배포본 env 목록(+ 내가 더한 것).

### talk 운영 DB를 pg_dump로 받으려는데 접속할 길이 없다
- 증상: 이 PC에 pg_dump·Supabase CLI·Docker가 없고, DB 비밀번호도 없다. 관리 API의 풀러 설정(`/v1/projects/<ref>/config/database/pooler`)은 트랜잭션 모드 6543만 돌려준다(10-17).
- 원인: pg_dump는 트랜잭션 풀러로는 못 쓴다. 세션 모드는 같은 호스트의 5432다. DB 비밀번호는 관리 API로 읽을 수 없다.
- 고침: 관리 API SQL로 읽기 전용 계정(`pg_read_all_data` + `BYPASSRLS`)을 만들고 비밀번호는 PC에서 SCRAM 해시로 만들어 해시만 보낸다(`~/Documents/SYNK_원본창고/talk백업.js 준비`). 접속은 세션 풀러 `<풀러 호스트>:5432`, 사용자 `<계정>.<ref>`, 비밀번호는 `%APPDATA%\postgresql\pgpass.conf`. 클라이언트는 EDB 「binaries」 zip(17.11, 서명 없음)의 `bin`만 풀어 쓴다. 서버가 17.6이라 클라이언트도 17이어야 한다.
- 다시 확인: `pg_dump --schema-only`가 종료 0으로 끝난다(10-17 648KB, 전체 `-Fc` 3.4MB·70초).

### pg_dump를 `pg_restore -l`에 같이 흘리면 덤프가 쓰기 실패로 끝난다
- 증상: `pg_dump -Fc | tee … | pg_restore -l`에서 pg_dump가 `could not write to output file: Invalid argument`, tee가 141(SIGPIPE)로 끝났다(10-17).
- 원인: `pg_restore -l`은 앞쪽 목차만 읽고 바로 끝나 파이프를 닫는다.
- 고침: 목차 확인 쪽 파이프의 쓰기 오류는 무시하고 덤프 흐름은 끝까지 읽는다(`talk백업.js`가 Node에서 그렇게 나눠 흘린다). 덤프가 끝까지 되는지는 `pg_dump … | wc -c`로 따로 본다.
- 다시 확인: 셸에서 같은 파이프를 돌리면 `PIPESTATUS`가 `1 141 0`이다.

## 라디오 서버

### 라디오 스크립트가 `Could not resolve hostname synk-radio`로 바로 끝난다
- 증상: 라디오 반영·검수·팩 스크립트가 `ssh: Could not resolve hostname synk-radio`(scp도 같은 문구)로 서버에 닿기 전에 끝난다(10-17 이후).
- 원인: 10-17에 저장소의 라디오 스크립트 52개가 서버 주소·계정(`synk@<주소>`) 대신 SSH 별칭 `synk-radio`를 쓰도록 바뀌었다. 주소는 저장소에 두지 않고 이 PC의 `~/.ssh/config` 한 곳에만 둔다. 같은 때 `StrictHostKeyChecking=no`를 `accept-new`로 바꿨다.
- 고침: `node tools/라디오서버열쇠.js`(상태 보기)가 찍는 `Host synk-radio` 블록을 `~/.ssh/config`(Windows는 `%USERPROFILE%\.ssh\config`)에 넣는다. 서버를 다시 만들어 호스트 키가 바뀌었으면 `ssh-keygen -R <주소>`로 옛 키를 지우고 한 번 접속한다 — `accept-new`는 처음 보는 키만 받고 바뀐 키로는 접속하지 않는다.
- 다시 확인: `ssh synk-radio "uptime"`이 서버 가동 시간을 찍는다.

### 라디오 서버 「설정만」 백업이 4GB 방송 묶음을 받기 시작한다
- 증상: `/opt/synk-radio`를 그림·소리 확장자만 빼고 tar로 받았더니 10분에 55MB(초당 약 90KB)로 끝없이 받았다(10-17). 서버 부하 평균은 2코어에 1.97이었고, 송출은 계속 🟢였다.
- 원인: 방송 묶음이 `.ts`(개당 75~100MB)이고, `.flac.first-blocksize…-backup`처럼 이름 끝이 다른 백업도 있어서 확장자로는 안 빠진다. 서버에서 나오는 속도도 송출 중이라 느리다.
- 고침: 크기로 고른다 — `find opt/synk-radio -type f -size -5M ! -name '*.log' ! -iname '*.ts' …(그림·소리·글꼴 형식)` 목록만 tar로 묶는다(10-17 125개 9.4MB, 90초). 받기를 멈출 때는 PC의 node·ssh를 끄고 서버에 tar가 안 남았는지 `pgrep -a tar`로 본다. 4.7GB 전체는 받지 않는다 — 방송 묶음은 창고의 원본으로 다시 만든다(`~/Documents/SYNK_원본창고/묶음백업.js`).
- 다시 확인: 서버 `du -sh /opt/synk-radio`(10-17 4.7GB, 디스크 30GB 중 95% 사용).

### 라디오 `.env`를 tar가 못 읽는다
- 증상: `tar: opt/synk-radio/.env: Cannot open: Permission denied`로 종료 2(10-17). 같은 폴더의 `송출/.env`는 읽혔다.
- 원인: 맨 위 `.env`는 root 전용(600)이고 ssh 계정은 `synk`다. 서비스(`radio-bot`)는 systemd가 root로 이 파일을 읽어 넘긴다.
- 고침: 목록은 `synk`로 만들고 묶기만 `sudo -n tar --null -T - -cf -`로 한다(이 서버는 비밀번호 없는 sudo가 된다).
- 다시 확인: `ssh … 'sudo -n true && echo ok'`.

### 공용 작업본에서 빌드한 공개 묶음에 남의 미커밋 변경이 실린다
- 증상: `tools/prepare-personal-public.mjs`가 다른 세션의 미추적 모듈을 import해 허용 목록 오류로 멈췄다(멈추지 않았다면 남의 미완성 코드가 공개될 뻔, 10-14). 공용에서 돌린 `node tools/build-world-life.mjs`가 남의 미커밋 `atlas/vellum.js`를 묶음에 섞었다(10-15). SYNK-website 공용 작업본 빌드에 다른 세션의 미커밋 변경이 섞였다(10-01).
- 원인: 빌드 도구의 기본 root가 작업본이라 미커밋·미추적 파일을 그대로 묶는다.
- 고침: `git -c core.autocrlf=false archive origin/master <필요한 경로들> | tar -x -C .tmp/<작업>/root`로 사본을 만들고 내 수정 파일만 복사해 빌드·시험한다(`preparePersonalPublic({ root })`처럼 root를 준다). esbuild는 `experiences/synk-account/node_modules` junction으로 잇고 끝나면 링크만 지운다([git 노트 · junction](git_줄끝_잠금.md#junction이-든-워크트리를-통째로-지우면-공용-node_modules가-지워질-수-있다)). 공용에서는 묶음을 빌드하지 말고 `git show HEAD:<묶음> > <파일>`로 커밋 판을 둔다. SYNK-website는 `robocopy SYNK-website <사본> /E /XD .git .tmp /XJ`로 뜨고(`.tmp`를 안 빼면 9GB를 복사하다 멈춘다) 사본 옆에 `SYNK-appsscript`·`SYNK-talk` junction을 둔다.
- 다시 확인: 사본 빌드 결과에서 내 변경을 뺀 나머지가 원본 빌드와 바이트로 같다.

### 공개 앱의 SYNK ID 콜백을 새 클라이언트로 만들 필요가 없다
- 증상: 공개 주소 하나를 더하려고 새 OAuth 클라이언트·제품 매핑을 만들 뻔했다(10-14 앨범).

- 고침: 그 클라이언트에 콜백만 더한다. 포털 `id/config.json`의 동의 목록에도 같은 콜백을 넣어 함께 게시한다. 공용 journal의 기존 키(`publicPersonal`)에 낯선 제품을 넣으면 그 도구가 `JOURNAL_INVALID`로 멈추니 새 키로 남긴다.
- 다시 확인: 공개 주소에서 SYNK ID 로그인 왕복이 끝난다.

## synk.im(synk-policy)

### SYNK-website의 dist를 올리면 라이브에만 있던 남의 작업이 되돌아간다
- 증상: 브랜치의 `dist/*.html`을 그대로 복사하면 그 사이 라이브에 올라간 다른 작업(아틀라스 진입, PATH 로고 간격, 질문 답)이 되돌아간다.
- 원인: synk.im은 synk-policy `origin/main`이 그대로 서빙된다. 홈페이지 원고 저장소 SYNK-website(기본 가지 `codex/company-conversations`, master·main 없음)의 `dist/`는 라이브의 정본이 아니다. 다른 세션·GPT가 공개본을 직접 고치거나 원고만 고친 일이 있어, 원고 빌드·커밋된 dist·공개본이 셋 다 다르다.
- 고침: 공개 후보는 「공개본 + 내가 바꾼 파일만」(또는 「공개본 + (손대지 않은 원고 빌드 → 내 빌드)의 차이」 3방향)으로 만든다. 바꾸지 않은 파일·토큰은 공개본 값 그대로 둔다. 페이지는 통째로 덮지 말고 바뀐 섹션만 id로 옮겨 심는다. synk-policy 로컬 클론은 작업본으로 쓰지 않고 객체 저장소로만 쓴다: 별도 인덱스 `read-tree origin/main` → `hash-object -w --no-filters` → `update-index --cacheinfo` → `write-tree` → `commit-tree -p origin/main` → `git push origin <커밋>:refs/heads/main`. 커밋 직전에 `fetch`해 `origin/main`이 그대로인지 다시 본다.
- 다시 확인: `git ls-remote origin main`이 새 커밋이고, 후보에서 내 변경을 뺀 나머지가 공개본과 같다.

### 올리기 전에는 빠진 파일·깨진 주소를 못 본다
- 증상: 새 페이지가 부르는 CSS·JS·자산 하나가 후보에 빠져 공개 뒤에야 깨진 것을 안다.
- 원인: 로컬 미리보기는 공개 트리와 파일 구성이 다르다.
- 고침: 페이지를 통째로 바꿀 때는 새 페이지가 부르는 파일을 전부 따라가(HTML → CSS/JS → 자산) 공개 트리와 견준다. 올리기 전에 Playwright `context.route('https://synk.im/**')`로 후보 파일(공개본 전체를 푼 폴더 위에 바뀐 파일만 든 폴더를 앞에 얹은 것)을 돌려주게 해 실제 주소로 열어 본다 — 빠진 파일·콘솔 오류·질문창·첫 화면 이동까지 공개 전 바이트로 확인된다. 같은 방법으로 공개 뒤에도 `live` 주소로 다시 돈다.
- 다시 확인: route로 연 후보에서 실패 요청 0, 콘솔 오류 0.

### 부분 클론에서 `ls-tree -l`·`git grep`이 몇 분씩 멈춘다
- 증상: 새 노트북의 synk-policy 클론(`--filter=blob:none --no-checkout`)에서 크기 목록·트리 전체 grep이 멈춘 듯 오래 걸린다(10-17).
- 원인: 빠진 blob을 하나씩 받으러 간다.
- 고침: 필요한 글 파일만 `git ls-tree -r`로 oid를 모아 `git fetch --no-tags --filter=blob:none origin <oid…>`로 한 번에 받고(208개 4초) `GIT_NO_LAZY_FETCH=1 git cat-file blob <oid>`로 읽는다. 큰 트리의 `write-tree`도 2분쯤 걸리니 백그라운드로 돌린다.
- 다시 확인: `git -C ../synk-policy config --get remote.origin.partialclonefilter`가 `blob:none`이면 부분 클론이다.

### 반영됐는지를 시각으로 판단하면 틀린다
- 증상: 「올린 지 몇 분 지났으니 반영됐다」고 봤는데 캐시·Pages 빌드가 아직이었다.
- 원인: Pages 반영에 1~3분, 바쁜 밤에는 curl 한 바퀴에 10분 넘게 걸렸다. Node fetch는 옛 노트북에서 synk.im 인증서를 거절했다([윈도우 셸 노트](윈도우_셸.md#node-fetch가-synkim-인증서를-거절했다)).
- 고침: `curl -H 'Cache-Control: no-cache' 'https://synk.im/<경로>?probe=<임의값>'`의 sha256이 올린 파일과 같을 때까지 잰다(지운 파일은 404). 오래 걸리면 백그라운드로 돌린다. Pages 빌드 상태는 `gh api repos/unmet23-lab/synk-policy/pages/builds/latest`.
- 다시 확인: 바뀐 파일 전부가 바이트로 같다(예: 21/21).

### 공개할 때마다 CDN 캐시가 비워져 큰 영상이 멈춘다
- 증상: 공개 직후 PATH 면접 준비가 60초를 넘겨 「영상 응답 시간이 초과되었습니다」로 멈춘다(10-12·10-13 재현). 남의 공개 뒤에도 같다.
- 원인: 공개할 때마다 사이트 전체 CDN 캐시가 비워져 4K 영상(장면당 약 10MB)이 원본에서 초당 약 200KB로 온다.
- 고침: 공개 뒤 흐름이 멈추면 코드보다 먼저 영상 캐시를 보고, 서울 지점은 영상 14개(`strict-*-4k.mp4`·`strict-*-720p.mp4`)를 한 번씩 받아 채운다. 작은 공개를 여러 번 나누지 말고 묶는다. 배포 직후 공개 주소 점검은 `GOTO_TIMEOUT=180000`처럼 넉넉히 준다.
- 다시 확인: `curl -s -o /dev/null -w '%header{x-cache} age:%header{age}' <영상 주소>`가 HIT를 낸다.

### 배포 점검(site-check)이 취소·일시 실패·옛 구조 요구로 빨개진다
- 증상: main에 올리면 GitHub Actions 「synk.im 배포 점검」(약 11분)이 도는데, 잇달아 올리면 앞 점검이 cancelled로 끝난다. 내가 올리지 않은 파일 하나가 503으로 실패한다. 페이지 구조를 바꾼 직후 점검이 8건 실패했다(사이트는 정상, 10-13).
- 원인: 뒤이은 push가 앞 실행을 취소한다. 배포 직후 몇 분은 Pages가 파일·모듈 하나에 503을 줄 수 있다. 점검 스크립트 `.github/site-check/check.mjs`가 옛 선택자·속성(LAB 카드의 `data-video` 등)을 요구하고 있었다.
- 고침: `gh run list -R unmet23-lab/synk-policy --workflow site-check.yml`로 내 커밋이나 그 뒤 커밋의 점검이 통과했는지 본다(취소됐으면 다음 실행으로 확인). 503 하나는 curl로 그 주소가 200이고 바이트가 커밋 blob과 같은지 본 뒤 `gh run rerun <id> -R unmet23-lab/synk-policy --failed`. 구조를 바꿀 때는 공개 전에 check.mjs에서 그 선택자를 grep해 같이 고친다. 게임 화면을 다시 만들면 점검의 시작 단추 표(`startOf`)를 지키거나 같이 고친다. 점검은 `brief/`를 화면·도구 이름 검사에서 빼므로 맞춤 도구(`/brief/meeting/` 등)는 공개 뒤 직접 열어 본다. 실패 화면은 artifact `site-check-screens`(7일). 통과를 보기 전에는 기록에 「배포 점검 통과」라고 쓰지 않는다. 같은 점검을 로컬에서: `SITE_BASE=<주소> PLAYWRIGHT_MODULE=<Codex 런타임 playwright/index.mjs> node .github/site-check/check.mjs`.
- 다시 확인: 내 커밋 이후 첫 완료 실행이 success다.

### 공개 파일에 제작 도구 이름이 남는다
- 증상: 음성 목록 JSON에 음성 모델·엔진·목소리 이름이, 레이싱 `assets/music/sources.json`에 음악 도구 이름이, 공개 파일 주석에 claude.ai 주소가 들어가 점검에 걸렸다(10-02·10-07·10-17).
- 원인: 화면에 안 나오는 데이터·주석·MP3 ID3 태그에도 이름이 남는다. 배포 점검은 저장소 공개 파일과 MP3 태그의 도구 이름을 본다(목록은 공개 저장소라 base64로 적혀 있다).
- 고침: 게임 묶음은 SYNK-website `strip-game-metadata.mjs`가 게임이 읽는 칸만 남기고 태그 크기 그대로 빈칸을 채운다. 새 데이터 종류가 생기면 규칙에 더한다. 첫 공개(10-02)에는 게임이 읽지 않는 제작 자료 97개(원본 그림 `*-original.*`, 음성 제작 기록 `*.source.json`, `source/` 그림 지시문)가 섞여 나갔다 — 지금은 묶기 스크립트가 빼지만, 새 게임을 넣을 때는 코드가 부르지 않는 큰 파일·지시문이 없는지 본다. `sync-play-games.mjs` 끝의 「남은 로컬 주소·입구·도구 이름」이 0이 아니면 올리지 않는다. 직접 올리는 후보는 stage 뒤 `git diff --cached -U0 | grep -iE "claude|gpt|codex|…"`로 본다.
- 다시 확인: 후보 폴더에서 같은 grep과 점검의 도구 이름 단계가 0건이다.

### 캐시 토큰 `?v=`를 다시 계산하면 안 바꾼 파일까지 바뀐다
- 증상: 깨끗한 빌드의 `?v=` 토큰이 공개본과 많이 달라 안 바꾼 페이지까지 바뀐 것으로 나온다.
- 원인: 공개본의 `?v=`는 작업본 파일을 그대로 해시한 값이 아니다(배포 시점이 제각각이고, 저장소는 LF·작업본은 CRLF). WORLD 진입 페이지와 게임 index의 `?v=`는 빌드가 붙이지 않는 공개 때 손질이다.
- 고침: 바뀐 파일만 새 값(예: sha256 앞 12자리, 또는 `?v=<작업>-<날짜>`)을 붙이고, 올리지 않는 파일은 공개본 값 그대로 쓴다. HTML은 통째로 덮지 말고 토큰 줄만 바꾼다.
- 다시 확인: `git diff --numstat -- '*.html'`이 파일마다 `1 1`이다.

### 성능 전후 비교가 부풀려진다
- 증상: 최적화본만 로컬 파일로 덧씌워 재니 LCP가 「1.34 → 0.37초」로 좋아 보였다(10-13, 잘못 적음).
- 원인: 한쪽만 망 지연이 빠졌다. 순서대로 재면 PC 부하 변화가 판 차이처럼 보인다.
- 고침: 두 판을 같은 로컬 정적 서버(gzip)에 올리고 같은 CDP 망 제한(PC 10Mbps·40ms, 휴대폰 1.6Mbps·150ms·CPU 4배)으로, 판을 번갈아 여러 번 재 가운데 값을 쓴다(`experiences/path-vr/qa/optimize-20261013/`).
- 다시 확인: 같은 판을 두 번 넣어 재면 차이가 잡음 범위 안이다.

### 맞춤 도구의 줄인 폰트를 같이 올리면 남의 글자가 빠지거나 바뀐다
- 증상: `brief/meeting/`을 부분 공개하는데 줄인 폰트 `assets/SUIT-subset.woff2`가 공개본과 달라진다(10-07).
- 원인: 줄인 폰트는 원고 글자에 따라 달라진다. 공개 `wizard.js`·`atlas-engine.js`도 원본과 달라, 통째로 다시 빌드하면 그 차이까지 나간다.
- 고침: 공개 파일 해시(`git ls-tree origin/main`)를 바꾸기 직전 원본 해시와 견줘 같은 것만 새 원고 blob으로 바꾼다. 폰트는 build.mjs와 같은 방식으로 공개 파일들에서 먼저 다시 만들어 공개 폰트와 바이트가 같은지 본 뒤, 새 원고 + 공개 파일로 새 폰트를 만든다. 새 글자가 없으면 폰트는 올리지 않는다.
- 다시 확인: 공개 파일로 다시 만든 폰트가 공개 폰트와 바이트로 같다.

### SYNK-website `npm run check`가 깨끗한 사본에서 실패한다
- 증상: 복제본에서 `npm run check`를 돌리면 시험이 ENOENT나 묶음 누락으로 실패하고, 영어 시험은 아예 안 돈다.

- 고침: 저장소 전체 checkout + `node_modules` junction + 형제 `../SYNK-appsscript` junction(또는 `SYNK_CANON_ROOT`) 위에서 돌린다. 영어 시험은 따로 돌린다. 실패하면 변경 전후의 실패 목록부터 견준다. v10 쪽만 바꿀 때는 `git clone --no-checkout` → `git checkout <rev> -- site-v10 package.json src`만 꺼내 `node site-v10/knowledge.mjs --base site-v10/knowledge/base --out out && node site-v10/build.mjs --out out --assets out`로 몇 초 만에 빌드하고, 변경 전 판도 같이 빌드해 둔다.
- 다시 확인: 10-13 `a4126b2` 이후 커밋된 dist 그대로 242/242 + 영어 139/139가 통과했다 — 같은 수가 나오는지 본다.

### 회사 VM SSH 22번이 시간 초과로 끝난다
- 증상: 회사 VM으로 가는 ssh가 거부가 아니라 시간 초과로 끝난다(10-10 저녁). 10-17 새 노트북에서도 22번 연결이 6초 안에 답이 없었다.
- 원인: GCP 방화벽 규칙 `synk-company-provision-ssh`가 IP 하나(/32)만 허용한다. 이 PC의 공인 IP는 집 회선에서 두 값 사이를 오갔고(10-10 새벽에는 허용된 쪽, 저녁에는 아닌 쪽), 새 노트북이나 다른 망이면 또 다르다.
- 고침: 먼저 IP 문제인지 읽기만 하는 검사로 본다(바꾸는 것 0). 방화벽은 보안 설정이라 AI가 바꾸지 않는다. 유호님이 임시 허용 스크립트(`temporary-operator-network.cjs`의 `apply`는 지금 IP /32를 하나 더하고, `restore`는 원래 하나로 되돌림)를 직접 실행한다. 열기 → VM 작업 → 닫기를 스크립트 하나로 묶어(IP가 이미 허용 쪽이면 열지 않음, 어디서 멈춰도 finally에서 닫음, 영수증 저장) 한 번만 누르게 한다(보기 `.tmp/workspace-signal-cleanup-20261010/cleanup-cold-copies.cjs`).
- 다시 확인: PowerShell `$c=New-Object Net.Sockets.TcpClient; $c.ConnectAsync("<VM 주소>",22).Wait(6000)`이 False면 막힌 쪽이다(10-17 False).

### 열기·닫기 명령을 함께 보여 주면 16초 만에 다시 닫힌다
- 증상: 10-10에 임시 허용의 열기·닫기 두 줄을 한꺼번에 보여 드리자 둘 다 실행되어 16초 만에 다시 닫혔다.
- 원인: 두 명령의 순서와 때를 글로만 나눠 적었다.
- 고침: 따로 실행할 명령은 한 번에 하나만 보여 준다. 열기를 실행했다는 말을 들으면 journal의 `temporary-access-verified`와 22번 연결로 확인하고, 닫기는 반영이 다 끝난 뒤 따로 보여 준 다음 `original-access-restored`와 22번 차단을 확인해 기록에 적는다. 잇단 반영 동안은 열어 두고 마지막에 한 번 닫는다. 가장 좋은 길은 위 항목처럼 한 스크립트로 묶는 것이다.
- 다시 확인: journal의 상태와 시각이 열기 → 작업 → 닫기 순서인지 본다.

### 임시 허용 `apply`가 시작하자마자 멈춘다
- 증상: `temporary-operator-network.cjs apply`가 `EXISTING_ACCESS_JOURNAL_INSPECT_FIRST`나 `OPERATOR_IP_CHANGED`로 멈춘다.
- 원인: 지난 기록(`network-private*/temporary-access-journal.json`)이 남아 있으면 `apply`가 멈춘다. 또 이 스크립트(v6)에는 허용 IP와 임시 IP가 고정값으로 들어 있어서, 지금 IP가 그 임시 값이 아니면 `OPERATOR_IP_CHANGED`로 멈춘다(10-17 코드를 읽어 확인).
- 고침: 새 작업 폴더에 스크립트와 `original-firewall.json`을 복사해서 쓴다(10-10 `.tmp/workspace-signal-v3-20261010/`). 막다른 길: 새 노트북에서는 아직 돌려 보지 않았다. IP가 바뀌었으면 고정값을 고친 판이 먼저 있어야 한다.
- 다시 확인: `rg -n "EXISTING_ACCESS_JOURNAL|OPERATOR_IP_CHANGED" .tmp/workspace-signal-v3-20261010/temporary-operator-network.cjs`(10-17 둘 다 있음).

### HA 계정 기준값을 읽은 뒤 재가동 QA의 소스 목록이 달라진다
- 증상: 10-17 성과 예약 릴리스 재가동에서 `bind-accounts`가 누락된 `read-account-baseline.cjs` 때문에 원격 호출 전에 멈췄다. 기존 검증 파일을 바이트 동일하게 복사해 기준값을 읽자, 다음 `prepare-arm`은 `COMPLETE_QA_SOURCE_CLOSURE`로 멈췄다.
- 원인: Linux QA는 `rearm-operations.cjs`의 상대 `require()`가 가리키는 실제 파일까지 재귀 수집한다. 누락 파일이 있던 QA 때 323개였고 복사 후 324개가 되어 고정 목록과 달랐다.
- 고침: 완료된 계정 읽기용 파일을 QA 수집 범위 밖의 같은 작업 폴더 루트로 옮겨 323개를 복원했다. 첫 준비에서 이미 만든 정적 입력은 지우거나 덮지 않고, 별도 재개 스크립트로 기존 `prepareFresh`와 같은 자연 관측→owner→snapshot 순서를 실행했다. 원격 백업·복원과 arm 요청을 다시 보내지 않았다.
- 다시 확인: `linux-qa.cjs.sources()`의 이름·SHA 323개가 고정 QA 결과와 전부 일치하고, 새 재가동 계약·설치 기록·사후 점검이 각각 통과하는지 본다. 이 사례 증거는 `.tmp/automation-performance-workroom-v2-20261017/README.md`.

### HA 설치 직후 사후 점검이 컨트롤러 관측 시간 부족으로 멈춘다
- 증상: `arm-status`는 `installed-armed`/서비스 성공인데 첫 `arm-postcheck`가 `ONE_LIVE_CONTROLLER_CYCLE_REQUIRED`로 나왔다.
- 원인: 첫 읽기 전용 스냅샷에서 같은 컨트롤러 실행을 7.2초만 관측했고 사후 점검의 최소 10초 조건에 못 미쳤다.
- 고침: 첫 결과를 보존하고 10초가 지난 뒤 새 출력 파일로 읽기 전용 사후 점검을 다시 했다. 설정·서비스·클라우드 상태는 바꾸지 않았다.
- 다시 확인: 새 결과에서 같은 invocation/PID의 정상 이벤트, 10초 이상 관측, `armed=true`, A epoch7·B 대기·복제·공개 TLS를 함께 확인한다. 10-17 결과는 23.9초 관측에 `passed`였다.

## Platform Mac DMG

판: electron-builder 26(10-17 `desktop/package.json` 26.15.3, dmgbuild) · macOS 15.7 GitHub 러너(Apple 칩 `macos-15`, Intel `macos-15-intel`) · 작업 폴더 `desktop/mac-dmg/`, 미리보기 synk-policy `.github/desktop-preview/mac-dmg-signal/`. 10-13 Platform 0.4.3 DMG 창 재포장(mac-signal.1)에서 잰 것이다.

### DMG 창에서 배경 아래쪽 28pt가 가려진다
- 증상: 배경 그림 아래쪽이 Finder 창에서 잘려 보인다. `dmg.window`로 창 크기를 정해도 듣지 않는다.
- 원인: electron-builder 26(dmgbuild)은 `dmg.background`가 있으면 `dmg.window`를 버리고 배경 그림 크기를 창 크기로 쓴다. Finder는 그 높이 안에 제목 막대 28pt를 넣는다.
- 고침: 내용은 위쪽에만 두고, 배경 그림을 28pt 더 길게 만든다(660×420 내용 → 660×448 그림).
- 다시 확인: 러너에서 DMG를 열어 Finder 창을 찍고(아래 「Finder 실제 창」 항목) 배경 아래 끝이 보이는지 본다.

### 어두운 배경에서 아이콘 이름이 안 보인다
- 증상: 어두운 배경 그림 위의 아이콘 이름이 거의 보이지 않는다.
- 원인: 배경 그림이 있는 창에서는 Finder가 아이콘 이름을 밝은 모드·어두운 모드 모두 검정으로 그린다.
- 고침: 어두운 바탕이면 이름 밑에 밝은 판(흰 알약)을 깐다. 112pt 아이콘·13pt 이름이면 이름 글자 중심은 아이콘 중심 +74pt다.
- 다시 확인: 러너에서 `System Events … dark mode`로 어두운 모드를 켜고 다시 찍는다.

### DMG 창이 화면 위쪽에 붙어 열린다
- 증상: 창이 화면 가운데가 아니라 위쪽에 붙어 열린다.
- 원인: 창 위치 y를 화면 아래에서 잰다. electron-builder 기본값은 (400, (1440−h)/2)라 보통 화면 위쪽으로 간다.
- 고침: 창 위치를 정할 때 y는 화면 아래에서 잰 값이라는 것을 넣고 계산한다. 10-13에 실제로 넣은 값은 기록에 없다.
- 다시 확인: 러너 캡처에서 `osascript … bounds of front window` 값을 본다.

### DMG 안에서 배경 파일을 `.background/` 폴더로 찾으면 없다
- 증상: 만든 DMG를 열어 `.background/` 폴더를 찾으면 없다.
- 원인: dmgbuild는 배경을 볼륨 루트의 `.background.tiff`로 넣는다. `background.png` 옆에 `background@2x.png`가 있으면 tiffutil로 Retina TIFF를 만든다.
- 고침: 검사 스크립트는 볼륨 루트의 `.background.tiff`를 본다.
- 다시 확인: `hdiutil attach` 뒤 `ls -a /Volumes/<이름>`.

### 공개 DMG를 다시 포장하면 앱까지 바뀌는지 모른다
- 증상: 창만 고쳐 다시 포장하려는데, 앱을 다시 만들거나 서명하면 공개본과 달라진다.
- 원인: 보통 빌드는 앱을 새로 만든다. `build({prepackaged:<.app>})`는 앱을 다시 만들거나 서명하지 않고 DMG만 만든다.
- 고침: 공개 DMG에서 `ditto`로 꺼낸 앱을 `prepackaged`로 바이트 그대로 다시 포장한다. 파일·권한·링크 트리를 비교하고 `codesign --verify --deep --strict`를 돌린다.
- 다시 확인: 다시 포장한 DMG의 앱 트리와 공개본 앱 트리의 비교가 0건 차이인지 본다.

### Finder 실제 창을 확인할 Mac이 없다
- 증상: DMG 창 모양을 이 PC에서 볼 수 없다.
- 원인: Windows PC다.
- 고침: macOS 러너에서 실제 Finder 창을 찍는다. `hdiutil attach`(‑nobrowse 없이) → `open /Volumes/…` → `osascript … bounds of front window` → `screencapture -x`. `System Events … dark mode`로 모드 전환도 된다. 호출마다 timeout 20s를 건다.
- 다시 확인: 워크플로(`desktop/mac-dmg/desktop-macos-dmg-signal.yml`)의 캡처 아티팩트에 창 그림이 있는지 본다.

### 1GB 가까운 릴리스를 집 Wi‑Fi로 올린다
- 증상: 큰 릴리스 파일을 이 PC에서 올리면 몇 시간 걸리고 다른 작업의 회선을 먹는다([백업·큰 업로드](백업_업로드.md)).
- 원인: 집 회선의 올림 속도가 낮고 크게 흔들린다.
- 고침: CI 릴리스 작업으로 만든다. 검사한 빌드 실행의 아티팩트를 `actions/download-artifact@v8`(run-id + github-token)로 받아 기록과 대조한 뒤 `gh release create`(GITHUB_TOKEN, `contents: write`)로 올린다. 아티팩트 업로드가 러너 망 오류(ENOTFOUND)로 한 번 실패한 적이 있는데, 다시 돌리면 된다.
- 다시 확인: 릴리스 작업 기록에 아티팩트 대조 단계가 통과로 남았는지 본다.

### 새 워크플로에 「Run workflow」 단추가 없다
- 증상: 새로 만든 workflow_dispatch 워크플로를 수동으로 돌릴 수 없다.
- 원인: workflow_dispatch는 기본 브랜치에 있는 워크플로만 돌릴 수 있다.
- 고침: 시험 반복은 push 트리거를 단 임시 브랜치에서 한다. 끝나면 main에 올리고, main에서 최종 빌드를 돌린 뒤 그 실행 번호로 릴리스한다.
- 다시 확인: 기본 브랜치의 `.github/workflows/`에 그 파일이 있는지 본다.
