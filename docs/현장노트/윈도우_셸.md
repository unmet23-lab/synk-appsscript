## PowerShell

### CloseMainWindow 성공은 Chrome 전체 종료를 보장하지 않는다 (2026-10-18)
- 증상: 정상 닫기 메시지는 true였지만 8초 뒤에도 Chrome 창·프로세스가 남았다. 실행 중 Preferences의 Crashed 값만으로 실제 충돌이라고 판단할 수도 없었다.
- 원인: 정상 메시지 발송과 전체 프로세스 종료는 별도다. 첫 요청에서 남은 창이 다른 창인지 닫기 취소인지는 확정하지 않았다.
- 고침: 발송 전에 중단하고 강제 종료하지 않았다. 새 시도에서 같은 PID·시작 시각·경로를 확인한 뒤 자기 Chrome의 보이는 최상위 창만 열거했다. 예상 클래스·활성·소유 창 없음 조건을 확인하고 WM_CLOSE 정상 메시지를 보냈다. 다른 창이나 모달이면 중단한다.
- 다시 확인: closed-chrome-check-attempt2는 Normal·프로세스0·세션6파일 DPAPI/SHA 보존을 확인했고, Chrome 종료 중 실제 Windows 플레저 수신 뒤 마지막 세션으로 다시 실행했다. [기록](../SYNK_플랫폼_계정과_연결_설계.md#care-native-closed-20261018).


### 앞 네이티브 명령이 실패해도 세미콜론 뒤 명령은 실행된다 (2026-10-18)
- 증상: 프로필 보존 사전 해시 수집이 외부 도구의 링크를 거절했지만, 뒤의 승인된 설치 명령은 계속 실행됐다.
- 원인: PowerShell의 `;`는 앞 프로세스 종료 코드에 따라 다음 명령을 막지 않는다. 링크 검사는 정상적으로 실패했고 설치 자체는 기존 엔진의 검증을 통과했다.
- 고침: 종속 명령은 도구 결과의 `exit_code`를 확인해 다음 호출을 하거나, `$LASTEXITCODE`를 검사해 throw한다. 계정판 보존 해시는 실제 재실행 직전에 필요한 보관 파일에만 걸고 자격증명·외부 프로그램 홈 링크는 순회하지 않는다.
- 다시 확인: 설치 전 전체 프로필 해시 증거가 생겼다고 보고하지 않았다. 현재 PC의 실제 재실행에서 로그인 보존·계정판 보관 파일 SHA 일치·강제 종료 없음을 별도로 확인했다(`native-handoff.json`).

### PowerShell에서 역슬래시로 큰따옴표를 감싼 인라인 Python이 나뉜다
- 증상: Python `-c`에 JS 조각까지 담은 명령이 나뉘어 `const`를 PowerShell 명령으로 실행하려 했다(10-18).
- 원인: PowerShell에서 `\"`는 큰따옴표 이스케이프가 아니며, 서로 다른 언어의 인용 규칙을 한 명령에 섞었다.
- 고침: 따옴표·JS 조각이 든 코드는 파일 쓰기 도구로 `.py`에 저장하고 `python -X utf8 <파일>`만 실행한다.
- 다시 확인: 같은 변경을 `.tmp/remove-member-benefits-20261018/wrap_up.py`로 실행해 파일·문법과 빌드 일치를 확인했다.

### 큰따옴표 안에서 변수 바로 뒤의 한글이 빈 값이 된다
- 증상: `"링크 $made개"`가 「링크 」로 찍힌다. 오류는 없다.
- 원인: PowerShell은 변수 이름에 한글을 허용해서 `$made개`라는 없는 변수로 읽는다.
- 고침: `"링크 $($made)개"`처럼 감싼다. 다 쓴 스크립트는 정규식 `\$[A-Za-z_][A-Za-z0-9_]*[가-힣]`로 한 번 훑는다.
- 다시 확인: `$made=3; "링크 $made개"`가 「링크 」이면 그대로다(10-17 재현).
- 기록: 10-15 노트북 옮기기 스크립트 두 곳.

### 대소문자만 다른 변수가 앞 변수를 덮는다
- 증상: 앞에서 사용자 폴더를 담은 `$H`가 뒤에서 엉뚱한 값이 된다.
- 원인: 변수 이름은 대소문자를 가리지 않는다. `$h`와 `$H`는 같은 변수다.
- 고침: 이미 쓰는 이름과 대소문자만 다른 변수를 만들지 않는다.
- 다시 확인: `$H='a'; $h='b'; $H`가 `b`다(10-17 재현).

## Git Bash와 명령 문자열

### 앱을 다시 켠 뒤 Claude Bash 도구가 작은따옴표·별표·한글이 든 명령을 전부 거부한다
- 증상: 10-18 17:15 데스크톱 앱을 다시 켠 뒤 같은 세션의 Bash 도구에서 `echo hi`는 되는데 `echo 'a'`·`echo /c/Users/q1212/Doc*`는 ``line 76: unexpected EOF while looking for matching `''``, `echo "한글"`은 `line 76: /de: No such file or directory`로 아무것도 실행되지 않았다. 다시 켜기 전에는 한글 경로·작은따옴표가 든 명령이 돌았다.
- 원인: 모른다. 셸 스냅숏(`~/.claude/shell-snapshots/` 최신 파일, 44줄)은 멀쩡해서, 명령 문자열을 감싸 넘기는 단계(76행 = 감싼 명령 자리)가 글자를 망가뜨리는 것으로 보인다.
- 고침: 같은 일을 PowerShell 도구로 옮겼다(한글 경로·따옴표·`-vf "select=eq(n\,1010)"` 모두 정상). 긴 명령은 파일 쓰기 도구로 `.ps1`·`.py`·`.cjs`를 만들고 PowerShell에서 실행만 한다. Monitor는 bash로 돌아 같이 막히니 기다리기는 `run_in_background` 완료 알림으로 한다.
- 다시 확인: Bash 도구로 `echo 'a'`와 `echo "한글"`을 돌려 본다. 둘 다 그대로 찍히면 Bash로 돌아가도 된다.

### heredoc으로 쓴 스크립트의 역슬래시가 줄어든다
- 증상: `cat > x.py <<'EOF'` 안의 `'\\r\\n'`이 `'\r\n'`이 되어 파이썬 문자열에 실제 줄바꿈이 들어간다. JS `/\\/g`는 `/\/g`가 되어 문법 오류, `\b`는 백스페이스 문자가 된다. 10-06에는 정규식 `'\?v='`가 역슬래시를 잃어 공개본 import 주소가 전부 `??v=`로 겹친 채 나갔다(`node --check`는 통과).
- 원인: 명령 문자열이 셸에 닿기 전에 한 번 더 해석된다. 따옴표 친 heredoc인데도 역슬래시 두 개가 하나로 준다. 홑 `\n`은 남아서 대부분의 스크립트가 그대로 돌아 알아채기 어렵다. 백틱이나 영어 작은따옴표(Men's)가 든 긴 heredoc은 `unexpected EOF while looking for matching '`로 아무것도 실행되지 않기도 한다.
- 고침: 역슬래시·백틱·영어 작은따옴표가 하나라도 든 스크립트는 파일 쓰기 도구로 파일을 만들고, 셸에서는 실행만 한다. 파이썬에서 CR·LF가 필요하면 `chr(13)`·`chr(10)`처럼 역슬래시 없이 쓴다.
- 다시 확인: 따옴표 heredoc으로 `x\\y`를 써서 `od -c`로 본다. 역슬래시가 하나만 남으면 그대로다(10-17 Claude Code Bash 도구에서 재현). 진짜 bash는 따옴표 heredoc을 글자 그대로 두므로, 다른 실행기에서는 이 확인부터 돌려 본다.
- 기록: 10-01 PULSE, 10-06 홈페이지 공개 도구, 10-17 빌드 스크립트.

### 큰따옴표 안의 백틱이 명령으로 실행된다
- 증상: `node -e "…"`로 쓴 JS 파일에서 템플릿 문자열·정규식이 비고, 「command not found」나 엉뚱한 도구 안내문이 찍힌다. 10-02에는 주석 속 `` `tools/원격배포.js` ``가 실제로 실행됐다(인자가 없어 배포는 안 났다).
- 원인: Bash 큰따옴표 안의 백틱과 `$(…)`는 명령 치환이다. `${…}`·역슬래시도 같이 망가진다.
- 고침: 백틱·`${`·역슬래시가 든 JS는 파일로 쓰고 `node 파일`로 돌린다. 셸에서 써야 하면 `<<'EOF'`로 연다. 실행 뒤 예상 밖 출력이 보이면 무엇이 실행됐는지부터 본다.
- 다시 확인: ``echo "a `echo X` b"``가 `a X b`다.

### 소스에 넣은 U+2028·U+2029 글자가 줄을 나눈다
- 증상: 정규식이 `SyntaxError: Invalid regular expression: missing /`로 깨진다. 편집기로 보면 멀쩡한 세 줄이라 원인이 안 보인다. 10-19에는 줄바꿈 없는 빈칸(U+00A0) 이스케이프가 Edit 도구로 실제 글자로 들어갔다(계정판 화면 코드 4곳·시험 정규식 2곳). 동작은 같지만 기존 코드는 이스케이프로 적는 약속이라 되돌렸다.
- 원인: 유니코드 줄 구분 문자가 글자 그대로 들어가 그 자리에서 줄이 나뉜다. 도구 입력이 JSON 문자열이면 역슬래시-u 이스케이프로 적어도 도구에 닿기 전에 실제 문자로 풀린다(10-03 Claude Write·Bash 도구).
- 고침: 이 두 글자는 소스에 적지 않고 문자 코드로 만든다: `new RegExp('[' + String.fromCharCode(0x2028, 0x2029) + ']', 'g')`. 이미 들어갔으면 셸 한 줄로 고치지 말고, 나뉜 줄을 다시 잇는 스크립트를 파일로 써서 고친다.
- 다시 확인: `node -e "const s=require('fs').readFileSync(process.argv[1],'utf8');console.log([...s].filter(c=>c.charCodeAt(0)===0x2028||c.charCodeAt(0)===0x2029).length)" <파일>`이 0이어야 한다.
- 10-19 오후 재발: 초기화권 화면 코드 1곳·시험 정규식 2곳에서 또 실제 글자로 풀렸다. 그리고 파일에 이미 역슬래시-u로 적힌 줄을 old_string에 넣은 Edit는 「맞는 글이 없음」으로 거절됐다(도구가 이스케이프·실제 글자 두 모양을 다 견줘 봐도). 이스케이프가 든 줄은 빼고 그 앞뒤 조각만 old_string으로 잡아 고쳤고, 편집이 끝날 때마다 문자 코드 0xA0을 역슬래시-u 이스케이프로 되돌리는 스크립트로 파일마다 0곳을 확인했다.

### `/`로 시작하는 인자가 윈도우 경로로 바뀐다
- 증상: `hf jobs run -v ./upload:/work`의 `/work`가 `C:\Program Files\Git\work`로 깨진다. `git show origin/main:.github/…` 같은 인자도 깨진다.
- 원인: Git Bash(MSYS)가 `/`로 시작하는 인자를 윈도우 경로로 바꿔 넘긴다. `;`로 이은 경로 목록은 거꾸로 바뀌지 않는다.
- 고침: 그 명령 앞에 `MSYS_NO_PATHCONV=1`을 붙이거나 PowerShell에서 돌린다. `;`로 잇는 경로 목록은 `cygpath -m`으로 바꿔 넘긴다.
- 다시 확인: `node -e "console.log(process.argv[1])" /work`가 `C:/Program Files/Git/work`, 앞에 `MSYS_NO_PATHCONV=1`을 붙이면 `/work`다(10-17 재현).
- 덧붙임(10-19): 반대로 `MSYS_NO_PATHCONV=1`을 붙이면 같은 줄의 `"$(pwd)/폴더"`도 `/c/Users/…` 그대로 넘어가 Node가 파일을 못 찾는다. 홈페이지 후보를 실제 주소에 끼우는 Playwright 점검이 `fs.existsSync`에서 조용히 false가 되어 공개본만 열었고, 「질문창 답이 안 바뀌었다」로 보였다. URL 같은 `/` 인자와 로컬 경로를 같이 넘길 때는 경로를 `W=$(cygpath -m "$(pwd)")`로 바꿔 넘기고, 점검 결과에 「후보에서 준 파일 수」를 찍어 0이면 멈춘다.

### Git Bash의 시각과 시간대를 믿지 않는다
- 증상: 10-07 옛 노트북에서는 `date`가 시간대 표시 없이 UTC를 찍어(19:08 KST에 09:08) 게시 예약을 놓칠 뻔했다. 10-17 새 노트북에서는 그냥 `date`는 한국 시각(+0900, 시간대 이름 빈칸)인데 `TZ=Asia/Seoul date`가 거꾸로 UTC(`03:19 GMT`)를 찍는다.
- 원인: 이 Git Bash에는 시간대 자료가 없어 모르는 `TZ` 이름을 GMT로 본다. PC마다 기본 표시도 달랐다.
- 고침: 시각에 맞춰 할 일(예약 게시·크론·마감)은 PowerShell `Get-Date -Format 'yyyy-MM-dd HH:mm:ss zzz'`로 지금 시각을 본다. Git Bash에서 `TZ`를 바꾸지 않는다.
- 다시 확인: `date +"%H:%M %z"`, `TZ=Asia/Seoul date +"%H:%M %Z"`, PowerShell `Get-Date`를 나란히 찍는다.

### Git Bash에 jq가 없다
- 증상: `gh … | jq …`로 짠 대기 루프가 `jq: command not found`만 찍으며 끝나지 않는다(조건이 늘 거짓). 감시 도구도 사건을 못 낸다.
- 원인: 이 PC에 jq가 깔려 있지 않다.
- 고침: GitHub 조회는 `gh … --json <칸> --jq '<식>'`으로 거른다. 대기 루프는 성공·실패·cancelled까지 끝 상태를 모두 잡게 짠다.
- 다시 확인: `command -v jq`가 비어 있으면 그대로다(10-17 없음).

### 코드를 고치는 Node 스크립트에서 `$$(`가 `$(`로 바뀐다
- 증상: 10-19 PATH 화면 코드(`planner-ui.mjs`)를 node 스크립트의 `s.replace(옛, 새)`로 고쳤더니 새 글 속 `$$('[data-preset-photo]')`가 `$('[data-preset-photo]')`로 들어가 「$ is not a function or its return value is not iterable」이 났다. 옛 글과 새 글에 똑같이 들어 있던 `$$('[data-view]')`도 `$(`로 바뀌었다.
- 원인: `String.prototype.replace`의 바꿀 글(두 번째 인자)에서 `$$`는 `$` 하나, `$&`·`` $` ``·`$'`는 맞은 글·앞·뒤를 뜻한다. jQuery식 `$`·`$$` 도우미를 쓰는 코드를 바꿀 때 그대로 걸린다.
- 고침: 코드 조각을 바꿀 때는 `s.split(옛).join(새)`를 쓰거나 `s.replace(옛, () => 새)`처럼 함수로 넘긴다. 바꾼 뒤 `$$(` 개수를 원래 파일과 대조했다(원래 15 → 새로 넣은 2개를 더해 17).
- 다시 확인: `node -e "console.log('a'.replace('a','$$(x)'))"`가 `$(x)`를 낸다.

## 파이썬·Node의 한글과 인증서

### 파이썬이 파이프로 찍은 한글 경로가 깨져 보인다
- 증상: 오류 메시지·`os.listdir` 출력에 `docs/ȫ����/…`가 찍혀 「깨진 이름 폴더로 옮겨졌다」고 오해한다(10-10, 실제로는 다른 정리 작업이 지운 파일이었다).
- 원인: 윈도우 파이썬은 표준 출력이 파이프면 로캘 인코딩(CP949)으로 쓰고, 받는 쪽은 UTF-8로 읽는다. 폴더 이름은 멀쩡하다(`ȫ`는 「홍」의 CP949 바이트).

### cv2가 한글 경로를 조용히 못 연다
- 증상: `cv2.imread('docs/디자인/…png')`가 None, `cv2.imwrite`가 False를 돌려준다. 경고 한 줄 말고는 오류가 없다.

### Node fetch가 synk.im 인증서를 거절했다

### 디스크를 어디에 썼는지 잴 때 git 팩이 새로 쓴 것처럼 잡힌다
- 증상: 「최근에 쓴 파일」로 재면 `.git/objects/pack` 18GB가 오늘 쓴 것처럼 나온다. 세 번 재귀하는 PowerShell 집계가 40분 넘게 안 끝난다. 여유 공간이 30분 사이 4.7GB → 0.9GB → 2.3GB로 출렁인다(10-14).
- 원인: git은 이미 있는 객체를 만나면 팩 파일의 수정 시각만 고친다(새 데이터가 아니다). 디스크 대기열이 20을 넘으면 재귀 집계가 거의 멈춘다. 다른 세션의 설치 파일 빌드(`.tmp/platform-unified-*`)와 페이지 파일 증가가 여유 공간을 흔든다.
- 고침: 한 번의 재귀로 폴더별 합을 내고, `.git`은 `git count-objects -vH`의 느슨한 객체 크기로 따로 본다. 여유 공간은 두 번 이상 재고 출렁인 까닭(빌드 중인 `.tmp` 폴더, `C:\pagefile.sys` 크기)을 같이 적는다. 지우기는 [공간 정리 항목](git_줄끝_잠금.md#공간-정리가-추적-파일을-지운다)을 따른다.
- 다시 확인: `git count-objects -vH`의 `size`(느슨한 객체)와 팩 파일 수정 시각을 견준다.

### Codex 「전체 권한」 대화에서 재귀 삭제가 프로세스 시작 전에 거절된다
- 증상: 10-17 Codex exec_command에서 검증용 임시 사본 두 폴더의 `Remove-Item … -Recurse -Force`가 ``CreateProcess { message: "Rejected(\"`<명령 전체>` rejected: blocked by policy\")" }``, 걸린 시간 0.0초로 거절됐다(05:14, 05:35 두 번). 대화에서 다시 승인하고 절대경로를 직접 적어도 같았다. 같은 대화의 읽기·쓰기·git 명령은 그대로 돌았다.
- 원인: Windows가 아니라 Codex 실행기가 막았다. 그 대화의 turn_context가 `approval_policy: "never"`, `sandbox_policy: danger-full-access`(앱의 전체 권한)였다. Codex는 규칙 파일(`~/.codex/rules/*.rules`)에 맞는 규칙이 없는 명령을 내장 위험 명령 판정(`shell-command/src/command_safety/is_dangerous_command.rs`)에 거는데, 위험으로 분류되면 원래는 사용자에게 묻는다. 그런데 승인을 묻지 않는 모드라 물을 길이 없어 곧바로 거절한다. 거절 문구에 「policy forbids commands starting with …」가 없으면 사용자 규칙이 아니라 이 내장 판정에서 나온 것이다. 대화창에서 「지워도 된다」고 말해도 이 판정에는 닿지 않는다. 10-17 Claude Code 점검: `codex execpolicy check --rules ~/.codex/rules/default.rules -- <pwsh> -Command "Remove-Item …"`가 `matchedRules: []`, 두 폴더는 읽기 전용·재분석 지점·거부 ACE·다른 프로세스 점유가 모두 0, 소유자 q1212 FullControl. 위험 판정 낱말 목록은 실행 파일에서 읽어 내지 못했다(codex-cli 0.163.0-alpha.10.2).
- 고침: ① Codex에서 끝내려면 그 대화를 승인을 묻는 권한 모드로 바꾼 뒤 같은 삭제를 시키고, 뜨는 승인 창을 유호님이 누른다. ② `~/.codex/rules/default.rules`에 `prefix_rule(…, decision="allow")`를 넣으면 전체 권한에서도 통과하지만 계속 남는 허용이라 삭제에는 쓰지 않는다. ③ Claude Code에서 유호님 승인 뒤 휴지통으로 옮기고(되돌릴 수 있음, C: 휴지통 한도 약 50GB) 비우기는 유호님이 한다. 어느 길이든 실행 직전에 경로·파일 수·바이트와 남길 `remote-download/`를 다시 대조한다. 10-17에는 ③으로 끝냈다: PowerShell 7에서 `[Microsoft.VisualBasic.FileIO.FileSystem]::DeleteDirectory`/`DeleteFile`(…, `OnlyErrorDialogs`, `SendToRecycleBin`), 도구 `.tmp/github-storage-20261017/recycle-temporary-copies.ps1`(대조가 하나라도 어긋나면 아무것도 안 옮김, `-CheckOnly`로 대조만). 휴지통 목록(`Shell.Application` `Namespace(10)`)에서 파일 이름은 확장자 없이 보이니 원래 위치 칸(`GetDetailsOf(item, 1)`)으로 찾는다.
- 다시 확인: 거절 문구에 `rejected: blocked by policy`만 있고 걸린 시간이 0초면 이 항목이다. 그 대화의 기록(`~/.codex/sessions/<날짜>/rollout-*.jsonl`)에서 거절 바로 앞 `turn_context`의 `approval_policy`가 `never`인지 본다. 진단 근거 `.tmp/github-storage-20261017/temporary-copy-cleanup-attempt.json`, [인계문](../_ops/github-storage/임시사본정리_Claude인계_20261017.txt).

### Electron 앱의 fs.rmSync가 junction을 따라 들어가 폴더 밖 파일을 지운다
- 증상: 10-18 회원 혜택 계정판 검토. 폴더 안에 바깥 폴더를 가리키는 junction을 두고 `fs.rmSync(dir,{recursive:true,force:true})`하자, 앱이 쓰는 Electron 44.5.1(Node 24.21.0)에서는 바깥 폴더의 파일까지 지워졌다. 시스템 Node 24.20.0과 `fs.promises.rm`은 링크만 지웠다. `node --test`는 시스템 Node로 돌아 이 차이를 못 잡는다.
- 원인: 그 런타임의 `rmSync`(recursive)가 junction을 링크가 아니라 폴더로 다룬다. `lstatSync`·`readdirSync({withFileTypes:true})`는 두 런타임 모두 junction을 `isSymbolicLink()` true로 본다.
- 고침: 앱(본체)에서 사용자 쪽 폴더를 통째로 지울 때는 `rmSync`를 쓰지 않는다. `lstatSync`로 링크면 링크만 `unlinkSync`(안 되면 `rmdirSync`), 폴더면 아래부터 하나씩 지우는 함수를 쓴다(`desktop/src/ai-subscriptions.cjs`의 `removeTree`, 지울 폴더 자체가 링크인 경우 포함). 시험은 `rmSync`를 막아 둔 채(`t.mock.method(fs,'rmSync',…)`) 바깥 파일이 남는지 본다.
- 다시 확인: 바깥을 가리키는 junction을 둔 임시 폴더로 `ELECTRON_RUN_AS_NODE=1 desktop/node_modules/electron/dist/electron.exe <스크립트>`와 `node <스크립트>`에서 각각 `rmSync`해 바깥 파일이 남는지 견준다. 같은 시험을 `ELECTRON_RUN_AS_NODE=1 electron.exe --test …`로도 돌린다.

## 프로세스·검은 창

### Node의 detached로 띄운 PowerShell·CLI에 창이 생기지 않는다
- 증상: 10-18 계정판의 「설치 창 열기」가 「설치 창을 열었어요」를 띄우는데 아무 창도 없고 설치도 안 됐다. Gemini 「검은 창」 로그인도 창이 안 떠 10분을 기다리다 끝났다.
- 원인: Node(libuv)의 `detached:true`는 Windows에서 `DETACHED_PROCESS`로 띄워 자식에게 콘솔을 주지 않는다(`windowsHide:false`여도 같다). 콘솔 없는 부모(설치본 Electron 본체)에서 띄운 PowerShell 스크립트는 한 줄도 돌지 않고 종료 코드 0으로 끝났다. `detached` 없이 띄우면 부모에 콘솔이 있을 때 그 콘솔을 함께 써서 역시 새 창이 안 생긴다.
- 고침: 숨긴 PowerShell 런처가 `Start-Process -FilePath … [-ArgumentList …] [-WorkingDirectory …] -PassThru`로 새 창을 띄우고 PID를 찍는다. 스크립트는 `-EncodedCommand`(UTF-16LE base64)로 넘겨 따옴표·한글이 깨지지 않게 한다. 환경변수(계정 폴더 USERPROFILE 등)·작업 폴더는 그대로 물려받고, `.cmd` 심과 공백 든 경로도 된다. 창을 끌 일이 있으면 런처가 `$p.WaitForExit()`로 창이 닫힐 때까지 기다리게 하고, 런처가 살아 있을 때만 그 PID를 끈다(손잡이를 쥐고 있어 PID가 재사용되지 않는다).
- 다시 확인: 콘솔 없는 부모(`spawn(process.execPath,[…],{detached:true,stdio:'ignore'})`로 띄운 node)에서 세 방식으로 `GetConsoleWindow()` 값을 파일에 적는 PowerShell을 띄운다. detached는 파일이 안 생기고, `Start-Process`(-WindowStyle Hidden으로 시험)는 0이 아닌 창 손잡이를 적는다.

### npm 설치본(.cmd) CLI를 끄면 cmd만 꺼지고 실제 CLI가 남는다
- 증상: 10-18 계정판 검토. cmd.exe로 감싸 띄운 `codex.cmd login`류에 `child.kill()`을 하자 cmd.exe는 꺼지고 손자(실제 CLI, node)는 살아 있었다. 로그인 취소 뒤 로그인 대기 포트를 계속 잡고 있어 다음 로그인이 「포트 사용 중」으로 막힐 수 있다.
- 원인: Windows에서 프로세스를 끄면 그 자식은 같이 꺼지지 않는다.
- 고침: `taskkill /PID <pid> /T /F`로 묶음째 끄고, 그것이 끝난 뒤에 `child.kill()`을 부른다(cmd를 먼저 끄면 부모 연결이 끊겨 `/T`가 손자를 못 찾는다). 이미 끝난 자식(`exitCode`가 null이 아님)의 PID로는 끄지 않는다(다른 프로그램이 그 PID를 다시 쓸 수 있다).
- 다시 확인: 손자 PID를 적고 기다리는 가짜 CLI를 `.cmd`로 감싸 띄운 뒤 `child.kill()`만 하면 손자가 살아 있고, `taskkill /T /F` 뒤에는 둘 다 없다.

## ssh

### 같은 ssh 명령이 Git Bash에서는 되고 PowerShell에서만 실패한다
- 증상: 유호님 PowerShell 터미널에서 `WARNING: UNPROTECTED PRIVATE KEY FILE!` … `This private key will be ignored.` 뒤에 `Permission denied (publickey)`가 난다. 유호님께는 「눌렀는데 아무 일도 안 났다」로 보인다. 같은 명령이 Claude Bash 도구(Git Bash)에서는 된다(09-07).
- 원인: 두 셸이 서로 다른 ssh를 쓴다. PowerShell은 윈도우 OpenSSH(`C:\Windows\System32\OpenSSH\ssh.exe`)를 쓰는데, 이 프로그램은 소유자 말고 다른 계정도 키 파일을 읽을 수 있으면 그 키를 쓰지 않는다. Git Bash의 ssh(`/usr/bin/ssh`)는 키 권한을 따지지 않는다. 연결이 서버까지 가지도 못한 것이라, 서버 문제부터 찾으면 시간을 버린다.
- 고침: `icacls "$env:USERPROFILE\.ssh\<열쇠>" /inheritance:r /grant:r "${env:USERNAME}:(R)"`로 본인 읽기 하나만 남긴다(본인 파일이라 관리자 권한이 필요 없다). 고친 뒤에도 Git Bash의 ssh는 그대로 된다. ssh가 들어간 명령을 유호님께 드리기 전에 그 키의 권한을 한 번 본다.
- 다시 확인: `icacls "$env:USERPROFILE\.ssh\<열쇠>"`에 본인 `(R)` 하나만 있는지 본다. 10-17 새 노트북의 키 셋은 모두 본인 `(R)` 하나다. 같은 날 Users 읽기를 더한 시험 키로 재 보니 윈도우 `ssh-keygen -y`(OpenSSH_for_Windows 9.5)는 「Bad permissions … UNPROTECTED PRIVATE KEY FILE」로 거부했고, Git Bash `ssh-keygen -y`(OpenSSH 10.5)는 권한을 따지지 않고 암호 묻기로 넘어갔다.

### 새 PC에서 node가 부르는 .ps1이 「이 시스템에서 스크립트를 실행할 수 없으므로」로 막힌다
- 증상: 10-17 새 노트북에서 `tools/sns-발행.js`·`.tmp/.../yt_channel_schedule.cjs`가 `Windows 자격 보관소 get 실패: … sns-자격.ps1 파일을 로드할 수 없습니다 … about_Execution_Policies`로 멈췄다(cp949라 처음엔 글자가 깨져 보임). 자격 보관소 항목은 그대로 있었다.
- 원인: 새 PC의 PowerShell 실행 정책이 기본값(모든 범위 Undefined → Restricted)이라 `powershell.exe -File <스크립트>`가 거부된다. 옛 PC는 정책을 바꿔 두었던 것으로 보인다.

- 다시 확인: `node tools/sns-발행.js --연결점검`에서 `lab-youtube connected`가 나온다(10-18 「SYNK LAB Mongolia」). `powershell -NoProfile -Command "Get-ExecutionPolicy -List"`로 정책이 그대로인지 본다.
