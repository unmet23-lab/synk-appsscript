## PowerShell

### 앞 네이티브 명령이 실패해도 세미콜론 뒤 명령은 실행된다 (2026-10-18)
- 증상: 프로필 보존 사전 해시 수집이 외부 도구의 링크를 거절했지만, 뒤의 승인된 설치 명령은 계속 실행됐다.
- 원인: PowerShell의 `;`는 앞 프로세스 종료 코드에 따라 다음 명령을 막지 않는다. 링크 검사는 정상적으로 실패했고 설치 자체는 기존 엔진의 검증을 통과했다.
- 고침: 종속 명령은 도구 결과의 `exit_code`를 확인해 다음 호출을 하거나, `$LASTEXITCODE`를 검사해 throw한다. 계정판 보존 해시는 실제 재실행 직전에 필요한 보관 파일에만 걸고 자격증명·외부 프로그램 홈 링크는 순회하지 않는다.
- 다시 확인: 설치 전 전체 프로필 해시 증거가 생겼다고 보고하지 않았다. 현재 PC의 실제 재실행에서 로그인 보존·계정판 보관 파일 SHA 일치·강제 종료 없음을 별도로 확인했다(`native-handoff.json`).

### PowerShell에서 역슬래시로 큰따옴표를 감싼 인라인 Python이 나뉜다
- 증상: Python `-c`에 JS 조각까지 담은 명령이 나뉘어 `const`를 PowerShell 명령으로 실행하려 했다(10-18).
- 원인: PowerShell에서 `\"`는 큰따옴표 이스케이프가 아니며, 서로 다른 언어의 인용 규칙을 한 명령에 섞었다.
- 고침: 따옴표·JS 조각이 든 코드는 파일 쓰기 도구로 `.py`에 저장하고 `python -X utf8 <파일>`만 실행한다.
- 다시 확인: 같은 변경을 `.tmp/remove-member-benefits-20261018/wrap_up.py`로 실행해 파일·문법과 빌드 일치를 확인했다.

### 큰따옴표 안에서 변수 바로 뒤의 한글이 빈 값이 된다
- 증상: `"링크 $made개"`가 「링크 」로 찍힌다. 오류는 없다.
- 원인: PowerShell은 변수 이름에 한글을 허용해서 `$made개`라는 없는 변수로 읽는다.
- 고침: `"링크 $($made)개"`처럼 감싼다. 다 쓴 스크립트는 정규식 `\$[A-Za-z_][A-Za-z0-9_]*[가-힣]`로 한 번 훑는다.
- 다시 확인: `$made=3; "링크 $made개"`가 「링크 」이면 그대로다(10-17 재현).
- 기록: 10-15 노트북 옮기기 스크립트 두 곳.

### 대소문자만 다른 변수가 앞 변수를 덮는다
- 증상: 앞에서 사용자 폴더를 담은 `$H`가 뒤에서 엉뚱한 값이 된다.
- 원인: 변수 이름은 대소문자를 가리지 않는다. `$h`와 `$H`는 같은 변수다.
- 고침: 이미 쓰는 이름과 대소문자만 다른 변수를 만들지 않는다.
- 다시 확인: `$H='a'; $h='b'; $H`가 `b`다(10-17 재현).

### Windows PowerShell 5.1이 BOM 없는 .ps1에서 한글 옆 따옴표·줄바꿈을 먹는다
- 증상: 10-17 세션 공유 설치기를 `powershell -File install.ps1`(5.1)로 돌리면 「The Try statement is missing its Catch or Finally block」이 났다. 문법 오류가 안 날 때도 한글 주석 다음 줄의 코드가 주석에 먹혀 조용히 빠졌다. PowerShell 7과 `irm … | iex`는 멀쩡했다.
- 원인: 5.1은 BOM 없는 파일을 ANSI(CP949)로 읽는다. UTF-8 한글의 끝 바이트가 CP949 앞 바이트로 남으면 바로 뒤의 따옴표·공백·줄바꿈까지 한 글자로 묶어 삼킨다. 반대로 UTF-8 BOM을 붙이면 `irm … | iex`가 첫 줄을 「'function' … 인식되지 않습니다」(앞에 보이지 않는 BOM 글자가 붙어 있다)로 거절한다(5.1·7 둘 다).
- 고침: 로컬에서만 도는 .ps1은 UTF-8 BOM으로 쓴다. `irm | iex`로도 돌릴 .ps1은 BOM 없이 두고, 바깥 코드는 ASCII만 쓰며 한글 본문은 here-string에 넣는다. 파일로 실행될 때는 `[IO.File]::ReadAllText($PSCommandPath, [Text.Encoding]::UTF8)`로 본문을 다시 읽어 `[scriptblock]::Create`로 돌린다(github.com/unmet23-lab/claude-session-share의 install.ps1).
- 다시 확인: 5.1에서 `[Text.Encoding]::GetEncoding(949).GetString([byte[]](0xB0,0x0A,0x5A)).Length`가 2다(줄바꿈이 사라짐, 10-17 재현).

### ConvertFrom-Json이 ISO 시각을 DateTime으로 바꿔 같은 프로세스 확인이 실패한다 (2026-10-18)
- 증상: Chrome 종료 전 PID·시작 시각 확인에서 `CHROME_PROCESS_IDENTITY_CHANGED`로 중단됐다. 경로는 같았고 실제 프로세스도 그대로였다.
- 원인: PowerShell 7.6의 `ConvertFrom-Json`이 저장한 ISO 시각을 `System.DateTime`으로 복원했다. 이를 ISO 문자열과 직접 비교해 형식 차이를 다른 프로세스로 판단했다. Chrome 종료·발송 전에 중단했으므로 실제 종료/시험 알림은 발생하지 않았다.
- 고침: 양쪽 시각을 `DateTime`의 UTC `Ticks`로 맞춰 비교했다. 실패한 시도의 임시 함수 제거·종료/발송 intent 부재를 먼저 확인하고 증거를 보존한 뒤 재개했다.
- 다시 확인: `.tmp/care-push-closed-20261018/browser.ps1`의 시작 시각 비교와 `attempt1-before-close/cleanup.json`을 본다. 수정 뒤 `closed.json`에서 정상 종료·프로세스0, `result.json`에서 종료 후 실제 1회 시험을 확인했다.

### Start-Process의 stdin 파일을 실행 중에 해시하면 파일 사용 중 오류가 난다
- 증상: 10-18 코드 검수 비교에서 `Start-Process -RedirectStandardInput input.txt`로 첫 CLI를 시작한 뒤 두 번째 실행의 `Get-FileHash input.txt`가 「다른 프로세스에서 사용 중」으로 실패했다. 파일 내용이 바뀐 것은 아니었다.
- 원인: 해당 리디렉션 실행이 살아 있는 동안 입력 파일에 대한 동시 열기가 제한됐다. 내부 핸들의 공유 플래그까지는 확인하지 않았다.

## Git Bash와 명령 문자열

### heredoc으로 쓴 스크립트의 역슬래시가 줄어든다
- 증상: `cat > x.py <<'EOF'` 안의 `'\\r\\n'`이 `'\r\n'`이 되어 파이썬 문자열에 실제 줄바꿈이 들어간다. JS `/\\/g`는 `/\/g`가 되어 문법 오류, `\b`는 백스페이스 문자가 된다. 10-06에는 정규식 `'\?v='`가 역슬래시를 잃어 공개본 import 주소가 전부 `??v=`로 겹친 채 나갔다(`node --check`는 통과). Bash `printf` 서식 문자열도 같다 — `\U`를 유니코드 이스케이프로 읽어 커밋 메시지의 사용자 폴더 경로가 `C:\Usersxample`로 깨졌다(10-17, push 전 `git log -1 --format=%B`로 잡음).
- 원인: 명령 문자열이 셸에 닿기 전에 한 번 더 해석된다. 따옴표 친 heredoc인데도 역슬래시 두 개가 하나로 준다. 홑 `\n`은 남아서 대부분의 스크립트가 그대로 돌아 알아채기 어렵다. 백틱이나 영어 작은따옴표(Men's)가 든 긴 heredoc은 `unexpected EOF while looking for matching '`로 아무것도 실행되지 않기도 한다.
- 고침: 역슬래시·백틱·영어 작은따옴표가 하나라도 든 스크립트는 파일 쓰기 도구로 파일을 만들고, 셸에서는 실행만 한다. 파이썬에서 CR·LF가 필요하면 `chr(13)`·`chr(10)`처럼 역슬래시 없이 쓴다.
- 다시 확인: 따옴표 heredoc으로 `x\\y`를 써서 `od -c`로 본다. 역슬래시가 하나만 남으면 그대로다(10-17 Claude Code Bash 도구에서 재현). 진짜 bash는 따옴표 heredoc을 글자 그대로 두므로, 다른 실행기에서는 이 확인부터 돌려 본다.
- 기록: 10-01 PULSE, 10-06 홈페이지 공개 도구, 10-17 빌드 스크립트. 10-19 내 성향 시험: `cat >> 시험.cjs <<'EOF'` 둘을 한 명령에 넣었더니 영어 작은따옴표(`report\'s`)가 든 두 번째가 중간에서 끝나 시험 파일에 반쪽만 붙고 뒤의 실행 줄은 돌지 않았다(`git checkout -- 파일`로 되돌리고 Edit로 붙임). 이어 붙일 때도 파일 쓰기 도구를 쓴다. 10-19 회사 릴리스 도구: heredoc 안 파이썬의 `/\\b1049\\b/` 고정 문자열이 `\b`(백스페이스)가 되어 「ANCHOR … found 0 times」로 멈췄다(쓰기 전 멈춤). 같은 수정은 Write로 만든 `.py` 파일과 `r"…"` 문자열로 했다. 10-20 되돌림 시험 스크립트: heredoc으로 쓴 JS의 찾을 글 `\\0`이 `\0`, 곧 NUL 글자가 되어 그 한 가지만 「0번 찾음」으로 건너뛰었다(다른 스물은 그대로 돌아 피해 없음). Write로 만든 파일에 `String.fromCharCode(92)`로 역슬래시를 붙여 다시 돌렸다. 10-21 WORLD 계획 판(Claude): heredoc이 아니라 `node -e '…'`(작은따옴표) 안의 템플릿 문자열에 쓴 `'\\u0000'`도 `'\u0000'`이 되어 화면 파일에 진짜 NUL 글자가 들어갔다. `node --check`·시험은 통과했고, 다음 `grep`이 「Binary file … matches」를 내서 알았다. Write로 만든 스크립트로 NUL을 `\u0000` 글자로 바꿔 되돌렸고, 그 뒤 고침 스크립트는 모두 파일로 만들었다(`grep -rlP "\x00" <폴더>`로 다른 파일에 없는지 확인). 10-21 PULSE 트랙 줄(Claude): heredoc 안 파이썬 문자열에 쓴 `C:\\SYNK-LoRA\\validation\\…\\v2_validate` 경로가 `\v`(세로 탭) 둘로 바뀐 채 공용 트랙 줄에 들어갔다. 파이썬이 같은 문자열의 `\S`에 「SyntaxWarning: invalid escape sequence」를 낸 것이 신호였다. 줄을 바이트로 읽어 `\x0b` 수를 세어 잡고, Write로 만든 스크립트로 `\v` 글자로 되돌렸다(커밋 전, 명세서 JSON도 같은 방법으로 0개 확인). 10-23 · 10-24 「매진 임박」(Claude): 같은 꼴이 두 번 더 — 생성기록에 쓴 `flow\\v4_clip.mjs`가 세로 탭이 됐고, heredoc 파이썬으로 만든 Flow 라운드 파일 22개의 `"\\n"`이 JS 문자열 안의 진짜 줄바꿈이 되어 ego가 「SyntaxError: await is only valid …」로 첫 라운드부터 돌지 않았다(접수 전이라 크레딧 0). 라운드 파일은 Write로 만든 생성기에서 `String.fromCharCode(10)`로 다시 쓰고 `node --check`로 본 뒤 돌렸다.

### 큰따옴표 안의 백틱이 명령으로 실행된다
- 증상: `node -e "…"`로 쓴 JS 파일에서 템플릿 문자열·정규식이 비고, 「command not found」나 엉뚱한 도구 안내문이 찍힌다. 10-02에는 주석 속 `` `tools/원격배포.js` ``가 실제로 실행됐다(인자가 없어 배포는 안 났다). 10-22에는 README에 넣을 마크다운 글(코드 꼴 경로가 열 곳 넘게 든)을 `node -e "…"` 문자열로 넘겼다가, 그 안의 `` `<폴더>/tests.tap` ``이 셸 스크립트로 실행돼 시험 결과 1,689줄이 줄마다 명령으로 돌았고(2분 넘게 안 끝나 멈춤), 시험 이름의 `;` 뒤 낱말 여덟 개도 명령으로 불렸다(모두 「command not found」, `` `git add` ``도 한 번 돌았지만 경로가 없어 아무것도 안 넣음). 줄에 `>`·`|`가 있었으면 파일을 만들거나 다른 명령으로 넘겼을 자리다.
- 원인: Bash 큰따옴표 안의 백틱과 `$(…)`는 명령 치환이다. `${…}`·역슬래시도 같이 망가진다. 코드 꼴(백틱)을 많이 쓰는 한국어 마크다운 기록이 특히 잘 걸린다.
- 고침: 백틱·`${`·역슬래시가 든 JS는 파일로 쓰고 `node 파일`로 돌린다. 셸에서 써야 하면 `<<'EOF'`로 연다. 마크다운 기록은 셸을 거치지 않고 Edit·Write 도구로 넣는다. 실행 뒤 예상 밖 출력이 보이면 바로 멈추고(백그라운드로 넘어갔으면 그 작업을 끈다) 무엇이 실행됐는지부터 본다 — 출력의 「command not found」 줄과 실행된 파일의 `[<>|;&]` 줄을 맞춰 보고, 그 폴더에 새로 생긴 파일을 찾는다.
- 다시 확인: ``echo "a `echo X` b"``가 `a X b`다.
- 10-22 덧붙임(Claude): 문서에 넣을 글(트랙 한 줄)을 `node -e "…"` 안에 두었더니 글 속 `` `~/.claude/settings.json` ``·`` `tools/세션환경_줄이기.cjs` ``가 실행됐다 — 설정 파일은 셸 스크립트로 돌다 첫 줄부터 「command not found」·문법 오류로 끝났고(파일은 그대로), 도구는 미리 보기로 돌아 그 출력이 글에 박혔다. 백틱 낀 글은 코드가 아니어도 파일에 쓰고(Write), 넣기는 그 파일을 읽는 스크립트 파일로 한다. `"$(cat 파일)"`로 넘기는 것은 안전하다(치환 결과는 다시 치환되지 않는다).

### `/`로 시작하는 인자가 윈도우 경로로 바뀐다

### Git Bash의 시각과 시간대를 믿지 않는다
- 증상: 10-07 옛 노트북에서는 `date`가 시간대 표시 없이 UTC를 찍어(19:08 KST에 09:08) 게시 예약을 놓칠 뻔했다. 10-17 새 노트북에서는 그냥 `date`는 한국 시각(+0900, 시간대 이름 빈칸)인데 `TZ=Asia/Seoul date`가 거꾸로 UTC(`03:19 GMT`)를 찍는다.
- 원인: 이 Git Bash에는 시간대 자료가 없어 모르는 `TZ` 이름을 GMT로 본다. PC마다 기본 표시도 달랐다.

### 파이썬 `Path.write_text`가 Windows에서 LF 파일을 CRLF로 바꾼다 (2026-10-19 Claude)

### Edit 도구의 old_string을 잘린 출력에서 만들면 새 글이 긴 줄 한가운데에 끼고, 그 줄의 꼬리가 새 글 끝에 붙는다 (2026-10-24 Claude · 메모에서 옮김)

- 원인: Edit는 old_string이 줄 끝에서 끝나는지 보지 않고, 파일 안에서 하나뿐이기만 하면 바꾼다. `cut -c`·`head -c`·Grep 미리 보기(「Omitted long matching line」)·「truncated」 출력은 줄이 거기서 끝난 것처럼 보여 알아채기 어렵다. 공용 문서에서는 남의 줄을 망가뜨린다.

- 다시 확인: 긴 줄 하나가 든 scratchpad 파일에서 그 줄의 앞부분만 old_string으로 잡아 뒤에 항목을 넣으면, 원래 줄의 꼬리가 새 항목 끝에 붙는다(10-24 재현).

## 프로세스·검은 창

### Node의 detached로 띄운 PowerShell·CLI에 창이 생기지 않는다
- 증상: 10-18 계정판의 「설치 창 열기」가 「설치 창을 열었어요」를 띄우는데 아무 창도 없고 설치도 안 됐다. Gemini 「검은 창」 로그인도 창이 안 떠 10분을 기다리다 끝났다.
- 원인: Node(libuv)의 `detached:true`는 Windows에서 `DETACHED_PROCESS`로 띄워 자식에게 콘솔을 주지 않는다(`windowsHide:false`여도 같다). 콘솔 없는 부모(설치본 Electron 본체)에서 띄운 PowerShell 스크립트는 한 줄도 돌지 않고 종료 코드 0으로 끝났다. `detached` 없이 띄우면 부모에 콘솔이 있을 때 그 콘솔을 함께 써서 역시 새 창이 안 생긴다.
- 고침: 숨긴 PowerShell 런처가 `Start-Process -FilePath … [-ArgumentList …] [-WorkingDirectory …] -PassThru`로 새 창을 띄우고 PID를 찍는다. 스크립트는 `-EncodedCommand`(UTF-16LE base64)로 넘겨 따옴표·한글이 깨지지 않게 한다. 환경변수(계정 폴더 USERPROFILE 등)·작업 폴더는 그대로 물려받고, `.cmd` 심과 공백 든 경로도 된다. 창을 끌 일이 있으면 런처가 `$p.WaitForExit()`로 창이 닫힐 때까지 기다리게 하고, 런처가 살아 있을 때만 그 PID를 끈다(손잡이를 쥐고 있어 PID가 재사용되지 않는다).
- 다시 확인: 콘솔 없는 부모(`spawn(process.execPath,[…],{detached:true,stdio:'ignore'})`로 띄운 node)에서 세 방식으로 `GetConsoleWindow()` 값을 파일에 적는 PowerShell을 띄운다. detached는 파일이 안 생기고, `Start-Process`(-WindowStyle Hidden으로 시험)는 0이 아닌 창 손잡이를 적는다.
- 두 번째(10-19, 세션 공유 윈도 알림): 콘솔이 있는 부모(PowerShell에서 띄운 node)에서도 `detached:true`로 띄운 PowerShell은 결과 파일을 쓰지 못했다. 창이 필요 없는 일(알림 띄우기 등)은 detached 없이 `{windowsHide:true, stdio:'ignore'}`로 띄우면 콘솔 있는 부모·없는 부모 모두 0.1~0.5초에 돌았다. 떼지 않은 자식은 node가 끝나면 같이 끝나니, 짧게 끝나는 node(`--once` 등)에서는 unref하지 않아 자식이 끝날 때까지 기다리게 한다.

- 증상: 10-18 계정판 검토. cmd.exe로 감싸 띄운 `codex.cmd login`류에 `child.kill()`을 하자 cmd.exe는 꺼지고 손자(실제 CLI, node)는 살아 있었다. 로그인 취소 뒤 로그인 대기 포트를 계속 잡고 있어 다음 로그인이 「포트 사용 중」으로 막힐 수 있다.

- 원인: 앱 터미널 패널과 코드 블록 실행 단추는 관리자 권한이 없는 보통 셸이다. `Cert:\LocalMachine`과 방화벽 규칙은 관리자만 고칠 수 있다.
- 고침: 보안 설정이라 Claude가 직접 바꾸지 않고 유호님이 하게 할 때는, 명령을 위 방법으로 클립보드에 넣고 `Start-Process powershell.exe -Verb RunAs -ArgumentList '-NoExit','-NoProfile'`로 관리자 창만 열어 둔다. UAC를 기다리느라 도구가 묶이지 않게 백그라운드로 돌린다. 유호님은 「예」 → 창 클릭 → `Ctrl+V` → `Enter`만 한다. 대화의 코드 블록은 실행 단추가 붙지 않게 `text`로 쓰고, 「클립보드」 대신 「복사해 둔 것을 붙여 넣기」로 안내한다.
- 다시 확인: 붙여 넣은 뒤 `Get-ChildItem Cert:\LocalMachine\Root | Where-Object Thumbprint -eq <지문>`이 비어 있고 `Get-NetFirewallRule -DisplayName <이름>`이 아무것도 내지 않는다.

### Bash 도구에서 남의 작업트리 안으로 `cd`하면 세션 작업 폴더가 그 작업트리로 바뀐다 (2026-10-21 Claude)
- 증상: 10-21 공용 작업본 세션에서 `cd .claude/worktrees/<이름>/.tmp && ls …`를 돌리자 다음 차례에 「Primary working directory: …\worktrees\<이름>\.tmp」와 「This is a git worktree … Do NOT `cd` to the original repository root」 안내가 붙었다. 그 전까지 다른 폴더로 간 `cd`는 명령마다 「Shell cwd was reset to …」로 공용 작업본에 돌아왔다.
- 원인: 하네스가 Bash 셸의 마지막 폴더를 세션 작업 폴더로 삼는다. 저장소 밖으로 간 `cd`는 되돌리지만 저장소 안 폴더(작업트리 포함)는 그대로 둔다. 그대로 두면 다음 git 명령과 경로 판단이 남의 작업트리 기준이 된다.
- 고침: 남의 작업트리는 `git -C <경로>`·`find <절대 경로>`로만 보고 그 안으로 `cd`하지 않는다. 바뀌었으면 곧바로 `cd <공용 작업본>`으로 되돌린다.
- 다시 확인: 되돌린 뒤 안내에 「The primary working directory is no longer a git worktree」가 붙는다.

### PowerShell 도구가 `cmd /c rmdir <연결 폴더>`의 `/c`를 시스템 경로 삭제로 보고 명령을 통째로 막는다 (2026-10-21 Claude)
- 증상: 10-21 임시 talk 작업본의 node_modules junction(다른 작업본을 가리킴)만 끊으려고 PowerShell 도구에서 `cmd /c rmdir "<작업본>\node_modules"`를 넣은 명령을 돌리자 「Remove-Item on system path '/c' is blocked」로 한 줄도 돌지 않았다.
- 원인: PowerShell 도구의 삭제 검사가 명령 줄의 `/c`를 루트 경로로 읽는다(위 「`Remove-Item` 글자만으로 막는다」와 같은 계열).
- 고침: Bash 도구에서 `cmd //c "rmdir C:\\…\\node_modules"`로 링크만 지웠다(junction의 `rmdir`은 대상을 건드리지 않는다). 그 뒤 `git worktree remove`가 남은 것 없이 통과했다.
- 다시 확인: 링크를 지운 뒤 대상 폴더(`<원래 작업본>\node_modules\yaml`)가 그대로 있다.

### 워크트리에 묶인 세션은 명령 글에 `git`이 든 경로만 있어도 Bash 명령을 통째로 거절한다 (2026-10-24 Claude)
- 증상: 10-24 `EnterWorktree`로 옮긴 세션에서 `cd <워크트리> && git fetch … && printf … $(git rev-parse …)`가 「this command names git in a form too complex to verify that it stays inside the worktree」로 막혔다. git을 부르지 않는 명령도 같았다 — `rg … docs/현장노트/git_줄끝_잠금.md`가 든 반복문, `awk … .github/workflows/*.yml`.
- 원인: 워크트리 격리 검사가 명령 글에서 `git` 낱말(경로 `.github`·`git_줄끝_잠금.md`, 변수 값 포함)을 보면 그 명령이 워크트리 안에서만 도는지 따지고, `cd`·`&&` 사슬·`$(…)`·반복문처럼 따지기 어려우면 거절한다.
- 고침: git 명령은 `cd` 없이 한 줄씩 돌린다(`git fetch -q origin master`, `git log -1 …`). git이 든 경로를 읽을 때는 Grep·Read 도구를 쓰거나, 명령을 스크립트 파일로 써서 `node <파일>`로 돌린다.
- 다시 확인: 같은 세션에서 `git diff --stat -- <경로>` 한 줄은 지나가고, 경로에 `.github`가 든 `for … awk` 사슬은 거절된다.

### `%TEMP%`의 오래된 항목을 스크립트로 한꺼번에 지우면 자동 모드 판정기가 「Shared Scratch Sweep」으로 막는다 (2026-10-24 Claude)
- 증상: 10-24 C: 여유 175GiB에서 `%TEMP%`(claude 폴더 뺌) 맨 위 항목 중 사흘 넘게 안 바뀐 20,536개·17.0GiB를 장부에 먼저 적고 지우는 `.tmp/공간정리_20261024/임시지우기.py --실행`이 「denied by the Claude Code auto mode classifier. Reason: [Shared Scratch Sweep]」으로 실행 전에 거절됐다. 같은 스크립트의 미리 보기(읽기만)는 지나갔다.
- 원인: 판정기는 여러 프로그램·세션이 같이 쓰는 임시 폴더를 나이만 보고 쓸어 지우는 일을 남의 작업물을 지울 수 있는 일로 본다. claude 폴더와 실행 중인 명령줄에 든 항목을 뺀 조건과 상관없다.
- 고침: 우회하지 않고 멈췄다. 유호님이 그 일을 이름 대어 허락한 뒤 다시 돌리거나, 유호님이 Windows 설정 › 시스템 › 저장소 › 임시 파일에서 직접 지운다. 판정기를 넓히는 allow 줄은 따로 이름 댄 승인 뒤에만 넣는다.
- 다시 확인: 같은 스크립트를 인자 없이 돌리면 대상 수·크기만 찍고 아무것도 지우지 않는다. 같은 날 유호님이 대화에서 「임시 파일 17GB, 세션 임시 18.7GB … 셋 다 지워」라고 한 뒤에는 같은 `--실행`이 지나가 17.4GiB를 지웠고, `Temp\claude`의 사흘 넘은 세션 임시 폴더 19.9GiB도 막히지 않았다.

## ssh

### 같은 ssh 명령이 Git Bash에서는 되고 PowerShell에서만 실패한다
- 증상: 유호님 PowerShell 터미널에서 `WARNING: UNPROTECTED PRIVATE KEY FILE!` … `This private key will be ignored.` 뒤에 `Permission denied (publickey)`가 난다. 유호님께는 「눌렀는데 아무 일도 안 났다」로 보인다. 같은 명령이 Claude Bash 도구(Git Bash)에서는 된다(09-07).
- 원인: 두 셸이 서로 다른 ssh를 쓴다. PowerShell은 윈도우 OpenSSH(`C:\Windows\System32\OpenSSH\ssh.exe`)를 쓰는데, 이 프로그램은 소유자 말고 다른 계정도 키 파일을 읽을 수 있으면 그 키를 쓰지 않는다. Git Bash의 ssh(`/usr/bin/ssh`)는 키 권한을 따지지 않는다. 연결이 서버까지 가지도 못한 것이라, 서버 문제부터 찾으면 시간을 버린다.
- 고침: `icacls "$env:USERPROFILE\.ssh\<열쇠>" /inheritance:r /grant:r "${env:USERNAME}:(R)"`로 본인 읽기 하나만 남긴다(본인 파일이라 관리자 권한이 필요 없다). 고친 뒤에도 Git Bash의 ssh는 그대로 된다. ssh가 들어간 명령을 유호님께 드리기 전에 그 키의 권한을 한 번 본다.
- 다시 확인: `icacls "$env:USERPROFILE\.ssh\<열쇠>"`에 본인 `(R)` 하나만 있는지 본다. 10-17 새 노트북의 키 셋은 모두 본인 `(R)` 하나다. 같은 날 Users 읽기를 더한 시험 키로 재 보니 윈도우 `ssh-keygen -y`(OpenSSH_for_Windows 9.5)는 「Bad permissions … UNPROTECTED PRIVATE KEY FILE」로 거부했고, Git Bash `ssh-keygen -y`(OpenSSH 10.5)는 권한을 따지지 않고 암호 묻기로 넘어갔다.
