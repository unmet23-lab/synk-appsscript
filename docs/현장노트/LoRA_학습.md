## 학습

### 학습이 시험 때보다 느리다(스텝당 4~7초)
- 증상: 하린 33장 학습이 처음 스텝당 5~7초, 안정된 뒤 약 4.2초. GPU 사용률은 96%인데 전력은 80W대였다(10-17).
- 원인: Windows 전원 「균형 조정」과 노트북 기본 모드에서 GPU 전력이 낮게 묶인 것으로 보인다(성능 모드로 다시 재 보지는 않았다). 원본이 최대 2400px라 첫 스텝들이 더 느리다.
- 고침: 충전기를 꽂고 돌린다. 노트북 성능 모드(Legion Space)로 바꿀지는 유호님이 정한다.
- 다시 확인: `nvidia-smi --query-gpu=utilization.gpu,power.draw --format=csv -l 1`.
- 10-19 밤: 유호님이 성능 모드로 바꿨다고 한 뒤에도(충전 중, 배터리 79%) `nvidia-smi -q -d POWER`의 현재 전력 한도가 98.9W(최대 175W)였고 「SW Power Cap」이 켜져 있었다. Windows 전원 구성표는 「균형 조정」이었다. 유나 33장이 스텝당 1.55~5.7초로 오르내렸다. 전원 설정은 AI가 바꾸지 않는다.
- 10-19 11:40: 08:48 재시작 뒤 현재 전력 한도가 150W(기본 95W·최대 175W)로 올라 있었고, 그리기 174~181W에 유호 v1이 스텝당 약 3초였다. 「SW Power Cap」은 그대로 켜져 있고 Windows 구성표도 「균형 조정」 그대로라, 한도는 Windows 구성표가 아니라 노트북 쪽 모드를 따르는 것으로 보인다. 서진은 10:44 무렵부터 스텝당 4.4초 → 3.1초로 빨라졌다(한도가 바뀐 시각은 못 봤다). 다시 확인은 `nvidia-smi -q -d POWER`의 Current Power Limit.

### 대기열을 끄면 돌던 학습까지 멈춘다 — 학습 사이 틈은 다음 작업을 보류로 만든다
- 증상: 10-19 밤 유나 학습 중에, 지유 광고 업스케일(SeedVR2, VRAM 23GB)과 검증(ComfyUI)을 학습 사이에 끼워야 했다. 다음 학습(서진)은 이미 대기열에 있어 유나가 끝나면 바로 이어 돌 참이었다.
- 원인: AI-Toolkit 대기열을 끄면(`/api/queue/0/stop`) 그 GPU에서 도는 작업에 `return_to_queue`를 걸어 멈춘다(`ui/cron/actions/processQueue.ts`). 대기열에 남은 작업이 없으면 대기열은 스스로 꺼진다.
- 고침: 대기열은 건드리지 않고 다음 작업을 `/api/jobs/<id>/mark_stopped`로 보류한다. 새로 만든 작업은 처음부터 stopped라 `/start`를 부르지 않으면 된다(`_v2공통\train.py <폴더> <트리거> <woman|man> hold`). 따로 띄운 `_v2공통\학습_사슬.py`가 학습이 끝나기를 기다렸다가 GPU 틈에 업스케일·검증 10장을 돌리고, `보류_대기열.txt` 순서대로 `/api/jobs/<id>/start`와 `/api/queue/0/start`로 다음 학습을 넣는다. 세션이 멈춰도 학습이 이어지게 떨어진 프로세스로 띄운다.
- 다시 확인: `_v2공통\학습_사슬.log`에 「다음 학습 넣음」이 찍히고 `/api/jobs`에서 그 작업이 running인지.
- 학습을 잠깐 멈출 때(`/api/jobs/<id>/stop`)는 **사슬을 먼저 끈다.** 사슬은 stopped도 「끝남」으로 보고(DONE에 stopped 포함) 검증 없이 다음 보류 작업을 넣는다(10-19 유호 이어 학습·얼굴 시험 때 두 번 이안을 멈추며 확인). 다시 넣을 때는 `/start` + `/api/queue/0/start` 뒤 사슬을 그 작업 이름으로 다시 띄운다. 멈춘 학습은 마지막 250스텝 저장점에서 이어 간다.

### PC를 다시 시작하면 학습 작업이 running으로 남아 대기열이 멈춘다
- 증상: 10-19 08:48 시작 메뉴 「다시 시작」 뒤 AI-Toolkit 화면·학습·학습 사슬이 모두 꺼졌다. 화면을 다시 띄우자 서진 작업이 죽은 pid를 단 채 `running`(1,321스텝)으로 남아, 대기열이 「이미 도는 작업이 있다」며 아무것도 시작하지 않았다.
- 원인: 작업 상태는 화면 서버 DB에 있고, 죽은 학습을 알아채는 감시(`watchDetachedJob`)는 그 학습을 띄운 화면 프로세스 안에서만 돈다(`ui/cron/actions/startJob.ts`).
- 고침: `AI-Toolkit_실행.cmd`로 화면을 띄운 뒤, 남은 pid가 정말 없는지 보고 `/api/jobs/<id>/mark_stopped` → `/api/jobs/<id>/start` → `/api/queue/0/start`. 학습은 마지막 저장점(250스텝마다)과 `optimizer.pt`에서 이어 간다(서진은 1,250부터, 잃은 것 71스텝). 학습 사슬(`학습_사슬.py <지금 작업 이름>`)도 다시 띄운다.
- 다시 확인: `outputs/<이름>/log.txt` 끝의 진행 막대가 마지막 저장점 바로 뒤 숫자(1252/3300 등)에서 다시 시작하는지.
- 10-19 19:10 재부팅(태준 1,286스텝)도 같은 순서로 되살렸다: `AI-Toolkit_실행.cmd`를 최소화 창으로 띄우고(17초 뒤 응답), run.py가 없는 것을 본 뒤 mark_stopped → start → queue start, 사슬은 `학습_사슬.py m02_taejun_v2`(기록 `학습_사슬.log.new3`). 다시 켜진 학습은 처음 몇 분 동안 모델을 불러 양자화하느라 CPU가 100%이고 GPU는 1%다 — 이때 크롬·Gemini 화면도 같이 느려진다. 5분쯤 뒤 GPU 99%, 스텝당 2.5초로 돌아왔다.
