# 현장 노트 · 수집(yt-dlp · RSS)

> 남의 공개 영상의 숫자 · 댓글을 읽는 수집(`tools/수요스캔/`, 10-22 시청자 수요 조사)에서 만난 함정. 읽기만 하는 수집이다 — 로그인 · 게시 · 영상 파일 받기를 하지 않는다.

## 먼저 볼 것

- 한글 · 키릴이 깨지지 않게 `PYTHONIOENCODING=utf-8`을 붙이고, 결과는 콘솔 대신 파일로 쓴다(윈도우 콘솔은 CP949라 키릴에서 죽는다).
- yt-dlp로 댓글을 받으면 영상 정보의 댓글 수가 「받은 개수」로 덮인다 → 전체 수가 필요하면 따로 읽는다 ([자세히](#yt-dlp로-댓글을-받으면-댓글-수가-받은-개수로-덮인다-2026-10-23))
- 유튜브 채널 RSS는 같은 채널에서도 404 · 500을 번갈아 낸다 → 연달아 실패하면 RSS를 멈추고 쇼츠 탭으로 읽는다 ([자세히](#유튜브-채널-rss가-같은-채널에서도-404500을-번갈아-낸다-2026-10-23))
- 검색의 날짜 거르기 · 조회순 정렬은 기대대로 안 된다 → 새 채널 찾기는 약하고, 시드 채널 목록이 주력이다 ([자세히](#검색의-날짜-거르기조회순-정렬이-기대대로-안-된다-2026-10-23))
- 쇼츠 탭 · 쇼츠 재생목록 항목에는 날짜 · 길이가 없다 → 후보만 개별 영상 정보로 다시 읽는다 ([자세히](#쇼츠-탭과-쇼츠-재생목록에는-날짜와-길이가-없다-2026-10-23))

## yt-dlp

### yt-dlp로 댓글을 받으면 댓글 수가 「받은 개수」로 덮인다 (2026-10-23)
- 증상: `--write-comments --extractor-args "youtube:comment_sort=top;max_comments=30,…"`로 받은 영상의 `comment_count`가 30으로 나온다(실제 1,066).
- 원인: 댓글을 받으면 yt-dlp가 댓글 수 칸을 받은 목록 길이로 다시 채운다.
- 고침: 전체 수는 `--verbose` 출력의 「Downloading ~N comments」 줄에서 읽거나, 댓글 없이 받은 영상 정보의 값을 따로 둔다(`tools/수요스캔/수요수집.js`).
- 다시 확인: 같은 영상의 댓글 없는 `--dump-json` 값과 요약의 댓글 수가 같다.

### 유튜브 채널 RSS가 같은 채널에서도 404·500을 번갈아 낸다 (2026-10-23)
- 증상: `https://www.youtube.com/feeds/videos.xml?channel_id=…`가 처음 몇 번은 되다가 40번쯤 부른 뒤 38번 중 24번이 404 · 500이었다(같은 채널도 됐다 안 됐다).
- 원인: 확인 못 함(호출 빈도 제한으로 보인다). yt-dlp 호출 50번은 같은 때 403 · 429 없이 됐다.
- 고침: 연달아 실패하면 그 회차의 RSS를 멈추고 쇼츠 탭(`--flat-playlist`)으로 새 편을 읽는다(도구에 들어 있음).
- 다시 확인: 요약의 「못 잰 채널」이 비고, 기록(`기록.jsonl`)에 RSS 멈춤 줄이 있으면 탭 읽기 줄이 뒤따른다.

### 검색의 날짜 거르기·조회순 정렬이 기대대로 안 된다 (2026-10-23)
- 증상: 「이번 주 · 이번 달」 거르기를 붙인 검색은 조회 수십 회짜리 새 영상만 주고, 조회순 정렬은 먹지 않으며, 관련순 결과는 대부분 롱폼이다.
- 원인: 검색 결과 순서 · 거르기는 유튜브가 정하고 yt-dlp `ytsearch`는 관련순 한 가지를 받는다.
- 고침: 새 채널 찾기는 보조로 두고, 튄 편 찾기는 시드 채널(설정 `tools/수요스캔/설정/수요_<브랜드>.json`)의 쇼츠 탭으로 한다. 검색에서 나온 새 채널은 시드 후보로만 올린다.
- 다시 확인: 요약의 튄 편 대부분이 시드 채널에서 나온다.

### 쇼츠 탭과 쇼츠 재생목록에는 날짜와 길이가 없다 (2026-10-23)
- 증상: `https://www.youtube.com/@<핸들>/shorts`를 `--flat-playlist`로 읽은 항목에 `upload_date` · `duration`이 비어 있다.
- 원인: 평평한 목록은 쇼츠 칸의 조회 · 제목만 준다.
- 고침: 기준선(조회 중앙값)은 탭으로 내고, 튄 편 후보만 개별 영상 정보(`--skip-download --dump-json`)로 날짜 · 길이를 다시 읽는다(상한을 넘친 편은 다음 회차에 ↻로).
- 다시 확인: 요약 표의 튄 편에 날짜 · 길이 칸이 다 차 있거나 ↻ 표시가 있다.

## 인스타·틱톡(ego)

### 인스타 공개 계정의 글 숫자는 웹 API를 직접 부르면 429 — ego에서 그 페이지가 받는 응답을 읽는다 (2026-10-23 Claude)
- 증상: 몽골 한국어 · TOPIK 인스타 계정 숫자를 모으려고 ego(로그인된 인스타)에서 `page.fetch('/api/v1/users/web_profile_info/?username=…')`를 부르자 HTTP 429와 「페이지를 찾을 수 없습니다」 HTML이 왔다. 10-22 수요 조사(`docs/마케팅/시청자수요조사_20261022.md`)도 인스타 · 틱톡 검색과 해시태그는 로그인 벽으로 못 보고 아는 계정만 로그아웃 화면 값으로 읽었다.
- 원인: 확실하지 않다. 페이지 밖에서 부른 API 요청이 막힌 것으로 보인다. 같은 계정을 ego로 열면 인스타 페이지가 스스로 GraphQL(`/api/graphql`, `/graphql/query`)로 글 목록을 받는다.
- 고침: `page.cdp('Network.enable')` → 프로필 열기 → 마우스 휠로 아홉 번쯤 내리기 → `page.events()`의 `Network.responseReceived` 가운데 graphql 응답만 `Network.getResponseBody`로 읽어, `data.xdt_api__v1__feed__user_timeline_graphql_connection.edges`의 글(code · taken_at · media_type · like_count · comment_count · carousel_media_count · 캡션 앞부분)만 남긴다. 계정 10곳에서 48~180편씩 읽혔다. **같은 묶음에 메시지함 응답(`get_slide_mailbox…`)이 섞여 오니 통째로 저장하지 말고 글 목록만 골라 쓴다.** 틱톡은 같은 방법으로 `api/post/item_list`(계정)와 `api/search/item`(검색) 응답을 읽는다. 이번 스크립트(세션 scratchpad의 `ig/round-02.mjs` · `ig/tt-round-01.mjs`)는 며칠 뒤 지워지니 다시 쓸 때는 이 순서대로 새로 짠다 — 본문이 `{`로 시작하는 응답만 JSON으로 읽고, 팔로우 · 좋아요 · 메시지 단추는 누르지 않는다.
- 다시 확인: 공개 계정 하나를 열어 읽은 글 수와 그 계정 첫 화면 「게시물」 수의 최근 줄이 맞는지, 저장한 JSON에 `inbox` · `thread` 낱말이 없는지 본다. ego가 다른 세션 스크립트를 받는 중이면 한 번에 하나씩이고, 앱이 다시 켜지면 작업 공간 번호로 못 잡는다([브라우저 노트](브라우저_게시.md#ego-앱이-다시-시작되면-작업-공간-번호로-못-잡는다-2026-10-21-claude)).
