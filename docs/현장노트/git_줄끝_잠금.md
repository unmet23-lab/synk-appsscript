## 절차 · 공용 작업본에서 내 것만 커밋하기

**워크트리(세션마다 따로 쓰는 작업본, 2026-10-20부터 기본):** `node tools/바로올리기.js <경로…> -m "<메시지>" --실행`(워크트리에서 바뀐 것을 모두면 `--모두`). 막 받은 origin/master 위에 내 경로만 커밋해 곧바로 push하고(그새 origin이 움직이면 다시 받아 다섯 번까지), 워크트리 가지를 올린 커밋으로 옮긴다. 로컬 가지에는 커밋을 따로 쌓지 않는다. 워크트리의 바뀐 것은 모두 그 세션 것이라 공용 문서도 조각 없이 통째로 올린다. origin 위에 얹기와 검사(올라갈 줄은 내 줄뿐·내 줄 빠짐 없음·줄끝은 origin 판·저장 용량·공개 검사)는 아래 `내커밋.js 올리기`와 같은 코드라, 로컬 master 꼬리에서 뜬 워크트리여도 내가 바꾼 것만 올라간다. 걸리면 아무것도 올리지 않는다 — 「내가 고친 줄이 원격 판에 그대로 없다」(그 줄을 origin이 그새 고침)면 그 파일만 사본을 두고 바탕 판으로 돌린 뒤 `따라가기 --실행`으로 최신을 받고 새 판에 다시 고쳐 올린다(10-20 첫 시범의 AGENTS.md 세션 마무리 줄). 따라가기는 아직 고치는 파일을 3방향으로 지키고(바탕은 HEAD 판과 그 사이 origin 판 가운데 작업본과 가장 가까운 판 — 공용 작업본에서 세션이 최신 판에 제 줄을 얹어 둔 경우, 10-21), 겹치거나 이 가지에만 있는 안 올린 커밋이 있으면 가지를 옮기지 않는다 — push는 된 것이고 다시 돌리면 「올릴 것 없음」이다. push 없이 최신으로만 옮기려면 `따라가기 --실행`, 큰 미디어 폴더(docs/캐릭터·홍보물·라디오, 약 2.1GB)를 그 워크트리에서 빼려면 `가볍게 --실행` — 워크트리 세션은 시작할 때 이것부터 한다(10-21, AGENTS.md). 필요한 폴더만 되살리기 `가볍게 --되살림 <폴더> --실행`, 전부는 `가볍게 --되살림 --실행`. Git Bash에서 `git sparse-checkout add /docs/…`를 직접 치면 앞의 `/`가 「C:/Program Files/Git/docs/…」로 바뀌어 아무것도 안 꺼내진다(10-21 Claude) — 도구는 무늬를 stdin으로 넘겨 이 함정을 피한다. 공용 작업본 master가 origin의 조상이면(꼬리 정리 뒤) 워크트리에서 올릴 때 공용 작업본도 빨리감기로 따라간다(겹치는 미커밋·스테이징이 있으면 건너뜀). 시험 `node --test tests/바로올리기.test.js`(꼬리에서 뜬 워크트리·같은 자리 덧붙임·코드 겹침·push 경합·미커밋 지키기·가지에만 있는 커밋·index.lock·줄끝·용량·공용 작업본 조각·스테이징·장부 덧붙임·장부올리기·가볍게).

**공용 작업본(메인) — 2026-10-20 꼬리 정리 뒤:** 워크트리와 같은 `node tools/바로올리기.js <경로…> -m "<메시지>" --실행`을 쓴다. 공용 인덱스(`git add` → `git commit`)로는 커밋하지 않는다 — 다른 세션이 올려 둔 스테이징이 내 커밋에 섞인다. 여러 세션이 같이 고치는 문서(아래 목록)는 미리 보기가 보이는 조각 가운데 내 것만 `--조각 <경로>=<id>[,<id>…]`로, 폴더는 그 아래가 모두 내 것일 때만 `--폴더`로 올린다(조각 id·고르는 법은 아래 `내커밋.js`와 같다). 공용 인덱스에 내 경로의 남의 스테이징이 있으면 멈춘다. 로컬 master에는 커밋을 쌓지 않는다 — `내커밋.js 커밋`은 꼬리 없는 공용 작업본에서 같은 경로·조각·메시지의 바로올리기 명령을 보이고 멈추고, `tools/참고카드_커밋.js`(팁 검토 예약)는 꼬리가 없으면 카드 폴더만 바로올리기로 push한다. 올린 뒤 공용 작업본은 그 커밋으로 따라가고, 남의 미커밋이 origin 변경과 겹치면 따라가지 않는다(push는 된 것). 꼬리가 다시 생기면 아래 「공용 작업본 꼬리 정리」.

**`tools/내커밋.js`(10-19~10-20 공용 작업본 도구 — 지금은 꼬리가 다시 생겼을 때 그 커밋을 `올리기`로 올리는 데 쓴다):** 두 명령 모두 기본은 미리 보기이고 `--실행`을 붙여야 반영한다.

- `node tools/내커밋.js 커밋 <경로…> -m "<메시지>"` — 아래 손 절차 1~6을 한 번에 한다. 바탕 고정 → 별도 인덱스 → 지정 경로만 → 줄끝을 바탕 판에 맞춤 → 저장 용량 검사 → `commit-tree` → `update-ref` CAS → 공용 인덱스의 그 경로만 reset 순서다. reset을 못 하면 가지를 되돌린다. index.lock은 기다렸다 다시 하고 주인 없는 잠금만 한 번 치운다. 줄끝을 맞추고 나니 바탕과 같으면 커밋하지 않는다(「커밋할 것 없음」).
- 남도 고치는 문서(AGENTS.md·CLAUDE.md·DESIGN.md·트랙·결정·문서 지도·AI 운영원칙·현장 노트·만족사례 장부)는 통째로 올리지 않는다. 미리 보기가 바탕 대비 조각을 id와 함께 보여 주면 내 것만 `--조각 <경로>=<id>[,<id>…]`로 고른다. 조각 안 일부 줄은 `<id>:<줄>-<줄>`(미리 보기가 조각의 줄 번호를 모두 보인다), 바뀐 곳이 모두 내 것이면 `=전부`다. 남의 줄은 작업본에 그대로 남는다.
- 공용 문서가 아닌 코드 파일은 도구가 멈추지 않고 작업본 판을 통째로 올린다. 같은 파일에 남의 미커밋 수정이 있으면 그 줄도 내 커밋에 섞인다. 미리 보기의 경로별 +/− 수가 내 차이와 같은지 보고, 다르면 `--자세히`로 조각을 본 뒤 그 파일도 `--조각 <경로>=<내 조각들>`로 고른다(10-19 공용 master `4b654e966`: `desktop/src/main.cjs`가 내 +5 −4가 아니라 +6 −5로 나와, 115행 남의 조각을 빼고 올렸다).
- 폴더 경로는 그 아래 남의 미커밋 수정·새 파일까지 올리므로, `--폴더` 없이는 그 아래 바뀐 파일 목록만 보이고 멈춘다. 내 파일만 하나씩 주거나, 모두 내 것일 때만 `--폴더`를 붙인다. 하위 git 저장소(gitlink)가 섞이면 멈춘다.
- 「공용 인덱스에 내 경로의 다른 스테이징이 있다」로 멈추면 아무것도 바뀌지 않았다. 남이 올린 것이면 그 세션과 맞추고, 내가 전에 `git add`한 판이면 `git reset -q -- <경로>`로 내린 뒤 다시 한다.
- `node tools/내커밋.js 올리기 <커밋…>` — 아래 「로컬 master를 통째로 push하면 남의 미푸시 커밋이 같이 나간다」의 절차를 한다. `--합치기`는 올린 뒤 로컬 가지에 「트리는 로컬 그대로」 병합 커밋을 더한다. origin에 있는 남의 커밋이 바꾼 경로가 모두 로컬과 같고, 다시 쌓으며 줄끝을 맞춘 경로가 없을 때만 한다.
- 로컬 master에 origin에 없는 커밋(꼬리)이 생기면 아래 「공용 작업본 꼬리 정리」를 따른다. `tools/master맞추기.js`(병합 커밋으로 맞추던 도구)는 10-20 은퇴해 안내만 찍는다 — 옛 판은 `git show 855e68eaa:tools/master맞추기.js`.
- `--줄끝그대로`(커밋·올리기)는 줄끝을 일부러 바꾸는 커밋(재정규화)에만 쓴다. 없으면 바탕·원격 판 줄끝으로 되돌려, 줄끝만 바꾼 커밋은 「커밋할 것 없음」·「올릴 것 없음」이 된다.
- git 2.31 이상(커밋)·2.43 이상(올리기, `merge-file --object-id`)이 필요하다. 모자라면 도구가 멈춘다(10-19 이 PC 2.55).

손 절차(도구를 못 쓸 때. 도구도 같은 일을 한다):

1. `BASE=$(git rev-parse HEAD)`를 먼저 잡는다. 내용은 반드시 이 BASE에서 만든다.
2. `export GIT_INDEX_FILE=<임시>/x.index; git read-tree $BASE`로 별도 인덱스를 만든다.
3. 별도 인덱스에 올린다.
   - 내 파일: 추적 여부부터 본다(`git cat-file -e $BASE:<경로>`). 그다음 `git add -- <경로>`.
   - 남도 고치는 문서(AGENTS.md·결정·트랙·문서 지도 등): `git cat-file blob $BASE:<경로>`를 버퍼 그대로(줄 끝을 자르지 않고) 받아 내 줄만 더한 파일을 만든다. `git hash-object -w --no-filters <파일>`로 blob을 만들고(내용이 이미 LF라 바이트 그대로. `--no-filters`와 `--path=`는 같이 쓸 수 없다 — git 2.55가 「Can't use --path with --no-filters」로 거절, 10-17) `git update-index --cacheinfo 100644,<blob>,<경로>`로 올린다.
4. `git write-tree` → `git commit-tree <트리> -p $BASE -F <메시지 파일>` → `git update-ref -m <설명> refs/heads/master <새 커밋> $BASE`. 그사이 HEAD가 움직였으면 update-ref가 실패하고 아무것도 바뀌지 않는다 — 1부터 다시 한다.
5. 곧바로 `unset GIT_INDEX_FILE; git reset -q -- <내 경로들>`로 공용 인덱스의 그 경로만 새 HEAD에 맞춘다. 막히면 미루지 않는다(아래 「커밋 뒤 공용 인덱스」).
6. 확인: `git diff --cached --name-only`에 내 경로가 없고, `git diff --stat $BASE <새 커밋>`의 줄 수가 내가 바꾼 양과 같다.

## 줄끝(CRLF·LF)

### 작업본이 CRLF인 문서로 「HEAD 판 + 내 줄」을 만들면 제목 비교가 전부 어긋난다
- 증상: 10-19 별도 인덱스 커밋에서 현장노트 단락을 제목 단위로 골라 넣을 때, `시험_화면확인.md`의 제목이 모두 「HEAD에 없음」으로 나와 앞 단락을 못 찾았고 `git diff --cached --check`가 새 줄마다 trailing whitespace를 냈다. 만족사례 장부의 표 줄도 끝에 `\r`가 붙은 채 들어갈 뻔했다.
- 원인: HEAD blob은 LF인데 공용 작업본에는 같은 파일이 CRLF인 것이 섞여 있다. 작업본 줄을 그대로 쪼개면 줄마다 `\r`가 남는다. 또 파일이 제목으로 시작하면 제목 단위로 나눈 첫 칸이 비어 있어, 그대로 이으면 맨 앞에 빈 줄이 생긴다.
- 고침: 작업본은 `replace(/\r\n/g, '\n')`로 LF로 맞춘 뒤 비교·삽입하고, 다시 이을 때 줄 없는 칸은 뺀다. 단락 안에 빈 줄이 있는 문서(만족사례 장부)는 빈 줄이 아니라 다음 제목까지를 한 단락으로 잡는다.
- 다시 확인: `git diff --cached --check`가 통과하고 `@@ -1,` hunk가 없으며, `git apply --numstat`의 줄 수가 넣은 단락 줄 수와 같다(10-19 `c055fe796`).
- 10-21 덧붙임(Claude): 워크트리에서 내가 LF로 쓴 도구 파일(`tools/topik-review.mjs`)도 `바로올리기.js --실행`의 따라가기(checkout) 뒤에는 `core.autocrlf=true` 때문에 CRLF가 된다. 그 뒤 줄바꿈이 든 앵커로 고치는 node 스크립트가 「anchor 없음」으로 멈췄다(한 줄짜리 앵커는 맞아서, 여러 줄 앵커만 깨지는 것이 표지다). 같은 고침 — 읽을 때 LF로 맞추고 쓸 때 원래 줄끝으로 되돌린다.

### 공용 문서 하나가 줄끝만 바뀌어 통째로 diff가 된다
- 증상: `git diff HEAD`가 트랙 87줄 전부 바뀐 것으로 나온다(내용은 몇 줄만 바뀜). 파이썬으로 고친 LF 파일(`KidsQuestion.tsx` 226줄)이 통째로 CRLF가 된다.
- 원인: 다른 도구가 작업본을 CRLF↔LF로 뒤집어 두었고, 「작업본 줄끝을 따르는」 스크립트가 그대로 이어 썼다. `sed -i`는 CRLF를 LF로, 파이썬 `open(p, 'w')`(text 모드)는 Windows에서 LF를 CRLF로 바꾼다. 한 파일 안에 CRLF 줄과 LF 줄이 섞여 있기도 하다(10-08 트랙 202줄 중 14줄 LF).
- 고침: 공용 문서를 쓰기 전후에 HEAD와 CR 개수를 견주고, 다르면 내용은 두고 줄끝만 HEAD 형식으로 되돌린다. 파이썬은 읽기·쓰기 모두 `newline=''`로 연다. 줄을 끼울 때는 `\n`으로 나누고 `\r`을 뗀 값으로 찾되, 넣는 줄은 이웃 줄의 `\r` 유무를 따른다. 남의 줄의 줄끝은 고치지 않는다.
- 다시 확인: `tr -cd '\r' < <파일> | wc -c`와 `git show HEAD:<파일> | tr -cd '\r' | wc -c`가 같고, `git diff HEAD --stat -- <파일>`이 실제로 바꾼 줄 수와 같다.
- 10-20 덧붙임(Claude): 워크트리(`core.autocrlf=false`)에서 Claude Edit 도구로 두 줄만 고친 LF 문서 `tools/company-messenger/API.md`가 통째로 CRLF가 돼 `git diff --stat`이 782줄이었다(Fable 검수가 짚음). 같은 파일 사본을 scratchpad에서 한 번·나란히 두 번 고쳐 봤지만 LF 그대로라 원인은 찾지 못했다. ### CR 개수를 `grep -c $'\r'`로 세면 모든 줄이 나온다
- 증상: LF뿐인 파일에서도 `grep -c $'\r' AGENTS.md`가 줄 수(21)를 그대로 낸다.
- 원인: Git Bash의 grep이 CR 한 글자짜리 패턴을 빈 패턴처럼 다룬다(`grep -c ''`과 같은 수가 나온다). 더 깊은 까닭은 캐지 않았다.
- 고침: `tr -cd '\r' < <파일> | wc -c`로 센다.
- 다시 확인: LF 파일에서 `grep -c $'\r'`이 줄 수, `tr -cd '\r' | wc -c`가 0이다(10-17 재현, CR 한 줄 + LF 한 줄 파일에서도 grep은 2, tr은 1).
- 10-24 덧붙임(Claude): Git Bash의 awk도 줄 끝 CR을 떼고 읽는다 — `awk '/\r$/{c++}'`가 411줄 전부 CRLF인 순서 문서에서 0을 냈다(그래서 10-23 밤 「전부 LF」라고 잘못 봤다). 줄마다 줄끝을 볼 때는 `node -e`로 `split('\n')` 뒤 `endsWith('\r')`를 센다.

### 파이썬이 git에 넘긴 입력 끝에 `\r`이 붙는다
- 증상: `git update-ref --stdin`이 「extra input」으로 거절한다. `Path.write_text`로 쓴 `objects/info/alternates`에서 「object directory …? does not exist」가 난다(10-17).
- 원인: `subprocess.run(..., text=True, input=s)`와 `write_text`가 Windows에서 `\n`을 `\r\n`으로 바꿔 보낸다.
- 고침: git 입력과 git이 읽는 파일은 바이트로 넘긴다(`input=s.encode()`, `write_bytes`).
- 다시 확인: 넘긴 바이트를 파일로 떠서 `tr -cd '\r' | wc -c`가 0인지 본다.

### `.gitattributes`에 `eol=lf`를 넣어도 작업본의 CRLF 파일이 안 바뀐다
- 증상: 해시·바이트를 대조하는 시험이 빨개진다(10-08 `atlas/personalization.js` CRLF 435개 → 런처 사본 해시 시험 실패). `git checkout HEAD -- <파일>`을 해도 그대로다.
- 원인: autocrlf=true 작업본에서 새 `eol` 속성은 파일이 다시 쓰일 때만 적용된다. checkout은 정규화한 뒤 같다고 보고 다시 쓰지 않는다.
- 고침: 파일을 지운 뒤 `git checkout HEAD -- <파일>`로 다시 받는다.
- 다시 확인: `tr -cd '\r' < <파일> | wc -c`가 0이고 그 시험이 통과한다.

### 내용이 HEAD와 같은데 `git status`에 M이 남는다
- 증상: `git apply -R`로 HEAD 내용에 되돌린 파일이 `git diff`·`git hash-object`로는 HEAD와 같은데 `git status`·`update-index --refresh`에는 「needs update」(M)로 남는다(10-14).
- 원인: autocrlf가 CRLF로 다시 써서 작업본 크기가 인덱스에 적힌 크기(LF)와 다르다. 크기가 다르면 git은 내용을 다시 재지 않고 바뀐 것으로 본다.
- 고침: `git show HEAD:<파일> > <임시> && mv <임시> <파일>`로 HEAD 바이트 그대로 쓴다. `git add`로 맞추면 공용 인덱스를 건드린다.
- 다시 확인: `git ls-files --debug -- <파일>`의 size와 작업본 파일 크기가 같고 status가 깨끗하다.

### `git archive`로 꺼낸 파일이 CRLF로 풀린다
- 증상: 공개본(LF)과 견주면 모든 줄이 다르게 나온다. 커밋 판을 꺼내 빌드한 결과가 공개본과 바이트로 안 맞는다.
- 원인: 이 PC의 `core.autocrlf=true`가 archive에도 적용된다.
- 고침: `git -c core.autocrlf=false archive <커밋> -- <경로들> | tar -x -C <폴더>`. 차이만 볼 때는 `diff --strip-trailing-cr`도 된다.
- 다시 확인: 꺼낸 파일의 `tr -cd '\r' | wc -c`가 blob(`git cat-file blob <커밋>:<경로> | tr -cd '\r' | wc -c`)과 같다.
- 10-19 덧붙임(`git apply`도 같다): SYNK-website처럼 `.gitattributes`가 `eol=lf`인 저장소를 archive로 꺼낸 사본은 LF로 나왔지만, 그 사본(저장소 밖 폴더)에서 `git apply <패치>`를 하자 고친 세 파일(build.mjs·site.css·site.js)만 모든 줄이 CRLF가 됐다. 저장소 밖에서는 `.gitattributes`를 보지 않고 시스템 `core.autocrlf=true`대로 쓴다. 홈페이지 빌드는 이 바이트로 `?v=` 토큰을 만들므로 공개본과 어긋난다. `git -c core.autocrlf=false apply`로 하거나, 패치를 만든 사본의 파일을 그대로 복사한다(10-19 질문창·서비스 시안). 확인은 Node로 CR 수를 센다(`(s.match(/\r/g)||[]).length`, 아래 「grep -c $'\r'」 항목).
- 10-26 덧붙임(반대 경우 — 저장소 **안** 폴더, Claude): 워크트리의 `.tmp/<작업>/new/`에 커밋 판을 archive로 꺼내 `cd new && git apply 고침.patch`를 하자 종료 0인데 아무 파일도 안 바뀌었다 — 빌드가 기준과 바이트까지 같게 나와서 알았다. 저장소 안의 하위 폴더에서는 git이 저장소를 찾아 패치 경로를 저장소 루트 기준으로 보고, 지금 폴더 밖 경로는 말없이 건너뛴다(`--verbose`로 보면 「Skipped patch」). 고침: `GIT_CEILING_DIRECTORIES=<그 폴더의 부모> git -c core.autocrlf=false apply --verbose 고침.patch`(저장소 찾기를 멈추고, 저장소 밖처럼 굴 때의 CRLF 변환도 끈다) 뒤에 고친 값이 들어갔는지 `grep -q`로 확인하고 없으면 멈춘다. 다시 확인: 「Applied patch … cleanly」가 파일마다 나오고, 기준 빌드와의 차이가 고친 줄뿐이며 CR이 0이다(싱크타운 귀뚜라미 공개 `.tmp/townw7b-crickets-20261026/build-new.sh`).

### `git hash-object --stdin-paths`가 CRLF가 든 blob의 깨끗한 파일을 다르다고 한다
- 증상: 10-19 `tools/master맞추기.js`를 짤 때 `core.autocrlf=true` 저장소에서 `git status`로는 깨끗한 파일(blob에 CRLF가 든 파일·줄끝 섞인 파일)을 `hash-object --stdin-paths`가 HEAD blob과 다른 해시로 냈다. 그대로 믿으면 남의 수정이 있는 파일로 잘못 본다.
- 원인: git은 인덱스 blob에 CRLF가 있으면 그 파일의 줄끝을 바꾸지 않는다. `git status`·`git add`는 이 규칙을 따르지만 `hash-object --stdin-paths`는 인덱스를 보지 않고 CRLF를 LF로 바꿔 해시를 잰다.
- 고침: 「작업본이 HEAD 판 그대로인가」는 `GIT_OPTIONAL_LOCKS=0 git status --porcelain=v1 -z --untracked-files=all`에 그 경로가 없는지로 본다(잠금 없이 읽는다). 해시는 새 판과 같은지 같은 다른 비교에만 쓰고, 다르면 줄끝을 LF로 맞춘 내용으로 다시 본다.
- 다시 확인: CRLF blob 파일에서 `printf '<경로>\n' | git hash-object --stdin-paths`와 `git rev-parse HEAD:<경로>`가 다르고 `git status --porcelain -- <경로>`는 비어 있다. 시험 「줄끝: core.autocrlf=true에서 …」(`tests/master맞추기.test.js`)이 이 파일을 「새 판」으로 잡는다.

## 당기기·push

### 워크트리끼리 같이 보는 `origin/master`로 판을 만들면 남의 새 줄이 내 변경에 섞인다 (2026-10-19)
- 증상: 10-19 통화·메신저 맞추기에서 워크트리를 origin/master로 빨리감기한 뒤 `git cat-file blob origin/master:<경로>`에 내 항목을 끼운 판을 썼는데, `git diff --numstat`의 이 파일이 예상한 +7이 아니라 +13이었다. 다른 세션이 막 올린 항목 하나가 내 변경처럼 들어 있었다(커밋 전에 줄 수로 발견).
- 원인: `refs/remotes/origin/*`는 공용 `.git`에 하나만 있어 모든 워크트리가 같이 본다. 그사이 다른 세션이 fetch해서 origin/master는 앞으로 갔고 내 HEAD는 빨리감기한 판 그대로였다. 앞선 origin 판 위에 만든 파일은 HEAD와 견주면 남의 새 줄까지 내 변경으로 잡힌다.
- 고침: 판을 만들 바탕은 `origin/master`가 아니라 고정한 커밋(HEAD)으로 준다. 만들기 직전에 `git rev-parse HEAD origin/master`가 같은지 보고 다르면 먼저 빨리감기한다. 이번에는 쓴 경로만 되돌리고 빨리감기한 뒤 바탕을 HEAD로 고정해 다시 만들었다.
- 다시 확인: 만든 뒤 `git diff --numstat`의 경로별 줄 수가 넣은 양과 같다(10-19 이 파일 +13 → +7).

### 로컬 master를 통째로 push하면 남의 미푸시 커밋이 같이 나간다
- 증상: 내 커밋만 올리려 했는데 아래에 깔린 다른 세션 커밋이 함께 올라갔다(10-03).
- 원인: `git push origin master`는 내 커밋의 조상인 남의 미푸시 커밋까지 올린다. 그 세션은 아직 유호님 확인을 기다리는 중일 수 있다.
- 고침: `node tools/내커밋.js 올리기 <내 커밋…>`(미리 보기 → `--실행`)로 올린다(10-19). origin/master를 fetch해, 내 커밋이 그 바로 위에 이어져 있으면 그 커밋을 그대로 올린다. 남의 것이 섞였으면 origin/master 위에 내 커밋의 바뀐 경로만 별도 인덱스로 다시 쌓는다(같은 메시지·작성자). 원격 판이 내 부모 판과 같으면 내 판, 다르면 `git merge-file`, 문서가 겹치면 원격에도 있는 다음 줄 앞에 내 줄을 붙인다. 코드·데이터 파일이 겹치거나 내가 고친 줄이 원격에 그대로 없으면 멈춘다. 다시 쌓는 판의 줄끝은 원격 판에 맞추고, origin 바로 위의 커밋이라도 줄끝만 원격 판과 다른 줄이 있으면 그대로 올리지 않고 맞춰 다시 쌓는다(줄끝을 일부러 바꾸는 커밋만 `--줄끝그대로`). 올리기 전에 경로마다 「올라갈 줄은 모두 내 커밋의 줄(남의 미푸시 줄이 새지 않음) · 내 커밋이 바꾸지 않은 경로는 그대로 · 내가 지우지 않은 원격 줄은 그대로 · 줄끝은 원격 판을 따름」과 저장 용량(`git-storage-check.cjs --base origin/master --head <올릴 머리>`)을 본다. 미리 보기의 새 커밋 번호는 실행 때 다시 만들어 달라지니, 원격 CI는 실행 출력의 번호로 본다. 그다음 빨리감기로만 push하고, origin이 그새 움직였으면 다시 fetch해 처음부터 한다. 로컬 master는 그대로 둔다. 옛 `.tmp/push-mine-20261013/` 도구(restack.py·restack_close.py·push_close.py·merge_local.py)는 10-19부터 쓰지 않는다. 「푸시해」는 내 커밋만이고, 남의 커밋까지 올리는 것은 유호님이 그렇게 말할 때만이다.
- 다시 확인: `git ls-remote origin master`가 올리기 출력의 올린 머리이고, 출력에 「검사: 올라갈 줄은 모두 내 커밋의 줄 · 내 줄 빠짐 없음 · 줄끝은 원격 판을 따름」과 저장 용량 통과가 있다. 10-19 임시 저장소 재현(시험 「재현: …」을 `--test-reporter=tap`으로 돌리면 명령과 출력이 찍힌다): 남의 미푸시 커밋·스테이징·미커밋 수정·새 파일·트랙의 남의 줄이 있는 채로 내 파일과 트랙 내 줄만 커밋했고, 그새 origin에 올라온 GPT 커밋 위에 내 커밋 하나만 올렸다. 남의 것은 작업본·공용 인덱스·로컬 master에 그대로였다.
- 10-19 덧붙임(병합 커밋은 이 도구로 못 올린다): `내커밋.js 올리기`는 부모가 하나인 커밋만 받는다. 가지를 병합 커밋으로 master에 합칠 때는 origin/master에서 만든 격리 작업본에서 합치고, `git-storage-check.cjs --base origin/master --head HEAD` 뒤 `git push origin HEAD:refs/heads/master`로 올린다. 바쁜 시간엔 검사하는 몇 분 사이에 origin이 움직여 push가 거절된다. 그때는 새 origin 커밋이 내 경로·생성 묶음 입력(atlas·계정 dist·generated·WORLD 묶음)과 겹치지 않을 때만 origin/master를 병합하고 곧바로 다시 push하는 고리로 올린 뒤, 올린 머리에서 묶음 검사·관련 시험을 다시 돌린다. 겹치면 멈추고 다시 빌드한다. 10-19 내 성향 합치기에서 두 번 따라 합쳐 `e241b2f77`을 올렸다(그 세션 scratchpad `merge-push.sh`, 요점은 이 줄).
- 10-19 덧붙임(워크트리 가지도 같다): 공용 작업본에서 `git worktree add -b <가지> <작업본 HEAD>`로 뜬 가지는 바탕이 로컬 master라, 그 밑에 남의 미푸시 커밋(이번에는 169개)이 깔린다. push 전 `node tools/git-storage-check.cjs --base origin/master --head HEAD`가 「New Git blob has no inspected path」로 먼저 멈춰 알았다(`git merge-base --is-ancestor <바탕> origin/master`가 거짓). 가지 이름을 `…-localbase`로 바꿔 남기고 origin/master에서 같은 이름을 새로 떠 내 커밋만 cherry-pick한 뒤, 생성 묶음은 새 바탕 원본으로 다시 만든다 — 옛 바탕 묶음에는 남의 미푸시 원본(`ebd905be5`의 `validateIncrement` 등)이 섞여 있었다. 워크트리는 처음부터 `origin/master`에서 뜨는 편이 낫다.

### 남의 미푸시 커밋이 같은 줄을 고쳤으면 `restack.py`가 그 파일에서 멈춘다
- 증상: 트랙 한 줄의 내 문장만 바꾼 커밋을 다시 쌓는데 `restack.py`가 `docs/_ops/트랙.md`에서 「병합 FAIL」로 멈췄다. 아무것도 올라가지 않았다(10-17).
- 원인: 다른 세션의 로컬 전용 커밋이 같은 줄의 다른 구절을 지워서, 내 커밋의 부모 판과 origin 판이 그 줄에서 다르다. 줄 단위 3방향으로는 두 수정을 가를 수 없다.
- 고침: 그 파일만 origin 판 blob에 내 문장 교체를 적용한다. 옛 문장이 origin 판에 꼭 한 번 있고 바뀐 줄이 하나일 때만 쓴다. 다른 경로는 origin 판이 내 부모 판과 같을 때만 내 판을 넣고, 다르면 멈춘다. 로컬 병합의 트리는 로컬 그대로 둔다(로컬이 남의 수정과 내 문장을 다 품는다). `tools/내커밋.js 올리기`도 이 경우 「내가 고친 줄이 원격 판에 그대로 없다」로 멈춘다(문장 단위 옮기기는 넣지 않았다) — 그 파일만 이 고침대로 손으로 한다.
- 다시 확인: 올린 커밋의 바뀐 파일이 로컬 커밋과 같고 트랙은 한 줄이며, 로컬 병합 전후 `git diff --stat`이 비어 있다.
- 10-19 덧붙임(`내커밋.js 올리기`로 나눠 올리기): 도구는 가지에 없는 커밋 번호도 받는다(`rev-parse --verify`, 부모 하나). 그래서 별도 인덱스와 `commit-tree`로 커밋 둘을 만들어 `올리기 A B`에 함께 넘긴다. 가지는 움직이지 않는다. A는 내 커밋에서 걸린 파일만 부모 판으로 되돌린 트리로, 같은 부모·같은 메시지로 만든다. B는 origin 머리를 부모로, 그 파일만 「origin 판 + 내 문장」으로 바꿔 만든다. 이렇게 넘기면 나머지 경로는 도구가 다시 쌓고, 검사(내 줄만·빠짐 없음·줄끝·용량)도 그대로 돈다. 10-19 Argon 커밋 `557316313`의 `docs/현장노트/AI_CLI.md` 「쓴 AI」 줄에서 썼다(origin `f36015517`·`4c3e47f30`). 확인: 올린 머리에서 그 파일을 뺀 경로의 blob이 로컬 커밋과 같은지(34경로 일치), 그 파일에 내 문장과 origin 구절이 둘 다 있는지 본다.
- 10-19 덧붙임(고친 줄이 origin에 아예 없을 때): 내가 고친 줄이 다른 세션의 아직 안 올린 커밋에만 있는 줄이면(origin 판에 그 항목 자체가 없으면) 그 고침은 B에 넣을 수 없다 — 남의 줄을 같이 올리게 된다. B에는 origin 판에 있는 줄에 얹을 수 있는 조각만 넣고(새 절·새 줄), 나머지 고침은 로컬 커밋에 남긴다. 그 항목을 만든 커밋이 origin에 올라간 뒤 같은 로컬 커밋을 다시 `올리기`하면 남은 줄만 간다. 10-19 공용 제작 도구 `73504a970`의 `영상_ffmpeg_자막.md`(머리 절 9줄만 `358a7ecd1`로 올림, 세 항목 한 줄씩은 로컬). 확인: 올린 머리에서 그 파일을 뺀 경로의 blob이 로컬 커밋과 같은지, `git diff` 줄 수가 로컬 커밋보다 걸린 줄만큼 적은지 본다.
- 10-19 덧붙임(코드 커밋 밑에 남의 미푸시 코드 줄기가 깔렸을 때): `올리기`가 내 코드 파일마다 「원격 판과 n곳이 겹친다 — 코드·데이터 파일은 손으로 합친다」로 멈추면 `git log --oneline origin/master..HEAD -- <그 파일들>`로 밑의 줄기부터 본다. 10-19 PULSE 캐스팅북 커밋(`712fc8c87`·`e1c45e05a`·`17db1ebcd`) 밑에는 운영에는 나갔지만 origin/master에 없는 `02f7c9593`(10-18 구조 판, origin에는 codex 가지에만)·`791d98127`(고객 검수 고침)이 있었고, 둘을 같이 넘겨도 `791d98127`이 「origin에 없는 파일을 고쳤다」(`casting-production.test.mjs`, 더 앞의 미푸시 커밋이 만든 파일)로 또 멈춰 줄기가 더 깊었다. 손으로 합치면 origin의 옛 화면 위에 시험하지 않은 판이 생기고, 문서 커밋만 올리면 앞 절이 없는 origin 문서에서 다른 절 머리 바로 밑 같은 엉뚱한 자리에 끼워진다(미리 보기의 「자리 맞춤」 줄로 보인다). 유호님은 「master 맞추기 때 함께」를 골랐다(앞 줄기까지 올리기·따로 가지 보관 대신) — 아무것도 올리지 않고 트랙에 남긴다.
- 10-20 덧붙임(현장 노트 「쓴 AI」 머리말): 가지·공용 master에 묵힌 내 커밋이 현장 노트 머리말을 고쳤으면, 그사이 다른 세션들이 그 줄에 항목을 덧붙여 `올리기`가 「내가 고친 줄이 원격 판에 그대로 없다」로 멈춘다(아무것도 안 올라감). origin/master에서 임시 워크트리를 떠서 내 커밋들의 차이를 경로마다 3방향으로 얹는다. 3방향은 세 판을 다 blob(LF)으로 꺼내 한다 — 체크아웃된 CRLF 작업본 파일에 `git show` 판을 대면 모든 줄이 부딪힌다. 머리말은 「마지막 확인」 = origin이 바탕 그대로면 내 줄, 「쓴 AI」 = origin 줄 + 내 항목으로 풀고 곧바로 커밋·`올리기`한다. 몇 분 사이에 또 바뀌어 한 번 더 막혔다. 최신 origin 위에서 다시 쌓아 바로 올리는 것을 한 스크립트로 묶자 첫 번째에 올라갔다(`855e68eaa`, 노트 폴더 `local_85757b09…/master맞추기_20261020_보강/`).

### 로컬 master에 남의 미푸시 커밋이 있어 origin과 갈라졌다
- 증상: 10-18 「로컬 master도 origin이랑 맞춰줘」 때 로컬만 69커밋(다른 세션 미푸시·이미 restack으로 올린 커밋의 옛 번호 포함), origin만 43커밋이었다. 빨리감기가 안 되고, master를 origin으로 옮기면 남의 미푸시 커밋이 가지에서 빠진다.
- 원인: 세션마다 내 커밋만 origin에 다시 쌓아 올리고(restack) 로컬 병합은 「origin has other commits」로 건너뛰어, 같은 내용이 양쪽에 다른 번호로 쌓였다.
- 고침: `node tools/master맞추기.js`로 맞춘다(10-19, 미리 보기 → `--실행 <지문>`, push 없음). 미리 보기가 origin을 fetch해 방법을 고른다 — 빨리감기(로컬이 origin 조상) · 빠른 길(origin에만 있는 커밋마다 같은 작성자·제목의 로컬 커밋이 있고 그 변경이 로컬에 다 있으면 병합 트리 = 로컬 트리, 작업본·공용 인덱스는 그대로) · 병합(로컬 트리에 origin만 바꾼 경로를 얹고, 양쪽이 바꾼 경로는 양쪽 이력에 함께 나오는 가장 최근 판 → 갈라진 곳 순으로 바탕을 골라 3방향). 겹친 곳은 한쪽이 다른 쪽 변경을 품으면 그쪽, 문서는 같은 자리에 양쪽이 끼운 줄을 2방향으로 맞춰 같은 줄은 한 번·따로 더한 줄은 둘 다 두고, 같은 머리(앞 40자)의 줄이나 같은 바탕 줄을 둘 다 고친 줄은 짝지어 한 줄로(한쪽이 통째로 품으면 긴 쪽, 「 · 」 항목 목록에 항목을 끼우기만 했으면 항목 단위로 — 「쓴 AI」 머리말처럼 다시 쌓으며 차례·자리가 바뀐 같은 항목은 한 번, 그 밖에는 양쪽이 바탕 낱말을 그대로 둔 채 덧붙이기만 했을 때 낱말 단위로. 같은 자리에 서로 다른 낱말(「공개」·「비공개」), 같은 글을 서로 다른 자리에, 바탕이 문장으로 끝나지 않았는데 둘 다 마지막 낱말 뒤에 이어 씀, 한쪽이 괄호·백틱 짝을 바꾼 목록 줄, 같은 문장·항목 조각이 두 번 들어가는 합침은 멈춘다. 줄 끝 공백은 따로 3방향), `merge=union` 경로는 합집합까지만 푼다. 합친 문서에 양쪽이 같은 절·행을 서로 다른 자리에 ### 다시 쌓기를 파이프로 거르면 충돌을 못 보고 push까지 돈다 (2026-10-19 Claude)
- 증상: 격리 작업본에서 `git rebase origin/master 2>&1 | tail -1 && … && git push origin HEAD:master`를 한 줄로 돌렸더니, 둘째 커밋이 충돌로 멈췄는데도 push가 돌아 첫 커밋만 올라갔다(`d6714e877`, 올리려던 커밋이라 피해는 없었다).
- 원인: 파이프의 종료 코드는 마지막 명령(`tail`)의 것이라 `&&`가 rebase 실패를 못 봤다. rebase가 멈춘 동안 HEAD는 그때까지 다시 쌓은 커밋을 가리킨다.
- 고침: rebase·merge·push처럼 멈출 수 있는 git 명령은 파이프 없이 돌려 종료 코드를 받거나(`git rebase …; rc=$?`), 한 줄 앞에 `set -o pipefail`을 건다. push 전에 `git status`에 「rebase in progress」가 없는지 본다.
- 다시 확인: Git Bash에서 `false | tail -1 && echo 돎`은 「돎」을 찍고, `set -o pipefail; false | tail -1 && echo 돎`은 안 찍는다.

### 공용 작업본 따라가기가 남의 미커밋에 막힌 동안 origin이 고친 공용 문서 줄을 다시 고칠 때는 origin 최신판의 임시 작업본에서 올린다 (2026-10-21 Claude)

- 고침: 백업 폴더 `파일/0`(`목록.json`의 경로)이 바꾸기 전 공용 파일이다. 줄끝을 LF로 맞춰 `git show <B>:<경로>`와 견주면 남의 미커밋만 보인다(이번에는 한 줄). 지금 작업 파일이 T 판 그대로인지(`git hash-object` = `git rev-parse HEAD:<경로>`) 본 뒤 `git merge-file -p <T 판> <B 판> <백업>`으로 얹고, 원래 줄끝(CRLF)으로 같은 폴더 임시 파일에 써서 바꿔 넣었다. 같은 날 도구도 고쳤다 — `tools/lib/git-publish-core.cjs`의 `바꿔쓰기()`가 공통 `replaceFile`(`tools/lib/backup-primitives.cjs`, EPERM·EACCES·EBUSY면 최대 20번 · 약 9.5초)로 다시 하고, 끝내 못 쓰면 쓰려던 3방향 결과를 백업 `결과/<차례>`에 남겨 「주의」에 「파일이 풀리면 <그 파일>을 그 자리에 복사한다」를 보인다(지금 파일은 origin 판이라는 것도 함께).
- 다시 확인: 되살린 뒤 공용 작업본 `git diff -- <경로>`가 그 세션의 줄뿐이고, 줄끝을 빼면 내용이 「T 판 + 백업의 B → 백업 차이」와 같다. `주의:`에 「미커밋을 얹은 결과를 쓰지 못했다」가 보이면 그 자리에서 안내된 `결과/<차례>`를 복사하고 이 확인을 한다. 도구 쪽은 `node --test --test-name-pattern="EPERM|끝내 못 쓰면" tests/바로올리기.test.js`(잠깐 EPERM이면 다시 해서 지킴 · 끝내 못 쓰면 결과를 남기고 알림 — 둘 다 고치기 전 도구에서 실패).

### 공용 작업본 HEAD가 내 앞 커밋보다 뒤에 있으면 `바로올리기`가 그 커밋까지 내 변경으로 보고 「원격 판과 N곳이 겹친다」로 멈춘다 (2026-10-22 Claude)
- 증상: 10-22 문의 지우기 델타 고침(2파일)을 `node tools/바로올리기.js <두 경로> -m … --실행`하니 「[멈춤] origin 위에 얹지 못한 경로가 있다 — 아무것도 올리지 않았다 … 원격 판과 2곳이 겹친다」. 그 두 파일을 origin에서 고친 남은 없었다(`git log c9131369d..origin/master -- <경로>` 빈 결과).
- 원인: 공용 작업본 HEAD(`a60538dba`)가 내가 바로 앞에 올린 `c9131369d`보다 앞선 판이었다. 그 push 뒤 따라가기가 남의 미커밋(PATH 문서·결정·트랙·마을 설계)과 origin 변경이 겹쳐 아무것도 옮기지 못했다(`따라가기` 미리 보기도 같은 멈춤). 도구는 HEAD 대비 차이를 내 변경으로 보므로, 이미 origin에 있는 내 앞 커밋까지 다시 얹으려다 겹쳤다.
- 고침: 공용 인덱스·HEAD는 그대로 두고 임시 인덱스로 origin 위에 내 경로만 얹었다 — `GIT_INDEX_FILE=<임시> git read-tree origin/master` → 경로마다 `git hash-object -w --path=<경로> <경로>`(줄끝 정규화 — 이 저장소 blob은 LF라 `--no-filters`로 넣으면 작업본 CRLF가 그대로 들어가 파일 전체가 바뀐 커밋이 된다, 첫 시도 +927/−893) → `git update-index --cacheinfo 100644,<blob>,<경로>` → `write-tree` → `commit-tree -p origin/master -F <메시지>` → `node tools/공개검사.js --바탕 <O> --머리 <C>` · `node tools/git-storage-check.cjs --base <O> --head <C>` → `git push origin <C>:refs/heads/master`(거절되면 다시 받아 다시 만든다, 그 사이 내 경로를 남이 고쳤으면 멈춘다).
- 다시 확인: `git diff --stat <O> <C>`가 내 줄 수만(+43/−9), 새 blob의 CRLF 0, `git merge-base --is-ancestor <C> origin/master`(10-22 `70c0fe285`).

## 워크트리·연결 폴더·공간 정리

### junction이 든 워크트리를 통째로 지우면 공용 node_modules가 지워질 수 있다
- 증상: `git worktree remove --force`가 등록만 풀고 폴더를 남긴다. 남은 폴더를 `rm -rf`·`Remove-Item -Recurse`로 지우면 링크를 따라 공용 작업본의 node_modules까지 지울 수 있다(모든 세션의 빌드가 멈춤). `cmd /c rmdir`은 하네스가 막는다.
- 원인: 빌드·시험용으로 `node_modules`를 공용 작업본에 잇는 junction을 만들어 둔다.
- 고침: PowerShell에서 `(Get-Item <p> -Force).LinkType -eq 'Junction'`을 보고 `[System.IO.Directory]::Delete(<p>, $false)`로 링크만 지운다. 그다음 남은 폴더를 지운다.
- 다시 확인: 지우기 전 `Get-ChildItem -Recurse -Force | Where-Object LinkType`이 비었고, 끝난 뒤 공용 쪽에서 esbuild가 돈다(`node tools/build-world-life.mjs --check`). 10-20 밤 `Documents/SYNK-worktrees`의 작업트리 둘에도 공용 `node_modules`·`desktop/node_modules`·`experiences/synk-account/node_modules`로 가는 junction이 셋씩 있었다(`git status --ignored`에는 `!! node_modules/`로만 보인다). 링크만 끊고 나니 `git worktree remove`(--force 없이)가 폴더까지 지웠다. 공용 쪽 항목 수(9·233·7)와 `require.resolve('esbuild')`는 그대로였다.

### 사본(거울)의 junction 폴더를 타고 시험·패치가 공용 작업본에 쓴다
- 증상: 격리 사본에서 고친 시험 맞춤 패치가 공용 `verify-*.mjs`에 들어갔고, 출력 위치를 박아 둔 시험이 GPT 증거 폴더 14개를 덮었다(10-13).
- 원인: 「실제 경로 사슬 + 나머지는 junction」 사본에서 junction인 폴더는 공용 작업본 그 자체다. Node는 그 경로를 실제 경로로 풀어 공용 코드를 돌린다.
- 고침: 사본에서 시험·패치하기 전에 쓸 폴더(`qa`, `docs/_ops`, 출력 폴더)가 junction인지 보고 실제 폴더로 끊는다. 출력 위치를 박아 둔 진입 파일 대신 본 시험 파일을 환경 변수(출력 폴더)로 직접 돌린다.
- 다시 확인: `fsutil reparsepoint query <폴더>`나 `fs.realpathSync`로 쓸 폴더가 사본 안이다.

### 워크트리의 비추적 결과물은 워크트리를 지울 때 함께 사라진다
- 증상: 데스크톱 앱에서 워크트리 세션을 지우자 그 워크트리의 비추적 파일(정지컷·도구·인계문)이 모두 사라지고 `.gitignore` 대상만 남았다(10-14, 휴지통에도 없음).
- 원인: 세션·워크트리 정리가 추적되지 않는 파일을 지운다. 사용자가 앱에서 하는 일이라 작업 세션은 미리 알 수 없다.
- 고침: 워크트리에서 오래 일하면 결과물을 커밋하거나 메인 `.tmp/`로 옮겨 둔다. 정리를 권하기 전에 워크트리마다 `git -C <워크트리> status`의 `??`를 보고 알린다.
- 다시 확인: 정리 후보 워크트리의 `git status --porcelain | grep '^??'`가 비었다.

### 보관한 세션의 깨끗한 앱 작업트리는 다음 새 세션이 다시 쓸 자리라, 손으로 지워도 공간이 늘지 않는다 (2026-10-20)
- 증상: 10-20 밤 공간 정리 후보로 「세션 보관됨·깨끗함」인 `.claude/worktrees/serene-matsumoto-6be923`을 골랐다. 그런데 지우기 직전에 보니 HEAD가 보관 직후(21:38) 분리 상태로 바뀌어 있었고, 앱 저장 공간 보고(`get_storage_usage`)는 이것을 「새 세션용으로 남겨 둔 작업트리 1개(4.1GB)」로 셌다.
- 원인: 앱은 깨끗한 작업트리를 보관된 세션에서 떼어 재사용 대기로 두고, 다음 새 세션에 다시 쓰거나 스스로 치운다. 미커밋 변경이 있는 것만 「보관 뒤에도 남긴 작업트리」(kept_after_archive)로 따로 센다.
- 고침: 재사용 대기 작업트리는 지우지 않는다. 지우면 다음 새 세션이 4.1GB를 새로 만들 뿐이다. 공간을 실제로 늘리는 것은 앱 밖에서 만든 작업트리(`Documents/SYNK-worktrees` 등), 일이 끝난 세션 보관, 미커밋 변경을 살린 뒤의 `discard_kept_worktree`다.
- 다시 확인: 정리 후보를 고르기 전에 `get_storage_usage`의 `kept_ready_count`·`kept_after_archive`와 그 작업트리의 `.git/worktrees/<이름>/HEAD`(분리 상태인지)를 본다.

### 공간 정리가 추적 파일을 지운다
- 증상: PC 공간 정리 뒤 시험이 「파일 없음」으로 깨진다. 10-03 정리가 추적 파일 185개(142MB)를, 10-10 정리가 메인 추적 파일 217개 + 워크트리 10곳 약 8,900개를 지웠다(같은 SHA가 Drive에 있으면 로컬 삭제). 10-14에는 폴더 통째 삭제가 안쪽에 둔 git 클론까지 지웠다.
- 원인: 정리 목록이 `git ls-files`를 거르지 않았다. 추적 파일은 이미 `.git`에 있어 지워도 백업이 늘지 않는데, 작업본이 「삭제됨」으로 남아 누가 `git add -A`·`commit -a`를 하면 그 삭제가 저장소에 들어간다. 맨 위 `.git`만 보고 거르면 한 단계 안의 클론은 못 거른다.
- 고침: 정리 목록에서 `git ls-files` 경로를 뺀다. 추적 파일이 정말 크면 지우지 말고 sparse-checkout으로 작업본에서만 뺀다. 폴더를 통째로 지우기 전에 그 안 어디에든 `.git`(폴더든 파일이든)이 있는지 보고, 있으면 그 아래는 빼고 따로 본다. 지워진 추적 파일은 `git status --porcelain | grep '^ D'` 목록을 `GIT_LITERAL_PATHSPECS=1 git restore --worktree --pathspec-from-file=<목록>`으로 되살린다(공용 인덱스는 그대로). 정리 기록(`removed*.jsonl`의 경로·sha256)이 있으면 바이트까지 맞춘다: 별도 인덱스(`read-tree HEAD`)의 `checkout-index`(체크아웃 판, autocrlf 적용)와 HEAD blob(LF) 가운데 기록된 해시와 같은 쪽을 쓴다(10-10 349개). 내용이 같아도 인덱스에 적힌 크기와 다르면 status가 ` M`으로 남으니, 지우기 직전 바이트 그대로 되살린다(`git ls-files --debug`의 size로 확인). 단 낡은 것을 일부러 없앤 정리라면 되살리지 않는다 — 정리 기록·커밋·진행 중인 GPT 작업으로 가리고, 헷갈리면 유호님께 여쭌다.
- 다시 확인: 정리 뒤 `GIT_OPTIONAL_LOCKS=0 git ls-files --deleted | wc -l`이 0이다(10-17 0). 정리가 아직 돌고 있을 수 있으니 정리 기록 파일의 수정 시각이 멈췄는지도 본다.

### 앱이 갈라진 로컬 master에서 뜬 워크트리는 바탕 맞추기가 공용 문서 충돌로 멈춘다 (2026-10-20 Claude)
- 증상: 새 앱 워크트리(`claude/nice-yalow-6c2596`)의 바탕이 로컬 master `832e4ccbf`였고, origin/master를 받으려고 `sync_with_base_branch`를 부르자 `AGENTS.md`·결정·트랙·현장노트 셋, 모두 6파일 충돌로 병합이 멈췄다. `git rev-list --count origin/master..HEAD`가 350이었다.
- 원인: 앱은 워크트리를 공용 작업본의 로컬 master에서 뜬다. 로컬 master는 남의 미푸시 커밋과, `올리기`로 origin에 다시 쌓기 전의 옛 번호 커밋을 품어 origin과 갈라져 있다. 같은 줄이 양쪽에 다른 번호로 있으니 공용 문서가 겹친다.
- 고침: 이 가지에 내 커밋이 아직 없으면 맞추기를 그만두고(`sync_with_base_branch`의 `abort: true`) 가지를 origin/master로 옮긴다 — `git branch --contains <지금 머리>`에 `master`가 있어 옛 머리가 로컬 master에 그대로 남는지 먼저 보고 `git reset --hard origin/master`. 일하는 사이 origin이 내 경로(생성 묶음 포함)를 또 바꾸면, 옛 머리를 적어 두고 `git reset --hard origin/master` → `git restore --source=<옛 머리> --worktree -- <내 경로들>`(스테이징 없이 — `내커밋.js 커밋`은 공용 인덱스에 내 경로의 스테이징이 있으면 멈춘다) → 생성 묶음은 그 도구의 `--check`로 새 바탕 원천과 맞는지 보고 → `내커밋.js 커밋`으로 다시 쌓는다. 공용 문서의 내 줄은 새 판에 손으로 다시 넣는다.
- 다시 확인: `git rev-list --count HEAD..origin/master`가 0이고, `git diff --stat <옛 머리> HEAD -- <내 경로들>`이 비어 있다(10-20: 코드 14경로 같음, 다른 차이는 그사이 들어온 남의 커밋 다섯 파일뿐).
- 10-20 덧붙임(자동 모드에서 옮기기가 막힐 때, Claude): 내 위치 세션(`.claude/worktrees/magical-borg-0ea51c`, 로컬 master에서 떠 origin보다 366 앞·47 뒤, 작업본 깨끗)에서는 `git reset --hard origin/master`·`git switch -c <새 가지> origin/master`·`git config --worktree core.autocrlf false`가 모두 자동 모드 판정기에 「Irreversible Local Destruction」으로 거절됐다. 세션은 그 워크트리에 묶여 Edit·Write가 다른 워크트리 파일을 쓰지 않는다. 덮지 않고 새 워크트리를 더해 옮겼다 — `git -c core.autocrlf=false worktree add -b <가지> .claude/worktrees/<이름> origin/master`(한 번만 쓰는 `-c`라 공용 설정은 그대로, 꺼낸 파일은 LF) → `EnterWorktree`에 `path`로 세션을 옮긴다 → 그 워크트리에서 파일을 쓰는 git 명령(cherry-pick·rebase)에도 `-c core.autocrlf=false`. 워크트리로 격리된 세션의 Bash는 값이 실행 중에 정해지는 인자(`$VAR`·`for`, 파이프에 섞인 git)를 「안에 머무는지 확인할 수 없다」며 돌리지 않으니, 시험 파일 목록처럼 인자를 모으는 일은 노드 스크립트가 모아 `spawnSync`로 돌린다. 확인: 새 워크트리에서 `git ls-files --eol`의 `w/crlf` 28개가 모두 blob 자체가 CRLF(`i/crlf`)이고 `git rev-parse HEAD`가 그때의 origin/master(`a6060676f`)였다.

### 일부 경로만 꺼낸 사본에서 `git stash`를 쓰면 고친 파일이 stash에 갇힌다 (2026-10-19)
- 증상: `clone --no-checkout` 뒤 `git checkout <rev> -- site-v10 qa …`로 꺼낸 사본에서 기준 판 시험을 돌리려고 `git stash` → `git stash pop`을 했더니 「The stash entry is kept」로 끝나고, 고친 원고가 모두 원래 판으로 돌아가 있었다.

- 놓친 것(10-21 저녁, 효율 점검 세션): 지운 넷 중 `ci-backup-incremental`은 보관 전인 「CI·백업은 바뀐 것만」 세션이 20:56 기록을 올리려 남겨 둔 자리였고, 「다른 프로세스가 연 빈 폴더」는 그 세션 셸의 자리였다(커밋은 origin에 있어 잃은 것은 없고, 그 세션은 origin 최신에서 새 가지로 옮겼다). 깨끗함·origin 커밋만으로는 「아직 쓰는 중」을 가르지 못한다. 세션이 손으로 만든 작업트리(`git worktree add -b <가지> .claude/worktrees/<이름>`)는 앱이 주인을 모르니, 고르기 전에 `search_session_transcripts`로 그 이름을 찾는다 — `git worktree list` 출력에만 나온 세션은 빼고, 보관 전 세션이 그 경로에서 일한 흔적(`cd`·`-C <경로>`·cwd)이 있으면 후보에서 빼거나 그 세션에 먼저 묻는다. 손으로 만든 세션은 다 쓰면 그 자리에서 지운다.
- 10-23 덧붙임: `platform-copy-audit-20261021`(8GB)은 깨끗하고 커밋도 origin에 있었지만, 그 작업트리의 git 무시 `.tmp/platform-copy-pc-release-20261022`·`.tmp/pub-20261022/`를 지금 도는 회사 릴리스 세션 셋이 경로로 쓰고 있어 유호님 승인 뒤에도 뺐다 — `search_session_transcripts`로 작업트리 이름을 찾아서 알았다. 승인이 있어도 지우기 직전에 이 검색을 한 번 더 한다.

### 「가볍게」로 미디어 폴더를 뺀 워크트리는 앱 바탕 맞추기가 「sparse checkout이라 합치지 않는다」로 거절한다 — 내 커밋이 다 올라갔으면 fast-forward로 (2026-10-22 Claude)
- 증상: 기존 게임 문항 고침 67 마감에서 트랙·결정을 고치기 전에 origin을 받으려고 `sync_with_base_branch`(base master)를 부르자 「The worktree is a sparse checkout … so the app won't merge into it. Merge yourself」로 거절됐다.
- 원인: 워크트리 시작 때 `node tools/바로올리기.js 가볍게 --실행`이 큰 미디어 폴더를 sparse checkout으로 뺀다. 앱은 희소 작업본에는 병합하지 않는다.
- 고침: 바로올리기로 올린 뒤라 가지 머리가 origin/master의 조상이고 작업본이 깨끗하면(`git merge-base --is-ancestor HEAD origin/master`, `git status --short`가 빔) `git merge --ff-only origin/master`로 옮긴다. 공용 문서는 그다음에 고친다. 내 커밋이 origin에 없으면 이 길을 쓰지 않는다.
- 다시 확인: `git log -1`이 origin/master 머리와 같고 `git status --short`가 비어 있다(10-22 `a93a305ac`).

### Windows에서 누가 연 파일 하나 때문에 `read-tree -m -u`가 128로 멈추면 다른 파일은 이미 새 판으로 남는다 — 운영 사본 갱신은 origin 판과 같은 파일을 고친 것으로 보지 않는다 (2026-10-22 Claude)
- 증상: 연결 작업본에서 바뀔 추적 파일 하나를 다른 프로세스가 연 채로 `git read-tree -m -u B T`를 하면 종료 128 `error: unable to unlink old 'tools/b.js': Invalid argument`로 멈춘다. HEAD·인덱스는 B 그대로인데 다른 바뀐 파일은 이미 T 내용으로 써져 `git status`에 ` M`으로 남는다(표준 입력이 터미널이 아니면 다시 할지도 묻지 않는다). `git checkout --detach --force T`도 HEAD만 T로 가고 그 파일만 옛 내용으로 남았다(10-22 「감시 예약을 깨끗한 작업본에서」 세션이 임시 저장소로 재현).
- 원인: Windows는 열린 파일을 지우거나 바꾸지 못한다. git은 파일을 하나씩 바꾸다 멈추고 이미 쓴 파일은 되돌리지 않는다. `tools/바로올리기.js` 따라가기의 되돌리기는 백업한 「고치던 파일」만 되돌린다. 그대로면 운영 사본 갱신이 그 자국을 「누가 고친 파일」로 보고 따라가기를 멈춘 채 스스로 못 푼다.
- 고침: `tools/운영사본.js` 갱신의 「고친 파일」 판정은 작업본 내용이 origin 판과 다른 경로만 센다(`git diff --name-only <origin> -- <경로…>`). origin 판과 같은 자국은 다음 따라가기가 3방향(작업본 = origin 판)으로 그대로 맞춘다. 인덱스까지 새 판이고 HEAD만 옛 판인 끊김(시간 한도로 죽음)은 인덱스 트리와 같은 커밋으로 HEAD만 옮긴다(끊긴 따라가기 마무리).
- 다시 확인: `node --test --test-name-pattern="중간에 끊겨|끊겼으면" tests/운영사본.test.js`.

### `가볍게 --되살림 <경로>`에 파일을 주면 「되살림」으로 끝나도 그 파일이 돌아오지 않는다 — 폴더 무늬만 더한다 (2026-10-22 Claude)
- 증상: 가볍게 한 WORLD 글 손질 워크트리에서 튜터 소개 정본을 읽는 시험이 ENOENT였다. `node tools/바로올리기.js 가볍게 --되살림 docs/캐릭터/소개글_정본.json --실행`이 「되살림」으로 끝났는데 파일은 그대로 없었다.

### 공간 정리에서 `git prune --expire=3.days.ago`는 자동 모드 판정기가 「Irreversible Deletion」으로 막는다 — 같은 정리의 세션 임시 폴더·gh-artifact zip·git `tmp_*` 지우기는 지나갔다 (2026-10-24 Claude · 메모에서 옮김)
- 증상: 10-13 공간 정리에서 `git prune --expire=3.days.ago`가 실행 전에 「Irreversible Deletion」으로 거절됐다. 같은 정리의 `%TEMP%` 세션 폴더, gh-artifact zip, git이 남긴 `tmp_*` 파일 지우기는 지나갔다.
- 원인: `git prune`은 어디서도 가리키지 않는 객체를 되살릴 길 없이 지운다. 판정기는 이것을 되돌릴 수 없는 지우기로 분류했다(까닭 글은 그 이름뿐). 나머지 셋이 지나간 기준은 모른다.
- 고침: 다른 명령·나눠 돌리기로 같은 지우기를 하지 않는다. 얻을 공간부터 재고(아래), 지울 것·크기·근거를 한 줄로 보여 그 일을 이름 댄 허락을 받은 뒤 같은 명령을 다시 돌린다(위 「주인 세션 없는 작업트리를 `git worktree remove`로 지우면 자동 모드 판정기가 막는다」와 같은 길). `%TEMP%`를 나이로 쓸어 지우는 일은 10-24에 따로 막혔다([윈도우 셸](윈도우_셸.md#temp의-오래된-항목을-스크립트로-한꺼번에-지우면-자동-모드-판정기가-shared-scratch-sweep으로-막는다-2026-10-24-claude)).
- 다시 확인: 읽기만 했다 — `git count-objects -vH`가 10-24 풀린 객체 603개 22MiB · 팩 15.33GiB · `prune-packable` 0 · 찌꺼기 23개 326MiB였다. prune이 줄일 수 있는 것은 풀린 객체 몫뿐이고, 찌꺼기는 대부분 `objects/<xx>/tmp_obj_*`(객체를 쓰다 끊겨 남은 파일)다. 찌꺼기 목록에는 가볍게 한 워크트리의 `.git/worktrees/<이름>/info/sparse-checkout`도 찍히는데, 그 워크트리가 쓰는 무늬 파일이라 지우지 않는다. 판정기 결과는 지우기를 실제로 보내야 보여 다시 보지 않았다(10-24 메모에서 옮김, 다시 확인 전).

## 이력 훑기

### 큰 blob을 거른 클론에서 `git log -S`·`--find-object`가 「could not fetch」로 끝난다
- 증상: `git clone --bare --filter=blob:limit=1m`로 받은 이력(1MB 넘는 blob 1,787개 빠짐)에서 `GIT_NO_LAZY_FETCH=1 git log --all -S<값>`과 `--find-object=<blob>`이 `fatal: could not fetch <blob> from promisor remote`로 끝났다(10-17 클라우드 비밀값 점검). 환경 변수가 없으면 빠진 큰 blob을 하나씩 받으러 간다.
- 원인: 경로를 주지 않으면 모든 경로의 바뀐 blob을 읽는다(`-S`는 내용 비교, 이름 바뀜 탐지도 내용을 읽는다). 받지 않은 큰 blob에서 멈춘다. 둘 중 어느 쪽이 먼저 막혔는지는 가르지 않았다.
- 고침: 글 파일 경로로 좁히고 `--no-renames`를 붙인다: `GIT_NO_LAZY_FETCH=1 git log --all --no-renames --find-object=<blob> -- <경로>`. 이력 전체를 훑을 때는 `git rev-list --all --objects --filter=blob:limit=1m --missing=print`로 받은 blob만 골라(빠진 것은 `?`로 시작) `git cat-file --batch`로 읽는다.
- 다시 확인: 같은 클론에서 경로 없이 돌리면 fatal, 경로와 `--no-renames`를 주면 커밋 줄이 나온다.

### PC에만 있는 파일을 읽는 시험이 클라우드 클론에서 실패한다
- 증상: 클라우드 클론에서 `미니게임_목소리`(voice-request.json), `learning-hub/server`(입문 게임 파일), `path-travel-server`(계획 화면 파일)가 404·ENOENT로 실패했다(10-17).
- 원인: 10-14 「pending changes」 일괄 커밋들이 바뀐 파일이 import하는 새 파일만 넣어, 시험이 부르는 파일 일부가 PC 작업본에만 남았다.
- 고침: `git log --all --oneline -- <경로>`로 origin의 다른 가지에 있는지 먼저 찾는다(입문 게임 277개는 `origin/codex/beginner-games-finish-20261010`에 있었다). 어디에도 없으면 PC에서 커밋한다(path-travel 계획 화면 8개·장소 사진 13장).
- 다시 확인: PC 작업본에서 `git status --short experiences/path-travel`이 비어 있다.
- 덧붙임(10-21 Claude): 워크트리(v2 기본)도 같은 꼴로 빨갛다 — `tests/라디오오버레이층.test.js`는 git 밖 굽기 원본 PNG(`docs/라디오/DJ장면_20261019/구운판/*.png`, 원본창고)를 CI에서는 건너뛰고(`tests/_git밖.js`의 `CI에없는로컬자료`) 개발 PC에서는 재도록 짰는데, 워크트리에는 그 원본이 없어 ENOENT로 실패한다. 고칠 시험이 아니다 — 원본이 있는 공용 작업본에서 돌리면 5/5다(10-21). 워크트리에서 재야 하면 그 PNG만 공용 작업본에서 복사해 온다.


### 임시 index 안에서 실제 공용 index 경로를 물으면 임시 파일이 돌아온다 (2026-10-20 GPT)
- 증상: exact-path 커밋 가드를 임시 index에서 시험한 뒤 공용 index 불변 검사만 실패했다.
- 원인: `GIT_INDEX_FILE`을 설정한 환경의 `git rev-parse --git-path index`는 공용 index가 아니라 해당 임시 index를 반환한다.
- 고침: 원래 환경에서 `GIT_INDEX_FILE`만 제거하고 실제 worktree index 경로를 먼저 구했다. 그 파일의 앞뒤 SHA를 대조하며, 가드는 임시 index 환경에서만 실행했다.
- 다시 확인: Talk 자동화 8개 경로의 가드를 재실행해 통과했고 실제 공용 index SHA가 유지됐다. `.tmp/business-automation-20261020/talk-index-guard-knsBgG/result.json`을 확인한다.

### 누가 쓴 줄인지 `git blame`·Co-Authored-By로 가르면 통합·들여오기 커밋 때문에 틀린다 (2026-10-20 Claude)
- 증상: Workspace 화면의 GPT 흔적을 셀 때 메신저 `voice.js`가 blame으로는 전부 GPT 커밋 `b7a5e24a5`(10-19 「Integrate publication performance and secure company voice」)였다. 실제로는 Claude 커밋 `5ba0721fb`가 만든 파일에 GPT가 7줄을 더한 것이었다. 반대로 10-02 「originals」 커밋(`59cabdb80`)은 Claude 트레일러가 붙었지만 git 밖에 있던 GPT 판을 들여온 것이라, 트레일러로 세면 GPT 글이 Claude 몫으로 잡혔다(메신저 `app.js` 보이는 글 747개 중 732개가 GPT 원문인데 blame 줄로는 43%).
- 원인: blame은 첫 부모 이력만 따라간다. 다른 가지 내용을 부모 하나짜리 커밋으로 한 번에 들여오면 그 커밋이 작성자가 된다. 트레일러는 커밋한 세션만 알려 주고, 내용을 누가 썼는지는 모른다.
- 고침: 줄(또는 보이는 문장)마다 `git log --all --follow --name-only -- <파일>`의 모든 판을 오래된 순으로 읽어 그 내용이 처음 나타난 커밋을 찾는다. 들여오기 커밋(「originals」·「기준선 사본」·「GPT 제작 보존」)은 메시지로 따로 갈라 둔다.
- 다시 확인: `git log --all --format='%h %s' -- tools/company-messenger/public/voice.js`의 맨 아래가 `5ba0721fb`(Claude)인데 `git blame -w`는 모든 줄을 `b7a5e24a5`로 보인다.

### 고정 문자열 수천 개를 `git grep -F -f`로 찾으면 10분이 지나도 끝나지 않는다 (2026-10-21 Claude)
- 증상: 10-21 공용 작업본 미추적 파일 이름 2,391개를 패턴 파일로 `git grep -I -n -F -f <패턴> origin/master -- '*.md' '*.js' …`에 넘기자 10분 시한에도 끝나지 않았다(git 하나가 292MB를 잡고 돌았다).
- 원인: 모른다(패턴이 많으면 줄마다 패턴을 하나씩 대 보는 쪽으로 가는 것으로 보인다). 같은 자료를 Node로 읽으면 14초였다.
- 고침: `git ls-tree -r -l origin/master`로 글 blob 목록(16,232개·473MB)을 만들어 `git cat-file --batch`로 한 번에 읽고, 줄을 경로 꼴 낱말로 쪼개 「파일 이름 → 찾는 경로」 표에서 찾았다. 상대 링크는 문서 폴더 기준으로 풀어 맞춘다. 스크립트는 공유 노트 `미추적판정_20261021/refs.cjs`.
- 다시 확인: 같은 패턴 파일로 `timeout 60 git grep -c -F -f <패턴> origin/master -- '*.md'`가 60초 안에 끝나는지 본다.
