> 마지막 확인: 2026-10-17(도구 폴더·회선 값을 새 노트북에서 다시 봄. 올림 속도 항목은 10-03·10-14 옛 노트북 실측)
> 쓴 AI: Claude Code·GPT(Codex) — 누가 언제 무엇을 더했는지는 [지난 기록](지난기록/백업_업로드.md#쓴-기록)에 있다.

어느 계정·폴더에 원본을 둘지는 [AI 운영 원칙](../AI_운영원칙.md)의 역할 표·[결정 표](../_ops/결정.md), 저장소 자산 보관은 [Git 자산 보관](../_ops/github-storage/README.md)이 정한다. 지우기 전 확인은 [git 노트의 공간 정리 항목](git_줄끝_잠금.md#공간-정리가-추적-파일을-지운다)을 따른다. 여기는 수백 MB가 넘는 백업·업로드를 할 때 겪은 함정이다. 틀은 [README](README.md)를 따른다.

지금까지의 Drive 백업 짜임: 09-26·09-30·10-01·10-03·10-14 백업이 모두 Drive 루트의 `PC_백업_YYYYMMDD/` 아래에 원래 경로대로 파일 하나씩 있다. 그래서 다음 백업은 Drive 전체 목록의 `md5Checksum`+`size`와 대조해 빠진 것만 올린다. 10-03 `복원목록.json`은 30,063개 모두의 위치를 적고, `되살리기.py`는 sha256으로 확인하며 받는다. 다른 원본 폴더를 올릴 때는 10-14 도구 셋을 복사해 `BASE`·`TOP`만 바꾼다. 올리기 전에는 Drive 자격(`tools/company-messenger/data/drive-storage.json`의 활성 연결)이 원본을 둘 계정인지 확인한다. 백업 뒤 로컬을 지울 때는 10-14 `이어서_지우기.py`처럼 업로드 끝을 기다린 뒤 Drive를 다시 대조하고, 되살리기 시험 3개를 받아 보고, 로컬을 다시 해시해 맞는 파일만 지운다. OneDrive로 보내려면 로컬 사본이 먼저 있어야 하니, 큰 것은 Drive API로 원본에서 바로 올린다.

## Drive 올리기·대조

### 숨김 백업 프로세스도 앱 재시작 때 종료된다
- 증상: 10-18 Codex 재시작 뒤 숨김 `pythonw`의 미디어·DB 보완 실행이 사라지고 heartbeat가 13:13에서 멈췄다. 업로드 완료 영수증 504건은 남아 있었다.
- 원인: 이 실행 환경에서는 `Start-Process -WindowStyle Hidden`만으로 앱의 프로세스 수명에서 완전히 독립하지 못했다.
- 고침: 긴 실행은 등록된 Windows 예약 작업에서 시작한다. `backup-command.py`가 창 없이 자식을 실행하고 종료값을 예약에 전달한다. 중복 실행은 OS/PID 잠금으로 막고 콘텐츠 지문 영수증으로 이어받아 이전 완료 파일을 재전송하지 않는다.
- 다시 확인: 13:18 `SYNK 미디어 원본 백업`·`SYNK 오늘 DB 백업 보완`을 작업 스케줄러에서 시작해 Running과 새로운 heartbeat를 확인했다. 앱을 일부러 다시 꺼서 재현하지는 않았다. 최종 완료는 해당 실행의 원격 검증 영수증을 별도로 확인한다.

### 같은 원본을 두 세션이 동시에 올린다
- 증상: 10-03 새벽 두 Claude 세션이 같은 미디어를 동시에 Drive에 올렸다. 한쪽은 파일 하나씩·속도 상한을 두고, 다른 쪽은 zip 묶음·상한 없이 올렸다. 상대 세션의 커밋 제목(「미디어 원본 Drive 백업 진행 위치」)을 보고 27묶음(0.88GB)에서 멈췄다. 그날 백업 세션이 넷이나 겹쳤다.
- 원인: 시작하기 전에 같은 일을 하는 다른 세션·GPT 작업이 있는지 보지 않았다.
- 고침: 수백 MB가 넘는 업로드·다운로드 전에 트랙의 해당 줄, `git log -10` 제목, 지금 도는 세션(Claude는 세션 목록, GPT는 세션 기록 끝 timestamp — [AI CLI](AI_CLI.md#codex-세션-기록))을 본다. 같은 일을 하는 쪽이 있으면 범위를 나눈다(그쪽 목록의 경로를 빼는 식). 같은 시각에 도는 다른 업로드(공간 확보 백업 등)도 회선을 나눠 쓴다.
- 다시 확인: 시작 전에 `git log -10 --format=%s | grep -iE "백업|Drive|업로드"`.

### 업로드가 회선을 채워 다른 세션의 gh·git push가 끊긴다
- 증상: 10-03 밤 Wi‑Fi가 26Mbps로 붙어 올림 합계가 9~11Mbps였다. 회선을 꽉 채우자 인터넷 지연이 평균 0.7초(최대 1.6초)까지 늘어 다른 세션의 gh 접속이 끊겼다. 6Mbps로 묶어도 지연이 2초를 넘은 때가 있었다. 09-05에도 백업이 회선을 먹어 git push가 죽었다.
- 원인: 이 집의 Wi‑Fi 연결 속도는 시각에 따라 크게 바뀐다(옛 노트북 10-03: 밤 26Mbps, 새벽 5시 292Mbps — 그때는 다른 업로드가 95Mbps를 쓰는 중에도 지연이 79~81ms였다). 고정 상한은 느릴 때는 막히고 빠를 때는 낭비다. 파일을 잘게 나누고 쉬는 것만으로는 순간 폭주를 못 막는다.
- 고침: 지연을 재며 속도를 맞춘다. `../PC_백업_20261003/media-upload.py`의 `Bucket.adapt`는 30초마다 `www.google.com:443` 연결 시간을 세 번 재서, 350ms를 넘으면 속도를 절반으로, 150ms 아래면 1.25배+0.5로 바꾼다(시작 4Mbps, 최대 25Mbps).
- 다시 확인: PowerShell `netsh wlan show interfaces`의 수신·전송 속도와 `www.google.com:443` 연결 시간을 잰다. 10-17 15:49 새 노트북은 802.11ax 수신 961·전송 817Mbps, 연결 57~119ms였다.

### Drive에 같은 날짜의 백업 폴더가 여럿 있어 중복처럼 보인다
- 증상: Drive에 `PC_백업_20261003/`, `PC_백업_20261003_미디어원본/`(4,210개), `PC_백업_20261003/old-sns-000N.zip`(GPT 공간 정리) 같은 폴더·묶음이 함께 있다.
- 원인: 10-03에 여러 세션이 따로 백업했고, 10-03 `복원목록.json`이 이 폴더들을 모두 가리킨다.
- 고침: 중복으로 보여도 지우거나 옮기지 않는다. 지우거나 옮기려면 먼저 복원 목록이 그 경로를 가리키는지 본다.
- 다시 확인: `../PC_백업_20261003/` README와 `복원목록.json`에서 그 폴더 이름을 찾는다(10-17 도구 폴더 있음).

### 작은 파일이 많으면 업로드가 느리다
- 증상: 10-14 HappyGangster 작업원본 33.75GB(8,258개) 중 5MB 이하 7,150개가 동시 8개로 초당 1.4개씩만 올라갔다. 상한 60Mbps를 줘도 평균 23Mbps였고, 전체가 약 3시간 10분 걸렸다(지연 36~60ms).
- 원인: 작은 파일은 파일마다 드는 요청 왕복이 전송 시간보다 길다.
- 고침: 작은 파일은 동시 수를 16으로 올린다(`hg_backup.py`에서 `do_files.__defaults__`를 바꿈).
- 다시 확인: 올리는 동안 초당 끝난 파일 수를 본다.

### 몇 시간짜리 업로드가 중간에 끊긴다
- 증상: Claude Code 세션의 백그라운드 작업으로 돌린 업로드가 2시간쯤에서 끊겼다(10-03).
- 원인: 세션 백그라운드 작업은 세션에 묶여 있어 오래 가지 못한다.
- 고침: PowerShell `Start-Process -WindowStyle Hidden`으로 세션과 떨어진 프로세스로 띄우고, 멈출 때는 stop 파일을 쓴다(10-03 `이어올리기.py`가 단계를 잇는다).
- 다시 확인: 띄운 뒤 `Get-Process python`에 그 프로세스가 남아 있는지, 진행 기록이 늘어나는지 본다.

### 업로드·대조 명령이 0으로 끝나도 백업 전체가 성공한 것은 아니다
- 증상: 10-17 `media-upload.py`의 `do_files`는 개별 오류 수, `do_verify`는 `missing_or_bad`를 기록하지만 그 수만으로 실패 종료하지 않았다. 원격 대조도 올렸다고 기록된 파일만 보므로 아직 올리지 못한 계획 파일은 빠질 수 있다.
- 원인: 작업 끝과 전체 파일 보존이 같은 종료값으로 표현됐다. 예약 작업의 0만 보면 부분 실패를 놓친다.
- 고침: `../SYNK_원본창고/매일백업.py`에서 종료값·업로드 오류 수·대조 결과 존재와 누락 수·계획 대비 영수증을 함께 확인하고, 성공·부분 실패·의도적 중지를 원자적 상태 JSON으로 남긴다. `백업상태.py`가 첫 실행 전·실행 중단·누락을 구분해 중복 없는 로컬 알림 원장을 만든다.
- 다시 확인: `python -X utf8 -B tests/백업상태.test.py`에서 종료값 0 + 원격 누락 2건, 대조 결과 없음, 예정 파일 미업로드, 중지, 첫 실행 누락을 격리 자료로 재현한다. 실제 백업 전체 성공과 복원 성공은 이 시험으로 주장하지 않는다.

### 완성본 이름으로만 찾으면 백업 원본을 놓친다

### 내용 없는 `data:` 표기와 검토한 예제 값이 OneDrive 사본을 막는다 (2026-10-19)

- 원인: 내장 미디어 규칙이 `data:image/` 글자나 `;base64,`만 보고, 뒤에 실제 내용이 이어지는지 보지 않았다. 삼항식 예외는 파일 전체 SHA에 묶여 있어(`onedrive-reviewed-literals.json`), 10-19 12:15 `sns-publisher.js` 커밋 뒤로 적용되지 않았다.
- 고침: `data:` 미디어는 쉼표 뒤에 실제 내용이 바로 이어질 때만 막는다. 이어지는 것이 `${`나 따옴표면 내용이 없는 것으로 본다. 일반 `;base64,`는 base64 16자 이상이 이어질 때만 막는다. 긴 base64와 그림 머리말 검사는 그대로다. 삼항식 1건과 합성 키 4건은 `tools/github-backup-reviewed-literals.json`에 경로+값 SHA로만 넣었다. 값은 출력하지 않았고, 스크립트로 모양(`text`, `synthetic-…`)만 확인했다. synk-tips `style.css`는 실제 인라인 SVG가 들어 있어 계속 막고, 암호화 보관으로 지킨다.
- 다시 확인: `node --test tests/이어하기꾸러미.test.js tests/onedrive-backup.test.cjs tests/백업.test.js tests/GitHub백업.test.cjs tests/보호소스보관.test.cjs tests/onedrive-recovery-index.test.cjs tests/Git보관묶음.test.cjs` 63개 통과. 옛 규칙은 새 시험의 허용 예 4개를 모두 막고, 새 규칙은 실제 자료가 든 예 5개를 모두 막는다. 드라이런에서 제외 수는 내장 미디어 475→334, 비밀 리터럴 213→210이 됐고, 보호 소스는 8→1(`style.css`)이 됐다. 검토 사유 문장에 따옴표 붙은 `password`·`text` 쌍을 그대로 적었더니 목록 파일 자체가 비밀 리터럴로 걸렸다. 사유 문장에는 따옴표 붙은 키·값 모양을 쓰지 않는다.
- 이어 확인: 16:02 커밋이 `tests/hermes-synk-overview.test.cjs`에 `accessToken: 'private-…'` 표식을 넣자, 이미 OneDrive에 있던 그 파일이 16:30 실행에서 다시 보호 대상으로 걸렸다. 그 값은 시험이 「출력·캐시에 절대 나오지 않는다」고 검사하는 표식이라(`private-secret`·`private-body`와 같은 줄), 같은 방식으로 경로+값 SHA 1건을 더했다. 새 시험 파일에 가짜 토큰을 넣을 때는 `synthetic-`·`private-` 같은 표식을 쓰더라도 이 목록에 한 줄이 필요하다.

### 제한에 끊긴 실행의 잠금이 남고 그 PID를 다른 프로세스가 받으면, 다음 GitHub 실행이 「already-running」으로 조용히 건너뛴다 (2026-10-21 Claude)

- 증상: 같은 PC 백업 문제가 「SYNK 백업 상태 확인」의 Windows 알림과 헤르메스 텔레그램으로 같이 갔다(10-20 20:17 알림 ↔ 20:19·21:13 텔레그램). OneDrive가 도는 동안(작업 결과 0x41301)에는 알림 지문이 회차마다 바뀌어 같은 문제를 다시 띄웠다(10-19 00:02~13:17 52건). 거꾸로 `missed`·`interrupted`·`partial_failure`·`blocked`·`unconfigured`·`unknown`은 Windows 알림으로만 갔다.
- 원인: 두 길이 각자 실패 상태 목록과 중복 막기를 가졌다. `tools/backup-health.py`의 `BAD`는 여덟 상태인데 `tools/hermes-synk/overview.cjs`는 `failed`·`attention`만 실패로 보고 나머지를 「상태 미확인」으로 넘겼다. 헤르메스 쪽은 구성 요소 + 마지막 성공 시각으로 한 사건을 한 번만 보내지만, Windows 알림 지문은 (id, 상태, 코드)라 「실행 중」이 끼면 바뀐다.
- 고침: 헤르메스가 `BAD`와 같은 목록(`BACKUP_FAILING`)을 실패로 본다. Windows 알림은 헤르메스 감시가 정상으로 도는 동안(`%LOCALAPPDATA%\hermes\runtime\synk-automation\health.json`이 `ok`이고 20분 안) 띄우지 않는다 — 그동안 열린 문제의 지문은 그대로 둬서, 감시가 멈추면 같은 문제를 예비로 한 번 띄운다. 공간 지킴이 자체 알림(`SYNK_원본창고/공간지킴이.py`)은 저장소 밖이라 그대로다.
- 다시 확인: `node --test tests/hermes-synk-overview.test.cjs`(44, 새 「백업 상태 도구가 실패로 치는 상태를 모두 알린다」) · `tests/backup-health.test.py`(57, 새 셋 — 감시 중에는 안 띄우고 멈추면 한 번, 감시 중 풀린 문제는 복구 알림도 없음, 20분 안 `ok`만 감시 중). 실제 회차에서는 `backup-notification-state.json`의 `delivery.skipped`가 `HERMES_WATCHING`인지 본다.
