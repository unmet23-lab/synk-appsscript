### 보호 소스 확인이 OneDrive 사본의 ctime 하나로 전체를 멈춘다 (2026-10-19)
- 증상: 10-18 16:30부터 OneDrive 백업은 사본이 모두 IN_SYNC인데도 `previously-backed-source-now-protected`로, GitHub 백업과 Git 암호문 백업은 `PROTECTED_SOURCE_PRIOR_COPY_CHANGED`로 계속 실패했다. `protected-source-backup-status.json`의 `files`는 0개였다.
- 원인: `tools/보호소스보관.cjs`는 보호 소스를 처리하기 전에 이전 OneDrive 사본(내장 미디어 판정 3개)을 한꺼번에 확인한다. 이때 읽기 전후 stat의 ctime까지 비교한다. 그런데 OneDrive Cloud 사본은 한동안 안 열다가 처음 열면 내용·크기·수정 시각·파일 ID는 그대로이고 ctime만 바뀐다. 10-19 13:15에 세 사본 모두에서 재현했고, 바로 다시 읽으면 바뀌지 않았다. NTFS 마지막 접근 갱신은 꺼져 있는데도 atime이 바뀐다. 2시간마다 도는 실행은 매번 이 첫 읽기에 걸렸다. 사본 하나만 걸려도 전체가 멈춰, 비밀값 판정 소스 약 300개의 새 판도 암호화 보관되지 않았다.
- 고침: ctime만 바뀐 읽기는 0.25초 뒤 최대 3번까지 다시 읽는다. ctime을 포함한 전후 stat가 모두 같고 SHA가 영수증과 같을 때만 받아들인다. 크기·수정 시각·SHA가 다르면 바로 실패하고, 안정성 비교 항목은 줄이지 않았다.
- 다시 확인: `node --test tests/보호소스보관.test.cjs` 5개 통과(첫 읽기의 ctime 변화는 통과, 매번 바뀌는 ctime·mtime 변화·내용 변화는 실패). 13:30 GitHub 실행이 보호 소스 296개 중 192개는 기존 암호문을 다시 쓰고 104개는 새로 암호화했다. 이어 Git 암호문 백업이 Drive 전송·대조 790/790을 마쳤고, 13:36:37에 GitHub·보호 소스가 success가 됐다.

### 내용 없는 `data:` 표기와 검토한 예제 값이 OneDrive 사본을 막는다 (2026-10-19)
- 증상: 위 실패에 걸린 보호 소스 8개는 모두 오탐이었다. 현장 노트의 `data:image/png` 설명, 시험 파일이 실행 중에 조립하는 `data:text/javascript;base64,${…}`, 회사 서버 시험 4개의 `synthetic-…` 채널 키, `secret ? 'password' : 'text'` 삼항식이다. 같은 규칙 때문에 그림을 실행 중에 data 주소로 굽는 빌드·도구 스크립트 139개도 OneDrive 사본에서 빠져 있었다.
- 원인: 내장 미디어 규칙이 `data:image/` 글자나 `;base64,`만 보고, 뒤에 실제 내용이 이어지는지 보지 않았다. 삼항식 예외는 파일 전체 SHA에 묶여 있어(`onedrive-reviewed-literals.json`), 10-19 12:15 `sns-publisher.js` 커밋 뒤로 적용되지 않았다.
- 고침: `data:` 미디어는 쉼표 뒤에 실제 내용이 바로 이어질 때만 막는다. 이어지는 것이 `${`나 따옴표면 내용이 없는 것으로 본다. 일반 `;base64,`는 base64 16자 이상이 이어질 때만 막는다. 긴 base64와 그림 머리말 검사는 그대로다. 삼항식 1건과 합성 키 4건은 `tools/github-backup-reviewed-literals.json`에 경로+값 SHA로만 넣었다. 값은 출력하지 않았고, 스크립트로 모양(`text`, `synthetic-…`)만 확인했다. synk-tips `style.css`는 실제 인라인 SVG가 들어 있어 계속 막고, 암호화 보관으로 지킨다.
- 다시 확인: `node --test tests/이어하기꾸러미.test.js tests/onedrive-backup.test.cjs tests/백업.test.js tests/GitHub백업.test.cjs tests/보호소스보관.test.cjs tests/onedrive-recovery-index.test.cjs tests/Git보관묶음.test.cjs` 63개 통과. 옛 규칙은 새 시험의 허용 예 4개를 모두 막고, 새 규칙은 실제 자료가 든 예 5개를 모두 막는다. 드라이런에서 제외 수는 내장 미디어 475→334, 비밀 리터럴 213→210이 됐고, 보호 소스는 8→1(`style.css`)이 됐다. 검토 사유 문장에 따옴표 붙은 `password`·`text` 쌍을 그대로 적었더니 목록 파일 자체가 비밀 리터럴로 걸렸다. 사유 문장에는 따옴표 붙은 키·값 모양을 쓰지 않는다.
- 이어 확인: 16:02 커밋이 `tests/hermes-synk-overview.test.cjs`에 `accessToken: 'private-…'` 표식을 넣자, 이미 OneDrive에 있던 그 파일이 16:30 실행에서 다시 보호 대상으로 걸렸다. 그 값은 시험이 「출력·캐시에 절대 나오지 않는다」고 검사하는 표식이라(`private-secret`·`private-body`와 같은 줄), 같은 방식으로 경로+값 SHA 1건을 더했다. 새 시험 파일에 가짜 토큰을 넣을 때는 `synthetic-`·`private-` 같은 표식을 쓰더라도 이 목록에 한 줄이 필요하다.

- 증상: 공간 지킴이 장부(`상태/공간지킴이/내려놓은목록.jsonl`)를 OneDrive 문서 백업 범위(`이어하기꾸러미.js`의 vault 정규식)에 넣으려고 보니, 첫 정리만으로 4,958줄·3.15MB(줄당 약 640바이트)였고 내려놓을 때마다 줄이 덧붙는다. 10MiB(약 16,500줄)를 넘으면 목록에서 `over-10MiB`로 빠진다.

- 고침: 장부·`latest.json`·`*_Drive에없음.json` 세 이름만 정확히 넣었다(같은 폴더의 `점검.log`·예약 사본 xml, 다른 상태 폴더의 `latest.json`은 계속 뺀다). 통합 감시 `tools/backup-health.py`의 `space` 칸이 장부가 8MiB를 넘으면 `SPACE_LEDGER_NEAR_ONEDRIVE_LIMIT`로 알린다. 그 전에 지킴이가 장부를 나눠 쓰고(읽는 쪽 `ledger_rows`·`서버백업받기.js`도 함께), 나눈 이름을 정규식에 더해야 한다(10-19 기준 아직 안 함).
- 다시 확인: `node --test tests/이어하기꾸러미.test.js` 22개 통과(새 시험은 정규식이 없으면 실패한다). 실제 창고에서 `시스템목록` → `oneDrivePlan`이 세 파일을 거절 없이 골랐다(10-19). 장부 크기는 `wc -c ../SYNK_원본창고/상태/공간지킴이/내려놓은목록.jsonl`로 본다.

### 백업 감시에 새 칸을 설정 파일로 넣으면 설치기가 지우고, 「준비 전」을 대기로 세면 정상 복구 알림이 막힌다 (2026-10-19)
- 증상: 공간 지킴이(`../SYNK_원본창고/공간지킴이.py`)를 통합 감시에 이으려는데, 예약 「SYNK 공간 지킴이」는 유호님 확인 전이라 아직 없다(10-19 「예약은 아직 등록하지 마」).
- 원인: `backup-health-config.json`은 `install-four-backups.ps1`을 다시 돌리면 정해진 칸만으로 통째로 다시 쓰인다(`workspace` 칸만 옮겨 둔다). 또 `gather()`는 정상이 아닌 칸이 하나라도 있으면 전체를 `pending`으로 두는데, 그러면 정상 복구 알림이 나가지 않는다(`choose_event`·`update_notifications`는 전체 `healthy`일 때만 복구를 알린다).
- 고침: 지킴이 칸은 `backup-health.py` 안의 `SPACE_GUARD`로 두고, 예약 조회는 설정의 임시 사본(`additionalChecks`에 더함)으로 `backup-task-status.ps1`에 넘긴 뒤 지운다. 예약이 없으면 새 상태 `not_ready`(준비 전)로 두고 문제로도 대기로도 세지 않는다. 등록 직후 첫 실행 전(다음 실행이 2시간 안)도 준비 전이다 — 손으로 돌린 옛 영수증을 멈춤으로 잘못 알리지 않게. 등록 뒤에는 점검이 2시간 넘게 없거나(예약이 돌고 있으면 실행 제한 2시간까지 기다림), 마지막 예약 실행이 실패했거나, 여유가 300GB 아래면 `attention`이다. Hermes 개요는 `failed`·`attention`만 실패로 보므로 문제 상태를 새로 만들지 않았다. 알림 본문에는 칸의 `detail`(「남은 공간 285GB(지킬 선 300GB)」 등)을 쓴다.
- 다시 확인: `python -X utf8 -B tests/backup-health.test.py` 27개 통과(새 7개는 사본을 일부러 망가뜨린 여섯 가지를 모두 잡는다). 10-19 19:57 실제 실행에서 전체 `healthy`, `space`는 `not_ready`·`SPACE_GUARD_SCHEDULE_NOT_REGISTERED`였다. 예약을 등록하면 `backup-health.json`의 `space`가 `healthy`로 바뀌는지 본다. 손으로 오래 `내려놓기 --실행`을 돌리는 동안에는 예약 점검이 `ALREADY_RUNNING`으로 건너뛰어, 2시간 뒤 멈춤으로 알릴 수 있다.
