어느 계정·폴더에 원본을 둘지는 [AI 운영 원칙](../AI_운영원칙.md)의 역할 표·[결정 표](../_ops/결정.md), 저장소 자산 보관은 [Git 자산 보관](../_ops/github-storage/README.md)이 정한다. 지우기 전 확인은 [git 노트의 공간 정리 항목](git_줄끝_잠금.md#공간-정리가-추적-파일을-지운다)을 따른다. 여기는 수백 MB가 넘는 백업·업로드를 할 때 겪은 함정이다. 틀은 [README](README.md)를 따른다.

지금까지의 Drive 백업 짜임: 09-26·09-30·10-01·10-03·10-14 백업이 모두 Drive 루트의 `PC_백업_YYYYMMDD/` 아래에 원래 경로대로 파일 하나씩 있다. 그래서 다음 백업은 Drive 전체 목록의 `md5Checksum`+`size`와 대조해 빠진 것만 올린다. 10-03 `복원목록.json`은 30,063개 모두의 위치를 적고, `되살리기.py`는 sha256으로 확인하며 받는다. 다른 원본 폴더를 올릴 때는 10-14 도구 셋을 복사해 `BASE`·`TOP`만 바꾼다. 올리기 전에는 Drive 자격(`tools/company-messenger/data/drive-storage.json`의 활성 연결)이 원본을 둘 계정인지 확인한다. 백업 뒤 로컬을 지울 때는 10-14 `이어서_지우기.py`처럼 업로드 끝을 기다린 뒤 Drive를 다시 대조하고, 되살리기 시험 3개를 받아 보고, 로컬을 다시 해시해 맞는 파일만 지운다. OneDrive로 보내려면 로컬 사본이 먼저 있어야 하니, 큰 것은 Drive API로 원본에서 바로 올린다.

## Drive 올리기·대조

### 숨김 백업 프로세스도 앱 재시작 때 종료된다
- 증상: 10-18 Codex 재시작 뒤 숨김 `pythonw`의 미디어·DB 보완 실행이 사라지고 heartbeat가 13:13에서 멈췄다. 업로드 완료 영수증 504건은 남아 있었다.
- 원인: 이 실행 환경에서는 `Start-Process -WindowStyle Hidden`만으로 앱의 프로세스 수명에서 완전히 독립하지 못했다.
- 고침: 긴 실행은 등록된 Windows 예약 작업에서 시작한다. `backup-command.py`가 창 없이 자식을 실행하고 종료값을 예약에 전달한다. 중복 실행은 OS/PID 잠금으로 막고 콘텐츠 지문 영수증으로 이어받아 이전 완료 파일을 재전송하지 않는다.
- 다시 확인: 13:18 `SYNK 미디어 원본 백업`·`SYNK 오늘 DB 백업 보완`을 작업 스케줄러에서 시작해 Running과 새로운 heartbeat를 확인했다. 앱을 일부러 다시 꺼서 재현하지는 않았다. 최종 완료는 해당 실행의 원격 검증 영수증을 별도로 확인한다.

### 같은 원본을 두 세션이 동시에 올린다
- 증상: 10-03 새벽 두 Claude 세션이 같은 미디어를 동시에 Drive에 올렸다. 한쪽은 파일 하나씩·속도 상한을 두고, 다른 쪽은 zip 묶음·상한 없이 올렸다. 상대 세션의 커밋 제목(「미디어 원본 Drive 백업 진행 위치」)을 보고 27묶음(0.88GB)에서 멈췄다. 그날 백업 세션이 넷이나 겹쳤다.
- 원인: 시작하기 전에 같은 일을 하는 다른 세션·GPT 작업이 있는지 보지 않았다.
- 고침: 수백 MB가 넘는 업로드·다운로드 전에 트랙의 해당 줄, `git log -10` 제목, 지금 도는 세션(Claude는 세션 목록, GPT는 세션 기록 끝 timestamp — [AI CLI](AI_CLI.md#codex-세션-기록))을 본다. 같은 일을 하는 쪽이 있으면 범위를 나눈다(그쪽 목록의 경로를 빼는 식). 같은 시각에 도는 다른 업로드(공간 확보 백업 등)도 회선을 나눠 쓴다.
- 다시 확인: 시작 전에 `git log -10 --format=%s | grep -iE "백업|Drive|업로드"`.

### 업로드가 회선을 채워 다른 세션의 gh·git push가 끊긴다
- 증상: 10-03 밤 Wi‑Fi가 26Mbps로 붙어 올림 합계가 9~11Mbps였다. 회선을 꽉 채우자 인터넷 지연이 평균 0.7초(최대 1.6초)까지 늘어 다른 세션의 gh 접속이 끊겼다. 6Mbps로 묶어도 지연이 2초를 넘은 때가 있었다. 09-05에도 백업이 회선을 먹어 git push가 죽었다.
- 원인: 이 집의 Wi‑Fi 연결 속도는 시각에 따라 크게 바뀐다(옛 노트북 10-03: 밤 26Mbps, 새벽 5시 292Mbps — 그때는 다른 업로드가 95Mbps를 쓰는 중에도 지연이 79~81ms였다). 고정 상한은 느릴 때는 막히고 빠를 때는 낭비다. 파일을 잘게 나누고 쉬는 것만으로는 순간 폭주를 못 막는다.
- 고침: 지연을 재며 속도를 맞춘다. `../PC_백업_20261003/media-upload.py`의 `Bucket.adapt`는 30초마다 `www.google.com:443` 연결 시간을 세 번 재서, 350ms를 넘으면 속도를 절반으로, 150ms 아래면 1.25배+0.5로 바꾼다(시작 4Mbps, 최대 25Mbps).
- 다시 확인: PowerShell `netsh wlan show interfaces`의 수신·전송 속도와 `www.google.com:443` 연결 시간을 잰다. 10-17 15:49 새 노트북은 802.11ax 수신 961·전송 817Mbps, 연결 57~119ms였다.

### Drive에 같은 날짜의 백업 폴더가 여럿 있어 중복처럼 보인다
- 증상: Drive에 `PC_백업_20261003/`, `PC_백업_20261003_미디어원본/`(4,210개), `PC_백업_20261003/old-sns-000N.zip`(GPT 공간 정리) 같은 폴더·묶음이 함께 있다.
- 원인: 10-03에 여러 세션이 따로 백업했고, 10-03 `복원목록.json`이 이 폴더들을 모두 가리킨다.
- 고침: 중복으로 보여도 지우거나 옮기지 않는다. 지우거나 옮기려면 먼저 복원 목록이 그 경로를 가리키는지 본다.
- 다시 확인: `../PC_백업_20261003/` README와 `복원목록.json`에서 그 폴더 이름을 찾는다(10-17 도구 폴더 있음).

### 작은 파일이 많으면 업로드가 느리다
- 증상: 10-14 HappyGangster 작업원본 33.75GB(8,258개) 중 5MB 이하 7,150개가 동시 8개로 초당 1.4개씩만 올라갔다. 상한 60Mbps를 줘도 평균 23Mbps였고, 전체가 약 3시간 10분 걸렸다(지연 36~60ms).
- 원인: 작은 파일은 파일마다 드는 요청 왕복이 전송 시간보다 길다.
- 고침: 작은 파일은 동시 수를 16으로 올린다(`hg_backup.py`에서 `do_files.__defaults__`를 바꿈).
- 다시 확인: 올리는 동안 초당 끝난 파일 수를 본다.

### 몇 시간짜리 업로드가 중간에 끊긴다
- 증상: Claude Code 세션의 백그라운드 작업으로 돌린 업로드가 2시간쯤에서 끊겼다(10-03).
- 원인: 세션 백그라운드 작업은 세션에 묶여 있어 오래 가지 못한다.
- 고침: PowerShell `Start-Process -WindowStyle Hidden`으로 세션과 떨어진 프로세스로 띄우고, 멈출 때는 stop 파일을 쓴다(10-03 `이어올리기.py`가 단계를 잇는다).
- 다시 확인: 띄운 뒤 `Get-Process python`에 그 프로세스가 남아 있는지, 진행 기록이 늘어나는지 본다.

### 업로드·대조 명령이 0으로 끝나도 백업 전체가 성공한 것은 아니다
- 증상: 10-17 `media-upload.py`의 `do_files`는 개별 오류 수, `do_verify`는 `missing_or_bad`를 기록하지만 그 수만으로 실패 종료하지 않았다. 원격 대조도 올렸다고 기록된 파일만 보므로 아직 올리지 못한 계획 파일은 빠질 수 있다.
- 원인: 작업 끝과 전체 파일 보존이 같은 종료값으로 표현됐다. 예약 작업의 0만 보면 부분 실패를 놓친다.
- 고침: `../SYNK_원본창고/매일백업.py`에서 종료값·업로드 오류 수·대조 결과 존재와 누락 수·계획 대비 영수증을 함께 확인하고, 성공·부분 실패·의도적 중지를 원자적 상태 JSON으로 남긴다. `백업상태.py`가 첫 실행 전·실행 중단·누락을 구분해 중복 없는 로컬 알림 원장을 만든다.
- 다시 확인: `python -X utf8 -B tests/백업상태.test.py`에서 종료값 0 + 원격 누락 2건, 대조 결과 없음, 예정 파일 미업로드, 중지, 첫 실행 누락을 격리 자료로 재현한다. 실제 백업 전체 성공과 복원 성공은 이 시험으로 주장하지 않는다.

### 완성본 이름으로만 찾으면 백업 원본을 놓친다
- 증상: HappyGangster 한글 완성본 4개가 백업에서 미발견으로 분류됐다.
- 원인: 백업은 `join186e_final.mp4`·`join186i_2k_final.mp4`·`join186n_J1w_fix_2k_final.mp4`·`join186n_J1k_std_2k_final.mp4` 같은 내부 이름을 썼고, 인계 기록에 복사 이름과 같은 MD5가 남아 있었다. 퀴즈 4개는 삭제가 아니라 새 노트북 이전 제외 목록에 있었다.
- 고침: 제작 인계의 이름 대응·날짜·체크섬과 백업 영수증을 함께 찾고, 이전 제외 목록은 옛 기기 회수 후보로 구분했다. 프롬프트는 실제 제출한 문자열만 별도 기록복구본에 저장했다.
- 다시 확인: `.tmp/automation-six-20261017/preservation/recovery/remaining-18/`과 원본창고 `추가복구_18곳/복구결과.json`. 원격 파일 존재·제출 내용 복구·옛 파일 자체 복원을 서로 구분한다.

## Drive·허깅페이스 내려받기

### Drive 부분 다운로드의 206 응답만으로 재개 성공을 판단한다
- 증상: 10-17 HG 원본의 74MB 수신분에서 Range 재개를 요청하자 206과 정확한 Content-Range가 왔지만, 120초 동안 새 본문 저장은 진행되지 않았다.
- 원인: 응답 헤더를 받은 것과 파일 본문을 실제로 받은 것은 별개다. 이번 정체의 네트워크 원인은 확정하지 못했다.
- 고침: 진행 기록과 파일 크기를 함께 확인하고 우리 다운로드 프로세스만 종료했다. 기존 partial 두 개는 보존한 채 일반 GET을 한 번 다시 시작했다. 원격 메타데이터·MD5를 다운로드 전후 대조하고 스트림 해시와 저장 파일 재해시를 기존 업로드 영수증 SHA256과 비교한다. 응답에 ETag가 없었으므로 ETag 검증을 했다고 기록하지 않는다.
- 다시 확인: `.tmp/automation-six-20261017/preservation/onedrive-live/hg3-resume-20261017T121817Z-2fab5e.json`의 실제 수신 바이트·개별 완료 상태·해시 대조를 본다. 재개 요청 성공이나 일부 파일 완료를 전체 복구 완료로 계산하지 않는다.

### 남이 공개한 Drive 폴더의 파일을 curl로 받으면 500이 온다
- 증상: 10-19 공모전 작품기술서 양식(공개 폴더 안 zip)을 `https://drive.google.com/uc?export=download&id=<파일 id>`로 받자 1.6KB짜리 「Error 500 (Server Error)」 HTML이 zip 이름으로 저장됐다. WebFetch로 폴더를 읽으면 파일 이름만 나오고 id는 나오지 않았다.
- 원인: 옛 `uc` 받기 주소가 막힌 것으로 보인다. 파일 id는 폴더 페이지 HTML 안에만 있다.
- 고침: `curl -L -A "Mozilla/5.0" <폴더 주소>`로 HTML을 받아 `"1[A-Za-z0-9_-]{30,40}"`에서 폴더 id가 아닌 것을 고르고, `https://drive.usercontent.google.com/download?id=<파일 id>&export=download`로 받는다. 받은 뒤 크기와 `Content-Disposition` 파일 이름을 본다.
- 다시 확인: 10-19 같은 파일이 43,764바이트 zip(「2026 별별화성 Awards AI CF 공모전 작품기술서 양식.zip」)으로 받아지고 HWPX·DOC 두 개가 풀렸다.

### 허깅페이스 큰 모델 받기가 메모리에만 쌓이거나, 끈 줄 알았던 스크립트가 계속 받는다
- 증상: 10-18 MiniMax H3 공개판(3파일 약 40GB)을 받을 때 curl 한 줄은 초당 2MB였다. `hf download`(1.29, xet, `HF_XET_HIGH_PERFORMANCE=1`)로 바꾸자 20분 동안 `hf.exe` 메모리만 3.2GB까지 커지고 `.incomplete` 파일은 5MB에서 멈춰 있었다. 그 사이 `TaskStop`으로 끈 첫 curl 스크립트(bash)는 살아 있어 다음 파일을 1.2GB 더 받다가, 내가 같은 이름으로 고쳐 쓴 스크립트를 읽고 문법 오류로 끝나며 같은 로그에 「FAIL」을 남겨 기다리던 감시가 잘못 깨어났다.
- 원인: xet은 조각을 메모리에 모았다가 나중에 파일로 쓰는 것으로 보인다(40GB를 다 메모리에 올리면 RAM 64GB 노트북이 위험하다). `TaskStop`은 Git Bash 스크립트와 그 자식(curl)을 다 끄지 못하고, bash는 스크립트를 실행 중에 줄 단위로 읽어서 실행 중인 파일을 고쳐 쓰면 뒷부분이 바뀐다. 이번에는 옆 세션도 같은 와이파이로 FLUX 모델을 받고 있어 전체 대역(약 11MB/s)을 나눠 썼다.
- 고침: 큰 파일은 바이트 범위로 나눠 조각을 바로 디스크에 쓰는 `C:/SYNK-LoRA/tools/measure/par_dl.py`(16연결, 끊기면 받은 조각은 건너뜀, 다 받으면 이어 붙이고 크기 대조)로 받는다. 받기 스크립트를 끌 때는 `Get-CimInstance Win32_Process`로 그 스크립트 이름이 든 bash와 curl·hf를 찾아 함께 끄고, 고친 스크립트는 새 이름으로 만든다. 로그도 새 파일에 쓴다.
- 다시 확인: 받기 폴더 크기가 15초마다 느는지 본다(`tools/measure/dl_speed.py <폴더>`). 다른 세션의 큰 받기가 있으면(`Get-CimInstance` 명령줄에 `hf.exe download` 등) 대역을 나눠 쓴다고 예상 시간에 넣는다.
- 10-18 다시(HunyuanVideo-Foley): 세션이 두 번 다시 시작되며 「멈춤」으로 보고된 받기 스크립트가 실제로는 살아 있었고, 내가 다시 띄운 것까지 **같은 받기 셋이 같은 `.parts` 조각에 이어 쓰기(append)**를 해서 5.85GB 파일이 6.53GB로 붙어 「크기가 맞지 않음」으로 끝났다. 받기를 다시 띄우기 전에 `Get-CimInstance Win32_Process`에서 `par_dl|받기\.sh`를 찾아 남은 것을 먼저 끄고, 받기 스크립트 맨 앞에 잠금 폴더(`mkdir 받기.lock || exit`, `trap 'rmdir 받기.lock' EXIT`)를 둔다(`C:/SYNK-LoRA/tools/hunyuan-foley/받기.sh`). 깨진 `.tmp`·`.parts`는 지우고 처음부터 받는다.

### 내용 없는 `data:` 표기와 검토한 예제 값이 OneDrive 사본을 막는다 (2026-10-19)

## 공간 지킴이·백업 감시

### 서버 백업 암호문을 로컬에서 지우면 다음 날 아침 전부 다시 받는다 (2026-10-19)
- 증상: C: 여유가 316GB까지 줄어 원본 창고 verify가 끝난 `서버백업/*.enc`(281개·37.7GB)를 로컬에서 내려놓으려 할 때, `서버백업받기.js`는 로컬 파일이 없으면 받은 목록에 있어도 다시 받을 것으로 센다는 것을 코드에서 확인했다. 회사 GCS 백업은 하루 5~19GB씩 늘어 PC에 그대로 쌓이고 있었다(10-17 13GB·10-18 19GB).
- 원인: 받은 목록(`_받은목록.jsonl`)은 받았다는 기록이고, 받기 도구는 로컬 사본이 있는지를 완료 증거로 썼다(`!fs.existsSync(local)` → 다시 받기).
- 고침: `../SYNK_원본창고/공간지킴이.py`가 Drive(계정·주인·휴지통·크기·md5·sha256)와 로컬(md5·sha256, 재는 동안 안 바뀜)을 다시 대조한 뒤에만 지우고, 지우기 전에 `상태/공간지킴이/내려놓은목록.jsonl`에 offloaded를 먼저 적는다. 받기 도구는 로컬이 없을 때 이 장부에 같은 경로·크기·sha256으로 offloaded가 있으면 다시 받지 않는다. 다른 받기 도구에도 「로컬 사본 = 완료」 가정이 있으면 같은 장부를 보게 한다.
- 다시 확인: 내려놓기 전후 `node 서버백업받기.js --목록`의 「받을것」이 6개(새 객체만) 그대로였다. 1.5KB·110MB 암호문을 실제로 되살려 크기·sha256이 맞았고, 다시 내려놓았다.

### 이어 커지는 창고 장부를 OneDrive 사본에 넣으면 10MiB를 넘는 날 OneDrive 실행 전체가 멈춘다 (2026-10-19)
- 증상: 공간 지킴이 장부(`상태/공간지킴이/내려놓은목록.jsonl`)를 OneDrive 문서 백업 범위(`이어하기꾸러미.js`의 vault 정규식)에 넣으려고 보니, 첫 정리만으로 4,958줄·3.15MB(줄당 약 640바이트)였고 내려놓을 때마다 줄이 덧붙는다. 10MiB(약 16,500줄)를 넘으면 목록에서 `over-10MiB`로 빠진다.
- 원인: 한 번 복사된 파일이 내용 사유(`over-10MiB` 포함)로 빠지면 `onedrive-backup.cjs`의 `protectedPriorSources`가 보호 대상으로 잡는다. 그런데 `protectedSourceInventory`는 비밀값·내장 미디어만 암호화 보관하므로, 그 뒤로는 매 실행이 `previously-backed-source-now-protected`로 실패한다. 장부 하나가 OneDrive 백업 전체를 멈추는 구조다.
- 고침: 장부·`latest.json`·`*_Drive에없음.json` 세 이름만 정확히 넣었다(같은 폴더의 `점검.log`·예약 사본 xml, 다른 상태 폴더의 `latest.json`은 계속 뺀다). 지킴이(`공간지킴이.py`의 `append_ledger`)는 지금 조각이 4MiB를 넘게 되면 `내려놓은목록-002.jsonl`, `-003`…에 이어 쓴다. 옛 한 파일 장부는 이름 그대로 첫 조각이고 다시 쓰지 않는다. 읽는 쪽 넷(지킴이 `ledger_parts`, `서버백업받기.js` `장부조각`, `tools/backup-health.py` `ledger_parts`, `tools/이어하기꾸러미.js` vault 정규식)은 같은 이름 규칙(원래 이름 다음 세 자리 이상 번호, 글자 순이 아니라 번호 순)을 쓴다. 통합 감시 `space` 칸은 어느 조각이든 8MiB를 넘으면 `SPACE_LEDGER_NEAR_ONEDRIVE_LIMIT`로 그 조각 이름과 크기를 알린다(나누기가 멈췄다는 뜻, 10-19).
- 다시 확인: `python -X utf8 -B ../SYNK_원본창고/공간지킴이.test.py` 21개, `node --test ../SYNK_원본창고/서버백업받기.test.cjs` 2개, `node --test tests/이어하기꾸러미.test.js` 22개, `python -X utf8 -B tests/backup-health.test.py` 28개 통과(조각을 안 읽거나 안 나누거나 글자 순으로 읽게 망가뜨린 사본 여덟 가지를 모두 잡는다). 실제 장부(4,958줄)를 임시 폴더에서 1MiB 조각 넷으로 다시 써도 이어 붙이면 원본과 바이트가 같았고, 파이썬·JS 읽기와 `oneDrivePlan`(거절 0)도 한 파일일 때와 같았다. 실제 창고 `node 서버백업받기.js --목록`의 받을것은 옛 동작과 같은 9개였다(장부를 안 읽으면 289개, 10-19). 조각 크기는 `ls -l ../SYNK_원본창고/상태/공간지킴이/내려놓은목록*.jsonl`로 본다.

### 백업 감시에 새 칸을 설정 파일로 넣으면 설치기가 지우고, 「준비 전」을 대기로 세면 정상 복구 알림이 막힌다 (2026-10-19)
- 증상: 공간 지킴이(`../SYNK_원본창고/공간지킴이.py`)를 통합 감시에 이으려는데, 예약 「SYNK 공간 지킴이」는 유호님 확인 전이라 아직 없다(10-19 「예약은 아직 등록하지 마」).
- 원인: `backup-health-config.json`은 `install-four-backups.ps1`을 다시 돌리면 정해진 칸만으로 통째로 다시 쓰인다(`workspace` 칸만 옮겨 둔다). 또 `gather()`는 정상이 아닌 칸이 하나라도 있으면 전체를 `pending`으로 두는데, 그러면 정상 복구 알림이 나가지 않는다(`choose_event`·`update_notifications`는 전체 `healthy`일 때만 복구를 알린다).
- 고침: 지킴이 칸은 `backup-health.py` 안의 `SPACE_GUARD`로 두고, 예약 조회는 설정의 임시 사본(`additionalChecks`에 더함)으로 `backup-task-status.ps1`에 넘긴 뒤 지운다. 예약이 없으면 새 상태 `not_ready`(준비 전)로 두고 문제로도 대기로도 세지 않는다. 등록 직후 첫 실행 전(다음 실행이 2시간 안)도 준비 전이다 — 손으로 돌린 옛 영수증을 멈춤으로 잘못 알리지 않게. 등록 뒤에는 점검이 2시간 넘게 없거나(예약이 돌고 있으면 실행 제한 2시간까지 기다림), 마지막 예약 실행이 실패했거나, 여유가 300GB 아래면 `attention`이다. Hermes 개요는 `failed`·`attention`만 실패로 보므로 문제 상태를 새로 만들지 않았다. 알림 본문에는 칸의 `detail`(「남은 공간 285GB(지킬 선 300GB)」 등)을 쓴다.
- 다시 확인: `python -X utf8 -B tests/backup-health.test.py` 27개 통과(새 7개는 사본을 일부러 망가뜨린 여섯 가지를 모두 잡는다). 10-19 19:57 실제 실행에서 전체 `healthy`, `space`는 `not_ready`·`SPACE_GUARD_SCHEDULE_NOT_REGISTERED`였다. 예약을 등록하면 `backup-health.json`의 `space`가 `healthy`로 바뀌는지 본다. 손으로 오래 `내려놓기 --실행`을 돌리는 동안에는 예약 점검이 `ALREADY_RUNNING`으로 건너뛰어, 2시간 뒤 멈춤으로 알릴 수 있다.
