# 현장 노트 · 백업·큰 업로드

> 판: Google Drive API(`tools/company-messenger/data/drive-storage.json`의 활성 연결) · 백업 도구 `../PC_백업_20261003/`(`media-backup.py`·`media-upload.py`·`되살리기.py`)·`../PC_백업_20261014_HappyGangster/`(`hg_backup.py`·`이어서_지우기.py`·`되살리기.py`) · 10-17 새 노트북 Wi‑Fi 802.11ax
> 마지막 확인: 2026-10-17(도구 폴더·회선 값을 새 노트북에서 다시 봄. 올림 속도 항목은 10-03·10-14 옛 노트북 실측)
> 쓴 AI: Claude Code(Claude Opus 5.5) — 10-03~10-14 Claude 메모에서 옮김(10-17 2차)

어느 계정·폴더에 원본을 둘지는 [AI 운영 원칙](../AI_운영원칙.md)의 역할 표·[결정 표](../_ops/결정.md), 저장소 자산 보관은 [Git 자산 보관](../_ops/github-storage/README.md)이 정한다. 지우기 전 확인은 [git 노트의 공간 정리 항목](git_줄끝_잠금.md#공간-정리가-추적-파일을-지운다)을 따른다. 여기는 수백 MB가 넘는 백업·업로드를 할 때 겪은 함정이다. 틀은 [README](README.md)를 따른다.

지금까지의 Drive 백업 짜임: 09-26·09-30·10-01·10-03·10-14 백업이 모두 Drive 루트의 `PC_백업_YYYYMMDD/` 아래에 원래 경로대로 파일 하나씩 있다. 그래서 다음 백업은 Drive 전체 목록의 `md5Checksum`+`size`와 대조해 빠진 것만 올린다. 10-03 `복원목록.json`은 30,063개 모두의 위치를 적고, `되살리기.py`는 sha256으로 확인하며 받는다. 다른 원본 폴더를 올릴 때는 10-14 도구 셋을 복사해 `BASE`·`TOP`만 바꾼다. 올리기 전에는 Drive 자격(`tools/company-messenger/data/drive-storage.json`의 활성 연결)이 원본을 둘 계정인지 확인한다. 백업 뒤 로컬을 지울 때는 10-14 `이어서_지우기.py`처럼 업로드 끝을 기다린 뒤 Drive를 다시 대조하고, 되살리기 시험 3개를 받아 보고, 로컬을 다시 해시해 맞는 파일만 지운다. OneDrive로 보내려면 로컬 사본이 먼저 있어야 하니, 큰 것은 Drive API로 원본에서 바로 올린다.

### 같은 원본을 두 세션이 동시에 올린다
- 증상: 10-03 새벽 두 Claude 세션이 같은 미디어를 동시에 Drive에 올렸다. 한쪽은 파일 하나씩·속도 상한을 두고, 다른 쪽은 zip 묶음·상한 없이 올렸다. 상대 세션의 커밋 제목(「미디어 원본 Drive 백업 진행 위치」)을 보고 27묶음(0.88GB)에서 멈췄다. 그날 백업 세션이 넷이나 겹쳤다.
- 원인: 시작하기 전에 같은 일을 하는 다른 세션·GPT 작업이 있는지 보지 않았다.
- 고침: 수백 MB가 넘는 업로드·다운로드 전에 트랙의 해당 줄, `git log -10` 제목, 지금 도는 세션(Claude는 세션 목록, GPT는 세션 기록 끝 timestamp — [AI CLI](AI_CLI.md#codex-세션-기록))을 본다. 같은 일을 하는 쪽이 있으면 범위를 나눈다(그쪽 목록의 경로를 빼는 식). 같은 시각에 도는 다른 업로드(공간 확보 백업 등)도 회선을 나눠 쓴다.
- 다시 확인: 시작 전에 `git log -10 --format=%s | grep -iE "백업|Drive|업로드"`.

### 업로드가 회선을 채워 다른 세션의 gh·git push가 끊긴다
- 증상: 10-03 밤 Wi‑Fi가 26Mbps로 붙어 올림 합계가 9~11Mbps였다. 회선을 꽉 채우자 인터넷 지연이 평균 0.7초(최대 1.6초)까지 늘어 다른 세션의 gh 접속이 끊겼다. 6Mbps로 묶어도 지연이 2초를 넘은 때가 있었다. 09-05에도 백업이 회선을 먹어 git push가 죽었다.
- 원인: 이 집의 Wi‑Fi 연결 속도는 시각에 따라 크게 바뀐다(옛 노트북 10-03: 밤 26Mbps, 새벽 5시 292Mbps — 그때는 다른 업로드가 95Mbps를 쓰는 중에도 지연이 79~81ms였다). 고정 상한은 느릴 때는 막히고 빠를 때는 낭비다. 파일을 잘게 나누고 쉬는 것만으로는 순간 폭주를 못 막는다.
- 고침: 지연을 재며 속도를 맞춘다. `../PC_백업_20261003/media-upload.py`의 `Bucket.adapt`는 30초마다 `www.google.com:443` 연결 시간을 세 번 재서, 350ms를 넘으면 속도를 절반으로, 150ms 아래면 1.25배+0.5로 바꾼다(시작 4Mbps, 최대 25Mbps).
- 다시 확인: PowerShell `netsh wlan show interfaces`의 수신·전송 속도와 `www.google.com:443` 연결 시간을 잰다. 10-17 15:49 새 노트북은 802.11ax 수신 961·전송 817Mbps, 연결 57~119ms였다.

### Drive에 같은 날짜의 백업 폴더가 여럿 있어 중복처럼 보인다
- 증상: Drive에 `PC_백업_20261003/`, `PC_백업_20261003_미디어원본/`(4,210개), `PC_백업_20261003/old-sns-000N.zip`(GPT 공간 정리) 같은 폴더·묶음이 함께 있다.
- 원인: 10-03에 여러 세션이 따로 백업했고, 10-03 `복원목록.json`이 이 폴더들을 모두 가리킨다.
- 고침: 중복으로 보여도 지우거나 옮기지 않는다. 지우거나 옮기려면 먼저 복원 목록이 그 경로를 가리키는지 본다.
- 다시 확인: `../PC_백업_20261003/` README와 `복원목록.json`에서 그 폴더 이름을 찾는다(10-17 도구 폴더 있음).

### 작은 파일이 많으면 업로드가 느리다
- 증상: 10-14 HappyGangster 작업원본 33.75GB(8,258개) 중 5MB 이하 7,150개가 동시 8개로 초당 1.4개씩만 올라갔다. 상한 60Mbps를 줘도 평균 23Mbps였고, 전체가 약 3시간 10분 걸렸다(지연 36~60ms).
- 원인: 작은 파일은 파일마다 드는 요청 왕복이 전송 시간보다 길다.
- 고침: 작은 파일은 동시 수를 16으로 올린다(`hg_backup.py`에서 `do_files.__defaults__`를 바꿈).
- 다시 확인: 올리는 동안 초당 끝난 파일 수를 본다.

### 몇 시간짜리 업로드가 중간에 끊긴다
- 증상: Claude Code 세션의 백그라운드 작업으로 돌린 업로드가 2시간쯤에서 끊겼다(10-03).
- 원인: 세션 백그라운드 작업은 세션에 묶여 있어 오래 가지 못한다.
- 고침: PowerShell `Start-Process -WindowStyle Hidden`으로 세션과 떨어진 프로세스로 띄우고, 멈출 때는 stop 파일을 쓴다(10-03 `이어올리기.py`가 단계를 잇는다).
- 다시 확인: 띄운 뒤 `Get-Process python`에 그 프로세스가 남아 있는지, 진행 기록이 늘어나는지 본다.
