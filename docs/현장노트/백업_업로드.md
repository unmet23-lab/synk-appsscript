지금까지의 Drive 백업 짜임: 09-26·09-30·10-01·10-03·10-14 백업이 모두 Drive 루트의 `PC_백업_YYYYMMDD/` 아래에 원래 경로대로 파일 하나씩 있다. 그래서 다음 백업은 Drive 전체 목록의 `md5Checksum`+`size`와 대조해 빠진 것만 올린다. 10-03 `복원목록.json`은 30,063개 모두의 위치를 적고, `되살리기.py`는 sha256으로 확인하며 받는다. 다른 원본 폴더를 올릴 때는 10-14 도구 셋을 복사해 `BASE`·`TOP`만 바꾼다. 올리기 전에는 Drive 자격(`tools/company-messenger/data/drive-storage.json`의 활성 연결)이 원본을 둘 계정인지 확인한다. 백업 뒤 로컬을 지울 때는 10-14 `이어서_지우기.py`처럼 업로드 끝을 기다린 뒤 Drive를 다시 대조하고, 되살리기 시험 3개를 받아 보고, 로컬을 다시 해시해 맞는 파일만 지운다. OneDrive로 보내려면 로컬 사본이 먼저 있어야 하니, 큰 것은 Drive API로 원본에서 바로 올린다.

### 백업 실패를 기록했지만 사용자 알림은 오지 않는다
- 증상: 10-18 서버 백업은 21단계 중 1단계 실패였지만 상태 감시 예약은 종료 0이고 알림은 로컬 JSONL에만 있었다.
- 원인: 기존 감시는 상태 파일을 읽어 원장에 쓸 뿐 전달 경로가 없었고 OneDrive·GitHub·새 미디어의 예약 누락도 확인하지 않았다.
- 고침: `tools/backup-health.py`가 다섯 실행 경로의 영수증·예약 활성·최근 성공·heartbeat를 15분마다 대조하고 Windows 알림을 보낸다. 같은 문제는 하루 한 번 다시 알리고 정상 복구 때 알린다. 전달 실패는 같은 이벤트 ID로 재시도하고, 문제가 해소되어 정상 대기로 바뀌면 예전 실패 알림을 취소한다. [Microsoft 알림 API 안내](https://learn.microsoft.com/en-us/windows/win32/shell/quickstart-sending-desktop-toast)의 앱 ID를 지정하며 `Show()` 반환만 보지 않고 해당 태그가 OS 알림 기록에 있는지도 확인한다.
- 다시 확인: `python -X utf8 tests/backup-health.test.py`의 실패·누락·죽은 프로세스·예약 비활성·지연·복구·전달 재시도·하루 재알림·오래된 실패 취소·실제 자식 종료값 전달 시험을 통과했다. 10-18 시험 알림과 실제 실패 알림 모두 `상태/알림/*.delivery.json`에 `OS_HISTORY_CONFIRMED`가 기록됐다. 사용자 열람이나 네 클라우드 전체 복원 성공을 뜻하지 않는다.

### 일부 단계의 복구가 전체 백업 날짜를 새로 바꾼다
- 증상: 10-18 통합 감시의 격리 검토에서 전날 실행의 DB 단계만 오늘 고친 영수증이 오늘 전체 백업처럼 표시됐다. 같은 복구 영수증이 현재 공개키 누락·의도적 중지도 덮을 수 있었다.
- 원인: 원래 실행 ID와 실패 단계의 일치만 검사하고, 전체 자료의 기준 시각을 부분 복구 완료 시각으로 바꿨다.
- 고침: 완료된 실패 실행의 모든 실패 단계를 정확히 보완한 때만 복구를 인정한다. 자료 신선도는 원래 실행 시작 시각을 유지하고 복구 확인은 `repairedAt`으로 분리한다. 현재 준비 차단·중지는 과거 복구가 덮지 않으며, 의도적 중지는 예전 예약 실패값 때문에 새 장애로 알리지 않는다.
- 다시 확인: `python -X utf8 -B tests/backup-health.test.py` 19개 통과. 32시간 전 실행의 한 단계만 지금 복구해도 다음 정기 실행 누락을 알리고, 공개키 누락·미완료 단계·알림 전송 실패를 정상으로 바꾸지 않는다.

### 숨김 백업 프로세스도 앱 재시작 때 종료된다
- 증상: 10-18 Codex 재시작 뒤 숨김 `pythonw`의 미디어·DB 보완 실행이 사라지고 heartbeat가 13:13에서 멈췄다. 업로드 완료 영수증 504건은 남아 있었다.
- 원인: 이 실행 환경에서는 `Start-Process -WindowStyle Hidden`만으로 앱의 프로세스 수명에서 완전히 독립하지 못했다.
- 고침: 긴 실행은 등록된 Windows 예약 작업에서 시작한다. `backup-command.py`가 창 없이 자식을 실행하고 종료값을 예약에 전달한다. 중복 실행은 OS/PID 잠금으로 막고 콘텐츠 지문 영수증으로 이어받아 이전 완료 파일을 재전송하지 않는다.
- 다시 확인: 13:18 `SYNK 미디어 원본 백업`·`SYNK 오늘 DB 백업 보완`을 작업 스케줄러에서 시작해 Running과 새로운 heartbeat를 확인했다. 앱을 일부러 다시 꺼서 재현하지는 않았다. 최종 완료는 해당 실행의 원격 검증 영수증을 별도로 확인한다.

### 예약 DB 백업이 no password supplied로 실패한다
- 증상: 10-18 05:30 첫 정기백업의 talk DB 단계가 `fe_sendauth: no password supplied`, pg_dump·pg_restore 종료 1, 목차 0으로 실패했다. 다른 단계와 이후 업로드는 진행 중이었다.
- 원인: `../SYNK_원본창고/talk백업.js`는 `%APPDATA%/postgresql/pgpass.conf`를 읽지만 일반 경로에는 파일이 없고 Claude MSIX의 `LocalCache/Roaming/postgresql/pgpass.conf`에만 있었다. [Windows 셸 노트](윈도우_셸.md)의 AppData 가상화 사례와 같은 경로 불일치다.
- 고침: 비밀값을 출력하지 않고 기존 파일의 활성 행이 프로그램의 host·port·database·user와 모두 같은지 확인했다. 아직 없던 일반 경로에 같은 바이트를 배타적으로 새로 만들고 상속을 끈 현재 사용자 전용 ACL을 설정했다. 원본 인증 파일·스크립트·예약과 진행 중인 정기백업을 그대로 두고, 별도 보호 폴더에서 DB만 한 번 덤프해 기존 공개키로 스트림 암호화했다. 평문 파일은 쓰지 않았다.
- 다시 확인: 10:51:37~10:52:36 KST(59.628초) pg_dump=0·pg_restore --list=0·목차 1,435개, 암호화 스트림 SHA·암호문 재해시·컨테이너 크기 일치, .part 없음, 대상 ACL 사용자 전용을 확인했다. 근거는 `.tmp/automation-six-20261017/preservation/onedrive-live/pgpass-path-repair-20261018.json`·`talk-db-recovery-20261018.json`. 실제 복호화·복원과 Storage 전체 백업 검증은 수행하지 않았고 정기백업의 원래 실패 기록은 유지했다.

- 고침: 수백 MB가 넘는 업로드·다운로드 전에 트랙의 해당 줄, `git log -10` 제목, 지금 도는 세션(Claude는 세션 목록, GPT는 세션 기록 끝 timestamp — [AI CLI](AI_CLI.md#codex-세션-기록))을 본다. 같은 일을 하는 쪽이 있으면 범위를 나눈다(그쪽 목록의 경로를 빼는 식). 같은 시각에 도는 다른 업로드(공간 확보 백업 등)도 회선을 나눠 쓴다.
- 다시 확인: 시작 전에 `git log -10 --format=%s | grep -iE "백업|Drive|업로드"`.

### 업로드가 회선을 채워 다른 세션의 gh·git push가 끊긴다
- 증상: 10-03 밤 Wi‑Fi가 26Mbps로 붙어 올림 합계가 9~11Mbps였다. 회선을 꽉 채우자 인터넷 지연이 평균 0.7초(최대 1.6초)까지 늘어 다른 세션의 gh 접속이 끊겼다. 6Mbps로 묶어도 지연이 2초를 넘은 때가 있었다. 09-05에도 백업이 회선을 먹어 git push가 죽었다.
- 원인: 이 집의 Wi‑Fi 연결 속도는 시각에 따라 크게 바뀐다(옛 노트북 10-03: 밤 26Mbps, 새벽 5시 292Mbps — 그때는 다른 업로드가 95Mbps를 쓰는 중에도 지연이 79~81ms였다). 고정 상한은 느릴 때는 막히고 빠를 때는 낭비다. 파일을 잘게 나누고 쉬는 것만으로는 순간 폭주를 못 막는다.
- 고침: 지연을 재며 속도를 맞춘다. `../PC_백업_20261003/media-upload.py`의 `Bucket.adapt`는 30초마다 `www.google.com:443` 연결 시간을 세 번 재서, 350ms를 넘으면 속도를 절반으로, 150ms 아래면 1.25배+0.5로 바꾼다(시작 4Mbps, 최대 25Mbps).
- 다시 확인: PowerShell `netsh wlan show interfaces`의 수신·전송 속도와 `www.google.com:443` 연결 시간을 잰다. 10-17 15:49 새 노트북은 802.11ax 수신 961·전송 817Mbps, 연결 57~119ms였다.

### 업로드·대조 명령이 0으로 끝나도 백업 전체가 성공한 것은 아니다
- 증상: 10-17 `media-upload.py`의 `do_files`는 개별 오류 수, `do_verify`는 `missing_or_bad`를 기록하지만 그 수만으로 실패 종료하지 않았다. 원격 대조도 올렸다고 기록된 파일만 보므로 아직 올리지 못한 계획 파일은 빠질 수 있다.
- 원인: 작업 끝과 전체 파일 보존이 같은 종료값으로 표현됐다. 예약 작업의 0만 보면 부분 실패를 놓친다.
- 고침: `../SYNK_원본창고/매일백업.py`에서 종료값·업로드 오류 수·대조 결과 존재와 누락 수·계획 대비 영수증을 함께 확인하고, 성공·부분 실패·의도적 중지를 원자적 상태 JSON으로 남긴다. `백업상태.py`가 첫 실행 전·실행 중단·누락을 구분해 중복 없는 로컬 알림 원장을 만든다.
- 다시 확인: `python -X utf8 -B tests/백업상태.test.py`에서 종료값 0 + 원격 누락 2건, 대조 결과 없음, 예정 파일 미업로드, 중지, 첫 실행 누락을 격리 자료로 재현한다. 실제 백업 전체 성공과 복원 성공은 이 시험으로 주장하지 않는다.

### OneDrive 원본을 해시하려다 온라인 파일을 내려받을 수 있다
- 증상: 10-17 만족 사례의 OneDrive 경로까지 해시한 첫 점검이 오래 걸렸다. 내려받기 발생 여부는 확인하지 못했다.

### 안전 필터나 중복 수집이 최신 소스 보존을 빠뜨린다
- 증상: 일반 인증 UI·테스트 예제의 문자열이 민감값으로 분류되고, C#·Unity 설정·Apps Script GS·텍스트 자막 등 실제 시스템 소스 확장자가 없었다. 작업트리와 본진의 같은 MD를 중복 생략한 직후 본진이 바뀌면 인덱스의 원래 SHA가 사본에 없을 수도 있었다.
