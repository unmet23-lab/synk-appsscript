### 총평 (5줄 이내)

1. **D안(기존 기관 내 SYNK반 시작)과 온라인 마케팅 공급 장치는 4,000만원 자본 한계와 초반 공실 위험을 넘기 위한 매우 영리한 설계다.**
2. **하지만 지금 숫자는 그대로 믿고 확정하면 위험하다.** 메인(LAB·PATH)이 아니라 아직 고객이 0명인 서브(SHIFT·PULSE·WORLD)가 2028년 이익의 **63%(1.61억원)**를 벌어 몽골 직영 출자금(1.34억원)을 대는 주객전도 구조이기 때문이다.
3. **현금흐름 계산에 두 가지 큰 착시가 있다.** 용도가 묶인 정부지원금(6,000만원)이 최저 가용 현금을 부풀렸고, D안에서 2028-08에 1.34억원을 몽골에 출자하면 한국 법인 현금이 500만원대로 바닥난다.

#### `[P1] D안에서 교실 4개(s2)로 직영 전환할 때 공사비 이중 계상 및 전환 현금 기준(freeCash) 과소 산정`
- **어디**: `model.mjs` `run` 함수 내 직영 전환 조건(`directPrepStart` 판정) 및 일회성 비용(`lab.capex`) 계산 줄 근처
- **무엇이 문제인지**:
  1. `hostRooms`가 3개로 늘어난 뒤 직영 전환할 때 `directStage = 's2'`가 되는데, `lab.capex` 계산에서 `L.stages.s1.capexMNT + L.stages.s2.capexMNT`(8,000만₮ + 1억 6,000만₮ = **2억 4,000만₮**)를 부과합니다. 처음부터 `s2`를 여는 B안은 1억 6,000만₮만 내는데, D안은 안 짓는 `s1` 공사비까지 이중으로 내고 있습니다(설령 `s2.capexMNT`가 증설분이라 해도 B안과 기준이 모순됨).
  2. 직영 전환 시작 조건은 `freeCash >= fdiKRW + krBuffer`만 확인하고, 정작 그달 바로 현금에서 빠져나갈 `capex + deposit`과 초기 운영비를 확인하지 않습니다. 주석에는 *"출자금은 몽골 법인 통장으로 옮겨 공사·운영에 쓰는 돈이라 그룹 현금에서 바로 빠지지는 않는다"*고 적혀 있으나, 실제 코드(`flow`)에서는 `labCapexKRW`를 그룹 현금(`cash`)에서 바로 차감합니다. 만약 출자금 안에서 공사비를 쓰는 것이라면 `freeCash`가 `fdiKRW - labCapexKRW` 아래로 내려가며 한국 고정비 버퍼를 까먹고, 별도라면 `s1 → s2` 확장 조건(`s2Need`)처럼 공사비·보증금을 전환 기준에 더해야 일관됩니다.
- **결과에 주는 영향**: D안 상방(`2028-07` 전환) 및 기본(광고비 2배 시 `2029-09` 전환)에서 공사비가 8,000만₮(약 2,963만원) 과대 차감되어 기말 현금이 약 3,000만원 줄어듭니다.
- **고칠 코드**:
```js
// 1) 직영 전환 capex (s2로 바로 갈 때는 s2 공사비만 부과)
if (hosted && directPrepStart && m === directPrepStart) {
  lab.capex += L.stages[directStage].capexMNT * (opts.capexMult || 1);
  lab.deposit += L.stages[directStage].areaM2 * L.rentPerM2MNT * rentM * L.stages[directStage].depositMonths;
}
```

#### `[P1] SYNK반(host) 기간의 PATH 몽골 매출이 몽골 법인세 대상에 포함되고 원천징수(remitCost)에서는 누락됨`
- **어디**: `model.mjs` `run` 함수 내 `lab.remitCost` 계산 및 `mnRev` / `mnProfit` 세금 계산 줄 근처
- **무엇이 문제인지**: `inputs.mjs` 주석에 *"SYNK반 기간에는 몽골 법인이 없어 기관이 강사를 고용하고 남는 몫을 한국 법인에 보낸다"*고 명시되어 있습니다. 그래서 `stageKey === 'host'`일 때 `labMnRev = 0`으로 두어 몽골 법인세를 면제했는데, 정작 같은 기간 울란바토르에서 일어나는 **PATH 매출·비용(`planMNT`, `admissionMNT`, `campMNT`, `singlesMNT`, `costMNT`)은 `mnRev`와 `mnProfit`에 그대로 들어가 몽골 법인세를 내고**, 반대로 한국 송금 시 원천징수(`remitCost`) 대상(`remitBase`)에서는 빠져 있습니다. 또한 직영 전환 뒤에도 PATH 몽골 수익이 한국 법인세(`krProfit`)와 몽골 법인세(`mnProfit`) 중 어디로 귀속되는지(설립 전엔 한국, 설립 후엔 몽골) 구분되어 있지 않습니다.
- **결과에 주는 영향**: D안 기본(`stageKey === 'host'`가 2029년까지 유지됨)에서 몽골 법인이 없는데도 PATH 매출 때문에 매년 12월 몽골 법인세가 빠져나가고, 반대로 PATH 몽골 순이익의 11%(`remitCostRate`)인 연 150만~400만원가량의 송금 원천징수 비용이 누락됩니다.
- **고칠 코드**:
```js

const pathMnRev = path_.planMNT + path_.admissionMNT + path_.campMNT + path_.singlesMNT;
const pathMnProfit = pathMnRev - path_.costMNT;

// ... 세금 계산부
const hasMnCorp = !partnerMode && stageKey !== 'host';
const mnRev = hasMnCorp ? lab.revenue + pathMnRev : 0;
const mnProfit = hasMnCorp ? lab.profit + pathMnProfit : 0;
```

#### `[P2] 손익분기(labBep)와 실제 월별 계산(run)의 반 편성·단가·비용 기준 불일치 6가지`
- **어디**: `model.mjs` `labUnit`, `labStageFixed`, `labBep` 함수 vs `run` 함수 내 LAB 매출·비용·인센티브 계산부
- **무엇이 문제인지**: `labBep`로 구한 `bepHost(44.4명)`·`bep1(53.8명)`·`bep2(97.1명)`는 매달 인센티브 지급 기준(`ratio = students / bepNow`)으로 직접 쓰이는데, 정작 `run`과 다음 6가지가 다릅니다:
  1. **반 수 올림(`Math.ceil`) 누락**: `labBep`는 `classes = seats / avgClassSize(...)`로 **연속 실수**를 쓰지만, `run`은 `Math.max(2, Math.ceil(seatsNeeded / lab.classSize - 1e-9))`로 **정수 올림**을 씁니다.
  2. **기간권 비중(`passMix`) 시점 불일치**: `labBep`는 인자를 생략해 **2028-09 이후 비중**(`m6: 0.30, m12: 0.10`, 평균 단가 낮음)을 쓰지만, 첫해(`2027-09 ~ 2028-08`) `run`은 **초기 비중**(`m1: 0.35, m3: 0.40`, 평균 단가 높음)을 씁니다.
  3. **강사 기본 보너스(`baseBonus`) 인원 누락**: `labStageFixed`의 `headcountBase`는 `ops + 1(댄스)`만 넣고 **강사 인원(`Math.ceil(teacherClasses / 2)`)을 아예 빼먹었습니다.**
  4. **송금 원천징수(`remitCost`) 및 예비비(`contingency`) 누락**: `labBep`는 `remitCost`(11%)를 고려하지 않으며(영업이익 0점이라 이론상 0이지만 `baseBonus` 등이 변할 때 영향), 회화 추가분(`premium`)의 32석 상한도 없습니다.
  5. **물가 상승(`priceM = 1.05`, `wageM = 1.08`) 미반영**: 2028-09부터 인건비·임대료는 8% 오르고 수강료는 5%만 올라 실제 손익분기 학생 수가 올라가는데, `bepNow`는 2027년 고정값으로 묶여 있어 2028~2029년 인센티브 배수(`ratio`)가 과대평가됩니다.
  6. **결과 요약 증거**: `결과요약.txt`의 `D 기본 months` 첫 줄(`2027-09`)을 보면 **`st 45`명으로 `bepHost(44.4명)`를 넘겨 `ratio 1.01`이 되었고 인센티브까지 나갔는데, 정작 `labP`(LAB 이익)는 `-22만`원 적자**입니다! 손익분기를 넘겼는데 적자가 나는 이유가 바로 ① 반 수 정수 올림(45명 → 40.5석 ÷ 9.0 = 4.5반 → **5반** 비용 지출)과 ③ 강사 기본 보너스 때문입니다.
- **결과에 주는 영향**: 손익분기 학생 수가 실제보다 3~6명 낮게 잡혀, 적자 구간에서도 `ratio >= 1.0` 보너스(인당 5만→10만₮ 및 이익배분 10%)가 조기 발동됩니다.
- **고칠 코드**:
```js
// labBep 내부 margin(n)에서 run과 동일하게 정수 반 수 및 강사 보너스 반영
const margin = (n) => {
  const seats = n * u.seatEq;
  const classes = Math.max(2, Math.ceil(seats / avgClassSize(inp, stageKey, seats) - 1e-9));
  const tClasses = Math.max(0, classes - st.directorTeachesClasses);
  const tBonus = Math.ceil(tClasses / 2) * L.incentives.baseBonus[0].each * si;
  return n * (revPer - otherVar) - classes * (classCost + o.cuPerClass) - tBonus - fixedAdj;
};
```

- **어디**: `model.mjs` `run` 함수 내 `partnerMode` 분기, `co.contingency`, `labFirstProfit` 요약, 그리고 `C안` 민감도

if (isOpen && !partnerMode && stageKey === 's1' && !s2Start) { ... }

if (r.lab.stage && r.lab.stage !== 'pre' && !r.labKRW.royalty && r.labKRW.profit > 0) { labFirstProfit = r.m; break; }

#### `[P2] 대표 및 한국 담당자(krLead) 시간 배분에서 비위임 시간(leadNonDeleg) 차감 방식의 모순`
- **어디**: `model.mjs` `run` 함수 내 `nonDelegCap`, `kC`, `kN`, `leadNonDeleg`, `leadDelegCap` 계산 줄 근처
- **무엇이 문제인지**:
  1. 한국 담당자(`krLead`)는 월 `capacityHours: 140`시간 중 `founderLikeShare: 0.6`(84시간)만큼 대표처럼 영업·연출(`nonDelegCap`)을 대신할 수 있습니다.

- **고칠 코드**:
```js

sh.digital = digitalSales * SH.digital.price * sc.priceRealization;
pu.exclusive = adClients * PU.exclusive.attach * PU.exclusive.monthly * sc.priceRealization;
pu.mongolia = toKRW(mnClients * PU.mongoliaContent.monthlyMNT) * sc.priceRealization;
```

#### `[P3] 회사 예비비(contingency 3%)가 대표 생활비(founderPay)와 공간 수수료(hostFee)·원천징수(remitCost)에까지 붙고, 법인세 과세표준(krProfit·mnProfit)에서는 빠짐`
- **어디**: `model.mjs` `run` 함수 내 `co.contingency`, `krProfit`, `mnProfit` 계산 줄 근처
- **무엇이 문제인지**:
  1. `co.contingency = C.contingencyRate * r.costKRW`는 모든 사업부 비용과 회사 공통비(`founderPay` 포함)를 다 합친 뒤 일괄 3%를 곱합니다. 대표가 가져가는 생활비(`founderPay`)나 매출 연동 수수료(`hostFee` 30%, `remitCost` 11%)에까지 예비비 3%를 얹는 것은 과도합니다.

#### `[P3] LTV(생애 가치) 계산에서 학원 직접 변동비(교재비 외)와 비자 탈락률(visaFailRate) 누락`
- **어디**: `model.mjs` `ltv` 함수
- **무엇이 문제인지**: `ltv` 함수에서 `labMonthly = u.tuitionPer + u.premiumPer + u.bookRev - u.bookCost`로만 계산하여 학생 1명당 직접 변동비(`appAI`, `benefits`, `paymentFee`, `reserve`, `hostFee`)가 빠져 매출총이익이 아니라 매출액에 가깝게 잡혔고, `pathValue`에서는 입학 지원금의 마지막 마일스톤(40%)과 대학 수수료·정착비에 곱해져야 할 **`1 - P.visaFailRate`(0.9)가 빠져 있습니다.**
- **결과에 주는 영향**: 요약 지표인 `ltv.total`(123.9만원)이 실질 공헌이익 기준보다 약 15~35% 높게 표시됩니다(시뮬레이션 본문 현금흐름에는 영향 없음).
- **고칠 코드**:
```js
const visaKeep = 1 - P.visaFailRate;
const admFactor = 0.6 + 0.4 * visaKeep; // 마일스톤 30%+30%+40%*(1-0.1) = 0.96
const pathValue = pAdm * (P.prices.admissionLab * sc.priceRealization * admFactor / inp.fx.mntPerKrw
  + visaKeep * (sc.partnerUnivShare * P.prices.univCommissionKRW + P.settlementUptake * (P.prices.settlementKRW - P.prices.settlementCostKRW)));
```

### 잘 된 점 (3줄)
1. **지원금 전용 통장(`grantBal`)과 가용 현금(`free`)의 완벽한 분리**: 정부 지원금이 통장 잔고 착시를 일으켜 무리한 직영 전환이나 확장을 유발하지 않도록 `freeCash = cash - grantBal`로 의사결정 기준을 세운 점과, 기존 비용 대체분(`gSub`)만 현금 흐름에 더해 이중 계상을 막은 설계가 매우 정교합니다.
2. **초기 소규모 학원의 반 쪼개짐(`classFill`)과 광고비 자동 감액(`paidNew <= room`) 구현**: 학생이 적을 때 반 평균 인원이 낮아지는 현상을 이분법(`labCapacity`·`labBep`)으로 풀고, 정원이 차면 그달 광고비를 자동으로 줄여 헛돈을 쓰지 않게 한 점이 실제 학원 운영과 정확히 부합합니다.
3. **자체 검산(`checks`)과 하방 안전장치(`stopRule`·`expansionBuffer`) 내장**: 매 실행마다 매출 합계·정원 초과·전용 통장 음수 여부를 자동으로 검증하고, 적자와 현금 부족이 겹치면 C안(파트너 로열티)으로 자동 전환하는 멈춤 규칙을 코드로 구현해 모델의 신뢰도를 크게 높였습니다.
