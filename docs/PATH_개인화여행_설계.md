# PATH 개인화 여행 서비스 설계

SYNK PATH의 방문·문화 체험 사업을, 취향과 이번 여행의 조건에 맞춰 식당·숙소·경험·동선을 함께 설계하는 서비스로 발전시킨다. 2026-10-06 사용자 요청으로 반영한 사업 방향이며, 아래 48개 조건·국가 확장·수익 방식 전체의 구현·제휴·판매 완료를 뜻하지 않는다. 공통 개인화 기술은 SYNK가 맡는다. [사업 역할](마케팅_정본.md) · [Core 담당 계약](코어엔진_설계.md#travel-bundle-design).

**현재 제공·공개 상태의 담당 원문은 [서울 개인화 여행 앱](../experiences/path-travel/README.md)이다.** 10-09 v4와 SYNK ID 운영 연결을 공개했고, 공개 파일·운영 합성 저장/복원·공개 브라우저를 확인한 범위는 [배포 증거](../experiences/path-travel/qa/production-20261009/README.md)에 있다. 이 문서의 개발 중 ‘원격 미배포·계정 미연결’ 기록은 후속 공개로 대체됐다. 실제 이용자 만족도·현장 여행 성공·물리 두 기기 검증을 완료했다는 뜻은 아니다.

현재 실제 장소·사진·동행/시간 조건과 구현 수치는 제품 원문에서 관리한다. 숙박 상품·실시간 재고·예약·결제·가이드 동행은 이 설계만으로 제공을 약속하지 않는다. 10-07 공개판과 가상 시제품, 10-09 각 단계의 검사 기록은 제품 원문의 이력과 해당 QA에서 보존한다.

## 0 2026-10-09 전면 재설계 — 현재 작업 기준

사용자가 공개판의 그래픽과 개인화 부족을 지적하고, 실제 여행 경험 전체의 재설계와 Atlas 활용을 요청했다. 아래가 이번 개발의 기준이다. **설계 확정과 구현·로컬 검증·공개 운영·실제 이용자 만족은 각각 구분한다.** 기존 48개 조건 사전과 숙박·국가 확장 방향을 버리지 않으며, 현재 실제 데이터가 있는 서울에서 사용자 경험을 먼저 끝까지 연결한다.

### 사용자가 얻을 결과

“부모님과 오후 네 시간, 많이 걷지 않고, 식사와 차까지 예산 안에서 즐기기”를 입력하면 장소 이름 목록 대신 사진·지도·시간표·전체 비용의 확인 범위·추천 이유가 함께 나온다. 한 장소를 고정하고 다른 곳을 바꾸면 남은 경로·도착 시각·비용이 다시 계산된다. 비·피로·늦은 시작은 이번 여행의 조건으로만 적용한다. 다음에도 기억할 선호는 별도로 본인이 확인한다.

### 화면과 상호작용

1. **출발 화면:** 실제 지역 사진과 짧은 가치 제안, 날짜·시간·출발점·동행·예산의 첫 입력. 장소 탐색도 바로 가능하다. 가상 업체 시뮬레이션은 기본 사용자 흐름에서 분리한다.
2. **추천 결과:** 같은 코스의 지도와 시간표를 한 화면에 놓는다. 사진·분야·이유·예상 체류, 도보 구간, 확인된 비용과 미확인 비용을 표시한다. 최초 결과 전 설명문·저장 동의를 길게 늘어놓지 않는다.
3. **바꾸기:** 장소 유지/제외/직접 교체, 덜 걷기, 예산 낮추기, 실내 위주, 늦게 시작을 제공한다. 적용 전에 바뀐 장소·시간·금액과 유지된 조건을 비교하고 사용자가 결과를 선택한다. 미확인 필수조건을 타협으로 자동 승격하지 않는다.
4. **가져가기:** 새로고침 복원, 날짜·조건·일정 저장, 다른 기기에서 검증해 가져올 여행 파일과 개인 선호를 뺀 공유용 일정 제공. SYNK ID에는 기존 유학 PATH의 `path`와 별개 `path-travel` 자원을 사용한다. 운영 등록·배포 전 계정 저장 완료를 표시하지 않는다.
5. **여행 중/이후:** 완료·건너뜀 자기보고와 다시 출발할 시각·위치·남은 예산·도보를 입력해 남은 1~5곳을 비교한다. 수락 때만 바꾸고 취소·후보 없음은 기존 계획을 보존한다. 마치기·진행 정정·재개를 제공하며 만족/아쉬움과 다음에도 반영할 선호는 별도로 확인한다. 클릭·저장·완료 표시는 만족도 평가가 아니다. 한 번의 후기를 업체의 객관적 혼잡도·청결로 바꾸지 않는다.

시각 기준은 순백 바탕, 승인 로고·SUIT, 실제 펠트 조작 부품, 근거 있는 실제 장소 사진이다. 가짜 여행 사진이나 서로 다른 장소의 사진을 대신 쓰지 않는다. 사진 없는 장소는 출처 링크와 정보 중심 카드로 표현한다. 모바일에서는 조건 입력·결과·지도 전환을 한 손으로 쓸 수 있게 하고 상세 출처는 펼침 안에 둔다. 지도는 실제 좌표와 출처 있는 도로 자료를 쓰며 선형 장식 그림을 길안내로 표시하지 않는다.

### 데이터와 판단 계약

- 장소 속성마다 출처·확인일·범위·불확실성을 둔다. 실내/야외·문화 종류와 같이 확인 가능한 사실부터 개인화한다. 조용함·대기·접근성은 근거가 없으면 미확인이다.
- 실제 업체와 가상 업체의 입력·후보를 섞지 않는다. 공식 운영 구간, 마지막 입장, 전체 체류가 끝나는 시각을 검증한다.
- 여행 분야 모듈이 후보 코스를 구성하고 이동·시간·비용·필수조건을 검사한다. 공통 Core는 확인된 선언과 실제 후보 특성을 비교한다. 동점은 안정적으로 처리한다.
- 지도 기반 경로도 예상이다. 출처시각, 스냅 지점의 불확실성, 신호·공사·대기·시설 내부 이동의 미포함 범위를 남긴다. 걷기 상한은 예상 범위의 상단으로 검사한다. 접근성 조건을 확인하지 못하면 “계단 없음”으로 추론하지 않는다.
- 성인/아동 비용 단위를 분리한다. 무료·금액 확인·예시 메뉴·미확인을 구분하며, 확인하지 못한 아동 가격을 성인 가격으로 임의 계산하지 않는다. 부분합을 전체예산 확정으로 표시하지 않는다.
- 원하는 장소 수보다 시간·예산·걷기·필수조건이 우선한다. 짧은 대안을 낼 때 줄인 이유를 보이며 후보 없음은 실패 원인과 수정 가능한 조건으로 설명한다.

숙박의 날짜별 실제 객실·재고·요금, 국가/도시 추가, 실시간 날씨·혼잡·예약은 공급자 계약과 데이터가 필요한 후속 단계다. 이번 재설계의 전체 구조에는 포함하지만, 연결되지 않은 기능은 화면에서 작동한다고 약속하지 않는다. 당일 실제 여행과 숙박 검색 계약을 분리해 한쪽의 완성을 다른 쪽의 증거로 쓰지 않는다.

**후속 개인화 보강(2026-10-09):** 세부 음식·카페 8개 선호/회피, 한 구간 도보 상한, 일정에 포함되는 휴식, 실제 두 답의 일정 비교 질문을 연결했다. 식음료 8곳의 공식 메뉴·가격 단위·운영 충돌·예약/입구 근거를 보강했다. 현재 여행 검사 228/228·공개후보 빌드 7/7·개인자료 서버 21/21, 로컬 1280·390·320px 흐름 확인. 구현·공식 자료 확인이며 현장 만족도 효과가 아니다. ### 2026-10-09 여행 중 조정의 구현 계약

현재 날짜가 된 여행에서 다녀온 곳·건너뛴 곳을 직접 표시하고 다시 출발할 시각과 대표 역/장소 위치, 앞으로 쓸 일행 전체 예산과 도보 상한을 입력한다. GPS·실제 출입·지출을 자동 확인하지 않으며 이전 일정의 표시 비용을 쓴 돈으로 가정하지 않는다. 완료한 분야의 필수 포함은 충족한 것으로 처리하고 남은 유지 장소·시간·예산·도보·휴식·필수조건은 재검사한다. 일반 하루 계획은 최소 2곳, 남은 일정은 최소 1곳이다.

`memory.progress`는 날짜·보고 시각·완료 장소와 시각·건너뛴 장소·원래 필수 분야·마침 여부·수정 시각을 보관한다. 완료/건너뜀은 중복·교집합 없이 해당 판의 당일 후보 안에서 기록하며 남은 동선과 제외 목록이 일치해야 한다. 후보 수와 읽기 호환성은 제품 원문의 현재 자료·저장 계약을 따른다. 완료 시각은 사용자가 입력한 시각까지 방문했다는 표시다. 마친 여행은 `plan:null`이고, 정정 후 원래 필수 분야를 다시 고려해 재개할 수 있다. 이전 v4 파일에 진행 기록이 없어도 불러온다.

진행 수정은 미리보기 수락 때만 적용하며 취소·잘못된 조건·가능한 후보 없음은 기존 여행을 유지한다. 진행 기록은 동의한 브라우저와 검증한 JSON 파일에 포함된다. 완료 표시로 방문 평가·평소 선호·Temper 만족도 결과를 만들지 않으며 방문 경험은 별도로 남긴다. **여행 246/246, 서버 개인자료 21/21과 생성본 검사 통과**. 로컬 브라우저 진행·취소·적용·저장 후 새로고침의 범위는 [이번 증거](../experiences/path-travel/qa/progress-20261009/README.md)를 따른다. 원격 배포·운영 DB 적용·실계정·현장 만족도 검증은 별개다.

## 1 제공할 가치

같은 도시, 같은 예산으로 가더라도 여행자가 좋아할 하루는 다르다. 숙소에는 아끼고 음식에 쓰고 싶은 사람, 숙면과 이동 편의를 위해 숙박비를 더 내는 사람, 클럽보다 조용한 바를 좋아하는 사람을 구별한다. 같은 사람도 혼자 갈 때와 부모님·친구와 갈 때는 다른 계획이 필요하다.

서비스의 목표는 조건의 개수를 늘리는 것이 아니라 **그 사람에게 중요한 선택을 정확하게 바꾸는 것**이다. 나라별 장소 데이터에 여행자의 소비 우선순위·취향·피로·동행 관계를 대조하고, 식당 하나가 바뀌면 이동과 다음 일정까지 다시 맞춘다. 장소의 별점, 숙박 등급, 비싼 가격을 개인 적합도의 대리값으로 쓰지 않는다.

장기 차별화는 네 가지에서 만든다. 사용자가 확인한 취향이 다음 여행에도 이어지고, 나라가 바뀌어도 취향의 의미를 옮겨 적용하며, 추천 이유와 포기한 조건을 설명하고, 실제 여행 후기를 다음 선택에 반영한다. 경쟁 서비스에도 맞춤 여행 기능이 있으므로 독점 기능이나 검증된 우위를 약속하지 않는다.

## 2 사용자가 겪는 흐름

1. **이번 여행을 알려 준다.** 목적지 또는 원하는 여행 분위기, 날짜·도착/출발 시간, 동행 구성, 예산 범위와 포함 항목, 꼭 지킬 조건을 받는다. 미정은 미정으로 둔다.
2. **짧은 선택으로 취향을 좁힌다.** 5~7개의 질문을 첫 설계값으로 삼되 필요한 것만 묻는다. 선택한 이유가 불분명하면 한 번 더 확인한다. 이 문항 수는 사용성 시험 뒤 조정한다.
3. **첫 여행안과 다른 방향의 대안을 받는다.** 기본안, 비용을 줄인 안, 중요한 경험에 더 쓴 안을 비교한다. 엄격한 예산을 넘는 대안은 가능한 추천과 분리한다.
4. **마음에 안 드는 부분을 바꾼다.** “이 호텔은 좋아요. 그런데 수영장은 필요 없어요”, “유명해도 줄 서기는 싫어요” 같은 교정으로 선택 근거를 고친다. 확정한 예약은 잠근다.
5. **여행 중 필요한 부분을 조정한다.** 사용자가 알려 준 피로·비·휴무·지연에 맞춰 남은 일정을 바꾼다. 위치 사용은 선택이며 수동 출발지 입력도 제공한다.
6. **다녀온 경험을 남긴다.** 식당을 저장한 것, 예약한 것, 방문했다고 알린 것, 만족한 것을 구분한다. 다음 여행에도 기억할 취향은 따로 확인한다.

‘집요하게 파악한다’는 말은 긴 설문을 견디게 한다는 뜻이 아니다. 질문을 건너뛰어도 기본안을 주고, 결과를 보여 준 뒤 비교·교정·후기로 더 정확해지는 흐름이다. 모르는 항목을 전부 채우려 하지 않는다.

## 3 개인화 조건 48개

다음은 조건 사전 초안이다. 각 줄의 네 항목을 따로 저장·교정할 수 있게 설계한다. 모든 이용자에게 48개를 묻거나 동일한 가중치를 적용하지 않는다. 조건은 필요에 따라 필수·선호·무관으로 구분한다.

재산이나 소득을 추정해 ‘부자/가난한 사람’으로 고정하지 않는다. 필요한 것은 본인이 밝힌 이번 여행의 지출 여력과 의향이다. 나이·성별·국적·직업으로 소비 수준이나 유흥 취향을 짐작하지 않는다. 식이·접근성은 필요한 조건만 선택적으로 받고, 종교·질병의 이유를 요구하지 않는다. 알레르기와 같은 필수 조건은 업체의 확인 없이 충족했다고 표시하지 않는다.

상품의 요금·이용 자격은 취향 추정과 구분한다. 가족 객실·아동 요금, 야간 업소 입장, 렌터카 이용처럼 공급자가 실제로 요구할 때만 성인/아동 구성·필요 연령대·입장 또는 운전 자격 충족 여부를 확인한다. 추천 단계에서 여권·면허 원본을 요구하지 않으며, 미확인 자격은 ‘확인 필요’로 남긴다. 자격 조건을 통과했다는 이유로 해당 활동을 좋아한다고 해석하지 않는다.

## 4 취향을 알아내는 질문과 기억

질문은 추천을 바꿀 수 있을 때 낸다. “여행 스타일이 무엇인가요?”처럼 큰 분류를 고르게 하는 질문보다 실제 비용·시간의 교환을 보여 준다. 다음 예시는 가상이며 현지 가격이나 실제 숙소를 뜻하지 않는다.

| 비교 질문 | 파악하는 것 | 피할 해석 |
|---|---|---|
| 같은 조건이라면 역 앞 숙소에 1박 3만 원을 더 낼까요? | 이동 편의에 대한 지출 의향 | 비싼 쪽을 골랐으니 재산이 많다는 판단 |
| 같은 가격이라면 한적한 식당과 유명하지만 40분 기다리는 식당 중 어디가 좋을까요? | 유명세 대비 대기 부담 | 한 번의 선택을 평생 취향으로 고정 |
| 오늘 밤은 대화하기 좋은 바, 라이브 공연, 클럽, 쉬기 중 무엇이 좋을까요? | 이번 여행의 밤 활동 | 음주·사교성·성격을 자동으로 단정 |
| 숙소를 낮춰 특별한 저녁 한 끼를 넣을까요, 숙면에 더 쓸까요? | 분야 간 우선순위 | 복합 선택에서 모든 세부 이유를 안다고 가정 |

선택 장면에서 달라진 조건이 여러 개면 이유를 확인하거나 한 조건만 바꿔 다시 비교한다. Core의 질문 가치 계산은 제품이 준비한 선택지·후보를 전제로 한다. 답 분포가 없으면 기대값은 설계 가정이며, 실제 사람을 정확히 이해하는 능력이 검증됐다는 뜻은 아니다.

기억은 세 층으로 나눈다.

- **평소 취향:** 사용자가 다음에도 쓰겠다고 확인한 조용한 숙소·긴 대기 회피 등의 선호.
- **이번 여행:** 이번 총예산·동행·기념일·고정 예약·이번에만 해 보고 싶은 활동. 여행 종료나 철회로 끝낼 수 있다.
- **지금 상황:** 현재 출발지·피로·남은 시간·오늘의 날씨. 만료 시각을 둔다.

각 값에는 출처, 확인 여부, 적용 범위, 확인 시각, 만료/철회 상태를 붙인다. 자유 대화에서 읽은 취향은 ‘이렇게 이해했어요’라는 제안으로 보이고 본인 확인 뒤 적용한다. 클릭·체류시간·한 번의 거절은 확인 질문의 단서일 수 있지만, 스스로 말한 취향보다 우선하지 않는다. 학습·상담·관계 앱의 자료를 여행 프로필에 자동으로 합치지 않는다. 여행 밖으로 가져갈 정보와 장기 저장 여부는 이용자가 고른다.

**현재 로컬 v4 구현:** 이번 여행의 날짜·시간·인원·예산·출발점·걷기·선호/필수조건과 본인이 확인한 평소 선호를 구분한다. 이번 입력이 평소 기억보다 우선하며, 방문 자기보고의 이유에서 제안한 선호는 별도 확인해야 다음 추천에 들어간다. 클릭·일정 선택·사진 열람을 취향이나 실제 방문으로 자동 확정하지 않는다. 방문 기록·선호는 수정·철회할 수 있고, 이전 저장본의 관심/방문 기록을 가져올 때 확인된 평소 선호로 자동 승격하지 않는다. 일반 자유 대화 AI와 48개 조건 전체를 실제 장소에 적용한 것은 아니다.

브라우저 저장은 동의 후에만 하고, 동의 철회는 저장본을 지우되 현재 화면을 유지한다. 여행 파일은 구조·장소 ID·시각·크기·계획을 검증해 가져오며 공유용 일정에는 개인 취향·방문 의견을 넣지 않는다. 다른 탭의 저장 변경을 감지하면 자동 저장을 멈춘다. 공통 계정의 충돌/오프라인 저장 계약과 여행 validator는 운영 연결로 이어졌다. 운영 합성 로그인·저장·삭제/철회 검증과 실제 이용자의 물리 두 기기 사용은 구분하며, 정확한 확인 범위는 위 배포 증거를 따른다. [저장 계약](../experiences/path-travel/planner-storage.mjs) · [후기와 확인 선호](../experiences/path-travel/planner-feedback.mjs) · [계정 경계](../experiences/path-travel/planner-account.mjs).

**이전 가상 v3 구현:** 평소와 이번 여행의 두 층을 구현했다. 직접 선택한 조건은 필수/선호/상관없음과 중요도 1~5를 가지며, 원선언 시각에서 30일이 지나면 재확인이 필요하다. 재계산이나 복원이 선언 시각을 새로 만들지 않는다. 이번 조건의 교정·철회, 평소로 복귀, 이번 조건을 종료하는 새 여행 시작을 제공한다. ‘아직 모름’은 평소 값을 잠시 가리는 별도 상태로 보관하고 엔진 관측에 보내지 않는다. 제한된 한국어 명시 조건을 읽는 로컬 해석은 연결했다. 문장 제안은 입력만으로 반영되지 않으며 원문·읽은 값·강도·기간을 확인하거나 고친 뒤 적용한다. 그대로 확인하면 원문+30일, 값 정정이면 새 선언+30일이다. 독립된 ‘지금 상황’ 층과 일반 자유 대화 AI는 아직 없다.

이전 가상 v3의 저장은 별도 동의한 브라우저에서만 했다. v1 기록을 옮길 때 새 취향 장부는 비워 두어 옛 설정을 확인된 취향으로 만들지 않는다. 다른 탭에서 저장을 지우면 삭제 이벤트를 받은 탭도 자동 저장을 중단한다. 원자적인 다중 탭 revision/충돌 조정과 운영 계정의 동의·삭제 체계까지 구현한 것은 아니다.

## 5 장소를 하루 일정으로 맞추는 방법

**필수 조건 → 사실 확인 → 가능한 일정 구성 → 선호 비교 → 설명** 순서로 처리한다. 필수 조건을 어긴 장소가 높은 취향 점수로 살아남게 하지 않는다.

1. 날짜·인원·예산·객실·식이·이동 요구와 고정 예약을 확인한다. 상충하거나 빠진 필수 조건이 있으면 가능한 초안 범위와 확인할 질문을 보여 준다.
2. 후보마다 위치·영업/체크인 시간·가격 조건·요금/이용 자격·자료 기준시각을 붙인다. ‘확인됨/조건 위반/확인 필요’를 구분한다.
3. 숙소를 출발점으로 식사·활동·이동·대기·휴식을 묶는다. 영업시간뿐 아니라 마지막 입장, 주문 마감, 예약 시간, 현지 시간대를 확인한다. 날씨나 교통 자료가 없으면 추정임을 표시한다.
4. 전체 비용을 공통 통화로 합산하되 환율 기준시각, 1인/전체·1박/전일 단위, 세금·필수 수수료·교통비·예비비의 포함 범위를 남긴다. 모르는 비용을 0으로 넣지 않는다. 상한을 확인할 수 없는 계획을 ‘예산 내 확정’으로 내지 않는다.
5. 가능한 묶음 중 개인 선호를 비교한다. 숙소가 싸더라도 추가 교통비와 잃는 시간이 큰지 함께 본다. 분위기·수면·청결처럼 확실한 측정이 어려운 속성은 근거와 불확실성을 유지한다.
6. 동행자별 필수 조건의 교집합을 먼저 찾고, 충돌하면 질문·일정 분리·조건 수정안을 제시한다. 평균 점수로 한 사람의 필수 조건을 지우지 않는다.
7. 결과 변경 시 잠근 예약을 보존하고 남은 시간·돈만 다시 계산한다. 취소 가능하다는 사실만으로 예약을 취소하거나 변경하지 않는다.

불가능한 요청에는 ‘완벽한 일정’을 만들지 않는다. “이 예산과 객실 조건을 모두 확인한 숙소가 아직 없어요. 지역을 넓히거나 날짜를 바꾸면 다시 찾을 수 있어요”처럼 막힌 조건을 알려 준다. ‘당신과 97% 일치’ 같은 검증되지 않은 확률 대신 무엇이 맞고 무엇은 타협했는지 설명한다.

## 6 결과물

결과 첫 화면에는 **추천 여행안, 총비용 범위, 나에게 맞는 이유, 아직 확인할 조건**을 놓는다. 지도와 시간표는 같은 일정을 보여 주어야 한다. 여행자는 지도로 위치를 보고, 시간표로 하루를 이해하고, 선택지를 바꾸며 계획을 완성한다.

| 결과 | 꼭 들어갈 내용 |
|---|---|
| 여행안 | 날짜별 식사·활동·이동·휴식, 도착/출발, 고정 예약, 자유시간 |
| 숙소 비교 | 실제 객실과 인원·날짜, 총액/포함 항목, 위치, 개인에게 필요한 시설, 취소 조건 |
| 식당과 경험 | 추천 이유, 맞지 않을 수 있는 점, 예약/대기/메뉴·입장 확인, 가까운 대안 |
| 예산표 | 분야별 합계, 이미 쓴 비용과 남은 비용, 환율·확인 시각, 미확인 비용 |
| 변경안 | “덜 걷기”, “식비 줄이기”, “오늘은 늦게 시작”, 변경 전후의 시간·비용 차이 |
| 가져갈 여행 계획 | 지도 링크·주소·일정·확인 항목을 저장/내보내기. 민감한 취향 설명은 공유본에서 제외 |

팁은 [맞춤 도구 제작 절차](마케팅/맞춤도구/제작절차.md)의 원칙을 적용한다. 숙소 위치·조식·무료 취소·교통패스 등 선택 요소마다 무엇인지, 필요한 이유, 비싼 이유, 필요 없는 경우, 함정, 직접 확인 방법을 준비한다. 밤늦게 돌아오는 사람에게 조식이 의미 있는지처럼 해당 여행자의 조건으로 골라 보여 준다. 이 문서는 계정과 외부 여행 데이터를 쓰는 PATH 제품 설계이며, 기존 무AI·기기 저장형 마케팅 도구를 유료 AI 제품으로 변경하는 지시가 아니다.

## 7 나라별 확장과 데이터

나라는 서비스를 확장하는 단위이며, 첫 품질 관리는 도시·동네·실제 날짜 단위로 한다. 같은 ‘조용한 바’, ‘걸어서 다닐 만한 숙소’, ‘가성비’도 도시의 가격대·교통·운영 방식에 따라 다르므로 공통 취향과 현지 기준을 분리한다.

여행자는 나라를 바꿔도 취향을 다시 전부 설명하지 않는다. 다만 이전 도시에서 적당했던 숙박비를 다른 도시에도 강제하지 않고 새 여행의 예산과 선택지를 확인한다. 특정 국적의 여행자가 같은 취향일 것이라고 간주하지 않는다.

| 데이터 층 | 맡는 것 | 추천에 붙이는 근거 |
|---|---|---|
| 장소·현지 맥락 | 위치·분류·주소·운영 안내, 현지에서 확인한 분위기 | 공급자/공식 안내, 확인 시각, 관찰 조건 |
| 날짜별 상품 | 실제 객실·요금제·인원·날짜별 가격과 재고·취소 조건 | 상품 식별자, 조회 조건/시각, 세금·수수료 포함 범위 |
| 이동·상황 | 이동 시간, 교통편, 시간대, 날씨, 임시 휴무 | 조회 조건/시각, 추정과 확인의 구분 |
| 개인 경험 | 선택·방문 자기보고·좋았던 이유·싫었던 이유 | 당사자·여행 범위·확인/철회 상태 |

출처마다 저장·갱신·표시 조건을 지킨다. 장소 서비스의 별점이나 가격대만으로 특정 날짜의 객실 재고와 총액을 만들 수 없다. 예약 직전에는 해당 공급자의 최신 조건을 다시 확인한다. 데이터가 오래됐거나 공급자가 응답하지 않으면 기존 초안과 마지막 확인 시각을 보여 주고 예약 가능하다는 표시는 거둔다.

첫 개발은 사람이 검수한 소수 도시 자료와 가상 가격·시간 자료로 시작한다. 실제 지역 추천으로 공개할 때는 지역별 원문 탐색, 가격·교통·장소 확인, 공급자 이용 조건과 갱신 방법을 갖춘다. 전 세계에 빈약한 추천을 펼치는 것보다 한 도시에서 조건이 다른 사람의 하루가 왜 달라지는지를 먼저 검증한다.

## 8 Atlas 담당과 새로 필요한 능력

Atlas는 기존 8개 엔진의 총칭이다. 여행이라는 이유로 여덟 엔진을 모두 연결하거나 별도 여행 판단 엔진을 신설하지 않는다.

| 담당 | 여행에서 쓸 역할 | 현재 기반과 추가 범위 |
|---|---|---|
| **Core** | 평소/이번/현재 조건 구분, 확인된 선호, 필수 조건, 후보 비교, 결과를 바꾸는 질문 | 현재 v4는 `domain.js`·`travel.js`·`ask.js`를 재사용해 실제 후보의 필수조건·선호·변경 질문을 연결한다. 이전 가상 v2는 `personalization.js`의 `preferences.toDomain`과 `domain.js`의 `objectives`를 추가했다. 원선언의 값·기간·시각·사건 ID를 유지하고 기본·예시 정렬 정책을 사용자 취향과 분리한다. `travel.js`는 묶음 적격성, 기존 `ask.js`는 기본·세부 질문 비교를 맡는다. 이전 가상 v3는 기존 Interpretation의 원문·본인·현재·충돌·검토 검증을 재사용하고 확인된 문장과 선호 사건의 계보를 PATH에서 연결한다. 일반 자유 대화 해석·독립된 지금 상황 층은 후속 |
| **Vellum** | 왜 맞는지, 어떤 조건이 달라져 바뀌었는지, 무엇을 확인해야 하는지 설명 | 현재 v4는 제품 템플릿 설명이며 Vellum 호출은 미연결이다. 향후 기존 도움·이유 표현 계약을 적용하더라도 장소 사실을 생성하지 않음 |
| **Trail** | 추천→선택→방문/자기보고→평가→다음 추천의 이력 | v4 `planner-feedback.mjs`에서 기존 `trail-life.js`를 재사용해 여행 사건·출처·정정/철회를 연결했다. 이동 경로 계산이나 일정 최적화를 맡는 엔진으로 바꾸지 않음 |
| **Temper** | 실제 전달과 결과 구분, 질문 전후 차이, 잘못된 추천과 여행 후 만족 검증 | v4는 기존 `temper-outcomes.js`로 화면 노출과 방문/전체 여행 결과를 구분해 기록한다. 클릭을 만족·방문 성공으로 간주하지 않으며 실제 만족도 효과는 미측정 |
| **Loom** | 계획표·지도·비교의 표현 | v4 화면에서 기존 `tools/lib/loom-motion.js`를 재사용한다. 장소를 고르는 판단을 맡지 않으며 화면 확인 범위는 제품 원문·배포 증거를 따른다 |

Prism은 충분하고 적법하게 쓸 집계가 생겼을 때 검토한다. Reed는 음성 안내, Strata는 현지 언어 학습 기능이 필요해졌을 때 검토한다. 어느 것도 첫 여행 추천의 필수 연결이 아니다.

현재 공통 모듈은 여행 추천 완제품이 아니다. **로컬 v4는 PATH가 실제 장소·OSM 길망으로 후보 일정을 구성하고, Core가 선호와 필수조건을 비교하며, Trail·Temper가 추천 노출과 방문 자기보고/결과의 관계를 남기고, Loom이 화면 움직임을 맡는다.** 네 엔진의 기존 코드 재사용이며 엔진 기능 발전으로 보고하지 않는다. 미확인 필수조건은 점수로 충족 처리하지 않고, 취향·후기는 장소 사실을 바꾸지 않는다. Temper의 사건 연결은 실사용 효과나 만족도 개선의 인과 증거가 아니다. Vellum은 실제 호출하지 않았다. 실제 상품·교통 공급자 연동은 PATH 제품이 맡으며 공통 판단 능력은 [Core 원문](코어엔진_설계.md#travel-bundle-design)의 담당 범위에서 발전시킨다.

**이전 가상 v3 기록:** 당시 로컬 v3는 **PATH가 가상 여행 묶음을 만들고, 원시 조건과 선언 사건을 Core 관측·판단에 전달한 뒤 결과 설명으로 연결**한다. 후보 자료가 없는 선호는 미확인으로 남기고, 미확인인 필수 조건은 가능한 추천에서 차단한다. 기본·예시 설정은 `declared` 0개에서 시작하며 `any` 상태도 사용자 취향으로 엔진에 전달하지 않는다. JSON 내보내기로 원선언과 실제 엔진 전달·설명 기록을 검토할 수 있다. 그 당시에는 Trail 여행 사건·Temper 결과 연결·Vellum 호출을 하지 않았다. 실제 상품·이동 자료로 확장할 때도 공통 판단 능력은 [Core 원문](코어엔진_설계.md#travel-bundle-design)에서 발전시키고, 나라별 자료·상품·교통 공급자 연동은 PATH 제품이 맡는다.

## 9 같은 목적지에서 달라지는 여행 예시

가상의 세 여행자이며 실제 장소·가격 추천이 아니다. 나라와 총예산이 같아도 다음처럼 결과가 달라져야 한다.

| 여행자 | 확인한 선호 | 달라지는 계획 |
|---|---|---|
| A | 숙소는 청결하면 충분, 로컬 음식에 더 쓰기, 긴 대기는 싫음, 도보 가능 | 실속형 숙소를 기준으로 가까운 로컬 식당을 묶고 특별한 식사에 예산 배분. 유명 대기 식당은 대안으로 교체 |
| B | 숙면·전망 우선, 택시 선호, 조용한 바, 아침은 늦게 | 소음 근거를 확인한 숙소에 더 쓰고, 저녁 식사와 바의 귀가 동선을 짧게 구성. 다음 날 오전 여백 |
| C | 친구끼리 공연·클럽, 숙박비는 나눔, 첫날 도착이 늦음 | 늦은 체크인과 객실 인원 조건을 먼저 확인. 공연/클럽 취향과 귀가수단을 묶고 첫날·다음 날 활동량을 줄임 |

이 차이는 소개 문구만 바뀌는 것으로 통과하지 않는다. 실제 숙소 조건·식당 후보·예산 배분·시간표·질문 가운데 관련된 결과가 달라져야 한다. 반대로 여행과 무관한 프로필 항목을 바꿨을 때 결과가 흔들리면 안 된다.

## 10 개발 순서와 완료 기준

첫 시제품 도시는 사용자 선택으로 **서울**이며 무료 체험을 공개했다. 유료 서비스의 대상 고객·판매 가격·첫 출시 지역은 아직 확정하지 않았다. 현재 v4는 실제 장소·공개 길망·기록 연결을 공개했고, 운영 계정의 합성 저장·복원까지 확인했다. 이전 가상 v3와 현재 실제 장소 구현 모두 아래 단계의 제한된 범위이며, 날짜별 숙박 상품·실사용과 아래 반례 전체를 완료했다고 보지 않는다. 상세 구현·미구현 경계는 [README](../experiences/path-travel/README.md)를 따른다.

| 단계 | 만드는 것 | 완료를 판단할 증거 |
|---|---|---|
| 1 로컬 핵심 | 한 도시의 검수/가상 자료, 첫 질문, 조건 비교, 숙소·식사·하루 일정, 변경 전후 차이 | 아래 반례를 재현하고 필수 조건을 지킨 결과. 유료 AI·실시간 API 없이 검사 가능 |
| 2 실제 데이터 연결 | 장소와 날짜별 숙박, 이동 데이터, 갱신·장애·재조회 | 계약된 공급자 자료로 날짜·인원별 실제 조건 일치. 비용이 드는 연결·검증은 출시 준비 시점에 진행 |
| 3 현지 여행 확인 | 소수 이용자의 계획 사용과 여행 후 확인 | 실제 불편·추천 채택 이유·예산 편차·이동 무리·재사용 의향. 합성 검사와 별도 기록 |
| 4 다음 도시 | 같은 사람의 취향을 다른 도시에서 적용 | 기존 기억의 유용함과 현지 차이 확인, 도시별 자료 품질과 운영 능력 |

최소 반례는 다음과 같다.

- 예산이 같고 지출 우선순위만 다르면 배분과 추천 이유가 달라진다.
- 필수 식이/접근성 조건을 확인할 수 없으면 충족으로 표시하지 않는다.
- 높은 취향 점수여도 휴무·시간 충돌·초과 예산이면 실행 가능한 안에서 제외한다.
- 누락 비용·세금·환율·가격 단위를 처리하며, 불명 금액을 0으로 넣지 않는다.
- 늦은 도착·자정 이후 영업·현지 시간대·다음 날 일정을 올바르게 잇는다.
- 날씨·피로 변경 시 고정 예약을 보존하고 남은 일정만 다시 맞춘다.
- 동행자의 필수 조건이 충돌하면 평균으로 숨기지 않는다.
- 성인/아동 구성에 맞지 않는 객실·요금과 입장/운전 자격이 확인되지 않은 상품을 이용 가능한 안으로 확정하지 않는다.
- 이번 여행의 소비 성향이 평소 취향을 덮지 않고, 철회/만료한 정보가 다음 추천에 남지 않는다.
- 후기를 쓰지 않거나 추천을 누르지 않았다는 이유만으로 싫어한다고 학습하지 않는다.
- 공급자 장애·오래된 자료·후보 없음에서 이유와 확인할 항목을 보여 준다.

질문 수·결과까지 걸린 시간·직접 수정 횟수·조건 위반·가격/시간 불일치·방문 후 만족을 함께 본다. 질문이 적어졌다는 이유만으로 추천이 좋아졌다고 결론 내리지 않는다. 기존 정렬 또는 첫 초안과 동일 조건에서 비교하고, 이용자 결과는 여행 형태·자료 시점과 함께 기록한다. 성과 수치와 개선 목표값은 파일럿 설계 때 정한다.

## 11 사업 운영과 수익 방식

PATH는 여행자의 계획과 현지 경험을 담당하고 SYNK는 공통 개인화 기술을 관리한다. 기존 방문·문화 체험의 초기 제휴 운영사 연결 방향을 유지한다. 첫 고객 후보는 한국 방문·체류 고객이며, 나라별 여행 확장은 이번 방향에 포함하되 첫 출시 지역은 자료와 현지 확인 능력에 따라 고른다.

수익 방식은 무료 기본안, 여행 1회별 상세 계획·수정, 잦은 여행자를 위한 구독, 희망자 현지 컨시어지·제휴 예약 연결을 비교할 수 있다. 가격과 유료 범위는 가설이다. 예약 수수료가 추천 순위를 바꾸지 않게 하고 광고·제휴 여부를 구분한다. 제휴되지 않은 곳도 적합하면 후보에 넣는 구조를 검토한다.

초기 제공물은 추천·계획이며 예약·결제·가이드 동행·24시간 대응은 실제 운영 범위를 갖춘 뒤 별도 상품으로 정한다. 국가별 운영 요건과 책임 주체는 판매 방식이 정해질 때 확인한다. 외부 API와 AI 비용, 사람이 검수/수정하는 시간, 실제 데이터 오류 처리 비용을 함께 측정한 뒤 가격을 정한다.

대외 소개 초안: **“어디에 쓰고 무엇을 즐길지, 당신의 취향에 맞춰 여행을 준비합니다. 식당·숙소·하루 동선까지, 왜 잘 맞는지 함께 알려 드립니다.”** 이는 장기 제공 범위의 소개 초안이다. 공개 서울 체험 안내에서는 실제 제공 기능을 제품 원문에 맞추고, 숙박 추천·현지 운영이 완료된 것처럼 사용하지 않는다.
