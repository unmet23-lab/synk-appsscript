# SYNK 동기화 구조 — 상담 접수 → 운영 시트 → Supabase → SYNK-talk

> 2026-09-11 현재 작업본의 실행 코드로 갱신한 운영 지도. 함수명으로 실제 구현을 찾는다. 코드 대조는 원격 설정·배포·실학생 반영 확인을 대신하지 않는다.
> Notion은 2026-08-04 워크스페이스 삭제, 08-26 동기화 코드 제거로 종료됐다. Glide도 현재 앱 통로가 아니다. 역할의 현행 배치는 [운영 정본 6부](<정본/SYNK LAB/About Syestem/SYNK_리라이팅_v2/05_운영_시스템.txt>)를 따른다.

## 0. 데이터 흐름

```text
크루카드 / Google Form
  ↓ 접수 기록 (Google Form은 parentSweep → importFormResponses)
상담 스프레드시트: 상담데이터입력 / 수강·납입
  ↓ 사람의 반배정 확인 → 학생ID_발급_
  ↓ syncProfiles
운영 스프레드시트: profiles
  ├─ calcAll → 현재급수 등 운영 계산 갱신
  ├─ 명부스윕_ → Supabase roster-ingest → engine.learners 등 허용된 명부 필드
  │                                        ↓ 권한을 확인하는 서버 통로
  │                                     SYNK-talk
  └─ 궤적갱신_ → outcome_log / trajectory (운영 내부 기록)
       ↑ 의도와 결과는 상담시트·면접 응답에서 읽는다
```

폼 제출만으로 학생ID를 발급하지 않는다. 접수는 `신규접수`로 기록하고, 사람이 `반배정` 또는 `앱편입` 상태를 확인한 뒤 `학생ID_발급_`가 발급한다. Supabase 명부 수신도 계정이나 동의를 자동 생성하지 않는다. 첫 계정 등록과 동의는 SYNK-talk의 별도 계약을 따른다.

학생 서비스의 데이터층은 Supabase이고, 시트는 상담 접수·명부 운영·계산·리포트의 연결 경로다. `profiles` 모든 열이 Supabase나 앱으로 복사되는 구조가 아니다.

## 1. 설정을 확인하는 위치

실제 ID·연락처·키 값은 이 문서에 복제하지 않는다.

| 이름 | 용도 / 보관 위치 |
|---|---|
| `CONSULT_SHEET_ID` | 외부 상담 스프레드시트 참조. `Code.js` 상수와 실제 공유 권한 확인 |
| 운영 스프레드시트 | Apps Script에 연결된 컨테이너. `SpreadsheetApp.getActiveSpreadsheet()`로 열림 |
| `ROSTER_INGEST_URL` | 명부 수신 함수 주소. Apps Script Script Properties(스크립트 속성)에 보관 |
| `ROSTER_INGEST_KEY` | 명부 수신 함수 전용 비밀값. 같은 환경의 Supabase `ROSTER_INGEST_SECRET`과 일치해야 함 |
| `ROSTER_INGEST_ANON` | Supabase 플랫폼 요청용 키. 명부 권한 판정은 별도로 `x-roster-ingest-key`가 맡음 |
| `ADMIN_EMAIL` | 운영 실패 알림 수신 설정. 실제 값은 담당 설정에서 확인 |

`명부스윕_`는 세 `ROSTER_INGEST_*` 속성 중 하나라도 없으면 요청 없이 종료한다. 속성 존재·인증 성공·명부 처리 성공·앱 조회 성공을 각각 확인한다. 학생 기록 없는 `{}` 요청이 `bad_body`를 반환한 것은 인증 통과의 증거이며 명부 등록 성공은 아니다. DB 전체 권한인 `service_role`을 Apps Script에 추가하지 않는다.

### 가드 (데이터 사고 방지) — 디버깅 시 필독
1. **연결 실패 방어** (`try/catch` — `엔진_운영배치.js` `syncProfiles` 도입부): 상담시트 못 열면 profiles를 **마지막 정상 상태로 유지**하고 원장에게 실패 메일. 아침 분할 배치에서는 후속 계산·명부 전송의 선행 조건도 통과시키지 않는다. → profiles가 안 바뀌면 매일 아침 메일함 확인.
2. **퇴소자 제외**: `payStatus === '퇴소'`면 profiles에서 빼되, 삭제 전 전 열을 `exit_snapshot`에 보존하고 `exit_log`에 사건을 남긴다. 종료사유·종료일은 사람이 확인할 칸이다. Supabase 학생 계정 삭제를 뜻하지 않는다.
3. **비학생 행 보존**: teacher/parent/admin 행은 매 동기화마다 지워지지 않고 재기록 (`syncProfiles` 내부).
4. **학생 급감/0 가드** (`syncProfiles` 내부): 기존 자료가 있는 상태에서 새 동기화 대상 학생이 **0명** 이거나, 기존 5명+ 인데 **30% 넘게 급감**하면 → **profiles 덮어쓰기 보류** + 원장 알림.
   - **v9.22b dedup**: `app_state`의 `동기화보류_상태`(= `신규/기존` 시그니처)가 바뀔 때만 1회 알림. 빈 상담시트가 매일 경보 도배하는 것 방지. 정상 동기화 시 시그니처 초기화(재무장).
5. **created_at 안정화** (v9.22 — `syncProfiles` 내부): 예전엔 매일 `now`로 덮여 "가입 경과일" 기반 리텐션이 고장 → 등록일 우선 → 보존값 → now 순으로 확정.

## 3. 상담서술과 동의

상담시트의 `📝자유서술→노션`은 현재 코드가 읽고 쓰는 **과거 호환 열 이름**이다. 실제 보관 장소는 상담시트이며 이름에 남은 서비스로 전송한다는 뜻이 아니다. 이름만 일괄 치환하면 폼 응답·크루카드 서술·동의 판정·강사 고충 표시가 함께 끊길 수 있다. 개명은 생산자·소비자·실제 시트·기존 기록의 호환을 함께 이관한다.

폼 질문은 헤더 이름으로 대응한다. 1~59열과 63열 이후에 응답을 쓰고 60~62열 학생ID·자동 계산 구간은 보호한다. 대응 헤더 없는 응답과 동의 증빙은 자유서술 칸에 보관한다.

- 동의 버전은 `엔진_폼리포트.js`의 `CONSENT_VERSION`이 정한다. `migrateConsentV186()`라는 기존 함수명과 현재 적용 버전은 다를 수 있다. 폼 문구와 실제 시트 열이 모두 준비됐을 때에만 `상담동의` 상태를 기록한다.
- `음성동의`는 별도 헤더이며 녹음 관련 소비자가 확인한다. 자유서술의 동의 표식은 `consultRowConsented_` 등이 읽고, 표식 없으면 고충을 강사 뷰에 싣지 않는다.
- 문구 개정과 명부 수신 성공은 과거 학생의 동의 범위를 확대하지 않는다. 수신 함수는 신규 명부에 동의가 없는 경우를 알리고 동의를 대신 만들지 않는다.
- 학생 원문·연락처·음성·상담 메모를 저장소나 공개 콘텐츠로 옮기지 않는다. 활용·철회는 [SYNK-talk 동의 문구](../../SYNK-talk/docs/동의_문구_v1.md)와 [L0 데이터 계약](../../SYNK-talk/docs/L0_데이터계약.md)을 따른다.

## 4. profiles → Supabase → SYNK-talk

보내는 쪽: `엔진_운영배치.js`의 `명부스윕_()`. 받는 쪽: SYNK-talk `supabase/functions/roster-ingest/index.ts`. 명부 판정은 서버 동봉 `명부규칙.mjs`와 원천 `lib/명부규칙.js`를 따른다.

### 전송 계약

- profiles A:H를 **표시값**으로 읽어 머리글과 함께 보낸다. 연락처 앞자리 0을 보존하기 위해 숫자로 재해석하지 않는다.
- `현재급수`와 `입학시즌`은 헤더 이름으로 찾아 있을 때만 동봉한다. 급수는 `calcAll()`이 먼저 계산한 값을 보낸다. 입학시즌은 기존 값 우선이며 서버에서도 빈 값만 채운다.
- 빈 행과 `DEMO-` 시연 행만 원천에서 제외한다. 역할·학생번호·연락처의 적합성은 서버 공용 규칙이 판단한다.
- `groups`의 현 시즌 조·좌석을 함께 보낸다. `조편성` 키 없음은 **모름·변경 없음**, 빈 배열은 **확인된 빈 편성·기존 배정 해제**다. 둘을 서로 바꾸지 않는다.

### 처리와 제한

수신 함수는 전용 비밀값과 헤더·행을 검증한 뒤 정상 명부를 `engine.learners`에 추가하거나 허용된 반·급수·입학시즌 필드에 반영한다. 같은 입력 재전송과 경쟁 삽입은 중복 학생을 만들지 않게 처리한다. 조·좌석과 담당 반 연결은 해당 서버 계약을 따른다.

연락처 불일치는 기존 값을 덮어 해결하지 않는다. 반이 비었다고 기존 반을 자동 해제하지 않으며 잔존 수를 알린다. 앱 계정·동의·모든 profiles 열·관찰 메모를 이 함수 하나에서 생성하거나 복제하지 않는다. 문제 행은 알리고 정상 행은 처리한다.

HTTP 200만으로 모든 행이 반영됐다고 결론 내리지 않는다. 응답의 읽은행·넣음·건너뜀·막힘·문제들·무동의·반비움잔존·조편성문제를 함께 확인한다. 같은 문제는 `명부스윕_상태`가 바뀔 때 알리고 해소 시 상태를 비운다.

## 5. 실행 순서와 진단

주기 정의는 `엔진_셋업확장.js`의 `resetAllTriggers` 및 `triggerManifest_`를 확인한다. 아래 시각은 코드의 시간대별 예약이며 정확한 분 실행이나 라이브 설치 상태를 보증하지 않는다.

| 증상 | 먼저 확인할 곳 |
|---|---|
| 접수는 있는데 학생ID가 없음 | 처리상태, 사람의 반배정 확인, `학생ID_발급_` 실행 증거 |
| profiles가 오래됨 | 상담시트 권한·탭·ID, 동기화 실패 및 `동기화보류_상태` |
| profiles는 최신인데 앱 명부가 오래됨 | 계산·명부 전송 단계의 선행 상태, 명부 수신 3속성, `명부스윕_상태` |
| 명부 요청 401 / 503 / 400 | 전용 비밀값 불일치 / 서버 비밀값 미설정 / 본문·헤더·행수 오류 |
| 요청 성공 후 특정 학생만 없음 | 문제 행·역할·번호·연락처 충돌. 학생 계정 등록과 앱 권한은 별도 확인 |
| 반·조가 오래되거나 없어짐 | 반 빈 값 잔존, 현 시즌 groups, `조편성` 키 없음과 빈 배열의 차이 |
| 상담 고충이 안 보임 | 자유서술 보관 열·행별 동의 표식·실제 동의 문구 적용 상태 |

## 7. 궤적 레일 — 의도 × 결과 (`outcome_log` · `trajectory`)

**파일:** `엔진_궤적.js` · **진입점:** `궤적갱신_(src)` — `syncProfiles` 말미에서 **매일 아침 1회**.

왜 여기가 발동층인가: ① 그 함수가 이미 상담시트를 열어 두었다(openById 중복 회피) ② morningJobs가
매일 부른다 = **스스로 발화하는 자리**다. 메뉴 버튼을 일부러 안 만들었다 — 유호님이 눌러야 도는 장치는
결국 안 눌린다. 실패는 자체 try로 격리되고(로스터 동기화는 이미 끝나 있다), 상태가 바뀔 때만 1회 알린다.

### 왜 있나
로드맵 ④(유학 집약 봇)의 유일한 비복제 자산은 **「무엇을 목표했고 실제로 어디로 갔나」의 짝**이다.
의도는 이미 넘치게 쌓이는데(크루카드 100+문항) 결과를 담을 자리가 없었다 —
`exit_log`는 「나갔다」만 알고 「어디로」가 없고, `hall_of_fame`은 사람은 읽지만 집계가 못 읽는다.
🔴 **소급 불가**: 학생이 떠나면 연락이 끊긴다. 코드를 나중에 짜도 데이터는 안 돌아온다.

### 두 축은 직교다 (이 설계의 요점)
| | 뜻 | 값 |
|---|---|---|
| **결과종류** | 어느 **길**로 갔나 | 유학 비자 · 대학·대학원 입학 · 어학연수 · E-9/E-7/기타 취업 · 창업무역 · 결혼이민 · 방문·기타 · 제3국 · 몽골 내 · 중도 포기 · 기타 |
| **단계** | 그 길에서 **어디까지** | 지원·접수 · 합격·승인 · 불합격·거절 · 보류·추가서류 · 대기중 · 출국·입국 · 정착 확인 |

섞으면(「비자 거절」을 결과종류에 넣으면) **거절당한 사람이 목표하던 길이 통째로 사라진다.**
거절은 결과가 아니라 어느 길 위의 한 단계다 — 재도전이 정상이기 때문이다.

### 시트 2장
- **`outcome_log`** — 관측 「사건」 원장(append-only, 1인 N행). 원장 수기 칸은 **드롭다운으로 어휘를 못 박는다**
  (자유 입력이면 「E-9」·「E9 취업」·「이피나인」이 섞이고, 그 순간 집계는 영원히 불가능해진다).
  `근거키`(= `출처:학생ID:원천식별자`)가 멱등의 전부 — 두 번 수확하면 한 사람이 두 번 합격한 것으로 집계된다.
  `활용동의`는 **거르지 않고 실어 나른다** — 수확 단계에서 거르면 운영 커버리지가 동의율만큼 거짓으로 낮아진다.
  거르는 자리는 「내보낼 때」다.
- **`trajectory`** — 파생 조인표(1인 1행, 매번 재작성). 의도 4칸 × 최신 결과 × **`의도↔결과`** 판정.
  손으로 고치면 다음 아침에 덮인다 — 고칠 곳은 언제나 `outcome_log`다.
  **상담시트에서 읽는다**(profiles가 아니라): profiles는 퇴소자를 지우는데, 궤적이 필요한 사람이 바로 그들이다.

### `의도↔결과` — 로드맵 ④의 학습 신호
`미관측` / `진행중` / `좌절(재도전 가능)` / `의도 미정` / `분류 불가` / `일치` / `불일치(유학→취업)`
🔑 **「모른다」를 「일치」로 세지 않는다.** 뭉치는 순간 커버리지가 부풀고, 부푼 커버리지는
「데이터가 쌓이고 있다」는 착각이 된다. 커버리지 실값 = `app_state`의 `궤적커버리지`(`확인/전체 (날짜)`).

### 자동 수확
`면접기록_응답` → 학생ID가 적힌 행만. **헤더 이름으로 읽는다** — 라이브 폼에 문항이 끼어들면 응답 시트에
열이 붙어 위치 파싱은 그날 조용히 어긋난다. 익명 응답은 그대로 질문 은행에 기여한다(설계 · [v9.180] 계보).

**운영 내부 기록:** 두 시트 전체를 학생·학부모 화면이나 공개 지식으로 노출하지 않는다. 실제 앱 노출은 별도 서버 권한과 데이터 계약으로 검증한다. 관측의 동의를 보존하는 것과 외부 사용 허용을 구분한다. 삭제된 과거 시험의 통과 건수는 현재 검증으로 인용하지 않는다.
