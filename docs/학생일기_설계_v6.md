## 0. 🔴 v5 에서 틀린 다섯 — 철회한다

### ㉠ 「라디오 승격 행이 통째로 고아 잡을 만든다」는 범위를 넓혀 읽은 것이다

GPT 정정: `!출석`·`!목표` 승격 행은 **`submission.created` 이고 실제 교정 대상이며 소비자가 있다.**
고아는 **퀴즈 응답(`quiz.answered`) 제출 행뿐**이다.
⇒ §5 의 「딸려 오는 이득」에서 라디오 한 갈래를 뺀다. 남는 이득은 배정 행과 퀴즈 행 둘이다.

### ㉡ 🔴 `transcript_state` 를 앱이 넣는 줄 알았다 — **서버가 정한다**

`SYNK-talk/supabase/functions/events/index.ts:520` 의 INSERT 는 그 칸을 열 목록에 두고,
값은 서버가 `전사대상()` 으로 정한다. 앱이 `null` 을 보내도 소용이 없다.

⇒ **`전사대상()` 함수 자체를 고쳐야 한다**(§6). v5 의 「행에 null 을 넣는다」는 실행 불가였다.

### ㉢ `code_switch_spans` 에 언어를 넣겠다는 것도 실행 불가다

그 칸은 열만 있고 **생산자가 0곳**이다. `/events` 의 INSERT 열 목록에 없고, 전사기도
`stt_segments` 까지만 쓴다. 게다가 그 칸은 «구간 배열»이라 「이 글의 언어」와 축이 다르다.

⇒ **언어를 적을 칸이 지금 없다.** 새 열 하나가 필요하다(§3).

### ㉣ 계약 등재 자리를 잘못 짚었다

v5 는 값목록이 `lib/이벤트검증.js` 에 있다고 썼는데, **정본은 `계약/수집_교정_계약.json`** 이고
검증기는 그 사본이다. DB 의 `event_type`·`task_type` CHECK 제약 교체도 빠졌다.

### ㉤ 🔴 맞장구를 기존 개입 사건에 얹은 것이 위험하다

`intervention.delivered` 는 「지도 방식 → 반응 → 1·7·30일 성과」를 재는 **교수 개입의 닻**이고,
성과 회수가 그 사건 **전건**을 대상으로 센다. 맞장구는 고치지도 평가하지도 않는 반응이라
같은 사건이 아니다. 맞장구 한 줄이 교수 개입 한 건으로 세어진다.

⇒ **새 사건 `diary.acknowledged`** 로 가른다(§7).

## 1. 🔀 두 집안이 갈린 자리 — 「물음을 띄웠다」를 남기나

이번에 처음으로 둘이 정반대를 말했다.

| | 말 |
|---|---|
| GPT | 남기는 것 자체가 유호님 확정과 부딪친다 ⇒ **폐기하라** |
| 제미나이 | 분모를 지우면 이탈을 못 잰다 ⇒ **남겨라** |

**제미나이 논지를 받는다.**

> 결손 감점을 주지 않는 것과 이탈을 관측하는 것은 **별개**인데 … 100번 열고 100번 다 포기한
> 학생과 일기 탭을 한 번도 안 누른 학생이 엔진 내부에서 동일한 상태로 취급된다.

유호님 확정은 「안 쓴 날은 **결손으로 세지 않는다**」이지 「보지 마라」가 아니다.

**⇒ 판정: 남기되, 세 곳에서 뺀다.**

| 자리 | 처분 |
|---|---|
| 자발발화축의 분모 | **안 쓴다** (열고 안 쓴 것이 점수를 깎지 않는다) |
| 진행률 「첫날인가」 | **거른다** (GPT 가 짚은 충돌이 여기서 난다) |
| 이탈을 보는 자리 | **쓴다** — 운영이 물음 품질을 보는 계기판(엔진 축 아님) |

## 3. 🔴 계약 개정의 «진짜» 크기 — 여덟 자리

v5 까지 나는 이 크기를 계속 작게 말했다. 실물로 세면 이렇다.

| # | 무엇 | 어디 |
|---|---|---|
| 1 | `event_type` **+3** (`diary.opened`·`diary.written`·`diary.acknowledged`) | 계약 JSON + 검증기 사본 |
| 2 | `task_type` **+1** (`일기`) | 같은 자리 |
| 3 | payload 화이트리스트 (물음 넷) | 검증기 `이벤트별필수` |
| 4 | `앱사건`·`사건출처`·생산자·엔진도달 장부 | `이벤트검증.js`·`사건출처.js` |
| 5 | **`submissions` 열 +1** (`input_lang`) | 마이그레이션 |
| 6 | **`pipeline_jobs` 열 +1** (`job_kind`) + 유일 제약 교체 | 마이그레이션 |
| 7 | DB CHECK 제약 판 접미 전량 교체 | 마이그레이션 |
| 8 | **배포 사후검사 수정** | `확인_적용후상태.sql` |

🔑 8번이 새로 드러난 자리다 — §5 가 그것을 설명한다.

## 4. 사건 셋

| 사건 | 누가 만드나 | payload 필수 |
|---|---|---|
| `diary.opened` | 앱 | `prompt_id` · `prompt_text` · `prompt_pack_ver` · `diary_date` |
| `diary.written` | 앱 | 제출 규격 다섯(기존 `submission.created` 와 같다) |
| `diary.acknowledged` | **서버** | `parent_event_id` · `output_text` · `model` · `prompt_ver` |

🔴 **날짜와 물음이 세 곳에 적힌다**(`task_ref` · `task_snapshot` · `diary.opened.payload`).
세 사본이 갈리면 날짜 목록과 종이가 어느 것을 믿을지 못 정한다.
⇒ **정본은 `task_snapshot.diary_date` 하나**로 못 박고, 나머지 둘은 그것과 **같은지 검사**한다.
`task_ref` = `diary:{prompt_id}` 로 **날짜를 빼서** 사본을 하나 줄인다.

🔑 사건과 표 행은 **한 트랜잭션**이다(기존 `/events` 규약 그대로).

## 5. 트리거와 배포 확인은 «한 벌»이다

```sql
create or replace function engine.enqueue_pipeline_job() returns trigger
  language plpgsql as $function$
begin
  if exists (select 1 from engine.learning_events e
              where e.event_id = NEW.event_id
                and e.event_type in ('submission.created', 'diary.written')) then
    insert into engine.pipeline_jobs (submission_id, job_kind)
      values (NEW.submission_id,
              case when (select event_type from engine.learning_events
                          where event_id = NEW.event_id) = 'diary.written'
                   then 'diary_ack' else 'correction' end)
      on conflict (submission_id, job_kind) do nothing;
  end if;
  return NEW;
end
$function$;
```

🔴 **그리고 같은 커밋이 배포 사후검사를 고친다.** 지금 `확인_적용후상태.sql:254` 는
「**모든** 제출 행에 잡이 있어야 `잡없는제출=0`」으로 판정하고, 그 값이 최종 통과 조건에 든다.
트리거만 고치면 **다음 배포 확인이 실패한다.**

```sql
-- 뒤: 「제출·일기 사건인데 잡이 없는 것」만 센다
(select count(*) from engine.submissions s
   join engine.learning_events e on e.event_id = s.event_id
  where e.event_type in ('submission.created','diary.written')
    and not exists (select 1 from engine.pipeline_jobs j
                     where j.submission_id = s.submission_id)) as 잡없는제출,
```

**딸려 오는 이득 둘** — 배정 행과 퀴즈 응답 행의 고아 잡이 멈춘다(라디오는 §0㉠ 에서 뺐다).
⚠ 이미 쌓인 고아 잡을 걷는 것은 별건이고, **`!출석`·`!목표` 승격 잡은 걷으면 안 된다.**

⚠ 트랜잭션 순서 걱정(제미나이 P0)은 성립하지 않는다 — `submissions.event_id` 가 사건을
외래키로 참조하므로 사건이 **먼저** 들어가고, 같은 트랜잭션 안에서 그 행이 보인다.

## 6. 전사를 끄는 법 — 서버 함수를 고친다

v5 는 「행에 `null` 을 넣는다」고 썼는데 실행 불가였다(§0㉡). 값을 정하는 것은 `전사대상()` 이다.

```js
// lib/전사.js — 인자 하나를 더한다
function 전사대상(audio_ref, server, task_type) {
  if (task_type === '일기') return null;   // 🔴 일기 소리는 전사줄에 안 선다
  if (typeof audio_ref !== 'string' || !audio_ref) return null;
  if (server && server.state === 'missing') return null;
  return 상태.대기;
}
```

🔑 판정을 **한 곳에** 둔다. `/events` 가 이미 이 함수를 부르므로 호출부에 인자 하나만 더한다.

⚠ **미루는 값을 정직하게 적는다.** 한국어로 «말한» 학생의 발음·어휘가 그동안 엔진에 안 닿는다.
두 집안이 이것을 게이트 위반이라 짚었고 반박하지 않는다 — §10-1 이 이것을 첫 자리에 세운다.

## 7. 맞장구 — 사건·통로·출력 검사 셋이 한 벌

### ㉠ 사건은 새로 판다

`intervention.delivered` 재사용은 §0㉤ 에서 물렸다. `diary.acknowledged` 를 세운다.

| 칸 | 왜 |
|---|---|
| `parent_event_id` | 어느 일기에 대한 답인가 (**필수**) |
| `output_text` | 맞장구 원문 — 시즌 종이가 이것을 그대로 찍는다 |
| `model` · `prompt_ver` | 다시 만들지 않고 계보를 안다 |
| 멱등키 = `diary-ack:{written_event_id}` | **일기 하나당 답 하나**를 물리로 막는다 |

### ㉡ 통로는 기존 잡 큐를 탄다

v5 는 저장 자리만 정하고 **누가 언제 부르는지**를 안 적었다. §5 의 트리거가 `job_kind='diary_ack'`
잡을 만들고, 맞장구 함수가 그 잡을 집는다. 실패·재시도·리스는 기존 큐 규약 그대로.

### ㉢ 🔴 「고치지 않고 평가하지 않는다」를 프롬프트에만 맡기지 않는다

v5 는 「그 규율은 프롬프트가 진다」 한 줄로 때웠다. 제미나이 지적이 맞다 — 모델은 지시를
무시하고 「한국어 실력이 뛰어나네요!」 같은 칭찬을 뱉는다. **칭찬도 평가다.**

⇒ 출력을 **검사**한다. 교정 표시(고침표·「틀렸」·「~이 맞아요」)나 실력 평가(「잘」·「뛰어나」·
「늘었」)가 섞이면 그 답을 버리고 고정 문구로 내린다. 검사기는 순수 함수라 회귀가 문다.

### ㉣ 소리만 남긴 날은 맞장구를 어떻게 만드나

§6 이 전사를 껐으므로 서버는 그 소리의 내용을 모른다. 고정 문구를 내면 유호님 확정
「AI 가 읽고 짧게 맞장구」가 거짓이 된다.

**⇒ 갈래 둘 중 하나를 골라야 한다** — ⓐ소리를 직접 읽는 모델을 이 자리에만 쓴다
ⓑ소리 일기에는 맞장구 대신 「잘 들었어요」류의 **받았다는 표시**만 낸다(거짓이 아니게 문구를 바꾼다).
**이 판은 ⓑ 로 두고 §10 에 남긴다** — ⓐ는 돈과 모델 선택이 걸린 유호님 판정 자리다.

## 10. 남은 일

1. 🔴 **소리를 안 캐는 동안 잃는 값을 잰다.** §6 이 미룬 그 값. 두 집안이 게이트 위반이라 짚었다.
2. 🔴 **㉡ 이해 대장을 무엇으로 채우나.** 내용 연결 하나가 아니라 후보가 여럿이다(§9).
   각 후보마다 「정의 · 소비자 · 회수 시점」 셋을 대야 한다.
3. **소리 일기 맞장구** — §7㉣ 의 ⓐ/ⓑ 판정(돈이 걸린 자리).
4. **맞장구 언어** — 몽골어는 감수자가 한 분뿐이라 검수 전엔 화면에 못 올린다.
5. **중복과 의도를 못 가른다** — 같은 초안 재전송은 접히지만 두 기기가 각자 초안을 만들면 둘 다 선다.
6. **화면 규격** — 첫 화면 문안, 글/소리 고르기, 저장 상태, 맞장구 대기·실패, 목록 상한,
   소리만 남긴 날의 종이 표현.
7. **최신 수단 정찰.**

## 11. 심문에 바라는 것

1. **§0 의 철회 다섯이 충분한가.**
2. **§1 의 판정(남기되 세 곳에서 뺀다)이 두 집안 지적을 «둘 다» 닫는가.**
3. **§3 의 여덟 자리가 계약 개정의 전부인가.** 아홉째가 있나.
4. **§5 의 트리거+사후검사 한 벌이 다른 검사를 깨지 않는가.**
5. **§7㉢ 의 출력 검사가 「평가」를 실제로 가려낼 수 있는가.** 낱말 목록으로 되는 일인가.
