# 숙제 답변의 명시 선호·관심을 다음 도움에 연결하는 설계

> 2026-10-17 코드 대조. 2026-08-27 원안의 학생 원문·본인 확인·정정 계약을 유지하고, 삭제된 생산자와 옛 착수 절차를 구분했다. 파일명은 기존 참조를 위해 유지한다.

## 1. 목적과 현재 상태

학생이 숙제에 “저는 혼자 있을 때가 편해요”라고 직접 썼다면, 그 문장을 근거로 본인에게 뜻을 확인하고 허용한 범위에서 다음 과제의 상황·도움 방식을 바꾼다. 문법 연습으로 시킨 문장이나 인물의 대사는 학생의 실제 선호로 저장하지 않는다. 관심·선호·목표·자기보고를 고정 성격이나 능력으로 바꾸지 않는다.

이 통로는 LAB 학습의 후속 설계다. 모든 사업·작품에 숙제나 학생 모델을 요구하지 않는다. 공통 능력은 기존 Core의 [해석·확인 계약](코어엔진_설계.md), 제품별 목적·동의·범위는 [공통 개인화 기반](SYNK_전사용자_개인화_기반_20261002.md)을 재사용한다.

| 구분 | 2026-10-17 로컬 파일 대조 | 다음 작업의 경계 |
|---|---|---|
| 학습 사건 | talk `lib/이벤트검증.js`에 `preference.stated`와 `estimate.responded` 정의·소비자 등록이 남아 있음 | 계약 존재와 현재 생산을 구분 |
| 생산자 | 같은 파일은 두 사건 모두 생산자 없음으로 등록. 옛 게임 확인 화면·라디오 승격은 10-03 정리됨 | 옛 `오늘의확인`이 지금 작동한다고 전제하지 않음 |
| 옛 확인·요약 구현 | `lib/성향확인.js`와 `lib/과제요약.js`는 현재 없음 | 파일명을 복원하는 작업부터 시작하지 않음 |
| 숙제 내용 추출 | 교정 함수·엔진에서 `hw_text` 후보의 추출→본인 확인→다음 도움 소비를 확인하지 못함 | 실제 생산자·확인 UI·소비자·시험이 이어져야 완료 |
| 플랫폼 회원 성향 | [별도 계정 계약](SYNK_플랫폼_계정과_연결_설계.md)에 명시 서술·미리보기·본인 확인과 판본 보존 경로가 있음 | 이 경로를 숙제 사건 생산이나 학생 효과로 세지 않음 |

## 2. 뽑는 정보와 버리는 정보

| 종류 | 사용할 수 있는 명시 문장 | 제외할 것 |
|---|---|---|
| 선호 | “매운 음식을 좋아해요”, “혼자 있는 시간이 편해요” | 글 길이·날씨·클릭을 근거로 한 기분·성격 추측 |
| 관심 | “요즘 웹툰을 그려요”, “BTS 노래로 공부해요” | 과제가 시킨 말, 등장인물의 말 |
| 목표 | “서울에서 디자인을 공부하고 싶어요” | 이를 이미 이룬 진로나 능력으로 기록 |
| 자기보고 | “아침에 집중이 잘돼요”, “말하기가 제일 어려워요” | 고정 성격 유형, 관측하지 않은 숙달·취약성 |

각 후보는 원문 인용·제출 참조·시각·해석판을 가져야 한다. 인용이 없거나 원문과 맞지 않으면 사용하지 않는다. 학생이 직접 쓴 감정 문장을 자동 상태 진단이나 개입의 근거로 쓰지 않는다. 필요한 강사 도움은 해당 제품의 동의·공유·보호 계약에서 다룬다.

관찰로 알 수 있는 것은 활동에서 얻고, 목표·제약·선호는 결과를 바꿀 필요가 있을 때 직접 묻는다. 옛 “새 설문·새 입력·새 화면 0”을 구현 제약으로 적용하지 않는다. 필요한 확인을 건너뛰어도 기본 학습은 계속 쓸 수 있어야 한다.

## 3. 계약과 원천

물리 필드·값목록·스키마 판은 [수집·교정 계약](../계약/수집_교정_계약.json)과 talk [`lib/이벤트검증.js`](../../SYNK-talk/lib/이벤트검증.js)가 정본이다. 옛 c13→c14 개정 제안이나 한글 의사코드를 현재 JSON 규격으로 복사하지 않는다.

| 실제 계약의 칸 | 이 후속 설계에서 맡길 의미 |
|---|---|
| `preference_dimension` | 선호·관심·목표·자기보고의 구분. 실제 허용값은 정본을 따름 |
| `stated_option` | 본인이 말한 내용을 벗어나지 않는 짧은 값 |
| `stated_via` | 실제 수집한 접점. 없는 라디오·화면을 출처로 만들지 않음 |
| `evidence_text` | 학생이 직접 쓴 근거 문장 |
| `confirm_status` | 계약에 정의된 확인 상태 |
| `hw_ref` | 실제 숙제 제출 참조 |

기존 사건 검증의 필수 칸과 특정 생산자가 추가로 보장해야 할 칸을 구분한다. 숙제 내용 생산자를 만들 때는 근거 인용·제출 참조·확인 상태를 함께 검증한다. 이 때문에 다른 기존 출처의 필수값을 임의로 늘리지 않는다. 필드나 의미가 달라질 때는 계약·검증기·저장·소비·이전 판 호환을 한 범위로 맞춘다.

## 4. 원문에서 실제 도움까지

1. 사용이 허용된 숙제 답변에서 후보를 만든다. 학생 본인의 말인지, 연습 예문인지부터 구분한다.
2. 원문과 해석을 함께 보여 주고 맞음·수정·아님·건너뛰기를 받는다. 미확인 후보는 개인화 입력에 넣지 않는다.
3. 확인된 선언을 목적·제품·사용자 범위 안에서 실제 과제 상황이나 도움에 연결한다. 선택한 이유와 쓴 근거를 추적할 수 있게 한다.
4. 부정·정정·사용 중지·철회 뒤에는 예전 해석을 되살리지 않는다. 원문·정정 이력의 보존과 삭제는 해당 계정·동의 계약을 따른다.
5. 실제로 어떤 도움을 전달했고 어떤 후속 수행이 있었는지 따로 기록한다. 확인 버튼을 누른 것 자체를 학습 향상으로 세지 않는다.

확인은 추정 행을 몰래 사실로 덮어쓰는 동작이 아니다. 학습용 확인 사건과 플랫폼의 계정 문서 확인은 각 저장 계약을 유지한다. 오래된 선호를 영구 성격으로 만들지 않으며 유효기간·재확인은 제품에서 근거와 사용 맥락에 맞게 정한다. 원안의 “두 시즌 약 4개월”과 하루 한 번·두 장은 당시 가정·구현 이력이며 현재 공통 상한이 아니다.

## 5. 실행 방식과 비용

교정 AI가 이미 읽는 답변에서 구조화 후보를 함께 내는 방법은 재사용 후보다. 별도 호출을 줄일 수 있지만 출력 토큰·평가·저장·검토 비용이 0이라는 뜻은 아니다. 교정 품질에 미치는 영향과 실제 후보 발생률을 먼저 확인하고, 기존 Core 해석·확인 능력을 연결할 수 있는지 살핀다. 자체 LLM 실행기나 새 중앙 엔진을 만들지 않는다.

모델 호출이 필요하면 [AI 운영 원칙](AI_운영원칙.md)의 비용·승인 기준과 [WORLD AI 한도](SYNK_WORLD_AI_효율화_20261002.md)를 따른다. 옛 “4회전 먼저”, 고정 검수 루프·평가 모델·현재 없는 프롬프트 파이프라인을 착수 관문으로 되살리지 않는다.

## 6. 구현·검증의 완료 조건

- 실제 제출의 본인 발화·연습 예문·인용·부정·조건문을 구분하고 원문과 후보를 대조한다.
- 확인 전 사용 금지, 수정·거절·건너뛰기·철회, 다른 계정과 목적의 격리를 확인한다.
- 확인된 값이 실제 다음 도움을 바꾸는지, 바뀐 이유가 근거와 일치하는지 확인한다.
- 교정 겸임을 택하면 같은 독립 평가셋에서 교정 품질·후보 정밀도·비용을 함께 비교한다.
- 몽골어·한국어 혼용, 긴 문장·모호한 문장·표본 없음은 별도 실패·보류로 남긴다. 합성 회귀 통과와 새 실제 사용자 문장의 해석 품질을 구분한다.

실제 학생의 후보 발생률, 교정 품질 영향, 학습 효과는 이 문서 정리로 검증되지 않았다. 다음 구현 범위는 현재 요청과 실제 소비처에 맞춰 정한다.

2026-08-27 원안의 법·연구 메모, 비용 가정, 버전별 착수 판단은 [정리 전 원문](_ops/qa/document-cleanup-20261017/_archive/pass2-originals/docs/성향추출_설계_v1.md)에 보존한다. 출처·적용 범위를 다시 확인하지 않은 법·연구 요약을 현행 규칙이나 효과 증거로 쓰지 않는다.
