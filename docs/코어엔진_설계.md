## 1. 【설계안】 정의 — 두 부분

**SYNK 코어 엔진 = ① 코어 층 + ② 내부 관리 프로그램.**

1. **코어 층**: 회사의 모든 지식·학습 데이터·학생 개인화가 한 곳에 쌓이고 서로 연결되어, 모든 SYNK 앱의 AI 기능이 「무엇을 아는가(지식) × 이 학생을 아는가(개인화)」를 여기서 꺼내 쓴다.
2. **내부 관리 프로그램(비출시)**: 유호님·직원이 그 두뇌를 열어 보고 기르는 옵시디언형 화면. 유호님 원문의 「옵시디언같은 프로그램」·「완전 교육적인 느낌」이 사는 자리다(UI는 브랜드 킷·이모지 절제·「명품 앱」 지향 정본 적용). 형태 답은 §8-1 【확정】(시트 + 화면만 옵시디언 느낌) — 세부 해석(열람=별도 웹 화면)은 【설계안】 · §8-1.

## 2. 【설계안】 왜 엔진인가 (유호님 논리를 구조로)

- 학원 운영 앱을 뺀 모든 미래 앱 = AI 챗봇 필요. 챗봇 품질 = **지식 × 개인화** — 앱마다 따로 만들면 N번 만들고 N번 낡는다.
- 엔진 하나에 모으면 지식 1건 추가·개인화 1단계 개선이 **모든 앱에 동시에** 반영된다 — 5·10·20년 복리. 「엔진이 발전하면 앱들이 다같이 발전한다」의 기계적 실체.
- ⚠같은 배선은 **틀린 지식 1건도 전 앱에 동시 전파**한다 — 그래서 회수(무효화) 경로가 계약 조항이다(부록 A-5).

## 7. 【도전안·기각 종결】 지식층 정본을 「마크다운 + git」으로, Supabase는 인덱스로

> **기각 종결 (2026-08-05)**: §8-1 답(편집=시트 · 화면만 옵시디언 느낌)으로 이 안은 소멸 — 충돌 3건의 해제가 더는 필요 없다. **🚫재제안 금지 대상 = 지식 정본을 마크다운+git에 두는 안 · 옵시디언을 편집 관리창으로 쓰는 안**(읽기 전용 뷰어 보조 통로는 별건 — §8-1 도전안 · E1 검토). 기록=memory `core-engine-obsidian-2026-08-05`. 아래 본문은 근거 보존용.

**안**: 지식 노트의 정본을 DB가 아니라 마크다운 파일+git(별도 저장소의 **지식 전용 볼트**)으로 두고, Supabase에는 검색용 인덱스만 적재. 옵시디언과 동형(파일=노트·`[[링크]]`=그래프)이라 옵시디언 실물이 관리 화면이 될 수 있고, 모든 개정이 git 이력으로 남는다. 근거 실물 = 회사 AI 메모리가 이 구조로 실운영 중.

**⚠정직한 경고 — 이 안은 기존 확정 3건과 충돌한다(채택하려면 유호님이 명시적으로 해제해야 한다)**:
1. 「Obsidian=정본 뷰어로 축소 · 제2두뇌 금지」(ai-stack 확정) 2. 「유호 직접 편집 볼트 = 미커밋 상주 사고 경로라 금지」(노션 대체 트랙) 3. 현 볼트는 memory 폴더 위라 파일 만드는 코어 플러그인을 일부러 꺼 뒀고, 그 동기화 트랙(synk-memory)은 세션이 안 만지는 자산이다 — 그래서 **별도 볼트**가 전제다.
그리고 「관리창 비용 0원」이 아니다 — 열람권·발행 게이트(어느 노트가 봇에 실리나)·다국어·학생 데이터 경계는 어느 안에서든 만들어야 하고, 그것이 관리창 비용의 본체다. **학생 개인정보(학습자 모델·말뭉치)는 어느 안에서도 git에 두지 않는다.**

## 8. 유호님 결정 3건 — 답 원문은 【확정】 · 반영 판정은 【설계안】 (2026-08-05)

1. **관리 프로그램 형태 = 시트 + 「화면만 옵시디언 느낌」** — 원문(그대로): "학습 난이도나 구현 및 실용성이 상관크게 상관없다면 시트+(화면만 옵시디언느낌으로) 하는게 좋을것같은데 ?"

## 부록 A — P0·L0 계약에 넣을 엔진 조항 (E0의 실체)

> **A-0. 필드 정본은 이 문서가 아니다.** 학습 산출물의 필수 필드·오류 태그·골든 판정·반출 규칙의 정본 = **`계약/수집_교정_계약.json`**(양쪽 CI가 기계로 지킴) **+ `docs/학습데이터_스키마감사.md`**(v9.187 구현: model·prompt_ver·문항 스냅샷·audio_ref·행 단위 consent_ver 등). **L0 DDL은 거기서 벗어나지 않는다** — 아래는 거기 없는 신규 조항만이다(제3의 계약 원천을 만들지 않는다).

1. **이름공간**: Postgres에 `engine.*` 스키마 예약 — 학습자 모델·말뭉치는 확정, **지식 인덱스는 이름공간만 예약**(`engine.knowledge_*` — 내용 정의는 E1 · §8-1 시트 편집면의 단방향 파생 · A-5 회수/발행 플래그 동반). **L0 DDL은 학습자 모델·말뭉치 둘로 착수**(지식 테이블을 지금 정의하지 않는다).
2. **AI 호출은 서버측만**: 모델 호출은 서버측(Supabase Edge Function 또는 Apps Script)에서만 — **앱 번들에 모델 API 키를 두지 않는다**. 앱↔서버 인터페이스는 C0 계약에 예시 payload·오류 규격·버전 정책과 함께 동결(기존 C0 절차 그대로). 게이트웨이 전환일에 앱 코드가 안 바뀌는 것은 이 동결이 지켜질 때만이다.
3. **개인정보 경계(분해)**: 외부 모델로 **나가지 않는 것 = 식별자**(이름·연락처·student_id·생년·학교 등). **나갈 수 있는 것 = 비식별 학습 산출물**(발화·오류·교정 원문 — 식별자 제거 후). 비식별 기준 실물 = 골든 픽스처 반출 규칙(`수집_교정_계약.json`)과 같은 축 · ⚠소수 인원에선 날짜도 식별자일 수 있다(실측 판정 승계).
4. **강등 경로**: AI 기능마다 「엔진(서버) 무응답 시 기본 동작」을 P0 기능표에 열 1개로 명시 — 내부 엔진이 전 앱의 단일 장애점이 되지 않게.
5. **지식 레코드 규격**: 출처·갱신일·**유효범위(대상 도메인 — E3 지식팩 경계의 씨앗)** 필수 + **회수(무효화) 1회가 전 소비자에 즉시 반영**되는 배선(틀린 답 방치가 유일한 치명 실패 — 기존 판정 승계). **지식 시트 필수 열 = 현 `두뇌지식` 헤더(대상·주제·확정·내용·출처·갱신일)에 유효범위·회수/발행 플래그를 더한 것** — E1 시트 신설 때 이 열로 시작한다. 회수 판정은 시트→DB 동기 주기에 얹지 않는다 — 소비자(게이트웨이)가 회수·발행 플래그를 실시간으로 본다(「즉시」가 동기화 지연에 걸리는 순간 이 조항이 죽는다).
6. **동의 철회 전파**: 말뭉치 행은 원본 레코드와 조인 가능해야 한다(철회 시 파기 전파용) · **저장소 밖(git·픽스처·외부 모델)으로 나가는 것은 비식별본만**.
7. **평가셋 씨앗(E3 역산)**: 오류·교정 쌍과 골든 판정 구조를 평가셋으로 재사용 가능하게 유지한다 — 이미 계약에 있는 것을 지우지 않는다는 선언.
8. **행 단위 스키마 버전** *(2026-08-05 외부 검토 채택 · 소급 불가)*: 수집 행에 `schema_ver` 1열 — 계약 파일의 `버전`(현 `c2`)을 **행이 스스로 들고 있게** 한다. 계약 파일에는 버전이 있지만 **데이터 행에는 없다**(실측: `엔진_수집.js` 헤더 상수에 `model`·`prompt_ver`·`audio_ref`·급수는 있고 `schema_ver`는 없음). 3·4년차에 한 시트 안에 c1·c2·c3 행이 섞이면 어느 규격인지 행이 말하지 못하고, 변환기를 쓰려 해도 대상을 못 고른다 — **불변식 1(「4년 호환」)을 지키는 유일한 기계 장치**이고, 과거 행은 영원히 빈칸이라 지금 박는 것 말고 방법이 없다.
9. **운영 전제 — 실학생 게이트** *(2026-08-05 외부 검토 채택)*: Supabase 무료 티어는 비활성 프로젝트 정지·**다운로드 가능한 자동 백업 부재**. 실학생 데이터가 처음 들어가는 날 **전에** 유료 전환 + **복구 시험 1회**를 파일럿 게이트 조건으로 둔다(지출 승인은 유호님 몫 — 결정큐). 「신규 스택 전부 무료」는 개발 환경까지만 참이다.
