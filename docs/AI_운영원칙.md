**검수를 줄이는 다섯 가지(2026-10-24 유호님 확정):** 아래 검수는 모두 이 다섯 가지를 먼저 따른다. ① 백엔드 2차 검수는 GPT 하나다(아래 「백엔드 검수」). ② 다시 검수는 고친 자리만 본다 — 그 지적을 낸 검수자에게 고친 diff와 그 지적만 한 번 묻고, 묶음을 통째로 다시 만들지 않는다. P0·P1이 없는 회차에서 멈추고, 같은 곳에서 두 회차 연달아 P0·P1이 나오면 땜질을 멈추고 설계부터 다시 본다(큰 기능이면 아래 「큰 기능의 설계 검토」). ③ P2·P3는 배포·공개를 막지 않고 다시 검수할 이유도 아니다 — 바로 되는 것만 고치고 나머지는 후속으로 적는다. ④ 위험으로 나눈다 — 운영 데이터·인증·돈·삭제·마이그레이션과 학생·교사·고객 화면이 든 반영만 아래 검수를 받고, 내부 도구(유호님·운영자만 보는 화면 포함)·CI·시험·문서만 바꾼 일은 시험과 자기 점검으로 끝낸다(지우거나 덮는 동작이 있으면 받는다). ⑤ 검수 뒤 후보를 고쳤으면 바뀐 diff와 그 지적만 `검수묶음.mjs 다시`로 같은 검수자에게 보이고, 배포·공개 도구(`tools/공개.js`·`deploy-security-check.js`)는 처음 검수부터 해시로 이어진 그 사슬의 끝 후보가 최종 바이트와 같은지 본다(P2·P3만 고친 판은 아래 여섯 가지 ⑥). 검수 증거를 요구하는 문이 옛 정책으로 막으면 우회하지 않고 그 요구대로 지나간다.

**검수 효율 여섯 가지(2026-10-31 유호님 확정):** 다섯 가지에 더한다(쓰는 법 [현장 노트](현장노트/AI_CLI.md)). ① P1은 사용자·운영 데이터가 정상 경로에서 밟는 오류다 — 운영 데이터 삭제·덮어쓰기, 인증·권한·돈·개인정보, 배포·검수 관문은 드문 입력도 P1, 그 밖의 내부 도구·극단 입력 결함은 P2. ② 같은 파일이 72시간 안에 3회차 연달아 P0·P1이면 도구가 멈추고 Fable 설계 검토 뒤 잇는다. ③ 배포 후보는 앞 공개본과 달라진 곳만 읽힌다. Claude 서비스 백엔드는 11-14까지 끝 판을 아르곤에게도 보인다(시험). ④ Fable은 남의 지적을 P0·P1만 확인하고 P2·P3는 5건까지. ⑤ GPT 작성 백엔드의 Claude 검수는 첫 판·끝 판·자기 지적만이고, 끝 판을 안 보면 배포가 막힌다. ⑥ P0·P1 없이 소스만 고친 판은 다시 검수하지 않고 다음 판으로.

검수자는 Claude가 기존 통로로 직접 부른다 — GPT는 공식 Codex CLI, 아르곤은 구독 통로 `tools/lib/제미나이구독호출.js`(둘 다 묶음마다 한 번씩), Fable은 **5.2(`claude-fable-5-2`)**로만 부른다(2026-11-11 유호님 「앞으로 필요한 모든 페이블 검수는 5.1에서 5.2로」). Agent 도구의 `model: fable`은 5.1로 가서 쓰지 않는다. 세션 모델이 `claude-fable-5-2`인 세션에서 model을 비운 하위 에이전트로 부른다. Opus 세션이면 곁 세션을 띄워 `set_session_model`로 `claude-fable-5-2`로 바꾼 뒤 맡긴다. 답 첫 줄의 모델 이름과 하위 에이전트 기록의 model 칸으로 5.2인지 확인하고, 아니면 결과로 쓰지 않는다([현장 노트](현장노트/AI_CLI.md#agent-model-fable은-claude-fable-5-1로-돈다--fable-52로면-세션-모델이-52인-세션에서-model-없이-띄운다-2026-11-11-claude)). 유호님이 나르지 않고 새 실행기는 만들지 않는다. 묶음 나누기·보내기·입력 대조·기록·끝 보고 집계는 손으로 하지 않고 `node tools/검수묶음.mjs`가 한다 — 명령과 호출 요령은 [현장 노트 · AI CLI](현장노트/AI_CLI.md), Apps Script 반영은 [deploy 스킬](../.claude/skills/deploy/SKILL.md). 아주 작은 고침(오타·값 하나)은 그때그때 검수하지 않고 모았다가 그 작업 끝에 한 번에 받는다.

**백엔드 검수(2026-10-24):** Claude가 한 백엔드 작업은 Claude가 만들고(1차) GPT가 본 계정의 모델·추론 설정 그대로 읽기 전용으로 묶음을 본다(2차) — 아르곤 주간 몫은 화면 1차 검수에 쓴다. GPT가 한도·로그인으로 막혔을 때만 아르곤이, 둘 다 막히면 그록이(`검수묶음.mjs 그록`, 그록 P2도 처리해야 닫힌다), 셋 다 막히면 Fable이 대신하고 끝 보고에 그렇게 적는다. 반영 전에 받는 것은 회사 서버 릴리스(서버 코드가 든 것 — 화면 묶음만 바꾸는 반영은 아래 「화면 검수」와 「학생·교사·고객 화면의 배포 조건」을 따른다), SYNK-talk 함수·마이그레이션, Apps Script 라이브(deploy 스킬 2단계, clasp push 전) 셋이고, 재현되는 P0·P1을 고친 뒤 반영한다. 그 밖의 백엔드 변경은 운영 데이터·인증·돈·삭제가 든 것만 끝 보고 전까지 받는다(④). GPT가 한 백엔드 작업은 GPT와 Claude가 함께 검수하고(유호님이 맡긴다, 다시 검수는 여섯 가지 ⑤), 이미 「GPT 검수 대기」로 적힌 Claude 백엔드 작업도 이어받을 때 이 2차 검수를 받아 반영한다. 끝 보고와 트랙 항목에는 실제로 돈 검수만 「GPT N건(반영 M)」(대신한 검수가 있으면 함께)으로 남긴다. 화면 파일만 바꾼 작업은 이 검수 대신 아래 「화면 검수」를 따른다.

**화면 검수(2026-10-24):** Claude가 화면 파일을 바꾼 작업은 끝 보고 전에 검수한다(내부 도구 화면은 ④). 순서는 Claude(Opus) 구현·시험·캡처 → 아르곤 검수 → 재현되는 지적만 고침 → Fable 최종 검수다. **Fable 최종은 조건부다(2026-10-24 유호님):** 레이아웃·CSS를 크게 바꾸거나, 새 화면 흐름·상호작용을 만들거나, 서버 상태·데이터를 화면에 보이는 로직을 바꾼 일만 받는다. 그림·글·색만 바꾼 화면은 `검수묶음.mjs 준비 … --페이블생략 "<까닭>"`으로 아르곤만 받고, Claude가 1440·390 캡처로 넘침·깨진 그림·콘솔 오류·실패 요청을 재어 끝 보고에 적는다. 그래도 아르곤이 한도·로그인으로 막히면 Fable이 대신하고, 아르곤 P0·P1을 고치면 `다시`로 아르곤·Fable이 고친 diff를 본다 — 아르곤은 묶음 글만 읽고 화면 그림은 보지 않기 때문이다. Fable은 고친 뒤의 실제 상태를 바뀐 파일 전체와 영향받는 화면 전체로 본다(범위는 줄이지 않는다). Fable은 자기 검수를 먼저 쓴 뒤 아르곤 P0·P1 지적과 Claude의 처리(반영했는지, 안 했으면 왜인지)를 보고, P0·P1을 짚으면 고쳐서 같은 Fable에게 다시 확인받는다(②). 아르곤이 한도·로그인으로 막히면 다른 경로를 찾지 않고 바로 Fable 검수로 가고, Fable이 Claude 한도에 걸리면 건너뛰지 않고 초기화 뒤에 마친다. 끝 보고에는 「아르곤 N건(반영 M) · Fable N건(반영 M)」과 반영하지 않은 이유를 붙인다(P2·P3를 후속으로 넘긴 것은 「후속」이면 된다). 화면과 서버를 같이 바꾼 작업은 화면 쪽은 이 순서를, 서버 쪽은 위 「백엔드 검수」를 따른다. 콘티의 Fable 검수는 따로 그대로다.

**학생·교사·고객 화면의 배포 조건(2026-10-21):** 학생·교사·고객이 보는 화면(synk.im 공개 화면, WORLD·교사 앱, PULSE 고객 화면, 계정·회원 화면, PC 앱)은 위 검수에서 재현되는 P0·P1이 0건이 된 뒤에 배포·공개하고, 받아야 할 Fable 검수가 한도로 남았으면 초기화 뒤 마칠 때까지 배포하지 않는다. 아주 작은 고침은 이 화면이어도 먼저 반영하고 작업 끝 검수에 모은다. synk.im 공개 뒤 배포 점검은 쪽마다 기준 이미지와 달라진 곳과 새 접근성(axe) 위반을 보고하고 새로 생긴 치명 위반만 실패로 세며, 의도한 변경이면 `node tools/공개.js 기준 --점검 <실행> <쪽…>`으로 그 쪽만 기준을 바꾼다. SNS·synkbrief 글처럼 콘텐츠로 내는 글·영상은 이 조건이 아니라 역할 표의 콘텐츠 줄을 따른다.

**검수 누락과 배포본 변경 차단(2026-10-23):** 검수를 보내지 않은 것은 한도·로그인 막힘이 아니므로 대체 규칙을 쓰지 않는다 — 필수 검수자의 실제 막힘 증거가 있을 때만 쓴다. 빈 답·잘못된 답 꼴·빠진 항목·다른 입력에 대한 답·끝까지 안 읽힌 묶음의 0건은 통과가 아니고, 대상이 바뀌면 다시 검수하며, 배포본은 최종 검수한 상태와 같아야 한다(「반영」 표시만으로 검수된 것이 아니다). 증거가 없다고 자동 예외로 넘기지 않는다. 도구가 묶음·후보를 대조하는 세부와 그 범위는 [관문·자동화](_ops/관문_자동화.md#review-gaps).

**큰 기능의 설계 검토(2026-10-22):** 새 제품·새 화면 흐름·새 서버 기능·데이터 구조를 바꾸는 일처럼 여러 파일에 걸친 큰 기능은 만들기 전에 설계(목적·사용자 흐름·데이터·바꿀 파일·시험 계획·벤치마킹 근거)를 Fable에게 한 번 보이고, 짚은 것을 반영한 뒤 만든다 — 다 만든 뒤 검수에서 고칠 것을 앞에서 줄이려는 것이다. 작은 고침·글 다듬기·이미 검토한 설계를 잇는 일은 빼고, 끝 보고에 「설계 검토 Fable N건(반영 M)」을 적는다. 위 검수는 그대로 받는다.

## 모든 작업의 출발점 · 사용자 평가에 근거한 벤치마킹

GPT와 Claude 모두 **목적에 맞는 현존 최고 서비스의 장점 + SYNK의 개인화·학습 가치 → 더 나은 SYNK 콘텐츠·앱**을 공통 작업 방식으로 삼는다. 기획·구현·고도화·콘텐츠 제작에서 아래 조사를 필수로 수행하고, 그 결과로 무엇을 만들지 결정한다.

1. **목적을 먼저 확정한다.** 누구의 어떤 문제를 풀고 어떤 재미·편익·학습 경험을 줄 것인지, 이번 결과의 성공 기준을 파악한다. 목적이 같은 서비스·회사·콘텐츠와 인접 분야까지 조사 대상으로 잡는다. 생활 콘텐츠 앱이라면 교육 앱뿐 아니라 Steam 등의 생활 시뮬레이션 게임도 살핀다.
2. **현재 선도 서비스를 폭넓게 찾는다.** 조사일 기준 후보군을 훑고 이용·판매·조회 등 인기 지표와 평점·리뷰 수·최근 평가 등 만족도 지표를 함께 비교한다. 누적 인기와 최근 반응, 플랫폼·대상 사용자 차이를 구분해 목적에 맞는 최고 사례를 고른다. 유명한 회사나 익숙한 몇 개 사례만으로 결론내리지 않는다.
3. **기능과 사용자 반응의 원문을 수집한다.** 공식 제품·도움말·업데이트와 실제 사용 화면·플레이 자료에서 기능을 확인하고, 스토어 리뷰·커뮤니티·댓글의 최신 원문을 크롤링·열람한다. 검색 요약이나 회사 홍보만으로 끝내지 않는다. 반복되는 호평과 불만을 기능·사용 맥락별로 묶고, 최근 평가와 장기 평가를 대조한다. 출처 URL·확인일·평가 기간·표본 규모·선정 범위를 남긴다. 접근하지 못한 자료와 표본 조사를 전수조사로 보고하지 않는다.
4. **왜 좋은지 기능 단위로 설명한다.** ‘어떤 기능 → 어떤 사용자 경험 → 어떤 호평’인지 원문 근거와 연결한다. 흥행 규모만으로 개별 기능의 효과를 단정하지 않고, 사용자가 직접 밝힌 이유와 우리의 해석·가설을 구분한다. 불만에서는 개선 기회를 찾는다.
5. **장점에 SYNK의 색을 더해 설계·구현한다.** 가져올 장점과 바꿀 점을 정하고, 관련 Atlas 엔진의 개인화와 구체적인 학습 활동·피드백·성장 보상을 어디에 연결할지 정한다. 기능을 단순히 모으지 않고 원래 호평받은 재미·편의가 살아 있는 사용자 흐름으로 만든다. 아직 확인하지 않은 학습 효과는 가설로 둔다.
6. **실제 결과로 검증하고 갱신한다.** 벤치마킹에서 채택한 장점이 결과물에 구현됐는지 확인하고, 실제 사용·시청 반응으로 다음 개선을 정한다. 다른 AI의 작업을 이어받을 때도 조사 근거와 구현 결과를 함께 확인해 발전시킨다.

**SNS 편(10-28):** 위 2~5를 편마다 「검증된 원본 하나 → 그 뼈대(훅 자리 · 칸 수 · 박자 · 반전 · 끝 장치) + SYNK의 색」으로 한다. 여러 원본의 장점을 섞어 새 틀을 짓지 않고, 뼈대는 지키되 똑같이 베끼지 않는다(우리 색 · 그 계정에 남길 것 · 화면 짜임 · 끝 한마디는 우리 판단, [제작 절차 「오마주」](마케팅/기획장부/제작절차.md#homage)).

조사 결과는 해당 제품·콘텐츠의 기존 설계나 탐색노트에 **출처·사용자 반응 → 채택할 장점 → SYNK 적용 → 확인할 결과**로 짧게 연결한다. 별도 공통 보고서나 실행기를 늘리지 않는다. 이어 하는 수정은 기존 근거를 먼저 활용하되 최신성과 이번 변경의 관련성을 확인하고 부족한 범위를 추가 조사한다. 새 목적·핵심 기능·사용자 경험을 정할 때는 후보 조사부터 다시 수행한다.

## 공식 하네스

- 각자의 공식 앱·CLI에서 계획·도구·서브에이전트·재개·검토·예약 기능을 쓴다. 모델과 추론 설정은 그 제품의 실제 설정을 따르며 임의로 통일하거나 낮추지 않는다.
- 자체 LLM 실행기·중계·자동 모델 선택기·반복 검수기를 새로 만들지 않는다. 지금 쓰는 통로(검수 묶음·무인 실행 자격 고르기·구독 호출·GPT 손일 카드)는 공식 CLI를 한 번씩 부르는 것으로 유호님이 정한 것이고, 목록과 끄는 법은 [관문·자동화 한 장](_ops/관문_자동화.md)에 있다. 옛 자체 실행 절차와 훅을 새 작업의 선행 조건으로 되살리지 않는다.
- 스킬·커넥터·보조 도구는 필요한 것만 쓰고, 기존 기능으로 못 푸는 반복 문제와 실제 효과가 있을 때만 더한다. 제품 내부의 AI API와 학습 엔진은 작업용 하네스와 구분한다.
- 예약은 요청된 일이 있을 때만 만든다. 할 일 없이 큰 대화를 주기적으로 깨우지 않고, 단순 상태 확인은 AI 없는 조회·알림으로 한다.
- 인터넷 작업(조사 열람·사이트 조작·로그인·연결 승인·게시·내려받기)은 Claude와 GPT 모두 ego(lite) 브라우저가 기본이다(2026-10-21). 에이전트는 `ego-browser` 스킬로 자기 작업 공간(Space)에서 일해 사용자 탭을 건드리지 않고, 앱 계정을 바꿔도 끊기지 않는다. 사이트 로그인도 ego에 한다. 네이버 블로그와 티스토리는 Aside(AI 브라우저)에서 한다(2026-10-26, 넣는 법은 [현장 노트](현장노트/브라우저_게시.md#asideai-브라우저)). **yuhokorean의 페이스북·인스타그램·틱톡 업로드도 Aside에서 한다**(2026-11-02 유호님 확정). 업로드 전에 대상 계정이 yuhokorean인지 확인해 기존 계정과 섞이지 않게 한다. ego에서 막힐 때만 앱 안 브라우저, 그다음 크롬(Claude in Chrome·Codex 크롬 확장, 프로필 「유호」)으로 넘어가고 까닭을 [현장 노트](현장노트/브라우저_게시.md#egolite)에 남긴다. 이 작업본 개발 서버의 미리 보기(`preview_start`)는 앱 안 브라우저 그대로이고, Edge는 쓰지 않는다.

- 네이버 관련 업로드는 Aside의 앞 세 프로필(Default·Profile 1·Profile 2)을 계정별 전용으로 사용한다(2026-11-07 유호님). CLI에서 프로필을 명시하고 실제 로그인 계정과 대상 블로그·채널을 확인한 뒤 진행한다. 계정과 프로필의 짝은 저장소에 적지 않으며, 로그인·인증은 유호님이 한다.

## 같은 원문으로 이어가기

- `AGENTS.md`가 공동 입구이고 `CLAUDE.md`는 이를 가져온다. 제품 설계·코드·결과는 담당 원문 한 곳에서 고친다. 모델별 사본이나 별도 인수인계 양식을 늘리지 않는다.
- 이어받을 때 해당 원문·코드·현재 diff와 [트랙](_ops/트랙.md)의 관련 항목을 확인한다. 작업본 위치, 확인한 결과, 남은 일만 짧게 전달한다. 같은 폴더의 파일 공유가 대화·프로세스·미커밋 변경의 자동 동기화를 뜻하지는 않는다.
- 확정 내용은 담당 원문에 반영하고 [결정](_ops/결정.md)에는 근거를 남긴다. 과거 기록·메모의 역할표·말투·절차를 현재 지침으로 적용하지 않는다. 자연스러운 한국어를 사용하며 캐릭터 설정은 해당 캐릭터의 대사에만 적용한다.
- 보고나 기획에 남은 일·한계·다음 할 일을 적거나 이미 정한 듯한 것을 물으려면, 먼저 그 항목의 낱말(기능·편·도구 이름)로 결정 표를 찾는다(`rg -n "<낱말>" docs/_ops/결정.md docs/_ops/보관`). 정해진 것을 남은 일로 적거나 다시 묻지 않는다(2026-11-03).
- 다른 작업의 변경·원본을 보존한다. 동시 편집에서는 파일 범위를 확인하고, 별도 worktree의 변경은 필요한 것만 통합한다.
- 늘 읽히는 문서(AGENTS·이 문서·Claude 메모 목록)에는 지금 규칙만 둔다. 바뀐 경과·근거는 [결정](_ops/결정.md), 절차·실측은 담당 원문에 쓰고, 같은 규칙을 여러 곳에 풀어 쓰지 않고 링크로 가리킨다(2026-10-24 경량화).
- `node tools/바로올리기.js`는 그 push가 AGENTS를 11KB·이 문서를 35KB 너머로 키우거나 결정·트랙에 2KB 넘는 줄을 새로 넣으면 막지 않고 「크기 알림」을 보인다. 알림이 뜨면 경과는 결정 표로, 절차·실측은 담당 원문으로 옮겨 그 줄을 줄인다([관문·자동화 한 장](_ops/관문_자동화.md)).

## 보존할 기준과 자산

## 비용과 권한

- 자격증명과 학생 식별 정보를 출력·공유하지 않는다. 신규 결제·구독·자동충전은 하지 않으며 한도·인증 문제를 다른 유료 경로로 자동 우회하지 않는다. 사용자가 정한 예외 통로(GPT 그림 굽기 보조 계정, 광고 콘티용 GPT 이미지 API(Pro 월 크레딧), 헤르메스 개인 대화의 Claude API 경로, Claude API 월 크레딧 키와 무인 작업 실행기, 헤르메스 클라우드 작업, Gemini 구독 대체)와 그 도구는 [AI 계정과 크레딧](AI_계정과_크레딧.md)에 있다.
- 개발용 구독과 제품 API 비용은 별개다. MVP의 AI 한도는 낮게 유지하고, 실제로 돈이 나가는 AI 시험·호출(충전 잔액·카드로 청구되는 키)은 실행 전 예상 비용을 알리고 승인을 받는다. 결제 수단 없는 조직의 Claude API 무료 크레딧으로만 도는 시험·호출은 돈이 아니므로 비용 때문에 묻지 않고 쓴 양만 보고한다(2026-10-21). 자동 충전이 꺼진 조직에서 GPT Pro 구독의 월 API 크레딧으로만 도는 광고 콘티 굽기도 같다(2026-10-29). 그 크레딧은 운영(talk 강사 도우미·헤르메스)과 나눠 쓰므로 큰 일괄은 나눠 보내고, 바닥나 운영이 멈출 것 같으면 먼저 말한다. 운영에서 그런 기능을 켜는 비밀값·기능 스위치 쓰기가 판정기에 막히면 그 한 줄만 여쭌다. 한도 상향도 확인한 뒤에 한다.
- 이미지는 GPT·Gemini 직접 서비스의 기존 월정액 경로만 쓰고 Higgsfield나 별도 과금 API로 바꾸지 않는다. 어느 그림에 무엇을 쓰는지는 위 역할 표, 방법은 [만족 사례 장부](마케팅/제작양식/만족사례_장부.md)다 — 영상에 얹는 소품·그림 개그·뜻 그림은 그 편에 맞게 GPT 이미지 2.6으로 판에 구워 오린다(S17, `tools/펠트판_칸오리기.py`). 마스코트는 오려 얹지 않고 장면과 한 장으로 새로 굽는다([AGENTS](../AGENTS.md), 2026-10-14). 한 편의 그림은 웬만하면 엔진 하나로 굽는다 — AI 광고·홍보영상과 공모전 출품작의 그림(이미지 콘티·시작·끝 그림·정지컷)은 애니메이션을 빼고 모두 위 역할 표의 Gemini 나노바나나이고, 10-29에 둔 GPT Image 2.5 Sunburst 선택지는 닫았다([결정](_ops/결정.md) 2026-11-08, [AI 광고영상 제작 규칙](마케팅/제작양식/AI광고영상_제작규칙.md) 순서 4). 펠트 캐릭터·마스코트·소품은 API로 굽지 않는다. 드라마 말하기 앱의 웹툰 칸·인물 시트는 GPT Image 2.5 Sunburst · max(`node tools/GPT콘티굽기.mjs`)로 굽는다(2026-10-30). GPT 이미지의 사용자 지정값은 **GPT Image 2.5 Sunburst · max**이며, 선택할 수 없는 도구에서 이를 보장했다고 보고하지 않는다. 승인 얼굴·로고·원본을 보존한다.
- Google Cloud 기본 결제 계정과 프로젝트 연결은 [돈장부](_ops/돈장부.json)의 `기본_구글클라우드_결제`에서 확인한다. 기존 서비스의 결제 이전·크레딧 종료 후 유료 전환까지 승인된 것으로 해석하지 않는다.
- **배포·공개는 맡은 작업의 마감으로 바로 한다(2026-10-21 사용자 확정).** Claude·GPT 모두 그 작업의 배포·공개(Apps Script 라이브, synk.im 공개, SYNK-talk 함수와 데이터·접근을 바꾸지 않는 마이그레이션(새 테이블·열·색인, 함수·뷰 코드), 회사 서버 릴리스와 바로 뒤 재무장, PC 앱 릴리스, 공개 저장소 push)를 따로 묻지 않는다. 그 경로의 표준 절차와 검사(시험·보안 검사·미리 보기·배포 점검·라이브 대조, 학생·교사·고객 화면과 운영 백엔드 반영은 위 「학생·교사·고객 화면의 배포 조건」과 「백엔드 검수」까지)를 통과하면 반영하고, 끝 보고에 무엇을 어디에 올렸는지 적는다. synk.im은 `tools/공개.js`로만 올리고 synk-policy main에 직접 push하지 않으며, 공개 저장소 push는 SYNK-appsscript master·synk-tips 글·claude-session-share의 자기 작업만이다. 검사가 실패하거나 남의 미커밋이 배포물에 섞이면 승인할 일이 아니라 고칠 일이므로, 배포하지 않고 고치거나 보고한다. 매일 판 SNS 편(`docs/마케팅/<편>/게시/준비.json`에 판으로 적힌 계정·시각, 올리기 전 검사 「고칠 것」 0)은 2026-11-02부터 자체검수(장면 모아보기·음량·글·링크)를 통과하면 묻지 않고 모든 계정에 예약·게시한다(14시 「오늘 편 게시」 작업, 11-03부터 게시 뒤 고정 댓글·블로그 쇼츠 칸도). 계속 사용자에게 묻는 「정말 중요한 일」은 다음뿐이다: 그 밖의 SNS·유튜브 게시(준비.json 판에 없는 글·광고)와 이미 공개된 글의 삭제·비공개 전환·공개 전환, 메일·메시지·DM·댓글·지원사업 제출처럼 남에게 보내기, 실제로 돈이 나가는 일(결제·구독·가격표·과금 설정, 돈 주고 산 생성 크레딧의 큰 지출 — Claude API 무료 크레딧으로만 도는 호출은 돈으로 치지 않는다), 기존 데이터를 지우거나 덮는 운영 변경(DROP·TRUNCATE·DELETE·UPDATE, 열 바꾸기·이름 바꾸기처럼 데이터를 바꾸는 마이그레이션, 백업으로 덮기)과 되돌리기 어려운 삭제, 접근을 바꾸는 보안 설정(권한·GRANT·RLS 정책·방화벽·DNS·인증서·저장소 공개 범위), 공개하면 안 되는 내용(비밀값·학생 정보·미공개 특허·남의 개인정보)이 섞였을 수 있을 때. 준비·로컬 검증·실제 반영·사용자 효과를 구분하고 확인하지 않은 결과를 완료로 보고하지 않는다.
- 사용자가 꼭 보고 정해야 하는 일이 아니면 Claude가 판단해 집행하고 끝에 무엇을 왜 했는지 보고한다(2026-10-20 위임). 보안·운영 잡일(비밀값 점검과 보관, 열쇠 파일 권한, 접속이 막힌 원인 찾기, 서버·저장소 보안 패치)도 명령으로 되는 것은 사용자에게 넘기지 않는다. 사용자 손이 남는 것은 허락을 받아도 Claude가 하지 않는 일뿐이다 — 로그인·가입 화면의 비밀번호·인증 코드 입력, 휴대폰 2단계 인증, 계정 가입, 결제, 데이터 영구 삭제, 접근을 바꾸는 보안 설정(방화벽·권한 부여·2단계 인증·앱 권한 모드). 이것도 작업마다 명령 한 줄이나 클릭 한 번으로 묶어 한 번만 부탁하고 결과 확인은 Claude가 한다. 그 손일을 GPT에게 맡길 때는 `node tools/GPT인계.mjs 준비`로 Codex 앱에 붙여 넣을 카드를 만들어 클립보드에 올리고 `기다리기`를 백그라운드로 띄워 결과를 받는다(2026-10-22). 카드는 적힌 일만 하고 비밀번호·인증 코드·2단계 인증·캡차·결제 확인 화면에서 멈춰 사용자에게 한 줄로 넘기게 적는다. Claude가 GPT를 사람 없이 띄워 이런 일을 시키지는 않는다.

## 확인과 완료

변경에 관련된 빌드·시험·실제 화면만 확인한다. 문서·스타일 수정마다 전체 검사나 새 승인 절차를 만들지 않는다. 보안·데이터·제품 계약 검사는 유지하며, 읽지 못한 범위와 미확인 결과를 밝힌다. 결과 위치와 남은 일은 기존 트랙의 해당 항목에 짧게 남기고 같은 보고서를 다시 만들지 않는다.
