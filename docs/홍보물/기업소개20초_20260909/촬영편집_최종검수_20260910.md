## 최초 결론 — 현행은 §8

촬영·색관리·의미 중심 컷 편집의 방향은 유지할 만하다. 그러나 **자동화 최종 승인과 "영상 하나만 넣으면 준비 완료" 판정은 보류**한다. 기존 5개 테스트와 자체 검사는 통과하지만, 그 검사 밖에서 파일 오선택·저장 실패·방향 오판정 등이 재현됐다. "1억짜리 광고와 동급"은 설정값으로 보장하거나 이번 검수로 인증할 수 있는 품질 등급이 아니다.

현재 준비된 것은 기준 문서와 설치된 준비 도구다. 실제 촬영본에 대한 샷 선택·피부·조명·소리·합성·최종 출력은 아직 수행하지 않았다. 높은 목표를 낮추는 것이 아니라, 목표와 확인된 결과를 구분한다.

## 2. 문서의 목표값과 자동 적용 범위의 차이

- 정본 60~63줄은 LUT 보간 Tetrahedral, Half DNxHR LB 프록시, 최종 원본 렌더를 제시하지만, 코드 185~217·260~300줄에는 일부 설정을 확정하거나 읽어 확인하는 처리가 없다. 프록시 사용 모드·반 해상도 설정만 있고 DNxHR LB 형식 선택과 프록시 생성은 구현돼 있지 않다.
- 코드 398~399줄은 `proxy`, `project_backups` 폴더를 만들지만, 해당 폴더로 프록시·프로젝트 백업을 연결하는 설정이 없다. 폴더 생성은 백업 완료가 아니다. 캐시 경로는 별도로 설정한다.
- 코드 220~239줄의 `applied`는 API에 전달해 True를 받은 요청값이다. `GetSettings()`로 다시 읽은 실제 값이 아니다. 정본 80줄의 "실제 적용값"과 구분해야 한다.
- 코드 201·427줄은 입력을 Samsung Log로 취급하지만 원본이 APV HDR·일반 SDR인지 검증하지 않는다. APV 기본 촬영 모드는 HDR이므로, 원본 분류가 확실하지 않으면 자동으로 Log를 강제하지 않는 입력 확인이 필요하다. 이는 지원 계약 보강 권고이며 실제 촬영본의 색 오류를 확인했다는 뜻은 아니다.
- HQX 렌더 코덱 선택은 이름에 `dnxhr hqx`가 든 첫 항목을 쓴다. 실제 앱에는 10-bit와 12-bit가 모두 있어, 정본의 10-bit를 보장하려면 정확한 항목을 선택하고 확인하는 편이 안전하다.

## 3. 실제 Resolve에서 확인한 상태

설치된 `computer-use` 스킬의 Windows 제어 통로로 Resolve를 열어, 내부 Lua 콘솔에서 읽기 전용 API를 실행했다. 예전 "orca가 없으므로 네이티브 화면 확인 불가" 기록은 **현재 가능한 제어 범위를 설명하지 못하는 오래된 관찰**이다.

- `resolve:GetVersionString()` = `21.1.0.14`, `resolve:IsStudio()` = false.
- 현재 프로젝트 `New Project`는 미디어가 없고, `GetSettings()`의 해상도 1920×1080, 24fps, `colorScienceMode=davinciYRGB`, 입력 Rec.709 Gamma 2.4, 타임라인/출력 Rec.709 (Scene), 캐시 none, 프록시 original이었다. SYNK 색관리·4K가 적용된 프로젝트가 아니다.
- `GetProjectSettingsPresetList()`는 Current Project, System Config, guest default config만 반환했다. `SYNK_S26U_APV_HQ_4K24`는 없었다.
- `GetRenderPresetList()`에도 SYNK 마스터 프리셋이 없었다. 프리셋을 생성할 코드가 설치된 것과 프리셋이 실제 저장된 것은 다르다.
- `GetRenderCodecs("mov")`에는 `Avid DNxHR HQX 10-bit` / `DNxHRHQX_10`과 HQX 12-bit가 있었다. 무료판에서도 이 마스터 출력 항목이 존재함은 확인했지만 실제 렌더 성공을 확인한 것은 아니다.
- `Workspace > Scripts`에서 Comp/Edit/Color/Deliver 및 `No Scripts`가 보였고 SYNK 도구는 노출되지 않았다. 설치 파일 수정 시각은 22:01:18, Resolve 시작 시각은 20:51:58이다. 설치된 공식 README는 시작 시 스크립트 폴더를 스캔한다고 설명하므로 **재시작 후 재열거가 필요할 가능성이 높다**. 재시작 후 노출은 미확인이다. 임의로 앱을 종료하지 않았다.
- 원본·변환본의 잘못된 재사용 및 저장 오류를 발견했으므로 이번 검수에서 이 도구로 제작 프로젝트를 생성하거나 프리셋을 덮어쓰지 않았다. 내부 전체 실행, 실제 가져오기→타임라인→마스터 출력은 미완료다.
- 외장 SSD는 연결되지 않았고 이번 재측정 C: 여유는 약 24.79GiB였다. 용량은 시점에 따라 바뀐다.

설치된 공식 API 문서는 `C:/ProgramData/Blackmagic Design/DaVinci Resolve/Support/Developer/Scripting/README.md`와 `DaVinciResolveScript.pyi`를 사용했다. README 갱신 표시는 2026-08-31이다. `bmd.scriptapp("Resolve")`에서 이어지는 설정 조회는 nil 인덱싱 오류가 났지만, 이미 주입된 `resolve` 객체로 읽기 조회는 성공했다.

## 4. 촬영·색관리에서 유지할 것과 더 좋아질 부분

### 유지할 제작 기준

- Galaxy S26 Ultra, 프로 동영상, APV 422 HQ **Log**, UHD4K24, 1× 메인, 고정 화이트밸런스·초점, 충분한 빛, 원본 보존.
- Samsung Log → DaVinci Wide Gamut/Intermediate → Rec.709 Gamma 2.4의 관리 경로를 기본으로 하되 실제 클립 입력 해석을 확인. 같은 Log→Rec.709 변환을 LUT로 또 적용하지 않는다.
- 큰 확산광, 빛을 빼서 만드는 얼굴의 입체감, 정리된 작은 세트, 실제 재질, 절제된 움직임, 선명한 실제 목소리. 이것은 촬영·미술 판단이며 비용 등급 보장은 아니다.

삼성 공식 문서는 S26 Ultra의 APV HQ/LQ, HDR/Log 선택, HQ 4K24 637Mbps, 외장 UHD≤60fps 지속 쓰기 200MB/s 이상·전력 최대 4.5W·exFAT 등을 명시한다. Log 모드는 기본 HDR에서 따로 선택해야 한다. [삼성 APV](https://developer.samsung.com/mobile/apv.html)

Standard LUT Preview는 모니터링용이며 원본에는 굽혀 저장하지 않는다. Zebra/False Color는 노출 확인 도구다. [삼성 Log](https://developer.samsung.com/mobile/samsung-log-video.html)

### 최종 확정 전에 개선할 판단

1. **밴딩 때문에 곧바로 전체를 30fps로 바꿀 필요는 없다.** 24fps·1/50은 정상 출발값이지만 60Hz 조명에서 줄무늬가 생기면 우선 24fps를 유지한 1/60과 조명 밝기/전원 조건을 시험하는 방법도 있다. LED 구동 방식에 따라 1/60도 해결책이 아닐 수 있다. 실제 녹화 파일에서 확인 후 장면 내 조건을 통일한다. 이는 일반 촬영 원리를 적용한 개선안이며 S26 실기 시험 완료값은 아니다. [Sony 촬영 원리·플리커](https://www.sony.com/electronics/support/articles/00268256)
2. **ISO 50~200·상한 400은 공식 최적 감도나 절대 제한이 아니다.** 현재 제작의 시작 목표일 뿐이다. 이 숫자를 지키려고 Log를 어둡게 찍어 후반에서 심하게 밝히면 안 된다. 광량·피부·밝은 부분 보존·노이즈를 실제 샘플로 함께 판단한다.
3. 배경 -1.5~-2.5스톱, 인물-배경 2~3m, 윤곽광 각도는 작은 세트를 만들 때의 초기 배치다. 실제 방 크기·피부·의상·재질을 보기 전의 고정 정답으로 확정하지 않는다.
4. 말하는 본편 외에 가능하면 손·물건·실제 작업/결과·반응을 각각 5~8초 정도 확보하면 의미 있는 컷 전환의 선택지가 늘어난다. 추가 파일 개수를 강제하지 않는다. 한 파일 안에서 구도를 바꿔 이어 찍어도 된다. 각 테이크 앞뒤 여유와 조용한 현장음도 도움이 된다.
5. APV HQ는 원본만 약 4.78GB/분이다. 10분 약 47.8GB에 편집 중간본·캐시·마스터·별도 백업이 더해진다. 촬영 SSD의 유일한 원본을 곧바로 작업 캐시와 함께 쓰는 것보다 별도 검증 복사본을 확보해야 한다. 구매나 포맷은 이번에 수행하지 않았다.
6. 4K24는 현행 작업 흐름의 기본값이지 모든 샷에서 화질이 가장 좋은 유일한 설정이라는 뜻은 아니다. S26 Ultra는 APV 8K 촬영도 지원한다. 강한 조명 아래 정적인 세부 묘사·재구도가 필요한 샷은 8K 원본과 4K 원본을 같은 4K 출력으로 비교할 여지가 있다. 실제 디테일·노이즈·발열·저장 부담을 시험하기 전에는 8K로 일괄 상향하지 않는다. 현재 무료 Resolve의 출력 한계와 원본 촬영 해상도도 구분한다. [삼성 APV](https://developer.samsung.com/mobile/apv.html), [Resolve 버전 안내](https://www.blackmagicdesign.com/products/davinciresolve)

## 5. 지루하지 않은 컷 편집 검수

현재 `docs/명품_기준_v1.md` §3-1과 `컷편집_리듬정본_20260910.md`는 일치한다. 의미 하나당 샷 1.5~3초를 출발점으로 삼되, 증거·감정·읽기에 필요한 샷은 더 길게 남긴다. 도입에 볼 이유를 주고, 중복을 줄이고, 말과 화면의 경계를 달리하는 J/L컷·실제 보조 장면·동작/시선 연결·빠름과 쉼으로 리듬을 만든다.

이를 고정 간격 자동 분할, 모든 박자마다 컷, 무음 일괄 삭제, 모든 전환 효과 사용으로 바꾸지 않는 기준은 유지한다. TikTok의 구조·소리·시각 자극 원리와 Adobe의 J/L컷 정의를 다시 대조했다. 숫자 1.5~3초나 도입 1~2초는 보편 최적값·성과 보장이 아니다. [TikTok Creative Codes](https://ads.tiktok.com/business/en-US/creative-codes), [Adobe J/L컷](https://helpx.adobe.com/kr/premiere/desktop/edit-projects/trim-clips/perform-j-cuts-and-l-cuts.html)

자동화는 보관 타임라인과 편집 트랙·안내서를 준비하는 도구다. 컷의 의미·자막 읽힘·음악과 목소리의 균형을 자동 완성하는 도구로 구현돼 있지 않다. 이것은 의도된 작업 분리이며 오류가 아니다. 실제 편집 때 다음 확인이 필요하다.

- 처음 10~15초를 실제 촬영본으로 조립해 도입·문장·컷 리듬을 확인한다.
- 휴대폰 크기로 재생하고, 소리만 듣고, 무음으로 자막을 읽어 각각 흐름·말 잘림·읽기 부족을 확인한다.
- 좋은 표정·중요한 증거가 짧아지지 않았는지, 시각 효과가 사람과 메시지를 가리지 않는지 확인한다.
- 게시 후 실제 이탈 구간이 있어야 시청 지속 시간 개선을 판단할 수 있다. 이번 검수는 재미나 광고 성과의 실측이 아니다.
