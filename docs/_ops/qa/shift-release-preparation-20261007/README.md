# SHIFT 운영 반영 준비

2026-10-07. 기존 회사 작업실의 계정 실습과 홈페이지 BM 변경을 운영에 반영하기 위한 준비 기록이다. 공개 배포, 운영 서버 재시작, 운영 DB 변경은 실행하지 않았다.

[종합 검증·전달 파일 기록](report.json)은 아래 개별 결과와 배포 후보 원본·문서 원고·전달 사본의 현재 해시 일치를 확인한 기록이다.

이 기록은 해당 실행 당시의 후보를 보존한다. 같은 날 후속으로 기존 DB의 원래 키가 없으면 시작을 거부하는 보호와 복구 후보 대조 도구를 추가했다. 이후 현재 후보와 실행 결과는 [운영·실증 후속 기록](../shift-operational-acceptance-20261007/README.md)에서 확인한다.

## 로컬에서 확인한 결과

회사 서버의 기존 Docker 배포 파일에는 현재 서버가 사용하는 Atlas·메신저·SHIFT 모델과 정적 자료가 빠져 있었다. 실제 COPY 파일만 임시 폴더에 옮겨 실행했을 때 `atlas/work.js` 누락으로 시작하지 못하는 것을 재현했다. 필요한 실행 원본·화면·인증된 안내 문서만 명시적으로 포함했고, DB·암호화 키·연결 자격증명은 이미지에 포함하지 않는다. 회사와 메신저의 DB는 같은 영구 데이터 볼륨 아래에 둔다. `MESSENGER_DATA_DIR`를 기존 회사 서버 설정에 연결하되 명시적 실행 옵션과 기존 통합 설정이 우선한다.

수정한 COPY 파일을 새 임시 폴더에 옮겨 실제 Node 서버를 실행했다. 합성 계정 로그인·실습 저장/조회·메신저/실습 자산·회사 안내 17원문·작업실 제작 원문·승인 자산 18개 다운로드 등 **71항목**을 통과했다. 관련 서버·인증·동기화·백업 시험은 **129/129** 통과했다. 이 컴퓨터에는 Docker CLI가 없어 실제 Linux 이미지 빌드·컨테이너 실행은 검증하지 않았다.

독립 검토에서 기존 통합 설정과 환경 경로가 함께 있을 때 서버와 백업이 서로 다른 메신저 DB를 선택하는 오류도 재현했다. 백업 도구의 우선순위를 서버와 같은 **명시 옵션→기존 통합 설정→환경→기본값**으로 맞추고 네 경로 조합에서 실제 서버·백업 대상 일치를 확인했다. 배포 묶음에서 빠진 제작 소스 13개도 승인된 파일만 추가하고 실제 다운로드로 확인했다.

- [배포 묶음·회귀 결과](container-report.json), [실행 출력](release-tests.txt)
- [배포 후보 원본 SHA-256](candidate-sources.json): 현재 COPY 후보와 관련 검사 파일의 해시이며 컨테이너 이미지의 해시는 아니다. 검수 이후 원본이 바뀌면 그 변경을 확인하고 다시 검증한다.
- [백업·복구 결과](backup-report.json), [백업 경계](backup-README.md): 합성 자료의 기존 백업 도구→새 폴더 복구→HTTP 로그인·조회·저장·삭제와 경로 일치 확인 **13/13**. 이 13개는 위 129개에 포함된다.
- 이전 계정 기능의 [두 격리 브라우저 검사](../shift-account-sync-20261007/browser/report.json)는 물리적 두 기기 검증을 대신하지 않는다.

## BM 자료 보완

[PDF·수정용 Word](../../../유지비_BM/바탕화면_정리_20261005/v2/output-20261007/README.md)에 한 업무의 도입·운영, 반복 공급 뒤 API·라이선스 확장을 반영했다. 각각 14쪽이며 전페이지 렌더와 내용·편집 가능 여부를 확인했고 **114/114** 검사를 통과했다. [통합 Excel](../../../유지비_BM/통합계산_20261007/qa/report.json)은 23항목·10시트다. 현행 도입·운영·추가 사용 3단위는 미확정 입력으로, 과거 8단위는 참고 이력으로 분리했다. 계산 검사 109개·실제 Excel 재계산 76개·원천/입력/수식 보존 대조 4,440개를 통과했다. 다른 브랜드의 수치와 기존 원본은 유지했다.

새 전달 사본은 바탕화면 `bm 설계표/20261007_SHIFT_개정/`의 PDF·Word·Excel 3파일이다. 검증한 원본과 SHA-256이 모두 일치하며 바탕화면 최상위의 기존 전달본은 덮어쓰지 않았다. 실제 고객·가격·판매 개시·성과·수익성 검증은 포함하지 않는다.

## 운영 반영 순서

1. 실제 회사 HTTPS 주소와 서버·영구 데이터 위치를 정한다. 두 DB와 키·기존 통합 설정·로컬 첨부를 같은 운영 환경에서 유지한다. 다른 서버로 옮길 때 통합 설정의 `messengerDataDir`는 그 서버의 실제 영구 볼륨 경로로 맞추고 계정 연결 목록 `identityLinks`는 보존한다. 기존 회사 계정과 명시적 SYNK ID 연결을 재사용하며 외부 고객 공간을 새로 만들지 않는다.
2. 준비한 소스와 기존 홈페이지 BM 결과를 검수한다. [AI 운영 원칙](../../../AI_운영원칙.md)에 따라 **라이브 배포·공개 게시로 나가는 결과는 Claude Opus 5.5 최대 추론의 최종 검수**를 완료해야 한다. 이번 로컬 준비를 검수 완료나 공개 반영으로 부르지 않는다.
3. 서버 운영 환경에서 Docker 이미지의 실제 빌드·비관리자 실행을 확인한다. 회사·메신저 데이터 경로는 영구 볼륨에 두고 운영 DB가 소스 이미지에 들어가지 않는지 확인한다. 새 주소는 현재 운영 계정의 로그인/콜백 설정과 맞춘다.
4. 반영 직전 회사·메신저 쓰기를 중지하고 `workspace-backup.mjs`로 DB 둘·원래 키·등록된 로컬 첨부를 함께 백업한다. `COMPLETE`와 무결성, 등록 파일, 키 일치를 확인하고 별도 폴더에서 복구해 본인 기록과 삭제 상태를 읽는다. 키·본문을 로그나 검수 자료에 출력하지 않는다. Drive 본문은 로컬 백업에 포함되지 않는다.
5. 새 코드를 반영하고 실제 계정으로 홈·메신저·내 작업실을 확인한다. 실습 저장을 직접 켜기 전에는 계정 실습 저장이 시작되지 않아야 한다. 홈페이지는 실제 공개 주소의 한·영 소개와 문의 입구를 확인한다.
6. 아래 실물 기기 왕복을 확인한 뒤 운영 인수를 기록한다. 사용자 실제 효과와 고객 업무의 비용·수익성은 별도 시범 운영에서 측정한다.

단계 1~6은 준비한 절차이며 실행 완료 기록이 아니다. 실제 도메인·상시 서버는 아직 확정된 운영 값으로 이 문서에 기입하지 않았다. 임의의 예시 주소를 실기기 접속 주소로 사용하지 않는다.

## 실물 두 기기의 인수 기록

PC와 휴대폰에서 실제 회사 HTTPS 주소로 같은 회사 계정에 로그인하고 각각 계정 저장을 직접 켠다. `localhost` 주소는 다른 기기에서 공유할 수 없다. 개인 작업물 대신 가상 연습 자료로 아래 결과를 확인하고 두 기기 종류·브라우저·시각·문제를 남긴다. 현재 모든 항목은 **미실행**이다.

| 확인 | 통과 기준 | 실제 결과 |
|---|---|---|
| 첫 왕복 | PC 작성→휴대폰 조회·수정→PC 조회 시 수정문·최근 실습 결과가 일치 | 미실행 |
| 동시에 수정 | 양쪽 내용이 다르면 선택 전에 작성물을 보존하고 양쪽 기록을 확인할 수 있음 | 미실행 |
| 끊김·다시 연결 | 전송되지 않은 글이 현재 창에서 유지되며 다시 연결 시 충돌을 확인함. 창을 닫은 뒤 복원은 기기 저장을 직접 켠 경우에만 기대함 | 미실행 |
| 삭제와 오래된 사본 | 한 기기에서 계정 삭제 후 다른 기기의 오래된 사본이 자동으로 재저장되지 않음 | 미실행 |
| 계정 전환 | 다른 계정에는 이전 계정의 글이 보이지 않음. 원래 계정 재로그인과 복구 이후 삭제 상태도 일치 | 미실행 |

## 되돌리기와 복구

**코드 롤백은 최신 DB와 맞는 원래 키를 유지한다.** 되돌릴 코드가 현재 저장 형식과 호환되는지 검수하고, 호환되지 않으면 쓰기를 재개하지 않는다. 이 문서가 임의의 과거 코드 호환성을 보증하지 않는다.

**과거 백업 복원은 다른 절차다.** 삭제 전 백업에는 이후 삭제 revision이 없다. 실제 재현에서도 삭제된 본문이 돌아왔고 오래된 클라이언트의 저장을 수락했다. 오래된 백업만으로 이후 삭제·수정을 보존했다고 판단하지 않는다. 복구는 사용자 접속을 막은 별도 위치에서 하고, 이후 삭제·수정 사항을 대조·반영할 수 없으면 접속을 열지 않는다. 해당 사항을 자동 재적용하는 기능은 현재 없다.

이 시험 당시 Store는 키가 없으면 새 키를 만들어 서버 시작·로그인이 가능했다. [후속 보완](../shift-operational-acceptance-20261007/README.md)은 기존 회사 DB가 있는데 원래 키가 없으면 키 재생성·DB 변경 전에 시작을 거부한다. 다른 32바이트 키의 일치 여부는 별도 복구 대조와 실제 본인 작성물 조회까지 확인해야 한다. 최신 운영 자료를 과거 스냅샷으로 덮어쓰거나 이번 합성 시험을 운영 데이터 복구 실적으로 보고하지 않는다.
