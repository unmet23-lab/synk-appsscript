## 트랙 정리 방식

- 항목 하나 = 원래 판의 `- **제목:**` 줄 하나(이어지는 들여쓴 줄 포함). ID `tN-NN`은 절 번호와 절 안 순서다.
- §1 유호님 차례·§2 위험은 **한강2126 줄(t1-16)만** 줄였다(1차에서 제안하고 「전부 진행」으로 적용). 판마다 적힌 「남은 일」은 다음 판이 대신했으므로 지금 남은 일(v33 수정, 마감 확인)만 남겼다. 나머지 §1·§2 줄은 글자 그대로다(6차에 §1 맨 위에 PC 후속 한 줄만 더했다).
- §3~§9에서 끝난 일(완료·공개·종료·운영 반영)의 긴 서술이 섞인 항목은 「무엇이 끝났나 한두 줄 + 남은 일 원문 + 기록 링크 + `보관 tN-NN`」으로 줄였다. 남은 일·미검증·보류·주의 문장은 줄인 줄에 옮겼다. Platform 0.4.19~0.4.22 넷(t3-02~05)은 한 줄로 합쳤다. 짧거나 남은 일 중심인 78개 항목은 그대로다.
- 줄인 항목의 원래 줄은 [트랙 보관](../../트랙_보관_20261017.md)에 ID 앵커와 원래 줄 번호를 달아 글자 그대로 옮겼다(옮긴 줄이 보관에 그대로 있는지 스크립트로 확인). 보관 안 링크는 같은 폴더라 원래대로 이어진다. 트랙 새 줄·보관에 새로 깨진 링크는 0건이다.
- 정리 안내 한 줄은 머리 인용문 아래에 둔다(4차에 옮김). GPT 문서 정리 브랜치가 본문 단락 아래에 넣는 줄과 떨어져 있어, 두 브랜치를 합칠 때 트랙에서 부딪히지 않는다(6차에 실제로 부딪히지 않았다).

### 로컬 미푸시 수정과 3방향으로 합칠 때

기준(BASE)은 `1676291a:docs/_ops/트랙.md`다.

1. 로컬에서 고친 줄이 아래 표의 「그대로」 항목이면 보통 3방향 병합이 충돌 없이 들어간다(§1·§2는 t1-16 말고 전부 「그대로」).
2. 로컬에서 「줄임」 항목의 원래 줄을 고쳤으면 그 줄에서 충돌한다. 로컬 판과 BASE 판의 그 줄 차이(새 결과·새 남은 일)를 새 판의 짧은 줄에 옮기고, 보관은 BASE 그대로 둔다.
3. 로컬에서 새 항목을 더했으면 위치만 맞춰 그대로 넣는다.
4. 트랙은 LF다. 합친 뒤 `tr -cd '\r' < docs/_ops/트랙.md | wc -c`가 0인지 본다([줄끝 노트](../../../현장노트/git_줄끝_잠금.md)).

## 정한 것과 처리

5차까지 「유호님이 정하실 것」으로 남겼던 세 가지다. 10-17 유호님 「이건 지금 니가 전부 자율주행해줘」(세 판단을 맡김)와 「pc에서할수있게 저장해주고 저거 전부 자율주행으로 마무리하고 푸시하고 종료해줘」에 따라 6차에 정하고 처리했다. [결정 표](../../결정.md) 10-17 「문서 정리 합치기 · Claude 판단」 줄에 근거를 남겼다.

### 1. 합치는 순서

- **정한 것:** 제안한 순서 그대로 이 브랜치에 커밋으로 쌓았다. 이 정리(커밋 1~12) → master `64704bb52` 다시 합치기 → ZIP을 뺀 GPT 문서 정리 → 자격증명 기록 링크 → HA 원본 19개.
- **master:** 처음 지시(「master에 push·merge 하지 말 것」)대로 이 세션은 master에 올리지 않았다. PR [#198](https://github.com/unmet23-lab/synk-appsscript/pull/198)을 합치면 네 단계가 한 번에 들어간다.

### 2. GPT 문서 정리 브랜치의 ZIP 두 개

- **상황:** `codex/document-cleanup-20261017`(GPT, 10-17 13:47 `86334dd99`)은 103개 추가·463개 수정이고 지운 파일은 없다. 그 가운데 `docs/_ops/qa/document-cleanup-20261017/recovery-20261017.zip`(16,734,372B)과 `docs/_원고/기록_202609_기획과조판.zip`(2,998,291B)은 [저장소 용량 정책](../../../../tools/git-storage-policy.json)상 새 Git 이력에 넣지 않는 `.zip`이다. 복구 ZIP은 파일 하나 한도 10MiB도 넘는다.
- **정한 것:** ZIP 두 개만 뺀 같은 변경을 같은 바탕(`b32ca0542`)에 다시 만들어(`1493a597e`, 작성자·시각은 원 커밋 그대로) 합쳤다. ZIP은 master에 넣지 않고 원 브랜치에 그대로 둔다. [Git 자산 보관](../../github-storage/README.md)도 「기존 문서 정리 복구 ZIP과 `codex/document-cleanup-20261017` 브랜치는 유지한다」고 적는다.
- **무엇이 어디 있나:** `기록_202609_기획과조판.zip`의 원고 6개(MD 3·HTML 3)는 요약 전 판이 master 이력에 그대로 있다. 복구 ZIP에는 Git 밖 원본(미추적 문서 55쌍, 전역 스킬 26개의 전후 판, 은퇴한 스킬 사본)이 들어 있어 지금은 그 브랜치와 유호님 PC에만 있다. 그 브랜치를 지우려면 먼저 복구 ZIP을 비공개 Release로 옮긴다([PC 할 일](#pc에서-할-일) 9).
- **링크:** GPT 문서가 두 ZIP과 `_archive/` 원문을 가리키는 링크는 원래 경로대로 두었다(.gitignore 대상으로 셈). Release로 옮기면 목록에 적어 「Release 보관」이 된다.

### 3. 회사 HA 감시기 원본

- **상황:** master의 `deploy/ha/release-transition.py`는 서버의 `/opt/synk/ha/node-agent.mjs`·`/etc/synk/ha/plan.json`을 전제로 동작하지만, 그 원본은 합치지 않은 `codex/workspace-latency-fix-20261013`(10-13 14:25 `9c7c80429`)에만 있었다. 그 브랜치를 통째로 합치면 138파일이 부딪힌다(더한 382파일 중 363개는 다른 커밋으로 이미 master에 있음).
- **정한 것:** master에 없는 19개만 바이트 그대로 옮겼다. HA 원본 8개(감시기 `controller.mjs`, `node-agent.mjs`, `failover-policy.mjs`, `node-host.py`, `plan.json`, 시험 3개)와 서버 지연 증거 `verification/server-latency-20261013/` 11개다. 경로가 겹치지 않아 충돌이 없다.
- **확인:** 키·토큰·메일·전화번호가 없다. 공인 IP 하나(회사 고정 IP)는 이미 CLOUD-OPERATIONS에 적힌 값이다. HA 시험 3개(69개) 통과, 원본 문법 검사·`plan.json` 형식 통과.
- **주의:** 10-14~16에 HA를 다시 켤 때 쓴 판이 이 10-13 판보다 새것일 수 있다. [CLOUD-OPERATIONS 실행 계약](../../../마케팅/온라인마케팅지도/engagement/company/CLOUD-OPERATIONS.md#실행-계약)에 출처와 「서버 `/opt/synk/ha/`의 현재 판과 대조하기 전에는 배포 원본으로 쓰지 않는다」를 한 문장 더했다. master에는 저장소 파일을 서버로 복사하는 도구가 없다. 대조는 [PC 할 일](#pc에서-할-일) 8이다.

## PC에서 할 일

클라우드에서는 할 수 없어 남긴 것이다. PC 세션은 이 목록과 [트랙](../../트랙.md) §1 맨 위 「클라우드 문서 정리 합치기」 줄에서 시작한다.

## 자동 승인에 한 번 막혔던 것

3차에 위 두 가지(겹치는 문단을 GPT 문장으로 맞추기, 트랙 안내 줄 옮기기)를 하려 했으나, 이 세션의 자동 승인 단계가 「공유 자원 변경」으로 막았다. 다른 브랜치 내용을 공용 문서에 들여오는 일이라 막힌 것으로 보인다. 실행 전에 막혀 바뀐 파일은 없었다. 유호님께 권한 규칙 추가와 이번 일만 허락하는 방법의 장단점을 설명드렸고, 「1번 먼저 하자」(이번 일만 허락)에 따라 4차에 했다. 권한 규칙은 추가하지 않았다. 6차(GPT 정리·HA 원본 합치기)는 유호님의 위임 문장에 따라 진행했고 막히지 않았다.
