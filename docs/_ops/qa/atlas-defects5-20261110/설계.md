## 1. 결함 1 — 계정 호스트가 저장소 열거를 넘긴다

**원인(다시 확인).** `account/world-learning-host.js` 25행 `shared`가 `getItem · setItem · removeItem`만 넘기고 115행에서 그대로 엔진 저장소가 된다. `atlas/learning-pages.js`는 열거(`key` · `length`)가 없으면 헌 페이지를 지우지 않고 쓰는 쪽 울타리(writer fence)도 세우지 않는다(46~49 · 99 · 133~144행). 실제로 호스트에 들어오는 저장소는 두 곳 모두 `scopedStorage(localStorage, …)`(`experiences/synk-account/src/core.mjs` 134행)이고, 이것은 계정 구역 안의 열쇠만 세는 `length` · `key`를 이미 갖췄다(`world-game-host.mjs` 25~27행, `account-view.mjs` 115~118행). 열거가 호스트 한 겹에서만 끊긴다. PC 앱(`desktop/`)에는 이 호스트를 감싸는 코드가 없다(`world-learning-host` · `createWorldLearningHost` 검색 0건).

**고침.**

```js
const enumerated = (target, store) => {
  if (typeof store?.key !== 'function' || !('length' in store)) return target;
  Object.defineProperty(target, 'length', { enumerable: true, get() { check(); return store.length; } });
  target.key = index => { check(); return store.key(index); };
  return target;
};
const shared = enumerated({ getItem…, setItem…, removeItem… }, storage);
// 개인 기억 저장소(ownStorage)도 같은 꼴로 감싼다.
```

열거가 없는 저장소는 지금처럼 페이지를 다 남긴다(보수적 동작 그대로). 세션이 끝난 뒤(`check()`가 던짐)의 열거는 `learning-pages.js`의 정리 `try`가 받아 정리만 건너뛴다.

**시험(새로).** 「호스트를 지나 페이지로 쓰는 시험」이 없었다. `tests/atlas-host-pages.test.js`: 실제 호스트 + 실제 엔진 + 열거되는 저장소(5MiB 한도)로 첫 기기 열흘 → 둘째 기기 복원 · 사흘 연습, 날마다 ① 루트가 가리키지 않고 쓰는 쪽 울타리에도 없는 페이지 0 ② 동기화 `synced` ③ 서버 건수가 는다. 그리고 `stop()` 뒤 `length` · `key`가 `MEMORY_SESSION_ENDED`로 막히는지.

**문서.** [아틀라스 설계](../../../아틀라스_설계.md)의 10-30 C8 줄 「실제 계정 호스트는 키 열거를 제공」을 실제와 맞춘다(11-10까지 호스트가 열거를 버렸다는 사실 포함).

## 2. 결함 2 — 이력이 다 모인 페이지 꼴은 접는다

**원인.** 10-18 `ebd905be5`(「Preserve complete account learning history with resumable paged storage」)가 `compact()` 첫 줄에 `|| paged`를 더했다. 주석은 「큰 서버 복원은 완전한 인과 로그를 페이지에 둔다 — 뒤 페이지에 앞 부모의 피드백 · 철회가 있을 수 있다」. 1,024건을 넘으면 `paged = true`가 되고 되돌리는 길이 없어, 둘째 기기 · 오래 쉰 기기는 이력 전체를 영영 들고 다닌다.

**고침.** `if (!folding || paged && !complete) return;` — 주석을 「복원이 끝나기 전까지는 완전한 인과 로그를 둔다. 서버가 다 보낸 뒤에는 다른 저장소처럼 접는다」로 고친다.

**왜 안전한가.**
1. 원래 막은 까닭(뒤 페이지에 늦은 부모 연결)은 **복원 중에만** 성립한다. 복원 중에는 `complete`가 거짓이라(`learning-sync.js` 169~170행 — 마지막 쪽에서만 참) 지금처럼 접지 않는다. 마지막 쪽 뒤 `settle()`(173행)이 저장하며 처음 접는다.
2. `Ledger.plan`(`learning-ledger.js` 178~209행)은 항목을 통째로 접고, 뒤의 답 · 피드백 · 철회도 부모 결정의 묶음에 넣어 그 묶음의 마지막 시각을 늦춘다 — 남는 로그는 늘 인과적으로 닫혀 있다. 이 규칙은 페이지가 아닌 동기화 저장소가 이미 매일 쓰는 길이다.
3. 동기화 저장소는 서버가 돌려보낸(settled) 기록만, 하루 지난 것만 접는다(`fold.remote`). 접힌 기록은 `dropped`로 동기화기에 알린다 — 바뀌지 않는다.
4. 접힌 뒤 늦게 온 다른 기기 기록(stray · demote)도 페이지가 아닌 저장소와 같은 길이다.
5. `paged`는 접힌 뒤에도 참으로 남고(쓰기는 계속 `pages.write` — 바뀐 쪽만 새로 쓴다), 결함 1이 고쳐져 헌 페이지가 지워진다. 페이지 꼴에서 한 열쇠 꼴로 되돌아가는 길은 만들지 않는다 — 되돌리면 남은 페이지를 지울 길이 따로 필요하다.

**바뀌는 시험.** `tests/atlas-learning-pages.test.js`의 둘이 「복원 뒤 모든 기록이 그대로 남는다」를 단언해 고친 사본에서 실패한다(나머지 11은 통과).
- 「more than 20000 events restore …」: 새 단언 — 복원 완료 · 커서 끝 · 올림 0 · 루트 페이지 꼴 · 쪽마다 128 이하 · 남는 기록 ≤ 접기 한도(400) · **Core 요약(skills · concepts)이 같은 기록을 접지 않는 저장소(`fold: false`)로 읽은 요약과 같다** · 늦은 부모 연결 셋(late-a · late-f · late-x)이 그 요약에 반영 · 다시 열고 이어도 같은 요약 · 남은 기록의 정확한 재전송은 쓰기 0. 접힌 기록의 재전송은 다른 접힌 저장소와 같이 stray로 처리됨을 시험 이름에 적는다.
- 「history durable but outbox publication interrupted …」: 새 단언 — 다시 시작 뒤 완료 · 올림 0 · 남은 기록에 겹친 id 없음 · 요약이 접지 않은 판과 같다.

**시간.** 고친 사본의 2만 건 복원 끝 접기는 226ms(plan 15ms), 복원 전체 11.2초(고치기 전 13.6초). 시험이 129초 걸린 것은 실패한 단언이 2만 개 배열 차이를 그리느라였다.

**한계(그대로 남김).** 새 기기가 서버 이력을 다 받는 동안에는 페이지에 그대로 쌓이므로, 약 110일치에서 새 기기 복원이 5MiB 한도에 닿는 문제는 남는다. 재설계 6-2(계정은 서버가 접는다)의 몫이고 시한은 코호트 시작 뒤 3개월 안이다.

## 3. 결함 3 · 4 · 5 — 추천 정책판 5 (`learning-priority-5`)

칸 상태(`summarizeLearning` — 내 위치 · Temper · 보고가 읽는 측정)는 바꾸지 않는다. 바뀌는 것은 **고르는 순서**(`rankLearning`)와 **이유 한 줄**뿐이다.

### 3-1. 「다 봄」을 단일 계열에도 (결함 3)

지금: 복수 `familyKeys` 후보만 「다 봄」 −0.5, 단일 `familyKey` 후보는 「본 적 있음」 −0.10뿐이다. 그래서 「연습」 칸(우선도 1.0)의 본 문항(0.9)이 다른 칸의 새 문항(0.65)을 늘 이긴다 — 결함 3 그대로다. −0.5를 단일에도 걸어도 「연습」 칸 본 문항(0.4)이 「혼자 해냄」 칸 새 문항(0.15)을 이겨, 은행 모양에 따라 같은 덫이 다시 생긴다.

고침: 단일 계열 후보도 그 계열(`familyKey || itemKey`)이 제시된 적 있으면 「다 봄」이다. 정렬은 ① 「다 봄」이 아닌 후보가 모두 앞(점수와 상관없이) ② 「다 봄」끼리는 제시 횟수가 적은 것부터 ③ 그다음 지금의 점수 · 동점 규칙. 새 첫 시도를 줄 수 있는 후보가 남아 있는 동안은 갇히지 않고, 은행을 다 쓰면 고르게 돈다(같은 횟수 안에서는 놓친 칸이 앞). ~~활동 추천의 `spent`도 단일 대상에 같이 걸린다~~ — **v0.3에서 거뒀다(설계 검수 Fable F1).** WORLD는 생활 레슨 · 말하기에 일부러 `familyKeys`를 넘기지 않는다(같은 표현 계열을 새 장면에서 다시 쓴다 — Atlas × WORLD D §4-3 · E §4-4, `life-items.mjs` `lifeTarget`). 단일 대상까지 「다 씀」으로 보면 아직 안 한 다음 레슨이 「이 활동의 새 문항은 모두 만났어요」로 혼자 해낸 게임 뒤로 밀린다(Fable 재현: 레슨 2 `practice.checking` → `practice.spent`, 말하기 여섯 `[recent-independent, goal]` → `[spent, goal]`). 그래서 「다 봄」 첫 열쇠는 문항 고르기(`recommend`)에만 두고, 활동 추천의 「다 씀」과 점수(`activityScore`)는 정책판 4처럼 명시적 `familyKeys` 후보에만 건다. 활동 점수에서도 1분 안의 다시는 「방금 본」 −0.45를 받는다(아래 3-2).

### 3-2. 처음 시도를 놓친 계열은 한 번 다시 (결함 3 · 4)

「다 봄」만 고치면 놓친 문항은 새 문항이 남아 있는 동안 다시 안 나온다 — 「약한 것 먼저」(결함 4)가 더 나빠진다. 그래서 하나를 더한다.

- **한 번 다시:** 단일 계열이 **딱 한 번** 제시됐고 그 계열의 처음 시도(최근 30일 근거, `missed`)가 틀렸으면 「다 봄」이 아니다. 점수 = 칸 우선도 + 0.05(「본 적 있음」 −0.10은 빼지 않는다) — 같은 칸의 새 문항보다 조금 앞, 더 급한 칸의 새 문항보다는 뒤.
- **간격:** 그 제시가 1분 안이면 **기다린다** — 「다 봄」 후보보다도 뒤로 가서 다른 후보가 하나라도 있으면 나오지 않고, 혼자 남았을 때만 나온다. 그래서 한 번뿐인 다시가 1분 안에 쓰이지 않는다. 1분은 「마지막 넷」이 아니라 시각으로 잰다 — 하루 쉬고 온 사람에게 어제 마지막 문항이 「방금 본」이 되지 않게. (v0.1은 1분 안을 감점 −0.45로만 줘서, 다른 칸 새 문항 점수가 낮거나 나머지가 모두 「다 봄」이면 10초 만에 다시 나와 기회를 썼다 — 설계 검수 GPT GA1 · GA2.) 정렬 첫 열쇠는 ① 새 첫 시도 · 1분 지난 한 번 다시 ② 「다 봄」(덜 제시된 것부터) ③ 1분 안의 한 번 다시 순이다.
- **한 번뿐:** 다시 나온 뒤(제시 2회)에는 「다 봄」이다. 다시 푼 답은 근거가 아니다(Trail 판정 그대로) — 칸 상태를 내리지 않는다.

**v0.3 — 세 상태를 한 곳에서(설계 다시 검수 GPT GA1~GA3, 11-10).** GPT가 같은 자리에서 두 회차 연달아 P1을 냈다(앞 회차 GA1 · GB1 → 다시 GA1 · GA2 · GA3). ① 활동 추천은 대상의 `exhausted` · 점수로 정렬하는데 1분 안의 다시는 `exhausted`가 거짓이고 가산점까지 받아(.90) 새 문항 활동(.65)을 이겼다 ② 다른 후보가 없어 1분 안에 나온 제시가 「제시 1회」 조건을 깨 한 번뿐인 다시를 써 버렸다. 운영 원칙 ②대로 땜질을 멈추고 상태를 다시 짰다 — 한 번 다시의 상태는 `rankLearning` 한 곳에서 정하고, 모든 소비처는 그 행의 `exhausted` · `tier` · `retry` · 점수만 읽는다.

| 다 봄 | 두 번 이상 제시됨(v0.4 — 횟수) | `tier` 1, 덜 제시된 것부터 | −0.10 · −0.5 | −0.10(명시적 `familyKeys`를 다 봤을 때만 다 씀) | 칸 상태 |

- ~~**썼는지는 횟수가 아니라 시각으로 잰다.**~~ (v0.4에서 거둠 — 아래) 첫 제시 1분 뒤 이후의 제시가 있으면 쓴 것이다. 1분 안에 혼자 남아 나온 제시(게임이 후보 하나만 줄 때, 순간 맞춤이 위 다섯에서 난도로 고를 때)는 쓰지 않는다. 접힌 제시는 하루 넘은 것이고 시각이 없어, 둘이면 또는 하나에 뒤 제시가 있으면 쓴 것으로 본다(보수적 — 1분 안의 두 제시가 접기 경계에 걸리면 접힌 쪽만 「썼음」이 되는 드문 갈림은 남긴다).
- **시각 없는 제시 기록(끝 판 전체 시험, 11-10).** 마을(synk-town `support.mjs`)은 제시 기록에 시각을 넘기지 않는다. 시각으로만 재면 두 번째 제시가 다시를 쓰지 못해 다시가 끝없이 나오고, 접은 판(횟수)과 갈렸다(`tests/town-fold.test.js` 「접은 세계는 접지 않은 세계와 똑같이 읽힌다」 실패). 시각이 하나라도 없으면 v0.2처럼 두 번째 제시가 쓰고, 1분 대신 「바로 앞 넷」 안에서 기다린다(마을 접기는 앞 넷을 남겨 접은 판과 같다).
- **소비처 점검(rg, v0.3 — 순간 맞춤 줄은 v0.4 ⓒ에서 바뀜):** 순위 행을 직접 읽는 곳은 `learning.js`의 `recommend` · `recommendActivities` 둘뿐이다. `game-flow.js`는 `recommend` 순서의 위 다섯 안에서 난도로 고르므로, 후보가 적으면 기다림 후보를 고를 수 있지만 위 시각 판정으로 다시를 쓰지 않는다. 키트의 `return-practice.mjs`는 안 본 문항만 골라 상관없다.
- **시험(더함):** 「1분 안에 혼자 남아 나온 제시는 한 번 다시를 쓰지 않는다」 · 「활동 추천: 1분 안의 다시만 든 활동은 방금 본 것처럼 새 문항 활동 뒤」 · 「시각 없는 제시 기록 … 접은 판과 같게 읽힌다」 · 「다 본 단일 대상만 든 활동은 다 쓴 활동이 아니고 familyKeys를 다 본 활동만 다 쓴 활동」(WORLD 레슨 · 말하기 꼴, `tests/atlas-learning-priority-5.test.js`).

**v0.4 — 「썼는지」는 다시 횟수로, 이른 제시는 막는다(끝 판 검수 GPT, 11-10).** v0.3 뒤 끝 판 GPT가 같은 자리에서 셋째 회차 P1을 냈다. ① 활동 단계: 칸이 「연습」이면 1분 안의 다시만 든 활동이 급한 줄(활동 `tier` 0)이 되어 점수 감점과 상관없이 새 문항 활동을 이겼다(GA1 · GI1 · GK1 · GM1 · GN1, 같은 뿌리) ② 시각으로 잰 「썼는지」가 접힌 기록(시각 없음)에서 갈려, 1분 안에 두 번 나온 뒤 접히면 접은 판만 「썼음」이 됐다(GH1 — 접은 판 ≠ 접지 않은 판). 운영 원칙 ②대로 땜질을 멈추고 규칙을 다시 정했다. Atlas가 지켜 온 불변식은 「접은 판 = 접지 않은 판」(§2 · `tests/town-fold.test.js`)이므로 다른 쪽을 바꾼다.

- **쓰기는 횟수로:** 단일 계열이 **한 번** 제시됐고 처음 시도를 놓쳤을 때만 다시 대상이다(v0.2와 같다). 두 번째 제시가 무엇이든 그것이 한 번 다시다 — 접힌 제시도 횟수는 남아 같은 답이다.
- **이른 제시는 막는다:** 1분 안의 다시는 ⓐ 문항 고르기에서 맨 뒤(`tier` 2) ⓑ 그것만 든 활동은 칸 상태와 상관없이 급한 줄에 서지 않고 맨 뒤(활동 `tier` 2, 이유 코드는 칸 상태 그대로) ⓒ 순간 맞춤(`game-flow.js` `pick`)은 `recommend().waiting`에 든 후보를 위 다섯 창에서 뺀다(Core 첫째가 그것일 때 — 다른 후보가 없을 때 — 만 남는다). 그래서 1분 안에 나오는 것은 기다리지 않는 후보가 하나도 없을 때뿐이고(그때는 가장 오래 기다린 것부터), 그 제시가 한 번 다시다. ⓓ 활동의 대표 대상을 고를 때도 기다림은 맨 뒤이고, 그것뿐인 활동은 호스트 일정(`reviewAt` 도래 · `practiceNeed`)이 있어도 그 1분은 기다린다(끝 판 `-c` 검수 아르곤 K1 · K2 · GPT 11 — 섞인 활동의 대표 · 모두 기다림 · 호스트 일정)(v0.3의 「혼자 남아 나온 제시는 안 쓴다」는 거뒀다 — 접힌 기록과 갈렸다).
- **기다림은 시각으로:** 그 한 번의 제시가 1분 안이면 기다린다(시각이 없는 제품은 바로 앞 넷). 접기는 10분(동기화 저장소는 하루)이 지난 항목만, 마을은 앞 넷을 남기므로 기다림은 접어도 같다.
- **시험:** 「다른 후보가 하나도 없으면 1분 안에도 나오고 그 제시가 한 번 다시다」 · 「순간 맞춤은 1분 안의 다시를 위 다섯에서 고르지 않는다」 · 「연습 칸이어도 1분 안의 다시만 든 활동은 급한 줄에 서지 않는다」(`tests/atlas-learning-priority-5.test.js`), 공개 검사도 같은 장면을 끼운 판에서 돈다.

이것은 간격 반복의 「다시 배우기」를 가장 작게 들인 것이고 기억 모델(재설계 6-1)이 아니다 — 반복 정답을 약한 근거로 받아 상태를 내리고 간격을 늘리는 일은 그쪽 몫이다.

### 3-3. 이유 한 줄 (결함 5)

`recommend()`의 이유는 지금 `learningReason({ status: 칸 상태 })`이다. 칸(능력 × 난도 × 응답 꼴)이 처음이면 능력 이름으로 「아직 기록이 적어요」라고 말한다. 고침 — 이유 한 줄만 고른다(`reasonOf`, `state` 필드는 칸 상태 그대로). 앞 단계 · 다른 방식 이유는 **그 이유가 인용한 칸의 근거**를 따로 싣는다(v0.3 — 설계 검수 Fable F2: 근거 0건인 이유 문장이 나갔다). `evidence`는 지금처럼 그 칸(빈 칸) 그대로다 — 한 응답 꼴의 근거가 다른 꼴의 근거가 되지 않는다는 계약(`tests/atlas-formats.test.js`)이라, 처음 고친 판(`evidence` 자리에 인용 칸 근거)은 그 시험 셋을 깼다. 그래서 인용한 칸의 `reasonEvidence`를 `recommend()`와 활동 판정에 **`reasonEvidence` 필드**로 더하고, 활동 `basis`와 이유 코드(`practice.unseen` · `cold-start`)는 그대로 둔다:

| 경우 | 문장 |
|---|---|
| 3-2의 한 번 다시 | 「X」에서 놓친 문제를 한 번 더 풀어 봐요. |
| 칸은 처음, 같은 꼴 앞 단계가 「혼자 해냄」 | 「X」 앞 단계를 최근 혼자 해냈어요. 한 단계 올려 봐요. |
| 칸은 처음, 같은 능력 · 같은 단계를 다른 응답 꼴로 한 기록이 있음 | 「X」를 다른 방식으로 확인해 봐요. |
| 그 밖의 처음 칸 | 지금 문장 그대로(「X」는 아직 기록이 적어요. 짧게 확인해 봐요.) |

활동 추천(`recommendActivities`)도 고른 대상으로 같은 문장을 쓰되 **이유 코드는 그대로 둔다**(`practice.unseen` 등). WORLD 계획(`world-learning-plan.mjs` 217 · 228행)이 코드로 생활 레슨 · 이번 주 숙제 문장을 고르기 때문이다 — 코드를 바꾸면 그 화면의 문장이 바뀐다.

그래서 WORLD에서 새 문장이 닿는 곳과 안 닿는 곳이 갈린다(설계 검수 아르곤 A1):
- **생활 레슨(route `lesson`)이 처음 칸 대상으로 뽑히면** WORLD가 지금처럼 「생활 팩의 다음 레슨이에요. 아직 기록이 없는 표현을 새로 만나요.」로 덮는다. 앞 단계 · 다른 방식 대상이어도 그 문장은 레슨의 표현에 대해 참이라(그 칸에 근거가 없다) 그대로 둔다 — 제품이 고른 레슨 문장이다.
- **한 번 다시 대상은 이 분기에 들지 않는다.** 놓친 처음 시도가 있는 칸이라 상태가 `checking` · `practice` 등이고 코드가 `practice.<상태>`다(`practice.unseen`이 아니다). 시험이 이것을 단언한다.
- **게임(route `game`) · 짧은 연습**은 숙제와 맞지 않으면 엔진 문장 그대로라 새 문장이 보인다.

번역: `experiences/brand-opening/world-strings.mjs`에 `msg.vellum.step-up` · `new-format` · `retry`(en · mn)를 더한다. `world-lang.mjs`의 틀 맞추기가 `「{skill}」에서` · `「{skill}」 앞 단계를`도 받는지 시험한다. 몽골어는 `node tools/몽골어대조.js --파일 <묶음> --구독`으로 검문했다(11-10 — 무료 문은 네트워크 시간 초과, 구독 문으로 다시):

### 3-4. 찰칵 낱말 낱말 태그 (결함 4)

`experiences/snap-words/learning.mjs`에 `WORD_CONCEPT`(20개 → `ko.word.w…`)를 두고 `conceptIds`에 넣는다. 37개 가운데 국립국어원 학습용 어휘(A · B) 20개가 TOPIK I 지도의 낱말 마디와 한국어로 하나씩 맞고(겹침 0), 생활 · 안내문 17개는 마디가 없어 태그가 없다. 시험: 마디가 `kind: word`이고 `label_ko`가 낱말의 `ko`와 같다 · A · B 띠 낱말은 모두 태그가 있다 · 두 낱말을 틀린 뒤 1분이 지나면 `weak()`가 그 둘을 먼저 낸다.

## 5. 배포

**synk.im.** 공개본 엔진 사본은 `적용/공개묶음.cjs`가 공개본 전체에서 Core · 계정 호스트 표식으로 찾는다(11-10 `fb170437`: 엔진 사본 28 · 묶음 종류 11 + 찰칵 `learning.mjs` + 번역 표 = 30파일). 공개본 = 바탕 생성물인 7곳(`world/` 게임 여섯 · 드라마)은 새 생성물로, 나머지는 파서로 Core(`learning.js` · `vellum.js` — 둘은 함께, Fable F5) 모듈을 통째로 바꾸고, `game-learning.js`는 접기 막는 줄만 · `game-flow.js`는 순간 맞춤 창 줄만 앵커로, 계정 호스트는 `shared` · `ownStorage` 두 자리만 파서로 고친다 — 호스트는 공개본마다 판이 달라서다(계정 묶음은 연결 끊기 · 재확인 인자 전 판, ID · WORLD는 손으로 덧댄 `__atlasDisconnect` 판: 기존차이 9~11곳). Core · Vellum의 기존차이는 내보내기 이름 꼬리뿐이다. 번역 표는 공개본 + (바탕 → 작업본) 3방향. `적용/공개검사.mjs`가 끼운 판과 공개본을 묶음 종류마다 불러 정책판 · 작은 칸 · 한 번 다시 · 활동 기다림 · 앞 단계 이유 · 다 모인 페이지 꼴 접기 · 호스트 열거를 돌린다(공개본은 같은 장면에서 결함이 재현돼야 통과).

**PC 앱.** 학습 호스트를 감싸지 않고 공개 WORLD를 읽는다(§1). 회원 화면 묶음(`desktop/renderer/generated/member-*`)은 vellum 해시만 바뀌어 다음 PC 판에 실린다 — 새 이유 셋은 Core 추천에서만 나와 회원 화면 동작은 그대로다.

**Talk.** 서버 사본은 정책판 3인 별도 운영 판이라 건드리지 않는다(`--local`).

## 7. 검수에 묻는 것

1. §2: 복원이 끝난 뒤 페이지 꼴을 접는 것이 원래 막은 까닭(늦은 부모 연결)을 다시 열지 않는가. `complete`가 참인데 아직 안 온 기록이 있는 경로가 있는가.
2. §3-1: 「다 봄」을 점수가 아니라 정렬 첫 열쇠로 둔 것 — 놓친 칸의 본 문항보다 쉬운 칸의 새 문항이 먼저 나오는 것이 연습으로 받아들일 만한가, 아니면 덫보다 나은 다른 꼴이 있는가.
3. §3-2: 한 번 다시의 조건(제시 1회 · 처음 시도 놓침 · 30일 · 1분)과 +0.05가 다른 게임(주문 폭주 · 바람길 · 달리기 · 리듬)의 순서를 해치지 않는가.
4. §3-3: 활동 이유 코드를 그대로 두고 문장만 바꾼 것이 WORLD 계획 · 번역 층에서 어긋나는 곳이 있는가. 몽골어 세 줄.
5. 이 다섯을 막는 데 빠진 것, 다른 덫을 새로 만든 것.
