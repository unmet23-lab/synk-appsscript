## 1. 결함 1 — 계정 호스트가 저장소 열거를 넘긴다

**원인(다시 확인).** `account/world-learning-host.js` 25행 `shared`가 `getItem · setItem · removeItem`만 넘기고 115행에서 그대로 엔진 저장소가 된다. `atlas/learning-pages.js`는 열거(`key` · `length`)가 없으면 헌 페이지를 지우지 않고 쓰는 쪽 울타리(writer fence)도 세우지 않는다(46~49 · 99 · 133~144행). 실제로 호스트에 들어오는 저장소는 두 곳 모두 `scopedStorage(localStorage, …)`(`experiences/synk-account/src/core.mjs` 134행)이고, 이것은 계정 구역 안의 열쇠만 세는 `length` · `key`를 이미 갖췄다(`world-game-host.mjs` 25~27행, `account-view.mjs` 115~118행). 열거가 호스트 한 겹에서만 끊긴다. PC 앱(`desktop/`)에는 이 호스트를 감싸는 코드가 없다(`world-learning-host` · `createWorldLearningHost` 검색 0건).

**고침.**

```js
const enumerated = (target, store) => {
  if (typeof store?.key !== 'function' || !('length' in store)) return target;
  Object.defineProperty(target, 'length', { enumerable: true, get() { check(); return store.length; } });
  target.key = index => { check(); return store.key(index); };
  return target;
};
const shared = enumerated({ getItem…, setItem…, removeItem… }, storage);
// 개인 기억 저장소(ownStorage)도 같은 꼴로 감싼다.
```

열거가 없는 저장소는 지금처럼 페이지를 다 남긴다(보수적 동작 그대로). 세션이 끝난 뒤(`check()`가 던짐)의 열거는 `learning-pages.js`의 정리 `try`가 받아 정리만 건너뛴다.

**시험(새로).** 「호스트를 지나 페이지로 쓰는 시험」이 없었다. `tests/atlas-host-pages.test.js`: 실제 호스트 + 실제 엔진 + 열거되는 저장소(5MiB 한도)로 첫 기기 열흘 → 둘째 기기 복원 · 사흘 연습, 날마다 ① 루트가 가리키지 않고 쓰는 쪽 울타리에도 없는 페이지 0 ② 동기화 `synced` ③ 서버 건수가 는다. 그리고 `stop()` 뒤 `length` · `key`가 `MEMORY_SESSION_ENDED`로 막히는지.

**문서.** [아틀라스 설계](../../../아틀라스_설계.md)의 10-30 C8 줄 「실제 계정 호스트는 키 열거를 제공」을 실제와 맞춘다(11-10까지 호스트가 열거를 버렸다는 사실 포함).

## 2. 결함 2 — 이력이 다 모인 페이지 꼴은 접는다

**원인.** 10-18 `ebd905be5`(「Preserve complete account learning history with resumable paged storage」)가 `compact()` 첫 줄에 `|| paged`를 더했다. 주석은 「큰 서버 복원은 완전한 인과 로그를 페이지에 둔다 — 뒤 페이지에 앞 부모의 피드백 · 철회가 있을 수 있다」. 1,024건을 넘으면 `paged = true`가 되고 되돌리는 길이 없어, 둘째 기기 · 오래 쉰 기기는 이력 전체를 영영 들고 다닌다.

**고침.** `if (!folding || paged && !complete) return;` — 주석을 「복원이 끝나기 전까지는 완전한 인과 로그를 둔다. 서버가 다 보낸 뒤에는 다른 저장소처럼 접는다」로 고친다.

**왜 안전한가.**
1. 원래 막은 까닭(뒤 페이지에 늦은 부모 연결)은 **복원 중에만** 성립한다. 복원 중에는 `complete`가 거짓이라(`learning-sync.js` 169~170행 — 마지막 쪽에서만 참) 지금처럼 접지 않는다. 마지막 쪽 뒤 `settle()`(173행)이 저장하며 처음 접는다.
2. `Ledger.plan`(`learning-ledger.js` 178~209행)은 항목을 통째로 접고, 뒤의 답 · 피드백 · 철회도 부모 결정의 묶음에 넣어 그 묶음의 마지막 시각을 늦춘다 — 남는 로그는 늘 인과적으로 닫혀 있다. 이 규칙은 페이지가 아닌 동기화 저장소가 이미 매일 쓰는 길이다.
3. 동기화 저장소는 서버가 돌려보낸(settled) 기록만, 하루 지난 것만 접는다(`fold.remote`). 접힌 기록은 `dropped`로 동기화기에 알린다 — 바뀌지 않는다.
4. 접힌 뒤 늦게 온 다른 기기 기록(stray · demote)도 페이지가 아닌 저장소와 같은 길이다.
5. `paged`는 접힌 뒤에도 참으로 남고(쓰기는 계속 `pages.write` — 바뀐 쪽만 새로 쓴다), 결함 1이 고쳐져 헌 페이지가 지워진다. 페이지 꼴에서 한 열쇠 꼴로 되돌아가는 길은 만들지 않는다 — 되돌리면 남은 페이지를 지울 길이 따로 필요하다.

**바뀌는 시험.** `tests/atlas-learning-pages.test.js`의 둘이 「복원 뒤 모든 기록이 그대로 남는다」를 단언해 고친 사본에서 실패한다(나머지 11은 통과).
- 「more than 20000 events restore …」: 새 단언 — 복원 완료 · 커서 끝 · 올림 0 · 루트 페이지 꼴 · 쪽마다 128 이하 · 남는 기록 ≤ 접기 한도(400) · **Core 요약(skills · concepts)이 같은 기록을 접지 않는 저장소(`fold: false`)로 읽은 요약과 같다** · 늦은 부모 연결 셋(late-a · late-f · late-x)이 그 요약에 반영 · 다시 열고 이어도 같은 요약 · 남은 기록의 정확한 재전송은 쓰기 0. 접힌 기록의 재전송은 다른 접힌 저장소와 같이 stray로 처리됨을 시험 이름에 적는다.
- 「history durable but outbox publication interrupted …」: 새 단언 — 다시 시작 뒤 완료 · 올림 0 · 남은 기록에 겹친 id 없음 · 요약이 접지 않은 판과 같다.

**시간.** 고친 사본의 2만 건 복원 끝 접기는 226ms(plan 15ms), 복원 전체 11.2초(고치기 전 13.6초). 시험이 129초 걸린 것은 실패한 단언이 2만 개 배열 차이를 그리느라였다.

**한계(그대로 남김).** 새 기기가 서버 이력을 다 받는 동안에는 페이지에 그대로 쌓이므로, 약 110일치에서 새 기기 복원이 5MiB 한도에 닿는 문제는 남는다. 재설계 6-2(계정은 서버가 접는다)의 몫이고 시한은 코호트 시작 뒤 3개월 안이다.

## 3. 결함 3 · 4 · 5 — 추천 정책판 5 (`learning-priority-5`)

칸 상태(`summarizeLearning` — 내 위치 · Temper · 보고가 읽는 측정)는 바꾸지 않는다. 바뀌는 것은 **고르는 순서**(`rankLearning`)와 **이유 한 줄**뿐이다.

### 3-1. 「다 봄」을 단일 계열에도 (결함 3)

지금: 복수 `familyKeys` 후보만 「다 봄」 −0.5, 단일 `familyKey` 후보는 「본 적 있음」 −0.10뿐이다. 그래서 「연습」 칸(우선도 1.0)의 본 문항(0.9)이 다른 칸의 새 문항(0.65)을 늘 이긴다 — 결함 3 그대로다. −0.5를 단일에도 걸어도 「연습」 칸 본 문항(0.4)이 「혼자 해냄」 칸 새 문항(0.15)을 이겨, 은행 모양에 따라 같은 덫이 다시 생긴다.

고침: 단일 계열 후보도 그 계열(`familyKey || itemKey`)이 제시된 적 있으면 「다 봄」이다. 정렬은 ① 「다 봄」이 아닌 후보가 모두 앞(점수와 상관없이) ② 「다 봄」끼리는 제시 횟수가 적은 것부터 ③ 그다음 지금의 점수 · 동점 규칙. 새 첫 시도를 줄 수 있는 후보가 남아 있는 동안은 갇히지 않고, 은행을 다 쓰면 고르게 돈다(같은 횟수 안에서는 놓친 칸이 앞). 활동 추천의 `spent`(모든 대상이 「다 봄」)도 단일 대상에 같이 걸려, 다 본 단일 대상만 남은 활동이 홈에서 늘 급한 칸으로 남지 않는다.

### 3-2. 처음 시도를 놓친 계열은 한 번 다시 (결함 3 · 4)

「다 봄」만 고치면 놓친 문항은 새 문항이 남아 있는 동안 다시 안 나온다 — 「약한 것 먼저」(결함 4)가 더 나빠진다. 그래서 하나를 더한다.

- **한 번 다시:** 단일 계열이 **딱 한 번** 제시됐고 그 계열의 처음 시도(최근 30일 근거, `missed`)가 틀렸으면 「다 봄」이 아니다. 점수 = 칸 우선도 + 0.05(「본 적 있음」 −0.10은 빼지 않는다) — 같은 칸의 새 문항보다 조금 앞, 더 급한 칸의 새 문항보다는 뒤.
- **간격:** 그 제시가 1분 안이면 **기다린다** — 「다 봄」 후보보다도 뒤로 가서 다른 후보가 하나라도 있으면 나오지 않고, 혼자 남았을 때만 나온다. 그래서 한 번뿐인 다시가 1분 안에 쓰이지 않는다. 1분은 「마지막 넷」이 아니라 시각으로 잰다 — 하루 쉬고 온 사람에게 어제 마지막 문항이 「방금 본」이 되지 않게. (v0.1은 1분 안을 감점 −0.45로만 줘서, 다른 칸 새 문항 점수가 낮거나 나머지가 모두 「다 봄」이면 10초 만에 다시 나와 기회를 썼다 — 설계 검수 GPT GA1 · GA2.) 정렬 첫 열쇠는 ① 새 첫 시도 · 1분 지난 한 번 다시 ② 「다 봄」(덜 제시된 것부터) ③ 1분 안의 한 번 다시 순이다.
- **한 번뿐:** 다시 나온 뒤(제시 2회)에는 「다 봄」이다. 다시 푼 답은 근거가 아니다(Trail 판정 그대로) — 칸 상태를 내리지 않는다.

이것은 간격 반복의 「다시 배우기」를 가장 작게 들인 것이고 기억 모델(재설계 6-1)이 아니다 — 반복 정답을 약한 근거로 받아 상태를 내리고 간격을 늘리는 일은 그쪽 몫이다.

### 3-3. 이유 한 줄 (결함 5)

`recommend()`의 이유는 지금 `learningReason({ status: 칸 상태 })`이다. 칸(능력 × 난도 × 응답 꼴)이 처음이면 능력 이름으로 「아직 기록이 적어요」라고 말한다. 고침 — 이유 한 줄만 고른다(`reasonStatus`, `state` 필드는 칸 상태 그대로):

| 경우 | 문장 |
|---|---|
| 3-2의 한 번 다시 | 「X」에서 놓친 문제를 한 번 더 풀어 봐요. |
| 칸은 처음, 같은 꼴 앞 단계가 「혼자 해냄」 | 「X」 앞 단계를 최근 혼자 해냈어요. 한 단계 올려 봐요. |
| 칸은 처음, 같은 능력 · 같은 단계를 다른 응답 꼴로 한 기록이 있음 | 「X」를 다른 방식으로 확인해 봐요. |
| 그 밖의 처음 칸 | 지금 문장 그대로(「X」는 아직 기록이 적어요. 짧게 확인해 봐요.) |

활동 추천(`recommendActivities`)도 고른 대상으로 같은 문장을 쓰되 **이유 코드는 그대로 둔다**(`practice.unseen` 등). WORLD 계획(`world-learning-plan.mjs` 217 · 228행)이 코드로 생활 레슨 · 이번 주 숙제 문장을 고르기 때문이다 — 코드를 바꾸면 그 화면의 문장이 바뀐다.

그래서 WORLD에서 새 문장이 닿는 곳과 안 닿는 곳이 갈린다(설계 검수 아르곤 A1):
- **생활 레슨(route `lesson`)이 처음 칸 대상으로 뽑히면** WORLD가 지금처럼 「생활 팩의 다음 레슨이에요. 아직 기록이 없는 표현을 새로 만나요.」로 덮는다. 앞 단계 · 다른 방식 대상이어도 그 문장은 레슨의 표현에 대해 참이라(그 칸에 근거가 없다) 그대로 둔다 — 제품이 고른 레슨 문장이다.
- **한 번 다시 대상은 이 분기에 들지 않는다.** 놓친 처음 시도가 있는 칸이라 상태가 `checking` · `practice` 등이고 코드가 `practice.<상태>`다(`practice.unseen`이 아니다). 시험이 이것을 단언한다.
