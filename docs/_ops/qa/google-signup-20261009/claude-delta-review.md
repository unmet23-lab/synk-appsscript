## 이전 지적 수정 확인

**P1 · Google 가입 때 고른 학습 기록 저장이 무시됨 → 수정 적절**
- 프런트가 이제 `x-synk-app-version: 0.2.0`을 보냅니다(`google-auth.mjs:103`).
- 서버 쪽 경로도 맞습니다.
  - CORS에서 이 헤더를 허용합니다(`synk-server.js:38`).
  - `:48` → `index.ts:15` → `release-policy.js:38-39` 순서로 판정하고, 0.2.0 하한을 통과합니다.
- 회귀 테스트가 실제 `parsePolicy`/`featureDecision`과 PGlite로 확인합니다(`google-registration.test.js:137-160`).
  - 헤더가 없으면 false, 0.2.0이면 true입니다.
  - DB의 `learning_enabled` 값까지 확인합니다(`validation.tap:12`, 109/109 통과).
- 프런트 테스트(`google-auth.test.mjs:153`)와 브라우저 증거 두 개도 헤더 0.2.0을 확인합니다.

**P2-2 · Google 콜백이 실패하면 로그인 화면이 뜸 → 수정 적절**
- `google_flow`가 붙은 실패 콜백만 `GOOGLE_CALLBACK_INCOMPLETE`로 분류하고, 그때만 `clearCallback()`을 부릅니다(`portal.mjs:325-330`).
- 번들된 SDK 동작이 이 수정과 맞습니다.
  - URL에 오류가 있어도 기존 세션을 지우지 않습니다(`GoTrueClient.js:415-417`).
  - 코드 교환에 성공할 때만 URL의 `code`를 지웁니다(`:3290-3293`).
  - 따라서 "실패로 판정됐는데 사실은 이번 콜백으로 로그인된 경우"는 생기지 않습니다.
- 차단 상태(`callbackBlocked`)가 유지되어 앱 연결 동의와 자동 승인이 막힙니다(`:182`, `:186`).
- 콜백이 성공했는데 일회용 확인값(nonce)이나 사용자가 다르면 계속 막힙니다(`boundaries:186-196`).
- Google 세션의 가입 확인 절차는 그대로라(`google-auth.mjs:166-173`) 가입을 건너뛸 수 없습니다.

**P2-3 · 같은 번호로 다시 요청하면 인증 상태가 지워짐 → 보고한 경우는 해결**
- 이미 인증한 번호로 다시 누르면 문자 없이 인증 상태를 유지합니다(`:133`).
- Auth가 아무것도 바꾸지 않은 응답(no-op)에서도 인증 상태를 되살립니다(`:136-138`).
- 띄어쓰기·하이픈 같은 서식만 바꾼 입력은 인증 상태를 유지합니다(`:125-128`).
- 기기 시계와 비교하는 부분을 없앴습니다(`:75-79`, `:171`).
- 서버가 미래 시각의 인증을 거부하는 검사는 그대로입니다(`synk-auth.js:59-61`).
- 아직 남은 드문 경우는 아래 P3-1·P3-2에 적었습니다.

**P2-4 · Google이 꺼져도 연결 카드가 보임 → 수정 적절**
- 카드 표시 여부를 Google 사용 가능 여부·계정 화면 표시·가입 필요 여부로 함께 판단합니다(`:83`).
- 계정 화면 표시, 초기화, 설정 변경(`:176-180`)이 모두 같은 경로로 화면을 다시 그립니다.

**P2-5 · 동의 전에 번호를 보내고, 중단하면 지울 방법이 없음 → 코드·문구는 적절**

## P2 (새로 생김): 공개 설정 키를 기존 번들이 거부함

**원인**
- `readConfig`는 모르는 키가 하나라도 있으면 설정 전체를 거부합니다(`frontend/src/core.mjs:26`).
- 이번 수정으로 `googlePhoneVerificationEnabled`를 허용 목록에 넣었고(`:25`), 예시 파일에도 `false`로 넣었습니다(`config.example.json:9`).
- 그런데 같은 `synk-account/config.json`을 읽는 다른 번들은 다시 빌드하지 않았습니다(`sharedDistModified:false`).
  - 작업본의 `dist/client.js`·`platform.js`·`preview.js`·`app.js`는 모두 옛 허용 목록을 가지고 있습니다. 예: `dist/client.js:2`.
  - 이 번들들의 소스에서 config를 읽는 곳은 `src/client.mjs:159,166`, `src/platform.mjs:140`입니다.
- 문서도 순서를 안내하지 않습니다.
  - README(`:103`)는 예시 파일을 그대로 `config.json`으로 복사하라고 안내합니다.
  - 운영 문서(`GOOGLE-SMS-SETUP.md:83,89`)는 이 키를 켜라고만 하고, 이 설정을 읽는 번들을 언제 갱신할지는 적지 않았습니다.

**깨지는 동작**
- 공개 config에 이 키가 들어가면, 값이 `false`여도 옛 번들을 쓰는 화면은 시작할 때 "공개 설정 파일의 형식을 확인해 주세요."로 멈춥니다.
- 영향받는 화면은 `client.html`(제품 SSO 입구)과 `platform.html`입니다.
- 두 화면은 캐시 키 없이 번들을 불러옵니다(`client.html:2`, `platform.html:7`). 그래서 빌드 도구로 네 번들을 함께 다시 만들어도(README `:143`), 브라우저 캐시가 남아 있는 동안에는 같은 문제가 생길 수 있습니다.

**재현:** `reviewed-v1/src/core.mjs`의 `readConfig`(작업본 `dist/client.js`와 허용 목록이 같음)에 `frontend/config.example.json`을 넣으면 `:26`에서 예외가 납니다.

**제안**
- 예시 파일에서 `false` 줄을 뺍니다. 키가 없으면 `false`로 처리됩니다(`core.mjs:35`).
- 운영 문서에 순서를 적습니다. `true`는 네 번들을 모두 새 `core.mjs`로 배포하고 캐시가 지난 뒤에만 넣습니다.

## P3

1. **대기 중인 번호 변경이 있을 때 원래 번호로 되돌리면, 문자가 안 가는데 보냈다고 안내함** (`google-auth.mjs:136-139`)
   - 상황: P1을 인증한 뒤 P2로 문자를 요청해 `new_phone=P2`인 상태에서, 60초 뒤 P1로 다시 요청합니다.
   - upstream Auth는 현재 번호와 같은 번호 요청을 처리하지 않습니다. 그래서 응답의 `new_phone`은 여전히 P2이고, 확인된 번호도 없는 것으로 나옵니다.
   - 결과적으로 "인증번호를 요청했어요"가 표시되지만 문자는 오지 않습니다. 서버도 이 상태에서는 P1을 인증으로 인정하지 않습니다(`synk-auth.js:61`).
   - 재현: 테스트 픽스처에서 `updateUser`가 `{...confirmedUser, new_phone: SECOND}`를 돌려주게 하고 위 순서대로 진행합니다.
   - 이 Auth 동작은 실제 서비스로 확인하지 않았습니다.
2. **번호를 지웠다가 다시 쓰면 인증번호 확인이 막힘** (`:127`, `:144`)
   - 입력 도중에 '문자를 보낸 번호' 기록이 지워지고, 같은 번호를 다시 써도 되살아나지 않습니다.
   - 그래서 인증번호 확인이 `PHONE_CODE_REQUIRED`로 막히고, 60초 뒤 유료 문자를 한 번 더 보내야 합니다.
   - v1부터 있던 동작입니다. 확인 단계(`:144`)에서 이미 번호를 비교하므로, 입력할 때는 이 기록을 지우지 않아도 됩니다.
3. **이미 다른 계정에 연결된 Google로 연결하다 실패해도 일반 문구만 나옴** (`portal.mjs:21,326`)
   - 이 경우 SDK는 `identity_already_exists` 오류를 돌려줍니다(`GoTrueClient.js:409`).
   - 그런데 화면에는 "취소했다면 다시 계속해 주세요"만 보여서, 다시 시도해도 같은 이유로 실패합니다.
   - `error_code`에 따라 다른 안내를 보여 주는 편이 좋습니다.
