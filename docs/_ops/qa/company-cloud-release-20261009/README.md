# 회사 클라우드·고객 상담·업무 알림 릴리스

2026-10-09. PC에 있던 회사·메신저를 영구 저장소가 있는 HTTPS 서버로 이전했다. 직원과 고객 로그인 경로를 분리하고 개인별 AI 한도, 백업·감시, SNS 수집과 독립된 예약·마감 알림을 준비했다. 유료 AI와 SNS 수집은 꺼져 있다.

## 배포와 이번 푸시의 차이

현재 배포는 `aeb1620ebc40`이며 이미지 SHA256은 `79a7377a443ba5759ce76159a77fd8026531d14be38c5f3967c2686a84ccb45e`다. 이 커밋은 해당 고정본의 실행 코드·시험·배포 구성을 원격 저장소에 보존하며 공용 작업본의 이후 고객 관리·로그인 유지 작업은 포함하지 않는다.

푸시 준비의 확대 시험에서 업무카드 검증 오류 두 건이 HTTP 500으로 보이는 문제를 재현했다. Atlas 입력 검증의 `TypeError`만 HTTP 400으로 바꾸고 예상하지 못한 서버 오류의 익명화는 유지했다. 세션 철회 시험은 비동기 인증이 끝난 뒤 본문 수신 중에 철회하도록 고쳤다. **이 작은 후속 수정은 소스·시험에만 반영했으며 운영 서버에 다시 배포하지 않았다.** 운영 Linux 검사·공개 검증을 이 수정의 배포 증거로 사용하지 않는다.

Git에는 실행에 필요한 파일과 검증 요약·해시를 남긴다. 중복 보존하던 캡처 등 67파일 약10.2MB는 푸시 묶음에서 제외했으며 원본은 로컬에 보존했다. 운영 DB·암호화 키·개인 메일 화면·OAuth 상태 기록은 포함하지 않는다. 운영 문서는 반복된 배포 이력을 줄이고 실행 계약과 미완료 사항을 앞에 모았다.

## 검증

- 배포 고정본: Linux **576/576**, skip0. Docker 전달108항목, 실제 이미지 기동·교체 각24항목과 알림 lifecycle·권한 철회·일시 인증 장애·VAPID 회귀 통과.
- 푸시 작업본: 회사·메신저 전체119파일에서 **1,159개 통과·실패0·Windows 심볼릭 링크 시험2개 skip**. 최종 결과는 [verification.json](verification.json)의 `pushVerification`에 기록했다. 첫 확대 검사1156통과·3실패·2skip도 보존하고 위 두 문제를 수정했다.
- SYNK ID 등록·기존 연결 회귀 **81/81**. 업무카드·요청 보안·포털 생성의 후속 검사 **25/25**. 포털 시험은 깨끗한 작업본의 `dist/app.js`가 없어 먼저 실패했으며 기존 빌드 도구로 준비한 뒤 통과했다. 생성물은 푸시하지 않는다.
- 직원·고객의 실제 로그인과 기존 메모·첨부·고객 초안 보존 확인. 브라우저가 열린 상태에서의 조회 없이 서버가 예약 알림1건을 생성했고 재접속 후 읽음 처리했다. 시험 기록은 보존했고 실물 푸시 등록·발송은0이다.
- 배포 전후 두 DB 전체 행·스키마와 암호화 키·VAPID·DB 밖 파일의 정지 사본 대조에서 문제0, token 삭제0. 이전 릴리스의 세션1건 수동 수락과 이번 결과는 구분한다.
- 완료된01:10 수동 백업166,980B를 GCS에서 직접 내려받아 SHA를 대조하고01:44 현재 배포 이미지로 격리 복구했다. 회사6표·메신저27표·키·계정 관계와 무결성을 확인했다. 과거 온라인 백업의 복구 증거이며 현재 실시간 자료와 동일하다는 뜻은 아니다.
- HTTPS·TLS 경보 메일2종 실제 수신·정책 원복·사건 닫힘 확인. 실제 장애나 인증서 손상은 만들지 않았다.

원래 배포의 [파일 해시 목록](deployed-source-manifest.json)과 [검증 요약 및 보호된 원시 자료의 해시](verification.json)를 함께 본다. Git의 텍스트 줄끝 정규화와 후속 문서·업무카드 수정 때문에 이 커밋 전체를 원래424파일의 바이트 동일본으로 주장하지 않는다.
