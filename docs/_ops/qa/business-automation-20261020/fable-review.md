# Fable 검수 기록

2026-10-20 사용자 요청에 따라 공식 Claude CLI의 `claude-fable-5-1`으로 검수했다. 실행은 기존 Claude 구독을 사용했고 새 결제는 하지 않았다. 도구는 Read·Grep·Glob으로 한정했으며 실행·외부 요청·배포·발송은 하지 않았다. 아래 시험은 구현 담당자가 실행한 결과다.

| 검수 | 범위 | 결과 |
|---|---|---|
| 1차 | 서버 서비스, 승인 게시와 DM 연결, 로컬 잠금 | 확정 지적 3건 수정, 재현·회귀 시험 통과 |
| 2차 | 화면 연결, 운영 상태, SNS 발견·성과, Talk 조회 권한 | 확정 지적 7건 수정, 단위 68개·격리 브라우저 1개 통과 |
| 최종 | 앞선 10건 수정, PC→서버 문의 동의, 기존 수집 분기·라우트, 자동 삭제 제외 | 성공, 앞선 10건 모두 닫힘, 새 확정 결함 없음 |
| 추가 | 회사·Talk 배포 대상 고정, DM stdin 설치, 문의 후보 해시 보정 | 82턴으로 성공, 읽은 범위에서 새 확정 P0~P2 결함 없음 |

## 수정한 문제

| 번호 | 문제 | 반영 |
|---|---|---|
| F1 | DM 등록 예외가 독립적인 게시 성과 등록도 중단 | 만료·영수증 충돌·확인 필요 상태를 저장하고 성과 등록을 계속 |
| F2 | 종료된 프로세스의 잠금이 남아 이후 실행 차단 | 죽은 PID만 복구하고 불명확한 외부 결과는 재조회로 확인 |
| F3 | 만료와 입력 오류를 모두 승인 변경으로 표시 | 실제 오류 원인별 상태·안내 사용 |
| F4 | 선택적 성과 데이터 오류가 전체 SNS 연결 상태를 숨김 | 성과 파싱 실패를 해당 구역에 격리 |
| F5 | 백업 회차 ID가 모두 없으면 같은 회차로 인정 | 비어 있지 않은 ID가 정확히 일치할 때만 복구 영수증 연결 |
| F6 | 본문에 나중에 등장한 과거 성공을 최신 실행으로 선택 | 실행 시각을 기준으로 최신 상태 선택 |
| F7 | 브라우저 시험이 실제 Hermes 런타임을 읽음 | 합성 원문과 빈 Hermes 홈으로 시험 격리 |
| F8 | 주기적 화면 갱신마다 Git 명령 반복 | 성공한 대상별 응답을 최대 60초 재사용, 수동·원문 변경 시 즉시 갱신 |
| F9 | 일부 근거 상태에 한국어 안내 누락 | `no_changes`·`needs_attention` 안내 추가 |
| F10 | 성과 요약의 계정 출처 링크가 잘못된 필드 참조 | 실제 `canonicalUrl` 사용 |

최종 검토는 65턴으로 완료됐다. 미확인 운영 설정을 결함으로 단정하지 않았고, Forms 403 진단 세분화와 정적 자산 개수 하한에 대한 개선 의견을 남겼다. 당시 남긴 Google 동의 이후 확인 사항과 이후 실제 운영 결과는 [사업 자동화 기록](README.md)에 구분했다. 정적 자산 검사는 실제 index 참조 전수·서빙 버전 URL·파일 해시·신규 문의 자산 2개를 대조하므로 고정 개수만으로 검증하지 않는다.

10-20 승인 전 v5 후보의 Windows 시험은 143개 파일·2,006개 통과, Linux도 같은 2,006개와 호환 시험 2개 통과, 실패·취소·건너뜀 0이다. 문의 동의·전송 보완은 Node 54개와 Python 7개를 통과했다. 이 검수 시점에는 실제 Google 동의와 첫 문의 수집, 회사·Talk 운영 반영 및 자동 작업의 첫 실제 완료를 확인하지 않았다. 이후 운영 반영·재무장·연결 결과는 [사업 자동화 기록](README.md)에 있다. 검수 통과와 운영 완료를 같은 의미로 쓰지 않는다.

읽기 범위의 한계: 생성 코어와 서비스 본문 일부는 앞선 검토 범위이며 최종 검토에서 전부 다시 읽지 않았다. 주작업본 밖에 있는 기존 SSH 전송·HA 보조 모듈 2개는 최종 Fable 실행에서 읽지 못했다. 구현 담당자의 별도 원문 검토에서 SSH 소스·승인 증거가 stdin으로 전달되고, import만으로 유지보수 작업이 실행되지 않음을 확인했다. 실제 비밀값·DB·계정 원문은 검토에 포함하지 않았다.

## 배포 준비 추가 검수

추가 검수는 공식 CLI의 기존 구독(`apiKeySource: none`)에서 Read·Grep·Glob만 허용해 완료했다. DM의 단일 저장 지점과 nonce 응답, 기존 SSH stdin 전달, 실제 재무장 영수증의 필드·해시 결합, Forms의 LF 후보·정확한 릴리스/이미지 확인, 기존 회사 배포 절차의 계획/실행 구분, Talk의 고정 HEAD와 두 GET 대조 경로를 읽었다. 새로운 확정 결함은 없었다. 앞선 세 차례 검수를 대체하는 전체 재검수는 아니다.

담당자의 추가 자체 시험은 연결 어댑터 Node 15개·DM Python 11개·Forms Python 7개, Talk 배포 도구 58개가 통과했다. 회사 준비는 기존 Node 94개와 마지막 경로 보정 관련 9개·공개/runtime 핀 보정 관련 17개를 각각 확인했다. Python은 26개 통과, Linux directory fsync 1개는 기존 Windows 조건으로 건너뛰었다. 이 숫자를 더해 새 전체 통합 시험으로 보고하지 않는다. 준비 파일 129개와 연결 어댑터의 소스·시험·결과 해시는 구현 담당자가 다시 대조했다.

추가 검수에서 읽지 않은 범위는 재무장 core·dispatch·collector·Linux QA, DR·delta-transfer·HA/runtime 전체의 정본 대조, release/transport/disarm 본문과 일부 시험, Talk 배포 도구의 내부 미커밋 검사·자격 모듈의 import 부작용이다. 해당 범위의 기존 시험과 파일 대조를 실행한 담당자의 증거와 Fable이 직접 읽은 범위를 구분한다. 컨테이너의 실제 설치 전송·절대경로 import·Store 종료 이후 프로세스 종료는 운영 연결 때 확인해야 한다. Google 동의, 실제 배포·재무장·자격 설치·첫 수집·DM 등록/발송은 추가 검수로 수행되지 않았다.
