# SHIFT 복구 후보 인수 — 2026-10-07

이 결과는 **합성 데이터로 기존 백업 도구와 복구 후보 인수 절차를 검증한 것**이다. 운영 환경과 고객은 아직 미정이며 실제 운영 DB·계정·서버·물리적 PC/휴대폰은 변경하거나 시험하지 않았다.

## 추가한 범위

회사 호스트의 [작은 복구 인수 도구](../../../마케팅/온라인마케팅지도/engagement/company/workspace-restore-acceptance.mjs)는 기존 `backupWorkspace`가 만든 완성 백업을 읽기 전용으로 대조한다. Atlas 공통 엔진, 자동 동기화 저널, 과거 백업 병합, 별도 백업 시스템은 추가하지 않았다. 기존 운영 원본을 덮어쓰거나 서버를 자동 시작하지 않는다.

비교 기준은 **쓰기 중지 직후 최신 상태를 보존한 별도 백업**이고, 복구 후보는 다른 물리적 폴더여야 한다. 다음을 확인한다.

- 두 폴더의 `COMPLETE`와 통합 manifest, 두 SQLite DB의 무결성·외래키 관계.
- 32바이트 암호화 키, 기존 암호문 복호화 가능 여부와 기준/후보 키 일치.
- SHIFT 계정 소유 관계, 수정 revision, 본문 없는 삭제 tombstone, 두 DB의 전체 논리 행.
- 회사/메신저 계정 연결과 등록된 로컬 영상·첨부·Drive 연결 설정의 파일 내용. Drive 원격 파일 본문은 검증 범위가 아니다.
- 실행 전후 원본 파일이 그대로인지. SQLite `mode=ro&immutable=1`로 열어 WAL/SHM을 생성하거나 수정하지 않는다. 기존 백업 도구가 남긴 빈 WAL/SHM 잔여물은 허용하되 내용 있는 WAL은 거절한다.

보고서와 CLI 실패 출력에는 계정 ID, 작성물, 암호문, 키, 자격증명, 이들의 해시, 원래 예외·SQL을 출력하지 않는다. 백업 내용이 기준과 다르면 격리 복사 전 거절하고 자동으로 합치지 않는다.

## 최신성과 접속 허용의 한계

최신성 증거는 필수 입력이지만 **운영자의 외부 증거를 기록하는 선언**이다. 이 도구는 실제 서버 쓰기 중지나 ‘이 백업이 운영의 가장 최신 상태’라는 사실을 독립적으로 증명하지 못한다. 같은 오래된 백업을 서로 다른 두 폴더에 복사해 넣어도 일치할 수 있다. 따라서 성공 명칭은 `candidate-matches-declared-baseline`이며 `latestnessIndependentlyVerified=false`, `productionTrafficAllowed=false`를 항상 유지한다. 최신 기준이 없으면 정상 운영 복구로 인수하지 않는다.

`PREPARATION_INCOMPLETE`는 운영 인수가 끝나지 않았다는 **작업상태 표식**이다. 현행 서버가 이를 읽지 않으므로 자동 부팅/접속 차단 장치가 아니다. 격리 실행과 트래픽 차단은 운영 환경의 네트워크·유지보수 설정으로 보장해야 한다. 이 도구의 일치 결과만으로 표식을 삭제하거나 공개 접속을 열지 않는다.

## 실제 운영에서 적용할 순서 — 아직 미실행

1. 실제 서버·회사 데이터·메신저 데이터 경로와 계정 연결을 확인하고, 쓰기를 중지한다. 원래 최신 두 DB와 키는 보존한다.
2. 중지 직후 기존 `workspace-backup.mjs`로 별도 최신 기준 백업을 생성하고 COMPLETE를 확인한다. 중지 시점, 최신 상태 확인 근거, 백업 manifest 시각을 운영 인수 기록에 남긴다.
3. 다음 증거 파일을 관리자 전용 위치에 준비한다. 예시는 구조 안내이며 실제 시각·근거가 채워지기 전 실행 증거가 아니다.

```json
{
  "kind": "operator-attestation",
  "declaredLatest": true,
  "writersStopped": true,
  "writersStoppedAt": "실제 쓰기 중지 시각(ISO 8601)",
  "baselineCreatedAt": "최신 기준 integration-manifest.json.createdAt 그대로",
  "recordedAt": "실제 인수 기록 시각(ISO 8601)"
}
```

4. 인수 도구로 후보와 최신 기준을 비교한다. 선택한 목적지의 부모 폴더는 있어야 하고 목적지 폴더 자체는 없어야 한다.

```text
node workspace-restore-acceptance.mjs <복구 후보 완성 백업> <중지 직후 최신 기준 완성 백업> <증거 JSON> [새 격리 폴더]
```

거절 시 종료 코드는 2이며 신규 복사·접속 준비를 진행하지 않는다. 성공 시 별도 폴더에 두 DB·키·로컬 파일을 복사하고 메신저 경로와 identityLinks를 새 위치에 연결한다. 기존 경로, 입력 폴더 내부·상위 경로 또는 이미 존재하는 목적지는 거절한다. 부분 복사가 실패하면 해당 폴더는 미완료이므로 사용하지 않는다.

5. 네트워크를 격리한 운영 후보 환경에서 복호화·로그인·계정 소유·최신 revision·삭제 유지·재시작을 별도로 확인한다. 실제 PC/휴대폰 왕복과 도입 고객의 인수 결과까지 기록한 뒤 운영 환경 책임자가 공개 접속 여부를 판단한다. 코드 롤백에는 최신 DB/키를 유지한다. 과거 DB를 복구하는 경우 이후 삭제/수정 내역을 해결할 증거가 없으면 트래픽을 열지 않는다.

## 로컬 합성 결과

**14/14 시험 통과, 검사 실행 중 담당 코드 변경 0개.** [시험 결과](recovery-report.json)와 [전체 시험 로그](recovery-tests.txt)는 `node recovery-verify.mjs`로 다시 생성한다. 실제 기존 `backupWorkspace`로 초기 상태 및 수정·삭제 이후의 두 백업을 만든 뒤 최신 백업의 격리 준비, 과거 백업 거절, 두 DB 혼합 거절, 키·tombstone·연결·첨부 오류, 기존 경로 보존, 최신성 선언의 한계, 비밀 생략, CLI 종료 코드를 확인했다. 이전 [HTTP 백업 복구 검증](../shift-release-preparation-20261007/backup-README.md)은 별도 근거이며 이번 인수 시험에 실제 계정 증거로 섞지 않는다.

같은 후속 작업에서 기존 `Store`에도 **회사 DB가 있는데 키가 없으면 새 키를 생성하거나 DB를 열기 전에 부팅을 거절하는 보완**이 추가됐다. 그 부팅 검사는 담당 서버 시험의 별도 근거이며, 위 14개 인수 시험이나 실제 운영 서버 시험으로 합산하지 않는다. 인수 도구는 애초에 Store 생성자를 쓰지 않는다.

새 검사로 확인한 것은 **복구 후보를 선언한 최신 기준과 안전하게 대조할 수 있는 로컬 절차**다. 운영 복구·배포·실사용자 효과 완료를 뜻하지 않는다.
