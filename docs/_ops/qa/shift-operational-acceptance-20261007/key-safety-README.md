# 회사 DB의 원래 키 누락 시 시작 거부

2026-10-07. [검증 결과](key-safety-report.json)와 [실행 출력](key-safety-tests.txt)에 로컬 수정과 합성 데이터 검증을 기록했다. 실제 운영 DB·키·실행 프로세스는 변경하지 않았다.

기존 `company.sqlite`가 있는데 `encryption.key`가 없으면 회사 Store가 새 키를 만들지 않고 SQLite를 열기 전에 시작을 거부한다. 오류 코드는 `SYNK_ENCRYPTION_KEY_MISSING`이며, 백업의 원래 키를 함께 복구하라는 안내만 제공한다. 데이터 경로·작성문·키·암호문은 오류에 넣지 않는다. 새 디렉터리와 이미 있는 빈 디렉터리의 정상 첫 설정은 유지한다. 기존 DB 파일이 0바이트여도 원래 키 없이 임의 초기화하지 않는다.

새 시험 5개와 관련 초기화·암호화·인증·백업 회귀를 합쳐 **14/14** 통과했다. 원래 DB에서 키를 제거한 뒤 세 번 시작을 시도해도 키가 생성되지 않고 DB·WAL 등의 파일 목록·내용 해시·수정 시각이 그대로임을 확인했다. 원래 키를 다시 넣으면 기존 작성 기록과 암호화된 가상 비밀을 실제로 읽을 수 있었다. 검사 도중 원본 변경은 0개였다.

이 보완은 키가 없는 기존 회사 DB의 잘못된 재초기화만 막는다. 길이는 맞지만 다른 32바이트 키인지 전체 기록을 읽어 판별하는 시작 검사는 포함하지 않는다. 같은 길이의 잘못된 키는 기존 복호화 시 실패하는 동작을 유지하며, 실제 복구에는 키 대조와 본인 기록 확인이 별도로 필요하다.

기존 백업 시험의 `missing` 사례는 이제 HTTP 로그인·500 응답까지 진행하지 않고 `createCompanyApp` 생성 단계에서 위 오류 코드로 거부돼야 한다. 원래 키가 다시 만들어지지 않는지와 DB SHA-256이 변하지 않는지를 확인하는 기대로 바꿔야 한다. `wrong` 사례의 로그인 뒤 개인 기록 읽기 500·비밀 미노출 검증은 그대로 적용된다. 해당 파일은 이 작업에서 직접 수정하지 않았으며 루트 작업이 담당한다.
