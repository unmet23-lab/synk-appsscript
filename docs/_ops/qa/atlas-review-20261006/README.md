# Atlas 2.4 공통 능력 묶음 — 검수 기록 (2026-10-06, Claude)

유호님 요청 「GPT로 아틀라스 엔진 업그레이드했는데 검수·검토해서 판단하고, 보완할 것 보완해서 커밋」에 따른 기록이다. 대상의 계약과 GPT 쪽 검증은 [공통 능력 고도화](../../../아틀라스_공통능력_고도화_20261005.md)에 있고, 여기에는 검수에서 확인한 것·고친 것·남긴 것만 적는다.

## 범위와 방법

- **대상:** GPT가 10-05 21시~10-06 05시에 만든 미커밋 변경 가운데 Atlas 묶음. 엔진 `atlas/`(domain·interpretation·ask·temper-outcomes·temper-interpretation과 engine·trail·personalization 변경), 생성 사본(게임 9개·런처·PATH), 소비처(SHIFT 실습, 컴퓨터 상담과 소개팅 검증판 `experiences/atlas-lab`, 회사 서버의 AI 해석 경로), 평가 도구와 시험.
- **기준 상태:** GPT의 591개 검증 시점(10-06 05:14). 그 검증 기록의 소스 해시 96개 가운데 95개가 일치했고 나머지 하나는 다른 세션이 고친 트랙 문서였다.
- **방법:** 엔진 본체는 직접 읽고 시험이 다루지 않은 입력으로 눌러 봤다(`repro/engine-boundaries.js`). 소비처 세 묶음은 서로 결론을 모르는 읽기 전용 검토자 셋에게 나눠 맡기고, 돌아온 지적은 재현을 직접 다시 돌려 확인한 것만 적었다. 마지막으로 **커밋할 내용만** 빈 폴더에 풀어 시험했다 — 줄바꿈을 그대로 둔 경우와 새 체크아웃처럼 CRLF로 바꾼 경우 둘 다.
- **하지 않은 것:** 동결 평가 30문장과 그 출력은 열지 않았다(검토자 포함). 브라우저 화면 검사, 유료 모델 호출, 운영 배포, talk·홈페이지 저장소의 커밋도 하지 않았다.

## 판단

엔진 본체는 그대로 받아도 된다. 제품이 의미와 필수 조건을 선언하고 Core가 근거의 시점·독립성·모순·정정·철회를 가리는 구조가 일관되고, 경계마다 시험이 있다(이번에 더한 엔진 시험만 112개). 미확인 제안이 추천에 섞이지 않고, 철회·만료·제외 뒤에 옛 값이 되살아나지 않으며, 「완료했지만 반응이 없음」을 약한 찬성으로 세던 가중치를 뺀 것도 옳다. 본체에서 고칠 결함은 찾지 못했다.

문제는 본체가 아니라 **붙인 자리**에 있었다. 커밋에 넣어 고친 것 여섯 가지와, 범위가 커서 다음 작업으로 남긴 것 네 묶음으로 나뉜다. 남긴 것 가운데 사용자가 받는 결과를 실제로 바꾸는 것은 상담 질문 정책과 SHIFT의 복습 추천 둘이다.

### 배포 순서 — 서버가 먼저

게임 9개의 공통 묶음(`experiences/*/atlas-learning.js`)과 런처·PATH 사본이 Core 2.4가 됐다. 새 결정 기록에는 `atlas-2.4.0`이 찍힌다. talk 운영 함수(`synk-account`·`synk-learning`)에 실린 판정기는 2.3이고 모르는 정책판을 「invalid decision record」로 거절한다. **계정 동기화가 켜진 게임이나 앱을 새 묶음으로 공개하기 전에 talk 서버부터 2.4로 올려야 한다.** 2.4 서버는 2.3 기록도 읽는다.

로컬 `SYNK-talk` 작업본은 origin보다 54커밋 뒤처진 상태에서 2.4 사본이 미커밋으로 들어가 있다(GPT의 `tools/sync-atlas.js` 실행 결과). 그 상태로 커밋하지 않았다. talk 최신 master에서 `node tools/sync-atlas.js`를 다시 돌려 커밋·배포한다. 홈페이지 저장소의 사본도 GPT 가지에 미커밋으로 있다.

### 컴퓨터 상담 질문 정책 — 질문은 줄었지만 추천이 달라진다

`node tools/probe-atlas-consultation-fidelity.mjs` (무작위 답 1,500조합, 고정 시드. 기준은 같은 규칙에 물을 수 있는 질문을 전부 답한 추천)

| 멈추는 규칙 | 평균 질문 수 | 전체 답 추천과 다름 | 그중 상담이 선언한 손실로도 손해 |
|---|---:|---:|---:|
| 전부 묻기 | 9.58 | 0 | 0 |
| 지금: 가치가 양수인 질문만 | 6.45 | 172 (11.5%) | 27 |
| 이전: 답이 추천을 바꿀 수 있으면 묻기 | 6.81 | 11 (0.7%) | 5 |

질문 0.36개를 더 줄이는 대신 아홉 명에 한 명꼴로 추천이 달라진다. 다른 칸은 대부분 램(160건)이고 한 단계 낮게 나온다. 건너뛴 질문은 예산·켜 두는 개수·휴대·작업 세부 순이다.

- **원인 1 — 상담의 손실 정의.** `consultation.mjs`의 `evaluate`가 램·저장공간을 「동작 가능」(`ram.workable`·`storage.min`)에 못 미칠 때만 부족으로 센다. 화면에 내는 값은 추천값(`ram.value`)이다. 그래서 답에 따라 추천이 16GB에서 32GB로 바뀌는 질문도 손실 0, 가치 0이 된다(`repro/consultation-skipped-details.mjs`).
- **원인 2 — 한 번에 한 질문만 본다.** Ask는 질문을 하나씩 따로 평가한다. 하나씩은 영향이 없고 함께일 때만 바뀌는 답은 어느 규칙에서도 놓칠 수 있다(이전 방식의 0.7%). 손실로도 손해인 27건이 여기에 원인 1이 겹친 경우다.
- **GPT의 05시 보완(완료 기준 `computer-completion-1`)이 덮은 부분:** 사진·개발·영상 세부와 휴대·예산은 이제 「임시 사양 안내」로 표시되고 직접 채울 수 있다. 다만 자동 질문은 그대로라, 합성 11사례 가운데 질문이 끝난 7건 중 필수 확인까지 끝난 것은 1건이다. 「켜 두는 개수」는 필수가 아닌 가정(보통)으로만 표시되고 **답할 화면이 없다** — 많이 켜 두는 사용자는 「필수 확인 완료」 화면에서 램 16GB를 받는데, 공개 도구에 같은 답을 넣으면 32GB다.
- **다음 작업(둘 중 하나, 또는 둘 다):** ① 새로 사는 경우의 부족을 추천값 기준으로 센다(기존 기기 유지 판단에만 「동작 가능」을 쓴다). ② Ask가 멈추면 필수·가정 항목을 같은 질문 카드로 이어 묻고, 그 항목은 「건너뛴 질문」 목록에서 뺀다. 고친 뒤 위 측정에서 다름이 1% 안팎으로 내려오는지 본다. `tests/atlas-lab-consultation.test.js`의 「건너뛸 수 있다」 기대와 문서의 질문 수(34→21, 53→32)는 함께 바뀐다.

같은 화면의 작은 것: 학습 허브처럼 AI 경로가 없는 서버에서 실험실을 열면 404가 한 번 나고 「서버에 최대 24시간 보관」 안내와 바닥글이 그대로 보인다(실제로는 아무것도 보내지 않는다).

<a id="before-paid-eval"></a>
### 유료 모델 평가 전에 고칠 것

평가는 유호님 「이건 다음에 정하자」로 보류 중이다. 시작하기 전에:

1. **캡처 도구가 한 사례의 실패에서 영원히 멈춘다.** 서버는 실패로 닫힌 요청(`invalid`·`uncertain`)의 재전송에 항상 409를 준다. 도구는 그 사례를 건너뛰지 못해 실행할 때마다 같은 요청을 다시 보내고 멈추며, 폴더 한도 30회가 그렇게 소진된다. 새 폴더는 요청 번호가 새로 생겨 이미 받은 사례까지 다시 과금된다. 모델의 형식 실패가 「실패한 결과」가 아니라 「결과 없음」으로 남는 문제이기도 하다(`repro/capture-stuck-after-failure.mjs`: 2/30에서 고정).
2. **실패 사유가 남지 않는다.** 거절·잘린 응답·인용 불일치·모델 이름 불일치가 장부에서 모두 `invalid` 하나고, 제공자의 401(키·권한 문제)도 `uncertain`으로 예약을 영구히 붙잡는다. 짧은 문장 기준 약 66번이면 누적 한도($0.25)가 차는데 푸는 절차가 없다.
3. **응답의 모델 이름을 글자 그대로 비교한다**(`model-extraction.mjs`, 동결 파일). 공식 모델 문서에는 스냅숏이 `gpt-6-luna` 하나뿐이라 지금은 맞을 가능성이 높지만, 날짜가 붙은 스냅숏이 생기면 과금된 응답이 전부 거절된다. 첫 호출 한 건으로 확인한다.
4. **로컬 한국어 규칙의 오단정**(`interpretation.mjs`, 동결 파일). 「제 램은 16GB가 아닙니다」→ 램 16, 「8GB에서 16GB로 바꿨어요」→ 램 8, 「Tom은 프리미어로…」「민수 컴퓨터가 있어요」→ 본인 사실로 제안한다. 확인 전에는 추천에 들어가지 않지만 「현재 내 조건」으로 보이고 한 번 누르면 반영된다(`repro/local-rules-wrong-assertions.mjs`). 금칙어를 늘리기보다 맞는 서술어까지 일치시키는 쪽이 낫다.
5. **원문을 고쳐 꺼진 용도의 직접 답이 되살아난다**(같은 동결 파일). 칩으로 끄면 지워지는 세부 답이, 원문 편집으로 상위 답이 사라진 경우에는 숨었다가 다시 켤 때 적용된다. 문서의 약속과 다르다.

3~5는 동결 6개 파일이라 고치면 `freeze.json`을 다시 만들어야 한다. 모델 결과를 보기 전에 한 번에 하는 것이 맞다.

<a id="shift"></a>
### SHIFT 실습

1. **세대가 바뀌면 완료·복원·평가가 예외로 끝난다**(`repro/shift-generation-change.mjs`). 동의 철회 뒤 재동의, 설정 하나 잊기가 해당한다. 지금 두 화면에는 그 조작이 없어 사용자가 닿을 길은 없다. 고도화 문서의 「세대 변경이 평가에 적용된다」는 추천·설명까지만 참이라 그렇게 고쳐 적었다. 철회 화면을 붙이기 전에 고친다.
2. **방금 놓친 유형이 다음 실습에서 빠질 수 있다**(`repro/shift-recent-miss.mjs`). 최근 20회·30일의 다수결이라, 세 번 맞힌 뒤 한 번 놓치면 「맞힘 0.75」로 읽혀 순서·제안·설명 어디에도 나오지 않는다. 커밋돼 있던 판은 직전에 놓친 유형을 앞에 냈다. 두 번 놓치고 한 번 맞혀도 2/3 = 0.667이 기준 0.67에 못 미쳐 「엇갈림」이 된다. 같은 문항을 다시 푼 것이 매번 독립 근거로 세어지는 것과 한 뿌리다 — 관측의 독립 단위를 「실습 한 번」이 아니라 「문항」으로 두면 같은 문항의 최신 결과만 남아 둘 다 풀린다.
3. **다음 실습 제안이 동점이면 이름순**이라 정답을 이미 본 실습으로 되돌아간다. 제품이 넘긴 순서(돌아가는 차례)가 아니라 Domain의 id 순이 쓰인다.
4. **계약판·정책판·문항을 바꾸면 저장분 복원이 통째로 실패한다.** 분석 기록만 버리고 요약·초안은 살리는 이행 단계가 필요하다.
5. Temper 집계에서 완료 체인은 20개, 중도 포기 체인은 199개까지 남아 미응답 비율이 부풀려진다(지금은 화면에서 쓰지 않는다).

### 엔진 경계 — 결함은 아니고, 붙이는 쪽이 알아야 하는 것

`node docs/_ops/qa/atlas-review-20261006/repro/engine-boundaries.js`

- **Domain에는 「최근 것이 우선」이 없다.** 유효 기간 안의 독립 관측을 모두 같은 무게로 센다. 시간이 지나며 바뀌는 속성(SHIFT의 「방금 놓친 유형」)에는 맞지 않는다. 제품이 독립 키로 풀거나, 다음에 엔진을 열 때 필드 정책으로 넣을 후보다.
- **만료된 선언은 그 뒤에 쌓인 관측까지 막고 `needsCheck`에도 나오지 않는다.** 상태가 `expired`인 필드는 제품이 보고 다시 물어야 한다(소개팅 검증판은 그렇게 한다).
- **기본 합의 기준 0.67은 2:1을 「엇갈림」으로 본다.** 3분의 2를 통과시키려면 제품이 0.66 이하를 선언한다.
- **`Domain.decide`는 쓸 사실이 하나도 없어도 `ready`를 준다.** 점수 0·이유 없음으로 id 순 첫 후보가 뽑힌다. 제품은 `reasons`가 비었는지 봐야 한다. 동점을 id 순이 아니라 넘겨받은 순서로 가르는 쪽이 Ask와도 맞는다(동결 파일이라 다음 재봉인 때).
- **Ask의 가치 모드는 손실 정의만큼만 옳다.** 위 상담 사례가 그 예다. 손실이 추천값이 아니라 최소 조건을 기준으로 하면 「질문을 줄였다」가 「덜 맞춘다」가 된다.
- **Temper outcomes는 평가 시각 뒤에 접수된 기록이 섞이면 걸러 내지 않고 예외를 던진다.** 제품이 미리 거른다.
- **`Personalization.domain`은 모듈이 없으면 던지는 getter다.** 내보낸 객체를 통째로 펼치거나 열거하지 않는다.

## 재현 스크립트

`repro/`의 스크립트는 저장소와 네트워크를 건드리지 않고 그 자리에서 돈다. 상담·SHIFT·회사 서버 것은 검토자가 쓴 것을 상대 경로로만 고쳐 옮겼고, 여기 적은 출력은 직접 다시 돌려 확인했다.

| 파일 | 보여 주는 것 |
|---|---|
| `engine-boundaries.js` | 위 엔진 경계 |
| `consultation-skipped-details.mjs` | 건너뛴 세부 답이 추천을 바꾸는 사례 |
| `local-rules-wrong-assertions.mjs` | 로컬 규칙이 잘못 단정하는 문장(직접 지은 문장만) |
| `capture-stuck-after-failure.mjs` | 캡처 도구가 실패 한 건 뒤 끝내지 못함(`quote` 또는 `http`) |
| `shift-generation-change.mjs`, `shift-recent-miss.mjs` | SHIFT 1·2번(`shift-lib.mjs`를 같이 쓴다) |

검토자 보고에만 있고 직접 다시 돌리지 않은 지적(사용량 합계 불일치 처리, 캡처 잠금 파일, 검토 200건 상한 등 작은 것)은 여기 옮기지 않았다.
