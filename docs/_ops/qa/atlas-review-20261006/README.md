# Atlas 2.4 공통 능력 묶음 — 검수 기록 (2026-10-06, Claude)

유호님 요청 「GPT로 아틀라스 엔진 업그레이드했는데 검수·검토해서 판단하고, 보완할 것 보완해서 커밋」에 따른 기록이다. 대상의 계약과 GPT 쪽 검증은 [공통 능력 고도화](../../../아틀라스_공통능력_고도화_20261005.md)에 있고, 여기에는 검수에서 확인한 것·고친 것·남긴 것만 적는다.

**2026-10-08 후속:** 아래 상담의 필수 확인·로컬 해석·원문 편집, 평가 캡처의 확정 실패 처리·실패 사유·신규 인증 거절 예약 문제는 [8종 보완 기록](../atlas-eight-fix-20261008/README.md)에서 수정·검증했다. 동결 문장은 그대로 두고 변경 원본의 해시를 다시 봉인했다. 불확실 전송 예약은 유지하며 실제 유료 모델 평가와 첫 응답의 모델명 확인은 아직 실행하지 않았다. 아래 수치·재현은 당시 기록으로 보존한다.

## 범위와 방법

- **대상:** GPT가 10-05 21시~10-06 05시에 만든 미커밋 변경 가운데 Atlas 묶음. 엔진 `atlas/`(domain·interpretation·ask·temper-outcomes·temper-interpretation과 engine·trail·personalization 변경), 생성 사본(게임 9개·런처·PATH), 소비처(SHIFT 실습, 컴퓨터 상담과 소개팅 검증판 `experiences/atlas-lab`, 회사 서버의 AI 해석 경로), 평가 도구와 시험.
- **기준 상태:** GPT의 591개 검증 시점(10-06 05:14). 그 검증 기록의 소스 해시 96개 가운데 95개가 일치했고 나머지 하나는 다른 세션이 고친 트랙 문서였다.
- **방법:** 엔진 본체는 직접 읽고 시험이 다루지 않은 입력으로 눌러 봤다(`repro/engine-boundaries.js`). 소비처 세 묶음은 서로 결론을 모르는 읽기 전용 검토자 셋에게 나눠 맡기고, 돌아온 지적은 재현을 직접 다시 돌려 확인한 것만 적었다. 마지막으로 **커밋할 내용만** 빈 폴더에 풀어 시험했다 — 줄바꿈을 그대로 둔 경우와 새 체크아웃처럼 CRLF로 바꾼 경우 둘 다.
- **하지 않은 것:** 동결 평가 30문장과 그 출력은 열지 않았다(검토자 포함). 브라우저 화면 검사, 유료 모델 호출, 운영 배포, talk·홈페이지 저장소의 커밋도 하지 않았다.

## 판단

엔진 본체는 그대로 받아도 된다. 제품이 의미와 필수 조건을 선언하고 Core가 근거의 시점·독립성·모순·정정·철회를 가리는 구조가 일관되고, 경계마다 시험이 있다(이번에 더한 엔진 시험만 112개). 미확인 제안이 추천에 섞이지 않고, 철회·만료·제외 뒤에 옛 값이 되살아나지 않으며, 「완료했지만 반응이 없음」을 약한 찬성으로 세던 가중치를 뺀 것도 옳다. 본체에서 고칠 결함은 찾지 못했다.

문제는 본체가 아니라 **붙인 자리**에 있었다. 커밋에 넣어 고친 것 일곱 가지와, 범위가 커서 다음 작업으로 남긴 것 네 묶음으로 나뉜다. 사용자가 받는 결과를 실제로 바꾸는 것은 상담 질문 정책(추천이 달라지던 부분은 고침)과 SHIFT의 복습 추천(남김) 둘이다.

- **고친 것(세 번째 커밋).** 상담의 손실(`consultation.mjs`의 `evaluate`)이 램·저장공간·그래픽 메모리를 「동작 가능」에 못 미칠 때만 부족으로 셌다. 화면에 내는 값은 추천값이라, 답에 따라 추천이 16GB에서 32GB로 바뀌는 질문도 손실 0·가치 0으로 건너뛰었고, 아홉 명에 한 명꼴로 추천이 달라졌다(대부분 램이 한 단계 낮게). 새로 사는 경우에는 추천값에 못 미치는 것도 부족으로 세게 했다. 기존 기기를 계속 쓰는 판단은 그대로 「동작 가능」 기준이다. 정책판은 `computer-question-value-3`.
- **확인.** 합성 11사례의 질문 수와 결과(53→32, 완료 6/1)는 그대로다. 브라우저 스모크 다섯 개(질문 가치·완료 기준·원문 해석·AI 화면·소개팅)를 고친 판으로 다시 돌려 모두 통과했다. `tests/atlas-consultation-fidelity.test.mjs`가 같은 측정을 150조합으로 돌려 5%를 넘으면 실패한다(고치기 전 판에서는 16건으로 실패).
- **남은 2.1%(32건).** 하나씩은 영향이 없고 함께일 때만 바뀌는 답 14건, 기존 기기를 계속 쓰는 결론이 낀 경우 9건, 영상 프로그램처럼 추천 운영체제·그래픽 종류를 바꾸는데 손실 정의가 세지 않는 질문 9건이다. Ask는 한 번에 한 질문만 보기 때문에 첫째는 어느 규칙에서도 남는다. 셋째는 완료 기준의 필수 항목이라 아래 「남은 일」을 하면 함께 풀린다.
- **남은 일 — 자동 질문과 완료 기준을 잇기.** GPT의 05시 보완(`computer-completion-1`)으로 화면은 「임시 사양 안내 / 필수 확인 완료」를 구분하지만, 자동 질문이 끝났을 때 필수 확인까지 끝난 경우는 1,500조합 가운데 79건(5%)뿐이다. 나머지는 예산·휴대처럼 추천을 바꾸지 않아 건너뛴 필수 항목을 사용자가 접힌 「남은 필수 항목 확인하기」에서 직접 채워야 한다. Ask가 멈추면 아직 답하지 않은 필수 항목을 같은 질문 카드로 이어 묻고, 그 항목은 「건너뛴 질문」 목록에서 빼는 것이 맞다. 이때 완료 기준 스모크(8경로)의 기대도 함께 바뀐다.

같은 화면의 작은 것: 「켜 두는 개수」는 이제 추천을 바꿀 때 묻지만, 묻지 않은 경우의 가정(보통)을 직접 바꿀 단추는 없다. 학습 허브처럼 AI 경로가 없는 서버에서 실험실을 열면 404가 한 번 나고 「서버에 최대 24시간 보관」 안내와 바닥글이 그대로 보인다(실제로는 아무것도 보내지 않는다).

<a id="before-paid-eval"></a>
### 유료 모델 평가 전에 고칠 것

평가는 유호님 「이건 다음에 정하자」로 보류 중이다. 시작하기 전에:

1. **캡처 도구가 한 사례의 실패에서 영원히 멈춘다.** 서버는 실패로 닫힌 요청(`invalid`·`uncertain`)의 재전송에 항상 409를 준다. 도구는 그 사례를 건너뛰지 못해 실행할 때마다 같은 요청을 다시 보내고 멈추며, 폴더 한도 30회가 그렇게 소진된다. 새 폴더는 요청 번호가 새로 생겨 이미 받은 사례까지 다시 과금된다. 모델의 형식 실패가 「실패한 결과」가 아니라 「결과 없음」으로 남는 문제이기도 하다(`repro/capture-stuck-after-failure.mjs`: 2/30에서 고정).
2. **실패 사유가 남지 않는다.** 거절·잘린 응답·인용 불일치·모델 이름 불일치가 장부에서 모두 `invalid` 하나고, 제공자의 401(키·권한 문제)도 `uncertain`으로 예약을 영구히 붙잡는다. 짧은 문장 기준 약 66번이면 누적 한도($0.25)가 차는데 푸는 절차가 없다.
3. **응답의 모델 이름을 글자 그대로 비교한다**(`model-extraction.mjs`, 동결 파일). 공식 모델 문서에는 스냅숏이 `gpt-6-luna` 하나뿐이라 지금은 맞을 가능성이 높지만, 날짜가 붙은 스냅숏이 생기면 과금된 응답이 전부 거절된다. 첫 호출 한 건으로 확인한다.
4. **로컬 한국어 규칙의 오단정**(`interpretation.mjs`, 동결 파일). 「제 램은 16GB가 아닙니다」→ 램 16, 「8GB에서 16GB로 바꿨어요」→ 램 8, 「Tom은 프리미어로…」「민수 컴퓨터가 있어요」→ 본인 사실로 제안한다. 확인 전에는 추천에 들어가지 않지만 「현재 내 조건」으로 보이고 한 번 누르면 반영된다(`repro/local-rules-wrong-assertions.mjs`). 금칙어를 늘리기보다 맞는 서술어까지 일치시키는 쪽이 낫다.
5. **원문을 고쳐 꺼진 용도의 직접 답이 되살아난다**(같은 동결 파일). 칩으로 끄면 지워지는 세부 답이, 원문 편집으로 상위 답이 사라진 경우에는 숨었다가 다시 켤 때 적용된다. 문서의 약속과 다르다.

3~5는 동결 6개 파일이라 고치면 `freeze.json`을 다시 만들어야 한다. 모델 결과를 보기 전에 한 번에 하는 것이 맞다.

<a id="shift"></a>
### SHIFT 실습

1. **세대 변경 뒤 완료·복원·평가 예외 — 2026-10-07 로컬 수정.** 당시 `repro/shift-generation-change.mjs`로 동의 철회·재동의와 설정 삭제 문제를 확인했다. 후속에서 SHIFT 제품 모델이 이전 분석을 제외하고 원고·초안을 별도 작성물로 보존하도록 고쳤으며, 같은 재현의 예외 8건이 0건이 됐다. [후속 검사](../shift-record-migration-20261006/report.json). 두 화면에 새 동의 조작을 추가하거나 공개 배포한 것은 아니다.
2. **방금 놓친 유형이 다음 실습에서 빠짐 — 2026-10-07 로컬 수정.** 당시 `repro/shift-recent-miss.mjs`에서 최근 20회·30일의 다수결이 직전 오답을 가리고 같은 문항의 반복이 매번 독립 근거가 되는 것을 확인했다. 후속 제품 모델은 업무·문항·판본을 독립 단위로 두고 마지막 결과만 투영한다. 제품의 `shift-review-order@2`가 30일 이내 미해결 문항을 복습 순서에 반영한다. 서로 다른 문항의 결과가 엇갈린다는 Domain의 전체 해석은 유지하며, 특정 문항의 복습 근거와 구분한다. 최신 정정 제외 뒤 구오답 부활, 만료된 저장 설명, 실제 첫 문항과 평가 선택의 불일치도 함께 보완했다. [후속 검사](../shift-recommendation-20261007/report.json), [제품 계약](../../../../experiences/shift-workbench/README.md#review-order).
3. **다음 실습 동점의 이름순 회귀 — 2026-10-07 로컬 수정.** 당시에는 Domain의 id 순 때문에 정답을 이미 본 실습으로 되돌아갔다. 제품이 같은 복습 우선순위의 후보를 현재 기록의 미경험 → 실제 노출·완료가 가장 오래전 → 등록 순서로 정하고 선택 이유를 두 화면에 표시한다. 선택만 하고 실제 표시하지 않은 실습은 경험으로 세지 않는다. 공통 Domain의 정렬 규칙은 바꾸지 않았다. [화면 검사](../shift-recommendation-20261007/browser/report.json).
4. **제품 판본 변경 뒤 작성물 복구 — 2026-10-07 로컬 수정.** 명시된 문항/규칙 manifest가 달라지면 소유자·Core 원로그·완료·평가 연결을 확인하고 요청문·초안만 분석 제외 보관본으로 이행한다. 문항 변경·삭제, 규칙 판본 변경, 메타 없는 구형 v1, 완료 20개+진행 초안, 저장 재복원을 검증했다. 지원하지 않는 바깥 저장 형식·Core 판본·손상 원로그는 복구 대상이 아니다. [제품 경계](../../../../experiences/shift-workbench/README.md#storage-upgrade), [후속 검증](../shift-storage-retention-20261007/report.json).
5. **완료/중도 포기 평가 보관 차이 — 2026-10-07 로컬 수정.** 당시 완료 20개/중도 포기 최대 200개의 서로 다른 범위가 섞였다. 이제 결과와 무관하게 원결정 순 최근 20시도와 전체 후손을 함께 보관하고 정책판 필터는 이후 적용한다. 구판에서 체인이 이미 빠졌으면 작성물을 유지하며 집계를 새 실습부터 시작한다. 실제 노출의 업무별 마지막 기록은 평가와 별도로 유지해 오래전 경험이 사라지지 않는다. 성과 비교는 여전히 사용자 화면에 표시하지 않는다. [보관 계약](../../../../experiences/shift-workbench/README.md#evaluation-retention).

<a id="engine-notes"></a>
### 엔진 경계 — 결함은 아니고, 붙이는 쪽이 알아야 하는 것

`node docs/_ops/qa/atlas-review-20261006/repro/engine-boundaries.js`

- **Domain에는 「최근 것이 우선」이 없다.** 유효 기간 안의 독립 관측을 모두 같은 무게로 센다. 시간이 지나며 바뀌는 속성(SHIFT의 「방금 놓친 유형」)에는 맞지 않는다. 제품이 독립 키로 풀거나, 다음에 엔진을 열 때 필드 정책으로 넣을 후보다.
- **만료된 선언은 그 뒤에 쌓인 관측까지 막고 `needsCheck`에도 나오지 않는다.** 상태가 `expired`인 필드는 제품이 보고 다시 물어야 한다(소개팅 검증판은 그렇게 한다).
- **기본 합의 기준 0.67은 2:1을 「엇갈림」으로 본다.** 3분의 2를 통과시키려면 제품이 0.66 이하를 선언한다.
- **`Domain.decide`는 쓸 사실이 하나도 없어도 `ready`를 준다.** 점수 0·이유 없음으로 id 순 첫 후보가 뽑힌다. 제품은 `reasons`가 비었는지 봐야 한다. 동점을 id 순이 아니라 넘겨받은 순서로 가르는 쪽이 Ask와도 맞는다(동결 파일이라 다음 재봉인 때).
- **Ask의 가치 모드는 손실 정의만큼만 옳다.** 위 상담 사례가 그 예다. 손실이 추천값이 아니라 최소 조건을 기준으로 하면 「질문을 줄였다」가 「덜 맞춘다」가 된다.
- **Temper outcomes는 평가 시각 뒤에 접수된 기록이 섞이면 걸러 내지 않고 예외를 던진다.** 제품이 미리 거른다.
- **`Personalization.domain`은 모듈이 없으면 던지는 getter다.** 내보낸 객체를 통째로 펼치거나 열거하지 않는다.

## 재현 스크립트

`repro/`의 스크립트는 저장소와 네트워크를 건드리지 않고 그 자리에서 돈다. 상담·SHIFT·회사 서버 것은 검토자가 쓴 것을 상대 경로로만 고쳐 옮겼고, 여기 적은 출력은 직접 다시 돌려 확인했다.

| 파일 | 보여 주는 것 |
|---|---|
| `engine-boundaries.js` | 위 엔진 경계 |
| `consultation-skipped-details.mjs` | 건너뛴 세부 답이 추천을 바꾸던 사례(고친 뒤에는 그 질문들의 가치가 양수로 나온다) |
| `local-rules-wrong-assertions.mjs` | 로컬 규칙이 잘못 단정하는 문장(직접 지은 문장만) |
| `capture-stuck-after-failure.mjs` | 캡처 도구가 실패 한 건 뒤 끝내지 못함(`quote` 또는 `http`) |
| `shift-generation-change.mjs`, `shift-recent-miss.mjs` | SHIFT 1·2번(`shift-lib.mjs`를 같이 쓴다) |

검토자 보고에만 있고 직접 다시 돌리지 않은 지적(사용량 합계 불일치 처리, 캡처 잠금 파일, 검토 200건 상한 등 작은 것)은 여기 옮기지 않았다.
