## §3. 처분 — 36갈래

### A군. 실행 장부의 물리 계약 (V6-1 ~ V6-9)

**V6-1 회수 RPC 가 없다 — 자기 선언과 정면 충돌** · 원건 L1-1·L2-3·S3-4 · **채택(P0)**
§3-5-b 는 「전이는 이 다섯 밖에서 일어나지 않는다」고 선언하고, 같은 절 전이표에 `claimed → 대기`
(회수)를 넣었다. 다섯에 회수가 없으니 **그 전이는 일어날 수 없다.** `jobs_claim` 은 `대기` 만 집으므로
죽은 워커의 일감은 06:00 마감까지 고착된다 — §3-2-a 가 「워커가 죽어도 다음 10분이 이어받는다」고 적은
**재진입의 핵심 경로가 문서상 부재**다. `_lease_sec` 초기값도 어느 절에도 없다(S3-4 후반).
**처방** = ㉥ `jobs_reclaim(_assign_date date, _now timestamptz default now()) returns int` 를 여섯째로
신설(`status='claimed' and lease_until < _now` → `대기` · `owner`·`lease_until` 비움 · **fence 안 올린다**)
· 호출자 = `generate-worker` 잡이 `jobs_claim` **직전에** 1회 · `_lease_sec` **초기값 = 1800**(워커
예산 100초의 넉넉한 배수 · §5-1 판지문 재료 5에 편입).

**V6-2 ⑥' 비대상 착지가 «현재 규격으로 실행 불가»** · 원건 L1-2·L2-2 · **채택(P0)**
두 벌이 독립으로 같은 자리를 두 각도에서 쳤고 **둘 다 맞다**: ①`jobs_finalize(_mode='정상')` 의 가드는
`status='claimed'` 인데 비대상 행은 `대기` 라 **가드에 걸린다**(L2-2) ②`jobs_load._targets` 에는
`task_snapshot`·문장·질문·`event_id`·`intervention_id` 가 없어 **`_event` 를 조립할 재료가 없다**(L1-2).
**처방** = ①`_mode='적재'` 를 셋째 모드로 신설 — 가드 = `status='대기' and not_target_reason is not null`
· fence 안 올린다 ②`jobs_load` 가 **자기 트랜잭션 안에서 `오늘과제()` 를 이미 부른다**는 사실을 명시
(선판정이 그 함수를 부르므로 `task_snapshot` 은 손에 있다) — `_targets` 원소에 `event_draft` 를 더한다.

**V6-3 배치 실행판이 job 에 안 박힌다** · 원건 L1-4·L2-11·S3-7 · **채택(P0)**
§5-1 은 「배치 시작 1회 산출 · 그날 모든 job 이 같은 값」이라 적었는데 그 값이 사는 칸이 `attempts`
뿐이다. 00:10~05:50 사이 배포가 일어나면 **같은 배정일에 두 판이 섞이고**, `branch_snapshot` 은 옛 판으로
만들어졌는데 생성은 새 판으로 돈다. **처방** = `generation_jobs` 에 `model`·`prompt_ver`·`policy_ver`·
`estimator_version` **4칸 추가**(`jobs_load` 가 박는다 · not null) · `attempts` 의 같은 이름 칸은 **그대로
둔다**(대조가 곧 「배포가 갈렸다」의 탐지기다) · `attempt_open` 이 job 값과 다르면 **거절**.

**V6-4 `snapshot_as_of` 가 상태 계산에 전달되는 규칙이 없다** · 원건 L1-3·L2-7 · **채택**
§11-4 C4 가 `옵션.ingested_as_of` 배선을 이미 선행 작업으로 넣었으므로 **절반은 닫혀 있다.** 남은
절반이 진짜 구멍이다 — **워커 호출 계약에 「그 값이 job 에서 온다」가 없다.** 지연된 워커가 `now()` 로
읽으면 큐에 박은 시점이 장식이 된다. **처방** = §3-5-b 워커 계약에 1줄 — `as_of := job.snapshot_as_of` ·
`ingested_as_of := job.snapshot_as_of`(**둘 다 같은 값** · 워커는 시각을 «만들지 않는다») ·
`branch_snapshot` 에 `ver` 필수키 + `jobs_load` 가 그 키 없으면 예외.

**V6-5 `outcome` 값목록이 물리적으로 안 닫혔다** · 원건 L1-7·L2-5·S3-3 · **채택(P0)**
3/3 합의. DDL 의 `outcome text` 에 CHECK 가 없다. 그런데 §12-21 은 「**DDL CHECK 리터럴 집합** ==
§4-1 값 집합」을 기계 대조하라 한다 — **대조할 집합이 없으므로 그 회귀는 원리상 아무것도 안 막는다**
(「검사 통과」와 「검사 불능」이 같은 모양 · 이 문서가 스스로 금지한 형태다).
**처방** = `check (outcome is null or outcome in (…14값…))` 추가(`이미배정` 은 응답 전용이라 **뺀다**).

**V6-6 `gate_failed_reasons` 가 절반만 막힌다** · 원건 S3-13 · **채택**
`attempts_result_gate` 는 `검문탈락` 일 때 non-null 만 본다 ⇒ **빈 배열·목록 밖 사유·성공 행에 붙은
사유**가 전부 통과한다. §4-1 의 「검문탈락일 때만 7값」과 어긋난다.
**처방** = CHECK 를 쌍조건으로 — `(result='검문탈락') = (gate_failed_reasons is not null and
array_length(…,1) >= 1)` + 원소 허용목록 `gate_failed_reasons <@ array[…7값…]`.

**V6-7 승리 시도가 남의 일감에 붙는다** · 원건 L1-6·S3-5 · **채택(P0)**
FK 가 `attempt_id` 만 본다 ⇒ **학생 A 의 job 이 학생 B 의 attempt 를 승리 시도로 가리켜도 DB 가 승인**
한다. append-only 계보라 저장된 뒤 복구 불가. **처방** = `attempts` 에 `unique (attempt_id, job_id)` 를
얹고 jobs 의 FK 를 **복합**으로 — `foreign key (winning_attempt_id, job_id) references
engine.generation_attempts(attempt_id, job_id)` · `착지` 상태면 `winning_attempt_id is not null` 을
`jobs_terminal_cols` 에 더한다(`마감폴백`·`대상아님` 은 null 허용 — 시도가 원래 없다).

**V6-8 append-only 가 «문장»이라 아무것도 안 막는다** · 원건 L1-8 · **채택**
「행 삭제·값 덮어쓰기 금지」는 규격이지 계약이 아니다. `attempt_close` 의 1회 채움만 있고 **DELETE·자유
UPDATE 를 막는 물리 장치가 0**이다. **처방** = `revoke update, delete on engine.generation_attempts from
authenticated, anon, service_role` + 다섯(→일곱) RPC 를 `security definer` 로 두고 **그 함수만 쓴다**
(기존 events fn 선례) · §12-21 에 「service_role 로 직접 UPDATE 를 시도하면 거절」 픽스처 1벌.

**V6-9 시도 성공과 학생이 받은 것의 계보가 갈린다** · 원건 L2-4 · **부분 채택**
「마감 폴백 뒤 낡은 워커가 성공으로 닫을 수 있다」는 **맞다.** 다만 그건 **오염이 아니라 사실**이다 —
시도는 실제로 성공했고 착지를 못 했을 뿐이고, 시도 장부는 그 사실을 적는 표다(가리면 「응답 직후 죽으면
시도가 사라진다」는 ㉱ 로 되돌아간다). 갈라지는 것은 **「학생이 받은 것」의 판정 하나**이고 그건 V6-7 의
복합 FK + `jobs.status` 가 이미 진다. **채택분** = §3-6 표에 1줄 — 「`attempts.result='성공'` 은 «학생에게
갔다»가 아니다. 그 판정은 `jobs.winning_attempt_id` 하나가 진다」 + §12-18 픽스처 1벌(마감폴백 뒤 성공
close → job 은 `마감폴백` 이고 `winning_attempt_id` 는 **그 시도가 아니다**). **기각분** = `attempt_close`
에 job 상태·펜스 가드 추가(닫으면 증거가 사라진다).

### B군. 착지 사건의 모양 (V6-10 ~ V6-13)

**V6-10 배달 순간에 «가짜 제출 사건»을 만든다** · 원건 L2-1 · **채택(P0 · 실1)**
`_event.submission` 에 `"event_type": "submission.created"` 가 박혀 있다. **실측 — `engine.submissions`
에는 `event_type` 열이 없다.** 그 표는 배정 사건(`event_id`)에 딸린 **보조 행**이다. 이 JSON 대로 구현하면
①그 칸을 무시하거나 ②`learning_events` 에 `submission.created` 를 **학생이 제출하기도 전에** 만든다.
②가 나면 리듬 축(제출률·마감여유)이 **전량 오염**되고 append-only 라 복구 불가다.
**처방** = 블록 이름을 `submission_row` 로 바꾸고 `event_type` 을 **뺀다** · 칸을 실물 열로 고정
(`event_id`·`task_type`·`task_ref`·`task_snapshot`·`task_schema_ver`) · §13 에 🚫 1줄 신설.

**V6-11 원자 착지 입력이 자기 조인을 표현 못 한다** · 원건 L2-13·S3-6 · **채택(P0)**
(S3-6 의 나머지 절반은 V6-10 과 같은 처방이다.) §3-0 이 「`task.assigned` 와 `intervention.delivered` 가
**같은 `intervention_id`**」를 v4.2 판정의 뼈대로 삼았는데, `_event.task_assigned` 에 그 칸이 **없다.**
라이브가 이미 그렇게 넣는데(`deliver:601`) 계약 JSON 이 안 적었다 ⇒ 구현마다 조인 그래프가 갈린다.
**처방** = `task_assigned` 에 `"intervention_id": "<intervention_delivered 와 같은 값>"` 추가 + 「이 값은
`jobs_finalize` 가 **한 번 생성해 두 블록에 같이 넣는다**(호출자가 두 번 적지 않는다)」 1줄.

**V6-12 정본 이벤트에서 급수·목표 스냅샷이 빠진다** · 원건 L1-5 · **부분 채택(실4)**
**채택** — `level_snapshot`·`goal_snapshot` 은 `learning_events` 의 **물리 열로 실재**한다(신설 0 · 면적
+0). 이 트랙이 §6 에서 `estimator_version`·`evidence_refs` 를 「정본 열에 싣는다」고 한 것과 **같은
논리**인데 이 둘만 빠졌다. `branch_snapshot` 은 운영 큐의 JSON 이라 사건표 소비자가 안 읽는다 —
지적이 옳다. **기각** — `valid_from`·`expires_at`·`user_confirmed` 는 `learning_events` 에 **없는 열**이다
(실4). 없는 칸을 요구하는 것은 계약 면적을 여는 일이고 §11-1 의 「열지 않는 것」에 걸린다.

**V6-13 `degraded` 의 뜻이 문서 안에서 갈린다** · 원건 L2-6 · **채택(P0)**
§1 표는 ①첫날·②교정문을 `degraded=false` 로 두고(라이브 실물), §5-4 는 「`true` = 그날의 **최상
갈래(③생성)가 아닌 것**이 나갔다」로 정의한다 — **첫날·교정문은 ③이 아닌데 false 다.** 정면 충돌이고,
새 `_event` 스키마에는 `degraded` 자체가 없어 **DB 기본값 false 에 조용히 기댄다.**
