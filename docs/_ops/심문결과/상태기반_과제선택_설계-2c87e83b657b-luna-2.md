지적 19건.

1. [P0] `correlation_id` 세 행 원자성은 물리적으로 불가능하다 — §3-0은 `task.assigned`·`intervention.delivered`·`engine.submissions`가 같은 `correlation_id`를 갖는다고 요구한다. 그러나 현재 `submissions` 테이블에는 해당 열이 없고, C0의 `correlation_id`는 학습자 한 회의 흐름 키다. 그대로는 인수 조건을 만족할 수 없으며, 열 추가나 의미 변경은 문서에 없는 계약 변경이다.

2. [P0] 600초 총예산은 Supabase 실행환경과 충돌한다 — §3-2는 순차 루프에 `생성총예산_MS=600000`을 둔다. 현재 `deliver`는 HTTP Edge Function인데 Supabase 공식 문서는 Edge Function 실행시간 제한을 60초로 설명한다. [Supabase Edge Functions 실행시간 제한](https://supabase.com/docs/guides/troubleshooting/edge-function-takes-too-long-to-respond)보다 긴 예산은 실제로 측정·보장할 수 없고, 중간 종료 뒤 claim만 남기는 실패를 만든다.

3. [P0] 102건 실호출 증거가 생성 기능의 증거가 아니다 — §0-2와 §12-3은 `evals/출력_v1api.json`을 생성 경로의 키·실호출 증거로 사용한다. 그러나 해당 실행은 `prompts/교정.md`와 `correct?평가=1`을 사용한 교정 평가이며, `prompts/과제생성.md`도 없다. 따라서 생성 벤더 호출·응답 스키마·`intervention.delivered` 착지는 아직 입증되지 않았다.

4. [P0] `generation_outcome` 필수화가 불변 이벤트와 모순된다 — §11-2는 모든 `intervention.delivered`에 필수라고 하면서 `payload.ver=2`를 새로 요구하고 과거 v1 행은 그대로 둔다. `learning_events`는 불변이므로 기존 intervention 행에 이 필드를 소급해 채울 수 없다. 버전별 필수성 규칙이나 이행 계약이 없어 필수 필드 주장이 거짓이다.

5. [P0] `이미배정`은 문서가 요구한 방식으로 기록할 수 없다 — §3-5와 §12-6은 두 번째 실행이 `이미배정`을 반환한다고 하지만, §4-1은 `generation_outcome`을 intervention 행에 기록하도록 한다. 착지 행은 정확히 1개이고 불변이므로 두 번째 실행에는 새 행도, 기존 행을 바꿀 권리도 없다. §12-7의 “14값 각각 자기 행에 남긴다”와도 동시에 성립하지 않는다.

6. [P0] `generation_claims`에 동시성 펜싱이 없다 — §3-5의 열은 유일키·시각·상태·`correlation_id`뿐이며 lease 소유자, fencing token, 시도 번호, 최종 event 식별자가 없다. 첫 호출이 claim만 잡고 멈추면 두 번째 호출은 기존 배정을 찾지 못한 채 멈추고, 24시간 후 `abandoned` 처리된 뒤 늦게 살아난 첫 호출이 새 결과를 착지할 수도 있다. “최소 1회 호출”과 “착지 정확히 1회”를 보장할 실행 규격이 아니다.

7. [P0] 구제 경로와 야간 배치가 같은 날짜를 두고 경쟁한다 — §3-1은 `/tasks` 구제에서는 생성을 금지하지만 현재 `tasks/index.ts`는 단순히 `deliver?learner_id=...`를 호출하며 맥락 인자를 보내지 않는다. 구제가 먼저 폴백을 착지하면 일일 유일키 때문에 이후 생성 결과가 버려지고, 배치가 claim만 잡은 상태면 구제가 무엇을 반환해야 하는지도 정해져 있지 않다. 이 경쟁에 대한 원자 규칙과 회귀 픽스처가 없다.

8. [P0] 입력 스냅샷이 아직 닫히지 않았다 — §0-3과 §6-1은 `evidence_refs`가 계약에서 거부되면 나중에 payload로 내리겠다고 적어, 저장 위치를 스스로 미결 상태로 둔다. 현재 `학습자상태.js`는 사건 목록이 200개를 넘으면 `잘림`을 남기지만 §6-1의 고정 모양에는 이 표시가 없다. `occurred_at <= as_of`만으로는 늦게 도착한 사건과 당시 DB 읽기 범위를 복원할 수 없어 같은 판정판에서 입력 표본이 달라진다.

9. [P0] `position`을 배치 순서로 재사용하면 기존 계약을 오염시킨다 — §11-5는 회전 처리 순서를 기존 payload의 `position`에 기록하라고 한다. 하지만 C0와 현재 검증기는 `position`을 선택지의 실제 위치로 정의하고, 0·-1·임의 값을 거부한다. 배치 순서를 넣는 순간 선택 사건의 의미가 바뀌고 기존 소비자와 회귀가 깨진다.

10. [P0] 실패 원인 필드명과 값목록의 언어가 닫혀 있지 않다 — §4-1은 `gate_failed`라고 쓰고 §11-2는 `generation_gate_failed`라고 확정한다. 동시에 §4-1은 “영문 정본 이름”을 예고하면서 실제 값은 `성공`, `검문탈락`, `용량초과` 같은 한글 문자열만 제시한다. 저장·조회·픽스처가 어느 이름과 문자열을 정본으로 삼는지 결정되지 않았다.

11. [P0] c12 payload가 실제 저장 경로에서 강제되지 않는다 — §11-2는 세 필드와 닫힌 값목록을 선언하지만 `이벤트검증.js`의 허용 목록, `deliver` 직접 insert, 마이그레이션, DB 검증식의 변경이 없다. 현재 배달 함수는 이벤트 API 검증을 우회해 직접 쓰므로 순수 함수 픽스처만으로는 실제 착지 행의 타입·미지 키·조건부 null을 검증할 수 없다. 잘못된 payload가 정상 intervention으로 저장될 수 있다.

12. [P0] `policy_ver` 지문이 처치 결과를 가르는 재료를 빠뜨린다 — §5-1의 여섯 재료에는 생성 대상 여부, 구제/배치 맥락, 학생 순서 회전 알고리즘, roster, 사건 표본 절단, 응답 정규화·파서 구현이 완전히 닫혀 있지 않다. 이 값들이 달라도 같은 `오늘과제.v4`가 될 수 있어 같은 규칙 단위의 성공·폴백 분포를 비교할 수 없다. §11-5에서 순서가 결과에 영향을 준다고 인정하면서 그 순서를 지문에 넣지 않은 것은 계보 단절이다.

13. [P0] `generation_input_text`는 실제 요청 재현물이 아니다 — §5-3은 벤더 요청을 렌더된 문자열 한 개로 축소하고 §11-2는 그 문자열을 “실제 요청 본문”이라고 부른다. provider message role, JSON envelope, serializer, 호출 옵션의 실제 값, 응답 파서 판, 요청 식별자가 저장되지 않는다. `prompt_ver`에 포함한다고만 적은 것은 재현 규격이 아니다.

14. [P0] 학생에게 나가는 문장의 의미 품질 게이트가 비어 있다 — §8은 길이·한글 비율·금칙 서식·물음표만 검사하며 문장과 질문의 의미적 연결, 한국어 사용 도움, 목표·약점 관련성, 사실성을 검사하지 않는다. §8은 런타임 품질 문턱을 금지하고 §12-14의 102문항은 생성 시험지가 아니라 교정 픽스처다. 문법적으로만 통과한 무관하거나 쓸모없는 과제가 학생에게 전달되고, 그 상호작용이 원본 증거로 쌓인다.

15. [P1] 재미와 신선함을 낳는 장치가 없다 — §2·§7은 산출물을 문장 1개와 질문 1개로 고정하고, §8은 형식 탈락만 막는다. 상태 숫자를 프롬프트에 넣는 것만으로 학생이 왜 다시 열어야 하는지, 무엇이 새롭고 어떤 피드백이 재미를 만드는지는 정의되지 않는다. 엔진 수집에는 맞아도 학생 접점의 기본 게이트 중 재미·신선함 층이 비어 있다.

16. [P1] 실력 이해와 생성 과제의 연결이 끊겨 있다 — §6-2의 입력은 행동·성향 축 중심이고 §10은 오류 태그를 제외하며, `skill_id`·오류 유형·TOPIK 목표와 생성 문장의 연결 필드가 없다. `level_snapshot`과 `goal_snapshot`은 맥락일 뿐 어떤 언어 약점을 겨냥했는지 기록하지 않는다. 따라서 이 기능이 엔진의 어휘 지도·학습자 모델·평가셋 중 무엇에 어떤 증거를 공급하는지 답하지 못한다.

17. [P1] 초급 제외로 기능 도달률 0을 허용한다 — §7-1은 1~2급과 미정을 모두 생성 대상에서 빼고, §14는 실제 도달 학생이 0명일 수 있음을 인정한다. 그런데 학생 분포를 측정하거나 초급 학생에게 이 기능 대신 제공할 목표 관련 산출물을 정의하지 않았다. 구현·시험이 모두 통과해도 개원 초기에는 학생에게 아무것도 전달하지 않는 기능이 될 수 있다.

18. [P1] 인수 조건이 성과 회수의 관측 사슬을 검사하지 않는다 — §12-3은 `intervention.delivered → task.assigned → 조회 → 제출`만 확인한다. 그러나 `성과회수.js`는 `content.viewed.parent_event_id = intervention.event_id`를 요구하므로 제출만 성공하고 열람 사건이 빠져도 현재 인수 조건은 초록이 된다. 그러면 기술적으로 생성된 과제가 있어도 효과 소비자에는 관측 0건으로 남는다.

19. [P1] 배치 공통 `as_of`와 공통 읽기 스냅샷이 구현 계약에 없다 — §11-4는 “배치가 상태를 읽기 시작한 시각”이라고 단수로 정의하지만, 현재 `deliver`는 학생별로 `new Date()`를 만들고 각 학생의 상태를 별도로 읽는다. 배치 ID, 공통 `as_of`, 동일 DB snapshot, 학생별 실제 읽기 시각의 저장 규칙이 없다. 같은 배치 안에서도 서로 다른 시점의 상태를 같은 `policy_ver`로 묶게 된다.

이 문서보다 나은 대안 구조 1개: 학급 전체 단일 HTTP `deliver` 안에서 벤더를 순차 호출하지 말고, 배치 오케스트레이터가 학생별 단건 작업을 호출하는 구조로 분리한다. 기존 `generation_claims`에는 lease 소유자·fencing token·시도 번호를 추가하고, claim 보유자만 최종 세 행을 원자 착지하게 하며, 구제 경로는 착지된 결과만 읽거나 명시된 폴백만 반환하게 한다. `correlation_id`는 실제 학습자 흐름에만 유지하고, 배정·열람 연결은 기존 event/intervention 키를 사용하며, v1/v2 payload를 버전별로 검증한다.
