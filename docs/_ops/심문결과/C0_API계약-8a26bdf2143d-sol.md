판정: 동결 불가 — P0 18건, P1 5건.

[P0] 동결 시험이 계약 표면 대부분을 보지 않는다 — §4는 “엔드포인트 둘”이라면서 실제로는 이벤트·업로드·조회 3종·인증 3종, 총 8개를 규정한다. §7의 왕복 6은 사실상 `/events`만 검사하므로 Storage·조회 격리·인증 동시성·세션 폐기·c8 교정 고리가 깨져도 §8상 동결할 수 있다.

[P0] c8 교정 사건은 API로 저장되지 않는다 — §4-1은 `correction_id`를 두 교정 사건에 필수화했지만 `functions/events`의 INSERT 열 목록에는 `correction_id`가 없다. DB CHECK가 전건 거절하며, “12/12” 시험은 API가 아니라 직접 SQL로 삽입해 이 결함을 우회한 거짓 초록이다.

[P0] 초기화 뒤 옛 access token이 계속 접근한다 — §4-5는 `revoked_before=now()`로 기존 세션이 폐기된다고 주장하고, L0 §4-3은 RLS를 우회하는 Edge Function도 `session_alive()`를 직접 확인하라고 명시한다. `events`·`uploads`·`tasks`·`corrections`·`progress`는 `auth_user_id`만 보고 `active`·`revoked_before`를 전혀 검사하지 않는다.

[P0] 동의 화면을 구현할 API가 없다 — §5와 §7-5는 녹음 전에 동의 상태를 확인하고 동의 화면에서 새 동의를 세우라고 요구하지만, 동의 조회·동의 생성 엔드포인트가 하나도 없다. `/first-login`도 동의를 받지 않으므로 앱은 업로드의 403을 맞은 뒤에야 무동의를 알 수 있다.

[P0] 빈 과제 폴백이 정상 화면 모양으로 데이터를 버린다 — §4-3 ①은 빈 배열이면 고정 과제로 내려가라고 하면서 `task_ref`가 없으면 발화를 보내지 말라고 한다. 배치 실패·동의 누락·첫날이 모두 같은 빈 상태로 접히고, 화면은 작동하지만 그날 발화는 Supabase에 0건 남는다.

[P0] 철회 후 수집 0건을 보장하지 못한다 — §4-2의 업로드 서명은 구현상 1시간 유효해 철회 전에 받은 URL로 철회 후에도 파일을 올릴 수 있다. `/events`도 `ingested_at`이 아니라 기기 `occurred_at`만 동의 시각과 비교하므로 철회 전에 발생했다고 주장한 큐를 철회 뒤 저장한다.

[P0] 확정된 `level_snapshot:null` 처방이 계약에 반영되지 않았다 — §4-3 ①은 유호님 확정 ⓑ를 적으면서도 바로 아래에서 “아직 구현 안 됨”이라고 인정한다. 현행 검증기는 `null`을 필수 누락으로 보므로 급수 없는 개원 첫 주 발화가 그대로 400으로 소실된다.

[P0] 멱등키 규칙이 문서 안에서 충돌하고 실제로 별도 발화를 삼킨다 — §4-1은 앱 키를 “한 번 생성해 보존하는 UUID v4”로 정했지만 §4-3과 앱 코드는 `submission:{날짜}:{호흡}:{시도}` 결정론 키를 쓴다. 재설치·다중 기기·로컬 로그 초기화 후 다른 녹음이 같은 키를 쓰면 서버는 payload 비교 없이 원래 `event_id`를 돌려주고 새 녹음을 버린다.

[P0] `schema_ver`가 실제 입력 규격을 거짓 표기한다 — §6은 구 계약판도 받는다고 하지만 서버는 선언된 판이 아니라 현행 c8 검증기만 실행하고 행에도 DB 최신판 c8을 찍는다. 구 앱 payload는 새 필수 필드 때문에 거절되거나, 변환 없이 저장되면서 c8 행으로 위장된다.

[P0] 한 앉음의 쌍 고리가 계약상 선택 사항이다 — `correlation_id`는 예시에만 있고 §4-1의 앱 필수표와 공통 검증 필수목록에는 없다. 현 앱이 보내도록 고친 것과 무관하게 구 큐나 다음 소비자는 생략해도 통과하므로 ②낭독과 ③자유발화가 같은 90초에서 나왔다는 사실이 다시 소실된다.

[P0] 배정→개입→첫 성과 고리가 끊겼다 — `/tasks`는 `task_id`와 `intervention_id`를 주지만 제출 요청은 `task_id`를 되돌리지 않고 앱의 `intervention_id` 전송은 금지한다. 서버는 `retry_of_event_id`가 있을 때만 개입 ID를 계승하므로 최초 제출의 `intervention_id`는 null이고 즉시 성과가 어느 개입 결과인지 남지 않는다.

[P0] 교정→재발화 고리는 실행 불가능하다 — `/corrections`가 주는 것은 `submission_id`인데 `/events`가 요구하는 `retry_of_event_id`는 학습 사건의 `event_id`다. 변환 통로가 없고, 임의 사건 ID를 보내도 서버는 “실제로 교정된 제출인가·그 교정을 봤는가”를 검사하지 않아 `/progress`가 아무 재시도나 교정 성과로 계산한다.

[P0] 문항·목표·스킬 맥락의 필수성이 강제되지 않는다 — `task_snapshot`·`task_schema_ver`·`goal_snapshot`은 소급 불가라고 서술됐지만 검증기는 이들을 요구하지 않고 현 앱 제출도 snapshot을 보내지 않는다. `skill_ids`는 존재 검증이 없고 `skill_taxonomy_ver`도 선택이라 오타 스킬·판본 미상 행이 정상 저장된다.

[P0] 선택 로그가 불변 선택지를 보존하지 않는다 — §4-1은 `{option_id,label}`을 요구하지만 실제 검증과 테스트는 문자열 배열을 정상으로 통과시키며 `choice_dimension`도 계약 필드에 없다. 문구 변경 뒤 동일 선택지를 묶을 수도, 서로 다른 선택 질문을 구분할 수도 없다.

[P0] 추천→선택→전달 사슬에 공통 결정 키가 없다 — `choice.selected`에는 후보·추천·선택은 있지만 이후 `intervention.delivered`와 잇는 식별자가 없다. L0의 `policy_ver`·`strategy_code`·`target_skill_ids`·`rationale`도 C0 허용 payload와 실제 배달 행에서 빠져, 어떤 지도 정책이 어떤 결과를 냈는지 복원할 수 없다.

[P0] 훈련 승격 사건이 정본의 최소 계보를 표현하지 못한다 — §9는 `data_use.granted`를 현행 사건으로 열었지만 C0에는 `artifact_ref`·`content_hash`·`serializer_ver`·`dataset_ver`·정확한 `consent_id`·검사시각·비식별/라벨 규칙·승인자·평가·제외/롤백을 실을 규격이 없다. L0 §6-2의 승격 계약과 정면으로 갈리며 빈 승격 사건도 물리적으로 만들 수 있다.

[P0] `session.abandoned`가 “어디서 왜 막혔나”를 버린다 — 이 사건은 공통 필드만 요구해 호흡 단계·`task_ref`·`task_format`·머뭇거림·발화 길이·문턱을 남기지 않는다. 낭독에서 막힌 것과 자유발화에서 막힌 것이 동일 행이 되고, 기기 로컬 로그가 사라지면 복원할 수 없다.

[P0] 음성 원본 규격이 동결 게이트 밖에 있다 — §4-2는 PCM WAV를 정본으로 선언하지만 현 앱은 `.m4a`를 저장하고 서버는 손실 압축본을 그대로 수용한다. §8에는 실기기 WAV 헤더·AGC 요청·녹음 설정 검사를 동결 조건으로 넣지 않아, “규격 위반 기록”만 남긴 채 이미 지워진 발음 신호를 복원하지 못한다.

[P0] 임시번호 1회성과 비밀번호 초기화가 동시성·부분 실패에서 깨진다 — `/temp-login`은 해시를 읽고 GoTrue 비밀번호를 바꾼 뒤 DB에서 해시를 지우므로 동시 요청 둘이 모두 통과해 마지막 비밀번호가 승리할 수 있다. `/reset`도 DB의 임시번호·폐기·감사를 먼저 커밋한 뒤 GoTrue를 호출해 후자가 실패하면 “초기화 기록은 섰지만 옛 비밀번호는 산” 혼합 상태가 된다.

[P1] 교정의 생성 시각을 확정 시각으로 치환할 근거가 없다 — §4-3 ②는 모든 `corrections.created_at`을 `confirmed_at`으로 노출한다. L0는 AI 초안과 그 초안을 검수한 강사 행을 별도로 허용하므로 발행·검수 조건 없이 AI 초안까지 학생 목록에 노출된다.

[P1] 업로드 상한과 고아 파일 처리가 성립하지 않는다 — `/uploads/sign`은 앱이 주장한 `byte_size`만 보고 서명하며 실제 PUT 크기를 제한하지 않는다. 서명 재시도마다 새 UUID 경로가 생기고 업로드 뒤 앱 종료·영구 이벤트 거절을 정리할 예약 ID·완료 표식·고아 청소 규칙이 없다.

[P1] 오류 계약이 같은 오류에 세 HTTP 의미를 준다 — `CONSENT_MISSING`은 §5에서 409지만 업로드 구현은 403, 배치 이벤트에서는 HTTP 200 내부 항목이다. `AUTH_EXPIRED`·`RATE_LIMITED`는 표에만 있고 실제 함수 경로가 없으며, 달력상 불가능한 `date`와 잘못 배치된 cursor UUID는 정규식을 통과한 뒤 DB 500으로 바뀐다.

[P1] 기록한다고 약속한 진단 메타가 기록되지 않는다 — §3의 `X-App-Ver`는 “로그용”이지만 함수들이 읽지도 저장하지도 않는다. 미래 `occurred_at`도 “로그에 남긴다”고 했으나 실제 `events` 함수에는 미래 비교·로그가 없어 오염된 앱 빌드와 기기 시계 사고를 추적할 수 없다.

[P1] 첫 등록의 “이미 등록됨” 응답이 두 계약이다 — §4-4 게이트 실패 표는 이미 등록된 계정을 다른 실패와 같은 401로 돌린다고 하고, 성공 표는 `{ok:true, already:true}`를 허용한다. 실제 구현은 동시성 패자에게 200을 주므로 소비자는 어느 분기를 정본으로 삼아야 할지 결정할 수 없다.

대안 구조: C0를 현재 산문+분산 검증기 대신, 이벤트별 `발생 주체·필드 타입·필수/null·인과 참조·동의 판정·버전 변환`을 담은 단일 실행 계약 매트릭스로 바꿔야 한다. 그 매트릭스에서 서버·앱 검증기·문서·픽스처를 생성하고, 기존 `task_id`·`intervention_id`·`correction_id`를 명시적 인과축으로 되돌려 받으며, 기능별 실제 DB/Auth/Storage 왕복이 통과한 슬라이스만 동결해야 한다.
