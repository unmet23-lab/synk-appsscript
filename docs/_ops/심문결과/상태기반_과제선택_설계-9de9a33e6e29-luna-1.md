결론: 동결 불가. P0 7건, P1 10건, P2 1건이다.

1. [P0] 미해결 계약 충돌 상태에서 동결을 시도한다 — §0·§8·§11  
`P0 §6-3`의 입력 둘/셋 문제가 아직 유호님 판정 대기다. ㉢이면 문서의 핵심인 상태 기반 생성이 사라지고, ㉠·㉡이면 P0 계약을 먼저 개정해야 하므로 현재는 실행 가능한 단일 규격이 없다.

2. [P0] 모델이 본 상태 입력을 소급할 수 없다 — §3(a~b)·§5.1·§7  
문서는 상태 축·급수·목표를 모델에 보내지만, 실제 전달 시점의 값, `as_of`, 상태 산출 버전, 정규화된 요약 또는 렌더링된 입력을 어떻게 보존할지 정하지 않았다. 이후 상태 계산 코드나 기간 창이 바뀌면 원자료에서 재계산해도 당시 모델 입력을 복원할 수 없다.

3. [P0] 생성 결과와 후속 학습 사건의 연결이 끊긴다 — §3(d)·§4·§9.3  
`생성문장`을 `오늘과제()`에 넘긴다고만 하고, 실제 문장 원문·불변 스냅숏·해시와 응답·교정·즉시/1/7/30일 성과를 어떤 기존 상관관계로 묶는지 정하지 않았다. 비결정적 모델 출력은 나중에 재생성할 수 없으므로 학생이 실제로 본 과제를 엔진이 학습할 수 없다.

4. [P0] 정상 폴백과 생성 실패가 같은 행으로 뭉개진다 — §4·§4-1·§9.2~3  
키 없음, 벤더 오류, 검문 탈락, 생성 미시도, 정상적인 전날/도입 폴백이 모두 `degraded=true`와 `출처=전날/도입`으로 끝난다. 따라서 행 분포가 초록이어도 실제 생성 경로가 한 번도 실행되지 않았는지 알 수 없다.

5. [P0] 재실행·동시 실행의 멱등성이 없다 — §3·§4·§6  
결정적 해시는 대조군 배정에만 언급되고, 생성 요청·배달 기록의 중복 방지, 동시 잠금, 벤더 성공 후 DB 실패 시 재사용 규칙은 없다. 밤 배치가 겹치거나 재시도되면 서로 다른 문장이 여러 번 생성·배달될 수 있고, 사후에 어느 문장이 실제 전달됐는지 판별할 수 없다.

6. [P0] 대조군을 사후 식별할 수 없다 — §6·§11  
학생×날짜 해시와 비율만 있고, 실제 배정 arm, 적용 비율, 배정 규칙 버전을 저장하는 계약이 없다. `출처=전날/도입`은 대조군·생성 실패·키 없음·정상 폴백을 모두 포함하므로 효과 비교의 분자와 분모를 만들 수 없다.

7. [P0] 배치의 상태 시점과 날짜 경계가 닫혀 있지 않다 — §3(a~d)·§6  
`오늘`, `전날`, 상태 조회 시점, 목표 변경 시점, 시간대, 배치 기준 시각이 정의되지 않았다. 같은 학생·같은 날짜에 배치가 재실행되거나 새 사건이 들어오면 서로 다른 상태로 서로 다른 과제가 생성되며, `policy_ver`만으로는 그 차이를 복원할 수 없다.

8. [P1] 상태 스키마가 설계 계약이 아니다 — §3(a)·§7·§8 표  
본문은 `축 5·confidence·evidence_refs`를 말하다가 실제 모델 입력에서는 막연한 숫자 몇 개만 말한다. 필드별 단위, 기간 창, 빈 값·초기값, 신뢰도 사용 여부, 상태 산출 버전이 없어 동일한 상태라는 말이 구현마다 달라진다.

9. [P1] 생성 출력 형식이 모순된다 — §3(c~d)·§4-1  
벤더 출력은 “후보 문장·질문”으로 복수형인데 `오늘과제()`에는 단수 `생성문장` 하나를 넣는다. 복수 후보의 선택 규칙, JSON/텍스트 형식, 답변 기대값, 추가 설명문 처리, 선택 실패 시 결과가 정의되지 않았다.

10. [P1] 검문 규격이 실행 가능한 판정표가 아니다 — §4-1·§5.1·§9.1  
길이·한국어 비율·금칙·질문 형식을 외부 문서와 일반어로만 참조하고, 유니코드 길이 계산, 정규화, 빈 출력, 혼합 문장, 경계값 처리 규칙을 닫지 않았다. 그런데 `판지문`은 이 문턱을 결정적인 입력으로 취급하므로, 검문 구현 차이가 곧 동일 `policy_ver` 내부의 행동 차이가 된다.

11. [P1] `model_ref`가 재현성 계약이 아니다 — §5.1~2·§9.4  
`payload.model_ref`에 모델과 프롬프트 해시를 넣는다고만 하고, 필수 여부·필드 형식·템플릿 해시인지 렌더링 입력 해시인지·생성 파라미터·응답 파서 버전을 정하지 않았다. `payload` 자유칸에 의존하면 값이 빠져도 배치와 테스트가 통과한다.

12. [P1] `degraded` 의미 전환이 화면 메모에만 남는다 — §1-1·§5.3  
기능 도입 전의 `true`와 도입 후 벤더 실패의 `true`가 다른 의미라는 것을 인정하면서도 전환 날짜를 화면 옆에 남기라고만 한다. 기계가 읽는 해석 버전이나 전환 사건이 없어 장기 집계에서 두 의미가 섞인다.

13. [P1] SRS를 피한다는 논증이 폴백과 충돌한다 — §4·§8  
§4는 생성 실패 시 `전날문장`을 재사용한다고 명시한다. 그런데 §8은 “어제 낸 것을 다시 내지 않는다”고 주장하므로, 이것이 허용된 1일 재출제인지 금지된 재출제인지 계약이 갈린다.

14. [P1] 폴백 단계 수가 자기모순이다 — §4  
절 제목과 첫 설명은 “3단”이라고 하지만 표에는 성공 1단과 실패 2단만 있고, 뒤에서는 다시 “2단짜리”라고 한다. 검문 탈락·키 없음·전날·도입을 몇 단계와 상태로 검증해야 하는지 인수 조건이 고정되지 않았다.

15. [P1] 인수 조건이 실제 생성 경로를 검증하지 않는다 — §9.2~3  
키가 없는 상태의 초록 배치와 리허설 행 분포만 요구하고, 키가 있는 벤더 호출·시간초과·형식 오류·부분 DB 실패·후속 응답 연결을 통과 조건으로 삼지 않는다. 순수 모듈 테스트가 모두 초록이어도 운영에서는 전원 폴백일 수 있다.

16. [P1] 교육적 적합성의 사전 게이트가 없다 — §4-1·§9  
검문은 길이와 형식만 보며 학생에게 좋은지 판단하지 않는다고 했지만, 골든셋의 문항·합격 기준·급수·목표 일치 검사가 인수 조건에 없다. 문법적으로 그럴듯한 질문이 학생 상태와 목표를 무시해도 첫 학생에게 그대로 전달되고 그 경험은 소급 복구되지 않는다.

17. [P1] 결정적 해시가 결정적 규격으로 정의되지 않았다 — §6  
학생 키, 날짜의 시간대, 직렬화 방식, 시드, 해시 함수, 버전, 비율 경계 계산이 없다. `게임배정.js`를 선례로 가리키는 것만으로는 재현 계약이 아니며, 키나 시간대가 달라지면 같은 학생의 arm이 바뀐다.

18. [P2] “학생 20명”은 측정 가능한 대조군 개시 기준이 아니다 — §11  
20명의 의미가 학생 수인지 유효 사건 수인지, 필요한 추적 기간·성과 지표·최소 표본이 무엇인지 없다. 유호님 판정 후에도 동일 조건에서 같은 시점에 켤 수 없는 임의 숫자다.

이 문서보다 나은 대안 구조가 있으면 1개:

상태 입력 여부를 먼저 확정한 뒤, 기존 배달 사건 안에 하나의 불변 결정 봉투를 남기는 구조다. 봉투에 정책판·`correlation_id`·실제 상태/급수/목표 스냅숏과 산출 시점·모델/프롬프트 판·생성 원문·검문 결과·대조군 arm·폴백 사유를 함께 기록하고, 배달 기록과 생성 결과를 하나의 멱등 트랜잭션으로 묶어 재실행 시 같은 봉투를 재사용해야 한다.
