동결 불가 — 지적 17건.

1. [P0] 임대 만료 작업이 재시도 큐로 돌아가는 통로가 없다 — §3-5-b의 RPC 다섯 개에는 `claimed→대기` 회수 RPC가 없다. `jobs_claim`은 `대기`만 집으므로 워커가 죽은 job은 재시도되지 않고 마감 스윕에서 폴백으로 밀린다.

2. [P0] ⑥' 비대상 착지는 현재 입력으로 만들 수 없다 — §3-4의 `_targets`에는 완성된 `task_snapshot`, 문장·질문, 이벤트 ID, 개입 ID가 없다. 그런데 같은 절은 `jobs_finalize(_event=…)`로 세 사건을 원자 착지하라고 한다. 구현자는 문서 밖의 별도 생산 경로를 발명해야 한다.

3. [P0] `snapshot_as_of`가 실제 상태 계산에 연결되지 않는다 — §3-5-b는 큐에 시점을 저장하지만, 워커 호출 계약에는 그 값을 `as_of`와 `ingested_as_of`에 전달하는 규칙이 없다. 지연된 워커가 최신 사건을 읽으면 저장된 스냅샷과 실제 생성 입력이 달라진다.

4. [P0] 한 배치의 모델·프롬프트·정책 판이 고정되지 않는다 — §5-1은 모든 job이 같은 판을 써야 한다고 하지만 `generation_jobs`에는 `model`, `prompt_ver`, `policy_ver`, `estimator_version`이 없다. 큐 처리 중 배포나 설정 변경이 일어나면 같은 배정일 안에 서로 다른 판이 섞인다.

5. [P0] 정본 이벤트에서 급수·목표·상태 유효기간이 빠진다 — §3-5-b의 `_event` 예시는 `skill_ids`와 추정 메타만 싣고 `level_snapshot`, `goal_snapshot`, `valid_from`, `expires_at`, `user_confirmed`를 싣지 않는다. `branch_snapshot`은 운영 큐의 JSON일 뿐 `learning_events` 계약을 대체하지 못한다.

6. [P0] `winning_attempt_id`가 선택 사항이고 같은 job 소속도 보장하지 않는다 — DDL은 nullable이며 `jobs_finalize` 기본값도 `null`이다. FK도 attempt 존재만 확인하고 해당 attempt가 같은 job인지 확인하지 않는다. 재시도 뒤 학생에게 실제로 전달된 응답을 복원할 수 없다.

7. [P0] 종료사유 값목록이 물리적으로 닫혀 있지 않다 — `generation_jobs.outcome`은 자유 `text`이고 CHECK가 없다. `_outcome`과 `_event` JSON도 RPC 주석에만 규격이 있다. §12-21의 “DDL 값 집합 대조” 자체가 실행할 DDL 집합을 갖지 못한다.

8. [P0] append-only 시도 장부가 실제로 보호되지 않는다 — `attempt_close`의 1회 채움 조건만 있고 행 삭제·다른 필드 UPDATE를 막는 물리 장치가 없다. “자유 UPDATE 금지”는 문장이지 데이터 계약이 아니므로 원응답 계보가 나중에 덮어써질 수 있다.

9. [P0] `skill_ids`가 엔진의 다음 행동으로 되돌아가지 않는다 — §6-0 H3은 `성과회수.js`가 기술별 결과를 읽는다고만 하고, 그 결과의 저장 형식·학습자 상태 반영·다음 job 선택 규칙을 정의하지 않는다. 실제 선택 규칙은 여전히 급수와 미겨냥 기술 회전이다. `늘었나`는 이름 붙인 리포트에 머문다.

10. [P0] 상태 요약을 모델이 실제로 사용한다는 보장이 없다 — §5-3은 응답의 `sentence`·`question`만 닫고, 요청 본문에 어떤 상태 축이 필수인지 정하지 않는다. 상태 하나를 바꿔도 생성 결과가 달라지는 회귀가 없어, 학생별 상태를 무시한 일반 문장이 모든 런타임 검문을 통과할 수 있다.

11. [P0] 출시 평가 게이트가 낡은 초록을 재사용할 수 있다 — §8-B는 결과 파일의 8개 메타데이터만 정의하고, 사례별 출력·축별 점수·채점 근거의 정본 구조를 정의하지 않는다. 더구나 §12-19의 차단기는 `model+prompt_ver+policy_ver`만 확인하고 `estimator_version`은 확인하지 않는다. 상태 계산이 바뀌어도 옛 평가 결과로 기능을 열 수 있다.

12. [P0] 판정 픽스처 숫자가 문서 안에서 충돌한다 — §5-1은 정책 재료와 회귀를 6개로 적지만 §12-5는 7벌을 요구한다. §12-7은 행 14개라고 정정했는데 §13은 여전히 “13 + 응답 1 + 행 없음”을 금지 규칙으로 둔다. 해시·실패 경로·인수 조건의 정본을 하나로 결정할 수 없다.

13. [P0] 분모 0이 파이프라인 사망과 정상 게임날을 구분하지 못한다 — 게임날은 `generation_jobs`가 없고, 오케스트레이터가 죽어도 역시 없다. 전체 학생의 기대 목록이나 배치 매니페스트가 없어 두 상태가 같은 0으로 남는다. 게다가 `generation_jobs` 수에는 `대상아님`이 들어가 실제 생성 후보 수와도 섞인다.

14. [P1] 워커 상한과 예산의 계산식이 닫히지 않았다 — 표는 `워커학생상한=3`을 쓰면서 뒤에서는 두 상수로 계산한다고 한다. 계산식·여유분·RPC 차단값이 없고 `_count`도 제한되지 않는다. CPU는 측정만 하고 허용 한계와 상한 재결정 규칙은 없다.

15. [P1] N=40 평가셋이 재현 가능한 시험이 아니다 — 12개 셀에 “3~4개씩”이면 36·40·48 모두 가능하지만 어느 셀에 몇 개를 넣을지 없다. 반복 2회의 점수 합산, 반올림, 호출 실패와 누락 출력의 처리도 없다. 실행자마다 다른 시험을 같은 판으로 보고할 수 있다.

16. [P1] 학생 경험의 재미를 실제 기능에서 밀어냈다 — §8-A는 “학생이 왜 한 번 더 여는가”를 범위 밖으로 보낸다. 생성 문장·질문·폴백만 있고 재방문, 시작, 완료, 피드백, 자기 성장 체감으로 이어지는 장치가 없다. 오프라인 합성물 채점만으로 학생 접점의 재미 게이트를 충족했다고 볼 수 없다.

17. [P1] 신선함 검사가 표현 변형을 모두 통과시킨다 — §8의 14일 검사는 정규화 후 완전 일치만 잡으므로 단어·어순·조사 하나만 바꾼 상투 문장은 새 문장으로 통과한다. §8-B의 상투구 평가는 일회성 오프라인 표본이고, 라이브에서 다시 여는 사건·소비자·임계가 없다.

이 문서보다 나은 대안 구조 1개: 학생·날짜·갈래·스냅샷·모델/프롬프트/정책 판을 전부 고정하는 불변 `daily_assignment_manifest`를 먼저 만들고, 생성 대상만 `generation_jobs`로 넘긴다. `claim→requeue→attempt_open→attempt_close→finalize`를 DB 제약과 단일 종결 RPC로 닫고, 모든 attempt는 같은 job의 winning attempt임을 복합 FK로 강제한다. 게임날·비대상·생성대상의 기대 분모를 매니페스트에서 보존하며, 기술별 결과는 기존 학습자 모델 소비자에 실제 값으로 연결하고 평가 결과는 사례별 출력·점수까지 저장한다.
