## 0. 이 판정이 먼저 말해야 하는 것

**과녁이 654KB · v5.13 이다.** 앞의 두 판정(엔진도달 19건 · 세층합류 18건)은 문서 전문을 읽고
지적을 하나씩 실물에 댔다. **이 문서에는 그 방법이 안 통한다** — 그래서 방법을 바꿨다:

1. 지적 24건 중 **실물로 답이 나는 6건을 골라 끝까지 쟀다**(SQL 스키마 · lib 상수 · 문서 내부 대조).
2. 나머지 18건은 **조건부**로 남기고 재는 자리를 못 박았다. **「안 재봤다」를 「기각」으로 접지 않는다.**
3. 그러다 **여섯이 전부 같은 병**이라는 것이 드러났다 — 그게 이 판정의 결론이고, 심문이 준
   24건보다 값이 크다(§2).

⚠ **실제로 연 실물**: talk `supabase/L0_스키마.sql`(freeze 트리거 · `jobs_claim` · `jobs_load` ·
`generation_jobs` 열) · `lib/생성상수.js` · 과녁 문서의 §6-0·§8-B·§12-19·§16-1 구간.
**안 연 것**: 라이브 DB · `deliver` 오케스트레이터 전문 · `jobs_finalize` 본문 · §12 검사기 전량 · 앱 층.

## 2. 🔴 결론 — 여섯이 전부 «한 값을 두 곳이 안다»였다

확인된 여섯을 늘어놓으면 하나만 빼고 전부 같은 무늬다:

| # | 무엇이 두 곳에 있나 | 두 곳 | 갈리면 무슨 일 |
|---|---|---|---|
| ⑪ | **워커 학생 상한** | `lib/생성상수.js` = **식** ↔ `L0_스키마.sql:12360` = **리터럴 3** | 한쪽이 2를 계산해도 DB 는 3을 허용 · 4를 계산하면 워커가 죽는다 |

| ⑨ | **cron 잡 수** | :3128 = 「**3잡**」 ↔ :1886·:5443 = 「**4잡**」 | 판 지문 재료가 실제 배선을 덜 덮는다 |
| ⑰ | **엔진 소비자 #7 의 «현재 상태»** | §6-0 H3(:3488) = 「`skill_ids` 0회 읽음 · `✗✗✗`」 ↔ §16-1(:5392) = 「**✅**」 | 착수·완결 판정이 원리상 불가능하다 |

이 문서는 654KB 로 자라면서 **같은 사실이 여러 절에 사는 곳**이 됐다. 확인된 여섯 중 **넷이
문서가 자기 자신과 어긋난 것**이고, 실물 결함 둘도 「규칙의 정본이 한 곳이 아니다」와 같은 뿌리다.

**⇒ 이 문서에 필요한 것은 스물넷째 수리가 아니라 «정본 가르기»다.** 지적 하나씩 기워도
655KB 째 절이 하나 더 붙을 뿐이고, 다음 심문은 또 문서 내부 모순부터 집는다.
🔴 **이건 유호님 판정 자리다** — 문서를 쪼개는 것은 방향 결정이라 내가 못 넘는다(§6).

## 3. 채택 — 실물이 답한 여섯

### ① 적재실패→대기 전이가 **불변 계보 검사를 전량 건너뛴다** → **채택**

`supabase/L0_스키마.sql` 실물:

```
create or replace function engine.generation_jobs_freeze() returns trigger ... as
begin
  if OLD.status = '적재실패' and NEW.status = '대기' then
    return NEW;                              -- 🔴 여기서 끝난다
  end if;
  if NEW.branch_snapshot is distinct from OLD.branch_snapshot
  or NEW.event_draft     is distinct from OLD.event_draft
  or NEW.snapshot_as_of  is distinct from OLD.snapshot_as_of
  or NEW.batch_run_id    is distinct from OLD.batch_run_id then
    raise exception '선판정 스냅샷은 고치지 않는다 — 계보가 거짓이 된다';
  end if;
```

되돌리는 전이 하나에서 **네 칸 전부**가 자유가 된다. 트리거가 지키려던 것이 바로 그 넷이다.

🔑 **심문의 세부는 절반 틀렸다** — `learner_id`·`assign_date`·`skill_ids` 는 「예외 때문에」
안 지켜지는 게 아니라 **애초에 이 트리거가 안 보는 칸**이다(정상 경로에서도 자유다).
그래도 결론은 같고 오히려 넓다: **예외가 필요보다 넓고, 보호 범위는 필요보다 좁다.**

**처방(둘)**:
- 예외를 「검사 생략」이 아니라 **「이 전이에서만 `event_draft`·`snapshot_as_of` 를 다시 쓸 수 있다」**로
  좁힌다 — 재적재가 실제로 필요한 것은 그 둘이다. `branch_snapshot`·`batch_run_id` 는 예외에서도 언다.
- `learner_id`·`assign_date` 를 **모든 경로에서** 언다. 이 둘이 바뀌면 사건의 임자가 바뀐다.

⚠ **안 재봤다**: 재적재 경로가 정말 그 둘만 고치는지는 `jobs_load` 본문 전량을 안 읽었다.
좁히기 전에 그 함수부터 읽어야 한다(좁혔다가 재적재가 죽으면 학생이 빈손이 된다).

### ④ `event_draft` 에 학생 귀속을 검증할 독립 재료가 없다 → **채택**

`jobs_load` 실물의 허용 키:

```
draft키들 = ['task_ref','task_snapshot','estimator_version','estimator_confidence','evidence_refs']
draft허용 = 위 + ['요약','reads']
```

**`learner_id` 가 없다.** 그리고 `task_ref` 는 날짜만 문다(`task-<날짜>`). ⇒ 학생 B 의 draft 를
학생 A 의 `_targets` 원소에 넣으면 **날짜 검사를 통과해 A 의 append-only 사건으로 착지한다.**
append-only 라 **되돌릴 수 없다.**

**처방**: draft 에 `learner_ref` 를 넣고 `jobs_load` 가 원소의 `learner_id` 와 **대조**한다
(불일치 = 그 원소만 `적재실패`). 새 표 0 · 새 사건 0 · 계약은 draft 허용 키 하나 추가.
🔑 **지금이 싼 이유**: 학생 0명이라 아직 잘못 붙은 사건이 하나도 없다. 학생이 온 뒤에 발견하면
**어느 사건이 잘못 붙었는지 가릴 재료 자체가 없다**(그게 바로 이 지적의 내용이다).

### ⑪ 워커 학생 상한의 정본이 둘이다 → **채택** 🔑 이 판정에서 가장 싼 수리

| 곳 | 값 |
|---|---|
| `lib/생성상수.js:30` | `워커학생상한 = Math.min( … )` — **파생 식** |
| `L0_스키마.sql:12360` | `상한 constant int := 3;` — **박힌 수** |

SQL 주석은 스스로 **「150÷생성타임아웃 파생 · 판지문 재료 5」**라 적어 두고 그 파생 결과를 손으로 박았다.
⇒ 생성 타임아웃을 고치면 JS 는 다시 계산하고 DB 는 그대로다. **어긋남이 양방향으로 다르게 아프다**:
JS 가 더 작으면 DB 가 조용히 더 허용하고, JS 가 더 크면 `jobs_claim` 이 **예외를 던져 워커가 죽는다.**

**처방**: 상한을 **DB 한 곳**이 쥐고 JS 가 읽어 가거나(설정 테이블 한 줄), 반대로 JS 가 인자로 주고
DB 는 「받은 값이 자기 상한 이하인가」만 본다. 지금은 **둘 다 스스로 진리라고 믿는다.**

### ⑱ ⑦ 목표 활용의 통과선이 두 곳이다 → **채택**

- :4072·:4091·:4155 — 채점표 **v2**(유호 확정 08-25): 「⑦은 통과선이 없다 — **구간 3~10건**」.
  게다가 :4155 는 **「「비율 ≥ 선」 표에 ⑦을 두면 그 표가…」**라고 경고까지 적었다.
- :4773 — 그 경고가 가리키는 표에 **`⑦ ≥ 0.7` 이 그대로 살아 있다.**

**처방**: :4773 표에서 ⑦을 빼고 「⑦은 구간 축 — §8-B v2」 한 줄로 대체. **문서 안에서 끝난다.**

### ⑨ cron 잡 수가 3과 4로 갈린다 → **채택(문면)**

:3128 판 지문 재료 9 = 「cron 배선(**3잡**의 주기·시각)」 ↔ :1886·:5443 = 「cron **4잡**」.
지문 재료가 실제 배선보다 하나 적으면 **그 하나를 바꿔도 판이 안 올라간다** — 같은 `policy_ver`
아래 다른 입력이 쌓인다. 심문이 든 나머지(활성 함수·오케스트레이터 코드가 재료에 없다)는
**안 재봤다** → 조건부.

### ⑰ 「현재 보드 상태」가 두 개다 → **채택(문면)**

§6-0 H3(:3488) = 「`lib/성과회수.js` 는 `skill_ids` 를 **0회** 읽는다 … 지금 상태는 **`✗✗✗`**」
↔ §16-1(:5392) = 「**#7 엔진 소비자 ✅**」.
🔑 **이 문서는 같은 병을 한 번 앓고 기록까지 해 뒀다** — :3490 이 「이 산문만 `✓✓✗` 로 남아 바로
아래 표(`✗✗✗`)와 **한 절 안에서 갈려 있었다**」고 적었다. 고친 뒤 **다른 절에서 다시 갈렸다.**
⇒ 처방이 「이번 자리를 고치기」였기 때문이다. **상태 칸의 정본을 한 곳으로 못박지 않으면 계속 난다.**

## 5. 조건부 18건 — 재는 자리를 못 박는다

**「안 재봤다」이지 「없다」가 아니다.** 묶어서 적는다(자리가 겹친다).

| 지적 | 재는 자리 |
|---|---|
| ② draft 있는 `적재실패` 마감처리 · ③ draft 없는 `적재실패` 영구 고착 · ⑬ 구제 `snapshot_as_of` 원천 | `L0_스키마.sql` 의 `jobs_finalize_due`(마감 스윕) · `jobs_load_one` 본문 전량 + `deliver` 의 폴백 갈래 |
| ⑤ `task_snapshot` 내부 계약 · ⑭ 생성 입력↔draft 계보 결속 | `jobs_finalize` 본문(무엇을 무엇과 비교하는지) + `lib/과제검문.js` |
| ⑥ `jobs_load` 오류가 롤백인가 격리인가 | `jobs_load` 본문의 예외 처리 + RPC 반환표 대조 — **이 하나는 정본이 갈리면 학급 전체가 지워질 수 있다(조건부 중 제일 무겁다)** |
| ⑦ 00:00 워커 vs B3 재호출 vs 00:05 cron | 등록된 cron SQL + `deliver` 오케스트레이터 B3 갈래 · 리허설에서 00:00~00:10 실행 로그 |
| ⑧ 최신 완주 run 한 행에 날짜 분모와 실행 값이 섞인다 | `generation_batch_runs` 열 의미 + 감시 질의 + §12-8 |
| ⑩ 모델 미설정이 실패 사건조차 안 남긴다 | `deliver` 오케스트레이터의 `GENERATION_MODEL` 갈래 — **키없음 폴백 행이 실제로 나는지** |
| ⑫ 워커 상한 밖의 나머지 판 지문 재료(활성 함수·오케스트레이터) | `lib/판독기.js` 재료 13종 목록 vs 실제 배선 전수 |
| ⑮ 평가 게이트가 학생 접점을 못 막는다 | `prompts/과제생성.md` 배포 경로에 실행 게이트가 있는지 |
| ⑯ 구앱·신앱 식별 조건 · ⑲ `assignment_status`↔`data` 정합 | `supabase/functions/tasks/index.ts` 응답 조립 + 앱 소비부 |
| ⑳ 재방문 부모 사건 둘 · ㉑ 성과회수 운영 공급자 | `lib/성과회수.js` 전문 + `content.viewed` 생산자 |
| ㉒ ⑧ 상태 활용 채점 기준 공백 · ㉓ 「상태 기반」 이름과 실제 선택의 괴리 | §8-B 채점표 + `lib/기술선택.js`(회전이 상태를 안 읽는 것은 **확정**이다 — 세층합류 §2 오해 ①) |
| ㉔ 롤백 절차 · P2 판 지문 폭 | §12-27 + `policy_ver` 재계산 비용 실측 |

🔑 **㉓ 은 한 줄 미리 답한다** — 「상태를 읽어 짓는다」가 **과제 «겨냥 문법»에는 지금 거짓**인 것이

세층합류 §2 오해 ①이 같은 자리를 이미 못박았다. **다만 문서 제목이 「상태 기반 과제 선택」인 채로
그 사실이 §6-0 깊숙이 있는 것은 사실**이라, 제목 곁에 한 줄이 필요하다.

## 6. 🔴 유호님 자리 하나

**이 문서를 쪼갤 것인가.**

- **왜 올리나**: 확인된 여섯 중 넷이 «문서가 자기와 어긋난 것»이고, 문서는 654KB · v5.13 이다.
  지적을 하나씩 기우면 655KB 가 되고 다음 심문은 또 내부 모순부터 집는다. **수리 방식 자체가
  결함을 만들고 있다.**
- **왜 내가 못 정하나**: 쪼개는 선(무엇이 정본이고 무엇이 파생인가)은 **방향 결정**이다.
  그리고 이 문서는 지금 **착수 직전**이라, 쪼개는 동안 착수가 멈춘다 — 그 맞바꿈은 유호님 몫이다.
- **내가 준비해 둘 것**: 유호님이 「쪼개」라고 하시면 그 자리에서 후보 선을 낸다(지금 쪼개기 전에
  선을 그려 두면 그것도 낡을 자리라 안 만든다).

**그때까지 이 판정이 하는 일**: §3의 여섯 중 **문면 셋(⑨⑰⑱)은 지금 고친다** — 문서 안에서
끝나고 착수를 안 막는다. **실물 셋(①④⑪)은 처방까지 적어 두되 손대지 않는다** — 셋 다
`jobs_load`·`jobs_finalize` 본문을 먼저 읽어야 안전하고, 그 독해는 착수 커밋의 몫이다.
