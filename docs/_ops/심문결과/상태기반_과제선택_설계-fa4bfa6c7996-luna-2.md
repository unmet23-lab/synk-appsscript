지적 13건.

- [P0] `batch_run_id` 전량 채움이 DDL로 보장되지 않는다 — `generation_jobs.batch_run_id`가 `NULL` 허용이고 복합 FK도 `MATCH SIMPLE`이다. 구제·재적재 어느 경로든 null job이 저장될 수 있어, “모든 job이 자기 실행을 가리킨다”는 계보 계약이 거짓 초록이 된다(§3-5-b DDL, §14-16-1).

- [P0] 최신 미완주 실행을 감시가 놓친다 — 감시가 “최신 완주 run”만 읽도록 되어 있다. 이전 run은 완주했고 새 run이 시작 후 죽으면, 새 run의 `finished_at IS NULL` 사고가 이전 완주 run 때문에 정상처럼 보인다(§3-2-a ②, §3-5-b `generation_batch_runs` 정본 실행 규칙).

- [P0] 재실행 run의 실행판과 실제 job 실행판이 갈린다 — 재실행은 새 `batch_runs` 행을 만들지만 기존 job은 `batch_run_id`를 그대로 둔다. 새 run이 최신 완주 run으로 선택되면 보고서는 새 모델·정책판을 읽고, 실제 학생 job은 옛 판을 사용한 것으로 기록된다(§3-5-b A1, `jobs_load` 기존 행 무변경 규칙).

- [P0] 롤백 금지가 상위 정본과 정면 충돌한다 — §12-27은 빈 DB 재적용을 롤백의 갈음으로 선언하지만, 분업 인계문과 L0 계약은 빈 DB·중간 실패·롤백 경로 검증을 요구한다. “개원 전 한정”이라는 문구는 상위 계약의 필수 검증을 면제할 권한이 없다(§12-21·§12-27).

- [P0] job 증거의 불변성이 물리적으로 닫히지 않았다 — `branch_snapshot`, 실행판, `event_draft`를 사실상 불변이라고 선언하지만 `generation_jobs`에 직접 `UPDATE`·`DELETE` 차단이 없다. `generation_attempts`에만 권한 차단을 둔 상태라, 핵심 선판정 스냅샷은 RPC 밖에서 변조될 수 있다(§3-5-b DDL, §6-0 H2).

- [P0] attempts append-only도 완성되지 않았다 — `UPDATE`·`DELETE`만 revoke하고 직접 `INSERT` 경로와 삽입 권한을 닫지 않았다. 게다가 `result text check (result in (...))`는 PostgreSQL의 3값 논리상 `NULL`을 거절하지 않으므로, RPC를 우회하면 열린 행·허용되지 않은 gate 배열이 저장될 수 있다(§3-5-b attempts DDL).

- [P0] `잘림`의 원래 개수가 영속 스냅샷에 남지 않는다 — 문서는 원래 개수를 상류 `학습자상태` 객체가 가진다고 하지만 그 객체를 DB에 저장하지 않는다. `evidence_refs`에는 `truncated`만 있고, 요약 문자열에도 원래 개수를 반드시 넣는 계약이 없다. 코드판이 바뀐 뒤 “50개로 잘린 것”과 “애초 50개였던 것”을 구분할 수 없다(§6-1, §6-2).

- [P0] `engine.skills`가 비었을 때 실행 경로가 닫히지 않는다 — §6-0은 빈 배열을 “시드가 깨진 상태”라고 정의하지만, 대상 job은 `skill_ids` 1~2개가 필요하다. `적재실패`로 내릴지 `내부오류`로 닫을지, `load_error`와 어떤 상태 전이를 할지가 명시되지 않아 첫 생성 대상에서 DDL 거절 또는 구현자 임의 처리가 발생한다(§6-0, §3-5-b `jobs_skill_ids_present`).

- [P1] roster hash와 `level_distribution`의 정본 직렬화가 없다 — 학생 ID 정렬과 SHA-256만 적고 UTF-8, 구분자, 중복 처리, JSON 키·값 구조를 닫지 않았다. 같은 명단이 구현자마다 다른 hash를 낼 수 있고, malformed한 급수 분포가 `batch_run_start`를 통과할 수 있다(§3-5-b `batch_run_start`, §8-B E8).

- [P1] 구제 경로의 run 명단 범위가 정의되지 않았다 — `/tasks` 구제는 학생 1명 단위인데 `batch_run_start`는 전체 재적 명단·급수 분포·roster hash를 요구한다. 구제 호출이 한 학생만 넣으면 배치 등식과 감시 분모가 왜곡되고, 전체 명단을 읽는다면 그 조회·시점·동시성 계약이 비어 있다(§3-1, §3-5-b ⓪·㉨).

- [P0] 첫 생성 행 전 필수 선행물이 아직 실제 산출물로 존재하지 않는다 — c12 개정·policy reader·현재 `quality_ver` 평가 결과가 모두 §16-1의 필수 조건인데, 문서 자체가 policy reader 실물 0과 평가 결과 0을 인정한다. 따라서 이 문서는 “동결 후보”가 아니라 첫 append를 금지하는 미완성 선행계약이다(§11-2, §16-1 #1·#5·#6).

- [P1] `policy_ver` 산출은 실행 가능한 생산자 계약이 아니다 — JS 파일 해시, DB 함수 본문, cron 실물을 한 값으로 묶으라고 하지만 어느 층이 무엇을 어떻게 읽고 직렬화하는지 정의하지 않았다. 배포된 Edge Function은 저장소 전체를 자동으로 읽지 못하므로, 첫 job에 들어갈 판 값부터 구현자별로 달라질 수 있다(§5-1, §16-1 #5).

- [P1] 목표 활용과 목표 도움을 혼동한다 — §8-B ⑦은 출력이 목표 맥락을 “사용했는가”만 채점한다. 그 목표에 실제로 도움이 되는 한국어인지, 학생이 말하거나 쓰게 되는지는 측정하지 않는다. 판단 정본의 “그 학생의 목표에 도움이 되는가” 게이트가 문맥 삽입 여부로 축소됐다(§8-A, §8-B ⑦).

- [P1] `생성중`·`오류`의 학생 경험은 사실상 미완성이다 — 새 앱 어댑터는 상태를 다르게 그려야 하지만 실제 문구는 다른 트랙으로 미루고, 현재 인수 조건은 문구가 비어 있지 않은지만 본다. 어떤 문구든 통과할 수 있어 학생에게 “기다려야 하는지, 실패한 것인지”를 재미·신선함·도움의 기본 게이트로 검증하지 못한다(§3-1, §12-11, §14-5).

이 문서보다 나은 대안 구조는 1개다: `batch_runs`를 불변 실행 매니페스트 부모로 만들고 `jobs.batch_run_id NOT NULL` 복합 FK를 강제한다. 감시는 “최신 완주”가 아니라 최신 시작 run의 완주 여부를 먼저 판정하고, jobs·attempts·run 모두 RPC 외 직접 쓰기를 차단한 뒤 c12·policy reader·quality 결과를 첫 생성 전 단일 preflight에서 막아야 한다.
