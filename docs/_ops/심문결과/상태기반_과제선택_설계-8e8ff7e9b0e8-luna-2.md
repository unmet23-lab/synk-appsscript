아래는 문서 전문 내부 대조만으로 확인되는 결함이다.

[P0] 불변 트리거가 적재실패 복구를 스스로 차단한다 — §3-5-b의 `generation_jobs_freeze()`는 `branch_snapshot`, `event_draft`, `snapshot_as_of`, `batch_run_id` 변경을 모두 거부한다. 그런데 같은 절의 `적재실패 → 대기` 복구 규칙은 이 네 칸과 `skill_ids`·실행판을 새 값으로 갱신하라고 한다. 복구 RPC는 항상 트리거에서 실패하고, 학생은 적재실패에 고착된다.

[P0] 비대상 오염 행이 생성 대상으로 통과한다 — `jobs_nontarget_cols`는 `status='대상아님'`일 때만 사유를 요구하고 역방향을 금지하지 않는다. 따라서 `status='대기' + not_target_reason` 행은 `jobs_skill_ids_present`의 면제를 받고, `jobs_claim`도 사유를 읽지 않아 생성 워커가 집는다. §12-21은 사후 탐지만 할 뿐, 학생에게 잘못된 과제를 내는 것을 막지 못한다.

[P0] 구제 경로가 배치가 전혀 없던 날에 실행 불능이다 — §3-5-b의 `batch_run_start(_run_kind='구제')`는 그 날짜의 정본 배치 실행에서 명단과 판을 복사해야 하며, 정본이 없으면 예외다. 반면 §3-1과 v5.8 처분은 바로 “배치 시작 행이 없는 날”을 구제해야 한다고 한다. 가장 필요한 전멸 복구 경로가 `실행없음`으로 끝나 `task.assigned`조차 남기지 못한다.

[P0] 동시 오케스트레이터가 서로 다른 실행판을 정상 완료로 만든다 — `batch_run_start`는 항상 새 행을 만들고 날짜별 실행 리더 잠금이 없다. 두 `deliver`가 동시에 돌면 한 실행이 job을 만들고 다른 실행은 유일키 충돌을 `existing`으로 세어 완주할 수 있으며, job은 첫 실행을 가리키는데 감시의 “최신 완주 실행”은 두 번째 실행을 읽는다. `snapshot_as_of`, `policy_ver`, roster가 달라도 배포 갈림으로 차단되지 않는다(§3-2-a ②-a·②-b, §3-5-b ④).

[P1] 적재 실패 재호출에 배치 단위 상한이 없다 — `jobs_load`가 roster hash·draft·판 검증에서 롤백되면 `generation_jobs`는 0행이고 실행 행은 `finished_at=null`로 남는다. `generate-worker`는 job 0 + 미완 실행이면 오케스트레이터를 다시 부르므로, 같은 결정적 오류가 36회까지 새 `batch_runs`를 만든다. `load_retry_count`는 학생별 `적재실패`에만 적용되어 이 실패 루프를 제한하지 않는다.

[P0] 상태 스냅샷과 실제 생성 입력의 동일성이 선언뿐이다 — §6-1은 `event_draft`의 상태 메타를 정본으로 삼지만, §3-5-b 봉투 표에서는 `estimator_confidence`, `evidence_refs`, `retry_of_event_id`, payload를 호출자가 넘긴다. `jobs_finalize`가 검사하는 것은 버전·as_of·근거 사건 일부이며, draft와 `evidence_refs` 전체·상태 요약 원문의 동일성을 강제하지 않는다. 다른 상태 요약으로 생성하고도 정상 사건을 남길 수 있다.

[P0] `policy_ver`·`quality_ver` 지문 규격이 실행 불가능하게 갈린다 — §5-1은 13개 재료를 full SHA-256으로 직렬화한다고 하지만, 같은 절은 기존 테스트의 `JSON.stringify` 3값과 SHA-256 앞 16자를 정본으로 지목한다. 이어서 값 형식은 `오늘과제.v4+<해시12>`로 적혀 있다. 첫 생성 행이 어느 지문을 사용했는지 구현자가 결정하게 되며, append-only 사건의 판 계보를 재현할 수 없다.

[P0] fallback 원본 `event_draft`의 구조가 기계 계약으로 닫히지 않았다 — §3-5-b는 `event_draft`가 필수라고만 물리화하고, 내부 모양은 §7의 주석·기존 조립기 참조로 남긴다. `호흡[]`의 ③행 존재, 선택지 키 생략, 날짜·학생 결속, 필수 메타의 전량 검사는 문서상 목록이지 독립 JSON 계약이 아니다. 마감 스윕에서 처음 malformed draft가 드러나면 학생에게 fallback을 내지 못하고, 소급 복구도 없다.

[P0] 엔진 완결 `✗✗✗`인데 첫 생성 행을 막는 조건에는 없다 — §6-0 H3와 §12-17은 `skill_ids`의 소비자가 0줄이고, `error_tags`도 비어 있으며, `늘었나`가 ✗라고 명시한다. 그런데 §16-1의 첫 생성 전 필수 조건은 c12·ingested cutoff·판독기·평가 결과뿐이고, 이 엔진 소비자 조건은 없다. 저장·배선 문서만 남기고 “나중에 쓸 수 있는 모양”을 첫 학생 데이터로 굳히는 구조다.

[P1] `level_distribution`이 평가 게이트의 거짓 입력을 허용한다 — DDL은 `Lv1~Lv6`·`null` 키가 존재하는지만 검사하고 값의 정수성·음수·합계가 `enrolled_count`와 같은지는 검사하지 않는다. §8-B E8은 이 값을 사용해 시험지 표본과 재채점 여부를 결정하므로, 잘못된 분포도 정상 실행판으로 저장될 수 있다. roster 등식은 학생 수만 검증할 뿐 분포 내용은 검증하지 않는다.

[P0] 출시 차단이 실제 배포 경로를 차단하지 않는다 — §8-B는 평가 결과가 없으면 생성 경로를 막는다고 서술하지만, §12-19는 실제 실행을 로컬 `node tools/test-ci.js`에 의존하고 GitHub Actions는 정지 중이며 수동 경로는 기계적으로 막지 못한다고 인정한다. 따라서 `prompts/과제생성.md`만 존재하고 평가 결과가 없는 상태에서 수동 배포가 가능하다. “게이트가 있다”와 “학생에게 열리지 않는다”가 같은 문장 안에서 분리되지 않았다.

[P1] 구앱은 생성 중 과제를 ‘없음’으로 오인한다 — §3-1의 호환 규칙은 `assignment_status`를 모르는 앱이 `data`만 보고 있음/없음으로 그리게 한다. 생성 중인 학생은 실제로 곧 과제가 생겨도 빈 과제로 읽고 닫을 수 있으며, 알림·재시도·대체 행동이 없다. 사고 시나리오가 좁다는 설명은 이 학생 경험을 제거하지 않는다.

[P1] 학생이 왜 다시 열어야 하는지에 대한 설계가 없다 — §8-B는 재방문 이유를 범위 밖으로 밀고, §12-29는 ③행·꼬리·효과음의 배선만 검사한다. 같은 통로를 탔다는 사실은 학생이 다시 열 이유가 아니다. 재미·실사용 도움·신선함 중 학생의 실제 재방문으로 이어지는 층이 생성 과제에 연결되지 않은 채 첫 시즌 회고까지 미뤄져 있다.

[P1] 기능 도달률 0을 보고만 하고 막지 않는다 — §7-1은 Lv1·Lv2·미정 학생을 모두 생성 대상에서 제외하고, §12-8은 대상아님 100%가 7일 지속되면 별건을 연다고만 한다. 개원 초기 학생 구성이 초급이면 이 기능은 학생에게 한 번도 닿지 않을 수 있는데, 그 상태에서도 기술 구현·평가 게이트만 충족하면 기능 완성처럼 진행된다. 실사용 도움의 실패를 운영 보고로 대체한 것이다.

[P1] 적재실패는 마감 후 자동 종결되지 않는다 — `jobs_claim`과 `jobs_finalize_due`는 `적재실패`를 집지 않고, 자동 재적재는 마감 전으로 한정된다. 마감 뒤에는 학생이 `/tasks`를 열어야 구제가 발동한다. 학생이 열지 않으면 그 날짜의 배정·개입 증거가 영원히 없고, 시스템은 적색을 기록할 뿐 복구하지 않는다.

[P2] 품질 지문이 무관한 변경까지 사람 평가를 강제한다 — `quality_ver`가 `과제검문.js`·`과제생성.js` 파일 전체 해시라 주석·리팩터도 새 판으로 취급된다. §8-B는 그때마다 40사례×2회차의 사람 채점을 요구한다. 문서가 이 비용을 “안전한 실패”라고 부르지만, 실제 운영에서는 평가 우회가 더 빠른 통로가 될 위험을 스스로 만든다.

대안 구조 1개: `generation_jobs`를 불변인 “생성 의도·draft·스냅샷”과 가변인 “큐 상태·재시도 상태”로 분리하고, 복구는 기존 불변 행을 수정하지 않고 새 실행 세대가 이전 의도를 참조하게 해야 한다. 동시에 날짜별 배치 실행은 하나의 리더만 만들도록 닫고, `jobs_finalize`는 그 불변 의도와 현재 claim 세대만 소비하게 해야 한다.
