판정: 동결 불가.

1. [P0] L0 필드명 규칙을 정면으로 어긴다 — §4-1·§6·§11은 물리 payload 키로 `출처`·`생성결과`·`생성입력`·`배정판`·`적용비율` 등 한글 이름을 적는다. 닫힌 M0 규칙은 L0 snake_case가 유일한 필드명이며, 기존 `source_kind`도 다른 뜻으로 존재한다. 생산자와 소비자가 서로 다른 키를 읽는 조용한 분기가 생긴다.

2. [P0] 예약이 멱등성이 아니라 영구 빈자리를 만든다 — §3은 외부 호출 전에 일일 키를 예약하고 기존 행이면 반환한다고 하지만, 예약 상태·lease·재개·실패 복구 규칙이 없다. 예약 직후 프로세스가 죽으면 이후 실행이 빈 예약행을 정상 결과로 반환할 수 있고, 벤더 성공 후 착지 실패도 같은 문제를 만든다. §12-6의 정상 재실행 시험만으로는 이 사고를 검출하지 못한다.

3. [P0] `task_snapshot` 위치가 분모와 모순된다 — §7은 스냅샷의 물리 위치를 `engine.submissions`로 못박지만 §9·§12는 `task.assigned`를 미제출 분모로 사용한다. 제출하지 않은 학생에게는 `submissions` 행이 없으므로 실제 배정된 문장을 복원할 수 없다. 배정 payload와 제출 스냅샷 사이의 불변 링크·해시도 정의되지 않았다.

4. [P0] 배정·전달·관측·제출의 학습 고리가 끊겨 있다 — §4-1과 §11은 생성 메타데이터를 `task.assigned`에 싣지만, 코어엔진의 실제 개입 사건은 `intervention.delivered`이고 관측은 `content.viewed`다. 동일한 `intervention_id`·`correlation_id`로 이 네 사건을 잇는 규칙이 없다. 따라서 `쓴축`을 남겨도 어떤 생성 개입이 어떤 반응과 성과를 냈는지 조인할 수 없다.

5. [P0] 모델 입력 스냅샷이 실제 요청 전체가 아니다 — §6은 요약문·축값·산출판·시점만 저장한다. 렌더링된 전체 프롬프트, 변수 직렬화, 시스템 지시, 생성 파라미터와 응답 스키마는 보존되지 않으며 `prompt_ver`만으로 복원할 수 없다. 같은 판이라도 실제 모델 입력이 달라진 행을 사후에 구분할 수 없다.

6. [P0] `as_of`가 기준 시각이 아니라 사후 라벨이다 — §3·§6은 `오늘`·`전날`·일일 키의 시간대와 상태 계산의 데이터 cutoff를 닫지 않았다. 늦게 들어온 사건이나 동시 배치에 따라 같은 학생·같은 날짜가 다른 상태로 계산될 수 있다. 행에 `as_of`만 남기는 것은 어떤 사건 집합을 읽었는지 보장하지 않는다.

7. [P0] 타임아웃 예산이 구현자 재량이다 — §3-2가 학생별·배치 전체 예산의 초기값을 “첫 배치에서 재고 정한다”고 남긴다. 단조 시계, 예산 시작점, 취소가 실제로 끝나는 지점, DB 시간 포함 여부와 예산판이 없다. 순차 루프에서 외부 호출이 멈추면 뒤 학생도 계속된다는 보장이 없다.

8. [P0] 폴백 문장과 스냅샷 부속물이 갈라질 수 있다 — §4는 `전날문장`만 재사용한다고 쓰지만 §7의 스냅샷은 프롬프트·선택지·선택차원·`task_format`까지 포함한다. 이전 전체 스냅샷을 복사하는지, 부속물을 새로 조립하는지 정의되지 않았다. 문장과 질문이 서로 다른 과제가 되어도 정상 행으로 저장된다.

9. [P1] 실패 사유 enum이 실제로 닫혀 있지 않다 — §4-1의 `검문탈락`은 어느 항목인지 함께 남긴다고 하지만 그 하위값의 필드명·타입·허용값이 없다. `상태없음`도 빈 상태와 계산 예외를 합치며, `벤더오류`도 응답 오류와 형식 파손을 합친다. 인수 조건은 상위 enum만 검사하므로 오분류가 초록으로 남는다.

10. [P1] JSON 실행 계약이 없다 — §4-2의 “JSON 고정”과 §7의 “문장 1개+질문 1개”만으로는 속성명·자료형·추가 키·누락 키·파싱 실패 규칙이 정해지지 않는다. 파서 판을 `prompt_ver`에 포함한다고 해도 어떤 JSON을 유효로 보는지는 닫히지 않는다. 서로 다른 구현이 같은 판을 찍을 수 있다.

11. [P1] 검문표가 여전히 실행 규격이 아니다 — §8은 `말하기_설계 §6`의 상한과 “질문으로 끝나는가”를 참조하지만 하한값, 한글 코드포인트 범위, 질문 판정식, 금칙 서식의 정확한 패턴을 제시하지 않는다. ±1 경계 픽스처만으로는 정규화·혼합문자·표현식 차이를 잡지 못한다.

12. [P1] 판지문은 선언이지 강제가 아니다 — §5는 프롬프트·요약·검문·폴백을 해시한다고 하지만 해시 알고리즘·바이트 정규화·자동 판올림 훅이 없다. 네 가지 선택적 픽스처를 통과한 뒤에도 구현자가 코드를 바꾸고 `policy_ver`를 유지할 수 있다. 그러면 §5-4의 `degraded` 의미 전환도 행 단위로 신뢰할 수 없다.

13. [P1] 낮은 신뢰 상태가 개인화 성공으로 위장한다 — §4-3은 상태가 없거나 예외일 때만 폴백시키고, §6의 `estimator_confidence`는 표본 충분도라고만 한다. 빈 축·0값·부분 상태·낮은 표본을 유효 상태로 볼 기준이 없어 `생성결과=성공`, `degraded=false`가 찍힐 수 있다. 상태 기반 입력 실패와 정상 생성이 같은 모양이 된다.

14. [P1] arm은 배정이지 노출·처치 기록이 아니다 — §9의 `arm`, `생성결과`, `content.viewed`, 실제 제출 사이의 분석 연결 규칙이 없다. 기간 버킷의 기준점·갱신 시점·정책판 변경 시 처리와 `적용비율`이 설정 비율인지 실제 비율인지도 비어 있다. 같은 `arm=생성` 행이 실제 생성 성공·키 없음·미열람을 모두 포함할 수 있다.

15. [P1] 키 없음 인수 조건이 전체 흐름과 모순된다 — §12-2는 전원이 `키없음`이어야 한다고 하지만 §1·§4에 따르면 게임·첫날·교정문은 `대상아님`이고 벤더를 호출하지 않는다. 생성 대상만 넣은 픽스처라면 전역 우선순위를 검증하지 못하고, 전체 학생을 넣으면 조건 자체가 실패한다.

16. [P1] 오프라인·앱 재시도 규칙이 없다 — §3의 멱등성은 서버 배치 재실행만 다루며, 앱의 캐시된 과제 재조회·중복 제출·오래된 폴백 제출을 정의하지 않는다. `retry_of_event_id`와 생성 과제의 연결도 없다. 네트워크 단절 뒤 제출된 스냅샷이 어느 배정 결과에 속하는지 복원할 수 없다.

17. [P1] `출처`가 세 가지 뜻으로 중복된다 — §7의 `task_snapshot.출처`, §4-1 payload의 `출처`, 기존 계약의 `source_kind`가 함께 등장한다. 문서는 이 세 값의 관계나 불일치 방지 규칙을 정하지 않는다. 소비자가 `생성`을 과제 원천으로 읽어야 할지 사건 출처로 읽어야 할지 갈린다.

18. [P1] 생성 과업의 `task_format`이 닫히지 않았다 — §7은 조립기를 거친다고만 하고 생성분의 `task_type`·`task_format` 값을 정하지 않는다. 문장·질문·초급 선택지가 어느 학습 형식인지 행마다 구현자가 임의로 정할 수 있다. 이후 낭독·응답·자유발화 데이터가 다시 섞인다.

이 문서보다 나은 대안 구조 1개:

`전역 배정판 → 기존 일일 멱등키 예약·확정 → 생성 대상만 호출 → 하나의 불변 결정 봉투 착지` 구조가 낫다. 봉투에 L0 필드명으로 실제 스냅샷·실제 입력·모델/프롬프트/정책·파서 판·결과·실패 사유·`intervention_id`·`correlation_id`·arm을 함께 고정하고, 제출·관측·성과는 같은 ID를 참조해야 한다. Re-run은 확정된 봉투만 반환해야 한다.
