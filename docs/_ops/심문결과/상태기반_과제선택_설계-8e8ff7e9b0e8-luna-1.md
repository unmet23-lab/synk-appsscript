지적 11건.

- [P0] 마이그레이션이 빈 DB에서 즉시 실패한다 — §3-5-b DDL은 `generation_batch_runs`를 생성하기 전에 `ALTER TABLE engine.generation_batch_runs`와 `REVOKE`를 실행한다(§3-5-b, `docs/상태기반_과제선택_설계.md:1331~1377`). §12-21은 빈 DB 전량 적용을 필수로 하지만, 이 순서에서는 테이블 미존재 오류로 RPC·cron까지 도달하지 못한다.

- [P0] `적재실패` 자동 재적재가 불변 트리거에 막힌다 — `generation_jobs_freeze`는 `branch_snapshot`, `event_draft`, `snapshot_as_of`, `batch_run_id` 변경을 거부한다(§3-5-b). 그런데 `적재실패 → 대기` 재적재는 바로 이 네 칸을 새 실행값으로 갱신하도록 요구한다(§3-5-b ㉠·㉨, §3-2-a). 첫 조립 실패가 발생하면 `load_retry_count`만 증가하고 실제 복구는 영원히 실패한다.

- [P0] 배치 전멸 구제의 두 계약이 정면으로 충돌한다 — §12-11과 §3-1은 job 0건이어도 `jobs_load_one`으로 학생별 폴백을 착지한다고 한다. 하지만 §3-5-b ④와 `batch_run_start`는 그날 정본 배치 실행 행이 없으면 구제 run을 거절하고 학생을 라이브 폴백으로 돌린다. 바로 “배치가 아예 돌지 않은 날”에 `task.assigned`와 `intervention.delivered`가 영구 누락된다.

- [P0] 추정 상태의 필수 시간·확인 메타가 사라진다 — 후보 문서의 사건 봉투는 `estimator_confidence`, `evidence_refs`, `estimator_version`만 싣고 `valid_from`, `expires_at`, `user_confirmed`를 싣지 않는다(§0-3, §3-5-b, §11-2). 그러나 `docs/코어엔진_설계.md:172·236`과 `계약/수집_교정_계약.json`은 추정 메타 7종을 요구한다. 첫 생성 사건부터 추정의 만료·학생 확인 여부를 복구할 수 없어 학습자 모델이 추정을 사실처럼 누적한다.

- [P0] 첫 학생의 재방문 증거를 아직 정의하지 않았다 — §16-1은 재방문을 “같은 배정을 다시 연 사건의 횟수·간격”으로 기록해야 한다고 하면서, 바로 다음 줄에서 어떤 기존 `learning_events` 사건을 쓸지 구현 시점에 정한다고 미룬다. 첫 학생이 오기 전에 열람 사건의 종류와 배정 연결 필드를 확정하지 않으면 첫 재방문은 사후에 식별·복원할 수 없다(§16-1, §12-17).

- [P0] 과거 `적재실패`가 자동 감시와 복구에서 빠진다 — §3-2-a 감시 ⑤는 과거 날짜에서 `대기·claimed`만 세고 `적재실패`는 제외한다. `jobs_finalize_due`도 `대기·claimed`만 닫으며, `적재실패` 재적재 방아쇠는 마감 전으로 제한되어 있다(§3-2-a, §3-5-b ㉧). 마감 직전 실패한 행은 다음 날부터 감시되지 않고 이벤트도 없이 영구 고아가 된다.

- [P1] 실행 장부의 핵심 계보가 물리적으로 불변이 아니다 — 문서는 `batch_runs`의 `snapshot_as_of`, 실행판 여섯, 명단 스냅샷을 원천 계보로 쓰지만 `batch_runs`에는 불변 트리거나 변경 회수 장치가 없다(§3-5-b ④). `finished_cols`는 숫자가 채워졌는지만 검사한다. 실행 후 원천 행이 바뀌면 기존 job과 run의 판이 달라져 감시·재현·성과 귀속이 모두 거짓이 된다.

- [P0] `input_hash`의 대상 바이트가 한 문서 안에서 두 개다 — §8-B 결과 구조는 `generation_input_text`를 “요약 문자열”로 해시한다고 적고, 같은 절의 실행 규격은 “렌더된 요청 본문 전체”라고 적는다(§8-B, §12-21 ③). 이 상태에서는 프롬프트 템플릿 변경이 옛 평가 결과와 불일치할 수도, 조용히 옛 초록을 재사용할 수도 있어 첫 생성 품질 게이트의 증거가 성립하지 않는다.

- [P1] `degraded`의 생산자가 아직 단일하지 않다 — §3-5-b는 함수가 모드로 `degraded`를 결정한다고 하지만, `event_draft`에는 오케스트레이터가 그 값을 굳힌다고 적혀 있고 `_event` 예시는 호출 봉투가 `"degraded": true`를 직접 싣는다(§3-5-b, §11-1). 함수값·draft값·호출값 중 무엇이 최종 권위인지 명시되지 않아 폴백이 성공 또는 장애로 잘못 분류될 수 있다.

- [P1] `level_distribution` 물리 제약이 이름만 검증한다 — DDL은 `Lv1~Lv6`와 `null` 키가 존재하는지만 검사하고, 값의 자료형·정수성·음수·합계·미지 키를 제한하지 않는다(§3-5-b ④). 그러나 §8-B E8은 이 값을 비율과 표본 수 계산에 직접 사용한다. malformed JSON 한 건이 시험지 표본을 조용히 왜곡하거나 런타임 계산을 깨뜨릴 수 있다.

- [P1] 학생 화면이 생성 상태를 사실과 다르게 보여줄 수 있다 — §3-1은 구앱이 `assignment_status`를 무시하고 `data`만 읽어 `생성중`을 `없음`처럼 표시하도록 한다(§3-1). 신앱도 §12-11에서는 문구가 비어 있지 않은지만 검사하고, “기다려야 하는지 실패한 것인지 이해하는가”는 다른 트랙으로 넘긴다(§12-11, §14 B12). 학생은 과제가 곧 생기는 상황에서 없다고 판단하거나, 오류 상태에서 의미 없는 문구를 볼 수 있어 기본 게이트의 실사용 도움을 통과했다고 할 수 없다.

이 문서보다 나은 대안 구조는 1개다: `batch_runs`와 최초 `generation_jobs`는 불변 매니페스트로 고정하고, 재적재는 기존 job의 스냅샷을 수정하지 않고 새 실행 버전을 자식 행으로 만든다. 모든 이벤트는 승자 실행 버전을 가리키게 하며, 마이그레이션은 테이블 생성 → 제약·트리거 → 권한 → RPC → cron 순서로 고정한다.
