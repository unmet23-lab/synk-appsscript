동결 불가 — 지적 25건.

1. [P0] 실행 장부의 정본이 둘이다 — §3-5는 `generation_claims`를 정본으로 쓰고, §3-5-b는 이를 폐기해 `generation_jobs`·`generation_attempts`로 나눈다. 그런데 §3-6·§12-13은 여전히 `시도`·`landed`·`포기`·`generation_claims`를 전제로 한다. 구현자와 회귀가 서로 다른 상태기계를 보게 된다.

2. [P0] 시도 장부가 자기 규칙상 기록될 수 없다 — §3-5-b는 `generation_attempts`를 append-only·갱신 금지로 정의하지만, 요청 전 삽입한 행의 `원응답`·`결과`·`응답시각`은 호출 뒤 갱신해야 한다. 세 RPC에도 시도 시작·응답 기록 함수가 없다. 호출 직후 프로세스가 죽으면 §3-6이 보장한다는 원문 보존이 사라진다.

3. [P0] lease 회수가 펜싱을 되살린다 — §3-5는 회수 때 토큰을 올리라고 하지만 §3-5-b 전이표는 `claimed → 대기`에서 펜싱을 올리지 않는다. `임대만료`와 본문에서 말하는 24시간 회수의 관계도 없다. 같은 토큰을 든 낡은 워커가 새 워커보다 먼저 `job_종료`를 성공시킬 창이 남는다.

4. [P0] `/tasks` 구제 경로가 동시 실행 중 빈 화면을 만든다 — §3-1은 워커가 `claimed` 상태면 구제가 기존 배정을 재조회한다고 한다. 그러나 claim은 벤더 호출 전이고, 그 순간 `task.assigned`는 아직 없다. 대기·재시도·명시적 pending 응답 규칙이 없어 학생에게 과제가 없거나 구제 오류가 난다.

5. [P0] 큐가 우선순위 입력을 보존하지 않는다 — `generation_jobs`에는 `snapshot_as_of`·`skill_ids`만 있고 첫날 여부, 교정문, 전날 스냅샷, 급수·목표, 게임 판정, 선택 정책이 없다(§3-5-b). 워커가 늦게 이 값을 다시 읽으면 새 교정·게임 승인·급수 변경이 기존 선판정을 덮는다. 결과를 어느 판정으로 냈는지 소급할 수 없다.

6. [P0] `배정일`과 사건 시각의 관계가 비어 있다 — job은 `배정일`을 갖지만 `job_종료`의 `_사건 jsonb`에서 `occurred_at`을 배정일로 쓸지 착지 시각으로 쓸지 정하지 않았다(§3-5-b). 06:00 뒤 착지한 행은 오늘 조회에서 사라지거나 다른 날의 리듬 분모에 들어갈 수 있다. 날짜·마감·성과 창이 모두 달라진다.

7. [P0] 실패값 산술이 틀렸다 — §4-1에는 `generation_outcome` 값이 15개인데 §3-6·§12-7은 14값과 `13 + 응답 1 + 행 0`으로 계산한다. 게다가 job 상태·종료사유에는 `마감폴백`을 쓰면서 enum에는 `예산소진`만 있다. 최소 한 값의 저장 위치와 픽스처가 반드시 갈린다.

8. [P0] `job_종료`는 물리 계약이 아니다 — `_사건 jsonb`의 정확한 구조, 이벤트별 필수 필드, 멱등키, 시각, 스냅샷, 상태 전이 결과가 정의되지 않았다(§3-5-b). `returns uuid`만으로는 stale·duplicate·이미 완료를 구분할 수 없다. “0행·사이드이펙트 0”이라는 §12 조건을 이 시그니처로 검증할 수 없다.

9. [P0] c12가 선언만 있고 계약이 없다 — §11-2는 현재 계약이 c11이고 c12를 먼저 개정하라고 하지만, c12 JSON diff·검증 스키마·마이그레이션·역방향 회귀가 없다. `payload.ver >= 2`만으로는 `intervention.delivered`에만 적용되는지, 호출 시 `generation_input_text`가 필수인지 강제되지 않는다. 첫 생성 행이 조용히 거절되거나 서로 다른 모양으로 저장된다.

10. [P0] `응답초과`의 판정값이 없다 — §4-1에는 `응답초과`가 있지만 응답 상한의 숫자, 바이트/코드포인트/JSON 크기 기준, 측정 시점이 없다. 같은 응답을 구현자마다 성공·파손·초과로 다르게 분류한다. 이 값은 판지문에도 재료로 고정되지 않는다.

11. [P0] 생성 성공이 학생의 ①듣기에 연결되지 않는다 — 현재 `tasks/index.ts`와 `lib/오늘과제.js`에서 ①듣기는 `intervention.delivered.payload.output_text`를 읽는다. 그러나 §7 매핑은 `sentence → 호흡[].문장`, `question → 호흡[].프롬프트`만 정의하고 기존 `output_text`를 어떻게 채울지 말하지 않는다. 생성 성공인데 학생 화면의 첫 듣기 콘텐츠가 비는 경로가 남는다.

12. [P0] 과제 요약 입력이 계약으로 닫히지 않았다 — §6-2는 `과제요약.js`가 정본이라고 하면서 하위 지표, 단위, 반올림, 순서, null 표기를 모두 문서에서 제외한다. `쓸축수`도 요약기가 무엇을 생략했는지에 따라 달라진다. 같은 `policy_ver` 아래 서로 다른 프롬프트가 만들어져 첫 행부터 비교가 불가능하다.

13. [P0] `skill_ids` 생산자는 아직 없다 — §6-0은 “배치가 먼저 고른다”고만 하고 어떤 함수·원자료·매핑·비어 있을 때의 판정을 정의하지 않는다. DDL의 `default '{}'`는 생산 실패와 “기술 없음”을 같은 정상값으로 만든다. §8-B의 기술 연결 채점도 빈 기술 목록으로 회피할 수 있다.

14. [P0] `skill_ids`를 실력 이해로 오인한다 — 해당 값은 생성 전에 고른 개입 의도이지 학생이 실제로 틀린 기술이 아니다(§6-0). 코어엔진의 A-1 ㉠은 관찰된 오류·제출·교정으로 채워야 한다. 사전 가설을 “무엇을 틀리는가”로 저장하면 append-only 원본에 잘못된 약점이 굳는다.

15. [P0] A-1 소비자가 존재하지 않는다 — §6-0은 `skill_ids` 착지가 A-1 ㉠을 채운다고 선언하지만 소비자 파일·질의·갱신 규칙을 하나도 지목하지 않는다. 현재 `docs/이해대장.html`도 “읽은 성향으로 다음 과제를 바꾸는 자리”를 비어 있는 상태로 표시하고, 상태 기반 선택 구현은 0줄이다. 저장을 배선·성장으로 잘못 세는 허위 완결이다.

16. [P0] 상태 판본과 입력 스냅샷이 현재 정본과 갈린다 — 문서 §4-3은 `학습자상태.v7`·9축·30일·근거 200·`잘림` 원래 개수를 말하지만, §6-1은 14일·근거 50·`잘림: true`를 제시한다. 현재 `lib/학습자상태.js` HEAD는 이미 `학습자상태.v9`이며 `탐지`·`강제산출` 축까지 추가되어 있다. 어느 입력으로 생성했는지 행만으로 확정할 수 없다.

17. [P0] `ingested_at` cutoff가 실제 배선으로 고정되지 않았다 — §11-4는 `occurred_at`과 `ingested_at`을 모두 `as_of` 이하로 자르라고 하지만, 현재 `deliver` 질의는 `occurred_at`과 `now()`만 사용한다. 새 job에는 시각 하나만 저장되고 필터 결과나 쿼리 판본은 저장되지 않는다. 늦게 들어온 과거 사건이 재시도 때 상태를 바꿀 수 있다.

18. [P0] 원자 착지가 학습 분모를 숨긴다 — §3-0은 `task.assigned`를 `intervention.delivered`와 동시에 만들도록 하면서 `generation_jobs`는 상태 계산에서 제외한다. 워커가 마감 전 죽으면 다음 상태 계산에는 “과제가 없었던 날”만 남고 “과제가 있었지만 배달 실패한 날”은 사라진다. §12-8의 두 분모 보고는 운영 숫자일 뿐 학습자 모델이 읽는 원본이 아니다.

19. [P1] `degraded`가 의도적 구제와 AI 실패를 합친다 — `/tasks` 구제는 벤더를 일부러 호출하지 않지만 `generation_outcome='구제경로'`다(§3-1). §5-4는 이후 `degraded=true`를 “AI가 오늘 실패했다”로 정의한다. 기존 `degraded` 소비자는 의도적 동기 구제와 장애를 구분할 수 없다.

20. [P0] 반복 워커의 실제 운영 통로가 없다 — §3-2는 최소 네 번의 워커 호출과 06:00 마감 스윕을 전제로 하지만 스케줄러 함수, 주기, 재시도 횟수, 중복 호출 처리, 실패 알림이 없다. §12-15의 수동 반복 픽스처는 운영 배선을 검증하지 않는다. 스케줄러가 한 번만 돌면 학급 전체가 마감 폴백으로 떨어진다.

21. [P0] 폴백의 출처 정본이 둘이다 — §7-2는 `출처='폴백'`이라고 하지만 §1·§4·§11-3은 `전날` 또는 `도입`이라고 한다. 현재 `오늘과제()`도 `전날`·`도입`만 반환한다. 동시에 중복 검사는 생성문만 대상으로 하므로 폴백은 같은 문장을 무기한 반복할 수 있어 신선함 게이트를 우회한다.

22. [P1] 출시 평가셋이 재현 불가능하다 — §8-B는 N=40과 통과선을 제시하지만 상태 갈래의 실제 목록, 갈래별 반복 횟수, 표본 seed, 채점자 불일치 처리값을 제공하지 않는다. §12-19도 이 값들을 “적어야 한다”고만 한다. 실행자가 표본과 반복 수를 임의로 정해도 같은 이름의 시험으로 통과시킬 수 있다.

23. [P1] 학생 목표 정합성이 평가축에서 빠졌다 — 판단 정본의 기본 게이트는 그 학생의 목표에 도움이 되는지까지 요구한다. 그러나 §8-B의 다섯 축은 연결성·답변 가능성·급수 적합성·신선함·재미이고 목표 정합성 채점이 없다. 기술 연결은 학생의 드림맵 목표와 같은 뜻이 아니다.

24. [P1] 큐 회전 규칙이 실행 계약에 없다 — §11-5는 날짜 해시로 `learner_id` 순서를 회전하라고 하지만 `jobs_집기` 시그니처에는 seed·정원·정렬 인자가 없고 인덱스는 `created_at` 순서다. 같은 시각에 생성된 행의 순서는 DB가 임의로 정할 수 있다. `예산소진` 배분이 바뀌어도 실제 순서를 복원할 기록이 없다.

25. [P1] 물리 DDL이 닫힌 필드명 규칙과 충돌한다 — §3-5-b는 `배정일`, `상태`, `펜싱`, `종료사유`, `배정사건_id` 등 한글 DB 식별자를 새로 만든다. L0·코어엔진 정본은 필드명을 영문 snake_case로 통일하고 한글 필드명을 금지한다. 그대로 구현하면 기존 계약·도구와 충돌하고 영문 별칭을 추가하면 물리 정본이 둘이 된다.

이 문서보다 나은 대안 구조 1개:

`generation_jobs` 하나를 유일한 workflow 정본으로 두고, 전체 선택 입력(급수·목표·첫날·교정문·전날 스냅샷·게임 판정·as_of/cutoff·skill·policy·폴백)을 불변 스냅샷으로 저장한다. `claim → attempt_open → attempt_record → finalize`를 각각 명시하고 시도 기록은 매번 새 append-only 행으로 남긴다. `/tasks`는 claim이나 생성을 하지 않고 완료된 배정만 읽으며, 마감 폴백도 같은 `finalize` 경로를 사용한다. `skill_ids`는 개입 의도로만 두고 A-1 실력 이해는 실제 제출·오류·교정 소비자가 별도로 채우게 해야 한다.
