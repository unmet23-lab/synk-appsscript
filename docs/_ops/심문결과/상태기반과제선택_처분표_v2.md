## 0. 먼저 — v2 는 «후퇴»가 아니다

v1 도 3벌 만장일치 「동결 불가」였고 v2 도 그렇다. 건수만 보면 제자리로 읽히지만 **지적의 층이 갈렸다.**

| | v1 의 P0 | v2 의 P0 |
|---|---|---|
| 성격 | **장(章)이 통째로 없다** — 입력 스냅샷 없음 · 산출물 계약 없음 · 실패가 한 모양으로 붕괴 · 멱등 없음 | **자리는 잡혔는데 규격이 안 닫혔다** — 필드 «이름» · `payload.ver` · JSON 속성 · 판정식 · 예약의 원자성 |
| 고치는 비용 | 새로 쓴다 | 값과 이름을 못박는다 |

v1 이 지적한 20갈래 중 **되돌아온 것은 3갈래뿐**이다(검문 실행 규격 · 빈 상태 위장 · 대조군 정합).
나머지 17갈래는 v2 가 실제로 닫았고 심문 3벌이 다시 꺼내지 않았다. **그러나 게이트는 통과가 아니다** —
아래 §1 의 P0 는 하나하나가 「구현자가 임의로 정하면 소급 불가한 행이 쌓이는」 자리다.

### 🔑 3벌이 «독립으로» 같은 대안을 냈다 — 이것이 v3 의 축이다

셋의 「더 나은 구조 1개」가 표현만 다르고 같은 곳을 가리킨다:

- luna-1 — 「하나의 **불변 결정 봉투**에 실제 입력·모델/프롬프트/정책·결과·`intervention_id`·`correlation_id` 를 함께 고정」
- luna-2 — 「학생×날짜 **실행 장부** 원자 claim → `intervention.delivered` 와 `task.assigned` 를 **같은 `intervention_id`** 로 착지」
- sol-3 — 「**`intervention.delivered` 중심 단일 정본**. `task.assigned` 는 분모만. 학생판은 `submissions.task_snapshot` 한 곳. `출처` 는 복제하지 않는다」

**v2 는 새 메타를 전부 `task.assigned.payload` 에 뒀다. 셋 다 그 닻이 틀렸다고 말한다.** 그 판정은 옳다 —
실측: 성과 소비자 `lib/성과회수.js`·성과계기판은 **`intervention.delivered` 를 닻으로 읽는다.**
`task.assigned` 에만 실은 `arm`·`생성결과`·`생성입력`은 저장돼도 **효과 소비자에 도달하지 않는다.**
「수집은 엔진 도달까지가 한 벌」이 정확히 여기서 끊긴다.

전체를 오단정한다(F183). 정정해 위 표에 반영했다.
