판정: 동결 불가. P0 13건, P1 5건, P2 1건이다.

1. [P0] 실행 가능한 단일 규격이 없다 — §8·§11은 상태 입력 여부를 ㉠·㉡·㉢으로 남겨 P0 §6-3과 충돌한다. 이 선택은 단순 인자 하나가 아니라 프롬프트·판지문·실험 모집단·저장 증거를 바꾸므로, 답을 기다리지 않고 구현할 수 있다는 §8의 결론은 거짓이다.

2. [P0] 전역 배정 우선순위에서 게임 갈래가 증발했다 — §1·§3의 「넷→다섯」 표는 `오늘과제()` 내부만 설명하지만 실제 `deliver`는 그보다 먼저 `게임배정()`을 실행하고 같은 일일 멱등키를 쓴다. 게임일 생성 호출의 선후와 실험 모집단이 정의되지 않아 게임을 밀어내거나, 배달되지 않을 문장을 생성하거나, 하루 1건 계약과 대조군을 오염시킬 수 있다.

3. [P0] 모델이 실제로 본 상태를 복원할 수 없다 — §3·§5·§7은 상태 축을 모델 입력으로 쓰면서 실제 축 값·널 처리·렌더링된 요약을 행에 남기지 않는다. 현행 `intervention.delivered`에는 추정판·신뢰도·근거 참조만 저장되므로, 늦게 수신된 과거 사건이 생기면 같은 `as_of` 재계산도 당시 입력과 달라진다.

4. [P0] 생성 산출물의 불변 `task_snapshot` 계약이 없다 — §3은 모델이 문장과 질문을 낸다고 하지만 `오늘과제()`에는 `생성문장` 하나만 전달한다. 세 호흡, 생성 질문, 초급 선택지, 호흡별 `task_format`, `task_schema_ver`의 정확한 조립 규격이 없어 실제 학생이 본 과제와 저장 스냅숏이 갈릴 수 있다.

5. [P0] `payload.model_ref`가 확정 계약을 우회한다 — §5-2는 새 자유 필드에 모델과 프롬프트 해시를 넣고 계약 개정이 없다고 주장한다. 정본은 이미 최상위 `model`·`prompt_ver`·`policy_ver`를 정의하므로 `model_ref`는 계약 밖 중복이며, 기존 소비자는 정본 칸이 빈 행으로 읽게 된다.

6. [P0] 생성 미시도·대조군·장애·검문 탈락이 같은 증거로 붕괴한다 — §4는 키 없음, 호출 실패, 검문 탈락을 모두 `degraded=true`와 `전날|도입`으로 접는다. 시도 여부·실패 단계·사유·검문 결과가 발생 순간에 남지 않아 이후에는 전원 대조군인지 생성기가 죽었는지 복원할 수 없다.

7. [P0] 생성 성공 0건이어도 인수된다 — §9-2는 키 없이 전원 폴백인 배치를 초록으로 요구하고, §9-3은 분포를 출력할 뿐 생성 성공 하한이나 경보 기준이 없다. 생성기가 한 번도 호출되지 않아도 모든 인수 조건을 통과할 수 있다.

8. [P0] 대조군 노출 기록이 없다 — §6은 학생×날짜 해시와 비율만 정의하고 실제 `arm`, 실험판, 할당기판, 적용 비율을 사건에 남기지 않는다. 비율이나 해시가 바뀐 뒤에는 과거 대조군을 생성 실패 폴백과 구분할 수 없다.

9. [P0] 일별 교차 배정이 7·30일 성과를 오염시킨다 — §6의 학생×날짜 배정은 같은 학생이 후속 날짜마다 다른 arm을 받게 한다. 한 개입의 7·30일 창 안에 양쪽 처치가 반복해서 섞이므로 어느 과제가 만든 변화인지 영구히 분리할 수 없다.

10. [P0] 기존 `성과회수`는 이 기능의 학습 성과를 재지 않는다 — §6은 현행 즉시·1·7·30일 창이면 충분하다고 하지만 즉시는 열람 여부이고 지연 창은 일반 행동 상태다. 생성 과제가 겨냥한 한국어 기술의 오류 감소도, arm 간 효과 차이도 계산하지 않아 「기능→성과→엔진 학습」 사슬이 끊긴다.

11. [P0] 어휘 지도와 개입 의도가 끊긴다 — §2·§3·§7에는 `skill_ids`·목표 기술·전략 코드·난이도·선택 이유가 없다. 생성 문장만 보고 사후 추측해도 모델이 왜 그 개입을 골랐는지는 복원되지 않아 어떤 기술에 어떤 처방이 통했는지 학습할 수 없다.

12. [P0] 상태 계산 실패가 개인화 성공으로 위장할 수 있다 — 현행 `deliver`는 상태 계산 예외를 삼키고 배달을 계속하지만 §3·§4는 이때 생성할지 폴백할지 정의하지 않는다. 상태 없이 급수·목표만으로 생성하고 `degraded=false`를 찍는 구현도 문서상 통과해 상태 기반 기능의 실패가 정상 개입으로 섞인다.

13. [P0] 폴백에 도달하기 위한 시간 제한이 없다 — §3은 학생별 외부 호출을 밤 배치에 넣지만 타임아웃·취소·부분 응답 처리 규칙이 없다. 현행 `deliver`는 학생을 순차 처리하므로 한 호출이 멈추면 해당 학생의 폴백뿐 아니라 뒤 학생 전원의 배달도 실행되지 않는다.

14. [P1] 외부 생성 호출은 멱등하지 않다 — §6의 결정적 해시는 대조군에만 있고, 벤더 호출은 DB의 일일 중복 제약보다 먼저 일어난다. cron·조회 구제·수동 재실행이 겹치면 같은 논리 과제에 서로 다른 생성 호출이 발생하며, 예약키·호출 ID·기존 결과 재사용 규칙이 없다.

15. [P1] 상태 입력 인터페이스가 실제 구현과 다르다 — §3·§7은 「5축+confidence」라고 하지만 현행 `학습자상태.v6`은 8축을 내며 `estimator_confidence`는 정확도가 아니라 표본 충분도다. 어떤 축을 어떤 단위·순서·반올림·널 표현으로 보낼지 없어 동일 `policy_ver` 아래 입력이 달라질 수 있다.

16. [P1] 검문과 골든셋 통과 기준이 실행 규격이 아니다 — §4-1은 길이·한국어 비율·질문 형태를 일반어와 외부 절 참조로만 두고 정규화·경계값·응답 JSON·파서판을 정하지 않는다. §9에도 100문항 골든셋의 합격 기준이 없어 형식만 맞는 교육 부적합 출력이 `degraded=false`로 통과한다.

17. [P1] 고정 갈래에도 불필요한 생성 호출이 선행한다 — §3 흐름은 상태 조회와 벤더 호출 뒤에 `오늘과제()`가 첫날·교정문 우선순위를 판정한다. 따라서 첫날·교정문·게임 학생에게 버릴 출력을 생성하며, 그 호출의 비용과 실패는 어떤 배달 사건에도 귀속되지 않는다.

18. [P1] SRS 회피 논증이 자체 폴백과 모순된다 — §8은 「어제 낸 것을 다시 내지 않는다」고 주장하지만 §4는 생성 실패 시 전날 문장을 그대로 다시 낸다. 허용된 장애 폴백 반복과 금지된 재출제를 구분하는 계약이 없어 같은 행을 서로 반대로 해석할 수 있다.

19. [P2] 폴백 단계 수가 문서 안에서 세 번 갈린다 — §4 제목은 3단, 표와 본문은 2단, §9-2는 다시 「2·3단 폴백」이라고 쓴다. 인수 시험이 어느 상태 기계를 검증해야 하는지 고정되지 않는다.

이 문서보다 나은 대안 구조가 있으면 1개:

`전역 배달계획 → 일일키 잠금 → 조건부 생성 → 원자 착지 → 고정기간 평가` 구조다. 단일 순수 함수가 기존 게임 갈래까지 포함해 첫날·교정·게임·생성·대조군·폴백을 먼저 확정하고, 생성 대상만 학생×날짜 잠금 아래 호출한다. 기존 사건과 JSONB에 실제 상태 스냅숏, `model`·`prompt_ver`·`policy_ver`, 입력 해시, 파서판, 전체 `task_snapshot`, `skill_ids`, 개입 이유, arm·할당기판·실패 사유를 계약 필드로 남기고 중복 실행은 저장된 결과를 재사용해야 한다. 대조군은 학생별로 최소 30일 고정하고, 목표 기술별 즉시·1·7·30일 결과를 같은 `intervention_id`에 연결해야 한다.
