## §2 최상단 — 「닫힌 결정」을 어긴 것 2건

다른 60건보다 **먼저** 처분해야 한다. 결함이 아니라 **이미 유호님 판단으로 닫힌 자리를 설계가 되열었다**는 뜻이라, 고치는 방향이 기술이 아니라 결정이다.

### ① `correlation_id` 를 서버가 묶는다 — 🚫서버가묶기 위반 · **3/3 합의**
v3 §3-0·§12-12 는 야간의 `task.assigned`·`intervention.delivered`·`submissions` 에 **같은 `correlation_id`** 를 요구한다.
- 공용 계약(C0)에서 그 값은 **학생 한 앉음(세션) 흐름의 봉투**다.
- 이 저장소의 닫힌 결정은 `🚫서버가묶기`(메모리 「S1 배선」 절).
- sol 이 그 결정 이름을 직접 지목했고, luna 2회차는 **물리적 불가**까지 덧붙였다 — `engine.submissions` 에 그 열이 **아예 없다**.
- 급소: 야간 서버가 **학생의 미래 세션 값을 미리 정할 수 없다.** 세션 흐름과 일일 배달 묶음을 한 키에 섞으면 **사후 분리가 원리상 불가능**하다(append-only).

### ② `estimator_confidence < 0.2` 분기 — 🚫문턱분기 위반 · **1/3**(sol 단독 · 대상은 2/3)
v3 §4-3 은 신뢰도 0.2 미만이면 생성 대신 폴백으로 **처치를 가른다**.
- 이 저장소의 닫힌 결정은 `🚫문턱분기`(메모리 `task-selection-by-state`).
- sol: 「입력 유무」로 개명해도 **실행 동작은 문턱 분기**다.
- luna 1회차는 다른 축으로 같은 자리를 쳤다 — **0.2 는 충분도 문턱이 아니다**(전체 표본 3개만 돼도 약 0.23이라, 거의 아무것도 모르는 학생에게 개인화 생성이 돈다).
- ⚠ 이 둘은 **서로 반대 방향의 처방**을 함의한다(하나는 문턱을 없애라, 하나는 문턱이 너무 낮다). 처분 때 갈라 읽는다.

## §4 세 회차가 **각자** 낸 대안 구조 — 방향이 하나로 모인다

세 벌 다 「이 문서보다 나은 구조」로 **같은 것**을 지목했다:

> 단일 HTTP `deliver` 안에서 학급 전체를 순차 생성하지 말고, **학생별 단건 작업을 부르는 배치 오케스트레이터**로 분리한다.
> `대상 판정 → fenced claim → 생성 시도 기록 → 검문 → 원자 착지 → 관측·성과 회수` 를 **명시적 상태기계**로 만들고,
> 상태마다 있어야 할 행·없는 행·멱등키·재시도·소비자·픽스처를 한 줄씩 고정한다.
> `correlation_id` 는 학습 세션 의미로 두고 사건 연결은 기존 event/parent 키를 쓴다.
> **생성 전용 평가셋을 교정용 102문항과 분리해 별도 출시 게이트로 둔다.**

합의도 3/3 인 이 대안은 v3 의 §3(순차 루프) 구조 자체를 바꾸라는 뜻이다.

- **F348** — 설계문의 실측 주장을 «한 층만» 열고 통과시켰다(`출처` 는 이미 착지하고 있었다).
- **F350** — 그 정정으로 나온 v2 처분표가 «file:line 을 달고» 또 틀렸다(`as_of` 는 스키마에 0건인데 「이미 물리 열」이라 적었다).

그래서 **합의 3/3 이라도 「참」이 아니라 「오독일 확률이 낮다」까지만** 읽는다. 특히 아래 셋은 **반드시 직접 열어서** 재야 한다:

1. **㉮ 호스팅 상한** — 두 회차가 **60초 vs 400초**로 갈렸다. 남의 문서 인용이지 우리 실측이 아니다. 실제 `deliver` 의 실행시간 상한을 우리 판에서 확인한다.
2. **㉠ `submissions.correlation_id` 열 유무** — 「없다」는 부정 주장이다. F348 의 교훈대로 **값이 살 수 있는 층을 먼저 열거하고**(열 · payload · `task_snapshot` · 별도 표) 전부 연 뒤에만 「없다」로 적는다.
3. **㉬ `skill_ids` 가 이미 계약에 있다** — 있다면 v3 §6-1 의 「미래 트랙으로 민다」는 근거가 통째로 무너진다. 한 자리만 찾으면 되는 «있다» 주장이라 검증이 싸다.

**그래서 v3 §6-1(`:449~450`) 의 근거가 무너진다.** 설계문은 「`skill_id` **물리 칸 신설**은 이 트랙이

`learning_events` 행이므로 **그 행 자신의 `skill_ids` 열**이 곧 「무엇을 겨냥한 개입인가」의 자리다.
- 🔴 추가 결함(심문자도 안 짚음): 대신 쓰기로 한 `evidence_refs.쓴축` 은 **한글 키**다.

  열 이름에만**」이라 못 박았다. 정본 열을 두고 한글 사본을 jsonb 안에 새로 만드는 꼴이다.

### ㉠ `submissions.correlation_id` — ✅**채택**, 단 **「닿을 수 없다」는 거짓**

§5-2 가 요구한 대로 **값이 살 수 있는 층을 먼저 열거하고 전부 열었다**(F348 처방):

| # | 살 수 있었을 층 | 실측 |
|---|---|---|
| 1 | `submissions` 물리 열 | ❌ **없다** — CREATE 전문 24열 전수(`L0_스키마.sql:434~458`) · 이후 `ALTER … add correlation_id` **0건** |
| 2 | `submissions.task_snapshot` (jsonb) | ⚪ 열은 있으나(`:440`) 규약상 **과제 스냅샷**이고 봉투 자리가 아니다 |
| 3 | `submissions.payload` | ❌ 그 표에 `payload` 열 자체가 없다 |
| 4 | 별도 매핑 표 | ❌ 없다 — 저장소 전체 `correlation_id` 정의는 `learning_events`(`:55`·`:412`) 하나뿐 |
| 5 | **FK 조인** | ✅ **닿는다** — `submissions.event_id` → `learning_events.event_id`(FK `submissions_event_id_fkey`) → `.correlation_id` |

- ✅ 「**열이 없다**」 = **참**(luna 2회차 지적 그대로).
- 🚫 「그래서 셋을 못 묶는다」 = **거짓**. 조인 1회면 닿고, `submissions_event_idx`(`:618`) 가 그 조인을 받친다.
- 🔑 **그래서 ㉠ 의 무게는 물리 열이 아니라 §2-① 쪽에 전부 실린다** — `🚫서버가묶기` 위반과
  「야간 서버가 학생의 **미래 세션** 값을 미리 정할 수 없다」. 실제로 v3 `:273~275` 는 신설 표
  `generation_claims` 에도 `correlation_id` 를 두어 **배치가 그 값을 발급**하게 했다. 그게 그 위반의 실물이다.
- ⚠ 처분 때 「열이 없으니 P0」로 인용하지 말 것. 열은 **부수 논거**이고, 그 문장만 옮기면 다음 판이
  「열 하나 추가하면 끝나는 일」로 오독한다 — 닫힌 결정 위반은 열을 추가해도 그대로 남는다.

### ㉮ 호스팅 실행시간 상한 — ✅**채택**, **두 회차가 «둘 다» 틀렸다**

공식 상한(플랫폼 정본):

| 축 | 값 | 플랜 의존 |
|---|---|---|
| Wall clock | **Free 150초 · Paid 400초** | ✅ 갈린다 |
| **Request idle timeout** | **150초** — 넘으면 `504` | ❌ **플랜 무관** |
| CPU time | 2초(async I/O 제외 — 벤더 대기는 여기 안 잡힌다) | ❌ |
| Memory | 256MB | ❌ |

- 🚫 luna 「**60초**」 — 그런 상한은 **없다**. 근거 없는 숫자다.
- 🚫 sol 「**400초**」 — 실재하지만 **Paid 플랜 wall clock** 이고 **우리 판이 아니다**.
- ✅ **우리 판의 하드 상한 = 150초.** 두 갈래가 같은 자리로 모인다:
  1. 우리 코드에 `EdgeRuntime.waitUntil`(배경 작업)이 **0건**(`functions/` 전수 grep) → 응답을 먼저
     못 보내므로 **idle timeout 150초가 먼저 때린다**. 이건 유료로 올려도 안 풀린다.
  2. Supabase 유료 전환은 메모리 실측상 **「파일럿 게이트」로 미집행**이다
     (`p0-product-contract` ⑥ · `core-engine-obsidian` 채택2) → 지금은 Free = wall clock 도 150초.
- 🔴 **그래서 v3 `:196` 의 `생성총예산_MS = 600000`(600초)은 우리 판 상한의 «4배»다.** 심문자 둘 다
  숫자를 틀렸는데 **결론은 오히려 더 강해졌다** — 400초였다면 1.5배지만 실제로는 4배다.
- 📏 **미측정으로 남긴 것**(분모를 밝힌다): Supabase 대시보드를 직접 열어 플랜을 확인하지 않았다.
  다만 그 확인은 **배경 작업을 도입할 때만** 값이 갈린다(150 → 400). 지금 구조에선 어느 쪽이든 150초다.
