[P0] 승격 사건을 현재 계약으로 저장할 수 없음 — §3의 `data_use.granted`는 자기 `event_id`와 별도로 원본 사건을 참조해야 하지만 그 물리 매핑이 없다. 공용 c9에도 `artifact_ref`·`content_hash`·`serializer_ver`·`redaction_ver`·`consent_id`·`dataset_ver`·승인자 필드가 없으므로 이 문서가 제3의 필드 정본이 된다.

[P0] 교정 판정과 승격 판정이 여전히 기계적으로 분리되지 않음 — §1·§3은 “버튼 하나, 기록 둘”이라고만 하고 두 판정의 독립 값·미결 상태·기본값·각 결정 ID를 정의하지 않는다. 더구나 `data_use.granted`는 산출물 생성 뒤 발행되므로, 버튼 클릭과 산출물 완성 사이에 사람의 승격 의사를 보존할 별도 불변 기록이 없다.

[P0] 승격과 데이터셋 편입을 한 사건에 합침 — §3은 데이터셋 조립 전에 발행하는 승격 사건에 `dataset_ver`를 요구한다. 동일 승격 산출물이 여러 데이터셋 판본에서 재사용될 수 있는데 `(원본 event_id, 목적)` 유일성은 두 번째 판본 편입을 막으므로 승격 승인과 데이터셋 멤버십의 의미가 충돌한다.

[P0] train/eval 혼입 차단이 반대로 설계됨 — `(event_id, 목적)` 유일성은 같은 원본을 `train`과 `eval`에 각각 한 번씩 넣는 것을 허용한다. 같은 학생·과제·재시도·유사 문장까지 한 분할 그룹으로 묶는 규칙도 없어 평가 점수가 훈련 데이터 누출로 오염된다.

[P0] 재검수·제외·롤백 경로가 없음 — §3은 teacher 행이 여러 개여도 승격은 한 번이라고 못박아, 첫 라벨이 틀린 뒤 수정된 교정·산출물을 승격할 수 없게 한다. `correction_id`·원본 판본·후계 관계가 없고, 상위 최소 요건인 평가 결과 참조·라벨링 규칙 버전·제외·롤백 사건도 빠졌다.

[P0] 비식별 공정이 실패해도 승격됨 — §3의 `redaction_ver`는 어떤 코드를 돌렸는지만 말할 뿐 성공·실패·미해결 식별자·검사 결과를 말하지 않는다. 원문을 그대로 반환한 작업도 버전과 해시만 있으면 정상 산출물 모양으로 `data_use.granted`까지 갈 수 있다.

[P0] 음성을 비식별 산출물로 오인 — §3-1은 `audio_ref`를 회사 훈련 산출물에 포함하면서 비식별이라고 부른다. 이름 구간을 가려도 화자 음색은 식별 신호이며, `audio_ref`가 원본·가변 객체를 가리키면 산출물 해시가 실제 음성 바이트의 불변성도 보장하지 않는다.

[P0] 골든셋은 비식별도 아니고 ⑤ 통과 재료도 아님 — §2-1은 골든 픽스처를 비식별이라 하지만 실제 `골든픽스처_()`는 ID·날짜 열만 버리고 학생 `원문`과 교정을 그대로 Git에 보낸다. `teacher_gold`에는 훈련 사용 판정·정확한 원본 `event_id`·`consent_id`가 없고 내보낼 때 ID도 `G001...`로 다시 매기므로, §6의 “이미 ⑤를 통과한 첫 대상” 주장은 거짓이다.

[P0] 같은 Postgres라는 이유로 외부 실행을 내부 적재로 위장 — §2-1은 수집과 엔진이 같은 DB에 있으면 ⑥⑦이 외부 발행이 아니라고 단정한다. 실제 소비자가 외부 모델·훈련 API·n8n·Git 저장소라면 DB에 큐가 있다는 사실과 무관하게 데이터는 시스템 밖으로 나간다.

[P0] 철회 경쟁에서 사용이 계속됨 — §3은 한 번의 확인 시각과 추상적인 “철회 전파”만 적었고, 승인→비식별→데이터셋 조립→소비 사이 각 단계의 재확인과 원자적 차단을 정의하지 않았다. 철회와 작업이 경쟁하면 철회 뒤 산출물 생성·데이터셋 편입·모델 소비가 모두 가능하며, 경로 A와 오프라인 대기 사건의 차단 시점도 없다.

[P0] 개인화 인과 사슬이 실제 노출을 다시 버림 — §3 경로 A 입력에는 c9가 따로 만든 `content.viewed`가 없고 기준도 `intervention.delivered`에 걸려 있다. 네트워크 실패·미열람 개입이 처치로 계산되며, 즉시·1·7·30일 성과의 기준 시각·성과 사건·강사 판정 연결도 정의되지 않았다.

[P0] `as_of` 보정이 실행 규격이 아님 — §3의 `as_of ≤ intervention.delivered.occurred_at`은 증거 행이 `as_of` 이전이라는 조건이 아니며, 어떤 시각을 실제로 저장하는지도 없다. 신뢰할 수 없는 기기 `occurred_at`과 오프라인 지연 사건을 그대로 쓰면 개입 뒤 행동이 개입 전 상태로 역류한다.

[P0] 13사건을 하나의 교정 파이프라인으로 처리할 수 없음 — §3 경로 B의 `AI 1차→교정 검수`는 발화·쓰기에는 적용되지만 `choice.selected`·`content.viewed`·`task.assigned`·`exam.result`에는 교정 대상 자체가 없다. `data_use.granted`·`data_use.revoked` 같은 제어 사건까지 같은 학습 사슬에 넣으면 자기 자신을 다시 승격해야 하는 순환도 생긴다.

[P0] 성향·습관을 집계만 남겨 핵심 학습 신호를 절단 — §3-1은 두 축을 “비식별 집계만”으로 제한한다. 학생별 선택→개입→관측→지연 성과의 순서를 없애면 회사 엔진은 어떤 성향에서 어떤 지도가 효과적이었는지 학습할 수 없으며, 닫힌 「구조·통계만 복원 금지」 결정과도 충돌한다.

[P0] 마감 원신호를 발견만 하고 계약하지 않음 — §3-2는 마감 시각·마감 판본이 소급 불가라고 인정하지만 필드명·시각 의미·판본 식별자·생산자·C0 전달·출시 게이트를 하나도 정하지 않는다. 이 상태로 동결하면 문서가 스스로 밝힌 영구 손실을 그대로 허용한다.

[P0] 도달 장부가 일부 배선만으로 전부 초록이 됨 — §4의 단일 `{경로, 부품, 소비자}`는 한 사건의 A/B 양쪽 경로, 음성/텍스트 변형, 여러 엔진 부품과 소비자를 표현하지 못하고 필수 필드도 검사하지 않는다. 파일에 뷰·테이블 문자열만 있으면 주석·죽은 코드·미호출 함수도 통과하며, 다른 저장소·n8n·실배포 DB의 소비자는 원리상 검증할 수 없다.

[P0] “읽힘”을 다시 “학습”으로 개명 — §5는 뷰 대신 소비자가 읽으면 ⑦이라고 정의하지만, SELECT 후 폐기해도 그 기준을 통과한다. 데이터셋 멤버십 확정, 평가 실행 완료, 모델·정책 산출물 반영, 학습자 상태가 실제 개입에 사용된 증거 중 어느 것이 종착점인지 정의되지 않아 ⑦은 여전히 물리 계약이 없다.

[P0] 라이브 이관은 거절 아니면 증거 위조로 끝남 — §7의 옛 시트 행은 c9 필수 맥락·버전·승격 계보를 다 갖고 있지 않아 현재 C0 검증을 통과하지 못하거나, 수입기가 현재 판본 값을 과거 행에 꾸며 넣어야 한다. 행 ID만 멱등키로 쓰면 같은 행의 후속 강사 수정은 조용히 버려지고, 원천 판본·행 내용 해시·매핑 버전·부분 실패 상태도 없다.

[P0] 동결 대상의 핵심 범위가 아직 두 갈래임 — §6은 E0 계약만 남기는 ㉮와 엔진 코드를 즉시 짓는 ㉯를 동시에 둬 단일 설계가 아니다. ㉮는 “나중에 물건을 붙인다”를 허용해 개원 즉시 사용 원칙과 충돌하고, ㉯는 닫힌 E0 코드 0줄·E2 후행 결정을 명시적 해제 없이 뒤집는다.

[P1] 개입 당시 학습자 상태를 재현할 수 없음 — §3은 “계산 결과는 저장하지 않는다”고 한 뒤 버전·근거 ID·신뢰도만 적는다. 실제 상태 벡터·후보별 점수·관찰 창·정확한 코드 산출물 지문이 없어 같은 근거에서도 당시 추천 이유를 복원할 수 없다.

[P1] 계기판이 빈 파이프라인을 실패로 만들지 않음 — §5는 단계별 건수와 지연시간만 요구하고 0/0, 필수 필드 null, 부적격·대기·재시도·dead-letter·부분 성공의 판정을 정의하지 않는다. 모든 생산자가 멈춰 전 단계가 0이어도 “처리할 것이 없음”과 장애가 같은 모양이다.

[P1] `task.assigned`와 `daily_activity.expected`가 분모 정본 두 개가 됨 — §2는 `task.assigned` 생산자가 있다고 하면서 §3-2는 별도 `daily_activity.expected` writer가 필요하다고 주장한다. 후자가 전자의 재계산 가능한 파생인지 독립 원본인지 못박지 않아 둘이 어긋날 때 어느 값을 믿을지 없다.

## 이 문서보다 나은 대안 구조 1개

`원본 증거 → 독립 판정 → 불변 산출물 → 목적별 승격 → 데이터셋 멤버십 → 실제 효과 증거`의 6단 계약으로 다시 쓴다.

- 개인화 경로는 `원본 사건 → 신뢰 가능한 결정 시각+정확한 evidence set → 개입 → content.viewed → 즉시/지연 성과 → 강사 판정`으로 고정한다.
- 회사 경로는 한 UI 제출 안에서도 `교정 판정`과 `승격 의사`를 별도 ID·값으로 저장하고, 성공한 비식별 검사 산출물만 승격한다. 재검수·제외·철회·롤백은 원본을 고치지 않는 별도 사건으로 둔다.
- 승격과 데이터셋 편입을 분리하고, train/eval은 원본 사건이 아니라 학생·과제·연관 시도 묶음 단위로 상호 배타 분할한다.
- 도달 장부는 `(event_type, 변형, 필수 필드, 경로, 엔진 부품, 소비자, 종착 증거, as_of, 철회 처리)`를 의무 단위로 전량 열거하며 실제 왕복 결과를 검사한다.
- E0에서는 이 의미 계약과 출시 게이트만 동결한다. 엔진 물리 구현 여부가 명시적으로 결정되기 전에는 현 상태를 “도달 완료”로 기록하지 않는다.
