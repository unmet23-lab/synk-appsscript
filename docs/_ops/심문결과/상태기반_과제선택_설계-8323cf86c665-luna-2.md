- [P0] 닫힌 M0 필드명 규칙과 정면 충돌 — §11은 `출처`·`생성결과`·`생성입력`·`배정판`·`적용비율`을 payload 필드로 열지만, M0 정본은 필드명을 L0 컬럼명으로 통일하고 한글 필드명을 금지한다. 중첩 키 `요약문`·`축값`·`쓴축`도 같은 충돌이며 영어 매핑·값목록·널 규칙이 없다.

- [P0] 예약이 원자적이지 않고 상태를 자기 오염시킨다 — §3은 `task` 키를 예약한 뒤 상태를 계산한다. 예약을 `task.assigned` 행으로 만들면 실제 `학습자상태.js`가 그 사건을 리듬 분모로 읽어 자기 과제를 자기 상태에 포함하고, 행을 만들지 않으면 동시 호출이 모두 벤더를 부른다.

- [P0] 야간 배치 전용이라는 주장이 실제 경로와 모순된다 — §3-1은 생성이 야간 배치에서만 일어난다고 하지만, `SYNK-talk supabase/functions/tasks/index.ts`의 `지금세우기()`는 배정이 없으면 `/deliver?learner_id=...`를 즉시 호출한다. 생성기를 `deliver`에 넣으면 학생의 일반 조회가 모델 호출이 되고, 실패 시 조회 재시도가 생성 재시도가 된다.

- [P0] 생성 결과와 개입-성과 고리가 연결되지 않는다 — §4~§7은 결과를 `task.assigned` payload와 `task_snapshot`에 싣는다고만 하고 `intervention.delivered`, `intervention_id`, `output_text`, `model`, `prompt_ver`, `policy_ver`, `cited_refs`의 연결을 정의하지 않는다. 현재 `/tasks`와 `성과회수.js`는 `intervention.delivered`를 기준으로 읽으므로 화면에는 생성문장이 보여도 성과 데이터에는 다른 개입이나 빈 개입으로 남을 수 있다.

- [P0] `생성입력`이 실제 계약이 아니다 — §6은 정확한 축값·널 처리·순서·반올림을 새 `lib/과제요약.js`에 위임하지만 그 파일의 출력 계약은 문서에 없다. §10은 상태 축의 숫자만 허용하는 반면 실제 상태 출력에는 분포·맵·최근 시각 같은 비숫자 구조도 있어, 전체를 저장할지 투영할지에 따라 모델 입력이 달라진다.

- [P0] 초급 생성 출력 형식이 자기모순이다 — §4-2는 벤더 응답을 문장 1개와 질문 1개로 고정하지만 §7은 초급 생성분에 `선택지`와 `선택차원`도 채우라고 한다. 선택지를 같은 호출에서 만들지, 기존 고정 보기를 재사용할지, 자유발화로 내릴지 규칙이 없어 첫 생성 행부터 `task_format`과 선택 로그가 갈라진다.

- [P0] 동일 사실을 여러 위치에 중복 저장하면서 정합성 규칙이 없다 — `출처`는 스냅샷과 payload에, `degraded`는 이벤트 최상위와 `생성결과` 옆에, 모델 판 정보는 개입과 배정 경로에 나뉜다. 어느 조합이 합법인지 CHECK·정규화·회귀 조건이 없어 `degraded=false`인 검문탈락 행이나 스냅샷과 payload의 서로 다른 출처가 통과할 수 있다.

- [P0] `상태없음`이 정상적인 무증거와 장애를 합친다 — §4-1은 상태가 비었거나 계산에 실패한 경우를 같은 값으로 접는다. 실제 `학습자상태.js`는 사건이 없을 때 신뢰도 0과 널 축을 반환할 수 있는데, 예외·빈 표본과 구별되지 않아 학생 데이터 부족, 계산 버그, DB 장애가 모두 같은 폴백 분포로 남는다.

- [P0] `policy_ver`가 실제 정책 변화를 지문으로 못 잡는다 — §3-2의 학생별 타임아웃과 배치 총예산은 첫 구현에서 정한다고 하면서 §5.1의 지문 재료에는 포함하지 않는다. 타임아웃만 바꿔도 생성 성공과 폴백의 비율이 바뀌는데 같은 `policy_ver`에 섞이므로 개입 효과 비교가 오염된다.

- [P0] 대조군의 30일 고정이 규격상 보장되지 않는다 — §9은 `learner_id + 기간 버킷` 해시와 현재 적용 비율로 매일 arm을 계산한다. 버킷 중간에 비율을 바꾸면 같은 학생의 arm이 바뀌며, 행에 사후 비율을 남기는 것만으로는 그 변화를 막거나 복원할 수 없다.

- [P0] 계약 개정이 미결 상태다 — §11은 허용 payload 목록을 개정해야 한다고 인정하면서도 정확한 계약판, 키·값·필수성·널 규칙, 마이그레이션·롤백을 제시하지 않는다. 현재 `task.assigned` writer는 payload `{ver:1}`만 쓰므로, 이 문서를 얼리면 구현자는 아직 작성되지 않은 계약을 임의로 만든다.

- [P0] 벤더 부작용이 실패 사건보다 먼저 발생한다 — §3의 외부 호출 뒤 최종 이벤트·제출 행을 쓰는 트랜잭션이 실패하면 벤더 성공·타임아웃·DB 실패를 보존할 실행 기록이 없다. 다음 실행은 같은 학생에게 다시 호출하고 첫 호출의 비용과 결과는 어떤 `생성결과`에도 남지 않는다.

- [P1] 검문 판정표가 아직 실행 가능한 규격이 아니다 — §8은 한국어 코드포인트의 정확한 범위, 길이·비율을 문장과 질문에 각각 적용하는지, 정규화된 값을 저장하는지, 질문 판정 방법을 닫지 않았다. `검문탈락`의 세부 사유도 필드명과 값목록이 없어 구현마다 다른 자유 문자열이 된다.

- [P1] `cited_refs` 생산 규칙이 빠졌다 — c4 계약은 `intervention.delivered`가 어떤 지식·콘텐츠를 사용했는지 `cited_refs`로 남기도록 이미 자리를 냈다. 이 문서는 생성 입력·상태 축만 정의하고 참조가 없을 때의 명시값조차 정하지 않아 생성문장의 근거 회수가 끊긴다.

- [P1] 인수 조건의 분모와 운영 경로가 닫히지 않았다 — §12-8의 “생성결과 분포”가 게임·첫날·교정문·동의 누락·중복·배치 실패를 포함하는지 정하지 않았다. 또한 cron 실패와 `/tasks` 구제 호출을 포함한 실제 운영 관통 시험이 없어, 야간 생성이 한 번도 없는데도 리허설이 초록이 될 수 있다.

- [P1] raw payload 용량과 절단 정책이 없다 — `요약문`·축 묶음·버전·선택지·실패 세부 사유를 한 payload에 넣으면서 최대 바이트, 초과 시 판정, truncation 금지 여부를 정의하지 않았다. C0의 `PAYLOAD_TOO_LARGE`가 발생하면 생성 시도는 있었지만 `task.assigned`에 이유가 없는 새 실패 유형이 된다.

`상태 선조회(이벤트 삽입 전) → 학생×날짜 유일 실행 장부(task_generation_run) 원자 claim → 야간 배치에서만 벤더 호출 → 실행 장부에 결과 보존 → 기존 append-only인 intervention.delivered와 task.assigned를 같은 intervention_id로 착지 → /tasks는 착지 결과만 읽기` 구조가 낫다. 실행 장부는 학습자 상태표나 성과표가 아니라 외부 호출 멱등·재시도 기록으로 한정하고, `/tasks` 구제 경로는 생성 호출을 하지 않게 분리해야 한다.
