동결 불가 — P0 17건, P1 7건.

- [P0] `event_draft`·`load_error`의 물리 칸이 없다 — §3-5-b의 `generation_jobs` DDL에는 두 열이 없는데 `jobs_finalize_due`는 저장된 `event_draft`를 읽고 `jobs_load_one`은 이를 덮어쓰도록 규정한다. `_targets`에서는 `event_draft?`로 선택 표시하면서 C1에서는 전량 필수라고도 해 마감 스윕을 구현할 단일 계약이 없다. `load_error` 200자도 저장되지 않아 `적재실패·내부오류`만 남고 원인은 영구 소실된다.

- [P0] `적재실패` 행 자체를 만들 수 없는 실패 구간이 있다 — §3-5-b A9는 `오늘과제()`·`학습자상태()`·기술 선택 중 예외가 나면 실패 행을 만들라고 하지만, 같은 DDL은 `branch_snapshot`·`skill_taxonomy_ver` 등을 `not null`로 요구한다. 그 값들을 만들다가 실패한 경우 엄격한 A8 스키마를 만족시킬 수 없어 한 학생 격리가 아니라 `jobs_load` 전량 롤백으로 돌아간다. `jobs_load_one`도 같은 조립을 다시 실행하므로 지속 결함은 같은 자리에서 무한 재현된다.

- [P1] 문장+질문 중복 검사는 질문을 공급받지 못한다 — §8은 기존 문장 또는 질문 중 하나만 같아도 `중복`이라고 하지만 §3 ②′ 쿼리는 `payload.output_text`와 `skill_ids`만 읽는다. 질문은 `submissions.task_snapshot.호흡[].프롬프트`에 있으므로 조인이 없는 운영에서는 질문 중복이 항상 꺼진다. 같은 쿼리는 `generation_outcome='성공'` 필터도 없어 첫날·교정문·폴백 문장까지 생성 이력으로 오인한다.

- [P0] 실패 결과와 원인 시도의 계보가 끊긴다 — §3-5-b는 `winning_attempt_id`를 `outcome='성공'`에만 허용한다. 따라서 타임아웃·벤더오류·응답파손·응답초과·검문탈락이 최종 폴백을 결정해도 어느 attempt의 요청·원응답·검문 사유가 결정적이었는지 job에 남지 않는다. 회수와 늦은 응답이 존재하므로 attempt 번호나 시각으로 사후 추정할 수도 없다.

- [P0] 실행 봉투에 `schema_ver`가 없다 — job은 model·prompt·policy·estimator 네 판만 고정하고, §3-5-b 봉투 표는 `schema_ver`를 최종 호출자가 넣게 한다. 배치 중 c12→c13 배포가 일어나면 c12 모양으로 적재한 draft가 c13이라고 기록되거나 새 검증기에 거절된다. 같은 배정일에 계약판이 섞여도 이를 차단하거나 사후 분리할 값이 없다.

- [P0] `policy_ver`가 실제 전이 코드를 전부 지문하지 않는다 — §5-1은 DB 함수 중 `jobs_finalize`·`jobs_finalize_due`만 `pg_get_functiondef`로 묶고, `jobs_load`·`jobs_claim`·`jobs_reclaim`·`jobs_release`·`jobs_load_one`의 실제 정의는 제외한다. 이 함수들은 대상·순서·재시도·구제를 바꾸므로 같은 policy 아래 다른 처치를 만들 수 있다. 더구나 옛 job을 새 `jobs_finalize_due`가 처리할 때 현재 함수 지문과 job 판을 대조하는 가드가 없어 새 동작이 옛 policy로 기록된다.

- [P0] cron의 `오늘`은 날짜 계약이 아니다 — §3-2-a는 UTC 16~22시에 RPC에 `오늘`을 넘긴다고만 적고 `Asia/Ulaanbaatar` 날짜를 만드는 SQL을 정의하지 않는다. 이 시간대에서 PostgreSQL `current_date`는 UB 배정일보다 하루 전이므로 구현자가 이를 쓰면 워커와 마감 스윕이 매일 전날 큐를 처리한다. 시그니처가 `_assign_date date`인 이상 정확한 식이 없으면 동결할 수 없다.

- [P0] 0-job 배치는 어느 판이 실행됐는지 영구히 잃는다 — §3-5-b는 실행판 네 칸을 jobs가 이미 가진다는 이유로 `generation_batch_runs`에서 뺐다. 그러나 이 표가 존재하는 핵심 사례인 전원 게임일은 job이 0건이라 참조할 job 자체가 없다. 그날 `target_count=0`을 낸 policy·estimator·schema를 나중에 복원할 수 없다.

- [P0] 실제 입력과 학생에게 간 산출물에 복수 정본이 남는다 — §3-5-b `_event`에는 `task_assigned.task_snapshot`과 `submission_row.task_snapshot`이 중복되고, §7·§11은 같은 생성 문장을 다시 `task_snapshot.문장`과 `payload.output_text`에 둔다. 요청도 `generation_attempts.request_body`와 `generation_input_text` 두 곳에 서지만 결정적 투영·일치 검사가 없다. `jobs_finalize`가 기계로 대조하는 복제는 `generation_outcome`뿐이라 학생이 듣는 문장과 답하는 문장이 다른 채 원자 착지할 수 있다.

- [P0] 계약 정본 저장소가 뒤집혀 있다 — 문서 머리의 정본 관계와 §11은 SYNK-talk의 `계약/수집_교정_계약.json`을 정본처럼 지목한다. 실제 `tools/계약동기화.js`는 SYNK-appsscript를 정본, SYNK-talk를 사본으로 선언한다. 문서대로 talk에서 c12를 작성하면 다음 동기화가 덮어쓰거나 두 저장소 계약이 갈린다.

- [P0] c12 닫힌 payload 목록을 구현할 원천이 없다 — §11-2는 목록 밖 payload 키가 현재 검증기에서 거절된다고 전제하지만 실제 `lib/이벤트검증.js`는 payload 키 전수 화이트리스트를 검사하지 않는다. C0 §177의 산문 목록은 기존 생산 필드 `choice_dimension`조차 빠져 있어 그대로 엄격화하면 현행 사건이 거절된다. 완전한 기계 목록 없이 “미지 키 거절”을 동결하면 새 세 칸이 무검증으로 통과하거나 기존 경로가 깨진다.

- [P0] `배정상태`가 C0와 앱 사이에서 고아다 — §3-1은 `배정상태=있음|없음|생성중`을 열지만 위치가 응답 봉투인지 `data[]`인지도 없고, 정본 C0 §4-3은 여전히 `data:[] = 오늘 배정 없음 → 고정 도입`으로 정의한다. 앱 어댑터·화면 소비 인수 조건도 없어 서버가 값을 보내도 앱이 무시할 수 있다. `jobs_load_one` 계약 오류는 빈 응답으로 떨어지고, 마감 뒤 남은 `대기|claimed`도 계속 `생성중`으로 읽혀 오류·없음·진행 중이 다시 뭉친다.

- [P1] 평가 결과 행 계약이 자기모순이다 — §8-B와 머리 F1은 “3→7칸”이라 쓰지만 실제 열거는 기존 3개에 5개를 더한 총 8개다. `case_id`에는 반복 회차를 포함하면서 중복 `case_id` 0과 “각 사례 정확히 2회차”를 동시에 요구하고, base case 식별자와 run 번호를 분리하지 않았다. `raw_response_hash`·`input_hash`의 알고리즘·인코딩·대상 바이트도 없다.

- [P1] 오프라인 평가의 `attempt_id`는 존속 가능한 고리가 아니다 — §8-B는 결과 JSON에 `attempt_id`를 필수처럼 싣지만 `generation_attempts`는 실제 learner·assign_date를 가진 production-shaped job에만 연결된다. 평가용 namespace·run kind·DB 환경 식별자가 없어 운영 장부에 합성 job을 넣거나, 재구축되는 개발 DB의 끊어진 UUID를 결과 정본에 남기는 두 구현만 열린다.

- [P0] 품질 초록이 잘못된 판 축에 묶인다 — §8-B의 현행 조합에는 `skill_taxonomy_ver`가 없어 런타임 기술 집합·라벨이 바뀌어도 옛 초록이 살아남는다. 반대로 `policy_ver`에는 cron·큐 회전·마감 시각까지 들어가므로 문장 품질과 무관한 배관 변경도 80회의 사람 채점을 다시 요구한다. 품질을 바꾸는 축은 놓치고 품질을 안 바꾸는 축은 묶어, 거짓 초록과 사람 손 폭증을 동시에 만든다.

- [P0] `닿았나` 소비자는 이름만 있고 데이터 계약이 없다 — §6-0 H3과 §12-17은 `lib/성과회수.js`를 확장해 skill별 후속 산출을 조인한다고만 한다. 실물 함수는 `(개입, 사건들, 기준시각)`만 받는 순수 함수이고, 별도 `corrections` 행을 누가 어떤 키·창으로 읽어 넘기는지 정의되지 않았다. 픽스처가 미리 조인한 배열을 주면 운영 생산자가 0이어도 초록이 되므로 저장만 선 채 소비가 끊긴다.

- [P0] 롤백 절차 폐기는 상위 정본 위반이다 — §12-21·27은 빈 DB 재적용을 롤백으로 부르며 롤백 절차 자체를 만들지 않는다고 한다. `docs/개발_분업.md` §5·§8-4와 L0 §8은 중간 실패·롤백 검증 및 롤백/전진 경로 기록을 필수로 둔다. 역마이그레이션을 새로 만들라는 문제가 아니라, 첫 학생 뒤 데이터를 보존하는 백업·기능 비활성화·전진 복구 절차가 0이라는 결함이다.

- [P1] `generation_batch_runs.finished_at`은 기술된 실패를 표현하지 못한다 — §3-5-b는 batch row와 jobs를 같은 트랜잭션에서 만들면서 `finished_at=null`을 “도중에 죽음”이라고 정의한다. 트랜잭션 중 죽으면 batch row도 롤백되므로 그 null 상태는 지속될 수 없다. `assign_date` PK에 대한 재실행 시 `ON CONFLICT` 계약도 없어 성공한 오케스트레이터 재호출이 멱등 반환인지 예외인지 열려 있다.

### 이 문서보다 나은 대안 구조 1개
