### 발견 항목

- [P0] `미상`이 정상 재학생과 실패를 같은 상태로 만든다 — §5 ㉣②. 사건이 없으면 무조건 `미상`인데, 정상 명부 인제스트가 성공했을 때 `재학`으로 만드는 규칙이 없다. 따라서 정상 재학생·인제스트 실패·레거시 미확인이 모두 같은 값이 되어 졸업생 뷰와 배치 감시가 조용히 틀린다.

- [P0] append-only가 멱등 계약이 아니다 — §5 ㉡②, §6. `exit_log`에 불변 `event_id`, 원천 행 ID, 원천 버전, 이벤트 지문, 처리 커서가 없다. “학생 + 마지막 사건 이후”라는 기준도 정의되지 않아 재실행 시 중복 기록하거나 새 사건을 놓치며, 나중에 `enrollment_episodes`로 접을 때 어느 행이 같은 사건인지 복원할 수 없다.

- [P0] 자동 감지와 수동 판정의 기록 단위가 없다 — §5 ㉡, ㉣. 현재 감지기는 `payStatus === '퇴소'`를 보고 행을 만들지만, 새 행에는 원장이 `종료사유`와 `effective_at`을 적어야 한다. 미완성 행을 허용하면 빈 사유가 실제 종료처럼 남고, 입력을 기다리면 감지 시점이 사라지며, 기존 행을 나중에 수정하면 append-only가 깨진다.

- [P0] 단일 파생 열로 복학·재퇴소를 표현할 수 없다 — §5 ㉡②, ㉣, §8. `lifecycle_status`, `exit_reason`, `effective_at`은 모두 학생당 한 칸인데 휴학→복학→재퇴소의 상태 전이와 복귀 사건이 정의되어 있지 않다. `enrollment_episodes`를 미루는 동안 첫 학생에게 이 일이 발생하면 과거 상태와 현재 상태를 구분할 수 없다.

- [P0] “번호는 다시 발급되지 않는다”가 기계적으로 보장되지 않는다 — §3, §5 ㉠. `student_code` 변경 트리거만으로는 자식 기록이 없는 `learners` 행 삭제를 막지 못하고, `UNIQUE`도 삭제된 과거 번호를 기억하지 않는다. 코드 폐기 원장이나 삭제 금지 장치가 없으므로 직접 삭제·재삽입 경로에서 번호 재사용이 가능하며, `NULL → 코드` 초기 할당 예외도 정의되지 않았다.

- [P0] Apps Script 채번과 Supabase 저장이 분리된 채로 남아 있다 — §5 ㉠, ㉣-2, §7. `LockService`는 Apps Script 내부만 잠그며 시트 기입과 DB insert를 하나의 커밋으로 묶지 않는다. 시트만 성공하거나 DB만 성공한 뒤 재시도할 때 이를 복구할 불변 발급 사건·outbox·상태표가 없어 고아 번호와 미생성 학생이 남는다.

- [P0] `roster-ingest`의 충돌 판정은 동일인을 판정할 수 없다 — §5 ㉣-2. 문서는 기존 행과 새 행의 `learner_id·이름`을 비교하라고 하지만 새 학생에게 기존 `learner_id`가 있다는 보장이 없고, 이름은 신원 키가 아니다. 원천 등록 행 ID와 정확한 정규화 규칙이 없으므로 새 학생의 번호 충돌을 정상 재전송으로 삼키거나 정상 재전송을 사고로 처리할 수 있다.

- [P0] 과거 기록의 `learner_id` 매핑이 절차 이름만 있다 — §7. “행 수를 센 뒤 매핑 사건을 한 번 만든다”고 했지만 원천 행 식별자, 대상 UUID, 매핑 근거, 모호한 후보 처리, 재실행 키, 결과 스냅숏이 없다. 상담시트에 학생 ID가 하나라도 존재하면 소급 조인이 필요한데, 이 문서만으로는 그 결과를 재현하거나 검수할 수 없다.

- [P0] `enrolled_at`이 모르는 날짜를 현재 시각으로 위조할 수 있다 — §5 ㉣③, §2 ⑦. 현재 구현은 `regD || 보존값 || now`이고, 문서는 등록일이 없거나 파싱에 실패했을 때 `unknown`으로 남기거나 거부하는 변경을 정하지 않았다. 그 결과 실제 미상 날짜가 진짜 입학일처럼 저장되어 재원일수·시즌 귀속이 영구적으로 오염된다.

- [P0] 세 시각의 달력 의미와 유효성 제약이 없다 — §5 ㉣①, ㉣④. `effective_at`은 사람이 적는 “실제 날짜”인데 필드 타입은 `timestamptz`이고 원장 지역, 시각 정밀도, 날짜만 입력할 때의 기준 시각, 허용되는 순서가 정의되지 않았다. `effective_at < enrolled_at` 또는 `effective_at > observed_at` 같은 잘못된 값이 저장되어도 막을 장치가 없다.

- [P0] 마지막 완료 시즌이 학습 증거를 버리는 구조다 — §5 ㉡, §6-2. 시즌 ID가 아직 없으면 칸을 적지 말라고 했지만, 시즌 완료·부분 완료 사건이나 원천 결과를 별도로 보존하지 않는다. 나중에 시즌 규격을 만든 뒤에는 퇴소 행만 보고 마지막 완료 시즌을 복원할 수 없으며, `aiStudioBatch_` 소비자 표기도 실제 입력 계약·조회·출력물을 대신하지 못한다.

- [P0] §7은 실측 목록이지 동결 검증 계약이 아니다 — §7. 운영 DB 형상, `exit_log` 행 수, 학생 화면, 기존 학생 ID 수를 확인하지 않았고, 기준 스냅숏·합격 수치·중단 조건·롤백 검증 결과도 없다. 그런데 §6은 이 미확인 상태를 전제로 즉시 마이그레이션을 계획하므로, 잘못된 전제와 부분 적용이 정상으로 확정될 수 있다.

- [P1] 10년 연속성의 핵심 연결 사건이 여전히 없다 — §4, §6. 현재 `learner_id`는 DB 내부 키일 뿐이고, 미래 B2C 계정과 이를 연결하는 `learner_account` 사건 및 동일인 병합 규칙은 개원 전으로 미뤄졌다. 따라서 이 문서는 “다시 짓는 범위를 줄인다”는 가능성만 남기고, 바트가 실제로 새 계정으로 돌아오는 실행 가능한 경로는 동결하지 못한다.

- [P1] 학생 접점이 기본 게이트를 통과한다는 근거가 없다 — §5 ㉢, ㉤, §7. 졸업 카드와 복구 주소 입력은 학생이 보는 기능인데, 회사가 장기 조인에 쓰기 좋다는 설명만 있고 학생이 왜 다시 열고 보관할지, 한국어·개인 목표에 어떤 도움을 주는지, 무엇이 신선한지 없다. 번호가 앱 화면에 실제로 보이는지도 미측정이므로 학생은 자기 번호를 알지 못한 채 졸업할 수 있다.

- [P1] “사람 손은 판단 하나만” 규칙이 구현 단위로 내려오지 않았다 — §5 ㉡, §6-2. 원장은 종료사유·실제 종료일·완료 시즌을 각각 입력해야 할 수 있지만 어떤 하나가 유일한 판단이고 나머지는 자동 검증되는지 정해지지 않았다. 필수값·입력 큐·미정 전환·수정 사건이 없어 반복적인 시트 관리가 사람 손으로 남는다.

- [P1] 사람이 읽는 번호의 정규형이 없다 — §3, §5 ㉠, ㉣-2. `student_code text unique`만으로는 대소문자·공백·하이픈·선행 0을 통일하지 못하며, Sheets와 Postgres의 비교 규칙도 없다. `SYNK-042`, `synk-042`, `SYNK-042 `가 서로 다른 값으로 저장되어 번호 충돌 감지와 로그인 조인이 갈라질 수 있다.

### 이 문서보다 나은 대안 구조 1개

Postgres에 `learner_lifecycle_events`를 먼저 원장으로 두고, 모든 사건에 `event_id`, `learner_id`, `event_type`, `observed_at`, `effective_at`, `source_ref`, `idempotency_key`, `recorded_at`, `schema_ver`를 필수로 둔다. Sheets는 사건 입력 어댑터로만 쓰고, `learners`의 상태·사유·시간은 이 원장에서 재생성되는 projection으로 만든다. 재학·휴학·복학·졸업·중도이탈과 시즌 완료를 각각 사건으로 기록한 뒤, 별도의 상태 전이 규칙으로 현재 상태를 계산해야 한다.
