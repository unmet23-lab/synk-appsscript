지적 28건 — 동결 불가.

[P0] 계약 판과 동결 판이 다르다 — §0은 필드 정본을 c6이라고 쓰지만 실제 계약 파일은 c8이고, §9는 event_type 9종인 c4 상태로 남아 있다. §8은 c8 DB 제약·마이그레이션을 동결 조건으로 요구하지 않아 c8 앱과 c4 DB가 동시에 “통과”할 수 있다. 문제 절: §0·§8·§9.

[P0] 유일한 쓰기 통로가 거짓이다 — §1·§4-1은 모든 이벤트가 `/v1/events`를 거친다고 하지만 `deliver`는 `learning_events`와 `submissions`에 직접 SQL을 쓴다. 이 경로는 events의 동의·멱등·payload·서버필드 검증을 우회하므로 같은 사건이 서로 다른 품질로 저장된다. 문제 절: §1·§4-1.

[P0] 훈련 승격 사건이 이름만 있다 — §9는 `data_use.granted`를 추가했지만 artifact_ref, content_hash, serializer_ver, dataset_ver, consent_id, 비식별화 버전, 승인자, 평가 결과, 철회·롤백 고리를 담는 payload 계약이 없다. L0 §6-2의 필수 계보를 재현하거나 철회할 수 없다. 문제 절: §4-1 payload·§9.

[P0] 세션 폐기가 문장뿐이다 — §4-5는 재발급 시 기존 access token까지 차단한다고 하지만 Edge Function은 JWT의 `sub`만 읽고 `engine.session_alive()`나 `revoked_before`를 검사하지 않는다. 직접 DB 연결은 RLS도 우회하므로 옛 토큰이 만료될 때까지 조회·쓰기·업로드를 계속할 수 있다. 문제 절: §2·§4-5.

[P0] 동의 사전 게이트가 앱에 연결되지 않았다 — §5·§7은 녹음 화면 진입 전에 동의를 막고 서버로 나가는 이벤트를 0건으로 요구하지만 현재 말하기 화면에는 그 게이트가 없다. 과제가 없거나 조회에 실패해도 녹음은 진행되고, 제출 API는 로컬 기록을 버리므로 첫 발화가 복구 불가능하게 사라진다. 문제 절: §4-2·§5·§7.

[P0] 업로드 재시도가 영구 고아 파일을 만든다 — §4-2는 업로드 후 이벤트 전송 순서를 강제하지만 서명 때마다 새 UUID 경로를 만들고 이벤트 실패 뒤의 파일 삭제·재사용·정산 절차가 없다. 응답 유실이나 재시도마다 무한 보존 대상 파일이 남아 철회 시 수동 삭제 목록과 실제 저장물이 갈라진다. 문제 절: §4-2.

[P0] 신뢰하지 않는 `occurred_at`이 동의 효력을 결정한다 — §3은 미래 시각을 허용하면서 로그만 남긴다고 하지만 실제 동의 조회는 `occurred_at`을 기준으로 유효성을 판정한다. 기기 시계를 미래로 조작하면 실제 철회 뒤 사건이 동의 기간 안으로 판정될 수 있고, 별도 서버 관측시각·시계오차 판정도 없다. 문제 절: §3·§4-1·§5.

[P0] 멱등키 규칙이 시행되지 않는다 — §4-1은 앱 키를 UUID v4로 요구하지만 현재 앱은 `submission:날짜:단계:시도` 문자열을 보낸다. 서버는 형식과 payload hash를 검사하지 않으므로 같은 키로 내용이 바뀌어도 새 사건이 아니라 옛 사건의 `duplicate`로 조용히 접힌다. 문제 절: §4-1.

[P0] `correlation_id`가 서술상 필수일 뿐이다 — §4-1은 발화에서 사실상 필수라고 하지만 이벤트 검증기는 이를 필수로 걸지 않고 앱도 fallback에서 `null`을 보낸다. 저장된 뒤에는 같은 앉음의 낭독·자유발화를 연결할 근거가 없어 소급 복구가 불가능하다. 문제 절: §4-1.

[P0] S1 필수 학습 증거가 계약에서 빠졌다 — 제품 계약이 요구한 mission_id, target phoneme, duration, hesitation_ms, 재생 사건과 재시도별 관측값이 C0 payload 규격에 없다. 현재 앱은 일부 값을 로컬에서 측정하고도 전송하지 않으므로 첫 데이터가 쌓이는 순간 회복할 수 없다. 문제 절: §4-1 payload·§7.

[P0] 엔진 문맥 필드가 예시일 뿐 필수가 아니다 — `goal_snapshot`, `skill_ids`, `task_snapshot`은 요청 예시에 있지만 공통 필수 검증에는 없고 이벤트별 필수성도 대부분 정의되지 않았다. 누락된 목적·스킬·과제 문맥을 나중에 현재 학생 상태나 현재 과제에서 복원하면 과거 사실이 아니라 추정값이 된다. 문제 절: §4-1.

[P0] 스킬·개입·회수 사슬에 생산자가 없다 — C0에는 `skill_ids`, `model`, `prompt_ver`, `cited_refs`가 보이지만 앱 제출기는 skill_ids를 보내지 않고 서버 배달기는 model·prompt·citation을 저장하지 않는다. 따라서 기능→스킬→개입→성과→평가셋의 연결이 끊겨 약점 지도와 개입 효과를 회수할 수 없다. 문제 절: §4-1 서버/앱 필드표·§4-3①.

[P0] payload 검증 약속이 실행되지 않는다 — §4-1은 `payload.ver` 필수와 빈 껍데기 거부, 미등록 필드의 c9 승격을 요구하지만 실제 검증기는 `{}`와 임의 키를 허용한다. `options_shown` 같은 배열도 문자열 형태로 통과하므로 의미가 다른 행이 동일한 정상 데이터처럼 쌓인다. 문제 절: §4-1 payload.

[P0] 과제 스냅샷이 제출 사건에 강제되지 않는다 — §9는 `task_snapshot`을 소급 불가 원본 고리로 추가했지만 제출 검증기는 이를 요구하지 않고 현재 앱도 `task_snapshot`과 `task_schema_ver`를 보내지 않는다. `task_ref`만 남으면 문항·보기·정답·지시문 개정 후 학생이 실제로 본 내용을 재현할 수 없다. 문제 절: §4-1 요청 예시·§4-3①·§9.

[P0] 교정 응답의 실제 학습 결과가 없다 — `correction.responded`는 correction_id와 모호한 `learner_response`만 요구하며 수정된 문장·음성·변경 전후를 필수화하지 않는다. 학생이 “수정했다”는 사건만 남고 무엇을 어떻게 고쳤는지는 남지 않아 교정 효과와 오류 재발을 학습할 수 없다. 문제 절: §4-1 correction_id·§4-3②.

[P0] 하위호환 선언이 c8에서 깨진다 — §6은 구 앱이 계속 작동한다고 하지만 서버는 c6 헤더를 받아도 현재 c8 검증기를 사용하고 c8에서 추가된 correction_id를 요구한다. 구 앱의 correction 이벤트는 426 업데이트 안내가 아니라 항목별 400 격리로 사라진다. 문제 절: §4-1·§6.

[P0] 동결 시험이 실제 소비자 경로를 검증하지 않는다 — §7은 Mock 서버의 6개 시나리오만 동결 조건으로 삼고 조회·Storage·직접 SQL 배달·세션 폐기·실제 마이그레이션·실기기 음성을 제외한다. 현재 교정 왕복시험은 API가 아니라 SQL로 사건을 심어 F179 같은 API 결함을 놓쳤으므로 초록이 실제 통과를 증명하지 않는다. 문제 절: §7·§8.

[P0] 원본 제출물이 실제로 불변이 아니다 — L0의 trigger는 일부 원문만 보호하고 task_snapshot, task_ref, audio_ref, capture_meta 등의 수정과 제출 행 삭제를 막지 않는다. service_role 직접 경로가 동일 event_id의 원본 문맥을 바꿀 수 있어 이후 교정·훈련 결과가 어느 시점의 증거인지 증명할 수 없다. 문제 절: §4-1·관련 L0 스키마.

[P0] 음성 기준선이 첫 수집부터 위반된다 — §4-2는 PCM WAV 16kHz/16bit/mono를 정본으로 못박지만 현재 Expo 녹음 설정은 HIGH_QUALITY m4a/AAC다. 규격 밖 파일을 저장하면서 §8의 동결 시험에는 실기기 헤더 검사가 없어 압축으로 사라진 발음 신호가 정상 학습 데이터와 섞인다. 문제 절: §4-2·§8.

[P0] 토큰 만료 후 1회 재시도가 구현되지 않았다 — §5·§7은 401을 갱신 후 한 번 재전송하도록 하지만 현재 제출 API는 직접 fetch만 하고 refresh 경로가 없다. 응답이 표준 봉투가 아닌 401이면 retryable 판정도 잃어 오프라인 큐의 사건이 영구 격리될 수 있다. 문제 절: §5·§7.

[P1] 외부 correction_id 오류가 재시도 가능한 서버 오류가 된다 — §4-1은 다른 학생의 correction_id를 서버에서 막지만 실제 FK·trigger 오류는 5xx/SERVER_ERROR 경로로 흘러간다. 영구적인 참조 위반을 재시도 대상으로 만들면 큐가 같은 잘못된 항목을 계속 들고 있고 원인이 계약 위반인지 장애인지 구분되지 않는다. 문제 절: §4-1·§5.

[P1] 날짜·커서 형식 검증이 표면적이다 — `tasks`는 정규식만 통과한 `2026-02-31`을 DB cast까지 보내 500이 될 수 있고, corrections는 36자 비UUID cursor를 허용한 뒤 DB에서 실패할 수 있다. `progress`도 지나치게 큰 attempt_no가 정수 overflow를 일으켜 조회 전체를 500으로 만들 수 있다. 문제 절: §4-3·§5.

[P1] 빈 교정 필터가 문서와 다르다 — §4-3②는 빈 corrected_text와 빈 error_tags를 목록에서 제외한다고 하지만 실제 조건은 `IS NOT NULL`이라 빈 문자열은 통과한다. 학생 화면에 빈 카드가 나타나고, “교정이 전달됐다”는 사건과 “표시할 교정 내용이 있다”는 사실이 섞인다. 문제 절: §4-3②.

[P1] 업로드 크기와 종류를 실제 파일로 검증하지 않는다 — §4-2의 25MB 검사는 서명 요청의 client byte_size에 의존하고 PUT 후 실제 크기를 차단하지 않는다. 경로 검사도 audio_ref가 voice 폴더인지 image_ref가 image 폴더인지 결속하지 않아 잘못된 장기 보존 파일이 정상 참조처럼 남는다. 문제 절: §4-2.

[P1] 동의 오류의 HTTP 상태가 서로 다르다 — §5는 `CONSENT_MISSING`을 409로 정의하지만 uploads sign 구현은 403으로 반환한다. 앱이 상태코드와 code를 함께 분기하면 녹음 전 차단·재시도·개발자 보고가 경로마다 달라진다. 문제 절: §4-2·§5.

[P0] 철회 전파가 저장 이후에 정의되지 않았다 — §10은 삭제·철회 API를 미루고 수동 운영으로 남겼지만 Storage 객체, 원본 이벤트, 승격 산출물, 데이터셋·모델에서 무엇을 언제 제외했는지 기록하는 계약이 없다. 철회 뒤 수집 0건과 훈련 사용 0건을 실측하거나 증명할 수 없으므로 장기 엔진 데이터의 법적·계보적 상태가 끊긴다. 문제 절: §4-1·§4-2·§10.

[P1] 배달 배치의 대상 집합과 동의 판정이 어긋난다 — 배치 점검은 모든 learners를 재적으로 세지만 실제 배달은 동의 없는 학생을 건너뛰고, 미래 시각의 동의도 현재 동의처럼 취급한다. 결과적으로 “배정 실패 없음” 또는 “실패 있음” 모두가 실제 학생 대상과 다른 수치가 될 수 있다. 문제 절: §4-1·§4-3①.

[P1] 첫 등록 결과 계약이 상호 배타적이지 않다 — §4-4 성공 표에는 이미 등록된 경우 `already:true`가 있지만 게이트 실패 표에는 이미 등록됨이 401로 들어 있다. 클라이언트는 계정이 이미 선 정상 상태인지 실패 상태인지 일관되게 판정할 수 없다. 문제 절: §4-4.

C0를 서술문이 아니라 `c8` 기준 기계계약으로 재구성한다. 이벤트별 요청·응답·필수성·payload JSON Schema, 서버 내부 writer가 공통 ingest kernel을 호출하는 규칙, payload hash를 포함한 멱등키, upload intent–finalize–orphan reconciliation, consent/session 검증, 실제 DB·Storage·실기기까지 포함한 동결 매트릭스를 하나의 버전 묶음으로 관리해야 한다.
