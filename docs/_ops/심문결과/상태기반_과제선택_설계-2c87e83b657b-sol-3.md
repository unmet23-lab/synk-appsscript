동결 불가. 지적 21건.

1. [P0] 실행예산이 호스팅 상한을 초과한다 — §3-2의 `생성총예산_MS=600000`은 현재 Supabase Edge Function의 wall-clock 상한 400초보다 길다. 플랫폼이 폴백·원자 착지 전에 함수를 종료할 수 있으므로, 뒤 학생 배달은 끊기고 claim만 남는다. [Supabase 공식 한도](https://supabase.com/docs/guides/troubleshooting/edge-function-wall-clock-time-limit-reached-Nk38bW)

2. [P0] `correlation_id`를 닫힌 의미와 다른 일일 묶음 키로 바꾼다 — §3-0·§12-12는 야간의 `task.assigned`·`intervention.delivered`·`submissions`에 같은 값을 요구한다. 공용 계약은 이를 `learning_events`의 흐름 봉투에 두며, 닫힌 결정은 `🚫서버가묶기`다. 미래 앱 세션을 야간 서버가 미리 정하면서 세션 흐름과 일일 배달 묶음이 영구히 섞인다.

3. [P0] claim 상태기계에 소유권 펜싱이 없다 — §3-5에는 lease 소유자·fencing token·시도 번호·최종 event ID가 없다. 승자가 벤더 호출 중이면 패자는 재조회할 배정이 아직 없고, 24시간 후 재개방 뒤에는 죽었던 승자가 되살아나 새 실행과 동시에 착지할 수 있다. 유일키 하나로는 외부 호출 소유권을 보장하지 못한다.

4. [P0] 구제 경로가 claim을 건너뛰어 배치와 경쟁한다 — §3-1은 구제 시 ②~⑤를 통째로 건너뛰므로 claim도 잡지 않는다. 구제가 폴백을 착지하는 동안 배치가 생성하거나, 배치가 claim만 잡은 동안 구제가 폴백을 착지하면 최종 유일키가 사후에 승자를 정한다. 생성 결과 유실·stuck claim·응답 불일치가 정상 경로다.

5. [P0] `generation_outcome` 값목록은 문서가 요구한 행에 기록할 수 없다 — §3-4는 게임날에 `intervention.delivered`를 만들지 않지만 §4-1은 게임날을 `대상아님`으로 정의한다. `이미배정`도 두 번째 행을 만들거나 기존 불변 행을 고칠 수 없어 저장되지 않는다. 따라서 §12-7의 “14값 각각 자기 행에 남는다”는 인수 조건은 원리상 통과 불가능하다.

6. [P0] 부분 실패가 정상 분포로 위장한다 — §3-0은 착지 실패 시 세 행을 모두 없애고, §12-8은 존재하는 `intervention.delivered`만 분모로 센다. 일부 학생이 착지 전에 사라져도 분모만 줄어 각 사유 비율은 여전히 100%가 된다. §12-13은 claim 장부를 운영 소비자가 읽는 것까지 막아 이 누락을 탐지할 통로도 제거한다.

7. [P0] `as_of`가 실제 읽기 스냅샷을 보장하지 않는다 — §11-4는 `occurred_at <= as_of`만 요구한다. `as_of` 뒤에 적재됐지만 발생 시각이 더 이른 사건은 읽는 순간에 따라 포함되므로, 같은 `as_of`와 같은 판에서도 입력이 달라진다. `ingested_at` 경계나 동일 DB snapshot 없이 “당시 입력은 재계산하지 않는다”는 주장은 성립하지 않는다.

8. [P0] 입력 스냅샷의 저장 위치를 동결 후보가 스스로 미결로 둔다 — §6-1은 `evidence_refs`가 참조 필드임을 인정하면서 `as_of`·창일수·쓴축을 얹고, 계약이 거절하면 나중에 payload로 옮긴다고 적는다. 한 설계 안에서 정본 위치가 두 갈래이며, 절단 여부·읽기 범위 판도 모양에 없다. 이 상태로 쌓기 시작하면 같은 입력 메타가 서로 다른 구조에 남는다.

9. [P0] `position`에 두 의미를 섞는다 — §11-5는 배치 처리 순서를 기존 `position`에 기록한다. 현행 계약에서 `position`은 학생에게 보인 선택지의 표시 위치이며 선택로그 검증도 그 의미를 강제한다. 배치 순서를 넣으면 과거 선택 위치와 처리 순서를 사후 분리할 수 없다.

10. [P0] `payload.ver=2`의 적용 사건과 필수성 경계가 없다 — §11-2의 새 세 필드는 `intervention.delivered`에 싣는데, 판올림 근거는 `task.assigned.payload={ver:1}`이다. 동시에 `generation_outcome`을 모든 intervention 행에 필수라 하면서 과거 v1 행은 그대로 둔다. 어느 사건의 판을 올리고 어떤 판부터 필수인지 정하지 않아 검증기·소비자가 서로 다른 payload를 정본으로 삼게 된다.

11. [P0] 출시 게이트가 다른 제품을 시험한다 — §8·§12-14의 102문항은 오류 62건·정상 40건으로 이루어진 교정·오류태그 평가셋이다. 생성 문장과 질문의 연결성·답변 가능성·수준 적합성·신선함을 한 건도 재지 않는다. 102문항 통과가 생성 과제 품질의 초록으로 표시된다.

12. [P0] `0.2` 문턱이 닫힌 “문턱 분기 금지” 결정을 위반한다 — §2는 상태를 짓는 재료로만 쓰고 분기 잣대로 쓰지 못하게 한다. §4-3은 `estimator_confidence < 0.2`면 생성 대신 폴백으로 갈라, 비어 있지 않은 상태도 숫자 문턱으로 처치를 바꾼다. 이를 “입력 유무”라고 개명해도 실행 동작은 문턱 분기다.

13. [P0] 생성 과제와 한국어 기술의 고리가 없다 — 현행 계약에는 이미 `skill_ids`가 있는데 §6-1은 `skill_id`를 미래 트랙으로 밀고, 대신 성향 축 이름인 `쓴축`만 남긴다. 학생 답과 후속 오류가 쌓여도 어떤 문법·어휘·TOPIK 기술을 겨냥한 개입이었는지 복원할 수 없다. §9가 인정한 대로 이 구조는 “무엇이 통했는지”를 기술 단위로 학습하지 못한다.

14. [P1] 탈락한 모델 원출력이 영구 소실된다 — §11-2는 실제 입력만 저장하고, `응답파손`·`검문탈락` 때 받은 원응답은 저장하지 않는다. 비결정 모델 출력은 같은 입력으로 재생성할 수 없으므로, 검문 오판 감사와 생성 전용 평가셋 승격 재료가 사라진다.

15. [P1] `policy_ver` 지문이 처치를 바꾸는 규칙을 빠뜨린다 — §5-1의 여섯 재료에는 초급 제외, 처리 순서 회전, 입력 8000 상한, claim 24시간, 구제 분기, 읽기 절단 규칙이 없다. 특히 §11-5는 순서가 생성 여부를 바꾼다고 인정한다. 이 값들이 달라도 모두 `오늘과제.v4`로 합쳐진다.

16. [P1] 인수 조건이 실제 성과 소비자의 관측 고리를 검사하지 않는다 — §12-3은 배정·조회·제출까지만 관통한다. `성과회수`가 요구하는 `content.viewed.parent_event_id → intervention.event_id` 연결은 인수 조건에 없다. 제출은 생겨도 소비자가 읽는 즉시성과가 0건인 상태로 통과할 수 있다.

17. [P1] 두 모델 출력이 실제 과제 구조로 어떻게 내려가는지 닫히지 않았다 — §5-3은 `sentence`·`question` 두 문자열을 받고, §7은 세 호흡과 기존 `output_text`·`task_snapshot`을 사용한다. 어느 문자열이 어느 호흡과 `output_text`에 들어가는지 명시하지 않고, `task_type`도 값 대신 “기존 ③행과 같은 값”이라고만 쓴다. 구현마다 다른 과제를 만들 수 있다.

18. [P1] 「실제로 사용할 한국어에 도움」 게이트가 없다 — §8은 길이·한글 비율·서식·물음표만 검사한다. 문장과 질문이 서로 무관하거나, 답할 수 없거나, 학생 수준·목표와 동떨어져도 `성공`으로 배달된다. 학생이 말하게 만든다는 형식만 있고 그 산출이 학습에 유효한지는 비어 있다.

19. [P1] 학생이 왜 다시 열어야 하는지 답이 없다 — §2·§7은 문장 하나와 질문 하나만 정의하며 선택감·도전·즉시 반응·서사·보상 중 어느 재방문 장치도 없다. 상태 숫자를 프롬프트에 넣는 것은 개인화 배관이지 재미의 학생 경험이 아니다. 판단 정본의 「재미」 층이 비었다.

20. [P1] 신선함 실패를 정상 배달로 허용한다 — §7-2는 전날 `task_snapshot`을 통째로 재사용하고 §11-3은 생성문의 우연한 중복도 허용한다. 왜 같은 과제를 다시 하는지나 무엇이 달라졌는지 학생에게 주지 않는다. `degraded=true` 표시는 운영 메타일 뿐 학생 접점의 「신선함」 결함을 고치지 않는다.

21. [P1] 초급·미정 학생에게 개인화 기능이 0이어도 완료된다 — §7-1은 1~2급과 미정을 전부 제외하고 §14는 개원 초기 도달 학생이 0명일 수 있음을 인정한다. 기존 고정 과제는 남지만 이 문서가 약속한 “상태를 읽어 짓는 문장”은 제공되지 않는다. 사후 분포 보고는 학생 경험의 공백을 고치지 않는다.

이 문서보다 나은 대안 구조 1개: 학생별 일일 배달을 `대상 판정 → fenced claim → 생성 시도 기록 → 검문 → 원자 착지 → 관측·성과 회수`의 명시적 상태기계로 분리한다. `correlation_id`는 실제 학습 세션 의미를 유지하고 사건 연결은 기존 event/parent 키를 쓰며, 구제도 같은 일일 소유권 아래에서만 폴백을 착지하게 한다. 생성 입력은 구조화 스냅샷, 성공·탈락 원출력, 기존 `skill_ids`를 함께 남기고 생성 전용 평가셋을 별도 출시 게이트로 둔다.
