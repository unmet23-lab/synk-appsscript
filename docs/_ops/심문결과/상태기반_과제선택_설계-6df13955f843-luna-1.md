지적 13건.

1. [P0] `적재실패`는 자동 복구되지 않는다 — §3-5-b ㉠·§3-2-a·§12-21  
문서는 `적재실패`를 워커와 마감 스윕이 집지 않게 하고, 오케스트레이터 재실행 때만 `대기`로 되돌린다. 그러나 워커 재호출 조건은 실행 행 부재 또는 `finished_at=null`이고, 학생별 조립 실패는 `partial_count`를 남긴 채 완주할 수 있다. 학생이 `/tasks`를 열지 않으면 해당 학생의 `task.assigned`와 `intervention.delivered`가 영원히 생기지 않으며, 감시는 복구가 아니라 적색 보고에 그친다.

2. [P0] 구제 경로가 날짜·실행판 스냅샷을 오염시킨다 — §3-5-b `jobs_load_one`  
당일 시작 행이 없으면 가장 최근 시작 행의 실행판을 쓰고, 신규 구제 job은 `batch_run_id` 없이 `snapshot_as_of=now()`로 만들어진다. 이전 날짜의 `model`·`prompt_ver`·`policy_ver`·추정판이 오늘 사건에 기록될 수 있고, 같은 날짜를 여는 학생마다 서로 다른 상태 시점을 받을 수 있다. append-only 사건이므로 잘못된 날짜 계보와 입력 시점은 사후 복구할 수 없다.

3. [P0] `/tasks`가 아직 생성 경로를 호출할 수 있다 — §3-1·§12-11  
문서는 `tasks/index.ts:85`에 `&맥락=구제`를 붙이라고 하지만 실제 호출부는 현재 `learner_id`만 전달한다. 같은 문서가 맥락 누락의 기본값을 `배치`로 정했으므로, 정상적인 학생 화면 조회가 벤더 호출 경로로 들어갈 수 있다. “구제는 벤더 0회”라는 핵심 계약이 구현 전부터 깨져 있으며, 화면 조회가 동기 생성 대기로 변한다.

4. [P0] `payload.ver`가 금지된 생산자 식별자로 사용된다 — §3 ②'·§11-2·§13  
이력 조회는 `task_type='발화녹음'`과 `payload.ver=이 계약의 판`으로 생성 행을 가른다. 그런데 같은 문서는 `ver`가 사건 모양 판일 뿐 생산자 표식이 아니며, 다른 생산자도 `ver=2`를 쓸 수 있다고 명시한다. 별도 생산자 식별자가 없으므로 다른 개입이 중복 이력과 기술 회전에 섞이고, 잘못 포함된 원본 이력은 소급 수정할 수 없다.

5. [P0] `roster_hash`는 명단 스냅샷이 아니라 해시 하나다 — §3-5-b `batch_runs`·`batch_run_start`  
저장되는 것은 `roster_hash`, 재적 수, 급수 분포뿐이며 `_enrolled`의 실제 구성원과 `_targets`의 학생별 대상 사이를 묶는 제약이 없다. `loaded_count + skipped_game_count + skipped_existing_count = enrolled_count`만 맞추면 다른 학생을 넣거나 한 학생을 빠뜨려도 완주 행이 될 수 있다. 잘못된 학생에게 개인화 과제가 배정되거나 누락돼도 `finished_at`이 정상으로 남는다.

6. [P0] 상태 근거가 학생·사건·요약에 물리적으로 결속되지 않는다 — §3-5-b `event_draft`·`jobs_finalize`·§6-1  
문서가 실제로 검사하는 것은 `task_ref`의 학생·날짜와 `evidence_refs.as_of`의 시점 정도다. `evidence_refs.events`가 같은 학생의 사건인지, `occurred_at`·`ingested_at` 경계를 만족하는지, `axes_used`가 실제 요약 문자열과 일치하는지는 계약상 강제되지 않는다. 같은 `as_of`만 맞춘 잘못된 상태 근거가 정상 착지해 학습자 모델을 오염시킨다.

7. [P0] `as_of`·`ingested_at` 스냅샷은 아직 물리 배선이 아니다 — §11-4 C4·D1  
문서는 `ingested_as_of` 옵션과 조회층 수정을 “선행 작업”으로 적었지만, 실제 `lib/학습자상태.js`는 `ingested_at`을 필터링하지 않고 `deliver` 원신호 조회도 `now()` 기준 창을 사용한다. 첫 생성 행이 늦게 적재된 사건을 포함하거나 워커 시점에 따라 다른 입력을 쓰면, 문서의 `evidence_refs`와 실제 생성 입력이 달라진다. append-only 사건이 쌓인 뒤에는 당시 어떤 상태로 생성했는지 복원할 수 없다.

8. [P0] §8-B 평가 게이트는 실제 배포를 차단하지 못한다 — §8-B·§12-14·§16-1  
문서는 평가 결과가 아직 없고 Actions가 정지했으며 수동 경로를 모두 기계적으로 막지 못한다고 인정한다. 그런데 활성 조건은 프롬프트 파일 존재와 결과 파일 회귀 검사에 머물러, 현재 `quality_ver` 결과가 없어도 생성 경로를 켤 수 있다. 따라서 재미·실사용 도움·신선함을 포함한 학생 접점 기본 게이트가 미실행 상태로 학생에게 노출될 수 있다.

9. [P1] 실행 완료 등식이 음수·초과 건수를 허용한다 — §3-5-b `batch_runs` 제약  
`skipped_game_count`와 `skipped_existing_count`에는 음수·재적 초과 제약이 없고, 두 값을 합친 등식만 있다. 예를 들어 `loaded_count=0`, `enrolled_count=17`, `skipped_game_count=-1`, `skipped_existing_count=18`은 제시된 CHECK를 통과한다. 이런 행도 `finished_at`을 가질 수 있어 전원 처리 보고와 실제 학생 처리가 달라진다.

10. [P1] `skill_ids`는 실제 기술 체계의 참조가 아니다 — §3-5-b·§6-0·§12-17  
물리 제약은 배열 개수 1~2와 `skill_taxonomy_ver` 비공백만 확인하며, ID가 `engine.skills`에 존재하는지 또는 해당 버전에 속하는지 묶지 않는다. 삭제·오탈자·다른 분류판의 ID가 생성 성공 행에 들어갈 수 있다. 후속 기술 조인이 0행이어도 생성은 성공으로 보이므로, “무엇이 통했는가”의 학습 사슬이 조용히 끊긴다.

11. [P1] `attempt_open` 멱등성은 외부 호출 중복을 판별하지 못한다 — §3-5-b ㉢  
같은 fence와 요청본문의 열린 시도를 재사용하지만, 벤더 요청이 실제 전송됐는지를 나타내는 상태가 없다. RPC 응답 유실 뒤에는 이미 호출된 것인지 알 수 없어 재호출하면 중복 과금·중복 호출이고, 재호출하지 않으면 열린 시도가 영구 잔류한다. “최소 1회 호출”만으로는 이 두 결과의 처리 규칙이 닫히지 않는다.

12. [P1] 구앱은 `생성중`과 `없음`을 계속 같은 화면으로 그린다 — §3-1·§11-2·§12-11  
문서는 `assignment_status='생성중'`을 열지만 c12 전 클라이언트는 이 칸을 무시하고 `data`만 본다고 규정한다. 정상적인 동시 운영 기간에 워커가 생성 중이어도 학생은 오늘 과제가 없는 것처럼 보거나 읽기 실패 카드를 보게 된다. 문서를 수정하지 않아도 되는 호환 규칙이 학생 경험의 핵심 의미를 제거한다.

13. [P1] 학생에게 실제로 쓸 이유가 있는 생성문인지 증명하는 시험이 비어 있다 — §8-A·§8-B·§12-29  
§12-29는 생성 질문이 ③답하기 행에 연결되는지와 기존 꼬리·효과음 배선만 확인한다. 그 질문이 해당 학생의 목표에 실제로 도움이 되는지, 신선하고 다시 사용할 만한지에 대한 기존 §8-B 시험은 아직 실행되지 않았고 배포도 차단하지 않는다. 배선만 통과한 문장이 철학 ①의 학생 접점 게이트를 통과한 것처럼 노출될 수 있다.

이 문서보다 나은 대안 구조: 기존 `generation_batch_runs`를 날짜별 유일 매니페스트로 고정하고, 실제 명단·정규 직렬화·스냅샷·판을 그 매니페스트에 결속한다. 모든 job과 rescue는 반드시 그 매니페스트를 참조하며, 매니페스트가 없으면 이전 날짜 판을 빌리지 않고 명시적 오류로 끝낸다. `적재실패`는 마감 전 자동 재큐잉하고, 시도에는 외부 전송 상태를 남기며, 현재 `quality_ver` 평가 결과가 없으면 생성 경로 자체가 배포되지 않게 해야 한다.
