동결 불가.

[P0] 완결 게이트를 스스로 전부 ✗로 선언했다 — §9는 모였나·닿았나·늘었나를 모두 ✗로 적었고, 누구에게도 “학생(예정)”이라고 남겼다. 판단 정본상 데이터·엔진 배선·이해 대장 중 하나라도 ✗면 미완성이다. 재현: 첫 일기 제출은 저장·자동 소비·이해 대장 증가 중 어느 것도 보장되지 않는다(`docs/학생일기_설계_v7.md:191-196`).

[P0] 유일 제약 교체가 모든 제출을 끊는다 — §6 #6은 `job_kind` 추가와 기존 유일 제약 교체를 말하지만 제출 트리거 변경을 적지 않았다. 현재 트리거는 `ON CONFLICT (submission_id)`를 사용하므로 복합 유일 제약으로 바꾸면 충돌 대상이 사라진다(`SYNK-talk/supabase/L0_스키마.sql:2399-2415`). 재현: 마이그레이션 뒤 어떤 제출이든 삽입하면 트리거가 실패해 제출 트랜잭션 전체가 롤백된다.

[P0] `legacy` 이행이 기존 교정 작업을 유실시킨다 — §6은 기존 잡을 전부 `legacy`로 옮기고 새 워커는 `correction`만 집는다고 하지만, 기존 행에서 교정 잡과 다른 잡을 판별하는 규칙이 없다. 현재 `pipeline_jobs`에는 `job_kind`가 없고 제출당 잡 하나뿐이다(`SYNK-talk/supabase/L0_스키마.sql:557-568`). 재현: 마이그레이션 직전 대기 중인 정상 교정 잡이 `legacy`가 된 뒤 새 교정 워커에서 영구히 제외된다.

[P0] 세 사건은 계약이 아니라 이름만 추가됐다 — §5~§7은 `diary.*`의 이름을 제시하지만 필수 필드·payload 위치·`payload.ver`·생산자 파일·서버 사건 삽입·재시도 규칙을 닫지 않았다. 현재 계약 값록과 생산자·도달 장부에는 일기 사건이 없고, 검증기는 값록 밖 사건과 payload 밖 필드를 거절한다(`SYNK-talk/계약/수집_교정_계약.json:99-128`, `SYNK-talk/lib/이벤트검증.js:799-810,899-908`). 재현: `diary_id`·`ack_kind`·`opened_missing`를 보내면 거절되거나 저장 위치가 구현자 추정으로 갈린다.

[P0] `output_text`의 물리 위치가 공용 계약과 정면 충돌한다 — §4㉢은 맞장구 필드를 최상위로 둔다고 하고 §7㉠은 `output_text`까지 최상위로 둔다. 현재 `learning_events`에는 `model`·`prompt_ver`는 있지만 `output_text` 열이 없고, 공용 계약은 `output_text`를 payload 필드로 정의한다(`SYNK-talk/supabase/L0_스키마.sql:404-430`, `SYNK-talk/계약/수집_교정_계약.json:112-128`). 재현: 문서대로 맞장구를 저장하면 생성 문장이 물리 열에 착지하지 않아 복원이 불가능하다.

[P0] 음성 일기의 언어 감지가 현재 전사 통로에 연결되지 않았다 — 판단 정본은 일기 갈래에서 `language=ko`를 빼고 한국어 감지분만 엔진에 태우라고 했지만(`docs/_ops/결정.md:63`), 현재 전사기는 모든 대기 음성에 `language=ko`를 붙인다(`SYNK-talk/supabase/functions/transcribe/index.ts:46-52,117-146`). 또한 `transcript is null` 조건으로 첫 전사를 고정하므로 사후 감지·재전사 규칙이 없다(`SYNK-talk/supabase/functions/transcribe/index.ts:190-197`). 재현: 섞인 음성이 먼저 전사되면 잘못된 전사와 엔진 투입 여부를 나중에 결정할 수 없다.

[P0] 언어 값록이 혼합·불확실 상태를 표현하지 못한다 — §3에는 `ko`, `mn-Cyrl`, `roman`, `num`, `unknown`만 있고 `mixed`, `uncertain`, `detection_failed`가 없다. 그런데 정본은 몽골어·섞임·불확실을 전사만 남기고 엔진에서 제외하라고 한다(`docs/_ops/결정.md:63`), `code_switch_spans`도 단순 `jsonb` 열 외의 구간 형식·오프셋 단위·판본이 없다(`SYNK-talk/supabase/L0_스키마.sql:434-452`). 재현: “오늘 yavsan”과 혼합 음성이 모두 `unknown` 또는 단일 언어로 뭉쳐져 소비자가 미분류와 혼합을 구별할 수 없다.

[P0] 한국어 구간의 엔진 경로와 “고치지 않는다”가 동시에 비어 있다 — §1은 한국어 구간을 교정·어휘 엔진에 보내겠다고 하지만 §7은 `diary_ack` 잡과 맞장구 함수만 정의한다. 현재 이름이 붙은 교정 경로는 실제로 `engine.corrections`를 쓰는 워커이고(`SYNK-talk/supabase/functions/correct/index.ts:144-159`), 그 워커는 `diary.written`을 `event_type='submission.created'` 조건으로 제외한다(`SYNK-talk/supabase/functions/correct/index.ts:173-180`). 재현: 혼합 일기에 한국어 구간 하나를 넣으면 교정 워커를 허용할 경우 금칙을 깨고, 막으면 어휘 신호가 엔진에 전혀 닿지 않는다.

[P0] `diary_id`는 세 사건을 실제로 연결하지 못한다 — §5는 `diary_id`를 외래키로 만들지 않고 `opened_missing:true`로 대체하지만, 지연 도착·재연결·여러 번 열람·서로 다른 물음의 충돌 규칙이 없다. `diary.written`이 어느 `diary.opened`의 prompt 스냅샷을 답했는지 서버가 검증할 방법도 없다(`docs/학생일기_설계_v7.md:102-106`). 재현: 물음 A와 B를 차례로 열고 오프라인에서 한 번 쓴 뒤 이벤트가 역순으로 도착하면 어느 물음에 대한 기록인지 영구히 결정할 수 없다.

[P0] “같은 초안 재전송은 접힌다”는 멱등 규격이 없다 — §7의 멱등키는 `diary-ack:{written_event_id}`뿐이고 §10은 `diary.written`의 키·초안 ID·본문 지문·충돌 규칙을 정의하지 않는다(`docs/학생일기_설계_v7.md:132-134,198-206`). 공용 API는 같은 학생과 같은 `idempotency_key`만 접으므로(`SYNK-talk/docs/C0_API계약.md:160,197-198`) 두 기기의 서로 다른 키는 별도 제출이 된다. 재현: 같은 본문을 두 기기에서 보내면 두 작성 행과 두 맞장구가 생겨 중복 재전송인지 실제 두 장인지 복원할 수 없다.

[P1] 부모 사건 검사는 문장으로만 존재한다 — §7은 `parent_event_id`가 해당 학생의 `diary.written`이어야 한다고 하지만 현재 물리 제약은 같은 학생인지밖에 검사하지 않는다(`SYNK-talk/supabase/L0_스키마.sql:578-585`). 서버 고리 풀기도 사건 종류 검사를 정의하지 않았다(`SYNK-talk/supabase/functions/events/index.ts:400-409`). 재현: 같은 학생의 `diary.opened`를 부모로 넣어도 맞장구가 잘못된 사건에 붙을 수 있다.

[P1] 구조적 출력 검사는 평가를 막지 못한다 — 갈래 선택·한 문장·세 한국어 문형 금지만으로는 평가 의미를 닫은 출력 계약이 아니다(`docs/학생일기_설계_v7.md:149-158`). “의미가 또렷하게 전해졌어요”나 몽골어 평가문은 금지 패턴을 피하면서 학생 산출을 평가할 수 있고, 맞장구 언어도 미정이다(§10-3). 재현: 모델이 미등록 평가문을 내면 `fallback` 없이 정상 맞장구로 저장된다.

[P1] 수신 확인과 AI 맞장구를 같은 사건으로 접었다 — §7㉣은 전사 실패도 `diary.acknowledged`에 `ack_kind='received'`로 넣고, 모델·프롬프트는 비워 둔다. 이 사건이 AI가 읽고 반응한 것인지 파일만 받은 것인지 구분하는 상태·재시도 계약이 없다(`docs/학생일기_설계_v7.md:160-165`). 재현: 전사 장애 때 수신 사건이 먼저 멱등키를 차지하면 복구 뒤 개인화 맞장구가 중복으로 막힌다.

[P1] `task_format='자유발화'`가 글·소리·둘 다를 뭉갠다 — §6은 모든 일기에 `자유발화`를 쓰면서 §8은 글·소리·둘 다를 별도로 센다(`docs/학생일기_설계_v7.md:112-117,181-189`). 공용 계약은 `task_type`과 `task_format`을 다른 축으로 두고 형식 혼입이 잘못된 엔진 학습을 만든다고 경고한다(`SYNK-talk/계약/수집_교정_계약.json:130-131`). 재현: 글 일기와 음성 일기가 같은 형식값으로 저장되면 자유쓰기와 발화 샘플을 하류 소비자가 구분하지 못한다.

[P1] “과제 교정 먼저”가 실행 가능한 우선순위가 아니다 — §7㉡은 우선순위만 선언하고 claim SQL·우선순위 인덱스·공정성·기아 방지·재시도 상태를 정의하지 않는다(`docs/학생일기_설계_v7.md:137-147`). 현재 큐 인덱스는 `status, created_at`뿐이다(`SYNK-talk/supabase/L0_스키마.sql:621-622`). 재현: 교정 잡이 계속 생기면 맞장구가 언제 처리되는지 보장할 수 없고, 반대로 먼저 집으면 정본 우선순위를 위반한다.

[P1] 날짜 정본의 시간대와 형식이 비어 있다 — §5는 `diary.opened`의 `diary_date`를 정본으로 삼고 §8은 몽골 달력 기준 시각대를 요구하지만 날짜 형식·시간대·오프라인 제출 시 판정 기준을 쓰지 않았다(`docs/학생일기_설계_v7.md:102-119,181-189`). 재현: 몽골 현지 자정 직전 작성 후 다음 날 업로드하면 날짜 목록과 시각대 집계가 서로 다른 날을 가리킨다.

[P1] 학생에게 닿는 자기설명 층이 비어 있다 — §10은 첫 화면 문안, 글·소리 선택, 저장·실패 상태, 목록 상한, 시즌 종이 표현을 모두 남은 일로 둔다(`docs/학생일기_설계_v7.md:198-206`). 아래 탭이라는 위치만으로는 처음 본 학생이 이것이 무엇인지, 무엇을 하면 되는지, 왜 다시 열어야 하는지 알 수 없으므로 기본 게이트의 재방문 이유·실사용 도움·자기설명을 입증하지 못한다. 재현: 첫 화면이나 저장 실패 화면에서 학생은 기록이 실제로 쌓였는지와 다음 행동을 알 수 없다.

[P2] `글자 수`의 측정 단위가 닫히지 않았다 — §8은 글자 수만 요구하고 유니코드 코드포인트·자모·그래핌·공백 포함 여부를 정하지 않았다(`docs/학생일기_설계_v7.md:181-186`). 재현: 같은 문장을 자모 입력과 완성형 한글로 제출하면 클라이언트·서버 집계가 서로 다른 길이를 낸다.

### 이 문서보다 나은 대안 구조 1개

`learning_events`는 사건 장부로 유지하되, 일기 원본은 `engine.diary_entries` 한 표에 분리한다. `entry_id`와 전체 prompt 스냅샷·원문·매체·정확한 언어 구간 형식을 한 번에 저장하고, 맞장구는 별도 전용 잡과 서버 함수만 읽게 하며 기존 교정 워커는 `submission.created`만 읽게 한다. 이렇게 하면 오프라인 작성 연결, 혼합 언어 보존, 맞장구·교정 분리, 기존 `pipeline_jobs` 유일 제약 보존을 동시에 검증할 수 있다.
