동결 불가 — P0 12건, P1 4건.

[P0] 검수 완료를 훈련 승인으로 위조 — §1·§3-1은 teacher 교정 행이 생기면 `data_use.granted`를 자동 발행한다. 이는 “교정 검증본 ≠ 훈련 사용 적격”이라는 L0 §6-2·수집 파이프라인 정본과 정면충돌하며, 필수인 사람 승격 의사를 기록하지 않는다.

[P0] 승격 사건의 재현 정보 전멸 — §3-1에는 원본 `event_id`, `artifact_ref`, `content_hash`, `serializer_ver`, `dataset_ver`, 사용 목적, 정확한 `consent_id`·검사 시각, 비식별·라벨링 규칙 버전, 라벨 출처, 승인자·승인 시각, 평가 결과 참조가 없다. 이 상태의 `data_use.granted`는 이름뿐인 사건이어서 무엇이 어느 데이터셋과 모델에 들어갔는지 재현할 수 없고, 훈련셋·평가셋 혼입도 막지 못한다.

[P0] “비식별 칸”이라는 거짓 전제 — §3-1의 `transcript_verified`·`corrected_text`는 학생이 말하거나 쓴 이름·전화번호·주소를 그대로 포함할 수 있으므로 컬럼 자체가 비식별일 수 없다. `redaction_ver`·`redaction_result`·비식별 규칙 버전·별도 불변 산출물을 거치지 않은 채 반출 적격으로 간주한다. 또한 승격 후 `data_use.revoked`·제외·롤백을 뷰와 산출물에 전파하는 규칙이 없어 사후 철회가 엔진에서 효력을 잃는다.

[P0] 뷰를 학습으로 오인 — §2·§3·§6의 ⑦은 뷰에 행이 보이는 것을 “엔진이 배웠다”로 바꿔 부른다. 뷰를 읽는 소비자, 데이터셋 빌드 작업, 모델·정책 갱신, 소비 로그, 실패 재시도, 모델·데이터셋 계보가 전부 없으므로 실제 ⑦은 계속 물리 0이다. 행만 보이고 아무 소비자도 읽지 않아도 도달률은 성공으로 찍힌다.

[P0] 개인 서비스와 회사 공통 훈련을 한 경로로 합침 — §3-2·§3-3의 `learner_state`는 개인 원본 이벤트를 승격 없이 직접 읽지만, §3 서두는 세 축이 ⑥훈련 승격과 ⑦을 공유한다고 선언한다. 개인화용 현재 상태라면 회사 공통 엔진 훈련 도달이 아니고, 공통 훈련 입력이라면 승격 게이트를 우회한다. 개인 서비스 데이터·개인화 기억·회사 통계·회사 공통 훈련을 분리한다는 상위 원칙이 무너진다.

[P0] 미래정보 누출과 과거 상태 재현 불가 — §3-2의 일반 뷰에는 `as_of` 절단 시점·관찰 창·최소 근거 수가 없다. 나중에 과거 개입을 평가하면 그 개입 뒤에 발생한 성과까지 현재 뷰에 섞여 당시 상태인 것처럼 학습된다. Postgres 뷰는 정의 지문을 행과 과거 조회에 자동 스탬프하지 않으므로 “`estimator_version` 자동” 주장도 실행 규격이 아니다.

[P0] 마감 대비 여유의 원본 필드가 없음 — §3-3은 `occurred_at`으로 “마감 대비 여유”를 계산한다고 하지만 c9·L0에는 당시 마감 시각이나 마감 판본이 없다. `daily_activity.expected`는 그날 할 일이 있었는지만 말할 뿐 마감까지 몇 분 남았는지 복원하지 못한다. 수업표·마감이 바뀐 뒤에는 이 원신호를 영구 복구할 수 없다.

[P0] 개인화 인과 사슬 절단 — §3-2는 `recommended_option`과 선택만 읽고, 당시 학습자 상태·정책 버전·`intervention.delivered`·`content.viewed`·즉시 및 지연 성과·강사 검수를 동일 개입 ID로 잇는 규격이 없다. 추천 후보→추천→학생 선택→실제 전달→성과의 정확한 조인과 회수 시점이 없으므로 선호 상관만 남고 어떤 처방이 효과적이었는지는 학습할 수 없다.

[P0] 음성 경로가 음성을 버리고 텍스트 경로는 원문을 버림 — §3-1의 반출 대상에는 `audio_ref`·`capture_meta`·`task_format`·`stt_segments`·STT 신뢰도·기계 전사가 없어 발음·ASR·음성 평가셋을 만들 수 없다. 글 제출에서는 `body_original`이 빠져 오류 원문↔교정 쌍 자체가 서지 않는다. 또한 `AGC off`를 사실로 적었지만 현 C0 정본은 실측값을 `unknown`으로 남기는 상태라 음질 조건까지 거짓 확정한다.

[P0] 트리거 순서 경쟁과 중복 승격 — §3-1은 `corrections` insert와 `submissions.transcript_verified` 갱신을 하나의 원자적 명령으로 정의하지 않는다. 교정 행이 먼저 들어가면 트리거가 승격을 건너뛰고 이후 전사 갱신에는 재발화점이 없으며, 재검수로 teacher 행이 여러 개 생기면 같은 원본의 승격도 여러 번 생긴다. 결정론적 멱등키·원본+목적 유일성·실패 사유 저장 위치도 없다.

[P0] 실제 수집 경로를 범위 밖으로 추방 — §2-1은 현재 데이터가 쌓이는 유일한 라이브 경로가 시트 4종과 골든셋이라고 밝히면서 §7에서 그 전부를 설계 범위 밖으로 뺀다. 따라서 이 문서를 동결하는 순간 “모든 수집은 자동으로 엔진까지”라는 §1의 확정 명제가 실제 운영 경로에서 즉시 거짓이 된다. 골든셋도 `fb_id`·`student_id` 중심으로서 엔진 `event_id`·승격 산출물·정확한 승인 계보가 없으므로 예외 후보만으로 해소되지 않는다.

[P0] 닫힌 E0·E2 결정을 SQL 객체 종류로 우회 — §5의 뷰 2개와 트리거 1개는 명백한 엔진 전용 코드이며 `engine.learner_state`는 미뤄 둔 C계층 학습자 상태 그 자체다. “뷰는 테이블이 아니다”는 선행 구축 금지의 문언만 피할 뿐, 원본은 지금·파생은 나중이라는 결정 이유를 위반한다. 수집→학습 자동화의 설계 지시는 E0 구현 착수와 E2 조기 개통을 자동 승인하지 않는다.

[P1] c9 실측 숫자와 사건 우주가 틀림 — §2는 생산자 6/9라고 쓰지만 c9 값목록은 13종이고 현재 `생산자` 장부는 파일 7종·사유 6종이다. 심지어 구 9종만 세어도 `data_use.granted` 생산자가 없으므로 6/9가 성립하지 않는다. §4의 `// …` 예시는 13종 전량 명세가 아니어서 빠진 사건이 검문 밖에 남는다.

[P1] 도달 장부가 실제 도달을 검사하지 않음 — §4의 `{부품, 통로}`는 파일 존재·뷰 정의·필수 필드 투영·권한·실행 결과를 확인하지 않는 문자열이다. 생산자 장부가 `{사유}`에서 `{파일}`로 바뀐 뒤 엔진도달 쪽 사유가 남아도 이를 실패시키는 교차 불변식이 정의되지 않았다. 배선이 끊겨도 장부 두 개가 각각 초록일 수 있다.

[P1] 학습자 상태 계산 규격이 없음 — §3-2·§3-3에는 출력 컬럼, 축별 공식, 기간 창, 최소 표본, 결측과 0의 구분, 신뢰도 계산, 근거 사건 목록이 없다. `retry_of_event_id ÷ session.abandoned`는 재시도 기회와 포기 건수라는 서로 다른 분모를 나누며 0분모 처리도 없다. `daily_activity.expected`도 저장소에는 열 DDL만 있고 값을 채우는 생산자가 없어 “이미 있는 분모”가 아니다.

[P1] 엔진 도달률의 단위가 맞지 않음 — §6의 분모는 사건 수지만 `learner_state`는 학생·축 단위 집계이고 말뭉치는 검수·승격 단위라 분자와 일대일 대응하지 않는다. 검수 대기·부적격·철회·처리 실패까지 한 분모에 섞으면 낮은 값의 원인을 판별할 수 없다. “두 뷰를 세는 한 줄 쿼리”로는 `event_type`별 도달률을 계산할 수 없다.

## 이 문서보다 나은 대안 구조 1개

`E0 계약형 이중 경로`로 다시 써야 한다.

- 개인 서비스 경로: 원본 이벤트 → `intervention.delivered.occurred_at` 기준의 시점 절단 상태 계산 → `estimator_version`·`policy_ver`·`evidence_refs`를 실제 개입 사건에 스탬프 → 선택·관측 전달·즉시/지연 성과 연결. 이 경로는 `data_use.granted`를 요구하지 않는다.

- 회사 훈련·평가 경로: 검수 화면의 한 번의 명시적 확인 안에서 교정 판정과 승격 판정을 별도 기록 → 자동 작업 큐가 비식별 불변 산출물과 완전한 승격 계보를 생성 → 산출물 저장 성공 후에만 `data_use.granted` 발행 → 훈련셋과 평가셋을 목적별로 분리 → 실제 소비 작업이 dataset/model/eval 계보를 기록. 철회·제외·롤백 사건은 뷰·산출물·데이터셋·모델 계보까지 전파한다.

- c9 13종 전부에 대해 `기능/생산자 → 사건 → 필수 원본 필드 → 목적 경로 → 엔진 부품 → 소비자 → as-of 시점 → 철회 처리 → 단계별 계수`를 한 장부에 완전 열거한다. E0에서는 이 계약과 교차 검증만 만들고 뷰·트리거는 만들지 않는다.

- 라이브 시트는 직접 역방향 쓰기가 아니라 버전 관리된 이관 어댑터로 같은 C0 쓰기 통로를 통과시킨다. 기존 행 ID로 결정론적 멱등키와 import manifest를 남겨 중복·누락·원천 대조를 가능하게 한다.

- 지표는 단일 비율이 아니라 `수집 → 처리 → 검수 → 승격 → 산출물 생성 → 실제 소비` 단계별 고유 원본 사건 수와 지연시간으로 측정한다.
