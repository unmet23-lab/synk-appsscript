판정: 동결 불가. 지적 16건.

1. [P0] 미결정 P0를 구현 가능하다고 처리함 — §8은 P0 §6-3의 “입력은 둘뿐”과 정면 충돌한 채 ㉠·㉡·㉢을 남겨 둔다. 세 선택은 단순 인자 차이가 아니라 상태 입력·프롬프트·판지문·실험군 계약을 바꾸는 별도 설계다. 그런데 §0·§9·§11은 결정을 기다리지 않고 구현할 수 있다고 하므로, 생성 데이터가 서로 다른 계약으로 섞이면 소급 복구할 수 없다.

2. [P0] 생성 산출물과 `task_snapshot` 계약이 없다 — §3은 `생성문장` 하나와 “후보 문장·질문”만 말하고, `task_snapshot`의 정확한 JSON·두 호흡·`task_format`·질문·선택지·상관관계 연결을 정의하지 않는다. P0 §6-1과 C0/L0는 학생에게 실제 제시된 불변 스냅샷을 요구하지만, 이 문서는 문자열 하나만 저장해도 통과할 수 있다. 그 경우 실제 화면과 엔진이 본 과제를 나중에 복원할 수 없다.

3. [P0] `model_ref`와 “c-계약 개정 0”이 기존 계약과 충돌함 — §5-2는 `payload.model_ref`를 자유롭게 넣는다고 하지만 현재 L0/C0는 `model`, `prompt_ver`, `policy_ver`와 허용 payload 필드를 별도로 정의한다. `model_ref`의 표준 위치·검증·파생 규칙이 없고, `output_text`, `cited_refs`, 목표 기술 연결의 물리 기록도 정해지지 않았다. 결과는 계약 거부 또는 재현성 없는 행 중 하나다.

4. [P0] 모델 입력의 불변 스냅샷이 없다 — §3(b)·§5·§7은 프롬프트 규칙의 지문만 말할 뿐, 실제 상태 요약값·널 처리·절단 결과·입력 해시를 `task.assigned`나 `intervention.delivered`에 남기지 않는다. 현재 `evidence_refs`는 사건 참조와 `as_of`일 뿐 실제 파생 축 값을 보존하지 않으며, 늦게 들어온 과거 사건은 다음 계산에서 상태를 바꿀 수 있다. 같은 학생·같은 날짜의 생성 입력을 재현할 수 없으므로 출력의 원인과 효과를 연결할 수 없다.

5. [P0] 외부 생성 호출이 멱등적이지 않다 — §3의 벤더 호출은 DB 기록 전에 실행되고, §6의 결정적 키는 삽입 중복만 막는다. 동시 실행이나 재실행은 서로 다른 문장을 만들 수 있으며, 현재 `deliver`의 중복 응답은 저장된 행을 재조회하지 않고 현재 재계산 결과를 반환한다. 첫 실행의 성공·폴백과 두 번째 응답이 달라지는 사고가 영구 행에 남는다.

6. [P0] 대조군·실패·폴백을 구분할 물리 필드가 없다 — §6은 해시와 비율만 말하고 `arm`, 해시 버전, 적용 비율, 배정 시각, 대조군의 실제 처리를 저장하지 않는다. §4의 키 없음·생성 실패·검문 탈락은 모두 같은 `degraded=true`와 `전날|도입`으로 수렴한다. 비율이나 해시가 바뀐 뒤에는 과거 대조군과 실패군을 분리할 수 없고, 현재 `성과회수`도 순수 함수일 뿐 이를 읽는 결과 소비자가 없다.

7. [P0] 전원 생성 실패를 명시적으로 초록 처리함 — §9-2는 키가 없어도 전원 폴백으로 예외 없이 배치가 초록이어야 한다고 한다. 그러나 §4는 폴백률을 유일한 건강 지표라고만 하고 임계값·경보·실패 사유·운영 차단 조건을 정의하지 않는다. 현재 `deliver`의 미달 판정은 배정 행 수 중심이라, 100% 생성 실패도 배정만 되었으면 정상처럼 보인다.

8. [P0] 인수 조건이 성공 경로를 검증하지 않는다 — §9-2~§9-4는 키 없음 폴백과 리허설 분포를 중심으로 하고, 키가 있는 실제 생성 성공이 `task.assigned`·`intervention.delivered`·조회·제출까지 흐르는지를 요구하지 않는다. `생성문장`이 실제 벤더 결과인지 픽스처 주입값인지도 구분하지 않는다. 현재 저장소에 생성기와 프롬프트 파일이 없으므로, 새 경로가 전혀 호출되지 않아도 이 인수 조건을 통과할 수 있다.

9. [P0] 엔진 학습 귀속 필드가 빠졌다 — §3·§4·§7에는 상태 숫자와 목표만 있고 `skill_id`, `skill_taxonomy_ver`, `target_skill_ids`, `cited_refs`, 난이도·전략 등의 연결이 없다. 코어엔진과 L0가 요구하는 어휘 지도·학습자 모델·지식 근거와 생성 과제가 이어지지 않는다. 생성된 문장이 어떤 약점이나 학습 목표를 겨냥했는지 나중에 복원할 수 없으므로 학습 사슬이 생성 순간 끊긴다.

10. [P1] 고정 분기 학생에게도 생성 호출을 한다 — §3 흐름은 상태 요약과 벤더 호출을 먼저 실행한 뒤 `오늘과제()`가 ①·② 우선순위를 판정한다. 따라서 첫날과 교정문 학생에게도 결과가 버려질 생성 호출이 발생하며, 이는 §1-1의 “과녁은 ③④뿐”이라는 주장과 맞지 않는다. 버려진 호출의 비용·실패·입력은 어떤 사건에도 남지 않는다.

11. [P1] 상태 요약 인터페이스가 “숫자” 수준에 머문다 — §3(b)와 §7의 `{축 5, confidence, evidence_refs}`만으로는 키 이름·단위·기간·널과 0의 구분·순서·절단 규칙이 정해지지 않는다. 현재 `학습자상태`는 `estimator_confidence`, 널 축, 제한된 evidence를 반환하는데 문서는 이를 계약으로 고정하지 않는다. 구현자가 달라도 같은 `policy_ver`를 찍을 수 있어 모델 입력이 조용히 달라진다.

12. [P1] “어제 낸 것을 다시 내지 않는다”는 문서 내부에서 거짓이다 — §4의 폴백 2단은 생성 실패 때 `전날문장`을 그대로 재사용한다. 성공 시에도 §7 요약에는 직전 과제 내용이 없고 §4-1에는 동일·유사 문장 검사가 없다. 의도된 폴백 재출제와 모델의 우연한 중복 출제가 같은 모양으로 기록된다.

13. [P1] 검문 통과를 교육적 성공으로 오인한다 — §4-1은 길이·문자 비율·서식·질문 형태만 검사하고 목표·급수·기술 적합성·두 호흡의 관계·답변 가능성은 검사하지 않는다. 문법적으로 깨끗하지만 엉뚱하거나 수준이 맞지 않는 문장이 `degraded=false`로 배달될 수 있다. 탈락 사유와 교육적 부적합 판정도 남지 않아 후속 평가셋에 분리할 수 없다.

14. [P1] 벤더 실행 계약이 비어 있다 — §3·§4에는 요청·응답 JSON, 타임아웃, 부분 배치 실패, 비정상 응답, 일시 오류 분류, 모델 선택과 결과 매핑이 없다. “같은 프롬프트 재시도 금지”는 검문 실패 정책일 뿐 네트워크 실패나 시간 초과의 실행 정책이 아니다. 실제 오류는 사유 없이 2단 폴백으로 사라지고 다음 실행의 재현 규칙도 없다.

15. [P1] `출처`의 물리적 착지 위치가 없다 — §4·§9은 `출처='생성'|'전날'|'도입'`을 이미 존재하는 행 칸처럼 사용하지만, 현재 L0의 물리 계약은 `source_kind`와 `task_snapshot` 내부 값을 구분한다. 어느 테이블·어느 payload 경로에 어떤 허용값으로 쓰는지 마이그레이션과 소비자 계약이 없다. 리허설은 한 경로를 읽고 원장·성과회수는 다른 경로를 읽는 분리가 발생할 수 있다.

16. [P1] 판지문 계획이 실제 구현에 연결되지 않는다 — §5-1은 프롬프트·요약·검문·폴백 전체를 해시한다고 하지만 현재 `오늘과제.js`에는 정적 v1~v3만 있고 `prompts/과제생성.md`도 없다. 요약 코드·널 처리·검문 상수·정규화가 바뀔 때 `policy_ver`를 새로 발급하게 하는 기계적 훅도 정의되지 않았다. 따라서 “프롬프트 한 글자 변경” 테스트만 통과해도 다른 행동 변경은 같은 판으로 기록될 수 있다.

이 문서보다 나은 대안 구조가 있으면 1개: `선판정 → 멱등 예약 → 생성 → 검문 → 원자 배정` 구조다. `오늘과제()`가 먼저 ①·②·③④를 결정하고 ③④일 때만 생성하며, 학생·날짜 락과 기존 멱등키로 벤더 호출 자체를 1회로 제한한다. 생성 성공·실패·대조군·실패 사유를 계약 개정 후 버전 있는 `task_snapshot`, `model`, `prompt_ver`, `policy_ver`, 목표 기술, 근거, 입력 해시와 함께 기록하고, 중복 실행은 저장된 행을 재조회한다. 성공·키 없음·시간 초과·검문 탈락·동시 실행·조회·제출을 하나의 실제 픽스처로 검증해야 한다.
