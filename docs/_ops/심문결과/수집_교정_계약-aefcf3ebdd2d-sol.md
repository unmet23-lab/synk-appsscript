동결 불가.

[P0] 양쪽 CI 불일치 탐지가 실제로는 작동하지 않는다 — 최상위 `왜`·`고치는_법`은 한 저장소만 변경하면 그쪽 CI가 실패한다고 단언한다. 그러나 양 저장소의 `tests/계약.test.js`는 형제 저장소가 없으면 비교를 `skip`하고, GitHub Actions는 자기 저장소만 checkout하므로 서로 다른 계약을 가진 채 양쪽 CI가 모두 초록일 수 있다.

[P0] 필드 목록이 이벤트 계약을 가장하고 있다 — `learning_events.무엇`은 “필수 필드 규격”이라고 하지만 `필드`는 모든 이벤트의 합집합일 뿐 이벤트별 필수·선택·금지·자료형·null 규칙이 없다. 실제 의미는 `lib/이벤트검증.js`에 따로 존재하므로 검증기 변경만으로 c8의 의미가 바뀌며, `preference.stated`, `session.abandoned`, `exam.result` 같은 빈 껍데기 사건도 저장될 수 있다.

[P0] c8 실왕복 판정이 실제 계약 경로를 우회했다 — `c8에서_바뀐_것`의 완료 근거였던 `tools/교정왕복시험.js`는 Management SQL로 직접 삽입하여 앱→`/v1/events`→DB 경로를 검사하지 않았다. 그 결과 Edge가 `correction_id`를 버리던 결함이 12/12 초록을 통과했고 이후 F179로 별도 수리됐지만, 문서에는 배포된 Edge까지 관통해야 동결된다는 게이트가 여전히 없다.

[P0] `schema_ver`가 실제 행 의미를 증명하지 못한다 — `봉투`·`미구현_주의.schema_ver`는 행이 적용 계약판을 스스로 가진다고 주장하지만, 서버는 구판 클라이언트 요청도 현재 번들 검증기로 검사하고 DB 최신판을 저장한다. 실제로 `level_snapshot=null` 허용 여부가 c8 버전 상승 없이 코드에서 바뀌었으므로 같은 `schema_ver=c8`이 서로 다른 의미를 가리킨다.

[P0] 훈련 승격 사건을 기록할 필드가 없다 — `c4에서_바뀐_것`과 `event_type`은 `data_use.granted`를 훈련 승격이라고 부르지만, `필드.권한`에는 `consent_ver` 하나뿐이다. 확정 인계 기준의 `artifact_ref`, `content_hash`, `serializer_ver`, `dataset_ver`, 사용 목적, 정확한 `consent_id`·검사 시각, 비식별·라벨 규칙판, 승인자·승인 시각, 평가·제외·롤백 계보를 API로 보낼 이름조차 없다.

[P0] 승격 철회와 수집 동의 철회가 한 사건명에 섞였다 — `c5에서_바뀐_것`은 `data_use.revoked`를 녹음 삭제를 일으키는 동의 철회로 설명하지만, 대응하는 `data_use.granted`는 데이터셋 승격 사건이다. 어느 동의·승격·산출물·데이터셋을 철회했는지 식별자가 없어 삭제, 학습 제외, 모델 계보 롤백 중 무엇을 수행할지 결정할 수 없다.

[P0] 철회 후 오프라인 수집을 차단할 수 없다 — `왜_봉투가_따로인가`는 발생 시각과 수집 시각의 분리를 전제하면서도 `필드.권한`에는 사건별 동의 식별자나 서버 검증 시각이 없다. 클라이언트가 철회 이전의 `occurred_at`을 붙이면 철회 뒤 전송된 큐도 정상 사건처럼 수집될 수 있어 기본 기준인 “철회 후 수집 0건”을 증명하지 못한다.

[P0] 오프라인 사건끼리의 인과 연결이 불가능하다 — `parent_event_id`와 `retry_of_event_id`는 서버가 발급한 `event_id`를 참조하지만, 아직 업로드되지 않은 선행 사건을 가리킬 `client_event_id`나 로컬 참조 해석 규칙이 없다. 한 오프라인 배치 안의 대화 턴과 재시도는 선행 서버 UUID를 알 수 없으므로 핵심 고리가 영구 소실된다.

[P0] 멱등키 충돌이 정상 성공처럼 보인다 — `봉투`와 `왜_봉투가_따로인가`는 중복 방지를 선언하지만, 동일 멱등키 재사용 시 원 요청과 새 payload의 지문을 비교한다는 규칙이 없다. 서로 다른 사건이 같은 키를 쓰면 기존 `event_id`를 성공으로 돌려주며 두 번째 학습 증거를 조용히 폐기할 수 있다.

[P0] 추천에서 전달까지의 폐루프를 결합할 식별자가 없다 — `선택로그`와 `출처`에는 후보·추천·선택·`intervention_id`가 흩어져 있지만 하나의 의사결정을 나타내는 안정적인 ID와 선택 축, 후보 객체 규격이 없다. 같은 `correlation_id` 안에 선택과 개입이 여러 번 발생하면 어떤 추천이 어떤 선택과 실제 전달을 낳았는지 복원할 수 없다.

[P0] 즉시·지연 성과 계약이 없다 — `미구현_주의.retry_of_event_id`는 이를 “결과 변수는 이것 하나뿐”이라고 명시하지만, 재제출은 즉시 반응·1일·7일·30일 유지, 전이, 수행 품질을 표현하지 못한다. 성과 사건, 측정 시점, 지표, 기준선, 귀속된 개입 식별자가 없어서 엔진은 처방 효과를 학습할 수 없다.

[P0] 과제 스냅숏이 필수 증거로 강제되지 않는다 — `미구현_주의.task_snapshot`은 질문·보기·정답·지시문·버전을 새 앱 첫날부터 담는다고 하지만 중첩 JSON 스키마도 없고 이벤트별 필수 규칙도 없다. `submission.created`가 스냅숏 없이 저장될 수 있으며 별도 배정행과의 연결도 자유 문자열 `task_ref`에 의존해 당시 학생이 본 과제를 확정할 수 없다.

[P0] S1에서 이미 발생하는 소급 불가 신호가 계약 밖이다 — `event_type`과 `필드`에는 재생 완료, 자기 음성 재청취, 망설임 시간, 녹음 길이, 중도 이탈 단계가 없다. 이는 P0 제품 계약의 S1-1·S1-6·S1-7에서 요구되는 최초 세션 증거인데 로컬 상태로만 남기면 기기 삭제·재설치 뒤 복원할 수 없다.

[P0] 선택로그가 논리적으로 모순된 상태를 허용한다 — `선택로그`에는 `selected_option`, `skipped`, `rejected_all`의 배타성과 boolean 의미가 정의되지 않았다. 현재 존재 여부 중심 검증에서는 `skipped:false`도 충족으로 취급될 수 있고 선택하면서 동시에 전량 거절한 행도 가능해, 실패 데이터가 정상 선택처럼 쌓인다.

[P0] 선택지의 안정 식별자가 없다 — `options_shown`·`selected_option`의 자료형과 `option_id` 규칙이 `선택로그`에 없다. 표시 문구를 값으로 저장하면 번역·문구 수정 뒤 동일 선택지를 연결할 수 없고, 위치 효과와 의미 효과가 섞여 과거 집계를 다시 만들 수 없다.

[P0] `exam.result`는 결과를 담지 못한다 — `c6에서_바뀐_것`은 TOPIK과 학원 급수를 분리한다고 주장하지만 시험 체계, 시험판, 응시일, 점수, 만점, 급수, 출처, 입력자, 검증 시각 필드가 없다. 빈 `exam.result`도 계약상 유효하므로 “성적 사건이 있음”과 “성적을 알고 있음”이 같은 모양이 된다.

[P0] 전사 두 칸의 의미가 다른 정본과 충돌한다 — `c5에서_바뀐_것`과 `미구현_주의.transcript_verified`는 `transcript`를 기계 전사, `transcript_verified`를 사람이 들은 문장으로 정의한다. P0 제품 계약은 전자를 들린 문장, 후자를 의도 문장으로 사용하므로 ASR 오류·발음 오류·학생 의도가 같은 두 칸에서 뒤섞이고, 이미 쌓인 코퍼스의 라벨 의미를 사후 판별할 수 없다.

[P0] 검증된 전사의 출처와 판본이 없다 — `transcript_verified`에는 검수자, 검수 시각, 검수 상태, STT 모델·설정판이 결합되지 않는다. 값이 수정되면 최초 기계 출력과 누가 무엇을 확정했는지 사라져 평가셋과 음성 코퍼스의 정답 계보를 증명할 수 없다.

[P0] 대화 순서가 구조적으로 보장되지 않는다 — `parent_event_id`·`turn_no` 설명은 순서 보존을 주장하지만 같은 `correlation_id`인지, 선행 턴인지, `turn_no`가 양수·유일한지에 대한 불변식이 없다. 또한 발화 주체를 나타내는 `actor_kind`가 공용 필드에서 빠져 학생·AI·강사 발화를 안정적으로 구분할 수 없다.

[P0] 어휘 지도 미매핑이 정상 빈 값으로 굳어진다 — `skill_ids`와 `skill_taxonomy_ver`는 필드 목록에는 있으나 사건별 필수 규칙이 없고 빈 배열이 “관련 기술 없음”인지 “아직 태깅 안 함”인지 구분되지 않는다. 과제 스냅숏까지 비면 나중에 어느 기술을 측정한 사건인지 다시 분류할 근거가 없다.

[P1] 오류태그가 상호 모순될 수 있다 — `오류태그`는 `오류없음`과 실제 오류태그의 동시 존재를 금지하지 않고, 빈 배열도 미검수와 오류 없음 중 어느 뜻인지 정의하지 않는다. `골든판정` 역시 원문·교정문·오류태그와의 교차 불변식이 없어 상충 라벨이 평가셋에 들어갈 수 있다.

[P1] 음성 업로드와 이벤트 저장이 원자적이지 않다 — `audio_ref`·`capture_meta`에는 업로드 시도 ID, 소유권 확정 상태, 실패 정리 규칙이 없다. Storage 업로드 뒤 이벤트가 영구 거절되면 DB에서 추적할 수 없는 개인정보 파일이 남고, 재시도는 고아 파일을 추가할 수 있다.

[P1] 값목록 추가를 무조건 안전하다고 규정했다 — `값목록_규칙`은 추가는 안전하다고 단언하지만 구버전 소비자의 exhaustive 분기, SQL CHECK, 대시보드 집계는 새 값을 누락하거나 기타로 합칠 수 있다. 생산자·DB·소비자 배포 순서와 unknown 처리 규칙 없이 값 추가는 조용한 집계 손실을 만든다.

이 문서보다 나은 대안 구조 1개 — 단일 정본을 공통 봉투와 `event_type`별 판별 합집합으로 만든다. 각 사건마다 필수·선택·금지 필드, 자료형, null 규칙, 교차 불변식, 수정 가능성, 동의·계보 규칙을 기계 판독형으로 선언하고 여기서 검증기·SQL CHECK·타입·양성/음성 픽스처를 생성하며, 양 저장소 CI는 형제 폴더가 아니라 고정 커밋과 해시의 정본을 직접 검증해야 한다. 오프라인용 `client_event_id`·로컬 참조와 멱등 payload 지문을 이 구조에 포함하되 새 테이블이나 미뤄 둔 `dataset_item` DDL은 만들지 않는다.
