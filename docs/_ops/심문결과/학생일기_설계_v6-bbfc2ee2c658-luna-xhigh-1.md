동결 불가.

- [P0] 맞장구 잡의 소비자와 서버 사건 통로가 없다 — §3 #4·§5·§7㉡는 `diary_ack` 잡을 만든다고만 하고, 실제 맞장구 함수의 파일·호출 스케줄·서버 사건 삽입 경로를 정의하지 않는다. 현재 교정 워커는 `submission.created`만 읽고(`SYNK-talk/supabase/functions/correct/index.ts:173-180`), `/events`는 `actor_kind='learner'`로 고정되어 있다(`supabase/functions/events/index.ts:447-454`). 재현: `diary.written` 1건을 넣고 기존 워커를 실행하면 `diary_ack`가 계속 대기하며, `/events`로 우회하면 AI 사건이 학습자 사건으로 저장되거나 거절된다.

- [P0] `input_lang`은 열만 있고 생산 계약이 없다 — §3 #5는 마이그레이션만 요구하고, §4·§8에는 생산자·필수 여부·허용값·소비자가 없다. 실제 제출 INSERT에도 해당 열이 없다(`SYNK-talk/supabase/functions/events/index.ts:524-548`; `supabase/L0_스키마.sql:434-458`). 재현: 마이그레이션 뒤 글·소리 일기를 제출하면 `input_lang`은 비거나 임의값으로 쌓이고, 언어별 엔진 집계는 소급할 수 없다.

- [P0] 일기 음성의 학습 사슬을 스스로 끊었다 — §6은 모든 `task_type='일기'` 음성의 `transcript_state`를 `null`로 만들고 §10-1에서 발음·어휘 손실을 인정한다. 실제 `전사대상()`은 `null`을 전사 대상 아님으로 해석하며(`SYNK-talk/lib/전사.js:31-51`), 일기 음성을 읽는 별도 소비자나 손실 계측은 없다. 재현: 유효한 음성 일기를 제출하면 `audio_ref`만 남고 발음·어휘 데이터는 엔진에 닿지 않는다.

- [P0] 열람과 작성의 관계·일기 인스턴스가 없다 — §1은 `diary.opened`를 이탈 분모로 남기지만 §4에는 열린 사건과 작성 사건을 잇는 필드나 인스턴스 규칙이 없다. 기존 API의 멱등성은 학생별 `idempotency_key` 단위일 뿐이다(`supabase/functions/events/index.ts:444-516`); §10-5도 두 기기 작성이 모두 선다고 인정한다. 재현: 같은 물음을 세 번 열고 한 번 쓰거나, 두 기기에서 각각 쓰면 열람→작성 전환율·날짜 목록·“일기 하나당 답 하나”를 복원할 수 없다.

- [P0] 맞장구 필드의 위치가 공용 계약과 충돌한다 — §4는 `parent_event_id`·`output_text`·`model`·`prompt_ver`를 payload 필수라고 쓰지만, 공용 계약은 이를 top-level 필드로 둔다(`계약/수집_교정_계약.json:79-90,112-154`). payload에 넣으면 물리 열과 종이 조회가 비고, top-level에 넣으면 v6의 payload 검증이 잡지 못한다. 재현: 같은 사건을 두 구현 방식으로 각각 저장하면 둘 다 “유효한” 것처럼 보이지만 소비자는 서로 다른 칸을 읽는다.

- [P0] 소리 fallback은 `diary.acknowledged` 필수 계약을 만족하지 못한다 — §7㉠은 모든 맞장구에 `model`·`prompt_ver`를 요구하지만 §7㉣은 소리를 읽지 않은 채 「잘 들었어요」 표시를 고른다. 이 경우 모델·프롬프트 계보가 존재하지 않으므로 null이면 계약 위반이고, 값을 채우면 AI가 내용을 읽었다는 거짓 계보가 된다. 재현: 음성 일기에 ⓑ 경로를 적용하면 AI 맞장구와 수신 확인을 같은 사건으로 저장하게 된다.

- [P1] `parent_event_id`가 “그 일기”임을 보장하지 않는다 — §7은 부모가 일기를 가리킨다고 하지만 `diary.written` 사건인지, 잡의 `submission.event_id`와 같은지 검사하는 규칙이 없다. 현재 물리 FK는 같은 학생의 사건인지만 보장한다(`SYNK-talk/supabase/L0_스키마.sql:578-585`; `supabase/functions/events/index.ts:400-410`). 재현: 같은 학생의 `diary.opened` 또는 다른 `diary.written`을 부모로 넣어도 저장되어 맞장구가 엉뚱한 기록에 붙는다.

- [P0] 기존 `pipeline_jobs` 행의 `job_kind` 이행이 없다 — §3 #6은 열 추가와 유일 제약 교체만 적었고, 이미 존재하는 `submission_id`별 잡의 종류를 어떻게 정할지 정의하지 않는다. 현재 잡 표에는 `job_kind`가 없고 제출당 유일 제약만 있다(`SYNK-talk/supabase/L0_스키마.sql:557-568`; 기존 backfill은 `20260807120000_engine_c8.sql:124-141`). 재현: 기존 배정·퀴즈 잡에 `correction` 기본값을 넣으면 오분류되고, null로 두면 새 워커가 무시하며, `NOT NULL`로 바로 바꾸면 마이그레이션이 실패한다.

- [P1] 배포 사후검사가 잘못된 잡을 성공으로 센다 — §5의 새 트리거는 `correction`과 `diary_ack`를 구분하지만 제안한 사후검사는 `submission_id`에 잡이 하나라도 있으면 통과시킨다(§5, 141-147). 재현: 일기 제출에 `correction` 잡만 있고 `diary_ack`가 없어도 `잡없는제출=0`이 되어 배포 검사가 초록이 된다.

- [P1] 새 사건의 `source_kind` 판정값이 없다 — §3 #4는 `사건출처.js`를 고치라고만 하고 `opened`·`written`·`acknowledged` 각각의 출처를 정하지 않는다. 실제 `사건출처()`는 누락된 사건에 기본값을 주지 않고 `null`을 반환한다(`SYNK-talk/lib/사건출처.js:27-79`). 재현: event_type만 계약에 추가하고 매핑 한 줄을 빠뜨리면 사건은 쌓이지만 관측·학생 발화·AI 생성의 구분이 영구히 사라진다.

- [P1] 출력 금칙어 목록은 평가를 검출하지 못한다 — §7㉢은 `잘`·`뛰어나`·`늘었` 같은 낱말 목록으로 의미를 막으려 한다. 「한국어가 자연스럽네요」·「정확하게 표현했어요」는 통과하고, 반대로 §7㉣의 「잘 들었어요」는 `잘` 때문에 오탐된다. 재현: 위 두 문장을 검사기에 넣으면 평가 문장은 통과하고 수신 확인 문장은 폐기된다.

- [P1] 생성 맞장구·수신 표시·실패·열람을 구분할 상태가 없다 — §4·§7의 사건에는 원문과 모델 계보만 있고, §10-6은 대기·실패 화면을 미래 과제로 남긴다. `ack_kind`, 생성 결과, 검사 탈락 사유, 학생 열람 사건과의 연결이 v6 계약에 없다. 재현: 모델 출력이 금칙어로 대체된 경우와 음성 수신 표시가 저장된 경우가 같은 “acknowledged” 성공처럼 집계된다.

- [P1] 자발발화 네 지표의 계산 단위가 없다 — §8은 수·길이·시각대·매체만 열거하고 글자 수와 음성 초의 단위, 시간대, 재시도·복수 작성 처리, 매체 허용값을 정하지 않는다. `diary.written`의 `task_format`도 기존 값 중 무엇을 쓸지 없다(현재 CHECK `SYNK-talk/supabase/L0_스키마.sql:592-599`). 재현: 같은 날짜에 글 일기와 음성 일기, 재전송 두 건을 넣으면 소비자마다 수량·길이·매체가 달라진다.

- [P1] ㉡ 사람 이해는 여전히 이름만 있다 — §9는 후보 지표가 ㉡을 채울 수 있다고 하고 §10-2는 정의·소비자·회수 시점을 다음 일로 미룬다. `docs/제품방향.md:34-41`의 세로줄과 이해 대장 칸에 어떤 값이 들어가는지 없다. 재현: 일기가 여러 건 쌓여도 엔진은 “언제 쓰는가” 원자료만 갖고, 성향 값으로 언제 회수해 다음 과제를 바꿀지 결정할 수 없다.

- [P1] 학생 기본 게이트와 자기설명이 비어 있다 — §2는 탭·기록·맞장구·목록만 말하고 §10-6은 첫 화면 문안, 글·소리 선택, 저장·실패 상태, 종이 표현을 모두 미룬다. 판단 정본의 ① 실사용 도움·신선함과 ⑤ 자기설명에 대해 학생이 왜 다시 열고 무엇을 하면 되는지, 기록이 목표에 어떤 한국어 도움을 주는지 답이 없다. 재현: 처음 온 학생이 탭을 열면 입력 방식과 저장 완료를 판단할 규격이 없고, 기록만 남은 뒤 다시 열 이유도 없다.

안 본 것: 실제 Supabase 운영 DB 상태, 아직 존재하지 않는 일기 UI·맞장구 함수의 구현, 실행 시험 결과. 개인정보·보안·동의 축은 요청대로 검수하지 않았다.

이 문서보다 나은 대안 구조 1개: 새 표를 만들지 않고 `diary_id`를 공유하는 “일기 봉투”로 고정한다. `diary.opened`가 물음 스냅샷을 만들고 `diary.written`이 그 사건을 부모로 가리키며, `diary.acknowledged`는 작성 사건만 부모로 가리킨다. 맞장구에는 `ack_kind`를 두어 생성 맞장구와 음성 수신 표시를 분리하고, 잡에는 `legacy·correction·diary_ack`를 명시해 기존 행을 먼저 분류한 뒤 종류별 사후검사를 둔다.
