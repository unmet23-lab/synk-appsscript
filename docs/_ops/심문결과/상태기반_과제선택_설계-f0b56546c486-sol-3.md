[P1] CPU 상한을 인수 조건에서 빼먹었다 — §12-20은 벽시계 항목만 재며 함수의 active CPU 시간을 측정하지 않는다. 현재 Supabase Edge Functions는 요청당 CPU 시간이 2초로 제한되므로, 17명 상태 산출·기술 선택·JSON 조립이 벤더 호출 0이어도 종료될 수 있다. [Supabase Edge Functions limits](https://supabase.com/docs/guides/functions/limits)

[P1] 마이그레이션 인수 절차가 없다 — §3-5-b가 DDL과 RPC를 “그대로 쓰는 계약”으로 올렸지만 빈 DB 적용, 재실행, 중간 실패, 기존 판 공존, 롤백, 실제 함수 시그니처 재독증이 없다. §11-2의 c12 선행 순서만으로는 물리 적용 실패를 검출할 수 없다.

[P1] 상태 헤더와 본문이 서로 다른 착수 판정을 낸다 — 문서 머리는 A~K 집행이 아직 안 들어왔고 차단자 하나가 남았다고 쓰며, §16-1은 전부 집행돼 착수 차단이 해제됐다고 쓴다. §15에도 폐기된 `generation_claims`, `position` 기록, 전날 snapshot 복사, `용량초과`가 현행처럼 남아 있어 구현자가 어느 절을 따라야 하는지 확정할 수 없다.

[P2] 검문 항목의 적용 대상 문자열이 불명확하다 — §8은 `s` 하나만 사용하면서 문장과 질문 중 한국어 비율·금칙 서식·식별자 검사를 각각 적용할지 결합 적용할지 밝히지 않는다. 같은 응답이 구현 순서에 따라 통과하거나 다른 실패 라벨을 받는다.

이 문서보다 나은 대안 구조 1개 — `generation_job`에는 대상 판정 당시의 불변 입력 봉투와 `request_hash`를 영어 컬럼으로 한 번 저장하고, 벤더 호출은 `attempt_started`와 `attempt_finished`라는 append-only 두 사건으로 남긴다. 최종화 RPC는 펜싱을 확인해 `winning_attempt_id`와 세 배달 행을 한 트랜잭션으로 확정하고, 구제용 RPC는 learner/job을 명시해 생성 중이면 즉시 기존 과제를 반환하거나 폴백을 착지한다. `skill_ids`는 개입 목표로만 보존하고 학생 제출·교정 결과가 실제로 생긴 뒤 그 결과 소비자가 목표 기술과 조인해 실력 이해를 갱신해야 한다. 모델·프롬프트·정책·평가셋은 하나의 실행 manifest로 묶고, 정확히 일치하는 평가 결과가 없으면 학생 노출 플래그가 열리지 않게 해야 한다.
