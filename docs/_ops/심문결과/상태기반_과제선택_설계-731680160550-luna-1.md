## 지적 21건

1. [P0] `event_draft`가 DDL에 없다 — §3-5-b의 `jobs_load`·`jobs_finalize_due`는 모든 job에 `event_draft`를 저장한다고 하지만 `generation_jobs` 테이블에는 해당 열이 없다. 마감 스윕은 저장된 draft를 읽어야 하는데 읽을 물리 자리가 없어, 결국 금지된 `오늘과제()` 재호출이나 구현자 임의 저장소가 필요해진다.

2. [P0] 배치 실행 표식이 실패를 기록하지 못한다 — §3-5-b ④는 `generation_batch_runs`를 `jobs_load`와 같은 트랜잭션에 넣고 `finished_at=null`을 중간 실패로 해석한다. 트랜잭션이 죽으면 행도 함께 롤백되어 `finished_at=null` 행은 남지 않는다. `jobs_load_one` 구제 경로는 job을 만들 수 있지만 `batch_runs` 행 생성 규칙도 없어, “안 돌았다”와 “구제로 돌았다”가 다시 충돌한다.

3. [P0] `assign_date`의 시간대가 실행 계약으로 닫히지 않았다 — §3-2-a는 cron을 UTC로 표기하면서 RPC에는 `오늘`만 넘긴다. `date`가 UTC 날짜인지 `Asia/Ulaanbaatar` 날짜인지 변환식이 없으므로 06:00 마감 직전 워커가 전날 job을 읽거나 오늘 job을 놓칠 수 있다. 날짜가 어긋난 배정·마감·분모가 append-only 사건에 남으면 소급 복구가 불가능하다.

4. [P0] `deliver-check` 시간과 판정 기준이 서로 다르다 — §3-2-a 표에는 기존 `deliver-check`가 00:35로 남아 있지만 C4 본문은 06:05로 옮긴다고 한다. §12-21은 새 cron 세 개만 검사하고 기존 잡의 변경된 시간·본문을 검사하지 않는다. 옛 잡이 남으면 정상 배치를 매일 장애로 보고하고, 새 잡으로 바뀌어도 그 변경을 인수 조건이 보장하지 않는다.

5. [P0] 기존 `task.assigned`를 무조건 건너뛰면 닻 없는 배정이 영구 은폐된다 — C5는 같은 학생·날짜에 `task.assigned`가 있으면 `jobs_load`가 전부 건너뛰도록 한다. 게임날인지, `intervention.delivered`와 `submissions`가 함께 있는지 확인하지 않는다. 과거 라이브 경로가 배정만 남긴 부분 실패가 있으면 이후 재실행도 생성 job과 닻을 만들지 못한다.

6. [P0] 이력 조회가 스냅샷 경계를 실제로 구현하지 않는다 — §11-4는 `occurred_at <= as_of`와 `ingested_at <= as_of`를 모두 요구하지만, §3의 ②′·§6-0 조회 규격은 `occurred_at > as_of-window`라는 하한만 적는다. 상한과 `ingested_at` 조건이 없어서 미래 사건이나 늦게 적재된 사건이 중복 판정·기술 회전에 들어갈 수 있다. 같은 `snapshot_as_of` job이 실행 시점에 따라 서로 다른 입력을 읽는다.

7. [P0] 중복 검사가 스스로 모순되고 필요한 질문도 전달받지 않는다 — §8 F4는 처음에는 문장+질문 쌍의 완전일치라고 쓰고, 다음 문장에서는 문장 또는 질문 하나만 같아도 중복이라고 쓴다. 그런데 ②′ 이력 봉투는 `output_text`와 `skill_ids`만 읽고 질문을 가져오지 않는다. 어느 구현을 택해도 문서의 다른 절과 달라지며, 구세대·비생성 `intervention.delivered`를 생성 이력에서 제외하는 조건도 없다.

8. [P0] API 응답 키가 자체 필드명 규칙을 위반한다 — §3-1은 `배정상태`, §3-5-b는 `{"신규": n, "기존": m}`을 API 계약으로 제시한다. 같은 문서의 §11-2와 C0 규칙은 필드명을 영문 snake_case로 고정하고 한글 필드명을 금지한다. 앱은 어떤 이름을 구현해야 하는지 결정할 수 없고, 어느 한쪽을 따르면 다른 정본을 위반한다.

9. [P0] RPC 아홉 개를 요구하면서 인수 조건은 여섯 개만 검사한다 — §3-5-b는 `jobs_release`, `jobs_finalize_due`, `jobs_load_one`을 포함한 아홉 RPC를 정본으로 선언한다. 그러나 §12-21은 여전히 “RPC 여섯”을 검사한다고 적혀 있다. 구현에서 새 RPC 세 개가 빠져도 인수 조건이 초록이 될 수 있다.

10. [P0] 값목록 회귀가 원리상 통과할 수 없다 — §4-1은 `이미배정`을 포함한 15개 값을 제시하지만 DDL의 `outcome` CHECK에는 행에 저장되는 14개만 있다. §12-21은 DDL 리터럴 집합과 §4-1 집합이 같아야 한다고 한다. 이대로면 회귀는 항상 실패하거나, 응답 전용 값인 `이미배정`을 DB 값으로 잘못 넣어야 한다.

11. [P0] `status`와 `outcome`의 조합이 물리적으로 닫히지 않았다 — DDL은 종료 여부·anchor 존재·성공 승자만 검사하고, `대상아님→대상아님`, `마감폴백→예산소진` 같은 대응을 강제하지 않는다. 따라서 `status='대상아님', outcome='타임아웃'`이나 `status='마감폴백', outcome='성공'`이 저장될 수 있다. 운영 분포와 사건 payload가 서로 다른 사실을 말해도 DB가 거절하지 않는다.

12. [P0] `_event`의 작성자와 검증 범위가 닫히지 않았다 — §3-5-b는 함수가 learner·event type·intervention ID 등을 채운다고 하면서도 `jobs_finalize`에는 자유로운 `_event jsonb`가 들어온다. 함수가 호출자 값을 덮어쓰는지 거절하는지, learner·intervention·task·degraded·skill·gate 값의 일치를 어떻게 검사하는지 없다. 현재 명시된 비교는 `outcome` 하나뿐이라 append-only 원본에 잘못된 사건이 들어갈 수 있다.

13. [P0] c12는 아직 계약 정본이 아니다 — §11-2는 현행 계약이 c11이고 c12는 앞으로 개정해야 할 판이라고 명시한다. 그런데 생성 경로·DDL·인수 조건은 이미 c12의 세 필드를 전제로 한다. c12 개정 전에는 첫 `intervention.delivered`가 현재 검증기를 통과할 수 없으므로 이 문서는 실행 가능한 동결 계약이 아니다.

14. [P0] `모였나·닿았나` 상태가 문서 안에서 뒤집힌다 — §6-0 H3는 `skill_ids`가 실제로 모이지 않았고 `성과회수` 자동 배선도 없어 `✗✗✗`에 가까운 상태를 적는다. 그런데 §12-17과 §16-1은 `✓✓✗`라고 선언한다. `docs/엔진도달_설계.md`도 성과회수 호출자가 수동 CLI이고 자동 배선이 0이라고 적으므로, §12의 “조인이 값을 냈다”는 테스트는 사람 손 없는 엔진 도달을 증명하지 못한다.

15. [P0] 마이그레이션 재실행·부분 실패·롤백 계약이 서로 충돌한다 — §3-5-b의 DDL은 기본적으로 `create table`, `alter table`, `add constraint`, `create index`를 무조건 실행하지만 §12-21은 재실행 가드를 요구한다. 동시에 §12-21은 역마이그레이션을 만들지 않고 빈 DB 재적용을 롤백으로 간주한다. 첫 학생 이후 또는 중간 실패가 난 개발 DB에서는 재적용이 롤백이 아니며, 실패 지점에서 복구할 절차가 없다.

16. [P0] 구제 경로가 원래 입력의 계보를 보존하지 않는다 — `jobs_load_one`은 `적재실패`를 되살릴 때 `branch_snapshot`과 `event_draft`만 새로 쓰고 `snapshot_as_of`, `skill_ids`, `skill_taxonomy_ver`, 실행판 네 칸의 갱신 여부를 정하지 않는다. `load_error`도 DDL 저장 열이 없다. 그 결과 새 폴백 문장과 옛 기술 선택·옛 실행판이 한 job에 섞이거나, 최초 조립 실패의 원인이 사라진다.

17. [P1] 학생이 왜 다시 여는지에 대한 설계가 없다 — §7의 학생 접점은 생성 문장과 질문을 내고, §8 런타임 검문은 형식·중복만 본다. §8-B는 “학생이 왜 한 번 더 여는가”를 범위 밖으로 밀고, §12-3은 실제 학생 산출을 첫 학생 뒤로 미룬다. 따라서 학생이 실제로 말하고 싶어지는 재미, 즉시 반응, 성취감·다음 행동으로 이어지는 층이 비어 있어 기본 게이트의 `재미있는가`와 `실사용 도움`을 보장하지 못한다.

18. [P1] 목표가 저장될 뿐 생성에 사용된다는 계약이 없다 — `goal_snapshot`은 `branch_snapshot`에 들어가지만 `generation_input_text`에 목표 맥락을 반드시 포함하라는 규칙이 없다. §8-B의 목표 활용 점수는 오프라인 시험지에서만 검사하며 런타임 생성기와의 연결을 강제하지 않는다. 다른 상태 축 하나만 바뀌어도 §12-22 상태 변주 회귀를 통과하므로, 목표를 무시한 문장이 학생 맞춤 과제로 저장될 수 있다.

19. [P1] `skill_ids`가 학생 상태가 아니라 회전표를 기록한다 — §6-0은 18개 문법 기술을 순환 배정하고 급수·약점·목표와의 런타임 적합성을 보장하지 않는다. 급수→기술 매핑은 유호님 판정 대기로 남아 있어, 현재 구조에서는 학생에게 맞는 기술이 아니라 회전 순서가 처치가 된다. `skill_ids`를 사건에 남겨도 그것은 학생의 실력 이해가 아니라 시스템의 사전 가설만 기록한다.

20. [P1] 현재 철학 정본과 게이트 상태가 충돌한다 — `docs/SYNK_철학.md`의 A-1은 상태 기반 과제 선택을 v5.2, 5회차 종료, 6회차 착수 차단 상태로 기록한다. 후보 문서는 v5.4, 7회차 40/40 집행 완료, 8회차 대기라고 선언한다. 어느 파일을 보드·철학 훅·출시 판단이 읽는지 통일되지 않으면 동결 상태가 호출 경로에 따라 달라진다.

21. [P1] 실행판 지문이 재현 가능한 지문으로 닫히지 않았다 — §5-1·§8-B는 `policy_ver`, 시험지 해시, `input_hash`, `raw_response_hash`를 요구하지만 직렬화 규칙·문자 인코딩·해시 입력 범위·절단 규칙을 정하지 않는다. 같은 사례와 같은 판을 서로 다른 구현이 다른 해시로 만들거나, 반대로 중요한 정책 파일 변경을 해시에 포함하지 않을 수 있다. 이 상태에서는 평가 결과와 실제 생성 행을 동일 실행판으로 묶었다고 증명할 수 없다.

대안 구조 1개: `batch_run`을 학생 job과 같은 트랜잭션에 숨기지 말고 시작·실패·완료 상태를 독립적으로 남기는 실행 봉투로 만들고, `generation_jobs` 안에 타입이 닫힌 `event_draft`와 불변 스냅샷을 함께 저장한다. 이후 `attempt` → 단일 `finalize` RPC → 자동 성과 소비자까지 한 학생 수직 경로를 먼저 닫은 뒤 학급 배치로 확장해야 한다.
