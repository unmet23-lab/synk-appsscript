동결 불가. 지적 20건이다.

1. [P0] `c12`를 정본처럼 전제한다 — §11-2는 `generation_*` 3개 필드가 열린 `c12`를 전제로 하지만 현재 C0와 계약 JSON은 `c11`이고 L0 스키마에도 해당 필드가 없다. 검증기도 목록 밖 payload 키를 일반적으로 거절하지 않아, 구현자는 계약 위반과 정본 밖 저장 중 하나를 선택하게 된다. 버전 전환·마이그레이션·클라이언트 적용 경계도 없다.

2. [P0] `correlation_id`의 의미를 바꾼다 — §3-0은 야간 배정·개입·학생 제출에 같은 값을 요구하지만 C0는 이를 한 앉음·학생 세션의 키로 정의한다. 서버가 학생의 미래 발화 세션 값을 미리 만들 수 없고, 현재 앱도 화면 세션에서 생성한다. 세션 단위와 일일 배달 단위를 합치면 이후 사건의 의미를 복구할 수 없다.

3. [P0] `sentence`·`question`의 세 호흡 매핑이 없다 — §5-3은 두 문자열만 정의하지만 §7의 실제 과제는 듣기·따라 말하기·답하기 세 호흡이다. 어느 값이 `output_text`, 따라 말하기 문장, 답하기 프롬프트가 되는지와 각 호흡의 `출처`가 닫혀 있지 않다. 학생에게 실제로 무엇이 보였는지와 어떤 산출이 생성문장에 대한 답인지 소급할 수 없다.

4. [P0] claim 패배자가 존재하지 않는 배정을 재조회한다 — §3-5는 claim을 먼저 잡고, 실패하면 기존 배정을 재조회하라고 한다. 동시 실행에서 승자는 claim만 잡고 벤더 호출 중일 수 있어 패배자에게는 아직 배정 행이 없다. 승자가 죽으면 24시간 동안 빈 결과와 `이미배정`이 공존하며, 대기·재조회·복구 규칙이 없다.

5. [P0] 14개 `generation_outcome` 중 일부는 행으로 남길 수 없다 — §4-1은 값을 `intervention.delivered`에 필수로 요구하지만 §3-4는 게임날에 그 행을 만들지 않는다. `이미배정`도 중복 실행 시 새 행을 만들지 않으므로 행에 기록되지 않는다. 그런데 §12-7은 14값 각각의 픽스처 행을 요구해 문서 내부 조건이 서로 양립하지 않는다.

6. [P0] 벤더 호출과 증거 착지가 원자적이지 않다 — §3의 벤더 호출은 DB 트랜잭션 밖이고, 그 뒤에 세 행을 착지한다. 응답 직후 프로세스가 죽으면 실제 요청 본문·모델·응답·실패 사유가 전부 사라지고 claim에는 상태만 남는다. 24시간 뒤 재호출해도 최초 생성 시도의 증거는 복구되지 않는다.

7. [P0] 구제 경로는 실제 API 계약이 아니다 — §3-1은 `배치|구제` 호출 맥락을 요구하지만 현재 `tasks/index.ts`는 `deliver?learner_id=...`만 호출하고 맥락을 전달하지 않는다. 현재 `deliver`에도 그 분기를 읽는 계약이 없다. §12-11 픽스처만 통과하고 실제 학생 조회에서는 생성이 실행될 수 있다.

8. [P0] `as_of`가 읽기 스냅샷이 아니다 — §11-4는 읽기 시작 시각이라고 정의하지만 현재 `deliver`는 원자료를 읽은 뒤 학생별로 현재 시각을 찍는다. 필터도 `occurred_at <= as_of`뿐이라 `as_of` 뒤 도착한 늦은 사건을 제외할 `ingested_at` 경계나 DB 스냅샷이 없다. 같은 시각을 기록해도 실행 시점에 따라 입력 사건이 달라진다.

9. [P0] `evidence_refs`가 완전한 입력 스냅샷이라는 주장을 충족하지 못한다 — §6-1은 실제 사건 목록·창 길이·사용 축을 요구하지만 현재 `학습자상태.v7`은 창을 30일로 쓰고 사건을 200개에서 자르며 `잘림`을 추가한다. 문서 예시는 창 길이를 14로 제시하고 `쓴축`의 생산 규칙도 없다. 사건이 잘린 뒤에는 당시 생성 입력을 재구성할 수 없다.

10. [P0] 102문항 게이트가 전혀 다른 제품을 잰다 — §8과 §12-14는 생성 문장·질문의 출시 게이트로 102문항을 사용한다. 실제 `evals/픽스처.json`과 `tools/eval-score.js`의 102문항은 교정 출력·오류 태그·과교정을 평가하며 생성 문장, 질문, 목표 적합성, 신선함을 평가하지 않는다. 102/102 통과는 생성 기능의 품질에 대해 거짓 초록을 낸다.

11. [P0] `position`을 의미가 다른 값으로 재사용한다 — §11-5는 기존 `position`에 배치 처리 순서를 넣지만 C0와 선택로그 계약에서 `position`은 보기의 표시 순서다. 같은 payload 키에 처리 순서와 선택지 순서를 함께 저장하면 소비자가 둘을 구분할 방법이 없다. append-only 행에 이미 섞인 의미는 사후 분리가 불가능하다.

12. [P0] 게임날을 무신호라고 선언하면서 학습자 상태에는 신호로 넣는다 — §3-4는 게임날에 개입 행을 만들지 않는 이유를 학습 신호가 없기 때문이라고 한다. 그러나 현재 `학습자상태.js`의 리듬축은 `task.assigned`를 분모로 읽고 게임 배정 제외 규칙이 없다. 게임날이 이후 생성 입력을 바꾸므로 “신호 0” 판정과 실제 상태 계산이 충돌한다.

13. [P0] 원자 착지가 실패하면 실패 원인도 사라진다 — §3-0은 세 행 중 하나라도 실패하면 전부 없애고, §12-7은 모든 실패 사유를 행에 남기라고 한다. DB·RPC·제약 실패 자체를 기록할 별도 사건은 없으며 `generation_claims`도 `generation_outcome` 소비자가 읽는 기록이 아니다. 배치 미실행과 착지 실패가 같은 빈 상태가 된다.

14. [P1] `payload.ver=2`의 적용 범위가 없다 — §11-2는 이번 판의 값을 2라고 하지만 세 사건의 payload 중 어느 것만 올리는지, 기존 `task_snapshot.ver=1`과 어떻게 공존하는지 정의하지 않는다. 전체를 올리면 기존 소비자가 깨지고 일부만 올리면 사건별 버전표가 필요하다. append-only 데이터에서 같은 날의 버전 해석이 갈린다.

15. [P1] `0.2`는 상태 충분도 문턱이 아니다 — §4-3은 `estimator_confidence < 0.2`를 상태 없음으로 보지만 현재 계산식은 전체 표본 수가 3개만 되어도 약 0.23이 된다. 축별 최소 표본이나 핵심 축 존재 조건이 없고 `쓸축수`도 현재 상태 계약에 없다. 사실상 거의 아무것도 모르는 학생에게 개인화 생성이 실행된다.

16. [P1] 판지문 재료 목록이 닫혀 있지 않다 — §5-1은 여섯 재료가 전부라고 하지만 §11-2의 입력 상한 8000과 §3-5의 claim 만료 24시간도 성공·폴백 여부를 바꾼다. 이 값들을 바꿔도 같은 `policy_ver`가 남을 수 있다. 서로 다른 처치 조건이 한 규칙 집단으로 합쳐진다.

17. [P1] 폴백에서 신선함을 명시적으로 포기한다 — §7-2는 전날 `task_snapshot`을 그대로 재사용하고 §11-3은 우연한 중복을 허용한다. 학생 접점에 나가는 과제가 이전 과제와 같은지, 왜 다시 해야 하는지, 무엇이 새로워졌는지 검사하지 않는다. 판단 정본의 기본 게이트인 “신선함”이 실패해도 정상 배달로 기록된다.

18. [P1] 학생이 왜 다시 열어야 하는지가 없다 — §0·§7·§8은 생성·저장·형식 검문만 정의하고 학생의 재미, 선택감, 피드백, 재방문 동기를 정의하지 않는다. 길이와 한글 비율을 통과한 문장·질문은 학생의 관심이나 실제 목표와 무관해도 `성공`이 된다. 이는 수집 배관이 아니라 학생 접점의 기본 게이트 누락이다.

19. [P1] 초급·미정 학생은 이 기능의 실제 대상에서 빠진다 — §7-1은 1~2급과 미정을 전부 `대상아님`으로 보내며, 개원 초기 도달 학생이 0명일 수 있다고 인정한다. 기존 고르기 과제는 남지만 이 설계가 약속한 상태 기반 문장 생성과 자유 산출은 제공되지 않는다. §12-8의 분포 보고는 이 공백을 사후 표시할 뿐, 학생 경험 결함을 막지 않는다.

20. [P1] 생성 결과와 엔진 학습 대상의 연결이 없다 — §6과 §11은 상태 입력과 생성 요청 본문은 남기지만, 생성 문장이 어떤 어휘 지도 항목·학습자 모델 축·평가 항목을 위한 것인지 필수 연결을 정의하지 않는다. `skill_id`는 명시적으로 신설하지 않으며 응답 계약도 `sentence`·`question`뿐이다. 학생의 답이 쌓여도 엔진이 무엇을 가르치거나 평가한 결과인지 안정적으로 귀속할 수 없다.

이 문서보다 나은 대안 구조 1개: **일일 배달 상태기계 중심으로 재작성**한다. `claim → 벤더 시도 → 성공/검문탈락/폴백 → 세 행 착지 → 학생 스냅샷 → 성과 회수`를 상태별 표로 만들고, 각 상태마다 존재해야 할 행·없는 행·멱등키·세션용 `correlation_id`·재시도·소비자·픽스처를 한 줄씩 고정한다. 생성 전용 평가셋은 교정용 102문항과 분리한다.
