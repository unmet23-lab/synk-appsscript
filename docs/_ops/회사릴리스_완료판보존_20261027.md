# 완료된 회사 배포판 보존과 백엔드 경계 수정 반영

## 원인과 처리

사슬34의 생성기는 삭제된 워크트리의 후보·검수·QA 원문 10개를 다시 요구했다. 완료된 운영판의 소스·Linux 시험 영수증·재무장 증거는 공용 작업본에 남아 있었다.

10개 중 소스 목록·검증기·시험 실행기·QA 결과·TAP 5개는 과거 생성 기록과 보존 사본에서 원래 SHA-256과 같은 바이트로 복원했다. 나머지 5개를 복구한 것으로 처리하지 않았다. 기존 생성기와 증거도 바꾸지 않았다.

대신 완료34판의 소스 1,219개, 이미지 목록 881개, 선택 시험 217개, 실제 Linux 영수증, 재무장 승인·계약·최종 사후 확인과 그 검증기를 별도로 보존했다. 기존 검증기를 저장된 수집 시각으로 다시 실행해 과거의 passed·armed·동일판을 확인했다. 영수증 원문 해시가 실제 재무장 계약의 영수증 해시와도 같아야 한다. 이 확인은 현재 서버 상태 확인과 구분한다.

새 후보는 이 보존본에 백엔드 경계 수정 3파일만 얹었다. 소스 1,220개·이미지 882개·선택 시험 218개이며 비대상 소스 1,217개의 바이트를 보존했다. 공개 자산·스키마·환경 변수는 바꾸지 않았다. 운영 도구는 완료34판에서 다음 판으로 옮기고 기존 소유권·격리 시험·완료 백업·자료 보존·공개 대조·재무장 관문을 유지했다.

재사용 도구는 [완료판 보존 안내](../../tools/company-release/README.md)와 `tests/company-release-closed-parent.test.cjs`다. 준비 도구의 검증기 사본과 실행 자료는 워크트리 밖 공용 `.tmp/backend-release-recovery-20261027/`에 보존한다. 운영 정보가 있는 원문·핀·스냅숏은 공개 저장소에 올리지 않는다.

## 운영 확인

Linux 격리 시험과 재무장용 Linux 검증은 통과했다. 반영 전 백업은 같은 요청의 오프라인 복원 검사·업로드 영수증·로컬 해시·완료 이벤트와 inactive·exit 0까지 확인했다. 백업 진행 중 이미지 준비가 기존 서비스 충돌 관문에서 멈춘 최초 실행은 보존했고, 백업 완료 후 양 노드의 이미지·원천 준비를 마쳤다.

표준 교체는 세 노드 모두 FINALIZE·complete, 되돌림 없이 종료했다. 실제 새 manifest는 `e3affd1c27bd5fc5e6b41e818e85711b02d43d806b8135f6e2518fbe48f1ea25`, image는 `sha256:b975e39ce7abb362babc0a08a4994bccda67523c220d6cdb2dc7ef2da2207338`이다. 실행 사후 확인 passed, 공개 메신저 19/19·전체 공개 파일 246/246, health 200·ready, 익명 보호 API 401, 음성 연결용 CSP·마이크 정책 유지 확인을 통과했다. 이는 교체 중 무중단을 측정한 결과는 아니다.

쓰기 중지 상태의 교체 직전 논리 테이블·일반 파일 보존과 기동 후 DB 스키마 보존은 입증했다. 최초 기동 후 검사에서 `company.sqlite`의 `synk_identity_sessions`는 1행→1행이지만 해시가 달라 실제 로그인 연속성은 미확인으로 남겼다. 당시 집계 해시만으로 정상 만료·활동·회전과 개별 세션 손실을 구별하지 않았다. 아래 후속 검사에서 기존 토큰과 실제 브라우저를 추가 대조했다.

최초 재무장 준비는 `CURRENT_BOTH_NODE_SOURCE_REQUIRED`로 보류됐다. 양 노드 원천·계획·기동 확인은 수집됐으나 대기 노드 시각이 로컬 판정 시각보다 2,523ms 앞서 허용치 2,000ms를 넘었다. `time.google.com`을 읽기만 한 대조에서도 PC가 2.64~2.65초 늦었고 Windows 시간 서비스는 중지 상태였다. 서비스 시작은 권한 부족으로 실패했다. 유호님의 PC 시간 동기화 뒤 −0.0013~+0.0018초를 확인했다. 첫 시도의 static 입력과 held natural은 해시를 대조해 보존하고 새 수집을 실행했다. 원시 시각이나 판정 기준은 바꾸지 않았다.

## CI 설정과 로그인 유지 후속 확인 · 2026-10-27

사용자의 「남은 CI 설정 오류도 고치고 로그인 유지 여부까지 확인」 요청으로 다음을 확인했다.

- CI 실패는 `experiences/synk-town/assets/ask/`의 그림 6개가 희소 체크아웃에서 제외된 것이었다. `syntax-check.yml`과 `records-check.yml`에 같은 폴더 규칙을 추가했다. Git의 실제 `sparse-checkout check-rules`로 수정 전 포함 0개→수정 후 6개를 확인했고, 물음 화면 시험의 실제 파일 읽기 기록을 CI 대조기에 넣어 수정 전 거부·수정 후 통과를 확인했다. 관련 시험 13/13 통과. 원격 CI 결과는 새 커밋의 실행으로 별도 확인한다.
- 기존 Ego 브라우저에서 로그인 동작 없이 워크스페이스가 열렸고, `/api/me`가 새로고침 전후 모두 200·동일 사용자였다. HttpOnly·Secure 세션 쿠키도 같았다. 쿠키 원문이나 계정 식별자는 출력·저장하지 않고 대조용 단방향 해시만 비공개 증거에 남겼다.
- 운영 DB는 읽기 전용 트랜잭션으로 확인했다. 배포의 CAPTURE 영수증에 연결된 기존 토큰 214행 전체와, 현재 토큰 중 배포 후 새로 발급된 세션 4개를 제외한 214행의 집계 SHA-256이 정확히 같았다. 발급 시점 구분은 배포 코드의 7일 세션 만료 규칙으로 후보를 골랐으며, 마지막 판정은 행 수가 아닌 기존 전체 해시의 일치다. 따라서 기존 토큰 행의 삭제·변경 없이 4개가 추가된 것을 입증했다.
- 브라우저 세션의 해시가 그 배포 전 214행 안에 있고, 서버의 유효 세션·같은 사용자·SYNK ID 세션 연결과도 일치했다. **이 브라우저의 기존 로그인은 배포 후에도 유지됨을 확인했다.** 모든 기기·계정을 개별 로그인 시험한 것은 아니다.
- `synk_identity_sessions`의 암호문은 중앙 인증 재확인·갱신 때 `persist()`로 다시 저장되고 `store.encrypt()`는 매번 새 AES-GCM IV를 만든다. 따라서 암호문 전체 해시 변화만으로 로그인 손실을 판정할 수 없다. 실제 배포 후보의 재시작·갱신·중앙 장애·철회·종료 중 갱신 시험 6/6도 통과했다. 실제 고객 데이터·토큰·로그아웃 상태를 변경하거나 운영 서비스를 재시작하지 않았다.

후속 원문은 공용 작업본의 `.tmp/backend-release-recovery-20261027/` 안 `ci-ask-sparse-proof.json`, `login-browser-binding.json`, `retained-session-subset.json`에 보존했다. 최초 전체 토큰 비교가 추가 4행 때문에 불일치한 기록도 남겼으며, 새 부분집합 증거를 그 최초 결과에 덮어쓰지 않았다.

## 광범위 CI 설치 지연 수정 · 2026-10-27

광범위 CI를 끝까지 확인하라는 후속 요청에서 대기열 앞 실행 40502670651은 네 묶음이 통과하고 experiences가 의존성 설치에서 25분 넘게 머물렀다. 실행 중 로그 화면으로 npm 두 번이 2초·469ms에 끝난 뒤 APT 경로에서 출력 없이 지연되는 것을 확인했다. 미러·통신 중 정확히 어디가 멈췄는지는 이 로그만으로 확정하지 않는다.

`wide-tests.yml`은 ffmpeg·ffprobe가 모두 있으면 APT를 호출하지 않으며 둘의 실행 성공을 확인한다. 하나라도 없으면 통신 30초·재시도 2회·패키지 잠금 60초 한도로 설치하고, 단계 전체는 8분으로 제한한다. 설치 실패나 실행 불가는 그대로 실패한다. 시험을 빼거나 실패 기준선을 늘리지 않았다.

새 회귀는 실제 워크플로 Bash를 실행한다. 이전 설정은 6개 중 1통과·5실패, 수정 뒤는 6/6이며 넓은 시험 대조기와 함께 17/17이다. 이전 설정으로 시작한 내 실행 40505328916은 수정판 검증으로 대체하기 위해 취소했다. 다른 세션의 실행은 취소하지 않았다. 원격 완료 여부는 이 수정판의 CI로 확인한다.

## 후속과 보존

- 사라진 작업본을 다음 배포의 필수 입력으로 되살리지 않는다. 다음 판도 완료된 판을 보존하고 명시한 변경만 얹는다.
- 일회용 준비 생산자를 재사용하기 전 실제 별도 출력 재생 시험, 원자적 출력 전환, 시험 전후 소스 벡터 자동 기록을 보강한다. 이번 시험·검수에서 확인하지 않은 재사용 가능성을 보장하지 않는다.
- 읽기 전용 검사에서 현재 문서의 전후 해시 쌍과 QA 핀 존재를 따로 확인했다. 이 세부 단언을 재사용 검사기 자체에 넣는 개선과 추가 거부 조합 시험은 후속이다.
- 원래 QA 실행기, 수정 전 준비 도구, 실패 기록, 검수 원답·형식 정정 답과 전후 메타데이터를 남긴다. 최초 검증기 해시를 기록하지 않았던 한계도 숨기지 않는다.
