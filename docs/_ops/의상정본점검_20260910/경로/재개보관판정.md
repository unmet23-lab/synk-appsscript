## 실제 재사용 위험과 좁은 대응

1. **라디오 재제작 입력은 이미 수정됨:** 현재 `docs/라디오/선정무대_20260910/라이브준비.cjs:7~9`를 다시 읽었다. `leafOriginal`은 `정수리수정/leaf-base-514d7886949b.png`를 가리키며, 출력 이름도 이 파일의 SHA와 확장자로 만든다. 따라서 이 현재 도구가 구 라디오 본체 WebP를 직접 재사용해 점을 되살린다는 판정은 철회한다. 구 WebP 직접 참조는 이전 점검 당시의 위험이며, 재개 첫 보고가 과거 설명을 현재 상태처럼 재사용한 오류였다. 현재 코드 SHA-256은 `0891fbefdfb39b0fc2af9fe9baf8fd14052b8c7be463d02ea78c39ad0c6458b6`, 재조회 HEAD는 `61fe07f1193f7b94c372fea2b2c997fe9ee87ea2`다. 이 수정된 재제작 경로와 아래 아직 남아 있는 기존 PNG/AVIF 파생 경로는 구분한다. 이번 확인은 원문 읽기이며 도구 실행·새 배포는 하지 않았다.
2. **기존 파생물을 새 원본 결과로 오인:** `라디오차림굽기.py`는 `GPT_표정_누끼`에서 직접 파생하고, 앱은 기존 AVIF를 읽는다. 둘 다 수정 후 GPT 원본을 자동 추적하지 않는다. 기존 단계의 점이 남음을 기록하고, 이후 이 단독 차림을 제작할 때만 필요한 단계의 국소 수정/재파생을 검증해야 한다. 다른128차림·몽글·마린의 재생성 권한으로 확대하지 않는다.
3. **Drive 복원은 수리가 아님:** `restore`는 계획에 든 정확한 옛 SHA를 복원한다. pack5의 4K표정은 복원해도 점이 있는 수정 전 파생판이다. 기존 로컬파일을 덮지 않는 보호는 정상이며, 다른 원본을 조용히 대신 쓰지 않는다.
4. **수정 전후 원본의 원격 보관 미완료:** 수정 후 원본은 pack60 계획까지만, 수정 전 백업은 아예 이번 이관 목록 밖이다. 둘 다 로컬에서 보존하고 진행 중 이관 담당의 기존 절차에 원격 확인이 끝났는지 연결해야 한다. 이번 감사에서는 pack60을 앞당기거나 새로운 업로드를 중복 실행하지 않았다.

## Git와 재현 자료

대용량 정책대로 6.72MB 백업과 5.96MB GPT 원본을 새로 Git에 강제 추가하지 않는다. 수정 코드·원본 전후 SHA·복원검증 JSON·원본 상대경로·기존 Drive 계획/영수증 연결과 작은 실배포 PNG/HTML/helper를 Git에 보존하면 된다. 다만 **해시/코드만 보존했다고 원본 바이트 보관이 끝난 것은 아니다.** 두 원본은 실제 Drive 보관 검증 전까지 로컬 회수 대상에 넣지 않는다. 수정 전 백업도 재현 입력으로 필요하다면 기존 이관 담당이 그 파일을 별도 승인/상태 그대로 연결해야 한다.
