| 검수 항목 | 반영 |

## 판단

부분적으로 구조가 복잡해졌고, 변경 내용을 다른 사용처에 빠뜨린 실제 사례가 있다. 전체를 다시 만들기보다는 데이터 전달 오류부터 고치고, 원본과 사용처의 연결을 단순하게 정리하는 편이 적절하다.

| 대상 | 판단 | 가장 먼저 손볼 것 |
|---|---|---|
| 홈페이지 | 기능별 모듈은 작게 나뉘었지만 원본과 생성 결과의 경계가 혼재한다 | 답변의 이동 버튼 누락, 제작 원천과 생성 순서 정리 |
| 앱 | 공통 API·로그·검증은 분리했으나 실패 처리와 화면 중심 연결에 약점이 있다 | 일시 오류 재전송, 충돌 뒤 중복 방지 키 보존 |
| 철학 정본 | 본문은 목적·경계·제품·운영을 구분하고 있다. 파생 요약과 제작 안내가 늦게 따라온다 | 현재 안내에 노출되는 옛 요약·홈페이지 계약 갱신 |

아래 우선도는 저장소 규칙에 따른다. P0는 데이터·인증·라이브 손상, P1은 기능 오류, P2는 품질 문제다. P0 두 건은 특정 실패 조건에서 합성 재현한 데이터 위험이며 실제 학생 피해가 확인됐다는 뜻은 아니다.

## 확인된 문제

### 1. P0 — 일시 서버 오류가 영구 전송 실패로 남는다

- 위치: [사건통로.js:88](C:/Users/q1212/Documents/SYNK-talk/src/사건통로.js:88), [인증API.js:32](C:/Users/q1212/Documents/SYNK-talk/src/인증API.js:32), [제출로그.js:182](C:/Users/q1212/Documents/SYNK-talk/lib/제출로그.js:182).
- 조건: 사건 전송에 HTTP 429·502·503이 돌아오고, 응답에 앱의 표준 `error.retryable` 필드가 없다. 서버 함수 앞단의 오류나 JSON이 아닌 오류 응답이 해당할 수 있다.
- 원인: 통로는 401만 특별 처리하고 나머지는 빈 오류 필드를 인증오류 생성자에 넘긴다. 생성자는 `Boolean(undefined)`를 false로 바꾼다. 사건보내기는 이를 `끝:true`로 반환하며 로그의 `send_final`이 켜진다.
- 영향: `밀린것()`은 해당 항목을 이후 재전송에서 제외한다. 로컬 원본이 즉시 삭제되는 것은 아니지만 회선·서버가 회복돼도 정상 재전송 경로를 타지 못한다. 말하기 화면은 이 반환을 실제 전송 기록에 저장한다([말하기화면.js:317](C:/Users/q1212/Documents/SYNK-talk/src/말하기화면.js:317)).
- 재현: 실제 모듈에 합성 fetch 응답을 연결했다. 429·502·503 모두 `끝:true`, 재시도 목록 0건. 비교용 503에 `error.retryable:true`를 명시하면 `끝:false`였다.
- 정리 방향: 서버가 명시한 영구 거절과 응답 형식을 알 수 없는 일시 실패를 구분한다. 공통 통로의 오류 분류 한 곳에서 처리하고, 실패→로그 저장→회복 뒤 재전송까지 검증한다.

### 2. P0 — 충돌 해결용 새 키가 저장되지 않아 응답 유실 뒤 사건을 중복 저장할 수 있다

- 위치: [사건통로.js:138](C:/Users/q1212/Documents/SYNK-talk/src/사건통로.js:138), [서버 events:485](C:/Users/q1212/Documents/SYNK-talk/supabase/functions/events/index.ts:485).
- 조건: 기존 키가 다른 내용과 충돌 → 새 키로 재전송 → 서버 저장은 성공하지만 응답만 유실 → 같은 로컬 항목 재전송.
- 원인: 새 `idempotency_key`(동일 요청을 중복 저장하지 않도록 구별하는 키)를 임시 사건에만 넣고 원래 항목에는 보존하지 않는다. 다음 시도는 옛 키로 다시 충돌한 뒤 또 다른 새 키를 만든다.
- 영향: 서버의 중복 방지는 학생과 키의 조합 기준이므로 서로 다른 새 키는 별개의 학습 사건으로 남을 수 있다. 한 행동의 반복 집계로 이어질 위험이 있다.
- 재현: 합성 `content.viewed` 사건과 키별 저장을 흉내 낸 서버 응답으로 실제 사건보내기를 두 번 호출했다. 첫 호출은 저장 후 응답 유실, 둘째 호출은 성공했으며 새 사건 저장 수 2건·HTTP 호출 4회였다. 원래 사건의 키는 바뀌지 않았다. 실제 DB에는 쓰지 않았다.
- 정리 방향: 키 변경을 로컬 항목에 지속 저장한 뒤 송신하고, 이후 재시도·재시작이 그 키를 사용하게 한다. 저장 결과 응답을 못 받은 경우까지 검증해야 한다.
