[Supabase 공식 SMTP 문서](https://supabase.com/docs/guides/auth/auth-smtp)에 따르면 기본 발송 수단은 프로젝트 팀 주소와 시간당 2통으로 제한된다. 따라서 **일반 신규 사용자의 이메일 확인 가입은 발송 설정 미비로 막혀 있는 상태**로 분리한다. 관리자 확인된 합성 계정의 PKCE 성공은 이 제한을 검증하거나 해결하지 않는다. 이번 작업에서는 신규 구독·결제·확인 해제·실제 발송을 하지 않는다.

## 문제가 생겼을 때의 좁은 중지

- 새 API 장애는 같은 관리 요청에서 `SYNK_CARE_ENABLED=false`, `SYNK_PERSONAL_ENABLED=false` 두 값만 바꿔 추가 사용을 중지한다. 다른 제품 flag·OAuth mapping·fortune allowlist는 건드리지 않는다.
- OAuth 등록 중단은 journal을 보존하고 추가 등록을 멈춘다. 이미 발급한 ID·토큰·기존 네 클라이언트를 삭제하거나 이전 전체 매핑으로 덮어쓰지 않는다. 기능 중지는 flag로 처리한다.
- 포털 문제가 확인되면 fresh main/current 공개 config 위에서 이번에 더한 authorizationClients 변경만 되돌린다. 다른 작업이 더한 callback·등록·필드는 유지하고, 리허설 config와 bundle은 유지한다.
- migration/table/bucket/사용자/자료를 삭제하거나 schema를 강제로 내리는 rollback은 하지 않는다. 저장된 데이터와 tombstone을 남긴 채 원인과 후속 승인을 정리한다. 배포 도구의 함수 삭제 경로도 사용하지 않는다.
- 로컬 설정을 되돌릴 필요가 있으면 생성한 해당 환경 백업을 확인하고 원자 교체한다. 현재 프로세스 설정은 파일 변경만으로 바뀌지 않으므로 승인한 재시작에서 대상을 재확인한다.
