# 펠트 엔진 — 특허 논의의 기술 근거

확인일 2026-09-11 KST. 특허 상담과 구현 검토를 위한 자료이며, 아래 청구항은 변리사 검토 전의 기술 구성 초안이다. 특정 등록 확률을 산정한 자료가 아니다.

## 핵심 판단

**우리 펠트 엔진으로, 같은 원음의 여러 사용 자격을 나누고 실제 도움 전후의 증거가 잘못 섞이지 않게 처리하는 근거 작업실을 만들었다.** 보호를 검토할 대상은 ‘AI 한국어 학습’이라는 서비스 이름보다, **사용처·능력·평가 시점별 근거 판정이 다음 관측의 선택을 바꾸고, 실제 관측의 도움 내용·발화 시점이 다시 그 근거 자격을 바꾸는 연결 구조**다.

현재 코드에서 설명할 수 있는 좋은 사례는 다음과 같다. 사람이 정확히 확인한 따라 읽기 원음은 음성–전사 자료로 남길 수 있다. 그러나 그 응답만으로 도움 전의 독립 수행을 확정하지 않는다. 늦게 도착한 도움 기록이 이전 판정의 전제를 바꾸면 해당 수행을 다시 보류하거나 제외한다. 영향받지 않는 용도의 근거는 유지한다.

이 연결을 더 구체적으로 구현하고, 반례와 비교 결과로 재현할 수 있게 하는 것이 이번 업그레이드의 권고 방향이다. 구현량·기능 개수·해시·감사 기록 자체를 새 발명의 근거로 삼지는 않는다. 알려진 기술들을 통상적으로 결합한 것이라는 반론은 여전히 검토해야 한다.

- **구체적인 컴퓨터 처리:** 공식 AI 요건 페이지는 소프트웨어 정보처리를 하드웨어로 구체적으로 실현할 것을 설명한다. 펠트에서는 원음 입력 장치, 기록 저장소, 평가 프로세서, 도움 표시 장치, 실제 응답 수신과 갱신 절차를 연결해 제시한다. ‘AI가 신뢰성을 판단한다’는 결과 문장만으로 끝내지 않는다.
- **수단과 효과의 관계:** 같은 페이지는 구체적인 데이터·처리 수단과 입출력 관계, 그 차이로 발생하는 효과를 중시한다. 펠트의 중심은 음성 인식 모델 자체의 발명보다 그 출력과 실제 관측을 받아 사용 자격을 계산하고 갱신하는 처리다. 독자적인 음성 인식 모델을 개발했다고 설명할 이유가 없다.
- **기존 기술로부터 쉽게 도출되는지:** 특허법 제29조 제2항의 관점에서, 부분 인정·확인 질문·도움 전후 평가·의존성 갱신을 연결하는 구체 방식이 통상의 결합에 불과한지 검토한다.
- **재현 가능한 설명:** 특허법 제42조 제3항에 맞춰 입력 필드, 판정 조건, 처리 순서, 예외, 출력, 실행 사례를 명확히 적는다. 실제 코드와 시험은 그 설명을 구체화하는 자료다.

## 3. 독립청구항 후보의 구성 관계

기술 명칭 후보: **사용 목적 및 수행 시점별 증거 자격에 따라 관측을 선택하고 평가 기록을 갱신하는 음성 처리 방법 및 시스템.** ‘펠트’는 제품 명칭으로 함께 표시할 수 있지만 권리 구성의 필수 의미로 사용하지 않는다.

아래 여섯 단계의 연결이 상담용 주력 초안이다. 최종 청구항 문언·필수 구성의 범위는 선행기술 대조 후 정한다.

| 단계 | 처리와 데이터 관계 | 현재 구현에서 대조할 위치 |
|---|---|---|
| ① 증거 발생과 수신을 구분 | 원음 식별자, 녹음 사건 식별자, 원래/새 수행의 구분, 녹음 구간 또는 상대 순서 확인, 도움 표시 사건을 저장한다. 같은 바이트도 서로 다른 수행 사건일 수 있다. | `store.cjs`의 `attach`, `audioForSession`; `core.cjs`의 `captureInterval`, `confirmPerformanceTime` |
| ② 해석과 미확인 범위 유지 | 실제 전사 대안과 사람 확인, 의미·전사·도움의 미확인 범위를 보존한다. 단일 자동 전사 결과를 모든 해석의 완결 확인으로 바꾸지 않는다. | `applyEvent`, `unknownAffects` |
| ③ 목적·능력·시점별 셀 계산 | 각 해석의 효과값과 각 사용처의 자격을 계산한다. 관련 불명이 없고, 효과가 같고, 용도별 조건이 충족된 셀만 인정한다. 음성–전사 자격과 독립 수행 자격을 별도로 계산한다. | `makeCell`, `projectWithPolicy`, `timingFor` |
| ④ 보류 셀에 맞는 관측 선택 | 보류 이유와 목표 사용처·시점에 연결되는 관측 후보를 만든다. 답을 알려주는 새 응답 획득을 과거 독립 수행 확인에 대한 직접 증거로 선택하지 않는다. | `observationCandidates`, `planObservations` |
| ⑤ 실제 관측 수신 | 계획한 질문·예상 답과 실제 도움 표시·응답 사건을 나눈다. 원음 재청취는 기존 증거의 해석을 바꾸고, 새 응답은 새 수행의 증거로 처리한다. | `help-presented`, `review-original`, `review-response`, `response-added`; 실제 표시 후 저장하는 UI |
| ⑥ 귀속 후 갱신 | 실제 사건과 앞선 증거의 관계를 적용해 목적·시점별 결과를 재판정한다. 늦은 도움 사건 등으로 자격이 달라지면 종전 판정을 유지하지 않는다. 판정과 사건을 같은 저장 판본으로 보존한다. | `timingFor`, `earlierBoundary`; `StudioStore.apply`의 원자적 저장 |

중요한 연결은 **③의 결과가 ④의 선택 조건이 되고, ⑤의 실제 사건이 ③의 자격을 바꾸어 ⑥으로 돌아온다는 점**이다. 여섯 기능을 목록으로만 늘어놓으면 이 관계가 드러나지 않는다.

상담용 한 문장 초안:

> 프로세서가 원음과 실제 도움 및 응답 사건을 연결하고, 복수 해석에 대한 사용 목적·능력·수행 시점별 효과와 증거 자격을 계산하여 일부 셀을 반영하고 나머지를 보류하며, 보류 셀의 목표 시점에 적합한 관측을 선택한 후, 실제 관측이 제공한 정보와 도움 노출 순서에 따라 기존 증거의 재해석과 새 수행의 증거를 구별하여 해당 셀을 갱신하는 방법.

이 문장은 최종 법률 문안이 아니다. ‘적합한 관측’, ‘증거 자격’, ‘미확인 범위’의 실제 판정 조건을 아래 알고리즘과 실시예로 뒷받침해야 한다.

### 효과·자격 판정의 설명용 수식

셀 `c = (사용 목적, 능력, 평가할 수행)`에 대하여 지원되는 해석 집합을 `Hc`, 각 해석의 효과를 `effect(h,c)`, 용도별 자격을 `eligible(h,c)`, 관련 미확인을 `unknown(c)`라 둔다.

`admit(c) = Hc가 비어 있지 않음 ∧ unknown(c)=false ∧ 모든 h∈Hc의 자격 충족 ∧ 효과값 집합의 크기=1`.

해석 범위를 자동으로 완전하게 발견했다는 수식이 아니다. 현재 구현은 제한된 문장 규칙과 사람이 확인한 범위를 이용한다. 미지원 표현과 순서 불명은 보류하고, 그 범위 밖을 잘못됐다고 단정하지 않는다. 값이 다른 두 해석은 반례 묶음으로 남겨 보류 이유를 설명한다.

### 종속항·실시예로 검토할 재료

- 답 노출의 능력 범위와 녹음 구간의 선후·겹침을 비교하여 영향받는 수행 셀만 다시 보류하는 처리.
- 같은 원음 해시와 서로 다른 발생 사건을 구분하여 재전사 결과를 정확한 응답 사건에 귀속하는 처리.
- 늦은 기계 결과가 사람의 청취 확인을 덮지 않도록 원응답과 확인 기록을 별도로 유지하는 처리.
- 실제 관측이 예상 응답과 다른 경우 예상 분기를 폐기하고 실제 증거로만 다시 계산하는 처리.
- 판정 변경을 근거·가정·시점별로 설명하고, 내보낸 사건을 재생해 같은 판정을 확인하는 처리.
- 영향 범위만 갱신할 경우, 전체 계산과 같은 결과를 내는 의존성 갱신 방식과 예외 처리.

이 중 현재 구현된 부분과 이번 추가 검증이 필요한 부분은 구분해야 한다. 모델명·엔진 수·언어명·화면 배치·해시 알고리즘을 무조건 독립항에 누적할 필요는 없다.

### 관측 선택의 효과를 주장하려면 필요한 추가 비교

기존 비교 화면의 ‘관계없는 선호 질문’은 목표 연결이 어떤 역할을 하는지 설명하기 쉽지만 약한 비교군이다. 그 질문보다 낫다는 결과로 기존 기술보다 우수하다고 말하지 않는다.

더 강한 비교에서는 **실제로 쓸 만한 같은 후보들**을 모든 정책에 제공한다. 예: 원음의 모호한 구간 재청취, 앞뒤 문맥 재확인, 답을 알려주지 않는 중립 확인, 모범 답안을 제시한 새 응답, 독립적인 새 과제. 각 후보의 예상 시간과 답 노출 범위는 정책 간 동일하게 둔다.

비교 정책은 (A) 음성·해석 불확실성 감소 우선, (B) 목표 보류 셀의 사용 자격과 시점까지 고려, (C) B에서 도움의 영향을 제거한 정책으로 둔다. 이 정책들은 문헌의 제품을 그대로 재구현했다는 뜻이 아니라 비교를 위한 명시적인 기준 규칙이다. 중립 확인도 내용을 암시할 수 있으므로 실제 제시 문안의 답 노출 범위를 확인한다.

측정값은 다음처럼 분리한다.

- **잘못된 반영:** 근거가 불충분하거나 다른 수행 시점의 자료를 받아들인 셀 수 / 판정 대상 셀 수.
- **유효 자료 보존:** 별도 정답표상 사용 가능한 셀 가운데 실제 보존한 수. ‘모두 보류’로 첫 지표만 낮추는 전략을 드러낸다.
- **실제 보류 해소:** 관측 후 새로 자격을 충족한 목표 셀 수. 원래 시점의 해소와 새 시점의 유효 관측을 섞지 않는다.
- **관측 비용:** 실제 경과 시간, 질문·청취 횟수, 통신 호출 수. 현재의 1·5·8초 가정은 이 측정값을 대신하지 않는다.
- **정정 전파:** 정답표상 영향받아야 하는 셀과 실제 변경 셀의 일치, 무관한 셀 변경 수, 처리 시간.

정답표는 정책 출력에서 역으로 만들지 않는다. 원음, 실제 문항, 제시한 도움, 발생 순서를 보고 별도로 작성한다. 사람 평가를 했다면 불일치를 보존하고 조정 전후 결과를 나눈다. 자연음성·실제 사용자 자료 실험은 해당 자료와 환경이 준비된 뒤 수행할 별도 검증이다.

### 계산 규모 실험

응답 수 `R`, 응답별 해석 수 `H`, 목적·능력 셀 수 `C`, 도움 사건 수 `E`를 각각 변화시킨다. 실제 코어 계산·저장·직렬화·전사·통신 시간을 분리해서 잰다. 평균 하나보다 반복 측정의 중앙값과 상위 지연, 입력 크기, 분석 JSON 바이트를 함께 보관한다.

기존 `compared`에는 셀마다 `find`로 대응 셀을 찾는 경로가 있어 최악의 경우 비교 셀 수의 제곱에 비례하는 검색이 들어간다. `timingFor`도 각 수행·능력에서 도움 사건을 훑는다. 따라서 단순히 ‘응답 수에 선형’ 또는 ‘무한 확장’이라고 설명하면 안 된다. 색인이나 부분 계산을 추가했다면 그 코드 경로와 측정 결과로 변경 효과를 따로 보고한다.

## 6. 발표에서 바로 사용할 설명

### 30초 시작

> 우리 펠트 엔진으로 만든 근거 작업실입니다. 한 번의 말하기를 음성 자료와 학습 수행 기록에 함께 쓰다 보면, AI의 오인식이나 답을 알려준 뒤의 성공이 원래 실력으로 섞일 수 있습니다. 이 엔진은 같은 원음이라도 어디에, 어떤 능력의, 어느 시점의 근거로 쓸 수 있는지를 나눕니다. 필요한 확인을 고른 뒤 실제 도움과 응답을 받아 다시 판단하고, 판단이 바뀐 이유까지 남깁니다.

### 왜 보호를 검토하는가

> 저희가 보호를 검토하는 것은 학습 화면 전체가 아니라 근거를 재사용하는 처리 구조입니다. 음성 데이터 품질을 지키면서 도움 전의 수행을 과대평가하지 않고, 정정이 들어오면 영향을 받은 기록을 다시 판단하는 핵심 연결입니다. 같은 데이터가 여러 제품 기능으로 흘러가는 펠트 엔진의 기반이어서 기술 구성과 권리 범위를 검토하고 있습니다.

이는 사업상 보호 필요성에 대한 설명이다. ‘중요한 기능이므로 특허가 허용돼야 한다’는 법적 논증과 다르다. 기술적 차이와 진보성은 앞의 구성·선행기술·비교로 논의한다.

### 미팅의 핵심 요청

1. 가장 가까운 선행의 독립항·실시예와 **여섯 단계의 연결**을 대조해 달라고 요청한다.
2. 목적별 자격이 관측 선택에 영향을 주고 실제 도움 사건이 귀속을 다시 바꾸는 관계 중, 독립항에 남길 필수 구성을 정한다.
3. 구체적인 시간·자격·갱신 방식과 실험 결과 중 명세서에 필요한 실시예를 정한다.
4. 방법·시스템·프로그램 기록매체 청구 형태, 넓은 개념과 좁은 구현의 배치를 검토한다.

현재 단계에서 가장 유용한 답변은 ‘가능성이 높다’라는 인상평보다 **어떤 문헌의 어떤 구성과 겹치며, 어떤 결합과 효과가 남고, 이를 어느 청구범위로 뒷받침할 수 있는가**다.

- 현재 `AGENTS.md`, `docs/AI_운영원칙.md`를 읽었다.
