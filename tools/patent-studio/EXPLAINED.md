**현재 출원 전략은 [등록특허 1건 전략](registration-20260912/STRATEGY.md)을 우선한다.** 이 문서는 전체 원리·버튼·기존 근거의 참고 설명이다. 사용자는 2026-09-12에 권리 폭보다 실제 사업 기술의 등록과 마케팅 신뢰를 우선하도록 목적을 변경했다.

## 01. 이 엔진은 무엇을 판단할까요?

우리 SYNK Core의 근거 자격·관측·재판정 모듈로 작업실을 만들었습니다. 같은 말이라도 어떤 기록에 쓸 수 있는지 따로 판단하고, 확인한 뒤 달라진 이유까지 남깁니다.

예를 들어 학생이 한 문장을 말했습니다. 이 예제에서는 두 가지로 들렸을 가능성을 두었고, 학생은 나중에 모범 답안을 보고 다시 말했습니다. 이때 처음부터 혼자 할 수 있었는지, 받아쓴 문장은 정확한지, 과거형을 썼는지는 서로 다른 질문입니다.

| 우리가 알고 싶은 것 | 필요한 근거 |
| --- | --- |
| 정확히 어떤 말을 했나요? | 원래 음성, 받아쓴 후보, 사람의 청취 확인 |
| 문항의 역할 표현을 혼자 사용했나요? | 당시 문항, 그 발화의 역할 표현, 발화 전 도움 여부 |
| 그 발화에서 과거형을 사용했나요? | 과거형 구간의 해석, 다른 불확실성과의 관계, 과거형에 준 도움 |
| 도움 뒤에는 어떻게 말했나요? | 도움을 실제 보여 준 사건과 이후의 새 응답 |

**핵심은 하나의 점수가 아닙니다**

한 번의 말을 통째로 맞음·틀림으로 처리하지 않고, 각 질문에 쓸 수 있는 관측을 나눠 기록합니다. 여기서 반영은 장기 숙련도 상승이나 정답 인증이 아닙니다.

이 안내서는 먼저 한 문장의 원리를 이해하고, 실제 화면을 따라 시연한 뒤, 어떤 기술 구성을 특허로 검토할지 연결합니다. 설명과 시연에 쓴 가정, 구현된 동작, 아직 입증하지 못한 부분을 함께 표시합니다.

**미팅에서 이름을 세 층으로 구분합니다.** 전체 제품은 `SYNK Atlas`, 판단을 맡는 내부 기술은 `SYNK Core 근거 자격·관측·재판정 모듈`, 출원용 발명의 명칭 1안은 `학습 발화의 사용 목적·능력·시점별 근거 자격 판정 및 관측 기반 선택적 재판정 시스템 및 방법`입니다. 제품명은 기술 표제에 섞지 않고, 최종 청구항의 대상과 발명의 명칭을 일치시킵니다.

| 이미 작동하는 것 | 별도로 판단해야 하는 것 |
| --- | --- |
| 로컬 받아쓰기·용도별 판정·정정·저장·재현 | 학생 학습 효과·다양한 발화의 의미 판정·특허 등록 여부 |
| Loom의 표현 체계와 승인 로고·마스코트 | Loom L1 재질 시스템이나 그 안의 Felt 프로필이 이번 특허 판단의 필수 구성이라는 주장 |

## 02. 이해하고, 보여 주고, 검토받습니다

처음 읽을 때는 원리부터, 미팅 직전에는 시연부터, 변리사와는 권리 범위부터 봅니다.

## 03. 한 문장에서 세 가지 기록이 나옵니다

문항은 “내가 친구를 만난 뒤 카페에 간 일”을 말하는 상황으로 정해 두었습니다.

| 기록 | 해석 A | 해석 B |
| --- | --- | --- |
| 들린 말 | 친구를 만나서 카페에 갔어요 | 친구가 만나서 카페에 갔어요 |
| 정확한 전사 문장 | 친구를… | 친구가… |
| 문항의 역할 요구와 관계 | ‘친구’가 ‘만난 대상’이라는 문항 요구에 부합 | 누가 누구를 만났는지 다시 확인 필요 |
| 과거형 구간 | 갔어요 | 갔어요 |

정확한 전사와 역할 요구는 두 해석에서 결과가 다릅니다. 어느 한쪽으로 정하지 않고 보류합니다. 반면 두 해석 모두 과거형을 사용한 것으로 읽힙니다. 이 예제는 그 과거형 구간을 별도로 판단할 수 있다는 조건도 정해 두었으므로 이 관측을 반영합니다.

**그래서 처음 결과가 1개 반영·2개 보류입니다**

과거형 관측 1개를 반영하고, 정확한 전사·문항의 역할 요구 2개를 보류합니다. 서로 다른 해석의 문장 전체가 같아야만 모든 기록을 만들 수 있는 것은 아닙니다.

이 문장과 두 후보, 문항 조건은 통제 예제의 입력입니다. 실제 음성 인식 모델이 모든 가능한 해석을 빠짐없이 찾아냈다는 뜻이 아닙니다. “친구가”가 한국어에서 언제나 틀렸다는 규칙도 아닙니다. 현재 문항이 요구한 역할과의 관계를 확인하는 것입니다.

**과거형을 보존하는 조건**

관련 해석 범위를 다뤘고, 과거형 구간이 해당 조사 불확실성과 독립이며, 과거형에 영향을 준 도움과 시점을 확인했다는 조건이 필요합니다. 과거형도 불명확하거나 도움 범위를 모르면 보류합니다.

## 04. ‘반영’은 ‘정답’과 다릅니다

이 차이를 이해하면 시연 화면의 숫자에 덜 헷갈립니다.

| 화면 상태 | 정확한 뜻 | 예 |
| --- | --- | --- |
| 반영 | 이 용도의 관측 기록을 만들 조건이 충분함 | 역할 요구에 부합 / 역할 요구 재확인 모두 기록값이 될 수 있음 |
| 보류 | 필요한 해석·문항·시점·도움 조건이 아직 불명확함 | 친구를인지 친구가인지 구분하지 못함 |
| 사용 제외 | 현재 자료가 그 목적에 맞지 않는다는 이유가 있음 | 도움 뒤 응답으로 처음의 독립 수행을 확정하려 함 |

사람이 원래 말을 “친구가 만나서 카페에 갔어요”라고 확인했다고 해봅시다. 전사 후보가 하나로 정리되면 역할 요구와의 관계도 “재확인이 필요하다”로 정해집니다. 그러면 3개 반영이 될 수 있습니다. 세 항목을 모두 잘했다는 뜻은 아닙니다.

| 항목 | 이 경우 반영되는 값 |
| --- | --- |
| 정확한 전사 | 친구가 만나서 카페에 갔어요 |
| 문항의 역할 요구 | 명시된 역할 요구와의 관계 재확인 |
| 과거형 | 과거형 사용 관측 |

**발표할 때 이렇게 말합니다**

“반영은 점수를 올리는 버튼이 아닙니다. 어떤 관측을 근거 있게 남길 수 있는지를 결정합니다. 다시 확인해야 한다는 관측도 근거가 충분하면 기록할 수 있습니다.”

보류는 틀렸다는 낙인이 아닙니다. 제외도 학생의 실패와 같은 말이 아닙니다. 도움 뒤 잘한 응답은 새 응답의 관측으로 쓸 수 있지만, 처음의 독립 수행을 입증하는 사용에서는 제외될 수 있습니다.

## 05. 컴퓨터는 이 순서로 처리합니다

음성을 알아듣는 모델과, 그 결과를 어디에 사용할지 판단하는 처리는 서로 다른 단계입니다.

1. **원음을 고정합니다** — 처음 받은 바이트와 내용 지문을 저장합니다. 나중 전사·검수는 그 원음을 참조하며 원음을 고쳐 쓰지 않습니다.
2. **해석과 조건을 묶습니다** — 기계 후보, 사람 청취 기록, 당시 문항, 도움 사건, 발화 시점과 미확인 범위를 읽습니다.
3. **용도별 판단 칸을 만듭니다** — 사용 목적·능력 항목·평가 대상 발화를 정합니다. 같은 원음에도 다른 칸이 만들어집니다.
4. **사용 자격을 검사합니다** — 해석 범위, 원음·검수 요건, 문항과 시점, 능력별 도움·불명 조건을 검사합니다.
5. **각 후보가 만드는 기록값을 계산합니다** — 관련 후보들이 같은 값으로 모이고 자격 조건이 맞으면 반영합니다. 값이 갈리거나 조건이 부족하면 보류하고, 목적에 부적격이면 제외합니다.
6. **보류와 목적에 맞는 확인을 고릅니다** — 현재의 정해진 행동 후보를 대상 칸·시점·답 노출 여부로 걸러 추천합니다. 예상 결과는 실제 관측으로 저장하지 않습니다.
7. **실제 사건이 도착하면 다시 판단합니다** — 어떤 사건 때문에 어떤 효과를 유지·철회·정정했는지 저장하고 같은 사건으로 재현할 수 있게 합니다.

**현재 구현의 경계**

조사·역할·과거형 판단은 통제 문항의 명시된 규칙입니다. 범용 언어 이해 모델을 새로 학습한 것이 아닙니다. 사람의 청취 확인을 입력으로 받은 뒤, 정해진 규칙의 컴퓨터 처리가 반복됩니다.

## 06. 무엇을 저장해야 같은 판단을 재현할까요?

이름은 기술적이지만, 각 기록이 답하는 질문은 간단합니다.

| 기록과 현재 위치 | 무엇을 남기나 | 왜 필요한가 |
| --- | --- | --- |
| 원음 · audioRef | 원래 바이트의 참조·지문·MIME·녹음 사건 | 다른 응답의 소리를 같은 근거로 오인하지 않기 위해 |
| 기계 전사 · transcription | 실제 모델·텍스트·요청/응답·성공/실패·시도 이력 | 설정 준비와 실제 성공을 구분하기 위해 |
| 청취 확인 · review | 누구의 어느 발화를 어떤 문장으로 확인했는지 | 늦은 기계 전사가 사람 확인을 덮지 않기 위해 |
| 당시 문항 · task | 요구한 역할·지원 범위·과거형 독립 조건 | 나중에 원하는 답을 당시 문항에 덧붙이지 않기 위해 |
| 도움 · help-presented | 보여 준 내용·발생 시각·영향 능력 | 답 노출이 바꾼 수행 자격을 계산하기 위해 |
| 발화 시점 · performanceInterval | 녹음 구간 또는 사람이 확인한 상대 순서·그 출처 | 업로드 시각을 발화 시각으로 오인하지 않기 위해 |
| 판정 칸 · cell | 목적·능력·대상 발화·상태·값·이유·의존 입력 | 하나가 바뀌어도 관계없는 관측을 보존하기 위해 |
| 효과 원장 · effectLedger | 원인 사건·전후 판본·전후 효과·유지/철회·지문 | 최종값뿐 아니라 변화의 이유를 다시 검사하기 위해 |

같은 오디오 바이트를 두 번 응답으로 제출해도 두 사건은 다릅니다. 내용 지문만으로 “가장 최근 응답”에 임의 귀속하지 않습니다. 음성의 동일성과 그 음성을 사용한 사건의 동일성은 분리합니다.

**원장과 제품 반영**

현재는 로컬 SQLite에 저장합니다. 기존 제품의 원음 참조·사람 검수·도움 조회·새 응답 계약과 연결 위치를 대조했지만, 학생 운영 DB를 갱신하거나 숙련도를 낮추는 기능까지 연결한 것은 아닙니다.

## 07. 판정의 순서를 명세서로 옮기면

효과 집합은 각 해석이 만들어 내는 서로 다른 기록값의 모음입니다. 자격 검사와 이 집합을 함께 사용합니다.

| 입력 | 이 예제의 값 |
| --- | --- |
| 평가 대상 | 처음 발화 e0 · 역할 요구 object |
| 가능한 해석 | 친구를… / 친구가… |
| 각 해석의 효과 | 역할 요구 사용 관측 / 역할 요구와의 관계 재확인 |
| 효과 집합 크기 | 2 → 하나의 기록값으로 정할 수 없어 보류 |

과거형 칸에서는 두 해석 모두 “과거형 사용 관측”을 만듭니다. 서로 다른 값의 수는 1입니다. 다만 이것만으로 반영하지 않습니다. 관련 미확인, 지원하는 문장 범위, 과거형 독립성, 발화·도움 조건도 충족해야 합니다.

1. **먼저 대상과 자격을 고정** — 목적·능력·평가 대상 발화를 정하고, 관련 불명·범위·시점·도움 조건을 읽습니다. 조건에 따라 보류 또는 사용 제외 사유를 먼저 남길 수 있습니다.
2. **그다음 지원 해석들의 효과를 계산** — 대안이 없거나 관련 범위를 확인하지 못하면 보류합니다. 자격이 있는 비어 있지 않은 대안들의 효과값이 하나로 모일 때 그 값을 반영합니다.
3. **반영할 값과 이유를 함께 저장** — 상태만 저장하지 않고 실제 값·원인·의존 입력·판본을 남깁니다. 재판정 결과와 직전 반영 기여의 차이를 원장으로 만듭니다.

**현재 코드에 맞춘 설명**

현 구현은 발화·능력 공통 자격을 먼저 검사한 뒤 후보별 효과를 비교합니다. 임의의 해석마다 다른 자격 규칙을 자동 생성하는 범용 논리 엔진이라고 설명하지 않습니다.

## 08. 확인하는 행동도 증거를 바꿉니다

“원래 말을 다시 듣기”와 “정답을 알려 주고 다시 말하기”는 얻는 증거가 다릅니다.

| 행동 | 얻을 수 있는 것 | 얻을 수 없는 것 |
| --- | --- | --- |
| 처음 원음 재청취 | 그때 실제로 어떤 말을 했는지에 대한 해석 정정 | 새로운 학생 수행 |
| 문항·도움·시점 확인 | 기존 관측이 어떤 용도에 적격인지 판단할 조건 | 체크만으로 만들어진 실제 문항·도움 사건 |
| 모범 문장을 보여 준 뒤 새 응답 | 도움 뒤의 실제 새 수행 | 처음에 혼자 했다는 소급 증명 |
| 들리지 않는 구간을 들렸다고 예상 | 계획상의 가능한 분기 | 실제 청취 결과 |

지금 풀고 싶은 것이 “처음 발화의 역할 요구를 독립적으로 사용했는가”라면, 모범 답안을 따라 말하게 해도 그 보류가 풀리지 않습니다. 그래서 그 행동을 처음의 독립 수행 보류를 해소할 추천으로 선택하지 않습니다. 교육 활동으로 실행하는 것은 가능합니다.

**화면의 추천은 어떤 알고리즘인가요?**

현재는 준비된 확인 행동과 조건부 결과를 사용합니다. 보류 칸을 대상으로 삼는지, 그 시점에 쓸 자격이 있는지 먼저 검사하고 정해 둔 비용 가정도 사용합니다. 1·5·8초 비용은 현장 실측값이나 보편적인 최적값이 아닙니다.

“가장 싼 질문을 한다”만으로 설명하지 마세요. 현재 목표의 근거를 만들 자격이 있는 확인인지를 먼저 따져야 합니다. 실제 응답이 없거나 재청취해도 불분명하면 해소된 항목 수는 0일 수 있습니다.

## 09. 나중에 알게 된 사실은 무엇을 철회하나요?

사건이 일어난 때와 시스템이 그 사실을 알게 된 순서는 다를 수 있습니다.

1. **처음 계산** — 예제에서 원래 전사와 문항·독립 조건을 확인해 세 항목을 반영했습니다.
2. **뒤늦은 기록 추가** — 발화보다 1분 전에 조사 표현 “친구를”를 보여 줬다는 가상의 사건을 추가합니다. 이 예제의 영향 능력은 조사·역할 항목입니다.
3. **자격 재검사** — 그 조사 표현을 도움 전에 혼자 사용했다는 전제가 깨집니다. 이미 반영했던 해당 수행의 기여를 철회하고 사용 제외로 바꿉니다.
4. **관계없는 관측 유지** — 정확한 음성–전사 자료의 자격은 도움 유무와 별도입니다. 이 예제에서 독립 조건을 둔 과거형 관측도 유지합니다.

| 정정 전 | 추가 사실 | 정정 후 |
| --- | --- | --- |
| 전사 자료 반영 | 조사 표현 도움 | 반영 유지 |
| 처음 역할 수행 반영 | 그 발화 전에 조사 도움 | 기존 기여 철회 → 사용 제외 |
| 과거형 관측 반영 | 과거형에 준 도움 아님·독립 조건 | 반영 유지 |

**다른 조건이면 결과도 달라집니다**

도움이 문장 전체·과거형에 영향을 주면 과거형도 유지한다고 단정할 수 없습니다. 또 정확한 발화 구간 없이 상대 순서만 확인한 파일에 늦은 도움이 추가되면, 먼저 순서를 다시 확인해야 하므로 보류할 수 있습니다.

일반 “도움 문장 보여 주고 기록” 버튼은 현재 지원하는 조사·과거형 두 능력에 대한 도움으로 기록합니다. “늦은 도움 정정 예제”는 조사만의 가상 과거 도움을 추가하는 별도 통제 사례입니다.

## 10. 바뀐 이유를 남기고 다시 계산합니다

현재 값이 맞는지뿐 아니라, 그 값이 어떤 사건에서 나왔는지도 확인합니다.

원장 한 줄은 “이 사건이 들어와 v1에서 v2가 됐고, 역할 수행 1개를 철회하며 다른 2개를 유지했다”를 연결합니다. 전후 값·상태·이유·참조 지문이 함께 남습니다. 이 저장은 사건과 현재 판정의 갱신과 같은 트랜잭션으로 처리합니다.

| 검사 | 확인하는 것 | 확인하지 않는 것 |
| --- | --- | --- |
| 저장 기록 재현 | 같은 코드와 저장 사건으로 같은 판정이 나오는지 | 기록하지 않은 현실 사건의 존재·부재 |
| 원음 내용 지문 | 내려받은 바이트가 참조한 원음과 일치하는지 | 현실에서 누가 언제 발화했는지에 대한 외부 인증 |
| 코드 지문 | 이 실행과 같은 판정 코드를 사용하는지 | 다른 버전에도 결과가 언제나 같다는 보장 |

입력과 결과의 지문이 맞는 효과는 재사용합니다. 한 응답 정정에 관련 없는 효과를 매번 다시 계산하지 않도록 했습니다. 그러나 입력 지문 비교, 관측 계획, 설명 조립은 계속 필요합니다.

| 41개 발화의 통제 측정 | 전체 효과 계산 | 이전 결과 재사용 |
| --- | --- | --- |
| 실제 효과 함수 실행 | 488회 | 12회 |
| 7회 실행 시간 중앙값 | 29.067ms | 26.760ms |
| 의미 판정 결과 | 같음 | 같음 |

**정확한 발표 표현**

“이 조건에서 반복 효과 계산이 줄었고 결과가 같았습니다.” 전체가 40배 빨라졌다고 말하지 않습니다. 음성 인식·통신·DB 저장·동시 사용자 부하는 이 측정에 포함하지 않았습니다.

## 11. 488회에서 12회로 줄었다는 뜻

줄어든 것은 특정 효과 함수의 실행 횟수입니다. 전체 응답 시간은 별도로 측정했습니다.

| 조건/측정 | 이번 실제 기록 |
| --- | --- |
| 규모 | 첫 발화 1개 + 응답 40개 · 본 판정 163칸 · 본 판정과 비교 4개의 5개 설정 |
| 정정 입력 | 중간 응답 하나를 정정 · 동일 입력의 전체/재사용 계산 대조 |
| 효과 함수 | 전체 488회 / 재사용 12회 · 기존 결과 476회 재사용 |
| 전체 연산 중앙값 | 7회에서 29.067ms / 26.760ms · 저장·전사·통신 제외 |
| 동일성 | 1,280개 생성 사건 전환에서 본 판정과 4개 비교가 전체 계산 결과와 일치 |

효과 함수 호출은 약 97.5% 줄었습니다. 입력 지문·계획·결과 조립 작업이 남기 때문에 실행 시간이 같은 비율로 줄지는 않았습니다. 이 측정만으로 운영 서버 처리량이나 대규모 학습 데이터의 성능을 보장할 수 없습니다.

**규모가 커지면 따로 볼 축**

응답 수 R, 응답당 후보 수 H, 판정 칸 수 C, 도움 사건 수 E, 저장 이력 길이를 각각 변화시킵니다. 현재 도움 선후 검사는 관련 도움 목록을 훑고, 비교 셀 대응에는 반복 검색이 있어 단순히 전체 선형이라고 부를 수 없습니다.

다음 부하 실험에서는 계산·SQLite 저장·직렬화·음성 인식·전송을 나누고 중앙값과 느린 구간, 메모리, 내보내기 바이트를 기록해야 합니다. 캐시·내용 지문·부분 갱신 자체의 새로움보다, 목적별 자격 정정을 같은 의미 결과로 수행하는 구체 수단과 효과를 설명합니다.

## 12. 기존 제품의 어디에 연결될까요?

원음을 모으는 곳과 그 원음을 근거로 사용하는 곳 사이에, 목적별 판정과 정정 계약을 연결합니다.

| 현재 제품의 연결 지점 | 연결할 책임 | 현재 남은 일 |
| --- | --- | --- |
| TALK uploads · events | audio_ref와 제출 사건·당시 task_snapshot 고정 | 로컬 파일 참조를 운영 원음 참조로 바꾸고 사건 귀속 검증 |
| TALK transcribe · review | 기계 transcript와 사람 transcript_verified 분리 | 후보·지원 범위·청취 근거판 연결 |
| TALK correction.viewed · retry 관계 | 도움의 실제 표시와 후속 발화 사건 연결 | 도움 내용·능력 범위·발생 순서·미확인 보존 |
| TALK 학습자상태 · GAS 교재연동 | 적격 관측만 해당 시점의 상태·도달 판단에 제공 | 용도별 소비 계약과 정정 반영을 운영 DB에서 검증 |
| TALK review supersedes | 재검수가 이전 근거를 바꾼 영향 추적 | 취소할 파생 기여·유지할 기여를 소비처와 합의 |

이 표는 INTEGRATION.md에서 기존 함수 본문과 계약을 대조한 연결안입니다. 현재 실제 실행은 로컬 SQLite 작업실까지입니다. 학생 DB·Apps Script·Supabase 운영 경로를 이번 시연으로 갱신하지 않습니다.

**책임 경계**

전사기는 들린 말의 기계 후보를 반환합니다. 검수자는 실제 청취·문항·시점 조건을 확인합니다. 근거 코어는 그 입력의 자격과 효과를 계산합니다. 제품 소비자는 적격 관측으로 다음 과제나 상태를 계산하고, 철회 사건을 받았을 때 자신의 파생 결과를 정정합니다.

기존 masteryApply_의 상향 규칙을 자동 강등 규칙으로 바꾸는 작업은 별개입니다. “근거 한 칸의 사용 철회”가 바로 학생의 등급 하락을 뜻하지 않도록 소비 계약을 구체화해야 합니다.

## 13. 세 장면을 나누면 설명이 선명해집니다

실제 받아쓰기와 통제 예제의 판단 원리를 각 장면에서 분명히 보여 줍니다.

| 장면 | 무엇을 증명하나 | 보여 줄 결과 |
| --- | --- | --- |
| A · 합성 음성 실제 전사 | 원음 바이트를 인식기에 넣고 실제 결과를 저장 | 기계 전사만으로 사람 확인·독립 수행이 되지 않음 |
| B · 두 해석의 부분 반영 | 한 발화의 후보를 용도별 기록값으로 나눔 | 1개 반영·2개 보류 → 청취 조건 확정 후 값 확인 |
| C · 늦은 도움의 정정 | 새 사건이 바꾼 자격만 철회하고 이유를 저장 | 3개 반영 → 1개 철회·2개 유지 → 재현 일치 |

1. **시작** — start.cmd를 실행합니다. 또는 이미 켜져 있으면 http://127.0.0.1:4318을 엽니다.
2. **받아쓰기 방식** — “기기 안에서 · 인터넷 없이”를 확인합니다. 외부 모델 선택은 다음 전송·재시도에 적용됩니다.
3. **준비 확인** — “시연 준비 확인”에서 저장·자산·합성 원음·실제 로컬 전사·판정 예제의 결과를 확인합니다.
4. **기록 구분** — 장면마다 새 시연을 만듭니다. 실제 음성과 가상 청취·도움 조건을 같은 종류의 증거로 설명하지 않습니다.

**5분 구성**

원리 40초 → 장면 B 1분20초 → 장면 C 1분30초 → 장면 A 1분 → 특허로 검토할 관계와 범위 30초. 자세한 질문이 나오면 뒤의 요건·구성 페이지로 이동합니다.

처음 원음의 재청취와 도움 뒤 새 수행은 별개의 경로입니다. 준비된 10개 판본의 전체 실험 기록도 함께 가져가되, 그 사람 확인 칸은 자동 시험에서 넣은 조건임을 밝힙니다.

## 14. 실제 받아쓰기와 사람 확인을 나눕니다

클릭부터 결과를 읽는 문장까지 이 순서를 그대로 따라가면 됩니다.

1. **직접 녹음 → 합성 음성으로 시작** — 준비된 WAV를 실제 로컬 인식기에 보냅니다. 합성 음성 표시를 먼저 가리킵니다. “지금은 학생 자료 없이 실제 전사 연결을 보여 드립니다.”
2. **받아쓴 말 확인·직접 입력을 펼칩니다** — 실제 받아쓴 문장과 원음 재생기를 확인합니다. 처리 경로를 열면 기기 안에서의 인식과 모델 정보를 볼 수 있습니다.
3. **가운데 세 칸을 봅니다** — 기계 전사만 도착한 새 합성 파일 시연은 0개 반영·3개 보류입니다. “모델이 문장을 돌려줬다는 사실만으로 사람 확인이나 수행 근거가 되지는 않습니다.”
4. **원음을 재생하고 들린 말을 확인합니다** — 실제 들은 문장을 입력하고 청취 확인만 저장합니다. 발화 시점·독립 수행 체크를 학생의 실제 사실처럼 누르지 않습니다.
5. **1개 반영·2개 보류를 설명합니다** — 정확한 음성–전사 자료의 자격을 반영할 수 있지만, 실제 학생의 문항 수행·독립 시점을 입증한 것이 아니므로 수행 칸은 남습니다.

**입력 문장은 들은 대로**

샘플의 실제 결과는 “친구를 만나서 카페에 갔어요.”였습니다. 다른 결과가 나오면 정답에 맞춰 덮어 쓰지 말고 원음을 들어 실제로 들린 말을 확인합니다. 실패해도 원음은 저장됩니다.

본인 목소리로 시연할 때는 새 녹음 기록을 만들고 녹음·종료·재생을 진행합니다. 이번 자동 검증은 본인 물리적 마이크의 품질이나 학생 음성 정확도를 검증하지 않았습니다.

## 15. 후보가 갈려도 남길 수 있는 기록이 있습니다

먼저 두 해석이 들어 있는 통제 예제를 열어 주세요.

1. **예제로 보기 → 조사는 보류, 과거형은 보존 → 이 예제로 시작** — 왼쪽의 예제 입력 표시를 보여 줍니다. “이 장면은 두 해석과 문항 조건을 정한 통제 사례입니다.”
2. **문항의 역할 요구 사용 → 판정에 연결된 근거 보기** — 친구를/친구가가 서로 다른 기록값을 만든다는 것을 보여 줍니다. 정확한 전사와 역할은 보류, 독립 조건의 과거형은 반영됩니다.
3. **원음을 다시 듣고 확정하기에 후보 하나 입력** — 이 예제의 가상 청취 결과를 정합니다. 실제 원음이 없는 예제에서 들었다고 말하지 않습니다.
4. **친구가 만나서 카페에 갔어요 → 예제 확인 → 청취 전사 확정** — 3개 반영이 되지만 역할 항목의 값은 “명시된 역할 요구와의 관계 재확인”입니다. 그 문구를 읽어 줍니다.
5. **판단이 바뀐 이유를 봅니다** — “모든 항목을 정답으로 바꾼 것이 아닙니다. 이제 어떤 관측인지 정할 근거가 생겼다는 뜻입니다.”

**실패·다른 결과가 나왔을 때**

다른 예제·이전 사건이 섞였는지 확인하고 새 예제로 시작합니다. 코드와 조건에 맞지 않는 수치를 외워서 말하지 말고, 현재 칸의 상태·값·이유를 읽습니다.

예제의 모르는 원인이 남은 경우도 볼 수 있습니다. 후보가 같아 보여도 관련 범위를 다뤘다고 확인할 수 없으면 보류합니다. 단순한 후보 수 감소와 근거 자격은 다릅니다.

## 16. 화면의 어디를 가리킬까요?

설명은 숫자와 함께 항목의 값·이유를 가리킬 때 정확해집니다.

화면 기록: 13-object-before.png — 처음 · 전체는 1개 반영·2개 보류. 역할 칸은 두 해석의 기록값이 달라 보류합니다.

화면 기록: 14-object-after.png — 친구가로 확정한 뒤 · 전체는 3개 반영. 이 역할 칸에 남은 값은 “관계 재확인”입니다.

**숫자 다음에 이 칸의 값을 가리킵니다**

“반영은 정답 인증이 아닙니다. 역할 요구를 다시 확인해야 한다는 관측도, 그 관측의 근거가 정해지면 기록할 수 있습니다.” 전체 화면은 근거묶음의 상세캡처에 함께 보존했습니다.

## 17. 기존 판단을 철회하는 순간을 보여 줍니다

현재 화면의 전용 버튼으로 실행하고, 저장 원장까지 이어갑니다.

1. **예제로 보기 → 늦은 도움 정정 예제** — 새 통제 기록을 만듭니다. “정정 전 · 3개 반영 · 0개 보류”를 확인합니다.
2. **설명 문구를 먼저 읽습니다** — “발화 전에 조사 표현 ‘친구를’를 보여 줬다는 가상의 기록을 뒤늦게 추가합니다.” 실제 학생 도움 이력이라고 말하지 않습니다.
3. **발화 전 도움 기록을 뒤늦게 추가** — 서버가 예제 사건을 저장하고 새 판정을 돌려줍니다. 1개 철회·2개 유지가 나타납니다.
4. **세 항목의 전후를 읽습니다** — 역할 요구는 반영→사용 제외, 정확한 전사와 독립 조건의 과거형은 반영→반영입니다.
5. **근거가 바뀐 기록 → 저장 기록 재현 확인** — 원인 사건·v1→v2·철회와 유지를 보여 줍니다. 저장 사건과 판정이 일치하는지 검사합니다.
6. **기록 내려받기** — 실제 저장 사건과 원장·재현용 입력을 가져갑니다. 이 예제의 원음 수는 0입니다. 별도 합성 음성 실험의 원음 2개와 혼동하지 않습니다.

**중간에 조건을 바꿨다면**

이 전용 예제는 출발 조건을 바꾼 경우 과거 도움 추가를 잠급니다. 새 예제로 다시 시작합니다. 저장 성공 뒤 응답이 끊겨도 같은 사건을 재시도하면 중복 반영하지 않는 것을 시험했습니다.

## 18. 정정의 전후를 붙여서 봅니다

시연용 과거 도움을 추가한 실제 서버 응답 화면입니다.

화면 기록: 06-correction-before.png — 추가 전 · 3개 반영
화면 기록: 07-correction-after.png — 추가 후 · 1개 철회·2개 유지

화면 기록: 09-replay.png — 세 판본의 사건·판정 재현 검사 결과

**철회가 뜻하는 것**

새 사실로 인해 이전 기록이 해당 목적에 더 이상 적격하지 않다는 뜻입니다. 원음을 삭제하거나 학생의 전체 능력을 일괄 강등하는 동작이 아닙니다.

## 19. 도움을 준 뒤 새 응답까지 보여 주려면

기본 3장면을 마친 뒤 시간이 남으면 사용하는 전체 흐름입니다. 실제 수행과 합성 시험 가정을 구별합니다.

1. **새 기록에서 첫 원음을 저장** — 받아쓰기 local을 확인하고 녹음 시작 → 녹음 마치고 저장. 문항은 통제 예제와 같게 안내합니다. 물리적 마이크·스피커는 현장에서 직접 확인합니다.
2. **처음 발화를 실제 청취해 확인** — 문항의 역할 요구·독립성·앱 내 도움 범위를 사실에 맞게 입력합니다. 원음을 재생해 들은 말을 적고 청취 전사 확정. 모든 조건이 맞는 통제 문장에서는 3개 반영이 됩니다.
3. **도움 문장을 표시하고 사건 저장** — 진행자가 준비할 도움 문장 → 도움 문장 보여 주고 기록. 저장 확인 뒤 이제 다시 말해 보기. 도움을 보여 주는 것만으로 새 응답이 생기지는 않습니다.
4. **새 응답을 별도 원음으로 저장** — 새 응답 녹음 → 녹음 마치고 저장. 첫 원음을 덮어쓰지 않습니다. 저장된 응답의 청취 확인에서 해당 응답을 선택해 실제로 듣고 문장·도움 범위를 확인합니다.
5. **결과값과 시점을 함께 설명** — 조건이 모두 맞으면 6개 반영·1개 사용 제외. 새 응답의 원음–전사와 도움 이후 수행을 남기고, 이 응답을 처음의 독립 수행 증명으로 쓰는 한 칸은 제외합니다.

**이 전체 흐름에서 이미 확인한 것**

자동 브라우저 시험은 자체 합성 WAV를 Chrome 시험 입력 장치에 넣어 실제 MediaRecorder·로컬 전사·저장·재현을 통과했습니다. 세션 출처도 synthetic-speech로 저장됩니다. 사람 확인 항목은 시험 가정이며, 실제 학생이나 물리적 마이크의 성공을 입증하지 않습니다.

합성 파일의 업로드 시각을 실제 발화 시각으로 확인하지 마세요. 음성 파일만 넣고 시점이 불명확하면 6개 반영 결과가 나오지 않을 수 있습니다. 그 보류가 현재 조건에 맞는 결과입니다.

## 20. 6개를 남기고 1개를 제외하는 이유

나중에 잘 말한 사실을 보존하면서도, 그 사실로 과거를 바꾸지 않습니다.

| 판정 칸 | 통제 조건을 모두 확인한 결과 | 뜻 |
| --- | --- | --- |
| 첫 원음의 전사·역할·과거형 | 3개 반영 | 처음 발화에서 확인된 관측 |
| 새 응답의 전사 | 1개 반영 | 도움 이후 실제 원음과 청취 전사의 쌍 |
| 새 응답의 역할·과거형 | 2개 반영 | 도움 이후 그 표현을 사용했다는 관측 |
| 새 응답으로 처음 독립 수행 확정 | 1개 사용 제외 | 후속 발화로 이전 발화의 독립 수행을 소급 입증할 수 없음 |

**이때 발표할 문장**

“도움을 받은 뒤 잘한 것은 실제로 남깁니다. 다만 그 성공이 일어난 시점과 조건도 함께 남깁니다. 따라서 처음부터 혼자 할 수 있었다는 기록으로 바뀌지는 않습니다.”

기록 내려받기를 누르면 두 원음과 사건·판정 원장이 함께 나옵니다. 현재 합성 브라우저 시험 묶음은 v0~v9의 10개 판본과 원음 2개를 동일 코드로 재현했습니다. 이 재현은 저장된 사건에서 계산한 결과의 일치입니다. 앱 밖 도움의 부재나 학습 향상의 인과효과를 인증하지 않습니다.

**모든 응답에서 숫자를 맞추려 하지 않습니다**

규칙이 다루지 않는 “오늘은 집에서 쉬었어요”라면 전사는 남길 수 있어도 현재 문항의 수행 항목은 보류합니다. 실제 말이 예제와 달라지면 결과도 달라져야 합니다. 미응답·다른 응답을 예상 문장으로 채우지 않습니다.

## 21. 질문이 나오면 이 구분으로 돌아갑니다

아래 결과는 단어의 정의와 조건을 함께 설명해야 이해됩니다.

| 질문 | 답할 내용 |
| --- | --- |
| 같은 문장이면 바로 반영하나요? | 아니요. 관련 해석 범위와 문항·시점·도움·검수 자격을 함께 확인합니다. |
| 청취 확인을 누르면 AI가 맞아지는 건가요? | 사람이 확인한 별도 입력을 저장하는 것입니다. 모델의 원래 출력·시도 이력은 남습니다. |
| 도움이 있으면 모든 자료를 버리나요? | 아니요. 정확한 음성–전사 자료, 도움 뒤 수행, 도움 전 독립 수행은 다른 용도입니다. |
| 새 응답으로 처음을 고칠 수 없나요? | 처음 원음 재청취는 그 원래 말의 해석을 고칠 수 있습니다. 새 응답으로 처음의 독립 수행을 소급 확정하는 것은 제외합니다. |
| 과거형은 언제나 유지하나요? | 아니요. 예제의 독립 조건과 도움의 능력 범위에 한정합니다. 문장 전체 도움이나 불명은 다른 결과를 낼 수 있습니다. |
| 해시가 같으면 현실의 진실도 보장하나요? | 기록 내용의 일관성을 확인합니다. 외부 시각·발화자·기록 밖 사건을 인증하는 것은 아닙니다. |
| 예제 통과가 제품 통합 완료인가요? | 아니요. 현재 로컬 처리와 검증 범위를 확인했습니다. 학생 운영 DB 연결과 장기 학습 효과는 별도입니다. |

**정상적으로 멈춰야 하는 상황**

원음이 들리지 않거나, 문항의 조건을 모르거나, 파일의 발화 시점을 확인하지 못하면 그 보류를 남깁니다. 모든 칸을 반영으로 만드는 것이 이 시연의 목표가 아닙니다.

## 22. 기술이 작동한다는 것과 특허 요건은 다릅니다

실용적인 용도와 구체적인 구현의 근거는 있습니다. 같은 기술이 이미 있는지, 차이가 쉽게 도출되는지는 선행기술과 청구항을 대조해야 합니다.

| 요건 · 쉬운 뜻 | 현재 근거 | 현재 판단과 보완 |
| --- | --- | --- |
| 산업상 이용가능성 · 실용적인 기술인가 | 음성 자료와 수행 기록을 구분해 저장·정정하는 용도가 있습니다. | 실용 용도의 근거가 있습니다. 제품 배포 완료나 학습 효과 입증과는 별개입니다. |
| 발명 성립성 · 구체적인 컴퓨터 처리인가 | 원음·전사·도움·시점을 읽고 자격 계산과 관측 선택을 실행합니다. | 사람이 주는 입력과 이후의 연산을 나누고, 그 연결을 청구항에 적어야 합니다. |
| 신규성 · 같은 구성이 이미 있는가 | 목적·시점별 자격과 관측·재판정의 연결이 비교 대상입니다. | 미확정입니다. 하나의 선행발명마다 전체 구성과 연결을 대조해야 합니다. |
| 진보성 · 차이가 있어도 쉽게 만들 수 있는가 | 연결을 뺀 비교와 늦은 도움 정정의 재현 자료가 있습니다. | 미확정입니다. 알려진 기술의 통상적인 조합이라는 반론을 검토해야 합니다. |

신규성은 같은 구성인지의 문제이고, 진보성은 차이가 있어도 쉽게 만들 수 있는지의 문제입니다. 기능 이름이 새롭거나 코드가 길다는 사실로 두 요건이 충족되지는 않습니다. 여러 기술이 이미 알려졌다는 이유만으로 결합 전체의 진보성이 곧바로 부정되는 것도 아닙니다. 실제 연결과 결합의 근거를 따져야 합니다.

**컴퓨터라는 단어만 더하면 되나요?**

아닙니다. 목적에 맞는 구체적인 연산·가공을 적어야 합니다. 새로운 전용 칩이 필수라는 뜻도 아닙니다. 일반 PC가 어떤 입력을 어떤 조건으로 처리하는지 설명하는 것이 우선입니다.

근거: [특허법 제2조](https://www.law.go.kr/LSW/lsLinkCommonInfo.do?chrClsCd=010202&lsJoLnkSeq=1030487745), [제29조](https://law.go.kr/LSW/lsLinkCommonInfo.do?chrClsCd=010202&lsJoLnkSeq=1030488663), [AI 가이드 1310~1312쪽](https://kipo.go.kr/ko/kpoContFileDown.do?seq=5&fileNum=1). 위 표의 평가는 현재 Core 모듈 구현에 대한 검토 의견입니다.

## 23. 설명할 수 있는 범위와 권리의 주체를 맞춥니다

명세서는 발명을 설명하는 문서이고, 청구항은 보호받으려는 구성을 정하는 문장입니다. 코드와 시연 자료를 이 문서들에 맞게 옮겨야 합니다.

| 요건 · 쉬운 뜻 | 현재 근거 | 남은 설명 |
| --- | --- | --- |
| 실시가능한 설명 · 기술자가 재현할 수 있는가 | 실행 코드·사건 기록·정정 및 재현 사례가 있습니다. | 입력 필드, 조건 순서, 예외와 완전한 입출력 사례를 명세서에 적습니다. |
| 뒷받침 · 권리 범위가 설명을 넘지 않는가 | 통제 문장의 조사·역할·과거형 처리 관계를 보여 줍니다. | 범용 처리와 문항별 규칙을 나누고, 일반화할 수 있는 범위를 정합니다. |
| 명확성·간결성 · 보호할 처리가 구별되는가 | 반영·보류·제외와 발생·수신, 기존·새 수행을 구분합니다. | 적합한 관측·충분한 근거 같은 표현을 데이터와 조건으로 정의합니다. |
| 발명자·권리자 · 누가 발명하고 출원하는가 | 사용자는 단독 설계라고 확인했습니다. | 구체 기술 구성에 대한 인간 기여를 설명하고 개인·회사 출원 관계를 맞춥니다. |

현재 문장 하나만으로 모든 자연어·모든 능력·모든 도움을 자동 판정한다고 넓히기 어렵습니다. 반대로 현재 예문의 문장 자체를 반드시 권리 범위의 한계로 고정해야 하는 것도 아닙니다. 공통으로 재현되는 처리와 바꿔 넣어야 하는 규칙을 설명한 뒤 적절한 폭을 검토합니다.

**‘나 혼자했어’의 반영 범위**

단독 설계·공동 설계자 없음이라는 사용자 진술로 기록합니다. 회사 대표라는 지위만으로 발명자나 권리 승계 완료를 자동 확정하지 않습니다. AI를 사용한 사실과 사람이 구체적인 구성을 설계·판단한 역할도 구분합니다.

근거: [특허법 제42조 제3·4·6항](https://law.go.kr/LSW/lsSideInfoP.do?docCls=jo&joBrNo=00&joNo=0042&lsiSeq=279827&urlMode=lsScJoRltInfoR), [제33조](https://law.go.kr/LSW/lsSideInfoP.do?docCls=jo&joBrNo=00&joNo=0033&lsiSeq=279827&urlMode=lsScJoRltInfoR). 배경기술의 설명도 필요합니다. 현재 자료가 최종 명세서 심사를 통과했다는 뜻은 아닙니다.

## 24. 무엇을 권리로 묶을지 좁힙니다

청구항은 보호를 요구하는 기술의 범위입니다. 아래는 변리사와 다듬을 구성 관계 초안이며 확정 청구항이 아닙니다.

| 필수 관계 후보 | 구체적인 처리 |

| C1 · 사건과 시점 | 원음·발화 사건·발화 구간/확인 순서와 도움 사건 연결. 발생 순서와 뒤늦게 수신한 순서를 구분 |

**독립항과 종속항의 역할**

가장 가까운 기술과 대조해 꼭 필요한 관계를 독립항에 남깁니다. 구간 겹침·시점 불명·영향 능력별 정정·원음 불변·동일 결과 재계산 등 구체 구현은 뒷받침되는 범위에서 종속항을 검토합니다. 모델명·마스코트·색·해시 이름을 모두 필수로 넣을 이유는 없습니다.

실제 코드는 제한된 문항 규칙과 고정 행동 후보입니다. 그 한계를 넘는 범용 구현을 설명 없이 청구하지 않습니다. 반대로 특정 예문 하나로 반드시 권리를 한정해야 한다고 미리 결론내리지도 않습니다.

## 27. 사람이 준 정보와 컴퓨터의 연산을 나눕니다

청취 확인 버튼이 음성의 진실을 자동으로 만드는 것은 아닙니다. 사람의 확인을 입력으로 받은 다음, 컴퓨터가 어떤 처리를 반복하는지가 설명의 중심입니다.

| 단계 | 입력 또는 처리 | 설명할 결과 |
| --- | --- | --- |
| 사람·장치의 입력 | 원음, 들린 문장, 문항 조건, 도움 내용, 녹음 구간·상대 순서 | 무엇을 실제로 확인했고 무엇이 불명인지 출처와 함께 저장 |
| 컴퓨터의 자격 계산 | 목적·능력·수행을 정하고 관련 불명·시점·도움 조건 및 후보별 결과를 비교 | 반영·보류·제외의 상태와 이유 계산 |
| 컴퓨터의 관측 선택 | 보류 이유에 연결되는 후보인지, 목표 수행에 쓸 자격이 있는지 검사 | 현재 정해진 후보와 비용 가정 안에서 확인 행동 추천 |
| 실제 사건 뒤 갱신 | 새 확인·도움·응답을 기존 사건에 귀속하고 영향받는 입력을 재검사 | 해당 결과의 유지·철회·정정과 앞뒤 판본 저장 |

예를 들어 늦게 온 도움 기록은 녹음 시각보다 앞에 있었다는 사실을 담습니다. 컴퓨터는 그 도움의 능력 범위와 발화 구간을 비교해 해당 수행 칸을 다시 판단합니다. 정확한 전사 자료에 그 도움 조건이 필요하지 않으면 해당 자격은 유지합니다. 이것을 단순히 ‘AI가 다시 검토한다’라고 줄이면 처리 원리가 사라집니다.

1. **입력 사전** — 각 필드의 뜻·출처·허용값과 원음·사건 ID의 관계를 적습니다.
2. **조건과 예외** — 원음 없음, 후보 불명, 시점 미확인, 녹음 중 도움, 미지원 표현이 어떤 보류로 이어지는지 적습니다.
3. **완전한 실시예** — 정정 전 입력과 결과, 추가 사건, 정정 후 결과를 같은 사례로 이어 다른 기술자가 재현하게 합니다.

**순서도만으로 충분하다고 보지 않습니다**

코드 경로나 기능 상자만 나열하지 않고 각 단계의 순서와 조건을 풉니다. [특허법 제42조](https://law.go.kr/LSW/lsSideInfoP.do?docCls=jo&joBrNo=00&joNo=0042&lsiSeq=279827&urlMode=lsScJoRltInfoR)와 [AI 가이드 1201~1205쪽](https://kipo.go.kr/ko/kpoContFileDown.do?seq=5&fileNum=1)을 기준으로 설명의 재현 범위를 검토합니다.

## 28. 특허·AI·효과에 관한 세 질문

답변은 기술의 가치를 설명하면서도, 현재 확인한 결과의 범위를 유지해야 합니다.

**Q. 이미 있는 기능을 연결한 것 아닌가요?**

그 반론을 검토해야 합니다. 불완전한 정보 처리, 확인 질문, 도움 전후 평가, 의존성 갱신은 기존 기술과 겹칩니다. 비교할 대상은 목적·시점별 자격이 관측 선택을 바꾸고 실제 관측이 다시 자격을 바꾸는 연결입니다. 기존 구성에서 무엇을 바꿔야 이 연결이 되는지, 그 변경이 쉽게 도출되는지 확인하겠습니다.

**Q. 새 AI 모델을 만들지 않아도 되나요?**

새 모델 자체가 이번 주력은 아닙니다. 기존 음성 인식 결과와 실제 도움·응답 사건을 받아 사용 자격을 계산하는 처리를 검토합니다. 공식 가이드도 학습 결과 데이터의 구체적인 활용을 다룹니다. 다만 모델 이름만 바꾸거나 ‘AI가 판단한다’고 쓰는 것으로 기술 차이가 생기지는 않습니다.

**Q. 시험이 많이 통과했으니 특허성이 증명됐나요?**

86개 시험은 코드 계약을, 1,280개 사건 전환은 계산 방식 간 결과 일치를 확인한 것입니다. 기존 기술보다 쉽게 만들 수 없는 구성이라는 판단은 별도입니다. 실제 학생의 학습 효과나 자연 발화 정확도를 시험 개수로 바꿔 말할 수도 없습니다.

계산 비교에서는 효과 함수 실행이 488회에서 12회로 줄었지만, 전체 실행 중앙값은 29.067ms에서 26.760ms였습니다. 이를 전체 처리의 수십 배 가속이라고 말하면 안 됩니다. 입력 지문 비교와 관측 계획 등 다른 작업은 계속 수행되며, 현재 PC의 통제 사건열 측정입니다.

‘더 빠르다·오류를 줄인다’는 일반적인 효과만으로 끝내지 않고, 어떤 기술 차이가 어떤 잘못된 반영과 유효 자료 손실을 바꿨는지 연결해야 합니다. 근거: [AI 가이드 1311~1312·1320~1321쪽](https://kipo.go.kr/ko/kpoContFileDown.do?seq=5&fileNum=1).

## 29. 미팅이 끝나면 무엇이 정해져야 할까요?

‘가능성이 있어 보인다’는 인상평보다, 보호할 구성·설명의 위치·남은 비교가 구체적으로 정해지는 것이 유용합니다.

시작 문안: “같은 원음의 사용 자격을 목적과 수행 시점별로 계산하고, 보류 이유에 맞게 확인 행동을 고른 뒤 실제 도움과 응답으로 자격을 갱신하는 연결을 보호하고 싶습니다. 가장 가까운 선행과 대조해, 독립항에 남길 필수 관계와 이를 뒷받침할 실시예를 검토해 주세요.”

| 논의 | 담당 변리사와 정할 내용 | 가져갈 자료 |
| --- | --- | --- |
| 보호 범위 | 독립항의 필수 연결과 종속항으로 둘 세부 처리 | 처리 흐름·입력 필드·조건 표 |
| 선행 대조 | 같은 구성, 남는 차이, 결합이 쉬운지 검토할 근거 | 문헌의 해당 구성과 비교표 |
| 설명의 뒷받침 | 필요한 실시예·도면과 일반화할 수 있는 범위 | 정정 전후 결과·저장 사건·재현 자료 |
| 출원 주체 | 발명자 기재와 개인·회사 출원 관계 | 단독 설계 진술과 구체 기술 구성별 기여 설명 |

**단독 설계 진술을 구체적인 설명으로 잇습니다**

사용자는 ‘나 혼자했어’라고 확인했습니다. 목적별 자격, 수행 시점, 관측 선택·재판정 중 어떤 관계를 직접 설계·판단했는지 설명합니다. 도구가 작성한 코드나 조사와 사람의 기술적 판단을 구분하며, 확인하지 않은 기여 내용을 대신 만들어 넣지 않습니다.

발명자와 출원인은 항상 같은 지위를 뜻하지 않습니다. [특허법 제33조](https://law.go.kr/LSW/lsSideInfoP.do?docCls=jo&joBrNo=00&joNo=0033&lsiSeq=279827&urlMode=lsScJoRltInfoR)의 발명자·승계인 관계에 맞춰 기재합니다. 회사 대표라는 사실만으로 회사의 권리 취득이 확인되는 것은 아닙니다.

끝날 때는 후보 청구항, 각 구성의 설명 위치, 추가 비교가 필요한 효과, 다음 작성 담당을 짧게 남깁니다. 예제 실행과 법률 검토의 결과를 한 가지 ‘완료’로 묶지 않습니다.

핵심은 구체적 처리를 청구하고, 이해 가능한 범위로 설명하며, 선행과의 차이와 도출의 어려움을 각각 검토한다는 것입니다. 사이트의 2020·2021년 AI 요약표만으로 최신 전문을 대신하지 않았습니다. 가이드의 판 날짜를 법률 시행일로 바꿔 적지 않았습니다.

## 31. 기능을 더하기 전에 비교를 더 단단하게 만듭니다

현재 자료에서 가장 필요한 다음 작업은 새로운 기능의 개수보다, 핵심 연결과 효과를 다른 사람이 검토할 수 있게 만드는 일입니다.

| 순서 | 준비할 증거 | 확인할 질문 |
| --- | --- | --- |
| 1 · 기존 자료 정리 | 한 사례의 원음·문항·전사·도움·시점·판정 전후를 연결 | 이 입력 때문에 어떤 칸이 왜 바뀌었는가? |
| 2 · 현실적인 공통 후보 | 재청취·문맥 확인·중립 확인·도움 뒤 새 응답 등 같은 후보 제공 | 목적·시점 연결이 실제로 선택을 달리하는가? |
| 3 · 독립적인 정답 조건 | 정책 출력과 별도로 원음·실제 도움·발생 순서에서 기준 작성 | 잘못 반영한 칸과 유효 근거를 잃은 칸이 각각 얼마인가? |
| 4 · 주장 범위 확장 검토 | 다른 문항·표현·도움 범위·시점 불명·늦은 정정 사례 | 어디까지 같은 처리로 설명하고 재현할 수 있는가? |
| 5 · 실제 사용 검증 | 준비된 실제 음성과 교사 판단, 질문·청취의 실제 소요시간 | 통제 사례를 넘어 효과와 비용이 어떻게 달라지는가? |

현재 비교의 ‘관계없는 선호 질문’은 원리를 설명하기 쉽지만 약한 비교 상대입니다. 모든 정책에 실제로 쓸 만한 같은 후보와 같은 비용을 제공한 뒤, 목적과 시점의 연결을 바꾸어 비교해야 합니다. 중립 질문도 답을 암시할 수 있으므로 실제 제시 문안의 도움 범위를 확인합니다.

**한 지표만 좋게 만들지 않습니다**

모든 칸을 보류하면 잘못된 반영은 줄어도 유효 자료가 사라집니다. 잘못된 반영, 유효 자료 보존, 실제 보류 해소, 관측 비용, 정정의 영향 범위를 함께 봅니다. 정답 기준을 엔진의 출력에서 거꾸로 만들지 않습니다.

저장·재현 시험은 기록 처리의 증거로 이미 사용할 수 있습니다. 실제 학생의 학습 효과와 자연 발화 정확도는 별도 자료가 필요합니다. 이런 검증이 모두 끝나야만 미팅할 수 있다는 뜻은 아닙니다. 지금 가진 증거와 준비할 비교를 함께 보여 주고, 주장에 꼭 필요한 실시예부터 담당 변리사와 정합니다.
