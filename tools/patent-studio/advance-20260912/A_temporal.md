# A — 도움 발생 시각의 가능범위와 증거 자격을 연결하는 보수적 확장

2026-09-12 · 담당 범위: `temporal-evidence.cjs`, `temporal-evidence.test.cjs`.

**이번 확장은 SYNK Core의 판단에 쓸 시간 근거를 강화한다.** “도움 기록이 나중에 서버에 도착했다”는 이유만으로 학생이 도움 없이 답했다고 판단하지 않는다. 도움을 실제로 보았을 수 있는 시간 범위를 원래 녹음 구간과 비교하고, 순서가 확실하지 않으면 그 순서에 의존하는 수행 기록을 보류할 수 있게 한다. LOOM의 표현 계층이나 SYNK Atlas 전체를 이 단일 모듈로 부르지 않는다.

## 1. 사람이 이해하는 한 장면

원래 녹음은 **10초부터 20초까지**다. 도움을 보여 준 기기의 기록에는 오차가 있어 **9초부터 21초 사이**에 답이 노출됐다고만 안다. 서버에는 99초에 도착했다.

| 입력 근거 | 판단 | 원래 수행에 적용할 의미 |
|---|---|---|
| 도움 9–21초, 녹음 10–20초 | 순서 미확인 | 99초 도착을 이유로 “녹음 뒤 도움”이라고 승인하지 않는다. |
| 같은 도움을 확인한 추가 근거가 9–9.5초로 범위를 좁힘 | 확실히 녹음 전 | 이 도움에 영향받는 항목은 독립 수행의 근거에서 제외한다. |
| 추가 근거가 12–18초로 범위를 좁힘 | 확실히 녹음 도중 | 전체 녹음을 도움 전·후 중 하나로 단정하지 않는다. |
| 추가 근거가 20.5–21초로 범위를 좁힘 | 확실히 녹음 뒤 | 이 도움 때문에 생긴 시간 보류를 해소할 수 있다. 다른 보류 원인이 남으면 계속 보류한다. |

위 세 가지 추가 근거는 **가능한 서로 다른 시연 분기**다. 시스템이 유리한 분기를 실제 관측으로 선택하거나, 위 시간값을 자동으로 측정했다는 뜻이 아니다.

전사 문장이 정확한지를 판단하는 목적에는 원래 수행의 독립성 조건을 그대로 적용하지 않는다. 음성을 다시 듣고 문장을 확인할 수 있으면 전사 자료의 자격은 따로 평가한다. 새 답을 말하게 한 경우에는 새 수행 시점에 연결하고, 원래 수행의 답을 고쳐 쓰지 않는다.

## 2. 실제 데이터 계약

```json
{
  "id": "help-1",
  "at": "2026-09-12T00:01:39.000Z",
  "timeBounds": {
    "earliestAt": "2026-09-12T00:00:09.000Z",
    "latestAt": "2026-09-12T00:00:21.000Z",
    "basis": "clock-calibration",
    "sourceRef": "synthetic/clock-calibration-1"
  }
}
```

| 필드 | 뜻과 책임 |
|---|---|
| `at` | 기존 도움 이벤트가 제공하는 시각. 가능범위가 있으면 분류 계산에 대체 사용하지 않는다. 서버 수신 시각의 별도 보존은 저장 계층 책임이다. |
| `earliestAt`, `latestAt` | 입력자가 근거에 따라 선언한 가장 이른·가장 늦은 도움 발생 가능시각. 밀리초까지, 시간대가 있는 ISO 형식이어야 한다. |
| `basis` | `declared-bound`, `clock-calibration`, `transport-bound`, `human-review` 중 하나. 어느 종류의 자료를 토대로 입력했는지를 나타낸다. |
| `sourceRef` | 근거 자료를 찾을 수 있게 하는 비어 있지 않은 식별자. 식별자의 진실성이나 외부 문서의 신뢰성을 이 모듈이 인증하지는 않는다. |
| `performanceInterval.startedAt`, `.endedAt` | 비교 대상 원래 음성의 고정 녹음 구간. 업로드 시각으로 만들지 않는다. 구간의 확인 여부는 Core가 먼저 검사한다. |

명시된 가능범위가 잘못됐으면 `help.at`로 몰래 되돌아가지 않고 `unknown`을 반환한다. 기존 기록처럼 가능범위가 아예 없는 경우에만 기존 `help.at` 한 점을 비교한다. 한 점 비교의 출처는 `event-timestamp`로 구분한다.

녹음 구간 자체의 양 끝점에도 불확실성이 있는 일반화 모델은 이번 모듈에 포함하지 않았다. 이 모듈의 확실한 순서 판단은 **제공된 도움 가능범위와 확인된 고정 녹음 구간이 맞다는 조건 아래의 결과**다.

## 3. 핵심 알고리즘

도움 가능범위를 `[h_min, h_max]`, 녹음 구간을 `[s, e]`라고 한다.

1. `h_max < s`이면 모든 가능한 도움 시각이 녹음 전에 있으므로 `before`.
2. `h_min > e`이면 모든 가능한 도움 시각이 녹음 뒤에 있으므로 `after`.
3. `s ≤ h_min`이고 `h_max ≤ e`이면 모든 가능한 도움 시각이 녹음 도중에 있으므로 `overlap`.
4. 이외에는 가능한 시각별 순서가 달라질 수 있으므로 `unknown`.

녹음 시작·끝과 도움 시각이 같으면 독립 수행을 승인하는 쪽으로 해석하지 않고 `overlap`에 포함한다. 도움 가능범위가 녹음 구간에 조금이라도 닿았다는 이유만으로 반드시 도중 노출이었다고 확정하지도 않는다. **도중 노출 가능**과 **모든 가능시각에서 도중 노출**을 구별한다.

반환값에는 판단 이름뿐 아니라 비교에 쓴 두 구간, 출처 표시, 세 가지 비교의 참·거짓과 밀리초 차이를 함께 넣는다. 화면과 근거 묶음에서 같은 판단을 설명할 수 있다.

## 4. 범위를 다시 확인할 때

`refineTimeBounds(previous, next)`는 새 범위가 이전 범위의 부분집합인 경우만 허용한다. 동일 범위도 허용하므로 모든 호출이 불확실성을 줄이는 것은 아니다. 새 자료가 기존 범위 밖을 가리키면 수정이라고 받아들이지 않고 오류로 반환한다.

이 함수는 이전 값을 삭제하지 않는다. 순수 함수이므로 이력 저장도 하지 않는다. Core·저장 계층에서는 이전 근거, 새 근거, 확인 이벤트를 남기고, 정밀화 전에 인정·보류·제외됐던 자격을 다시 계산해야 한다. 범위 밖 반대 근거를 별도 사건으로 수용하는 일반적인 분쟁 해결 흐름은 별도 구현·검증 대상이다.

**동일한 범위를 더 정밀하게 확인하는 행위**와 **학생에게 답을 보여 주고 새 답을 받는 행위**는 다르다. 전자는 기존 도움 사건의 시간 근거를 다시 평가할 수 있다. 후자는 새 수행을 만든다. 이 차이를 관측 계획의 원래 시점 보존 조건과 결합하는 것이 전체 시스템의 검토 지점이다.

## 5. 도움 대상 코드가 잘못 들어온 경우

예전 입력에서 `skills: ["unmapped-skill"]` 같은 값을 받으면 실제 도움 기록이 어떤 수행 항목과도 관련 없는 것처럼 처리될 수 있었다. 이번 정규화는 다음을 구분한다.

| 입력 | 반환 |
|---|---|
| 생략 | 기존 계약을 유지해 `object`, `past`가 알려진 범위 |
| `object`, `past`, `all`로만 된 비어 있지 않은 배열 | 중복 제거·순서 정규화한 알려진 범위 |
| 미등록 코드, 섞인 코드, 빈 배열, 잘못된 자료형 | 원래 값을 보존하고 `status: unknown`, 관련 범위 `all` |

`unknown`의 `all`은 모든 항목에 도움이 실제로 영향을 줬다는 확정이 아니다. 영향 범위를 모르므로 어느 항목에서도 도움 사건을 조용히 버리지 않겠다는 뜻이다. 실제 자격 보류 여부는 시간 관계와 사용 목적을 함께 보고 결정해야 한다. Core는 정규화한 `skills`만 저장하지 말고 `status`, `rawSkills`, `reasonCode`, `basis`도 보존해야 한다.

## 6. 기존 시스템 연결과 책임

| 위치 | 연결 계약 | 확인 책임 |
|---|---|---|
| `core.cjs`의 도움 입력 처리 | 원래 scope 입력과 정규화 결과, 유효한 timeBounds를 함께 보존 | 미등록 코드가 조용히 빠지지 않는지 |
| `timingFor` | 기존 수행 시각 확인을 유지한 다음 실제 도움과 녹음 구간을 분류 | 도착 순서와 발생 순서를 혼동하지 않는지 |
| 목적별 자격 계산 | 독립 수행의 시간 조건과 정확한 전사의 조건을 나눔 | 같은 원음의 자격이 목적에 따라 다를 수 있는지 |
| 관측 계획 | 시간 확인과 새 답 유도 행위를 구별 | 원래 시점의 근거를 새 답으로 바꾸지 않는지 |
| 입력 지문·재계산 | 범위·출처·scope 상태를 판단 입력에 포함 | 정밀화 뒤 과거 캐시가 재사용되지 않는지 |
| 저장·재현 | 버전별 입력·출처·이벤트·계산 결과 보존 | 같은 입력을 같은 코드로 재현할 수 있는지 |

이 문서는 독립 모듈의 완료와 Core·저장·화면의 통합 완료를 구분한다. 통합 결과는 전체 작업의 검증 보고서에서 확인한다.

## 7. 검증 근거와 계산 규모

실행: `node --test tools/patent-studio/temporal-evidence.test.cjs`.

12개 시험을 통과했다. 사람이 정한 경계 사례, 시간대 정규화·달력 오류, 입력 순서 독립성, 업로드 시각 대체 금지, 원본 입력 보존, 범위 확대 거절, 미등록 scope를 포함한다.

별도 정답 검증은 7–23초 범위의 가능한 정수 시각을 하나씩 열거한다. 끝점 비교식을 정답 생성에 다시 쓰지 않고, 각 가능한 시각의 분류가 전부 같은지 확인하여 총 153개 가능범위를 대조했다. 추가로 이미 확정한 시간 관계가 그 안의 범위 정밀화 후에도 유지되는지 1,031개 부분범위 조합을 확인했다. 이는 합성 입력에 대한 논리 검증이며 학생 효과 실험이 아니다.

도움 한 건과 발화 한 건의 비교는 일정한 수의 시간 변환·비교를 한다. 도움 `H`건과 발화 `U`건의 모든 조합을 다시 보면 비교 횟수는 `H × U`에 비례한다. 이 모듈 자체는 전체 시스템의 시간·메모리 상한이나 색인 효율을 바꾸지 않는다. `sourceRef`나 scope 배열 길이 같은 실제 입력 크기도 존재한다. 전체 계산이 변경 항목 수에만 비례한다고 주장하지 않는다.

## 8. 변리사에게 검토할 구체적 한정 후보

다음은 발명 명세를 논의하기 위한 구성안이며 신규성·진보성이 확인된 청구항이 아니다.

> 동일 음성 기록에 대해 사용 목적별 증거 자격을 관리하는 컴퓨터가, 원래 수행의 녹음 구간 및 도움 사건의 발생 가능시각 범위와 그 입력 출처를 취득하고, 가능한 발생시각 전체에서의 선후 관계가 일치하는지에 따라 관련 수행 자격을 승인·보류·제외하며, 같은 도움 사건에 대한 범위 내 정밀화가 추가되면 원래 음성 및 수행 시점을 유지하여 해당 자격을 재평가하고, 다른 목적에 대한 독립적인 자격은 별도로 유지하며, 새 수행을 생성하는 관측을 원래 수행의 증거로 소급하지 않는 처리.

범위 관리·시간 비교·이력 자체를 독창성의 근거로 삼지 않는다. Google의 Spanner도 시간과 사건 순서, 버전별 읽기의 일관성을 이미 다룬다. 이번 검토에서는 위 기능들을 **원래 수행·새 수행·전사 자료의 서로 다른 증거 자격 및 원래 근거를 보존하는 관측 선택에 어떤 구체적 데이터·처리 관계로 연결했는지**를 한정해 기존 문헌과 대조해야 한다. [Google 공식 설명](https://docs.cloud.google.com/spanner/docs/true-time-external-consistency)

등록 가능성이 올라갔다고 수치화하지 않는다. 이번 구현의 확인 가능한 성과는 모호한 시각·잘못된 영향 범위가 들어왔을 때의 동작을 더 구체적으로 설명하고, 경계 사례를 재현하고, 출원 문서에 담을 수 있는 처리 구조와 제한을 분명히 했다는 것이다.
