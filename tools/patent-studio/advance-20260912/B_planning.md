# B — 원래 수행을 보존하는 다중 보류 관측 계획

작성 기준: 2026-09-12. 구현 파일은 `tools/patent-studio/observation-planner.cjs`, 독립 검증은 `observation-planner.test.cjs`다. 이 문서는 구현된 처리 방식과 특허 상담에서 검토할 결합 후보를 구분한다. 등록 가능성의 수치나 확정 판단을 제시하지 않는다.

## 1. 쉽게 설명하면

원래 녹음에 “소리가 불명확함”과 “도움을 먼저 받았는지 모름”이 동시에 남아 있으면, 녹음을 한 번 잘 듣는 것만으로 원래 독립 수행이라고 판정할 수 없다. 남은 문제도 함께 확인해야 한다.

이번 모듈은 목표마다 남은 보류 조건을 모아, 어떤 확인을 어떤 순서로 하면 목표의 보류 조건을 모두 해소할 수 있는지 계산한다. 답을 보여 준 뒤 다시 말하게 하는 행동은 새 수행을 얻는 방법이므로 원래 수행의 보류 조건을 해결했다고 세지 않는다. 계산한 계획은 실제 관측 기록을 바꾸지 않는다. 첫 확인을 실제로 하고, 나온 결과로 엔진이 다시 판정한 뒤 다음 계획을 계산한다.

“확인했다”와 “독립 수행을 뒷받침하는 결과가 나왔다”도 다르다. 시간 기록을 확인한 결과 도움이 먼저였다고 밝혀지면 원래 독립 수행의 근거로는 제외될 수 있다. 화면의 조건부 계획은 **보류 조건을 해소하는 뒷받침 결과가 나온다는 가정**이다. 확인 버튼 자체가 반영 자격을 주지 않는다.

## 2. 이번에 실제 구현한 범위

| 구성 | 책임 | 출력과 제한 |
|---|---|---|
| 목표 수집자의 입력 | 원래 수행·새 수행·음성 학습 자료의 목표와 모든 보류 조건을 제공 | 어느 발화의 어느 조건인지 식별해야 한다. 이 파일 밖의 엔진이 담당한다. |
| 행동 적격성 계산 | 답 노출·새 수행 생성·원래 수행 부적격 행동의 원래 목표 기여 차단 | 해당 행동을 선행 조건으로 요구하는 후속 행동에도 원래 목표 부적격을 전파한다. |
| 의존 관계 검사 | 선행 행동 필요 여부와 수행 가능성을 검사 | 순환·누락·사용 불가 선행 행동을 거절한다. |
| 제한된 부분집합 탐색 | 주어진 행동·예산·깊이 안에서 적격 계획을 비교 | 전체 보류가 조건부 해소되는 목표 수 → 해소 조건 수 → 낮은 비용 → 적은 행동 수 순서다. |
| 조건부 순서 출력 | 선택한 행동을 선행 조건 순서로 정렬 | 실제 결과별 분기 정책이 아니라, 뒷받침 결과를 가정한 순서다. |
| 재계획 계약 | 첫 행동을 관측한 뒤 실제 결과로 다시 판정하도록 표시 | `execute-one-observe-replan`; 이 모듈에는 실제 근거 저장·승격 함수가 없다. |
| 계산 상한 표시 | 탐색 중단과 입력 초과를 명시 | 계산을 다 못 했으면 최적이라고 인증하지 않는다. |

기존 `core.cjs`·API·화면 연결과 실제 기록 재생은 통합 담당의 검증 결과를 함께 봐야 한다. 이 독립 모듈의 시험 통과만으로 제품 배포나 학생 사용이 확인되는 것은 아니다.

## 3. 데이터 계약

```js
planEvidencePreserving({
  targets: [{
    id: 'e0:object', epoch: 'e0', purpose: 'original-performance',
    blockers: [
      { id: 'original:transcript-review', code: 'transcript-not-reviewed' },
      { id: 'original:help-time', code: 'help-time-order-unknown' }
    ]
  }],
  actions: [{
    id: 'review-original', title: '원래 녹음 확인', costUnits: 3,
    resolves: ['original:transcript-review'],
    requires: [], available: true,
    exposesAnswer: false, createsEpoch: false, eligibleForOriginal: true
  }, {
    id: 'inspect-original-help-time', title: '도움의 발생 시점 확인', costUnits: 2,
    resolves: ['original:help-time'],
    requires: [], available: true,
    exposesAnswer: false, createsEpoch: false, eligibleForOriginal: true
  }],
  budget: 5, maxDepth: 8, maxStates: 50000
});
```

- `purpose`는 `original-performance`, `response-performance`, `asr-data`만 허용한다. 목적 오타로 원래 수행 보호가 빠지면 안 된다.
- `blocker.id`는 전역 식별자다. 서로 다른 발화의 전사 검토에는 `original:transcript-review`, `response-1:transcript-review`처럼 다른 값을 쓴다. 같은 값을 여러 목표에 쓰면 **의도적으로 공동 해결되는 동일 조건**이라는 뜻이다.
- `action.resolves`는 실제 해결 이력이 아니라, 뒷받침 결과가 나올 경우 해결할 수 있는 조건의 선언이다. 현재 근거를 원천 기록에 적용하는 것은 별도 엔진의 책임이다.
- `costUnits`는 실제 초·원·성공률이 아닌 가산 가능한 설계 비용 단위다. 음수가 아닌 유한 수만 허용한다. 비용 합계와 실제 작업 시간은 구분한다.
- `eligibleForOriginal`를 생략하면 모듈 계약상 기본값은 참이다. 실제 엔진의 후보 생성기는 세 위험 플래그를 명시해야 하며, 이 기본값을 독립적인 근거 보존 인증으로 표현하지 않는다.
- 행동 또는 목표의 중복 id는 거절한다. 보류 조건 중복은 같은 조건으로 합친다.
- `requires`는 같은 입력의 행동 id를 가리킨다. 이미 외부에서 끝난 작업을 자동 추정하지 않는다.

## 4. 출력의 의미

| 필드 | 정확한 뜻 |
|---|---|
| `selectedActionIds` | 선택 집합의 안정적인 id 순서. 실행 순서는 `steps`다. |
| `nextActionId` | 선행 조건상 먼저 할 수 있는 첫 행동. 실제 관측은 하나씩 수행한다. |
| `steps` | 각 행동의 선행 조건, 선언 비용, 조건부 해소 대상, 실제 관측 필요 여부 |
| `unresolved` | 선택 계획의 뒷받침 결과를 모두 가정해도 남는 조건 |
| `projectedQualification.hypothetical` / `observed` | 항상 `true` / `false`; 실제 반영 기록이 아니다. |
| `assumption` | `all-declared-blockers-cleared-by-supporting-observations` |
| `requiresSupportingOutcomes` / `inspectionAloneIsInsufficient` | 둘 다 참. 확인 수행만으로 반영 자격이 생기지 않는다. |
| `inputFullyEvaluated` | 입력의 목표·조건 전체를 평가했는지. 모든 목표가 해결되었다는 뜻이 아니다. |
| `allTargetsConditionallyQualified` | 뒷받침 결과를 가정하면 모든 목표의 보류 조건이 없어지는지 |
| `score.fullyQualifiedTargets` | 해당 가정 아래 모든 보류 조건이 해소되는 목표 수. 실제 승인·학습 성과 수치가 아니다. |
| `score.coveredBlockers` | 목표/보류 조건 쌍의 조건부 해소 수. 공동 조건은 각 목표 기여를 센다. |
| `optimalWithinBounds` | 주어진 후보·예산·최대 단계 수 안의 탐색을 끝낸 경우에만 참 |
| `truncationReason` | 상태 수 상한 또는 입력 상한 때문에 계산을 마치지 못한 사유 |
| `actualEvidenceChanged` | 항상 거짓. 계획을 실제 관측으로 바꾸는 코드가 없다. |

## 5. 핵심 알고리즘

1. 목적·발화·보류 조건을 가진 목표를 정규화하고, 목표/조건 쌍에 비트를 부여한다.
2. 후보 행동의 의존 관계를 검사한다. 답 공개나 새 수행 생성 행동 및 그 선행 조건을 거치는 행동은 원래 수행의 보류 조건을 해소하는 데 쓰지 않는다.
3. 적격한 조건 해소 행동과 그 선행 행동을 후보 집합으로 만든다.
4. 빈 계획에서 시작해, 선행 조건을 만족하고 예산·깊이 안에 들어오는 행동을 더한다. 같은 행동 집합은 한 번만 탐색한다.
5. 각 집합을 완전히 조건부 해소되는 목표 수, 해소 조건 수, 선언 비용, 행동 수, 안정적 id 순으로 비교한다.
6. 최선의 **발견된 적격 집합**을 선행 관계에 맞춰 순서화한다. 계산 상한에 걸리면 결과의 비최적 가능성을 명시한다.
7. 원천 자료는 그대로 두고 조건부 계획만 반환한다. 실제 관측 결과가 뒷받침·반대·무응답 중 무엇인지 확인하는 작업은 호출 엔진이 수행한다.

이 구현은 성공 확률을 추정하거나 관측 결과별 최적 분기 정책을 학습하지 않는다. 결과별 확률을 요구하는 계획 문제와 혼동하지 않는다.

## 6. 직접 보여 줄 수 있는 차이

보류 목표 A에는 조건 두 개, 목표 B에는 조건 네 개가 있고 예산은 2라고 가정한다. 행동 X는 비용 2로 B의 조건 세 개만 해소할 수 있다. 행동 Y·Z는 각각 비용 1로 A의 조건을 하나씩 해소할 수 있다.

조건 개수 대비 비용만 보면 X가 좋아 보이지만 B에는 조건 하나가 남는다. 이번 계획은 Y·Z를 선택한다. A 하나의 모든 보류 조건이 해소될 가능성이 생기기 때문이다. 이것은 특정 선언 비용·조건 아래의 합성 예이며 실제 학생에게 더 효과적이라는 측정은 아니다.

두 번째 실연에서는 답을 보여 주고 새로 말하기를 비용 0으로 넣어도 원래 수행 목표에는 선택되지 않는다. 같은 행동이 새 수행 목표에는 조건부 후보가 될 수 있다. 화면에서는 원래 `e0`와 새 `e1`의 귀속이 달라지는 이유를 보여 준다.

세 번째 실연에서는 계획을 먼저 보여 준 뒤 실제 관측을 “도움이 먼저였음”으로 입력한다. 계획의 좋은 가정과 달리 원래 수행이 제외되는 것이 정상이다. 계획만 보여 준 단계에서는 원래 근거 상태가 바뀌지 않아야 한다.

## 7. 계산 규모와 검증

현재 상한은 행동 24개, 목표 64개, 목표/조건 쌍 256개다. 기본 최대 단계는 8, 기본 탐색 상태 상한은 50,000이며 요청 가능한 상태 상한은 100,000이다. 조합 탐색이므로 일반 경우 지수적으로 커질 수 있다. 제한이 없는 대규모 최적화를 주장하지 않는다.

후보 수를 `n`, 목표 수를 `t`, 목표/조건 쌍을 `b`, 실제 생성한 상태 수를 `S`라 할 때 현재 구현의 보수적인 처리량 설명은 `O(S × n × (t + b + n))`이다. 마지막 n은 동점일 때 선택 식별자 목록을 비교하는 비용까지 포함한다. 탐색 저장량은 `O(S × b)` 비트 수준의 상태 저장에 입력·출력 비용이 더해지는 형태다. 고정된 비트 상한 때문에 실제 상수는 작지만, 이는 선형 시간 전체 시스템이라는 주장이 아니다.

2026-09-12 로컬 Node 실행의 한 예에서, 행동 16개·목표 4개·각 목표 조건 4개·예산 8·최대 단계 8은 39,203개 상태를 탐색했고 약 44.3ms였다. 단일 실행 관찰이며 성능 보장·반복 평균·제품 규모 측정은 아니다. 두 목표의 조건 8개를 비용 8로 해소하는 조건부 집합이 선택됐고 주어진 범위 안의 탐색을 완료했다.

검증 명령은 `node --test tools/patent-studio/observation-planner.test.cjs`이며 17/17 통과했다. 내부 구현의 도달 가능 상태 탐색·비트 집합과 별개로, 모든 작은 부분집합을 먼저 나열한 뒤 문자열 집합으로 판정하는 독립 oracle을 만들어 80개 입력에서 점수와 선택 집합을 대조했다.

확인 항목은 다중 보류 결합, 단순 탐욕 선택의 실패 예, 공동 조건 해소, 원래/새 수행 분리, 위험한 선행 조건 전파, 순환·누락 의존 관계, 무응답 후 재계획, 반대 관측 비승격, 입력 불변, 입력 순열 불변, 예산·깊이·상태 상한, 불가능·빈 입력, 잘못된 목적·비용·식별자 거절이다.

## 8. 선행 기술과 상담용 청구 요소

가정과 의존 관계를 유지하며 여러 해를 다루는 방법 자체는 ATMS 계열의 기존 기술이다. 따라서 보류 조건·가정 집합을 썼다는 이유만으로 새로운 발명이라고 주장하지 않는다. [de Kleer, An assumption-based TMS, 1986](https://www.sciencedirect.com/science/article/pii/0004370286900809)

부분적으로만 아는 상태에서 정보를 얻는 행동과 일반 행동을 계획하는 연구도 오래 존재한다. 이번 구현은 그러한 일반 계획 이론을 새로 만들었다는 주장이 아니며, 관측 결과별 확률 모델과 최적 정책을 계산하는 POMDP 구현도 아니다. [Kaelbling·Littman·Cassandra, 저자 제공 1998 논문](https://www.cassandra.org/arc/papers/aij98.pdf)

상담에서 검토할 좁은 결합 후보는 다음과 같다. **원래 수행 구간·도움의 발생 범위·사용 목적에 따라 나뉜 보류 조건을 생성하고, 관측 행동이 답을 공개하거나 새 수행을 만드는지와 선행 행동의 영향을 함께 적용해 원래 수행의 조건 해소 후보를 제한하며, 제한된 후보로 다중 보류의 조건부 해소 계획을 계산하고 실제 관측 결과를 받은 뒤 원래 수행·새 수행의 귀속을 유지하며 재판정하는 처리**다.

이 문장의 구성 중 다중 보류 수집, 시간 범위 판정, 실제 이벤트 적용과 귀속은 통합 엔진에 속한다. 이 모듈 단독의 구현 범위는 적격성 전파·유한 탐색·조건부 계획 출력이다. 결합 전체의 신규성·진보성은 가까운 특허의 청구항과 명세서, 통상의 결합 가능성을 비교해 판단해야 하며 여기서 확인됐다고 쓰지 않는다.

변리사에게는 “계획 알고리즘을 넓게 독점하고 싶다”보다 “원래 근거를 훼손하거나 새 수행을 과거 증명으로 잘못 쓰는 상황에서 이 특정 데이터 계약과 처리 순서를 좁게 청구할 근거가 있는지”를 요청하는 편이 이번 목표와 맞는다.
