# 앱 안에서 수집한 도움 범위의 확인 — 최소 연결안

2026-09-13 · 한정 코드 검토·설계 · 실앱 변경·새 시험 없음

**현재 `exposureScopeConfirmed`는 사람이 보낸 확인값이다. 단조 순번과 수신 빈칸 검사로 조건부 산출할 수 있는 것은 ‘명시한 앱 생산자 범위에서 특정 녹음까지의 기록이 모두 도착했다’는 사실이다. ‘도움이 없었다’, ‘학생이 실제로 보았다’, ‘앱 밖에서도 독립적이었다’는 결론은 아니다.**

구현상 불가능한 구조는 아니다. 기존 전체 사건 저장·멱등성·원음 첨부 사건을 재사용할 수 있다. 다만 **현재 도움 모달과 녹음에 순번만 추가하여 기존 확인값을 곧바로 true로 바꾸는 것은 불충분**하다. 표시 전 기록, 범위의 시작/끝, 다른 탭, 다른 답 표시 경로, 전체 재생 계약을 함께 정해야 한다. 이 연결의 개발이나 명확화가 특허 진보성을 개선한다는 주장은 하지 않는다.

## 2. 먼저 해결해야 할 세 가지 범위 문제

1. **모달 밖에도 답이 보인다.** `renderSession`의 최근 도움(`public/app.js:202~203`), 타임라인, 전사/응답 표시, 예제 자료도 단서가 될 수 있다. `presentHelp`만 기록하면 이 화면 전체의 답 제시를 포괄하지 않는다. 측정 대상 화면·표시 종류·대상을 명시한 정책 판본을 정하고, 그 대상에 들어가는 표시 경로가 실제로 사건을 생산해야 한다. 들어가지 않는 경로까지 “앱 전체 관측 완료”로 표시하지 않는다.
2. **새 탭은 새로운 생산자다.** 같은 서버 세션을 열었다고 같은 브라우저 순번을 공유하지 않는다. 탭마다 서로 다른 `producerEpoch`를 사용한다. 서버 revision 충돌이나 BroadcastChannel 알림만으로 다른 탭의 실제 표시가 없었다고 입증할 수 없다.
3. **연속된 숫자만으로 숨은 끝부분을 찾을 수 없다.** 시작 기준과 제출에 결속된 끝 순번이 있어야 한다. 표시 뒤에 순번을 발급하면 표시 직후 프로세스 종료가 기록 전체에서 사라질 수 있다. 표시 전 지속 기록과 미완료 표시의 보류가 필요하다.

첫 적용 범위는 **정해진 정책을 실행하는 하나의 협조적인 UI 생산자와 그 녹음 시도**로 한정하는 편이 작다. 이 범위만 수집했다면 출력도 그 범위만 표현한다. 같은 학생이 다른 탭을 함께 쓸 수 있는데 기존 Core 판단이 그 탭까지 포함한 도움 범위를 요구한다면, 단일 탭의 연속성만으로 기존 boolean을 true로 만들 수 없다. 등록된 생산자 집합 전체의 수집 끝을 확인하거나 미확인으로 남겨야 한다. 이는 새 중앙 큐를 요구하는 주장이 아니라 확인 범위를 정하는 조건이다.

## 3. 최소 데이터 필드 10개

기존 `sessionId`, 사건 `id/type/at`, 도움 `text/skills`, 오디오 `audioRef`, 원음 첨부 사건 ID와 `responseId`는 재사용한다. 다음은 추가할 논리 필드다. 종류를 열거한 스키마 초안이며 현재 지원되는 API가 아니다.

| 필드 | 의미 |
|---|---|
| `scopeId` | 서버가 보관한 수집 범위의 시작 기준. 같은 서버 세션이라도 다른 수집 구간을 구분 |
| `scopePolicyId` | 어떤 UI·표시 종류·대상을 수집하는지 정의한 코드/정책 판본 |
| `producerEpoch` | 한 문서 실행 수명의 ID. 새 탭·새로고침·복구 후 새 실행을 기존 순번과 구별 |
| `producerSeq` | 해당 실행에서 증가하는 사건 순번. 서버 저장 순서와 분리 |
| `actionPhase` | 범위 시작, 표시 준비/DOM 확인/실패, 녹음 시작 요청/시작/종료 요청/종료/취소, 범위 종료 등 측정 단계 |
| `attemptId` | 특정 녹음 시도. 기존 첨부 사건 ID·응답 ID와 서버에서 연결 |
| `audience` | learner/reviewer/shared/unknown. UI가 선언한 대상이며 실물 사람의 신원 인증이 아님 |
| `localMonoMs` | 해당 producerEpoch 안의 단조 시간. 벽시계 변경과 별개이며 다른 탭/기기의 값과 직접 비교하지 않음 |
| `relatedEventId` | 표시 완료→표시 준비, 녹음 종료→시작, 범위 종료→해당 제출/첨부 사건의 연결 |
| `requiredThroughSeq` | 이 녹음 제출을 판단하기 전에 받아야 할 마지막 생산 순번. 제출 요청에 고정하며 재시도 때 임의로 줄이지 않음 |

각 번호에는 기존 사건 ID와 내용 지문이 연결되어야 한다. 같은 번호에 다른 사건을 넣으면 충돌이다. 도움의 본문·범위와 원음 바이트 참조는 기존 사건 필드를 사용하므로 중복된 별도 자료 저장소를 만들 필요가 없다. 서버의 연속 수신 끝·누락 번호·산출 사유는 이 입력으로 계산한 결과이며 클라이언트의 선언을 그대로 믿지 않는다.

## 4. 최소 생산 연결

### 도움 표시

`presentHelp` 및 정책에 포함된 다른 표시 경로에서 **번호 발급 + 표시 준비 사건의 로컬 지속 저장을 먼저 완료**한다. 그 뒤 DOM을 변경한다. 이는 이 화면의 작은 IndexedDB 기록 버퍼 등으로 구현할 수 있고 회사 공용 중앙 큐·강제 훅으로 일반화하지 않는다.

두 animation frame, `dialog.open`, 해당 요소 상태, `document.visibilityState`처럼 실제 확인한 조건을 별도 완료 사건에 기록한다. 이것을 인간의 시각적 노출 또는 GPU 출력 인증이라고 부르지 않는다. 숨겨진 탭·DOM 오류·프로세스 중단·저장 실패 때문에 성공을 확인할 수 없으면 표시 준비가 미완료 상태로 남는다. 미완료를 “도움 없음”으로 삭제하지 않는다. 이번 최소안은 미완료 표시가 있으면 자동 범위 확인을 보류한다.

### 녹음과 제출

녹음 시도 ID를 먼저 만들고 시작 요청을 기록한다. `MediaRecorder.start()` 호출·`onstart`, 종료 요청·`onstop`, 오류·취소를 구별한다. 시작 전 기록 시각이나 `onstart` 콜백 한 점을 원음의 정확한 물리 시작 시각으로 간주하지 않는다. 요청과 관측 사이가 불분명하면 그 구간의 도움 순서를 보수적으로 처리한다.

최종 `onstop`과 Blob 확정 뒤 해당 시도의 끝 사건을 지속 저장한다. 이 끝 번호를 업로드의 `requiredThroughSeq`로 고정하고 같은 파일 첨부 사건 ID에 결속한다. 네트워크 때문에 도움 사건보다 원음이 먼저 도착해도, 원음 저장은 보존하고 수집 범위 확인만 보류한다. 이후 빠진 사건이 도착하면 같은 제출을 다시 검사한다. 수신 실패를 이유로 원음을 다시 녹음했거나 새 시도로 바꾸지 않는다.

취소·오류에도 예약된 번호를 없애지 않고 해당 종료 결과를 남긴다. 앱 재시작 때 순번이 기억나지 않으면 새 producerEpoch를 열고 이전 구간을 미완료로 유지한다. `beforeunload`만으로 기록 보존이 보장된다고 하지 않는다.

## 5. 서버 소비와 boolean 산출

범위 시작 시 서버가 보관한 시작 번호를 s, 제출이 요구하는 끝 번호를 e라고 한다. 다음이 모두 성립할 때만 **정의한 생산자 범위의 수집 완료**를 산출한다.

1. `scopeId`·정책·producerEpoch·audience·attemptId가 서버의 범위/제출 기록과 맞는다.
2. s부터 e까지 각 번호의 사건 본문이 모두 있으며 같은 번호/ID의 내용 충돌이 없다. e 이후의 최신 서버 revision이 존재한다는 이유로 중간 빈칸을 채웠다고 하지 않는다.
3. 표시 준비가 완료/명확한 실패로 종결되고, 해당 녹음이 실제 생성된 파일 첨부 사건과 연결되며 취소·다중 종료·불명확한 겹침이 없다. 명확한 표시 실패도 성공한 도움으로 세지 않되, 실제 표시 가능성을 배제할 수 없으면 미완료로 남긴다.
4. 정책이 요구하는 생산자 집합이 닫혀 있다. 다른 탭·새로고침·관측되지 않은 표시 경로가 같은 판단 범위에 들어오면 기존 범위 확인을 자동으로 확대하지 않는다.
5. 범위와 근거를 함께 보존한다. `exposureScopeConfirmed=true`만 남기지 않고 산출 근거가 앱 수집 연속성인지 수동 선언인지, 어느 범위인지 구별한다.

수집 완료여도 알려진 발화 전/중 도움은 그대로 판정에 사용한다. **기록이 완전하다 = 도움 없이 수행했다**가 아니다. 완료되지 않았을 때도 이미 받은 도움 사건을 지우지 않는다. Core의 다른 문항·시간·전사 조건도 자동으로 참으로 바꾸지 않는다.

현재 Core가 boolean을 사용하는 의미와 산출 범위가 맞는 경우에만 이 결과를 기존 필드에 연결한다. 의미가 더 좁으면 별도 `appScopeCoverage` 결과로 남기고 기존 확인값은 보류한다. 수동 체크박스는 `manual-assertion`이라는 출처로 분리하고, 직접 payload로 보낸 true가 서버 산출 근거를 위조하지 못하도록 경로를 구분해야 한다.

## 6. 상황별 처리

| 상황 | 조건부 산출의 경계 |
|---|---|
| 도움 모달은 열렸으나 POST 실패 | 로컬 준비/완료 사건을 같은 번호로 재송신. e까지 빈칸이 있으면 보류. 이미 표시된 도움을 없던 일로 하지 않음 |
| 준비 저장 후 실제 표시 실패 | 실패가 명확한 범위만 기록. 표시 여부가 모호하면 자동 확인 보류 |
| 도움을 표시한 다른 탭이 있음 | 각 탭 순번을 벽시계로 억지 합치지 않음. 범위에 포함된다면 그 생산자의 시작/끝과 기록도 필요. 모르면 기존 앱 전체 확인값은 보류 |
| 녹음 중 도움 또는 표시/녹음 경계 겹침 | 기록 수집은 완료일 수 있으나 도움 시점 판정은 겹침/불명으로 남을 수 있음. 독립 수행 자동 승인 아님 |
| 벽시계가 변경됨 | 같은 실행의 순번·단조 시간만 내부 순서에 사용. 현재 Core의 절대시각 판정을 무조건 참으로 덮지 않음 |
| 녹음 뒤 도움 사건이 발생함 | 종료 후의 실제 도움을 과거 시도에 소급 적용하지 않음. 늦게 전송된 종료 전 사건은 번호 빈칸/연결로 구별 |
| 파일 업로드만 함 | 이 앱에서 생성된 시작·종료 사건이 없으므로 파일의 과거 도움 범위를 자동 확인하지 않음 |
| 복구/새로고침으로 미완료 꼬리가 남음 | 새 실행을 옛 순번의 연장으로 지어내지 않음. 옛 구간은 미확인 유지 |
| 예제의 가상 도움·합성 근거 | `fixture-assumption`으로 분리. 수집 완료에 관한 실제 행동 증거로 세지 않음 |

## 7. 중앙 큐 없이 필요한 코드 연결과 남는 한계

- **public/app.js:** 실제 표시·녹음 생산 위치에서만 국소 사건을 만든다. 화면에 이미 표시된 도움/후보를 재렌더하는 경로를 정책에서 빠뜨리지 않는다. 전사 완료 같은 서버 후처리 사건은 실제 도움 발생 순번으로 세지 않는다.
- **server.cjs:** 사건 스트림·제출 끝 참조의 검증과 조건부 산출을 담당한다. 현재 오디오 POST와 `/events`를 확장하는 최소 경로를 쓸 수 있으나 기존 generic API가 이미 이를 지원하는 것은 아니다.
- **store.cjs:** 기존 전체 `events.payload`·트랜잭션·멱등성·원음 첨부 참조를 활용한다. 사건 도착 순서와 생산 순번을 별개로 저장한다. 제출 때 연속성 판정과 근거 저장을 같은 상태 판본에 결속한다.
- **core.cjs:** 새로운 관측 사건/범위 결과의 결정적 처리와 수동·산출 출처를 추가해야 한다. 현재는 알 수 없는 사건 종류를 거절하므로 서버가 테이블에 넣기만 하면 기존 재생 검증을 통과하는 구조가 아니다. 저장된 전체 payload와 해당 엔진 판본으로 같은 결과를 재현하도록 바꿔야 한다.
- **시간 분류:** 현재 `timingFor`는 벽시각/확인 정보를 사용한다. 단조 순번만 추가해 `performanceTimeConfirmed`를 참으로 바꾸면 안 된다. 같은 실행의 요청/완료 순서를 별도 시간 근거로 해석하는 처리를 설계하거나, 시계 불명은 기존 보류로 유지한다.

검사의 상한은 **선택한 정책을 충실히 실행하는 앱 생산자**라는 가정 안에서의 기록 연속성이다. 수정된 클라이언트가 사건을 숨기거나, 앱 밖 사람이 답을 말해 주거나, 다른 기기로 내용을 보는 일을 인증하는 설계가 아니다. 허용 범위를 명시해야 한다는 사실을 추가 강제 훅·중앙 서비스·학생 감시 기능의 도입 이유로 쓰지 않는다.

이번 결과는 최소 생산자/소비자 연결과 10개 필드의 설계다. 실앱·운영 DB·기존 자산·테스트는 변경하지 않았다. 개발 착수나 등록성 우위 판단을 대신하지 않는다.

**통합 결정:** 같은 날 선행 대조에서 순번 누락 검사·완결 전 사용 보류에 가까운 기존 기술이 확인됐다. 이 설계를 등록 확률을 높이기 위한 추가 독립항으로 채택하거나 P1에 일괄 삽입하지 않는다. 제품에서 자동 수집 범위의 근거가 필요할 때 검토할 연결안으로 유지한다. 현 P1의 수동 확인값을 이미 자동 산출된 값처럼 설명하지 않는다.
