# P3 개발을 결정하기 위한 대조 사례 세 개

2026-09-13 · 독립 반론 검토 · 구현·추가 시험 실행 없음

**현재 자료로는 P3의 대규모 개발을 특허 등록성 개선 수단으로 정당화하지 못한다.** 먼저 아래 세 사례에서 목적·행동·시간 정보가 실제 선택과 결과 적용에 어떻게 쓰이는지 확인해야 한다. 이 자료는 청구항을 늘리는 제안이 아니라, P3를 계속 구체화할지 또는 특허 차별화 목적의 확장을 멈출지 결정하기 위한 입력·기대 결과 명세다.

P3는 **실제 행동이 제공한 정보와 답 노출·새 수행 영향을 함께 계산하여, 확인 대상과 결과 사용 조건을 정하는 전체 연결**이라는 개발 가설이다. 현 P2는 원음 재검토 한 종류의 계약이며 이 전체 연결은 미구현이다.

**현재 결정 상태는 보류다.** 이 관계에 대한 구체적인 변리사 의견은 아직 확보되지 않았다. 아래 사례는 추가 구현을 이미 하기로 정한 발주서나 전문가가 차별성을 인정한 결과가 아니다.

사례 1의 현재 결과는 루트가 실행한 `PURPOSE_SENSITIVITY.json`을 읽어 확인했다. 이 문서 작성자는 중복 실행하지 않았다. 사례 2·3은 향후 대조 입력과 기대 결과이며 새로 실행해 통과시킨 결과가 아니다.

## 공통 기준선: 같은 사실과 규칙을 받은 일반 처리 방식

POMDP는 **일부 상태를 직접 알 수 없는 환경에서 관측과 상태 변화를 고려해 행동하는 모델**이다. 행동이 정보를 주면서 동시에 상태를 바꾸는 문제 자체는 기존 연구에 있다. 따라서 ‘관측이 증거를 바꾼다’ 또는 ‘실행 결과를 보고 다시 계획한다’만을 P3의 새 효과로 삼지 않는다. [Kaelbling·Littman·Cassandra, 1998, §1~2, 인쇄쪽 100~101 / PDF 2~3](https://people.csail.mit.edu/lpk/papers/aij98-pomdp.pdf#page=2)

이번 세 사례에는 학습 확률이나 성공 확률을 지어 넣지 않는다. 유한한 사건·후보·행동과 명시한 조건을 다루므로, **일반 상태 전이 처리기 + 출처·시간·목적 정책 + 결과 수신 후 재계획**을 강한 기준선 B로 설계하면 충분하다. POMDP 제품을 실제 실행해 비교했다는 뜻은 아니다. 이 유한 사례가 일반적인 관측·행동 모델에 표현되지 않는다고도 주장하지 않는다.

| 양쪽에 동일하게 제공할 입력 | 제공 범위 |
|---|---|
| 원음·수행 | 원음 참조, 발화·시도 ID, 녹음 발생 구간, 원음 길이 |
| 해석·평가 | 같은 현재 후보 목록, 같은 단어 시각 입력, 같은 목적별 평가함수 F, 문항·독립 조건 |
| 목표 | 사용하려는 목적과 목표 기록. 특정 방법에만 목표를 숨기지 않음 |
| 행동 | 같은 후보 행동, 수신 대상 역할, 제시 자료·능력 범위, 원음 재생·새 수행 생성의 가능한 결과, 선언 비용 |
| 실행 이력 | 같은 실제 발생·수신 시각, 실행 대상, 답 제시 사건, 재생 구간, 새 원음·시도와 결과의 연결 |
| 불확실성 | 같은 미확인 값과 이력 수집 범위. 한쪽만 `unknown`을 도움 없음으로 바꾸지 않음 |
| 적용 정책 | 새 응답을 과거 원음의 전사로 쓰지 않는 규칙, 관련 도움의 전·중·후 처리, 다른 보류 조건 보존 규칙 |

기준선에는 P3가 만든 완성된 `resolves`·허용 목적 목록·확인 계약을 답안으로 미리 주지 않는다. **동일한 기초 입력과 정책에서 기준선도 스스로 관계를 계산**하게 설계한다. 별도로 완성된 계약을 양쪽에 주는 비교를 한다면, 그것은 실행기의 일치 검사이며 계약 생성의 차이를 검증하는 실험이 아니다.

현 Core의 비교 스위치인 `no-purpose`, `no-target`, `no-epoch`, `predicted-response`는 구성 제거 시의 동작을 보는 데 쓸 수 있다. 필요한 목적·귀속·실제 관측 조건을 일부러 끈 실행을 일반 선행기술의 대표 기준선으로 사용하지 않는다.

각 사례의 결과는 다음 출력 묶음으로 비교한다. 객체 ID나 해시가 달라지는 것은 의미 차이에 넣지 않는다.

```text
선택 = 다음 행동, 필요한 원음 구간, 실제 목표 기록
조건 = 허용 결과의 출처·시도·목적, 필요한 실행 근거, 미확인 조건
적용 = 원음별 현재 후보, 목적별 상태·값·도움 표지, 보류·제외 사유
이력 = 원인 사건과 전후 상태, 적용 거절·재계획·중복 처리
```

## 사례 1 — 목적을 바꿔도 같은 원음을 같은 범위로 확인한다

### 사건·입력

같은 원음 A/e0와 두 후보, 유효한 수동 정렬 자료를 사용한다. 다른 문항·시간·도움 관측 조건은 충족한 통제 입력이다.

```text
H1 = 친구를 만나서 카페에 갔어요
H2 = 친구가 만나서 카페에 갔어요
F(asr,H1) != F(asr,H2)
F(object,H1) != F(object,H2)
F(past,H1) == F(past,H2)

입력 1A: session.purpose = original-performance
입력 1B: session.purpose = asr-data
나머지 후보·정렬·행동·규칙·비용·상태는 동일
```

같은 비교를 세 번째 후보 `친구를 만나서 카페에 가요`가 있는 입력에서도 한다. 세 번째 후보는 과거형 평가도 바꾼다. 후보 수를 늘린 것이 별개의 발명 효과는 아니다.

### 현재 확인된 결과와 기대 상태

루트의 읽기 전용 실행 결과:

| 후보 | 목적 변경으로 달라진 Core 계획 대상 | 선택 행동 | 현 P2 계약의 대상·구간 |
|---|---|---|---|
| 두 개 | `e0:object` ↔ `e0:asr` | 양쪽 모두 `review-original` | 양쪽 모두 `e0:asr`, `e0:object`; 0~550ms |
| 세 개 | `e0:object,e0:past` ↔ `e0:asr` | 양쪽 모두 `review-original` | 양쪽 모두 `e0:asr,e0:object,e0:past`; 0~2350ms |

계약의 허용 결과 종류는 모두 `source-audio-review`이며, 각 후보 수 안에서 후보 목록과 차이 근거의 의미도 같다. 구간 숫자는 수동 정렬 입력에서 계산한 값이다. 실제 음성의 정답 경계를 측정한 값으로 해석하지 않는다. [실행 결과](C:/Users/q1212/Documents/SYNK-appsscript/tools/patent-studio/grant-path-20260913/decision/PURPOSE_SENSITIVITY.json)

계획만으로 자격 상태는 변하지 않는다. 두 후보 입력에서는 전사·조사가 보류이고 과거형은 다른 조건 충족 시 유지된다. 세 후보 입력에서는 과거형도 후보 효과가 달라 보류 대상이다. 실제 적격 확인 결과가 오기 전 후보를 임의로 지우지 않는다.

### 강한 기준선과 비교할 질문

기준선 B에도 같은 목적별 평가함수와 후보·정렬을 준다. 정확한 전사도 확인해야 한다면 모든 전사 차이를 포함하는 원음 범위를 고르는 것은 정상적인 기대 결과다. **양쪽의 선택·범위가 같아야 하는 입력을 억지로 달라야 한다고 채점하지 않는다.**

P3가 목적별 계산 때문에 선택이나 범위를 줄인다고 주장하려면, 이 사례의 동일성이 깨지는 **실제 제품 목표**를 먼저 명시해야 한다. 예를 들어 활성 목표를 조사 하나로 제한한다면, 원음 전사 목표를 계속 달성했다고 주장할 수 없다. 기준선에도 같은 활성 목표를 주고, 목표 밖 후보나 기록을 확인 완료로 승격하지 않는지 함께 본다. 단순 목표 필터의 추가와 행동 영향의 공동 계산은 별개다.

### 개발 결정

- **이 사례만으로 중단할 주장:** ‘현재 목적별 평가가 재생 구간을 바꾼다’, ‘현재 계약은 목적 선택에 맞춰 불필요한 구간을 제거한다.’ 실행 근거가 없다.
- **계속할 조건:** 제품이 요구하는 목표·행동 조합 중, 공동 계산을 빼면 필요한 입력이나 적용 관계가 실제로 사라지는 예가 식별된다. 무엇을 유지하고 무엇을 포기하는지 명시해야 한다.
- **중단할 조건:** 목적별 설명·태그만 달라지고 선택·범위·허용 목적·적용 기록은 계속 동일하다면, 이 관계를 특허 차별화 근거로 추가 개발하지 않는다. 현재 일반 기능의 개선으로 필요할 수는 있다.

이 결과는 현재 실험의 목적 민감도 한계다. P3의 모든 미래 구성을 반증하지도, 선행 결합의 용이성을 증명하지도 않는다.

## 사례 2 — 검토자 전용 계획 대신 학생에게 답이 표시되고 새 응답이 온다

### 사건·입력

원음 A/e0의 두 후보는 사례 1과 같다. A의 녹음은 `09:59:00~09:59:03`에 끝났고, 계획 P는 `10:00:00`에 생성한다. 실제 목표는 A의 원음 전사와 원래 조사 수행 확인이다.

```text
계획 P:
  action = 검토자에게 A의 필요한 원음 구간을 재생하여 전사 확인
  recipient = reviewer
  expectedSource = A/e0
  expectedKind = source-audio-review
  answerToLearner = false
  createsAttempt = false

실제 사건 X1, 10:00:01:
  action = 문장 '친구를 만나서 카페에 갔어요' 표시
  recipient = learner
  answerScope = object
  occurredAt = 10:00:01, receivedAt = 10:00:04
  source = 실제 표시 생산자의 사건 참조

실제 사건 X2, 10:00:05~10:00:08:
  action = 새 녹음
  audio = B, attempt = e1
  priorDisplay = X1

결과 Y, 10:00:09:
  planRef = P
  actualExecutionRefs = [X1, X2]
  describes = B/e1
  confirmedText = H1
  declaredKind = source-audio-review  # 이름만 원음 확인이라고 보낸 충돌 입력
  A 재생 근거 = 없음
```

수신자가 검토자 전용인 대조 분기에서는 X1의 `recipient`만 `reviewer`로 바꾼다. 나머지 정보는 같다. 새 녹음 B가 생겼다는 사실과 A를 듣지 않았다는 사실은 그대로다. 내용 분류 `object`는 통제된 정책 입력이며 모든 실제 문장의 인지적 영향을 자동 판별했다고 주장하지 않는다.

### 기대 결과

| 기록·출력 | 실제 learner 표시 | 실제 reviewer 전용 표시 |
|---|---|---|
| 계획 P의 신뢰 | 선언한 행동과 실제 행동이 다름. 기존 계약을 그대로 적용하지 않음 | 실제 새 응답이 들어온 점은 계획과 다름. 역시 원래 계약에 적용하지 않음 |
| Y를 A/e0의 확인으로 사용 | 불허. 종류 문자열보다 원음·시도·실행 출처가 우선 | 불허. 교사 전용이었다고 B가 A의 전사가 되지 않음 |
| A의 후보·조사 보류 | 두 후보 유지, 조사·전사 보류 유지 | 동일 |
| A의 과거 수행에 대한 X1의 영향 | A가 끝난 뒤이므로 이 사건만으로 소급 제외하지 않음 | 학생 도움 사건으로 만들지 않음 |
| B의 정확한 원음–전사 자료 | B 원음과 적격한 B 전사 확인·범위 등 별도 조건이 충족되면 B 자료로 반영 가능 | 동일 |
| B의 조사 수행 기록 | 별도 조건이 충족되면 **도움 후 수행 기록**으로 반영 가능. 독립 수행으로 바꾸지 않음 | 확인된 도움 관측 범위 안에서 **관련 기록된 도움 없음**으로 평가. 전 세계 도움 부재 인증은 아님 |
| B로 A의 최초 수행 입증 | 불허 | 불허 |
| 다음 확인 | 실제 사건·새 판본을 반영해 A 확인을 다시 계획 | 동일 |

현 Core에서 새 응답의 `response-performance`가 `accepted`이고 `assistance=after-help`일 수 있다. 이를 오류로 보고 일괄 `excluded`로 바꾸면 안 된다. **새 수행 관측을 저장하는 것과 독립 수행의 근거로 인정하는 것을 구분**한다. B를 원래 수행에 소급하는 `earlier-proof`는 제외된다.

과거 계획 ID를 새 revision에 붙이는 것만으로 재시도하지 않는다. A 확인이 여전히 필요하면 새 상태에서 계약을 계산하고 A에 대한 적격 결과를 받는다. B와 실제 실행 기록은 별도 자료로 보존한다. 표시 대상이나 발생 시점을 실제로 모르면 `unknown`을 유지하며, 위 확정 역할 분기의 답을 복사하지 않는다.

### 강한 기준선에 줄 정보와 필요한 I/O 차이

기준선 B도 X1·X2·Y의 원문 사건, 역할, 발생 시점, 원음·시도·의미 충돌을 모두 받는다. 같은 일반 출처·정책 검사로 Y의 A 적용을 거절하고 B를 분리해야 한다. 기준선에 계획 P만 주고 실제 실행을 숨긴 후 P3가 더 안전하다고 비교하지 않는다.

P3 구현이 보여야 할 기능 차이는 **계획 템플릿의 `exposesAnswer=false`를 계속 믿는 대신, 실제 learner/reviewer 분기에서 B의 도움 표지와 허용 사용 조건을 다르게 계산하는 것**이다. 동시에 두 분기 모두 B→A 소급을 막아야 한다. 이는 현재의 사전 선언 planner·미연결 실행 경로와 비교한 제품 기능 차이이며, 강한 일반 기준선에 대한 우월성은 아니다.

### 개발 결정

- **계속할 기능 범위:** 실제 사건을 받아 역할·출처에 따라 결과를 다르게 적용하고, 실제로 변한 상태에서 재계획하는 어댑터가 제품에 필요하다면 그 연결을 한정하여 개발한다.
- **중단·수정할 경우:** learner/reviewer가 달라도 B의 도움 표지가 같거나, 한 행동에 답 노출이 있었다는 이유로 A·B의 모든 목적을 제외하거나, 계획에 없던 B를 A의 확인으로 수용하면 P3 설계가 실패한 것이다.
- **특허 차별화 목적의 확장을 멈출 경우:** 같은 기초 정책에서 일반 기준선도 동일한 관계를 자연스럽게 계산하고, 추가로 설명할 처리 차이가 확인되지 않는다면 이 사례의 정상 동작을 새로운 등록 근거로 확대하지 않는다.

이 사례를 통과해도 일반적인 실행 감시·정책 검사·재계획과 구별된다는 증명은 아니다. 역할별 정책을 새 객체에 담았다는 것만으로 그 경계를 넘지 않는다.

## 사례 3 — A 뒤 도움과 A 전 도움의 늦은 도착을 구별한다

### 사건·입력

이번에는 시간 관계에 집중하기 위해 A의 실제 원음 확인 결과 H1이 이미 있고 다른 관련 보류 조건도 충족한 상태를 출발점으로 둔다. 시간은 통제 입력이다.

```text
A/e0:
  capture = 09:59:00~09:59:03
  ownAudioReview = H1, 원음·전사·문항·범위 조건 충족

B/e1:
  capture = 10:01:00~10:01:03
  ownAudioReview = H1, 별도 원음·확인 조건 충족

도움 H:
  recipient = learner
  answerScope = object
  receivedAt = 10:05:00

분기 3A: H.occurredAt = 10:00:00  # A 뒤, B 앞
분기 3B: H.occurredAt = 09:58:59  # A 앞, B 앞
```

각 분기 안에서는 H와 B 확인 결과의 **수신 순서를 바꾼 두 전달열**을 사용한다. 최종적으로 같은 사건 집합과 같은 범위 확인을 받은 상태를 비교한다. 전체 관계를 아직 받지 못한 중간 상태에서 ‘도움 없음’을 확정하도록 요구하지 않는다. 도움 관측 범위가 미확인이면 해당 조건은 보류로 남긴다.

### 최종 기대 상태

| 기록 | 3A — A 뒤 도움 | 3B — A 전 도움 |
|---|---|---|
| A 원음–전사 자료 | 반영 유지 | 반영 유지. 전사 조건이 그대로 충족한다는 전제 |
| A 조사 독립 수행 | 반영 유지. 나중에 보여 준 답으로 과거 수행을 오염시키지 않음 | 관련 도움을 이유로 독립 수행 제외, 기존 기여가 있으면 철회 |
| A 과거형 수행 | 별도 독립 조건·범위가 충족하므로 유지 | 도움 범위가 조사로 한정되고 과거형 독립 조건이 충족하면 유지 |
| B 원음–전사 자료 | B 자체 조건에 따라 반영 | 동일 |
| B 조사 수행 | 도움 후 관측으로 저장 가능; 독립 수행으로 승격하지 않음 | 동일 |
| B로 A를 증명 | 불허 | 불허 |
| 수신 순서를 바꾼 최종 상태 | 같은 사건 집합이면 같음 | 같은 사건 집합이면 같음 |
| 전이 이력 | 실제 받은 순서·판본 이력은 다를 수 있음 | 동일한 원칙. 최종 상태 일치가 로그 전체 일치를 뜻하지 않음 |

도움의 발생 구간이 A와 겹치거나 선후 불명이라면 A 조사 상태를 독립 수행 반영으로 만들지 않는다. 발생 시점 미확인을 서버 수신 시각으로 대체하지 않는다. 반대로 `receivedAt`이 늦었다는 이유만으로 도움을 A 전에 있었던 것으로 만들지도 않는다.

### 강한 기준선과 비교할 질문

기준선 B에도 동일한 고정 발화 구간, 도움의 실제 발생·수신 정보, 능력 범위, 원음·시도 관계를 준다. 사건 시각 기준 재처리와 목적별 정책을 가진 기준선이 위 최종 상태를 내야 한다. 수신 순서만 정렬하는 일부러 약한 방식이나, 아무 도움이나 모든 과거 기록에 붙이는 방식은 강한 대조가 아니다.

P3는 사례 2에서 수집한 실제 행동을 위 발생 관계와 연결해야 한다. **‘실제 행동에 답 노출이 있었다’에서 곧바로 ‘원래 시도가 오염됐다’로 넘어가면 안 된다.** 필요한 출력 차이는 3A와 3B 사이의 A 조사 기여 유지/철회이며, 이 차이는 기존 P1 시간·도움 처리에도 있는 관계다. P3가 새로 입증할 것은 이 기존 규칙을 실제 행동 생산자와 결과 소비에 일관되게 연결하는 기능 범위다.

### 개발 결정

- **중단·수정할 경우:** 3A에서 A 조사를 제외하거나, 3B에서 A 조사를 반영하거나, 같은 최종 사건 집합인데 수신 순서만으로 최종 자격이 달라지면 구현 확대 전에 시간·귀속 규칙을 바로잡는다.
- **필요할 수 있는 제품 개발:** 실제 표시·녹음 사건의 발생 관계를 기존 시간 처리기에 전달하고, 완전하게 받지 않은 이력을 미확인으로 유지하는 연결이다.
- **등록성에 관한 한계:** 정상적인 도움 후 평가와 늦은 사건 정정을 재현한 결과만으로 새로운 결합을 입증하지 않는다. P1의 기존 기능이므로 P3의 신규 효과로 중복 계산하지 않는다.
