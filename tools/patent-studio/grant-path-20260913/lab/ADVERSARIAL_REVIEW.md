2026-09-13 · 구현 작성자와 별도 검수 · 합성 입력만 사용

## 검수 결론

**현재 검토한 범위에서 잘못된 원음·시도·구간·후보를 승인하거나, 다른 보류 조건을 함께 지우는 P0/P1 결함을 재현하지 못했다.** 첫 판본의 명명 독립 반례 22개, 응답 귀속·도움 유지·재생 경계를 실행했고, 코드 판본 보강 뒤에는 현재 회귀 21개와 독립 코드 판본 반례를 다시 실행해 통과했다. 이는 아래 명시한 입력과 로컬 처리 계약의 검수 결과다. 전체 A_CORE 발전 설계, 제품 통합, 실제 사람의 청취, 등록 가능성의 검증 완료가 아니다.

특히 세 번째 후보가 문장 뒤에서 달라지는 반례에서도 그 구간을 확인 범위에 포함했고, 후보가 모두 같아졌더라도 별도 해석 범위·노출 범위·문항·미확인 원인은 자동 확인하지 않았다. 원래 수행에 조사의 도움이 있었던 사건은 보존하여 원래 독립 수행은 제외한 채, 적격한 원음–전사 자료만 사용할 수 있었다.

## 읽은 원문과 수행 방식

- `A_CORE.md`의 추가 데이터 계약, 독립항 검토 문언, 현재/추가 경계, 강한 비교군 조건.
- `lab/observation-contract.cjs` 전체 및 `lab/DESIGN.md`.
- 현재 `core.cjs`의 세션 생성·사건 처리·보류 조건·목적별 평가와 `temporal-evidence.cjs`의 도움 시간 규격.
- root가 작성 중인 `observation-contract.test.cjs`는 독립 반례 실행 이후 관련 항목을 읽었다. 아래 독립 입력은 그 테스트 파일을 수정하거나 가져다 실행한 결과가 아니다.

Node 24.18.0에서 인메모리 세션과 선언된 단어 정렬을 만들고 `node:assert/strict`로 실제 반환값과 전후 상태를 비교했다. 원음 A/B는 실제 학생 녹음이 아닌 합성 참조 문자열이다. 이 검수는 WAV 청취·ASR 정확도·시간 정렬의 실제 정확성을 검증하지 않는다. 구현·테스트·Core 원본은 수정하지 않았다.

## 실행한 명명 반례 22개

공통 입력은 통제 문장 후보 `친구를 만나서 카페에 갔어요`, `친구가 만나서 카페에 갔어요`와 5,000ms의 합성 원음 참조다. 세 번째 후보에는 `친구가 만나서 카페에 가요`를 썼다. 각 단어는 200ms부터 1,000ms 간격의 합성 정렬이고 후보에 따라 끝점을 30ms씩 달리했다.

## 추가 확인한 응답·재생·도움 경계

별도 세션에 원음 B를 갖는 `response-B/e1`을 만들고 그 응답의 확인 계약을 적용했다.

- `review-response`와 정확한 `responseId`가 생성되었고 원래 `original` 객체 내용은 그대로였다.
- 응답의 `humanConfirmed`는 확인 결과에 따라 true가 되었지만, 별도 `scopeConfirmed:false`는 그대로였다.
- 후보를 두 개 그대로 남기는 결과도 처리되며, `effect-disagreement`는 계속 남았다. 확인 결과를 받았다는 사실만으로 하나를 강제 선택하지 않았다.
- 동일 시도에서 조사 도움의 발생 범위를 녹음 이전으로 선언한 세션을 따로 만들었다. 확인 뒤에도 helpEvents가 같고 `original-was-assisted`가 남았다. ASR 자료는 accepted가 되었다.

추가 도움 입력의 첫 시도는 검수자가 `timeBounds.basis`와 `sourceRef`를 빠뜨려 Core 형식 검사에서 거절됐다. 선언 출처를 채운 올바른 입력으로 다시 실행하여 위 보존 결과를 확인했다. 잘못 만든 fixture를 구현 결함으로 세지 않았다.

### 재생은 두 층을 구분해야 한다

`Core.applyEvent(preState, record.event)`를 사용하면 **평가 cells와 해당 발화는 동일하게 재생**된다. 그러나 현재 Core는 eventLog payload를 보존하지 않으므로, 이렇게 재구성한 상태에 같은 receipt를 다시 보내면 `idempotent-replay`가 아니라 `event-id-conflict`가 반환된다. 이 동작을 실제로 재현했다.

현재 어댑터가 반환한 상태에는 payload를 부가하므로 그 상태에서는 동일 재송신이 정상이다. 장기 저장/재시작까지 지원하려면 전체 payload를 보존하는 저장·재생 경로가 필요하다. `DESIGN.md`에도 이 경계가 명시돼 있다. **Core 단독 재생만으로 장기 감사 기록과 재전송 처리까지 완성됐다고 보고하면 안 된다.** 현재 로컬 실험 범위의 구현 오류로 집계하지 않았지만 제품 통합의 남은 항목이다.

## 사실 주장과 기술 범위의 제한

1. **실제 행동 진위:** `kind:'source-audio-review'`, source, range, confirmed는 제공자가 제출한 기록이다. 다른 새 응답을 받고도 거짓으로 원래 원음을 적은 경우를 인증하는 장치는 아니다. 실제 노출·새 수행 사건의 독립 참조 검증은 현재 포함하지 않는다.
2. **정렬 정확성:** 단어열·범위·출처 필드의 형태와 관계를 검사한다. 원음 파형에서 해당 단어가 실제 발생한 위치를 검증하거나 정렬을 생성하지 않는다. 범위 누락은 전체 원음으로 처리하며 근거 없는 좁은 구간을 만들지 않는다.
3. **실제 후보 범위:** 제공된 40개 이하 후보 내부의 모든 쌍을 계산한다. 모든 가능한 해석을 포괄한다는 인증이 아니며 scopeConfirmed를 별도 유지한다.
4. **계약 봉인:** SHA-256은 직렬화 내용 결속이다. 지문까지 다시 만들 수 있는 발신자의 위변조를 막는 서명·인증이 아니다. 12번은 지문을 바꾸지 않은 변조 검출만 입증한다.
5. **보수적인 무효화:** 세션 전체 지문과 revision을 사용하므로 관련 없는 변화도 재계약시킨다. 유효 결과의 최대 수용이나 최소 재계획 비용을 입증한 방식이 아니다.
6. **계산 규모:** H개 후보와 W개 단어에서 편집 경로 확인이 O(H²W²)이다. 한도 H=40, W=512이면 최대 780쌍×262,144칸 = 204,472,320개의 동적 계획 셀 계산 규모다. 실제 시간·메모리 수치는 측정하지 않았다. 한도 존재를 저비용 보장으로 쓰지 않는다.

## 비교 실험을 해석할 때

이 검수는 올바른 동작을 검사한 것이며 기존 제품·선행기술 구현과의 우월성 실험이 아니다. root의 비교 실험에도 다음 경계를 유지해야 한다.

- 일반 기존 방식에도 원음·시도 ID, 현재 판본, 실행 결과 종류, 모든 후보 차이의 확인 범위, 별도 보류 조건을 동일하게 제공한다.
- 일부러 새 응답을 원음 전사로 덮어쓰거나 첫 두 후보만 보는 기준선만 제시하여 승리를 선언하지 않는다.
- 같은 계약을 받은 일반 연결 방식과 출력이 같으면, 그 실험에서는 우월한 효과가 입증되지 않는다. 그렇다고 그 계약 자체를 선행으로 쉽게 도출했다는 법적 결론도 아니다.
- 결합 동기, 필요한 인터페이스 변경, 결합 전체의 효과와 사후적 고찰은 별도 원문 대조로 판단한다. 이 22개 통과 수를 등록 확률로 환산하지 않는다.

## 판본 확인

첫 22개와 추가 경계 실행은 `observation-contract.cjs` SHA-256 `ca22b33860680bfd3bb645cd6f1b9adede7a2f58fcd69aacae2f4f8441656c73`에서 수행했다.

이후 작성자가 `engineIdentity`를 추가한 판본 SHA-256 `2a7ac4f4643907da19e4af9054b22f79c63c01c95deb6216ab2f8d079b8544d0`의 변경부와 `DESIGN.md`를 다시 읽었다. 현재 계약은 Core VERSION과 Core/직접 의존 4개 파일의 내용 지문을 포함하고, 적용 시 같은 실행 프로세스의 코드 식별과 비교한다.

독립 추가 반례에서는 VERSION을 그대로 두고 모듈 내용 지문만 다르게 변경한 뒤 계약 자체의 무결성은 다시 올바르게 계산했다. 실제 반환은 `engine-identity-mismatch`, 입력 상태는 불변이었다. 따라서 계약 봉인의 단순 손상 때문에 거절된 결과를 코드 판본 검사로 잘못 센 것이 아니다. 현재 계약의 네 파일 지문도 디스크 바이트와 직접 대조해 모두 일치했다.

코드 식별은 초기화 시 고정한 4개 파일 범위다. 이미 적재한 모듈 캐시와 당시 파일이 같다는 신뢰된 실행 환경이 전제이며 런타임 변조·핫 리로드·모든 간접 의존/Node 바이너리의 인증은 아니다. `DESIGN.md`에도 해당 제한이 반영돼 있다.
