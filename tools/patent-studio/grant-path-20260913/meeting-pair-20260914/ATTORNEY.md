# SYNK Core 특허 후보의 목적과 사실관계

<p class="lead">지연 수신한 도움 사건을 이용한<br>음성 기록의 목적·능력별 기여 갱신</p>

SYNK Core의 **근거 자격·관측·재판정 모듈**을 로컬 시제품으로 구현했습니다. 같은 원음의 기록을 용도별로 구분하고, 나중에 도움 사실을 알게 되면 기존 관측의 기여를 다시 판단합니다.

이번 요청은 **실제 사업에 쓰이는 좁은 처리 방식으로 한국 등록특허 한 건을 확보할 수 있는 출원 방향**을 검토하는 것입니다. 사업상 목적은 등록특허를 통한 마케팅과 기업 신뢰 확보입니다. 넓은 독점 범위보다 등록을 우선하되, 등록 요건은 그대로 충족해야 한다는 전제입니다.

> 검토 요청: 현행 주안 P1의 전체 처리 관계가 가까운 선행기술로부터 쉽게 도출되는지 판단해 주십시오. 진행할 수 있다면 독립항에 남길 관계와 추가 한정의 문안을, 부족하다면 결정에 필요한 조사·설명을 특정해 주십시오.

| 현재 위치 | 확인된 사실 |
|---|---|
| 구현 | Core 0.5.0 로컬 통제 시제품. 실제 학생 운영 경로 통합은 미완료 |
| 검증 | 합성 사건의 판정·저장·재현 및 제한된 계산 비교. 등록성·학습효과 측정은 아님 |
| 주요 미해결 | 전체 결합의 진보성, 일부 청구 조건의 기술적 필요, 발생 시각 누락 처리 |

<p class="small">작성 주체 SYNK · 유호 / 자료 정리 Codex. 이 문서는 변리사 검토를 위한 사실관계·문안 묶음이며, 출원 확정서나 등록 공보가 아닙니다. 검토 순서: 처리와 입력 2–4쪽 → 증거·선행 5–6쪽 → 결정 요청 7쪽 → 현행 청구 문안 8–9쪽 → 대안·출처 10쪽.</p>

## 같은 녹음을 서로 다른 용도로 판단합니다

SYNK가 지향하는 가치는 사람의 이해를 새로운 사실에 맞춰 고치고, 그 이해를 필요한 도움으로 연결하는 것입니다. 이 모듈은 그중 **어떤 기록을 어떤 판단의 근거로 사용할 수 있는가**를 다룹니다. 아래 사건은 원리를 설명하기 위한 합성 사례이며 실제 학습 현장에서 발견했다는 경위의 증명이 아닙니다.

<div class="phrase">친구를 만나서 카페에 갔어요</div>

| 원음 하나에서 구분하는 기록 | 의미 |
|---|---|
| 원음–전사 대응 자료 | 녹음과 확인된 텍스트의 대응을 이 용도에 사용할 수 있는가 |
| 조사 사용 관측 | 해당 문항·시도에서 조사 역할을 독립 수행의 근거로 사용할 수 있는가 |
| 과거형 사용 관측 | 해당 시도의 과거형 관측을 별도 조건 아래 사용할 수 있는가 |

세 기록이 반영된 후, **발화 전에 조사 표현 ‘친구를’을 보여줬다는 사건이 늦게 수신**되면 기존 판단을 재검토합니다. 대상 조사 기여는 철회할 수 있지만, 원음–전사와 과거형은 각각의 조건·값이 유지되는 경우에만 유지합니다. 과거형의 독립성은 입력된 확인값이며 자동 인지 인과 판정이 아닙니다.

<div class="flow">
<div><b>입력과 귀속</b> 원음·발화·시도·전사 후보·문항 조건·도움 사건</div>
<div><b>현재 자격 재판정</b> 발생 시간관계·능력 범위·후보 관측값·다른 사유</div>
<div><b>전후 기여 비교</b> 추가·철회·유지·교체와 이유를 계산</div>
<div><b>저장과 확인</b> 원인 사건·앞뒤 판본·전이 기록을 저장하고 재현</div>
</div>

<p class="small">위치: SYNK Atlas는 전체 체계의 이름, Core는 근거 판단의 책임, LOOM은 화면·재질·마스코트 표현의 책임입니다. 이번 주안은 Core 전체나 LOOM의 외형이 아니라 위 처리 관계입니다.</p>

## 발생 시각과 저장 시각을 구분합니다

| 논리 레코드·입력 | 의미와 생산·소비 책임 |
|---|---|
| 원음 식별·내용 참조 | 저장 계층이 원음 참조를 보존. 파일 내용과 발화·시도 귀속은 별개 |
| 발화·시도 식별자 | 원래 수행과 새 응답을 구분. 같은 문장·파일이어도 같은 시도로 단정하지 않음 |
| 발화 구간 [S,E] | 평가대상 캡처 구간. 업로드 시각으로 대체하지 않음 |
| 전사 후보·확인 정보 | 기계 전사, 직접 후보 입력, 청취 확인을 구분. 현재 제공된 후보 집합이 대상 |
| 문항·독립 확인값 | 역할 요구·과거형 독립 여부 등 외부 확인 입력. Core가 검사 |
| 도움 관측 범위 확인 | 앱 내 무엇을 확인했는지 나타내는 입력. 모든 도움의 부재를 자동 증명하지 않음 |
| 도움 사건 | 사건 ID, 답 노출 여부, 대상 능력, 발생 시각 at 또는 가능 구간 [L,U] |
| 수신·저장 기록 | 발생 정보와 별도 취급. 현재 recordedAt은 서버 저장 시각 |
| 자격·기여·판본 | 목적별 상태·관측값과 판본. 전후를 비교해 전이 기록 생성 |

**현행 시간 분류**는 다음과 같습니다. [L,U]는 도움의 발생 가능 범위이며 발화 구간 [S,E]와 비교합니다. 유효한 점 시각은 [at,at]로 취급할 수 있습니다.

| 조건 | 관계 | 독립 수행 판정에 대한 의미 |
|---|---|---|
| U &lt; S | 발화 전 | 해당 능력의 답 노출이라면 제외 사유 |
| L &gt; E | 발화 후 | 그 도움만으로 이전 수행을 제한하지 않음 |
| S ≤ L ≤ U ≤ E | 발화 중 | 해당 능력 보류 사유 |
| 나머지·판정 불가 | 불명 | 해당 능력 보류 사유 |

<p class="small">등호 경계는 발화 전·후에 포함되지 않습니다. 최종 상태는 시간 하나로 정하지 않고 4쪽의 다른 사유와 함께 결정합니다. 관련 구현: temporal-evidence.cjs / classifyHelpTime, core.cjs / collectBlockers.</p>

## 자격 상태와 기여 전이는 다른 레코드입니다

**반영·보류·제외**는 현재 자격 상태입니다. **철회·유지·추가·교체**는 직전 기여와 비교한 변화입니다. 이전에 반영한 기록이 보류로 바뀌어도 기여는 철회됩니다. 원음 삭제나 학습된 신경망 가중치의 역갱신을 수행하는 것이 아닙니다.

| 변경 전 → 변경 후 | 기여 처리 |
|---|---|
| 반영 → 보류 또는 제외 | 기존 기여 철회 |
| 반영 → 반영, 관측값 동일 | 유지 |
| 반영 → 반영, 관측값 변경 | 교체 |
| 비반영 → 반영 | 새 기여 추가 |

현행 Core는 해당되는 **모든 사유를 순서대로 수집·보존한 뒤 첫 사유로 상태를 정합니다.** 따라서 사유 순서는 표시만 바꾸지 않습니다. 예를 들어 도움 관측 범위 미확인과 발화 전 도움 사유가 함께 있으면 앞선 보류 사유가 상태를 결정할 수 있습니다. 전체 목록·순서는 9쪽 P1-05가 비교 기준입니다.

### 조사만 철회하고 과거형을 유지하는 조건

답 노출 도움의 대상이 조사로 한정되어야 합니다. 저장된 조사 해석과 과거형 관측의 독립 확인값이 참이고, 지원 전사 후보들의 과거형 관측값이 일치해야 합니다. 다른 보류·제외 사유가 없어 **전후 모두 반영이며 전후 값도 같아야** 유지합니다.

| 합성 대조 | 원음–전사 | 조사 | 과거형 |
|---|---|---|---|
| 세 기록 반영 후 발화 전 조사 도움 수신 | 유지 | 제외·철회 | 조건 충족 시 유지 |
| 위 결과에서 도움 관측 범위 확인 해제 | 유지 | 보류, 이미 철회됨 | 보류·철회 |
| 첫 정정 결과에서 과거형 독립 확인만 해제 | 유지 | 제외 유지 | 보류·철회 |

<p class="small">마지막 두 행은 첫 정정 결과에서 각각 분기한 별도 입력입니다. 조사 기여를 이미 철회했다면 다시 차감하지 않습니다. ‘갔어요’에서 ‘가요’로 후보가 바뀌어 전후 관측값이 달라지는 경우도 단순 유지 대상이 아닙니다.</p>

### 확인된 미수정 문제

도움 사건의 **at와 timeBounds가 모두 없으면** store.cjs와 core.cjs에 있는 현재 시각 기본값 때문에 실제 발생 순서를 모르는 입력이 ‘발화 후’로 분류될 수 있습니다. 두 경로와 입력 계약을 함께 수정해야 합니다. 반대로 timeBounds가 없다는 이유만으로 명시된 유효 at까지 버리면 안 됩니다.

시각 누락, 형식 오류, 시각과 구간의 충돌에 대한 계약과 시험은 추가 보완 대상입니다. 현재 도움 표시 UI는 표시 후 at을 제공하므로 모든 UI 사건이 이 문제를 겪는다고 확대하지 않습니다. **본 자료 작성에서 해당 제품 코드를 수정하지 않았습니다.**

### 계산과 제품 연결의 한계

같은 판정 코드·관련 입력 지문에서는 이전 평가 결과를 재사용합니다. 하지만 입력 확인·지문 생성·관측 계획·저장에는 전체 순회가 남습니다. N개 기록 중 K개가 영향을 받는다고 총비용이 항상 O(K)인 것은 아닙니다. 기록 수뿐 아니라 후보·단어·도움 사건 수, 상태 복사와 저장비용도 고려해야 합니다.

<p class="small">현재 학생 DB·Apps Script·Supabase 운영 경로 통합은 미완료입니다. 시제품 시연·시험 통과를 실제 학습효과, 전사 정확도 향상, 전체 연산량 절감 또는 등록 가능성의 수치로 해석하지 않습니다.</p>

**가장 강한 결합 반론:** 힌트의 차등 반영에 지연 사건 재처리와 의존성에 따른 철회를 적용하고, 음성 자료의 용도 구분을 추가하면 P1의 상당 부분을 도출할 수 있다는 주장입니다. 이 동기는 구체적으로 검토해야 합니다.

**검토할 남은 관계:** 도움의 시간·범위와 공유 전사 후보의 관측값을 함께 검사하여 기여 철회와 유지 조건을 정하는 전체 연결입니다. 선행이 각 요소를 개시하는지, 추가 규칙이 필요한지, 그 변경이 당시 기술자에게 통상적인지 구분해 주십시오.

‘17개 사유가 길다’, ‘신경망이어서 되돌리기 어렵다’, ‘여러 문헌이 필요하다’만으로 방어하지 않습니다. 모델 앞단의 자격 관리로 구현할 수 있다면 신경망 역갱신의 어려움은 결합 장애가 아닐 수 있습니다.

<p class="small">해외 특허·논문도 한국 심사의 선행 자료가 됩니다. 신규성은 단일 문헌과 전체 구성을, 진보성은 차이와 결합 용이성을 각각 판단해야 합니다. 이 표는 전체 선행조사 완료 선언이 아닙니다.</p>

### 요청하는 다섯 가지 결과

1. **P1의 진행·한정·재설계·보류 중 권고**와 가장 가까운 선행 문단.
2. 독립항에 꼭 남길 **처리 관계**와 종속항·실시예로 옮길 조건. 17개 사유의 순서 전체가 기술적으로 필요한지도 판단.
3. 시간 불확정과 후속 근거 정밀화 등을 포함한 **추가 한정 후보**. 각 후보의 기술적 효과·기재 근거·선행 차이.
4. 등록 판단을 위해 추가로 필요한 **구체 설명 또는 비교 최대 세 가지**. 기능 수·시험 수 확대만으로 요청하지 않음.
5. P1이 부족한 경우 P2 등 대안을 검토할 가치와 **판단을 바꿀 자료**. 대안 소개는 10쪽.
