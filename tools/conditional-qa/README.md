`conditional-qa.yml`은 master의 각 push에 세 관문을 건다. 파일과 시험 이름이 일치하는 실제 Node 시험 이벤트가 정확히 한 번 통과해야 한다. skip/todo, 이름 변경, 누락, 중복, 프로세스 실패·시간 초과는 실패다. 기존 syntax/wide CI에 처음 생긴 조건부 제외도 등록되지 않았으면 실패한다. 새 제외를 추가할 때에는 재현 입력과 자동 실행 경로를 함께 등록한다. 등록된 이름을 바꿀 때에는 같은 ID의 이름과 시험을 함께 바꾼다.

모든 실행 경로는 영수증 폴더 아래에 전용 TEMP/TMP를 만들고 Windows의 실제 경로로 고정한다. hosted runner의 `RUNNER~1` 별칭이 Git·PowerShell의 긴 경로와 달라지는 환경 문제를 시험으로 오인하지 않게 한다. 검사할 커밋과 다른 추적 파일 수정이 있으면 후보 표시가 없는 실행은 거절한다.

`worker.cjs`는 운영 사본에서 실행되며 별도 관리 체크아웃으로 신뢰하는 origin/master 커밋을 검증한다. 공용 작업본·운영 코드·운영 DB를 시험용으로 수정하지 않는다. PR/fork는 로컬 실행 대상이 아니다. 활성화 시점 이후 master 커밋은 순서대로 대기열에 보존한다. 한 회차는 검증 하나를 마칠 때마다 master를 다시 받아 대기열이 빌 때까지 차례로 처리하되, 새 검증은 회차 시작 뒤 60분 안에서만 연다(검증 하나가 길면 50분이고, 예약 작업과 숨김 실행이 2시간에 회차를 끊는다). 같은 회차에서 한 커밋은 한 번만 시도한다(11-02, 이전에는 회차마다 세 커밋까지만 재어 회차 사이가 비었다). 중단된 실행과 네트워크 장애는 다시 시도하며, 시험 자체의 실패는 실패로 남는다. 실행 도중 PC가 절전에 들어갔다 깨어난 회차(시스템 기록 Kernel-Power 42·107이 그 회차 시간 안에 있음)는 중단으로 보고 다시 잰다 — 11-01 덮개 절전 10분에 걸린 회차는 시험 둘이 606초로 끝났다. 기록을 읽지 못하면 절전이 없던 것으로 본다. 새 코드의 성공으로 과거 실패를 덮지 않는다.

이미 끝난 결과의 게시를 먼저 하고, 새 검증은 최신 master·나머지 최근 커밋 차례와 가장 오래된 대기 차례를 번갈아 고른다(11-02 과거 대기 전체 확인 후속). 처음에는 최신 차례로 시작하고 다음 차례는 `queue.json`의 `nextTurn`에 저장해 회차 종료·일꾼 재시작 뒤에도 이어 간다. 게시만 다시 하는 항목은 검증 차례를 소비하지 않는다. 새 push가 계속 들어와도 두 번 중 한 번은 오래된 준비 항목을 처리하며, 실행 중인 시험·과거 실패 증거는 그대로 보존한다. 진행 중인 검증·오래된 대기 한 차례·최신 검증이 각각 최대 50분이고 예약 간격이 5분이어서 [일꾼 무소식 한도](#local-status-check)는 155분이다. 시험 자체의 한도·통과 기준은 바꾸지 않으며, 아직 검증 중이면 통과시키지 않는다.

로컬 원문과 보관 fixture는 저장소 밖 `~/security-audit-skill/SYNK-conditional-qa`에 해시로 등록한다. `inputs.json`에는 이전 감사에서 보존한 출처·해시가 있고, `blobs/`에는 해당 바이트만 둔다. 추적 중인 현재 앱 소스가 과거 fixture보다 우선한다. Talk 실행·과제 참조판은 이전 검증의 고정 입력이고, 범위 표 비교는 매 실행 현재 Talk origin/master를 확인한다. 현재 Rust를 검사할 때 과거 WASM을 대신 쓰지 않는다. 의존성은 격리된 폴더의 lock 파일로 `npm ci --ignore-scripts` 설치한다.

GitHub 쪽 `local-coverage`는 호스트 시험이 통과한 뒤 그 커밋의 로컬 결과를 한 번만 읽는다. 통과면 초록, 실패면 빨강이고, 아직이면 대기 상태를 남기고 자기 실행을 취소해 러너를 놓는다. 취소는 통과가 아니며 빨강으로도 세지 않는다. 일꾼이 검증을 마치면(통과든 실패든) `resumeWaitingWorkflow`가 그 실행을 다시 돌린다. 같은 run ID에 attempt만 늘어, 커밋별 대조는 같은 실행의 마지막 결론을 본다. 예전에는 이 작업이 최대 155분을 폴링하며 러너를 잡고 있어, 하루 100회 넘는 push에서 계정의 동시 작업 한도가 차고 Pages 배포까지 밀렸다(11-04).

다시 돌리는 기준은 셋이다. 호스트 작업이 실제로 실패한 실행은 빨강 그대로 둔다. 손으로 취소돼 돌지 못한 호스트 작업은 그 커밋의 영수증에 필요하므로 함께 다시 돌린다. 로컬 결과가 나온 뒤에만 돌리므로 옛 판 커밋의 `local-coverage`도 곧바로 끝난다. 로컬 실패는 아직 기다리는 실행만 깨워 빨강으로 바꾸고, 이미 빨간 실행은 건드리지 않는다. 신호(`queue.json`의 `resumePending`)는 실행이 정리될 때까지 남아 회차 시작과 검증 사이마다 오래 안 본 것부터 10건씩 다시 보므로, 정리되지 않는 커밋이 있어도 다른 커밋이 밀리지 않는다. 회차를 시작할 때 최근 취소 실행 300개도 훑어, 로컬 결과가 있는데 취소로 남은 커밋을 attempt마다 한 번 다시 본다(`checkedRun`). 같은 실행은 attempt 6부터, 그리고 GitHub가 거절하는 첫 실행 뒤 30일부터 다시 돌리지 않는다(이때 실행은 닫히지 않은 채로 남고 결과는 커밋 상태에 있다). 실행이 없는 커밋은 깨울 것이 없다(나중에 생긴 실행은 게시된 결과를 스스로 읽는다). 이 커밋의 목록과 맞지 않는 `success`는 대기가 아니라 빨강이다. 게시에 실패한 로컬 실패는 대기로 읽히므로 회차 시작과 검증 사이마다 다시 게시하고, 그 뒤에 실행을 깨운다. 자기 취소는 GitHub가 단계를 멈추기까지 84초쯤 걸리고(11-04 실측), 5분 안에 멈추지 않으면 그 작업은 실패로 끝난다. GitHub API 오류는 세 번까지 다시 부르고, 그래도 안 되면 그 작업은 실패한다(실패는 통과가 아니고, 로컬 통과 뒤 일꾼이 다시 돌린다).

각 로컬 실행은 `runs/<commit>-<time>/`에 원래 이벤트, TAP, 화면 증거, 커밋·목록·입력 해시와 결과를 남긴다. 회차마다 70MB 남짓이 쌓여, 일꾼이 통과(게시까지 끝남)한 회차의 프로필 폴더 안 임시(시험 DB·`*_qa_out`·`*_run`·화면 캡처·`temp`·`server.log`)를 곧바로 지운다(11-04, [동시 검증](#local-parallel)이 하루 300회를 넘으면 하루 21GB라 C: 여유가 못 버틴다) — 맨 위 `result.json`·`started.json`·`runner.log`와 프로필의 `tests.tap`·`events.jsonl`·`process.log`는 남고, 실패·결과 없는 회차는 그대로 둔다(일꾼은 지난 회차 안쪽을 다시 읽지 않는다). 일꾼이 끊겨 남은 것은 공간 지킴이가 하루 한 번 같은 규칙으로 지운다(11-02 유호님 「세 가지 다 해」). 시험 전후 소스와 입력도 대조한다. GitHub에는 개인 자료 없이 해당 커밋의 `conditional-qa/local` 상태와 통과 수·목록 해시만 올린다. 같은 커밋의 검증이 끝나기 전에는 녹색이 되지 않는다. PC 꺼짐·로그아웃·입력 손상·도구 부재는 미완료/실패이며 과거 성공으로 대체하지 않는다. 검증이 끝나면 위 기준으로 그 커밋의 실행을 다시 돌리고, 호스트 작업의 실제 실패를 가리지 않는다.

고친 시험을 예약 일꾼 밖에서 미리 재 보는 **후보 사본**은 `inputs.cjs`의 `withCandidate({ original, state, commit, overlay }, run)`(만들고 → `run(context)` → `finally`에서 풂)이 기본이고, 직접 다룰 때는 `candidate(...)`로 만든다 — 일꾼 상태의 설정·입력 목록을 옮기고 `blobs/`는 junction으로 함께 쓰며, 준비 전에 임시 `context.json`(`candidate: true`)부터 적어 clone·fetch·`npm ci`가 끊겨도 풀 수 있다. 작업본·Talk 짝·`node_modules`로 하나 6.4GB라(11-02 GPT CI 백로그 수리가 끝난 후보 둘을 남겨 25분 사이 10.6GB) 결과를 상태 폴더 **밖** 회차 폴더(`<이름>-run/`의 TAP·`candidate-result.json`·로그)에 쓰고, 끝나면 `node tools/conditional-qa/inputs.cjs release <후보 상태>`(먼저 `--preview`)로 푼다. `release`는 일꾼 상태(`installation.json`·`queue.json`·`runs/`가 있거나 `candidate`가 아님)를 거절하고, 안에서 시험·프로세스가 쓰는 중이면 이름 바꾸기가 막혀 거절한다. git 객체·고정 blob(경로와 해시가 둘 다 같은 것만)·lock 설치로 다시 만들 수 없는 파일(덧씌운 시험 파일, 작업본 안에 생긴 출력, 바뀐 고정 입력)은 `kept/`로 옮기고, 공유 `blobs/`와 짝 작업본 같은 junction은 끊기만 하고 그 안으로 걷지 않으며, 지운 양·옮긴 것·못 지운 것을 `released.json`에 남긴다. 지울 폴더마다 `<이름>.releasing`으로 옮긴 뒤 훑고, 그 폴더의 `kept/`를 다 옮기면 폴더 안에 `.cqa-scanned`를 남기고(지울 때 맨 끝에 지움) 지운다 — 끊긴 뒤 다시 부르면 표식이 있는 폴더는 지우기만, 없는 폴더와 새로 옮긴 폴더는 처음부터 훑는다. 고정 입력은 `context.json`과 `inputs.json` 둘에서 읽어 준비가 끝나지 않은 후보도 같게 가린다. 한 번에 하나만(`releasing.lock`, 죽은 프로세스의 잠금은 넘겨받음), 잠긴 파일이 남으면 `released.json` 대신 `release-left.json`을 남겨 다음 호출이 마저 지운다. 풀거나 푸는 중인 상태는 `prepare`가 다시 쓰지 않는다. 부르지 않고 남은 후보는 공간 지킴이가 점검(30분)마다, 상태 폴더와 옆 회차 폴더(`<이름>-…`)가 두 시간 넘게 그대로이고 명령줄에 이름이 없는 것만 운영 사본의 같은 `release`로 푼다.

Windows 작업 `SYNK 조건부 시험`은 현재 사용자의 일반 권한·대화형 로그온으로 5분마다 시작한다. 작업 우선순위는 4(일반 CPU·I/O·메모리)다 — 작업 스케줄러 기본 7은 BelowNormal CPU·낮은 I/O·메모리 우선순위 2이고 그 아래 시험·시험 서버·Edge가 모두 물려받아, 바쁜 PC에서 브라우저 시작만 30초를 넘기고 평소 4초짜리 시험이 240초를 넘겼다(11-02). 일꾼도 시작할 때 CPU 우선순위가 일반보다 낮으면 일반으로 올린다. 중복 실행은 무시하며, 다시 켜지면 미실행 회차를 시작한다. 실행 명령은 운영 사본의 `tools/숨김실행.py` → `tools/conditional-qa/worker.cjs`다. 새 개인 토큰·관리자 권한·GitHub 자체 호스팅 러너는 만들지 않는다. 설치 영수증은 `installation.json`, 마지막 상태는 `last-run.json`, 전체 대기열은 `queue.json`이다. 보관된 원래 감사 자료는 건드리지 않는다.

설치는 `install.cjs --state <비공개 폴더> --ops <운영 사본> --pythonw <pythonw.exe> --first <첫 검증 커밋>`으로 미리 보고 같은 명령에 `--apply`를 붙인다. 최초 입력 등록은 `inputs.cjs`의 `provision`으로 이전 감사 manifest와 원문 해시를 검증한 뒤 수행한다. 상태 폴더는 공용 저장소 안에 두지 않는다. Codex 앱의 `%LOCALAPPDATA%` 가상화와 작업 스케줄러의 실제 경로가 달라질 수 있어 사용자 프로필 아래 명시적 경로를 쓴다.

운영 확인은 `node tools/conditional-qa/worker.cjs --state <비공개 폴더>`로 같은 회차를 실행할 수 있다. 이미 도는 회차가 있으면 잠금을 지우지 말고 완료를 기다린다. 입력이나 실행 도구 문제가 해결되면 인프라 실패는 다음 재시도에서 검증한다. 시험 자체가 실패하면 원인을 고친 새 코드로 다시 확인한다. 예약을 끄더라도 CI 로컬 단계는 미완료로 남으며 검증을 생략해 통과시키지 않는다.

과거 `failed` 항목은 저절로 성공 처리하거나 계속 재시도하지 않는다. 원인을 고친 뒤 같은 커밋을 다시 검사하려면 `node tools/conditional-qa/retry.cjs --state <비공개 폴더> --reason "확인한 원인과 재검사 이유" <커밋 SHA...>`로 미리 보고 `--apply`로 재등록한다(11-02 유호님 과거 대기·오류 전체 확인 요청). 실행 중인 일꾼이 있으면 재등록도 거절하므로 회차가 끝난 뒤 실행한다. 원래 실패 결과는 그대로 두고 `queue.json`의 `history`와 `retry-history/`에 원래 항목·결과 해시·이유를 남긴다. 대기열은 `retry`로 바뀔 뿐이며 GitHub 성공은 같은 커밋의 새 78건 영수증이 완전할 때에만 기존 일꾼이 올린다. 로컬 통과와 GitHub 전체 job의 복구도 각각 확인한다.

<a id="reregister-inputs"></a>

### git 밖 입력이 공용 작업본에서 바뀌었을 때

`inputs.json`의 앱 입력은 11-01 감사 때의 바이트로 묶여 있다. 그중 .gitignore에 걸린 파일(PATH 면접 영상 `*.mp4` 같은 것)을 공용 작업본에서 다시 만들고, 그 해시를 적은 추적 파일(`strict-manifest.json`)이 따라 바뀌면, 그 뒤 커밋은 모두 옛 바이트와 새 목록을 견주다 실패한다. 일꾼은 체크아웃마다 등록 해시와 다른 파일을 「Existing fixture changed」로 거절하므로 손으로 파일을 바꿔 넣을 수 없다.

이때는 운영 사본이 아닌 자기 작업본에서 `node tools/conditional-qa/reregister.cjs --state <비공개 폴더> --reason "바뀐 커밋과 이유" <저장소 상대 경로...>`로 미리 보고(옛 해시 → 새 해시 · 바이트), 같은 명령에 `--apply`를 붙인다. 공용 작업본(`config.json`의 `sourceRepo`)의 지금 바이트를 새 blob으로 넣고 그 줄의 해시를 바꾼다. 옛 판은 그 줄의 `replaced`에 남고 blob도 지우지 않는다. 다음 검증의 `materialize`는 체크아웃 파일이 그 줄의 `replaced`에 있는 해시일 때만 새 바이트로 덮고, 그 밖의 바이트는 여전히 거절한다. 작업본 둘·셋(`slots/`)은 회차 시작 때 `inputs.json`을 받아 같은 길로 바뀐다.

- 이미 등록된 앱 입력만 바꾼다. 추적 중인 파일 · 새 파일 · 저장소 밖 경로는 거절한다. 일꾼이 돌고 있으면 `retry.cjs`처럼 거절하므로 회차가 끝난 뒤 다시 친다.
- 바꾼 기록은 `input-history/<id>.json`(이유 · 전후 `inputs.json` 해시)에 남는다. 입력이 바뀌면 `inputDigest`도 바뀌어, 그 뒤 영수증이 어느 입력으로 쟀는지 구분된다.
- 바뀌기 전 커밋은 옛 바이트를 기대하므로, 그런 커밋을 `retry.cjs`로 다시 재면 이번에는 새 바이트로 실패한다. 대기열의 커밋이 모두 바뀐 커밋 뒤인지 먼저 본다(`git merge-base --is-ancestor <바뀐 커밋> <대기 커밋>`).
- 그 구간의 실패는 같은 번호로 줄곧 나므로, 다시 등록한 뒤 그 번호가 통과하면 [원인을 밝힌 구간 장부](#diagnosed-failures)에 `exactCases`로 적는다(아래 「적는 조건」의 예외). 다른 번호가 섞인 실패 커밋만 `retry.cjs`로 다시 잰다.

11-06 `6051236295`가 PATH 면접 720p 영상 넷(`strict-question` · `strict-listening` · `strict-followup-plan` · `strict-followup-experience`)을 다시 싸고 `strict-manifest.json`의 해시를 바꿨다. 등록된 앱 입력 2,610개를 공용 작업본과 견주니 다른 것은 이 넷뿐이었다(같음 150 · `.tmp` 고정 입력이라 공용 작업본에 없는 것 2,456). 11-06 04:12 회차부터 S063 · S064 · S065 · S067이 「Video hash does not match its file」로 실패했고, S067의 「Pages source checksum mismatch」는 앞 시험이 공개 판을 못 만들어 옛 커밋의 `.tmp/path-interview-pages`가 남은 것이다. 자세한 경과는 [현장 노트](../../docs/현장노트/시험_화면확인.md#conditional-qa-local이-11-06부터-연속-빨갛다--path-면접-영상을-다시-싼-뒤-일꾼이-11-01-바이트를-그대로-깐다-2026-11-08-claude)에 있다.

<a id="registered-verification"></a>

### 등록된 커밋 한 건을 먼저 확인할 때

운영 사본에서 `node tools/conditional-qa/worker.cjs --registered-commit <40자리 SHA>`를 실행한다. 예약 일꾼이 자리를 쓰고 있으면 회차가 끝난 뒤 다시 실행한다. 원래 검사 목록·입력·판정과 같은 실행 경로로 한 건을 재고 예약의 다음 차례를 보존한다. 이미 `passed`면 기존 결과를 보고하며, `failed`는 먼저 위의 `retry.cjs`로 원인을 기록하고 재등록한다.

자동으로 등록된 한 건을 재검사할 때는 같은 명령에 `--wait-for-room`을 붙인다. CPU 사용률이 85% 미만이고 남은 메모리가 3GiB 이상인 상태가 2분 이어져야 검사를 시작한다. 15분간 여유가 없으면 종료 코드 2와 `requested.attempted: false`를 반환한다. 그동안 지정한 커밋의 상태와 예약 순서는 유지된다. 저장된 영수증은 부하가 높아도 즉시 대조한다.

`last-run.json`의 `requested`에 SHA·상태·이번 회차 시도 여부를 남긴다. 종료 코드 0은 `passed`, 2는 PC 부하·시간·디스크 또는 게시 대기, 1은 검사 실패·잘못된 요청·잠금 사용 중이다. 검증한 결과의 게시를 다시 시도할 때에도 저장된 영수증을 대조한다.

말하기 기능 시험의 페이지 전환은 `qa/page-ready.mjs`로 해당 시험의 `t.signal`·기존 15분 전체 한도를 따른다. 별도의 Playwright 기본 30초가 먼저 종료하던 실패를 분리했으며 HTTP 오류·연결 거절은 재시도하지 않고 실패한다. 시험이 중단되면 전환 중인 페이지를 닫고, 시험 서버 종료까지 확인한 뒤 임시 파일을 정리한다. 전환별 HTTP 상태·경과 시간·실패는 그 실행의 `synk_speaking_qa_out/result.json`에 남긴다. 이 기능 시험은 페이지 응답 속도의 성능 기준으로 쓰지 않는다.

과제 화면의 로딩 캡처는 합성 서버 응답을 보류하는 동안 Playwright 시계도 잠시 멈춘다. 이미지 합성이 오래 걸렸다는 이유로 실제 앱의 12초 요청 제한에 걸리던 시험 오류를 분리한다. 캡처 중 1ms 타이머가 멈춰 있고 재개 뒤 다시 도는지 검사하며, 별도의 12초 초과 요청은 여전히 오류로 바뀌고 다시 불러오기로 복구되어야 한다. 실제 앱의 제한·오류 판정은 바꾸지 않는다. 캡처 경과 시간은 해당 실행의 `captureTimes`에 남긴다. 답을 내고 정답이 뜨는 구간도 같은 방식으로 시계를 멈춘다. 시트를 열 때부터 잡아 둔 정답 요청의 12초 제한이 낸 직후에 끝나면 앞 캡처 시간에 따라 시험이 갈렸기 때문이다(11-05 `0036e4e18`, [경과](../../docs/현장노트/시험_화면확인.md#s072가-드물게-정답-대기로-시간-초과된다-잡아-둔-요청이-앱의-12초-제한과-겹친다-2026-11-05-claude)).

시스템 기록으로 확인된 절전 중단은 대기열의 `retry`와 GitHub의 `pending`으로 남긴다. 기존 15분 뒤 재검사를 유지하며 같은 커밋의 새 78건 검증이 끝나기 전에는 성공으로 올리지 않는다. 절전 증거가 없는 실제 시험 실패·읽을 수 없는 절전 기록·그 밖의 오류는 기존 실패 판정을 유지한다. 저장된 완료 증거가 불완전한 경우도 절전 대기로 바꾸지 않는다.

일일 튜터의 같은 날 저장·새로고침·2분 뒤 복습 흐름은 시험의 한국 시각 정오를 고정한다. 실제 실행 시각이 자정 직전이어도 의도한 같은 학습일을 검사하며, 브라우저 타이머·실제 시험 제한은 계속 흐른다. 실제 한국 자정 뒤에는 전날 도움을 당일 도움으로 세지 않고 전날 기록을 보존해야 하는 별도 회귀를 유지한다. 시험 시간만 고정하며 앱의 날짜 기준은 바꾸지 않는다.

<a id="world-photo-status-fixture"></a>

WORLD의 일반 계정 화면 시험 네 가지(S070·S072·S074·S095)는 내 정보 화면을 열 때 사진 시범의 상태를 확인한다. 합성 계정에는 실제 서버와 같은 `off` 응답을 돌려준다. 이 응답은 지정된 경로의 `POST` 요청에 `action: status`만 있을 때 쓴다. 사진 올리기·동의·다른 경로는 각 시험의 예상하지 않은 요청 검사에 걸린다.

<a id="world-tab-deadline"></a>

### WORLD 두 탭의 계정 분리 시험

S078은 실제 Edge의 두 탭에서 서로 다른 합성 계정으로 로그인한다. 새로고침 뒤 각 탭의 계정, 한쪽 로그아웃 뒤 다른 쪽 계정, 쿠키 속성과 브라우저 저장소를 확인한다. 전체 180초 중 165초를 실행에 쓰고 나머지 15초는 시험이 연 Edge를 정리하는 데 둔다. 실행 한도에 걸리면 당시 단계와 API 상태를 남기고 브라우저 프로세스 트리를 종료한다.

한 탭의 홈 모듈을 보류한 상태에서 그 탭의 새 문서가 자기 계정의 bootstrap 응답을 받는지도 확인한다. 보류를 푼 뒤 각각의 계정과 로그아웃 결과까지 대조한다.

재현할 때는 격리된 리허설에서 첫 탭 생성의 응답이나 새로고침의 `/api/world/bootstrap` 응답 한 건을 34초 늦춘다. 두 경우 모두 실제 계정 검사를 끝내야 한다. 복원 응답의 계정 ID를 바꾸면 계정 대조에서, 탭 생성 응답을 끝까지 보류하면 실행 한도에서 실패해야 한다.

<a id="world-cafe-cleanup"></a>

### WORLD 카페 시험의 종료

S071은 고정된 공개판과 합성 계정으로 카페 진행·새로고침 복원·다섯 번째 방문의 수령까지 확인한다. 90초 안에서 전용 Edge의 정상 종료를 최대 5초 기다리며, 남은 시간이 짧아지면 종료 대기도 줄인다. 응답이 멈추면 그 브라우저의 프로세스 트리를 종료한다. 로컬 HTTP 서버가 닫힌 뒤 `report.json`에 기능 확인 시각과 정리에 걸린 시간, 오류를 기록한다.

페이지 전환은 전체 한도에서 정리 시간을 뺀 남은 시간 동안 문서와 자산의 로드를 기다린다. 각 화면에서는 계정·시도 ID·저장 상태를 확인한다. 새로고침 때 장식 그림 하나가 늦게 도착해도 진행을 복원하고 자산의 HTTP 오류를 확인해야 한다.

같은 고정판의 튜터 검사(S081)도 첫 화면·새로고침·단독 홈 이동에 이 기준을 쓴다. 첫 화면의 그림만 20초 늦춘 리허설에서 HTTP 상태와 튜터 선택, 소유자별 저장·로그아웃 등 10개 기능 확인을 마쳐야 한다.

재현할 때는 브라우저 종료만 지연시킨 경우와 화면 이동을 실패시킨 경우를 따로 검사한다. 전자는 기능 확인 26개와 자원 정리를 모두 마쳐야 한다. 후자에서는 실제 기능 오류가 Node 결과와 보고서에 모두 남아야 한다.

<a id="archive-and-speaking-fixtures"></a>

### 보관 묶음과 말하기 리허설

S007·S008·S009의 합성 저장소는 Windows에서 같은 Git 설치의 실행 파일을 직접 쓸 수 있으면 그렇게 한다. S008은 여섯 가지와 파일을 한 번에 만들고 실제 원격의 35개 ref 중 각 선행 커밋에 닿는 첫 ref를 대조한다. 같은 커밋을 가리키는 ref는 도달 가능성을 한 번만 검사한다.

### 로컬 시험 묶음의 시간 제한

로컬 기본 묶음은 시험 결과가 계속 쌓이면 최대 36분까지 진행한다. 결과 파일이 20분간 늘지 않으면 전용 시험 자식 프로세스를 종료한다. 로그 출력만으로는 시간이 늘지 않는다. 전체 48분 안에 과제와 계정 검사 몫 12분(계정 3분 포함)을 남기고, 일꾼의 50분 상한까지 끝 2분을 원천 대조와 영수증 기록에 둔다. 종료 이유는 `no-test-events` 또는 `deadline`으로 남기고 누락·실패 판정을 보존한다. GitHub와 개별 시험 시간 제한은 종전 값을 쓴다.

### 과거 커밋 재검사와 브라우저 종료

등록된 과거 묶음은 실행 파일과 판정 코드가 확인된 조합에서만 20분 고정 타이머를 위의 진행 감시로 교체한다. 시험 목록과 원천, 개별 제한, 입력, 이벤트 기록기와 판정은 그 커밋 것을 쓴다. 실행한 두 파일의 SHA-256과 입력 해시는 회차의 `profile-watchdog.json`에서 확인한다. 파일 조합이 다르면 해당 커밋의 실행기를 그대로 쓴다.

S049는 로컬 Caddy가 연결을 받을 때까지 최대 30초 기다리고, 실제 HTTP 502와 민감한 주소가 제거된 로그를 확인한다. S080과 S081은 홈·생활 튜터 기능을 확인한 뒤 시험이 띄운 Edge와 HTTP 서버의 종료를 기다려 결과를 쓴다. S071 카페는 기능 확인에 90초를 쓰고 자원 정리에 최대 60초를 더 둔다. 기능 확인 시간이 지나거나 종료를 확인하지 못하면 실패한다.
S010은 원래의 90초 안에서 설치된 Caddy의 버전·설정 변환·검증과 실제 HTTPS 응답을 확인한다. 시작할 때는 연결 거절만 다시 시도한다. TLS 오류, 잘못된 구성, 첫 HTTP 응답의 상태 오류는 즉시 실패한다. HTTP 응답도 같은 한도를 쓰고, 프록시가 반환하는 30초 상류 시간 초과는 실패한다.

튜터 기능 확인은 S080 120초, S081 90초다. S081의 읽기 단추도 남은 기능 시간 안에 실제로 나타나고 눌려야 한다. 기능 확인 뒤에는 두 시험 모두 별도 종료 훅에서 최대 150초 동안 시험의 Edge와 HTTP 서버가 닫히기를 기다린다. 기능 오류, 닫기 오류, 종료 시간 초과는 각각 실패로 남는다.

회귀 시험은 `node --test tests/conditional-qa-historical.test.cjs tests/conditional-qa.test.cjs tests/conditional-qa-retry.test.cjs`로 실행한다.

### 검사 디스크와 마을 재입장

일꾼은 새 검사를 열기 전에 상태 폴더가 있는 디스크의 여유 공간을 확인한다. 15 GiB 미만이면(11-04 유호님 공간 지킴이 B안 — 한 회차가 약 5 GiB를 더 쓰고 여유가 30분 사이 20 GiB 넘게 오르내린다. 전에는 2 GiB) 대기 순서를 유지하고 `last-run.json`의 `diskWait`에 측정값과 시작 기준을 남긴다. 이 대기가 155분을 넘으면 [일꾼 무소식](#local-status-check)으로 빨개져 `ci빨간불`이 한 통 알린다. 다음 5분 회차에서 다시 확인하며, 이미 검증한 결과는 공간을 기다리는 동안에도 게시한다. 파일 쓰기에서 운영체제가 `ENOSPC`를 반환하면 새 전체 검사를 기다린다. 시험에서 관측한 실패와 빠진 항목은 그 회차 영수증에 남긴다.

실행 중 공간이 바닥난 경우에도 원래 실패 영수증을 보존한다. 같은 회차의 Edge 임시 프로필에서 운영체제 오류 0x70과 초기 프로필 생성 실패가 함께 확인되고 다른 실패가 없으면 그 커밋 전체를 다시 검사한다.

WORLD 계정 브라우저 시험은 부모 화면의 애니메이션 프레임이 멎어도 마을 프레임 자체에서 250ms 간격으로 계정 연결을 확인한다. 마을이 접속 거절을 표시하거나 프레임이 닫히면 보호된 요청의 HTTP 상태를 실패 기록에 남긴다. 호스팅 환경의 대기 한도는 180초다.

### 작업본 셋으로 동시에 검증

커밋 하나를 재는 데 PC가 놀아도 6.2분이 걸려 작업본 하나로는 하루 232건이 천장이다. 바쁜 날 push는 그만큼 들어온다(10-30 232건, 11-03 227건). 11-03에 일꾼은 하루 1,440분 중 1,297분을 검증에 쓰고도 151건만 끝냈다. 파일 동시 실행을 늘려도 빨라지지 않는다 — 가장 긴 파일(`town-check-browser` 280초)이 이미 기본 묶음 시간을 정한다.

그래서 `slots/<번호>/`에 검증 작업본을 더 둔다(11-05 현재 2 · 3번). 만드는 것은 번호마다 한 번이고 `node tools/conditional-qa/inputs.cjs slot <상태 폴더> <번호>`다(작업본·Talk 짝·`node_modules`로 약 6.7GB, 입력 묶음은 junction으로 함께 쓴다). 일꾼은 `slot.json`이 있는 슬롯만 쓰고, 끄려면 그 파일을 지운다. 슬롯은 후보가 아니다 — 덧씌운 파일이 없고 `candidate: false`라 같은 영수증 대조를 받고, `release`와 공간 지킴이의 후보 정리가 건드리지 않는다. 회차 폴더는 슬롯이 어디든 `runs/` 한곳이다. 시험이 보는 바이트가 달라진 커밋은 전처럼 각자의 전체 79건을 돌리고([문서만 바꾼 커밋](#tested-tree)은 앞 통과를 잇는다), 차례를 고르는 규칙과 게시·실패·재검사 기준도 같다. 어느 작업본에서 돌았는지는 항목의 `slot`, 열 때의 CPU는 `cpuAtStart`에 남는다.

검증을 여는 때는 부하로 정한다. 부하가 걸리면 시험이 시간 한도까지 늘어나고 그 실패는 사람이 볼 때까지 남기 때문이다 — 조용할 때 3초인 S078이 CPU 100%에서 165초를 넘겼고, 11-04에 포화된 PC에서 연 회차 여섯 가운데 다섯이 18~40분을 쓰고 시간 초과로 실패했다(옛 커밋 · 새 커밋 모두, 우선순위를 올려도 마찬가지). 첫 검증은 CPU가 85% 아래이고 빈 메모리가 3 GiB 이상인 채로 2분 이어져야 연다. 포화가 몇 시간 가도 억지로 열지 않는다(한때 30분 기다린 뒤 열었지만 실패만 늘렸다). 돌아가는 검증 옆에 하나 더 여는 것은 CPU 70% 아래 · 빈 메모리 6 GiB 이상이 2분 이어질 때이고, 앞 검증을 연 지 1분이 지나야 재기 시작한다 — 그 전 읽기에는 앞 검증의 부하가 들어 있지 않다. 게시만 남은 결과와 지정한 커밋 한 건은 기다리지 않는다. 30초마다 다시 보며 기다린 횟수는 `last-run.json`의 `roomHeld`, 끝까지 기다린 회차는 `holdingAtCpu`에 남는다. 이 조건은 기다리기만 하고 시험 한도나 판정은 바꾸지 않는다.

작업본 셋은 조용할 때 서로 늦추지 않는다. 11-05 07:02~08:08 일반 회차에서 21건이 모두 통과했고, 건당 6.3~6.9분, 셋이 함께 돌 때 CPU 평균 30% · 최대 43%, 빈 메모리 최소 28.9 GB였다. 그런데 시간당 19.3건에서 멈춘다. 막는 것은 작업본 수가 아니라 여는 간격이다(중앙 2.8분 — 조용함 2분에 30초 확인과 열 때 작업본을 옮기는 시간이 더해진다). 그래서 넷째는 두지 않는다. 더 필요하면 둘째 이후의 조용함 대기부터 줄인다. 지정한 커밋을 줄지어 재는 동안에는 작업본 하나만 돈다(같은 날 08~10시, CPU 14~20%에 시간당 6.6건). 문턱을 올리지 않는 근거는 회차 동안의 평균 CPU별 통과다(회차 104건, 코드 탓 실패를 뺌): 70% 아래 74/74, 70~85% 4/5, 85~95% 12/14, 95% 이상 2/6.

기다리는 회차는 15분 뒤 끝나 다음 회차가 master를 다시 받는다. 일꾼은 기다리는 동안 한 시간에 한 번 아직 검증하지 않은 가장 새 커밋에 `pending`(「Waiting for room on the local PC; not verified yet」)을 올린다. 그래서 [멈춤 감시](#local-status-check)의 155분은 PC가 꺼지거나 일꾼이 멈춘 때만 울리고, 포화가 오래가면 72시간 넘은 대기가 울린다. 통과가 아니고 결과가 있는 커밋은 건드리지 않는다.

디스크 여유 15 GiB 조건은 검증마다 본다. 먼 커밋으로 옮기는 `git checkout`은 바쁜 PC에서 2분을 넘겼고(11-04), 끊기면 반쯤 쓴 작업본이 남아 뒤 커밋을 모두 막았다. 그래서 checkout 한도를 30분으로 늘리고, 다음 검증을 열 때 남은 잠금과 수정을 치운 뒤 `checkout-repairs.jsonl`에 남긴다. 추적 파일을 고친 시험은 그 커밋의 영수증에서 실패로 남고, `run.cjs`는 커밋과 다른 작업본을 여전히 거절한다. 한 작업본이 시험 결과가 아닌 오류(checkout·네트워크 등)로 끝나면 그 회차에는 다시 쓰지 않아, 고장 난 작업본이 대기열을 연달아 실패로 돌리지 않는다. 일꾼은 모든 검증이 끝난 뒤에야 잠금을 푼다.

상태 파일을 바꿔 쓸 때 누가 그 파일을 쥐고 있으면(`Get-Content`로 읽는 중 · 검사 · 색인) 3초까지 기다렸다 다시 한다. `queue.json` 저장이 끝내 실패해도 결과는 바뀌지 않는다. 메모리의 상태가 맞고 다음 저장이 따라잡으며, 재시작하면 같은 커밋을 다시 볼 뿐이다. 못 저장한 까닭은 `last-run.json`의 `queueNotSaved`에 남는다(11-05 `4db22931`: 통과를 올린 뒤의 저장 실패가 11초 뒤 실패 상태로 뒤집었다).

- **매 회차가 다시 증명한다.** 실제 검증의 모든 Node 프로세스에 [`read-trace.cjs`](read-trace.cjs)가 붙어, 뺀 경로를 열거나 재거나 있는지 묻거나 `docs` · 남긴 곳의 상위 폴더를 나열하면 그 자리에서 적는다. 적힌 것이 있으면 79건이 다 통과해도 그 회차는 실패다(`result.json`의 `touchedOutside`). 없는 파일은 시험을 깨뜨리고, 없는지 묻기만 해 조용히 덜 보는 시험은 이 기록이 잡는다. Node 밖에서 읽는 Chromium · Caddy · ffmpeg는 파일이 없어 깨지는 쪽으로 드러난다. 새 시험이 문서를 읽게 되면 그 경로를 목록에 더한다.
- **잇기.** 첫 부모에서 뺀 경로만 바뀐 커밋은 부모의 완전한 통과를 잇는다. 부모의 저장된 영수증을 다시 대조한 뒤 `runs/<커밋>-<시각>/result.json`을 쓰고(`carriedFrom`에 실제로 잰 커밋과 부모), 상태 줄은 `PASS n/n manifest=` 그대로 올린다. 옛 커밋의 얼어 있는 `wait-local.cjs`가 그 글자를 그대로 비교하기 때문이고, 상태의 링크는 실제로 잰 커밋으로 간다. 작업본도 부하 대기도 쓰지 않는다. 호스트 실행을 깨우는 수를 맞추려고 한 회차에 60건까지만 잇고, 나머지는 다음 회차로 넘긴다. 통과를 올리는 GitHub 호출이 실패하면 실패 상태를 올리지 않고 다음 회차에 다시 올린다(직접 잰 커밋도 같다).
- **통과만 잇는다.** 부모가 실패면 그 커밋은 직접 잰다. 부모 영수증을 못 읽어도 직접 잰다. `retry.cjs`로 부탁한 재검사와 [지정한 한 건](#registered-verification)도 직접 잰다. 부모가 아직이면 차례를 쓰지 않고 기다려(`awaitsParent`), 최신 차례는 직접 잴 필요가 있는 가장 새 커밋으로 간다. `last-run.json`의 `carried` · `awaitingParent`로 본다.
- **그대로인 것.** 호스트 40건과 `wide-tests`는 문서만 바꾼 커밋에서도 돈다. 79건 목록 · 통과 기준 · 시험 한도 · 부하 조건은 그대로다. 코드가 바뀐 커밋은 모두 직접 잰다.

잇는 커밋은 Talk 입력과 시각도 부모 회차의 것을 쓴다. 지금도 대기 탓에 커밋과 검증 사이에 며칠이 뜨므로 그 커밋이 그 시각의 Talk를 본다는 보장은 원래 없다.

### 러너를 쥐지 않는 동안의 감시

`local-coverage`는 11-04부터 기다리지 않고 자기 run을 취소한다. 취소는 빨강이 아니어서, 옛날처럼 155분 뒤 빨개지는 신호가 없어졌다. PC가 멈춰도 알림이 없고, 일꾼 차례가 뒤섞여 오래된 커밋의 실패 run은 더 새 초록 run에 가려진다. `conditional-qa-local`(`local-status.cjs`)이 이 빈자리를 맡는다. `conditional-qa` run이 끝날 때마다 돈다. 이 저장소의 예약 실행은 몇 시간씩 늦어(11-03 실측 5~10시간, 15분 예약은 4시간 동안 0회) 30분 예약은 뒷받침일 뿐이다. first-parent를 활성화 커밋까지, 또는 경보가 날 수 있는 범위 너머까지 읽고, 각 커밋 판 목록의 정확한 `PASS n/n manifest=`만 통과로 센다. 경보는 커밋된 지 72시간 안의 대기나 올라온 지 24시간 안의 실패에서만 나므로, 가장 오래 읽은 커밋 50개(한 쪽)가 모두 커밋된 지 96시간이 넘었고 끝난 상태(통과, 또는 24시간 지난 실패)면 거기서 멈춘다. 그 50개 안에 아직 대기하거나 새로 실패한 커밋이 있으면 더 읽는다 — 일꾼은 한 차례 걸러 가장 오래된 준비 커밋을 잡으므로 그런 줄 뒤에 대기가 숨어 있지 않다(11-08, 1,000커밋 창이 11-06 00:28에 차서 그 뒤 run이 고장 없이 모두 빨갰다). 상한은 3,000커밋이고, 11-08에는 900커밋 · 26초에 끝났다. 96시간보다 오래된 커밋을 `retry.cjs`로 다시 재 또 실패하면 그 커밋이 끝난 줄 뒤에 있을 때는 못 볼 수 있어, 재검사를 건 세션이 영수증으로 본다.

빨강은 다음 다섯 가지다. 새 실패(올라온 지 24시간 안, 커밋마다 이름이 달라 새 실패만 새로 알린다), 판 불일치, 대기가 있는데 일꾼이 155분 동안 아무 상태도 안 올린 때(`WAIT` 표시는 일꾼 활동이 아니고, [기다린다는 알림](#local-parallel)은 일꾼 활동이다), 커밋된 지 72시간 넘은 대기, 읽기가 활성화 커밋에도 96시간 지난 끝난 줄에도 닿지 못할 때. 24시간이 지난 실패는 빨강에서 빠질 뿐 커밋 상태와 로그의 「kept until a retry passes」 줄에 남고, `retry.cjs`로 다시 재기 전에는 통과가 되지 않는다. 호스트 40건은 커밋마다 돌고, 로컬 79건은 시험이 보는 바이트가 달라진 커밋마다 돈다([기준](#tested-tree)). 이어받은 통과도 같은 줄이라 여기서는 통과로 센다.

회귀는 `node --test tests/conditional-qa.test.cjs tests/conditional-qa-tested-tree.test.cjs tests/conditional-qa-retry.test.cjs tests/conditional-qa-diagnosed.test.cjs tests/conditional-qa-reregister.test.cjs tests/ci넓은시험.test.js`다. 이 자동화는 등록된 119건의 지속 검증이며, 새 보안 감사나 운영 접근 권한 전체의 재점검을 대신하지 않는다. 최초 실제 실행과 원격 CI 결과는 비공개 설치·실행 영수증과 해당 커밋의 GitHub Checks에서 확인한다.

<a id="diagnosed-failures"></a>

### 실패 읽기와 원인을 밝힌 구간

`conditional-qa-local`의 빨강은 커밋 하나가 깨졌다는 뜻이 아니다. 24시간 안의 로컬 실패를 run마다 다시 세므로, 실패 네 건이면 그동안 도는 run이 모두 빨갛다(11-05 48회 연속). 그래서 11-05부터 일꾼은 실패 상태에 시험 번호를 올린다(`FAIL 78/79: S070`). 번호는 공개된 `cases.json`의 것만이고, 소스·입력이 그대로이고 모든 행이 있는 영수증에서만 쓴다. 그 밖의 끝은 예전 문구를 쓴다. 알림과 CI 로그에는 번호와 시험 파일이 찍힌다. 실패 내용은 이 PC의 `~/security-audit-skill/SYNK-conditional-qa/runs/<커밋>-*/result.json`에서 `phases[].unexpectedFailures`를 읽는다.

여러 시험이 한 원인으로 함께 실패한 구간은 `exactCases: true`로 기록할 수 있다. [사진 시범의 상태 응답](#world-photo-status-fixture)처럼 이 옵션을 쓸 때는 원래 커밋의 시험 수와 실패 개수, 전체 번호가 모두 맞아야 반복 경보를 멈춘다. 번호가 빠지거나 하나라도 더 생기면 경보가 울린다.

커밋의 시험은 그 커밋에 고정되어 있다. 한 구간에서 시험이 틀렸으면 그 구간의 커밋은 일꾼이 닿을 때마다 하나씩 실패하고, 다시 재어도 통과할 수 없다. 원인을 밝힌 구간을 [`diagnosed.json`](diagnosed.json)에 적으면 그 구간·그 번호만 들어맞는 실패는 빨강에서 빠진다.

- 빠지는 것은 알림뿐이다. 커밋의 실패 상태, 로그의 「kept until a retry passes」, 그 커밋 run의 빨강은 그대로이고 통과로 세지 않는다. 로그에 `diagnosed, no alert:`로 까닭과 함께 남는다.
- 번호가 하나라도 더 있거나, 번호가 잘렸거나, 예전 문구면 빨강이다. 구간 끝(`fixedBy`)부터는 같은 번호도 빨강이다. master 줄에 없는 구간은 그 자체가 빨강이다. 다만 읽기가 [96시간 창](#local-status-check)에서 멈췄을 때 두 끝이 모두 창보다 오래된 구간은 설명할 실패가 없어 건너뛰고, `from`만 창 밖인 구간은 읽은 가장 오래된 커밋까지로 본다(11-08). 읽기가 `fixedBy`에서 딱 끝나면 읽은 커밋에 그 구간이 없으니 역시 건너뛴다 — 읽기는 50커밋 단위로 끝나 구간마다 50번에 한 번 걸렸다(11-08 `acd9aba92` 세 번 빨강, 다음 push 초록). `from`이 창 안인데 `fixedBy`가 없으면 여전히 빨강이다.
- 적는 조건: 실패를 재현해 원인을 찾았고, 뒤 커밋에서 그 시험이 통과했다. 부하·환경 때문인 실패는 적지 않고 `retry.cjs`로 다시 잰다. 예외는 일꾼 입력이 낡아 한 구간이 같은 번호로 줄곧 실패한 경우다. 입력을 [다시 등록](#reregister-inputs)하고 그 번호가 통과한 뒤 `exactCases: true`로 적고, `fixedBy`는 다시 등록한 뒤 처음 올라온 master 커밋으로 한다. 그 구간 전체를 `retry.cjs`로 다시 재면 대기열의 오래된 차례를 그 수만큼 차지해(11-08 205건, 바쁜 날 시간당 몇 건) 24시간 창보다 늦게 끝나고 가장 오래된 대기를 72시간 한도 쪽으로 민다.
