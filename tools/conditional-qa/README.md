# 조건부 시험의 지속 검증

2026-11-01 유호님 요청: 따로 검증했던 113건을 코드 변경 뒤에도 빠짐없이 자동 검증한다. 이전 수동 검증은 [101건과 추가 12건의 근거](../../docs/_ops/qa/ci-conditional-101-20261101/README.md)에 있다.

`conditional-qa.yml`은 master의 각 push에 세 관문을 건다. 파일과 시험 이름이 일치하는 실제 Node 시험 이벤트가 정확히 한 번 통과해야 한다. skip/todo, 이름 변경, 누락, 중복, 프로세스 실패·시간 초과는 실패다. 기존 syntax/wide CI에 처음 생긴 조건부 제외도 등록되지 않았으면 실패한다. 새 제외를 추가할 때에는 재현 입력과 자동 실행 경로를 함께 등록한다. 등록된 이름을 바꿀 때에는 같은 ID의 이름과 시험을 함께 바꾼다.

모든 실행 경로는 영수증 폴더 아래에 전용 TEMP/TMP를 만들고 Windows의 실제 경로로 고정한다. hosted runner의 `RUNNER~1` 별칭이 Git·PowerShell의 긴 경로와 달라지는 환경 문제를 시험으로 오인하지 않게 한다. 검사할 커밋과 다른 추적 파일 수정이 있으면 후보 표시가 없는 실행은 거절한다.

`worker.cjs`는 운영 사본에서 실행되며 별도 관리 체크아웃으로 신뢰하는 origin/master 커밋을 검증한다. 공용 작업본·운영 코드·운영 DB를 시험용으로 수정하지 않는다. PR/fork는 로컬 실행 대상이 아니다. 활성화 시점 이후 master 커밋은 순서대로 대기열에 보존한다. 한 회차는 검증 하나를 마칠 때마다 master를 다시 받아 대기열이 빌 때까지 차례로 처리하되, 새 검증은 회차 시작 뒤 60분 안에서만 연다(검증 하나가 길면 50분이고, 예약 작업과 숨김 실행이 2시간에 회차를 끊는다). 같은 회차에서 한 커밋은 한 번만 시도한다(11-02, 이전에는 회차마다 세 커밋까지만 재어 회차 사이가 비었다). 중단된 실행과 네트워크 장애는 다시 시도하며, 시험 자체의 실패는 실패로 남는다. 실행 도중 PC가 절전에 들어갔다 깨어난 회차(시스템 기록 Kernel-Power 42·107이 그 회차 시간 안에 있음)는 중단으로 보고 다시 잰다 — 11-01 덮개 절전 10분에 걸린 회차는 시험 둘이 606초로 끝났다. 기록을 읽지 못하면 절전이 없던 것으로 본다. 새 코드의 성공으로 과거 실패를 덮지 않는다.

이미 끝난 결과의 게시를 먼저 하고, 새 검증은 최신 master·나머지 최근 커밋 차례와 가장 오래된 대기 차례를 번갈아 고른다(11-02 과거 대기 전체 확인 후속). 처음에는 최신 차례로 시작하고 다음 차례는 `queue.json`의 `nextTurn`에 저장해 회차 종료·일꾼 재시작 뒤에도 이어 간다. 게시만 다시 하는 항목은 검증 차례를 소비하지 않는다. 새 push가 계속 들어와도 두 번 중 한 번은 오래된 준비 항목을 처리하며, 실행 중인 시험·과거 실패 증거는 그대로 보존한다. GitHub의 로컬 결과 대기는 155분, 해당 job은 160분이다. 진행 중인 검증·오래된 대기 한 차례·최신 검증이 각각 최대 50분이고 예약 간격이 5분임을 반영한다. 시험 자체의 한도·78건 통과 기준은 바꾸지 않으며, 시간이 끝났거나 아직 검증 중이면 통과시키지 않는다.

로컬 원문과 보관 fixture는 저장소 밖 `~/security-audit-skill/SYNK-conditional-qa`에 해시로 등록한다. `inputs.json`에는 이전 감사에서 보존한 출처·해시가 있고, `blobs/`에는 해당 바이트만 둔다. 추적 중인 현재 앱 소스가 과거 fixture보다 우선한다. Talk 실행·과제 참조판은 이전 검증의 고정 입력이고, 범위 표 비교는 매 실행 현재 Talk origin/master를 확인한다. 현재 Rust를 검사할 때 과거 WASM을 대신 쓰지 않는다. 의존성은 격리된 폴더의 lock 파일로 `npm ci --ignore-scripts` 설치한다.

각 로컬 실행은 `runs/<commit>-<time>/`에 원래 이벤트, TAP, 화면 증거, 커밋·목록·입력 해시와 결과를 남긴다. 회차마다 60MB 남짓이 쌓여(11-02 하루 100회 넘게) 공간 지킴이가 하루 한 번, 통과(`ok`·`passed == expected`)하고 하루 지난 회차의 프로필 폴더 안 임시(시험 DB·`*_qa_out`·`*_run`·화면 캡처·`temp`·`server.log`)를 지운다 — 맨 위 `result.json`·`started.json`·`runner.log`와 프로필의 `tests.tap`·`events.jsonl`·`process.log`는 남고, 실패·결과 없는 회차는 그대로 둔다(11-02 유호님 「세 가지 다 해」, 일꾼은 지난 회차 안쪽을 다시 읽지 않는다). 시험 전후 소스와 입력도 대조한다. GitHub에는 개인 자료 없이 해당 커밋의 `conditional-qa/local` 상태와 통과 수·목록 해시만 올린다. 같은 커밋의 검증이 끝나기 전에는 녹색이 되지 않는다. PC 꺼짐·로그아웃·입력 손상·도구 부재는 미완료/실패이며 과거 성공으로 대체하지 않는다. CI 대기가 끝난 뒤 검증이 완료되면 로컬 대기 단계만 실패한 run을 다시 돌린다. 다른 CI 실패를 가리지 않는다.

Windows 작업 `SYNK 조건부 시험`은 현재 사용자의 일반 권한·대화형 로그온으로 5분마다 시작한다. 작업 우선순위는 4(일반 CPU·I/O·메모리)다 — 작업 스케줄러 기본 7은 BelowNormal CPU·낮은 I/O·메모리 우선순위 2이고 그 아래 시험·시험 서버·Edge가 모두 물려받아, 바쁜 PC에서 브라우저 시작만 30초를 넘기고 평소 4초짜리 시험이 240초를 넘겼다(11-02). 일꾼도 시작할 때 CPU 우선순위가 일반보다 낮으면 일반으로 올린다. 중복 실행은 무시하며, 다시 켜지면 미실행 회차를 시작한다. 실행 명령은 운영 사본의 `tools/숨김실행.py` → `tools/conditional-qa/worker.cjs`다. 새 개인 토큰·관리자 권한·GitHub 자체 호스팅 러너는 만들지 않는다. 설치 영수증은 `installation.json`, 마지막 상태는 `last-run.json`, 전체 대기열은 `queue.json`이다. 보관된 원래 감사 자료는 건드리지 않는다.

설치는 `install.cjs --state <비공개 폴더> --ops <운영 사본> --pythonw <pythonw.exe> --first <첫 검증 커밋>`으로 미리 보고 같은 명령에 `--apply`를 붙인다. 최초 입력 등록은 `inputs.cjs`의 `provision`으로 이전 감사 manifest와 원문 해시를 검증한 뒤 수행한다. 상태 폴더는 공용 저장소 안에 두지 않는다. Codex 앱의 `%LOCALAPPDATA%` 가상화와 작업 스케줄러의 실제 경로가 달라질 수 있어 사용자 프로필 아래 명시적 경로를 쓴다.

운영 확인은 `node tools/conditional-qa/worker.cjs --state <비공개 폴더>`로 같은 회차를 실행할 수 있다. 이미 도는 회차가 있으면 잠금을 지우지 말고 완료를 기다린다. 입력이나 실행 도구 문제가 해결되면 인프라 실패는 다음 재시도에서 검증한다. 시험 자체가 실패하면 원인을 고친 새 코드로 다시 확인한다. 예약을 끄더라도 CI 로컬 단계는 미완료로 남으며 검증을 생략해 통과시키지 않는다.

과거 `failed` 항목은 저절로 성공 처리하거나 계속 재시도하지 않는다. 원인을 고친 뒤 같은 커밋을 다시 검사하려면 `node tools/conditional-qa/retry.cjs --state <비공개 폴더> --reason "확인한 원인과 재검사 이유" <커밋 SHA...>`로 미리 보고 `--apply`로 재등록한다(11-02 유호님 과거 대기·오류 전체 확인 요청). 실행 중인 일꾼이 있으면 재등록도 거절하므로 회차가 끝난 뒤 실행한다. 원래 실패 결과는 그대로 두고 `queue.json`의 `history`와 `retry-history/`에 원래 항목·결과 해시·이유를 남긴다. 대기열은 `retry`로 바뀔 뿐이며 GitHub 성공은 같은 커밋의 새 78건 영수증이 완전할 때에만 기존 일꾼이 올린다. 로컬 통과와 GitHub 전체 job의 복구도 각각 확인한다.

말하기 기능 시험의 페이지 전환은 `qa/page-ready.mjs`로 해당 시험의 `t.signal`·기존 15분 전체 한도를 따른다. 별도의 Playwright 기본 30초가 먼저 종료하던 실패를 분리했으며 HTTP 오류·연결 거절은 재시도하지 않고 실패한다. 시험이 중단되면 전환 중인 페이지를 닫고, 시험 서버 종료까지 확인한 뒤 임시 파일을 정리한다. 전환별 HTTP 상태·경과 시간·실패는 그 실행의 `synk_speaking_qa_out/result.json`에 남긴다. 이 기능 시험은 페이지 응답 속도의 성능 기준으로 쓰지 않는다.

과제 화면의 로딩 캡처는 합성 서버 응답을 보류하는 동안 Playwright 시계도 잠시 멈춘다. 이미지 합성이 오래 걸렸다는 이유로 실제 앱의 12초 요청 제한에 걸리던 시험 오류를 분리한다. 캡처 중 1ms 타이머가 멈춰 있고 재개 뒤 다시 도는지 검사하며, 별도의 12초 초과 요청은 여전히 오류로 바뀌고 다시 불러오기로 복구되어야 한다. 실제 앱의 제한·오류 판정은 바꾸지 않는다. 캡처 경과 시간은 해당 실행의 `captureTimes`에 남긴다.

회귀는 `node --test tests/conditional-qa.test.cjs tests/conditional-qa-retry.test.cjs tests/ci넓은시험.test.js`다. 이 자동화는 등록된 113건의 지속 검증이며, 새 보안 감사나 운영 접근 권한 전체의 재점검을 대신하지 않는다. 최초 실제 실행과 원격 CI 결과는 비공개 설치·실행 영수증과 해당 커밋의 GitHub Checks에서 확인한다.
