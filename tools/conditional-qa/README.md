`conditional-qa.yml`은 master의 각 push에 세 관문을 건다. 파일과 시험 이름이 일치하는 실제 Node 시험 이벤트가 정확히 한 번 통과해야 한다. skip/todo, 이름 변경, 누락, 중복, 프로세스 실패·시간 초과는 실패다. 기존 syntax/wide CI에 처음 생긴 조건부 제외도 등록되지 않았으면 실패한다. 새 제외를 추가할 때에는 재현 입력과 자동 실행 경로를 함께 등록한다. 등록된 이름을 바꿀 때에는 같은 ID의 이름과 시험을 함께 바꾼다.

모든 실행 경로는 영수증 폴더 아래에 전용 TEMP/TMP를 만들고 Windows의 실제 경로로 고정한다. hosted runner의 `RUNNER~1` 별칭이 Git·PowerShell의 긴 경로와 달라지는 환경 문제를 시험으로 오인하지 않게 한다. 검사할 커밋과 다른 추적 파일 수정이 있으면 후보 표시가 없는 실행은 거절한다.

`worker.cjs`는 운영 사본에서 실행되며 별도 관리 체크아웃으로 신뢰하는 origin/master 커밋을 검증한다. 공용 작업본·운영 코드·운영 DB를 시험용으로 수정하지 않는다. PR/fork는 로컬 실행 대상이 아니다. 활성화 시점 이후 master 커밋은 순서대로 대기열에 보존한다. 한 회차는 검증 하나를 마칠 때마다 master를 다시 받아 대기열이 빌 때까지 차례로 처리하되, 새 검증은 회차 시작 뒤 60분 안에서만 연다(검증 하나가 길면 50분이고, 예약 작업과 숨김 실행이 2시간에 회차를 끊는다). 같은 회차에서 한 커밋은 한 번만 시도한다(11-02, 이전에는 회차마다 세 커밋까지만 재어 회차 사이가 비었다). 중단된 실행과 네트워크 장애는 다시 시도하며, 시험 자체의 실패는 실패로 남는다. 실행 도중 PC가 절전에 들어갔다 깨어난 회차(시스템 기록 Kernel-Power 42·107이 그 회차 시간 안에 있음)는 중단으로 보고 다시 잰다 — 11-01 덮개 절전 10분에 걸린 회차는 시험 둘이 606초로 끝났다. 기록을 읽지 못하면 절전이 없던 것으로 본다. 새 코드의 성공으로 과거 실패를 덮지 않는다.

이미 끝난 결과의 게시를 먼저 하고, 새 검증은 최신 master·나머지 최근 커밋 차례와 가장 오래된 대기 차례를 번갈아 고른다(11-02 과거 대기 전체 확인 후속). 처음에는 최신 차례로 시작하고 다음 차례는 `queue.json`의 `nextTurn`에 저장해 회차 종료·일꾼 재시작 뒤에도 이어 간다. 게시만 다시 하는 항목은 검증 차례를 소비하지 않는다. 새 push가 계속 들어와도 두 번 중 한 번은 오래된 준비 항목을 처리하며, 실행 중인 시험·과거 실패 증거는 그대로 보존한다. 진행 중인 검증·오래된 대기 한 차례·최신 검증이 각각 최대 50분이고 예약 간격이 5분이어서 [일꾼 무소식 한도](#local-status-check)는 155분이다. 시험 자체의 한도·통과 기준은 바꾸지 않으며, 아직 검증 중이면 통과시키지 않는다.

로컬 원문과 보관 fixture는 저장소 밖 `~/security-audit-skill/SYNK-conditional-qa`에 해시로 등록한다. `inputs.json`에는 이전 감사에서 보존한 출처·해시가 있고, `blobs/`에는 해당 바이트만 둔다. 추적 중인 현재 앱 소스가 과거 fixture보다 우선한다. Talk 실행·과제 참조판은 이전 검증의 고정 입력이고, 범위 표 비교는 매 실행 현재 Talk origin/master를 확인한다. 현재 Rust를 검사할 때 과거 WASM을 대신 쓰지 않는다. 의존성은 격리된 폴더의 lock 파일로 `npm ci --ignore-scripts` 설치한다.

GitHub 쪽 `local-coverage`는 호스트 시험이 통과한 뒤 그 커밋의 로컬 결과를 한 번만 읽는다. 통과면 초록, 실패면 빨강이고, 아직이면 대기 상태를 남기고 자기 실행을 취소해 러너를 놓는다. 취소는 통과가 아니며 빨강으로도 세지 않는다. 일꾼이 검증을 마치면(통과든 실패든) `resumeWaitingWorkflow`가 그 실행을 다시 돌린다. 같은 run ID에 attempt만 늘어, 커밋별 대조는 같은 실행의 마지막 결론을 본다. 예전에는 이 작업이 최대 155분을 폴링하며 러너를 잡고 있어, 하루 100회 넘는 push에서 계정의 동시 작업 한도가 차고 Pages 배포까지 밀렸다(11-04).

다시 돌리는 기준은 셋이다. 호스트 작업이 실제로 실패한 실행은 빨강 그대로 둔다. 손으로 취소돼 돌지 못한 호스트 작업은 그 커밋의 영수증에 필요하므로 함께 다시 돌린다. 로컬 결과가 나온 뒤에만 돌리므로 옛 판 커밋의 `local-coverage`도 곧바로 끝난다. 로컬 실패는 아직 기다리는 실행만 깨워 빨강으로 바꾸고, 이미 빨간 실행은 건드리지 않는다. 신호(`queue.json`의 `resumePending`)는 실행이 정리될 때까지 남아 회차 시작과 검증 사이마다 오래 안 본 것부터 10건씩 다시 보므로, 정리되지 않는 커밋이 있어도 다른 커밋이 밀리지 않는다. 회차를 시작할 때 최근 취소 실행 300개도 훑어, 로컬 결과가 있는데 취소로 남은 커밋을 attempt마다 한 번 다시 본다(`checkedRun`). 같은 실행은 attempt 6부터, 그리고 GitHub가 거절하는 첫 실행 뒤 30일부터 다시 돌리지 않는다(이때 실행은 닫히지 않은 채로 남고 결과는 커밋 상태에 있다). 실행이 없는 커밋은 깨울 것이 없다(나중에 생긴 실행은 게시된 결과를 스스로 읽는다). 이 커밋의 목록과 맞지 않는 `success`는 대기가 아니라 빨강이다. 게시에 실패한 로컬 실패는 대기로 읽히므로 회차 시작과 검증 사이마다 다시 게시하고, 그 뒤에 실행을 깨운다. 자기 취소는 GitHub가 단계를 멈추기까지 84초쯤 걸리고(11-04 실측), 5분 안에 멈추지 않으면 그 작업은 실패로 끝난다. GitHub API 오류는 세 번까지 다시 부르고, 그래도 안 되면 그 작업은 실패한다(실패는 통과가 아니고, 로컬 통과 뒤 일꾼이 다시 돌린다).

각 로컬 실행은 `runs/<commit>-<time>/`에 원래 이벤트, TAP, 화면 증거, 커밋·목록·입력 해시와 결과를 남긴다. 회차마다 70MB 남짓이 쌓여, 일꾼이 통과(게시까지 끝남)한 회차의 프로필 폴더 안 임시(시험 DB·`*_qa_out`·`*_run`·화면 캡처·`temp`·`server.log`)를 곧바로 지운다(11-04, [동시 검증](#local-parallel)이 하루 300회를 넘으면 하루 21GB라 C: 여유가 못 버틴다) — 맨 위 `result.json`·`started.json`·`runner.log`와 프로필의 `tests.tap`·`events.jsonl`·`process.log`는 남고, 실패·결과 없는 회차는 그대로 둔다(일꾼은 지난 회차 안쪽을 다시 읽지 않는다). 일꾼이 끊겨 남은 것은 공간 지킴이가 하루 한 번 같은 규칙으로 지운다(11-02 유호님 「세 가지 다 해」). 시험 전후 소스와 입력도 대조한다. GitHub에는 개인 자료 없이 해당 커밋의 `conditional-qa/local` 상태와 통과 수·목록 해시만 올린다. 같은 커밋의 검증이 끝나기 전에는 녹색이 되지 않는다. PC 꺼짐·로그아웃·입력 손상·도구 부재는 미완료/실패이며 과거 성공으로 대체하지 않는다. 검증이 끝나면 위 기준으로 그 커밋의 실행을 다시 돌리고, 호스트 작업의 실제 실패를 가리지 않는다.

고친 시험을 예약 일꾼 밖에서 미리 재 보는 **후보 사본**은 `inputs.cjs`의 `withCandidate({ original, state, commit, overlay }, run)`(만들고 → `run(context)` → `finally`에서 풂)이 기본이고, 직접 다룰 때는 `candidate(...)`로 만든다 — 일꾼 상태의 설정·입력 목록을 옮기고 `blobs/`는 junction으로 함께 쓰며, 준비 전에 임시 `context.json`(`candidate: true`)부터 적어 clone·fetch·`npm ci`가 끊겨도 풀 수 있다. 작업본·Talk 짝·`node_modules`로 하나 6.4GB라(11-02 GPT CI 백로그 수리가 끝난 후보 둘을 남겨 25분 사이 10.6GB) 결과를 상태 폴더 **밖** 회차 폴더(`<이름>-run/`의 TAP·`candidate-result.json`·로그)에 쓰고, 끝나면 `node tools/conditional-qa/inputs.cjs release <후보 상태>`(먼저 `--preview`)로 푼다. `release`는 일꾼 상태(`installation.json`·`queue.json`·`runs/`가 있거나 `candidate`가 아님)를 거절하고, 안에서 시험·프로세스가 쓰는 중이면 이름 바꾸기가 막혀 거절한다. git 객체·고정 blob(경로와 해시가 둘 다 같은 것만)·lock 설치로 다시 만들 수 없는 파일(덧씌운 시험 파일, 작업본 안에 생긴 출력, 바뀐 고정 입력)은 `kept/`로 옮기고, 공유 `blobs/`와 짝 작업본 같은 junction은 끊기만 하고 그 안으로 걷지 않으며, 지운 양·옮긴 것·못 지운 것을 `released.json`에 남긴다. 지울 폴더마다 `<이름>.releasing`으로 옮긴 뒤 훑고, 그 폴더의 `kept/`를 다 옮기면 폴더 안에 `.cqa-scanned`를 남기고(지울 때 맨 끝에 지움) 지운다 — 끊긴 뒤 다시 부르면 표식이 있는 폴더는 지우기만, 없는 폴더와 새로 옮긴 폴더는 처음부터 훑는다. 고정 입력은 `context.json`과 `inputs.json` 둘에서 읽어 준비가 끝나지 않은 후보도 같게 가린다. 한 번에 하나만(`releasing.lock`, 죽은 프로세스의 잠금은 넘겨받음), 잠긴 파일이 남으면 `released.json` 대신 `release-left.json`을 남겨 다음 호출이 마저 지운다. 풀거나 푸는 중인 상태는 `prepare`가 다시 쓰지 않는다. 부르지 않고 남은 후보는 공간 지킴이가 점검(30분)마다, 상태 폴더와 옆 회차 폴더(`<이름>-…`)가 두 시간 넘게 그대로이고 명령줄에 이름이 없는 것만 운영 사본의 같은 `release`로 푼다.

Windows 작업 `SYNK 조건부 시험`은 현재 사용자의 일반 권한·대화형 로그온으로 5분마다 시작한다. 작업 우선순위는 4(일반 CPU·I/O·메모리)다 — 작업 스케줄러 기본 7은 BelowNormal CPU·낮은 I/O·메모리 우선순위 2이고 그 아래 시험·시험 서버·Edge가 모두 물려받아, 바쁜 PC에서 브라우저 시작만 30초를 넘기고 평소 4초짜리 시험이 240초를 넘겼다(11-02). 일꾼도 시작할 때 CPU 우선순위가 일반보다 낮으면 일반으로 올린다. 중복 실행은 무시하며, 다시 켜지면 미실행 회차를 시작한다. 실행 명령은 운영 사본의 `tools/숨김실행.py` → `tools/conditional-qa/worker.cjs`다. 새 개인 토큰·관리자 권한·GitHub 자체 호스팅 러너는 만들지 않는다. 설치 영수증은 `installation.json`, 마지막 상태는 `last-run.json`, 전체 대기열은 `queue.json`이다. 보관된 원래 감사 자료는 건드리지 않는다.

설치는 `install.cjs --state <비공개 폴더> --ops <운영 사본> --pythonw <pythonw.exe> --first <첫 검증 커밋>`으로 미리 보고 같은 명령에 `--apply`를 붙인다. 최초 입력 등록은 `inputs.cjs`의 `provision`으로 이전 감사 manifest와 원문 해시를 검증한 뒤 수행한다. 상태 폴더는 공용 저장소 안에 두지 않는다. Codex 앱의 `%LOCALAPPDATA%` 가상화와 작업 스케줄러의 실제 경로가 달라질 수 있어 사용자 프로필 아래 명시적 경로를 쓴다.

운영 확인은 `node tools/conditional-qa/worker.cjs --state <비공개 폴더>`로 같은 회차를 실행할 수 있다. 이미 도는 회차가 있으면 잠금을 지우지 말고 완료를 기다린다. 입력이나 실행 도구 문제가 해결되면 인프라 실패는 다음 재시도에서 검증한다. 시험 자체가 실패하면 원인을 고친 새 코드로 다시 확인한다. 예약을 끄더라도 CI 로컬 단계는 미완료로 남으며 검증을 생략해 통과시키지 않는다.

과거 `failed` 항목은 저절로 성공 처리하거나 계속 재시도하지 않는다. 원인을 고친 뒤 같은 커밋을 다시 검사하려면 `node tools/conditional-qa/retry.cjs --state <비공개 폴더> --reason "확인한 원인과 재검사 이유" <커밋 SHA...>`로 미리 보고 `--apply`로 재등록한다(11-02 유호님 과거 대기·오류 전체 확인 요청). 실행 중인 일꾼이 있으면 재등록도 거절하므로 회차가 끝난 뒤 실행한다. 원래 실패 결과는 그대로 두고 `queue.json`의 `history`와 `retry-history/`에 원래 항목·결과 해시·이유를 남긴다. 대기열은 `retry`로 바뀔 뿐이며 GitHub 성공은 같은 커밋의 새 78건 영수증이 완전할 때에만 기존 일꾼이 올린다. 로컬 통과와 GitHub 전체 job의 복구도 각각 확인한다.

### 등록된 커밋 한 건을 먼저 확인할 때

운영 사본에서 `node tools/conditional-qa/worker.cjs --registered-commit <40자리 SHA>`를 실행한다. 예약 일꾼이 자리를 쓰고 있으면 회차가 끝난 뒤 다시 실행한다. 원래 검사 목록·입력·판정과 같은 실행 경로로 한 건을 재고 예약의 다음 차례를 보존한다. 이미 `passed`면 기존 결과를 보고하며, `failed`는 먼저 위의 `retry.cjs`로 원인을 기록하고 재등록한다.

`last-run.json`의 `requested`에 SHA·상태·이번 회차 시도 여부를 남긴다. 종료 코드 0은 `passed`, 2는 시간·디스크 또는 게시 대기, 1은 검사 실패·잘못된 요청·잠금 사용 중이다. 검증한 결과의 게시를 다시 시도할 때에도 저장된 영수증을 대조한다.

말하기 기능 시험의 페이지 전환은 `qa/page-ready.mjs`로 해당 시험의 `t.signal`·기존 15분 전체 한도를 따른다. 별도의 Playwright 기본 30초가 먼저 종료하던 실패를 분리했으며 HTTP 오류·연결 거절은 재시도하지 않고 실패한다. 시험이 중단되면 전환 중인 페이지를 닫고, 시험 서버 종료까지 확인한 뒤 임시 파일을 정리한다. 전환별 HTTP 상태·경과 시간·실패는 그 실행의 `synk_speaking_qa_out/result.json`에 남긴다. 이 기능 시험은 페이지 응답 속도의 성능 기준으로 쓰지 않는다.

과제 화면의 로딩 캡처는 합성 서버 응답을 보류하는 동안 Playwright 시계도 잠시 멈춘다. 이미지 합성이 오래 걸렸다는 이유로 실제 앱의 12초 요청 제한에 걸리던 시험 오류를 분리한다. 캡처 중 1ms 타이머가 멈춰 있고 재개 뒤 다시 도는지 검사하며, 별도의 12초 초과 요청은 여전히 오류로 바뀌고 다시 불러오기로 복구되어야 한다. 실제 앱의 제한·오류 판정은 바꾸지 않는다. 캡처 경과 시간은 해당 실행의 `captureTimes`에 남긴다.

시스템 기록으로 확인된 절전 중단은 대기열의 `retry`와 GitHub의 `pending`으로 남긴다. 기존 15분 뒤 재검사를 유지하며 같은 커밋의 새 78건 검증이 끝나기 전에는 성공으로 올리지 않는다. 절전 증거가 없는 실제 시험 실패·읽을 수 없는 절전 기록·그 밖의 오류는 기존 실패 판정을 유지한다. 저장된 완료 증거가 불완전한 경우도 절전 대기로 바꾸지 않는다.

일일 튜터의 같은 날 저장·새로고침·2분 뒤 복습 흐름은 시험의 한국 시각 정오를 고정한다. 실제 실행 시각이 자정 직전이어도 의도한 같은 학습일을 검사하며, 브라우저 타이머·실제 시험 제한은 계속 흐른다. 실제 한국 자정 뒤에는 전날 도움을 당일 도움으로 세지 않고 전날 기록을 보존해야 하는 별도 회귀를 유지한다. 시험 시간만 고정하며 앱의 날짜 기준은 바꾸지 않는다.

### WORLD 두 탭의 계정 분리 시험

S078은 실제 Edge의 두 탭에서 서로 다른 합성 계정으로 로그인한다. 새로고침 뒤 각 탭의 계정, 한쪽 로그아웃 뒤 다른 쪽 계정, 쿠키 속성과 브라우저 저장소를 확인한다. 전체 180초 중 165초를 실행에 쓰고 나머지 15초는 시험이 연 Edge를 정리하는 데 둔다. 실행 한도에 걸리면 당시 단계와 API 상태를 남기고 브라우저 프로세스 트리를 종료한다.

재현할 때는 격리된 리허설에서 첫 탭 생성의 응답이나 새로고침의 `/api/world/bootstrap` 응답 한 건을 34초 늦춘다. 두 경우 모두 실제 계정 검사를 끝내야 한다. 복원 응답의 계정 ID를 바꾸면 계정 대조에서, 탭 생성 응답을 끝까지 보류하면 실행 한도에서 실패해야 한다.

재현할 때는 브라우저 종료만 지연시킨 경우와 화면 이동을 실패시킨 경우를 따로 검사한다. 전자는 기능 확인 26개와 자원 정리를 모두 마쳐야 한다. 후자에서는 실제 기능 오류가 Node 결과와 보고서에 모두 남아야 한다.

### 과거 커밋 재검사와 브라우저 종료

튜터 기능 확인은 S080 120초, S081 90초다. S081의 읽기 단추도 남은 기능 시간 안에 실제로 나타나고 눌려야 한다. 기능 확인 뒤에는 두 시험 모두 별도 종료 훅에서 최대 150초 동안 시험의 Edge와 HTTP 서버가 닫히기를 기다린다. 기능 오류, 닫기 오류, 종료 시간 초과는 각각 실패로 남는다.

회귀 시험은 `node --test tests/conditional-qa-historical.test.cjs tests/conditional-qa.test.cjs tests/conditional-qa-retry.test.cjs`로 실행한다.

<a id="local-browser-files"></a>

### 과제 화면과 실패 재검사의 파일 실행 순서

로컬 과제 묶음은 학생 화면과 교사 화면의 브라우저를 차례로 검증한다. 명시적으로 다시 등록한 실패 커밋은 기본·과제·계정 묶음 모두 한 번에 한 파일씩 실행한다. 회차 영수증의 각 묶음에 `fileConcurrency`를 기록한다. 각 파일의 제한 시간과 통과 판정은 해당 커밋에 등록된 것을 쓴다.

11-04에 원래 커밋의 소스와 입력으로 학생·교사 시험을 한 번씩 비교했다. 차례로 실행했을 때 176초, 함께 실행했을 때 190초였고 양쪽 모두 학생 화면 32장, 교사 화면 18장과 교사 검사 142개를 마쳤다.

<a id="local-storage-and-town-ready"></a>

### 검사 디스크와 마을 재입장

일꾼은 새 검사를 열기 전에 상태 폴더가 있는 디스크의 여유 공간을 확인한다. 2 GiB 미만이면 대기 순서를 유지하고 `last-run.json`의 `diskWait`에 측정값과 시작 기준을 남긴다. 다음 5분 회차에서 다시 확인하며, 이미 검증한 결과는 공간을 기다리는 동안에도 게시한다. 파일 쓰기에서 운영체제가 `ENOSPC`를 반환하면 새 전체 검사를 기다린다. 시험에서 관측한 실패와 빠진 항목은 그 회차 영수증에 남긴다.

실행 중 공간이 바닥난 경우에도 원래 실패 영수증을 보존한다. 같은 회차의 Edge 임시 프로필에서 운영체제 오류 0x70과 초기 프로필 생성 실패가 함께 확인되고 다른 실패가 없으면 그 커밋 전체를 다시 검사한다.

WORLD 계정 브라우저 시험은 부모 화면의 애니메이션 프레임이 멎어도 마을 프레임 자체에서 250ms 간격으로 계정 연결을 확인한다. 마을이 접속 거절을 표시하거나 프레임이 닫히면 보호된 요청의 HTTP 상태를 실패 기록에 남긴다. 호스팅 환경의 대기 한도는 180초다.

<a id="local-parallel"></a>

### 작업본 둘로 동시에 검증

커밋 하나를 재는 데 PC가 놀아도 6.2분이 걸려 작업본 하나로는 하루 232건이 천장이다. 바쁜 날 push는 그만큼 들어온다(10-30 232건, 11-03 227건). 11-03에 일꾼은 하루 1,440분 중 1,297분을 검증에 쓰고도 151건만 끝냈다. 파일 동시 실행을 늘려도 빨라지지 않는다 — 가장 긴 파일(`town-check-browser` 280초)이 이미 기본 묶음 시간을 정한다.

그래서 `slots/<번호>/`에 검증 작업본을 하나 더 둔다. 만드는 것은 한 번이고 `node tools/conditional-qa/inputs.cjs slot <상태 폴더> 2`다(작업본·Talk 짝·`node_modules`로 약 6.7GB, 입력 묶음은 junction으로 함께 쓴다). 일꾼은 `slot.json`이 있는 슬롯만 쓰고, 끄려면 그 파일을 지운다. 슬롯은 후보가 아니다 — 덧씌운 파일이 없고 `candidate: false`라 같은 영수증 대조를 받고, `release`와 공간 지킴이의 후보 정리가 건드리지 않는다. 회차 폴더는 슬롯이 어디든 `runs/` 한곳이다. 모든 커밋은 전처럼 각자의 전체 79건을 돌리고, 차례를 고르는 규칙과 게시·실패·재검사 기준도 같다. 어느 작업본에서 돌았는지는 항목의 `slot`, 열 때의 CPU는 `cpuAtStart`에 남는다.

검증을 여는 때는 부하로 정한다. 부하가 걸리면 시험이 시간 한도까지 늘어나기 때문이다 — 조용할 때 3초인 S078이 CPU 100%에서 165초를 넘겨 실패했고 그 회차들은 18~31분을 쓰고 실패로 남았다(11-04). 돌아가는 검증 옆에 하나 더 여는 것은 직전 20초 이상의 CPU 사용률이 70% 아래이고 빈 메모리가 6 GiB 이상일 때뿐이다. 앞 검증을 연 지 1분이 지나야 본다 — 그 전 읽기에는 앞 검증의 부하가 들어 있지 않다. 첫 검증도 CPU가 95% 이상이면 내려오기를 기다리되, 30분이 지나면 연다 — 멈춘 일꾼의 빨강(155분)이 거짓으로 울리지 않게 하려는 것이고, 게시만 남은 결과와 지정한 커밋 한 건은 기다리지 않는다. 30초마다 다시 보며 기다린 횟수는 `last-run.json`의 `roomHeld`에 남는다. 이 조건은 기다리기만 하고 시험 한도나 판정은 바꾸지 않는다. 디스크 여유 2 GiB 조건은 검증마다 본다. 한 작업본이 시험 결과가 아닌 오류(checkout·네트워크 등)로 끝나면 그 회차에는 다시 쓰지 않아, 고장 난 작업본이 대기열을 연달아 실패로 돌리지 않는다. 일꾼은 모든 검증이 끝난 뒤에야 잠금을 푼다.

<a id="local-status-check"></a>

### 러너를 쥐지 않는 동안의 감시

`local-coverage`는 11-04부터 기다리지 않고 자기 run을 취소한다. 취소는 빨강이 아니어서, 옛날처럼 155분 뒤 빨개지는 신호가 없어졌다. PC가 멈춰도 알림이 없고, 일꾼 차례가 뒤섞여 오래된 커밋의 실패 run은 더 새 초록 run에 가려진다. `conditional-qa-local`(`local-status.cjs`)이 이 빈자리를 맡는다. `conditional-qa` run이 끝날 때마다 돈다. 이 저장소의 예약 실행은 몇 시간씩 늦어(11-03 실측 5~10시간, 15분 예약은 4시간 동안 0회) 30분 예약은 뒷받침일 뿐이다. 활성화 커밋까지 first-parent를 읽고, 각 커밋 판 목록의 정확한 `PASS n/n manifest=`만 통과로 센다.

빨강은 다음 다섯 가지다. 새 실패(올라온 지 24시간 안, 커밋마다 이름이 달라 새 실패만 새로 알린다), 판 불일치, 대기가 있는데 일꾼이 155분 동안 새 결과를 안 낸 때(`WAIT` 표시는 일꾼 활동이 아니다), 커밋된 지 72시간 넘은 대기, 1,000커밋 창에 활성화 커밋이 안 들어올 때. 24시간이 지난 실패는 빨강에서 빠질 뿐 커밋 상태와 로그의 「kept until a retry passes」 줄에 남고, `retry.cjs`로 다시 재기 전에는 통과가 되지 않는다. 호스트 36건과 로컬 79건의 커밋별 실행은 그대로이며 경로 제외는 없다.

회귀는 `node --test tests/conditional-qa.test.cjs tests/conditional-qa-retry.test.cjs tests/ci넓은시험.test.js`다. 이 자동화는 등록된 115건의 지속 검증이며, 새 보안 감사나 운영 접근 권한 전체의 재점검을 대신하지 않는다. 최초 실제 실행과 원격 CI 결과는 비공개 설치·실행 영수증과 해당 커밋의 GitHub Checks에서 확인한다.
